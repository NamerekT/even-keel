# Chain: what the dispatcher owns and its state files

## What the dispatcher owns (invariant 2)

The tracker is the source of truth for statuses; the dispatcher keeps no status of its own. It owns only: the chain order, the pause, the list of skipped tasks, released tasks awaiting cleanup and their resting sessions eligible for a handover on return (`shelved`, including the release reason and blockers), cleanup warnings, unattended mode, the "trim the tools" switch, the questions it posted to the tracker, the pull requests it opened for tasks in PR mode, the landings of merges that have not gone through — the rounds a task went back to its session, whether it resolves a conflict or a red check (`resolving`), the message not delivered yet, whether it waits for a remote out of reach (`waitingRemote`) and the next try (`landings`, BTN-1581, `docs/chain/worktrees.md`, "Landing") — the GitHub issues it took into a tracker until they are closed, with whether each came from an outsider, an outsider's closed issue kept until its task is done (`IntakeEntry.outsider`, `closed`, BTN-1207, `docs/trackers.md`), the carries of release projects it holds after a conflict (in memory, "Carrying a release project forward"), the tasks it closed by a merge with the commits `main` had of their branches then (`merge_closes`, "Cleanup after Done"), the worktree folders a cleanup after Done left held, until removed or warned about (`left_folders`, BTN-925, `docs/chain/worktrees.md`), the run of each task that has one — the provider, model and effort its sessions start on (`task_runs`, BTN-983, `docs/sessions/models.md`), with the projects whose run labels are still to be moved into runs (`run_label_imports`) — the machines it gave a connection token and the commands they have not confirmed (`machines`, `machine_commands`, BTN-988, `docs/machines.md`), the machine this installation itself is (`machines.own`), the machines each project may run on and the machine each task went to with its launch, until its place there is cleaned up (`project_machines`, `machine_tasks`, BTN-1216), the capacity of each machine elsewhere and the machine of each lane and of each launch (`machines.capacity`, `ActiveChain.machine`, `LaunchEntry.machine`, BTN-993), the tasks moved by hand off a machine gone, with the machine left and the branch, until their next launch and cleanup (`task_moves`, BTN-1270), the project chats — sessions without a task started from the page, their account, model, effort, machine, title, last message and archive — with each project's last choice for a new one (`chats`, `chat_choices`, BTN-1230, `docs/sessions/project-chats.md`) — and the CI verdicts on main: the last green commit, the push it waits on (for the CI or for the project's own check), the last red commit whose failed jobs it reran (`ci[<project>].rerun`, BTN-846), the start and end of the last run of `commands.afterGreen` (`ci[<project>].afterGreenRun`, BTN-829), the last green commit each machine elsewhere was sent to run them on (`project_machines.after_green`, BTN-994, `docs/machines/landings.md`, "After a green main") and the fix of a red main — the session it started for it, or the task it created — with the task whose session it stopped for the fix, and the fix and carry sessions the user skipped, until their worktree is cleaned up (`skippedSessions`). Something new the dispatcher must remember goes on this list, never into a status.

The built-in tracker (BTN-767, `docs/trackers.md`) keeps its tasks in the same state database, yet they are tracker data, not the dispatcher's state: the chain reads and moves them only through the `builtin` adapter, by the same actions as on any other tracker (start, pull request, merge, `ready`/`unready`, a comment), and the person changes them through the page's `builtin/*` commands. Nothing of the list above goes into a built-in task, and no status of one is written outside these actions.

When a built-in project switches to the tracker its tasks were copied into (BTN-1074, `docs/trackers.md`), only the saved order, the skips and the tasks' runs move to the new ids (`Dispatcher.rename`, `TaskRuns.rename`), the computed order saved as the saved one when there was none (BTN-1195), ranking the backlog and the own waiting blockers with the chain, after a manual order (BTN-1199: a target without Backlog puts them into the chain, where unranked they would be new and go first); the switch is refused while the chain runs or holds a task of the project (the current one, a released or shelved one, an open pull request). Everything else that names a task by id — launches, `closed_tasks`, `merge_closes`, handoffs, questions — keeps the old id, linked to the new one by `tracker_export_tasks`.

The switch after an import into the built-in tracker (BTN-1405) is held by the same refusals. The tasks keep their numbers under the project's key, so ids change only where the source's own differ from `<key>-<number>`; those move the same way. The import's progress (`tracker_imports`, `tracker_import_tasks`) is the dispatcher's own until the switch, which drops it, and the source's tasks are never written to.

## State files and the schema version (BTN-132)

The machine's launch journal, retained session windows and mailbox changes reach the hub as numbered events (`launch.record`, `session.windows`, `chat.mailbox`, BTN-1219). The hub writes the existing tables and its receipt (`machines.last_event`) together in one transaction, so a repeated event after a lost answer or a restart adds no second journal row. The machine holds unconfirmed events in its own outbox. Current session views and the chat panel are the hub's in-memory mirror of the machine's snapshot and `facts` events; they are not extra persisted chain state. A move of a task's session runs on the machine (BTN-1221): its state comes back as `task.state` and the command's result, and the hub keeps it in its `CurrentTask` as before; the retry ladder of temporary errors and the sources of a handoff are the machine's memory. See [Hub and machines](../machines.md), "The chain over the link", "Moves" and "The mirror".

Since BTN-147 the chain state, the questions, the launch log and the handoff snapshots are in the state database (`state/even-keel/`, `docs/storage.md`); the files below are what v0.1 kept and what the first start of the new version imports. The config, `account.json`, `packages.json`, `rate-limits.json` and `codex/` stay files.

- A project has a key (`ABC`, not unique since BTN-271) and an id (`projects[].id`, a GUID that never changes). The state and the running service name a project by its id: the database (`project_id` of its tables) and before it `state/chain.json` (`active[].project`, `queue`, the keys of `orders`, `skipped`, `leftovers`, `released`, `ci`) and `state/launches.jsonl` (`project`), every map of `EvenKeelConfig` (`config.keys` gives the key of each id), the dispatcher, the page's state and its URLs. Task IDs, branches and worktrees go by the key, the tracker adapters get each id's key and value (`TrackerPlace`); nothing translates at the store's edge any more. An id the config does not have — a removed project — stays as it is.
- Every file carries the schema version (`SCHEMA_VERSION`, `src/storage/schema.ts`): `version` in the config, `chain.json`, `questions.json` (`{ version, questions }`), `account.json`, and the first line `{"version":<N>}` of `launches.jsonl`. A file newer than the code is refused (`storage.newer`). The database has its own version (the one row of `schema_version`, `docs/storage.md`).
- `upgradeStorage` (`src/storage/migrations.ts`) runs in `src/start.ts` before `src/service.ts` is imported: it reads all the files, migrates them step by step to the current version, checks the config with `parseConfig`, keeps `<file>.v<N>.bak` copies and writes all of them, restoring the written ones if a write fails. It also writes an id into a project entry added by hand without one. Any refusal (`storage.newer`, `storage.damaged`, `storage.unknownProject` — a project of the state the config lacks, `storage.writeFailed`) starts only the blocked page server (`createBlockedServer`, `src/server.ts`): the page from `dist/web`, `/api/events` sends `blocked` with the reason, the rest of `/api` is 503. Right after it `prepareDatabase` brings the database to its schema or imports the files into it; its refusals (`storage.newerDatabase`, `storage.importFailed`) block the same way.
- A format change is a new schema version, a migration step and a new frozen sample in `test/fixtures/schema-v<N>/` (`src/storage/fixtures.test.ts`); old steps and samples are never edited or removed.
- Schema v8 (BTN-173, run profiles, `docs/sessions.md`): `configV8` turns a project's `agent` into `provider` and `codexModel` into `models.codex`, the shared `model` into `models.claude`, a project's `codexBypassSandbox` (any project on) into the shared `execution.codex: "bypass"`, and moves `active` of `state/account.json` into the shared `accounts.claude`. A launch log entry may carry `fallback` — the provider of the task's run label the pool had no account for (`fallbacksSince` gives the page the last 24 hours of them).
