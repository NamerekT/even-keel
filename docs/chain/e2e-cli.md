# Real CLIs (`src/e2e-cli/`, BTN-572, BTN-784, BTN-819, BTN-818)

The scripted agent sees no process, no package hook, no MCP gateway and no real transcript. `src/e2e-cli/` runs the same `Harness` with a real adapter in `AGENTS` and its checked CLI, whose model is a script: no subscription, no limits, no provider billed. `npm run test:cli` runs it; `npm test`, `test:e2e` and `test:all` leave it out, and a merge does not wait for it — it runs every night (`docs/ci/workflows.md`, "This repository's workflows").

`Latest CLIs` (`.github/workflows/cli-latest.yml`) runs at 03:30 UTC, one hour after `Real CLIs`, and by hand. Scheduled runs check out `dev`; manual runs use their branch. It resolves Claude Code's `claudeLatest()` and the npm `latest` tags of the packages used by `fetchCodex` and `fetchOpenCode` (`@openai/codex` and OpenCode's platform package), then runs the same scenarios with `EVEN_KEEL_E2E_CLI_VERSION`. Without that variable the fixtures still use checked; an invalid or empty override fails before a download. Copies and the Actions cache are separate by CLI, version, OS and architecture; the service uses the selected binary through `EVEN_KEEL_<PROVIDER>_BIN`. Equal latest and checked versions skip the scenarios successfully; any different version runs, even if checked came from `next` and is higher. Discovery errors fail the job, and its summary always names the CLI, checked, latest (unknown on a discovery error) and result. It never holds a release (`nights-green.sh` lists only `cli-e2e.yml`, `trackers-e2e.yml` and `macos.yml`): a red run is an early warning to check a new CLI, with no issue filed automatically. There is no `claude-sdk` job because SDK sessions always use the checked CLI and SDK, including in a local run with the override; Copilot has no real-CLI scenarios.

- `Harness.realAgents` names the adapters kept in `AGENTS` (`['opencode']`); with `claude` among them the scripted agent no longer plays Claude. `Harness.pace` (ms) makes the clock's step wait that long in real time and leaves the service's `Date` real: a turn's process starts at the machine's time, and the adapter takes a process younger than its turn's start for a reused pid (`processBelongsToTurn`), so a fake `Date` a month back would read every live turn as over. The timers stay fake, so the service polls the process about ten times as often as live at 100 ms a step; a turn's detached, unref'd process does not hold `realWork`.
- `ScriptedModel` (`model.fixture.ts`) is BTN-500's local provider on a free port, streaming in SSE each of the three APIs (`wire.fixture.ts`): OpenAI-compatible `/v1/chat/completions` (OpenCode), Anthropic's `/v1/messages` (Claude Code) and OpenAI's `/v1/responses` (Codex). Each request of a task's session takes the task's next reply of `script(task, ...replies)` — `bash` commands for whatever the CLI's shell tool is called, `calls` of any offered tool, or a `text` that ends the turn — in order across turns, so a resume goes on where the last turn stopped. The task is the script's id that opens a line of the session's user messages, as the launch prompt does: Claude's own first message carries the checkout's recent commits, which name the earlier tasks. A reply may be a function of the offered tools, the last tool result and the whole text of the request, made when its request comes: a merge reads the branch Even Keel named, an MCP call finds the gateway's name of its tool, a turn waits for a hook's word; `{ wait }` answers and keeps the function for the next request. A reply's `tokens` is the input its answer reports (1000, `SMALL_USAGE`, by default): the context the CLI writes into its transcript and Even Keel reads from there. A request the CLI makes for itself takes no reply and gets what a model would say: a title, Claude's state classifier (`done`, or `blocked` after a question) and Codex's guardian (`allow`, JSON). `requests` keeps the task, the tools, the result and the reply of each, and a failed scenario prints them.
- `CliKit` (`kit.fixture.ts`) is what the shared scenarios (`chainOnRealCli`, `scenarios.fixture.ts`) need of one CLI; `checkedCopy` keeps the checked version once in `EVEN_KEEL_E2E_CLI_DIR` (`.temp/e2e-cli/<cli>/<version>/` by default).
  - `openCode`: `fetchOpenCode`, `EVEN_KEEL_OPENCODE_BIN`; the account `probe` with no credential and one provider, `scripted`, through `@ai-sdk/openai-compatible`, also as `small_model`. OpenCode installs that npm package into the account's cache at the first turn, so a run needs the npm registry. The project runs on `provider: opencode`, `models.opencode: scripted/scripted`.
  - `claudeCode`: `fetchClaude`, `EVEN_KEEL_CLAUDE_BIN` (so the `sdk` kind is off: it needs the pinned copy), and the `--bg` sessions of the account `script` on `ANTHROPIC_BASE_URL` with an `ANTHROPIC_API_KEY` from the service's environment, which the daemon inherits. `--bg` takes that key only once `.claude.json` has its last 20 characters in `customApiKeyResponses.approved`, and auto mode does not run with a base URL of its own, so the account's `settings.json` allows `Bash(git commit:*)`, `Bash(git -C:*)` and `mcp__notes`; `ENABLE_TOOL_SEARCH=false` keeps MCP tools in the request rather than behind ToolSearch. `release` stops the account's daemon (`claude daemon stop --any`).
  - `claudeSdk` (BTN-818): the same CLI and account on sessions of kind `sdk`. The SDK runs only on Even Keel's own pinned copy, so the kit sets no `EVEN_KEEL_CLAUDE_BIN`: `checkedCopy` keeps the SDK of the CLI's version (`sdkVersionOf`, `fetchSdk`) under `claude-sdk/<version>/` beside the CLI's copy, `prepare` links both folders (a junction on Windows) into the bench's `state/cli/claude/` and `state/cli/claude-sdk/`, where `PinnedCli` finds them as downloaded, and the config has `cli.claude: checked`, `execution.claude: sdk`. The `customApiKeyResponses` approval and the allow rules are the same files; the SDK session reads both. An SDK session's executor outlives the service, so `release` kills the executor of each session in `state/claude-sdk/sessions/` not marked stopped, then removes the links before the bench's folder goes. `CliKit.kind` (`sdk`) makes the scenarios that take a live session check its `kind`: with the SDK missing the adapter would start `--bg` quietly.
  - `codex`: `fetchCodex`, `EVEN_KEEL_CODEX_BIN`; the account `coder` with the provider `scripted` of its `config.toml` (`model_providers`, `wire_api = "responses"`) and a key in `auth.json`, which `codex login status` reads as signed in. The service asks OpenAI about such a key and takes a 401 for an expired login, so the kit answers `api.openai.com` itself (`withOpenAi`). Codex offers a server's MCP tools as one `namespace` tool: the model names them `mcp__notes__note` and calls them back split. Off Windows a `git` command goes with `sandbox_permissions: "require_escalated"` (`escalated`, EKR-126): the `approve-for-me` sandbox of Linux and macOS keeps the main checkout's `.git` read-only, and with it the worktree's index; a plain `git commit` fails with "Read-only file system", the merge finds nothing and no task reaches Done. A real model asks the same after the refusal (`docs/verified/codex.md`), and the guardian answers `allow`. On Windows Codex's sandbox lets git write and the escalation is left out: with it the gateway scenario's bench folder stayed locked at the cleanup.
- `NoteServer` (`mcp.fixture.ts`) is a package's remote MCP server of one tool, `note`, over streamable HTTP with JSON answers; `calls` keeps each `tools/call` with its headers.
- A commit and a merge are `git` commands the model sends through `bash` (`git -C <checkout> merge --no-edit <branch>`): one command each, no `&&`, no file written, so they read the same in bash and PowerShell.
- The branch is in main at the merge's tool call, so the board can show Done before the CLI asks for the report after it — under load, with the three files at once (BTN-870). A scenario that checks the script was played out right after Done waits for it (`playedOut`) rather than reading `left` at once; the session is stopped only once that turn ends, so a reply never asked still fails it.
- The `agent-bridge` plugin is built in and installs from Even Keel's own marketplace `even-keel` at the service's start, which needs no CLI. The hooks reach the service only through `EVEN_KEEL_URL`, which the service gives its sessions (BTN-817): the bench's service listens on a free port and sets nothing of its own, so the merge check scenario checks that too.
- Measured on the author's Windows workstation (2026-11-07, OpenCode 1.19.5, Claude Code 2.1.319, Codex 0.167.0, the three files at once): OpenCode's file 444 s — its provider's npm install weighs more than the turns — Claude Code's 136 s, Codex's 69 s. `claude-sdk.test.ts` alone (2026-11-08, the nine scenarios with the rules ones): 139 s.

`opencode.test.ts`, `claude.test.ts`, `claude-sdk.test.ts`, `codex.test.ts` — the same seven scenarios:

- the order by `blocks`, two tasks each committing and merging through the shell tool, cleaned up after each Done;
- a turn ending in `NO CHANGES:` closing its task with the comment;
- a turn ending in a question as text, the session idle, answered from the chat and resumed in the same session, which merges;
- a package's MCP server added with a key by `packages/server` and `packages/key`, its tool offered under the gateway's name and called once, the call reaching the server with the key the gateway put in. Claude's `--bg` session asks the model before its MCP servers connect, so the tool comes from the second request on: the scenario waits for it with `git status`;
- the built-in `agent-bridge` plugin, waited for until its install is done (`bridgeInstalled`), the project's `commands.check` failing on the first merge: the plugin's hook refuses it with "Even Keel's check before the merge failed", the model commits a fix and the second merge goes through;
- the `agent-bridge` plugin's chat mailbox (BTN-819): once the session's hook asks for mail mid-turn (`mailbox.listens`), a message sent by `session/answer` waits in the mailbox, a hook of the same turn takes it (`delivered` on `PreToolUse`, `PostToolUse` or `Stop`, not by a resume) and its word reaches the model's next request. The turn keeps working with `git status` until the word comes, at most three minutes of real time. A session that steers (`AgentEntry.steers`: an SDK session, `docs/sessions/sdk.md`) takes the message on its stdin at once instead: the mailbox stays empty and the word still reaches the model within the same turn. A Claude `--bg` session goes through its inbox socket (BTN-1322, `docs/sessions/chat.md`): the plugin's `SessionStart` hook has reported it (`inboxes.knows`), and the one row is `delivered` with the event `inbox` before the post answers (BTN-1392);
- the `agent-bridge` plugin's threshold (BTN-819): the project's `stats.checkpointTokens` pinned to 100000, the least it takes, and every answer reporting 120000 tokens of input; Even Keel reads the context from the transcript at its poll, the hook's next call nudges with "Context is now ~120k tokens" and asks for `CHECKPOINT: .temp/handoff.md`. The model takes the word and goes on to commit and merge: the handoff itself is the scripted agent's scenario in `chain.test.ts`.

`opencode.test.ts` also runs a rejected ask (EKR-119): the branch has a committed `.env`, the model's first reply is the `read` tool on it, which OpenCode's default rules ask for and `run` rejects on its own; the next reply commits only once the last tool result is that rejection, and the task merges. Without `experimental.continue_loop_on_deny` (`docs/sessions/opencode.md`, "Permissions") the turn ended at the rejection and the task stood with no question.

`claude.test.ts` and `claude-sdk.test.ts` also run two scenarios of a project's rules files (BTN-855), the alarm for the CLI's own reading of a lone `AGENTS.md` (`docs/unverified/sessions.md`): a branch with only an `AGENTS.md` gives its word to the session's first request (`ModelRequest.context`, the system prompt and the messages as text), and with a `CLAUDE.md` beside it the `CLAUDE.md`'s word goes and the `AGENTS.md`'s does not. Each task ends in `NO CHANGES:` and the scenario waits for its worktree to go: such a session quits slower and holds the folder. The two take about 40 s together on the author's workstation.

- **The remote defaults.** What decides the reading is the CLI's remote flag `tengu_agents_md_mod` (`AGENTS_MD_FLAG`), not its version. Measured 2026-11-08 on CLI 2.1.319: under the kit's `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` the CLI neither fetches its flags nor reads their cache (`cachedGrowthBookFeatures` in `.claude.json`) and runs on the built-in default, which reads the file; without it the CLI fetches the flags from Anthropic even with the bench's key and its own base URL, and a `--bg` session takes them before its first request. A cache set to `false` with Anthropic out of reach (a dead `HTTPS_PROXY`) kept the file out of the request, and the scenario failed naming the flag. So the two scenarios drop that variable (`remoteDefaults`, `claude.fixture.ts`), fill the cache with one `claude -p` first and fail when no flags came: they catch both a remote switch and a new built-in default. The flags are those of an API-key user with no account: a switch aimed at subscribers alone passes unseen.
- **A rules file above the bench.** The CLI reads the `CLAUDE.md` and `.claude/CLAUDE.md` of the folders above a checkout, and a lone `AGENTS.md` below one is not read. On Windows `~/.claude/CLAUDE.md` is such a file for the bench's folder in the user's temp once the account is another folder: the chain's worktree there did not get its `AGENTS.md` with the flag on. Even Keel then passes the file itself (`agentsFallback`, BTN-869), so the CLI's own reading has nothing to show and the scenarios skip themselves when one is above (`claudeRulesAbove`, `src/claude/instructions.ts`): run them with `TEMP` and `TMP` set to a folder with none above. A CI runner has none.

Not covered yet: Copilot, whose provider is GitHub's own; a real CLI's handoff after the nudge, the session's `CHECKPOINT:` handed to a new one. Linux has run only in the nightly workflow, which GitHub starts once it is on the default branch.

## A failure in a cut output (BTN-1108)

A pipe into `tail` eats vitest's exit code and cuts the failures' details off, and a session that saw only "1 failed" used to rerun the whole suite for a name. `LastRunReporter` (`scripts/vitest-last-run.ts`) runs beside vitest's own reporters in every vitest run of the repository — `npm test`, the e2e scripts, a single file, CI — and leaves the exit code alone:

- the last lines of the output are a `FAIL file > suite > test` line for each failed test, a line for a file that broke outside its tests and for an unhandled error, then a `RETRIED file > suite > test: <first failure>` line for each test that passed only on a retry, then the verdict `vitest: passed|FAILED|INTERRUPTED — …` with the counts ("1 passed only on a retry" among them); at most twenty lines, the failures first, so `| tail -3` names a single failure and a green run is one line;
- `.temp/vitest-last.json` of the working folder (each worktree has its own) keeps the totals and every failure with its message, stack and diff, and `retried` with the errors of the failed attempts of a test that passed on a retry: read it instead of rerunning. The next run of any scope overwrites it.

Only the macOS e2e job retries, and only a timeout (`E2E_SLOW_RUNNER`, `docs/ci/workflows.md`, "macOS"). A scenario's own timeout is written `{ timeout: scaled(60_000) }` (`test/slow-runner.ts`), never a bare number: `test/slow-runner.test.ts` fails on one in `src/e2e/`.
