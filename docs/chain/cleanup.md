# Cleanup after Done

The stop, deferred-stop and retry wiring is in `src/service/cleanup.ts`, re-exported by `src/service/chain.ts`. The log lines of a stop deferred mid-turn and of its result are marked `rare: 17c`; why and what to look for is in [unverified sessions](../unverified/sessions.md#a-session-left-mid-turn-by-the-cleanup-btn-616).

## The current task went to Done

Done is category `Won`; a cancelled or dropped task gets no cleanup. The chain's `closing`, in order:

- wait until the task's session is not busy ([words of the area](../chain.md#words-of-the-area)); a session in `shell` does not hold a done task ([background commands](background.md));
- `claude stop` its sessions in this worktree: otherwise a live process holds the folder — a `--bg` session does not exit after a turn, `claude agents` shows it `done`/`idle`;
- in the clean worktree, remove links and junctions in ignored folders (`node_modules` of npm workspaces, `npm link`): git on Windows follows them — it cleans someone else's folder or stumbles on a dangling one and abandons the worktree;
- `git worktree remove`, without `--force`. Every git call of Even Keel on Windows carries `-c core.longpaths=true`, and a folder git unregistered but left for another reason than a lock — `Filename too long` — is deleted from Node (BTN-559); only a lock is `cleanup.folderLeft`, the rest `cleanup.folderNotDeleted`;
- `git branch -d` of the task branch (only `<key>-<number>/…`), and `git push <remote> --delete` if it is on the task branches' remote (`taskRemote`, [task branches on the remote](worktrees.md#task-branches-on-the-remote-btn-1270));
- `git sync` if the project has a remote ("git sync" below).

The next task is started after that. A task returned from Done before the cleanup gets no cleanup: it is back in the chain. A slot is cleaned its own way ([slot mode](worktrees.md)); a project without git in [no-git](no-git.md). A parent closes by itself once all its subtasks are closed (adapters with `children`, `docs/trackers.md`); there is no cleanup then.

## Closing the task

- **Into which status.** A merged task is closed into the tracker's first done status, or into the one its source chose (BTN-554, `doneMove`; [status moves](entry.md#status-moves-btn-554-srcchainmovests-srctrackermoverts)). A chosen status the chain rules do not take for done is not tried: the task stays open with `statusMove.notDone` until the setting changes. Every way of closing takes the same choice (BTN-1163, `closeInto`; the list is in `docs/trackers.md`, "Moving a task to a chosen status"): a merged pull request, a pull request with nothing to open, a `NO CHANGES:` mark and "Accept as answer" too.
- **A merge closes the task at once.** A merge of the task's branch that landed in the remote's `main` ([landing](worktrees.md#landing-btn-1581); without a remote, the local one) closes the task even when it is only part of the work and the session is still mid-turn. The close does not wait for the turn to end; the cleanup does.
- **A reopened task** (BTN-219, BTN-689) is closed again only by a new merge. `MergeCloser` keeps the own commits of its branches `main` had at the close (`landedCommits` over `mergedCommits`, the newest of each branch, in `src/git/merged.ts`) in `MergeMarks` (`src/tracker/closes.ts`, the state table `merge_closes`, through a restart); a reopened task whose merged commits are all in that mark stays open, so a checkpoint handover on a branch merged before the reopen goes on in the new session.
  - A branch that only caught up with `main` adds no commit of its own; a branch removed by the cleanup and made anew has new ones. A task closed before this mark existed has none, so its first close after a reopen goes by the old rule.
  - Only a merge seen while the chain holds the reopened task closes it (BTN-694). While it is open and not held (neither the current task with a session nor a released one awaiting cleanup, `Dispatcher.held`), every tracker read adds its newly merged commits to the mark without closing it, so a session that merged again outside the chain does not close it the moment the chain takes it back. A hand session that finishes such a task outside the chain closes it itself.
- **The tracker refuses the close.** `MergeCloser` keeps a `tracker.completeRefused` notice for that reader and task in `TrackerView.completionFailures` (memory only). The page shows the tracker response and a link to the task, asks for the required field to be filled or the task to be closed by hand, and suppresses a false reply prompt in the header, lamp and session panel; a real question or permission remains visible. The task stays current and the normal 30 s full read retries the close. Success clears the notice; a task no longer held drops its refusal, and the page also hides one as soon as polling sees a closed status. Git inspection errors are separate from tracker refusals.

### Nothing to merge (EKR-10), out of PR mode

A task that needs no change in the repository (done in main already, research, an answer) never closes by a merge: `branchMerged` takes a branch with no commits of its own for unmerged, or every branch that only caught up with main would close its task.

- **The mark.** The prompt's `cleanup` tells such a session to end its turn with the last line `NO CHANGES: <why>` (`noChangesOf` in `src/sessions/transcript.ts`, Codex's rollout too; a tool call or a new prompt drops it, as `CHECKPOINT:`). The last line `TASK DONE` of a project without git ([no-git](no-git.md)) is read by the same `noChangesOf`, so in a git project it acts as `NO CHANGES:`.
- **The check.** `Unchanged.follow` (`src/chain/unchanged.ts`), once the session is not busy (a session in `shell` does not hold it, BTN-637, [background commands](background.md)), counts the commits of its folder beyond the local main and reads `git status` with untracked files (`changesOf`, `src/git/changes.ts`; ignored `.temp/` is not work).
- **Nothing** — `UnchangedDeps.complete` moves the task to Done in the tracker and comments the reason (`unchanged.comment` of the prompts; a comment that fails is only logged), the tracker is read at once and the chain's own Done cleans up — [exception 4](exceptions.md), `git branch -d`, the next task. A tracker that refuses pauses the chain with `chain.unchangedNotCompleted`, a git that cannot count with `chain.unchangedNotChecked`, the task staying current.
- **Commits or uncommitted changes** — the session gets `unchanged.ahead` or `unchanged.dirty` by `--resume` whatever its cache, as a chat answer does (merge them, or drop them and mark again). A mark acted on has its `lastReplyAt` remembered in the service's memory, so only a new turn tries it again.
- **Merged and still marked.** A session that merged commits and still marked `NO CHANGES:` closes by the mark (its branch has nothing beyond main once merged); the task closes into the same status, only the comment says no change was needed. The two are not told apart on purpose (BTN-1163): it would cost a git call per mark and touch the verdict a fix of main waits on.
- In PR mode the mark is ignored: `PULL REQUEST:` covers the case (BTN-222).

### Accept as answer (BTN-885)

A session that answered but forgot the mark (Codex most often) leaves its task waiting with no way to close it short of asking for the mark and waiting a turn. The session panel and the chat then offer "Accept as answer" (`offersAccept`, `web/src/pages/acceptAnswer.ts`).

- **When the page offers it:** the current task's session ended its turn on a message — not mid-turn, no question, permission or startup dialog, no error, limit or checkpoint mark; the task is no fix or carry, has no pull request under review, is not merged with its close refused, and `TaskWorks` knows no work in its folder.
- **What the dispatcher refuses.** The press (`chain/accept` with the session id the page saw) goes through `Dispatcher.accept`: `acceptable` (`src/chain/answers.ts`) refuses a task that is not current (`chain.notCurrent`), launching, a session moved on since the page read it (`answer.moved`), mid-turn or in a background command (`chain.midTurn`), waiting on an `AskUserQuestion` (`accept.asking`), with no last message (`accept.noMessage`), or done already in the last read (`accept.closed`, so a second press does not comment twice).
- **The folder.** In the dispatcher's turn `Unchanged.accept` counts the folder as for the mark: commits beyond main refuse with `accept.ahead` (such work closes by a merge, and the close would lose it), uncommitted files with `accept.dirty`, a git that cannot count with `accept.notChecked`.
- **Clean** — `UnchangedDeps.accept` puts the session's last message whole (as the transcript keeps it, `MESSAGE_LIMIT` — 30,000 characters at most since BTN-883) on the task under `unchanged.accepted`, then moves it to Done; the comment comes first and a failed one refuses (`accept.notCompleted`), since it is the answer. The tracker is read at once and the chain's own Done cleans up — exception 4 again. Every refusal goes back to the page and leaves the chain as it is, unpaused.

## Stopping the sessions and freeing the folder

- **The first read of the sessions** (BTN-646). After the service's start the dispatcher does nothing — no cleanup, launch, handoff, review, fix or slot switch — until the monitor has finished its first full tick (`DispatcherDeps.sessionsRead`, the service's `agentsRead`, set with the first `onChange`). Before it busy is unknown rather than false and the cleanup's `stopTaskSessions` sees no session at all, so a Done right after a restart removed the worktree past its live session and left the folder held (`cleanup.folderLeft`; BTN-537, BTN-587, BTN-642).
  - The forward merges (`chainQuiet`) and the account watcher (`sessionsKnown`) wait for the same flag.
  - A lane on a machine elsewhere waits besides for that machine's first snapshot since the hub's start (`sessionsRead(task)`, BTN-1610, `docs/machines.md`, "The port by task"): the dispatcher's pass skips it until then, so no Done, handoff, limit or review of it reads an empty mirror. The cleanup of a released task done meanwhile and of one whose pull request was closed unmerged (`Cleanups.working`) waits for its machine's read the same way.
- **A session left mid-turn** (BTN-616). The cleanup waits only for the task's own session (busy by its view); another session in the task's folder, or one whose status the view and the listing disagree on, may still be busy when `stopTaskSessions` runs. Such a session is not stopped then but kept in `Lingering` (`src/sessions/lingering.ts`, the service's memory) and stopped on the first monitor tick after its turn ends (`stopLingering`, from `onAgents`, since a session without a view of its task changes no view); once gone by itself it is forgotten. Without this nothing stopped it after its task left the chain, and a Codex session, which has no process between turns, rested on the page as `waiting` for good. A restart before its turn ends forgets it.
- **A stop that timed out** (EKR-99). A Claude `--bg` stop first lists the folder's sessions (`claude agents`), and that call waits in the account folder's queue (`FolderCalls`, EKR-15): right after the service's start `/usage` and the `/context` probes fill it, and a call whose timeout passes while it waits never starts. Since EKR-102 that listing goes ahead of the waiting calls and is tried again for up to 5 minutes (`QueueWait`, `docs/accounts.md`), so this is rare.
  - Such a `CallTimeout` (`isCallTimeout`, through wrapping causes) is no failure of the stop: `stopTaskSessions` keeps the session in `Lingering` with a retry (`STOP_RETRY_MS`, 5 min), and the worktree folder git unregistered but left because that session's process holds it (`cleanup.folderLeft`, Windows) is left to it too (`deferLeftFolder`), so neither goes into `leftovers`.
  - `stopLingering` tries the stop again on each monitor tick, one run at a time (`Lingering.alone`), then removes the folder (`removeLeftFolder`; a folder registered as a worktree again meanwhile is not touched).
  - Only a stop still timing out once the wait is over, or failing otherwise, is `cleanup.sessionNotStopped`, and a folder still held `cleanup.folderLeft` — added to the task's leftovers then (`Dispatcher.leftover`). A stop that fails for any other reason warns at once. A slot is not removed, so only its session is retried. A restart forgets the session's retries, as it forgets a session left mid-turn; the left folder it keeps (below).
- **A folder still held after a stop that went through** (BTN-870). A stopped process lets go of its folder a moment after it exits on Windows, and a child of it (a Codex `codex exec` turn's shell) later still: under load the cleanup's `git worktree remove` comes first and the folder is left (`cleanup.folderLeft`; seen in the real-CLI scenarios, [e2e-cli](e2e-cli.md)). So every such folder of a Done cleanup goes to `deferLeftFolder`, not only one of a timed-out stop: `stopLingering` tries it again on each monitor tick while no kept session of the task is left, and warns only if it is still held once `STOP_RETRY_MS` has passed.
- **A left folder outlives a restart** (BTN-925): in a project with `commands.afterGreen` the service may restart about a minute after nearly every Done, so a folder kept only in memory was forgotten almost always.
  - `Lingering.leave` saves it into the state table `left_folders` (`docs/storage.md`), and the row goes once the folder is removed or warned about. At the start the service reads them back (`Lingering.restore`), and `stopLingering` takes them up only after the monitor's first read of the sessions (`agentsRead`, BTN-646).
  - The wait is `until`, counted from the Done, not from the start: a wait that ran out while the service was down gets one try at once and, still held, the same `cleanup.folderLeft` warning on the task. A session kept with the folder is not saved, so after a restart its folder is tried at once rather than after the session's stop.
- **Orphaned processes of the task's sessions** (BTN-1268, `src/sessions/orphans.ts`). A Claude stop kills the processes it lists under the session (`killLeftovers`), but that misses a session that died before the cleanup — on Linux and macOS its children go to init — and anything that detached itself (`setsid`, `nohup`, a dev server's double fork); other agents only kill their own child's tree.
  - **The marks.** The CLIs mark every command they run with the session's id in its environment: `CLAUDE_CODE_SESSION_ID` (Claude, `--bg` and SDK alike) and `CODEX_THREAD_ID` (Codex). OpenCode and Copilot put none, so Even Keel marks their turn process itself (BTN-1389): `EVEN_KEEL_TASK` (`TASK_MARK`) holds `<project GUID>/<task key>` (`taskMark`; a key is not unique between projects), set by the service's launch and resume (`withTrust` in `src/service/accounts.ts`, `SessionStart.mark`) and put into the turn's environment by `markedEnv`. It names the task, not the session, since OpenCode's session id is unknown when its first turn starts.
  - **Which.** After the stops `stopTaskSessions` hands `killOrphans` the task's sessions from the launch log and those it just stopped, without any still live (kept mid-turn, a stop to retry, a stop refused), and the task's mark only when none of its sessions is left live — a kept session's turn carries it too. `stopLingering` does the same for a session once it stops it, the mark with the last kept session of the task (`Lingering.holds`).
  - **The kill.** It reads every process's environment (Linux `/proc/<pid>/environ`, macOS `ps -E`), takes those marked with one of the ids and every process under them (Chrome clears its children's environment) but never the service and the processes above it, kills them with `killLeftovers` and logs each with its pid, name and age. A hand session, the package gateway and another task's sessions carry other ids or none, so they are never taken.
  - Windows is left out: another process's environment is not readable there without the PEB, and an orphan still names its dead parent and holds its folder (`cleanup.folderLeft`). Not seen live on a chain yet: entry 237 of `docs/unverified.md`.

## git sync

- **What it is** (`src/git/sync.ts`): the `main` synchronization. If the repository has an `alias.sync` (`--local`), that one; the user's global alias only when the branch is named `main`, since such an alias is written for `main`. Otherwise Even Keel does it itself: the main checkout must stand on `main`; for each remote `git fetch` and `git merge --no-edit <remote>/main` (if it does not merge cleanly — `merge --abort` and an error), then `git push <remote> main` to each.
- **A rejected push** gets the whole sync once more, the alias's as well; a second rejection is the error. Rejected means `[rejected]` (another clone pushed between the fetch and the push, BTN-210) or `[remote rejected]` with a refused ref update — `incorrect old value`, `failed to update ref`, `cannot lock ref`, `failed to lock`, `stale info` (the other push landed inside this one, after it read the remote's refs, BTN-686). Any other `[remote rejected]`, a declined server hook among them, is the error at once.
- **The merge check** (BTN-995, `MergeCheck`). A project with `width` above 1 and its own `commands.check` runs those commands in the main checkout when Even Keel's own sync merged a remote's `main` that had commits the local one lacked (not a fast-forward either way) — a merge of another machine's work that nobody checked. Green — the push; a rejected push gets the whole sync with the check twice more instead of once. Red — `main` goes back to the commit before the sync (`reset --keep`), nothing is pushed and the error is `sync.checkRed` with the failed command, a warning in `leftovers` like a conflict. The alias's sync is not checked.
- **A failed sync** is a warning with its output, and the chain goes on; nothing is pushed by force: the next task takes the local `main`, and the next `git sync` after its Done repeats the push. Since the landing (BTN-1581) a task with a remote reaches Done only once its merge is pushed, so this sync has nothing of the task's left to push: what it can still meet is work merged into `main` by hand.
- **Retries** (BTN-267). A sync that never reached a remote — a fetch, a push or the alias whose output says `Failed to connect`, `Could not resolve host`, `Connection timed out`/`reset`/`refused` and the like (`transientFailure`) — or whose remote's server failed with a 5xx (as for the landing, BTN-1654) is tried twice more, 30 s and then 2 min later, before it becomes that warning; a refusal of the remote (`[rejected]` twice, permissions, a conflict) is the warning at once.
  - The retries do not hold the chain: the cleanup returns at once and the next task starts, and the dispatcher's tick (every 30 s) runs the try once it is due (`Cleanups.retrySyncs`). Each failed try is in the log; one that goes through is pushed as the cleanup's would have been (`MainCheck.pushed`).
  - The retry lives in memory, one per project and machine: it goes to the machine whose cleanup failed to sync (`FinishOutcome.machine`, BTN-995), since its `main` holds the commits, and the next cleanup's own sync on that machine takes its place; after a restart the next Done pushes what it could not.
  - A machine elsewhere that goes off the link mid-cleanup or mid-sync lets the hub go on at once (`RemoteMachine.lost`, `machine.lockLost`): that sync is a retry too, waiting without counting tries until the machine is back; a revoked machine's retry becomes the warning.

## Leftovers and work left

- **Leftovers.** A dirty worktree, a folder held by a process, an unmerged branch, a failed `git sync` — a warning in the log and on the project page (`leftovers` of the chain state, the "Done" button — `chain/dismiss`), and the chain goes on. A task whose folder still holds work after that keeps its row in the chain list, out of the archive, with the warning in its work chip's tip and "Done" on the row instead of in the head (BTN-332, `docs/web.md`).
- **Work left in a task's folder** (BTN-298), whatever its status and however it left the chain (`shelved`, a task moved by hand, a dead session). `TaskWorks` (`src/git/work.ts`) reads each project's `git worktree list` and, for every worktree or slot on a branch `<task>/…` of one of the project's tasks (not the main checkout), `changesOf` against the project's `branch`: the files left out of a commit (`status --porcelain`, so not what git ignores, `.temp/`) and the commits main does not have.
  - A project is read at most once a minute (a 15 s tick) and at once at the end of each cleanup after Done (`TaskWorks.refresh` from `finish`, after a read under way), so a removed folder does not linger.
  - A task's work read before its session last did anything (`lastActivityAt` of any of its sessions) is kept out of the state — the session may have committed or merged it since, and a closed task would flash "not committed" — and its project is read again on the next tick once no session of the task is mid-turn. So the page only tells of work that is really left.
  - The read runs in a folder whose session may be committing in it: every git call of Even Keel carries `--no-optional-locks` (`gitArgs`), so its `status` never takes `index.lock` and the session's `git add` is not refused meanwhile (BTN-697).
  - A change is broadcast with the state (`EvenKeelState.works`, only the tasks with something), a failed read keeps the last answer and logs once. It is in memory only; the page shows it as in `docs/web.md`.
- **The lines a branch changed**, for the chat's foot (BTN-1424, `branchDiffOf` in `src/git/diff.ts`), come from the same read: `git diff --numstat` from `merge-base <branch> HEAD` to the working tree, so uncommitted edits count, plus the lines of untracked files git does not ignore (a binary, one over 4 MB or unreadable counts none); a folder with no work gets zeros without the diff. These are `EvenKeelState.diffs`, every task folder git could read, and they are not kept out when read before the session's last activity: a count up to a minute behind mid-turn, fresh again after the turn, rather than one that vanishes each turn.

## Released tasks

What a released task is and what happens to it is in [entry](entry.md#released-tasks). For the sweep: each tracker read asks for them by id (`tracker.tasks`) and gives the answer to `Dispatcher.setReleased` together with the ids it asked about; one in Done is cleaned up as above by the released-task sweep (`Cleanups.sweep`) once its session is not mid-turn. Only the ids asked about are judged (BTN-766): the list is taken right after the read's task list goes to the chain and before the chain has followed it, so a task the chain releases while the answer is on its way is not in it and waits for the next read, instead of counting as gone and keeping its branch past its Done.
