# Chain: PR mode

## PR mode (`pullRequests`, BTN-205, `src/chain/reviews.ts`, `src/review/`)

With the project's `pullRequests` on, a session does not merge its branch: a human does, through a pull request. Off by default; a project of any tracker whose remote is GitHub, GitLab (merge requests, BTN-414) or Forgejo. Below, "pull request" covers a GitLab merge request too, its number the merge request's `iid`.

- **Before a launch** (EKR-12). `pullReadiness` (`src/review/open.ts`) is the one answer to "does PR mode have where to go": the `pullTarget` of the remotes and the token `ciToken` gives for it, or `review.noRemote`/`review.noToken`, or `review.unsupportedHost` for a target on a forge with no adapter (`remoteKind`, `docs/ci.md`; EKR-8), which asks for no token. The service's `blocked` hook (`pullBlock`) asks it of the remotes `ProjectRemotes.urls` rereads each minute (a project not read yet is not held), so no session of the project starts and the chain pauses with `review.notReady` and the cause. Start and Resume do not refuse this one block (`admit`, BTN-316): the chain goes in paused on it, other blocks still refuse them. Start, Resume and `wake` check the agent and account of the task that goes first — the current one, else the next by the order — since its run may pick another account; with no such task known only the tracker profile and PR mode are checked, and the launch checks the rest (`firstOf`, BTN-521). The dispatcher lifts that pause by itself (`cleared`) once the hook lets the project through — a remote or a profile added, or PR mode turned off. The page's save refuses to turn `pullRequests` on without a target (`review.cannotEnable`, read from git at once); turning it off always goes. A session already running whose remote went away still stops on `review.notOpened`. A tracker the sessions would not see pauses the same way (BTN-656): with `brief` off and no package bringing the tracker's MCP server (`noTrackerMcp`, `docs/packages.md`) the `trackerBlock` hook gives `chain.noTrackerMcp`, checked after `blocked` by every launch, Start, Resume and `wake` (`LaunchPauses.block`); Start and Resume go in paused on it and `cleared` lifts it once a package brings the server or `brief` is on — the codes that do this are `SELF_CLEARING` in `src/chain/pauses.ts`. `cleared` also lifts a pause on `chain.unknownModel` (BTN-679), which no launch block gives: it asks the async `modelBlock` hook (`ModelCatalog.refusal` for the first task's account and model) and goes on once the account has the model, as Resume would. A running chain whose package or `brief` goes off pauses before its next task; the session at work is not touched. The page puts "Turn on <package>" (or "Add the tracker's package", the add dialog) and "Turn the task description on" beside the reason (`web/src/pages/TrackerFixButtons.tsx`); no banner shows it. Packages only the user can make ready (not installed, failed to install, a key missing) pause the same way on `chain.packagesNotReady` (the `packagesPause` hook, BTN-657, `docs/packages.md`), except for a fix session of a red main.
- **What a running chain waits for** (BTN-657). A running chain with no session at work names the first thing that holds its next launch, in the order `step` checks them: the closing of a Done task (`closing`), the CI of main (`ciWait`), the first limits poll (`limitsWait`), a limit (`limitUntil`), the week of the task's model used up (`modelWeek`, BTN-816), the gateway or packages that pass by themselves (`packagesBlocked`), a free slot (`slotWait`). The chip of the card, the project page and the queue panel says "waiting · <reason>" (the card only "waiting": its line is right under it), and the card and the page add a line per wait with a button where one ends it (`chainWaits` in `web/src/waits.ts`, `web/src/pages/ChainWaits.tsx`). A wait that never passes by itself is a pause with a reason, not a wait.
- **On the page** (EKR-7). The state carries the same answer for every project read (`pullReadiness`: `null` or the notice), so the switch of the Check and CI tab cannot be turned on without a target, says why under it, and stays free to turn off once on (turning it on from the live page for a project with a Forgejo remote and profile was checked on 2026-10-25; the disabled switch was seen on the fake state only). `review.noToken` names the remote's kind and address: "Add profile" beside the switch and under a pause whose cause it is (`review.notReady`, `review.notOpened`) opens `/settings?profile=<kind>&host=<address>` — Trackers and CI with the dialog of that kind, no kind step, the address in its one host field (Forgejo's URL), the pull request rights stressed. A kind is not offered: `ciToken` takes a GitHub profile only for github.com and a Forgejo one only on the remote's host. A pause for `review.noRemote` leads to the project's Check and CI tab instead (`web/src/pages/PullButtons.tsx`, `pullFix.ts`).

- **The prompt.** `startPrompt`/`handoffPrompt` put `pullRequest(main)` in place of the cleanup rule (`src/chain/prompts.ts`): do not merge — this outranks the merge step of the tracker skill; when the work is done (and approved, where the project has a reviewer — a prompt that demanded one left a session without a reviewer waiting forever, BTN-221), commit the work, write the pull request's title (first line) and body into `.temp/pull-request.md`, which is not committed, and end the turn with the last line `PULL REQUEST: .temp/pull-request.md`. The mark is read like `CHECKPOINT:` (`pullRequestOf`, `TranscriptSummary.pullRequest`, Claude and Codex alike) into `HandoffSession.pullRequest`.
- **Opening** (`Reviews.follow`, on each step of the current task, once its session is not `busy`). A mark newer than the one the record holds (`markAt`) makes `openPull` (`src/review/open.ts`) push the folder's branch to the project's pull request remote (`pullTarget`: `origin` when its address parses, else the first remote that does; `github.com` is GitHub, `gitlab.com` and a GitLab profile's host are GitLab as for its CI — the subgroups in the owner, the installation prefix from the profile (`gitlabRepo`, `docs/ci.md`) —, `bitbucket.org` is not supported, any other host is taken for Forgejo) and open the pull request against the project's `branch`, or find the one already open — a session that fixed what the review asked marks again and its push goes to the same pull request. The record (`PullRequest`, `src/review/model.ts`) goes into `reviews` of the chain state (storage step 8), the journal gets `opened` (no launch; `review` before BTN-863, `docs/web/event-log.md`), and the task is set aside (`letGo`) like a postponed one: out of the chain, its session untouched. A mark that came while the chain was stopped is acted on at the step after "Start".
- **The issue's link** (BTN-295). A task id means nothing to GitHub, so for a pull request on GitHub of a task whose tracker names its GitHub issue (`TaskSource.closingRef`, only the GitHub adapter: `owner/repo#N` of the key's repository) `openPull` ends the body with `Closes owner/repo#N` (`closingBody`), always the full form, which GitHub takes for another repository too. The issue gets the pull request in "Development" and is closed by GitHub at the merge; a pull request into a branch other than the repository's default one is ignored by GitHub, and Even Keel closes the issue as before. A body that closes the issue itself (a closing keyword with `owner/repo#N`, the issue's address, or `#N` in the same repository) gets nothing; a mere mention does. The prompt does not ask the session for it and the title is left alone, by the user's decision; no setting. On GitLab (BTN-414) the GitLab Issues adapter's `closingRef` is the issue's address, and `closingOf` takes it only on the merge request's own server: an issue of the merge request's project is closed as `Closes #N`, of another project as `Closes group/name#N`; the body's own close counts by the same forms or the `/-/issues/N` address. A GitHub issue gives a GitLab merge request nothing, a GitLab one a GitHub pull request nothing, and Forgejo gets no line at all.
- **Nothing to open** (BTN-222). Before the push `openPull` fetches the base from the remote and counts the branch's commits beyond `<remote>/<branch>` (not the local main: in PR mode it may lag); none — nothing is pushed, and the worktree decides, before the note is read (`.temp/pull-request.md` is not needed then, and an untracked note is not work). Clean (`git status` with untracked files lists nothing but the note) — the task changed nothing in the repository (research, work already in main): no pull request, `complete` of the tracker moves it to Done as after a merge, the tracker is read at once (`refresh`) and the chain's own Done takes it — exception 4, the usual cleanup with `git branch -d`, the next task. A tracker that refuses the move pauses the chain with `review.notCompleted`, the task staying current: the user moves it and resumes, or skips it. No setting, by the user's decision: a stop there would give a human nothing but a Done to press. Dirty — the work is not committed: the session gets `review.nothingAhead` of the prompts by `--resume` whatever its cache, as a chat answer does (commit and mark again, or drop the changes and mark again), and the chain waits on it. The prompt's `pullRequest` tells a session of a task with no change in the repository to mark all the same.
- **A branch moved on the forge** (BTN-716). A push git refuses as `[rejected] … (fetch first)` or `(non-fast-forward)` — the branch on the remote has commits the session's lacks, say a conflict the user resolved on the forge while the session worked on its feedback — is `review.pushBehind`, not an access problem: the session gets `review.pushBehind` of the prompts the same way as `review.nothingAhead` (merge the branch from the forge with `git pull --no-rebase`, resolve the conflicts, commit and mark again; never push itself, never `--force`), and the chain waits on it, unpaused. Even Keel never forces the push and never merges in the session's worktree itself: the user's commits on the forge stay, and a conflict is the session's like any other.
- **A refused mark** (BTN-222, BTN-407). Any other failure pauses the chain with `review.notOpened` and the cause (a forge's refusal by the `message`s of its answer, `src/ci/http.ts`), the task staying current (`ReviewHost.hold`), so the chat, "New session" and "Skip" act on it; a chat answer or "New session" ends that pause. So does the task's end (BTN-715): once its earlier pull request is merged (`ReviewHost.settle`) or the tracker has it done (`Dispatcher.step`), the pause lifts by itself and the task goes as on any Done, its session untouched — a push refused by the forge no longer holds the chain and its `parallel` slot. Pauses for other reasons stay. Start on this pause (`resume` on the page, or `start`) forgets the current task's refused mark (`Reviews.retry`) and tries it again without touching its session, so access can be fixed in the project's Check and CI settings first. Another refusal pauses with its new cause. A mark that opened nothing has its `lastReplyAt` remembered in the service's memory (`Reviews.refused`): Skip and Unskip or Stop and Start do not retry it, only a new session turn, Start on `review.notOpened` or a service restart does. A profile or token change alone does not retry it.
- **Out of the chain.** A held task (`Reviews.holds`: open without feedback, or closed and not cleaned up after) enters neither the order nor the backlog, and an open task it blocks waits for it like for any open blocker. The page shows it as a dashed row between the closed tasks and the chain, with a "PR #N" link and a "feedback" chip (`ProjectOrder.reviews`, `chainBlocks`; in `dev:fake` it is DEMO-9). The task's panel has a "PR #N" button beside Chat and the chat window an icon in its head, both opening the pull request in a new tab (`PullButton`, BTN-224): the row's chip alone went unnoticed.
- **The poll** (`Dispatcher.pollReviews`, every 60 s from the service, and for one project on the page's task refresh, `chain/refresh`; `reviewDeps` in `src/review/wiring.ts` picks the forge by the remote and its token). `check` reads the pull request's state, the remarks after the last push and the failed runs of its head commit — one not told yet with the log tail of its first failed job, read as for a red main (`readFailure`, `docs/ci.md`; BTN-605); `outcomeOf` (`src/review/events.ts`) turns them into what the chain has not acted on yet — the events already told are in `seen` (`review:<id>`, `comment:<id>`, GitLab's `note:<id>`, `ci:<id>`, `conflict:<head>`).
  - **What counts as a remark** (`Forge.remarks`, BTN-223) — from a trusted author, the pull request's author included: a review that asks for changes, a review that comments (GitHub `COMMENTED`, Forgejo `COMMENT`) with words or line comments, and a comment in the pull request's conversation (the comments of the issue it is, read from the last push with `since`). Not a remark: an approval, a dismissed or pending review, a commenting review without a word, and on GitHub a comment by a bot account (`user.type` `Bot`) — coverage and preview bots comment on every push and would loop the session. Trusted on GitHub (`trustedAuthor`, `src/github/trust.ts`): the owner, the organization's members and the collaborators by `author_association`. Trusted on Forgejo (`accessOf`, `src/review/forgejo.ts`, BTN-653): the token's own login (`/user`, once per forge) and `write`, `admin` or `owner` in `/collaborators/{user}/permission`, asked once per author per poll. Forgejo answers that path for another user only to an admin of the repository; on its 403 only the repository's owner by name is trusted, and anyone else is skipped with a log line that asks for admin rights for the profile's account (BTN-703): nothing else Forgejo 16 answers such a token tells `read` from `write` — `/collaborators/{user}` is 204 for both, `/collaborators` lists no access, an organization's member may have `read` only — and a `read` collaborator can comment and request changes. Any other 4xx is "no". A skipped remark gets a log line once (`Skipped`) and is asked again on the next poll. Neither GitHub nor Forgejo lets the author request changes on their own pull request (Forgejo answers 422 "reject your own pull is not allowed"), and Even Keel opens it with the user's token, so a user alone gives feedback by commenting. Even Keel itself writes nothing on a pull request, but its session may, and often with the same token, so the author does not tell its words from a reviewer's (BTN-442): the PR-mode prompt has the session put the hidden mark `SESSION_MARK` (`<!-- even-keel:session -->`) into whatever it writes on its own pull request, and `othersOnly` (`src/review/model.ts`) drops in `check` a remark whose text is marked whole and a marked line comment alone, for an open pull request and for the `closedNote` of a closed one alike. A session that forgets the mark gets its words back once, as before. GitLab (`src/review/gitlab.ts`) has no reviews to group by: each note of the merge request's discussions made after the push is a remark (`note:<id>`), a line note (`DiffNote`) with its file and line, the rest a comment; not a remark: a system note (an approval, a request for changes, a push), a bot's (`author.bot`, or the `project_<id>_bot…`/`group_<id>_bot…` users of access tokens, which are members) and an author below Reporter in the project (`/members/all/:id`; a 404 or 403 is not trusted), skipped with a log line once, as the GitLab tracker skips comments. A conflict is `has_conflicts` or `detailed_merge_status` `conflict`; `unchecked`, `checking` and `preparing` are "not computed yet". Forgejo answers `mergeable: false` both for a conflict and while it checks mergeability after a push, with nothing in the answer to tell them apart, so in `check` (`src/review/wiring.ts`) its `false` within 60 s of Even Keel's push (`pushedAt`, `FORGEJO_RECHECK_MS`) is "not computed yet" too, and a real conflict reaches the session on the first poll after that (BTN-717); a push to the branch by someone else gets no such wait. The failed runs are the pipelines of the head commit, as the CI reads them; `opened` and `locked` (a merge going on) are open.
  - **Merged** — the tracker's `complete` moves the task to Done and it goes into `released`; the usual sweep cleans it up (exception 4), with the branch deleted by force (`-D`, it never merged locally) and on the pull request's remote (`PullCleanup`). A task the tracker closed first — a forge's integration closes it on the merge — is cleaned up the same way, and `Reviews.closedUp` says so in the log, as no poll will.
  - **Closed unmerged** — once no chain leads the task and its sessions rest, `Reviews.sweep` cleans up the same way but does not archive it, then puts the still open task among the skipped: it is the user's to run again. Its tracker status is left alone on purpose (BTN-211, invariant 2): putting it back to Todo would redo the rejected work the same way, and Backlog or Canceled would take the call away from the user — they return it to the chain, move it to Backlog or cancel it in the tracker themselves. The poll that sees the close reads every remark since the pull request was opened, seen or not, and keeps `closedText` (the link, the latest 20 remarks with a count of the earlier ones, "the branch is removed, start over from `main`") in the record's `closedNote`; after the cleanup the record stays with `cleaned` — out of `holds`, `views` and the poll — until the task's next launch carries the note in its prompt (`Reviews.closedNoteOf`, `review` in the launch log) and drops it, or the task is done. A record closed before BTN-223 has no note and goes at the cleanup, as before.
  - **Feedback** — `feedbackText` in `promptLanguage` (the link, each remark, each failed run with its log tail in a code block when the CI gave one, "merge `main` if it conflicts") waits in the record's `feedback`. The chain takes a task with feedback before the next one of its order (`Reviews.next`); if the task is the current one, its session gets it at once while it is not mid-turn: `--resume` with it while the cache is warm, otherwise a new session with a handoff carrying it (`review` in the launch log; exception 8 to invariant 1). A launch of the task with feedback carries it in the prompt (`delivered`). A chain that ran out of tasks and ended by itself (`ended, no task left to run`) marks the project's open pull requests `wakes` (`Reviews.ended`); feedback on one of them starts the chain again as "Start" does, or queues it (`Dispatcher.wake`, BTN-375; the log says `starts again: feedback came on a pull request of its tasks`), and the task takes the feedback by the path above (checked live on 2026-10-25: a comment on a Forgejo pull request of an ended chain started it within a minute and a new session pushed the change to the same pull request). "Stop" and taking the chain off the queue clear the marks (`Reviews.stopped`), so a chain the user stopped stays stopped, even if it would have ended by itself later: there "Start" sees the feedback task as work. A paused chain is still a chain and stays paused; a chain whose launches are blocked (other than by `review.notReady`) is not started, with a log line. A merge starts no chain: it completes the task without one. Unattended mode changes none of this.
- A service restart in the middle of delivering feedback is redone by `Handovers.recover` (the `review` move keeps its text in `reply`), as for an answer.
