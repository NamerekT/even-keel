# Chain: task worktrees, slots and cleanup

## Task worktree (`src/git/worktree.ts`)

`main` in this document is the project's main branch: its `branch` key (BTN-117), `main` without it. Every git call takes it from the current config, so a change applies without a restart. A branch the repository lacks pauses the launch with `git.noBranch`, naming the branch and the project. At the launch (not in the preparation ahead, while the chain waits for the CI) the main checkout must also stand on that branch (`git symbolic-ref --short HEAD`): on another branch or a detached HEAD the launch pauses with `git.wrongBranch`, since the merge, `git sync` and the search for the merged task all work on the project's branch.

- Before the first launch for a task — in the project's main checkout (`config.projects[project]`) `git worktree add -b <key>-<number>/task .claude/worktrees/<key>-<number> main`, all lowercase. The branch tail is always `task`: the hooks in `~/.githooks` need the form `<key>-<number>/<something>`.
- Before that, at every launch (not for a place made ahead), the main checkout's `main` is fast-forwarded to `<remote>/main` of each remote (`fastForwardMain`, `src/git/sync.ts`, BTN-210): another clone of the same remote may have pushed since this one's last `git sync`. Only when the checkout is on `main` without changes to tracked files; a `main` ahead or diverged, a fetch that fails — left as it is, silently. A place made ahead then comes up to the new `main` by `catchUp`, as after a fix.
- If a worktree already exists at that path, it is taken as is, with its branch; if only the branch exists, it is brought back into a new worktree. `.claude/worktrees/`, `.temp/` (a session's scratch, the pull request's description among it, BTN-221) and `/.codex/rules/even-keel.generated.rules` (the Codex deny rules, EKR-107) are appended to `.git/info/exclude` if git's patterns do not ignore them (`check-ignore --no-index`, so a file already committed does not add the line again).
- The session starts with `cwd` = the worktree, and the prompt is the task ID, a line about the ready worktree and that there is no need to clean up (`startPrompt`).
- Commands before start (BTN-97, `commands.beforeStart` of the project, `src/sessions/setup.ts`): after the worktree or slot is ready and before the session starts, each runs in order through the system shell in the task's folder, with the session's environment: that of the account the task runs on (`choiceFor(project, task).account`), through its agent's `envOf` — a Codex task gets Codex's, so a Codex-only install with no `~/.claude` runs them too (EKR-26) — and the service's own, keys removed as in `sessionBase`, while that account has no folder (`accountEnv`); `check` and `afterGreen` run the same way, `afterGreen` on the project's account. 20 min at most. Their output goes to the service log line by line (`setup: <task>: | …`); a non-zero exit stops the rest, the session is not started and the chain pauses with `setup.failed` and the last 40 lines of output. They run on every new launch of a task (a task the chain takes again runs them again), but not on `--resume`, a reply or a handoff.

## Task branches on the remote (BTN-1270)

A task's branch goes to the remote whatever the project's mode, so another machine can take the task over when its machine is gone ([machines](../machines.md#a-machine-gone)). Sessions never push it; Even Keel does, on the machine that runs the task (`pushTaskBranch`, `src/git/push.ts`, through `pushOf` in `src/service/machine-chain.ts`):

- at a handoff and a checkpoint (`relay`): once the previous session is stopped, from its folder, behind the next session's launch (the machine's `writes`), so a slow pre-push hook holds nothing;
- at a stop of a task's session (`stop`: a red main interrupting it, extra usage held);
- at the end of a turn of a session Even Keel launched (BTN-1274: a question, an `AskUserQuestion` or a permission prompt, a turn with no mark, a session that died mid-turn), from the session's folder, in the background (`writes`). The session monitor's tick (`wireMonitor`, `src/service/session-monitor.ts`) hands the ended turns to it: `TurnEnds` (`src/sessions/turn-ends.ts`) names a session once when it leaves `busy`/`shell`, and a live one first seen between turns, so work from before a restart goes too. Such a push is `onlyNew`: no `git push` when HEAD is already in the remote-tracking ref of the last push (`refs/remotes/<remote>/<branch>`, which a push updates) or in `main` (a merged task closes), two local `merge-base --is-ancestor` calls; a repository whose fetch refspec keeps no such ref pushes at every turn end, harmlessly. PR mode pushes at a turn's end too (BTN-1419), so a task stopped on a question is kept on the remote: the branch then reaches the forge before its pull request, and a workflow `on: push` of every branch runs on it early. `openPull`'s checks (the note, nothing ahead, an outsider's files) are about opening the pull request and stay where they are;
- in PR mode, when `openPull` opens the pull request (`docs/chain/pr-mode.md`).

Only the intake on the hub knows an outsider's task (BTN-1207). The hub's brief of a task (`LaunchBrief`, [machines](../machines.md)) carries `own: true` when `Intake.outsider` says it is not one, asked at every brief and never cached with it; the machine keeps the last brief received per task (`LaunchBriefs.own`). For a task with no such brief — an outsider's, a brief from a hub that does not tell, none kept since the machine's restart — none of the three pushes a branch whose changes against `main` (`git diff --name-only -z main...HEAD`) touch a file `guardedFiles` names, or that git cannot list (BTN-1274, BTN-1418, BTN-1419): a push of a changed workflow runs it with the repository's secrets. A `push:` line says so; such a branch stays only in its folder, and another machine cannot take the task over from the remote while it holds that change. A task the hub vouched for is pushed whatever files it changes. An author whose association changes mid-session reaches the machine with the task's next brief (a launch, a handoff, a move).

The remote is `taskRemote`: `origin` when the repository has one, else its first remote. Only a folder standing on the task's own branch (`<key>-<number>/…`) is pushed, never forced; a refused push (the remote moved on, a server hook) or a repository without remotes is a `push:` line in the log, never a pause. The chain's fix and carry sessions and a project without git push nothing. The cleanup after Done removes the remote branch with the local one (below), on the same `taskRemote`.

Not pushed: commits made mid-turn until that turn ends. A machine gone mid-turn takes them with it.

## Landing (BTN-1581)

**Done is the task's branch in the main of the remote, not in the local one.** The merge closer (`MergeCloser`, `landedCommits` in `src/git/merged.ts`) counts a branch merged once its own commits are in `refs/remotes/<remote>/<main>` of every remote of the checkout, as its last fetch or push left them. A checkout without a remote, and a project in PR mode (the forge lands the branch), go by the local `main` as before. A carry's release commit is counted the same way (`landedCommit`, the machine's `carried`); the merge `merged` of a machine elsewhere too.

The landing is Even Keel's, not the prompt's. The signal is the session's merge into the main checkout, seen on the dispatcher's step once the session's turn ended (`Landings.follow`, `src/chain/landings.ts`, called from `followCurrent` before the PR review and the hint of `Unchanged`, and from `stopAfterTurn`; a fix and a carry session land the same way, a carry by its release commit). The machine's `land` (`MachinePort.land`, `landTask` in `src/git/landing.ts`) then:

- returns `none` when there is nothing to land: no remote, no own commit of the task in the local `main`, or every one already in each remote's `main`; nothing is fetched;
- finds `main` before the session's merge — the newest commit of its first-parent line that holds none of the task's unlanded commits (the newest of each branch and the oldest one not landed yet, so a later round that fast-forwarded `main` over the whole branch rolls back past all of it); none within 200 commits — `landing.noBase`;
- for each remote: `fetch`, `merge --no-edit <remote>/<main>`; a conflict — `merge --abort`, `reset --keep` to that commit, `returned` with the files git left unmerged;
- when a remote had commits the local `main` lacked and the project has `commands.check` (any width, unlike the cleanup's merge check), runs them in the main checkout; red — `reset --keep`, `returned` with the command, its exit code and the end of its output;
- pushes `main` to each remote; a push rejected because another clone pushed meanwhile gets the whole landing again, twice at most, as `syncMain` does. A repository's own `alias.sync` (or the global one on a branch named `main`) does the fetch, the merge and the push itself, with no `commands.check`; its conflict is told by the files it leaves.

The dispatcher keeps what a landing still holds in `ChainState.landings` (`docs/chain/state.md`):

- **landed** — the record goes, the tracker is read at once, and the closer moves the task to Done; the cleanup after Done follows as before, its `git sync` now normally with nothing to push.
- **returned** — the main checkout is clean and on the commit before the merge; the worktree and the branch live on, since there was no Done. The session gets a message (`landingPrompt`, `src/chain/prompts.ts`): the remote and the files of the conflict, or the red command with the last 4,000 characters of its output — merge `<remote>/<main>` into the branch in its own folder, resolve, run the checks, merge again. The delivery is invariant 1's exception 13 (`docs/chain/exceptions.md`): a warm cache — `--resume`, else a stop and a new session with a handoff that carries the message (`landing`, the journal's cause `landing`). The message waits in the record while the account's limit or a launch block holds. The record gets `resolving` ("The hold while a landing resolves" below). A new merge of the session is a new landing.
- **Rounds** — one round is one return to the session; at most `LANDING_ROUNDS` (3), not a setting. A landing that would need a fourth pauses the chain on the task with `landing.exhausted` (a `USER_HOLDS` pause: the chat answers its session) and sends nothing more. A person's answer to the session (the chat's answer or a new session from it) starts the rounds over; a landing that went through drops them with the record.
- **Remote out of reach** (`isNetworkFailure`) — the task stays open and its session is told nothing; the landing is tried again 30 s and 2 min later, then every 10 min with `waitingRemote` set, until the remote answers. For a long outage the page's "Close without pushing" (BTN-1582, `chain/closeUnpushed`) closes such a task anyway: the dispatcher checks, on its own turn, that the task is a lane's current one and its record `waitingRemote` (else `landing.notWaiting`), moves it to Done through the tracker's `complete` with a comment saying its merge is not pushed yet (`landing.unpushed` of `PROMPTS`; a tracker failure — `landing.notClosed`) and drops the record; the cleanup after Done follows, and its `git sync`, or the next one, pushes the merge once the remote answers.
- **Refused** by the remote (a hook, permissions, `sync.notMain`) — the chain pauses on the task with `landing.refused` and git's text as its cause; no round.
- A task that leaves the chain meanwhile (cancelled, back in Backlog, Done by hand) drops its record; the main checkout is already clean after the roll-back. A session mid-turn is not landed: its turn may still be merging. For the same reason a fix of main (`MainFix.yields`) asks the machine's `merged(project, task, true)` — merged into the local `main`, not landed — so a session whose branch is merged only locally is not stopped mid-turn; its landing follows the turn.

The landing runs on the machine that holds the task's checkout. A project lands one task at a time on all its machines, and a landing that went through brings the other machines' `main` up to the pushed commit (BTN-1583, `docs/machines.md`, "Landings across machines"). A step waits for a landing at most `LANDING_WAIT_MS` (2 s); a longer one — a merge with `commands.check`, a machine off the link — goes on behind the chain with the task held, and its end wakes the chain.

### The hold while a landing resolves (BTN-1582)

While a session of the project resolves its landing, no lane of the project starts a new task: its merge would most likely meet the same conflict, and the resolving session's next merge would meet it again. The setting `landingHold` (`docs/settings.md`, G and P, on by default, live) turns it off. A resolving landing is a record with `resolving` and without `waitingRemote` whose task is the current one of a lane of the project (`resolvingLanding`, `src/chain/landing-hold.ts`); a task taken off with "Skip" holds nothing. Only a fresh start of the next task by the chain's order waits (`heldByLanding` in `launchNext`, `src/chain/step.ts`, logged once per lane and task): lanes whose tasks already run go on, and a live or returned session, a fix of main and a carry are not held. The page shows it as the "waiting" state under Start/Stop with the task in its tip; a task waiting for the remote is a line above the chain with "Close without pushing" (`docs/web.md`, "Chain waits").

## Cleanup after Done

The stop, deferred-stop and retry wiring is in `src/service/cleanup.ts`, re-exported by `src/service/chain.ts`. Rare mid-turn deferrals and their stop results use the `rare: 17c` diagnostics described in [unverified sessions](../unverified/sessions.md#a-session-left-mid-turn-by-the-cleanup-btn-616).

- A merged task is closed into the tracker's first done status, or into the one its source chose (BTN-554, `doneMove`; "Status moves", `docs/chain/entry.md`). A chosen status the chain rules do not take for done is not tried: the task stays open with `statusMove.notDone` until the setting changes. Every way of closing takes the same choice (BTN-1163, `closeInto`; the list is in `docs/trackers.md`, "Moving a task to a chosen status"): a merged pull request, a pull request with nothing to open, a `NO CHANGES:` mark and "Accept as answer" too.
- A session that merged real commits and still ended its turn with `NO CHANGES:` closes by the mark (its branch has nothing beyond main once merged): the task closes into the same status, only its comment says no change was needed. Left so (BTN-1163): telling the two apart costs a git call on each mark and touches the verdict a fix of main waits on.
- Any merge of the task's branch that landed in the remote's `main` ("Landing" above; without a remote, in the local one) closes it, a half of the work merged mid-task too: the close does not wait for the turn to end, only the cleanup does. A task the user takes back from Done is closed again only by a new merge (BTN-219, BTN-689): `MergeCloser` keeps the own commits of its branches `main` had at the close (`landedCommits` over `mergedCommits`, the newest of each branch, in `src/git/merged.ts`) in `MergeMarks` (`src/tracker/closes.ts`, the state table `merge_closes`, through a restart), and a reopened task whose merged commits are all in that mark stays open, so a checkpoint handover on a branch merged before the reopen goes on in the new session. A branch that only caught up with `main` adds no commit of its own; a branch removed by the cleanup and made anew has new ones. A task closed before this mark existed has none, so its first close after a reopen still goes by the old rule. Only a merge seen while the chain holds the reopened task closes it (BTN-694): while it is open and not held (neither the current task with a session nor a released one awaiting cleanup, `Dispatcher.held`), every tracker read adds its newly merged commits to the mark without closing it, so a session that merged again outside the chain does not close it the moment the chain takes it back. A hand session that finishes such a task outside the chain closes it itself.
- If the tracker refuses to close a merged task, `MergeCloser` keeps a `tracker.completeRefused` notice for that reader and task in `TrackerView.completionFailures` (memory only). The page shows the tracker response and a link to the task, asks for the required field to be filled or the task to be closed by hand, and suppresses a false reply prompt in the header, lamp and session panel; a real question or permission remains visible. The task stays current and the normal 30 s full read retries the close. Success clears the notice; a task no longer held drops its refusal, and the page also hides one as soon as polling sees a closed status. Git inspection errors remain separate from tracker refusals.

- The current task went to Done (category `Won`; a cancelled or dropped one does not) — the chain's `closing`: wait until its session is not mid-turn (`busy`/`waiting`; a session in `shell` does not hold a done task — see "Background command", `docs/chain/unattended.md`), then `claude stop` its sessions in this worktree (otherwise a live process holds the folder: a `--bg` session does not exit after a turn, `claude agents` shows it `done`/`idle`), then in the clean worktree remove links and junctions in ignored folders (`node_modules` of npm workspaces, `npm link`: git on Windows follows them — it cleans someone else's folder or stumbles on a dangling one and abandons the worktree), then `git worktree remove` (without `--force`; every git call of Even Keel on Windows carries `-c core.longpaths=true`, and a folder git unregistered but left for another reason than a lock — `Filename too long` — is deleted from Node, BTN-559; only a lock is `cleanup.folderLeft`, the rest `cleanup.folderNotDeleted`), `git branch -d` of the task branch (only `<key>-<number>/…`), `git push <remote> --delete` if it is on the task branches' remote (`taskRemote`, above), and `git sync` if the project has a remote. The next task is started after that. A task returned from Done before the cleanup — no cleanup, the task is back in the chain.
- **The first read of the sessions** (BTN-646). After the service's start the dispatcher does nothing — no cleanup, launch, handoff, review, fix or slot switch — until the monitor has finished its first full tick (`DispatcherDeps.sessionsRead`, the service's `agentsRead`, set with the first `onChange`): before it `busy` is unknown rather than false and the cleanup's `stopTaskSessions` sees no session at all, so a Done right after a restart removed the worktree past its live session and left the folder held (`cleanup.folderLeft`; BTN-537, BTN-587, BTN-642). The forward merges (`chainQuiet`) and the account watcher (`sessionsKnown`) wait for the same flag.
- **A session left mid-turn** (BTN-616). The cleanup waits only for the task's own session (`busy` by its view); another session in the task's folder, or one whose status the view and the listing disagree on, may still be `busy`/`waiting` when `stopTaskSessions` runs. Such a session is not stopped then but kept in `Lingering` (`src/sessions/lingering.ts`, the service's memory) and stopped on the first monitor tick after its turn ends (`stopLingering`, from `onAgents`, since a session without a view of its task changes no view); once gone by itself it is forgotten. Otherwise nothing stopped it after its task left the chain, and a Codex session, which has no process between turns, rested on the page as `waiting` for good. A restart before its turn ends forgets it.
- **A stop that timed out** (EKR-99). A Claude `--bg` stop first lists the folder's sessions (`claude agents`), and that call waits in the account folder's queue (`FolderCalls`, EKR-15): right after the service's start `/usage` and the `/context` probes fill it, and a call whose timeout passes while it waits never starts. Since EKR-102 that listing goes ahead of the waiting calls and is tried again for up to 5 minutes (`QueueWait`, `docs/accounts.md`), so this is rare. Such a `CallTimeout` (`isCallTimeout`, through wrapping causes) is no failure of the stop: `stopTaskSessions` keeps the session in `Lingering` with a retry (`STOP_RETRY_MS`, 5 min), and the worktree folder git unregistered but left because that session's process holds it (`cleanup.folderLeft`, Windows) is left to it too (`deferLeftFolder`), so neither goes into `leftovers`. `stopLingering` tries the stop again on each monitor tick, one run at a time (`Lingering.alone`), then removes the folder (`removeLeftFolder`; a folder registered as a worktree again meanwhile is not touched). Only a stop still timing out once the wait is over, or failing otherwise, is `cleanup.sessionNotStopped`, and a folder still held `cleanup.folderLeft` — added to the task's leftovers then (`Dispatcher.leftover`). A stop that fails for any other reason warns at once, as before. A slot is not removed, so only its session is retried. A restart forgets the session's retries, as it forgets a session left mid-turn; the left folder it keeps (BTN-925, below).
- **A folder still held after a stop that went through** (BTN-870). A stopped process lets go of its folder a moment after it exits on Windows, and a child of it (a Codex `codex exec` turn's shell) later still: under load the cleanup's `git worktree remove` comes first and the folder is left (`cleanup.folderLeft`). So every such folder of a Done cleanup goes to `deferLeftFolder`, not only one of a timed-out stop: `stopLingering` tries it again on each monitor tick while no kept session of the task is left, and warns only if it is still held once `STOP_RETRY_MS` has passed. Seen in the real-CLI scenarios with the three files at once (`docs/chain/e2e.md`, "Real CLIs"). A left folder outlives a restart (BTN-925): in a project with `commands.afterGreen` the service restarts about a minute after nearly every Done, so a folder kept only in memory was forgotten almost always. `Lingering.leave` saves it into the state table `left_folders` (`docs/storage.md`) and the row goes once the folder is removed or warned about; at the start the service reads them back (`Lingering.restore`) and `stopLingering` takes them up only after the monitor's first read of the sessions (`agentsRead`, BTN-646). The wait is `until`, counted from the Done, not from the start: a wait that ran out while the service was down gets one try at once and, still held, the same `cleanup.folderLeft` warning on the task. A session kept with the folder is not saved, so after a restart its folder is tried at once rather than after the session's stop.
- **Orphaned processes of the task's sessions** (BTN-1268, `src/sessions/orphans.ts`). A Claude stop kills the processes it lists under the session (`killLeftovers`), but that misses a session that died before the cleanup — on Linux and macOS its children go to init — and anything that detached itself (`setsid`, `nohup`, a dev server's double fork); other agents only kill their own child's tree. The CLIs mark every command they run with the session's id in its environment: `CLAUDE_CODE_SESSION_ID` (Claude, `--bg` and SDK alike) and `CODEX_THREAD_ID` (Codex). OpenCode and Copilot put none, so Even Keel marks their turn process itself (BTN-1389): `EVEN_KEEL_TASK` (`TASK_MARK`) holds `<project GUID>/<task key>` (`taskMark`; a key is not unique between projects), set by the service's launch and resume (`withTrust` in `src/service/accounts.ts`, `SessionStart.mark`) and put into the turn's environment by `markedEnv`; it names the task, not the session, since OpenCode's session id is unknown when its first turn starts. So after the stops `stopTaskSessions` hands `killOrphans` the task's sessions from the launch log and those it just stopped, without any still live (kept mid-turn, a stop to retry, a stop refused), and the task's mark only when none of its sessions is left live — a kept session's turn carries it too; `stopLingering` does the same for a session once it stops it, the mark with the last kept session of the task (`Lingering.holds`). It reads every process's environment (Linux `/proc/<pid>/environ`, macOS `ps -E`), takes those marked with one of the ids and every process under them (Chrome clears its children's environment) but never the service and the processes above it, kills them with `killLeftovers` and logs each with its pid, name and age. A hand session, the package gateway and another task's sessions carry other ids or none, so they are never taken. Windows is left out: another process's environment is not readable there without the PEB, and an orphan still names its dead parent and holds its folder (`cleanup.folderLeft`). Not seen live on a chain yet: entry 237 of `docs/unverified.md`.
- **Nothing to merge** (EKR-10), out of PR mode. A task that needs no change in the repository (done in main already, research, an answer) never closes by a merge: `branchMerged` takes a branch with no commits of its own for unmerged, or every branch that only caught up with main would close its task. The prompt's `cleanup` tells such a session to end its turn with the last line `NO CHANGES: <why>` (`noChangesOf` in `src/sessions/transcript.ts`, Codex's rollout too; a tool call or a new prompt drops it, as `CHECKPOINT:`). `Unchanged.follow` (`src/chain/unchanged.ts`), once the session is not `busy` (a session in `shell` does not hold it, BTN-637 — see "Background command", `docs/chain/unattended.md`), counts the commits of its folder beyond the local main and reads `git status` with untracked files (`changesOf`, `src/git/changes.ts`; ignored `.temp/` is not work). Nothing — `UnchangedDeps.complete` moves the task to Done in the tracker and comments the reason (`unchanged.comment` of the prompts; a comment that fails is only logged), the tracker is read at once and the chain's own Done cleans up — exception 4, `git branch -d`, the next task. A tracker that refuses pauses the chain with `chain.unchangedNotCompleted`, a git that cannot count with `chain.unchangedNotChecked`, the task staying current. Commits or uncommitted changes — the session gets `unchanged.ahead` or `unchanged.dirty` by `--resume` whatever its cache, as a chat answer does (merge them, or drop them and mark again). A mark acted on has its `lastReplyAt` remembered in the service's memory, so only a new turn tries it again. In PR mode the mark is ignored: `PULL REQUEST:` covers the case (BTN-222). The last line `TASK DONE` of a project without git (below) is read by the same `noChangesOf`, so in a git project it acts as `NO CHANGES:`.
- **Accept as answer** (BTN-885). A session that answered but forgot the mark (Codex most often) leaves its task waiting with no way to close it short of asking for the mark and waiting a turn. The session panel and the chat then offer "Accept as answer" (`offersAccept`, `web/src/pages/acceptAnswer.ts`): the current task's session ended its turn on a message — not mid-turn, no question, permission or startup dialog, no error, limit or checkpoint mark — the task is no fix or carry, has no pull request under review, is not merged with its close refused, and `TaskWorks` knows no work in its folder. The press (`chain/accept` with the session id the page saw) goes through `Dispatcher.accept`: `acceptable` (`src/chain/answers.ts`) refuses a task that is not current (`chain.notCurrent`), launching, a session moved on since the page read it (`answer.moved`), mid-turn or in a background command (`chain.midTurn`), waiting on an `AskUserQuestion` (`accept.asking`), with no last message (`accept.noMessage`), or done already in the last read (`accept.closed`, so a second press does not comment twice). Then, in the dispatcher's turn, `Unchanged.accept` counts the folder as for the mark: commits beyond main refuse with `accept.ahead` (such work closes by a merge, and the close would lose it), uncommitted files with `accept.dirty`, a git that cannot count with `accept.notChecked`. Clean — `UnchangedDeps.accept` puts the session's last message whole (as the transcript keeps it, `MESSAGE_LIMIT` — 30,000 characters at most since BTN-883) on the task under `unchanged.accepted`, then moves it to Done; the comment comes first and a failed one refuses (`accept.notCompleted`), since it is the answer. The tracker is read at once and the chain's own Done cleans up — exception 4 again. Every refusal goes back to the page and leaves the chain as it is, unpaused.
- `git sync` is the `main` synchronization (`src/git/sync.ts`): if the repository has an `alias.sync` (`--local`), that one; the user's global alias only when the branch is named `main`, since such an alias is written for `main`; if not, Even Keel does it itself: the main checkout must stand on `main`, for each remote `git fetch` and `git merge --no-edit <remote>/main` (if it does not merge cleanly — `merge --abort` and an error), then `git push <remote> main` to each. A push rejected as `[rejected]` (another clone pushed between the fetch and the push, BTN-210) or as `[remote rejected]` with a refused ref update — `incorrect old value`, `failed to update ref`, `cannot lock ref`, `failed to lock`, `stale info` (the other push landed inside this one, after it read the remote's refs, BTN-686) — gets the whole sync once more, the alias's as well; a second rejection is the error. Any other `[remote rejected]`, a declined server hook among them, is the error at once.
- **The merge check** (BTN-995, `MergeCheck`): a project with `width` above 1 and its own `commands.check` runs those commands in the main checkout when Even Keel's own sync merged a remote's `main` that had commits the local one lacked (not a fast-forward either way) — a merge of another machine's work that nobody checked. Green — the push; a rejected push gets the whole sync with the check twice more instead of once. Red — `main` goes back to the commit before the sync (`reset --keep`), nothing is pushed and the error is `sync.checkRed` with the failed command, a warning in `leftovers` like a conflict. The alias's sync is not checked.
- A dirty worktree, a folder held by a process, an unmerged branch — a warning in the log and on the project page (`leftovers` of the chain state, the "Done" button — `chain/dismiss`), and the chain goes on. A task whose folder still holds work after that keeps its row in the chain list, out of the archive, with the warning in its work chip's tip and "Done" on the row instead of in the head (BTN-332, `docs/web.md`). If `git sync` fails — likewise a warning with its output, the chain goes on, nothing is pushed by force: the next task takes the local `main`, and the next `git sync` after its Done will repeat the push. Since the landing (BTN-1581) a task with a remote reaches Done only once its merge is pushed, so this sync has nothing of the task's left to push: what it can still meet is work merged into `main` by hand.
- A `git sync` after Done that never reached a remote (a fetch, a push or the alias whose output says `Failed to connect`, `Could not resolve host`, `Connection timed out`/`reset`/`refused` and the like — `isNetworkFailure`, BTN-267) is tried twice more, 30 s and then 2 min later, before it becomes that warning; a refusal of the remote (`[rejected]` twice, permissions, a conflict) is the warning at once. The retries do not hold the chain: the cleanup returns at once and the next task starts, the dispatcher's tick (every 30 s) runs the try once it is due (`Cleanups.retrySyncs`). Each failed try is in the log; one that goes through is pushed as the cleanup's would have been (`MainCheck.pushed`). The retry lives in memory, one per project and machine: it goes to the machine whose cleanup failed to sync (`FinishOutcome.machine`, BTN-995), since its `main` holds the commits, and the next cleanup's own sync on that machine takes its place; after a restart the next Done pushes what it could not. A machine elsewhere that goes off the link mid-cleanup or mid-sync lets the hub go on at once (`RemoteMachine.lost`, `machine.lockLost`): that sync is a retry too, waiting without counting tries until the machine is back; a revoked machine's retry becomes the warning.
- Work left in a task's folder, whatever its status and however it left the chain (BTN-298; `shelved`, a task moved by hand, a dead session): `TaskWorks` (`src/git/work.ts`) reads each project's `git worktree list` and, for every worktree or slot on a branch `<task>/…` of one of the project's tasks (not the main checkout), `changesOf` against the project's `branch` — the files left out of a commit (`status --porcelain`, so not what git ignores, `.temp/`) and the commits main does not have. A project is read at most once a minute (a 15 s tick) and at once at the end of each cleanup after Done (`TaskWorks.refresh` from `finish`, after a read under way), so a removed folder does not linger. A task's work read before its session last did anything (`lastActivityAt` of any of its sessions) is kept out of the state — the session may have committed or merged it since, and a closed task would flash "not committed" — and its project is read again on the next tick once no session of the task is mid-turn; so the page only tells of work that is really left. The read runs in a folder whose session may be committing in it: every git call of Even Keel carries `--no-optional-locks` (`gitArgs`), so its `status` never takes `index.lock` and the session's `git add` is not refused meanwhile (BTN-697). A change is broadcast with the state (`EvenKeelState.works`, only the tasks with something), a failed read keeps the last answer and logs once. It is in memory only; the page shows it as in `docs/web.md`. The same read counts the lines each task's branch changed for the chat's foot (BTN-1424, `branchDiffOf` in `src/git/diff.ts`): `git diff --numstat` from `merge-base <branch> HEAD` to the working tree, so uncommitted edits count, plus the lines of untracked files git does not ignore (a binary, one over 4 MB or unreadable counts none); a folder with no work gets zeros without the diff. These are `EvenKeelState.diffs`, every task folder git could read, and they are not kept out when read before the session's last activity: a count up to a minute behind mid-turn, fresh again after the turn, rather than one that vanishes each turn.

- A parent closes by itself once all its subtasks are closed (adapters with `children`, `docs/trackers.md`); there is no cleanup in that case.
- **Released tasks** (skipped, postponed by a blocker, returned to an inactive status — Backlog in unattended mode — or the current task of a stopped chain): each tracker read asks for them by id (`tracker.tasks`) and gives the answer to `Dispatcher.setReleased` together with the ids it asked about. One in Done is cleaned up as above by the released-task sweep (`Cleanups.sweep`) once its session is not mid-turn; one cancelled or gone from the tracker is forgotten without a cleanup. Only the ids asked about are judged (BTN-766): the list is taken right after the read's task list goes to the chain and before the chain has followed it, so a task the chain releases while the answer is on its way is not in it and waits for the next read. Before that fix such a task counted as gone and was forgotten at once, and its branch outlived its Done. Seen on 2026-11-05: six question tasks of a slot project, each moved to Backlog by its unattended session in turn, kept their branches after the user closed them.

## "Slot" mode (`src/git/slot.ts`)

- `"slot": true` or a number of slots on a project — a pool of permanent worktrees per repository instead of a new one for each task: `.claude/worktrees/even-keel`, then `even-keel-2`, `even-keel-3`… (`true` — one). Ignored caches (Unity `Library`, `node_modules`) survive a task, and the first run of a new one processes only the difference; an extra slot is needed so that the live session of a released task (skipped, postponed by a blocker) stays in its own and is not stopped. The chain still leads one task at a time.
- Preparation: if a slot is already on the task's branch (`<key>-<number>/…`), it is used as is, even dirty. Otherwise, for each slot: a dirty one (`git status --porcelain` is not empty) or one with a session of another task mid-turn (`busy`/`waiting`, by the launch log, `src/sessions/occupants.ts`) is unfit. Of the fit ones, in order of preference: detached from a branch without foreign live sessions, on a foreign branch without them, not yet created (`git worktree add --detach <slot> main`), with idle sessions of other tasks — they get `claude stop` (the fifth exception to invariant 1); on a tie, the one with the lower number. If none is fit — a launch error, the chain is paused with the paths and reasons, and the slots are not touched. In unattended mode the chain is not paused: it stays running with `slotWait` (a yellow line with the same reasons on the page, one line in the service log) and tries the launch again at most every 30 s; the task is not released, since it never started. Then `git clean -fd` (without `-x`) and `git switch <branch>` or `git switch -c <branch> main`.
- After Done, a slot on the task's branch gets `git switch --detach main` (a dirty one stays on the branch, the branch is not deleted, a warning), then the branch, origin and `git sync`, as without a slot; the slot folder is not deleted. Slots on foreign branches (cleanup of a released task) are not touched, only the branch is deleted. `claude stop` after Done in a slot applies only to this task's sessions by the launch log.
- **Temporary files after Done** (BTN-1315, `cleanSlot` in `src/git/slot-clean.ts`). A slot keeps everything git ignores, and sessions' `.temp/` grew there to tens of GB. Once the slot has left the branch and the branch is dropped, `finishSlot` deletes the files matching the project's `slotCleanup.clean` (`.gitignore` syntax from the slot's root, default `[".temp/**"]`; `[]` turns it off) unless they match `slotCleanup.keep` (default `[]`; `!` is refused in both, `config.slotCleanup`; matcher in `src/git/patterns.ts`). Only what git reports ignored (`status --porcelain --ignored`, `!!`) is walked, so a tracked file is never touched: tracked files under a pattern warn `cleanup.slotTracked`. The ignored folders themselves stay, the subfolders emptied by the cleanup go. Links (junctions, symlinks) are removed as links, never entered. A file held by a process (Unity, a background run) is left with one warning `cleanup.slotTempLeft` with the count; the next Done in the slot takes it. The attachments cache `.temp/task-files/` is outside the patterns: the Done task's own folder is removed, open tasks' folders stay. One log line names the freed size (`cleanup: <task>: the slot <path> freed N MB of temporary files (k files)`). A dirty slot left on the branch, a released task (skipped, postponed) and a slot on a foreign branch get no cleanup. The start prompt of a task in a slot says what is deleted after Done (`slotTemp`).
- The number of slots changes on the fly (BTN-130); when it is reduced, Even Keel takes no new task into the extra folders, but still finds a busy task in one and cleans it after Done (`slotSpan` in `src/service/machine-chain.ts`: the most slots the project had since the start). A task's own worktree left over from the previous mode is taken and cleaned the old way.

## A project without git (BTN-883)

A project whose setting `git` is `false` (`isPlain`, `src/config.ts`) works in a folder that is no repository: for tasks that change no code — find something out and write it into the task. The mode is chosen when the project is added (the wizard's "Without git") and a project without git can turn git on later on the Repository tab (below, "Turning git on"); there is no way back.

- **The folder.** `projects[].repo` always holds a real path. A folder typed in the wizard is taken as it is, existing or not; a blank one becomes `ownFolder` (`src/projects/own-folder.ts`): `projects/<key in lowercase>-<first 8 characters of the id>` in Even Keel's data folder — a key is not unique and a bare id says nothing to a person. It is made when the project is added and again before every launch (`wirePlaces.place`: `mkdir`, the place is `{ path: repo, branch: null }`), and removing the project leaves it: the sessions' notes and the agent's memory, which is bound to the path, live there. The folder may lie inside a repository that is not the project's, so **nothing calls git in it**: no worktree, slot, branch, `catchUp`, `TaskWorks`, merge search, `git sync`, check of main, CI watch, remote profile or protection audit (`gitProjects` is what those readers go over). A few read-only readers that ask about any folder are left as they are (the badge's identity, the tools view, Copilot's remotes). One more reads the folder itself: the check whether it has become a repository (below, "The folder has become a repository"), whose single read-only `git rev-parse --show-toplevel` runs only once git starts and the folder has its own `.git`.
- **What is off.** The config reads such a project with no slots, no PR mode, no `mergeInto` (and it cannot be another project's target) and no guard of main, whatever its entry says; the settings panel shows the Repository tab as "Folder" (the mode, the path with a copy button, "Slots: not available") and "Check and CI" as one line. One session at a time works in the folder: before a launch the idle sessions released tasks left there are stopped, and one mid-turn holds the launch until its turn ends (the page names the wait "folder"; exception 5, `docs/chain/exceptions.md`, BTN-962).
- **Prompts.** `startPrompt` and `handoffPrompt` with `git = false` take the `plain` texts of `PROMPTS`: the folder line (shared by all the project's tasks, git off and refused — it does not say the folder is no repository, since it may be one) and the answer line in place of the worktree, branch and merge ones. A handoff does not `locate` the session's worktree. The handoff note is the task's own `.temp/handoff-<task>.md` (`noteFileOf`, BTN-964), since one `.temp/handoff.md` in the shared folder would be overwritten by the next task's; the nudges, the handoff prompt, the chat's `/handoff` and the mail name it (`docs/sessions/checkpoint.md`). In unattended mode the addition is `plain.unattended`, with nothing of git either (`docs/chain/unattended.md`).
- **Closing.** The session writes the whole result in the turn's last message and ends it with the last line `TASK DONE` (bare or `TASK DONE: <summary>`; `noChangesOf` reads it with the same markdown tolerance as `NO CHANGES:`). `Unchanged.follow` counts nothing in the folder: once the session is not `busy`, `UnchangedDeps.accept` puts the last message without its mark line (`withoutMark`; a message that was only the mark — its summary) on the task under `unchanged.answered`, then moves the task to Done. The comment is the answer, so it comes first and a failed one pauses the chain with `chain.unchangedNotCompleted`, the task staying current. The transcript keeps `MESSAGE_LIMIT` (30,000) characters of a last message, and one that long is commented with a note that it was cut; a handoff prompt still carries 6,000 (`HANDOFF_MESSAGE`). A turn that ends on a question is no answer: the task waits for the reply as in a git project, and "Accept as answer" closes a turn that forgot the mark.
- **A stop does not lose the mark** (BTN-1044). Nothing but the dispatcher closes such a task, so a stop must not leave a marked turn unread. "Stop after the turn" means "do not start the next task": once the turn has ended, the step still runs `Unchanged.follow` on the current task (`closesByMark`), a closed task goes through `closing` as usual, and only then the chain stops; a refused comment pauses the chain on the task with the flag kept, and "Resume" tries the same mark again (a failed close of such a task forgets its `tried`). A turn that ended on a question or without the mark closes nothing and the chain stops as before. After a plain "Stop" nothing reads the mark until the chain runs again; then, before a new launch of a task with no live session, `Unchanged.left` looks at the task's session as the monitor still lists it: if it is the one of the task's newest entry in the launch log (`lastSession`) and its last turn ended with the mark, the chain takes it as the current session (the log says `is not started again`) and closes the task by the mark instead of running it a second time — also after a service restart, since the monitor reads a finished session's transcript again. A message the user sent after the mark starts a new turn, which clears the mark in the summary: the last turn counts. A session the agent no longer lists cannot be read, and the task is launched anew.
- **Cleanup after Done** stops only the task's own sessions — those of the launch log, since every task's sessions share the folder (`stopTaskSessions` with `shared`) — and releases its packages. Nothing is removed and nothing is synced.
- **Agents.** `wireAgentExtras` sets `SessionStart.outsideRepo`; Codex then adds `--skip-git-repo-check` to `codex exec` (`docs/sessions/codex.md`) and writes its protection rules without asking git. A Claude session gets `worktree.bgIsolation: "none"` in its `--settings` (`chainSettings`, BTN-1181): from 2.1.306 the CLI refuses a `--bg` session's `Write`/`Edit` in a repository's checkout until it calls `EnterWorktree` (`docs/releases.md`), and a folder that is a repository or lies inside one has no worktree to enter. The key goes to the SDK sessions' settings too; nothing is written into the folder's `.claude/settings.json`, and the environment's `CLAUDE_BG_ISOLATION` would not do, frozen at the daemon's start.
- **Git is forbidden to the session** (BTN-1052). The prompt's folder line says git is off and a call will be refused, and it is: the folder may hold a `.git` (an existing repository added "Without git") or lie inside a repository that is not the project's. Every agent gets native deny rules on git itself and the `agent-bridge` hook refuses what they miss (`docs/sessions/protection.md`, "Git off"). The ban follows the setting `git`, not Protection: the page has no switch for it, a project with git has none of it, and it applies from a session's next launch (`gitSwitchBlock` already refuses turning git on under a live session). Even Keel's own git (`turnGitOn`, the worktrees it makes afterwards) and the branch the CLI writes into a transcript are not touched.
- **Setup.** The first run's Git step can be skipped while git is not ready (`gitHeld` in `Setup.tsx`), and the wizard's check of a folder without git never asks git, so a machine without git can add and run such a project. The commit of a changelog draft refuses it with `branch.noRepo`.

Not checked live: `docs/unverified/sessions.md`, "A project without git".

### Turning git on (BTN-884)

The command `project/git` `{ project, on: true, slot?, commit?, branch? }` (`settings.turnGitOn` in `src/service/hosting.ts`, `src/projects/git-mode.ts`) turns the setting `git` of a project already added on. Git is never turned off (BTN-1063: the turn back, added for symmetry, gave most of the bugs of its live check): `on: false` — from a tab open since before, or a hand call — is refused with `project.gitStaysOn` before anything is read, and nothing changes. A project whose entry already says `git: false` — written by an older version, or by `config-import`, which takes it as it is — is simply a project without git with "Turn on git". The switch runs only between tasks: `gitSwitchBlock` refuses with `project.gitBusy` while the chain holds a task of the project (`project.gitTaskInHand`), a live session works in its folders or a worktree or slot is held (the same `removalFacts` as removal); a running chain with no task in hand does not block. The page greys the button by the same facts it can see (`gitSwitchBusy` in `web/src/pages/`), the tip saying why.

- **The switch.** `turnGitOn` needs the folder to exist and the project's `branch` to be a valid name. A folder that is the top of a repository with commits is checked for the branch (`requireBranch`, as the wizard does) and gets Even Keel's folders and its Codex rules file in `info/exclude` (the rules written while git was off forbid git: committed, they would reach every worktree and clone, EKR-107); work left uncommitted in it while git was off (BTN-1054: `git status` past the excluded folders, read at the press) also needs the branch checked out (`git.wrongBranch` otherwise) and goes into one commit `Work done without git` (`add -A`, refused with `git.noIdentity` without a name and e-mail) only with `commit`; without it the switch is refused with `project.gitDirty`, which carries the fresh list of changes, and nothing is saved. Otherwise — a plain folder, one inside another repository, or a repository with no commit — it gets `git init -b <branch>` (or `HEAD` pointed at the branch), the exclude entries and a first commit `Initial commit` of everything in it (`--allow-empty`), refused with `git.noIdentity` without a name and e-mail and with `git.initFailed` when git refuses. Then `withProjectForm` saves the mode (on is the default, so it removes an explicit `git: false`) and the chosen `slot` (0 — a worktree per task, N — N slots), over whatever slot count the entry carried. The next task runs as a git project; nothing already closed is touched.
- **Page.** The Repository tab of a project without git has a card "History of changes" with "Turn on git"; its dialog shows the setup's Git step parts (`GitInstall`, `Identity` from `SetupGit.tsx`) and the wizard's choice of tasks' folders. For a repository with commits it first asks the query `project/git/changes` (`uncommittedChanges`): changes there add a card "Changes outside the history" listing the first 20 as `M file`, `?? dir/`, `R old → new` with "and N more", and the checkbox "Commit them in one commit" (ticked by default) that sends `commit`; a `project.gitDirty` refusal replaces the list with the one it carries. The button is greyed with a tip explaining the first blocking reason: busy project, git being checked or missing, missing name or e-mail, invalid slot count. Sending locks the button against another press. A refusal stays outside the scrolling body, above the action buttons. A git project's tab has no git card.
- **The folder has become a repository** (BTN-1025). Git does not turn itself on: a folder made a repository (by hand, or by an agent before BTN-1052 refused it git) stays a project without git. `GitFound` (`src/projects/git-found.ts`) checks each project without git at the start, once git's own read (`gitSetup`) is in, and after each Done cleanup of its task (`finish` in `src/service/machine-chain.ts`) — never on a timer. `foundRepository` goes step by step, each only when the one before holds: git starts on the machine (`state.git.version !== null`, no `git --version` of its own), the folder has a `.git` (`stat`, no git), and `git rev-parse --show-toplevel` names the folder itself (`samePath`) — the one git call, read-only; not `git status`, which walks the tree and may rewrite the index. An empty or broken `.git` and a folder without its own `.git` inside another repository fail the last step. A found repository is `EvenKeelState.gitFound[project]`: the branch `HEAD` names (read from the file; `null` for a detached `HEAD` or a `.git` file) and `since`, the `.git`'s birth time (its change time where the file system keeps none). The project page shows the band `git.found` with "Turn on git" (`noticeFixOf` → `gitOn`, the same dialog) and "Not now" — a "Got it" mark (`notices/dismiss`, `git.found@<project>`) stamped with `since`, so a repository removed and made anew asks again. A repository on a branch other than the project's (an agent's `git init` gives `master`) would refuse the switch with `git.noBranch`: the dialog then offers, ticked, to make that branch the project's main branch, and `project/git` takes `branch`, checks the switch against it and saves it with the mode.

Turning git on and restart persistence for an existing repository were checked on the installed service (BTN-1026, [verified log](../verified/sessions.md)). Initializing a plain folder, the next worktree task, the refusal to turn git off and a repository found after a Done and turned on with its own branch are covered by `src/e2e/plain.test.ts`; the remaining real-agent checks are in `docs/unverified/sessions.md`, "Turning git on" and "The folder has become a repository".
