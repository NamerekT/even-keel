# Chain: task worktrees, slots and cleanup

## Task worktree (`src/git/worktree.ts`)

`main` in this document is the project's main branch: its `branch` key (BTN-117), `main` without it. Every git call takes it from the current config, so a change applies without a restart. A branch the repository lacks pauses the launch with `git.noBranch`, naming the branch and the project. At the launch (not in the preparation ahead, while the chain waits for the CI) the main checkout must also stand on that branch (`git symbolic-ref --short HEAD`): on another branch or a detached HEAD the launch pauses with `git.wrongBranch`, since the merge, `git sync` and the search for the merged task all work on the project's branch.

- Before the first launch for a task — in the project's main checkout (`config.projects[project]`) `git worktree add -b <key>-<number>/task .claude/worktrees/<key>-<number> main`, all lowercase. The branch tail is always `task`: the hooks in `~/.githooks` need the form `<key>-<number>/<something>`.
- Before that, at every launch (not for a place made ahead), the main checkout's `main` is fast-forwarded to `<remote>/main` of each remote (`fastForwardMain`, `src/git/sync.ts`, BTN-210): another clone of the same remote may have pushed since this one's last `git sync`. Only when the checkout is on `main` without changes to tracked files; a `main` ahead or diverged, a fetch that fails — left as it is, silently. A place made ahead then comes up to the new `main` by `catchUp`, as after a fix.
- If a worktree already exists at that path, it is taken as is, with its branch; if only the branch exists, it is brought back into a new worktree. `.claude/worktrees/` and `.temp/` (a session's scratch, the pull request's description among it, BTN-221) are appended to `.git/info/exclude` if git does not ignore them.
- The session starts with `cwd` = the worktree, and the prompt is the task ID, a line about the ready worktree and that there is no need to clean up (`startPrompt`).
- Commands before start (BTN-97, `commands.beforeStart` of the project, `src/sessions/setup.ts`): after the worktree or slot is ready and before the session starts, each runs in order through the system shell in the task's folder, with the session's environment: that of the account the task runs on (`choiceFor(project, task).account`), through its agent's `envOf` — a Codex task gets Codex's, so a Codex-only install with no `~/.claude` runs them too (EKR-26) — and the service's own, keys removed as in `sessionBase`, while that account has no folder (`accountEnv`); `check` and `afterGreen` run the same way, `afterGreen` on the project's account. 20 min at most. Their output goes to the service log line by line (`setup: <task>: | …`); a non-zero exit stops the rest, the session is not started and the chain pauses with `setup.failed` and the last 40 lines of output. They run on every new launch of a task (a task the chain takes again runs them again), but not on `--resume`, a reply or a handoff.

## Cleanup after Done

The stop, deferred-stop and retry wiring is in `src/service/cleanup.ts`, re-exported by `src/service/chain.ts`. Rare mid-turn deferrals and their stop results use the `rare: 17c` diagnostics described in [unverified sessions](../unverified/sessions.md#a-session-left-mid-turn-by-the-cleanup-btn-616).

- A merged task is closed into the tracker's first done status, or into the one its source chose (BTN-554, `doneMove`; "Status moves" below). A chosen status the chain rules do not take for done is not tried: the task stays open with `statusMove.notDone` until the setting changes.
- Any merge of the task's branch into `main` closes it, a half of the work merged mid-task too: the close does not wait for the turn to end, only the cleanup does. A task the user takes back from Done is closed again only by a new merge (BTN-219, BTN-689): `MergeCloser` keeps the own commits of its branches `main` had at the close (`mergedCommits`, the newest of each branch, in `src/git/merged.ts`) in `MergeMarks` (`src/tracker/closes.ts`, the state table `merge_closes`, through a restart), and a reopened task whose merged commits are all in that mark stays open, so a checkpoint handover on a branch merged before the reopen goes on in the new session. A branch that only caught up with `main` adds no commit of its own; a branch removed by the cleanup and made anew has new ones. A task closed before this mark existed has none, so its first close after a reopen still goes by the old rule. Only a merge seen while the chain holds the reopened task closes it (BTN-694): while it is open and not held (neither the current task with a session nor a released one awaiting cleanup, `Dispatcher.held`), every tracker read adds its newly merged commits to the mark without closing it, so a session that merged again outside the chain does not close it the moment the chain takes it back. A hand session that finishes such a task outside the chain closes it itself.
- If the tracker refuses to close a merged task, `MergeCloser` keeps a `tracker.completeRefused` notice for that reader and task in `TrackerView.completionFailures` (memory only). The page shows the tracker response and a link to the task, asks for the required field to be filled or the task to be closed by hand, and suppresses a false reply prompt in the header, lamp and session panel; a real question or permission remains visible. The task stays current and the normal 30 s full read retries the close. Success clears the notice; a task no longer held drops its refusal, and the page also hides one as soon as polling sees a closed status. Git inspection errors remain separate from tracker refusals.

- The current task went to Done (category `Won`; a cancelled or dropped one does not) — the chain's `closing`: wait until its session is not mid-turn (`busy`/`waiting`; a session in `shell` does not hold a done task — see "Background command" below), then `claude stop` its sessions in this worktree (otherwise a live process holds the folder: a `--bg` session does not exit after a turn, `claude agents` shows it `done`/`idle`), then in the clean worktree remove links and junctions in ignored folders (`node_modules` of npm workspaces, `npm link`: git on Windows follows them — it cleans someone else's folder or stumbles on a dangling one and abandons the worktree), then `git worktree remove` (without `--force`; every git call of Even Keel on Windows carries `-c core.longpaths=true`, and a folder git unregistered but left for another reason than a lock — `Filename too long` — is deleted from Node, BTN-559; only a lock is `cleanup.folderLeft`, the rest `cleanup.folderNotDeleted`), `git branch -d` of the task branch (only `<key>-<number>/…`), `git push origin --delete` if it is on origin, and `git sync` if the project has a remote. The next task is started after that. A task returned from Done before the cleanup — no cleanup, the task is back in the chain.
- **The first read of the sessions** (BTN-646). After the service's start the dispatcher does nothing — no cleanup, launch, handoff, review, fix or slot switch — until the monitor has finished its first full tick (`DispatcherDeps.sessionsRead`, the service's `agentsRead`, set with the first `onChange`): before it `busy` is unknown rather than false and the cleanup's `stopTaskSessions` sees no session at all, so a Done right after a restart removed the worktree past its live session and left the folder held (`cleanup.folderLeft`; BTN-537, BTN-587, BTN-642). The forward merges (`chainQuiet`) and the account watcher (`sessionsKnown`) wait for the same flag.
- **A session left mid-turn** (BTN-616). The cleanup waits only for the task's own session (`busy` by its view); another session in the task's folder, or one whose status the view and the listing disagree on, may still be `busy`/`waiting` when `stopTaskSessions` runs. Such a session is not stopped then but kept in `Lingering` (`src/sessions/lingering.ts`, the service's memory) and stopped on the first monitor tick after its turn ends (`stopLingering`, from `onAgents`, since a session without a view of its task changes no view); once gone by itself it is forgotten. Otherwise nothing stopped it after its task left the chain, and a Codex session, which has no process between turns, rested on the page as `waiting` for good. A restart before its turn ends forgets it.
- **A stop that timed out** (EKR-99). A Claude `--bg` stop first lists the folder's sessions (`claude agents`), and that call waits in the account folder's queue (`FolderCalls`, EKR-15): right after the service's start `/usage` and the `/context` probes fill it, and a call whose timeout passes while it waits never starts. Since EKR-102 that listing goes ahead of the waiting calls and is tried again for up to 5 minutes (`QueueWait`, `docs/accounts.md`), so this is rare. Such a `CallTimeout` (`isCallTimeout`, through wrapping causes) is no failure of the stop: `stopTaskSessions` keeps the session in `Lingering` with a retry (`STOP_RETRY_MS`, 5 min), and the worktree folder git unregistered but left because that session's process holds it (`cleanup.folderLeft`, Windows) is left to it too (`deferLeftFolder`), so neither goes into `leftovers`. `stopLingering` tries the stop again on each monitor tick, one run at a time (`Lingering.alone`), then removes the folder (`removeLeftFolder`; a folder registered as a worktree again meanwhile is not touched). Only a stop still timing out once the wait is over, or failing otherwise, is `cleanup.sessionNotStopped`, and a folder still held `cleanup.folderLeft` — added to the task's leftovers then (`Dispatcher.leftover`). A stop that fails for any other reason warns at once, as before. A slot is not removed, so only its session is retried. A restart forgets the session's retries, as it forgets a session left mid-turn; the left folder it keeps (BTN-925, below).
- **A folder still held after a stop that went through** (BTN-870). A stopped process lets go of its folder a moment after it exits on Windows, and a child of it (a Codex `codex exec` turn's shell) later still: under load the cleanup's `git worktree remove` comes first and the folder is left (`cleanup.folderLeft`). So every such folder of a Done cleanup goes to `deferLeftFolder`, not only one of a timed-out stop: `stopLingering` tries it again on each monitor tick while no kept session of the task is left, and warns only if it is still held once `STOP_RETRY_MS` has passed. Seen in the real-CLI scenarios with the three files at once (`docs/chain/e2e.md`, "Real CLIs"). A left folder outlives a restart (BTN-925): in a project with `commands.afterGreen` the service restarts about a minute after nearly every Done, so a folder kept only in memory was forgotten almost always. `Lingering.leave` saves it into the state table `left_folders` (`docs/storage.md`) and the row goes once the folder is removed or warned about; at the start the service reads them back (`Lingering.restore`) and `stopLingering` takes them up only after the monitor's first read of the sessions (`agentsRead`, BTN-646). The wait is `until`, counted from the Done, not from the start: a wait that ran out while the service was down gets one try at once and, still held, the same `cleanup.folderLeft` warning on the task. A session kept with the folder is not saved, so after a restart its folder is tried at once rather than after the session's stop.
- **Nothing to merge** (EKR-10), out of PR mode. A task that needs no change in the repository (done in main already, research, an answer) never closes by a merge: `branchMerged` takes a branch with no commits of its own for unmerged, or every branch that only caught up with main would close its task. The prompt's `cleanup` tells such a session to end its turn with the last line `NO CHANGES: <why>` (`noChangesOf` in `src/sessions/transcript.ts`, Codex's rollout too; a tool call or a new prompt drops it, as `CHECKPOINT:`). `Unchanged.follow` (`src/chain/unchanged.ts`), once the session is not `busy` (a session in `shell` does not hold it, BTN-637 — see "Background command" below), counts the commits of its folder beyond the local main and reads `git status` with untracked files (`changesOf`, `src/git/changes.ts`; ignored `.temp/` is not work). Nothing — `UnchangedDeps.complete` moves the task to Done in the tracker and comments the reason (`unchanged.comment` of the prompts; a comment that fails is only logged), the tracker is read at once and the chain's own Done cleans up — exception 4, `git branch -d`, the next task. A tracker that refuses pauses the chain with `chain.unchangedNotCompleted`, a git that cannot count with `chain.unchangedNotChecked`, the task staying current. Commits or uncommitted changes — the session gets `unchanged.ahead` or `unchanged.dirty` by `--resume` whatever its cache, as a chat answer does (merge them, or drop them and mark again). A mark acted on has its `lastReplyAt` remembered in the service's memory, so only a new turn tries it again. In PR mode the mark is ignored: `PULL REQUEST:` covers the case (BTN-222). The last line `TASK DONE` of a project without git (below) is read by the same `noChangesOf`, so in a git project it acts as `NO CHANGES:`.
- **Accept as answer** (BTN-885). A session that answered but forgot the mark (Codex most often) leaves its task waiting with no way to close it short of asking for the mark and waiting a turn. The session panel and the chat then offer "Accept as answer" (`offersAccept`, `web/src/pages/acceptAnswer.ts`): the current task's session ended its turn on a message — not mid-turn, no question, permission or startup dialog, no error, limit or checkpoint mark — the task is no fix or carry, has no pull request under review, is not merged with its close refused, and `TaskWorks` knows no work in its folder. The press (`chain/accept` with the session id the page saw) goes through `Dispatcher.accept`: `acceptable` (`src/chain/answers.ts`) refuses a task that is not current (`chain.notCurrent`), launching, a session moved on since the page read it (`answer.moved`), mid-turn or in a background command (`chain.midTurn`), waiting on an `AskUserQuestion` (`accept.asking`), with no last message (`accept.noMessage`), or done already in the last read (`accept.closed`, so a second press does not comment twice). Then, in the dispatcher's turn, `Unchanged.accept` counts the folder as for the mark: commits beyond main refuse with `accept.ahead` (such work closes by a merge, and the close would lose it), uncommitted files with `accept.dirty`, a git that cannot count with `accept.notChecked`. Clean — `UnchangedDeps.accept` puts the session's last message whole (as the transcript keeps it, `MESSAGE_LIMIT` — 30,000 characters at most since BTN-883) on the task under `unchanged.accepted`, then moves it to Done; the comment comes first and a failed one refuses (`accept.notCompleted`), since it is the answer. The tracker is read at once and the chain's own Done cleans up — exception 4 again. Every refusal goes back to the page and leaves the chain as it is, unpaused.
- `git sync` is the `main` synchronization (`src/git/sync.ts`): if the repository has an `alias.sync` (`--local`), that one; the user's global alias only when the branch is named `main`, since such an alias is written for `main`; if not, Even Keel does it itself: the main checkout must stand on `main`, for each remote `git fetch` and `git merge --no-edit <remote>/main` (if it does not merge cleanly — `merge --abort` and an error), then `git push <remote> main` to each. A push rejected as `[rejected]` (another clone pushed between the fetch and the push, BTN-210) or as `[remote rejected]` with a refused ref update — `incorrect old value`, `failed to update ref`, `cannot lock ref`, `failed to lock`, `stale info` (the other push landed inside this one, after it read the remote's refs, BTN-686) — gets the whole sync once more, the alias's as well; a second rejection is the error. Any other `[remote rejected]`, a declined server hook among them, is the error at once.
- A dirty worktree, a folder held by a process, an unmerged branch — a warning in the log and on the project page (`leftovers` in `state/chain.json`, the "Done" button — `chain/dismiss`), and the chain goes on. A task whose folder still holds work after that keeps its row in the chain list, out of the archive, with the warning in its work chip's tip and "Done" on the row instead of in the head (BTN-332, `docs/web.md`). If `git sync` fails — likewise a warning with its output, the chain goes on, nothing is pushed by force: the next task takes the local `main`, and the next `git sync` after its Done will repeat the push.
- A `git sync` after Done that never reached a remote (a fetch, a push or the alias whose output says `Failed to connect`, `Could not resolve host`, `Connection timed out`/`reset`/`refused` and the like — `isNetworkFailure`, BTN-267) is tried twice more, 30 s and then 2 min later, before it becomes that warning; a refusal of the remote (`[rejected]` twice, permissions, a conflict) is the warning at once. The retries do not hold the chain: the cleanup returns at once and the next task starts, the dispatcher's tick (every 30 s) runs the try once it is due (`Cleanups.retrySyncs`). Each failed try is in the log; one that goes through is pushed as the cleanup's would have been (`MainCheck.pushed`). The retry lives in memory, one per project: the next cleanup's own sync takes its place, and after a restart the next Done pushes what it could not.
- Work left in a task's folder, whatever its status and however it left the chain (BTN-298; `shelved`, a task moved by hand, a dead session): `TaskWorks` (`src/git/work.ts`) reads each project's `git worktree list` and, for every worktree or slot on a branch `<task>/…` of one of the project's tasks (not the main checkout), `changesOf` against the project's `branch` — the files left out of a commit (`status --porcelain`, so not what git ignores, `.temp/`) and the commits main does not have. A project is read at most once a minute (a 15 s tick) and at once at the end of each cleanup after Done (`TaskWorks.refresh` from `finish`, after a read under way), so a removed folder does not linger. A task's work read before its session last did anything (`lastActivityAt` of any of its sessions) is kept out of the state — the session may have committed or merged it since, and a closed task would flash "not committed" — and its project is read again on the next tick once no session of the task is mid-turn; so the page only tells of work that is really left. The read runs in a folder whose session may be committing in it: every git call of Even Keel carries `--no-optional-locks` (`gitArgs`), so its `status` never takes `index.lock` and the session's `git add` is not refused meanwhile (BTN-697). A change is broadcast with the state (`EvenKeelState.works`, only the tasks with something), a failed read keeps the last answer and logs once. It is in memory only; the page shows it as in `docs/web.md`.

- A parent closes by itself once all its subtasks are closed (adapters with `children`, `docs/trackers.md`); there is no cleanup in that case.
- **Released tasks** (skipped, postponed by a blocker, returned to an inactive status — Backlog in unattended mode — or the current task of a stopped chain): each tracker read asks for them by id (`tracker.tasks`) and gives the answer to `Dispatcher.setReleased` together with the ids it asked about. One in Done is cleaned up as above by the released-task sweep (`Cleanups.sweep`) once its session is not mid-turn; one cancelled or gone from the tracker is forgotten without a cleanup. Only the ids asked about are judged (BTN-766): the list is taken right after the read's task list goes to the chain and before the chain has followed it, so a task the chain releases while the answer is on its way is not in it and waits for the next read. Before that fix such a task counted as gone and was forgotten at once, and its branch outlived its Done. Seen on 2026-11-05: six question tasks of a slot project, each moved to Backlog by its unattended session in turn, kept their branches after the user closed them.

## "Slot" mode (`src/git/slot.ts`)

- `"slot": true` or a number of slots on a project — a pool of permanent worktrees per repository instead of a new one for each task: `.claude/worktrees/even-keel`, then `even-keel-2`, `even-keel-3`… (`true` — one). Ignored caches (Unity `Library`, `node_modules`) survive a task, and the first run of a new one processes only the difference; an extra slot is needed so that the live session of a released task (skipped, postponed by a blocker) stays in its own and is not stopped. The chain still leads one task at a time.
- Preparation: if a slot is already on the task's branch (`<key>-<number>/…`), it is used as is, even dirty. Otherwise, for each slot: a dirty one (`git status --porcelain` is not empty) or one with a session of another task mid-turn (`busy`/`waiting`, by the launch log, `src/sessions/occupants.ts`) is unfit. Of the fit ones, in order of preference: detached from a branch without foreign live sessions, on a foreign branch without them, not yet created (`git worktree add --detach <slot> main`), with idle sessions of other tasks — they get `claude stop` (the fifth exception to invariant 1); on a tie, the one with the lower number. If none is fit — a launch error, the chain is paused with the paths and reasons, and the slots are not touched. In unattended mode the chain is not paused: it stays running with `slotWait` (a yellow line with the same reasons on the page, one line in the service log) and tries the launch again at most every 30 s; the task is not released, since it never started. Then `git clean -fd` (without `-x`) and `git switch <branch>` or `git switch -c <branch> main`.
- After Done, a slot on the task's branch gets `git switch --detach main` (a dirty one stays on the branch, the branch is not deleted, a warning), then the branch, origin and `git sync`, as without a slot; the slot folder is not deleted. Slots on foreign branches (cleanup of a released task) are not touched, only the branch is deleted. `claude stop` after Done in a slot applies only to this task's sessions by the launch log.
- The number of slots changes on the fly (BTN-130); when it is reduced, Even Keel takes no new task into the extra folders, but still finds a busy task in one and cleans it after Done (`slotSpan` in `src/service.ts`: the most slots the project had since the start). A task's own worktree left over from the previous mode is taken and cleaned the old way.

## A project without git (BTN-883)

A project whose setting `git` is `false` (`isPlain`, `src/config.ts`) works in a folder that is no repository: for tasks that change no code — find something out and write it into the task. The mode is chosen when the project is added (the wizard's "Without git") and a project without git can turn git on later on the Repository tab (below, "Turning git on"); there is no way back.

- **The folder.** `projects[].repo` always holds a real path. A folder typed in the wizard is taken as it is, existing or not; a blank one becomes `ownFolder` (`src/projects/own-folder.ts`): `projects/<key in lowercase>-<first 8 characters of the id>` in Even Keel's data folder — a key is not unique and a bare id says nothing to a person. It is made when the project is added and again before every launch (`wirePlaces.place`: `mkdir`, the place is `{ path: repo, branch: null }`), and removing the project leaves it: the sessions' notes and the agent's memory, which is bound to the path, live there. The folder may lie inside a repository that is not the project's, so **nothing calls git in it**: no worktree, slot, branch, `catchUp`, `TaskWorks`, merge search, `git sync`, check of main, CI watch, remote profile or protection audit (`gitProjects` is what those readers go over). A few read-only readers that ask about any folder are left as they are (the badge's identity, the tools view, Copilot's remotes).
- **What is off.** The config reads such a project with no slots, no PR mode, no `mergeInto` (and it cannot be another project's target) and no guard of main, whatever its entry says; the settings panel shows the Repository tab as "Folder" (the mode, the path with a copy button, "Slots: not available") and "Check and CI" as one line. One session at a time works in the folder: before a launch the idle sessions released tasks left there are stopped, and one mid-turn holds the launch until its turn ends (the page names the wait "folder"; exception 5, `docs/chain/exceptions.md`, BTN-962).
- **Prompts.** `startPrompt` and `handoffPrompt` with `git = false` take the `plain` texts of `PROMPTS`: the folder line (shared by all the project's tasks, no git) and the answer line in place of the worktree, branch and merge ones. A handoff does not `locate` the session's worktree. The handoff note is the task's own `.temp/handoff-<task>.md` (`noteFileOf`, BTN-964), since one `.temp/handoff.md` in the shared folder would be overwritten by the next task's; the nudges, the handoff prompt, the chat's `/handoff` and the mail name it (`docs/sessions/checkpoint.md`). In unattended mode the addition is `plain.unattended`, with nothing of git either (`docs/chain/unattended.md`).
- **Closing.** The session writes the whole result in the turn's last message and ends it with the last line `TASK DONE` (bare or `TASK DONE: <summary>`; `noChangesOf` reads it with the same markdown tolerance as `NO CHANGES:`). `Unchanged.follow` counts nothing in the folder: once the session is not `busy`, `UnchangedDeps.accept` puts the last message without its mark line (`withoutMark`; a message that was only the mark — its summary) on the task under `unchanged.answered`, then moves the task to Done. The comment is the answer, so it comes first and a failed one pauses the chain with `chain.unchangedNotCompleted`, the task staying current. The transcript keeps `MESSAGE_LIMIT` (30,000) characters of a last message, and one that long is commented with a note that it was cut; a handoff prompt still carries 6,000 (`HANDOFF_MESSAGE`). A turn that ends on a question is no answer: the task waits for the reply as in a git project, and "Accept as answer" closes a turn that forgot the mark.
- **A stop does not lose the mark** (BTN-1044). Nothing but the dispatcher closes such a task, so a stop must not leave a marked turn unread. "Stop after the turn" means "do not start the next task": once the turn has ended, the step still runs `Unchanged.follow` on the current task (`closesByMark`), a closed task goes through `closing` as usual, and only then the chain stops; a refused comment pauses the chain on the task with the flag kept, and "Resume" tries the same mark again (a failed close of such a task forgets its `tried`). A turn that ended on a question or without the mark closes nothing and the chain stops as before. After a plain "Stop" nothing reads the mark until the chain runs again; then, before a new launch of a task with no live session, `Unchanged.left` looks at the task's session as the monitor still lists it: if it is the one of the task's newest entry in the launch log (`lastSession`) and its last turn ended with the mark, the chain takes it as the current session (the log says `is not started again`) and closes the task by the mark instead of running it a second time — also after a service restart, since the monitor reads a finished session's transcript again. A message the user sent after the mark starts a new turn, which clears the mark in the summary: the last turn counts. A session the agent no longer lists cannot be read, and the task is launched anew.
- **Cleanup after Done** stops only the task's own sessions — those of the launch log, since every task's sessions share the folder (`stopTaskSessions` with `shared`) — and releases its packages. Nothing is removed and nothing is synced.
- **Agents.** `wireAgentExtras` sets `SessionStart.outsideRepo`; Codex then adds `--skip-git-repo-check` to `codex exec` (`docs/sessions/codex.md`) and writes its protection rules without asking git. The other agents get nothing special.
- **Setup.** The first run's Git step can be skipped while git is not ready (`gitHeld` in `Setup.tsx`), and the wizard's check of a folder without git never asks git, so a machine without git can add and run such a project. The commit of a changelog draft refuses it with `branch.noRepo`.

Not checked live: `docs/unverified/sessions.md`, "A project without git".

### Turning git on (BTN-884)

The command `project/git` `{ project, on: true, slot?, commit? }` (`settings.turnGitOn` in `src/service/hosting.ts`, `src/projects/git-mode.ts`) turns the setting `git` of a project already added on. Git is never turned off (BTN-1063: the turn back, added for symmetry, gave most of the bugs of its live check): `on: false` — from a tab open since before, or a hand call — is refused with `project.gitStaysOn` before anything is read, and nothing changes. A project whose entry already says `git: false` — written by an older version, or by `config-import`, which takes it as it is — is simply a project without git with "Turn on git". The switch runs only between tasks: `gitSwitchBlock` refuses with `project.gitBusy` while the chain holds a task of the project (`project.gitTaskInHand`), a live session works in its folders or a worktree or slot is held (the same `removalFacts` as removal); a running chain with no task in hand does not block. The page greys the button by the same facts it can see (`gitSwitchBusy` in `web/src/pages/`), the tip saying why.

- **The switch.** `turnGitOn` needs the folder to exist and the project's `branch` to be a valid name. A folder that is the top of a repository with commits is checked for the branch (`requireBranch`, as the wizard does) and gets Even Keel's folders in `info/exclude`; work left uncommitted in it while git was off (BTN-1054: `git status` past the excluded folders, read at the press) also needs the branch checked out (`git.wrongBranch` otherwise) and goes into one commit `Work done without git` (`add -A`, refused with `git.noIdentity` without a name and e-mail) only with `commit`; without it the switch is refused with `project.gitDirty`, which carries the fresh list of changes, and nothing is saved. Otherwise — a plain folder, one inside another repository, or a repository with no commit — it gets `git init -b <branch>` (or `HEAD` pointed at the branch), the exclude entries and a first commit `Initial commit` of everything in it (`--allow-empty`), refused with `git.noIdentity` without a name and e-mail and with `git.initFailed` when git refuses. Then `withProjectForm` saves the mode (on is the default, so it removes an explicit `git: false`) and the chosen `slot` (0 — a worktree per task, N — N slots), over whatever slot count the entry carried. The next task runs as a git project; nothing already closed is touched.
- **Page.** The Repository tab of a project without git has a card "History of changes" with "Turn on git"; its dialog shows the setup's Git step parts (`GitInstall`, `Identity` from `SetupGit.tsx`) and the wizard's choice of tasks' folders. For a repository with commits it first asks the query `project/git/changes` (`uncommittedChanges`): changes there add a card "Changes outside the history" listing the first 20 as `M file`, `?? dir/`, `R old → new` with "and N more", and the checkbox "Commit them in one commit" (ticked by default) that sends `commit`; a `project.gitDirty` refusal replaces the list with the one it carries. The button is greyed with a tip explaining the first blocking reason: busy project, git being checked or missing, missing name or e-mail, invalid slot count. Sending locks the button against another press. A refusal stays outside the scrolling body, above the action buttons. A git project's tab has no git card.
