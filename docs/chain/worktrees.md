# Chain: task worktrees and slots

Cleanup after Done is in [`cleanup.md`](cleanup.md), a project without git in [`no-git.md`](no-git.md). `main` here is the project's main branch ([words of the area](../chain.md#words-of-the-area)).

## Task worktree (`src/git/worktree.ts`)

Every git call takes the main branch from the current config, so a change of `branch` (BTN-117) applies without a restart. A launch goes in this order:

- **The branch checks.** A branch the repository lacks pauses the launch with `git.noBranch`, naming the branch and the project. At the launch (not in the preparation ahead, while the chain waits for the CI) the main checkout must also stand on that branch (`git symbolic-ref --short HEAD`): on another branch or a detached HEAD the launch pauses with `git.wrongBranch`, since the merge, `git sync` and the search for the merged task all work on the project's branch.
- **The fast-forward of `main`** (`fastForwardMain`, `src/git/sync.ts`, BTN-210), at every launch but not for a place made ahead: the main checkout's `main` goes to `<remote>/main` of each remote, since another clone of the same remote may have pushed since this one's last `git sync`. Only when the checkout is on `main` without changes to tracked files; a `main` ahead or diverged, a fetch that fails — left as it is, silently. A place made ahead then comes up to the new `main` by `catchUp`, as after a fix.
- **The worktree.** Before the first launch for a task, in the project's main checkout (`config.projects[project]`): `git worktree add -b <key>-<number>/task .claude/worktrees/<key>-<number> main`, all lowercase. The branch tail is always `task`: the hooks in `~/.githooks` need the form `<key>-<number>/<something>`. A worktree already at that path is taken as is, with its branch; if only the branch exists, it is brought back into a new worktree.
- **Excludes.** `.claude/worktrees/`, `.temp/` (a session's scratch, the pull request's description among it, BTN-221) and `/.codex/rules/even-keel.generated.rules` (the Codex deny rules, EKR-107) are appended to `.git/info/exclude` if git's patterns do not ignore them (`check-ignore --no-index`, so a file already committed does not add the line again).
- **Commands before start** (BTN-97, `commands.beforeStart`, `src/sessions/setup.ts`): once the worktree or slot is ready, each runs in order through the system shell in the task's folder, 20 min at most.
  - The environment is the session's: that of the account the task runs on (`choiceFor(project, task).account`), through its agent's `envOf` — a Codex task gets Codex's, so a Codex-only install with no `~/.claude` runs them too (EKR-26) — and the service's own, keys removed as in `sessionBase`, while that account has no folder (`accountEnv`). `check` and `afterGreen` run the same way, `afterGreen` on the project's account.
  - The output goes to the service log line by line (`setup: <task>: | …`); a non-zero exit stops the rest, the session is not started and the chain pauses with `setup.failed` and the last 40 lines of output.
  - They run on every new launch of a task (a task the chain takes again runs them again), but not on `--resume`, a reply or a handoff.
- **The session** starts with `cwd` = the worktree, and the prompt is the task ID, a line about the ready worktree and that there is no need to clean up (`startPrompt`).

## Task branches on the remote (BTN-1270)

A task's branch goes to the remote whatever the project's mode, so another machine can take the task over when its machine is gone ([machines](../machines/landings.md#a-machine-gone)). Sessions never push it; Even Keel does, on the machine that runs the task (`pushTaskBranch`, `src/git/push.ts`, through `pushOf` in `src/service/machine-chain.ts`):

- at a handoff and a checkpoint (`relay`): once the previous session is stopped, from its folder, behind the next session's launch (the machine's `writes`), so a slow pre-push hook holds nothing;
- at a stop of a task's session (`stop`: a red main interrupting it, extra usage held);
- at the end of a turn of a session Even Keel launched (BTN-1274), from the session's folder, in the background (`writes`) — see below;
- in PR mode, when `openPull` opens the pull request ([PR mode](pr-mode.md)).

**The push at a turn's end.** A turn ends with a question, an `AskUserQuestion` or a permission prompt, with no mark, or by the session dying mid-turn.

- The session monitor's tick (`wireMonitor`, `src/service/session-monitor.ts`) hands the ended turns to it: `TurnEnds` (`src/sessions/turn-ends.ts`) names a session once when it leaves busy, and a live one first seen between turns, so work from before a restart goes too.
- Such a push is `onlyNew`: no `git push` when HEAD is already in the remote-tracking ref of the last push (`refs/remotes/<remote>/<branch>`, which a push updates) or in `main` (a merged task closes) — two local `merge-base --is-ancestor` calls. A repository whose fetch refspec keeps no such ref pushes at every turn end, harmlessly.
- PR mode pushes at a turn's end too (BTN-1419), so a task stopped on a question is kept on the remote: the branch then reaches the forge before its pull request, and a workflow `on: push` of every branch runs on it early. `openPull`'s checks (the note, nothing ahead, an outsider's files) are about opening the pull request and stay there.
- Not pushed: commits made mid-turn until that turn ends. A machine gone mid-turn takes them with it.

**An outsider's task** (BTN-1207). Only the intake on the hub knows one. The hub's brief of a task (`LaunchBrief`, [machines](../machines.md)) carries `own: true` when `Intake.outsider` says it is not one, asked at every brief and never cached with it; the machine keeps the last brief received per task (`LaunchBriefs.own`).

- For a task with no such brief — an outsider's, a brief from a hub that does not tell, none kept since the machine's restart — none of the pushes takes a branch whose changes against `main` (`git diff --name-only -z main...HEAD`) touch a file `guardedFiles` names, or that git cannot list (BTN-1274, BTN-1418, BTN-1419): a push of a changed workflow runs it with the repository's secrets. A `push:` line says so; such a branch stays only in its folder, and another machine cannot take the task over from the remote while it holds that change.
- A task the hub vouched for is pushed whatever files it changes. An author whose association changes mid-session reaches the machine with the task's next brief (a launch, a handoff, a move).

**The remote** is `taskRemote`: `origin` when the repository has one, else its first remote. Only a folder standing on the task's own branch (`<key>-<number>/…`) is pushed, never forced; a refused push (the remote moved on, a server hook) or a repository without remotes is a `push:` line in the log, never a pause. The chain's fix and carry sessions and a project without git push nothing. The cleanup after Done removes the remote branch with the local one, on the same `taskRemote` ([cleanup](cleanup.md)).

## Landing (BTN-1581)

**Done is the task's branch in the main of the remote, not in the local one.** The merge closer (`MergeCloser`, `landedCommits` in `src/git/merged.ts`) counts a branch merged once its own commits are in `refs/remotes/<remote>/<main>` of every remote of the checkout, as its last fetch or push left them. A checkout without a remote, and a project in PR mode (the forge lands the branch), go by the local `main`. A carry's release commit is counted the same way (`landedCommit`, the machine's `carried`); the merge `merged` of a machine elsewhere too.

The landing is Even Keel's, not the prompt's. The signal is the session's merge into the main checkout, seen on the dispatcher's step once the session's turn ended (`Landings.follow`, `src/chain/landings.ts`, called from `followCurrent` before the PR review and the hint of `Unchanged`, and from `stopAfterTurn`; a fix and a carry session land the same way, a carry by its release commit). The machine's `land` (`MachinePort.land`, `landTask` in `src/git/landing.ts`) then:

- returns `none` when there is nothing to land: no remote, no own commit of the task in the local `main`, or every one already in each remote's `main`; nothing is fetched;
- finds the base — `main` as it was before the session's merge. It walks `main`'s first-parent line back to the newest commit that holds none of the task's unlanded commits, testing two of them: the newest of each branch and the oldest one not landed yet. So when a later round fast-forwarded `main` over the whole branch, the walk goes back past all of it. None within 200 commits — `landing.noBase`;
- for each remote: `fetch`, `merge --no-edit <remote>/<main>`; a conflict — `merge --abort`, `reset --keep` to the base, `returned` with the files git left unmerged;
- when a remote had commits the local `main` lacked and the project has `commands.check` (any width, unlike the cleanup's merge check), runs them in the main checkout; red — `reset --keep`, `returned` with the command, its exit code and the end of its output;
- pushes `main` to each remote; a push rejected because another clone pushed meanwhile gets the whole landing again, twice at most, as `syncMain` does. A repository's own `alias.sync` (or the global one on a branch named `main`) does the fetch, the merge and the push itself, with no `commands.check`; its conflict is told by the files it leaves.

The dispatcher keeps what a landing still holds in `ChainState.landings` ([state](state.md)):

- **Landed** — the record goes, the tracker is read at once, and the closer moves the task to Done; the cleanup after Done follows, its `git sync` now normally with nothing to push.
- **Returned** — the main checkout is clean and on the base; the worktree and the branch live on, since there was no Done. The session gets a message (`landingPrompt`, `src/chain/prompts.ts`): the remote and the files of the conflict, or the red command with the last 4,000 characters of its output — merge `<remote>/<main>` into the branch in its own folder, resolve, run the checks, merge again. The delivery is [exception 13](exceptions.md): warm (exception 1) — `--resume`, else a stop and a new session with a handoff that carries the message (`landing`, the launch log's cause `landing`). The message waits in the record while the account's limit or a launch block holds. The record gets `resolving` ("The hold while a landing resolves" below). A new merge of the session is a new landing.
- **Rounds** — one round is one return to the session; at most `LANDING_ROUNDS` (3), not a setting. A landing that would need a fourth pauses the chain on the task with `landing.exhausted` (a `USER_HOLDS` pause: the chat answers its session) and sends nothing more. A person's answer to the session (the chat's answer or a new session from it) starts the rounds over; a landing that went through drops them with the record.
- **Remote out of reach** (`transientFailure`) — the task stays open and its session is told nothing; the landing is tried again 30 s and 2 min later, then every 10 min with `waitingRemote` set, until the remote answers. The log names which of the three signs it was:
  - the network;
  - the remote's server failing with a 5xx (BTN-1654): `Internal Server Error`, `Bad Gateway`, `Service Unavailable`, `Gateway Timeout` in `[remote rejected]` or a `remote:` line, curl's `The requested URL returned error: 5xx` or `HTTP 5xx` — unless a server hook declined the push;
  - a race for this clone's own refs (BTN-1720): git's `error:` line `fetching ref … failed` (`incorrect old value provided`), `cannot lock ref`, `failed to lock`, `update_ref failed` or `Unable to create '….lock'` — never the remote's `[remote rejected]`.
- **Close without pushing** (BTN-1582, `chain/closeUnpushed`) — for a long outage the page closes such a task anyway. The dispatcher checks, on its own turn, that the task is a lane's current one and its record `waitingRemote` (else `landing.notWaiting`), moves it to Done through the tracker's `complete` with a comment saying its merge is not pushed yet (`landing.unpushed` of `PROMPTS`; a tracker failure — `landing.notClosed`) and drops the record; the cleanup after Done follows, and its `git sync`, or the next one, pushes the merge once the remote answers.
- **One remote call at a time** (BTN-1720, `remoteCallsInTurn` in `src/git/in-turn.ts`): a machine's `fetch`, `pull`, `push` and `git sync` of one folder run one after another, others and other folders at once. A landing once lost its remote-tracking ref to another `fetch origin` of the main checkout in the same second. A session's own git in its worktree and another process are not queued, so the retry above stays.
- **Refused** by the remote (a hook, permissions, `sync.notMain`) — the chain pauses on the task with `landing.refused` and git's text as its cause; no round.
- **Left the chain** meanwhile (cancelled, back in Backlog, Done by hand) — the record goes; the main checkout is already clean after the roll-back.
- **Mid-turn** — not landed: its turn may still be merging. For the same reason a fix of main (`MainFix.yields`) asks the machine's `merged(project, task, true)` — merged into the local `main`, not landed — so a session whose branch is merged only locally is not stopped mid-turn; its landing follows the turn.

The landing runs on the machine that holds the task's checkout. A project lands one task at a time on all its machines, and a landing that went through brings the other machines' `main` up to the pushed commit (BTN-1583, `docs/machines/landings.md`, "Landings across machines"). A step waits for a landing at most `LANDING_WAIT_MS` (2 s); a longer one — a merge with `commands.check`, a machine off the link — goes on behind the chain with the task held, and its end wakes the chain.

### The landing on the page (BTN-1779)

From its end of turn until Done, a session whose merge is being landed asks nothing, though its own lamp is `waiting`. The page's `chain.landings` (`Landings.facts`) marks such a task `underway`: a landing behind the chain, one waiting to try the remote again or holding a message not delivered yet, and one that went through while the session that merged is still the lane's current one and the tracker has not closed the task. A landing given back to its session (`resolving`) and a task with nothing to land are not under way. The page shows such a task at work, merging into the main branch, not waiting for an answer; a real question, a permission or a startup dialog (`needsReply`) still shows as a question. The state comes from what `Landings` holds in memory, with no git call per tick. How the page draws it: `docs/web/project-page.md`.

### The hold while a landing resolves (BTN-1582)

While a session of the project resolves its landing, no lane of the project starts a new task: its merge would most likely meet the same conflict, and the resolving session's next merge would meet it again. The setting `landingHold` (`docs/settings.md`, G and P, on by default, live) turns it off.

- A resolving landing is a record with `resolving` and without `waitingRemote` whose task is the current one of a lane of the project (`resolvingLanding`, `src/chain/landing-hold.ts`); a task taken off with "Skip" holds nothing.
- Only a fresh start of the next task by the chain's order waits (`heldByLanding` in `launchNext`, `src/chain/step.ts`, logged once per lane and task): lanes whose tasks already run go on, and a live or returned session, a fix of main and a carry are not held.
- The page shows it as the "waiting" state under Start/Stop with the task in its tip; a task waiting for the remote is a line above the chain with "Close without pushing" (`docs/web/project-page/head.md`, "The chain's buttons and the run strip").

## "Slot" mode (`src/git/slot.ts`)

- **What.** `"slot": true` or a number of slots on a project — a pool of permanent worktrees per repository instead of a new one for each task: `.claude/worktrees/even-keel`, then `even-keel-2`, `even-keel-3`… (`true` — one). Ignored caches (Unity `Library`, `node_modules`) survive a task, and the first run of a new one processes only the difference; an extra slot is needed so that the live session of a released task (skipped, postponed by a blocker) stays in its own and is not stopped. The chain still leads one task at a time.
- **Choosing a slot.** A slot already on the task's branch (`<key>-<number>/…`) is used as is, even dirty. Otherwise a dirty slot (`git status --porcelain` is not empty) or one with a busy session of another task (by the launch log, `src/sessions/occupants.ts`) is unfit. Of the fit ones, in order of preference: detached from a branch without foreign live sessions, on a foreign branch without them, not yet created (`git worktree add --detach <slot> main`), with idle sessions of other tasks — they get `claude stop` ([exception 5](exceptions.md)); on a tie, the one with the lower number. Then `git clean -fd` (without `-x`) and `git switch <branch>` or `git switch -c <branch> main`.
- **None fit** — a launch error: the chain is paused with the paths and reasons, and the slots are not touched. In unattended mode the chain is not paused: it stays running with `slotWait` (a yellow line with the same reasons on the page, one line in the service log) and tries the launch again at most every 30 s; the task is not released, since it never started.
- **After Done**, a slot on the task's branch gets `git switch --detach main` (a dirty one stays on the branch, the branch is not deleted, a warning), then the branch, origin and `git sync`, as without a slot; the slot folder is not deleted. Slots on foreign branches (cleanup of a released task) are not touched, only the branch is deleted. `claude stop` after Done in a slot applies only to this task's sessions by the launch log.
- **Temporary files after Done** (BTN-1315, `cleanSlot` in `src/git/slot-clean.ts`). A slot keeps everything git ignores, and sessions' `.temp/` grew there to tens of GB.
  - Once the slot has left the branch and the branch is dropped, `finishSlot` deletes the files matching the project's `slotCleanup.clean` (`.gitignore` syntax from the slot's root, default `[".temp/**"]`; `[]` turns it off) unless they match `slotCleanup.keep` (default `[]`; `!` is refused in both, `config.slotCleanup`; matcher in `src/git/patterns.ts`).
  - Only what git reports ignored (`status --porcelain --ignored`, `!!`) is walked, so a tracked file is never touched: tracked files under a pattern warn `cleanup.slotTracked`. The ignored folders themselves stay, the subfolders emptied by the cleanup go. Links (junctions, symlinks) are removed as links, never entered.
  - A file held by a process (Unity, a background run) is left with one warning `cleanup.slotTempLeft` with the count; the next Done in the slot takes it. The attachments cache `.temp/task-files/` is outside the patterns: the Done task's own folder is removed, open tasks' folders stay. One log line names the freed size (`cleanup: <task>: the slot <path> freed N MB of temporary files (k files)`).
  - A dirty slot left on the branch, a released task (skipped, postponed) and a slot on a foreign branch get no cleanup. The start prompt of a task in a slot says what is deleted after Done (`slotTemp`).
- **The number of slots** changes on the fly (BTN-130); when it is reduced, Even Keel takes no new task into the extra folders, but still finds a busy task in one and cleans it after Done (`slotSpan` in `src/service/machine-chain.ts`: the most slots the project had since the start). A task's own worktree left over from the previous mode is taken and cleaned the old way.
