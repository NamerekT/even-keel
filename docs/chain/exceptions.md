# Chain: the exceptions to invariant 1

## The exceptions to invariant 1 in detail

Exception 1 also covers detected paid subscription usage (BTN-577, `OverageStops.guard`). Before following the chain, even while it is paused or waiting for Stop after turn, fresh evidence can stop only its current live session mid-turn through its own `Agent.stop`. Detection is described in [accounts.md](../accounts.md#stopping-paid-subscription-usage-btn-577). An in-flight move is recovered first. The persisted `LimitHold.overage` keeps the full `LimitedSession` snapshot and successful-stop marker; the snapshot supports recovery even after the session vanishes, including a handoff interrupted by a service restart. Once stopped it waits without repeated stops or immediate relaunches; an unknown reset stays unknown rather than entering the unknown-limit retry ladder. A new account whose included window is still exhausted (also a shared ChatGPT pool) keeps the wait. Once usable, the usual warm resume/cold handoff keeps the worktree, branch and context without stopping the old process again. Pausing still holds continuation, and unattended mode never skips this retained wait. Actual paid-provider execution remains [unverified](../unverified/accounts.md#paid-subscription-usage-stops).

Exception 1 also covers a temporary model or service refusal (`apiError.kind: transient`, BTN-498). For the current session of an unpaused chain, `Handovers.followTransient` uses `LimitRetries` per session: 15 minutes, doubling after another refusal up to four hours, reset after a successful answer or a human continuation. It resumes the same session with a short continuation prompt, even if the cache has cooled; it does not create a handoff. No retry mid-turn, during a move, without a ready account or while launches are blocked. A chat answer or "New session" cancels the scheduled retry; the last continuation time keeps an old transcript refusal from scheduling it again. The existing limit hold carries the next attempt time on the page and through a restart; the ladder itself is in memory. This is an overload retry, independent of account usage windows and API credit checks. A real provider outage has not yet exercised the full path ([unverified](../unverified/sessions.md#temporary-model-errors-btn-498)).

1. **Limit** on the session of the current task of an unpaused chain: a minute after the limit resets (an agent may round the reset down to the minute; a reset already over a minute gone at the refusal waits 10 minutes from it, EKR-34, `docs/sessions.md`) or once the account is switched, the dispatcher continues it via `--resume` if the cache is still warm (the same account, within the session's warm window since the last response: 55 min for Claude on a subscription, 25 for Codex and Copilot, `docs/sessions/cache.md`, "Every agent's cache"), otherwise it stops it (`claude stop`, not `rm`) and starts a new one in its working folder with a handoff (`src/chain/relay.ts`). A limit is both the `rate_limit` error and the CLI's soft warning (`usageLimitNote: "wrap_up"`), after which the session wraps up its turn on its own. The reset time comes from the limit's text; the warning has none and comes before the window shows 100%, so it comes from the limits of the session's account polled after the limit (`limitResetAfter`, `src/limits/model.ts`): the exhausted window's reset, else the end of the five-hour window the limit fell into, or the start of a newer one. Until such limits arrive the reset is unknown (`resetsAt: null`, the page says only an account switch helps) and is asked for again on every check. A provider may reset limits early (BTN-530): a poll of the account taken after the refusal that shows it open again ends the wait as the reset would, a minute after the poll (`limitReopenedAt`, `src/limits/model.ts`; `Handovers.reopenEarly`). ChatGPT's `wham/usage` says so itself (`rate_limit.allowed: true`, `limit_reached: false`, `RateLimits.open`); a Claude `/usage` reading counts when no window is at 100% and none resets within an hour of the named reset — a window started over resets later. A poll less than 10 minutes before the named reset is no early reset (`REOPEN_MARGIN_MS`): `/usage` drops the window minutes before the CLI lets requests through. A statusline, a session's `rate_limit_event`, Copilot, keys, spending caps and paid-usage stops keep their own paths. An account whose limit nothing tells — no window known and its poll said there is nothing to read (`noKnownLimit`: OpenCode Zen, Copilot signed in on the machine, BTN-342) — is tried again instead (`LimitRetries`, `src/limits/retry.ts`): 15 minutes after the hit, the wait doubling up to 4 hours while each retry hits the limit again, back to 15 minutes once the account worked longer than its last wait; in memory, so a restart starts over. The working folder and the branch for the handoff come from git (the worktree root from the last `cwd`), not from the transcript: its `gitBranch` is the branch of the launch folder. A repository nested in the launch folder that is not a worktree of the same repository (another common git dir — a clone the session made under `.temp/`) is skipped for the one around it (`locateWorktree`): otherwise the new session would start in the clone, and the CLI refuses a folder not trusted on its own. A session on an API account (`docs/accounts.md`) has no windows to wait out, so its `rate_limit` stops it like any error; it is held on spent credit (`billing_error`, `apiError.kind` `credit`, BTN-165) and a spending cap (`apiError.kind` `spend`, BTN-382). A spending cap takes its explicit UTC reset from the refusal and keeps the five-minute key checks active: a 2xx permits an earlier resume or handoff. For spent credit the "reset" is the moment a check of the key finds credit again (`limitRecovery` in `src/limits/recovery.ts` asks `AccountWatcher.creditBackAfter`), and the cache is warm by the session's own window (`HandoffSession.warmMs`): a Claude key's is under 55 min with a 1-hour cache in the transcript, else under 4 min, since a key writes the 5-minute cache unless `cacheTtl` is `1h`. A switch of the account hands over at once, as on a limit.
   The service log records each new limit once, with the task, account folder, reset time (or `reset unknown`) and the planned continuation. A learned or earlier reset is logged with the updated plan. Successful continuation records the actual resume or handoff and the resulting session id (also the previous id for a handoff); failed attempts use the chain's pause log.
2. **"New session"** (`restart`): the user replaces the session of the current task if it is not mid-turn — the same handoff, with `restart` in the log, referencing the previous session. A working turn silent for five minutes can also be interrupted, after explicit confirmation tied to that session and its last write; new output invalidates the confirmation, including while the replacement is queued. This is still a user-requested replacement, never an automatic stop. After thirty quiet minutes the turn is treated as hung and the usual replacement needs no confirmation. "Skip" remains refused mid-turn. A chat reply to a session whose cache went cold may take the same way at the user's choice (BTN-757, `docs/sessions/chat.md`, "A reply to a cold session"): `Dispatcher.renew` refuses as `answerable` does and for a loose session, then hands over with the message at the end of the prompt; the log says `restart` with cause `message`.
3. **Checkpoint** that the session set itself: the session of the current task of an unpaused chain finished a turn, and the last line of its last response is `CHECKPOINT: <path>` (that is what the hook of the `checkpoint@even-keel` plugin, `plugins/checkpoint`, asks for when the context has grown; its `Stop` hook sends back a session that wrote the note but ended with a report instead of the mark). The dispatcher does the same handoff, with the path to the note from the worktree root in the prompt and `checkpoint` in the log, referencing the previous session. A mark followed by a tool call, a new response without the mark, or a message to the session cancels it. The handoff repeats as many times as sessions ask for it; the number of handoffs per task is visible on the page, and after the third one the hook asks only from 300k (`docs/sessions/checkpoint.md`, "Checkpoint threshold"). A session with a limit goes by the limit rule (its prompt also points at the note), and while the limit is used up or new sessions are not started, the mark waits.
4. **Task in Done**: when its session has finished a turn and is not waiting for a reply (not `busy`/`waiting`; a turn that ended on a background command counts as finished), the dispatcher stops it (`claude stop`, not `rm`; the transcript stays, `--resume` by hand is possible) and removes the worktree. A task with nothing to merge gets to Done by its session's `NO CHANGES:` mark (EKR-10, "Nothing to merge" above) and goes the same way; so does a fix session of a red main that marked it once a rerun of the red commit is green (EKR-88, `docs/chain/main-ci.md`, "Nothing to fix"). A session the monitor has not read since the service's start is neither: its status is unknown, so nothing is stopped or removed until the first read (BTN-646, "The first read of the sessions" above). A session in the task's folder the cleanup found mid-turn is stopped once that turn ends (BTN-616, "A session left mid-turn" above). After the merge, sessions make no more than a couple of checks in the same turn and finish with a report (measured from transcripts, 2026-09-29).
5. **A slot is switched** to another task's branch (only when the pool has no free slot): the dispatcher first stops the live sessions of released tasks (skipped, postponed by a blocker) in the slot (`claude stop`, not `rm`), otherwise the answer to such a session through Remote Control would land in another task's branch. If such a session is mid-turn (`busy`/`waiting`), the slot is not switched and the chain is paused with its task (unattended — it waits for the slot the same way as when none is fit).
6. **The user's answer** (BTN-101) from the chat window (`POST /api/session/answer`, `docs/web.md`) or from tracker comments posted after the question Even Keel put there (`TrackerQuestions`, `docs/trackers.md`). A pending `AskUserQuestion` cannot be closed from outside, so the dispatcher stops the session (`claude stop`, not `rm`) and continues it via `--resume` with the answer; the stop loses the session's last message, which the CLI had not written yet, so the prompt repeats the question (`docs/sessions.md`) (`Dispatcher.answer` → `deliver`, the same path as after a limit; `answer` in the launch log, referencing the previous session; `resumedAt` is reset). `Dispatcher.answerable` refuses unless all hold: the task is the current one of its chain (`chain.notCurrent`) and is not being launched (`chain.launching`) — or the project's chain is stopped and the task's session lives on (the page marks such a row `loose` and keeps its chat; `Handovers.deliverLoose` resumes it and journals `answer`, a failure only goes to the log); the session is still the one the user answered and waits on the same open question (`ask` id, or none for a question in plain text) — otherwise `answer.moved` (say, the user already answered through Remote Control); it is not mid-turn (`answer.busy`); launches are allowed and the limit is not spent (`chain.limitSpent`). Files are saved first into `.temp/inbox/` of the task's folder (`src/sessions/inbox.ts`); the prompt is `replyPrompt` (`docs/sessions.md`).
7. **A red main** with `ci.fixTask` off (BTN-115): the session of the current task that is mid-turn is stopped (`claude stop`, not `rm`) so that it does not work on a broken `main`, and continued with a message once the fix session has landed. Detected paid subscription usage under exception 1 also permits a mid-turn stop. A session that waits for an answer is not stopped: a new message would wipe its open question. In detail — "The fix session" above.
8. **Feedback on a pull request** in PR mode (BTN-205): the review, failed run or conflict the poll found goes to the task's session only while it is not mid-turn — `--resume` with it while the cache is warm (the same account, within the session's warm window as in exception 1), otherwise `claude stop` and a new session with a handoff carrying it. A mark on a branch with nothing beyond main and uncommitted work, or one whose push is refused as behind the branch on the forge (BTN-716), is told to its session by `--resume`; with a clean worktree the task goes to Done and its sessions go as exception 4 has them (BTN-222). A pull request closed unmerged stops the task's resting sessions at its cleanup, as a Done does. In detail — "PR mode" above.
9. **A task back from an inactive status** (BTN-245): the current task left the chain for an inactive status (Backlog and the like) while its session was not mid-turn and waited on no `AskUserQuestion` of its own — the case of unattended mode, where the session asks in a tracker comment, moves the task to Backlog and ends its turn in plain text. The dispatcher remembers the task and its session in `shelved` (`shelve` in `src/chain/shelved.ts`; releases by a blocker or "Skip" are remembered with their own reason, exception 10; "Stop" is not remembered). When the task is back in an active status and the chain takes it, the old session is not adopted: `claude stop` and a new session with a handoff (`returned` in `src/chain/shelved.ts` → `Handovers.handOverCurrent` with `returned`; `relay` in the launch log and the snapshot, as after a limit with a cold cache), whose prompt says the task came back from the user after a question and the answer is in the description or the comments after it — read them in spite of the tracker skill's rule against the activity feed. The answer in a comment is not one of Even Keel's tracker answers (exception 6 reads only those to questions it posted itself), and the old session's cache is cold by then. The old session is adopted as before, with no stop, if by then it is mid-turn, waits on an `AskUserQuestion`, or its feed has a prompt or an answer after the task left (someone talked to it — through Remote Control or the chat of a stopped chain). A busy session keeps its task in the chain (`enters`), so a task leaves only once its session's turn has ended. A handover waits for the account's limit and the project's packages like a launch, and does not wait for the CI of main, like a relay after a limit. `shelved` goes with `released`: a take of the task or its cleanup forgets it.

10. **A task returned after a blocker or skip** (BTN-547): releasing the current task with `postpone` or `skip` remembers its session, time, reason and blockers in `shelved`, unless it waits on its own `AskUserQuestion`. The release itself only stops waiting. Once the task is eligible again and the chain takes it, the same safeguards as exception 9 apply: no turn in progress, no open question, and no prompt or answer since the release. Otherwise the old session is adopted. Eligible idle sessions are stopped through the agent and replaced with a handoff on the same branch and worktree. The launch log records `relay` with cause `unblocked` or `unskipped`; the snapshot keeps that distinct reason. An unblocked prompt names the closed blockers; an unskipped one explains that Skip was undone, without assuming a Backlog question. Limits and packages hold the handover as in exception 9; an interrupted move retains its reason and blocker context for recovery. Taking or cleaning up the task clears the shelf record.

**An answer to a permission dialog** (BTN-269) is the other write without a stop, and the user's explicit act as in exception 6. A Claude session that waits on a permission dialog while the `checkpoint` plugin's hook holds it (`docs/sessions/chat.md`, "Permission dialogs") has the call as its question; an answer from the page or a tracker comment goes through `Dispatcher.answer` as any answer, but `resumeWith` hands the decision to the hook instead of stopping and resuming, so the session goes on in the same turn with the same id. Nothing else decides such a call — but unattended mode, where nobody is at the page and the call is refused at once, as for an SDK session (BTN-303).

**A message to a working session** (BTN-181) is the third write to a session without a stop. A chat message in plain text to the current task's session while it is mid-turn (`busy`) is refused with `answer.busy` unless the session steers or its hooks have asked for mail since the service started (`Mailbox.listens`): then `Dispatcher.answerable` gives `midTurn` instead of the refusal, skipping the launch and limit checks since nothing is launched. A session that steers (`AgentEntry.steers`, an SDK session, BTN-291) gets the message straight into its live CLI by `Agent.reply` and takes it after the running tool call, in the same turn, with no mailbox; otherwise the message goes into the `mailbox` table. A hook of `checkpoint@even-keel` takes it on the session's next tool call or stop and hands it over without ending the turn (`docs/sessions/chat.md`, "Chat mailbox"). A session waiting on a question gets the chat as an answer (exception 6), never mail. When the hooks miss the message — the turn ended, or the session asked, before the next tool call — the mailbox settles it once the session is no longer mid-turn and 10 s have passed since the post: a turn ended without a question gets it by `--resume`, like an answer (`Dispatcher.answer`, `resume` as its event); a session that asked meanwhile, or is gone, gets nothing — the message goes back to the chat window, and the user sends it as the answer or dismisses it. A task over for the chain (BTN-558) — done in the tracker's last read or after its cleanup, or its branch merged into the main branch before the tracker knows (`Dispatcher.closed`, the same `merged` check as the CI of main) — gets no message at all: whatever it asks would land uncommitted in the worktree of a closed task, which no merge closes again. The chat refuses such a send at once with `answer.closed`, an answer to a question included; a message posted before the merge goes neither to the hook (`mailFor` returns nothing) nor by `--resume`, and comes back to the chat with the reason `closed`, without "As the answer" — what it asks is a new task.

**A keep-warm ping** (BTN-437, `src/sessions/keepwarm.ts`) is the touch that neither stops nor writes: the session is only read. With "Keep the cache of a waiting session warm, hours" (`keepWarm`, Even Keel's own, 0 — off, the default until its live check) above zero, a check every 30 s takes the sessions a running chain will go on in (`warmTasks`): the current task's session of each unpaused, unhalted chain not waiting on a limit, unless the task is starting or being moved (`starting`); a temporary model error scheduled for a resume remains eligible, and the live session of each task whose pull request is open in such a chain's project. Only an agent with `Agent.warm` (Claude Code, Codex) is pinged. The decision is made in one place (`warmStep`) from facts read anew at each check — the transcript's cache window (`SessionView.cache`), mid-turn (`agentStatus`, a resume hold), a limit lamp, an open `AskUserQuestion` (`SessionView.asking`): no ping mid-turn, on a limit, of a session waiting on `AskUserQuestion` (a fork of such a `--bg` session read 0 of its prompt from the cache, BTN-704), or of a cache already cold; a ping 5 minutes before an hour or a half-hour cache (Codex's) ends, 1 minute before a five-minute one. The ceilings: `keepWarm` hours since the session's last answer, and the break-even — 20 pings of an hour cache, 12 of a half-hour or a five-minute one, after which a miss would have been cheaper. A ping that read under 90% of its prompt from the cache, or failed for a non-transient reason, turns pinging off for that session until a restart. An overload refusal skips that ping without disabling the session or claiming a cache hit; it can be tried again on the next check while the cache stays warm. What was sent is in memory, so after a restart a cache looks cold and is let go.
The ping itself is a fork: `claude -p --resume <id> --fork-session --no-session-persistence --max-turns 1 --permission-mode dontAsk` with the session's model, packages and `--settings` plus `disableAllHooks` for a `--bg` session, the SDK's `query` with `forkSession`, `persistSession: false` and every tool call denied for an SDK one, `codex exec --ephemeral --sandbox read-only --disable hooks … fork <id> -` with the session's model, servers and packages for a Codex one (`docs/sessions/cache.md`, "Keep-warm"). It writes no transcript, so neither the page nor Tally sees it; the service log has a `keepwarm:` line per ping. A ping that read the cache counts as the session's last moment of warmth for the chain's own warm checks (`HandoffSession.warmedAt`, `warmSince`): an answer, PR feedback or the end of a main fix an hour after the last answer still goes by `--resume` if a ping kept the cache since.

**A service restart in the middle of a move** (BTN-164). While the dispatcher resumes or replaces the session of a running task (exceptions 1–3, 6 and 9–10), `CurrentTask` holds `starting`, the kind of move (`move`: `answer`, `resume`, `relay`, `restart`, `checkpoint`, `returned`, `unblocked`, `unskipped`, `message`) and, for an answer or a new session with the user's message, its text and the question it answers (`reply`, `ask`). Loading the state keeps them for a task with a session (a cut first launch is still dropped and pauses the chain with `chain.interrupted`), and the chain's next step sees the move through (`Handovers.recover`) before the limit and the checkpoint: no session of the task read yet — it waits; the task already has another session — the chain takes it and journals the move; the old session works, replied after the move began or waits on another question — the move went through (an answer or a resume is journaled); otherwise the move is made again — the answer delivered once more, "New session" and the handover of a returned task repeated with the same reason and blocker context, the limit step redone, and a checkpoint left to its mark, which is still the last line. Within one process the step never sees these marks: moves and steps run one after another. The marks are transient like `answering`, so they did not change `SCHEMA_VERSION`.

In every exception a session `claude agents` shows `failed` or `stopped` is stopped as well while its process lives (`pid` from a live `sessions/<pid>.json`): a session that failed at start (an API 400) keeps running, and `claude stop` run from a terminal marks the job `stopped` without reaching the service's daemon (`isGone` in `src/claude/cli.ts`, `stopTaskSessions`, `slotOccupants`). The other way round, a job the CLI still shows `blocked` after its daemon dropped it and exited is gone and needs no stop (`abandoned`, `docs/sessions.md`).

Every handoff (limit, "New session", checkpoint, a returned task, a task unblocked or unskipped) leaves a snapshot `<state>/handoffs/<new session>.json` (`src/chain/snapshots.ts`): the whole prompt, the note's path and its text as read just before the launch, the reason in the launch log's words and the previous session. The note itself is overwritten by the next handoff and goes with the worktree; Tally loads the snapshots into `handoffs` (`docs/tally.md`). A failed save is a warning in the log, the handoff goes on.

A handoff from a session that never answered (BTN-650: no `lastReplyAt` and no text or tool line — a bad key, no credit, a refusal at the start) carries what the session before it left. `Handovers.handOver` remembers, by task, the session each handover started and the answered session it carried on from (`HandoffSession` with its transcript path, in its own account's folder); a handover from that failed session takes the steps, the last message, the note and the main transcript from the remembered one, and adds a line per failed session after it with its last API error and its transcript (`answered`, `failedOf`, `PromptTexts.failed` in `src/chain/relay.ts`). Several failed ones in a row add up. The folder, the branch, the stop and the reason stay the failed session's. The memory does not outlive a service restart: then the handoff carries the failed session alone, as before ([unverified](../unverified/sessions.md#a-handoff-past-a-failed-session-btn-650)).

The dispatcher may stop waiting for a session (without touching it) if it is not mid-turn (`busy`/`waiting`): the current task got an open blocker from the same chain (the session postponed it itself, `postpone` in the log) or the user pressed "Skip" (`skip`). The chain does not take a skipped task until the user returns it or it leaves the chain in the tracker (closed, in Backlog). On return, an idle session with no question and no messages since the release gets a new session with a handoff (exception 10); an active conversation keeps its old session. "Skip" is refused for any task whose session is mid-turn, also one released by "Stop": otherwise a restarted chain would launch the next task beside it instead of taking the live session again.
