# Hub and machines

The hub decides, a machine runs the sessions; the map of the roles is BTN-137. Three steps of it are in the code: the seam between the two roles inside the service ("The seam"), the link that carries it (`src/link/`) and the chain over that link inside one process ("One process" and the sections after it). The fourth, the hub's door for machines elsewhere ("Machines elsewhere", BTN-1242), lets a machine join and get projects, and an installation that joined runs as a machine alone ("The machine's process", BTN-1247). **It does not run the chain's tasks yet:** the chain's work still goes only to the hub's own machine, the installation itself, reached through the same protocol over a carrier that is a call.

## The seam

One installation is a hub and a machine in one process, and there is one code path: the chain (`src/chain/`) reaches sessions, accounts, packages and working folders only through `MachinePort` (`src/machine/port.ts`), which `DispatcherDeps.machine` carries. The chain is given the hub's side of the port, `RemoteMachine` (`src/machine/remote.ts`); the machine's own implementation is `wireMachine` (`src/service/machine-chain.ts`), run behind `MachineRunner`. `wireDispatcher` (`src/service/chain.ts`) builds the hub's side and takes the port as an argument.

| Side | In the chain | In the service's assembly |
| --- | --- | --- |
| Hub | `Dispatcher`: order, the queue and its fill, pauses, skips, released and shelved tasks, the launch of a task (`startTask`, `inTurn`, `src/chain/start.ts`), the skip of a quiet session (`unanswered`, `quietTooLong`, `src/chain/quiet.ts`), `MainCheck`, `MainFix`, `MainWait`, `MainCarry`, `Reviews`, `TaskLists`, `Cleanups`, `Unchanged`, questions to the tracker, the hub's side of the moves (`taskMoves`, `src/machine/tasks.ts`); the rest of `DispatcherDeps` and `MainCheckDeps` (`hubMainDeps`): projects, rules, `parallel`, the chain's state, statuses and comments in the tracker, the CI of main, PR mode | `src/service/hub-bootstrap.ts`, `src/service/chain.ts`: the state database, tracker and CI profiles, projects and settings, the page, Tally |
| Machine | `src/machine/`: the moves of a task's session ("Moves") — `MachineMoves` (`moves.ts`) running `Handovers` (`handover.ts`: limit, resume, relay, checkpoint, answer, "New session", a returned task) and `OverageStops` (`overage.ts`), the git and check side of the CI of main (`mainMachineDeps`, `main.ts`) | `src/service/machine-bootstrap.ts`, `src/service/machine-chain.ts`: accounts and limits, packages and the MCP gateway, slots and worktrees (`wirePlaces`), the session monitor, the launch journal for the slots' occupants, keep-warm |

- **A member of the port** is a command, a query or a snapshot field; the comment of each in `port.ts` says which. A command (`launch`, `launchFix`, `launchCarry`, `resume`, `reply`, `relay`, `stop`, `finish`, `sync`, `prepare`, `checkMain`, `runAfterGreen`) is a numbered command of the link with its result as an event; a query (`locate`, `head`, `tree`, `merged`, `carried`, `changes`, `history`, `modelBlock`) goes the same way and changes nothing on the machine; the facts (`liveSession`, `lastSession`, `busy`, `midTurn`, `shell`, `asked`, `silentSince`, `limited`, `overage`, `handoff`, `modelRefusal`, `sessionsRead`, `reportedTree`, `account`, `accountAt`, `launchBlock`, `sessionBlock`, `limitReset`, `modelWeek`, `limitResetAfter`, `limitReopenedAt`, `limitsUnread`, `accountsRead`, `packagesBlocked`, `packagesHeld`, `packagesPause`, `trackerMissing`) are read from the hub's mirror of the machine's snapshot ("The mirror").
- **An action of both sides is the hub's decision and one call of the port.** A red main: `MainFix` decides, `stop` stops. The cleanup after Done: `Cleanups` decides and records the closed task (`archiveClosed`), `finish` stops the sessions and removes the folder. The report of a red main: the hub writes it, `history` gives the commits.
- **Every touch of a session is the same exception to invariant 1 as before** (`docs/chain/exceptions.md`), now made on the machine's side.
- **The page, the hooks and the chat** reach the machine through `MachineServices` (`src/machine/services.ts`, BTN-1241), never its objects: account controls, transcript reads (a session's record, feed, pictures, inbox and shared files, the handoff note, the checkpoint's context), the chat's commands and the initial records ("The chain over the link"). The hub's transcript reads go to the machine of the session (`MachineLink.transcripts`, `src/service/session-transcripts.ts`, BTN-1574): the one whose mirror shows it, else the machine of its launch's task, the own one for a session none of them knows; a machine elsewhere off the link answers `machines.transcriptOffline`, never "not found", and the own machine never searches its account folders for a session another machine holds. The page's state of the machine's sessions and accounts reads the mirror ("The mirror").
- **A machine without its link** follows and guards the tasks the hub gave it by itself, on the hub's last word ("Moves", BTN-1226); every other decision waits for the hub.

## One process

`wireLinkedMachine` (`src/service/machine-link.ts`) assembles both roles of an installation: `HubEnd` over the state database, `MachineEnd` over the machine's own database (`wireMachineSide`, `src/service/machine-side.ts`, the same assembly a machine of its own runs over HTTPS), and `LocalTransport` (`src/link/local.ts`) between them — the ends call each other, without HTTPS and a certificate, with the same numbers, confirmations and snapshot; what passes is carried through JSON, so both sides see what a machine elsewhere would. A single installation has no other path. The pulse is `LOCAL_HEARTBEAT_MS` (10 days): there is no network to lose.

- **The own machine** (`ownMachine`, `src/machine/own.ts`) is made at the first start of a version that has machines: a row of `machines` named after the host, a token whose secret is kept in the machine's database (`identity`), its id in `service_state` as `machines.own`. Every later start finds it again. When the two databases no longer agree — one folder restored or removed — a new machine is made and the old one revoked; `storeToken` empties the machine's outbox and command numbers with the old token. The old own machine's rows of `project_machines` (turned on or off, its own settings, `after_green`) go to the new one, so a state database restored on another host keeps its projects running there; the tasks of `machine_tasks` stay with the revoked machine, for a person to move ("A machine gone").
- **Consent** to the installation's own projects, each in its folder, is given at the start and before a step of the chain after the projects changed (`agree`); a project gone from the config is served no longer. The same moment puts the own machine into the pool of every project that has none (`fillPool`).
- **The order at the start.** The port is built first, the dispatcher on it, and only then is the machine connected (`LinkedMachine.start`): the machine's facts read the chain's state. `start` waits for the first snapshot; until it is in the mirror `sessionsRead()` and `accountsRead()` are `false` and no chain steps. Before the monitor, hooks and chat start, the link drains the retained outbox, and the hub reads its own `launches`, `session_windows` and `mailbox` and hands them to the machine by the command `records.restore`: records replayed from the previous process must be included in their initial state, including the mailbox's next id. The mailbox gets only the machine's own messages (`loadMail(db, machine)`): its settling (`settleMail`) would otherwise give back to the chat another machine's waiting messages, whose sessions it does not have. The machine never reads the hub's database: its mailbox is made empty (`Mailbox.detached`) and filled by that command, and its launch journal (`MachineRecords.journal`, read by the slots' occupants and the stops) keeps the launches made before it, each once.
- **Commands the process before kept** and its machine never took are dropped at the start: nothing waits for their result, and a launch among them would start a session the chain did not ask for again. A command the machine took and did not finish is reported as `command.interrupted`, found without a waiter and logged; a launch it began is found by the chain's own recovery of a `starting` task.
- **Moving an installation of the version before** needs nothing by hand: the state database stays the hub's, accounts, packages and slots stay where the machine's code reads them, the own machine and its consents are made as above, and the chain's state is not touched — live sessions are picked up and the current task stays current.

## The machine's context

BTN-1246: the machine's assembly — `wireMachine`, `MachineRunner`, `wireMachineServices`, the places, keep-warm, the task folders (`TaskWorks`), the found repositories (`GitFound`) and the cleanup's lingering sessions — runs on `MachineContext` (`src/service/machine-context.ts`), never on `ChainContext`.

- **The host's objects** (`MachineHost`): accounts and limits, the session monitor, agents, daemons, packages, the mailbox and the launch journal. `assembleMachineHost` (`src/service/machine-host.ts`) builds them with the machine's `MachineContext` for both processes, the service and a machine of its own. Their assembly reads `MachineContext`, including the account watcher, monitor, CLI checks and approvals (BTN-1250). The account folders open on the machine database. `PackageHub` is a separate hub object: it owns the credentials, OAuth, tasks and memory servers; the machine's `Packages` has no tracker profiles or hub database.
- **What only the hub knows** comes in the brief (below) and is read from the machine's copy (`BriefCopy`, `src/machine/brief.ts`): the config with the machine's projects and their folders, the tasks' own runs, the trackers' task lists, the chains' current tasks, the demo's projects, `unattended`, `trimTools`, the sessions keep-warm pings and the check reports. Over it the machine builds its own `choiceFor`, `planFor`, `agentExtras`, `settingsFor`, `withProject`, `branchOf`, `promptLanguage`, `projectOf` and `taskNote`; the hub keeps its own `choiceFor` for its changelogs and packages.
- **The launch's brief** is split: the hub's `Briefed.prepare` reads the tracker and sends the text with the launch's command; the machine's `launchBriefs` keeps it for the task's later sessions and the tasks server.
- **What the machine tells the hub** besides the chain's results is an event of the link (`MachineTell`): `task.leftover` — what a cleanup finished late left on a task (`stopLingering`), which the hub puts on the task's row (`Dispatcher.leftover`); `transcript.changed` — a watched transcript changed, signalled to the page; a change of the task folders or of a found repository has the machine post its facts. The hub writes the stop of a session into the event log on the `stop` command's result, and adds where a launch's task is read from (`withSource`) when it saves the machine's `launch.record`.

## The brief

The command `hub.brief` (`BRIEF_COMMAND`, `HubBrief`) hands the machine what its assembly reads of the hub, whole each time. `hubBrief` (`src/service/hub-brief.ts`) builds it; `BriefSender` sends it at every catch-up when it differs from the one the machine took (`sameJson`), and again after a failed send or a new connection (a new process of the machine holds none). The machine takes it before the command's first await, so a command after it reads the new one even when run side by side.

- **Before the first brief** the machine holds an empty config, and its `accountsRead()` is `false`: no chain steps. The start waits for the first snapshot and sends the first brief before it restores the records; the projects without git are read for a repository once it comes.
- **Freshness** is the mirror's: in one process every step, page command and reply catches up first, and the brief goes before the facts, so a check report or a run just set is on the machine when the step reads it.
- **Folders.** The brief's `config.projects` holds only the machine's projects, each with its folder there; for the own machine that is the installation's own folder of each project (`agree`).

## The machine's stores

The machine's own database (`state/machine/`, "The stores") keeps since step 3 of `MACHINE_STEPS` the account folders' `account_limits`, `account_settings` and `machine_state` (`cli.downloaded`). Step 4 (schema version 6, BTN-1250) adds `global_accounts`, `key_organizations`, `management_keys`, `left_folders` and `context_windows`. `machine_state` also keeps `cliCheck.history`, the pending `accounts.adoptLegacy` marker and the local CLI choices (`cli`), and on a machine of its own the hub's last word for its moves without the hub, `moves.held` and `brief.kept` ("Moves", BTN-1226). Approvals stay in memory, configured by the brief; there is no approvals table.

`importMachineStores` (`src/machine/state.ts`) imports the first group once under `stores.imported`, and the second under `stores.hostImported`, so an installation that already passed the first import still gets the second. Each group is transactional, retains existing machine rows and leaves the old hub rows untouched. Later starts read only the machine rows. The frozen machine sample is `test/fixtures/machine-v6/machine.sql`. Machine state is not included in the hub's automatic backups: preserve this folder with the service stopped when moving an installation.

`key_spends` stays at the hub for statistics: a machine emits `key.spend` with each measured growth. The hub commits it and the event receipt together, so a lost confirmation cannot add the same growth twice. `warm_pings` is kept the same way: a machine emits `warm.ping` with each answered keep-warm ping (BTN-1413). `task_retries` also stays at the hub: it is the idempotency journal of the hub's `tasks_create` executor, including writes queued by a machine. No machine reads that table.

The brief also supplies the active projects and their pause state for account sign-in protection, tracker MCP requirements and `hubServers` (route names only). CLI selection and fallback are kept locally, then reported as `machine.selection`; account activation and filling an empty shared pool use the same event. The hub applies these selections to its settings and sends them back in the next brief. A changed hub CLI choice supersedes a local fallback. `sessions.read` asks the hub to settle mail after catching up with the monitor; the monitor never reads the dispatcher to make that decision.

## The chain over the link

`RemoteMachine` is the hub's side of the port, `MachineRunner` (`src/machine/runner.ts`) the machine's.

- **A command or a query** is the link's command `port.<member>` with `{args}` as its payload and `project` and `folder` in its own fields: the project of the call, and the session's folder (`resume`, `reply`, `relay`, `stop`, `locate`) or the working folder (`changes`). The machine runs it on its local port and answers with the event `command.done` — `{seq, value}`, or `{seq, notice, cause}` when the handler threw: the chain branches on message codes (`cliCheck.busy`, `slot.*`), so a handler's error is a result, not `command.failed`.
- **The call waits** for the event that names its number, as it waited for the direct call before. A project's steps go one at a time (`Dispatcher.work`), so a project never steps twice while it waits. The machine takes commands in order and runs their handlers side by side (`MachineOptions.concurrent`): a check of main or a launch does not hold a stop or a query of another project.
- **`command.interrupted`, `command.failed`, `command.refused`** reject the waiting call with `machine.commandInterrupted`, `machine.commandFailed`, `machine.commandRefused`: the chain's own error branches pause it, and nothing launches again. A result nobody waits for (the hub restarted) is a line in the log.
- **A handoff snapshot** (`src/chain/snapshots.ts`) is the machine's event `handoff.snapshot`; the hub keeps it in the state database (`handoffs`). A save that fails leaves the event with the machine, which brings it again.
- **The services** (BTN-1241): every member of `MachineServices` is the command `<group>.<member>` — `account.*` (the page's `AccountControl`), `transcript.*`, `chat.*`, `records.restore`, `git.identity` (BTN-1503, the machine page's commit author) — with `{args}` and its value in `command.done`, as for `port.*`; `SERVICE_COMMANDS` lists them, and a member left out of it fails the build. `chat.steer` carries the session's project and folder, `chat.saveInbox` the project and the working folder: the machine refuses them outside its consents. A file goes whole as base64 inside the JSON (`CarriedFile`), both ways: a picture or a file of the transcript to the page, a reply's files into the session's `.temp/inbox/`. The checkpoint hook answers on the hub: only the session's context and its compaction point come from the machine.
- **Journal, session records and chat** (BTN-1219, `src/machine/records.ts`): `MachineRecords` sends `launch.record` (`LaunchEntry`), `session.windows` (the monitor's changed `[sessionId, size]` pairs with their observation time) and `chat.mailbox` (complete changed `Mail` rows and the producer's optional retention cutoff). `Mailbox` keeps its immediate claim/settle behaviour but publishes typed changes, never SQL. The hub keeps the sending machine with each `mailbox` row (`machine_id`, BTN-1251): the cutoff removes only that machine's old settled rows, and those kept before rows knew their machine. Each machine numbers its own messages, so a row's key is its machine and its number (step 62, BTN-1284): two machines' messages of the same number are two rows, and a machine's change never reaches another's. The own machine takes the rows kept before rows knew their machine (`adoptMail`, at `LinkedMachine.start`, before its replayed records). A row's `fate` only moves forward (`waiting` to `delivered` or `returned`, `returned` to `dismissed`), so a late or repeated change never brings a settled message back. The hub awaits the writes to `launches`, `session_windows` and `mailbox`; its journal in memory and the event log update after the launch is committed. Live session views and chat delivery state travel in `facts` (below).
- **A receipt is part of the write.** `saveMachineRecord` locks the machine's row and commits the record with `machines.last_event` in one transaction. A retry at or below that number writes nothing, even after a restart between the commit and the link's separate confirmation. A failed write rolls back both, leaving the event in the outbox. The tables keep their existing layout. The wire API is version 19 (BTN-1567 added the commands `branch.move` and `branch.back` and the facts' `checkouts`; 18 — BTN-1565 added `POST /link/skills`; 17 — BTN-1541 added `POST /link/credentials`; 16 — BTN-1503 added the command `git.identity`; 15 — BTN-1413 added the record `warm.ping`, which an older hub refuses as unknown; 14 — the query `folders.probe`; BTN-1311 added the brief's `accounts`; BTN-1313 made `port.merged` answer the merged commits, not a yes; BTN-1280 added `POST /link/tally`; BTN-990 added `POST /link/mcp`, BTN-991 the command `limits.plan` and the facts' `identities`, BTN-1241 the services' commands, BTN-1242 the join, BTN-1250 `key.spend`, BTN-1244 the event `projects.taken` and the refusal `taken`, BTN-1260 `POST /link/hook`, BTN-1226 `alone` and `halt` of `task.state`). Closing the local link drains the writes into its outbox and attempts their delivery before closing its database.
- **Every touch of a session** is made by the machine's local port, as before: the list of `docs/chain/exceptions.md` is unchanged.

## Moves

A move of a task's session is what the chain does to the session it already has (BTN-1221): the limit and the temporary model error (resume or handover), the checkpoint, a move a restart cut short, the user's answer and the feedback on a pull request (`deliver`, `deliverLoose`), "New session" (`renew`), a session restarted (`replace`), a returned task and the fix's handoff (`handOverCurrent`, `handOver`), and the stop on paid usage (`guard`). The machine makes them; the hub decides when.

- **The command** is `task.<move>` (`src/machine/move-call.ts`, `MOVES`) with a `MoveCall`: the project, the task as the hub holds it (`CurrentTask`), whether it is still the chain's current task and whether the chain is active, the move's own arguments, and `MoveContext` — what only the hub knows: `blocked`, the prompt language, the main branch, PR mode, a project without git and the report of a fix or carry session.
- **The machine** (`MachineMoves`, `src/machine/moves.ts`) runs the same `Handovers` and `OverageStops` code over its local port and a copy of the task. Their `save` — the task's state kept before the session is touched (`starting`, `move`, `answering`, `reply`, `ask`) — is the event `task.state`, sent in order before the result. The result in `command.done` is `MoveDone`: the move's value, the task's move fields after it and a pause of the chain (`halt`, with `keep` for a refused model). The memory of the moves — the retry ladder of temporary errors and the sources of a handoff after a session that never answered (BTN-650) — is the machine's, shared by all moves; the launch journal goes through the outbox as for any launch.
- **The hub** (`HubMoves`, `src/machine/tasks.ts`) copies the move fields (`fieldsOf`/`applyFields`: `sessionId`, `resumedAt`, `limit`, `starting`, `move`, `answering`, `reply`, `ask`, `message`) from `task.state` and the result into its `CurrentTask` and saves the chain's state, as `save` did in the hub's process. A link error (`machine.command*`) pauses the chain, or for an answer leaves it undelivered, as a failed move would.
- **Only when there is work.** `follow` is sent when the mirror shows the machine something to do — a refused model, a move under way, a limit held or hit, a checkpoint (`followDue`); `guard` when there is a hold or evidence of paid usage (`guardDue`). Otherwise a step would send a command per chain.
- **Without the hub** (BTN-1226). A machine of its own (`wireMachineSide` with `alone`, only `src/machine-service.ts`: the hub's own machine never loses its link) keeps the hub's last move call of each task of an active chain (`HeldMove`: the task, its `MoveContext` and `base`, the move fields the hub is known to hold) and the hub's last brief, in `machine_state` as `moves.held` and `brief.kept`, read back at the start before the link's (`MachineMoves.start`, `BriefCopy.keep`; a kept brief is not `received`, so the hub's own still comes before a chain step). While the link is not `online`, every `ALONE_TICK_MS` (15 s) it makes a step's guard and follow of each held task by its own facts (`followDue`, `guardDue` over its local port), as long as its newest brief has the task as its project's current one of a chain not paused; one move of a task at a time, the hub's and its own. The end of such a move is `task.state` with `alone` and, when it paused the chain, `halt`: the hub takes the fields into the task and pauses the chain as on its own move's result, and the machine makes no more moves of that task until the hub's next call. The hub's next step follows from the fields it took, so a continuation made without it is not made again; a call of the hub that still holds the task as before (`base`) goes on from the machine's state instead.
- **In tests** a port without `moves` (the dispatcher's fake ports) has `taskMoves` run the same code in the hub's process; the service always goes through the link.

## The mirror

The snapshot members of the port read `MachineFacts` (`src/machine/facts.ts`), values the machine computes with its local port for every key the chain may ask about: per task with a session (`live`, `busy`, `midTurn`, `shell`, `asked`, `silentSince`, `limited`, `overage`, `handoff`, `sessionBlock`, model refusals by session), per project (packages, the tracker's server, check reports) and per "run" — the project's default and each task whose run differs (`account`, `launchBlock`, `limitReset`, `modelWeek`, `limitsUnread`, the model). The reads with a free time are computed by the hub: `accountAt` from the posted account ledger, `limitReopenedAt` from the posted limits; `limitResetAfter` is a table by the sessions a limit stopped, because the call has side effects on the machine. `lastSession` is the hub's own launch journal.

- **The snapshot** of every connection replaces the mirror whole (`{boot, rev, facts}`: `boot` names the machine's process, `rev` grows with each post). Between snapshots the event `facts` carries the entries that changed (`patchOf`, `applyPatch`); one from another `boot` or not newer than the mirror is dropped.
- **The page's task folders** (BTN-1246): `works` is `TaskWorks.view` by project and task, `diffs` the lines of each task's branch (`TaskWorks.diffs`, BTN-1424), `gitFound` the repositories found in projects without git; the machine reads its folders on its own clock (`assemblePollWorks`, a project once the brief lists its tasks) and the page's state reads both from the mirror.
- **The page's sessions and chat** are the `sessions` and `mailbox` sections, keyed by session id. Each session carries its `SessionView`, including its current action and feed; each mailbox carries its messages and the listens/steers flags. Changes and removals go in the same patches as the chain's facts, and a reconnect replaces both sections. These live views stay in memory, as before; the retained session windows and chat messages use the record events above. The hub broadcasts a changed mirror, and the local monitor and mailbox publish on change as well as at the regular catch-up points. The page's state takes the sessions of every mirror, the own machine's first and then each machine elsewhere's (`LinkedMachine.sessions`, `allSessions` in `src/machine/page.ts`, BTN-1314): `sessions`, the runs' accounts, agents and compactions in `taskSessions` (an ended session's agent is its account folder's, since one e-mail may be signed in to two agents, BTN-1341), the tray's questions and the checkpoint's window. So a task a machine elsewhere runs leaves its start ("loading") at the first transcript line that machine posts, its row shows the session's lamp and its panel the session, as on the hub (`dev:fake` `?chain=elsewhere`). A session two mirrors show is the first one's.
- **The page's accounts** (BTN-1220): `panel` is the accounts panel (`AccountWatcher.view` with `missing` read with it), posted whole when anything in it changed; `usage` is by account folder beside `limits`; `owners` gives, for each session of the launch journal and each live agent, its account folder (the agent's, else the transcript's, `TranscriptOwners`); `compactions` the compactions counted in a transcript. The hub reads all of them, and the sessions and the mailbox, through `PageReads` (`src/machine/page.ts`, `RemoteMachine.page`): `wireGetState` and the tray, the built-in tracker's and the tasks server's "is a session live", and the replies from the page (`createChat`: `liveView`, `midTurn`, `steering`). A change the machine's watchers see — accounts, limits, transcripts' owners, a CLI copy, a login block — has the machine post at once (`machineChanged` in `src/service.ts`), so the page does not wait for `PUBLISH_EVERY_MS`. The mailbox's own settling (`settleMail`, `machineLive`) stays on the machine's reads: it runs right after the monitor's read, before the mirror has it.
- **Freshness.** The machine posts its facts before every `command.done`, so the mirror is never older than a result the chain acts on; every `PUBLISH_EVERY_MS` (5 s); and, in one process, before every step of the chain, every command and query of the page (`ServerDeps.catchUp`) and every reply to a session from the page, a tracker or the mailbox (`createChat`): `MachinePort.catchUp` has the machine post what changed and waits until the hub took it, so each reads the machine as it is now. A new entry point that reads the port outside a step catches up first. So do Start and Resume themselves (`assembleStartChain`, `assembleChainControl`, BTN-1550): they admit a chain by the mirror's launch block at once, and callers past the page's route — the first run's demo right after it refreshes the accounts, the e2e harness — found the accounts told within the settle window not there yet (`account.activeGone`). Without a connection `catchUp` does not wait. A machine elsewhere will have a mirror as fresh as its last event.
- **Which posts read** (BTN-1475). A command that changes something (`launch`, a move, `account.*`, `chat.*`…) always reads the facts before its result. A change told outside a command (`MachineTell.changed`: the session monitor, the limits, the accounts, the packages) is `MachineRunner.changed`: posted at once when the last read began `SETTLE_MS` (250 ms) ago or earlier, otherwise once that window is up, in one read for everything told by then. The own machine's catch-up before a step and a query (`MachinePort`'s queries, `transcript.*`) go through `MachineRunner.refresh`, which reads only after a change told or once the last read is `FRESH_MS` (1 s) old; otherwise it waits for the post under way. A command of the page and a chat reply catch up whole (`catchUp(true)`, `publish`): the user's next look must see what the command did. So a fact that changes without telling (a time passing) reaches the mirror within a second of the next step, or at once with the next command that changes something. Before this every post of the facts woke a step, whose catch-up read them again and posted what time had changed, so the machine read its facts about 1.4 times a second, 5% of a core (profile of 2026-11-22); the page's requests and every query read them too.
- **Whose packages hold a launch.** `packagesBlocked` and `packagesPause` of a task are asked of the machine its lane went to (`machinePool`, BTN-1475), not of the own one: the own machine's packages of a project it does not run may be unready or failing (a server that is not set up here), and that would hold the other machine's lane for good. Before BTN-1517 a hub taken off the project's pool also had its probes of the project's hub servers refused. The page reads the own machine's packages from the state's `packages`, so for a lane elsewhere the chain writes what holds it into the lane (`ActiveChain.packagesWait`, BTN-1524): `packagesHeld` of the pool names the machine and gives its gateway and the enabled packages with their problems (`Packages.held`, the facts' `packagesHeld`); a machine older than the field only says it is held, and the page names the machine alone.
- **Cost.** The facts are computed several times a second (every step catches up), each time for every project and every task with its own run, so a read in them must not search the disk per call. One computation runs inside `RunnerDeps.scope`: the accounts view is built once for it (`AccountWatcher.batch`, which otherwise builds it on every read, reading every folder's files) and the tasks with a session are grouped by project once; a launch's check of the CLI copy reads `cliCopy.state`, not `view`, which looks for the system binary. Without these the facts took the whole event loop (2026-11-16, 20 projects: requests 16 s, the gateway's probes timing out, the event log filled with "does not answer"). The same scope computes each `choiceFor` once (`ChoiceFor.pass`, BTN-1223): a run's six members ask for it, and an OpenCode choice reads its folder's `auth.json`, which `readAuth` keeps while the file's size and time stay (BTN-1475). Posts asked while one waits for its turn share it (`MachineRunner.publish`): its read has not begun, so each caller still gets the machine as it is after its call. `patchOf` compares entries with `sameJson`, not by writing both out as JSON.
- **Per task, without a scan** (BTN-1254). The facts ask about every task that ever had a session on the machine (1147 sessions on 2026-11-17, 1142 of them finished), so a per-task read must not scan the sessions or the agents: `liveView`, `liveSession`, `modelRefusal`, `shell`, the turn status and the mailbox's steering go through `sessions/view-index.ts`, built once per list (the monitor replaces both lists whole on each tick); a transcript's summary is kept until its next line (`TranscriptFold.summary`). The same scope checks each project's package set once (`PackageService.pass`, with the key pool built once per check: `keyPool` copies the whole environment); a CLI's search among the npm global folders is kept `NPM_BINARY_TTL_MS` (15 s, `npmCliBinary`), so an install is seen that much later; the CLI check's lease resolves no path while no check runs. Before these one computation took about 2 s and ran every 5 s: the thread was busy 66% of the time, with stretches up to 4.3 s.
- **Per project, not per listed task** (BTN-1317). A project's brief lists all its tracker's tasks (about 16 000 on 2026-11-18), so `runs` first keeps only the tasks with their own run (`brief.runOf`) and compares the choice of those alone. In a pass `choiceFor` reads the project's settings here (`runHere`) once per project and each hub folder's folder here (`folderOf`) once per key; `foldersHere` reads each folder's e-mail through `AccountWatcher.shownEmailOf`, never `view`: outside a batch — the page's packages state, the badge — each `view` read every folder's files again. `hubRoutes` (`src/packages/hub.ts`) builds a project's key pool once for all its servers. Before these the thread was busy 91% of the time with the page open, with stretches up to 11 s, and every command and query of the page waited behind them.

## Tasks to machines

- `project_machines` is the pool: the machines a project may run on, each with `enabled`. `machine_tasks` is which machine runs which task: written with the task's launch (`Assignments.assign`), removed when its place there is cleaned up (`finish`), by "Reassign" ("A machine gone") and with the project (`forgetProjectRows`). Both are the hub's own record, never a status (invariant 2): the tracker does not know about machines.
- A connection's snapshot squares the machine's rows (`Assignments.reconcile`, `RemoteMachine`'s `held`), once the machine has read its sessions — at the snapshot, or at the first post after it that says so: a row of a task the snapshot does not name at all goes, a task with a live session there and no row (or another machine's) gets one; every change is a line in the log. A task whose session stopped is still named and keeps its row until `finish`. Between connections the rows follow only the launches and the cleanups.
- `AssignedTasks` (`src/tracker/source.ts`) is the contract a machine's chain will read its work through, next to the trackers': "the tasks assigned to me, in this order" — `Assignments.assigned(machine)` gives them project by project in the chain's order. Nothing asks it yet: the hub's chain decides and launches on each machine through the pool (below).

## The pool

BTN-993: the hub's one chain runs the tasks of a project on the machines of its pool, several at once. With one machine and `width` 1 nothing changes: at most `parallel` projects, one task each.

- **Lanes.** A project's running tasks are its lanes: several `ActiveChain`s of one project in `active`, each with its `machine` (none — the own one) and its own current task, pause, waits and handoff; `Dispatcher.step` runs each lane as it ran a chain (`src/chain/lanes.ts`). The first is the project's head: only it fixes a red `main` and carries a release project in. A lane takes no task a sibling lane holds, none another machine holds (`machine_tasks`, a machine gone or revoked too, "A machine gone" below) and none its machine cannot run, nor what depends on them. "Skip", "New session", an answer and a restart find the lane by the task they name; "Stop", "Resume" and "Stop after the turn" take every lane of the project. A lane with nothing left ends alone; the last one ends the chain, unless a task is left that only another machine may take — then the project waits at the head of the queue.
- **Two numbers.** A machine's capacity is how many of the hub's tasks it runs at once: the own machine's is `parallel`, a machine elsewhere's is its `machines.capacity` (step 56, `null` — 1); both are set on the machine's page ("The machine's page" below). A project's `width` (`docs/settings.md`, 1 by default) is how many of its tasks run at once. A paused lane, one winding down, fixing only or held by a red `main` widens nothing (`widens`).
- **Pulling.** Each machine with a free place pulls, the own one first, then the machines elsewhere that are online and have read their sessions (`MachineNetwork.takers`): it gets a lane of the first project by the chain's order — the active ones, then the queue — whose pool has it turned on (`project_machines.enabled`; a project with no pool runs on the own machine only), whose lanes are fewer than its width and which has a ready task the machine may run (`LanePlacement.placeFor`, `src/chain/placement.ts`). Each new lane of a running project is a line in the log.
- **May run.** A machine runs a task when it has an account folder of the task's agent (its run's provider, else the project's), or when no other machine of the pool has one: with one machine the chain falls back to another agent as before (`chainMachines`, `src/machine/chain-machines.ts`). OS, hardware and environment are not matched (BTN-1000).
- **The project's account on a machine** (BTN-1311). The run names the hub's account folder; a machine finds its own folder of the same account, not of the same name. The brief's `accounts` (`briefAccounts`, `src/machine/account-here.ts`) tells by each hub folder its agent, its claude.ai account (`oauthAccount.accountUuid`, or `LongToken.account` of a long token) and its e-mail; the machine's `choiceFor` (`ChoiceContext.folderOf`, `src/service/accounts.ts`) takes the folder of that name when it is of the same account, else a full sign-in of the account, else a long token of it (`folderHere`); with no account told, the e-mail of the agent's folders; with neither told (a long token with no `sameAs`, BTN-1512), only a folder of the same name and agent, none here being the account absent rather than a key passed on to fail `account.activeGone`. It reads the brief it holds, so a machine off the link chooses the same. A folder of the same name and another account is not taken. None there — the choice keeps its provider with `absent` and no fallback, and the launch is refused `machines.accountAbsent`, named by the hub's chain with the machine and the account's e-mail, its button "Add account" with that machine picked (`addOn`, `web/src/pages/noticeFix.ts`). The pool counts such a machine as one that cannot run the task (`lacks`, `chainMachines`): its lane stays free and the project is not paused while another machine of the pool has the account; with none, the first machine takes it and its lane pauses with that notice.
- **The port by task.** `machinePool` (`src/machine/pool.ts`) is the chain's one `MachinePort` over every machine: a launch and every call about a task go to its `machine_tasks` row, which the lane writes (`ChainMachines.bind`) before the launch; a call about a session to the machine that has it (its sessions, then the launch journal); a call about a folder to the machine whose session works there; the project's main, fix and carry sessions, the sync and the account reads to the own machine. A machine whose port is missing (not connected since the hub started, or revoked) falls back to the own one; so a lane on a revoked machine ends before anything is asked of it (below).
- **A task merged on a machine elsewhere** (BTN-1313). Its session merges into that machine's main, which reaches the remote only with the cleanup after Done. So the merge closer (`MergeCloser`, the tracker's read) asks the task's machine, not the hub's checkout: `LinkedMachine.mergedElsewhere` sends `port.merged` (the own commits of its branches, `mergedCommits`) to the machine of the `machine_tasks` row. A machine off the link answers none at once, so a read never waits for it, and the task closes at a read after it is back. The tracker's Done then brings the cleanup to that machine (`finish`), which brings its main together with the remote's and pushes it under the lock (BTN-995). The own machine's tasks, and those of a machine with no port, are asked of the hub's checkout as before.
- **The launch log remembers the machine.** `LaunchEntry.machine` is the task's `machine_tasks` row at the launch, else the own machine; the sessions of a task carry it (`TaskSession.machine`). The page's state names every machine the hub ever had (`machineNames`) and each lane's machine; where there is more than one, a chain row shows the machines its task ran on, oldest first, the lane's now last (`Workstation → Home server`, `web/src/ui/MachineTag.tsx`, each name in its machine's colour and a link to its page; `dev:fake` `?chain=lanes`).
- **Lanes by component** (BTN-1273): the project's switch `componentLanes` (`docs/settings.md`), off by default. On, a lane takes no task of the tracker component that a task held by a sibling lane of the project is in (`heldFrom`, `src/chain/lanes.ts`), so tasks at once seldom edit the same files; what depends on such a task waits too, as for any held one. A task without a component goes as before, beside any lane. The component is the task's name of it in a tracker that keeps them (`TrackerTask.component`: Huly, Jira's first one); elsewhere no task has one and the switch changes nothing. Lanes are not bound to a component: each takes the first task by the order that no sibling's component holds back.

## Past a limit

BTN-996: whether a task leaves a machine whose limit is spent is the shared switch `switchOnLimit`, "Go on where a limit is left" (`docs/settings.md`), off by default. Pulling alone settles nothing: a machine whose window is spent asks for no task, and another would take it anyway.

- **Off** — a limit is no reason to move. The lane waits on its machine for the reset (`limitUntil`, as before); a project of width 1 waits with it, and no other machine gets its tasks, since the lane is still there (`placeFor`).
- **On** — a lane whose next task would wait for its machine's limit (`limitReset` or the model's week of the task's run there) goes to the first listed machine that has a free place, serves the project, may run the task and has limit left for it (`ChainMachines.hasLimit`: the account's limits read, no window spent, no model week; `moveOffLimit`, `src/chain/limit-moves.ts`). The lane's `machine` and the task's `machine_tasks` row change, a line goes to the log and an entry `eventLog.limitMoved` (the machines by name) to the event log. No such machine — the lane waits as with the switch off.
- **Only a task never launched moves**: one with an entry in the launch journal stays with its machine, its worktree and its sessions; a session stopped by a limit is continued there (`docs/sessions/limits.md`). Fix and carry sessions never move.
- **Width over 1** — the lanes on other machines are the plain pull; the switch moves only the waiting lane, and only to a machine with a free place.
- **Whose machines.** Machines of different people, each on an account of their own, would need no switch; until machines have owners (BTN-502) every machine counts as one person's, so the switch decides for all of them. Turning it on shows the warning on provider terms first (BTN-125's text); the switch of accounts on one machine (BTN-125) is not built yet, and the setting shows only while the hub has more than one machine.

## The main branch on machines

BTN-1567: a project's main branch (`branch`, `docs/settings.md`) is one for its checkout on the hub and its folders on the machines elsewhere of its pool. `BranchControl` (`src/projects/branch-control.ts`) reaches those machines through `BranchMachines`, built on the hub by `branchMachines` (`src/service/branch-machines.ts`) from the machine network.

- **A save moves every folder.** A new branch saved on the page goes first to each machine of the pool turned on, the own one apart (its folder is the hub's checkout), one by one: the command `branch.move` (`branchHere`, `src/machine/branch-here.ts`) fetches the folder's remotes with the project's credentials, so a branch only on a remote is taken with `--track`, then moves it by the hub's rules (`shiftBranch`, `src/projects/branch-move.ts`) and answers what undoes it (`BranchShift`). Then the hub's checkout moves and the key is written. A machine off the link refuses the save (`branch.machineOffline`: turn it on or off in the pool); one that cannot move, a dirty tree say, refuses it with its name and git's reason (`branch.machineFailed`); a refusal of the hub's checkout too. Each refusal puts back the machines already moved (`branch.back`, `shiftBack`: the folder goes where it stood, a branch the move made is dropped). There is no move when a machine comes back: a machine left on the old branch shows the drift below.
- **The checkouts.** A machine elsewhere tells in its facts the branch each folder of its projects with git stands on (`MachineFacts.checkouts`, `null` — detached; `CheckoutWatch`), read at each brief changed, after a command and every 30 s (`CHECKOUT_READ_MS`), so a folder switched by hand shows within that. The hub's own machine does not tell them: its checkout is read as before. The machine tells the branch, not a drift: the hub compares it with its own `branch`, so a save has no false drift before the machine's next brief.
- **The drift of a machine** is `EvenKeelState.machineDrift` (project → machine → `BranchDrift`, `BranchControl.machineDrift`), for the machines of the project's pool turned on. The page shows it as a band on the machine's page and over the rows of the project's "Machines" tab (`BranchDriftBand` with `machine`), with the same two buttons: "Put the folder back" sends `project/branch/restore` with `machine` (`branch.move` on that machine), "Make it the main branch" sends `project/branch/adopt` with `machine`, a save of the machine's branch as any new one (the hub's checkout and the other machines go there too). While the drift lasts the machine serves none of the project's tasks (`held` of `chainMachines`, `src/machine/chain-machines.ts`); a task it holds goes on.
- **Busy.** The refusal `branch.busy` counts a task in hand on any machine (the chain's state is one) and a session of the project's launches mid-turn on a machine elsewhere (its mirror's lamp `working`), besides the own machine's.

## After a green main

## A machine gone

BTN-1270. A machine elsewhere that went off the link, or was revoked, keeps its tasks: their `machine_tasks` rows stay, so no lane takes them (`ChainMachines.holder` names it either way), and the chain never moves them by itself — the machine may come back with the work it did meanwhile. Only a person moves one, with "Reassign".

- **Its lanes.** A lane on a machine merely away stays: the chain waits for it as for any session it cannot read. A lane on a revoked machine ends at the next step (`goneLanes`, `leaveLane` in `src/chain/lanes.ts`): nothing reaches its session any more, and `machinePool` would send its calls to the own machine. Its task is not released; a project left without a lane goes to the head of the queue, so its other tasks go on on the other machines.
- **What the page shows.** The state's `stranded` (`Reassigner.stranded`, `src/service/reassign.ts`) lists, by project, the tasks whose row names a machine elsewhere that is not connected (`MachineNetwork.connected`) or is revoked, each with whether the task's branch is on the remote: `git ls-remote` in the hub's folder of the project, asked behind and again after `PUSHED_FRESH_MS` (a minute), a new answer broadcasting the state. A chain row of such a task without a lane carries "Reassign" (`web/src/pages/ChainList.tsx`), off with a tip saying why while the branch is not known to be there; `dev:fake` `?chain=stranded`.
- **"Reassign"** (`chain/reassign`, `Reassigner.reassign`) asks the remote again and refuses by `reassignable` (`src/machine/reassign.ts`): no machine elsewhere holds the task (`reassign.notHeld`), its machine is connected (`reassign.machineOnline`), the repository has no remote (`reassign.noRemote`), the remote did not answer (`reassign.remoteUnknown`) or lacks the branch (`reassign.notPushed`). Otherwise the row goes, a `task_moves` row keeps the machine left and the branch (step 57, `TaskMoves`, `src/machine/task-moves.ts`), and `Dispatcher.moved` ends the task's lane if it still has one. The pull then gives the task to the first machine with a free place that may run it — never the machine it left (`ChainMachines.runs`).
- **The first launch elsewhere.** While the move has not launched, the hub's brief of the launch carries `restore` (`LaunchBrief`, built in `remoteOf.brief` of `machine-link.ts`): the branch and the text the start prompt ends with — where the task came from (`moved` of the prompts) and the last handoff note the hub keeps (`lastHandoffNote`, BTN-1046), whole. The machine first fetches the branch from its remote over any local one (`restoreBranch`, `src/git/push.ts`; a refusal is `reassign.notRestored` and pauses the lane), then prepares the worktree as usual: an existing branch is brought back into it. The launch marks the move launched; the cleanup after Done (`released`) drops it with the row.
- **The old machine back.** Squaring its snapshot (`Assignments.reconcile`) never gives it a task moved off it, a live session there notwithstanding: the task stays where it went, `HeldChanges.refused` is a line in the log, and that session is left alone (invariant 1) — the person stops it. Its work after the last push is not merged anywhere: the new machine started from the pushed branch, and a later push of the old one is refused as not a fast-forward.
- **What is lost.** Whatever the machine had not pushed: the commits of a turn still running, since the branch goes to the remote at the end of each turn as well as at a handoff, checkpoint or stop (`docs/chain/worktrees.md`, "Task branches on the remote"), and anything a refused push left behind. A branch the machine never pushed cannot move at all; the person brings the machine back or finishes the task there.

## Account limits

BTN-991: the hub holds the picture of each claude.ai account's limits, and one place polls `/usage` per account, so two machines signed in to one account do not both poll its token (`docs/sessions/limits.md`; whether a 429 counts per token or per account does not matter then).

- **The account** of a Claude folder is `oauthAccount.accountUuid` of the `.claude.json` the CLI reads with it (`AccountIdentities`, `src/limits/identity.ts`, read again at most every 30 s). The machine posts it in the facts' `identities` section by folder (`AccountTie`): the account, its e-mail, whether its watcher could poll the folder (`LimitsWatcher.pollable`: a full sign-in, not a long token, not an API key) and whether it skips it now. A long-token folder has no `oauthAccount`: it is posted under the hub's account its token was said to be of (`LongToken.account`, BTN-1002; `accountTie`), never as a poller, so it gets the poller's limits in `picture` and its sessions' windows reach the account's other machines. An account only long tokens are signed in to has no poller: each machine knows it from its sessions alone. Codex, OpenCode and Copilot folders are not in it and each machine polls them as before.
- **The poller** (`AccountPolls`, `src/limits/polls.ts`) is chosen among the machines on the link whose folder of the account could be polled: the hub's own machine whenever it is one of them; otherwise the machine named before, while it stays on the link; otherwise the first by id, a line in the log. A machine that went off the link gives the account to another. An account none can poll has no poller and nobody skips it.
- **The plan** is the command `limits.plan` (`LimitsPlan`): `skip` — the folders whose account another machine polls, sent whole when it changes; `picture` — by folder, the newest limits another machine posted of the folder's account, sent once per time and only when newer than what the machine itself posted, so a picture handed over and posted back is no news. The hub works it out at every change of the mirror and at a machine's going offline; a new connection forgets what the machine was told, and the first plan of every machine but the hub's own carries `skip`, an empty list too (BTN-1247), so a machine elsewhere always gets the plan it waits for. A command that fails makes the hub tell everything again.
- **On the machine** `LimitsWatcher.plan` keeps the skip list and the handed limits (`hub`, newest of all sources as any other): a skipped folder is not polled, its chain does not wait for a first poll of it (`unread`), and its health is "ok". A folder given back is polled no sooner than a poll interval later: its poller may just have polled it. Handed limits are not saved to `account_limits`; the hub hands them again after a restart. A machine off the link keeps the plan it had: it takes a limit from the session's refusal, as before, and does not start polling an account another machine polls.
- **One account on two machines** — the hub logs once that they share one limit window, and `AccountPolls.shared()` lists them for the page of machines (BTN-993).
- **Limits from sessions only** (BTN-1266). A machine's long-token folder whose account has no poller (`AccountPolls.poller`, handed in as `polled`) — or, with no account known, no `sameAs` folder on a full sign-in in its panel — is `MachineAccount.sessionsOnly` (`sessionsOnly` in `src/service/machine-page.ts`), in `machineSignIns` and on the machine's page. The page marks it "limits from sessions only", the tip the notice `usage.sessionsOnly`: under the hub's account row in the machine's line (`machineTokens`, the hub's folder signed out too — its "Sign in" is the fix), and on the machine's page with "Sign in fully" (`fullSignIn`: again in the hub's Claude folder of the e-mail, else a new one). A hub long-token row gets the same line with "Sign in fully" while no Claude folder of the hub is on a full sign-in (`hubSessionsOnly`): such a token names no account, so a full sign-in of another one also takes the mark off.
- **A token's windows against the poll** (BTN-1267). At each plan the hub compares what a long-token folder's own sessions told (`polls: false`, `source: 'sdk'`; the poll it was handed and posts back is no evidence) with the newest poll (`source: 'usage'`) of a full sign-in of the same account (`tokenWindowsDiffer`, `src/limits/token-windows.ts`): a five hours or a week whose reset stands more than an hour off (`/usage` names it to the hour), or whose later reading spent over 5 points less than the earlier one, while neither window had ended before the other reading. Then the account `AccountPolls.differs`: a line in the log names the window, the machines and that the full sign-in's poll is taken, and `newestElsewhere` stops handing the token folders' session windows to other machines, so the hub's picture does not swing between the two; a later pair that agrees takes it back, with a line. The machine's page marks such a folder "limits differ from the hub's" (`MachineAccount.limitsDiffer`), the notice `usage.tokenWindowsDiffer` in its tip, and "New token" next to it opens the token window for the hub's full sign-in of the e-mail. `dev:fake`: `/machines/machine-2?machines=tokenDiffer`.
- **With one machine** the hub's own machine polls every account and nothing is ever sent: behaviour does not change.
- **A machine elsewhere** (BTN-1247) starts its watcher with `planFirst`: no round of polls before the hub's first `limits.plan`, or it might poll what another machine polls. The hub plans its accounts with the own machine's (`MachineNetwork.accounts()` in `steerLimits`) and sends the plan through that machine's own `RemoteMachine` (`tellLimits`).

## Machines elsewhere

The hub's door for machines (BTN-1242; the page's window of machines is BTN-1056, the machine's own service BTN-1247). `MachineNetwork` (`src/service/machine-network.ts`) is a second `HubEnd` over the same store, serving every machine but the hub's own (`HubOptions.admits`), behind the HTTPS carrier of `hub-server.ts`.

- **The setting** "Hub address for machines" (`machinesAddress`, shared, empty by default): the name or IP machines reach the hub by, a port after it when a router or proxy forwards another one. Set — the hub listens on all interfaces at `EVEN_KEEL_MACHINES_PORT` (4749, read at the start); empty — it does not listen, and no string can be issued. It applies live: a change of the address changes only the strings issued from then on. The page offers the names of `allowedHosts`, the addresses of the network cards (no loopback, no link-local, with the card's name) and `EVEN_KEEL_HOST` when it is no wildcard (`machines/addresses`). A name behind a proxy works only if the proxy passes the machines' port too.
- **The connection string** is the token of "The token and the certificate", issued with no machine yet joined: good for `INVITE_MS` (30 min) and for one join. `HubEnd.invite` revokes every string issued before and never joined with ("Issue again"); `revoke` takes a string or a joined machine back. The machine sends it once, to `POST /link/join` with `{api, about}`, and gets its own secret in exchange (`{secret}`); the string's secret works for nothing else — a stream or a post with it is refused `token` — and a second join with it is `used`, a late one `expired`.
- **`even-keel join <string> [--root <folder>]`** (`src/machine/join.ts`) refuses, in order: a test instance (`EVEN_KEEL_TEST_INSTANCE=1` — the sandbox and bench kits set it, so no test installation reaches a real hub), a line that is not a string, a running service of the installation (the machine's database has one owner), an installation that has projects (it is a hub; a machine joins from a clean one). Then it makes the folder of projects, sends the report, keeps the new token and the root in the machine's database and writes `state/machine-link.json` (hub, machine, root, the time of the join). `even-keel status` prints that file.
- **The installer** (BTN-1243): `even-keel install --machine <string> [--root <folder>] [--service]` (`src/cli-args.ts`, `src/cli-install.ts`) refuses a Node older than 24 and a machine without git, joins in a child process (the tray start) or inside `install.sh`/`install.ps1 -Machine -Projects`, then installs the service; a checkout builds `build:machine` (no page). A string already joined with (`joinedWith`) is not joined again. `install-check.js --machine` waits for 10 s of a running process instead of the page, the CLI 30 s for `contactAt`; the tray shows the contact's age. `machines/invite` answers with `command`, `npx even-keel@<hub version> install --machine <string>`. Guide: `docs/guide/setup.md`, "A machine of a hub".
- **Docker** (BTN-1440, guide `docs/guide/docker.md`, "Machines"). The hub's `compose.yaml` publishes 4749 at `${EVEN_KEEL_MACHINES_PUBLISH:-127.0.0.1}` (a Compose variable only). The templates `compose.machine.yaml` (service `machine`, the tag required) and `compose.hub-machine.yaml` (`even-keel` and `machine`, a volume each, one tag) share the image. Every service sets `hostname:` (`even-keel`, `even-keel-machine`; BTN-1496, held by `src/service/compose.test.ts`): a string issued without a name names the machine by `about.host` at the join (`HubStore.joined`), and the hub's own machine by `os.hostname()`, which Docker would otherwise make the container's ID. `machines/invite` also answers `docker` (`dockerJoinOf` in `src/cli-install.ts`): `EVEN_KEEL_IMAGE_TAG=<hub version>` and `docker compose run --rm machine even-keel join <string>`; the window's step 2 switches between npx and Docker (Docker first when the page's `updates.blocked` is `container`) and shows them with `docker compose up -d`. A hub in a container (`inContainer`) offers no network card in `machines/addresses`, its cards being the container's. The `machine` service sets `EVEN_KEEL_MACHINE=1`: `src/start.ts` then waits for `machine-link.json` (`waitForJoin`, 5 s) instead of starting a hub, holding nothing, so the join from `compose run` goes through and the process goes on as the machine. A machine in the hub's Compose project reaches it as `even-keel`: the pinned fingerprint makes the name irrelevant to TLS. Its report has `container: true`; `HubFollower` with `container` stays `manual` at the hub's version without a launch, and the machine's page replaces `even-keel update` (and the `manual` band) with the `.env` line, `docker compose pull && docker compose up -d` and `docker compose build --pull && docker compose up -d`.
- **The report** (`MachineAbout`, `src/machine/about.ts`): the host, the OS, the versions of Even Keel, Node and git, the agent CLIs found on `PATH` with their versions, whether git has a name and an email, the folder of projects. It goes with the join and with every handshake.
- **Projects.** The window "Add a machine" puts a joined machine into the pools of projects with the command `machines/join` (`{machine, projects: [{project, clone?, folder?}]}`, BTN-1263; `clone` absent — `auto`, the folder decides, BTN-1298): one step job of kind `machine-join` (`joinPlan`, `src/service/machine-pool.ts`) runs the steps of `connectPlan` ("Connect" above) for each project in turn, each step id `<step>@<project>` (`stepOf` in `src/jobs/model.ts`), the subject the machine's name. A failed step stops the whole job, and Retry goes on from it; Cancel takes back only the projects not yet turned on, so the ones already connected stay. `MachineNetwork.attach` (the folder named as the hub's under the machine's root, no checks) is left only to tests. The chain's tasks go to the machine by "The pool".
- **Each machine's own mirror** (BTN-1247). `MachineNetwork` keeps, per machine elsewhere, a peer: its own `RemoteMachine` (made by `remoteOf` in `machine-link.ts` with the same deps as the own machine's), its `BriefSender` and the folders of its pool. A snapshot of that machine fills its mirror, never the own machine's; its launches write its `machine_tasks` rows and its snapshots square them, as the own machine's (`assigned`, `released`, `held`). The chain reaches it through the peer's `port`, and the peer's `capacity` is read at each snapshot. An event goes to its `RemoteMachine` too, except three: `machine.selection` is only a line in the log (the hub's settings follow its own machine, not one elsewhere), `tasks.write` goes to `HubMcp.write` with the machine's id, and `sessions.read` sends its brief. A `/link/mcp` request goes to `HubMcp.relay` with the machine's id, so the pool decides what it may reach; going offline replans the limits. A revoked machine's peer is dropped.
- **The version** (BTN-994). The hub gives tasks only to a machine of its own version of Even Keel: `MachineNetwork.takers` leaves out a peer whose last report (`MachineAbout.evenKeel`, read at each snapshot, `versionOf`) names another, a line in the log at the change. Such a machine stays on the link and finishes the tasks it holds; its card's lamp is blocked with "Even Keel X, not the hub's" (`MachineCard.otherVersion`), and its page (`MachinePage.hubVersion`) says to install the hub's version there with the command `even-keel update <hub's version>`, which on a machine waits for the hub's contact, not for a page. The CLIs are not compared: a machine takes its `cli.<provider>` from the brief and downloads a checked copy itself on the hub's consent ("The checked CLI" below). Another API version is refused at the handshake as before (`VersionRefusal`), but the hub first keeps the report the machine sent, so its page names both versions, and the refusal carries the hub's version of Even Keel, which the machine's log names with the command. Updating from the hub's page is not built (a "Refresh" button is BTN-994's follow-up); a machine of another API version catches up by itself, next bullet.
- **Catching up with the hub** (BTN-1275, `HubFollower` in `src/updates/follow.ts`). The `version` refusal carries the hub's commit (`commit`, HEAD of a git checkout read once at the hub's start, `headOf`) and its version of Even Keel (`evenKeel`); `MachineOptions.versionRefused` hands each refusal to the follower, which launches the update process at most once per process. A git checkout runs mode `follow` (`src/updates/runner.ts`): stop, `git fetch --all --tags`, `git checkout --detach <hub's commit>` — the hub's commit, not the newest `dev`, since the hub may have skipped a red one or rolled back; the branch does not move, a rollback puts it back — `npm ci` only when the lock changed, `npm run build:machine`, start, and the answer is a `contactAt` in `machine-link.json` newer than the run's start; a rollback waits for no answer, the hub would refuse the old version anyway. A global npm package installs `even-keel@<hub's version>` the same way. What keeps a machine where it is goes into its report as `MachineAbout.follow` `{to, stuck}`: `failed` (`logs/update.json` names a `follow` to this target that failed: the same commit is never tried again, only another one), `dirty` (tracked changes in the checkout), `manual` (no service manager, a package not installed globally, a hub without a commit for a checkout — it does not move by tag). The machine's page shows it as a warning band, and its fact "Even Keel" names a checkout's commit next to the version (`MachineAbout.commit`, "X · abc1234").
- **What a machine elsewhere tells** (BTN-1559, `src/machine/scope.ts`). Its session monitor reads every session of its account folders, and a computer that served a project before — a hub moved there — holds hundreds of old ones; told whole, they made the snapshot over the link's limit (`MAX_BODY_BYTES`, 8 MB). So `wireMachineSide` with `alone` wraps the runner's reads in `scopedDeps(deps, factsScope(…))`, computed once per pass: the facts name only a task the hub asks about — one its brief lists (`brief.tasks`), a chain's current one, a warm one, a fix, a carry or a chat (`isFixName`, `isCarryName`, `isChatName`) — one with a session not finished, and one whose session was active in the last `RECENT_MS` (24 h), which the cleanup after Done reads. Its sessions are their views and their journal's launches; `mailbox`, `owners` and `compactions` are cut to those sessions. The hub's own machine tells everything: its facts never cross the network. A task done more than a day ago on a machine elsewhere has no session view in the facts any more, so its history window does not name it.
- **Its brief** is `hubBrief` with the machine's own folders: for each project of its pool, `folderUnder(root, repo)` inside the root its report names. It is sent at the connection, after an attachment and at the service's 5 s publishing tick (`MachineNetwork.catchUp`), never inside a chain step's catch-up, so a step never waits on a machine elsewhere. The one exception is a command whose result rests on the task's run (BTN-1514): before `launch`, `launchFix`, `launchCarry`, `relay`, `resume`, `modelBlock` and a move that may start a session, `RemoteMachine` awaits `briefNow`, which sends the brief if it changed (a no-op otherwise) and waits until the machine took it. Without it a run set just before `chain/start` reached the launch only at the next tick, and the session started on the project's model. The own machine has the same `briefNow`, though its step's catch-up mostly covers it.
- **The checked CLI** (BTN-1516). A machine elsewhere has no page to give consent to a checked copy on, so the hub's consent is its: the brief's `cliConsent` is the hub's own `cli.downloaded` (`copies().consented()`, the own machine's), and a machine's `copies` (`CopyConsent.hub`) fetches a missing checked copy of a provider in it as of its own consent, at once when a new brief brings it (`resume` in `wireMachineSide`) and at every `blocked`; the copy it finishes is added to its own `cli.downloaded`. The own machine keeps `agent.copyMissing`, whose download the hub's page has. Both codes lift by themselves. A failed download on a machine elsewhere falls back to Yours there only, as every local choice (`machine.selection`).
- **The page's API:** queries `machines/addresses`, `machines/list` (`MachineView`: the report, online, the projects, a pending string's time, the folders another machine holds — `taken`), `machines/invite` (`{name, address?, color?, proxied?}` → `MachineInvite`: the string, the machine's id, its time and the command; an `address` other than the setting's is saved as `machinesAddress` first, through `ConfigStore.saveMachinesAddress`, and the door applied, so the window issues with one call; a `color` outside the palette is refused, a good one is stored as the machine's colour); commands `machines/revoke`, `machines/join`, `machines/takeOver` ("The folder's mark"), `machines/login`, `machines/code`, `machines/cancel` ("Signing in on a machine"). A string issued with no name names its machine by the report's host at the join (`HubStore.joined`).
- **The window "Add a machine"** (BTN-1056, `web/src/layout/AddMachineDialog.tsx`, `MachineJoined.tsx`): opened by `?addMachine=new` from "+ Machine" at the foot of the machines panel; with one machine there is no panel, so the same button stands under the address in Settings → Interface until a second machine joins (`poolShown`). ## The folder's mark

BTN-1244: a project's folder is served by one machine, whatever host and path reach it — a container, a network share, a second installation on the same repository. The machine that takes the folder writes `.git/even-keel-machine`, one line of JSON `{machine, name}`: its id and the name it knows itself by (the own machine's is its row's, the host's name; a machine elsewhere writes its host's). `GitFolderMarks` (`src/machine/marks.ts`) keeps it in the repository's common git folder, so a linked worktree shares its checkout's mark; a folder without git has none and is free; a mark that cannot be read is nobody's.

- **When.** The own machine claims each project's folder in `agree` (`src/service/machine-link.ts`), before it consents to it. A machine elsewhere claims at `projects.assign` and, at every start of its process (`MachineEnd.settleMarks`), again for every folder it consented to: one that got its git since is marked then.
- **Another machine's mark** leaves the folder without the consent. The machine's end keeps the holder by project (`MachineEnd.hold`) and refuses a command of that project with `command.refused` and the reason `taken`, the holder's id and name; `RemoteMachine` makes it `machines.folderTaken` (`{name, owner}`), and the chain pauses on it. An assignment refused so is the event `projects.taken` (`FolderTaken`); `MachineNetwork.holds` keeps it in memory by machine and project for `MachineView.taken`, named as the hub names the holder when it knows it, else by the mark. A machine that gives a folder up at its start because another took it over loses the consent too.
- **A mark of a machine this hub revoked** is free: the hub sends the assignment again with `takeOver` itself, and the own machine claims over it at once. That is how a new own machine (`ownMachine`) takes the folders of the one it replaced.
- **Off with the token.** A machine whose token the hub refuses (`token`: revoked or unknown) takes its marks off every folder it consented to (`FolderMarks.release`), once per run of refusals; another machine's mark stays.
- **Taking over** a dead machine's folder is explicit: `machines/takeOver {machine?, project, owner}`, after the page's confirmation, with `owner` the holder its refusal named; no `machine` is the own one. The hub checks that the holder it keeps for the project is still `owner` (else `machines.notTaken`, so a confirmed takeover never overwrites a newer mark), then the own machine claims with `takeOver` at the next `agree`, a machine elsewhere gets `projects.assign` with `{takeOver: owner}` in its payload. The pause stays until the chain is resumed. On the page it is `TakeOverButton` (`web/src/pages/TakeOverButton.tsx`, BTN-1261): under the pause `machines.folderTaken` through `noticeFixOf` (`{to: 'takeOver', owner, name}`), with a confirmation naming the machine that loses the folder, then `chain/resume`; a refusal (`machines.notTaken`) stays in the dialog. A machine's page (`/machines/<id>`, `web/src/pages/MachinePage.tsx`, BTN-1262) puts the same button, with `machine` and no resume, into the warning band of each of its `MachinePage.taken`.
- **A test instance** (`EVEN_KEEL_TEST_INSTANCE=1`, `folderMarks`) neither writes nor reads marks; `dev:fake` has no machine at all.

## The machine's process

BTN-1247: an installation that joined a hub starts as a machine. `src/start.ts` checks `state/machine-link.json` (`joinedHub`, written by `join`) and, when it is there, loads `src/machine-service.ts` instead of the state database's preparation and the service.

- **What runs:** `assembleMachineHost` with `planFirst` and its own `Writes`, then `wireMachineSide` over `httpsTransport` with the token kept in the machine's database (`storedHub`) and the report with its root (`storedRoot`), and the host's own starts and ticks of the service (monitor, transcripts' owners, limits, CLI versions and copies, the account watcher, VS Code, packages, keep-warm, CLI checks, the task folders). No state database, no page or its server, no trackers, no Tally database, no dispatcher. The gateway turns to the hub (`throughHub`) once the hub took the first snapshot, so the first brief may have named the hub's servers; then the machine's Tally collector starts and sends its rows over `POST /link/tally` (BTN-1280, `docs/tally.md`, "Machines elsewhere").
- **One per installation.** `holdInstallation` (`src/service/machine-process.ts`) claims `state/even-keel/` as the service does (`src/storage/claim.ts`) with a loopback port that only proves the process lives, so `join` and a second start see it runs; no `pgdata/` is made there, and `readStateDatabase` finds nothing. Without a kept token the process says to join again and exits 1.
- **`contactAt`.** `contactKeeper` writes the time of the last contact into `machine-link.json` when the link comes up, then at most once a minute; `even-keel status` prints it.
- **The sessions' hooks.** With no page here, `HookReceiver` (`src/machine/hook-receiver.ts`) listens at the page's address and carries the hooks' routes to the hub's page (BTN-1260, below, "Hooks through the hub"); the sessions' `EVEN_KEEL_URL` is its address.
- **What is not there yet.** The chain launches on no machine but the hub's own (BTN-993).

## The two directions

The machine opens every connection, so a machine behind NAT needs no open port.

- **Down, hub → machine:** one long answer to `POST /link/stream`, server-sent events. A frame is `hello` (the handshake), `ping` (the hub's pulse) or `command`.
- **Up, machine → hub:** `POST /link/snapshot` (what the machine holds right now) and `POST /link/events` (its numbered events; an empty one is the machine's pulse). `POST /link/mcp` (`{connection, request}`) carries a session's request to an MCP server of the hub and answers it with `{status, headers, body}`. It is not numbered and is not kept, so a lost answer is the session's to repeat. It counts as the machine's pulse, and its failure leaves the connection alone (below, "MCP through the hub"). `POST /link/hook` (`{connection, request: {method, path, body?}}`) is the same for a session's hook asking the hub's page, answered with `{status, body}` (below, "Hooks through the hub"). `POST /link/tally` (`{connection, rows}` → `{taken}`) carries the rows of the machine's Tally collector, as unnumbered as these two: its receipt is the machine's read mark (`docs/tally.md`, "Machines elsewhere"). `POST /link/credentials` (`{connection, project, urls}` → `{credentials}`, BTN-1541, API 17) asks the tokens of a project's HTTPS remotes for one git call of the machine (`docs/ci.md`, "Git over HTTPS"): the machine keeps them only in that call's environment and asks again for the next, so a token never lands on its disk. The hub answers only for a project the machine has a folder of in `project_machines`, turned on or off (a connect checks the right to push before it turns the folder on), or that the hub's connect is cloning onto it now (`MachineNetwork.clones`); any other gets `[]` and a log line (`hubGitCredentials`, `src/service/git-credentials.ts`). The own machine asks the same through `LocalTransport`. No answer — the hub away or a refusal — and git goes on the machine's own credentials. `POST /link/skills` (`{connection, install}` → `{skills}`, BTN-1565, API 18) gives a machine elsewhere the files of the hub's install of the user's skills package, whose marketplace is the hub's `state/skills/` (`docs/packages.md`, "The user's own skills"); `null` — the hub holds no folder of that install.

Every request carries `Authorization: Bearer <machine id>.<secret>`. A refusal is JSON `{refused}` under a status: `token` 401 (unknown, wrong or revoked), `version` 426 (the API versions differ; the body is `{refused, api, evenKeel?, commit?}` — the hub's API version, its version of Even Keel and the commit of its checkout — and never changes in any later API version, since a machine of any version must read it to catch up, "Catching up with the hub"), `connection` 409 (the post names a connection that is no longer the machine's), `expired` and `used` 410 (a connection string past its time or already joined with, "Machines elsewhere").

The handshake: the machine's `{api, host, lastCommand, about?}` is the body of the stream's request, `about` its report about itself (`MachineAbout`), kept by the hub on every handshake that has it; the hub's first frame is `hello` with `{api, connection, heartbeatMs, lastEvent}`. `API_VERSION` is compared before anything else; a change of a frame, a post or their meaning is a new version.

## MCP through the hub

BTN-990 keeps the keys on the hub. A server that holds a key runs only in the hub, and the machine's gateway carries its requests over the link (`McpGateway.throughHub`, `src/packages/gateway.ts`). Such a server has a key, a token or OAuth in its target, or it is a tracker whose deletes Protection refuses (`hubOwned`). The tasks server always runs in the hub, and so does the memory server (BTN-1029, `docs/sessions/memory.md`): the project memory is the hub's records, and its routes are always in `Packages.hubServers()`, so a machine's session reads and writes the same records as the hub's, each write with the version it read. Servers without a key, such as Playwright or a files server, run on the machine.

- **Two gateways in one process.** The machine's `Packages` gateway listens on `EVEN_KEEL_MCP_PORT`; the separate `PackageHub` gateway listens on a free port of 127.0.0.1, which only the link asks. The machine's gateway switches to the link before its listener starts (`LinkedMachine.start`). The hub reads the local package catalog independently, resolves its targets with its profiles and publishes only route names in the brief. The machine does not resolve keys for those routes; its probes ask the hub through the link.
- **The pool.** The hub admits a machine only to the servers of the projects it is briefed: the own machine to every project of the hub, a machine elsewhere to each project with its row in `project_machines`, turned on or off (`placedIn`). It admits a machine to `/tasks` with no project only when it is briefed every project; anything else gets 403 (`HubMcp`, `src/service/hub-mcp.ts`). A row turned off counts (BTN-1517): the machine keeps the project in its brief, installs and probes its packages (the connection's `machine-packages` step runs before `machine-enable`) and finishes the task it holds, its session's tasks and memory calls included. Before, its probes asked the memory server of a project it was only placed in, or just taken off, and the log had `a server of a project outside its pool: refused`. Now a refusal means a machine taken out of the pool, asking until its next brief, or one asking what it was never briefed; the log has it once per machine and project until the machine is admitted there again (BTN-1325). The hub reads the answer whole before it sends it back, so no stream is opened through the hub, and a GET is answered 405.
- **Files.** The machine's tasks server (`MachineTasks`, `src/taskmcp/machine.ts`) reads the files a call attaches from the session's folder and sends them in the call's `_meta` (`even-keel/session`, `src/taskmcp/carried.ts`). The hub returns the files `task_read` downloaded in the result's `_meta` (`even-keel/files`). The machine writes them into the folder's `.temp/task-files/` and puts their paths in place of the hub's tokens. The limit is `attachmentLimit` on both sides, and the hub never reads or writes a folder of the machine.
- **The handoff note.** For `handoff_write` the machine stamps the writer, the task's live session there, into the same `_meta`, and the hub's link adds the header `x-even-keel-machine`; the hub keeps the note only from the task's newest launch (`docs/sessions/checkpoint.md`, "The note kept with Even Keel").
- **The hub away.** A write (`task_comment`, `task_update`, `tasks_create`, `handoff_write`) is kept in the outbox as the event `tasks.write` with its files already read. The session is told that the call goes later and must not be repeated. The hub makes the write once it takes the event: an unreachable gateway throws, and the machine sends the event again; any answer of the tasks server, a refusal included, ends it in the log. A write waits for the outbox to drain before it goes, so it never overtakes a kept one. A read of the session's own task is answered from the machine's last read of it, otherwise from the brief its last start had (`Briefed.kept`). Other tasks and every other server's call get a tool error saying that the hub is unreachable, and other requests get a JSON-RPC error. `initialize`, `ping` and the tools list are still answered. Nothing here touches a session: it is the answer to the session's own call.
- **Server ownership without keys** (BTN-1238). The hub computes `Packages.hubServers()`: route paths for every retained install, including a task's pins, excluding the tasks server that has its own stand-in. `GatewayHub.servers` supplies this serializable list to the machine. The machine checks it before resolving any target, so a hub route needs neither an installed local server nor the hub's keys. The list is carried in `hub.brief` and refreshed at catch-up; the machine reads its copy, never the hub's packages. Pool, OAuth and Protection changes are reflected in the next list.
- **The catalog of a machine elsewhere** (BTN-1299). Its `state/packages.json` follows the hub's: the brief's `packages` (`CatalogBrief`, `src/packages/follow.ts`) carries every package its projects get, each with the hub's current install, and those projects' sets; the own machine gets none, as it shares the hub's file. `Packages.follow` takes the definitions and replaces the sets, marks every other package removed (the built-in one stays) and installs each hub install it lacks under the hub's id (`materialize`): a plugin copied from the machine's own marketplace, a pinned server at the hub's npm version, nothing for a server the hub runs for every project there. The same id is what makes a hub route the machine's session asks name the install the hub resolves. A failed install is tried again by a brief ten minutes on; a new set or a hub Update comes with the next brief. The settings of a package whose servers all run in the hub stay there. The connection's step `machine-packages` refuses a project whose tracker's server no package brings (`pool.packagesNoTracker`). End to end, from the connection to a task done on the machine: `src/e2e/elsewhere.test.ts` (BTN-1306, `docs/chain/e2e.md`).
- **The launch brief** (BTN-1238). `RemoteMachine` prepares the brief on the hub and sends it as the fourth argument of `MachinePort.launch`: `LaunchBrief.prompt` is the tracker location, vocabulary and task text (or the instruction to read it); `task` is the structured `TaskBrief` for offline answers; `own: true` — `Intake.outsider` says the task is not an outsider's, asked at every brief (BTN-1419), so the machine pushes its branch without the guarded files check ([worktrees](chain/worktrees.md)). `Briefed.apply` on the machine adds and retains only this received data, without reading a tracker. A later launch without task text clears the old structured brief. The hub also supplies a brief with a direct `relay` or a session move that may hand off (`MoveContext.brief`), so a handoff after a machine restart still has the task's text. An explicit handoff prepares it anew; a regular `follow` reuses the hub's prepared brief, reading it once if the hub restarted, so a waiting limit does not poll the tracker for its text. Replies and paid-usage guards need no brief. A move names its task in `MoveCall.task`, which the hub prepares the brief for and routes the move by. Without a new payload a handoff uses the machine's retained brief; each in-memory cache holds at most 200 tasks and does not survive its process restart. With neither, `apply` throws `chain.briefMissing` for a chain task (a fix or carry session has its report instead) and the chain pauses (BTN-1252): a launch before its session starts, a handoff before it stops the session it replaces, never a prompt without the task.

## Hooks through the hub

BTN-1260. A session's hooks (`plugins/agent-bridge/hooks/evenkeel.mjs`, the trackers' calibration hooks) ask Even Keel's page at `EVEN_KEEL_URL`: the checkpoint and the note, the checks, the standards, the chat's mail, the permission requests and a project's calibration. A machine elsewhere has no page, so its process answers them with the hub's.

- **The receiver.** `HookReceiver` (`src/machine/hook-receiver.ts`) listens on 127.0.0.1 at the page's port (`EVEN_KEEL_PORT`), or on a free port when another process holds it (the log says which); `assembleMachineHost` gets its address as `listen`, so the sessions are given it. It turns away a request with an `Origin` or a `Host` that is not loopback (403), answers `GET /api/state` itself with the machine's own accounts panel (the settings guard of its account folders reads it), keeps `POST /api/sessions/<id>/inbox` on the machine (`MachineHost.inboxes`, BTN-1322: the inbox socket's token never goes over the link, and the hub's page takes the route from loopback only, `docs/sessions/chat.md`), sets the mail hook's `inbox` flag on the hub's answer by the machine's own `Inboxes` (BTN-1506) and carries only a route of `hookRouteOf` (`src/link/hooks.ts`) through `MachineEnd.hook`; any other path is 404, a body over 1 MiB is 413.
- **The hub away.** No connection, a failed or refused post: the receiver answers 503 at once, and each hook does what it does when Even Keel does not answer (nothing; the permission hook keeps asking). `HOOK_TIMEOUT_MS` (1.8 s) bounds the post's connection and answer, under the hooks' own 5 s.
- **The hub's side.** `HubHooks` (`src/service/hub-hooks.ts`, `peers.hook` in `machine-link.ts`) checks the route again and refuses (403) a session another machine holds: the hub's own machine by its page's sessions, a machine elsewhere by its mirror (`MachineNetwork.holderOf`). A session no mirror shows yet is let through, since the mirror lags the launch. It asks the hub's own page (`localUrlOf(listen)`) the path as a session of the hub's machine would; no page is 503, a failed request 502.
- **Not kept.** As `/link/mcp`, a hook's request is not numbered and not kept, and it counts as the machine's pulse. The chat's mail is marked delivered when the hub's page answered the hub, so an answer lost on the link loses that message's delivery into the session.
- **A fallback port.** On a free port instead of `EVEN_KEEL_PORT` the sessions get the right address, but the settings guard of the account folders (`src/account/share.ts`) still names the port of the environment.

## Numbers and what is kept

- **Commands** are numbered per machine by the hub (`machines.last_command`) and kept in `machine_commands` until the machine names their number as taken: in `lastCommand` of its handshake and of every post. At a connection the hub sends, after `hello`, every kept command above the machine's `lastCommand`. All of one machine's work on the hub runs in the order it was called (`queued`), so a command sent during a reconnect never overtakes the ones sent again. A command sent from inside the machine's own turn — a handler of its event or snapshot, such as the take-over of a folder marked by a revoked machine — is part of that turn and is not queued again (an `AsyncLocalStorage` of the turn): queued behind the post that waits for it, it stood the machine's queue for good, every later post and `open` with it (BTN-1555). Work a turn leaves running past its end is queued as usual. A handler still must not await a command's result: that comes in a later post.
- **A command runs at most once.** The machine records its number before the handler runs (`commandReceived`); a number at or below the last recorded one is a repeat and is dropped. Commands are taken in order; a handler ends before the next command is taken unless the machine is `concurrent` ("The chain over the link"). A machine that stopped between the record and the end does not run the command again: at its next start it reports `command.interrupted` and the hub decides. So a command's handler must be safe to lose, not safe to repeat.
- **Events** are numbered by the machine (the `outbox` table's identity) and kept there until the hub's answer names their number in `lastEvent`. The hub takes an event once: one at or below `machines.last_event` is dropped; a handler that throws leaves the event and the ones after it untaken, and the machine brings them again with its next pulse. Events go in order, `EVENT_BATCH` a post.
- **The snapshot** is not an event and has no number: it is the state now, posted first on every connection, before any event, and never queued. The hub reconciles what it believes about the machine with it.
- **The body limit** (BTN-1559). A post but an MCP call is at most `MAX_BODY_BYTES` (8 MB, `protocol.ts`); the hub answers a larger one 413 with a line in its log (the path and the declared size), but cuts the connection mid-body, so the machine mostly saw only `ECONNRESET`. The transport therefore never sends a larger body: it throws `TooLarge` with `partsOf(body)` (`src/link/body-size.ts`), the sizes of the body's parts level by level down the largest one (events by type), and takes a 413 the same way. An events post over it goes again in halves; a single event over it alone is dropped with a line in the log — it would hold back every event after it, and the next snapshot tells the state. A snapshot over it is told once in the log with its parts, the notice `link.tooLarge`, and tried again at the 30 s pace until one fits.
- One machine has one connection. A new stream of the same machine closes the older one, whose posts are then refused with `connection`.

The machine's store belongs to its connection token. If the hub has taken more events than the store ever numbered (the store was made anew under an old token), the numbering jumps past the hub's `lastEvent`; events written before that first handshake are lost, so a machine set up anew takes a new token.

## Pulse and reconnect

- The hub writes a `ping` frame every `HEARTBEAT_MS` (20 s); the machine posts its events, or an empty post, at the same pace. The pace is the hub's: the machine takes `heartbeatMs` from `hello`.
- `MISSED_PULSES` (2) intervals without a frame — the machine closes the stream and connects again; the same time without a post — the hub closes the machine's connection (`handlers.offline`). The lock of the main branch will later hang on exactly this.
- A post that fails or times out breaks the connection too: the machine does not go on over a link that carries one direction only.
- The pause before an attempt is 1, 2, 4 … 30 s and starts over at 1 s after a handshake. After a refusal of the token or the version the machine keeps trying at the 30 s pace: the token may be issued again, the hub updated.
- A machine without its hub keeps what it has to say in the outbox and goes on; what it may do without the hub is the roles' matter, not the link's.

`MachineEnd.status()` is `{state, notice?}`: `offline`, `connecting`, `online` (the snapshot was taken), and a message code for the machine's page — `link.token`, `link.version`, `link.buffered`, `link.tooLarge`.

## Behind a proxy

A reverse proxy, a corporate proxy or an antivirus that inspects HTTPS may hold a streamed answer in its buffer. The connection is then alive, the hub writes its pulse, and the machine sees nothing: by the pulse alone that is a break, a reconnect, and the same again forever.

- The stream's answer carries `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no` (nginx turns its buffering off for that answer by itself), the headers are flushed at once, Nagle's algorithm is off and each frame is one write.
- The machine tells the case apart: the connection opened and **not one frame** came over it in two pulse intervals — `link.buffered` and one line in the log, not only a quiet reconnect. The notice stays through the reconnects and goes with the first `ping` that arrives: the handshake alone could be the proxy's first flush.
- An idle timeout (about 100 s on a Cloudflare tunnel, `proxy_read_timeout` 60 s on nginx) is covered by the pulse in the stream itself, which is more frequent than either.

The guide ("A machine of a hub", "Behind a proxy") tells the user the same: buffering off and a long read timeout, for nginx `proxy_buffering off; proxy_read_timeout 1h;`. A proxy that ends TLS shows the machine its own certificate, so only a token with an empty fingerprint passes it (below). The window "Add a machine" issues one with its switch "Behind a proxy with a public certificate" (BTN-1286): `machines/invite` with `proxied: true`, and `MachineNetwork.invite` leaves the fingerprint out and reads an address without a port as 443, the proxy's, not `EVEN_KEEL_MACHINES_PORT`. The switch is not a setting: the browser keeps its last state (`even-keel.machines.proxied` in `localStorage`), and a string issued without it is pinned as before. The hub does not listen differently behind such a proxy: the door stays HTTPS with the self-signed certificate on all interfaces, and the proxy goes to it over HTTPS without verifying (nginx by default, a Cloudflare tunnel with `noTLSVerify`, Caddy with `tls_insecure_skip_verify`). A plain HTTP door on loopback for a proxy on the same computer was weighed and left out: one more listener and a door without TLS for a gain the HTTPS one already gives.

## The token and the certificate

The hub has a port of its own for machines, apart from the page's address, and a self-signed certificate made at the first need (`hubIdentity`: ECDSA P-256, built by hand in `cert.ts` without a dependency, kept with its key in `service_state` as `machines.certificate`). A new certificate turns every machine away, so it is made once.

A connection token is one line, `ekm1.` and base64url JSON `{hub, fingerprint, machine, secret}`: the hub's address for machines, the SHA-256 of the certificate, the machine's id and its secret. `HubEnd.issue` is the only moment the secret exists on the hub; the store keeps its SHA-256 (`machines.secret_hash`). `HubEnd.revoke` stops the token and closes the connection; the row stays.

- **Machine → hub** is the token: unknown, wrong or revoked — `token`.
- **Hub → machine** is the pinned certificate. The machine connects (`connectPinned`), compares the certificate's SHA-256 with the token's and only then writes anything: the secret goes to no other server, and a command comes from no other hub. The chain and the name are not looked at. Node's `checkServerIdentity` cannot do this: it is not called when the chain does not verify.
- **An empty fingerprint** is a hub behind a certificate of a public authority, such as a proxy that ends TLS and renews its certificate: the machine then verifies the certificate as any HTTPS one. An HTTPS-inspecting proxy in front of a pinned token is refused, as it should be.
- Each post is a connection of its own (the check comes before the request); the stream is one more.

## What a command may touch

A command names what it touches in its own fields, `project` (the project's id) and `folder`, never in its payload. The machine keeps the projects and folders it agreed to (`consents`) and checks every command before the handler (`refusalOf`):

- no `project` and no `folder` — a command about the machine itself, run;
- a `project` the machine did not agree to — refused, `project`;
- a `folder` outside the folders agreed for that project (compared through `src/paths.ts`), or a `folder` without a `project` — refused, `folder`.

A refused command is reported as the event `command.refused` with its number, type and reason; a handler's throw as `command.failed`. So a hub in the wrong hands gets the agreed folders, not the machine's disk. Consent is given on the machine (`MachineStore.agree`), by whatever connects a project to it; a hub's command cannot give it, with one exception the machine itself chose:

- **The folder of projects.** A machine that joined a hub agreed to one folder at `join` (`--root`, by default `projects` in the user's home), kept in `identity` as `root`. The hub's `projects.assign` (`ASSIGN_COMMAND`, `{project, folder}`) is agreed to by the machine itself when the folder is inside that root — the consent is recorded and the command runs — and refused `folder` otherwise; a machine with no root refuses it `project`. So the hub can give a machine a project, never a folder outside what its owner named.

## The stores

- **Hub:** the state database, step 51 — `machines` and `machine_commands`, step 52 — `project_machines` and `machine_tasks`, step 55 — `machines.invite_expires`, `joined_at` and `about` (`docs/storage.md`), through `DatabaseHubStore` and `Assignments`.
- **Machine:** a PGlite database of its own with its own steps (`MACHINE_STEPS`, opened by `openMachineDatabase`, numbered like the state database's and never edited once merged): `outbox` (the unsent events), `commands` (the numbers taken, with the newest `KEPT_COMMANDS` finished ones), `consents` and `identity` (the connection token, and after a `join` the hub's address as `hub` and the folder of projects as `root`), and since step 3 `account_limits`, `account_settings` and `machine_state` ("The machine's stores"). Its folder is `state/machine/`, next to the hub's `state/even-keel/` and apart from it in a process that is both: a machine apart from its hub will have the same folder with nothing to move. It is not in the backups: lost or out of step with the state database, it is made anew with a new own machine.
