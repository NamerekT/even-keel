# What has not been verified: OpenCode

One area of [What has not been verified](../unverified.md), which says what an entry is, how to report a run into one and where a new one goes. What has been checked in this area is in [What has been verified: OpenCode](../verified/opencode.md).

## OpenCode Go limits (BTN-803)

No live Go account. The usage endpoint, three windows and 403 handling come from the MIT t3code reader; the 401 shape and relative refusal come from public issues linked in `test/fixtures/limits/README.md`. Unit tests cover the synthetic 200/403/401 answers, account creation/replacement without sending the key to OpenAI, invalid data and relative resets. The add/replacement dialogs and the three-window, expired-key and no-Go states were checked only on fake UI data. **Check:** on the checked OpenCode 1.19.5, add a Console Go key from the page, compare each window and reset with Console (especially whether `percent` is 0–100 or 0–1), wait for a real refusal and compare its duration with the chain's reset, restart with a saved snapshot, then replace a revoked key and try a Console key without Go. OpenCode 2's credential table is outside this implementation. **Symptoms:** percentages off by 100×, no windows, a wrong reset or replacement rejected. **Workaround:** compare limits in Console; use Replace key for 401, and pause the chain or switch accounts if the displayed reset or percentage is wrong.

## The OpenRouter balance by a management key (BTN-868)

An OpenRouter account's management key is checked by `GET openrouter.ai/api/v1/credits` before it is kept, and the balance is `total_credits − total_usage` of that answer (`docs/accounts.md`, "The OpenCode folders"). Checked only by tests on a faked answer. Never seen with a real key: `/credits` answering a management key 200 with `data.total_credits` and `data.total_usage`, the key a session runs on refused there with 403 and a revoked management key with 401 (both taken from OpenRouter's documentation), and the card's balance matching the one on openrouter.ai after a session spent from the key (whether `total_usage` lags as `usage` might, see the entry below). Check: add a management key to an OpenCode account on an OpenRouter key with money, then the session key in its place, then a revoked one, and compare the card with OpenRouter's credits page. **Workaround:** a working key refused on saving cannot be kept — the account works without it; a wrong balance — remove the key from the row's menu and open an issue with the log line.

## The real spend of a session on an OpenRouter key (BTN-860)

Even Keel reads an OpenRouter key's `usage` before each turn of a chain session, at each turn's end and once a minute for 10 minutes after the account's last turn, and gives the growth to the session that ran (`docs/tally.md`, "Cost"). Seen live on 2026-11-08 and 2026-11-11 ([verified log](../verified/opencode.md)): `usage` grows within about a minute of a turn's end, a lone session's real spend equals the key's growth, and two sessions at once on one key are marked shared. Still not seen: a real spend that differs from the estimate — on `deepseek/deepseek-v4.1-flash-1017` OpenRouter routes to an endpoint priced as the catalogue and without a time-of-day price, so real and estimate matched to the cent by day and in the evening, and a model whose route has a discount was not found; that the key used by hand outside the chain during those 10 minutes is counted to the chain's last session (expected, a known limit); that the sum on `/stats` matches OpenRouter's activity page and the tip there; that a session whose turn goes on through a service restart is marked shared and shows the estimate (BTN-871: found live as a real spend of $0.0066 against $0.0497, fixed by tests only). Check: restart the service in the middle of a turn of such a session and read `key_spends` through Tally's `sql.mjs`; compare one task on `/stats` with openrouter.ai's activity page.

## The OpenCode auto-compaction window (BTN-856)

With `openCodeAutoCompactWindow` set below the chosen model's catalogue window, a chain session's `OPENCODE_CONFIG_CONTENT` gives the model `limit = { context: W, input: W, output }` and `compaction.reserved = 32000`. Checked on OpenCode 1.19.5 (2026-11-08): `opencode models opencode --verbose` with such a config shows `big-pickle` at `150000/150000/32000` in place of `200000/160000/32000`, and the config accepts `compaction.reserved`. Read from the code, not seen in a session: OpenCode compacting at `W − 32000` (`SessionCompaction.isOverflow`), a resume keeping the window from the session's record, and the page showing `W` as the session's window. If the override is ignored, the session grows up to the model's own window (1M on MiniMax M3.1 Flash) and the checkpoint thresholds, measured against `W`, come long before any compaction. Run a long task on MiniMax with the window at 250000 and watch the session's context fall after ~218000 (BTN-857). **Workaround:** none needed for the checkpoint: its thresholds still ask for a handoff; clear the setting to go back to the model's own window.

## OpenCode on an OpenRouter key (BTN-843)

An `sk-or-` key goes into `auth.json` under `openrouter`, in the form OpenCode 1.19.5's own login code writes for every provider; with a fake key there `opencode models` listed OpenRouter's catalogue (365 models, `openrouter/minimax/minimax-m3.1-flash` among them) on 2026-11-07. Never seen with a real key: `GET openrouter.ai/api/v1/key` answering a working key 200 and a revoked or disabled one 401/403 (taken from OpenRouter's documentation), a chain session's turn on an OpenRouter model, a 402 reaching the session's error as "Insufficient credits" or "requires more credits" and held as `credit`, and the money check's one-token turn on the cheapest paid model answering 402 while the balance is empty. **Workaround:** a working key refused on adding cannot be added, so run the task on another provider and open an issue with the log line; a session held for credit while the key has money — "New session" or switch the account.

## OpenCode stream errors in the account log (BTN-497)

After 30 seconds without an event or changed session row, the adapter reads newly appended account-log bytes for an `ERROR` / `stream error` belonging to that session and newer than its activity. A limit uses the existing limit recovery; another failure exposes a translated notice while preserving the live process for stop/resume. Parser and adapter tests cover attribution, incremental reads, persistence and classification. A real provider refusal under the service was seen on 2026-10-29 ([verified log](../verified/opencode.md)): an OpenAI key at zero, "You have no credits remaining", reached the turn as a stream error, was held as `credit` (BTN-566), and when the task's account was switched the new session started with no process of the old turn left. Still unverified under the service: a free model's limit with its retry plan, and an ordinary stream failure. **Workaround:** answer from the chat or choose "New session" once the turn is idle; otherwise use the existing hang check.

## A spent limit on OpenCode

An OpenCode account signed in to ChatGPT or Copilot has its windows read from the provider (BTN-341, the entry below), so a limit waits for their reset; one on OpenCode Zen has none and no reset time, so the chain tries it again after 15 minutes, doubling the wait up to 4 hours while it keeps hitting the limit (BTN-342, `docs/chain/exceptions.md`, exception 1). The fold recognizes limit text, a 429 `statusCode` or `FreeUsageLimitError`. On 2026-10-27 a real free-model refusal appeared only in the account log as `AI_APICallError: Free usage limit reached`, with no turn event or database error and a process that stayed alive. The log fallback above (BTN-497) covers that path locally; recovery from a fresh real refusal under the service and a limit stored in the database remain unverified. Zen's free limits are published nowhere, so the waits are a guess: a limit that resets in minutes waits up to the next retry, a daily one is tried a few times in vain. **Workaround:** wait for the reset and press "New session".

## OpenCode's Copilot limits (BTN-341)

Since BTN-573 this combination is blocked for all session execution pending a separate live verification. Existing sign-ins and allowance reads stay visible; the assumptions below are retained, not evidence that Copilot sessions are supported.

An OpenCode folder signed in to Copilot is asked `api.github.com/copilot_internal/user` with the `github-copilot` token of its `auth.json`, the one GitHub's editors read (`docs/sessions/limits.md`, "Limits of OpenCode and Copilot"), an internal endpoint whose shape is taken from what others have published. If its answer has no `quota_snapshots` or free-plan counts, the card says the answer was not read, and the chain waits on a limit as before, with no reset time. **Workaround:** none needed for the chain; the card's numbers are on GitHub's site.

The ChatGPT side was checked in Windows Sandbox on 25.10.2026 (OpenCode 1.18.25, a Plus account): the folder's `openai` token got the five-hour and weekly windows from `wham/usage` (`source: "api"`), and the card's pool was the same `chatgpt:<account id>` as the Codex card of that account.

Copilot Free's chat allowance (`limited_user_quotas`, `monthly_quotas`) and the switch of paid plans to AI credits in June 2026 were not seen in an answer: a plan whose allowance moved elsewhere shows "no data".

## The OpenCode model check (BTN-336)

Since BTN-573 `github-copilot/*` is rejected independently of this catalogue check, even if the catalogue is unavailable or lists it. Copilot-only folders are unavailable and the provider is disabled in turn configs until separate live verification; the Copilot uncertainty below remains recorded for that future check.

A launch or a resume on an OpenCode model that `opencode models` of the account does not list is refused: the chain pauses with `chain.unknownModel` (`docs/sessions/models.md`, "Model lists"). Checked from a terminal on OpenCode 1.18.25 on Windows with a free OpenCode Zen account (nine models listed, a made-up one refused), and on ChatGPT Plus in Windows Sandbox on 25.10.2026: the chain launched a task on `openai/gpt-6.1-sol`, one of the 17 `openai/*` models listed; the list omits `gpt-6-sol`, `gpt-6-astra` and `gpt-6-luna`, which Codex's own model list offers the same plan, but `opencode run -m openai/gpt-6-sol` fails there with an `UnknownError`, so refusing them is right. On a ChatGPT Free sign-in under the service (2026-10-29, [verified log](../verified/opencode.md)) the pause came for `openai/gpt-6-luna`, but `opencode models` lists every OpenAI model whatever the plan: `openai/gpt-6.1-sol` passed the check and the provider refused it at the first turn (BTN-584), and the pause's message named other providers' models first (BTN-585). On API keys (2026-10-31) `opencode models` holds every model of Anthropic's `/v1/models` and omits many of OpenAI's, but `opencode run` refuses those itself with `ProviderModelNotFoundError`, so nothing that would run is refused ([verified log](../verified/opencode.md)). Never on a Copilot account, blocked since BTN-573: if `opencode models` there omits a model the account can run (a provider that lists lazily), the task is refused although its session would work. Since BTN-679 the pause lifts by itself once the project's model or the task's label names a model the list has; only the scripted e2e scenario has run it, never a live account: if the pause stays, Resume still starts the task. **Workaround:** leave the model field empty so the session runs on OpenCode's default, and open an issue with the output of `opencode models`.

## OpenCode ChatGPT model filtering (BTN-584)

The subscription filter and fallback pause are covered by tests: visible slugs only, intersection without altering other providers, a complete empty intersection, no requests for API keys, expired/missing tokens without renewal, HTTP/JSON/network failure with one sanitized log line, stored and terminal refusals, account-only catalogue invalidation (including in-flight reads), waiting lamp, settings button, pause before unattended skipping, and replacement followed by resume. The read-only endpoint was checked on 2026-10-29 from a terminal with an existing OpenCode free ChatGPT sign-in: HTTP 200 for `client_version=0.164.0`, visible `gpt-6-luna`, `gpt-5.6-terra`, `gpt-5.6-luna` ([verified log](../verified/opencode.md)). No generation or token renewal was requested. Under the service on 2026-10-31 the Model field of that sign-in suggested only `openai/gpt-5.6-luna` and `openai/gpt-5.6-terra` among `openai/*`.

Not run as a new service chain: a forbidden model prevented before launch, an unavailable/expired endpoint followed by a real provider refusal, the pause and catalogue invalidation, then changing Model/Account or a run label and using New session. Plus and other plan responses were not rechecked. An endpoint change may leave the full OpenCode list available; an incomplete but valid visible list may reject a working model. **Workaround:** select a model known to work on the plan, or another account, change the model on the task's card if it has one, then use New session and resume. Leaving Model empty bypasses preflight and uses OpenCode's default, which can also be refused.

## OpenCode's model by the account's sign-in (BTN-984)

Covered by tests: the slot a folder's `auth.json` keys name, the launch taking that slot's model, the page's slot from the account's `subscriptionType`, and the config and database moving a bare `models.opencode` by its prefix. Not run live: a chain session launched on a folder whose `auth.json` was read at that launch, a folder with several sign-ins (the first of `openai`, `anthropic`, `openrouter`, `github-copilot`, `opencode-go` wins), a sign-in changed while the service runs (the page's slot follows the next status read, the launch reads the file again), and the migration of a live config. If the page and the launch disagree, the session runs a model other than the field shows. **Workaround:** set the model on the task's card, which goes to the session whatever the account.

## A hung OpenCode turn

A live turn that has changed no row of its session and written no event for 30 minutes is taken for hung: the session shows as idle with a note, and writing to it or "New session" kills the turn first (`docs/sessions/opencode.md`). Built from the database's shape and never seen with a real hang: whether OpenCode retrying a refused request touches the rows meanwhile (then the watchdog never fires), and whether a tool that runs longer than 30 minutes, a long build or test run, really writes nothing (then a working turn is taken for hung, and in unattended mode the chain stops waiting for it 10 minutes later). **Workaround:** for a hang the watchdog misses, kill the turn's `opencode` process and press "New session"; a long build that is not hung goes on regardless — nothing stops it, unless someone writes to the session or presses "New session".

## OpenCode sign-in from the page

Since BTN-573 Copilot sign-in is removed from the page and rejected by the server until the combination is verified. The old Copilot sign-in observations below are retained for that future check.

ChatGPT's headless method was checked from the page in Windows Sandbox on 25.10.2026 (OpenCode 1.18.25): the window got the device link and its code, and the sign-in landed in the account's folder. Copilot's `opencode providers login` was run only in a terminal, not through the page: the window shows the CLI output unfolded and looks for a link in it, as for Codex. Copilot first asks between GitHub.com and Enterprise, and Even Keel answers with Enter after 3 seconds; if the question comes later or changes, the sign-in waits for good. **Workaround:** cancel it and sign in in a terminal with the folder's four `XDG_*_HOME` variables pointing into it (`docs/accounts.md`).

## The OpenCode database read while a turn writes

Even Keel and Tally open `opencode.db` read-only while OpenCode writes it in WAL mode. A read during a checkpoint of the WAL may fail with "database is locked"; the feed then keeps its last state until the next poll, and a stats run logs the file as failed and reads it next time. Never seen in the checks.


## OpenCode Protection (BTN-486)

BTN-500 checked OpenCode 1.18.25 on Windows: actual tool denials for the default command patterns, group switches,
custom `*`/`?` patterns, Huly deletion tools through the real gateway, broad account/project allows, and shared and
project rules saved on the running service reaching fresh chain sessions without a restart
([verified.md](../verified.md), Sessions). The local provider emitted predetermined tool calls; no model refusal was
counted as Protection. A safe `rm` executable and MCP stub recorded calls; git pushes used a disposable bare remote.

BTN-501 corrected and rechecked the account/project build-agent override on the same safe fixture: scalar, broad,
explicit MCP-tool and late wildcard allows no longer bypass Protection. Both the source and compiled adapter were
checked; the denied calls reached neither recording stub ([verified.md](../verified.md), Sessions).

On Linux (2026-10-31, a real model in a chain session of the service) the push patterns were refused by OpenCode
itself, `cd . && …` included, but `git -C . push --force` went through (BTN-642), and a Huly comment was deleted
through the server's `invoke_tool` meta-tool, which neither the native rules nor the gateway looked inside (BTN-641,
any agent) ([verified.md](../verified/opencode.md)). Since BTN-641 the gateway looks into the nested call
([Tracker deletes refused by the gateway](packages.md#tracker-deletes-refused-by-the-gateway-btn-541)).
Since BTN-642 the push groups also deny `git -* push …` on Claude and OpenCode and the literal `git -C . push …` and
`git --no-pager push …` on Codex and Copilot. On Linux again (2026-11-02, a real model in a chain session of the
service, [verified](../verified/opencode.md)) OpenCode refused `git -C . push --force` and `git --no-pager push -f`
to a disposable remote, `rm -rf ~/…`, `rm -fr ../…` and `rm -rf /tmp/…` on throwaway folders, and the gateway
refused the same `invoke_tool` delete; `rm -r -f ~/…` ran, as the guide says split flags are outside the rules.
On Linux (EKR-47, 2026-11-04, Codex 0.166.0 in a Docker Desktop container, [verified](../verified/opencode.md)), six native denials were confirmed: the force flags, remote deletion, `cd . && git push --force`, `git -C . push --force` and `git --no-pager push -f`. A plain push created a branch, and `git push origin +HEAD:refs/heads/check-plain` ran; the branch remained at the same commit. This refspec names a non-main branch: the generated Codex rules cover +refspecs of the project's main branch only, as the guide already says. EKR-66 accepted correcting the scenario without broadening the contract: keep the non-main +refspec as an allowed control and check denial of +HEAD:refs/heads/<main branch> on a disposable remote; the Codex main-branch denial has not yet been run live.
On Linux (EKR-48, 2026-11-05, Copilot Checked 1.0.105 in a Docker Desktop container, [verified](../verified/opencode.md)), the same six force/delete spellings received actual CLI denials. A plain push and the non-main +refspec ran as expected. The extra main-branch +refspec required by EKR-66 also ran (Everything up-to-date), exposing missing generated Copilot rules (EKR-74). EKR-74 now passes the project's main branch to the generator and emits five force-refspec prefixes for it. A direct CLI check on the same bench using the adapter's generated arguments refused all five with error.code=denied; plain push, non-main refspecs and a branch with the main name as a prefix ran. Resume also refused the main form and allowed the non-main one. The disposable main ref stayed at an older commit, and the original remote's URL and refs stayed unchanged. This checks the native rules and adapter arguments; a new service-chain launch with the fix has not been run.

Not run: BTN-642's push spellings on Claude and Copilot outside Linux, Codex on other platforms and a live Codex main-branch +refspec denial on Linux, the `rm -rf` groups on macOS, other agents/subagents. Copilot's new main-branch force-refspec rules in a service-chain launch and on other platforms remain open.
**Workaround:** retain server-side branch protection and use disposable targets when checking native rules.
