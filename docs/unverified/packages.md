# What has not been verified: Packages

One area of [What has not been verified](../unverified.md), which says what an entry is, how to report a run into one and where a new one goes. What has been checked in this area is in [What has been verified: Packages](../verified/packages.md).

Checked live on 17.10.2026 (BTN-174) from a second instance in a terminal: plugins installed into Even Keel's state, a Claude chain session with `--strict-mcp-config` and `--plugin-dir` called the Huly server through the gateway, a plugin's hook ran. On 18.10.2026 (BTN-161) the gateway's server (`npx @firfi/huly-mcp`) also started and answered from the Windows service's session 0 of a fresh install, and its chain sessions called the remote GitHub server (a Claude session) and the Linear one (a Codex session) through the gateway, with the headers filled from the tracker profile. The rest:

## "Add to Claude Code" on /tools (BTN-226)

The button runs `claude plugin marketplace add <checkout>` from the service in the default config. Checked on 22.10.2026 on a second instance started from a terminal with an empty default config: the command added the checkout as a `directory` marketplace to that config's `known_marketplaces.json` and the offer went away. On 23.10.2026 the same from the Windows service (session 0) of an npm install in Windows Sandbox, its account's default config knowing no marketplace: the package's global folder was added as a `directory` marketplace and the offer went away. Not from systemd or launchd. If the CLI fails from the service, the banner shows `packages.marketplaceAdd`; if it adds the marketplace to another folder than the one your terminal uses, the banner stays. **Workaround:** run the command the banner shows in your own terminal; chain sessions do not need it either way.

## Packages on Linux and macOS

Installing a package and the gateway's server processes were run on Windows and, for `huly@even-keel`, on Linux (2026-10-31, [verified.md](../verified/packages.md)), and for the GitHub and agent-bridge packages on macOS (BTN-312, 2026-11-03); other packages on Linux and macOS were not run. If `npm` or a server does not start there, the cell shows "install failed" or "no response" and the chain waits.

## The bridge rename with running tasks (BTN-999)

The startup transition from `checkpoint@<own marketplace>` to `agent-bridge@<own marketplace>` is covered by unit tests: retirement and project choices, a single old plugin for pinned tasks across launches and restarts, new tasks on agent-bridge, pruning after release, first seeding and idempotence. Codex's arguments disable a configured old plugin and trust hooks under the new name. An update from 0.2.4 with no task running replaced the project's `checkpoint@even-keel` by the bridge at the first start, and the button's update from 0.2.4 in the middle of a task's turn let that turn end with its Stop hooks and no error, the task close and a new task run after it (2026-11-14, [verified](../verified/updating.md)). Not run live, and left so by choice (2026-11-14): a handoff of a task pinned to the old package, and a restart while such a task is still open; it touches only an update from 0.2.x made in the middle of a long task. If the assumption fails, a task loses its hooks or gets duplicate mail and merge checks. **Workaround:** finish the running tasks before upgrading; use Update or Check on agent-bridge's row in Settings → Packages. For manual Claude configurations, uninstall the old plugin as [setup](../guide/updating.md#plugins) says; installing the bridge by hand is unnecessary.

## Tracker deletes refused by the gateway (BTN-541)

Protection's tracker switches are enforced in the MCP gateway (`docs/packages.md`, "The gateway"), checked by unit tests; live, Claude's and Codex's deletes on GitLab (`delete_issue`) and GitHub (`label_write`), Codex's Huly `invoke_tool` with `toolName: "delete_comment"` and Codex's Linear `delete_comment` were refused, and Claude never sees Huly's delete tools (2026-11-01, [verified log](../verified/packages.md)); an OpenCode chain session's Huly `invoke_tool` with `toolName: "delete_comment"` was refused on Linux (2026-11-02). Jira's Rovo server has no tool named `delete` at all: whatever deletes or irreversibly changes data goes through `executeDestructive` with an operation `name` from `discover` and its `inputs`. On 2026-11-01 Rovo offered no Jira delete operation (`discover` for deleting an issue, a comment or a link returned none; its destructive ones were `manageJiraProjectVersion` and Confluence's `removeConfluenceContentPermissions`). Since BTN-659 `executeDestructive` is refused whatever it runs, so with Jira's switch on archiving a version is refused too; and a tool name in the arguments of a tool that is no dispatcher (`get_tool_schema` with `toolName: "delete_comment"`, which an OpenCode session was refused before) is a read and passes. Assumed: a tracker's server reaches the session under the adapter's `mcpServer` name; a deleting tool has the word `delete` or `destructive` in its name, or takes `method: "delete"` (GitHub's `label_write`, from memory, not read from the server's tool list); Linear's tool list, read on 2026-11-01, has `delete_comment`, `delete_attachment` and `delete_status_update` and nothing else that deletes. A dispatcher — a tool with `invoke`, `call`, `execute` or `run` in its name — is judged by the tool it calls, named in `toolName`, `tool_name`, `name` or `tool`, with its arguments in `arguments`, `args`, `params`, `input` or `inputs` (Huly's `invoke_tool`, BTN-641); Huly's and Rovo's are the only ones seen, GitHub's, GitLab's (`@zereight/mcp-gitlab` 2.3.11 has none) and Linear's have none. Agents other than Claude and Codex are assumed to show the refusal as a failed tool call and to stop there, as those two did. If an assumption is wrong, a delete goes through (a tool named otherwise, a server under another name) or a call that deletes nothing is refused (a tool named with `delete` that only reads). **Workaround:** for a delete you want, turn that tracker off in Sessions → Protection (a Claude session's auto mode may still refuse it: then delete it yourself); for one you do not, keep the tracker's own permissions narrow. To check (after BTN-659): a session on Jira calling `executeDestructive`, with the log line `Protection refused`; an OpenCode session on Huly reaching a delete through `get_tool_schema` first.

## Servers installed with no install scripts (BTN-1131)

A pinned server is installed with `--ignore-scripts` and `--save-exact`, keeping `package-lock.json` in its prefix; checked by unit tests on the npm arguments, the lock's diff and the install records. Installs of `huly@even-keel` and `gitlab@even-keel` without scripts, the switch turned on and off and the servers' `initialize` over stdio were seen on 2026-11-14 ([verified](../verified/packages.md)); the GitHub and Linear packages are remote servers with no npm install. Not run live: those servers' `initialize` behind the gateway and a chain session using them; the dependency notice after an Update that changed a lock (it needs a new upstream version). If it is wrong, a server whose dependency builds or fetches a binary in a script fails to start after its next install, and the chain waits on the package. **Workaround:** turn "Install scripts" on in the package's details and press Check.

## Update all on a stalled service (BTN-1480)

On 2026-11-22 Update all updated `agent-bridge` and the service never logged `installing tasks@even-keel`, while its event loop stalled 5–8 s at a time and tracker calls timed out. Why the second command did not reach `Packages.update` was not found: a request waits for `catchUp(true)` before the command runs, and a command refused before the log (`packages.busy`) or a `fetch` the page lost left no trace once the section was left and its result reset. Since BTN-1480 the run and its failures outlast the section (`web/src/tools/updateAll.ts`), checked by unit tests and on `dev:fake` (`?packages=updateFails&delay=…`, leaving for Interface and back); not seen live on a stalled service. If it is wrong, the button keeps saying "Updating 2 of 2" for as long as the request hangs, or a row is left with its Update and no band. **Workaround:** press the row's own Update; the band, when there is one, names what refused it.

## A waiting chain's server asked again within a minute (BTN-1518)

In the BTN-1441 check (2026-11-22, `0.4.0-rc.1`, a hub in Docker) the hub's own machine was put back into a project's pool after a long time out of it: the hub had refused its probes of `memory` and `tasks` with 403 all that time, the probes had backed off to once an hour, and the chain stood "active" with no task for 15 minutes until a restart, while `initialize` on the same route answered in 56 ms. Since BTN-1518 a failing server of a project whose chain runs is asked at least once a minute, and at once when a brief brings a chain started or resumed (`Probes.result`, `PackagesDeps.waited`, `wireMachineSide`); checked by a unit test of the probes over a real HTTP server, not live. If it is wrong, a chain whose package answers again still waits on it for up to an hour. **Workaround:** stop and start the chain, or restart the service.

## A bridge's GET stream kept alive by a comment (BTN-1543)

The CLI 2.1.330 cut a bridge's `GET` stream ~358 s after it opened and every 360 s after, and closed the transport after three cuts ([packages.md](../packages.md), "The gateway"). Since BTN-1543 each open stream gets `: keep-alive` every 30 s, on the assumption that the cut is the idle timeout of the CLI's `fetch`: checked against Bun 1.3.11's own `fetch` (an idle stream failed at 301 s, one with the comment was still open at 450 s) and by unit tests, not against the CLI's binary. If it is wrong (the CLI's timeout counts the whole request, not its silence), the MCP log of the server still shows `HTTP connection dropped after …s uptime` every ~6 minutes and a new `initialize` every ~18. **Workaround:** none needed, the session reconnects by itself; the drops only make a service restart more likely to lose the server.

## A bridged server through a service restart (BTN-1544)

The CLI 2.1.330 gave a bridged server up about 18 s after its stream dropped, and a restart of the Windows service was down 19–27 s, so a live session lost the server until a resume ([packages.md](../packages.md), "The gateway"). Since BTN-1544 the new process holds the gateway's port from its first seconds and answers what waited once the gateway is ready; checked by unit tests over real sockets, not with a live session through a restart. The assumption is that a request held for the rest of the start is no error to the CLI and its reconnects land in time; if it is wrong (the CLI times a held request out, or node itself takes longer than ~18 s to start), the server's MCP log still ends in `Maximum reconnection attempts` and the server stays `failed`. **Workaround:** resume the session.

## Your own skills for Codex, Copilot and OpenCode from ~/.agents/skills (BTN-1691)

`docs/packages/files.md`, "The user's own skills". Without the package `my-skills@even-keel-skills` the user's skills reach Codex, Copilot and OpenCode only through `~/.agents/skills/<name>`, the links `ConfigCopy` lays into the skill store. Covered by `src/account/agent-skills.test.ts` (links laid, the user's own folders and links elsewhere kept, a link to a deleted skill removed) and `src/memory/git/config-copy.test.ts` (a skill synced from another copy linked after the sync); `skillDirs` passes the home folder's `~/.agents/skills` to OpenCode through `skills.paths`.

Assumed: each of the three reads `~/.agents/skills` of the home folder outside the project, its own account folder notwithstanding: Codex with its `CODEX_HOME` set to an account folder, Copilot with its `COPILOT_HOME`, OpenCode with `OPENCODE_DISABLE_EXTERNAL_SKILLS` through `skills.paths`; and each follows a link (a junction on Windows) to a skill's folder. Only the project's `.agents/skills` was seen read by all three (2026-10-24, `docs/sessions/protection.md`). If not, an agent's chain sessions miss the user's own skills: its sessions' skill listing has none of them.

To check, on the benches: with a skill in `~/.claude/skills` on the bench hub, start the service and see `skills: … linked <name>` in the log and the link in `~/.agents/skills`; then on a chain session of each of Codex, Copilot and OpenCode ask for the list of its skills (`copilot skill list` for Copilot) and see the skill there. Delete the skill and see its link gone after the next sync.
