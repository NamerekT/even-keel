On 18.10.2026 (BTN-161) the gateway's server (`npx @firfi/huly-mcp`) also started and answered from the Windows service's session 0 of a fresh install, and its chain sessions called the remote GitHub server (a Claude session) and the Linear one (a Codex session) through the gateway, with the headers filled from the tracker profile. The rest:

## "Add to Claude Code" on /tools (BTN-226)

The button runs `claude plugin marketplace add <checkout>` from the service in the default config. Checked on 22.10.2026 on a second instance started from a terminal with an empty default config: the command added the checkout as a `directory` marketplace to that config's `known_marketplaces.json` and the offer went away. On 23.10.2026 the same from the Windows service (session 0) of an npm install in Windows Sandbox, its account's default config knowing no marketplace: the package's global folder was added as a `directory` marketplace and the offer went away. Not from systemd or launchd. If the CLI fails from the service, the banner shows `packages.marketplaceAdd`; if it adds the marketplace to another folder than the one your terminal uses, the banner stays. **Workaround:** run the command the banner shows in your own terminal; chain sessions do not need it either way.

## Packages on Linux and macOS

Installing a package and the gateway's server processes were run on Windows and, for `huly@even-keel`, on Linux (2026-10-31, [verified.md](../verified/packages.md)), and for the GitHub and agent-bridge packages on macOS (BTN-312, 2026-11-03); other packages on Linux and macOS were not run. If `npm` or a server does not start there, the cell shows "install failed" or "no response" and the chain waits.

## The bridge rename with running tasks (BTN-999)

The startup transition from `checkpoint@<own marketplace>` to `agent-bridge@<own marketplace>` is covered by unit tests: retirement and project choices, a single old plugin for pinned tasks across launches and restarts, new tasks on agent-bridge, pruning after release, first seeding and idempotence. Codex's arguments disable a configured old plugin and trust hooks under the new name. Not run live: upgrading a service with a task pinned to the old package, that task's handoff and a new task after it, then restarting again. If the assumption fails, a task loses its hooks or gets duplicate mail and merge checks. **Workaround:** finish the running tasks before upgrading; use Update or Check on agent-bridge's row in Settings → Packages. For manual Claude configurations, uninstall the old plugin as [setup](../guide/setup.md#plugins) says; installing the bridge by hand is unnecessary.

## Tracker deletes refused by the gateway (BTN-541)

Protection's tracker switches are enforced in the MCP gateway (`docs/packages.md`, "The gateway"), checked by unit tests; live, Claude's and Codex's deletes on GitLab (`delete_issue`) and GitHub (`label_write`), Codex's Huly `invoke_tool` with `toolName: "delete_comment"` and Codex's Linear `delete_comment` were refused, and Claude never sees Huly's delete tools (2026-11-01, [verified log](../verified/packages.md)); an OpenCode chain session's Huly `invoke_tool` with `toolName: "delete_comment"` was refused on Linux (2026-11-02). Jira's Rovo server has no tool named `delete` at all: whatever deletes or irreversibly changes data goes through `executeDestructive` with an operation `name` from `discover` and its `inputs`. On 2026-11-01 Rovo offered no Jira delete operation (`discover` for deleting an issue, a comment or a link returned none; its destructive ones were `manageJiraProjectVersion` and Confluence's `removeConfluenceContentPermissions`). Since BTN-659 `executeDestructive` is refused whatever it runs, so with Jira's switch on archiving a version is refused too; and a tool name in the arguments of a tool that is no dispatcher (`get_tool_schema` with `toolName: "delete_comment"`, which an OpenCode session was refused before) is a read and passes. Assumed: a tracker's server reaches the session under the adapter's `mcpServer` name; a deleting tool has the word `delete` or `destructive` in its name, or takes `method: "delete"` (GitHub's `label_write`, from memory, not read from the server's tool list); Linear's tool list, read on 2026-11-01, has `delete_comment`, `delete_attachment` and `delete_status_update` and nothing else that deletes. A dispatcher — a tool with `invoke`, `call`, `execute` or `run` in its name — is judged by the tool it calls, named in `toolName`, `tool_name`, `name` or `tool`, with its arguments in `arguments`, `args`, `params`, `input` or `inputs` (Huly's `invoke_tool`, BTN-641); Huly's and Rovo's are the only ones seen, GitHub's, GitLab's (`@zereight/mcp-gitlab` 2.3.11 has none) and Linear's have none. Agents other than Claude and Codex are assumed to show the refusal as a failed tool call and to stop there, as those two did. If an assumption is wrong, a delete goes through (a tool named otherwise, a server under another name) or a call that deletes nothing is refused (a tool named with `delete` that only reads). **Workaround:** for a delete you want, turn that tracker off in Sessions → Protection (a Claude session's auto mode may still refuse it: then delete it yourself); for one you do not, keep the tracker's own permissions narrow. To check (after BTN-659): a session on Jira calling `executeDestructive`, with the log line `Protection refused`; an OpenCode session on Huly reaching a delete through `get_tool_schema` first.

## Tasks on from a new project's creation (BTN-1028)

A project added from the wizard gets `tasks@even-keel` on as soon as its entry is written (`docs/trackers.md`, "On from the project's creation"), and an amber band in its packages turns it off in one press while the tracker's own server is on too; checked by unit tests. A new project on the built-in tracker from a catalog without the package was seen on 2026-11-13 ([verified](../verified/packages.md)). Not run live: a new project on Huly whose first chain session files a task through `tasks_create`; "Turn off tasks" after `huly@even-keel` is turned on; an older project left as it was. If it is wrong, a new project's sessions see only their task's text, or the creation job fails on its packages step with the project kept. **Workaround:** turn `tasks@even-keel` on in the project's packages by hand.

## Servers installed with no install scripts (BTN-1131)

A pinned server is installed with `--ignore-scripts` and `--save-exact`, keeping `package-lock.json` in its prefix; checked by unit tests on the npm arguments, the lock's diff and the install records. Not run live: an Update of `huly@even-keel` (`@firfi/huly-mcp` with `@napi-rs/keyring`) and of the GitHub and Linear packages without scripts, whose servers then pass `initialize` behind the gateway; the dependency notice after an Update that changed a lock; the "Install scripts" switch turned on and Check installing anew. If it is wrong, a server whose dependency builds or fetches a binary in a script fails to start after its next install, and the chain waits on the package. **Workaround:** turn "Install scripts" on in the package's details and press Check.
