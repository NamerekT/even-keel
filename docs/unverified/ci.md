# What has not been verified: CI

One area of [What has not been verified](../unverified.md), which says what an entry is, how to report a run into one and where a new one goes. What has been checked in this area is in [What has been verified: CI](../verified/ci.md).

## When a CI run counts as stuck

A queued run, or a push without a run, is called stuck after 2 minutes (`STUCK_MS`). An end-to-end scenario covers the chain's side (`src/e2e/ci.test.ts`): a queued run holds the next launch until `STUCK_MS` has passed, then the push stays unchecked with a line in the log and the next task starts. The figure was chosen without live runs, and it is too short for a runner shared by several repositories: on 2026-11-02 the service log and the self-hosted Forgejo's run history ([verified log](../verified/ci.md)) showed live chains calling a push unchecked after 2 minutes while the one runner built another repository, the run taken later (161–347 s), and one such run failing unnoticed. GitHub Actions and GitLab.com runs started within a second. Since BTN-719 (covered by `src/ci/verdict.test.ts`, `src/chain/maincheck.test.ts` and an end-to-end scenario, not yet live) a run at work in any repository the service watches on the same host and CI counts as a busy runner, and a push left unchecked for want of a runner is still watched for an hour: a run taken later and failed files the fix like any red main. What stays assumed: a runner busy with a repository Even Keel does not watch is still taken for no runner after 2 minutes; the watch lives in memory, so a restart of the service ends it, and so do the chain's next push and the hour. **Workaround:** give the forge's runner more capacity than one job at a time, or watch the CI panel after a push that stays unchecked.

## A command after a green main that restarts Even Keel on Linux and macOS

`commands.afterGreen` run as children of the service's node process. The service stops only that process, not its tree — the Windows wrapper (`service/EvenKeelService.cs`, `OnStop`), `KillMode=process` under systemd, `AbandonProcessGroup` under launchd — so a restart command is expected to outlive the stop and start the service again. Checked live on the author's Windows service (2026-10-25): a chain task's push green by the project's check ran `pwsh -NoProfile -Command "Restart-Service EvenKeel; …"`, the service stopped and was up again within 2 s, the rest of that `pwsh` line ran after the start, the command after it never ran, and the commands were not run again after the restart. On Windows the `cmd.exe` running a line dies with node (node's children are in its job object) while the processes it started live on, so the restart has to be one process — `net stop EvenKeel && net start EvenKeel` loses its second half. Under a systemd user service (2026-11-02, [verified](../verified/ci.md)) one line `…; systemctl --user restart even-keel; …` restarted the service within a second, the shell outlived the stop and ran its rest after the start, and the commands did not run again; the same `KillMode=process` left the MCP gateway's servers of the stopped run alive (BTN-720). Since BTN-720 the service closes the gateway on `SIGINT`/`SIGTERM` before it exits (`shutdown` in `src/service/lifecycle.ts`): its shared servers and bridges are killed and its open connections dropped, within the same 15 s as Tally and the state database. Three restarts by hand under systemd (2026-11-02, [verified](../verified/ci.md)) left no `huly-mcp` of an earlier run behind for good, but each was still alive when systemd counted the unit stopped (`remains running after unit stopped`, `Found left-over process` at the start): `close()` did not wait for the servers to exit. Since BTN-723 it waits for each to exit, with `SIGKILL` after 5 s (`stopProcess` in `src/packages/gateway.ts`); not checked live: after `systemctl --user restart even-keel`, `journalctl --user -u even-keel --since -1min` should name no `huly-mcp` in a `left-over` or `remains running` line. Under a launchd agent on macOS (BTN-312, 2026-11-03, [verified](../verified/ci.md)) one line `launchctl kickstart -k gui/$(id -u)/local.even-keel; …` from `afterGreen` restarted the service, the shell ran its rest after the start, the next line never ran, the commands did not run again, and no process of the old run was left. Not run: a restart from `commands.afterGreen` under systemd since BTN-720. If the command dies with the service there, the service stays stopped. **Workaround:** make the restart the last command and one process, hand it to something outside the service's process tree (`systemd-run`, a scheduled task), or restart by hand (`docs/ci.md`).

## The log tail of a failed job (BTN-605)

A fix session of a red main and a PR-mode session told of a failed run of its head get the tail of the first failed job's log under the run's link (`readFailure`, `docs/ci.md`). Covered by tests for the three adapters' addresses and headers, the shared reading, the PR feedback text and a log that fails; end-to-end scenarios (`src/e2e/ci.test.ts`) carry the tail a CI adapter gives into the fix session's prompt and into the text of a fix task (`ci.fixTask`). Checked live ([verified log](../verified/ci.md)): Forgejo 16.0.3 gave a job's log at `/actions/jobs/<id>/logs` with the token, its lines stamped as GitHub's; on 2026-11-02 the tail reached the fix session of a red main on Forgejo and on a self-managed GitLab CE 19.5, and the PR feedback of a failed head run on Forgejo; a GitLab job whose log came back empty gave the run's link alone and the fix went on. GitLab.com's `trace` reached both the fix session of a red main and a merge request's feedback, plain after BTN-701. On GitHub the PR feedback of a failed head run first came with the link alone (GitHub answered the job log 415 to `accept: text/plain`), and after BTN-708 with the tail. Not run: a log the token is refused (a 403; tests only). If a forge answers otherwise, the session gets the run's link alone, as before. **Workaround:** none needed; the session opens the run page or reproduces the failure locally.

## Chains of several projects on one remote (BTN-210)

The git side is checked on real clones of one remote (`docs/chain/projects.md`, "Projects of one remote"): the fast-forward of `main` before a launch and the second try of a rejected sync. Run in Windows Sandbox (2026-10-25) as two live chains on one remote with a CI: their pushes raced, one broke `main`, its project started the fix session, the other's red push logged that the fix was already under way and started none, and its next task launched only once the fix was green. End-to-end scenarios (`src/e2e/remote.test.ts`) replay that run on two clones of one bare remote, with the fast-forward before the other project's next task, and cover a fix dropped with "Skip", after which the other project goes on, and a sync rejected because another clone pushed between its fetch and its push, done on the second try. They also cover the fix ending in ways the code does not see (BTN-685): a fix task of `ci.fixTask` closed by hand with no push lets the other project go; a fix session stopped from outside holds the other project for as long as it holds its own chain (invariant 1: main is still red), and "Skip" on it lets both go. Not seen: a real CLI's session stopped from outside (the bench's process dies mid-turn), and a project with no remote read yet, which is in no group and may still start a second fix. The fix's prompt lists commits only from the last green one of any project of the remote (BTN-702; before it, commits green in another project's pushes were listed too): seen live on 2026-11-02 ([verified log](../verified/ci.md)), the one commit that broke it. **Workaround:** a project waiting on another's fix that is over — "Skip" on that fix session, or close its fix task; to stop sharing at all, put `ci.guard: false` on all projects of the remote but one: only that one judges and fixes `main`.

## A conflict resolved by an agent (BTN-369)

The carry session (`docs/chain/projects.md`, "The carry session") is covered by tests of the forward tick, the dispatcher's order, the skip and the page's rows; the page was checked on fake data only. End-to-end scenarios (`src/e2e/carry.test.ts`) run it on real git with the scripted agent: "Resolve with the agent" starts one `<KEY>-CARRY` in a worktree of the main project, its merge of the ref `refs/even-keel/forward/<id>` into the main branch closes it by `merge-base --is-ancestor`, its worktree and branch are removed, the next forward tick lifts the hold, and its record outlives a restart of the service with nothing merged or started anew. Never run live: a real agent's session on a real conflict. Assumed: that such a session merges the commit the prompt names and resolves it as the report says, and that a red main of the main project meanwhile waits behind the carry rather than stopping it. If wrong, the carry row stays open after the merge, or the hold stays on the release project's page. **Workaround:** "Skip" on the carry row and merge by hand, as above; the hold clears by itself once the branch has the commits.

## A conflict given to the agent by itself (BTN-370)

The carry session asked for at the conflict itself (`carryAgent` or unattended mode, `docs/chain/projects.md`, "The carry session") is covered by tests of the forward tick with git's answers and by end-to-end scenarios (`src/e2e/carry.test.ts`): with either, the forward tick's conflict starts one session in the main project's chain, as the button does; once it is skipped, no second one comes for the same release commit, and a new release fix asks for a carry again. They found two defects: unattended mode never lets an idle carry session go (BTN-693), and the carry asked after a skip is taken by the skipped session, still alive under the same name, instead of a new one (BTN-692). Never run live on the service. Assumed: nothing beyond the scenarios but the timing of a real forward tick against a real chain. If wrong, a conflict waits on the page with no session. **Workaround:** turn the switch off and press "Resolve with the agent", or merge by hand.

## Your own skills as a package (BTN-339)

The wrap (`src/packages/skills.ts`, `docs/packages.md`, "The user's own skills") is covered by tests on temporary folders: the listing, the hash version, the copy again after an edit, the plugin found and installed through Even Keel's own folders. Seen on the PC (2026-10-24): the skills of `~/.claude/skills`, linked into the shared store (BTN-256), are copied with their files, and `claude plugin validate` (2.1.309) passes the marketplace and the plugin. Chain sessions of the service loaded a skill of the package on Copilot (2026-10-27) and on OpenCode (2026-10-28) ([verified log](../verified/opencode.md)). Not run as a chain session on Codex: that it takes the plugin `my-skills` as it takes another plugin's skills (seen for other plugins in BTN-340), and that its `plugin/install` accepts the version `1.0.0+<hash>`. If wrong, a Codex session lacks the skills, or its launch fails with `codex.pluginsFailed`. **Workaround:** turn the package off for the project in `/tools` and keep the skills in the repository's `.agents/skills`.

## A fresh session idling before its prompt

Seen on the service (2026-11-01): a Claude chain session, nine seconds after its start, had context 0, no feed and the lamp `waiting`, so the page dropped the start card, counted it in "waiting for a reply" and wrote "The session hasn't done anything yet." The page now takes such a session for a boot (`idleBeforePrompt`, `docs/web/session-panel.md`), checked by tests and on `dev:fake` (`?chain=idle`, "Start": the third step idles as waiting). A start watched on the service since (2026-11-02, [verified log](../verified/page.md)) did not come to the race: its prompt was in the transcript 40 ms after the start. Not seen: a start that idles before its prompt with the fix — start a chain and watch the first seconds of the session: the card goes Prepare, Boot, First answer, and the header never counts the session as waiting. The race comes on some starts only; one start that answers at once proves nothing. Assumed: the CLI reports the idle of a job that has not taken its prompt as `idle` with no question, startup dialog or API error, and the other agents' fresh sessions look the same or never idle. If wrong, the start card still gives way to the waiting state for a few seconds. **Workaround:** none needed; the session moves on by itself.
