# What has not been verified: Copilot

One area of [What has not been verified](../unverified.md), which says what an entry is, how to report a run into one and where a new one goes. What has been checked in this area is in [What has been verified: Copilot](../verified/copilot.md).

## Copilot chain sessions under the service (BTN-215)

Whole tasks ran as chain sessions of the Windows service on the machine's own sign-in, which reached session 0 ([`verified.md`](../verified.md), "Copilot"). A question answered from the page's chat resumed the session inside the chain (TSK-42, `verified.md`). A task ran to Done on a folder with a fine-grained token outside the service (sandbox, 2026-10-31, `verified.md`), with the machine's sign-in of the same GitHub user still there, so which one the CLI used was not told apart. On macOS a folder with a fine-grained token ran a whole task under the launchd agent (BTN-312, 2026-11-03, [verified](../verified/copilot.md)). On Linux in a Docker Desktop container without systemd (EKR-48, 2026-11-05, [verified](../verified/copilot.md)), whole tasks ran on both a plaintext OAuth sign-in in the account's own `COPILOT_HOME` and a separate fine-grained token folder. Never run on a folder with a token under the Windows service or on the machine's sign-in on macOS; a Linux systemd service and keyring access remain unchecked. **Workaround:** add the Copilot account with a fine-grained token, or run the task on another provider (a run label).

## Hooks and plugins in Copilot sessions

The agent-bridge package's hooks from `--plugin-dir` run at every step of a chain session, and plugin skills load ([`verified.md`](../verified.md), "Copilot"). Copilot drops `hookSpecificOutput.additionalContext` on `PostToolUse` and takes a top-level `additionalContext` on every event (a probe plugin, `verified.md`), so since BTN-467 Even Keel starts Copilot with `EVEN_KEEL_AGENT=copilot` and the hooks answer in the top-level shape there (`contextOutput`, covered by tests). A page message sent mid-turn reached the model on `PreToolUse` (2026-10-28, BTN-516) and one with a picture on `PostToolUse` (TSK-41, `verified.md`), though the chat showed neither. Since BTN-519 the chat shows such a message from `hook.end`'s text where Copilot writes it (`postToolUse`, seen live: one bubble per message, TSK-42) and otherwise from the mailbox at the time it was taken (`docs/sessions/chat.md`), covered by tests only: a message taken on `preToolUse` was not seen since. The mail on `Stop` (its reason becomes the next prompt), the context nudge and a standard reached the model from a terminal against a stub (2026-10-30, BTN-471, `verified.md`). A handoff on a real threshold crossing ran in the sandbox (1.0.98, 2026-10-31, `verified.md`): the session went on past the first nudge, wrote the note on the second, and the next one finished the task; there too the repository's `.claude/settings.json` hooks ran in no chain session until the repository was in the account folder's `trustedFolders`, and then on every event (`docs/sessions/copilot.md`). Since BTN-645 Even Keel writes that entry itself before every turn (`trustFolder`, covered by tests). Not yet seen: a message taken on `preToolUse` shown in the chat; a chain session on a fresh account folder running the repository's `.claude/settings.json` hooks with the entry Even Keel wrote, and a running Copilot keeping it rather than rewriting `config.json` over it. **Workaround:** if a message sent mid-turn shows no bubble in the chat, it still reached the model; if the repository's hooks do not run, check that the account folder's `config.json` lists the project's checkout in `trustedFolders`.

## A spent Copilot budget

BTN-804 (2026-11-12) adds parsing of token-billed AI-credit allowance readings from public sources, with synthetic tests only. This does not verify a paid plan's actual refusal when its AI credits run out: neither the refusal wording nor recovery at reset has been observed. No plan was bought for this check.

The free plan's spent month was seen in the sandbox (2026-10-31, [`verified.md`](../verified/copilot.md)): mid-turn, `session.error` with `errorType: "quota"`, 402, `quota_exceeded`, taken as a limit; a folder with a token then waited for the reset on the 1st, one on the machine's sign-in for the 15-minute retry. Until the next poll of the allowance the token folder's limit had no reset and the page called it an API key out of credit (BTN-647). Since BTN-647 a refusal naming the monthly quota spends the month at once, so the hold takes the month's reset and the card shows 0 left, and a Copilot token never gets the "out of credit" text (covered by tests; a refusal of another wording still waits for the poll). Never seen: that fix on the next spent month, what a paid plan's spent AI credits or premium requests write (the fold takes a text about billing or AI credits as spent credit, any other wording stops the session like an error), a session cut by the spent month going on in a new session at the reset, and the machine sign-in's retries after the first. A task held by the spent month on the machine's sign-in did start by itself after the reset (2026-11-01, [verified.md](../verified/copilot.md)), on the chain's first pass once the machine was back online. **Workaround:** after the budget is back, press "New session".

## A Copilot token's monthly allowance (BTN-341)

A Copilot folder with a token is asked `copilot_internal/user` first, then the billing API's `premium_request/usage` of the token's user. Since BTN-804, an empty report or 404 tries `ai_credit/usage`; both require "Plan" read permission according to the [REST documentation](https://docs.github.com/en/rest/billing/usage#get-billing-ai-credit-usage-report-for-a-user), which now explicitly supports fine-grained PATs (checked 2026-11-12). With a fine-grained token on the free plan (sandbox, 2026-10-31, [`verified.md`](../verified.md), "Copilot") `copilot_internal/user` answered, the card showed what was left and the count went down by one after a chain session; the billing API was not reached, nor was a paid plan.

Public evidence consulted for BTN-804: [paseo#8478](https://github.com/getpaseo/paseo/issues/8478) shows a personal education plan's legacy `remaining`/`entitlement` reading; [ghcp-spend-tray's wire model](https://github.com/DamianEdwards/ghcp-spend-tray/blob/main/src/GHCPSpendTray.Core/JsonModels.cs) includes `credits_used`, `entitlement`, `has_quota` and `token_based_billing`, and [its issue #18](https://github.com/DamianEdwards/ghcp-spend-tray/issues/18) reports live validation on Enterprise only. Our synthetic tests read credits spent out of entitlement, preserve the legacy shape, explain missing quota, and exercise both billing addresses. The documented `Copilot AI Credits` product and the aliases `Copilot`/`AI credits` are counted; unknown products are logged rather than shown as zero. Two empty reports show no data. Still unseen live: a paid allowance, the billing fallback with either report, empty/no-quota messages and the provider's response at exhaustion. **Workaround:** check the allowance and usage on GitHub's billing page.

## Copilot models in the stats

Copilot names Claude models with dots (`claude-sonnet-4.6`), which no price key of `tally.config.json` matches, so such calls show no cost in `/stats` and the collector logs them as unpriced; the GPT names seen were the API's own. **Workaround:** add a price key with the dotted name.


## Copilot folder sign-in refresh (EKR-73)

The probe was checked against CLI 1.0.105 on the Linux Docker bench without a keyring: an empty folder reported signed out despite an existing global plaintext sign-in, and the managed OAuth folder reported signed in ([verified](../verified/copilot.md)). EKR-84 repeated these checks from its source, verified an unavailable binary as unknown, and ran the sh command with fake tokens and a failing fake executable twice: tokens were absent in the child and the parent environment stayed intact. Unit tests exercise cmd and sh with present/absent inherited tokens, success/failure and repeats; fake-page shots cover cmd/sh instructions and unknown status at desktop/mobile sizes. Unknown is now shown as "Could not check" and allows launch, as agreed in EKR-81; each refresh/restart checks again. Still unverified: the whole service observing a new terminal login through the displayed command and refreshing its card, and credential-store access under Windows service, Linux systemd or macOS. A fresh login was not completed; EKR-48 checked plaintext login with the managed folder. **Workaround:** run the displayed command in its named shell as the service user and wait for the next account check; a token account remains an alternative.

## Copilot's machine token and model availability (BTN-516)

The GitHub CLI fallback and its allowance moved to [verified.md](../verified/copilot.md) in BTN-520: `auth.getStatus` confirms `gh-cli`, host and login before its token is read. The tested Windows machine had no `copilot-cli` credential and no saved OAuth user or token in either the global or managed `config.json`; removing `gh` from PATH made CLI 1.0.105 fail authentication. Thus the separate `copilot-language-server/oauth-token-key` credential was not sufficient to sign this CLI in and was not read as a token. Own OAuth in the Windows credential store was checked in the sandbox on 2026-10-31 ([verified.md](../verified/copilot.md)): sessions run on it, `auth.getStatus` names it `user`, and the card has no allowance, as designed. The Linux plaintext fallback was checked in a Docker Desktop container without a keyring (EKR-48, 2026-11-05, [verified](../verified/copilot.md)): login with the account's `COPILOT_HOME` saved `authTokens` in its mode-0600 `config.json`, `auth.getStatus` reported `user`, and a chain task completed; the card had no allowance. Login without that variable saved into the global folder instead, invisible to the managed session, although its card said signed in (EKR-73). The user also observed that login without a terminal reported "token was not saved" and did not ask about plaintext. macOS OAuth, Linux keyring/systemd access, enterprise hosts and paid-plan eligibility remain unchecked; an own OAuth allowance remains unavailable. The model endpoint remains open: on 2026-10-28, `copilot_internal/v2/token` returned 403 without an editor-identification header, so `/models` was not called; the Linux account's `models/list` returned no hints in EKR-48. Do not substitute GitHub CLI credentials for another source, or impersonate VS Code to unlock models. **Workaround:** on Linux without a keyring, run `copilot login` in a terminal with the managed account's `COPILOT_HOME`; or add a Copilot account with its own token for its existing usage support. Leave its model field unset when no models are offered.
