# What has not been verified: Codex

One area of [What has not been verified](../unverified.md), which says what an entry is, how to report a run into one and where a new one goes. What has been checked in this area is in [What has been verified: Codex](../verified/codex.md).

Checked live on codex-cli 0.162.1 (BTN-168): a detached turn outlives its parent killed hard, `exec resume <id>` goes on with the history, a resume of an unknown id fails instead of starting a new thread, `CODEX_HOME`, `rate_limits` and the context fill in the rollout. The rest:

## Chain sessions in the Codex app and on the phone (BTN-178)

That the Codex desktop app and the ChatGPT app on the phone do not list the chain's threads is read from the app-server protocol (`thread/list` without `sourceKinds` leaves `exec` threads out). Seen in the Windows desktop app (2026-10-23): `~/.codex/state_5.sqlite` holds 36 `exec` threads, the chain's TSK-20 among them, and the app lists none; the Coldbloom chain tasks it does list are its imports of Claude Code transcripts from `~/.claude/projects`, copies that never write back. Not seen on the phone. If an app lists them after all and the user writes there, that turn runs in the app's own app-server and appends to the same rollout: the page shows it in the feed, but Even Keel may `resume` the thread at the same time, and two turns on one thread is untested. **Workaround:** answer Codex sessions only from the page's chat or the tracker (`docs/sessions.md`).

## A package server and a Codex server of the same name

A Codex chain session called the Linear server of its package through the gateway (`-c mcp_servers.<name>.url=<gateway address>`) on a fresh install from the Windows service (BTN-161, 18.10.2026). If Codex also has a server of the same name in its own `config.toml`, which one wins is unknown. **Workaround:** remove that server from Codex's config or give the tools through the package alone (`docs/packages.md`).

## Sign-in from the page

`codex login --device-auth` runs through the panel's sign-in flow, whose reading of the link was written for Claude's output. Checked live from the Windows service (BTN-284, 2026-10-22, Windows Sandbox): signing the built-in `codex` account in from the page showed the link, the link worked and the account signed in. The one-time code is parsed out of the output (`loginCode`, BTN-313) and shown large with a "Copy" button; that parsing was written from the codex-cli 0.162.1 and opencode 1.18 binaries' format strings. A live Codex sign-in showed the code box (codex-cli 0.166.0, 2026-11-01, [verified.md](../verified/codex.md)); OpenCode's was not seen live. If a later CLI words it otherwise, the window shows no code box and keeps the CLI output unfolded, the code in it, as before. If a later Codex words its output otherwise and the window shows no link, sign in with `codex login` in a terminal with the same `CODEX_HOME` (`docs/accounts.md`). Adding an account into a new folder under `~/.codex-accounts` (BTN-176) was checked live on 2026-10-25 (codex-cli 0.164.0, Windows Sandbox): `codex login --device-auth` signed in the folder Even Keel made empty, and a second free sign-in was refused at once by the plan in its `id_token`, the folder removed.

## Codex on an OpenAI API key (BTN-177)

Checked with a fake key: `codex login --with-api-key` writes the `auth.json` Even Keel writes, `codex login status` reads it, a turn on it goes to the API and fails with 401, and OpenAI's models list answers 401 to a fake key. A key at zero was seen live ([verified log](../verified/codex.md)): on 2026-10-25 the rollout's `usage_limit_exceeded` with the quota text, and on 2026-10-29 a chain session of the service on such a key held as `credit`, the task handed over to a new session when its account was switched. Never seen with a funded key: that a turn runs on it, whether its rollout has `rate_limits` (the card shows the spend instead either way), the price of the model it runs on in Tally. By Codex's source (2026-11-02, `codex-rs/codex-api/src/rate_limits.rs`) the rollout's `rate_limits` come only from the `x-codex-*` header families of the ChatGPT backend; `api.openai.com` sends the standard `x-ratelimit-*` ones, so a key's rollout is expected to have no windows. The money check — `/v1/responses` on a `nano`/`mini` model with `max_output_tokens: 16`, the API's floor by its own error text ("Expected a value >= 16"), waiting for 2xx or a 429 `insufficient_quota` — was never seen saying 2xx after a top-up: if it never does (the key lists no such model, the request shape is refused), the chain keeps waiting and the log has the check's reason. **Workaround:** top the key up and press "New session" on the task.

## A crashed turn and a service restart mid-turn

Liveness is the pid of the last turn: a pid reused by another process after a crash would keep the session busy.

A service restart mid-turn was checked live with the real service on Windows (BTN-284, 2026-10-22, Windows Sandbox, the service `EvenKeel` under a local user that is not an administrator): an update restarted the service while a chain session's Codex turn ran. `codex.exe` outlived its dead parent, the new service showed the session working, and once the turn ended it showed it waiting; an answer from the page's chat resumed the thread in about a second, the session merged its branch and Even Keel closed the task.

## Stopping a turn on macOS and Linux

For Codex, Copilot and OpenCode, the turn's process group is killed with `process.kill(-pid)`, and since BTN-643 also the groups of its descendants found by parent in one `ps -A -o pid=,ppid=,pgid=` ([sessions/agents.md](../sessions/agents.md#stopping-a-turn-killtree-btn-643)); before that it was run only on Windows (`taskkill /T`). During polling and before a stop, the process creation time is read from `/proc/<pid>/stat` plus boot time and `getconf CLK_TCK` on Linux, or `ps -o lstart=` on macOS, to leave a newer process that reused the pid alive. Neither platform's creation-time lookup has been checked live. If it fails, polling and stopping keep their previous behaviour and can mistake a reused pid for the turn; a wrong creation time can also leave the turn running. The equivalent Windows checks were verified with owned parent/child processes for all three adapters: a reused pid was shown resting and preserved even with a stale live result at stop, the current resumed turn was busy and its tree was killed, and trailing stderr did not hide a terminal event. On Linux (2026-10-31) an OpenCode turn read `busy` through its command and "New session" killed its process group, but the shell tool's command, in its own session and group, outlived the stop (BTN-643, [verified.md](../verified/opencode.md)); a reused pid was not staged, and Codex and Copilot were not run. The fix killed a `setsid sleep` started by a detached `sh` on Ubuntu under WSL, where the old `-pid` left it alive ([verified.md](../verified/sessions.md)), and on the same server through the service (2026-11-02, [verified](../verified/codex.md)): "New session" on a silent OpenCode turn whose shell tool ran `sleep` in a session and group of its own killed both the turn and the `sleep`; on macOS `ps` was not run. Whether Codex and Copilot put a shell tool's command into a group of its own was not checked: their copies on the author's workstation are Windows builds. **Workaround:** after stopping a turn on Linux or macOS, look for its commands left running (`ps -o pid,ppid,pgid,cmd`) and kill them by hand; if an agent process has crashed, verify its pid and creation time in the operating system before stopping the session or cleaning up its task.

## Codex stats (BTN-170)

Checked on the rollouts on disk: 0.148 desktop sessions and 0.162 exec ones; on 0.164.0 (2026-10-25), the 12 finished chain sessions of a day had in Tally exactly their `token_usage_record` responses and token sums, and the turn refused at a limit, which writes one record and two equal `token_count` lines, was counted once. On 2026-10-31 all 433 rollouts on disk were summed: every exec rollout with records matched its own total but one, where a stop between a record and its `token_count` left the later `token_count` totals behind the records', and three responses were counted twice; since BTN-626 a `token_count` after the first record is not counted, the session sums to its own total, and schema step 9 drops the extra rows (`docs/verified.md`). Still never seen: a non-zero `cache_write_input_tokens` — it is assumed to be inside `input_tokens` and is subtracted from it; a rollout in `archived_sessions/`. If one of these differs, a Codex response is counted twice or its input is off. **Workaround:** none needed for the chain; compare `/stats` with the `usage` in the rollout and fix `src/rollout.ts` (`docs/tally.md`).

## Plugin hooks that block (BTN-180)

All five hook events of a plugin were seen running in Codex, and `additionalContext` reaching the model. Checked live on Windows with Codex 0.164.0 on 2026-10-25: a nested code-mode shell call ignored a `PreToolUse` exit code 2, while `permissionDecision: deny` blocked it before execution; `Stop` with `decision: block` continued the turn. The checkpoint plugin now uses explicit denial: a failed project check held the merge, a passing check allowed it, and the Stop guard saw a shell-written note in the rollout and made the session add `CHECKPOINT:` (`docs/sessions.md`). The Huly plugin's `show-calibration` denial was seen on a real MCP call from a chain session (BTN-387, 2026-10-25): the estimate was refused once with the calibration and the retry went through. `check-marks` now returns the same explicit denial (EKR-32); still unverified: its refusal on a real Codex MCP call. If ignored there, a malformed description reaches Huly. **Workaround:** check the description in Huly.

## The schema hint on a deferred MCP call (BTN-625)

The checkpoint plugin's `schema-hint.mjs` (`plugins/checkpoint/README.md`, "MCP calls without the tool's schema") runs on `PostToolUseFailure` for `mcp__*` tools. Seen: in Claude Code transcripts such a call is a `tool_result` with `is_error: true` and the server's text `Invalid parameters for update_issue: estimation: Expected PositiveTimeHours | null | undefined`; in the code of Claude Code 2.1.314 an MCP result with `isError` throws `McpToolCallError`, and a failed tool fires `PostToolUseFailure` with `tool_input` and `error` and takes `hookSpecificOutput.additionalContext`. Codex 0.164.0 skips the event: its `hooks/list` of a copy of the package with the event listed the other eleven hooks and no warning ([verified log](../verified/codex.md)). Not seen: the hook firing in a live session — the exact `error` text (a prefix such as `Error:` is matched either way) and the hint reaching the model; and Copilot, which reads the same `hooks.json`, meeting an event it does not know. If the event does not fire or the text differs, the session gets no hint and may leave the field out as before; if Copilot refuses the file, its session loses the package's hooks. **Workaround:** load a tracker tool with `ToolSearch` before the first call that sends a number; for Copilot, check that the chat's messages still reach its sessions.

## Project standards on each agent (BTN-359)

The hooks of a project's standards (`docs/sessions/protection.md`, "Project standards") were run by their tests with the inputs Claude Code documents, and live on Codex (0.164.0, 2026-10-25): four chain sessions had their first edit of a screen file refused with `docs/design.md` ("Not yet: … falls under the project's standard"). Live on OpenCode (1.18.25, 2026-10-28): two chain sessions got the document appended to their first read of a screen file, so their edits went through without a refusal, and one merge was refused for stale shots, then ran once they were new ([verified log](../verified/opencode.md)); OpenCode's edit refusal (`tool.execute.before`) was not seen. Live on Copilot (1.0.98, 2026-10-31, sandbox, [verified log](../verified/copilot.md)): the hooks get Claude's tool names, a read of a guarded file gave its document and the session followed it, but no edit was refused, since `apply_patch` comes as `Edit` with the patch as a bare string. Since BTN-640 `callOf` takes the paths from such a string, checked by tests only: the first live check is a Copilot chain session creating a guarded file before reading it, which should be refused with the document — and whether Copilot honors the hook's `permissionDecision: "deny"` at all. Assumed, per agent: Codex's compaction fires `SessionStart` with `compact`. OpenCode fires `session.compacted` after a compaction; its PR mode mark is not held, as its turn's end cannot be blocked. If a name or a field differs, that agent's session edits a guarded file without the document, or gets it only once per session; if a compaction is missed, the document is not given again after it. The merge's check is plain files and git and does not depend on the agent. **Workaround:** name the document in the task's text; the merge still waits for the shots and the answers.

## A patched handoff note seen by the Codex Stop hook

Checked live with Codex 0.164.0 on Windows on 2026-10-25: a shell write of the note was already in the rollout when the Stop hook asked `/api/sessions/<id>/note`, and the hook made the session add the mark. The timing of a last `FileChange` from `apply_patch` is still unverified. If that event has not reached disk, the hook lets the turn end. **Workaround:** end with `CHECKPOINT: .temp/handoff.md` explicitly, or press "New session".

## Plugins in a Codex folder on Linux and macOS

The install and the check that a plugin is already in a folder (`<CODEX_HOME>/plugins/cache/<marketplace>/<plugin>`) were run only on Windows. If the path differs, every first turn of a service run installs the plugin again, which costs a few seconds and changes nothing else.

## Codex memory off in the CLI check (BTN-724)

A Codex session of `npm run cli-check` runs with `-c features.memories=false -c memories.use_memories=false -c memories.generate_memories=false` (`SessionStart.noMemory`), so that its saved capture holds no summary of the account folder's memories. Only `config/read` of codex-cli 0.166.0 was seen to take the keys; no session has run with them. If they do not keep the summary out, the check still saves nothing: it refuses a capture holding a line of the folder's `memories/` and names the file. Run the next Codex `cli-check` in a folder that has memories: it should pass and save its capture.
