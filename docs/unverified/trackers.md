# What has not been verified: Trackers

One area of [What has not been verified](../unverified.md), which says what an entry is, how to report a run into one and where a new one goes. What has been checked in this area is in [What has been verified: Trackers](../verified/trackers.md).

## A tracker that did not answer (BTN-825)

The page's calls to a tracker that did not answer fail at once with the error it failed with, instead of waiting the whole timeout again (`TrackerLink.page`, `docs/trackers.md`): the card of a task, a file of it, the task's actions, the vocabulary of a project and the changelog's list of a milestone. The chain's own poll is not silenced — it is what brings the tracker back. Checked by tests against a fake tracker (`src/tracker/link.test.ts`, `src/tracker/control.test.ts`): a timeout, a broken connection ("fetch failed" with its cause), and a tracker that answered (that what was asked for is not there, or that the credentials are refused) — the last two leave the page's calls alone. Seen live on 2026-11-09 with the author's GitLab CE host down: a task card's first call waited the whole 15 s, the second and the project's vocabulary failed in 2–13 ms with the timeout's text naming the tracker; when the host came back, its projects read again within 12 s of its first answer and a task card opened in 1.1 s (`docs/verified/trackers.md`). Still assumed:

- after a longer outage, when the poll's wait has grown to its 300 s, the page may keep saying that the tracker is down for minutes after it is up;
- "fetch failed" for a broken connection is what the page shows, its cause only in the log and on the `/status` page;
- a tracker that refuses the credentials or answers that what was asked for is not there is not a tracker that "did not answer" and does not hold the page's calls.

If an assumption is wrong, the page either waits the whole timeout on every request or says that the tracker is down while it is up. **Workaround:** open the page again when the tracker answers again; the poll notices it by itself. To check: keep a tracker's host down for over ten minutes, bring it back and time the page's recovery; point a profile at a wrong token and open a task card twice.

## A turned-off tracker profile (BTN-830)

A tracker profile turned off in Trackers and CI reaches nothing of its host, and a chain starts only by tasks read since its tracker last answered (`docs/trackers.md`, "Profiles"). Checked by tests: the profile's rechecks and retries stop, its tracker view is off with no link, its CI gets no token, its task card, vocabulary and project list answer `profiles.disabled` with no call, turning off is refused while a chain on it runs, waits or is queued, and Start refuses a list read before the tracker came back (`src/profiles/service.test.ts`, `src/tracker/trackers.test.ts`, `src/ci/adapters.test.ts`, `src/tracker/control.test.ts`, `src/chain/dispatcher.fresh.test.ts`). Seen live on 2026-11-09 with the author's GitLab CE profile off and its host down: over eight hours and a dozen service restarts the log held no call to the host, the task card and the vocabulary answered `profiles.disabled` in 2 ms, the tasks server refused at once, and the home card was dimmed with "is off: tasks are not read" and "Turn on"; with the host up, turning the profile on read its projects in 1.1 s (`docs/verified/trackers.md`). On 2026-11-14 (BTN-1156) a listener on the turned-off Gitea profile's port saw no request in almost 15 minutes and a service restart, and its first calls within a second of turning it on. On 2026-11-15 (BTN-864) turning the GitLab profile off was refused while GLP's chain ran and while it stood paused, with "Stop the chain" on the profile's row; Start on a project of the turned-off profile was refused at once and on the home card opened only the dialog that turns the profile on; turned on, the chain did not start and its first read took a task created while it was off; with the host down and while it answered 502, Start was refused as unread, and it started the next press after the first answer. Still assumed: unattended mode skips a project of the turned-off profile and picks it up again once it is on (the check ran with unattended mode off; it starts no chain by itself, and a chain on the profile cannot be left running when it goes off).

If the assumption is wrong, the page keeps waiting on a host that is off. **Workaround:** press Check on the tracker's card in `/status`, which reads its projects now. To check: BTN-864.

## Automatic milestone order (BTN-791)

Unit tests cover transitivity with missing dates and native positions, Linear's position conversion and queries, and Jira versions going by date with no catalog read. On 2026-11-08 (BTN-835, [verified log](../verified/trackers.md)) the chain, the card's choices, the filled active milestone and a restart followed Linear's milestone `sortOrder` live (and Jira's version sequence, since dropped), with positions set through the API. On 2026-11-11 (BTN-849) dragging a milestone in a Linear project's milestone list rewrote its `sortOrder` and the chain and the card followed. Jira has no such drag: the Releases page sorts versions by release date with no handle, a Kanban board shows no Versions panel, and the catalog's sequence is in effect the order the versions were created; so since BTN-1021 Jira gives no native position and its versions go by date, number and name, as the Releases page lists them. On 2026-11-14 (BTN-1155) four EKJ versions created against their dates went by date in the chain and the card's choices, the undated one last, and a Huly feed's dated milestone took its place among them by date. Still assumed: Linear's native order mixed with another tracker's milestones (no Linear feed could be added on the bench), which falls back to date for the whole set; that the Releases page orders undated versions among themselves as the chain does (by number, then name: not compared). Huly, GitHub, Forgejo, GitLab, Jira and the built-in tracker provide no native order. A mixed-source or incomplete set falls back to date, number and name; dated milestones precede undated ones. If an assumption is wrong, the chain can choose the wrong milestone, hold a task or stop with a milestone-order conflict. **Workaround:** correct dates/names or blocking links in the tracker and refresh, or set the project's own milestone order in Even Keel. To check: a Linear project with a feed of another tracker, its milestones dragged against their dates; two undated Jira versions against the Releases page. The missing-date and mixed-source policy is recorded for discussion in BTN-834.

Live on 2026-11-14 (BTN-1155): the pull request move on Huly (In Progress on the start, In Review on the pull request, Done on its merge); "leave as is" on a Linear project over its profile's start move; a Huly feed's own start moves over its profile's, both ways; a chosen done status on Linear (a second completed state), its `statusMove.notDone` band when the chain rules did not take it and the close once they did, and the `tracker.completeRefused` band with the status and the level when the state was archived, closing into Done once the choice was removed; both bands' button opens the project's Tracker tab. Found there: a merged pull request and a `NO CHANGES:` mark close into the tracker's first done status, past the chosen one; BTN-1163 sends every close through the choice, checked by tests and the e2e `statuses.test.ts`, and live on 2026-11-15. Live on 2026-11-15 (BTN-555): the add-profile step on Huly, both Save and Skip; "only forward" on Huly; the pull request move on Jira; a chosen done status on Huly and Jira and a Huly feed's own, through a merge and a `NO CHANGES:` mark; a Jira start move with no transition in, for the band and its button; the `notDone` band on Huly and the `completeRefused` band on Huly and Jira, each closing once fixed. Later that day: the pull request move on Linear (In Review on the pull request, Done on its merge) and the `notDone` band on Jira, closing on the next pass once the rules took the status. Seen on the save: a status name the tracker does not have was taken without a word, and the move then failed only when it ran; BTN-667 refuses it on the save (`statusMoves.unknown`), checked live on Linear and Jira on 2026-11-15, and marks such a value "not in the tracker" at its field and logs one set by `config-import`, checked by tests only. Assumed:

- Huly writes the named status like any status change, and every issue status of the workspace is a choice, though a project's type may not have it: such a move is refused by name ("no status") rather than written.
- Linear's `workflowStates` lists the states of every team the key sees, and a name shared by teams is one choice; a team without that name refuses the move.
- Jira's `/rest/api/3/status` lists the site's statuses; a workflow with no transition from the task's status to the chosen one leaves the task where it is (a refusal on the page), and a transition with a screen of required fields is refused by Jira like a refused close.
- The start move runs after the session started and the pull request move after the pull request opened, both asynchronously; a slow tracker answers after the chain has already moved on, which only delays the band.

If one is wrong, a task stays in its status or, at worst, the tracker refuses the move and the page says so; the chain is never held by a move. **Workaround:** move or close the task in the tracker, or set "leave as is" and "automatic". To check: a status name the tracker lacks set through `config-import` — marked "not in the tracker" at its field, and that import's log line.

## MCP through OAuth on a tracker profile (BTN-475)

The flow, the refresh and the gateway's Bearer header are checked by tests against fake providers (`src/profiles/oauth.test.ts`, `oauth-protocol.test.ts`, `src/packages/gateway.test.ts`), and the dialog on `dev:fake`. BTN-485 applies that discovery in the service; its implementation's discovery and public-client registration with the advertised scopes passed against live Jira and Linear on the same date. BTN-490 additionally checked the running service's starts and guard refusals from localhost and an HTTPS proxy, site access with the saved v2 profile through its gateway, and two consecutive live refresh rotations through isolated instances of the actual profile service and gateway. BTN-495 confirmed that v2 refuses a new controlled HTTPS callback outside the organization's domain rules: consent identifies the callback as restricted and disables Accept. No domain rule or working grant was changed ([verified log](../verified/trackers.md)). Linear and GitHub lost MCP OAuth in BTN-604 before any live check: their MCP servers take the tracker's token. On 2026-11-14 (BTN-1155) a chain session on a Jira profile connected through OAuth with no MCP token got the Jira MCP tools through the gateway on the grant alone and read its own issue with them. Assumed:

- a fresh browser callback completes over direct HTTPS too. Jira's proxy callback and matching `Host`/`Origin` passed in BTN-490, but loopback proxy requests need no cookie. BTN-494 checked the direct network guard's scoped Lax callback cookie, successful code exchange, one-use state, draft binding, provider denial and guard refusals with clean final URLs in Chromium against a simulated provider and non-local socket addresses ([verified log](../verified/trackers.md)); a fresh consent on a live provider over direct HTTPS has not been repeated;
- a refused refresh or a second 401 marks the grant for reconnecting, and a session's tool call meanwhile fails with an MCP error rather than hangs. On Jira (2026-10-29) a revoked app made the gateway answer with an error rather than hang, but its refresh refusal, 403 `unauthorized_client`, did not mark the grant: BTN-589 ([verified log](../verified/trackers.md)).
- The profile dialog's Check and Save verify the selected MCP OAuth grant against the live providers, including an expired unsaved grant refreshed before its original ten-minute deadline (BTN-491). On Jira a saved and a fresh unsaved grant passed both (2026-10-29, [verified log](../verified/trackers.md)); the expired unsaved grant's refresh has not been exercised live. If it refuses working access, reconnect in the dialog or disconnect OAuth and use the fallback token.
- A refused consent (Cancel or Escape on Atlassian's page, a callback with `error=access_denied`) shows "MCP access was not granted" and logs one `consent` line with the provider's `error`, while a failed code exchange or grant check shows "MCP OAuth did not complete" (BTN-588). If one is wrong, the button ends in "MCP OAuth did not complete" or the profile's row says "MCP access lost" soon after; sessions get no tracker tools while REST keeps working. **Workaround:** disconnect OAuth in the profile and use the Atlassian MCP V2 token.

## The person of a Jira MCP grant (BTN-590)

Atlassian gives an MCP grant to whoever is signed in to Atlassian in the browser, so it may be another person of the site than the profile's REST token (seen in BTN-489). The dialog checks a new grant at once, and Check, Save and the row compare the grant's person with the REST token's `/myself` `accountId`; a different one is a warning with "Connect again", never a refusal. Assumed, from Atlassian's MCP tool list and its `/me` answer, never seen live: Rovo MCP v2's `atlassianUserInfo` answers a text block of JSON with `account_id` and `name` (a `data` envelope, `accountId`, `displayName`, `nickname` or `email` are read too), and that `account_id` is the `accountId` of Jira's `/myself`. Checked only by tests on fake providers. If the tool is missing or answers otherwise, the person is unknown and nothing is shown: a grant of another person goes unnoticed, as before. If the ids differ for the same person, the warning shows for a correct grant; press "Connect again" signed in as the profile's person, or ignore it. Linear, GitHub and GitLab have no MCP grant (BTN-604): their sessions use the profile's own token, so there is no second person to compare.

## A Jira MCP grant revoked in Atlassian (BTN-589)

A grant revoked in id.atlassian.com → Connected apps was seen in BTN-489: the token check answered 401 `invalid_token`, the refresh 403 `unauthorized_client`, and the probe asked Atlassian's token endpoint every 30 s, two log lines each time. Now any 4xx of the token endpoint with an OAuth `error` (but `slow_down`, `temporarily_unavailable`, `server_error`, 408 and 429) marks the grant for reconnecting, so the row says "MCP: reconnect needed" and nothing more goes to Atlassian; the gateway and the refresh log a failure once per reason and once when it works again, and a failing probe waits longer each time, up to an hour. Checked only by tests on fake providers. If Atlassian answers a revoked grant otherwise (a 5xx, a 4xx without `error`), the profile stays "connected" and is asked again less and less often; press "Connect again" in the profile dialog. If a passing refusal looks like these, a working grant is marked for reconnecting and needs one.

Assumed: `repository.issues` with no `states` gives open and closed issues and no pull requests; `timelineItems` with the nine item types asked (closed, reopened, renamed, milestoned, demilestoned, labeled, unlabeled, parent added and removed) is accepted on an issue's `node` and gives the labels and milestone set at creation as events too, so replaying them from an open issue with none gives the right `from`; `ClosedEvent.stateReason` is set on closures since GitHub has had reasons; an upload in an issue's description or a comment is a `github.com/user-attachments/` link the token downloads, or, where it does not (a fine-grained token on a private repository), a signed link in the description's or the comments' `body_html`; the token's account is the agent's and the repository's owner, when a person, is the user.

If it is wrong, the read fails on a field GitHub refuses, the plan shows pull requests as tasks, a change's `from` is wrong or the status history is empty, an upload comes over as a dead link, or comments come over under the wrong author. **Workaround:** the repository is untouched; stay on GitHub. To check: on a sandbox repository with an open and a closed issue (one as not planned), a pull request, an issue whose labels, a `priority: high` label, milestone, title and parent were changed and that was closed and reopened, a picture and a PDF in its description and comments, read it through `importSource` and compare with the issues' timelines.

## Reading a Linear project's whole history for the import (BTN-1404)

The import reads a Linear team or Linear project through `linearImport` (`src/linear/import.ts`, `docs/trackers.md`, "Reading a project's whole history"). Checked by tests against a fake API; never against api.linear.app. Assumed: `issues` with `includeArchived: true` gives archived closed issues and those in the trash, the latter with `trashed: true`; a page of 25 issues with 25 relations, inverse relations and labels each stays under the complexity limit; `issue(id:)` by the issue's uuid answers for an archived issue, its `comments` take `includeArchived` and give replies flat with `parent`; `Comment.botActor`, `Project.creator`, `Issue.completedAt`/`canceledAt` and the `IssueHistory` fields asked (`fromState`/`toState`, `fromTitle`/`toTitle`, `fromPriority`/`toPriority`, `fromEstimate`/`toEstimate`, `fromParent`/`toParent`, `addedLabels`/`removedLabels`, `actor`) exist as named, a field left unchanged by an entry is `null`, and the creation has no `fromState`; an upload of an attachment is an `uploads.linear.app` link the key downloads.

If it is wrong, the read fails on a field Linear refuses or on the complexity, archived issues are missing from the plan, deleted issues come over, a reply comes over as a comment of the task, a change is missing or has empty values, an upload is a dead link, or comments come over under the wrong author. **Workaround:** the team is untouched; stay on Linear. To check: on the NAM sandbox team (`stands/README.md`) with a completed issue Linear archived, one cancelled, one marked duplicate of another and one in the trash linked from an open one, an issue whose state, title, priority, estimate, parent and labels were changed, a picture in its description, an uploaded attachment and a link attachment, a thread with a reply and a comment of an integration, read it through `importSource` and compare with each issue's history in Linear.

## The import into the built-in tracker on a live project (BTN-1405)

The import writes a project's whole history into the built-in tracker and switches the project there (`BuiltinImports`, `docs/trackers.md`, "The import into the built-in tracker"). Checked by tests on a fake source and by an e2e scenario through the service with the bench's board; never on a real tracker's project or with a service restarted mid-run. Assumed: a run that stops (a read that fails, a restart) goes on from its rows with nothing written twice; the pictures' rewritten addresses open on the page; the last pass before the switch takes the comments and tasks added in the source since, and the check matches on a project the source reads whole.

If it is wrong, a task's comments or attachments come over twice or not at all, a picture in a description is a dead link, or the check does not match on a clean import. **Workaround:** the source is not changed by the import — leave the project on it, or switch past the check after a look at the built-in tasks. To check: import a small Huly project with a closed task, a subtask, a blocking link, a picture in a description and comments of three authors; stop the service mid-run once and start the import again; add a comment in Huly before the switch, switch, and compare the numbers, comments with their authors, attachments and links; see nothing changed in Huly.

## Closed tasks in a copy to a real tracker (BTN-1289)

With "Move the closed tasks too" the copy creates every closed task in the target and gives it the target's status of its category (`docs/trackers.md`, "The copy into another tracker"). Checked by tests with a fake target and on the fake page only. Assumed: each adapter's `create` with a `Won` or `Lost` status leaves the task closed in one go (GitHub closes the issue as completed or not planned, GitLab and Forgejo close it, Huly, Linear and Jira move it to the status); the journal's first entry with the dates comes first on the card; GitHub's secondary rate limits on creating issues and comments slow a long copy down without failing it for good.

If it is wrong, a closed task lands open in the target and the chain there takes it, or the copy stops on GitHub with a rate-limit refusal. **Workaround:** close such tasks in the target by hand before the switch; after a refusal press "Continue" later. To check: copy a bench built-in project with a Done, a Canceled and a closed parent of an open task into each tracker of the sandbox; see them closed there under the right status with the dates entry first and the parent link kept; switch and see the chain there skip them.

## An outsider's task held on CI and agent files (BTN-1207)

A task the GitHub intake took from an outsider's issue (`IntakeEntry.outsider`) is not landed by its session when its branch changes a CI workflow, a `.claude` or `.codex` folder, `CLAUDE.md`, `AGENTS.md` or `package.json` (`guardedFiles`, `docs/chain/pr-mode.md`, "An outsider's branch"): the merge hook refuses the merge and the service pauses the lane, and in PR mode `openPull` does not push the branch. Checked by tests (`src/review/outsider.test.ts`, `open.test.ts`, `src/chain/reviews.test.ts`, `src/intake/intake.test.ts`, `plugins/agent-bridge/hooks/merges.test.mjs`) and by an e2e scenario of PR mode with the scripted agent (`src/e2e/intake.test.ts`), which runs no hooks; never live. Assumed: GitHub's `author_association` of an issue is `NONE`, `CONTRIBUTOR` or `FIRST_TIME_CONTRIBUTOR` for an outsider and stays so while the task runs; a session's merge goes through `git merge` of its branch in a shell, where the hook sees it; `git diff --name-only <main>...HEAD` in the worktree lists every file the merge brings; the remote's base ref is fresh after `openPull`'s fetch.

If it is wrong, an outsider's branch lands its workflow or agent files before a person looks, or a member's task waits for no reason. **Workaround:** keep PR mode on with a protected main branch and CI secrets behind an approval (`docs/guide/security.md`); read an outsider's branch before it lands. To check: on a public bench repository with the intake on and a Huly project, open an issue from a second account asking for a change to `.github/workflows/ci.yml`, label it, let the chain run it without PR mode and see the merge refused, the chain paused with the files named and the log listing them; merge by hand and see the chain go on at Done; then with PR mode on see no branch pushed and no workflow run; the same issue opened by the owner lands as before.
