# What has not been verified: Trackers

One area of [What has not been verified](../unverified.md), which says what an entry is, how to report a run into one and where a new one goes. What has been checked in this area is in [What has been verified: Trackers](../verified/trackers.md).

## A tracker that did not answer (BTN-825)

The page's calls to a tracker that did not answer fail at once with the error it failed with, instead of waiting the whole timeout again (`TrackerLink.page`, `docs/trackers.md`): the card of a task, a file of it, the task's actions, the vocabulary of a project and the changelog's list of a milestone. The chain's own poll is not silenced — it is what brings the tracker back. Checked by tests against a fake tracker (`src/tracker/link.test.ts`, `src/tracker/control.test.ts`): a timeout, a broken connection ("fetch failed" with its cause), and a tracker that answered (that what was asked for is not there, or that the credentials are refused) — the last two leave the page's calls alone. Seen live on 2026-11-09 with the author's GitLab CE host down: a task card's first call waited the whole 15 s, the second and the project's vocabulary failed in 2–13 ms with the timeout's text naming the tracker; when the host came back, its projects read again within 12 s of its first answer and a task card opened in 1.1 s (`docs/verified/trackers.md`). Still assumed:

- after a longer outage, when the poll's wait has grown to its 300 s, the page may keep saying that the tracker is down for minutes after it is up;
- "fetch failed" for a broken connection is what the page shows, its cause only in the log and on the `/status` page;
- a tracker that refuses the credentials or answers that what was asked for is not there is not a tracker that "did not answer" and does not hold the page's calls.

If an assumption is wrong, the page either waits the whole timeout on every request or says that the tracker is down while it is up. **Workaround:** open the page again when the tracker answers again; the poll notices it by itself. To check: keep a tracker's host down for over ten minutes, bring it back and time the page's recovery; point a profile at a wrong token and open a task card twice.

## A turned-off tracker profile (BTN-830)

A tracker profile turned off in Trackers and CI reaches nothing of its host, and a chain starts only by tasks read since its tracker last answered (`docs/trackers.md`, "Profiles"). Checked by tests: the profile's rechecks and retries stop, its tracker view is off with no link, its CI gets no token, its task card, vocabulary and project list answer `profiles.disabled` with no call, turning off is refused while a chain on it runs, waits or is queued, and Start refuses a list read before the tracker came back (`src/profiles/service.test.ts`, `src/tracker/trackers.test.ts`, `src/ci/adapters.test.ts`, `src/tracker/control.test.ts`, `src/chain/dispatcher.fresh.test.ts`). Seen live on 2026-11-09 with the author's GitLab CE profile off and its host down: over eight hours and a dozen service restarts the log held no call to the host, the task card and the vocabulary answered `profiles.disabled` in 2 ms, the tasks server refused at once, and the home card was dimmed with "is off: tasks are not read" and "Turn on"; with the host up, turning the profile on read its projects in 1.1 s (`docs/verified/trackers.md`). On 2026-11-14 (BTN-1156) a listener on the turned-off Gitea profile's port saw no request in almost 15 minutes and a service restart, and its first calls within a second of turning it on. On 2026-11-15 (BTN-864) turning the GitLab profile off was refused while GLP's chain ran and while it stood paused, with "Stop the chain" on the profile's row; Start on a project of the turned-off profile was refused at once and on the home card opened only the dialog that turns the profile on; turned on, the chain did not start and its first read took a task created while it was off; with the host down and while it answered 502, Start was refused as unread, and it started the next press after the first answer. Still assumed: unattended mode skips a project of the turned-off profile and picks it up again once it is on (the check ran with unattended mode off; it starts no chain by itself, and a chain on the profile cannot be left running when it goes off).

If the assumption is wrong, the page keeps waiting on a host that is off. **Workaround:** press Check on the tracker's card in `/status`, which reads its projects now. To check: BTN-864.

## Automatic milestone order (BTN-791)

Unit tests cover transitivity with missing dates and native positions, Linear's position conversion and queries, and Jira versions going by date with no catalog read. On 2026-11-08 (BTN-835, [verified log](../verified/trackers.md)) the chain, the card's choices, the filled active milestone and a restart followed Linear's milestone `sortOrder` live (and Jira's version sequence, since dropped), with positions set through the API. On 2026-11-11 (BTN-849) dragging a milestone in a Linear project's milestone list rewrote its `sortOrder` and the chain and the card followed. Jira has no such drag: the Releases page sorts versions by release date with no handle, a Kanban board shows no Versions panel, and the catalog's sequence is in effect the order the versions were created; so since BTN-1021 Jira gives no native position and its versions go by date, number and name, as the Releases page lists them. On 2026-11-14 (BTN-1155) four EKJ versions created against their dates went by date in the chain and the card's choices, the undated one last, and a Huly feed's dated milestone took its place among them by date. Still assumed: Linear's native order mixed with another tracker's milestones (no Linear feed could be added on the bench), which falls back to date for the whole set; that the Releases page orders undated versions among themselves as the chain does (by number, then name: not compared). Huly, GitHub, Forgejo, GitLab, Jira and the built-in tracker provide no native order. A mixed-source or incomplete set falls back to date, number and name; dated milestones precede undated ones. If an assumption is wrong, the chain can choose the wrong milestone, hold a task or stop with a milestone-order conflict. **Workaround:** correct dates/names or blocking links in the tracker and refresh, or set the project's own milestone order in Even Keel. To check: a Linear project with a feed of another tracker, its milestones dragged against their dates; two undated Jira versions against the Releases page. The missing-date and mixed-source policy is recorded for discussion in BTN-834.

Found there: a merged pull request and a `NO CHANGES:` mark close into the tracker's first done status, past the chosen one; BTN-1163 sends every close through the choice, checked by tests and the e2e `statuses.test.ts`, and live on 2026-11-15. Live on 2026-11-15 (BTN-555): the add-profile step on Huly, both Save and Skip; "only forward" on Huly; the pull request move on Jira; a chosen done status on Huly and Jira and a Huly feed's own, through a merge and a `NO CHANGES:` mark; a Jira start move with no transition in, for the band and its button; the `notDone` band on Huly and the `completeRefused` band on Huly and Jira, each closing once fixed. Later that day: the pull request move on Linear (In Review on the pull request, Done on its merge) and the `notDone` band on Jira, closing on the next pass once the rules took the status. Seen on the save: a status name the tracker does not have was taken without a word, and the move then failed only when it ran; BTN-667 refuses it on the save (`statusMoves.unknown`), checked live on Linear and Jira on 2026-11-15, and marks such a value "not in the tracker" at its field and logs one set by `config-import`, checked by tests only. Assumed:

- Huly writes the named status like any status change, and every issue status of the workspace is a choice, though a project's type may not have it: such a move is refused by name ("no status") rather than written.
- Linear's `workflowStates` lists the states of every team the key sees, and a name shared by teams is one choice; a team without that name refuses the move.
- Jira's `/rest/api/3/status` lists the site's statuses; a workflow with no transition from the task's status to the chosen one leaves the task where it is (a refusal on the page), and a transition with a screen of required fields is refused by Jira like a refused close.
- The start move runs after the session started and the pull request move after the pull request opened, both asynchronously; a slow tracker answers after the chain has already moved on, which only delays the band.

If one is wrong, a task stays in its status or, at worst, the tracker refuses the move and the page says so; the chain is never held by a move. **Workaround:** move or close the task in the tracker, or set "leave as is" and "automatic". To check: a status name the tracker lacks set through `config-import` — marked "not in the tracker" at its field, and that import's log line.

BTN-490 additionally checked the running service's starts and guard refusals from localhost and an HTTPS proxy, site access with the saved v2 profile through its gateway, and two consecutive live refresh rotations through isolated instances of the actual profile service and gateway. BTN-495 confirmed that v2 refuses a new controlled HTTPS callback outside the organization's domain rules: consent identifies the callback as restricted and disables Accept. No domain rule or working grant was changed ([verified log](../verified/trackers.md)). Linear and GitHub lost MCP OAuth in BTN-604 before any live check: their MCP servers take the tracker's token. On 2026-11-14 (BTN-1155) a chain session on a Jira profile connected through OAuth with no MCP token got the Jira MCP tools through the gateway on the grant alone and read its own issue with them. Assumed:

BTN-494 checked the direct network guard's scoped Lax callback cookie, successful code exchange, one-use state, draft binding, provider denial and guard refusals with clean final URLs in Chromium against a simulated provider and non-local socket addresses ([verified log](../verified/trackers.md)); a fresh consent on a live provider over direct HTTPS has not been repeated;
- a refused refresh or a second 401 marks the grant for reconnecting, and a session's tool call meanwhile fails with an MCP error rather than hangs. On Jira (2026-10-29) a revoked app made the gateway answer with an error rather than hang, but its refresh refusal, 403 `unauthorized_client`, did not mark the grant: BTN-589 ([verified log](../verified/trackers.md)).
- The profile dialog's Check and Save verify the selected MCP OAuth grant against the live providers, including an expired unsaved grant refreshed before its original ten-minute deadline (BTN-491). On Jira a saved and a fresh unsaved grant passed both (2026-10-29, [verified log](../verified/trackers.md)); the expired unsaved grant's refresh has not been exercised live. If it refuses working access, reconnect in the dialog or disconnect OAuth and use the fallback token.
- A refused consent (Cancel or Escape on Atlassian's page, a callback with `error=access_denied`) shows "MCP access was not granted" and logs one `consent` line with the provider's `error`, while a failed code exchange or grant check shows "MCP OAuth did not complete" (BTN-588). ## The person of a Jira MCP grant (BTN-590)

Atlassian gives an MCP grant to whoever is signed in to Atlassian in the browser, so it may be another person of the site than the profile's REST token (seen in BTN-489). The dialog checks a new grant at once, and Check, Save and the row compare the grant's person with the REST token's `/myself` `accountId`; a different one is a warning with "Connect again", never a refusal. Assumed, from Atlassian's MCP tool list and its `/me` answer, never seen live: Rovo MCP v2's `atlassianUserInfo` answers a text block of JSON with `account_id` and `name` (a `data` envelope, `accountId`, `displayName`, `nickname` or `email` are read too), and that `account_id` is the `accountId` of Jira's `/myself`. Checked only by tests on fake providers. If the tool is missing or answers otherwise, the person is unknown and nothing is shown: a grant of another person goes unnoticed, as before. If the ids differ for the same person, the warning shows for a correct grant; press "Connect again" signed in as the profile's person, or ignore it. Linear, GitHub and GitLab have no MCP grant (BTN-604): their sessions use the profile's own token, so there is no second person to compare.

## A Jira MCP grant revoked in Atlassian (BTN-589)

A grant revoked in id.atlassian.com → Connected apps was seen in BTN-489: the token check answered 401 `invalid_token`, the refresh 403 `unauthorized_client`, and the probe asked Atlassian's token endpoint every 30 s, two log lines each time. Now any 4xx of the token endpoint with an OAuth `error` (but `slow_down`, `temporarily_unavailable`, `server_error`, 408 and 429) marks the grant for reconnecting, so the row says "MCP: reconnect needed" and nothing more goes to Atlassian; the gateway and the refresh log a failure once per reason and once when it works again, and a failing probe waits longer each time, up to an hour. Checked only by tests on fake providers. If Atlassian answers a revoked grant otherwise (a 5xx, a 4xx without `error`), the profile stays "connected" and is asked again less and less often; press "Connect again" in the profile dialog. If a passing refusal looks like these, a working grant is marked for reconnecting and needs one.
