# What has not been verified: Sessions

One area of [What has not been verified](../unverified.md), which says what an entry is, how to report a run into one and where a new one goes. What has been checked in this area is in [What has been verified: Sessions](../verified/sessions.md).

## Writing Claude folder trust before launch (EKR-59)

Without a consent setting (EKR-83), the Claude adapter writes `projects["<checkout>"].hasTrustDialogAccepted = true` in the selected account's `.claude.json` before each background launch/resume. Existing and newly added projects behave alike; JSON schema 26 and database step 27 remove the legacy flag. Tests cover atomic writes preserving other data, malformed-file refusal, config migration, repeated launches, account changes and SDK routing.

The prerequisite passed in Windows Sandbox on 2026-11-05 with CLI 2.1.318: both previously untrusted locations answered after only the checkout flag was set, a launch after daemon restart answered too, and the compiled writer preserved the neighbouring project and admitted a worktree session. Checkout resume answered in place; a worktree resume answered in a copy after a stop/exit race, so strictly in-place worktree resume remains open. The account file was restored and all probe jobs and daemon stopped. Details are in [verified sessions](../verified/sessions.md); the blocked 2026-11-04 bench attempt remains there as history.

The full wizard → automatic trust → chain launch ran in Windows Sandbox on 2026-11-06 ([verified sessions](../verified/sessions.md)) and found EKR-92: a backslash key for a folder the CLI had never seen was ignored. With the fix, a fresh checkout's first Start through the chain API wrote the forward-slash key and launched a real worktree session on CLI 2.1.319; it merged, the tracker task closed and the chain ended. Settings, trust entries and installed modules were restored. The installed package of the fix then ran wizard → Start → merge for a folder never seen and for one with only an old backslash key, both without a trust pause. On Linux (Docker, 2026-11-06, [verified sessions](../verified/sessions.md)) a fresh folder launched without a pause; an unwritable account folder paused with `claude.trustWriteFailed` (access) and went on after Check again and resume; a project folder reached through a symlink paused with `claude.untrusted`, since the CLI trusts the resolved path only (EKR-94), and the page's command run as the service's own user accepted it through the CLI's dialog and resume went on. Since EKR-94 the key is written and checked under the folder's `realpath` off Windows: with the fix a launch from the symlinked folder on Linux wrote the real path's key and went through without a pause; `/tmp` or `/var` on macOS was not run. A Windows junction is resolved by the CLI too: under the Windows service (below) a folder reached through one paused while only its own key was written. Since EKR-96 the Windows key is the junction's real path: with the fix a launch from the junction under the service wrote `C:/…/repo` and went through without a pause. A `subst` drive and a mapped network drive are kept as written (`realpathSync.native` turns them into the target drive or a UNC path), and what the CLI reads there was never checked: such a folder may still pause on its first launch. Until EKR-95 the write turned the account's `.claude.json` from mode 600 into 644; with the fix the file stayed 600 after the write on Linux. Under the Windows service `EvenKeel` run as a local non-admin user (Windows Sandbox, 2026-11-06, [verified sessions](../verified/sessions.md)) the trust went into that user's account folder and sessions ran in session 0; a junction folder paused with `claude.untrusted` and the service command `runas /user:<user> "powershell -NoExit -NoProfile -ExecutionPolicy Bypass -File <state>\trust\<task>.ps1"`, typed into an administrator's cmd, asked the user's password, opened `claude` as that user in the folder with its account folder (the CLI's first-run theme choice came before the trust dialog), and after the dialog Check again and resume went on (EKR-85, EKR-86, EKR-87). Still not run live: changing the session's account in a real chain, another Linux service user (`sudo -u` command), and macOS. The UI was inspected on fake-page fixtures only. EKR-86 captures the refused invocation's executable and account override; tests cover launch/resume snapshots despite changing settings, persisted notice rendering, global/managed folders and Windows/shell quoting. Executing the snapshot commands on macOS and as another Linux user remains open; older pauses retain the PATH fallback. EKR-87's script and quoting beyond that run are covered by tests only; never run are a script path with spaces typed into cmd, `-ExecutionPolicy Bypass` under a group policy that forces one, and non-ASCII paths read from the BOM'd file by Windows PowerShell 5. Repeat on the authorized benches in `even-keel-backstage/stands/README.md`, with a previously untrusted checkout and a backup of its account file; inspect actual jobs and transcripts, then restore the file and settings and stop probe processes. A fresh account's separate bypass-permissions disclaimer may still block a launch: the flag does not accept it. **Workaround:** fix a damaged/unwritable account configuration, then use Check again and resume to retry automatic trust; for a CLI trust refusal, accept the dialog manually under the session's account before retrying.

## Agent SDK locks the checked CLI (BTN-610)

Execution = Agent SDK for Claude needs `cli.claude: checked`: the config refuses the pair with `system` (`config.executionCli`), DB step 21 and config v22 move a stored pair to `checked`, and a failed download no longer falls back to Yours. Unit tests cover the rule, both migrations and the fallback; the page's switch and lock were looked at on `dev:fake`, and on a Linux server (2026-10-31, [verified.md](../verified/sessions.md)) Yours stayed disabled with its tip under Agent SDK, but moving Execution to CLI --bg was refused with `config.executionCli` although Checked was chosen (BTN-638), so Yours opening again was not seen. The cause was the page, not the save: an unsaved CLI --bg opened Yours, and its pick switched the source at once against the saved Agent SDK. BTN-638 kept Yours shut until the new Execution was saved; since BTN-682 the CLI version on /settings is a field of the form, saved together with Execution, so Yours opens as soon as the form leaves Agent SDK, and the download of a missing copy is asked after the save. A unit test covers one save moving both ways (`ConfigStore.saveShared`); the page was looked at on `dev:fake` only. The sandbox ran the BTN-638 page before BTN-682 (2026-11-01, [verified.md](../verified/sessions.md)): Agent SDK picked over a saved Yours moved the source to Checked at once when a copy was there, and Yours opened after the new Execution was saved. Not yet run live: that picking Agent SDK with Yours chosen and no copy, then saving, opens the consent and a real download, that moving Execution to Auto or CLI --bg and Yours in one save is taken, that a consent cancelled after the save leaves the header's "Download" band, and that a real database with the pair, upgraded to step 21, starts SDK sessions once the copy is downloaded. **Workaround:** if a save is refused under Execution, pick "Checked" in "CLI version" and save again; if the copy is not downloaded after the save, press "Download" in the header's band or under "CLI version"; if sessions still go on `--bg`, check that `EVEN_KEEL_CLAUDE_BIN` is unset.

## Silent turn recovery (BTN-496)

The shared five-minute confirmed replacement and thirty-minute hang rule is covered by unit tests for Claude Code, Codex and Copilot file activity, OpenCode's database/output stamp, resumed processes, stale confirmations and the dispatcher handoff. Page states can be reproduced with `?chain=silent-short`, `?chain=silent` and `?chain=hung`. Windows file-size activity with Codex's frozen rollout modification time and Copilot's advancing `events.jsonl` time was checked in BTN-518 (see `verified.md`), and Claude's on Linux through the SDK on 2026-10-31: the warning at five minutes and its reset by the transcript's growth; file-size activity on macOS remains unverified. Not yet run against a genuinely stalled model request on every CLI and the Claude SDK: that observed file growth or agent stamps keep tracking real output and that the existing stop/handoff path ends the silent turn before a new agent starts. A long silent but healthy tool can qualify too; the five-minute action is deliberately confirmed and neither threshold stops the session automatically. **Workaround:** leave a healthy long command running, or confirm "New session" once its silence is unexpected. Screenshot checks and the controlled local activity check are recorded in `verified.md`; they do not claim a provider outage was reproduced.

## Temporary model errors (BTN-498)

Codex's `Selected model is at capacity. Please try a different model.` was reported from a real refusal (2026-10-27) and seen again on 2026-10-29 with `codex_error_info: "server_overloaded"`; the text held it then, and since BTN-709 the pattern matches that code too. OpenCode's was seen under the service (2026-11-02, [verified.md](../verified/sessions.md)): OpenAI's `Our servers are currently overloaded` in the account log made a retry, OpenCode went on by itself half a minute later and closed the task, and the retry did not fire after Done. Unit tests cover all four transcript formats, the `overloaded_error`, `server_is_overloaded` and `server_overloaded` codes (the last two with a generic message in a Codex rollout), 503/529 with an overload/unavailability message, a 15-minute retry doubling up to four hours, reset on success, cancellation by a human answer or a replacement, and keep-warm after an overloaded ping. The fake page checks the waiting lamp, next-attempt time, chat and replacement controls. Not run through a real provider outage: Claude and Copilot variants, a scheduled resume under the service (both refusals seen ended before it: a restart by hand, the agent's own retry), and a Claude keep-warm fork refused by the overload and later recovering. A refusal with an unknown spelling remains a permanent error and waits for a person; a misclassified refusal could resume unnecessarily. **Workaround:** answer from the chat, choose another model and use "New session", or pause the chain to stop automatic retries. No overload is manufactured against a live provider.

## A handoff past a failed session (BTN-650)

A handoff from a session that failed before its first answer carries the steps, the last message, the note and the transcript of the session before it, plus a line on each failed one (`docs/chain.md`). Unit tests and an end-to-end scenario with the scripted agent cover one and two failed sessions in a row. Not run live: a real `Invalid API key` or empty-balance session on an API-key account followed by "New session", a limit or an account switch, with the earlier session's transcript in another account's folder. ## A session left mid-turn by the cleanup (BTN-616)

**Log check (17c):** search `rare: 17c` for `cleanup-deferred status=busy` or `status=waiting`, then `cleanup-stop result=stopped` for the same session. A failed stop has `result=failed` and its reason. Repeated polls and service restarts do not repeat the deferral or result. A session that exits on its own needs no stop and has no stop-result line; a restart forgets the deferred stop, as before. The code lives in `src/service/cleanup.ts` and `src/sessions/lingering.ts`.

A session in a done task's folder that the cleanup found `busy`/`waiting` is stopped once its turn ends (`docs/chain/worktrees.md`, "A session left mid-turn"). An end-to-end scenario with the scripted agent covers a second session in the task's folder. Not run live: a real Codex or Claude session caught that way — the mismatch between the task's view and the listing that leaves one behind cannot be made on purpose — so whether a real stop of such a session lands is assumed from the usual cleanup's stop. A restart before its turn ends forgets it, as before. **Workaround:** stop the session from the page or kill its pid.

## A stop after Done that timed out in the folder's queue (EKR-99)

A cleanup after Done whose stop of the session timed out in the account folder's queue keeps trying it for 5 minutes and removes the worktree folder after it, warning only if that fails (`docs/chain/worktrees.md`, "A stop that timed out"). Unit tests cover the retry, the folder and the warning once the wait is over. Not run live: a real Done right after a service restart, when `/usage` and the `/context` probes fill the queue (seen 2026-11-07, EKR-CARRY on the host) — the queue cannot be filled on purpose without a slow CLI — so whether the stop lands on the next ticks and the Windows folder goes after it is assumed. **Workaround:** if the banner still comes, stop the session from the page or kill its pid from an administrator terminal (the service's session 0), then delete the folder.

## The chain's session listing in a clogged folder queue (EKR-102)

A chain step waiting on `claude agents` — a launched or resumed session showing, a stop before a handoff, a resume or a slot switch — paused the chain when the listing timed out in the account folder's queue right after a service restart (seen 2026-11-06 on the host, BTN). Now that listing goes ahead of the waiting calls and, if it still times out, is tried again for up to 5 minutes without using up its wait (`docs/accounts.md`). Unit tests cover the retry, the wait's growth and the priority. Not run live: a real restart with a chain step due at once while the `/context` probes fill the queue — the queue cannot be filled on purpose without a slow CLI — so whether the step goes on is assumed. Meanwhile the dispatcher's step can hold up to 5 minutes, holding the other chains' steps too. **Workaround:** if the chain still pauses with `agents --json --all timed out`, resume it from the page.

## A resume that starts a copy

**Log check (18):** search `rare: 18` for `resume-copy`, with `oldSession`, the adopted session id, `transcript=true/false` and `elapsedMs` since resume began. If initially missing, `transcript-appeared` records the first monitor observation of its file, with the old id and elapsed time, also when the service restarted in between. A copy that never gets a followed transcript has no appearance line; an in-place resume has no copy line. The elapsed time measures observation, not the file's exact creation time.

A resumed session in place was seen to show a fresh session id for under a second before it takes its old one, and the chain now waits for the old id (`docs/sessions.md`). When the CLI starts a copy instead (a new job), the chain takes the first session of that new job; whether a copy also passes through a throwaway id first was not seen. If it does, the chain follows an id with no transcript: the chat says the transcript is not found and the card shows "Session booting" for 5 minutes. The workaround is "New session".

## A tool approval in an SDK session (BTN-303)

Out of unattended mode, a tool call the CLI puts to `canUseTool` waits as a question with "Allow" and "Deny", and an answer allows it with its own input or refuses it (`docs/sessions.md`). Covered by tests only: no live session has asked for an approval yet. Assumed: that the CLI in `auto` mode asks for one at all and only for calls its classifier leaves to a human; that `allow` with the unchanged input runs the call; that an approval already waiting is refused within a poll once unattended mode goes on. If the CLI never asks, nothing changes against before; if an allowed call does not run, the session gets an error for it and goes on without it; if a waiting one is not refused, the chain stands on it. **Workaround:** answer "Deny" from the page, or "New session" on the task.

## A permission dialog answered from the page (BTN-269)

A `--bg` session waiting on a permission dialog has the call as its question while the `checkpoint` plugin's `PermissionRequest` hook holds it, and the answer goes to the hook, not by a resume (`docs/sessions/chat.md`, "Permission dialogs"). Seen live on CLI 2.1.308 with a hook of the same protocol written by hand: the hook runs beside the open dialog, its `allow` and `deny` are taken there without a stop, and a decision from elsewhere leaves it running. Not run: the whole path through the service — a chain session, its question on the page, the answer from the chat or a tracker comment; an answer through Remote Control while the hook waits (assumed to leave the hook running too, so the service closes the call once the session stops waiting); a hook held for the full 29 minutes against its 1800 s `timeout`; a dialog the `auto` classifier opens rather than an `ask` rule; Codex taking the hook for its own approvals (it skips them by `turn_id`). If the answer does not reach the dialog, the session keeps waiting and the page shows the question as answered; if a closed call lingers, the page shows a question the session no longer has. **Workaround:** answer the dialog through Remote Control; "New session" on the task.

## Keeping a waiting session warm (BTN-437)

With `keepWarm` above 0 a fork of a waiting Claude chain session asks for one word shortly before its cache goes cold (`docs/chain/exceptions.md`, "A keep-warm ping"; `docs/sessions/cache.md`, "Keep-warm"). Seen on probes (CLI 2.1.310, Haiku, 2026-10-26): forks of short `-p` and `--bg` sessions read 88–100% of their prompt from the cache and wrote no transcript. Seen through the service on a short Opus `--bg` chain session without packages (BTN-446, [verified log](../verified/sessions.md)): one ping read 96.6% and left the session, its question and its process as they were, and the answer an hour after the last one read the cache; a Haiku session waiting on a question in text read 95.5%. A Haiku `--bg` session waiting on an `AskUserQuestion` missed the cache whole once (BTN-704, CLI 2.1.316, read 0 of 18.8k against the session's 23.1k), and such sessions went unpinged until BTN-705 rechecked it through the service on CLI 2.1.319: the fork's request had the session's own shape (the same system blocks and tools) and read 95.5% and then 100%, so they are pinged again. Why the BTN-704 fork sent 4.3k fewer tokens than the session's own first call is not known: that session asked on its very first call, before any deferred tool was loaded, and the CLI has changed since; a repeat shows as a `missed the cache` line, at the price of one cache write per session. Not run: a long session with its packages through the local MCP gateway and the `checkpoint` hooks off for the fork only; a fork of an SDK session (`forkSession`, `persistSession: false`, the preset system prompt with the project's appended rules); a ping kept up for hours. The `keepWarm` ceiling and the break-even are left to the tests of `warmStep` (`src/sessions/keepwarm.test.ts`): they turn on time alone. Assumed: that the fork's system prompt, tools and model match the session's closely enough for the 90% hit share — a mismatch shows as a `keepwarm: … missed the cache` line in the service log and turns the pings off for that session, at the price of one cache write; that a fork leaves the waiting session and its question untouched. If the fork does change the session, its question or the next answer looks different on the page. **Workaround:** set "Keep the cache of a waiting session warm, hours" to 0 in Settings → Sessions; it applies at the next check.

## Keeping a Codex session warm (BTN-564)

The same setting pings a waiting Codex chain session too: `codex exec --ephemeral --sandbox read-only --disable hooks … fork <id> -` (`docs/sessions/cache.md`, "Keep-warm"). Seen live only on probes (codex-cli 0.164.0, `gpt-6-luna` on a free ChatGPT account, 2026-11-01, BTN-677): forks of a one-turn `--approve-for-me` session 1.5–4 minutes after its turn read 97–99.6% of their own request from the cache, wrote no rollout, refused a command and ran no hook. Seen through the Windows service (session 0) on a short `execution.codex: bypass` chain session of the same account (BTN-446, [verified log](../verified/sessions.md)): the ping 25 minutes after the last call, the prompt on stdin, read 98.6%, left no rollout, no registry record and the session's own rollout unchanged, and the answer 43 minutes after the last call read 99.2%. Not run: a long multi-turn session on Plus with `gpt-6.1-sol`, a session after a compaction, more than one ping in a row. Assumed: that the fork's usage is its own request plus the total the session's rollout last wrote, so that taking that total out (`forkSpend`) leaves what the ping read — a total the rollout has not caught up with shows as a miss; that the cache lives 30 minutes from the last model call; and that a read-only fork of a bypass session still reads the cache. A miss or a wrong spend shows as a `keepwarm: … missed the cache` line in the service log and turns the pings off for that session, at the price of one ping. **Workaround:** set "Keep the cache of a waiting session warm, hours" to 0 in Settings → Sessions; it applies at the next check.

## How long each agent's prompt cache lives (BTN-560)

The lifetimes in `docs/sessions/cache.md` ("Every agent's cache") come from the providers' documentation and from a handful of pauses in Tally. Codex's 30 minutes rests on 17 pauses longer than 3 minutes, all on a ChatGPT sign-in; a pause of 35 minutes went both ways. Never seen: Codex on an API key, OpenCode on ChatGPT, Copilot or an Anthropic key, Copilot on a Claude model, a Claude SDK session on a key, and more than one long pause of an SDK session. Assumed: that these follow their model's documented lifetime, as the measured ones did. Since BTN-563 the chain takes the window per agent (Codex 25 minutes, Copilot by `cacheExpiresAt`, else 25; Claude and OpenCode 55), so a wrong lifetime either resumes a cold session as if warm, paying a whole cache write, or hands a still-warm session to a new one. Never run live: a Codex or Copilot chain session handed over rather than resumed after a pause of 25–55 minutes, and the Copilot window read from a live transcript (the tests fold events shaped as 1.0.98 writes them). **Workaround:** none needed; the share of `cache_read` in the first answer after a resume in Tally shows which it was.

## Handoffs by context size turned off (BTN-255)

With `contextHandoffs` off the checkpoint endpoint answers `source: "off"` and the hook asks for no handoff at any context size (`docs/sessions/checkpoint.md`, "Checkpoint threshold"). Checked by tests of the hook's plan and the settings levels, and on 2026-10-26 by the real `context-checkpoint.mjs` process against a fake endpoint: at 500k tokens it stayed silent on `source: "off"` and nudged on `calibration`. The service's own answer for a live session was read on 2026-11-07 ([verified log](../verified/sessions.md)): `source: "off"` with the switch off on the project, `window` once it was back. Not run: a real chain session past its threshold with the switch off, and its own compaction afterwards. Assumed: that the session's `checkpoint` package is 0.13.0 or later — an older one does not know `source: "off"` and keeps nudging at the threshold; that the agent's compaction then keeps the session going without a handoff. **Workaround:** if a session still gets the nudge, update the `checkpoint` package on `/tools` and press "New session"; to stop the nudges at once, set the threshold to its highest value as before.

## A task label selecting compaction

The label `Break | compaction` pins a task's checkpoint threshold to 999999; the handoff label or no label inherits the project's threshold. The settings resolver is tested, and the path from a live tracker task to the service's checkpoint endpoint was checked on 2026-11-07 ([verified log](../verified/sessions.md)): the label on a Huly task answered `first: 999999` for its session. ## A key refused after it was added

The check of a key was seen live answering 200 for a working key and 401 for a made-up one, and on 2026-10-25 401 `authentication_error` "invalid x-api-key" for a key disabled in the Console after it was added and again once it was deleted: the check at the service's start made the account `needsLogin`. ## An API key's organization header

Replacing an API account's key (BTN-418, `docs/accounts.md`, "The key's organization") refuses a key of another organization by the header a working key's answer carries: Anthropic's `anthropic-organization-id` on the models list, OpenAI's `openai-organization` on `GET /v1/me`. ## A dead `--bg` job left blocked by its daemon (BTN-648)
