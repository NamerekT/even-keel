# What has not been verified: The page

One area of [What has not been verified](../unverified.md), which says what an entry is, how to report a run into one and where a new one goes. What has been checked in this area is in [What has been verified: The page](../verified/page.md).

## Header account after a labelled task closes (BTN-539)

The server selector and fake page cover a saved session account, changed project settings, paused/stopped chains, fallback, deduplication, skipped/held tasks and the next ordered task after Done. The real service has not been watched while a labelled task closes and the next labelled task waits to start. Check that the header switches immediately on the tracker update, before launch, and keeps the current session's original folder after a settings change. **Workaround:** read the session's account and the project's Providers and models settings until this live check passes.

## Secret fields and the browser's password manager (BTN-633)

A key, token or password field is a text field dotted by `-webkit-text-security` (`secretInput`, `web/src/ui/secret.ts`), so Chrome and Edge are assumed not to offer "Save password?" for it: their password manager watches only `type="password"` fields. Checked headless: every secret field of the settings, the Tally form, the account dialog and the package keys is a text field with its value in dots; headless Chromium has no password manager, but a desktop Chrome and Edge showed no bubble on any of the four forms below (2026-11-01, [verified.md](../verified/page.md)). Not seen: Firefox, where `CSS.supports('-webkit-text-security', 'disc')` decides — false leaves the field a password and the offer stays — and Opera. To check, in such a browser: fill the Tally writer password and press "Check and save", add an account with a key, save a package key and the page token; no bubble should come up. **If it does:** decline it with "Never" for the page's address.

## A chain paused for a tracker its sessions would not see (BTN-656)

With "Task description in the prompt" off and no package of the project bringing the tracker's MCP server, Start and Resume put the chain in paused with that reason and two buttons beside it, "Turn on <package>" (or "Add the tracker's package") and "Turn the task description on"; once either is done the chain goes on by itself within a minute. A running chain whose package is turned off pauses before its next task. Checked by the dispatcher's tests and on `dev:fake` (`?chain=tracker|trackerAdd`). An end-to-end scenario covers the service: the description off and no package bringing the tracker's server, Start, the pause with its reason, the description turned on in the project's settings and the first task starting within a minute without Resume. Not run live: the Huly plugin as the package, either button on the page, and the package turned on instead of the description. **If it does not go on:** press Resume once the package or the description is on.

## A chain paused for packages that are not ready (BTN-657)

An enabled package that is not installed, failed to install or lacks a key puts the chain in paused with "Open the project's packages" beside the reason, instead of a running chain waiting under the banner; once the package is ready the chain goes on by itself within a minute. Packages that only start or do not answer, the gateway, a closing task, CI, limits and a slot stay waits, named by the project's chip "waiting · <reason>" and a line on its card and page. Checked by the dispatcher's tests and on `dev:fake` (`?chain=packagesPause|packages|packagesSilent|gateway|closing`). An end-to-end scenario covers the service: a remote MCP package whose header needs an unset key, Start, the pause with its reason, the key set through `packages/key`, the gateway's probe passing with it and the first task starting within a minute without Resume. Not run live: a plugin or `npx` package not installed or failed to install, the button on the page, and the key set from `/tools`. **If it does not go on:** press Resume once the key is set.

## The wizard's trust check

It counts a folder trusted when the global `~/.claude.json` or the `.claude.json` of the shared Claude account's folder trusts it: `claude` started with an account folder's `CLAUDE_CONFIG_DIR` records the accepted dialog in that folder's file only (seen live on 22.10.2026, BTN-300). It does not check Codex's trust at all. The warning does not hold the add: if you trusted the folder under the account the chain runs on, add it anyway. Seen in the sandbox (2026-11-01, [verified.md](../verified/page.md)): the warning with both commands, and the wizard reading the folder again by itself once the dialog was accepted in a terminal. Not seen: a folder that passes the check but is not trusted for the chain's account, pausing the chain at its first launch. The second command, for a terminal of another user than the service's (BTN-310: `runas /user:<user> "cmd /k cd /d <folder> && claude"` on Windows, `sudo -u <user> -H claude` elsewhere), was never run: assumed, `runas` asks for that user's password and opens a console in its profile, so the trust lands in that user's `~/.claude.json`; a service on a built-in account (LocalSystem, a user without a password) cannot be reached this way, and a folder path with `&` or `%` breaks the `cmd` line. Since BTN-687 the second command shows only while Even Keel runs as a system service (`runsAsService`): on Windows the parent process is a service in `tasklist /svc` and not the tray host, on Linux `/proc/self/cgroup` puts the process in `system.slice/<unit>.service`, on macOS `XPC_SERVICE_NAME` names a job with a plist in `/Library/LaunchDaemons`. Covered by tests for the cgroup line and the page's pick; not seen live in any of the three, nor `npm start` and the tray giving one command. If the guess is wrong, a service shows only the first command, or `npm start` still shows `runas`. **Workaround:** if it does, sign in to the machine as the service's user, or open `claude` in the folder from any shell of that user, and accept the dialog.

## The setup's Git step on a machine without git (BTN-731)

The step reads `git --version` from the service and takes an ENOENT of the start as "git is missing" (`GitResult.missing`); a test checks that with an empty `PATH`, and the page's states on `dev:fake` (`?git=missing|bare|anon`). Since EKR-54 the command comes from the package manager the service finds on its `PATH` (winget by `lstat`, since `stat` refuses its app alias; seen found on the host by `lstat` and missed by `existsSync`), with the git-scm.com download link always under it and alone where none is found; awaits the sandbox, which has no winget: the step should show only the link. The wizard's `git init` and first commit ran live on real git ([verified](../verified/page.md)). Seen in the sandbox with the start at sign-in (2026-11-04, [verified](../verified/page.md)): a machine with no git showed the step red with the winget command, which the sandbox lacks (before EKR-54); git installed meanwhile stayed unseen through "Check again" and even the tray's Restart, since the host handed node the `PATH` of its own start, until the machine restarted or the tray's Quit and `even-keel install` from a new terminal. Since EKR-57 the host builds node's `PATH` anew from the registry at every start, with its own leftover entries after, and the step on Windows says to restart from the tray; awaits a check in the sandbox: no git, install it, the tray's Restart, "Check again" — green. Not narrowed: once, git removed and the machine restarted, the step still showed git installed on a reload of the page; whether "Check again" was pressed is not known. Not seen: a Windows service, the install commands of macOS and Linux; "Save" on a service that runs as another user than the one at the page, which writes that user's global config (assumed from `git config --global` run in the service's home). **If it is wrong:** install git, then Quit Even Keel in the tray and run `even-keel install` from a new terminal (or restart the machine), and set the name with `git config --global user.name` and `user.email` as the service's user.
