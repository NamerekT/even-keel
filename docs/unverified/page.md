# What has not been verified: The page

One area of [What has not been verified](../unverified.md), which says what an entry is, how to report a run into one and where a new one goes. What has been checked in this area is in [What has been verified: The page](../verified/page.md).

## A built-in task's edit saved as the tab closes (BTN-1027)

Unit tests cover the drafts (key by project GUID, task and field, the leftover rule, the `keepalive` size cap); on `dev:fake` a script checked the title saved by the backdrop and dropped by Escape, the description saved by × and by a hidden tab, the note kept unsent across a close, a leftover title re-sent on the next open, and a leftover title and description refused as a conflict opening their windows with the draft kept. A real tab and browser close with the title editor open was seen against the service on 2026-11-13, and on 2026-11-15 a description of 89,889 bytes closed with the tab stayed a draft that the next open put back and sent ([verified](../verified/page.md)); that send was refused by the server's body cap, BTN-1183, which keeps any description over ~32 KB from being saved from the card. On 2026-11-24 a title edit survived an iPhone killing the page installed as an app ([verified](../verified/page.md)). Not checked: Chrome on Android discarding a backgrounded tab, a Safari tab killed in the background. **If it is wrong:** the edit is not in the task after the tab closed; open the card again — the kept draft is sent anew, or the conflict window shows it.

## The setup's Git step on a machine without git (BTN-731)

Since BTN-877, a nonzero exit containing `xcrun: error: invalid active developer path` is also treated as missing git
on macOS: `/usr/bin/git` may be only the stub without Command Line Tools. The setup always offers
`xcode-select --install`, even with Homebrew on PATH, with a note that full Xcode is unnecessary and an existing
Xcode installation may need `sudo xcodebuild -license accept`. A license failure stays an ordinary git error with
its output. Pure-function tests cover the stub, ENOENT, other platforms, successful exits and unrelated failures.
Not checked live: the actual macOS stub opening its system dialog, the setup after installing Command Line Tools,
and a retry after accepting the Xcode license. **Workaround:** install Command Line Tools with
`xcode-select --install` (or accept the installed Xcode's license), then press Check again.

The step reads `git --version` from the service and takes an ENOENT of the start as "git is missing" (`GitResult.missing`); a test checks that with an empty `PATH`, and the page's states on `dev:fake` (`?git=missing|bare|anon`). Since EKR-54 the command comes from the package manager the service finds on its `PATH` (winget by `lstat`, since `stat` refuses its app alias; seen found on the host by `lstat` and missed by `existsSync`), with the git-scm.com download link always under it and alone where none is found; awaits the sandbox, which has no winget: the step should show only the link. The wizard's `git init` and first commit ran live on real git ([verified](../verified/page.md)). Seen in the sandbox with the start at sign-in (2026-11-04, [verified](../verified/page.md)): a machine with no git showed the step red with the winget command, which the sandbox lacks (before EKR-54); git installed meanwhile stayed unseen through "Check again" and even the tray's Restart, since the host handed node the `PATH` of its own start, until the machine restarted or the tray's Quit and `even-keel install` from a new terminal. Since EKR-57 the host builds node's `PATH` anew from the registry at every start, with its own leftover entries after. The step on Windows names the restart by how Even Keel was started (`windowsStart`, the parent process): the tray's Restart, a restart of the Windows service by its name, or a start from a new terminal; node checks git at its start, so after the restart the step should turn green by itself. Seen in the sandbox on 0.2.1-rc.1 (2026-11-04, [verified](../verified/page.md)): git installed, and the page showed it as soon as it was in. Awaits: `even-keel` started in cmd: the line says a new terminal, and a start from one turns the step green. Assumed, not seen: node started by `npm start` or the npm shim has `cmd.exe` for its parent and reads as a terminal. Not narrowed: once, git removed and the machine restarted, the step still showed git installed on a reload of the page; whether "Check again" was pressed is not known. Seen under a Windows service run as another user than the one at the page (Windows Sandbox, 2026-11-06, [verified](../verified/page.md)): "Save" wrote the name and email into that user's own `.gitconfig`, and its sessions merged with them. Not seen: the step's restart line under a Windows service, the install commands of macOS and Linux. **If it is wrong:** install git, then Quit Even Keel in the tray and run `even-keel install` from a new terminal (or restart the machine), and set the name with `git config --global user.name` and `user.email` as the service's user.

## Paste from the clipboard in the chat on a phone (BTN-1350)

## Files of the phone's sheet without the camera in Chrome on Android (BTN-1421)

A file input with no `accept` makes Chrome on Android offer Camera, Camera Video and Files, though the sheet has its own Camera tile. Chromium's `SelectFileDialog` (read at its source, 2026-11-22) adds the camera and camcorder to its chooser only when `accept` is empty, holds `*/*` or names an `image/` or `video/` type, and drops the file manager's type filter when a type is `application/octet-stream` ("generic"). So in Chromium on Android (a user agent with `Android` and `Chrome/`) the sheet's Files has `accept="application/octet-stream"` (`sheetSources` in `web/src/pages/fileTiles.ts`): the file manager should open at once, pictures and videos still pickable. Firefox on Android (which filters by the type), iOS and the desktop's `+` keep the plain input. Unit tests cover the choice by user agent. Not seen on a real phone: that the chooser is skipped when the file manager is its only target, that pictures, videos and a PDF are all pickable, and Samsung Internet. **If it is wrong:** Files still shows the camera menu, or the file manager greys out some files; attach a picture through Photos, and report the browser's version.

## The effort's bar scale beside a model outside Chromium (BTN-1369)

An effort next to a model — a task's run label, a chat's card, the chat's status line, a session's Model fact — is a scale of five bars (`EffortBarsIcon`), an inline SVG a word's space after the model, sized `1cap` high and `1.75cap` wide (`0.7em` and `1.225em` where `cap` is unknown) and standing on the text's baseline by `vertical-align: baseline`. Headless Chromium on Windows (Segoe UI) shot it at 2× and 3× in the four places: the bars' bottom on the baseline, the tallest bar a capital's height, the label no wider than with " · high". Not seen in Firefox (no `text-box`) nor Safari, nor with macOS fonts. **If it is wrong:** the bars sit a pixel or two off the text's line or stand taller than the capitals; the effort's word is still in the tip.

## Dictation into the chat field (BTN-1343)

The chat field's microphone (`DictateButton` in `web/src/pages/DictateButton.tsx`, the pure parts in `dictation.ts`) runs the browser's `SpeechRecognition` (`webkitSpeechRecognition` in Chrome and Safari) in the page's language, with interim results written into the field as they come. A desktop listens continuously until a second press; a touch screen stops at the first pause, since Chrome on Android was reported to repeat earlier phrases in a continuous session. Unit tests cover joining the results, the space before them and the error codes; headless Chromium showed the button and its listening state at 1600×1000 and 390×844, without a microphone. Not seen with a real microphone: Chrome and Edge on Windows, Chrome on Android, Safari on iOS and macOS, a page over Tailscale's HTTPS, the browser's permission prompt and the text the recognizers give. **If it is wrong:** nothing appears in the field, a phrase is repeated, or the tip names an error; type, or dictate with the keyboard's own microphone.

## Dictation through the classifier's model (BTN-1391)

With the classifier's LiteLLM set the microphone records (`useRecording` in `web/src/pages/useRecording.ts`) and the service sends the sound to the Dictation model (`Dictation` in `src/dictation/transcribe.ts`), which hears the language. Checked: TTS phrases sent straight to LiteLLM as Opus in WebM and AAC in MP4 through `google-gemini-3.5-flash-lite` came back verbatim, a Russian one with English terms in Latin, in ~0.75–1 s for 5 s of speech (`docs/verified/page.md`); headless Chromium with a fake microphone showed the recording pill, the spinner, the text and the quota refusal's tip in `dev:fake`; real recordings from a desktop browser on Windows and Chrome on Android through the service came back in Russian, German and English with a switch inside one recording, ~8 s after the stop, with misses on a short phrase's English term and an English phrase's start (`docs/verified/page.md`). Not seen: Safari's MP4 on iOS and macOS, Firefox; a real 429 of the whole fallback chain and the hour of the browser's recognition after it; a two-minute recording. **If it is wrong:** the tip says the recording was not transcribed, or the text is in the wrong language or translated; press the microphone again — after a refusal it is the browser's recognition for a while — or clear the Address in Settings → Stats to dictate through the browser only.

## A chat opening at the end of its feed on a phone (BTN-1372)

A chat's feed and the Activity feed keep to their end through `useFeedPin` (`web/src/pages/feedPin.ts`): a pinned feed lets go only when the reader moves it — the wheel, a touch on the feed, a press on it or its scrollbar, a scroll key or Tab within the last 800 ms — and any other scroll puts it back at its end. Headless Chromium opened a project chat and a task's chat at 390×844, 1280×800 and 1600×1000 at the end of the feed (before it, 390×844 stopped ~440 px short), and the wheel took it up and back down. Not seen on a real phone: a touch fling that runs on past 800 ms after the finger leaves, the keyboard opening over the chat, find in page and a screen reader moving through the feed while it is pinned. **If it is wrong:** the chat still opens short of its end, or the feed jumps back to its end while you scroll or read up it; scroll a little up first and the feed stays where you leave it.

## A sent picture on view through its delivery (BTN-1425)

A picture the user sends keeps the browser's copy as its address from the send through the transcript to the agent's read (`transcriptMedia`), the window holds the picture on view by its key (`TranscriptMedia.keys`) and closes the viewer only on a handoff or when the picture left the chat, and without the browser's copy the viewer keeps the picture on screen until its next address has loaded (`.viewer__next`). Unit tests cover the three stages' address, the key, the viewer through a new project chat's first session and a handoff, and the held picture in happy-dom; headless Chromium showed the viewer unchanged at 1600×1000 and 390×844. Not seen in a real browser: a send with pictures, the viewer opened before the delivery, a new project chat's session starting under it and the agent reading the picture, on a desktop and a phone, nor the same chat opened on a second device. **If it is wrong:** the viewer closes when the session starts, or the picture blinks or turns into a neighbour as the message is delivered; open it again from the bubble.

## A mailed picture as a thumbnail (BTN-1431)

A letter of the mailbox (waiting for the hook, queued, returned) draws its pictures as the feed's bubble does (`SentFiles`), from the browser's copy when the window sent it (`onMailed`) and from the service's otherwise, and the letters' pictures join the window's after the feed (`letterLine`), so one keeps its key when its message lands. Unit tests cover the thumbnail of a waiting letter, the viewer and the same address through the delivery without a file chip, and a returned letter's picture with no browser copy; headless Chromium showed the fake letter's thumbnail at 1600×1000, 390×844 and in the light theme, and opened the viewer from it. Not seen in a real browser: a picture mailed to a working Claude session and delivered by its hook, on a desktop and a phone, nor the letter opened on a second device, where the service serves the inbox file by its name. **If it is wrong:** the letter shows the file's name instead of the picture, or the picture blinks as the message is delivered; it is in the feed's bubble once delivered.

## Report a problem's prefilled issue forms (BTN-1494)

**Report a problem** in the gear menu opens `issues/new?template=<form>.yml` with the text fields filled by their `id` (`reportLinks` in `web/src/layout/reportLinks.ts`): `version` with Even Keel's version, `cli` (the bug form) and `cli-now` (the CLI update form) with each agent's CLI version as its sessions run it, "Claude Code 2.1.0, Codex 0.9.0". GitHub's documentation says only that a field's `id` is its key in "URL query parameter prefills"; whether a dropdown (`os`, `agent`, `run`, `tracker`) takes its option's text that way is not documented, and the form needs a GitHub sign-in a session does not have, so the dropdowns are left out. ## Sign-in with a passkey and the owner key in a real browser (BTN-1619)

With the owner key set, a request by a proxy's name from loopback (`tailscale serve`, a Tailscale Service) is asked to sign in, a passkey is made and used on the name the page was opened by (its RP ID), and a revoked device's page loses its event stream at once (`docs/web/sign-in.md`). Unit and server tests cover the guard's verdicts, the key's sign-in, the cookie, the revoke closing a stream and both passkey ceremonies against a fake authenticator of the tests (`src/access/authenticator.fixture.ts`), a passkey of another name refused; headless Chromium showed the screen and the settings group on fake data, with the browser's passkey dialog skipped. On 2026-11-24 the bench hub in Docker showed real passkeys made and used by Safari on an iPhone (Face ID), its installed page and Chrome on Windows (Google Password Manager), the key changed live, a revoked installed page going to the sign-in screen, the hooks passing and recovery by the key ([verified](../verified/page.md)). Not seen: the proxy's `X-Forwarded-For` as the devices list shows it (in Docker the proxy is not on the container's loopback); a proxy forwarding a loopback name on a native install being asked to sign in while plain `localhost` goes without one; Windows Hello as the authenticator; since BTN-1629, a revoked Safari page brought back from the background and a Chrome tab signed out by a new key going to the sign-in screen within a second or two rather than after the reconnecting banner (the check of BTN-1621 saw the banner first; the page now asks `/api/auth/state` on every failed stream and on coming into view, covered by `web/src/live/connection.test.ts`); since BTN-1630, Telegram's in-app browser on iOS saying "This browser cannot use passkeys" rather than "No passkey was picked" (its refusal is told from a person's by being under 1 s with the page never losing focus, covered by `web/src/pages/passkey.test.ts`), while Face ID closed in Safari and the Chrome dialog closed on Windows still say "No passkey was picked"; since BTN-1631, on a real hub, the screen without the passkey button on a name with no passkey made on it (a server test and fake data only) and a device's tag naming its passkey's host. **If it is wrong:** the passkey button fails or a passkey made on one name is offered on another — sign in with the owner key and use it; a proxy that forwards a loopback name goes without a sign-in — make it forward its own name; a signed-out page keeps the reconnecting banner — reload it; a closed dialog reads as a browser without passkeys, or the other way round — press the button again, or open the page in Safari or Chrome.

## A new device let in by an invitation (BTN-1655)

"Invite a device" in "Sign-in and devices" makes a link `<page origin>/invite#<secret>` and its QR; the first browser to open it claims it by an `HttpOnly` cookie, both sides show the same two digits, and after "Let in" the new device gets a token of its own (`docs/web/sign-in.md`, "Invitations"). Unit and server tests cover the life of 10 minutes, the single use, the decline, two browsers racing for one link, the rate limit of the open routes and the token going only to the claiming browser; headless Chromium showed the dialog, the rows of "Devices" and the new device's screens on fake data. Not checked live: a phone's camera reading the QR from the dialog in the dark theme and opening the link in Safari over HTTPS by the proxy's name; the dialog turning from "Waiting…" to the opener and the digits through the event stream, without a reload; the long `invite/wait` request (25 s) held open through `tailscale serve` and the phone's Safari without a cut; the passkey offer after "Let in" on the phone; an installed page of the phone, whose cookies differ from Safari's, not being signed in by a link the camera opened in Safari. **If it is wrong:** the QR does not read — copy the link to the phone by hand; the dialog does not turn — let the device in from its row in "Devices" after reopening the settings; the new device stays on "Waiting…" — reload it, its claim cookie keeps its place; nothing works — sign in with the owner key.

## "Scan a QR" on the sign-in screen of an installed app (BTN-1657)

The sign-in screen offers "Scan a QR" where the browser has a camera; the window reads the invitation's QR with jsQR, bundled into the page, and opens a link of the page's own address in the same window (`docs/web/sign-in.md`, "Invitations"). Unit tests cover the link's check (this origin and `/invite#<secret>` only, another address named, anything else refused), the camera's presence by `enumerateDevices`, the camera's errors and jsQR reading the dialog's own QR (`uqr`) from pixels; in headless Chromium a camera stubbed with the QR drawn on a canvas opened `/invite#…` in the same window, a code of another address and plain text gave their lines, a browser without a camera had no button. Not checked live: the page installed on an iPhone ("Add to Home Screen") asking for the camera and showing the back camera inline, not full screen; reading the dialog's QR off a monitor in the dark theme at arm's length within a second or two; the link opened by the scan staying inside the app, so the app — not Safari — ends up signed in after "Let in"; the camera released when the window closes (the green indicator going off). **If it is wrong:** the button is missing or the camera does not start — allow the camera for the app in the iPhone's settings, or copy the link into the app by hand; the scan opens Safari or the app stays unsigned — sign the app in with the owner key.

## The sign-in an invitation turns on, on a hub without the owner key (BTN-1656)

A hub without `EVEN_KEEL_TOKEN` asks nobody to sign in until the first "Let in"; from then a proxy's name is asked as with the key, kept by the mark `sign_in_on` (step 83), and the browser that pressed "Let in" by the proxy's name gets a token of its own (`docs/web/sign-in.md`, "Who is asked"). "Turn sign-in off" in "Sign-in and devices" drops the mark and signs every device out. Unit and server tests cover the guard with and without the mark, the mark kept through "Sign out everywhere" and a restart, the decider's token, no token for a decider on a loopback name, and the refusal to turn off with the key set; headless Chromium showed the band, the line and the off button on fake data. Not checked live: on a hub without the key behind `tailscale serve`, the phone that let the first device in staying signed in while the open pages of other browsers by the proxy's name turn to the sign-in screen; "Turn sign-in off" opening the proxy's name again for every browser. **If it is wrong:** the page by the proxy's name shuts out the device that let the first one in — open it by `localhost` on the hub, or set the owner key and sign in with it; to start over, "Turn sign-in off" from `localhost` on the hub.
