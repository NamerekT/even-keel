# What has not been verified: Machines

One area of [What has not been verified](../unverified.md), which says what an entry is, how to report a run into one and where a new one goes. What has been checked in this area is in [What has been verified: Machines](../verified/machines.md).

## The machines' stream through a real proxy (BTN-988)

The link between a hub and a machine (`docs/machines.md`) is covered by tests over a wire in memory and by the real HTTPS carrier on loopback: the stream's headers (`Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`), each frame written at once, the pinned certificate, and the machine's `link.buffered` notice when a connection opens and not one frame comes over it. It never ran through a real proxy, and no machine connects from elsewhere yet, so there is nothing to run before the service is cut into the two roles.

Assumed: nginx with its default `proxy_buffering on` honours `X-Accel-Buffering: no` for the stream; a proxy that does hold the stream gives the machine an open connection without frames, which is the case the notice tells from a break; the hub's pulse every 20 s keeps a Cloudflare tunnel (about 100 s idle) and nginx's `proxy_read_timeout` (60 s) from closing an idle stream; a proxy that ends TLS works with a token without a fingerprint — the string of the "+ Machine" window's switch "Behind a proxy with a public certificate" (BTN-1286), the address without a port at 443 — while it reaches the hub's door over HTTPS without verifying its self-signed certificate (nginx's default, a Cloudflare tunnel's `noTLSVerify`, Caddy's `tls_insecure_skip_verify`); the join's `POST /link/join` passes such a proxy as the stream and the posts do. If a proxy answers the stream's request with its own error instead, or passes the first frames and holds the later ones, the machine only reconnects and its page shows it offline without the notice about the proxy.

To check, once a machine can be connected: a hub behind nginx with default settings and with `proxy_buffering off; proxy_read_timeout 1h;`, a Cloudflare tunnel (each with a string issued with the switch on: the machine joins and stays online), and an HTTPS-inspecting proxy or antivirus between the two (refused with the switch on and off).

## The chain over the link in a live installation (BTN-1216)

Since BTN-1216 the chain of every installation reaches its sessions through the hub ↔ machine protocol inside one process (`docs/machines/seam.md`, "One process"): a call of the port is a numbered command and its result an event, the chain reads the machine from a mirror, and the first start of the new version makes the installation's own machine, its token and its consents by itself. This is covered by `src/machine/remote.test.ts`, the sample of the state database before the step and every scenario of `src/e2e/` with the scripted agent. On 2026-11-16 the author's service was updated onto it with a chain running and ran a day of chains on it (BTN-1217's rows in [verified](../verified/machines.md)): the own machine, the kept journal and snapshots, the current task kept across the update, limits, checkpoints, Done and restarts with a session mid-turn passed. Still open: an update from the version before the link while a session is mid-turn, a restart that falls inside a launch, a question across an update, and the page compared before and after.

Assumed: an update over a running chain picks up a session that is mid-turn and keeps the current task; every result and argument of the port survives JSON as the chain reads it; every folder a command names — a session's working folder, a slot — lies inside the project's folder the machine agreed to; a restart of the service in the middle of a launch leaves `command.interrupted` in the log and the launch to the chain's recovery of a starting task. If a session works in a folder outside its project's, its stop, resume or handover is refused and the chain pauses with "the machine refused …: the folder is outside the project's agreed ones"; if a command fails on the machine in a way the chain did not know before, it pauses with "the machine could not run …". Resume goes on once the cause is gone; the log of the service names the command.

To check (BTN-1228): on a second installation, update from a commit before BTN-1216 while a bench task's session is mid-turn and compare the page before and after; ask a question and answer it across an update; restart the service a few seconds after a chain's start, inside the launch (one session, one launch row, the log's `link:` and `machine:` lines); and remove `state/machine/` between two starts (a new own machine is made, the chain goes on).

BTN-1219 also sends launch records, session windows and mailbox changes through the machine's outbox, and reads the page's sessions and mailbox from its mirror. Wire tests cover an offline producer, a lost answer, failure of the separate receipt after a commit, rollback on a failed write, and stale views at reconnect. A live process crash with pending chat changes has not been checked: on the bench, send and deliver mail, restart, and compare the journal, the retained window and the chat before and after; no launch or message should appear twice. A failed record remains in the outbox and holds later events; the service log names the record that failed.

BTN-1221 makes the moves of a task's session on the machine (`docs/machines/seam.md`, "Moves"): a limit, a temporary error, a checkpoint, an answer, "New session", a returned task and the paid-usage stop are commands `task.<move>`, and their state comes back as `task.state` and the result. `src/machine/moves.test.ts` covers them over the wire in memory, and every `src/e2e/` scenario runs them through the one-process link. Assumed: the hub's task gets the move's marks before the session is touched, so a restart mid-move is seen through as before; a `follow` sent only when the mirror shows a refusal, a limit, a move under way or a checkpoint misses none of them. If one is missed, a limit or checkpoint waits until the next fact changes; a move's link failure pauses the chain with "the machine could not run task.…". To check on the bench: a limit with a resume and a handover, a checkpoint, an answer from the chat and a restart of the service in the middle of a handover; the log's `chain:` lines should be the same as before the version.

BTN-1246 gives the machine's assembly its own context (`docs/machines/seam.md`, "The machine's context"): what it reads of the hub comes in the `hub.brief` command, a cleanup's leftover and a watched transcript go back as events, and the account limits, account settings and `cli.downloaded` move into `state/machine/` at the first start. `src/service/hub-brief.test.ts`, `src/machine/state.test.ts`, `remote.test.ts` and every `src/e2e/` scenario cover it. Assumed: a brief sent at every catch-up reaches the machine before the step reads it, so a run set on the page, a check report or a keep-warm task is never a step late; the move of the stores keeps every account's limits and its own settings layer. If the brief lags, a launch picks the account of the project's default run or keep-warm pings a step late; if the move lost rows, the accounts panel shows limits unread until the first poll and a settings transfer writes again. To check on the bench: update across the version with signed-in accounts and compare the accounts panel and each folder's `settings.json` before and after; set a task's run and watch the launch take it.

## MCP servers through the hub in a live installation (BTN-990)

Once the link has started, the machine's gateway carries every server that holds a key to the hub, together with the tasks server (`docs/machines/link.md`, "MCP through the hub"). `src/packages/gateway.test.ts`, `src/service/hub-mcp.test.ts`, `src/taskmcp/machine.test.ts` and `src/link/link.test.ts` cover the route, the pool check, the hub's absence, the files and the kept writes. No live session has gone this way yet.

BTN-1238 removes two shared-process dependencies: a launch carries its brief from the hub, and the gateway consumes a list of hub routes before resolving a target. Unit and in-memory wire tests cover a machine without a tracker or hub target, retained installs and a handoff without an earlier launch. A separate-machine live check awaits BTN-992: with no tracker credentials on the machine, launch a task, read its brief while the hub is unreachable, hand off after a machine restart, and call a keyed server through both its current and a pinned install. The network assembly must deliver and refresh the hub route list, including after reconnect; a missing route would run locally or fail, and a missing brief pauses the chain with `chain.briefMissing` (BTN-1252). The machine's brief cache is in memory: after a restart, an offline task read has no launch brief until a new launch or handoff supplies one.

Assumed:

- huly-mcp, the GitHub and Forgejo servers and a remote server with OAuth answer a whole POST as they did when the gateway proxied them directly.
- An SSE answer to a POST, read whole and then sent back, is read by Claude Code, Codex, OpenCode and Copilot.
- A server's own messages on a GET stream are not needed: the gateway answers that GET with 405.
- A file a session attaches arrives in the tracker unchanged.

If one of these is wrong, the session's calls of that server fail or time out, the probe holds the chain on `noResponse`, and the log names the request (`link: …`, `hub mcp gateway: …`).

To check on the bench, with a chain task in a Huly project and one in a GitHub project:

- `task_read` with an attachment, and a `task_comment` with a file from `.temp/`.
- A tracker server's list call.
- With the hub's gateway made unreachable mid-session, a comment the session is told is kept should arrive once the gateway is back, and a second task's read should answer that the hub is unreachable.

BTN-1250 moves the account watcher, monitor, approvals, packages and CLI selection onto the machine context, separates the hub's credentialed gateway, and imports the remaining host stores with a second marker. OpenRouter spend now goes through the durable outbox. Unit and scripted service tests cover this separation and repeated delivery; a real upgrade with an active account and queued spend has not been checked; the standalone machine process (BTN-1247) has its own entry below. On the upgrade bench compare global registrations, the management-key balance, context windows and CLI history before and after, change the active account and CLI choice, then restart with an unconfirmed spend event. A missing import loses the host's remembered state; a duplicate spend would inflate statistics. Preserve `state/machine/` before that check; the hub backup alone does not contain newer machine rows.

## One account's limits across machines (BTN-991)

The hub picks one machine to poll `/usage` per claude.ai account and hands the newest limits to the others (`docs/machines/limits.md`). `src/limits/polls.test.ts`, `src/limits/watcher-plan.test.ts` and `src/machine/remote.test.ts` cover the choice, the plan and its command over the wire in memory. With one machine nothing is sent, so a live installation runs none of it yet.

Assumed: `oauthAccount.accountUuid` of `.claude.json` is the same for one account on every machine and every folder, and it changes in the file when another account signs in to the folder; the 30 s between reads of the file is soon enough after a sign-in. If the id differs per machine, both machines poll the account as before and may meet the 429; if it is stale after a switch, a folder skips polling an account it no longer has until the next read.

To check, once a machine can be connected (BTN-992): sign one account in on the hub and on a machine and see the machine's log stay without its own `/usage` calls while its card shows the hub's numbers; then the account only on two machines, take the polling one off the link and see the other start polling no sooner than five minutes later, with a `limits: machine … polls` line.

## A machine joining from another computer (BTN-1242)

The hub's door for machines (`docs/machines/elsewhere.md`, "Machines elsewhere"): the listener on the machines' port while "Hub address for machines" is set, the one-time connection string, `even-keel join` and the attachment to a project. `src/service/machine-network.test.ts` and `src/link/carrier.test.ts` run the join over real HTTPS on loopback; `src/machine/join.test.ts` the refusals of the command. No machine has joined from another computer yet.

Assumed: Windows Firewall asks once about node listening on all interfaces, and a "Private network" answer is enough for a LAN and Tailscale; the network cards offered are the ones another computer can reach; a Tailscale Service that publishes only the page's port does not pass the machines' port, so its name must not be the address (the field's hint says so); the agent CLIs a machine reports are found on its `PATH` as the user who runs `join` sees it. If the firewall blocks the port, `join` says the hub was not reached and nothing is kept; if a report is wrong, only the page's facts about the machine are.

To check, on the benches: set the address to the hub's Tailscale IP, issue a string, run `even-keel join` on a second computer with a clean installation and see it in `machines/list` with its report; join with the same string again (refused as used), wait 30 min with another (expired), issue twice (the first refused); attach it to a project and see the consent in its `consents` and the folder under its root.

## A machine joining by the hub's address (BTN-1620)

`even-keel join <address>` asks the hub to let the machine in, prints a code and waits; the hub's page shows the request window with the same code, Admit or Decline (`docs/machines.md`, "The request by the address"). The direct join between containers on one Docker network is checked (BTN-1622, [verified](../verified/machines.md)): the code, Admit, Decline, the expiry, a hub restart and a second request. Left: a machine on another computer, across a real network; a task taken by a machine joined this way (the checked one had no account signed in); and the join behind a proxy — no bench has a hub behind a proxy with a public certificate.

Assumed: behind a proxy with a public certificate the machine sends an empty fingerprint and the hub computes the code from the nonce alone, so the codes match there too; the proxy's socket address is the requests' one, so the hub takes one request at a time. If the codes differ behind the proxy, the person declines a good machine and can join only by the string; if the proxy holds the polls, `join` waits 10 minutes and says the request expired.

To check: a hub behind a proxy with a public certificate, the switch "Behind a proxy with a public certificate" in "Add a machine", `even-keel join <the proxy's address>` on another computer: the same code in the terminal and the window, Admit, a second request while one waits (refused at once); then a task on Haiku on that machine.

## A machine's own process against a live hub (BTN-1247)

An installation that joined starts as a machine alone (`docs/machines/machine-side.md`, "The machine's process"): the machine's assembly and its end of the link over HTTPS, no state database or page; the hub keeps its own mirror of it, sends it a brief of its pool's projects, plans its account limits and relays its MCP requests. `src/service/machine-network.test.ts` runs a `MachineEnd` over the real HTTPS carrier on loopback into that mirror, brief and plan; `src/service/machine-process.test.ts` the claim of the installation and `contactAt`. The process itself was started only with a link file and no token (it exits saying to join again); it has never connected to a hub from another computer.

Assumed: the host's assembly starts without the hub's process around it (no state database, no page server) and its watchers, monitor and packages run as they do in the service; the first brief comes soon after the first snapshot, so the gateway's turn to the hub finds the hub's servers named; the limits watcher's wait for the first plan ends at the first plan, an empty one too. If the brief does not come, the machine holds an empty config and its sessions' tracker and tasks calls fail; if the plan does not come, the machine never polls `/usage` and its accounts' limits stay unread; if the process fails at the start, `even-keel status` shows no `contactAt` and the log names the step.

To check, on the benches, after the join of the entry above: start the second computer's service and see its log say it connects and that the hub took the first snapshot, `even-keel status` there show the last contact, the hub's `machines/list` show it online; attach a project and see its folder in the machine's brief (`consents` and the folder under the root); sign in an account only there and see its first `/usage` poll after the hub's first plan; stop the service and see the claim in `state/even-keel/` gone.

## The folder's mark across installations and shares (BTN-1244)

The mark `.git/even-keel-machine` (`docs/machines/machine-side.md`, "The folder's mark"): a machine writes it on the folders it takes, another machine is refused them and its chain pauses with "already served by machine …", a revoked token takes the marks off, and `machines/takeOver` takes a dead machine's folder. `src/machine/marks.test.ts` writes real marks in temporary repositories (a linked worktree's in the common folder), `src/link/link.test.ts` and `src/service/machine-network.test.ts` run the refusal, the start's settling, the release on a refused token and the takeover over the link, and `src/e2e/pauses.test.ts` pauses a chain on a mark put there before the start and resumes it after the takeover. It never ran with two real installations on one repository, over a network share or a container's mount.

Assumed: both installations see the same `.git` and its file through the share or the mount, with its writes at once; nothing else in `.git` minds the file (git ignores unknown files there, a backup or a sync tool copies it); the user's service marks every project's checkout at its first start of this version and nothing refuses it then. If a share caches the file, a second machine is refused late or not at all and both work in the folder; if the installation's own folders turn out marked by something else (a restored copy of another installation), its chains pause with "already served by machine …" until the folder is taken over.

To check, on the benches with `EVEN_KEEL_TEST_INSTANCE` unset for the run (a test instance writes no marks): two installations with one bench repository as a project — the second one's chain pauses with the first one's name; revoke a joined machine and see its marks gone from its folders; take the folder over with `machines/takeOver` and resume; the same with the repository on an SMB share and in a container's bind mount. Put the bench's `EVEN_KEEL_TEST_INSTANCE` back afterwards and remove the marks.

## The hooks of a machine's sessions through the hub (BTN-1260)

## A machine's moves without its hub (BTN-1226)

## The global configuration between machines (BTN-1690)

`docs/sessions/memory.md`, "The global configuration". `~/.claude-config` is a working copy of the hub's `memory/config.git` on the hub and on every machine, `CLAUDE.md` and `settings.json` (without `env`, `hooks`, `statusLine` and `extraKnownMarketplaces`, BTN-1707) are carried between it and `~/.claude`, and the stores of before BTN-1690 (`~/.claude-skills`, `~/.claude-agents` and the like) are moved into it and left as links. Covered by unit tests with real git on folders of one disk (`src/memory/git/sync-config.test.ts`, `config-files.test.ts`, `hub.test.ts`, `hub-git.test.ts`, `src/account/share.test.ts`) and the hook process (`plugins/agent-bridge/hooks/memory-conflicts.test.mjs`); never run on a live home folder with the old stores.

Seen live once (2026-11-25, a Windows hub and a Linux machine, BTN-1707): the copies met and the page showed the banner for `hooks/secret-scan-allow.txt` and `settings.json`. The `settings.json` conflict differed only in keys holding a machine's absolute paths — hook commands, `statusLine`, the `even-keel` marketplace's folder — and the hub's newer version wrote Windows paths into the machine's `~/.claude/settings.json`: its Tally hook failed on every event, the status line broke, the marketplace pointed at no folder. Since BTN-1707 those keys stay each machine's own as `env` does, and a copy an older build left holding them loses them at the next sync. Checked on 2026-11-26 between two Linux copies (`docs/verified/machines.md`): the same `settings.json` key on both, a change of `hooks` and `statusLine` alone, a skill's text conflict and its note to a session reading it through `~/.claude/skills/<name>`; found BTN-1746 (a text conflict saved unchanged stays open). Since BTN-1746 such a save is marked by the hook at PostToolUse of Edit, Write and MultiEdit and ends the conflict by a `Config-Settled` commit at the next sync (`sync.test.ts`, `memory-conflicts.test.mjs`); not run live yet. "Own configuration" of the machine page (BTN-1745) keeps a machine's `CLAUDE.md` and `settings.json` out of the sync and, turned off, has them meet the network's as a conflict; covered by `config-copy.test.ts`, `own-config.test.ts`, `machine-page.test.ts` and `hub-brief.test.ts`, never run live.

Assumed: the move of the old stores renames them on a live home, re-points the account folders' links, and hook commands that name `~/.claude/hooks/…` or `~/.claude-hooks/…` keep running; on Windows the hook finds the conflicts file of a skill opened through its junction by its real path; Claude Code runs the PostToolUse hook of a Write that left the text as it was. If not, an old store stays where it was with a warning in the log, and the account links to it as before; or a Windows session misses the note of a text conflict (`git -C ~/.claude-config log --grep '^Config-Conflict:'` lists them); or a conflict saved unchanged stays open and every session touching the file gets its note again (no `.git/even-keel-saved.json` after the save).

To check, on the benches: on a machine-1 with `~/.claude-skills` and `~/.claude-hooks` of the old layout, start the service: they are inside `~/.claude-config`, the old names are links, a hook still runs. On a Windows hub or machine, change one line of a skill on two copies with the link of one cut: a Claude session that reads the skill through `~/.claude/skills/<name>` gets the merge note. Then tell it to keep the file's version and save it unchanged: within a minute the copy has a `Config-Settled` commit and no `.git/even-keel-conflicts.json`, the other copy neither after its next sync, and a new session reading the skill gets no note. "Own configuration": turn it on for machine-1 on its page, change `settings.json` on the hub and on machine-1 — neither reaches the other within ten minutes, while a new skill on the hub reaches machine-1; turn it off with the two files different — the hub's page shows the `settings.json` banner, and a session reading `CLAUDE.md` gets the merge note.
