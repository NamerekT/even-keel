# Claude accounts

Reference for sessions: account folders, sign-in, switching, transferring the shared configuration.

## Folders and sign-in

- One configuration folder per account (`CLAUDE_CONFIG_DIR`): the global `~/.claude` (key `global`, listed only after explicit registration) and `~/.claude-accounts/<name>` (`EVEN_KEEL_ACCOUNTS_DIR`).
- **Adding an existing CLI sign-in (BTN-543).** Global Claude and Codex folders are hidden until added through the common Add account dialog, including from setup and the project wizard. Selecting a provider checks its unregistered global folder once (`account/discover`, `AccountWatcher.discoverGlobal`), without polling its limits. A signed-in identity offers "Use this sign-in" (`account/global`, `useGlobal`, which rechecks sign-in) or "Sign in with another account"; without a sign-in the normal choices open directly. Browser Back returns from the other-account choices. Registration is in `global_accounts` (`openAccountHomes`, `src/account/globals.ts`), never in the CLI folder. An upgrade adopts only the global folders present at its first start, once; a fresh installation never adopts them automatically. OpenCode already has only managed folders; Copilot's machine sign-in is added explicitly through its existing choice, without a readable per-machine identity.
- **A first account (BTN-227).** The shared pool names `global` and `codex` by default, folders a fresh install may not have. An account added from the page (signed in or on a key) takes the shared pool's entry of its agent while that entry names no listed folder of the agent (`takesShared`, `withSharedAccount`, `ConfigStore.saveSharedAccount`); the provider is left as it is. Once the entry names a real folder, a new account does not move it.
- **A CLI that is not found.** Each agent says whether `spawn` without a shell starts its binary (`Agent.installed`, `findBinary` in `src/paths.ts`: a path as is, a bare name on `PATH`; on Windows only no extension, `.com` or `.exe`, so an npm `codex.cmd` shim alone does not count). Its agents are `AccountView.missing`: the add dialog shows that provider as an off card with where to get the CLI (`CLI_MISSING` in `web/src/accounts.ts`), the section has no "+ Add" and an empty section of it is not shown. A sign-in whose spawn fails with `ENOENT` says the same. Apart from that, the shared and the project settings offer a provider (the provider field, the rows of models and accounts) only once it has an account or the setting already names it (`offeredProviders`).
- The CLI itself stores and refreshes the tokens; Even Keel reads only the expiry times from `.credentials.json` (`expiresAt`, `refreshTokenExpiresAt`) and neither reads nor copies the tokens. `claude auth status --json` runs for each folder once a minute.
- A folder that needs sign-in is not polled for `/usage`, and its previous usage warning is hidden immediately. The header's usage warnings cover every account named by a shared or project pool, each once and with the same name as its account card, regardless of the shared provider. Each account's warning is dismissed separately; the technical reason is in its keyboard-accessible tip. On `/setup`, usage, CLI version and CLI download banners are hidden; sign-in and downloads are shown on the agent cards. Unit tests and fake-page shots cover this; the real sign-in and polling check belongs to BTN-542.
- "Add account" — `claude auth login --claudeai` in a temporary `.pending-*` folder; after sign-in the folder is named after the e-mail. "Renew" (next to the sign-in's days left) — signing in again in the account folder. The page shows the link and the code field in the add dialog or, for a renewal, the sign-in dialog (below, "Accounts: the drawer, the page…").
- Removing a managed folder — `claude auth logout` and the folder goes away (not the active one, not one a pool entry names: the shared pool's — `account.sharedPool` — or a project's own — `account.projectPool`; `AccountView.pool`, `poolEntries` in `src/config.ts`). Removing a global account only forgets its registration: the folder and CLI sign-in stay, with no logout. If there are live sessions, removal is deferred until they end (the menu names the ones holding it); "Don't remove" clears the mark.
- A live session of a folder is one with a live process (a `sessions/<pid>.json` entry), not by `state` from `claude agents`: `blocked`/`working` stay there even for a session whose process and daemon died long ago, and such entries interfere neither with removing the folder nor with stopping its daemon (`liveSessions`).
- `*.lock` folders are locks the CLI puts next to an account folder while a token is refreshed; they are not accounts.
- **Token renewal (EKR-15).** Any call of the CLI may renew the folder's sign-in, and the refresh token it renews with is single-use: a call killed between sending the renewal and writing the answer, or two calls renewing at once, may leave `.credentials.json` with no tokens and the account signed out (21.10.2026, after a reboot; unconfirmed, `docs/unverified.md`). So:
  - Even Keel's short calls of a folder — `claude agents`, `auth status`, `-p /usage`, `-p /context` — run one at a time (`FolderCalls`, `src/claude/calls.ts`). A call past its timeout is given up on, not killed: it holds the folder until it ends and is killed only after five minutes; a call whose timeout passes while it waits never starts. Launches, `stop` and `daemon` calls go around it.
  - `auth status` and `/usage` wait until the provider's API answers (`Reachability`, `src/account/network.ts`: any HTTP answer from `api.anthropic.com`, `api.openai.com` or, for OpenCode, `opencode.ai`, probed at most every 30 s); the service starts before the network after a reboot. Meanwhile an account keeps what it showed, and `/usage` tries again in 30 s. The log says once when the API stops and starts answering.
  - The CLI leaves a `.oauth_refresh.lock.owner.tmp.<8 hex>` behind when writing the owner of its renewal lock fails half-way; with the session poll's `claude agents` every 3 s they came in bursts of hundreds while a token waited for renewal. Before each `auth status` such files older than an hour are deleted (`sweepRefreshLeftovers`, `src/claude/leftovers.ts`).
- The account e-mail in `auth status` is the saved profile from `.claude.json`, not the token owner: the Claude desktop app runs the CLI in `~/.claude` with its own account and rewrites the profile, so keep in `~/.claude` the same account as in the app, or launch the app on an account folder ("The Claude desktop app" below).

## API accounts (BTN-99)

- An API account is a folder whose sessions pay from an Anthropic API key instead of a subscription. "Add an API key" in the panel (command `account/api`, `AccountHomes.addApiKey`) creates `~/.claude-accounts/<folder>` with `settings.json` = `{ "env": { "ANTHROPIC_API_KEY": "…" } }` and `.claude.json` with the key's last 20 characters in `customApiKeyResponses.approved`, otherwise the CLI asks whether to use the key. A key shorter than 21 characters or with spaces is refused (`account.apiKeyInvalid`). Before the folder is made, the key is checked with Anthropic (`checkApiKey`, `src/account/keycheck.ts`): `GET /v1/models?limit=1` with it, which costs no tokens; 401 or 403 refuses it (`account.apiKeyRejected`), and a network error, a timeout or any other status refuses it too, as unchecked (`account.apiKeyUnchecked`), so no folder is made with a key nobody looked at. After that the watcher checks each API account's key from its `settings.json` once an hour (`KeyChecks`, in memory, so on every start too): a refused key makes the account `needsLogin` — the page says the key isn't accepted, the chain does not switch to it or launch on it — and a check that learns nothing keeps the last verdict. A folder with `apiKeyHelper` is not checked: there is no key to read. A folder set up by hand with `apiKeyHelper` instead of the variable works the same way. Chain sessions on such a folder's key were run live from the Windows service on 2026-10-25 (CLI 2.1.310, Haiku): one on `--bg` (the SDK was not downloaded yet at its launch) and one through the SDK, each to a merge and Done.
- **Replacing the key** (BTN-418). A revoked or expired key needs no new account: "Replace key" in the card's ⋯ menu, and the button next to "The key isn't accepted", open a field for the new one (`ReplaceKeyDialog`, command `account/key`, `AccountWatcher.replaceApiKey`). The key goes into the same folder, so its name, roles, pools and Tally history stay: Claude's `env.ANTHROPIC_API_KEY` in `settings.json` and its last 20 characters in `customApiKeyResponses.approved` of `.claude.json` in place of the old key's (the rest of both files as it was), Codex's `OPENAI_API_KEY` in `auth.json`, OpenCode's provider entry in `auth.json` (`replaceKey`), Copilot's token. Refused before anything is written: a key of the wrong form, as on adding; a folder that does not keep its key itself — the agent's own folder or one with `apiKeyHelper`, which have no such item (`AccountEntry.keyReplaceable`, `account.keyNotHeld`); an OpenCode key of another provider than the one it holds (`account.keyOtherProvider`); a key the provider refuses or that cannot be checked, as on adding; a key of another organization (below). A replaced key's verdict is the new one at once, so the card stops saying it is refused and the chain may switch to the account again. Running sessions keep the key they started with (invariant 1); new ones read the new one, as `settings.json` and `auth.json` are read at a session's start.
- **The key's organization.** An API key's account is the organization that pays: a key of another one is another account. A working key's answer to the models list names it — Anthropic's header `anthropic-organization-id`, OpenAI's `openai-organization` (`KeyVerdict.organization`) — and a refused key's 401 names none, so it is kept while the key works: on adding and on each hourly check with a 2xx, in the state database (`key_organizations`, step 14, `docs/storage.md`; `src/account/organizations.ts`), which gives accounts added before it one at their next check. A replacing key of another organization than the kept one is refused (`account.keyOtherOrganization`) and the old key stays; with none kept (a key refused before this was there) or an answer without the header, the key is taken and its organization kept. A workspace inside the organization is not checked: it cannot be seen without an Admin key, and the same organization pays. That the headers come is known from the providers' documentation only ([unverified](unverified.md#an-api-keys-organization-header)).
- The account name from the form is not the folder name. The folder is the name made safe for a path (`folderName`: `Team API` → `team-api`, `api` when the name is empty, `-2` when taken) and stays the account's identity: the key in commands and `state/`, and its stand-in e-mail (`withIdentity`). The name itself is kept in `state/account.json` as `accounts.<folder>.name` (schema v4, `nameAccount`) and goes away with the account; the page shows it instead of the folder, and the folder in the account's details.
- `claude auth status --json` in such a folder says `loggedIn: true`, `authMethod: "api_key"` (`"api_key_helper"` with a helper) and no e-mail (`isApiKey`). The folder key stands in for the e-mail wherever an account is told apart by it (`withIdentity`): the limit owner, `state/account.json`, the session pills.
- The transfer of the shared configuration keeps the folder's own `env.ANTHROPIC_API_KEY` and `apiKeyHelper` over the global settings (`mergeSettings`); every other key still comes from `~/.claude`.
- How a Claude folder runs its sessions — `--bg` or the Agent SDK — is the shared setting `execution.claude` since BTN-353 (`auto` by default, `bg`, `sdk`; `transportOf`): `auto` runs an API folder through the SDK and a subscription on `--bg` (`docs/sessions.md`, "The Agent SDK transport"). The card only says it (`TransportNote`, "Sessions through …", with Anthropic's rule in the tip of a subscription on the SDK); adding a key asks nothing. Before, it was each folder's `transport` in `state/account.json` (schema v10, switched on the card by `account/transport`, chosen with a key by `account/api`); schema v11 (BTN-302) wrote `bg` to each account of an older file without a choice, all but Codex's own folder. Schema v12 moves those choices out of the records into the file's `transports`, and the service's start turns them into the setting once (`executionOfChoices`): `auto` when each is what `auto` gives its folder (a key on `sdk`, a subscription on `bg`), `sdk` when every Claude folder chose it, otherwise `auto` with a log line per folder whose way changes; a folder gone or no Claude one is left out, whether a folder holds a key is read from its `settings.json` (`apiKeyOf`). `transports` is dropped once the setting is written.
- What an API account does not have: limits — `/usage` is not polled for it (it would answer free with no window lines anyway), there are no limit bars, and a key's `rate_limit` stops a session like any error (invariant 1); sign-in renewal and `claude auth logout` on removal; Remote Control, which needs a claude.ai sign-in (`RemoteOff` `api-key`).
- A key out of credit (BTN-165) is held on the current task as on a limit (`docs/chain.md`, exception 1): the CLI's `billing_error` ("Credit balance is too low") is `apiError.kind` `credit`, its lamp is `limit`. Its "reset" is the moment the credit is back: while the dispatcher asks (`AccountWatcher.creditBackAfter`), the watcher checks the key every 5 minutes (`CreditChecks`, `checkCredit` in `src/account/credit.ts`, in memory; a Codex key — below) — the models list for the cheapest model (a Haiku, else the newest), then `/v1/messages` with `max_tokens: 1`, a fraction of a cent. Only 2xx restores access; a 400 saying "credit balance is too low" or that the specified API usage limits were reached keeps waiting; anything else learns nothing and is logged. The checks start 5 minutes after the stop and end once access returns or 10 minutes after the dispatcher stopped asking. The panel says the key is out of credit and is checked (`t.session.creditOut`).
- An Anthropic spending cap (BTN-382) is held too: "reached your specified API usage limits" is `apiError.kind` `spend` even when the CLI records `error: unknown`. Its "regain access on YYYY-MM-DD at HH:mm UTC" gives the reset directly (`src/limits/spending.ts`); a missing, invalid or already elapsed date leaves it unknown. The five-minute key check continues even with a known reset: a 2xx permits an earlier resume or handoff if the cap was raised. The account card, drawer and session panel name the spending limit and its reset in local time; their hint explains the checks and account switching. The workspace variant is accepted defensively, and actual automatic recovery remains [unverified](unverified.md#api-spending-cap-recovery).
- Instead of the limits, the panel row, the account card and the header (while the API account is the active one) show the folder's spend since local midnight, from Tally (`/api/stats/spend`, `docs/stats.md`), refreshed every 5 minutes and fetched only while some account is on a key. Without Tally there is no figure.
- The prompt cache lifetime of sessions on a key is 5 minutes by default; the `cacheTtl` config key changes it (`docs/sessions.md`).

## The Codex folders (BTN-168, BTN-176)

- Codex's own folder `CODEX_HOME` or `~/.codex`, key `codex`, listed only after it exists and is explicitly registered (Codex does not create it); and one `CODEX_HOME` per added account under `~/.codex-accounts/<name>` (`EVEN_KEEL_CODEX_ACCOUNTS_DIR`), the same way as Claude's (`AccountHomes`, `src/account/homes.ts`). `CODEX_HOME` isolates everything — `auth.json`, `sessions/`, `state_5.sqlite`, `config.toml` — so each folder has its own sign-in, limits and sessions. A folder name is its account key across both roots: a new one is named apart from every Claude and Codex folder (`folderName`), and a Codex folder named like a Claude one by hand is not listed.
- "+ Add" in the Codex section (`account/add` with `agent: "codex"`) makes a `.pending-*` folder under the Codex root, runs `codex login --device-auth` in it and, signed in, names it by the e-mail — as Claude's add does. Removing an added folder is Claude's too: `codex logout` and the folder goes, after its sessions end. Removing Codex's own folder as an account only forgets its registration, keeping the folder and sign-in, and no Codex account is given to an app (`account.codexApp`).
- A new folder has no `config.toml`: its model is the shared or the project's `models.codex`, else Codex's default (a `config.toml` model the free plan refuses, such as `gpt-5.4-mini`, stays in `~/.codex`). The tracker's plugin in Codex is installed per folder: a new one has none until the user installs it there.
- A Codex account takes the Even Keel role like a Claude one (below). A Codex session starts in the pool's `accounts.codex` (`codex` by default; `docs/sessions.md`, "Run profiles"), and the chain judges a Codex task's launch block, limits and handoff account by that folder, not by the active one. There is no switching to another account on a spent limit — the chain waits for the reset or a change of the pool, as with Claude.
- **One free account.** Several free Codex accounts of one person to get round the limits break OpenAI's terms, so Even Keel keeps at most one (`extraFree`, `secondFreeProblem` in `src/account/model.ts`). The plan is `chatgpt_plan_type` of the `id_token` in `auth.json`; `free` is the free plan, any other (Plus, Pro, Business…) has no limit on the count. Adding an account that signs in on the free plan while another Codex account already is on it is refused (`account.secondFree`; `account.sameFree` when the sign-in's e-mail is the free account's own): the new folder is signed out and removed. The CLI has signed in by then and its output ends in its success, so the sign-in window (BTN-389, `planRefused` in `web/src/accountAdd.ts`) folds it under "CLI output: the sign-in, before the plan check" and its button reads "Sign in with another account" instead of "Retry". If a folder's plan turns free later and there are two, the first free in the folders' order (Codex's own, then the added by name) keeps working; each other one has the warning on its card (`account.extraFree`), no session starts in it and it does not take the Even Keel role.
- **On an OpenAI API key (BTN-177).** "API key" in the Codex step of adding (`account/api` with `agent: "codex"`) makes a folder under the Codex root, named as Claude's API folders are, with `auth.json` = `{ "auth_mode": "apikey", "OPENAI_API_KEY": "…" }` — what `codex login --with-api-key` writes (checked on 0.162.1); Codex reads the key from there on every turn, so the turn's environment is unchanged and `codex login status` says "Logged in using an API key" (0.162.1) or "API key configured" (0.164.0, BTN-383), both read as a key (`parseLoginStatus`, `isApiKey`). The key is in the folder in plain text, as Claude's is in `settings.json`. Before the folder is made, the key is checked with `GET https://api.openai.com/v1/models` (`checkOpenAiKey`, no tokens): 401 or 403 refuses it (`account.codexKeyRejected`), anything else refuses it as unchecked (`account.codexKeyUnchecked`); then hourly, as Claude's. The free-account rule does not apply: a key is used under OpenAI's API terms, not ChatGPT's. Spend today comes from Tally as for Claude's keys (Codex rollouts are priced by GPT model, `docs/tally.md`); a model Tally has no price for shows no figure. A key out of money is waited out as Claude's (BTN-195): OpenAI answers 429 `insufficient_quota`, which codex-cli 0.162.1 words "Quota exceeded. Check your plan and billing details." (read from its binary; seen live on 0.164.0 with a key at zero, 2026-10-25, as the rollout's `task_complete.error`, `codex_error_info` `usage_limit_exceeded`, while the API's own 429 had the code `credit_balance_exhausted` and "You have no credits remaining…"); the rollout fold takes that text, or OpenAI's own "You exceeded your current quota", as `credit` (`CREDIT_TEXT`, `src/codex/rollout.ts`) — any other `quota`, `usage limit` or `rate limit` stays `limit`. The watcher asks the folder's provider (`checkCredit(agent, key)`): for Codex `checkOpenAiCredit` — the models list for a `gpt-` text model with `nano` in its id, else `mini`, then `POST /v1/responses` with `max_output_tokens: 16` (the API's least) and `store: false`. 2xx is money; a 429 with `insufficient_quota` is none yet; a 429 of a rate limit and anything else learns nothing.
- Sign-in status is `codex login status` (`Logged in using ChatGPT` / an API key, above / `Not logged in`); the e-mail and plan come from the `id_token` claims. "Renew" and adding run `codex login --device-auth` through the same sign-in flow as Claude's, with a window of its own: no code field, the one-time code read out of the output (`loginCode`: the line under "Enter this one-time code", or OpenCode's "Enter code: …") into the login's `deviceCode` and shown large with a "Copy" button, the CLI output folded; a code not read leaves the output unfolded, the code in it (not checked live, `docs/unverified.md`); sign-out is `codex logout`.
- Limits are read from the folder's rollouts, not polled (`docs/sessions.md`, "Codex"); Tally collects the rollouts of every Codex folder (`docs/tally.md`). The shared configuration is not transferred: Codex reads its own `config.toml`, and the tracker's MCP server comes with every turn.

## The OpenCode folders (BTN-214)

- Only added ones, under `~/.opencode-accounts/<name>` (`EVEN_KEEL_OPENCODE_ACCOUNTS_DIR`): OpenCode keeps its files in the XDG folders of the user, shared with every OpenCode the user runs, so there is no "own folder" to list as with `~/.claude` and `~/.codex`. A folder holds the four XDG folders (`data`, `config`, `state`, `cache`) and the empty `config/opencode/AGENTS.md` that keeps `~/.claude/CLAUDE.md` out (`docs/sessions.md`, "OpenCode"). Names are unique across all three roots, as for Codex.
- Ways in (`SIGN_INS` in `src/agent/providers.ts`, `LOGIN_METHODS` in `src/opencode/cli.ts`), chosen in the add dialog and sent as `account/add` with `agent: "opencode"` and `method`:
  - `chatgpt` — `opencode providers login -p openai -m "ChatGPT Pro/Plus (headless)"`, a device link and code, shown as Codex's;
  - `copilot` — `-p github-copilot`, GitHub's device sign-in; Even Keel presses Enter for "GitHub.com" on the first question;
  - `none` — no sign-in: the folder is made at once and runs OpenCode's own free models (`opencode/big-pickle`);
  - an API key (`account/api` with `agent: "opencode"`) — written into `data/opencode/auth.json` as `opencode providers login` writes it, under `anthropic` for an `sk-ant-` key and `openai` for any other (`keyVendor`), and checked with that provider's API as Claude's and Codex's keys are (`keyProvider` in `src/account/homes.ts`).
- **No Claude subscription.** Anthropic allows the Pro/Max sign-in only in Claude Code, and OpenCode dropped it: Claude runs in OpenCode only on an API key. The add dialog says so under the API key way.
- Status comes from `auth.json`, not a CLI call: no file is a folder signed in with `none`; a folder with credentials lists its providers where Claude's plan goes, and has no e-mail, so a folder added by a sign-in or with none is named after the agent (`opencode`, `opencode-2`…). Sign-out deletes `auth.json`. One folder may hold several providers; the run profile's model (`<provider>/<model>`) picks which one a session uses.
- Limits only from a ChatGPT or Copilot sign-in (BTN-341): the 5-hour and weekly windows of ChatGPT, Copilot's monthly allowance, read from the provider's API (`docs/sessions.md`, "Limits of OpenCode and Copilot"). A folder on ChatGPT and a Codex folder on the same ChatGPT account share one limit, and both cards say so. A folder on the free models or an API key has none: its card shows one line with why, not empty window rows.
- An account whose limit nothing tells (OpenCode Zen, Copilot signed in on the machine; BTN-342) shows what is known instead: its tokens from Tally, cache included, since local midnight and over the last 30 days (`/api/stats/tokens`, `docs/stats.md`; `UnknownLimit` in `web/src/layout/accountParts.tsx`), and "last refused by its limit …" once a chain session hit it (`AccountEntry.lastLimitAt`, from `LimitRetries`, in memory since the start). Tokens, not dollars: Tally prices neither the free models nor Copilot's. On such a limit the chain tries again with a growing wait (`docs/chain.md`, exception 1). No numbers of the free models' limits anywhere: OpenCode publishes none and the list of free models changes.

## The Copilot folders (BTN-215)

- Only added ones, under `~/.copilot-accounts/<name>` (`EVEN_KEEL_COPILOT_ACCOUNTS_DIR`), each a `COPILOT_HOME` (`src/copilot/home.ts`): config, `mcp-config.json`, `session-state/`. `~/.copilot` is not listed: it is the user's own Copilot, as `~/.local/share/opencode` is OpenCode's. Names are unique across all four roots.
- **The machine sign-in.** `copilot login` normally keeps its token in the OS credential store under `copilot-cli`, with a plaintext fallback in `config.json` if the store is unavailable ([GitHub's authentication reference](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli)). The CLI can fall back to `gh auth token`. Before reading that fallback, Even Keel asks the same CLI binary with the session's `COPILOT_HOME` and environment for `auth.getStatus` over `--headless --stdio` (`src/copilot/machine.ts`, `machineToken`). Only an authenticated `gh-cli` answer for GitHub.com permits `gh auth token --hostname github.com --user <the CLI's login>`. An own OAuth sign-in, another host or an unreadable answer stays unavailable; no different account is substituted. Tokens exist only during the allowance request, never in logs, state or a token cache. So there are two ways in (`SIGN_INS`):
  - `none` — "This machine's sign-in" in the add dialog makes the folder at once (named `copilot`, `copilot-2`…): its sessions run on whatever the machine is signed in with. Its card reads the allowance when the CLI confirms its GitHub CLI fallback; otherwise it has no allowance. The folder always counts as signed in, and a `copilot` missing from the machine fails the first turn.
  - a token (`account/api` with `agent: "copilot"`) — a fine-grained PAT with the "Copilot Requests" permission (`github_pat_`) or an OAuth token (`gho_`, `ghu_`); a classic `ghp_` token is refused (`account.copilotTokenInvalid`), since Copilot refuses it too. It is kept in the folder's `even-keel.json` and handed to every turn as `COPILOT_GITHUB_TOKEN`, which beats the stored sign-in, so each such folder is its own GitHub identity. It counts as a key: checked with `GET https://api.github.com/user` before the folder is made and hourly after (`checkGitHubToken`; 401 or 403 is `account.copilotTokenRejected`, anything else `account.copilotTokenUnchecked`), a refused one makes the account `needsLogin`. Default folder name `github`.
- **The monthly allowance** (BTN-341, BTN-520). Copilot's budget is AI credits or premium requests, which the CLI does not tell outside its interactive footer. A token folder has its month read from GitHub (`copilot_internal/user`, else the billing API, which needs the token's "Plan" read permission; the card names it when it is missing) and shown as one bar, "N left, resets on the 1st", or the requests used when only the billing API answers. Extra-usage permission and net billing spend are described below. A confirmed machine fallback reads `copilot_internal/user` directly, without an editor-identification header or a model-token exchange. This source and the adapter's allowance were [checked in Windows session 0](verified.md#copilot) with CLI 1.0.105 and the checked 1.0.98; own OAuth credentials and Linux/macOS remain [unverified](unverified.md#copilots-machine-token-and-model-availability-btn-516). Though a token folder counts as a key, it is polled like a subscription (`Agent.keyUsage`), and a spent budget or a limit waits for the month's reset, not for a credit check (`CREDIT_CHECKS` never learns anything for a GitHub token). No Tally figure on the card: Tally prices a Copilot call at the model's API price, not at its credits.
- **One free account.** GitHub's terms allow one free account per person, and Copilot Free comes with it. Even Keel cannot see a token's plan, so unlike Codex it does not check: several tokens are for several paid seats or several people's own accounts, not to get round one free budget.

## Subscription credits and extra usage (BTN-532)

`RateLimits.overage` (`src/limits/overage.ts`) carries provider facts, with its own source and `updatedAt`, independently of the included usage windows. A newer window-only reading keeps the last extra-usage reading without refreshing its timestamp; `currentLimits` drops one older than the account's latest sign-in. Availability is never consent to spend. BTN-567 chose waiting for included allowance; BTN-577 implements detection and stopping separately from the display indicator.

| Claude background CLI | The checked 2.1.310 `-p /usage` answered with zero turns and zero cost, but no extra-usage line on the checked subscription ([live log](verified.md#accounts)) | Extra usage stays unknown; no undocumented line parser or extra OAuth endpoint |

On the wide accounts page, **Extra usage** follows the included windows in the common grid: a credit balance, paid USD spent, on/off permission, availability, or `—` for an unknown source. Keyboard-accessible tips name the source, its age and what it does not report. The drawer and widths up to 760 px show no extra column and keep `tightestWindow` unchanged.

An amber **on credits** chip appears beside the name on the page, in the drawer and on the active header account only while a session is working and the extra-usage evidence is at most ten minutes old. Claude needs an explicit `isUsingOverage: true`. ChatGPT needs available credits plus an exhausted included window whose reset is still ahead; its tip states that spending is inferred. Idle, resting, waiting or signed-out accounts do not get the chip. Copilot's historical amounts do not get it either. Extra usage does not enter the red problem band. Positive balances, actual paid use and automatic refresh through the live service remain [unverified](unverified.md#subscription-extra-usage-btn-532); BTN-531 owns that check.

### Stopping paid subscription usage (BTN-577)

`overageLimit` accepts evidence at most ten minutes old, including the boundary, and rejects future readings. It checks the window and credit timestamps independently. For a live, busy current chain session, Claude SDK `isUsingOverage: true` is direct evidence; Claude background CLI requires an exhausted `/usage` window with a future reset; Codex/OpenCode on ChatGPT require an exhausted included window and available credits; Copilot/OpenCode on Copilot require an exhausted monthly quota and `overage_permitted`. Historical counts and bills alone never stop a session, nor does a positive balance without an exhausted window. Missing evidence is not proof that spending has stopped. Zen has no invented balance source. API-key recovery is unchanged; Copilot tokens with subscription quotas still use the quota policy.

Only the current managed session id is eligible, including on paused chains. The dispatcher saves its handoff snapshot and limit hold before invoking its own `Agent.stop`, then records successful stopping. The hold survives disappearance from the monitor and service restarts; it waits for a known reset or another ready account with usable allowance. Warm recovery resumes the session; cold recovery hands off in the same worktree and branch. Neither repeats an already successful stop. An unknown reset remains unknown, without a speculative retry timer. `LimitsWatcher.limits` combines the newest windows and credit facts in the same `chatgpt:` pool, after each contributor's sign-in boundary; switching between Codex/OpenCode cannot bypass an exhausted pool. Poll frequency remains unchanged.

Available paid usage adds an amber warning on the account row, in both the page and drawer. Its tip explains detection delay and recommends provider spending controls for chain accounts, with a link beside it. This is a reaction after a request or poll, potentially five minutes late, not a zero-charge guarantee. Disable additional usage, disable automatic credit reload, or set a provider monthly cap where supported ([Claude](https://support.claude.com/en/articles/12429409-manage-usage-credits-for-paid-claude-plans), [ChatGPT](https://help.openai.com/en/articles/12642688-using-credits-for-flexible-usage-in-chatgpt-personal-plans)). No global or project spending opt-in is added, and a session's nominal dollar budget is not an extra-usage ceiling. Paid live checks require separate consent: [remaining checks](unverified.md#paid-subscription-usage-stops), manual task BTN-580 alongside BTN-531.

## Active account

- The active account is the shared provider's entry of the shared pool, `accounts[provider]` of the config (BTN-173; before schema v8 `active` of `state/account.json`; until 2026-10-17 always `accounts.claude`): the account pool of the run profiles (`docs/sessions.md`). Moving the "Even Keel" role to an account (the roles field), Claude's or Codex's, writes the shared `provider` of that account's agent and its pool entry (`ConfigStore.saveActive`, `withRunAccount`), so it moves only projects without their own `provider` or account entry; a project with them runs on those. The header shows the shared one, then every other account a project runs on by its provider's pool entry (`projectsByAccount` in `src/config.ts`, `AccountEntry.projects`), its card naming the projects of each (BTN-175). What only Claude has — the `.claude.json` sessions read, MCP failures, the tools view — stays on the shared `accounts.claude` (`claudeAccount` in `src/service.ts`). The project's commands (`beforeStart`, `check`, `afterGreen`) run in the environment of the account the task's session runs on, not the shared Claude one (EKR-26, `docs/chain.md`).
- The active account can be switched at any time, even with a chain running: the switch only picks the folder for new launches, so sessions of the active account, mid-turn or not (VS Code chats included), stay where they are and the chain's next session starts on the new account (`switchProblem`). The roles menu says so under "Even Keel". Renewing the active one's sign-in rewrites the folder's tokens, so it waits until every chain is paused or stopped and no session of the active account is mid-turn — `busy` or `waiting`.
- While signing in to the active account is in progress, or it is not signed in or its sign-in has expired, new sessions are not started (the chain pauses with a reason).
- `state/account.json` — for each folder, its account, since when it has been in effect and which one was before it. Folder limits received before the account change in it are not shown; the account that hit a limit is the session's folder and its e-mail at the time of the limit, and `--resume` only if the same folder with the same e-mail is active. An account without an e-mail (OpenCode or Copilot on the machine's sign-in) is identified by its folder key, in both the current view and `accountAt`, including an empty ledger; its e-mail stays null. Readiness requires `loggedIn: true` and no `launchBlock`, not an e-mail. This also lets the interrupted task continue after a fix of main without forcing a handoff while its cache is warm.

## The Claude desktop app

Even Keel does not switch the app's account (BTN-121): each profile needs its own sign-in by e-mail, and the usual ways of starting the app ignore the profile. Whoever needs it launches the app on an account folder by hand. Checked on Windows with the Store (MSIX) build 2.42304.0.0 on 2026-10-17:

- By default the app keeps its data in `%APPDATA%\Claude`, and the Claude Code it starts (its Code tab) works in `~/.claude` with the app's sign-in.
- The Electron flag `--user-data-dir=<folder>` opens a separate profile with its own sign-in, chats and settings. Several profiles run side by side; launching the same folder again focuses its window.
- `CLAUDE_CONFIG_DIR` set when the app is launched reaches the Claude Code it starts: that folder, not `~/.claude`, gets `sessions`, `projects` and `.claude.json`.

```powershell
$env:CLAUDE_CONFIG_DIR = "$HOME\.claude-accounts\<name>"
& "$env:LOCALAPPDATA\Microsoft\WindowsApps\claude-desktop.exe" --user-data-dir="$env:APPDATA\Claude-<name>"
```

- Sign in to a new profile only with "Continue with email". Google sign-in finishes in the browser with a `claude://` link, Windows hands the link to the app without the flag, and the sign-in lands in the default profile instead.
- The Start menu, a taskbar pin, autostart and an update relaunch open the default profile. A Windows shortcut cannot set an environment variable, so a shortcut to a profile has to run the two lines above (e.g. `pwsh -WindowStyle Hidden -Command …`).
- Even Keel cannot launch the app for you: from the service's Windows session 0 it does not start at all ("Access is denied").
- The shared configuration in the folder is as fresh as the last Even Keel launch there: the app's launch does not transfer it.
- Not checked: the installer (non-Store) build on Windows, macOS and Linux. On macOS the same is packaged by [claude-multiprofile](https://github.com/jmdarre-v/claude-multiprofile).

## Transferring the shared configuration (`src/account/share.ts`)

- Before every launch in an account folder, the following is transferred into it: `settings.json` (the global one on top of its own), `CLAUDE.md`, the plugin registry, a junction (a symlink outside Windows) to `agents`, `commands`, `hooks`, `output-styles` and skills. Each of the four folders lives in its own store next to the global folder, `~/.claude-<name>` (`linkedStore`), the way skills do (below): a real `~/.claude/<name>` is moved there and a link is left in its place, so the hook commands in `settings.json` that name `~/.claude/hooks/…` keep working; a missing one is linked back to the store; the account folder's `<name>` links to the store, an old link of its into `~/.claude/<name>` is re-pointed; a `~/.claude/<name>` that links elsewhere stays and the account links to it. Shared skills live in a store next to the global folder, `~/.claude-skills/<name>` (`skillStore`): a skill kept in `~/.claude/skills` as a real folder is moved there whole and leaves a link in its place, and the account folder's `skills/<name>` links to the store; an old account link to `~/.claude/skills/<name>` is re-pointed. A store folder that already holds the skill is merged into as memory is (below); a folder the move cannot rename (a file in it is open) stays with a warning in the log until the next launch, and the account links to it as before. The CLI's own `synced` and `.trash` stay, a global skill that links elsewhere (a repository's skill folder) stays and the account links to it, and an account skill that links to a live folder of its own choosing is not touched. Project memory lives in a store next to the global folder, `~/.claude-memory/<project>` (`memoryStore`, `sharedMemory`): both `~/.claude/projects/<project>/memory` and the account folder's `projects/<project>/memory` are links to it. Memory begun in either of them (a real folder, not a link) is first moved into the store, the global folder's first: files the store lacks are moved, identical ones dropped, and a file with the same name but different content stays where it is with a warning in the log (merging those, `MEMORY.md` included, is for a human). The folder becomes a link once nothing of its own is left; a link pointing elsewhere (the old target in `~/.claude`, a dangling one) is re-pointed. The walk covers the projects of the account folder as well as the shared ones.
- Why the stores are outside `~/.claude`: the CLI asks before every write whose real path lies in a `.claude` folder that is not the session's own, so a link from an account folder into `~/.claude` made it ask even with `--permission-mode auto` (a chain session stood 9 minutes on such a question, 2026-10-10). With the store outside, writes through both links pass without a question (verified on CLI 2.1.296 and 2.1.310 with a Haiku session), including sessions started by hand. Chain sessions also get the store folder as `autoMemoryDirectory` in `--settings` (`chainSettings`), whatever the "Trim the tools" switch. Skills had the same question (an edit of a shared `SKILL.md` from an account folder, 2026-10-20) and got their own store for it (BTN-256). Checked live on CLI 2.1.310 (BTN-294, a probe skill, Haiku, `--permission-mode auto`): the transfer moved a new skill from `~/.claude/skills` into the store and linked it from both account folders; a `SKILL.md` and a memory file are written without a question from an account folder and from `~/.claude`; sessions in `~/.claude` load skills through its links. `agents` and `hooks` (and so `commands`, `output-styles`) then linked straight into `~/.claude`: from an account folder an edit through them was refused in `auto` ("resolves through a symlink to `~/.claude/hooks/…`, which is outside the allowed working directories"), from `~/.claude` it passed; they got their stores for it (BTN-373). Checked live on CLI 2.1.310 the same way: the transfer moved the real `~/.claude/hooks` and `~/.claude/agents` into `~/.claude-hooks` and `~/.claude-agents` and linked both account folders to them; a hook file and an agent file are written without a question from an account folder and from `~/.claude`; both folders' sessions list the probe agent; the hook commands of `settings.json` that name `~/.claude/hooks/…` run through the link. `commands` and `output-styles` did not exist on that machine and were not seen; they take the same path.
- From `~/.claude.json` — trust and project settings (MCP local scope, `allowedTools`) for projects that are already trusted. The CLI creates several keys for one folder: VS Code writes the drive letter in lowercase — `d:/…`, the CLI — `D:/…` and `D:\…`; a folder counts as trusted if any spelling is trusted, and all its keys are transferred. Path case is ignored only on Windows and macOS, as everywhere Even Keel compares paths — `src/paths.ts`.
- The first-run completion mark (`hasCompletedOnboarding`, `lastOnboardingVersion`), if the folder lacks it: without it an interactive `claude` with the folder's `CLAUDE_CONFIG_DIR` shows the sign-in wizard even though the token is in place.
- The folder's temporary daemon (`claude --bg` starts it itself) keeps its own environment: the environment of the `claude --bg` that started it plus the `settings.json` `env` as it was then. Every session it spawns, a new one or a resumed one, inherits that environment and puts the `settings.json` `env` read at its own start on top (CLI 2.1.302, BTN-129, a probe variable in a sandbox account folder):
  - a new or changed `env` key reaches the next session at once, with the daemon running — through the transfer, at the next launch in the folder; a session already running keeps the value it started with;
  - a removed key stays in every session of that daemon with the value the daemon started with, until the daemon restarts;
  - the environment of a later `claude --bg` does not reach its session at all while the daemon runs, so Even Keel passes nothing per session that way.

  Only `env` was checked; whether the daemon holds on to any other part of the transfer (`CLAUDE.md`, the plugin registry, the links) was not. So if the transfer changed something and there are no live sessions in the folder (a fresh `claude agents` and `sessions/<pid>.json` entries), Even Keel stops its daemon before launching — `claude daemon stop --any` with the folder's `CLAUDE_CONFIG_DIR`; it does not touch the global daemon (`src/account/daemon.ts`). If there are live ones, the daemon is left alone, the account menu says the configuration will arrive after they finish, and the stop is postponed to the first launch without them. The mark lives in the service's memory. The stop is what keeps removed keys out of new sessions; it is held back by live sessions because `claude daemon stop` terminates every background session of the daemon, idle ones between turns included.
- The transfer only reads the global folder (besides moving its memory and skills into their stores, which leaves what its sessions see the same), so it never marks it as changed. What does is the removal of a profile's key on `/settings` → Trackers and CI (BTN-131, `docs/settings.md`): `DaemonRefresh.expire` marks the global folder and stops its daemon by the same rule — `claude daemon stop --any` with its `CLAUDE_CONFIG_DIR`, only while it has no live `sessions/<pid>.json` (the user's own sessions in `~/.claude` hold it too). While they do, the tab says the removal arrives after they end, and the stop is tried again at the next launch in the global folder. A key written or changed needs no stop: sessions read `env` at their start.
