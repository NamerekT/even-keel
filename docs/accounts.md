# Claude accounts

Reference for sessions: account folders, sign-in, switching, transferring the shared configuration.

## Folders and sign-in

- One configuration folder per account (`CLAUDE_CONFIG_DIR`): the global `~/.claude` (key `global`, listed only once it exists) and `~/.claude-accounts/<name>` (`EVEN_KEEL_ACCOUNTS_DIR`).
- **A first account (BTN-227).** The shared pool names `global` and `codex` by default, folders a fresh install may not have. An account added from the page (signed in or on a key) takes the shared pool's entry of its agent while that entry names no listed folder of the agent (`takesShared`, `withSharedAccount`, `ConfigStore.saveSharedAccount`); the provider is left as it is. Once the entry names a real folder, a new account does not move it.
- **A CLI that is not found.** Each agent says whether `spawn` without a shell starts its binary (`Agent.installed`, `findBinary` in `src/paths.ts`: a path as is, a bare name on `PATH`; on Windows only no extension, `.com` or `.exe`, so an npm `codex.cmd` shim alone does not count). Its agents are `AccountView.missing`: the add page shows that provider as an off choice with where to get the CLI (`login.claudeMissing`/`login.codexMissing`/`login.opencodeMissing`), the section has no "+ Add" and an empty section of it is not shown. A sign-in whose spawn fails with `ENOENT` says the same. Apart from that, the shared and the project settings offer a provider (the provider field, the rows of models and accounts) only once it has an account or the setting already names it (`offeredProviders`).
- The CLI itself stores and refreshes the tokens; Even Keel reads only the expiry times from `.credentials.json` (`expiresAt`, `refreshTokenExpiresAt`) and neither reads nor copies the tokens. `claude auth status --json` runs for each folder once a minute.
- "Add account" — `claude auth login --claudeai` in a temporary `.pending-*` folder; after sign-in the folder is named after the e-mail. "Renew" (next to the sign-in's days left) — signing in again in the account folder. The page shows the link and the code field in the sign-in dialog (below, "Accounts: the drawer, the page…").
- Removing — `claude auth logout` and the folder goes away (not the active one, not the global one, not one a pool entry names: the shared pool's — `account.sharedPool` — or a project's own — `account.projectPool`; `AccountView.pool`, `poolEntries` in `src/config.ts`). If there are live sessions, the folder is marked (`removing` in `state/account.json`), cannot be switched to, and is deleted at the first check after they end (the menu names the ones holding it); "Don't remove" clears the mark.
- A live session of a folder is one with a live process (a `sessions/<pid>.json` entry), not by `state` from `claude agents`: `blocked`/`working` stay there even for a session whose process and daemon died long ago, and such entries interfere neither with removing the folder nor with stopping its daemon (`liveSessions`).
- `*.lock` folders are locks the CLI puts next to an account folder while a token is refreshed; they are not accounts.
- **Token renewal (EKR-15).** Any call of the CLI may renew the folder's sign-in, and the refresh token it renews with is single-use: a call killed between sending the renewal and writing the answer, or two calls renewing at once, may leave `.credentials.json` with no tokens and the account signed out (21.10.2026, after a reboot; unconfirmed, `docs/unverified.md`). So:
  - Even Keel's short calls of a folder — `claude agents`, `auth status`, `-p /usage`, `-p /context` — run one at a time (`FolderCalls`, `src/claude/calls.ts`). A call past its timeout is given up on, not killed: it holds the folder until it ends and is killed only after five minutes; a call whose timeout passes while it waits never starts. Launches, `stop` and `daemon` calls go around it.
  - `auth status` and `/usage` wait until the provider's API answers (`Reachability`, `src/account/network.ts`: any HTTP answer from `api.anthropic.com`, `api.openai.com` or, for OpenCode, `opencode.ai`, probed at most every 30 s); the service starts before the network after a reboot. Meanwhile an account keeps what it showed, and `/usage` tries again in 30 s. The log says once when the API stops and starts answering.
  - The CLI leaves a `.oauth_refresh.lock.owner.tmp.<8 hex>` behind when writing the owner of its renewal lock fails half-way; with the session poll's `claude agents` every 3 s they came in bursts of hundreds while a token waited for renewal. Before each `auth status` such files older than an hour are deleted (`sweepRefreshLeftovers`, `src/claude/leftovers.ts`).
- The account e-mail in `auth status` is the saved profile from `.claude.json`, not the token owner: the Claude desktop app runs the CLI in `~/.claude` with its own account and rewrites the profile, so keep in `~/.claude` the same account as in the app, or launch the app on an account folder ("The Claude desktop app" below).

## API accounts (BTN-99)

- An API account is a folder whose sessions pay from an Anthropic API key instead of a subscription. "Add an API key" in the panel (command `account/api`, `AccountHomes.addApiKey`) creates `~/.claude-accounts/<folder>` with `settings.json` = `{ "env": { "ANTHROPIC_API_KEY": "…" } }` and `.claude.json` with the key's last 20 characters in `customApiKeyResponses.approved`, otherwise the CLI asks whether to use the key. A key shorter than 21 characters or with spaces is refused (`account.apiKeyInvalid`). Before the folder is made, the key is checked with Anthropic (`checkApiKey`, `src/account/keycheck.ts`): `GET /v1/models?limit=1` with it, which costs no tokens; 401 or 403 refuses it (`account.apiKeyRejected`), and a network error, a timeout or any other status refuses it too, as unchecked (`account.apiKeyUnchecked`), so no folder is made with a key nobody looked at. After that the watcher checks each API account's key from its `settings.json` once an hour (`KeyChecks`, in memory, so on every start too): a refused key makes the account `needsLogin` — the page says the key isn't accepted, the chain does not switch to it or launch on it — and a check that learns nothing keeps the last verdict. A folder with `apiKeyHelper` is not checked: there is no key to read. A folder set up by hand with `apiKeyHelper` instead of the variable works the same way.
- The account name from the form is not the folder name. The folder is the name made safe for a path (`folderName`: `Team API` → `team-api`, `api` when the name is empty, `-2` when taken) and stays the account's identity: the key in commands and `state/`, and its stand-in e-mail (`withIdentity`). The name itself is kept in `state/account.json` as `accounts.<folder>.name` (schema v4, `nameAccount`) and goes away with the account; the page shows it instead of the folder, and the folder in the account's details.
- `claude auth status --json` in such a folder says `loggedIn: true`, `authMethod: "api_key"` (`"api_key_helper"` with a helper) and no e-mail (`isApiKey`). The folder key stands in for the e-mail wherever an account is told apart by it (`withIdentity`): the limit owner, `state/account.json`, the session pills.
- The transfer of the shared configuration keeps the folder's own `env.ANTHROPIC_API_KEY` and `apiKeyHelper` over the global settings (`mergeSettings`); every other key still comes from `~/.claude`.
- How a Claude folder runs its sessions — `--bg` or the Agent SDK — is its `transport` in `state/account.json` (schema v10, `chooseTransport`, command `account/transport`); unset, an API folder takes the SDK and a subscription `--bg` (`docs/sessions.md`, "The Agent SDK transport"). A Claude key is added with the choice (`ApiKeyFields`, `transport` of `account/api`, the SDK preselected); a subscription gets none in the wizard and takes the default. Schema v11 (BTN-302) wrote `bg` to each account of an older `account.json` without a choice, all but Codex's own folder: the file does not tell a key from a subscription, `bg` is a subscription's default anyway, and a key that ran on `--bg` before the SDK came stays there.
- What an API account does not have: limits — `/usage` is not polled for it (it would answer free with no window lines anyway), there are no limit bars, and a key's `rate_limit` stops a session like any error (invariant 1); sign-in renewal and `claude auth logout` on removal; Remote Control, which needs a claude.ai sign-in (`RemoteOff` `api-key`).
- A key out of credit (BTN-165) is the one thing an API session waits out: the CLI's `billing_error` ("Credit balance is too low") is `apiError.kind` `credit`, its lamp is `limit`, and the session of the current task is held as on a limit (`docs/chain.md`, exception 1). Its "reset" is the moment the credit is back: while the dispatcher asks (`AccountWatcher.creditBackAfter`), the watcher checks the key every 5 minutes (`CreditChecks`, `checkCredit` in `src/account/credit.ts`, in memory; a Codex key — below) — the models list for the cheapest model (a Haiku, else the newest), then `/v1/messages` with `max_tokens: 1`, a fraction of a cent. 2xx is credit; a 400 saying "credit balance is too low" is none yet; anything else learns nothing and is logged. The checks start 5 minutes after the stop and end once the credit is back or 10 minutes after the dispatcher stopped asking. The panel says the key is out of credit and is checked (`t.session.creditOut`).
- Instead of the limits, the panel row, the account card and the header (while the API account is the active one) show the folder's spend since local midnight, from Tally (`/api/stats/spend`, `docs/stats.md`), refreshed every 5 minutes and fetched only while some account is on a key. Without Tally there is no figure.
- The prompt cache lifetime of sessions on a key is 5 minutes by default; the `cacheTtl` config key changes it (`docs/sessions.md`).

## The Codex folders (BTN-168, BTN-176)

- Codex's own folder `CODEX_HOME` or `~/.codex`, key `codex`, listed only once it exists (Codex does not create it); and one `CODEX_HOME` per added account under `~/.codex-accounts/<name>` (`EVEN_KEEL_CODEX_ACCOUNTS_DIR`), the same way as Claude's (`AccountHomes`, `src/account/homes.ts`). `CODEX_HOME` isolates everything — `auth.json`, `sessions/`, `state_5.sqlite`, `config.toml` — so each folder has its own sign-in, limits and sessions. A folder name is its account key across both roots: a new one is named apart from every Claude and Codex folder (`folderName`), and a Codex folder named like a Claude one by hand is not listed.
- "+ Add" in the Codex section (`account/add` with `agent: "codex"`) makes a `.pending-*` folder under the Codex root, runs `codex login --device-auth` in it and, signed in, names it by the e-mail — as Claude's add does. Removing an added folder is Claude's too: `codex logout` and the folder goes, after its sessions end. Codex's own folder is not removed from the page (`account.codexHomeKept`), and no Codex account is given to an app (`account.codexApp`).
- A new folder has no `config.toml`: its model is the shared or the project's `models.codex`, else Codex's default (a `config.toml` model the free plan refuses, such as `gpt-5.4-mini`, stays in `~/.codex`). The tracker's plugin in Codex is installed per folder: a new one has none until the user installs it there.
- A Codex account takes the Even Keel role like a Claude one (below). A Codex session starts in the pool's `accounts.codex` (`codex` by default; `docs/sessions.md`, "Run profiles"), and the chain judges a Codex task's launch block, limits and handoff account by that folder, not by the active one. There is no switching to another account on a spent limit — the chain waits for the reset or a change of the pool, as with Claude.
- **One free account.** Several free Codex accounts of one person to get round the limits break OpenAI's terms, so Even Keel keeps at most one (`extraFree`, `secondFreeProblem` in `src/account/model.ts`). The plan is `chatgpt_plan_type` of the `id_token` in `auth.json`; `free` is the free plan, any other (Plus, Pro, Business…) has no limit on the count. Adding an account that signs in on the free plan while another Codex account already is on it is refused (`account.secondFree`): the new folder is signed out and removed. If a folder's plan turns free later and there are two, the first free in the folders' order (Codex's own, then the added by name) keeps working; each other one has the warning on its card (`account.extraFree`), no session starts in it and it does not take the Even Keel role.
- **On an OpenAI API key (BTN-177).** "API key" in the Codex step of adding (`account/api` with `agent: "codex"`) makes a folder under the Codex root, named as Claude's API folders are, with `auth.json` = `{ "auth_mode": "apikey", "OPENAI_API_KEY": "…" }` — what `codex login --with-api-key` writes (checked on 0.162.1); Codex reads the key from there on every turn, so the turn's environment is unchanged and `codex login status` says "an API key" (`isApiKey`). The key is in the folder in plain text, as Claude's is in `settings.json`. Before the folder is made, the key is checked with `GET https://api.openai.com/v1/models` (`checkOpenAiKey`, no tokens): 401 or 403 refuses it (`account.codexKeyRejected`), anything else refuses it as unchecked (`account.codexKeyUnchecked`); then hourly, as Claude's. The free-account rule does not apply: a key is used under OpenAI's API terms, not ChatGPT's. Spend today comes from Tally as for Claude's keys (Codex rollouts are priced by GPT model, `tally/CLAUDE.md`); a model Tally has no price for shows no figure. A key out of money is waited out as Claude's (BTN-195): OpenAI answers 429 `insufficient_quota`, which codex-cli 0.162.1 words "Quota exceeded. Check your plan and billing details." (read from its binary, never seen live); the rollout fold takes that text, or OpenAI's own "You exceeded your current quota", as `credit` (`CREDIT_TEXT`, `src/codex/rollout.ts`) — any other `quota`, `usage limit` or `rate limit` stays `limit`. The watcher asks the folder's provider (`checkCredit(agent, key)`): for Codex `checkOpenAiCredit` — the models list for a `gpt-` text model with `nano` in its id, else `mini`, then `POST /v1/responses` with `max_output_tokens: 16` (the API's least) and `store: false`. 2xx is money; a 429 with `insufficient_quota` is none yet; a 429 of a rate limit and anything else learns nothing.
- Sign-in status is `codex login status` (`Logged in using ChatGPT` / `an API key` / `Not logged in`); the e-mail and plan come from the `id_token` claims. "Renew" and adding run `codex login --device-auth` through the same sign-in flow as Claude's, with a window of its own: no code field, the one-time code read out of the output (`loginCode`: the line under "Enter this one-time code", or OpenCode's "Enter code: …") into the login's `deviceCode` and shown large with a "Copy" button, the CLI output folded; a code not read leaves the output unfolded, the code in it (not checked live, `docs/unverified.md`); sign-out is `codex logout`.
- Limits are read from the folder's rollouts, not polled (`docs/sessions.md`, "Codex"); Tally collects the rollouts of every Codex folder (`tally/CLAUDE.md`). The shared configuration is not transferred: Codex reads its own `config.toml`, and the tracker's MCP server comes with every turn.

## The OpenCode folders (BTN-214)

- Only added ones, under `~/.opencode-accounts/<name>` (`EVEN_KEEL_OPENCODE_ACCOUNTS_DIR`): OpenCode keeps its files in the XDG folders of the user, shared with every OpenCode the user runs, so there is no "own folder" to list as with `~/.claude` and `~/.codex`. A folder holds the four XDG folders (`data`, `config`, `state`, `cache`) and the empty `config/opencode/AGENTS.md` that keeps `~/.claude/CLAUDE.md` out (`docs/sessions.md`, "OpenCode"). Names are unique across all three roots, as for Codex.
- Ways in (`SIGN_INS` in `src/agent/providers.ts`, `LOGIN_METHODS` in `src/opencode/cli.ts`), chosen on the add page and sent as `account/add` with `agent: "opencode"` and `method`:
  - `chatgpt` — `opencode providers login -p openai -m "ChatGPT Pro/Plus (headless)"`, a device link and code, shown as Codex's;
  - `copilot` — `-p github-copilot`, GitHub's device sign-in; Even Keel presses Enter for "GitHub.com" on the first question;
  - `none` — no sign-in: the folder is made at once and runs OpenCode's own free models (`opencode/big-pickle`);
  - an API key (`account/api` with `agent: "opencode"`) — written into `data/opencode/auth.json` as `opencode providers login` writes it, under `anthropic` for an `sk-ant-` key and `openai` for any other (`keyVendor`), and checked with that provider's API as Claude's and Codex's keys are (`keyProvider` in `src/account/homes.ts`).
- **No Claude subscription.** Anthropic allows the Pro/Max sign-in only in Claude Code, and OpenCode dropped it: Claude runs in OpenCode only on an API key. The add page says so.
- Status comes from `auth.json`, not a CLI call: no file is a folder signed in with `none`; a folder with credentials lists its providers where Claude's plan goes, and has no e-mail, so a folder added by a sign-in or with none is named after the agent (`opencode`, `opencode-2`…). Sign-out deletes `auth.json`. One folder may hold several providers; the run profile's model (`<provider>/<model>`) picks which one a session uses.
- No limits and no spend from Tally on the cards yet; Tally does count OpenCode sessions (`tally/CLAUDE.md`).

## The Copilot folders (BTN-215)

- Only added ones, under `~/.copilot-accounts/<name>` (`EVEN_KEEL_COPILOT_ACCOUNTS_DIR`), each a `COPILOT_HOME` (`src/copilot/home.ts`): config, `mcp-config.json`, `session-state/`. `~/.copilot` is not listed: it is the user's own Copilot, as `~/.local/share/opencode` is OpenCode's. Names are unique across all four roots.
- **The sign-in is not in the folder.** `copilot login` keeps its token in the OS credential store under `copilot-cli`, one for the whole machine, and the CLI falls back to `gh auth token`; a new `COPILOT_HOME` runs under it. So there are two ways in (`SIGN_INS`):
  - `none` — "Add" in the Copilot step makes the folder at once (named `copilot`, `copilot-2`…): its sessions run on whatever the machine is signed in with. Even Keel cannot read that sign-in, so the card shows no e-mail or plan and the folder always counts as signed in; a `copilot` missing from the machine fails the first turn.
  - a token (`account/api` with `agent: "copilot"`) — a fine-grained PAT with the "Copilot Requests" permission (`github_pat_`) or an OAuth token (`gho_`, `ghu_`); a classic `ghp_` token is refused (`account.copilotTokenInvalid`), since Copilot refuses it too. It is kept in the folder's `even-keel.json` and handed to every turn as `COPILOT_GITHUB_TOKEN`, which beats the stored sign-in, so each such folder is its own GitHub identity. It counts as a key: checked with `GET https://api.github.com/user` before the folder is made and hourly after (`checkGitHubToken`; 401 or 403 is `account.copilotTokenRejected`, anything else `account.copilotTokenUnchecked`), a refused one makes the account `needsLogin`. Default folder name `github`.
- **No limits and no spend on the cards.** Copilot's budget is AI credits or premium requests, which the CLI does not tell outside its interactive footer: the card says so instead of limit bars or a Tally figure (Tally prices a Copilot call at the model's API price, not at its credits). A spent budget (`session.error` about billing or AI credits) is waited out as a key out of credit, but the credit check for a GitHub token never learns anything (`CREDIT_CHECKS` in `src/service.ts`), so the session waits until "New session" or a new budget is noticed by hand (`docs/unverified.md`).
- **One free account.** GitHub's terms allow one free account per person, and Copilot Free comes with it. Even Keel cannot see a token's plan, so unlike Codex it does not check: several tokens are for several paid seats or several people's own accounts, not to get round one free budget.

## Active account

- The active account is the shared provider's entry of the shared pool, `accounts[provider]` of the config (BTN-173; before schema v8 `active` of `state/account.json`; until 2026-10-17 always `accounts.claude`): the account pool of the run profiles (`docs/sessions.md`). Moving the "Even Keel" role to an account (the roles field), Claude's or Codex's, writes the shared `provider` of that account's agent and its pool entry (`ConfigStore.saveActive`, `withRunAccount`), so it moves only projects without their own `provider` or account entry; a project with them runs on those. The header shows the shared one, then every other account a project runs on by its provider's pool entry (`projectsByAccount` in `src/config.ts`, `AccountEntry.projects`), its card naming the projects of each (BTN-175). What only Claude has — the `.claude.json` sessions read, MCP failures, the tools view — stays on the shared `accounts.claude` (`claudeAccount` in `src/service.ts`). The project's commands (`beforeStart`, `check`, `afterGreen`) run in the environment of the account the task's session runs on, not the shared Claude one (EKR-26, `docs/chain.md`).
- The active account can be switched at any time, even with a chain running: the switch only picks the folder for new launches, so sessions of the active account, mid-turn or not (VS Code chats included), stay where they are and the chain's next session starts on the new account (`switchProblem`). The roles menu says so under "Even Keel". Renewing the active one's sign-in rewrites the folder's tokens, so it waits until every chain is paused or stopped and no session of the active account is mid-turn — `busy` or `waiting`.
- While signing in to the active account is in progress, or it is not signed in or its sign-in has expired, new sessions are not started (the chain pauses with a reason).
- `state/account.json` — for each folder, its account, since when it has been in effect and which one was before it. Folder limits received before the account change in it are not shown; the account that hit a limit is the session's folder and its e-mail at the time of the limit, and `--resume` only if the same folder with the same e-mail is active.

## Accounts: the drawer, the page, adding, switching (BTN-169)

The server side is the same `account/*` commands for all four; the shared parts are in `web/src/layout/accountParts.tsx`.

- **The account's name** (BTN-335, `accountName` in `web/src/accountName.ts`) — one name wherever an account is seen or chosen: the header and its card, the drawer, `/accounts`, the account field of the shared and the project settings and their "As shared: …" (`accountOptions`, `folderLabel`), the session tags of the stats. The name the user gave it (`accounts.<folder>.name`), else its e-mail, else its provider's — "OpenCode Zen" for an OpenCode folder with no provider signed in (its providers are its plan tag) — with a number by the folder keys when two folders would read the same ("OpenCode Zen 2"). An API account's stand-in e-mail (`withIdentity`) is not taken for a name. The header's badge shortens an e-mail to its local part. The folder key (`global`, `codex`, `opencode`…) stays the identity and shows only in the mark's tip. A card's name is a field on a click (`AccountName` with `send`): Enter or leaving it saves through `account/name` (`AccountWatcher.rename`, `nameAccount`), Esc gives up, empty goes back to the default; only `state/account.json` changes, never the folder.

- **The account mark** (`AccountMark`, `accountParts.tsx`) — before every account's name: its agent's icon (Claude, Codex) in the account's colour and its connection's icon (CLI, API key), so two folders with similar names are told apart without reading. Pointed at or focused, it opens a tip at once (`Tipped`, `web/src/ui/Tipped.tsx`, over `useTip`; not the slow native `title`): the agent and the connection by name, the sign-in left (unless a warning already says it), the folder, and a configuration still on its way. The account's colour is its place by e-mail (`entrySlot`, `web/src/accounts.ts`; a key-only folder by its key), the same on the card's top edge, the mark and the header's dot.
- **The roles field** (`AccountRoles`, `web/src/layout/AccountRoles.tsx`, `roles.css`) — one per Claude account, on the page and in the drawer: chips of what works on the account (Even Keel — the active account of the chain; each app, `src/account/apps.ts`, `src/account/vscode.ts`), or "Not in use". A chip is an icon only — our own sail for Even Keel, a neutral editor window for VS Code (`APP_ICONS`; no trademarked logos, the repository is public) — with its name in a tip, so the field stays one line and the card's foot one height however many roles there are. A click opens a menu: first the roles held here, named (a touch screen has no pointing to open the chips' tips), then the roles held by other accounts; picking one moves it here, and its chip leaves the other card. An item that cannot move is greyed with the reason as a line under it (open VS Code chats); one that can has its note there (the sessions already working stay where they are; VS Code's reload hint). The menu is a `popover="manual"` inside the field, so picking in the drawer does not close the drawer. A Codex account's field offers only the Even Keel role: the apps are Claude's (`account.codexApp`). Moving the role to another agent's account says in its note that projects without their own provider move with it.
- **Working now** (`AccountWork`, same file) — the account's live sessions under the roles: chain and Even Keel sessions by their CLI name, VS Code chats by their tab title with "VS Code · working/open". The title is the last `custom-title` in the transcript, else the last `ai-title` (`titleOf`, `ChatTitles` in `src/sessions/title.ts`, which reads the transcript's last 256 KB and caches it by size); without either, the CLI name.
- **The drawer** (`AccountPanel`, `web/src/layout/Account.tsx`; BTN-328) — a side panel on the right that answers at a glance where the work runs, how much is left and where to move it. Two parts, each in the page's order (`panelSections` over `accountGroups`, `web/src/accounts.ts`): "At work" — the folders holding Even Keel or an app, named by a project's pool entry or running a session (`atWork`) — in full: the windows with their names, today's spend for a key, or one grey "no data" with why in its tip; "Others" a line each, with what is left of the tightest window as one number on the right (`tightestWindow`: "wk 36%", amber from 80 % used, red at 100 %; the window and its reset in the tip), the spend for a key, or a dash with why in the tip. A row is plain — no band, no tint: the account's colour is a dot before a muted agent icon (`AccountMark` with `dot`, the connection in its tip), and the address is whole in one weight (`AccountName` with `whole`). The roles are bare chips, and "Here ▾" (`AccountRoles` with `compact`) opens the same menu; it shows only on the row pointed at or in focus (always on a screen without hover), keeping its room so the numbers stay under the "free" head. A row shows, only when there is one, an exception with its action (`AccountNotes` with `quiet`: the stale reason and a pending configuration are in tips, a failed check is short). Below: "+ Add account" (to `/accounts/add`) and "All accounts" (to `/accounts`).
- **The sign-in dialog** (`LoginDialog`, `web/src/layout/LoginDialog.tsx`) — a renewal or sign-in started from the drawer or a card opens a modal with its steps (`LoginSteps`: the link, the code field, the CLI output), on any page but `/accounts/add`, which walks its own in place. It follows the server's `account.login`, not the click, so it is there in every tab and after a reload and goes once the sign-in ends. × and Escape cancel the sign-in (`account/cancel`): left running out of sight, it would keep every sign-in button greyed with nothing on screen, which is how the steps at the drawer's bottom read before. A backdrop click does nothing, so a stray click on return from the sign-in tab does not end it.
- **The page `/accounts`** (`web/src/pages/Accounts.tsx`, `accounts.css`) — a section per provider (`accountGroups`, `web/src/accounts.ts`): Claude Code, then Codex, an agent the page does not know after them; a provider that can be added keeps its section with "No accounts yet" when it has none. The section's head has its own "+ Add", straight to the connection step of that provider (`/accounts/add?provider=…`); the page's head has no add button. Inside a section, a card per account in a grid: the chain's account first, then the drawer's order. In sight stays only what needs a look or an action: the mark, the name and the plan; the limits, or today's spend for a key; working now (session names run on in one wrapping line, a VS Code chat takes a row); the warnings with an action (`AccountNotes` with `bare`: sign-in needed or ending, a key not accepted, removal pending). The rest opens on pointing or focus: the sign-in left, the folder and a pending configuration in the mark's tip; why there are no limits on the "no data" cells (dotted underline); a failed check is one short line with the error in its tip. What the card changes sits in its foot, one row pinned to the bottom so it is level across a row of cards: "Remove" behind a modal confirmation (`ConfirmDialog`: the card is too narrow to ask in line; "Don't remove" holds the focus) — greyed (`aria-disabled`, so it still takes the focus) with why the folder is kept in its tip (`RemoveAction`) — renew or sign in (greyed the same way, with the running chain or the busy sessions in its tip, while the active account is held) and keep (`NoteActions`), and the roles field taking the rest of the row; its "Not in use" is cut with an ellipsis rather than wrapped, so the foot stays one line.
- **Adding** — `/accounts/add` (`web/src/pages/AccountAdd.tsx`), the step in the URL (`?provider=…&connection=…`, `addStep`), so the browser's Back goes a step back: the provider (Claude Code, Codex, OpenCode, GitHub Copilot), then the connection (CLI, Agent SDK, API key), then the sign-in. What cannot be added yet is a dashed card with a "not yet" tag (`canAdd`): the Agent SDK (no SDK engine, BTN-136). Each kind has its own sign-in window: Claude CLI — "Sign in" (`account/add`), the link and the code field; an API key, Claude's or Codex's — the name and key form (`ApiKeyFields`, the agent goes with the key); Codex CLI — device-auth into a new folder (`account/add` with `agent: "codex"`), with the one-free-account rule under the button; OpenCode CLI — a button per way in (`OpenCodeSignIn`: ChatGPT, GitHub Copilot, free models) and the note that Claude goes only by key; Copilot CLI — one button that adds a folder on the machine's own sign-in (`CopilotSignIn`), its key step taking a GitHub token. A Codex or OpenCode sign-in window (`deviceLogin`, by the login's `agent`) has no code field: the one-time code, which goes on the provider's page, is shown apart from the output, large and with a "Copy" button (`DeviceCode` in `web/src/layout/accountParts.tsx`); the button falls back to `execCommand('copy')` where the page has no clipboard API. Without a `deviceCode` the window is as before — the hint and the CLI output unfolded. A sign-in that ends (the login turns `null`) or a key that is added leads back to `/accounts`.
- Every place that shows a session — the current chain row, the session panel and its list of the task's sessions, the session and transcript windows, the last session on `/tools`, the session timeline of a task on `/stats` — names its account with a pill in the account's colour (`AccountTag`; the colour is the folder's place among the keys sorted, `accountSlot` in `web/src/accounts.ts`). A live session's account is its folder; a finished one's is the folder holding its transcript (`TranscriptOwners`, `src/sessions/owners.ts`, rescanned at most every 5 min on a miss), with the e-mail the folder had at the session's start.
- Limit bars turn amber from 80% and red at 100%, in the panel and in the header.
- For now there is one app — VS Code: its account is `CLAUDE_CONFIG_DIR` in `claudeCode.environmentVariables` of the user `settings.json` (`%APPDATA%\Code\User` on Windows, `~/Library/Application Support/Code/User` on macOS, `$XDG_CONFIG_HOME/Code/User` or `~/.config/Code/User` on Linux); `global` means no variable.
- The file is rewritten only if it is pure JSON (with comments it is an error in the panel, fix by hand); other keys, indentation and line endings are preserved.
- Switching is impossible while any Claude chat is open in VS Code — a live `sessions/<pid>.json` entry with `entrypoint: "claude-vscode"` in any account folder (polled every 5 s and again before writing); the chain and Even Keel sessions do not interfere. Before writing, the shared configuration is transferred to the folder (`DaemonRefresh.prepare`).
- The account an app sits on is not removed. VS Code picks up the new account after Developer: Reload Window.
- The Claude desktop app is not in the panel: it is launched on an account folder by hand, see below.

## The Claude desktop app

Even Keel does not switch the app's account (BTN-121): each profile needs its own sign-in by e-mail, and the usual ways of starting the app ignore the profile. Whoever needs it launches the app on an account folder by hand. Checked on Windows with the Store (MSIX) build 2.42304.0.0 on 2026-10-17:

- By default the app keeps its data in `%APPDATA%\Claude`, and the Claude Code it starts (its Code tab) works in `~/.claude` with the app's sign-in.
- The Electron flag `--user-data-dir=<folder>` opens a separate profile with its own sign-in, chats and settings. Several profiles run side by side; launching the same folder again focuses its window.
- `CLAUDE_CONFIG_DIR` set when the app is launched reaches the Claude Code it starts: that folder, not `~/.claude`, gets `sessions`, `projects` and `.claude.json`.

```powershell
$env:CLAUDE_CONFIG_DIR = "$HOME\.claude-accounts\<name>"
& "$env:LOCALAPPDATA\Microsoft\WindowsApps\claude-desktop.exe" --user-data-dir="$env:APPDATA\Claude-<name>"
```

- Sign in to a new profile only with "Continue with email". Google sign-in finishes in the browser with a `claude://` link, Windows hands the link to the app without the flag, and the sign-in lands in the default profile instead.
- The Start menu, a taskbar pin, autostart and an update relaunch open the default profile. A Windows shortcut cannot set an environment variable, so a shortcut to a profile has to run the two lines above (e.g. `pwsh -WindowStyle Hidden -Command …`).
- Even Keel cannot launch the app for you: from the service's Windows session 0 it does not start at all ("Access is denied").
- The shared configuration in the folder is as fresh as the last Even Keel launch there: the app's launch does not transfer it.
- Not checked: the installer (non-Store) build on Windows, macOS and Linux. On macOS the same is packaged by [claude-multiprofile](https://github.com/jmdarre-v/claude-multiprofile).

## Transferring the shared configuration (`src/account/share.ts`)

- Before every launch in an account folder, the following is transferred into it: `settings.json` (the global one on top of its own), `CLAUDE.md`, the plugin registry, a junction (a symlink outside Windows) to `agents`, `hooks`, skills. Shared skills live in a store next to the global folder, `~/.claude-skills/<name>` (`skillStore`): a skill kept in `~/.claude/skills` as a real folder is moved there whole and leaves a link in its place, and the account folder's `skills/<name>` links to the store; an old account link to `~/.claude/skills/<name>` is re-pointed. A store folder that already holds the skill is merged into as memory is (below); a folder the move cannot rename (a file in it is open) stays with a warning in the log until the next launch, and the account links to it as before. The CLI's own `synced` and `.trash` stay, a global skill that links elsewhere (a repository's skill folder) stays and the account links to it, and an account skill that links to a live folder of its own choosing is not touched. Project memory lives in a store next to the global folder, `~/.claude-memory/<project>` (`memoryStore`, `sharedMemory`): both `~/.claude/projects/<project>/memory` and the account folder's `projects/<project>/memory` are links to it. Memory begun in either of them (a real folder, not a link) is first moved into the store, the global folder's first: files the store lacks are moved, identical ones dropped, and a file with the same name but different content stays where it is with a warning in the log (merging those, `MEMORY.md` included, is for a human). The folder becomes a link once nothing of its own is left; a link pointing elsewhere (the old target in `~/.claude`, a dangling one) is re-pointed. The walk covers the projects of the account folder as well as the shared ones.
- Why the stores are outside `~/.claude`: the CLI asks before every write whose real path lies in a `.claude` folder that is not the session's own, so a link from an account folder into `~/.claude` made it ask even with `--permission-mode auto` (a chain session stood 9 minutes on such a question, 2026-10-10). With the store outside, writes through both links pass without a question (verified on CLI 2.1.296 with a Haiku session), including sessions started by hand. Chain sessions also get the store folder as `autoMemoryDirectory` in `--settings` (`chainSettings`), whatever the "Trim the tools" switch. Skills had the same question (an edit of a shared `SKILL.md` from an account folder, 2026-10-20) and got their own store for it (BTN-256, not yet checked live — `docs/unverified.md`).
- From `~/.claude.json` — trust and project settings (MCP local scope, `allowedTools`) for projects that are already trusted. The CLI creates several keys for one folder: VS Code writes the drive letter in lowercase — `d:/…`, the CLI — `D:/…` and `D:\…`; a folder counts as trusted if any spelling is trusted, and all its keys are transferred. Path case is ignored only on Windows and macOS, as everywhere Even Keel compares paths — `src/paths.ts`.
- The first-run completion mark (`hasCompletedOnboarding`, `lastOnboardingVersion`), if the folder lacks it: without it an interactive `claude` with the folder's `CLAUDE_CONFIG_DIR` shows the sign-in wizard even though the token is in place.
- The folder's temporary daemon (`claude --bg` starts it itself) keeps its own environment: the environment of the `claude --bg` that started it plus the `settings.json` `env` as it was then. Every session it spawns, a new one or a resumed one, inherits that environment and puts the `settings.json` `env` read at its own start on top (CLI 2.1.302, BTN-129, a probe variable in a sandbox account folder):
  - a new or changed `env` key reaches the next session at once, with the daemon running — through the transfer, at the next launch in the folder; a session already running keeps the value it started with;
  - a removed key stays in every session of that daemon with the value the daemon started with, until the daemon restarts;
  - the environment of a later `claude --bg` does not reach its session at all while the daemon runs, so Even Keel passes nothing per session that way.

  Only `env` was checked; whether the daemon holds on to any other part of the transfer (`CLAUDE.md`, the plugin registry, the links) was not. So if the transfer changed something and there are no live sessions in the folder (a fresh `claude agents` and `sessions/<pid>.json` entries), Even Keel stops its daemon before launching — `claude daemon stop --any` with the folder's `CLAUDE_CONFIG_DIR`; it does not touch the global daemon (`src/account/daemon.ts`). If there are live ones, the daemon is left alone, the account menu says the configuration will arrive after they finish, and the stop is postponed to the first launch without them. The mark lives in the service's memory. The stop is what keeps removed keys out of new sessions; it is held back by live sessions because `claude daemon stop` terminates every background session of the daemon, idle ones between turns included.
- The transfer only reads the global folder (besides moving its memory and skills into their stores, which leaves what its sessions see the same), so it never marks it as changed. What does is the removal of a key on `/settings` → Access (BTN-131, `docs/settings.md`): `DaemonRefresh.expire` marks the global folder and stops its daemon by the same rule — `claude daemon stop --any` with its `CLAUDE_CONFIG_DIR`, only while it has no live `sessions/<pid>.json` (the user's own sessions in `~/.claude` hold it too). While they do, the tab says the removal arrives after they end, and the stop is tried again at the next launch in the global folder. A key written or changed needs no stop: sessions read `env` at their start.
