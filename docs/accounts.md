# Claude accounts

Reference for sessions: account folders, sign-in, switching, transferring the shared configuration.

## Folders and sign-in

- One configuration folder per account (`CLAUDE_CONFIG_DIR`): the global `~/.claude` (key `global`) and `~/.claude-accounts/<name>` (`EVEN_KEEL_ACCOUNTS_DIR`).
- The CLI itself stores and refreshes the tokens; Even Keel reads only the expiry times from `.credentials.json` (`expiresAt`, `refreshTokenExpiresAt`) and neither reads nor copies the tokens. `claude auth status --json` runs for each folder once a minute.
- "Add account" — `claude auth login --claudeai` in a temporary `.pending-*` folder; after sign-in the folder is named after the e-mail. "Renew sign-in" — signing in again in the account folder. The page shows the link and the code field in the account menu.
- Removing — `claude auth logout` and the folder goes away (not the active one, not the global one). If there are live sessions, the folder is marked (`removing` in `state/account.json`), cannot be switched to, and is deleted at the first check after they end (the menu names the ones holding it); "Don't remove" clears the mark.
- A live session of a folder is one with a live process (a `sessions/<pid>.json` entry), not by `state` from `claude agents`: `blocked`/`working` stay there even for a session whose process and daemon died long ago, and such entries interfere neither with removing the folder nor with stopping its daemon (`liveSessions`).
- `*.lock` folders are locks the CLI puts next to an account folder while a token is refreshed; they are not accounts.
- The account e-mail in `auth status` is the saved profile from `.claude.json`, not the token owner: the Claude desktop app runs the CLI in `~/.claude` with its own account and rewrites the profile, so keep in `~/.claude` the same account as in the app, or launch the app on an account folder ("The Claude desktop app" below).

## API accounts (BTN-99)

- An API account is a folder whose sessions pay from an Anthropic API key instead of a subscription. "Add an API key" in the panel (command `account/api`, `AccountHomes.addApiKey`) creates `~/.claude-accounts/<folder>` with `settings.json` = `{ "env": { "ANTHROPIC_API_KEY": "…" } }` and `.claude.json` with the key's last 20 characters in `customApiKeyResponses.approved`, otherwise the CLI asks whether to use the key. A key shorter than 21 characters or with spaces is refused (`account.apiKeyInvalid`). Before the folder is made, the key is checked with Anthropic (`checkApiKey`, `src/account/keycheck.ts`): `GET /v1/models?limit=1` with it, which costs no tokens; 401 or 403 refuses it (`account.apiKeyRejected`), and a network error, a timeout or any other status refuses it too, as unchecked (`account.apiKeyUnchecked`), so no folder is made with a key nobody looked at. After that the watcher checks each API account's key from its `settings.json` once an hour (`KeyChecks`, in memory, so on every start too): a refused key makes the account `needsLogin` — the page says the key isn't accepted, the chain does not switch to it or launch on it — and a check that learns nothing keeps the last verdict. A folder with `apiKeyHelper` is not checked: there is no key to read. A folder set up by hand with `apiKeyHelper` instead of the variable works the same way.
- The account name from the form is not the folder name. The folder is the name made safe for a path (`folderName`: `Team API` → `team-api`, `api` when the name is empty, `-2` when taken) and stays the account's identity: the key in commands and `state/`, and its stand-in e-mail (`withIdentity`). The name itself is kept in `state/account.json` as `accounts.<folder>.name` (schema v4, `nameAccount`) and goes away with the account; the page shows it instead of the folder, and the folder in the account's details.
- `claude auth status --json` in such a folder says `loggedIn: true`, `authMethod: "api_key"` (`"api_key_helper"` with a helper) and no e-mail (`isApiKey`). The folder key stands in for the e-mail wherever an account is told apart by it (`withIdentity`): the limit owner, `state/account.json`, the session pills.
- The transfer of the shared configuration keeps the folder's own `env.ANTHROPIC_API_KEY` and `apiKeyHelper` over the global settings (`mergeSettings`); every other key still comes from `~/.claude`.
- What an API account does not have: limits — `/usage` is not polled for it (it would answer free with no window lines anyway), there are no limit bars, and limit exception 1 (`--resume` or a handoff) does not apply, so a session that runs out of credit stops like any error (invariant 1); sign-in renewal and `claude auth logout` on removal; Remote Control, which needs a claude.ai sign-in (`RemoteOff` `api-key`).
- Instead of the limits, the panel row, the account card and the header (while the API account is the active one) show the folder's spend since local midnight, from Tally (`/api/stats/spend`, `docs/stats.md`), refreshed every 5 minutes and fetched only while some account is on a key. Without Tally there is no figure.
- The prompt cache lifetime of sessions on a key is 5 minutes by default; the `cacheTtl` config key changes it (`docs/sessions.md`).

## Active account

- The active account can be switched at any time, even with a chain running: the switch only picks the folder for new launches, so sessions of the active account, mid-turn or not (VS Code chats included), stay where they are and the chain's next session starts on the new account (`switchProblem`). The panel warns while chains run. Renewing the active one's sign-in rewrites the folder's tokens, so it waits until every chain is paused or stopped and no session of the active account is mid-turn — `busy` or `waiting`.
- While signing in to the active account is in progress, or it is not signed in or its sign-in has expired, new sessions are not started (the chain pauses with a reason).
- `state/account.json` — the active account and, for each folder, its account, since when it has been in effect and which one was before it. Folder limits received before the account change in it are not shown; the account that hit a limit is the session's folder and its e-mail at the time of the limit, and `--resume` only if the same folder with the same e-mail is active.

## Accounts panel (`AccountMenu`)

- A side panel on the right. On top, one row per account folder with its colour dot and its 5-hour and weekly limits in aligned columns; the folders that can work now (signed in, not being removed, no used-up window) go first, the rest keep their order below (`accountOrder`, `limitedUntil` in `web/src/state.ts`). A row shows, only when there is one, an exception with its action: sign-in needed or ending, removal pending, configuration pending, a failed check. "⋯" opens the details: plan, sign-in, sessions, folder and "Remove" (or why the folder is kept).
- Each row ends with one button per role — Even Keel (the active account of the chain) and each app (`src/account/apps.ts`, `src/account/vscode.ts`). The role the account holds is a pressed, inactive button with a check; a role the account cannot take is disabled with the reason in its tooltip; hovering an active button highlights its row. Below the list, "Roles" holds the notes: the running chains a switch will not stop, the open chats that hold VS Code, its reload hint.
- Every place that shows a session — the current chain row, the session panel and its list of the task's sessions, the session and transcript windows, the last session on `/tools`, the session timeline of a task on `/stats` — names its account with a pill in the account's colour (`AccountTag`; the colour is the folder's place among the keys sorted, `accountSlot` in `web/src/accounts.ts`). A live session's account is its folder; a finished one's is the folder holding its transcript (`TranscriptOwners`, `src/sessions/owners.ts`, rescanned at most every 5 min on a miss), with the e-mail the folder had at the session's start.
- Limit bars turn amber from 80% and red at 100%, in the panel and in the header.
- For now there is one app — VS Code: its account is `CLAUDE_CONFIG_DIR` in `claudeCode.environmentVariables` of the user `settings.json` (`%APPDATA%\Code\User` on Windows, `~/Library/Application Support/Code/User` on macOS, `$XDG_CONFIG_HOME/Code/User` or `~/.config/Code/User` on Linux); `global` means no variable.
- The file is rewritten only if it is pure JSON (with comments it is an error in the panel, fix by hand); other keys, indentation and line endings are preserved.
- Switching is impossible while any Claude chat is open in VS Code — a live `sessions/<pid>.json` entry with `entrypoint: "claude-vscode"` in any account folder (polled every 5 s and again before writing); the chain and Even Keel sessions do not interfere. Before writing, the shared configuration is transferred to the folder (`DaemonRefresh.prepare`).
- The account an app sits on is not removed. VS Code picks up the new account after Developer: Reload Window.
- The Claude desktop app is not in the panel: it is launched on an account folder by hand, see below.

## The Claude desktop app

Even Keel does not switch the app's account (BTN-121): each profile needs its own sign-in by e-mail, and the usual ways of starting the app ignore the profile. Whoever needs it launches the app on an account folder by hand. Checked on Windows with the Store (MSIX) build 2.42304.0.0 on 2026-10-17:

- By default the app keeps its data in `%APPDATA%\Claude`, and the Claude Code it starts (its Code tab) works in `~/.claude` with the app's sign-in.
- The Electron flag `--user-data-dir=<folder>` opens a separate profile with its own sign-in, chats and settings. Several profiles run side by side; launching the same folder again focuses its window.
- `CLAUDE_CONFIG_DIR` set when the app is launched reaches the Claude Code it starts: that folder, not `~/.claude`, gets `sessions`, `projects` and `.claude.json`.

```powershell
$env:CLAUDE_CONFIG_DIR = "$HOME\.claude-accounts\<name>"
& "$env:LOCALAPPDATA\Microsoft\WindowsApps\claude-desktop.exe" --user-data-dir="$env:APPDATA\Claude-<name>"
```

- Sign in to a new profile only with "Continue with email". Google sign-in finishes in the browser with a `claude://` link, Windows hands the link to the app without the flag, and the sign-in lands in the default profile instead.
- The Start menu, a taskbar pin, autostart and an update relaunch open the default profile. A Windows shortcut cannot set an environment variable, so a shortcut to a profile has to run the two lines above (e.g. `pwsh -WindowStyle Hidden -Command …`).
- Even Keel cannot launch the app for you: from the service's Windows session 0 it does not start at all ("Access is denied").
- The shared configuration in the folder is as fresh as the last Even Keel launch there: the app's launch does not transfer it.
- Not checked: the installer (non-Store) build on Windows, macOS and Linux. On macOS the same is packaged by [claude-multiprofile](https://github.com/jmdarre-v/claude-multiprofile).

## Transferring the shared configuration (`src/account/share.ts`)

- Before every launch in an account folder, the following is transferred into it: `settings.json` (the global one on top of its own), `CLAUDE.md`, the plugin registry, a junction (a symlink outside Windows) to `agents`, `hooks`, skills. Project memory lives in a store next to the global folder, `~/.claude-memory/<project>` (`memoryStore`, `sharedMemory`): both `~/.claude/projects/<project>/memory` and the account folder's `projects/<project>/memory` are links to it. Memory begun in either of them (a real folder, not a link) is first moved into the store, the global folder's first: files the store lacks are moved, identical ones dropped, and a file with the same name but different content stays where it is with a warning in the log (merging those, `MEMORY.md` included, is for a human). The folder becomes a link once nothing of its own is left; a link pointing elsewhere (the old target in `~/.claude`, a dangling one) is re-pointed. The walk covers the projects of the account folder as well as the shared ones.
- Why the store is outside `~/.claude`: the CLI asks before every write whose real path lies in a `.claude` folder that is not the session's own, so a link from an account folder into `~/.claude` made it ask even with `--permission-mode auto` (a chain session stood 9 minutes on such a question, 2026-10-10). With the store outside, writes through both links pass without a question (verified on CLI 2.1.296 with a Haiku session), including sessions started by hand. Chain sessions also get the store folder as `autoMemoryDirectory` in `--settings` (`chainSettings`), whatever the "Trim the tools" switch.
- From `~/.claude.json` — trust and project settings (MCP local scope, `allowedTools`) for projects that are already trusted. The CLI creates several keys for one folder: VS Code writes the drive letter in lowercase — `d:/…`, the CLI — `D:/…` and `D:\…`; a folder counts as trusted if any spelling is trusted, and all its keys are transferred. Path case is ignored only on Windows and macOS, as everywhere Even Keel compares paths — `src/paths.ts`.
- The first-run completion mark (`hasCompletedOnboarding`, `lastOnboardingVersion`), if the folder lacks it: without it an interactive `claude` with the folder's `CLAUDE_CONFIG_DIR` shows the sign-in wizard even though the token is in place.
- The folder's temporary daemon (`claude --bg` starts it itself) caches the configuration: the transfer reaches sessions started after its restart. So if the transfer changed something and there are no live sessions in the folder (a fresh `claude agents` and `sessions/<pid>.json` entries), Even Keel stops its daemon before launching — `claude daemon stop --any` with the folder's `CLAUDE_CONFIG_DIR`; it does not touch the global daemon (`src/account/daemon.ts`). If there are live ones, the daemon is left alone, the account menu says the configuration will arrive after they finish, and the stop is postponed to the first launch without them. The mark lives in the service's memory.
