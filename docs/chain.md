# Chain

Reference for sessions: entry into the chain, order, task worktrees, cleanup and the details of the exceptions to invariant 1. The invariants themselves are in `CLAUDE.md`.

## Entry into the chain

- The rules are `chain` in `even-keel.config.json` (`src/chain/rules.ts`): a global top-level one and a project's own on top of it (a project is a path string or `{ "repo", "chain" }`; the project key replaces the global one entirely).
- `active` and `terminal` are status names (case-insensitive, whitespace trimmed); without the key, by category: active are `ToDo` and `Active`, terminal are `Won` and `Lost`. A name that Huly does not have is a warning in the log; a status in both lists is a config error.
- `requiredLabels` — at least one of them is needed (empty — not needed), `excludedLabels` (`["Manual", "Вручную"]` by default) removes a task altogether, the user starts it themselves. A task that fails the label rules is cut off in the same place as closed ones (`Dispatcher.setTasks`), but as an open blocker it still holds a chain task (below).
- By default the chain includes tasks in Todo and beyond: Backlog (category `UnStarted`) is a store of ideas, neither active nor terminal, and the chain does not take it. A move to an active status lets a task into the chain.
- The backlog for the page (`ProjectOrder.backlog`) is open tasks outside the chain by status or without the needed label, except locked blockers and tasks with an excluding label. The progress on the card counts only closed tasks and the chain, with the backlog in a separate caption; on the project page it is a chip in the header that opens the backlog in the side panel (`#backlog` in the address, the same place as the session panel). `ProjectOrder.landing` says where each backlog task and each of the project's own locked blockers (not parents or other projects' tasks) the label rules admit would stand once it is active: the chain task it would precede, `null` for the end (`Dispatcher.landing` places it with `[...chain, task]` the way a new task is placed); the page shows a ghost there for a backlog task. Where that order does not build, the task is in `ProjectOrder.refused` with the reason instead, and every "Move to Todo" of it (backlog panel, card, locked row) is off with that reason as its title: taking it would halt the chain.
- The order does not build when blockers form a cycle (`order.cycle`), a task is blocked by one from a later milestone (`order.later`), or blockers go against the milestone order through tasks without one (`order.against`). The chain then halts (`halt`: paused with the notice), and the page shows the notice and the open tasks by number, without locks. A blocker from a later milestone that waits in the backlog holds its task quietly, filed on the page under the held task's milestone; only its move to Todo would halt the chain, which `refused` prevents from the page — not from the tracker.
- An open blocker outside the chain — in an inactive status, with an excluding label (a manual task, a question), without a needed one, a parent or a task of another project (BTN-68, `waitingBlockers` in `src/chain/order.ts`, and further by its blockers of the same kind) — holds a chain task: it is not started, and the current one with such a blocker is postponed (`postpone`), as with a blocker from the chain; if all tasks hold such blockers, the chain ends. The page shows it (`ProjectOrder.waiting`) in front of the task it holds (`withWaiting`), dimmed and locked: without a number or dragging, the key goes to the task in the tracker and the title opens its card. In place of the number, a blocker with a `landing` or `refused` entry in the backlog status (`UnStarted`) of a tracker that can move it has the "Move to Todo" button (`readyButton` in `web/src/state.ts`). Moved to an active status — it is an ordinary chain task; closed — the task is free. Blockers that are not among the project's open tasks (parents, other projects, closed ones) are requested by ID on every tracker poll (`tracker.tasks`) and handed to the chain through `Dispatcher.setOutside`; the open ones among them reach the page in `ProjectOrder.outside`.
- Closed tasks reach the page two ways: those sharing a milestone with the project's open tasks (`TaskSource.chainTasks`), and those the chain itself started in the last 7 days by `state/launches.jsonl` (`ranSince` in `src/chain/launches.ts`, requested by ID on every tracker poll), so a task without a milestone does not vanish the moment it is closed.
- A project's `fillMilestone` (BTN-107, off by default, applied on the fly; `src/chain/milestones.ts`) gives a task that entered the chain without a milestone the active one, in the tracker (`setMilestone` of the adapter). The active milestone is the current task's; when the current task has none or there is no current task — the earliest by `compareMilestones` among the chain's tasks (`activeMilestone`). A chain without milestones is left alone, and its tasks get one when a milestone appears in it.
  - It runs after every task refresh (`refreshTasks` in `src/tracker/start.ts`, every 30 s) on `Dispatcher.view`, so a task moved to Todo gets its milestone within that time, whoever created it.
  - Once per stay in the chain: `MilestoneFiller` remembers in memory the tasks it has settled — filled, refused, or entered with a milestone — and does not come back to them, so a milestone a person changes or clears afterwards stays. A task that left the chain and re-entered, a restart of the service and turning the setting on start over: every chain task without a milestone counts as entering. A task outside the chain (Backlog) is never touched.
  - A blocker must not end up in a later milestone than the task it holds (`order.milestone`). Before each assignment the order is built (`chainOrder`) over the chain and its open blockers that may yet enter it (not parents or other projects' tasks) with the milestone applied; if it does not build, the task is left without a milestone. While the order does not build even without the assignment, nothing is assigned.
  - A tracker error leaves the task for the next refresh. An assignment is a line in the service log; the page shows it by the task's milestone after the next refresh. An adapter without `setMilestone` — one warning in the log per project.
- "Start" with nothing to run by the last task list (or before the first one) reads the project's tracker out of turn first (BTN-158, `DispatcherDeps.refresh` → `refreshProject` in `src/tracker/start.ts`, queued behind a read already under way), so a task created a moment before the click is taken. Still nothing — the start is refused with `chain.empty` and the reason as its cause (no open tasks, none in a status the chain takes, without a required label, all skipped, held by blockers), the same line goes to the log; the list never read — `chain.notRead`. A chain that ends later for want of tasks writes `chain: <KEY> ended, no task left to run` to the log.
- A task led by a session and returned to an inactive status stays in the chain while the session is mid-turn (`busy`), then drops out (`Dispatcher.enters`). The worktree cleanup happens only when the terminal status is of the `Won` category; a task that went to a terminal status of another category simply drops out.

## Order (`src/chain/order.ts`)

`blocks` blockers, then the saved order (`state/chain.json`), milestone, priority (Urgent → High → Medium → Low → none), task number. A new task is placed before the first task of its own or a lower priority, after more urgent ones (`withFresh`); the current task stays first.

## Task worktree (`src/git/worktree.ts`)

`main` in this document is the project's main branch: its `branch` key (BTN-117), `main` without it. Every git call takes it from the current config, so a change applies without a restart. A branch the repository lacks pauses the launch with `git.noBranch`, naming the branch and the project.

- Before the first launch for a task — in the project's main checkout (`config.projects[project]`) `git worktree add -b <key>-<number>/task .claude/worktrees/<key>-<number> main`, all lowercase. The branch tail is always `task`: the hooks in `~/.githooks` need the form `<key>-<number>/<something>`.
- If a worktree already exists at that path, it is taken as is, with its branch; if only the branch exists, it is brought back into a new worktree. `.claude/worktrees/` is appended to `.git/info/exclude` if git does not ignore it.
- The session starts with `cwd` = the worktree, and the prompt is the task ID, a line about the ready worktree and that there is no need to clean up (`startPrompt`).
- Commands before start (BTN-97, `commands.beforeStart` of the project, `src/sessions/setup.ts`): after the worktree or slot is ready and before the session starts, each runs in order through the system shell in the task's folder, with the session's environment (`envOf`), 20 min at most. Their output goes to the service log line by line (`setup: <task>: | …`); a non-zero exit stops the rest, the session is not started and the chain pauses with `setup.failed` and the last 40 lines of output. They run on every new launch of a task (a task the chain takes again runs them again), but not on `--resume`, a reply or a handoff.

## Cleanup after Done

- The current task went to Done (category `Won`; a cancelled or dropped one does not) — the chain's `closing`: wait until its session is not mid-turn (`busy`/`waiting`, and also `shell` — see "Background command" below), then `claude stop` its sessions in this worktree (otherwise a live process holds the folder: a `--bg` session does not exit after a turn, `claude agents` shows it `done`/`idle`), then in the clean worktree remove links and junctions in ignored folders (`node_modules` of npm workspaces, `npm link`: git on Windows follows them — it cleans someone else's folder or stumbles on a dangling one and abandons the worktree), then `git worktree remove` (without `--force`), `git branch -d` of the task branch (only `<key>-<number>/…`), `git push origin --delete` if it is on origin, and `git sync` if the project has a remote. The next task is started after that. A task returned from Done before the cleanup — no cleanup, the task is back in the chain.
- `git sync` is the `main` synchronization (`src/git/sync.ts`): if the repository has an `alias.sync` (`--local`), that one; the user's global alias only when the branch is named `main`, since such an alias is written for `main`; if not, Even Keel does it itself: the main checkout must stand on `main`, for each remote `git fetch` and `git merge --no-edit <remote>/main` (if it does not merge cleanly — `merge --abort` and an error), then `git push <remote> main` to each.
- A dirty worktree, a folder held by a process, an unmerged branch — a warning in the log and on the project page (`leftovers` in `state/chain.json`, the "Done" button — `chain/dismiss`), and the chain goes on. If `git sync` fails — likewise a warning with its output, the chain goes on, nothing is pushed by force: the next task takes the local `main`, and the next `git sync` after its Done will repeat the push.

- A parent closes by itself once all its subtasks are closed (adapters with `children`, `docs/trackers.md`); there is no cleanup in that case.

## Released tasks

A task that the chain started and released other than through Done — dropped out (became a parent: tasks with subtasks do not enter the chain; went to an inactive status), postponed by a blocker, skipped, or the chain was stopped or halted with an error — is remembered in `released` in `state/chain.json`. Even Keel asks the tracker for their statuses together with the chain's tasks (every 30 s); if one went to `Won` and its session is not mid-turn — the same cleanup as for the current one, but the chain does not wait for it and does not pause: a failed `git sync` is a warning in `leftovers`. If it went to a terminal status of another category, disappeared from the tracker or the chain took it again — it is forgotten.

## The CI of main (BTN-103, `src/chain/maincheck.ts`)

After a cleanup whose `git sync` succeeded (the current task or a released one), `MainCheck.pushed` reads the main checkout's `main` and remembers it as the push to check (`ci[<project>].check` in `state/chain.json`: commit, time, the tasks of the push). A new push while the previous one is awaited replaces its commit and adds its tasks to the previous ones. The CIs counted and the wait are the project's `ci` key (`docs/ci.md`); with `ci.guard: false` none of what follows happens — no wait, no check, no fix.

- **The wait.** The next launch of the project waits (`heldByMain`) while the push has no verdict and `waitMinutes` has not run out since the push (`null` — no limit, `0` — no wait). Meanwhile the chain is running with `ciWait = { commit, since }` (a yellow line on the card and the project page), and the next task's place is prepared ahead: `TaskPlaces.prepare` makes the worktree or slot and runs the commands before start once per task. A place made ahead stays detached at `main` (`ahead`): the task branch is made only at the launch, since its checkout is what starts the task in the tracker (a git hook moving it to In Progress) — a task the chain has not launched yet must not look started. A task that already has a branch gets it ahead as before. At the launch `TaskPlaces.ready` takes the same place (`at`: a slot prepared ahead is the task's while it is detached, dirty or not), makes the branch at its commit, brings it up to `main` with `merge --ff-only` if it has no commits or changes of its own (`catchUp`, so a task prepared during the wait starts from a fix that came meanwhile) and runs the commands again only if it moved, the preparation ahead failed or the launch had to take another slot. The project's own check of main (`readyAhead`) runs in that detached place too.
- **The verdict** (`src/ci/verdict.ts`, asked on every dispatcher tick; a CI change wakes the dispatcher): any failed run of the commit — red; a CI still at work — wait; a CI without a token, not answering or that did not take the commit within `STUCK_MS` (2 min, a busy runner extends it) — unavailable: the chain does not wait, and the commit stays unchecked with a line in the log unless the project has its own check, which then takes it (`docs/ci.md`, "The check without a CI"). A project with no counted CI (`none`) goes to its own check at once, without the wait. Right after the service starts it is a wait, not `none` or unavailable, until the service has found the projects' CIs (`MainCiDeps.watches` is `null`) and each CI has answered once (`checkedAt`): otherwise a push awaited across a restart would be dropped as unchecked and its red verdict never reach a fix. A cancelled or skipped run is not red. Green is remembered as `ci[<project>].green` — the base of the next fix task's commit list.
- **Red.** What broke is `redReport` (`src/ci/report.ts`): the failed jobs, the GitHub job log tail (Forgejo gives no logs — the run link), the commits since the last green one and the tasks of the push. Who fixes it is the project's `ci.fixTask` (`docs/ci.md`): off, the default — a session without a tracker task (below); on — a task. One automatic fix at a time, `ci[<project>].fix`, is the guard against recursion.
- **Red after the fix** (the push holds the fix) — the chain is halted with `ci.fixFailed` and no new fix is made. A project without an active chain (it ended while waiting) gets one, paused with the notice, out of the queue.
- **Commands after green** (`commands.afterGreen`, BTN-156, `docs/ci.md`). A green verdict starts them in the main checkout; while they run, `heldByMain` holds the next launch with `ciWait = { commit, since, after: true }` (its own yellow line), so a command that restarts Even Keel does not cut off the launch of the next session. The run lives in memory only (`MainCheck.afterGreenRun`): after a restart nothing waits, and the mark `ci[<project>].afterGreen` keeps the commands from running again. A fix session does not wait for them.

### The fix session (BTN-115, `src/chain/mainfix.ts`)

With `ci.fixTask` off nothing is created in the tracker, and the adapter needs no `create`.

- **The name** is `<KEY>-FIX` (`fixName`, `src/chain/fix.ts`), used wherever a task id is: the session name, `chain.current.task`, the launch log, the worktree `.claude/worktrees/<key>-fix` and the branch `<key>-fix/task`. The worktree is its own even in "slot" mode. The name never reaches the tracker: `held`, `released` and the tracker questions leave it out. The page tells the fixes apart as episodes `<KEY>-FIX.<n>` (`fixEpisodeId`; `fixTaskOf` turns one back into the name for commands to the service), see "The launch log of a fix" below.
- **The launch.** `MainCheck.red` writes `ci[<project>].fix = { task: <KEY>-FIX, at, commit, report }`, `report` being the session's prompt in `promptLanguage`; a report that cannot be built halts the chain with `ci.fixNotStarted` / `check.fixNotStarted`. While `report` is there (`MainCheck.sessionFix`) the fix goes before the chain's order and does not wait for the CI: `deps.launchFix` starts it with `fixPrompt` (the report, the worktree, the branch and the rules: no task, no task id in commits, merge into `main` yourself). A project with no active chain and not in the queue gets a chain with `fixOnly`, which ends with the fix; "Start" pressed meanwhile clears `fixOnly`, and the chain goes on with its tasks after the fix. A handoff of the fix session (limit, checkpoint, "New session") carries the report again (`withReport`).
- **Done** is not a tracker status: the session is not `busy` and its branch is in `main` with commits of its own (`branchMerged`) — a merge of another task that moves `main` does not close the fix. Then the usual cleanup and `git sync`; `report` is dropped (`MainCheck.fixLanded`), and the new push waits for its verdict like any other. A turn that ended with nothing merged (a question, an error) is invariant 1: the chain waits, the page shows the session.
- **The session it interrupts** (`MainFix.yields`, exception 7 to invariant 1). The fix is due while a task's session leads the chain: a session mid-turn (`busy`) is stopped (`claude stop`), the chain keeps `interrupted = { task, sessionId, since, at, commit }` and `current` is free for the fix. Not stopped: a session whose branch is already in `main`, and one that is not mid-turn — waiting on a question or idle — which is only set aside (`letGo`), like a task postponed by a blocker; it meets the fix at its own merge. Until the chain takes it again it is not the current task, so the chat window does not answer it (BTN-119): the page shows the chat locked with the reason (`docs/web.md`), Remote Control works as ever.
- **The continuation** (`MainFix.resume`) once the fix has landed, without waiting for the verdict on its push: `--resume` while the cache is warm, otherwise a new session with a handoff (`resume` and `relay` in the launch log, as after a limit), in both cases with `mainFixedPrompt` — the red commit, the commit `main` is on after the fix, "merge `main` into your branch and carry on". A task the user skipped or that left the chain meanwhile is released instead; a session the user already continued by hand is taken as it is.
- **Red after the fix** with an interrupted task: the halt as above, and the stopped session becomes the paused chain's current task again (`MainFix.giveBack`) — the user continues it from the chat window or with "New session".
- **Handover of the fix session** (a limit, a checkpoint, "New session") is the usual one plus the report from `ci[project].fix.report`, since there is no task to read it from (`Handovers.handOver`, `withReport`). Without the report it fails with `chain.fixReportMissing`, the chain halts and no session starts.
- **"Skip"** on the fix session (`Dispatcher.skip` → `MainFix.skip`, only while it is current and not `busy`): the fix is dropped, `main` stays as it is, the session is not touched; the interrupted task goes on with "the fix is not confirmed".
- **The launch log of a fix** (BTN-153, schema v3). The first launch of a fix keeps the red commit (`commit`), and the end of the fix is an entry of its own with `reason: 'landed'` (with `commit`, the commit `main` went out at) or `'dropped'` ("Skip", or the fix is no longer wanted while its session leads the chain) — `MainFix.ended`. `fixEpisodes` (`src/chain/launches.ts`) cuts the log into episodes: a launch with its handovers, resumes and answers up to its outcome; a launch for the same red commit stays in the episode, one for another commit with no outcome before it closes the previous one as `lost`. An outcome entry is not a launch (`isLaunch`): session lists, the stats and Tally's `launchMap` skip it. The state sends the episodes to the page in `fixes` (`EvenKeelState`).
- **The page.** `chainBlocks` (`web/src/state.ts`) adds a block for the fix ahead of the open tasks, with the usual panel (stage, action, context, chat); it has no task card and no tracker link and cannot be dragged. Its id is the open episode (`liveFixId`); `#ABC-FIX` in the URL leads to it. In place of its number and lamp the row has a forge (`web/src/pages/Forge.tsx`) in the lamp's colour: two smiths take turns with hammers on a red-hot ingot (the red main) while the session works and stand with hammers down by a cooling one otherwise; with `prefers-reduced-motion` — two crossed hammers. The interrupted task carries a chip.
- **A fix that is over** stays in the chain as a closed row among the closed tasks, by its end time, in the milestone of its neighbour: lamp `fixed` (purple, `--lamp-fix`), crossed hammers, the title "Fix main: <red> → <commit>" or "… — dropped". It goes into the archive like a closed task, and the archive counts it apart ("16 tasks · 1 fix"). With a CI the title links to the CI panel (`#ci/ABC-FIX.<n>`), which marks the runs of its red and landed commits and names the landed run's "Push tasks" as the fix, a link back to the row. Its panel holds the episode's sessions.

### The fix task (`ci.fixTask: true`)

- The text of the task is `redReport` in `language`, otherwise `promptLanguage`. If the chain's fix task is still open — the report is a comment on it and no new task is made. Otherwise `TaskSource.create` makes "CI on main failed: <commit>" in the ready status, priority high, the milestone of the push's last task. The chain is halted with `ci.cannotCreate` or `ci.fixNotCreated` when the adapter has no `create` or it fails.
- **The fix goes first**, before the chain's order, while it is open (`MainCheck.fixOf`). Until the tracker lists the new task the chain waits for it, up to `FIX_LISTED_MS` (5 min).
- A session already started (the wait ran out before a red verdict) is not touched (invariant 1): the red verdict only files the fix task, which the chain takes after the current one.

## Several chains (`parallel`, BTN-67)

- `parallel` in the config is how many chains of different projects run at once, 1 by default; applied on the fly. Active chains are `active` in `state/chain.json`, an array in launch order (the old form — a single object or `null` — is still read, `src/chain/store.ts`); the other projects are in `queue`.
- A paused chain also holds a place. When a chain ends or is stopped, the next project is taken from the queue at once, and the other chains go on. Lowering `parallel` stops nobody, and no new ones are taken until there are fewer active ones.
- Each chain has its own current task, pause, error, handoff and `closing`. "Resume", "Stop" (`chain/resume|stop` with `{ project }`) act on their own project. There is no manual pause: only the dispatcher itself pauses a chain on an error, it keeps its place and queue, and "Resume" retries. Stopping releases the task (its session keeps working, the cleanup is as for a released task) and frees the place.
- The account limit is shared and is not split between chains: all take tasks until the window is used up; once it is used up, all wait for the reset (`limitUntil` on each), and the continuation after the reset is per chain.
- Renewing the active account's sign-in is blocked by any chain that is not paused (`LoginBlock.chains`, `src/account/model.ts`). Switching the account is not: the session working now stays on its folder, the next launches go to the new one, as the roles menu says under "Even Keel" (`docs/accounts.md`).

## "Slot" mode (`src/git/slot.ts`)

- `"slot": true` or a number of slots on a project in `even-keel.config.json` — a pool of permanent worktrees per repository instead of a new one for each task: `.claude/worktrees/even-keel`, then `even-keel-2`, `even-keel-3`… (`true` — one). Ignored caches (Unity `Library`, `node_modules`) survive a task, and the first run of a new one processes only the difference; an extra slot is needed so that the live session of a released task (skipped, postponed by a blocker) stays in its own and is not stopped. The chain still leads one task at a time.
- Preparation: if a slot is already on the task's branch (`<key>-<number>/…`), it is used as is, even dirty. Otherwise, for each slot: a dirty one (`git status --porcelain` is not empty) or one with a session of another task mid-turn (`busy`/`waiting`, by the launch log, `src/sessions/occupants.ts`) is unfit. Of the fit ones, in order of preference: detached from a branch without foreign live sessions, on a foreign branch without them, not yet created (`git worktree add --detach <slot> main`), with idle sessions of other tasks — they get `claude stop` (the fifth exception to invariant 1); on a tie, the one with the lower number. If none is fit — a launch error, the chain is paused with the paths and reasons, and the slots are not touched. In unattended mode the chain is not paused: it stays running with `slotWait` (a yellow line with the same reasons on the page, one line in the service log) and tries the launch again at most every 30 s; the task is not released, since it never started. Then `git clean -fd` (without `-x`) and `git switch <branch>` or `git switch -c <branch> main`.
- After Done, a slot on the task's branch gets `git switch --detach main` (a dirty one stays on the branch, the branch is not deleted, a warning), then the branch, origin and `git sync`, as without a slot; the slot folder is not deleted. Slots on foreign branches (cleanup of a released task) are not touched, only the branch is deleted. `claude stop` after Done in a slot applies only to this task's sessions by the launch log.
- The number of slots changes on the fly (BTN-130); when it is reduced, Even Keel takes no new task into the extra folders, but still finds a busy task in one and cleans it after Done (`slotSpan` in `src/service.ts`: the most slots the project had since the start). A task's own worktree left over from the previous mode is taken and cleaned the old way.

## The exceptions to invariant 1 in detail

1. **Limit** on the session of the current task of an unpaused chain: after the limit resets or the account is switched, the dispatcher continues it via `--resume` if the cache is still warm (the same account, < 55 min since the last response), otherwise it stops it (`claude stop`, not `rm`) and starts a new one in its working folder with a handoff (`src/chain/relay.ts`). A limit is both the `rate_limit` error and the CLI's soft warning (`usageLimitNote: "wrap_up"`), after which the session wraps up its turn on its own. The reset time comes from the limit's text; the warning has none and comes before the window shows 100%, so it comes from the limits of the session's account polled after the limit (`limitResetAfter`, `src/limits/model.ts`): the exhausted window's reset, else the end of the five-hour window the limit fell into, or the start of a newer one. Until such limits arrive the reset is unknown (`resetsAt: null`, the page says only an account switch helps) and is asked for again on every check. The working folder and the branch for the handoff come from git (the worktree root from the last `cwd`), not from the transcript: its `gitBranch` is the branch of the launch folder. A repository nested in the launch folder that is not a worktree of the same repository (another common git dir — a clone the session made under `.temp/`) is skipped for the one around it (`locateWorktree`): otherwise the new session would start in the clone, and the CLI refuses a folder not trusted on its own. A session on an API account (`docs/accounts.md`) has no windows to wait out, so its `rate_limit` stops it like any error; what it is held on is a key out of credit (`billing_error`, `apiError.kind` `credit`, BTN-165). There the "reset" is the moment a check of the key finds credit again (`limitResetAfter` in `src/service.ts` asks `AccountWatcher.creditBackAfter`), and the cache is warm by the session's own cache lifetime (`warmCacheMs`, `LimitedSession.warmMs`): under 55 min with a 1-hour cache in the transcript, else under 4 min, since a key writes the 5-minute cache unless `cacheTtl` is `1h`. A switch of the account hands over at once, as on a limit.
2. **"New session"** (`restart`): the user replaces the session of the current task if it is not mid-turn — the same handoff, with `restart` in the log, referencing the previous session.
3. **Checkpoint** that the session set itself: the session of the current task of an unpaused chain finished a turn, and the last line of its last response is `CHECKPOINT: <path>` (that is what the hook of the `checkpoint@even-keel` plugin, `plugins/checkpoint`, asks for when the context has grown; its `Stop` hook sends back a session that wrote the note but ended with a report instead of the mark). The dispatcher does the same handoff, with the path to the note from the worktree root in the prompt and `checkpoint` in the log, referencing the previous session. A mark followed by a tool call, a new response without the mark, or a message to the session cancels it. The handoff repeats as many times as sessions ask for it; the number of handoffs per task is visible on the page, and after the third one the hook asks only from 300k (`docs/sessions.md`, "Checkpoint threshold"). A session with a limit goes by the limit rule (its prompt also points at the note), and while the limit is used up or new sessions are not started, the mark waits.
4. **Task in Done**: when its session has finished a turn and is not waiting for a reply (not `busy`/`waiting`), the dispatcher stops it (`claude stop`, not `rm`; the transcript stays, `--resume` by hand is possible) and removes the worktree. After the merge, sessions make no more than a couple of checks in the same turn and finish with a report (measured from transcripts, 2026-09-29).
5. **A slot is switched** to another task's branch (only when the pool has no free slot): the dispatcher first stops the live sessions of released tasks (skipped, postponed by a blocker) in the slot (`claude stop`, not `rm`), otherwise the answer to such a session through Remote Control would land in another task's branch. If such a session is mid-turn (`busy`/`waiting`), the slot is not switched and the chain is paused with its task (unattended — it waits for the slot the same way as when none is fit).
6. **The user's answer** (BTN-101) from the chat window (`POST /api/session/answer`, `docs/web.md`) or from tracker comments posted after the question Even Keel put there (`TrackerQuestions`, `docs/trackers.md`). A pending `AskUserQuestion` cannot be closed from outside, so the dispatcher stops the session (`claude stop`, not `rm`) and continues it via `--resume` with the answer; the stop loses the session's last message, which the CLI had not written yet, so the prompt repeats the question (`docs/sessions.md`) (`Dispatcher.answer` → `deliver`, the same path as after a limit; `answer` in the launch log, referencing the previous session; `resumedAt` is reset). `Dispatcher.answerable` refuses unless all hold: the task is the current one of its chain (`chain.notCurrent`) and is not being launched (`chain.launching`) — or the project's chain is stopped and the task's session lives on (the page marks such a row `loose` and keeps its chat; `Handovers.deliverLoose` resumes it and journals `answer`, a failure only goes to the log); the session is still the one the user answered and waits on the same open question (`ask` id, or none for a question in plain text) — otherwise `answer.moved` (say, the user already answered through Remote Control); it is not mid-turn (`answer.busy`); launches are allowed and the limit is not spent (`chain.limitSpent`). Files are saved first into `.temp/inbox/` of the task's folder (`src/sessions/inbox.ts`); the prompt is `replyPrompt` (`docs/sessions.md`).
7. **A red main** with `ci.fixTask` off (BTN-115): the session of the current task that is mid-turn is stopped (`claude stop`, not `rm`) so that it does not work on a broken `main`, and continued with a message once the fix session has landed — the only exception that stops a session mid-turn. A session that waits for an answer is not stopped: a new message would wipe its open question. In detail — "The fix session" above.

**A service restart in the middle of a move** (BTN-164). While the dispatcher resumes or replaces the session of a running task (exceptions 1–3 and 6), `CurrentTask` holds `starting`, the kind of move (`move`: `answer`, `resume`, `relay`, `restart`, `checkpoint`) and, for an answer, its text and the question it answers (`reply`, `ask`). Loading the state keeps them for a task with a session (a cut first launch is still dropped and pauses the chain with `chain.interrupted`), and the chain's next step sees the move through (`Handovers.recover`) before the limit and the checkpoint: no session of the task read yet — it waits; the task already has another session — the chain takes it and journals the move; the old session works, replied after the move began or waits on another question — the move went through (an answer or a resume is journaled); otherwise the move is made again — the answer delivered once more, "New session" repeated, the limit step redone, and a checkpoint left to its mark, which is still the last line. Within one process the step never sees these marks: moves and steps run one after another. The marks are transient like `answering`, so they did not change `SCHEMA_VERSION`.

In every exception a session `claude agents` shows `failed` or `stopped` is stopped as well while its process lives (`pid` from a live `sessions/<pid>.json`): a session that failed at start (an API 400) keeps running, and `claude stop` run from a terminal marks the job `stopped` without reaching the service's daemon (`isGone` in `src/claude/cli.ts`, `stopTaskSessions`, `slotOccupants`).

Every handoff (limit, "New session", checkpoint) leaves a snapshot `<state>/handoffs/<new session>.json` (`src/chain/snapshots.ts`): the whole prompt, the note's path and its text as read just before the launch, the reason in the launch log's words and the previous session. The note itself is overwritten by the next handoff and goes with the worktree; Tally loads the snapshots into `handoffs` (`tally/CLAUDE.md`). A failed save is a warning in the log, the handoff goes on.

The dispatcher may stop waiting for a session (without touching it) if it is not mid-turn (`busy`/`waiting`): the current task got an open blocker from the same chain (the session postponed it itself, `postpone` in the log) or the user pressed "Skip" (`skip`). The chain does not take a skipped task until the user returns it or it leaves the chain in the tracker (closed, in Backlog). "Skip" is refused for any task whose session is mid-turn, also one released by "Stop": otherwise a restarted chain would launch the next task beside it instead of taking the live session again.

## Unattended mode (`unattended`)

A switch on `/settings`, the Chain group — for when nobody is there to answer, for example at night. Stored in `state/chain.json` (`unattended`, the command `chain/unattended` with `{ on }`); when on, there is the banner `UnattendedBanner`.

- `PROMPTS.unattended` (`src/chain/prompts.ts`) is appended to every prompt — launch, `--resume`, handoff: ask no questions, do everything that the question does not hold up; a question with a default option — as usual (finish and merge, the question as a task); a task that cannot be finished without an answer — commit it to its branch until `git status` is clean, do not merge, put the question with options in a comment, add the question label, and as the last step move to Backlog (the post-commit hook moves the status forward, so after the commit and with a check). Sessions started before it was turned on do not get the text — only with the nearest `--resume` or handoff.
- A task in Backlog drops out of the chain like any returned to an inactive status: it is released, and the worktree or slot with its branch stays. A clean tree matters in "slot" mode: a dirty slot is not taken, and a couple of parked tasks with litter would stop the chain.
- A safeguard in the dispatcher (`Dispatcher.unanswered`): the session of the current task finished a turn or is waiting for a reply (not `busy`), without a limit or checkpoint, and 10 minutes of silence — counted from the last response, from when the chain took the task, and from the last `--resume` or handover by a checkpoint or "New session" (`resumedAt`), whichever is later — the task is skipped, as with the "Skip" button (`skip` in the log). The dispatcher does not touch the session. So the night does not stand still if the session did ask or a hook returned the status. A merged task goes to Done within seconds, and the 10 minutes do not touch it.
- The chain also does not wait for a task in Done (`closing`) longer than 10 quiet minutes (`Dispatcher.quietTooLong`, from the session's last response): the task goes to `released`, its cleanup is done by the released-task sweep when the session is not mid-turn, and the chain goes on. The dispatcher does not touch the session.
- **Background command.** The CLI writes the status `shell` into `sessions/<pid>.json` when the turn is over but a background command started by the session (`run_in_background`) is still running; when it ends, the session gets a notification and continues. For the chain such a session is mid-turn (`turnStatus`, `src/sessions/agents.ts`): a long run of 15–20 minutes is neither skipped nor cleaned up. An hour without a new line in the transcript — the command counts as hung, the session as idle. A turn that ended on a limit is the exception: the session is idle and goes by the limit rule at once (the lamp is `limit`), otherwise a command that never ends, a dev server, would hold the chain for good. A slot with a session in `shell` is always occupied.

## State files and the schema version (BTN-132)

Since BTN-147 the chain state, the questions, the launch log and the handoff snapshots are in the state database (`state/even-keel.db`, `docs/storage.md`); the files below are what v0.1 kept and what the first start of the new version imports. The config, `account.json`, `packages.json`, `rate-limits.json` and `codex/` stay files.

- A project has a key (the tracker's, `ABC`) and an id (`projects[].id`, a GUID that never changes). The state names a project by its id: the database (`project_id` of its tables) and before it `state/chain.json` (`active[].project`, `queue`, the keys of `orders`, `skipped`, `leftovers`, `released`, `ci`) and `state/launches.jsonl` (`project`). The running service, the tracker, task IDs, branches and worktrees go by the key; `src/chain/store.ts` translates at the edge with `config.ids` (key → id), and an id the config does not have — a removed project — stays as it is.
- Every file carries the schema version (`SCHEMA_VERSION`, `src/storage/schema.ts`): `version` in the config, `chain.json`, `questions.json` (`{ version, questions }`), `account.json`, and the first line `{"version":<N>}` of `launches.jsonl`. A file newer than the code is refused (`storage.newer`). The database has its own version (`PRAGMA user_version`, `docs/storage.md`).
- `upgradeStorage` (`src/storage/migrations.ts`) runs in `src/main.ts` before `src/service.ts` is imported: it reads all the files, migrates them step by step to the current version, checks the config with `parseConfig`, keeps `<file>.v<N>.bak` copies and writes all of them, restoring the written ones if a write fails. It also writes an id into a project entry added by hand without one. Any refusal (`storage.newer`, `storage.damaged`, `storage.unknownProject` — a project of the state the config lacks, `storage.writeFailed`) starts only the blocked page server (`createBlockedServer`, `src/server.ts`): the page from `dist/web`, `/api/events` sends `blocked` with the reason, the rest of `/api` is 503. Right after it `prepareDatabase` brings the database to its schema or imports the files into it; its refusals (`storage.newerDatabase`, `storage.importFailed`) block the same way.
- A format change is a new schema version, a migration step and a new frozen sample in `test/fixtures/schema-v<N>/` (`src/storage/fixtures.test.ts`); old steps and samples are never edited or removed.
- Schema v8 (BTN-173, run profiles, `docs/sessions.md`): `configV8` turns a project's `agent` into `provider` and `codexModel` into `models.codex`, the shared `model` into `models.claude`, a project's `codexBypassSandbox` (any project on) into the shared `execution.codex: "bypass"`, and moves `active` of `state/account.json` into the shared `accounts.claude`. A launch log entry may carry `fallback` — the provider of the task's run label the pool had no account for (`fallbacksSince` gives the page the last 24 hours of them).
