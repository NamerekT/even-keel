# Chain

Reference for sessions: entry into the chain, order, task worktrees, cleanup and the details of the exceptions to invariant 1. The invariants themselves are in `CLAUDE.md`.

## Entry into the chain

- The rules are `chain` in `even-keel.config.json` (`src/chain/rules.ts`): a global top-level one and a project's own on top of it (a project is a path string or `{ "repo", "chain" }`; the project key replaces the global one entirely).
- `active` and `terminal` are status names (case-insensitive, whitespace trimmed); without the key, by category: active are `ToDo` and `Active`, terminal are `Won` and `Lost`. A name that Huly does not have is a warning in the log; a status in both lists is a config error.
- `requiredLabels` — at least one of them is needed (empty — not needed), `excludedLabels` (`["Manual", "Вручную"]` by default) removes a task altogether, the user starts it themselves. A task that fails the label rules is cut off in the same place as closed ones (`Dispatcher.setTasks`), but as an open blocker it still holds a chain task (below).
- By default the chain includes tasks in Todo and beyond: Backlog (category `UnStarted`) is a store of ideas, neither active nor terminal, and the chain does not take it. A move to an active status lets a task into the chain.
- The backlog for the page (`ProjectOrder.backlog`) is open tasks outside the chain by status or without the needed label, except locked blockers and tasks with an excluding label. The progress on the card counts only closed tasks and the chain, with the backlog in a separate caption; on the project page it is a chip in the header that opens the backlog in the side panel (`#backlog` in the address, the same place as the session panel). `ProjectOrder.landing` says where each backlog task the label rules admit would stand once it is active: the chain task it would precede, `null` for the end (`Dispatcher.landing` places it with `[...chain, task]` the way a new task is placed); the page shows a ghost there.
- An open blocker outside the chain — in an inactive status, with an excluding label (a manual task, a question), without a needed one, a parent or a task of another project (BTN-68, `waitingBlockers` in `src/chain/order.ts`, and further by its blockers of the same kind) — holds a chain task: it is not started, and the current one with such a blocker is postponed (`postpone`), as with a blocker from the chain; if all tasks hold such blockers, the chain ends. The page shows it (`ProjectOrder.waiting`) in front of the task it holds (`withWaiting`), dimmed and locked: without a number, buttons or dragging, the link goes to the task in the tracker. Moved to an active status — it is an ordinary chain task; closed — the task is free. Blockers that are not among the project's open tasks (parents, other projects, closed ones) are requested by ID on every tracker poll (`tracker.tasks`) and handed to the chain through `Dispatcher.setOutside`; the open ones among them reach the page in `ProjectOrder.outside`.
- Closed tasks reach the page two ways: those sharing a milestone with the project's open tasks (`TaskSource.chainTasks`), and those the chain itself started in the last 7 days by `state/launches.jsonl` (`ranSince` in `src/chain/launches.ts`, requested by ID on every tracker poll), so a task without a milestone does not vanish the moment it is closed.
- A task led by a session and returned to an inactive status stays in the chain while the session is mid-turn (`busy`), then drops out (`Dispatcher.enters`). The worktree cleanup happens only when the terminal status is of the `Won` category; a task that went to a terminal status of another category simply drops out.

## Order (`src/chain/order.ts`)

`blocks` blockers, then the saved order (`state/chain.json`), milestone, priority (Urgent → High → Medium → Low → none), task number. A new task is placed before the first task of its own or a lower priority, after more urgent ones (`withFresh`); the current task stays first.

## Task worktree (`src/git/worktree.ts`)

- Before the first launch for a task — in the project's main checkout (`config.projects[project]`) `git worktree add -b <key>-<number>/task .claude/worktrees/<key>-<number> main`, all lowercase. The branch tail is always `task`: the hooks in `~/.githooks` need the form `<key>-<number>/<something>`.
- If a worktree already exists at that path, it is taken as is, with its branch; if only the branch exists, it is brought back into a new worktree. `.claude/worktrees/` is appended to `.git/info/exclude` if git does not ignore it.
- The session starts with `cwd` = the worktree, and the prompt is the task ID, a line about the ready worktree and that there is no need to clean up (`startPrompt`).
- Commands before start (BTN-97, `commands.beforeStart` of the project, `src/sessions/setup.ts`): after the worktree or slot is ready and before the session starts, each runs in order through the system shell in the task's folder, with the session's environment (`envOf`), 20 min at most. Their output goes to the service log line by line (`setup: <task>: | …`); a non-zero exit stops the rest, the session is not started and the chain pauses with `setup.failed` and the last 40 lines of output. They run on every new launch of a task (a task the chain takes again runs them again), but not on `--resume`, a reply or a handoff.

## Cleanup after Done

- The current task went to Done (category `Won`; a cancelled or dropped one does not) — the chain's `closing`: wait until its session is not mid-turn (`busy`/`waiting`, and also `shell` — see "Background command" below), then `claude stop` its sessions in this worktree (otherwise a live process holds the folder: a `--bg` session does not exit after a turn, `claude agents` shows it `done`/`idle`), then in the clean worktree remove links and junctions in ignored folders (`node_modules` of npm workspaces, `npm link`: git on Windows follows them — it cleans someone else's folder or stumbles on a dangling one and abandons the worktree), then `git worktree remove` (without `--force`), `git branch -d` of the task branch (only `<key>-<number>/…`), `git push origin --delete` if it is on origin, and `git sync` if the project has a remote. The next task is started after that. A task returned from Done before the cleanup — no cleanup, the task is back in the chain.
- `git sync` is the `main` synchronization (`src/git/sync.ts`): if the repository or the user has an `alias.sync`, that one; if not, Even Keel does it itself: the main checkout must stand on `main`, for each remote `git fetch` and `git merge --no-edit <remote>/main` (if it does not merge cleanly — `merge --abort` and an error), then `git push <remote> main` to each.
- A dirty worktree, a folder held by a process, an unmerged branch — a warning in the log and on the project page (`leftovers` in `state/chain.json`, the "Done" button — `chain/dismiss`), and the chain goes on. If `git sync` fails — likewise a warning with its output, the chain goes on, nothing is pushed by force: the next task takes the local `main`, and the next `git sync` after its Done will repeat the push.

- A parent closes by itself once all its subtasks are closed (adapters with `children`, `docs/trackers.md`); there is no cleanup in that case.

## Released tasks

A task that the chain started and released other than through Done — dropped out (became a parent: tasks with subtasks do not enter the chain; went to an inactive status), postponed by a blocker, skipped, or the chain was stopped or halted with an error — is remembered in `released` in `state/chain.json`. Even Keel asks the tracker for their statuses together with the chain's tasks (every 30 s); if one went to `Won` and its session is not mid-turn — the same cleanup as for the current one, but the chain does not wait for it and does not pause: a failed `git sync` is a warning in `leftovers`. If it went to a terminal status of another category, disappeared from the tracker or the chain took it again — it is forgotten.

## The CI of main (BTN-103, `src/chain/maincheck.ts`)

After a cleanup whose `git sync` succeeded (the current task or a released one), `MainCheck.pushed` reads the main checkout's `main` and remembers it as the push to check (`ci[<project>].check` in `state/chain.json`: commit, time, the tasks of the push). A new push while the previous one is awaited replaces its commit and adds its tasks to the previous ones. The CIs counted and the wait are the project's `ci` key (`docs/ci.md`).

- **The wait.** The next launch of the project waits (`heldByMain`) while the push has no verdict and `waitMinutes` has not run out since the push (`null` — no limit, `0` — no wait). Meanwhile the chain is running with `ciWait = { commit, since }` (a yellow line on the card and the project page), and the next task's place is prepared ahead: `TaskPlaces.prepare` makes the worktree or slot and runs the commands before start once per task. At the launch `TaskPlaces.ready` brings that place up to `main` with `merge --ff-only` if it has no commits or changes of its own (`catchUp`, so a task prepared during the wait starts from a fix that came meanwhile) and runs the commands again only if it moved or the preparation ahead failed.
- **The verdict** (`src/ci/verdict.ts`, asked on every dispatcher tick; a CI change wakes the dispatcher): any failed run of the commit — red; a CI still at work — wait; a CI without a token, not answering or that did not take the commit within `STUCK_MS` (2 min, a busy runner extends it) — unavailable: the chain does not wait, and the commit stays unchecked with a line in the log unless the project has its own check, which then takes it (`docs/ci.md`, "The check without a CI"). A project with no counted CI (`none`) goes to its own check at once, without the wait. A cancelled or skipped run is not red. Green is remembered as `ci[<project>].green` — the base of the next fix task's commit list.
- **Red.** The text of the fix task is `redReport` (`src/ci/report.ts`) in `language`, otherwise `promptLanguage`: the failed jobs, the GitHub job log tail (Forgejo gives no logs — the run link), the commits since the last green one and the tasks of the push. If the chain's fix task (`ci[<project>].fix`) is still open — the report is a comment on it and no new task is made: one automatic fix task at a time, that is the guard against recursion. Otherwise `TaskSource.create` makes "CI on main failed: <commit>" in the ready status, priority high, the milestone of the push's last task.
- **The fix goes first**, before the chain's order, while it is open (`MainCheck.fixOf`). Until the tracker lists the new task the chain waits for it, up to `FIX_LISTED_MS` (5 min).
- **Red after the fix** (the push holds the fix task) — the chain is halted with `ci.fixFailed` and no task is made. The same halt, with `ci.cannotCreate` or `ci.fixNotCreated`, when the adapter has no `create` or it fails. A project without an active chain (it ended while waiting) gets one, paused with the notice, out of the queue.
- A session already started (the wait ran out before a red verdict) is not touched (invariant 1): the red verdict only files the fix task, which the chain takes after the current one.

## Several chains (`parallel`, BTN-67)

- `parallel` in the config is how many chains of different projects run at once, 1 by default; applied on the fly. Active chains are `active` in `state/chain.json`, an array in launch order (the old form — a single object or `null` — is still read, `src/chain/store.ts`); the other projects are in `queue`.
- A paused chain also holds a place. When a chain ends or is stopped, the next project is taken from the queue at once, and the other chains go on. Lowering `parallel` stops nobody, and no new ones are taken until there are fewer active ones.
- Each chain has its own current task, pause, error, handoff and `closing`. "Resume", "Stop" (`chain/resume|stop` with `{ project }`) act on their own project. There is no manual pause: only the dispatcher itself pauses a chain on an error, it keeps its place and queue, and "Resume" retries. Stopping releases the task (its session keeps working, the cleanup is as for a released task) and frees the place.
- The account limit is shared and is not split between chains: all take tasks until the window is used up; once it is used up, all wait for the reset (`limitUntil` on each), and the continuation after the reset is per chain.
- Renewing the active account's sign-in is blocked by any chain that is not paused (`LoginBlock.chains`, `src/account/model.ts`). Switching the account is not: the session working now stays on its folder, the next launches go to the new one, and the accounts panel warns with the list of running chains.

## "Slot" mode (`src/git/slot.ts`)

- `"slot": true` or a number of slots on a project in `even-keel.config.json` — a pool of permanent worktrees per repository instead of a new one for each task: `.claude/worktrees/even-keel`, then `even-keel-2`, `even-keel-3`… (`true` — one). Ignored caches (Unity `Library`, `node_modules`) survive a task, and the first run of a new one processes only the difference; an extra slot is needed so that the live session of a released task (skipped, postponed by a blocker) stays in its own and is not stopped. The chain still leads one task at a time.
- Preparation: if a slot is already on the task's branch (`<key>-<number>/…`), it is used as is, even dirty. Otherwise, for each slot: a dirty one (`git status --porcelain` is not empty) or one with a session of another task mid-turn (`busy`/`waiting`, by the launch log, `src/sessions/occupants.ts`) is unfit. Of the fit ones, in order of preference: detached from a branch without foreign live sessions, on a foreign branch without them, not yet created (`git worktree add --detach <slot> main`), with idle sessions of other tasks — they get `claude stop` (the fifth exception to invariant 1); on a tie, the one with the lower number. If none is fit — a launch error, the chain is paused with the paths and reasons, and the slots are not touched. In unattended mode the chain is not paused: it stays running with `slotWait` (a yellow line with the same reasons on the page, one line in the service log) and tries the launch again at most every 30 s; the task is not released, since it never started. Then `git clean -fd` (without `-x`) and `git switch <branch>` or `git switch -c <branch> main`.
- After Done, a slot on the task's branch gets `git switch --detach main` (a dirty one stays on the branch, the branch is not deleted, a warning), then the branch, origin and `git sync`, as without a slot; the slot folder is not deleted. Slots on foreign branches (cleanup of a released task) are not touched, only the branch is deleted. `claude stop` after Done in a slot applies only to this task's sessions by the launch log.
- The number of slots changes after a restart; when it is reduced, Even Keel no longer takes or cleans the extra folders. A task's own worktree left over from the previous mode is taken and cleaned the old way.

## The exceptions to invariant 1 in detail

1. **Limit** on the session of the current task of an unpaused chain: after the limit resets or the account is switched, the dispatcher continues it via `--resume` if the cache is still warm (the same account, < 55 min since the last response), otherwise it stops it (`claude stop`, not `rm`) and starts a new one in its working folder with a handoff (`src/chain/relay.ts`). A limit is both the `rate_limit` error and the CLI's soft warning (`usageLimitNote: "wrap_up"`), after which the session wraps up its turn on its own. The working folder and the branch for the handoff come from git (the worktree root from the last `cwd`), not from the transcript: its `gitBranch` is the branch of the launch folder.
2. **"New session"** (`restart`): the user replaces the session of the current task if it is not mid-turn — the same handoff, with `restart` in the log, referencing the previous session.
3. **Checkpoint** that the session set itself: the session of the current task of an unpaused chain finished a turn, and the last line of its last response is `CHECKPOINT: <path>` (that is what the hook of the `checkpoint@even-keel` plugin, `plugins/checkpoint`, asks for when the context has grown; its `Stop` hook sends back a session that wrote the note but ended with a report instead of the mark). The dispatcher does the same handoff, with the path to the note from the worktree root in the prompt and `checkpoint` in the log, referencing the previous session. A mark followed by a tool call, a new response without the mark, or a message to the session cancels it. The handoff repeats as many times as sessions ask for it; the number of handoffs per task is visible on the page, and after the third one the hook asks only from 300k (`docs/sessions.md`, "Checkpoint threshold"). A session with a limit goes by the limit rule (its prompt also points at the note), and while the limit is used up or new sessions are not started, the mark waits.
4. **Task in Done**: when its session has finished a turn and is not waiting for a reply (not `busy`/`waiting`), the dispatcher stops it (`claude stop`, not `rm`; the transcript stays, `--resume` by hand is possible) and removes the worktree. After the merge, sessions make no more than a couple of checks in the same turn and finish with a report (measured from transcripts, 2026-09-29).
5. **A slot is switched** to another task's branch (only when the pool has no free slot): the dispatcher first stops the live sessions of released tasks (skipped, postponed by a blocker) in the slot (`claude stop`, not `rm`), otherwise the answer to such a session through Remote Control would land in another task's branch. If such a session is mid-turn (`busy`/`waiting`), the slot is not switched and the chain is paused with its task (unattended — it waits for the slot the same way as when none is fit).
6. **The user's answer** (BTN-101) from the chat window (`POST /api/session/answer`, `docs/web.md`) or from tracker comments posted after the question Even Keel put there (`TrackerQuestions`, `docs/trackers.md`). A pending `AskUserQuestion` cannot be closed from outside, so the dispatcher stops the session (`claude stop`, not `rm`) and continues it via `--resume` with the answer (`Dispatcher.answer` → `deliver`, the same path as after a limit; `answer` in the launch log, referencing the previous session; `resumedAt` is reset). `Dispatcher.answerable` refuses unless all hold: the task is the current one of its chain (`chain.notCurrent`) and is not being launched (`chain.launching`); the session is still the one the user answered and waits on the same open question (`ask` id, or none for a question in plain text) — otherwise `answer.moved` (say, the user already answered through Remote Control); it is not mid-turn (`answer.busy`); launches are allowed and the limit is not spent (`chain.limitSpent`). Files are saved first into `.temp/inbox/` of the task's folder (`src/sessions/inbox.ts`); the prompt is `replyPrompt` (`docs/sessions.md`).

In every exception a session `claude agents` shows `failed` or `stopped` is stopped as well while its process lives (`pid` from a live `sessions/<pid>.json`): a session that failed at start (an API 400) keeps running, and `claude stop` run from a terminal marks the job `stopped` without reaching the service's daemon (`isGone` in `src/sessions/claude.ts`, `stopTaskSessions`, `slotOccupants`).

Every handoff (limit, "New session", checkpoint) leaves a snapshot `<state>/handoffs/<new session>.json` (`src/chain/snapshots.ts`): the whole prompt, the note's path and its text as read just before the launch, the reason in the launch log's words and the previous session. The note itself is overwritten by the next handoff and goes with the worktree; Tally loads the snapshots into `handoffs` (`tally/CLAUDE.md`). A failed save is a warning in the log, the handoff goes on.

The dispatcher may stop waiting for a session (without touching it) if it is not mid-turn (`busy`/`waiting`): the current task got an open blocker from the same chain (the session postponed it itself, `postpone` in the log) or the user pressed "Skip" (`skip`). The chain does not take a skipped task until the user returns it or it leaves the chain in the tracker (closed, in Backlog). "Skip" is refused for any task whose session is mid-turn, also one released by "Stop": otherwise a restarted chain would launch the next task beside it instead of taking the live session again.

## Unattended mode (`unattended`)

A switch in the status menu (the gear, `SystemMenu`) — for when nobody is there to answer, for example at night. Stored in `state/chain.json` (`unattended`, the command `chain/unattended` with `{ on }`); when on, there is the banner `UnattendedBanner`.

- `PROMPTS.unattended` (`src/chain/prompts.ts`) is appended to every prompt — launch, `--resume`, handoff: ask no questions, do everything that the question does not hold up; a question with a default option — as usual (finish and merge, the question as a task); a task that cannot be finished without an answer — commit it to its branch until `git status` is clean, do not merge, put the question with options in a comment, add the question label, and as the last step move to Backlog (the post-commit hook moves the status forward, so after the commit and with a check). Sessions started before it was turned on do not get the text — only with the nearest `--resume` or handoff.
- A task in Backlog drops out of the chain like any returned to an inactive status: it is released, and the worktree or slot with its branch stays. A clean tree matters in "slot" mode: a dirty slot is not taken, and a couple of parked tasks with litter would stop the chain.
- A safeguard in the dispatcher (`Dispatcher.unanswered`): the session of the current task finished a turn or is waiting for a reply (not `busy`), without a limit or checkpoint, and 10 minutes of silence — counted from the last response, from when the chain took the task, and from the last `--resume` or handover by a checkpoint or "New session" (`resumedAt`), whichever is later — the task is skipped, as with the "Skip" button (`skip` in the log). The dispatcher does not touch the session. So the night does not stand still if the session did ask or a hook returned the status. A merged task goes to Done within seconds, and the 10 minutes do not touch it.
- The chain also does not wait for a task in Done (`closing`) longer than 10 quiet minutes (`Dispatcher.quietTooLong`, from the session's last response): the task goes to `released`, its cleanup is done by the released-task sweep when the session is not mid-turn, and the chain goes on. The dispatcher does not touch the session.
- **Background command.** The CLI writes the status `shell` into `sessions/<pid>.json` when the turn is over but a background command started by the session (`run_in_background`) is still running; when it ends, the session gets a notification and continues. For the chain such a session is mid-turn (`turnStatus`, `src/sessions/agents.ts`): a long run of 15–20 minutes is neither skipped nor cleaned up. An hour without a new line in the transcript — the command counts as hung, the session as idle. A turn that ended on a limit is the exception: the session is idle and goes by the limit rule at once (the lamp is `limit`), otherwise a command that never ends, a dev server, would hold the chain for good. A slot with a session in `shell` is always occupied.
