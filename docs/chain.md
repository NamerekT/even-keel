# Chain

Reference for sessions: entry into the chain, order, task worktrees, cleanup and the details of the exceptions to invariant 1. The invariants themselves are in `CLAUDE.md`.

`chainOrder` keeps the ready tasks sorted by saved order, milestone, priority and number. It sorts the initial ready list once and inserts newly unblocked tasks by binary search, rather than scanning and comparing every ready task again for each result. This matters on the page too: `closedOrder` uses it to order the archive. A regression test bounds collation calls for a large independent archive (BTN-515).

## Entry into the chain

- The rules are the `chain` setting (`src/chain/rules.ts`): a global top-level one and a project's own on top of it (a project is a path string or `{ "repo", "chain" }`; the project key replaces the global one entirely). Between them sit the rules of the tracker profile the project — or, for a feed's task, the feed — runs on (BTN-66, `rulesWith`/`projectRules` in `src/profiles/rules.ts`, `docs/settings.md`): `active`, `terminal`, `requiredLabels`, `excludedLabels`, each key the project's own, else the profile's, else the shared one. A profile save that would make a project or feed on it clash is refused; a clash made later by a project's own change leaves the profile's rules out, with one line in the log while it lasts. The page shows these lists by what they are about — a place per status, a rule per label, where each comes from (BTN-334, `docs/web.md`) — and stores them as the same lists.
- `active` and `terminal` are status names (case-insensitive, whitespace trimmed); without the key, by category: active are `ToDo` and `Active`, terminal are `Won` and `Lost`. A name that Huly does not have is a warning in the log; a status in both lists is a config error.
- `requiredLabels` — at least one of them is needed (empty — not needed), `excludedLabels` (`["Manual", "Вручную"]` by default) removes a task altogether, the user starts it themselves. A task with an excluding label is cut off in the same place as closed ones (`Dispatcher.setTasks`); an open task that lacks only a required label waits in the backlog (below) — on GitHub and GitLab, which have no backlog status, that label is the whole line between the backlog and the chain (BTN-509). Either kind, as an open blocker, still holds a chain task (below).
- "Into the chain" (`TaskControl.ready`, `src/tracker/control.ts`) puts the first required label on a task that has none of them (`missingLabel` in `src/chain/rules.ts`, through the tracker's `relabel`) and moves an `UnStarted` task to Todo where the tracker has `ready`; the button stands when the tracker can do at least what this task needs (`ProjectOrder.requiredLabel`: `false` — the task lacks the label). "To the backlog" (`TaskControl.unready`) mirrors it: takes the required labels off (`requiredOn`) and moves the task to the first `UnStarted` status where the tracker has `unready` (Huly, Linear, Jira). It is refused for a task with a live session (`task.unreadyLive`): that would be a new way to touch a session (invariant 1). Both put the task's new state in at once, without waiting for a poll. On a public repository every open issue, an outsider's too, lands in the backlog; only people with triage rights can label it, so entry into the chain stays the user's decision.
- By default the chain includes tasks in Todo and beyond: Backlog (category `UnStarted`) is a store of ideas, neither active nor terminal, and the chain does not take it. A move to an active status lets a task into the chain.
- The backlog for the page (`ProjectOrder.backlog`) is open tasks outside the chain by status or without the needed label, except locked blockers and tasks with an excluding label. The progress on the card counts only closed tasks and the chain, with the backlog in a separate caption; on the project page it is a chip in the header that opens the backlog in the side panel (`#backlog` in the address, the same place as the session panel). `ProjectOrder.landing` says where each backlog task and each of the project's own locked blockers (not parents or other projects' tasks) the excluding labels let in would stand once it is active and carries a required label: the chain task it would precede, `null` for the end (`TaskLists.landing` in `src/chain/lists.ts` places it with `[...chain, task]` the way a new task is placed); the page shows a ghost there for a backlog task. Where that order does not build, the task is in `ProjectOrder.refused` with the reason instead, and every "Into the chain" of it (backlog panel, card, locked row) is off with that reason as its title: taking it would halt the chain.
- The order does not build when blockers form a cycle (`order.cycle`), a task is blocked by one from a later milestone (`order.later`), or blockers go against the milestone order through tasks without one (`order.against`). The chain then halts (`halt`: paused with the notice), and the page shows the notice and the open tasks by number, without locks. A blocker from a later milestone that waits in the backlog holds its task quietly, filed on the page under the held task's milestone; only its move to Todo would halt the chain, which `refused` prevents from the page — not from the tracker.
- An open blocker outside the chain — in an inactive status, with an excluding label (a manual task, a question), without a needed one, a parent or a task of another project (BTN-68, `waitingBlockers` in `src/chain/order.ts`, and further by its blockers of the same kind) — holds a chain task: it is not started, and the current one with such a blocker is postponed (`postpone`), as with a blocker from the chain; if all tasks hold such blockers, the chain ends. The page shows it (`ProjectOrder.waiting`) in front of the task it holds (`withWaiting`), dimmed and locked: without a number or dragging, the key goes to the task in the tracker and the title opens its card. In place of the number, a blocker with a `landing` or `refused` entry in the backlog status (`UnStarted`) of a tracker that can move it has the "Into the chain" button (`readyButton` in `web/src/state.ts`). Moved to an active status — it is an ordinary chain task; closed — the task is free. Blockers that are not among the project's open tasks (parents, other projects, closed ones) are requested by ID on every tracker poll (`tracker.tasks`) and handed to the chain through `Dispatcher.setOutside`; the open ones among them reach the page in `ProjectOrder.outside`.
- Closed tasks reach the page three ways: those sharing a milestone with the project's open tasks (`TaskSource.chainTasks`); those the chain itself started in the last 7 days by the launch log (`ranSince` in `src/chain/launches.ts`, requested by ID on every tracker poll, each from the profile it was launched through), so a task without a milestone does not vanish the moment it is closed; and those of the archive closed in the last 7 days that no tracker gives any more — a feed or a profile removed, a task deleted (`archivedShown`, BTN-66, `docs/storage.md`).
- A project's `fillMilestone` (BTN-107, off by default, applied on the fly; `src/chain/milestones.ts`) gives a task that entered the chain without a milestone the active one, in the tracker (`setMilestone` of the adapter). The active milestone is the current task's; when the current task has none or there is no current task — the earliest by `compareMilestones` among the chain's tasks (`activeMilestone`). A chain without milestones is left alone, and its tasks get one when a milestone appears in it.
  - It runs before a new task list reaches the chain — every task refresh (`refreshTasks` in `src/tracker/start.ts`, every 30 s) and every status change the 5 s status poll sees, the latter queued behind the project's read — on the view that list would give (`Dispatcher.preview`, the lists untouched). So a task moved to Todo, whoever moved it, enters the chain and the page already in its milestone, never first without one. The page's "Into the chain" reads the project anew instead of patching the status for the same reason.
  - Once per stay in the chain: `MilestoneFiller` remembers in memory the tasks it has settled — filled, refused, or entered with a milestone — and does not come back to them, so a milestone a person changes or clears afterwards stays. A task that left the chain and re-entered, a restart of the service and turning the setting on start over: every chain task without a milestone counts as entering. A task outside the chain (Backlog) is never touched.
  - A blocker must not end up in a later milestone than the task it holds (`order.milestone`). Before each assignment the order is built (`chainOrder`) over the chain and its open blockers that may yet enter it (not parents or other projects' tasks) with the milestone applied; if it does not build, the task is left without a milestone. While the order does not build even without the assignment, nothing is assigned.
  - A tracker error leaves the task for the next refresh. A successful assignment puts the donor's full milestone into the list before it is set, without another tracker read. An adapter without `setMilestone` — one warning in the log per project.
  - The landing preview uses the same donor and order check (`milestoneCandidate`): `ProjectOrder.landingMilestones` carries the milestone the task would get, so its ghost joins that milestone's section. If filling would break the order over the chain and its open blockers, the preview keeps the task without a milestone. A task that already has a milestone and a project with filling off keep their existing preview.
- "Start" with nothing to run by the last task list (or before the first one) reads the project's tracker out of turn first (BTN-158, `DispatcherDeps.refresh` → `refreshProject` in `src/tracker/start.ts`, queued behind a read already under way), so a task created a moment before the click is taken. Still nothing — the start is refused with `chain.empty` and the reason as its cause (no open tasks, none in a status the chain takes, without a required label, all skipped, held by blockers), the same line goes to the log; the list never read — `chain.notRead`. A chain that ends later for want of tasks writes `chain: <KEY> ended, no task left to run` to the log.
- A task led by a session and returned to an inactive status stays in the chain while the session is mid-turn (`busy`), then drops out (`Dispatcher.enters`). The worktree cleanup happens only when the terminal status is of the `Won` category; a task that went to a terminal status of another category simply drops out.

## Order (`src/chain/order.ts`)

`blocks` blockers, then the saved order (`state/chain.json`), milestone, priority (Urgent → High → Medium → Low → none), task number. A new task is placed before the first task of its own or a lower priority, after more urgent ones (`withFresh`); the current task stays first, with or without a saved order, unless its blockers or milestone put a task ahead of it. A new order from the page may put above the current task only tasks the chain cannot take: skipped ones and those held by a blocker outside the chain (`startsAhead`, the logic of `nextTask`); anything else is `chain.currentFirst`.

## Task feeds (BTN-66)

A project's tracker is its main task feed; `feeds` adds others (`Feed` in `src/config.ts`: `{id, tracker, key}` and the tracker's project key — `github`, `linear` — where it needs one), each on a profile of its kind (`feed_profiles`, the kind's default without one). The tasks of all feeds make one chain of the project, in one repository.

- **Reading.** The tracker layer reads a feed as a project of the feed's id on its owner's repository (`readersOf`, `ownerOf`, `readerIds`); `ReaderTasks` (`src/tracker/readers.ts`) joins a project's readers into the one list the chain and the page get. Each profile in use has one connection (`Trackers`, `docs/trackers.md`), so a feed on a profile its project already uses shares its poll.
- **Ids.** A task keeps its tracker's id: Huly's and Linear's own, GitHub's `<feed key>-<number>`; the branch and the folder follow it (`btngh-66/task`). A task finds its feed by the prefix of its id (`readerOf`), so no project or feed may give a prefix another one gives (`config.feedPrefix`) or read a place another reads (`config.feedPlace`); a feed's id is unique among projects and feeds.
- **Rules, brief, closing.** A feed's task is judged by the feed's own rules over its profile's and the shared ones (`feedRules` in `src/config.ts`, BTN-553) — never the project's, whose statuses and labels are another tracker's; the feed sets them in its window in the Tracker tab (`project/feed/rules`, `docs/web.md`). It is briefed by its own tracker — `briefOn` looks for the MCP server of the feed's tracker among the project's packages, and a project's `brief: false` speaks only of its main tracker — and moved and commented on in its own tracker. A session has one server per tracker kind, signed in as one profile (`keyPool`, `docs/packages.md`): of the project's own kind, the project's; of another, the last feed's of that kind. A feed whose profile is not the one its server signs in as (a Huly feed on another workspace of a Huly project) gets the brief whatever the packages bring (`serverProfile`). The feed's tracker plugin is not added by itself.
- **Status moves.** A feed keeps its own `moves` over its profile's, the main tracker its project's `statusMoves` (BTN-554, "Status moves" below); the third tab of the source's window sets them (`project/moves`).
- **Order.** `blocks` does not cross trackers: a task of one feed is never held by a task of another. Tasks of different feeds are ordered by the saved order (drag and drop), milestone, priority and number.
- **The page.** The project's Tracker tab lists its feeds and adds one (profile, which names the tracker, place, key — filled as the wizard fills a project) or removes it, each at once (`web/src/pages/FeedList.tsx`, the commands `project/feed/add`, `project/feed/remove`, `project/feed/profile`). A feed's tracker, key and place are not edited — a change is a new feed; its profile is, until the chain has started its tasks, as `trackerLocked` keeps a project's (`launchedProjects` with `readerOf`); a project is locked only by its own tasks, not its feeds'. A removed feed's closed tasks stay in the archive.
- **The launch log** records a task's profile, url and title, so Tally and the archive know where it lived after its feed is gone (`docs/storage.md`, `docs/tally.md`).

## Status moves (BTN-554, `src/chain/moves.ts`, `src/tracker/mover.ts`)

Even Keel can move a task to a chosen status at three points: when it starts the task (`start`), when it opens the task's pull request (`review`, PR mode only) and when it closes the task after the merge (`done`). Only trackers with `moveTo` (Huly, Linear, Jira; `docs/trackers.md`, "Moving a task to a chosen status").

- **Levels.** A tracker profile sets them for its projects (`tracker_profiles.moves`), a source over it — the project's `statusMoves` for its main tracker, a feed's `moves` — key by key (`movesOf`). `start` and `review`: a status name, or `null` — leave the status; `done`: a done status name. Nothing set anywhere — nothing moves and the close is automatic, as before.
- **Only forward.** On a start only a task of the `ToDo` category moves (a task already started stays where it is), on a pull request any open one; a task already in the status is not touched. A start or review status the rules put out of the chain is never tried, or the chain would let the task go the moment it moved (`statusMove.outside`); the settings refuse to save one (`statusMoves.outside`, `statusMoves.notDone`), and a status the tracker does not list (`statusMoves.unknown`, BTN-667).
- **A failure never halts the chain.** The start move runs after the launch's session started, the review move after the pull request is opened; a refusal is logged and kept in memory (`TrackerView.moveFailures`) until a later move of the task goes through, and the page shows it with a button to the setting by its `level`. A refused close is the usual `tracker.completeRefused` with the chosen status (above, "Cleanup after Done").

## Task worktree (`src/git/worktree.ts`)

`main` in this document is the project's main branch: its `branch` key (BTN-117), `main` without it. Every git call takes it from the current config, so a change applies without a restart. A branch the repository lacks pauses the launch with `git.noBranch`, naming the branch and the project. At the launch (not in the preparation ahead, while the chain waits for the CI) the main checkout must also stand on that branch (`git symbolic-ref --short HEAD`): on another branch or a detached HEAD the launch pauses with `git.wrongBranch`, since the merge, `git sync` and the search for the merged task all work on the project's branch.

- Before the first launch for a task — in the project's main checkout (`config.projects[project]`) `git worktree add -b <key>-<number>/task .claude/worktrees/<key>-<number> main`, all lowercase. The branch tail is always `task`: the hooks in `~/.githooks` need the form `<key>-<number>/<something>`.
- Before that, at every launch (not for a place made ahead), the main checkout's `main` is fast-forwarded to `<remote>/main` of each remote (`fastForwardMain`, `src/git/sync.ts`, BTN-210): another clone of the same remote may have pushed since this one's last `git sync`. Only when the checkout is on `main` without changes to tracked files; a `main` ahead or diverged, a fetch that fails — left as it is, silently. A place made ahead then comes up to the new `main` by `catchUp`, as after a fix.
- If a worktree already exists at that path, it is taken as is, with its branch; if only the branch exists, it is brought back into a new worktree. `.claude/worktrees/` and `.temp/` (a session's scratch, the pull request's description among it, BTN-221) are appended to `.git/info/exclude` if git does not ignore them.
- The session starts with `cwd` = the worktree, and the prompt is the task ID, a line about the ready worktree and that there is no need to clean up (`startPrompt`).
- Commands before start (BTN-97, `commands.beforeStart` of the project, `src/sessions/setup.ts`): after the worktree or slot is ready and before the session starts, each runs in order through the system shell in the task's folder, with the session's environment: that of the account the task runs on (`choiceFor(project, task).account`), through its agent's `envOf` — a Codex task gets Codex's, so a Codex-only install with no `~/.claude` runs them too (EKR-26) — and the service's own, keys removed as in `sessionBase`, while that account has no folder (`accountEnv`); `check` and `afterGreen` run the same way, `afterGreen` on the project's account. 20 min at most. Their output goes to the service log line by line (`setup: <task>: | …`); a non-zero exit stops the rest, the session is not started and the chain pauses with `setup.failed` and the last 40 lines of output. They run on every new launch of a task (a task the chain takes again runs them again), but not on `--resume`, a reply or a handoff.

## Cleanup after Done

- A merged task is closed into the tracker's first done status, or into the one its source chose (BTN-554, `doneMove`; "Status moves" below). A chosen status the chain rules do not take for done is not tried: the task stays open with `statusMove.notDone` until the setting changes.
- Any merge of the task's branch into `main` closes it, a half of the work merged mid-task too: the close does not wait for the turn to end, only the cleanup does. A task the user takes back from Done is closed again only by a new merge (BTN-219, BTN-689): `MergeCloser` keeps the own commits of its branches `main` had at the close (`mergedCommits`, the newest of each branch, in `src/git/merged.ts`) in `MergeMarks` (`src/tracker/closes.ts`, the state table `merge_closes`, through a restart), and a reopened task whose merged commits are all in that mark stays open, so a checkpoint handover on a branch merged before the reopen goes on in the new session. A branch that only caught up with `main` adds no commit of its own; a branch removed by the cleanup and made anew has new ones. A task closed before this mark existed has none, so its first close after a reopen still goes by the old rule. Only a merge seen while the chain holds the reopened task closes it (BTN-694): while it is open and not held (neither the current task with a session nor a released one awaiting cleanup, `Dispatcher.held`), every tracker read adds its newly merged commits to the mark without closing it, so a session that merged again outside the chain does not close it the moment the chain takes it back. A hand session that finishes such a task outside the chain closes it itself.
- If the tracker refuses to close a merged task, `MergeCloser` keeps a `tracker.completeRefused` notice for that reader and task in `TrackerView.completionFailures` (memory only). The page shows the tracker response and a link to the task, asks for the required field to be filled or the task to be closed by hand, and suppresses a false reply prompt in the header, lamp and session panel; a real question or permission remains visible. The task stays current and the normal 30 s full read retries the close. Success clears the notice; a task no longer held drops its refusal, and the page also hides one as soon as polling sees a closed status. Git inspection errors remain separate from tracker refusals.

- The current task went to Done (category `Won`; a cancelled or dropped one does not) — the chain's `closing`: wait until its session is not mid-turn (`busy`/`waiting`; a session in `shell` does not hold a done task — see "Background command" below), then `claude stop` its sessions in this worktree (otherwise a live process holds the folder: a `--bg` session does not exit after a turn, `claude agents` shows it `done`/`idle`), then in the clean worktree remove links and junctions in ignored folders (`node_modules` of npm workspaces, `npm link`: git on Windows follows them — it cleans someone else's folder or stumbles on a dangling one and abandons the worktree), then `git worktree remove` (without `--force`; every git call of Even Keel on Windows carries `-c core.longpaths=true`, and a folder git unregistered but left for another reason than a lock — `Filename too long` — is deleted from Node, BTN-559; only a lock is `cleanup.folderLeft`, the rest `cleanup.folderNotDeleted`), `git branch -d` of the task branch (only `<key>-<number>/…`), `git push origin --delete` if it is on origin, and `git sync` if the project has a remote. The next task is started after that. A task returned from Done before the cleanup — no cleanup, the task is back in the chain.
- **The first read of the sessions** (BTN-646). After the service's start the dispatcher does nothing — no cleanup, launch, handoff, review, fix or slot switch — until the monitor has finished its first full tick (`DispatcherDeps.sessionsRead`, the service's `agentsRead`, set with the first `onChange`): before it `busy` is unknown rather than false and the cleanup's `stopTaskSessions` sees no session at all, so a Done right after a restart removed the worktree past its live session and left the folder held (`cleanup.folderLeft`; BTN-537, BTN-587, BTN-642). The forward merges (`chainQuiet`) and the account watcher (`sessionsKnown`) wait for the same flag.
- **A session left mid-turn** (BTN-616). The cleanup waits only for the task's own session (`busy` by its view); another session in the task's folder, or one whose status the view and the listing disagree on, may still be `busy`/`waiting` when `stopTaskSessions` runs. Such a session is not stopped then but kept in `Lingering` (`src/sessions/lingering.ts`, the service's memory) and stopped on the first monitor tick after its turn ends (`stopLingering`, from `onAgents`, since a session without a view of its task changes no view); once gone by itself it is forgotten. Otherwise nothing stopped it after its task left the chain, and a Codex session, which has no process between turns, rested on the page as `waiting` for good. A restart before its turn ends forgets it.
- **Nothing to merge** (EKR-10), out of PR mode. A task that needs no change in the repository (done in main already, research, an answer) never closes by a merge: `branchMerged` takes a branch with no commits of its own for unmerged, or every branch that only caught up with main would close its task. The prompt's `cleanup` tells such a session to end its turn with the last line `NO CHANGES: <why>` (`noChangesOf` in `src/sessions/transcript.ts`, Codex's rollout too; a tool call or a new prompt drops it, as `CHECKPOINT:`). `Unchanged.follow` (`src/chain/unchanged.ts`), once the session is not `busy` (a session in `shell` does not hold it, BTN-637 — see "Background command" below), counts the commits of its folder beyond the local main and reads `git status` with untracked files (`changesOf`, `src/git/changes.ts`; ignored `.temp/` is not work). Nothing — `UnchangedDeps.complete` moves the task to Done in the tracker and comments the reason (`unchanged.comment` of the prompts; a comment that fails is only logged), the tracker is read at once and the chain's own Done cleans up — exception 4, `git branch -d`, the next task. A tracker that refuses pauses the chain with `chain.unchangedNotCompleted`, a git that cannot count with `chain.unchangedNotChecked`, the task staying current. Commits or uncommitted changes — the session gets `unchanged.ahead` or `unchanged.dirty` by `--resume` whatever its cache, as a chat answer does (merge them, or drop them and mark again). A mark acted on has its `lastReplyAt` remembered in the service's memory, so only a new turn tries it again. In PR mode the mark is ignored: `PULL REQUEST:` covers the case (BTN-222).
- `git sync` is the `main` synchronization (`src/git/sync.ts`): if the repository has an `alias.sync` (`--local`), that one; the user's global alias only when the branch is named `main`, since such an alias is written for `main`; if not, Even Keel does it itself: the main checkout must stand on `main`, for each remote `git fetch` and `git merge --no-edit <remote>/main` (if it does not merge cleanly — `merge --abort` and an error), then `git push <remote> main` to each. A push rejected as `[rejected]` (another clone pushed between the fetch and the push, BTN-210) or as `[remote rejected]` with a refused ref update — `incorrect old value`, `failed to update ref`, `cannot lock ref`, `failed to lock`, `stale info` (the other push landed inside this one, after it read the remote's refs, BTN-686) — gets the whole sync once more, the alias's as well; a second rejection is the error. Any other `[remote rejected]`, a declined server hook among them, is the error at once.
- A dirty worktree, a folder held by a process, an unmerged branch — a warning in the log and on the project page (`leftovers` in `state/chain.json`, the "Done" button — `chain/dismiss`), and the chain goes on. A task whose folder still holds work after that keeps its row in the chain list, out of the archive, with the warning in its work chip's tip and "Done" on the row instead of in the head (BTN-332, `docs/web.md`). If `git sync` fails — likewise a warning with its output, the chain goes on, nothing is pushed by force: the next task takes the local `main`, and the next `git sync` after its Done will repeat the push.
- A `git sync` after Done that never reached a remote (a fetch, a push or the alias whose output says `Failed to connect`, `Could not resolve host`, `Connection timed out`/`reset`/`refused` and the like — `isNetworkFailure`, BTN-267) is tried twice more, 30 s and then 2 min later, before it becomes that warning; a refusal of the remote (`[rejected]` twice, permissions, a conflict) is the warning at once. The retries do not hold the chain: the cleanup returns at once and the next task starts, the dispatcher's tick (every 30 s) runs the try once it is due (`Cleanups.retrySyncs`). Each failed try is in the log; one that goes through is pushed as the cleanup's would have been (`MainCheck.pushed`). The retry lives in memory, one per project: the next cleanup's own sync takes its place, and after a restart the next Done pushes what it could not.
- Work left in a task's folder, whatever its status and however it left the chain (BTN-298; `shelved`, a task moved by hand, a dead session): `TaskWorks` (`src/git/work.ts`) reads each project's `git worktree list` and, for every worktree or slot on a branch `<task>/…` of one of the project's tasks (not the main checkout), `changesOf` against the project's `branch` — the files left out of a commit (`status --porcelain`, so not what git ignores, `.temp/`) and the commits main does not have. A project is read at most once a minute (a 15 s tick) and at once at the end of each cleanup after Done (`TaskWorks.refresh` from `finish`, after a read under way), so a removed folder does not linger. A task's work read before its session last did anything (`lastActivityAt` of any of its sessions) is kept out of the state — the session may have committed or merged it since, and a closed task would flash "not committed" — and its project is read again on the next tick once no session of the task is mid-turn; so the page only tells of work that is really left. The read runs in a folder whose session may be committing in it: every git call of Even Keel carries `--no-optional-locks` (`gitArgs`), so its `status` never takes `index.lock` and the session's `git add` is not refused meanwhile (BTN-697). A change is broadcast with the state (`EvenKeelState.works`, only the tasks with something), a failed read keeps the last answer and logs once. It is in memory only; the page shows it as in `docs/web.md`.

- A parent closes by itself once all its subtasks are closed (adapters with `children`, `docs/trackers.md`); there is no cleanup in that case.

## Released tasks

A task that the chain started and released other than through Done — dropped out (became a parent: tasks with subtasks do not enter the chain; went to an inactive status), postponed by a blocker, skipped, or the chain was stopped or halted with an error — is remembered in `released` in `state/chain.json`. Even Keel asks the tracker for their statuses together with the chain's tasks (every 30 s); if one went to `Won` and its session is not mid-turn (`shell` does not count, as for the current one) — the same cleanup as for the current one, but the chain does not wait for it and does not pause: a failed `git sync` is a warning in `leftovers`. If it went to a terminal status of another category, disappeared from the tracker or the chain took it again — it is forgotten.

## PR mode (`pullRequests`, BTN-205, `src/chain/reviews.ts`, `src/review/`)

With the project's `pullRequests` on, a session does not merge its branch: a human does, through a pull request. Off by default; a project of any tracker whose remote is GitHub, GitLab (merge requests, BTN-414) or Forgejo. Below, "pull request" covers a GitLab merge request too, its number the merge request's `iid`.

- **Before a launch** (EKR-12). `pullReadiness` (`src/review/open.ts`) is the one answer to "does PR mode have where to go": the `pullTarget` of the remotes and the token `ciToken` gives for it, or `review.noRemote`/`review.noToken`, or `review.unsupportedHost` for a target on a forge with no adapter (`remoteKind`, `docs/ci.md`; EKR-8), which asks for no token. The service's `blocked` hook (`pullBlock`) asks it of the remotes `ProjectRemotes.urls` rereads each minute (a project not read yet is not held), so no session of the project starts and the chain pauses with `review.notReady` and the cause. Start and Resume do not refuse this one block (`admit`, BTN-316): the chain goes in paused on it, other blocks still refuse them. Start, Resume and `wake` check the agent and account of the task that goes first — the current one, else the next by the order — since its run label may pick another account; with no such task known only the tracker profile and PR mode are checked, and the launch checks the rest (`firstOf`, BTN-521). The dispatcher lifts that pause by itself (`cleared`) once the hook lets the project through — a remote or a profile added, or PR mode turned off. The page's save refuses to turn `pullRequests` on without a target (`review.cannotEnable`, read from git at once); turning it off always goes. A session already running whose remote went away still stops on `review.notOpened`. A tracker the sessions would not see pauses the same way (BTN-656): with `brief` off and no package bringing the tracker's MCP server (`noTrackerMcp`, `docs/packages.md`) the `trackerBlock` hook gives `chain.noTrackerMcp`, checked after `blocked` by every launch, Start, Resume and `wake` (`LaunchPauses.block`); Start and Resume go in paused on it and `cleared` lifts it once a package brings the server or `brief` is on — the codes that do this are `SELF_CLEARING` in `src/chain/pauses.ts`. `cleared` also lifts a pause on `chain.unknownModel` (BTN-679), which no launch block gives: it asks the async `modelBlock` hook (`ModelCatalog.refusal` for the first task's account and model) and goes on once the account has the model, as Resume would. A running chain whose package or `brief` goes off pauses before its next task; the session at work is not touched. The page puts "Turn on <package>" (or "Add the tracker's package", the add dialog) and "Turn the task description on" beside the reason (`web/src/pages/TrackerFixButtons.tsx`); no banner shows it. Packages only the user can make ready (not installed, failed to install, a key missing) pause the same way on `chain.packagesNotReady` (the `packagesPause` hook, BTN-657, `docs/packages.md`), except for a fix session of a red main.
- **What a running chain waits for** (BTN-657). A running chain with no session at work names the first thing that holds its next launch, in the order `step` checks them: the closing of a Done task (`closing`), the CI of main (`ciWait`), the first limits poll (`limitsWait`), a limit (`limitUntil`), the gateway or packages that pass by themselves (`packagesBlocked`), a free slot (`slotWait`). The chip of the card, the project page and the queue panel says "waiting · <reason>" (the card only "waiting": its line is right under it), and the card and the page add a line per wait with a button where one ends it (`chainWaits` in `web/src/waits.ts`, `web/src/pages/ChainWaits.tsx`). A wait that never passes by itself is a pause with a reason, not a wait.
- **On the page** (EKR-7). The state carries the same answer for every project read (`pullReadiness`: `null` or the notice), so the switch of the Check and CI tab cannot be turned on without a target, says why under it, and stays free to turn off once on (turning it on from the live page for a project with a Forgejo remote and profile was checked on 2026-10-25; the disabled switch was seen on the fake state only). `review.noToken` names the remote's kind and address: "Add profile" beside the switch and under a pause whose cause it is (`review.notReady`, `review.notOpened`) opens `/settings?profile=<kind>&host=<address>` — Trackers and CI with the dialog of that kind, no kind step, the address in its one host field (Forgejo's URL), the pull request rights stressed. A kind is not offered: `ciToken` takes a GitHub profile only for github.com and a Forgejo one only on the remote's host. A pause for `review.noRemote` leads to the project's Check and CI tab instead (`web/src/pages/PullButtons.tsx`, `pullFix.ts`).

- **The prompt.** `startPrompt`/`handoffPrompt` put `pullRequest(main)` in place of the cleanup rule (`src/chain/prompts.ts`): do not merge — this outranks the merge step of the tracker skill; when the work is done (and approved, where the project has a reviewer — a prompt that demanded one left a session without a reviewer waiting forever, BTN-221), commit the work, write the pull request's title (first line) and body into `.temp/pull-request.md`, which is not committed, and end the turn with the last line `PULL REQUEST: .temp/pull-request.md`. The mark is read like `CHECKPOINT:` (`pullRequestOf`, `TranscriptSummary.pullRequest`, Claude and Codex alike) into `HandoffSession.pullRequest`.
- **Opening** (`Reviews.follow`, on each step of the current task, once its session is not `busy`). A mark newer than the one the record holds (`markAt`) makes `openPull` (`src/review/open.ts`) push the folder's branch to the project's pull request remote (`pullTarget`: `origin` when its address parses, else the first remote that does; `github.com` is GitHub, `gitlab.com` and a GitLab profile's host are GitLab as for its CI — the subgroups in the owner, the installation prefix from the profile (`gitlabRepo`, `docs/ci.md`) —, `bitbucket.org` is not supported, any other host is taken for Forgejo) and open the pull request against the project's `branch`, or find the one already open — a session that fixed what the review asked marks again and its push goes to the same pull request. The record (`PullRequest`, `src/review/model.ts`) goes into `reviews` of the chain state (storage step 8), the journal gets `review`, and the task is set aside (`letGo`) like a postponed one: out of the chain, its session untouched. A mark that came while the chain was stopped is acted on at the step after "Start".
- **The issue's link** (BTN-295). A task id means nothing to GitHub, so for a pull request on GitHub of a task whose tracker names its GitHub issue (`TaskSource.closingRef`, only the GitHub adapter: `owner/repo#N` of the key's repository) `openPull` ends the body with `Closes owner/repo#N` (`closingBody`), always the full form, which GitHub takes for another repository too. The issue gets the pull request in "Development" and is closed by GitHub at the merge; a pull request into a branch other than the repository's default one is ignored by GitHub, and Even Keel closes the issue as before. A body that closes the issue itself (a closing keyword with `owner/repo#N`, the issue's address, or `#N` in the same repository) gets nothing; a mere mention does. The prompt does not ask the session for it and the title is left alone, by the user's decision; no setting. On GitLab (BTN-414) the GitLab Issues adapter's `closingRef` is the issue's address, and `closingOf` takes it only on the merge request's own server: an issue of the merge request's project is closed as `Closes #N`, of another project as `Closes group/name#N`; the body's own close counts by the same forms or the `/-/issues/N` address. A GitHub issue gives a GitLab merge request nothing, a GitLab one a GitHub pull request nothing, and Forgejo gets no line at all.
- **Nothing to open** (BTN-222). Before the push `openPull` fetches the base from the remote and counts the branch's commits beyond `<remote>/<branch>` (not the local main: in PR mode it may lag); none — nothing is pushed, and the worktree decides, before the note is read (`.temp/pull-request.md` is not needed then, and an untracked note is not work). Clean (`git status` with untracked files lists nothing but the note) — the task changed nothing in the repository (research, work already in main): no pull request, `complete` of the tracker moves it to Done as after a merge, the tracker is read at once (`refresh`) and the chain's own Done takes it — exception 4, the usual cleanup with `git branch -d`, the next task. A tracker that refuses the move pauses the chain with `review.notCompleted`, the task staying current: the user moves it and resumes, or skips it. No setting, by the user's decision: a stop there would give a human nothing but a Done to press. Dirty — the work is not committed: the session gets `review.nothingAhead` of the prompts by `--resume` whatever its cache, as a chat answer does (commit and mark again, or drop the changes and mark again), and the chain waits on it. The prompt's `pullRequest` tells a session of a task with no change in the repository to mark all the same.
- **A branch moved on the forge** (BTN-716). A push git refuses as `[rejected] … (fetch first)` or `(non-fast-forward)` — the branch on the remote has commits the session's lacks, say a conflict the user resolved on the forge while the session worked on its feedback — is `review.pushBehind`, not an access problem: the session gets `review.pushBehind` of the prompts the same way as `review.nothingAhead` (merge the branch from the forge with `git pull --no-rebase`, resolve the conflicts, commit and mark again; never push itself, never `--force`), and the chain waits on it, unpaused. Even Keel never forces the push and never merges in the session's worktree itself: the user's commits on the forge stay, and a conflict is the session's like any other.
- **A refused mark** (BTN-222, BTN-407). Any other failure pauses the chain with `review.notOpened` and the cause (a forge's refusal by the `message`s of its answer, `src/ci/http.ts`), the task staying current (`ReviewHost.hold`), so the chat, "New session" and "Skip" act on it; a chat answer or "New session" ends that pause. So does the task's end (BTN-715): once its earlier pull request is merged (`ReviewHost.settle`) or the tracker has it done (`Dispatcher.step`), the pause lifts by itself and the task goes as on any Done, its session untouched — a push refused by the forge no longer holds the chain and its `parallel` slot. Pauses for other reasons stay. Start on this pause (`resume` on the page, or `start`) forgets the current task's refused mark (`Reviews.retry`) and tries it again without touching its session, so access can be fixed in the project's Check and CI settings first. Another refusal pauses with its new cause. A mark that opened nothing has its `lastReplyAt` remembered in the service's memory (`Reviews.refused`): Skip and Unskip or Stop and Start do not retry it, only a new session turn, Start on `review.notOpened` or a service restart does. A profile or token change alone does not retry it.
- **Out of the chain.** A held task (`Reviews.holds`: open without feedback, or closed and not cleaned up after) enters neither the order nor the backlog, and an open task it blocks waits for it like for any open blocker. The page shows it as a dashed row between the closed tasks and the chain, with a "PR #N" link and a "feedback" chip (`ProjectOrder.reviews`, `chainBlocks`; in `dev:fake` it is DEMO-9). The task's panel has a "PR #N" button beside Chat and the chat window an icon in its head, both opening the pull request in a new tab (`PullButton`, BTN-224): the row's chip alone went unnoticed.
- **The poll** (`Dispatcher.pollReviews`, every 60 s from the service, and for one project on the page's task refresh, `chain/refresh`; `reviewDeps` in `src/review/wiring.ts` picks the forge by the remote and its token). `check` reads the pull request's state, the remarks after the last push and the failed runs of its head commit — one not told yet with the log tail of its first failed job, read as for a red main (`readFailure`, `docs/ci.md`; BTN-605); `outcomeOf` (`src/review/events.ts`) turns them into what the chain has not acted on yet — the events already told are in `seen` (`review:<id>`, `comment:<id>`, GitLab's `note:<id>`, `ci:<id>`, `conflict:<head>`).
  - **What counts as a remark** (`Forge.remarks`, BTN-223) — from a trusted author, the pull request's author included: a review that asks for changes, a review that comments (GitHub `COMMENTED`, Forgejo `COMMENT`) with words or line comments, and a comment in the pull request's conversation (the comments of the issue it is, read from the last push with `since`). Not a remark: an approval, a dismissed or pending review, a commenting review without a word, and on GitHub a comment by a bot account (`user.type` `Bot`) — coverage and preview bots comment on every push and would loop the session. Trusted on GitHub (`trustedAuthor`, `src/github/trust.ts`): the owner, the organization's members and the collaborators by `author_association`. Trusted on Forgejo (`accessOf`, `src/review/forgejo.ts`, BTN-653): the token's own login (`/user`, once per forge) and `write`, `admin` or `owner` in `/collaborators/{user}/permission`, asked once per author per poll. Forgejo answers that path for another user only to an admin of the repository; on its 403 only the repository's owner by name is trusted, and anyone else is skipped with a log line that asks for admin rights for the profile's account (BTN-703): nothing else Forgejo 16 answers such a token tells `read` from `write` — `/collaborators/{user}` is 204 for both, `/collaborators` lists no access, an organization's member may have `read` only — and a `read` collaborator can comment and request changes. Any other 4xx is "no". A skipped remark gets a log line once (`Skipped`) and is asked again on the next poll. Neither GitHub nor Forgejo lets the author request changes on their own pull request (Forgejo answers 422 "reject your own pull is not allowed"), and Even Keel opens it with the user's token, so a user alone gives feedback by commenting. Even Keel itself writes nothing on a pull request, but its session may, and often with the same token, so the author does not tell its words from a reviewer's (BTN-442): the PR-mode prompt has the session put the hidden mark `SESSION_MARK` (`<!-- even-keel:session -->`) into whatever it writes on its own pull request, and `othersOnly` (`src/review/model.ts`) drops in `check` a remark whose text is marked whole and a marked line comment alone, for an open pull request and for the `closedNote` of a closed one alike. A session that forgets the mark gets its words back once, as before. GitLab (`src/review/gitlab.ts`) has no reviews to group by: each note of the merge request's discussions made after the push is a remark (`note:<id>`), a line note (`DiffNote`) with its file and line, the rest a comment; not a remark: a system note (an approval, a request for changes, a push), a bot's (`author.bot`, or the `project_<id>_bot…`/`group_<id>_bot…` users of access tokens, which are members) and an author below Reporter in the project (`/members/all/:id`; a 404 or 403 is not trusted), skipped with a log line once, as the GitLab tracker skips comments. A conflict is `has_conflicts` or `detailed_merge_status` `conflict`; `unchecked`, `checking` and `preparing` are "not computed yet". Forgejo answers `mergeable: false` both for a conflict and while it checks mergeability after a push, with nothing in the answer to tell them apart, so in `check` (`src/review/wiring.ts`) its `false` within 60 s of Even Keel's push (`pushedAt`, `FORGEJO_RECHECK_MS`) is "not computed yet" too, and a real conflict reaches the session on the first poll after that (BTN-717); a push to the branch by someone else gets no such wait. The failed runs are the pipelines of the head commit, as the CI reads them; `opened` and `locked` (a merge going on) are open.
  - **Merged** — the tracker's `complete` moves the task to Done and it goes into `released`; the usual sweep cleans it up (exception 4), with the branch deleted by force (`-D`, it never merged locally) and on the pull request's remote (`PullCleanup`). A task the tracker closed first — a forge's integration closes it on the merge — is cleaned up the same way, and `Reviews.closedUp` says so in the log, as no poll will.
  - **Closed unmerged** — once no chain leads the task and its sessions rest, `Reviews.sweep` cleans up the same way but does not archive it, then puts the still open task among the skipped: it is the user's to run again. Its tracker status is left alone on purpose (BTN-211, invariant 2): putting it back to Todo would redo the rejected work the same way, and Backlog or Canceled would take the call away from the user — they return it to the chain, move it to Backlog or cancel it in the tracker themselves. The poll that sees the close reads every remark since the pull request was opened, seen or not, and keeps `closedText` (the link, the latest 20 remarks with a count of the earlier ones, "the branch is removed, start over from `main`") in the record's `closedNote`; after the cleanup the record stays with `cleaned` — out of `holds`, `views` and the poll — until the task's next launch carries the note in its prompt (`Reviews.closedNoteOf`, `review` in the launch log) and drops it, or the task is done. A record closed before BTN-223 has no note and goes at the cleanup, as before.
  - **Feedback** — `feedbackText` in `promptLanguage` (the link, each remark, each failed run with its log tail in a code block when the CI gave one, "merge `main` if it conflicts") waits in the record's `feedback`. The chain takes a task with feedback before the next one of its order (`Reviews.next`); if the task is the current one, its session gets it at once while it is not mid-turn: `--resume` with it while the cache is warm, otherwise a new session with a handoff carrying it (`review` in the launch log; exception 8 to invariant 1). A launch of the task with feedback carries it in the prompt (`delivered`). A chain that ran out of tasks and ended by itself (`ended, no task left to run`) marks the project's open pull requests `wakes` (`Reviews.ended`); feedback on one of them starts the chain again as "Start" does, or queues it (`Dispatcher.wake`, BTN-375; the log says `starts again: feedback came on a pull request of its tasks`), and the task takes the feedback by the path above (checked live on 2026-10-25: a comment on a Forgejo pull request of an ended chain started it within a minute and a new session pushed the change to the same pull request). "Stop" and taking the chain off the queue clear the marks (`Reviews.stopped`), so a chain the user stopped stays stopped, even if it would have ended by itself later: there "Start" sees the feedback task as work. A paused chain is still a chain and stays paused; a chain whose launches are blocked (other than by `review.notReady`) is not started, with a log line. A merge starts no chain: it completes the task without one. Unattended mode changes none of this.
- A service restart in the middle of delivering feedback is redone by `Handovers.recover` (the `review` move keeps its text in `reply`), as for an answer.

## The CI of main (BTN-103, `src/chain/maincheck.ts`)

After a cleanup whose `git sync` succeeded (the current task or a released one), `MainCheck.pushed` reads the main checkout's `main` and remembers it as the push to check (`ci[<project>].check` in `state/chain.json`: commit, time, the tasks of the push). A new push while the previous one is awaited replaces its commit and adds its tasks to the previous ones. The CIs counted and the wait are the project's `ci` key (`docs/ci.md`); with `ci.guard: false` none of what follows happens — no wait, no check, no fix.

- **The wait.** The next launch of the project waits (`heldByMain`) while the push has no verdict and `waitMinutes` has not run out since the push (`null` — no limit, `0` — no wait). Meanwhile the chain is running with `ciWait = { commit, since }` (a yellow line on the card and the project page), and the next task's place is prepared ahead: `TaskPlaces.prepare` makes the worktree or slot and runs the commands before start once per task. A place made ahead stays detached at `main` (`ahead`): the task branch is made only at the launch, since its checkout is what starts the task in the tracker (a git hook moving it to In Progress) — a task the chain has not launched yet must not look started. A task that already has a branch gets it ahead as before. At the launch `TaskPlaces.ready` takes the same place (`at`: a slot prepared ahead is the task's while it is detached, dirty or not), makes the branch at its commit, brings it up to `main` with `merge --ff-only` if it has no commits or changes of its own (`catchUp`, so a task prepared during the wait starts from a fix that came meanwhile) and runs the commands again only if it moved, the preparation ahead failed or the launch had to take another slot. The project's own check of main (`readyAhead`) runs in that detached place too.
- **The verdict** (`src/ci/verdict.ts`, asked on every dispatcher tick; a CI change wakes the dispatcher): any failed run of the commit — red; a CI still at work — wait; a CI without a token, not answering or that did not take the commit within `STUCK_MS` (2 min, a busy runner extends it, a shared one too — a run of another watched repository on the same host, BTN-719) — unavailable: the chain does not wait, and the commit stays unchecked with a line in the log unless the project has its own check, which then takes it (`docs/ci.md`, "The check without a CI"). A commit left unchecked because no runner took it is still watched for an hour: a run taken later and failed files the fix like any red main (`docs/ci.md`, "Polling"). A project with no counted CI (`none`) goes to its own check at once, without the wait. Right after the service starts it is a wait, not `none` or unavailable, until the service has found the projects' CIs (`MainCiDeps.watches` is `null`) and each CI has answered once (`checkedAt`): otherwise a push awaited across a restart would be dropped as unchecked and its red verdict never reach a fix. A cancelled or skipped run is not red. Green is remembered as `ci[<project>].green` — the base of the next fix task's commit list.
- **Red.** What broke is `redReport` (`src/ci/report.ts`): the failed jobs, the log tail of the first failed job (GitHub, Forgejo and GitLab; a log that cannot be read — the run link), the commits since the last green one (of any project of the remote, below) and the tasks of the push. Who fixes it is the project's `ci.fixTask` (`docs/ci.md`): off, the default — a session without a tracker task (below); on — a task. One automatic fix at a time, `ci[<project>].fix`, is the guard against recursion.
- **Red after the fix** (the push holds the fix) — the chain is halted with `ci.fixFailed` and no new fix is made. A project without an active chain (it ended while waiting) gets one, paused with the notice, out of the queue.
- **Commands after green** (`commands.afterGreen`, BTN-156, `docs/ci.md`). A green verdict starts them in the main checkout; while they run, `heldByMain` holds the next launch with `ciWait = { commit, since, after: true }` (its own yellow line), so a command that restarts Even Keel does not cut off the launch of the next session. The run lives in memory only (`MainCheck.afterGreenRun`): after a restart nothing waits, and the mark `ci[<project>].afterGreen` keeps the commands from running again. A fix session does not wait for them.

### The fix session (BTN-115, `src/chain/mainfix.ts`)

With `ci.fixTask` off nothing is created in the tracker, and the adapter needs no `create`.

- **The name** is `<KEY>-FIX` (`fixNameOf`, `src/chain/fix.ts`; `<KEY>_<first four of the id>-FIX` for a project whose key an earlier one in the config has, BTN-271), used wherever a task id is: the session name, `chain.current.task`, the launch log, the worktree `.claude/worktrees/<key>-fix` and the branch `<key>-fix/task`. The worktree is its own even in "slot" mode. The name never reaches the tracker: `held`, `released` and the tracker questions leave it out. The page tells the fixes apart as episodes `<KEY>-FIX.<n>` (`fixEpisodeId`; `fixTaskOf` turns one back into the name for commands to the service), see "The launch log of a fix" below.
- **The launch.** `MainCheck.red` writes `ci[<project>].fix = { task: <KEY>-FIX, at, commit, report }`, `report` being the session's prompt in `promptLanguage`; a report that cannot be built halts the chain with `ci.fixNotStarted` / `check.fixNotStarted`. While `report` is there (`MainCheck.sessionFix`) the fix goes before the chain's order and does not wait for the CI: `deps.launchFix` starts it with `fixPrompt` (the report, the worktree, the branch and the rules: no task, no task id in commits, merge into `main` yourself, stop your background commands before the turn ends). A project with no active chain and not in the queue gets a chain with `fixOnly`, which ends with the fix; "Start" pressed meanwhile clears `fixOnly`, and the chain goes on with its tasks after the fix. A handoff of the fix session (limit, checkpoint, "New session") carries the report again (`withReport`).
- **Done** is not a tracker status: the session is not `busy`/`waiting` (a turn that ended on a background command, `shell`, does not hold it, BTN-202) and its branch is in `main` with commits of its own (`branchMerged`) — a merge of another task that moves `main` does not close the fix. Then the usual cleanup and `git sync`; `report` is dropped (`MainCheck.fixLanded`), and the new push waits for its verdict like any other. A turn that ended with nothing merged (a question, an error) is invariant 1: the chain waits, the page shows the session.
- **The session it interrupts** (`MainFix.yields`, exception 7 to invariant 1). The fix is due while a task's session leads the chain: a session mid-turn (`busy`) is stopped (`claude stop`), the chain keeps `interrupted = { task, sessionId, since, at, commit }` and `current` is free for the fix. After a launch, an empty monitor or an entry for an older session is unknown, not idle: the task retains its place until `handoff` or `liveSession` observes its current session id (BTN-550). A saved handoff also counts when the observed process has ended. Not stopped: a session whose branch is already in `main`, and one that is not mid-turn — waiting on a question or idle — which is only set aside (`letGo`), like a task postponed by a blocker; it meets the fix at its own merge. Until the chain takes it again it is not the current task, so the chat window does not answer it (BTN-119): the page shows the chat locked with the reason (`docs/web.md`), Remote Control works as ever.
- **The continuation** (`MainFix.resume`) once the fix has landed, without waiting for the verdict on its push: `--resume` while the cache is warm, otherwise a new session with a handoff (`resume` and `relay` in the launch log, as after a limit), in both cases with `mainFixedPrompt` — the red commit, the commit `main` is on after the fix, "merge `main` into your branch and carry on". A task the user skipped or that left the chain meanwhile is released instead; a session the user already continued by hand is taken as it is.
- **Red after the fix** with an interrupted task: the halt as above, and the stopped session becomes the paused chain's current task again (`MainFix.giveBack`) — the user continues it from the chat window or with "New session".
- **Handover of the fix session** (a limit, a checkpoint, "New session") is the usual one plus the report from `ci[project].fix.report`, since there is no task to read it from (`Handovers.handOver`, `withReport`). Without the report it fails with `chain.fixReportMissing`, the chain halts and no session starts.
- **"Skip"** on the fix session (`Dispatcher.skip` → `MainFix.skip`, only while it is current and not `busy`): the fix is dropped, `main` stays as it is, the session is not touched; the interrupted task goes on with "the fix is not confirmed". The skipped session lives on under the name the next fix gets, so the chain remembers its id (`ci[<project>].skippedSessions`, `src/chain/skippedown.ts`, BTN-692) and the next fix starts a session of its own instead of taking it, in the same worktree and branch; the newest session of a name is the one the monitor follows. A live session of an own name is taken without a launch only when it is not on that list — the recovery of a launch the chain lost track of. The list of a name goes with the cleanup of its worktree, which stops every session in it, the skipped ones too.
- **The launch log of a fix** (BTN-153, schema v3). The first launch of a fix keeps the red commit (`commit`), and the end of the fix is an entry of its own with `reason: 'landed'` (with `commit`, the commit `main` went out at) or `'dropped'` ("Skip", or the fix is no longer wanted while its session leads the chain) — `MainFix.ended`. `fixEpisodes` (`src/chain/launches.ts`) cuts the log into episodes: a launch with its handovers, resumes and answers up to its outcome; a launch for the same red commit stays in the episode, one for another commit with no outcome before it closes the previous one as `lost`. An outcome entry is not a launch (`isLaunch`): session lists, the stats and Tally's `launchMap` skip it. The state sends the episodes to the page in `fixes` (`EvenKeelState`).
- **The page.** `chainBlocks` (`web/src/state.ts`) adds a block for the fix ahead of the open tasks, with the usual panel (stage, action, context, chat); it has no task card and no tracker link and cannot be dragged. Its id is the open episode (`liveFixId`); `#ABC-FIX` in the URL leads to it. In place of its lamp the row has a forge (`web/src/pages/Forge.tsx`) in the lamp's colour, set right after the title "Fixing main" so it never meets the cache ring in the number column: two smiths take turns with hammers on a red-hot ingot (the red main) while the session works and stand with hammers down by a cooling one otherwise; with `prefers-reduced-motion` — two crossed hammers. The interrupted task carries a chip.
- **A fix that is over** stays in the chain as a closed row among the closed tasks, by its end time, in the milestone of its neighbour: lamp `fixed` (purple, `--lamp-fix`), crossed hammers, the title "Fix main: <red> → <commit>" or "… — dropped". It goes into the archive like a closed task, and the archive counts it apart ("16 tasks · 1 fix"). A press anywhere on the row opens its panel, as on a task: it holds the episode's sessions and, with a CI, a "CI" button beside the chat that opens the CI panel (`#ci/ABC-FIX.<n>`), which marks the runs of its red and landed commits and names the landed run's "Push tasks" as the fix, a link back to the row.

### The fix task (`ci.fixTask: true`)

- The text of the task is `redReport` in `language`, otherwise `promptLanguage`. If the chain's fix task is still open — the report is a comment on it and no new task is made. Otherwise `TaskSource.create` makes "CI on main failed: <commit>" in the ready status, priority high, the milestone of the push's last task. The chain is halted with `ci.cannotCreate` or `ci.fixNotCreated` when the adapter has no `create` or it fails.
- **The fix goes first**, before the chain's order, while it is open (`MainCheck.fixOf`). Until the tracker lists the new task the chain waits for it, up to `FIX_LISTED_MS` (5 min).
- A session already started (the wait ran out before a red verdict) is not touched (invariant 1): the red verdict only files the fix task, which the chain takes after the current one.

## Several chains (`parallel`, BTN-67)

- `parallel` in the config is how many chains of different projects run at once, 1 by default; applied on the fly. Active chains are `active` in `state/chain.json`, an array in launch order (the old form — a single object or `null` — is still read, `src/chain/store.ts`); the other projects are in `queue`.
- A paused chain also holds a place. When a chain ends or is stopped, the next project is taken from the queue at once, and the other chains go on. Lowering `parallel` stops nobody, and no new ones are taken until there are fewer active ones.
- Each chain has its own current task, pause, error, handoff and `closing`. "Resume" and "Stop" (`chain/resume|stop` with `{ project }`) act on their own project. On the page "Stop" sends `chain/stop` only for a paused chain; a running one gets `chain/stopAfter` (below), and its tip says the session is not stopped. There is no manual pause: only the dispatcher itself pauses a chain on an error, it keeps its place and queue, and "Resume" retries. Stopping releases the task (its session keeps working, the cleanup is as for a released task) and frees the place.
- "Stop" on a running chain (BTN-230, `chain/stopAfter` with `{ project, on }`) sets the chain's `stopAfter`: while the current session is mid-turn (`midTurn`; a pending question is not) the chain does nothing at all — it follows no Done, handoff, relay after a limit, blocker or review — and once the turn has ended, or at once when there is no session mid-turn, it stops as with "Stop" (the task is released, a Done after it is cleaned up as for a released task) and frees the place; the log says `stopped after its session's turn, as asked`. Meanwhile the task stays the chain's current one, so the page keeps its lead block until the turn ends. A pending `closing` is finished first. The flag is part of the chain's JSON in `chains`, so it survives a restart without a schema step (an older Even Keel only drops it); the same button, now "Keep going", takes it back, and a stopped chain loses it.
- The account limit is shared and is not split between chains: all take tasks until the window is used up; once it is used up, all wait for the reset (`limitUntil` on each), and the continuation after the reset is per chain.
- Renewing the active account's sign-in is blocked by any chain that is not paused (`LoginBlock.chains`, `src/account/model.ts`). Switching the account is not: the session working now stays on its folder, the next launches go to the new one, as the roles menu says under "Even Keel" (`docs/accounts.md`).

## One folder, one project

The wizard refuses a repository another project already has (`wizard.repoTaken`, `checkRepo` in `src/projects/check.ts`). Two projects on the same code — one per tracker, say — take separate clones with the same remotes. Two chains in one folder would get in each other's way:

- **Slots.** The pool's folders do not carry the project's key (`.claude/worktrees/even-keel`, `even-keel-2`, below): the chain of one project would switch a slot to its branch under a live session of the other.
- **The main checkout.** Everything that touches `main` runs in it: the session's merge of its branch, `git sync` after Done, `commands.afterGreen`. Two chains running at once (`parallel`) would merge into the working copy while the other one syncs it, and a session would stop on a checkout that is not on `main` or has local changes.
- **What is counted by folder.** Tally groups sessions by folder; the tools panel reads `.claude/` and the `.claude.json` entries of the folder. Task worktrees are named by key and stay apart, but whatever runs in the main checkout would merge into one.

Lifting it would take slots named by key and the work on `main` serialized per folder; a clone costs only disk space.

## Projects of one remote (BTN-210, BTN-217)

Separate clones with the same remote are allowed, and so are their chains at once (`parallel`). Each project syncs on its own and waits for the verdict on its own pushes; what they share is the remote and the fix of its red `main`.

- **Checked on real git** (two and three clones of one bare remote, Even Keel's own `syncMain` and the user's `git-sync.sh` alias, `prepareWorktree`/`finishWorktree`): without the fast-forward at the launch, B's task branched off B's `main` from before A's push; a change to the same lines then failed B's `git sync` (`sync.merge` / `sync.alias`), B's `main` stayed diverged and the next task branched off it, so every later Done failed the same way. With `fastForwardMain` (above, "Task worktree") the task starts from A's push and the sync goes through. Two clones pushing at once: the one whose push lands second is rejected `[rejected] … (fetch first)`; the second try of the sync (above, "Cleanup after Done") merges and pushes, in both ways of syncing.
- **A conflict that remains** — two tasks of two projects changing the same lines at the same time — is `cleanup.syncFailed` in `leftovers`, as for any sync; the agent for it is BTN-155.
- **The group** (`MainCheckDeps.peers`, `remotePeers` in `src/projects/remotes.ts`): the other projects whose checkout has a remote in common with this one's (`remoteRef`: host and path, not the remote's name or the URL's form — TSK's remote is `forgejo`, DT's `origin`) and the same `branch`, so a release clone on `release/*` of the same remote is not one of them; it is not transitive. Read from `ProjectRemotes`, on the config's change and the CI's interval. A project with `ci.guard: false` is in no group: it neither holds nor is held.
- **The commits of a red `main` start after the group's green ones** (BTN-702). Each project keeps its own last green commit (`ci[<project>].green`), moved only by its own pushes; the report of a red push lists `git log <red> ^<green>…` over the green commits of the project and of its group that are behind the red one (`git merge-base --is-ancestor`; one past it or not fetched into the clone yet is left out). So commits another project's push already found green are no suspects; with none behind it, the latest 20 commits of `main`.
- **A red `main` holds the group, one fix for it** (BTN-217). The fix is the author's, as for a project alone: the project whose push came out red first. While it is live (`MainCheck.peerFix`: a fix session with its report, a fix task the tracker still lists, or a push of either awaiting its verdict), every other project of the group waits at its next launch (`heldByMain`, `ciWait = { commit: <red>, since: <fix began>, by: <author> }`, its own yellow line naming the author by `projectLabel`), and a red push of its own starts no second fix: the log says `<task> of <author> is already fixing main of the remote`. The fix's green push lets the whole group go; so does its end without one — dropped with "Skip", red after the fix (the author's chain halts with `ci.fixFailed`; the next red push of another project then starts that project's fix), or a fix task gone from the tracker with no push of it. Sessions of the other projects already at work are not touched (invariant 1; exception 7 stops only the author's). Each project still waits for the verdict on its own pushes; a push awaited is no hold on the others — only a red one is. Checked in tests only (`src/chain/remotegroup.test.ts`), not on the live service with a CI (`docs/unverified.md`).
- **The check without a CI and the commands after green** run once per push, in the clone of the project that pushed: the check before the merge in its task's place, the check of `main` in its next task's place, `commands.afterGreen` in its main checkout. A push of B that carries A's commits runs B's commands, not A's again. Commands that act on something outside the clone (deploy one service, restart one server) belong to one project of the remote, or the two may run them out of order.

## Several projects on one tracker project (BTN-172, BTN-73)

The project's tracker value names the place it reads when that is not the key (`TrackerProjectKey.alias`/`placeOf`, `docs/trackers.md`): a Huly project (`huly: BTN`), a Linear `TEAM/Project` or `TEAM/` (the whole team); the task ids stay the tracker's (`BTN-300`). Two projects on one Huly project were read in Windows Sandbox (2026-10-25), and two on one Linear team (`TT/`, the second added with a milestone, so the first yielded it) ran as live chains side by side on the host the same day: each took only its own tasks, an issue without a Linear project included. Since BTN-271 the key is only a label and the default tracker project, and two projects may share it — a release clone keeps the key of the main one. The service names projects by id ("State files" below). What stays refused:

- **One key on two repositories of a tracker whose task ids are made of the key** (GitHub, an adapter without `placeOf`): the two repositories would both have `ABC-12`. `keyElsewhere` in `src/config.ts`, `config.keyElsewhere` from `parseConfig` and `wizard.keyTaken` from the wizard's check. Two projects on one GitHub repository are fine: they read it once and split it by milestone like any shared place.
- **One place without a split by milestone** (`config.trackerProjectShared`, below), whatever the keys.

What the user sees of two projects of one key carries a distinguisher (`projectLabel` in `src/config.ts`): `ABC (<name>)`, else `ABC (<branch>)`, else `ABC (<first four of the id>)`, in the page's notices, the service log and the wizard's refusals; a project whose key is its own shows just the key. The fix session of a red main is `ABC-FIX` for the first project of the key in the config and `ABC_<first four of the id>-FIX` for the others (`fixStem`, `src/chain/fix.ts`), so its worktree and branch do not clash either. `mergeInto` may name a project by its key only while no other project but the release one has it; otherwise by id. The stats of Tally stay by key: the projects of one key are one project there (`firstByKey`).

- **One read.** Projects with the same place (`readKeyOf` in `src/config.ts`) and the same `active`/`terminal` statuses share one tracker request per poll (`chainTasks` in `src/tracker/start.ts`); each then keeps its own tasks.
- **Split by milestone.** The chain rules `requiredMilestones` and `excludedMilestones` (`ownsMilestone`, `src/chain/rules.ts`): a project takes only tasks in a required milestone, if any are named, and never one in an excluded milestone. Unlike the label rules, a task left out is not the project's at all — not read, shown, ordered or closed by it, and its blockers outside are another project's. Projects on one place must split it so that no task, with or without a milestone, is owned by both (`splitsMilestones`): one names the release's milestones in `requiredMilestones`, the other excludes them; otherwise `parseConfig` refuses the config with `config.trackerProjectShared`. A milestone both required and excluded is `config.milestoneBoth`. Milestones are compared by name, case and edge spaces aside; the settings panel offers the tracker's open milestones (`vocabulary.milestones`).
- **A milestone moved** in the tracker moves the task to the other project at the next poll; a session already running for it is left alone (a released task, as when a task leaves the chain).

## Carrying a release project forward (`mergeInto`, BTN-172, `src/chain/forward.ts`)

A project is a main one or a release one. A release project names in `mergeInto` the main project its branch merges into (`release/v0.1` of `even-keel-github` into `dev` of `even-keel`); it must be another project, and one that merges into none (`config.mergeInto`). Nothing merges into `main`: it moves only by the release's push, by hand.

- **One repository** (BTN-285, `sameRepository` in `src/projects/remotes.ts`). The two checkouts must share a remote (`remoteRef`, however each names it) or one must have a remote at the other's folder (a clone of a local checkout). A common history (`merge-base`) is not asked: it needs the fetch that would pull every object of a foreign repository in. "Merges into" offers only main projects of the same repository (`sameRepository` in the state; every main project until the remotes are read). Saving the settings reads both folders' remotes anew and refuses another repository with `config.mergeIntoForeign`; `parseConfig` has no git, so a hand-made `config-import` gets through, and the carry then fetches nothing and holds `forward.foreign` on the page.

- **When.** Every minute (`FORWARD_TICK_MS` in `src/service.ts`), for each pair: `git fetch` of the release branch from the release project's folder into a private ref (`refs/even-keel/forward/<KEY>`), so `FETCH_HEAD` is not raced; nothing to carry (`rev-list --count <branch>..<ref>` is 0) — done. Otherwise the merge waits until the main project's chain is quiet (`chainQuiet`): stopped, empty, or paused with its current session not working (`busy`/`waiting`), and neither cleaning up after Done (`closing`) nor waiting on a push of main (`ciWait`). Fixes pile up meanwhile and go in one merge; the page shows "N commits wait to go into X" on the release project (`forwards` in the state, `ForwardView`).
- **"Carry now"** (`forward/carry`) merges at once, quiet or not, and clears a hold. A session of the main project merging at that moment is the user's risk. While a carry session (below) is asked for or at work, it is refused with `forward.agent` and the page hides it.
- **The merge** runs in the main project's main checkout: it must be on the project's `branch` (`forward.notOnBranch`) with no tracked changes (`forward.dirty`) — otherwise it waits and says so. `git merge --no-edit -m "Merge branch '<release branch>' of <KEY> into <branch>"`, then `syncMain` with the project's remotes, as after Done. A failed push stays on the page (`last.push`) until a later forward tick confirms that every remote has the carry's merge commit, including when it was pushed by hand or by another task's sync. While that warning remains, the tick fetches each remote's branch into a private ref (`refs/even-keel/forward-push/<project id>`) and checks `merge-base --is-ancestor` against the commit recorded before the sync; later local commits do not keep the warning alive. A remote that cannot be read leaves the warning in place. The merge commit is made under the service's account (session 0 on Windows), which needs a git name and email — the same assumption as the changelog commit (`docs/unverified.md`).
- **A conflict** is `git merge --abort` at once: the checkout stays clean and the main chain goes on. The carry is held with `forward.conflict` (the files) or, when git failed with no conflicted file (a missing committer identity, say), with `forward.failed` and git's message as its detail (BTN-314), and nothing is tried until "Carry now", a carry session (below) or until the branch has the commits from a merge by hand — or, with the carry session asked for by itself (below), until the release branch moves. The hold lives in memory, not in the state database: after a restart the carry is tried once more, aborted again and held again.
- **CI.** The merged `dev` is pushed like any push of main and gets its CI; at this installation a green `dev` restarts the service, which is why the carry waits for a quiet chain and goes in batches.

### The carry session (BTN-369, `src/chain/carry.ts`)

"Resolve with the agent" on a held `forward.conflict` (`forward/resolve`, `ForwardMerger.resolve`; refused with `forward.noConflict` for `forward.failed` or no hold) asks for a session without a tracker task that merges the release commit into the main project's branch, modelled on the fix session above.

- **The name** is `<KEY>-CARRY` of the release project (`carryNameOf`, the same stem as `fixStem`: `EKR-CARRY`), used as a task id like `<KEY>-FIX` (`isOwnName` covers both): the worktree `.claude/worktrees/<key>-carry` and the branch `<key>-carry/task` of the main project, made from its `branch`, its own even in "slot" mode; the model and the account are the main project's. The name never reaches the tracker.
- **The record** is `ci[<release project>].carry = { task, into, at, commit, commits, report }` in the state database (`CarrySession`), so the carry survives a restart. `commit` is the release commit read from `refs/even-keel/forward/<from>` at the press; `report` is `carryReport` in the main project's `promptLanguage` — the ref and the commit, the conflicted files, git's output and the rule: the main branch's structure wins, the release fix's meaning goes on top. `carryPrompt` adds the worktree, the branch and the rules of the fix session (no task, no task ids in commits, merge into the branch yourself, the checks, stop background commands). A handover of the carry session carries the report again (`withReport`).
- **The order.** The carry goes after the current task of the main project's chain and after the task a fix interrupted, before the next by the chain's order; nothing is stopped for it. A main project with no active chain and not in the queue gets a chain with `fixOnly`. A red main does not stop a carry session at work: the fix waits for its turn behind it.
- **While it lives** the forward tick still fetches and counts but never merges, and "Carry now" is refused. The view of the release project carries `agent` (`ForwardView.agent`).
- **Done** is the main branch holding the release commit (`merge-base --is-ancestor <commit> refs/heads/<branch>`), with the session not mid-turn (a turn that ended on a background command does not hold it). Then the usual cleanup (`closeUp`), the record is dropped and the launch log gets `reason: 'carried'` with `commits`; the next forward tick finds nothing behind and lifts the hold.
- **"Skip"** on the carry session at the head of the chain (not mid-turn) drops the record and journals `'dropped'`; the session is not touched and the hold stays, so "Resolve with the agent" and "Carry now" come back. As with the fix session, the skipped session's id goes into `ci[<main project>].skippedSessions` and the next carry of the name starts a new session in the same worktree (BTN-692). "Skip" on a carry still waiting for its turn takes it back with nothing journaled.
- **By itself** (BTN-370): with the release project's `carryAgent` on, or in unattended mode, the merge that conflicts asks for the session at once, as the button would (`ForwardDeps.auto`); a `forward.failed` never does. Once per release commit (`askedAt`, in memory like the hold): a session skipped, or let go by unattended mode after ten quiet minutes (`Dispatcher.unanswered` → `MainCarry.letGo`, the same as "Skip": the record dropped, `'dropped'` journaled, the hold kept, the session untouched, BTN-693), gets no successor while the release branch stands — "Carry now" conflicting again asks for none either, the button still does. While the hold stands the tick reads the release commit (`rev-parse` of the ref) and tries the merge again once it differs from the one that failed (`failedAt`), so a new release fix brings a new session, the skipped one left alone (BTN-692). A switch turned on over a held conflict asks for it at the next tick. After a restart both are forgotten with the hold: the retried conflict asks once more.
- **The page.** The carry is a block of the main project's chain like the fix (`chainBlocks`): "Carry of EKR: the agent will resolve the conflict" while asked, "… resolves the conflict" while it leads, then a closed row "Carry of EKR: N commits" or "… skipped, the conflict waits" (lamp `done`, the forge's crossed hammers). Its episodes are `<KEY>-CARRY.<n>` in `fixes` of the main project. The banner on the release project is in `docs/web.md`.

## "Slot" mode (`src/git/slot.ts`)

- `"slot": true` or a number of slots on a project — a pool of permanent worktrees per repository instead of a new one for each task: `.claude/worktrees/even-keel`, then `even-keel-2`, `even-keel-3`… (`true` — one). Ignored caches (Unity `Library`, `node_modules`) survive a task, and the first run of a new one processes only the difference; an extra slot is needed so that the live session of a released task (skipped, postponed by a blocker) stays in its own and is not stopped. The chain still leads one task at a time.
- Preparation: if a slot is already on the task's branch (`<key>-<number>/…`), it is used as is, even dirty. Otherwise, for each slot: a dirty one (`git status --porcelain` is not empty) or one with a session of another task mid-turn (`busy`/`waiting`, by the launch log, `src/sessions/occupants.ts`) is unfit. Of the fit ones, in order of preference: detached from a branch without foreign live sessions, on a foreign branch without them, not yet created (`git worktree add --detach <slot> main`), with idle sessions of other tasks — they get `claude stop` (the fifth exception to invariant 1); on a tie, the one with the lower number. If none is fit — a launch error, the chain is paused with the paths and reasons, and the slots are not touched. In unattended mode the chain is not paused: it stays running with `slotWait` (a yellow line with the same reasons on the page, one line in the service log) and tries the launch again at most every 30 s; the task is not released, since it never started. Then `git clean -fd` (without `-x`) and `git switch <branch>` or `git switch -c <branch> main`.
- After Done, a slot on the task's branch gets `git switch --detach main` (a dirty one stays on the branch, the branch is not deleted, a warning), then the branch, origin and `git sync`, as without a slot; the slot folder is not deleted. Slots on foreign branches (cleanup of a released task) are not touched, only the branch is deleted. `claude stop` after Done in a slot applies only to this task's sessions by the launch log.
- The number of slots changes on the fly (BTN-130); when it is reduced, Even Keel takes no new task into the extra folders, but still finds a busy task in one and cleans it after Done (`slotSpan` in `src/service.ts`: the most slots the project had since the start). A task's own worktree left over from the previous mode is taken and cleaned the old way.

## The exceptions to invariant 1 in detail

Exception 1 also covers detected paid subscription usage (BTN-577, `OverageStops.guard`). Before following the chain, even while it is paused or waiting for Stop after turn, fresh evidence can stop only its current live session mid-turn through its own `Agent.stop`. Detection is described in [accounts.md](accounts.md#stopping-paid-subscription-usage-btn-577). An in-flight move is recovered first. The persisted `LimitHold.overage` keeps the full `LimitedSession` snapshot and successful-stop marker; the snapshot supports recovery even after the session vanishes, including a handoff interrupted by a service restart. Once stopped it waits without repeated stops or immediate relaunches; an unknown reset stays unknown rather than entering the unknown-limit retry ladder. A new account whose included window is still exhausted (also a shared ChatGPT pool) keeps the wait. Once usable, the usual warm resume/cold handoff keeps the worktree, branch and context without stopping the old process again. Pausing still holds continuation, and unattended mode never skips this retained wait. Actual paid-provider execution remains [unverified](unverified.md#paid-subscription-usage-stops).

Exception 1 also covers a temporary model or service refusal (`apiError.kind: transient`, BTN-498). For the current session of an unpaused chain, `Handovers.followTransient` uses `LimitRetries` per session: 15 minutes, doubling after another refusal up to four hours, reset after a successful answer or a human continuation. It resumes the same session with a short continuation prompt, even if the cache has cooled; it does not create a handoff. No retry mid-turn, during a move, without a ready account or while launches are blocked. A chat answer or "New session" cancels the scheduled retry; the last continuation time keeps an old transcript refusal from scheduling it again. The existing limit hold carries the next attempt time on the page and through a restart; the ladder itself is in memory. This is an overload retry, independent of account usage windows and API credit checks. A real provider outage has not yet exercised the full path ([unverified](unverified.md#temporary-model-errors-btn-498)).

1. **Limit** on the session of the current task of an unpaused chain: a minute after the limit resets (an agent may round the reset down to the minute; a reset already over a minute gone at the refusal waits 10 minutes from it, EKR-34, `docs/sessions.md`) or once the account is switched, the dispatcher continues it via `--resume` if the cache is still warm (the same account, within the session's warm window since the last response: 55 min for Claude on a subscription, 25 for Codex and Copilot, `docs/sessions.md`, "Every agent's cache"), otherwise it stops it (`claude stop`, not `rm`) and starts a new one in its working folder with a handoff (`src/chain/relay.ts`). A limit is both the `rate_limit` error and the CLI's soft warning (`usageLimitNote: "wrap_up"`), after which the session wraps up its turn on its own. The reset time comes from the limit's text; the warning has none and comes before the window shows 100%, so it comes from the limits of the session's account polled after the limit (`limitResetAfter`, `src/limits/model.ts`): the exhausted window's reset, else the end of the five-hour window the limit fell into, or the start of a newer one. Until such limits arrive the reset is unknown (`resetsAt: null`, the page says only an account switch helps) and is asked for again on every check. A provider may reset limits early (BTN-530): a poll of the account taken after the refusal that shows it open again ends the wait as the reset would, a minute after the poll (`limitReopenedAt`, `src/limits/model.ts`; `Handovers.reopenEarly`). ChatGPT's `wham/usage` says so itself (`rate_limit.allowed: true`, `limit_reached: false`, `RateLimits.open`); a Claude `/usage` reading counts when no window is at 100% and none resets within an hour of the named reset — a window started over resets later. A poll less than 10 minutes before the named reset is no early reset (`REOPEN_MARGIN_MS`): `/usage` drops the window minutes before the CLI lets requests through. A statusline, a session's `rate_limit_event`, Copilot, keys, spending caps and paid-usage stops keep their own paths. An account whose limit nothing tells — no window known and its poll said there is nothing to read (`noKnownLimit`: OpenCode Zen, Copilot signed in on the machine, BTN-342) — is tried again instead (`LimitRetries`, `src/limits/retry.ts`): 15 minutes after the hit, the wait doubling up to 4 hours while each retry hits the limit again, back to 15 minutes once the account worked longer than its last wait; in memory, so a restart starts over. The working folder and the branch for the handoff come from git (the worktree root from the last `cwd`), not from the transcript: its `gitBranch` is the branch of the launch folder. A repository nested in the launch folder that is not a worktree of the same repository (another common git dir — a clone the session made under `.temp/`) is skipped for the one around it (`locateWorktree`): otherwise the new session would start in the clone, and the CLI refuses a folder not trusted on its own. A session on an API account (`docs/accounts.md`) has no windows to wait out, so its `rate_limit` stops it like any error; it is held on spent credit (`billing_error`, `apiError.kind` `credit`, BTN-165) and a spending cap (`apiError.kind` `spend`, BTN-382). A spending cap takes its explicit UTC reset from the refusal and keeps the five-minute key checks active: a 2xx permits an earlier resume or handoff. For spent credit the "reset" is the moment a check of the key finds credit again (`limitRecovery` in `src/limits/recovery.ts` asks `AccountWatcher.creditBackAfter`), and the cache is warm by the session's own window (`HandoffSession.warmMs`): a Claude key's is under 55 min with a 1-hour cache in the transcript, else under 4 min, since a key writes the 5-minute cache unless `cacheTtl` is `1h`. A switch of the account hands over at once, as on a limit.
   The service log records each new limit once, with the task, account folder, reset time (or `reset unknown`) and the planned continuation. A learned or earlier reset is logged with the updated plan. Successful continuation records the actual resume or handoff and the resulting session id (also the previous id for a handoff); failed attempts use the chain's pause log.
2. **"New session"** (`restart`): the user replaces the session of the current task if it is not mid-turn — the same handoff, with `restart` in the log, referencing the previous session. A working turn silent for five minutes can also be interrupted, after explicit confirmation tied to that session and its last write; new output invalidates the confirmation, including while the replacement is queued. This is still a user-requested replacement, never an automatic stop. After thirty quiet minutes the turn is treated as hung and the usual replacement needs no confirmation. "Skip" remains refused mid-turn.
3. **Checkpoint** that the session set itself: the session of the current task of an unpaused chain finished a turn, and the last line of its last response is `CHECKPOINT: <path>` (that is what the hook of the `checkpoint@even-keel` plugin, `plugins/checkpoint`, asks for when the context has grown; its `Stop` hook sends back a session that wrote the note but ended with a report instead of the mark). The dispatcher does the same handoff, with the path to the note from the worktree root in the prompt and `checkpoint` in the log, referencing the previous session. A mark followed by a tool call, a new response without the mark, or a message to the session cancels it. The handoff repeats as many times as sessions ask for it; the number of handoffs per task is visible on the page, and after the third one the hook asks only from 300k (`docs/sessions.md`, "Checkpoint threshold"). A session with a limit goes by the limit rule (its prompt also points at the note), and while the limit is used up or new sessions are not started, the mark waits.
4. **Task in Done**: when its session has finished a turn and is not waiting for a reply (not `busy`/`waiting`; a turn that ended on a background command counts as finished), the dispatcher stops it (`claude stop`, not `rm`; the transcript stays, `--resume` by hand is possible) and removes the worktree. A task with nothing to merge gets to Done by its session's `NO CHANGES:` mark (EKR-10, "Nothing to merge" above) and goes the same way. A session the monitor has not read since the service's start is neither: its status is unknown, so nothing is stopped or removed until the first read (BTN-646, "The first read of the sessions" above). A session in the task's folder the cleanup found mid-turn is stopped once that turn ends (BTN-616, "A session left mid-turn" above). After the merge, sessions make no more than a couple of checks in the same turn and finish with a report (measured from transcripts, 2026-09-29).
5. **A slot is switched** to another task's branch (only when the pool has no free slot): the dispatcher first stops the live sessions of released tasks (skipped, postponed by a blocker) in the slot (`claude stop`, not `rm`), otherwise the answer to such a session through Remote Control would land in another task's branch. If such a session is mid-turn (`busy`/`waiting`), the slot is not switched and the chain is paused with its task (unattended — it waits for the slot the same way as when none is fit).
6. **The user's answer** (BTN-101) from the chat window (`POST /api/session/answer`, `docs/web.md`) or from tracker comments posted after the question Even Keel put there (`TrackerQuestions`, `docs/trackers.md`). A pending `AskUserQuestion` cannot be closed from outside, so the dispatcher stops the session (`claude stop`, not `rm`) and continues it via `--resume` with the answer; the stop loses the session's last message, which the CLI had not written yet, so the prompt repeats the question (`docs/sessions.md`) (`Dispatcher.answer` → `deliver`, the same path as after a limit; `answer` in the launch log, referencing the previous session; `resumedAt` is reset). `Dispatcher.answerable` refuses unless all hold: the task is the current one of its chain (`chain.notCurrent`) and is not being launched (`chain.launching`) — or the project's chain is stopped and the task's session lives on (the page marks such a row `loose` and keeps its chat; `Handovers.deliverLoose` resumes it and journals `answer`, a failure only goes to the log); the session is still the one the user answered and waits on the same open question (`ask` id, or none for a question in plain text) — otherwise `answer.moved` (say, the user already answered through Remote Control); it is not mid-turn (`answer.busy`); launches are allowed and the limit is not spent (`chain.limitSpent`). Files are saved first into `.temp/inbox/` of the task's folder (`src/sessions/inbox.ts`); the prompt is `replyPrompt` (`docs/sessions.md`).
7. **A red main** with `ci.fixTask` off (BTN-115): the session of the current task that is mid-turn is stopped (`claude stop`, not `rm`) so that it does not work on a broken `main`, and continued with a message once the fix session has landed. Detected paid subscription usage under exception 1 also permits a mid-turn stop. A session that waits for an answer is not stopped: a new message would wipe its open question. In detail — "The fix session" above.
8. **Feedback on a pull request** in PR mode (BTN-205): the review, failed run or conflict the poll found goes to the task's session only while it is not mid-turn — `--resume` with it while the cache is warm (the same account, within the session's warm window as in exception 1), otherwise `claude stop` and a new session with a handoff carrying it. A mark on a branch with nothing beyond main and uncommitted work, or one whose push is refused as behind the branch on the forge (BTN-716), is told to its session by `--resume`; with a clean worktree the task goes to Done and its sessions go as exception 4 has them (BTN-222). A pull request closed unmerged stops the task's resting sessions at its cleanup, as a Done does. In detail — "PR mode" above.
9. **A task back from an inactive status** (BTN-245): the current task left the chain for an inactive status (Backlog and the like) while its session was not mid-turn and waited on no `AskUserQuestion` of its own — the case of unattended mode, where the session asks in a tracker comment, moves the task to Backlog and ends its turn in plain text. The dispatcher remembers the task and its session in `shelved` (`shelve` in `src/chain/shelved.ts`; releases by a blocker or "Skip" are remembered with their own reason, exception 10; "Stop" is not remembered). When the task is back in an active status and the chain takes it, the old session is not adopted: `claude stop` and a new session with a handoff (`returned` in `src/chain/shelved.ts` → `Handovers.handOverCurrent` with `returned`; `relay` in the launch log and the snapshot, as after a limit with a cold cache), whose prompt says the task came back from the user after a question and the answer is in the description or the comments after it — read them in spite of the tracker skill's rule against the activity feed. The answer in a comment is not one of Even Keel's tracker answers (exception 6 reads only those to questions it posted itself), and the old session's cache is cold by then. The old session is adopted as before, with no stop, if by then it is mid-turn, waits on an `AskUserQuestion`, or its feed has a prompt or an answer after the task left (someone talked to it — through Remote Control or the chat of a stopped chain). A busy session keeps its task in the chain (`enters`), so a task leaves only once its session's turn has ended. A handover waits for the account's limit and the project's packages like a launch, and does not wait for the CI of main, like a relay after a limit. `shelved` goes with `released`: a take of the task or its cleanup forgets it.

10. **A task returned after a blocker or skip** (BTN-547): releasing the current task with `postpone` or `skip` remembers its session, time, reason and blockers in `shelved`, unless it waits on its own `AskUserQuestion`. The release itself only stops waiting. Once the task is eligible again and the chain takes it, the same safeguards as exception 9 apply: no turn in progress, no open question, and no prompt or answer since the release. Otherwise the old session is adopted. Eligible idle sessions are stopped through the agent and replaced with a handoff on the same branch and worktree. The launch log records `relay` with cause `unblocked` or `unskipped`; the snapshot keeps that distinct reason. An unblocked prompt names the closed blockers; an unskipped one explains that Skip was undone, without assuming a Backlog question. Limits and packages hold the handover as in exception 9; an interrupted move retains its reason and blocker context for recovery. Taking or cleaning up the task clears the shelf record.

**An answer to a permission dialog** (BTN-269) is the other write without a stop, and the user's explicit act as in exception 6. A Claude session that waits on a permission dialog while the `checkpoint` plugin's hook holds it (`docs/sessions.md`, "Permission dialogs") has the call as its question; an answer from the page or a tracker comment goes through `Dispatcher.answer` as any answer, but `resumeWith` hands the decision to the hook instead of stopping and resuming, so the session goes on in the same turn with the same id. Nothing else decides such a call — but unattended mode, where nobody is at the page and the call is refused at once, as for an SDK session (BTN-303).

**A message to a working session** (BTN-181) is the third write to a session without a stop. A chat message in plain text to the current task's session while it is mid-turn (`busy`) is refused with `answer.busy` unless the session steers or its hooks have asked for mail since the service started (`Mailbox.listens`): then `Dispatcher.answerable` gives `midTurn` instead of the refusal, skipping the launch and limit checks since nothing is launched. A session that steers (`AgentEntry.steers`, an SDK session, BTN-291) gets the message straight into its live CLI by `Agent.reply` and takes it after the running tool call, in the same turn, with no mailbox; otherwise the message goes into the `mailbox` table. A hook of `checkpoint@even-keel` takes it on the session's next tool call or stop and hands it over without ending the turn (`docs/sessions.md`, "Chat mailbox"). A session waiting on a question gets the chat as an answer (exception 6), never mail. When the hooks miss the message — the turn ended, or the session asked, before the next tool call — the mailbox settles it once the session is no longer mid-turn and 10 s have passed since the post: a turn ended without a question gets it by `--resume`, like an answer (`Dispatcher.answer`, `resume` as its event); a session that asked meanwhile, or is gone, gets nothing — the message goes back to the chat window, and the user sends it as the answer or dismisses it. A task over for the chain (BTN-558) — done in the tracker's last read or after its cleanup, or its branch merged into the main branch before the tracker knows (`Dispatcher.closed`, the same `merged` check as the CI of main) — gets no message at all: whatever it asks would land uncommitted in the worktree of a closed task, which no merge closes again. The chat refuses such a send at once with `answer.closed`, an answer to a question included; a message posted before the merge goes neither to the hook (`mailFor` returns nothing) nor by `--resume`, and comes back to the chat with the reason `closed`, without "As the answer" — what it asks is a new task.

**A keep-warm ping** (BTN-437, `src/sessions/keepwarm.ts`) is the touch that neither stops nor writes: the session is only read. With "Keep the cache of a waiting session warm, hours" (`keepWarm`, Even Keel's own, 0 — off, the default until its live check) above zero, a check every 30 s takes the sessions a running chain will go on in (`warmTasks`): the current task's session of each unpaused, unhalted chain not waiting on a limit, unless the task is starting or being moved (`starting`); a temporary model error scheduled for a resume remains eligible, and the live session of each task whose pull request is open in such a chain's project. Only an agent with `Agent.warm` (Claude Code, Codex) is pinged. The decision is made in one place (`warmStep`) from facts read anew at each check — the transcript's cache window (`SessionView.cache`), mid-turn (`agentStatus`, a resume hold), a limit lamp, an open `AskUserQuestion` (`SessionView.asking`): no ping mid-turn, on a limit, of a session waiting on `AskUserQuestion` (a fork of such a `--bg` session read 0 of its prompt from the cache, BTN-704), or of a cache already cold; a ping 5 minutes before an hour or a half-hour cache (Codex's) ends, 1 minute before a five-minute one. The ceilings: `keepWarm` hours since the session's last answer, and the break-even — 20 pings of an hour cache, 12 of a half-hour or a five-minute one, after which a miss would have been cheaper. A ping that read under 90% of its prompt from the cache, or failed for a non-transient reason, turns pinging off for that session until a restart. An overload refusal skips that ping without disabling the session or claiming a cache hit; it can be tried again on the next check while the cache stays warm. What was sent is in memory, so after a restart a cache looks cold and is let go.
The ping itself is a fork: `claude -p --resume <id> --fork-session --no-session-persistence --max-turns 1 --permission-mode dontAsk` with the session's model, packages and `--settings` plus `disableAllHooks` for a `--bg` session, the SDK's `query` with `forkSession`, `persistSession: false` and every tool call denied for an SDK one, `codex exec --ephemeral --sandbox read-only --disable hooks … fork <id> -` with the session's model, servers and packages for a Codex one (`docs/sessions.md`, "Keep-warm"). It writes no transcript, so neither the page nor Tally sees it; the service log has a `keepwarm:` line per ping. A ping that read the cache counts as the session's last moment of warmth for the chain's own warm checks (`HandoffSession.warmedAt`, `warmSince`): an answer, PR feedback or the end of a main fix an hour after the last answer still goes by `--resume` if a ping kept the cache since.

**A service restart in the middle of a move** (BTN-164). While the dispatcher resumes or replaces the session of a running task (exceptions 1–3, 6 and 9–10), `CurrentTask` holds `starting`, the kind of move (`move`: `answer`, `resume`, `relay`, `restart`, `checkpoint`, `returned`, `unblocked`, `unskipped`) and, for an answer, its text and the question it answers (`reply`, `ask`). Loading the state keeps them for a task with a session (a cut first launch is still dropped and pauses the chain with `chain.interrupted`), and the chain's next step sees the move through (`Handovers.recover`) before the limit and the checkpoint: no session of the task read yet — it waits; the task already has another session — the chain takes it and journals the move; the old session works, replied after the move began or waits on another question — the move went through (an answer or a resume is journaled); otherwise the move is made again — the answer delivered once more, "New session" and the handover of a returned task repeated with the same reason and blocker context, the limit step redone, and a checkpoint left to its mark, which is still the last line. Within one process the step never sees these marks: moves and steps run one after another. The marks are transient like `answering`, so they did not change `SCHEMA_VERSION`.

In every exception a session `claude agents` shows `failed` or `stopped` is stopped as well while its process lives (`pid` from a live `sessions/<pid>.json`): a session that failed at start (an API 400) keeps running, and `claude stop` run from a terminal marks the job `stopped` without reaching the service's daemon (`isGone` in `src/claude/cli.ts`, `stopTaskSessions`, `slotOccupants`). The other way round, a job the CLI still shows `blocked` after its daemon dropped it and exited is gone and needs no stop (`abandoned`, `docs/sessions.md`).

Every handoff (limit, "New session", checkpoint, a returned task, a task unblocked or unskipped) leaves a snapshot `<state>/handoffs/<new session>.json` (`src/chain/snapshots.ts`): the whole prompt, the note's path and its text as read just before the launch, the reason in the launch log's words and the previous session. The note itself is overwritten by the next handoff and goes with the worktree; Tally loads the snapshots into `handoffs` (`docs/tally.md`). A failed save is a warning in the log, the handoff goes on.

A handoff from a session that never answered (BTN-650: no `lastReplyAt` and no text or tool line — a bad key, no credit, a refusal at the start) carries what the session before it left. `Handovers.handOver` remembers, by task, the session each handover started and the answered session it carried on from (`HandoffSession` with its transcript path, in its own account's folder); a handover from that failed session takes the steps, the last message, the note and the main transcript from the remembered one, and adds a line per failed session after it with its last API error and its transcript (`answered`, `failedOf`, `PromptTexts.failed` in `src/chain/relay.ts`). Several failed ones in a row add up. The folder, the branch, the stop and the reason stay the failed session's. The memory does not outlive a service restart: then the handoff carries the failed session alone, as before ([unverified](unverified.md#a-handoff-past-a-failed-session-btn-650)).

The dispatcher may stop waiting for a session (without touching it) if it is not mid-turn (`busy`/`waiting`): the current task got an open blocker from the same chain (the session postponed it itself, `postpone` in the log) or the user pressed "Skip" (`skip`). The chain does not take a skipped task until the user returns it or it leaves the chain in the tracker (closed, in Backlog). On return, an idle session with no question and no messages since the release gets a new session with a handoff (exception 10); an active conversation keeps its old session. "Skip" is refused for any task whose session is mid-turn, also one released by "Stop": otherwise a restarted chain would launch the next task beside it instead of taking the live session again.

## What the dispatcher owns (invariant 2)

The tracker is the source of truth for statuses; the dispatcher keeps no status of its own. It owns only: the chain order, the pause, the list of skipped tasks, released tasks awaiting cleanup and their resting sessions eligible for a handover on return (`shelved`, including the release reason and blockers), cleanup warnings, unattended mode, the "trim the tools" switch, the questions it posted to the tracker, the pull requests it opened for tasks in PR mode, the GitHub issues it took into a tracker until they are closed (`docs/trackers.md`), the carries of release projects it holds after a conflict (in memory, "Carrying a release project forward"), the tasks it closed by a merge with the commits `main` had of their branches then (`merge_closes`, "Cleanup after Done") and the CI verdicts on main: the last green commit, the push it waits on (for the CI or for the project's own check) and the fix of a red main — the session it started for it, or the task it created — with the task whose session it stopped for the fix, and the fix and carry sessions the user skipped, until their worktree is cleaned up (`skippedSessions`). Something new the dispatcher must remember goes on this list, never into a status.

## Unattended mode (`unattended`)

A switch on `/settings`, the Chain group — for when nobody is there to answer, for example at night. Stored in `state/chain.json` (`unattended`, the command `chain/unattended` with `{ on }`); when on, there is the banner `UnattendedBanner`.

- `PROMPTS.unattended` (`src/chain/prompts.ts`) is appended to every prompt — launch, `--resume`, handoff: ask no questions, do everything that the question does not hold up; a question with a default option — as usual (finish and merge, the question as a task); a task that cannot be finished without an answer — commit it to its branch until `git status` is clean, do not merge, put the question with options in a comment, add the question label, and as the last step move to Backlog (the post-commit hook moves the status forward, so after the commit and with a check). Sessions started before it was turned on do not get the text — only with the nearest `--resume` or handoff.
- A task in Backlog drops out of the chain like any returned to an inactive status: it is released, and the worktree or slot with its branch stays. Moved back to Todo once the user has answered, it gets a new session with a handoff that points at the answer, not the old session (exception 9). A clean tree matters in "slot" mode: a dirty slot is not taken, and a couple of parked tasks with litter would stop the chain.
- A safeguard in the dispatcher (`Dispatcher.unanswered`): the session of the current task finished a turn or is waiting for a reply (not `busy`), without a limit or checkpoint, and 10 minutes of silence — counted from the last response, from when the chain took the task, and from the last `--resume` or handover by a checkpoint or "New session" (`resumedAt`), whichever is later — the task is skipped, as with the "Skip" button (`skip` in the log). The dispatcher does not touch the session. So the night does not stand still if the session did ask or a hook returned the status. A merged task goes to Done within seconds, and the 10 minutes do not touch it. A carry session (`<KEY>-CARRY`) is let go the same way, as its "Skip" would ("The carry session", BTN-693). A fix session (`<KEY>-FIX`) is not: its "Skip" lets the chain launch tasks on a red main, so an idle fix holds the chain until the user answers or skips it.
- The chain also does not wait for a task in Done (`closing`) longer than 10 quiet minutes (`Dispatcher.quietTooLong`, from the session's last response): the task goes to `released`, its cleanup is done by the released-task sweep when the session is not mid-turn, and the chain goes on. The dispatcher does not touch the session.
- **Background command.** The CLI writes the status `shell` into `sessions/<pid>.json` when the turn is over but a background command started by the session (`run_in_background`) is still running; when it ends, the session gets a notification and continues. For the chain such a session is mid-turn (`turnStatus`, `src/sessions/agents.ts`): a long run of 15–20 minutes is neither skipped nor cleaned up. An hour without a new line in the transcript — the command counts as hung, the session as idle. A turn that ended on a limit is the exception: the session is idle and goes by the limit rule at once (the lamp is `limit`), otherwise a command that never ends, a dev server, would hold the chain for good. A turn that ended on the user is the other: the CLI's summary marks the job `state: blocked` (`jobs/<id>/state.json`), and with `shell` under it the session waits (the lamp is `waiting`, the status `waiting`). Seen on 2026-10-22: a session ended its turn with "waiting for you to press Start" and a `Monitor` on the service log, and the page showed it working for half an hour until the monitor ran out and the session asked again. A slot with a session in `shell` is always occupied.

  The end of the work is the other exception (BTN-202): a task in Done (`closing` and released tasks) and a fix session whose branch is in `main` do not wait for a session in `shell` — the status itself says the turn is over, and the merge or Done says the work is. `DispatcherDeps.shell` tells the raw status apart from the `busy` that `turnStatus` makes of it; `Cleanups.working` (`src/chain/cleanup.ts`) and `MainFix.follow` use it. The cleanup then stops the session (`stopTaskSessions` takes `shell` as idle). A `NO CHANGES:` mark ("Nothing to merge" above) says the work is over too (BTN-637): `Unchanged.follow` does not wait for `shell` and checks the folder; a clean one moves the task to Done, while commits or uncommitted changes wait for the session as before — the mark is not remembered, and the session is told once its command ends or counts as hung. Without the merge, Done or the mark, `shell` holds for the hour as before. Seen on 2026-10-31 on Linux: a session ended its turn with the mark and a `run_in_background` command still running, and the chain stood. Seen on 2026-10-18: a fix session merged and ended its turn with two `until grep … ci.log` loops left running, and the chain would have stood for an hour.

  `claude stop` ends the session's process but not its background commands: on Windows (CLI 2.1.302) the `bash.exe` of a `run_in_background` command outlived it, holding the worktree. `ClaudeCli.stop` therefore takes the session's process tree (`descendantsOf`, `src/claude/tree.ts`: `ps` before the stop, since an orphan there no longer leads back to its dead parent; `Get-CimInstance Win32_Process` on Windows alongside the stop, since it takes 1–2 s and Windows keeps an orphan's `ParentProcessId`) and kills what is still alive once the session is gone (`killLeftovers`: only live pids, all at once — a `taskkill` costs ~0.5 s even on a dead one, and most exit with the session).

## State files and the schema version (BTN-132)

Since BTN-147 the chain state, the questions, the launch log and the handoff snapshots are in the state database (`state/even-keel/`, `docs/storage.md`); the files below are what v0.1 kept and what the first start of the new version imports. The config, `account.json`, `packages.json`, `rate-limits.json` and `codex/` stay files.

- A project has a key (`ABC`, not unique since BTN-271) and an id (`projects[].id`, a GUID that never changes). The state and the running service name a project by its id: the database (`project_id` of its tables) and before it `state/chain.json` (`active[].project`, `queue`, the keys of `orders`, `skipped`, `leftovers`, `released`, `ci`) and `state/launches.jsonl` (`project`), every map of `EvenKeelConfig` (`config.keys` gives the key of each id), the dispatcher, the page's state and its URLs. Task IDs, branches and worktrees go by the key, the tracker adapters get each id's key and value (`TrackerPlace`); nothing translates at the store's edge any more. An id the config does not have — a removed project — stays as it is.
- Every file carries the schema version (`SCHEMA_VERSION`, `src/storage/schema.ts`): `version` in the config, `chain.json`, `questions.json` (`{ version, questions }`), `account.json`, and the first line `{"version":<N>}` of `launches.jsonl`. A file newer than the code is refused (`storage.newer`). The database has its own version (`PRAGMA user_version`, `docs/storage.md`).
- `upgradeStorage` (`src/storage/migrations.ts`) runs in `src/main.ts` before `src/service.ts` is imported: it reads all the files, migrates them step by step to the current version, checks the config with `parseConfig`, keeps `<file>.v<N>.bak` copies and writes all of them, restoring the written ones if a write fails. It also writes an id into a project entry added by hand without one. Any refusal (`storage.newer`, `storage.damaged`, `storage.unknownProject` — a project of the state the config lacks, `storage.writeFailed`) starts only the blocked page server (`createBlockedServer`, `src/server.ts`): the page from `dist/web`, `/api/events` sends `blocked` with the reason, the rest of `/api` is 503. Right after it `prepareDatabase` brings the database to its schema or imports the files into it; its refusals (`storage.newerDatabase`, `storage.importFailed`) block the same way.
- A format change is a new schema version, a migration step and a new frozen sample in `test/fixtures/schema-v<N>/` (`src/storage/fixtures.test.ts`); old steps and samples are never edited or removed.
- Schema v8 (BTN-173, run profiles, `docs/sessions.md`): `configV8` turns a project's `agent` into `provider` and `codexModel` into `models.codex`, the shared `model` into `models.claude`, a project's `codexBypassSandbox` (any project on) into the shared `execution.codex: "bypass"`, and moves `active` of `state/account.json` into the shared `accounts.claude`. A launch log entry may carry `fallback` — the provider of the task's run label the pool had no account for (`fallbacksSince` gives the page the last 24 hours of them).

## End-to-end tests (`src/e2e/`, BTN-571)

The unit tests of `src/chain/` go through `setup()` of `dispatcher.fixture.ts`, where every dependency of the dispatcher is a fake. `src/e2e/chain.test.ts` runs the assembled service instead: `src/main.ts` imported as the service starts, real git in a temporary folder (worktrees, merges, cleanup after Done), the real PGlite state database, the service's own HTTP server for the page's commands. The scenarios are out of `npm test` (BTN-699): `npm run test:e2e` runs them alone, `npm run test:all` both. A session runs before its merge only the files of the area it touched (the table below); the whole of `src/e2e/` runs on CI as a job of its own (`docs/ci.md`, "This repository's workflows"), and a scenario of another area broken by a merge shows up there as a red `main`. Vitest runs files side by side, not the scenarios inside one, so a file is kept to about two minutes and split by topic past that. On the author's 12-core workstation (2026-11-02) `test:e2e` takes 4 min 42 s, the longest files `accounts.test.ts` and `feedback.test.ts` two minutes each; before the split it was 5 min 49 s with `ci.test.ts` at 5.5 minutes, and inside the whole suite each scenario ran about twice as long as alone. One file is `npx vitest run src/e2e/ci-fix`: a filter after `npm test --` cannot reach `src/e2e/`.

- `Harness` (`service.fixture.ts`) prepares the folder, the config and the environment, imports the service on a fresh module graph (`vi.resetModules`) and reaches it through `service` of `src/service.ts`. `restart()` closes it and imports it again on the same folder. The timers and `Date` are fake: `until` moves the clock step by step, and after each step waits in real time while git or a file read is under way (`process.getActiveResourcesInfo`); without it, on a loaded machine the clock runs ahead of a tracker refresh that has not come back, and the scenario times out. The step ends once neither has run for 2 ms, polled by `setImmediate`: a timer of a few ms lasts ~15 ms on Windows, and two of them made a quiet step 40 ms. What is left of a step is the service's own git — none of it runs on every tick: the CI watch reads the remote's main every 5 s, the work poll lists worktrees every 15 s, the remotes are read every minute; the rest is the task's own (worktree, sync, push, cleanup), ~60 calls a task, 15,000 over the suite (BTN-700). The real time a scenario takes grows with its steps, not with the service's time it covers, and next to the other files each step and the import of the service (up to a minute) take several times longer than alone; so a long wait goes in big steps (10 minutes) up to a little before the moment it checks and in minutes from there, and waits no longer than the logic needs (BTN-676: the cold-cache limit resets an hour after the last reply, not three).
- `Board` (`tracker.fixture.ts`) is the tracker: an adapter registered in `ADAPTERS` under `board`, its tasks in memory, `blockedBy` for the order, comments kept per task. It has the optional parts of `TaskSource` the chain uses (BTN-672): labels (`label`, `relabel` through the page), statuses moved by the user (`move`) or by the service (`moveTo`, `ready`, `unready`; the adapter `moves`), subtasks (`child`, `children`), a `complete` into a named done status. Flags of the scenario: `refuseComplete` and `refuseRelabel` make those calls throw, `failReads` every read of tasks; `completions` counts the closes asked for. `create` files a task as `<KEY>-101` and on in Todo, keeping what the service asked for in `created` (the fix task of `ci.fixTask`); `keys` gives each project only the tasks of its key, so two projects share the board.
- **The forge and the CI** (BTN-664). With `Harness.forge` set before `start` the checkout is a clone of a bare repository `remote`: its `origin` is `http://127.0.0.1:9/john/example.git`, where nothing listens, and `url.<bare>.insteadOf` in the checkout's config leads git to the bare repository, while the service reads the address as a Forgejo remote (a committed `.forgejo/workflows/ci.yml`, `FORGEJO_TOKEN` in the environment made a Forgejo profile at the first start). `GIT_CONFIG_GLOBAL` points at a file of the bench, so the sync after Done is the built-in fetch, merge and push, not the machine's `git sync` alias, and the machine's hooks path is out of the way. `Ci` (`ci.fixture.ts`) is put into `CI_SOURCES` (`src/ci/adapters.ts`) in place of the Forgejo adapter on every start: each poll looks at the head of the branch in the bare repository and makes one run per new head, its status from `outcome(subject, commit)` (`success`, `failure`, `queued`, `running`, or `null` — no run); `finish(subject, status)` ends a run under way; a failed run has one job whose log is `log`. A poll without a branch — PR mode's look at a pull request's head — makes the runs of every branch of the bare repository.
- **The forge's pull requests** (BTN-683). `Pulls` (`forge.fixture.ts`, `Harness.pulls`) keeps the bench's pull requests in memory and answers as the Forgejo API through its own `fetch`; with `forge` set the start puts the real `forgejoPulls` over that `fetch` into `FORGES` (`src/review/wiring.ts`), so trust by access and the session's own words run the adapter's code, not a second `Forge`. Heads and mergeability come from the bare repository (`merge-tree --write-tree`); `merge(n)` makes a real merge commit there, `close(n)` closes unmerged; `comment` and `review` (with line comments) leave remarks; `access` gives an account other than `OWNER` `write` or `read`; `refuse` is the HTTP status of the next opening (403 — `review.denied`); `of(task)` finds a task's pull request by its branch. PR mode is `Harness.project.pullRequests`. GitHub's pull requests (BTN-688) are a second `Pulls` answering as api.github.com, `Harness.githubPulls` over the bare repository `githubBare`: with `githubRemote` set (and no `forge`, whose `origin` would win) the start puts the real `githubPulls` over its `fetch` into `FORGES`; `access` becomes the author's `author_association` (`OWNER`, `write` — `COLLABORATOR`, anyone else `NONE`), and `bots` names app accounts, answered with `type: 'Bot'`.
- **A second project** (`Harness.second`, with `forge`): the keys of a project `DEF` (`SECOND_ID`) whose checkout `repo2` is another clone of the same remote; `Harness.config` holds top-level keys of the config such as `parallel`. The scripted agent gives each session the main checkout its folder is in.
- **A release project** (`Harness.release`, with `forge`, BTN-684): the keys of a project `REL` (`RELEASE_ID`) whose checkout `releaseRepo` is a clone of the same remote on `release/v0.1` (pushed from `main` at the start), with `branch` and `mergeInto` the project `ABC`; `carryAgent` goes into its keys. `start(prepared)` runs `prepared` once the checkouts and the environment are ready, before the service reads them: the history a scenario carries, a git identity taken away, a hook of the bare repository.
- **A second source of tasks** (BTN-673). With `Harness.feed` set before `start` the project has a task feed `GHI` (`FEED_ID`) on a second board, `Harness.lane`: the same `Board` registered in `ADAPTERS` under `lane`, its own variable `LANE_TOKEN` in the environment making the lane's default profile at the first start, so the feed's tasks are briefed, commented on and closed in the lane, not on `board`. With `Harness.githubRemote` set the checkout has a `github` remote `https://github.com/john/example.git`, led to a bare repository `githubBare` by `insteadOf` (the global config of the bench, as with the forge), and `GITHUB_TOKEN` in the environment makes a GitHub profile whose token the remote takes; `GitHub` (`github.fixture.ts`, `Harness.github`) stands in for the global `fetch` and answers every request to api.github.com — the issues with their labels (`open`, `label`), comments with an author and an `author_association` (`comment`), `tags`, releases as a draft, a prerelease or published (`release`, `publish`), the profile's `/user` — while any other address goes to the real `fetch`. The intake (`intakeLabel` in `Harness.project`) runs its own `intakeRepo` over it, every 2 minutes of the bench's clock.
- `ScriptedAgent` (`agent.fixture.ts`) is an `Agent` registered in `AGENTS` for Claude in place of every provider, only in these tests; with `Harness.codex` set before `start` it plays Codex too, on the account folder `CODEX_ACCOUNT`, for a run label to pick (off by default: a second account is read on every step). Each launch or resume of a task's session plays the task's next turn from `script(task, ...turns)`; a turn does real git in the session's folder and ends as a transcript would show it: a reply, a question, a limit, `CHECKPOINT:`, `NO CHANGES:`, PR mode's mark (`pullRequest`; the turn `forReview` commits, writes the note `PULL_NOTE` and ends with it) or a crash. `parked(gate, turn)` keeps a turn mid-turn until the scenario opens the gate; `TurnContext.background()` ends the turn in `shell`, its process alive until a stop. Each `Call` records the account folder, its agent and the model asked for; `modelList` gives every account a complete model list; a busy session is listed with its turn's start as `silentSince`, hung past `TURN_HANG_MS` as the adapters' transcript reading gives it. It is neutral to the provider: the real CLIs are another level.
- **Limits and accounts** (BTN-663). `ScriptedAgent.windows(account, at)` gives the agent a `usage`: the windows by the bench's clock (`source: 'usage'`), `'missing'` for a provider that tells of none (Copilot, OpenCode Zen), `null` for an unreadable answer; unset, the agent has no `usage`, as before. `usageGate` holds every `usage` call, as a slow `/usage` does, and `polls` records each. A turn reports windows mid-turn by `TurnContext.limits`, as an SDK session's `rate_limit_event` does (`AgentOptions.onLimits`). A turn ends in `credit` (`billing_error`) beside `limit`. `statuses` sets what an account's sign-in shows over a subscription as `<key>@example.com`: `authMethod: 'api_key'` for a key, `email: null` for a folder with none. `Harness.spare` adds a second Claude account folder `SPARE_ACCOUNT` to switch to (`account/switch`). The network check before an account's call (`answers` of `src/account/network.ts`) is mocked to answer at once on the bench, and each start waits for the MCP gateway's line, so that a restart right after a start does not find the gateway's port still held.
