# Цепочка

Справка для сессий: вход в цепочку, порядок, worktree задач, уборка и подробности исключений инварианта 1. Сами инварианты — в `CLAUDE.md`.

## Вход в цепочку

- Правила — `chain` в `even-keel.config.json` (`src/chain/rules.ts`): общий верхний и поверх него свой у проекта (проект — строка-путь или `{ "repo", "chain" }`, ключ проекта заменяет общий целиком).
- `active` и `terminal` — имена статусов (без регистра и пробелов по краям); нет ключа — по категориям: активные `ToDo` и `Active`, терминальные `Won` и `Lost`. Имя, которого нет в Huly, — предупреждение в лог; статус в обоих списках — ошибка конфига.
- `requiredLabels` — нужен хоть один из них (пусто — не нужен), `excludedLabels` (по умолчанию `["Manual", "Вручную"]`) убирает задачу совсем, её запускает пользователь сам. Не прошедшая правила по ярлыкам задача отсекается там же, где закрытые (`Dispatcher.setTasks`), и блокером для задач цепочки не считается.
- По умолчанию в цепочку входят задачи в Todo и дальше: Backlog (категория `UnStarted`) — склад идей, ни активный, ни терминальный, цепочка его не берёт. Задачу пускает в цепочку перевод в активный статус.
- Бэклог для страницы (`ProjectOrder.backlog`) — открытые задачи вне цепочки по статусу или без нужного ярлыка, кроме блокеров под замком и задач с исключающим ярлыком. Прогресс на карточке считает только закрытые и цепочку, бэклог — отдельной подписью; на странице проекта — свёрнутый список под цепочкой, раскрыт ли он, помнит браузер.
- Открытый блокер в неактивном статусе (BTN-68, `waitingBlockers` в `src/chain/order.ts`, и дальше по его блокерам того же рода) держит задачу цепочки: она не запускается, текущая с таким блокером откладывается (`postpone`), как с блокером из цепочки; все задачи держат такие блокеры — цепочка кончается. Страница показывает его (`ProjectOrder.waiting`) перед задачей, которую он держит (`withWaiting`), приглушённым и под замком: без номера, кнопок и перетаскивания, ссылка — на задачу в трекере. Перевели в активный статус — обычная задача цепочки; закрыли — задача свободна.
- Задача, которую ведёт сессия и которую вернули в неактивный статус, остаётся в цепочке, пока сессия посреди хода (`busy`), потом выпадает (`Dispatcher.enters`). Уборка worktree — только когда терминальный статус из категории `Won`; ушедшая в терминальный статус другой категории просто выпадает.

## Порядок (`src/chain/order.ts`)

Блокеры `blocks`, затем сохранённый порядок (`state/chain.json`), милстоун, приоритет (Urgent → High → Medium → Low → без приоритета), номер задачи. Новая задача встаёт перед первой задачей своего или более низкого приоритета, после более срочных (`withFresh`); текущая задача остаётся первой.

## Worktree задачи (`src/git/worktree.ts`)

- Перед первым запуском по задаче — в основном чекауте проекта (`config.projects[project]`) `git worktree add -b <ключ>-<номер>/task .claude/worktrees/<ключ>-<номер> main`, всё в нижнем регистре. Хвост ветки всегда `task`: хукам в `~/.githooks` нужен вид `<ключ>-<номер>/<что-то>`.
- Worktree по этому пути уже есть — берётся как есть, с его веткой; есть только ветка — возвращается в новый worktree. `.claude/worktrees/` дописывается в `.git/info/exclude`, если git её не игнорирует.
- Сессия стартует с `cwd` = worktree, промт — ID задачи, строка про готовый worktree и что убирать за собой не надо (`startPrompt`).

## Уборка после Done

- Текущая задача ушла в Done (категория `Won`; отменённая или выпавшая — нет) — `closing` цепочки: ждать, пока её сессия не посреди хода (`busy`/`waiting`, а также `shell` — см. «Фоновая команда» ниже), затем `claude stop` её сессий в этом worktree (иначе живой процесс держит папку: `--bg`-сессия после хода не выходит, `claude agents` показывает её `done`/`idle`), затем в чистом worktree — снять ссылки и junction в игнорируемых папках (`node_modules` воркспейсов npm, `npm link`: git на Windows идёт по ним — чистит чужую папку или спотыкается о висячую и бросает worktree), затем `git worktree remove` (без `--force`), `git branch -d` ветки задачи (только `<ключ>-<номер>/…`), `git push origin --delete`, если она есть на origin, и `git sync`, если у проекта есть remote. Следующая задача запускается после этого. Задачу вернули из Done до уборки — уборки нет, задача снова в цепочке.
- `git sync` — синхронизация `main` (`src/git/sync.ts`): есть алиас `alias.sync` у репозитория или пользователя — он; нет — Even Keel сам: основной чекаут должен стоять на `main`, по каждому remote `git fetch` и `git merge --no-edit <remote>/main` (не сливается чисто — `merge --abort` и ошибка), затем `git push <remote> main` в каждый.
- Грязный worktree, папка, занятая процессом, неслитая ветка — предупреждение в лог и на страницу проекта (`leftovers` в `state/chain.json`, кнопка «Убрал» — `chain/dismiss`), цепочка идёт дальше. Упал `git sync` — так же предупреждение с его выводом, цепочка идёт дальше, силой ничего не пушится: следующая задача берёт локальный `main`, а очередной `git sync` после её Done повторит отправку.

- Родитель закрывается сам, когда закрыты все его подзадачи (адаптеры с `children`, `docs/trackers.md`); уборки при этом нет.

## Отпущенные задачи

Задача, которую цепочка запустила и отпустила не через Done, — выпала (стала родителем: задачи с подзадачами в цепочку не входят; ушла в неактивный статус), отложена блокером, пропущена, цепочку остановили или она встала с ошибкой, — запоминается в `released` в `state/chain.json`. Их статусы Even Keel спрашивает у трекера вместе с задачами цепочки (раз в 30 с); ушла в `Won` и её сессия не посреди хода — та же уборка, что у текущей, но цепочка из-за неё не ждёт и на паузу не встаёт: упавший `git sync` — предупреждение в `leftovers`. Ушла в терминальный статус другой категории, пропала из трекера или цепочка снова её взяла — забывается.

## Несколько цепочек (`parallel`, BTN-67)

- `parallel` в конфиге — сколько цепочек разных проектов идут одновременно, по умолчанию 1; применяется на лету. Активные цепочки — `active` в `state/chain.json`, массив в порядке запуска (старый вид — один объект или `null` — читается, `src/chain/store.ts`); остальные проекты — в `queue`.
- Место занимает и цепочка на паузе. Цепочка кончилась или её остановили — из очереди сразу берётся следующий проект, другие цепочки идут дальше. Уменьшили `parallel` — никого не останавливает, новые не берутся, пока активных не станет меньше.
- У каждой цепочки свои текущая задача, пауза, ошибка, передача дел и `closing`. «Продолжить», «Остановить» (`chain/resume|stop` с `{ project }`) действуют на свой проект. Ручной паузы нет: на паузу цепочку ставит только сам диспетчер при ошибке, она держит место и очередь, «Продолжить» её повторяет. Остановка отпускает задачу (её сессия работает дальше, уборка — как у отпущенной) и освобождает место.
- Лимит у аккаунта общий и между цепочками не делится: все берут задачи, пока окно не выбрано; выбрано — ждут сброса все (`limitUntil` у каждой), продолжение после сброса — у каждой своё.
- Смену аккаунта и продление входа блокирует любая цепочка не на паузе; окно блокировки перечисляет все такие (`LoginBlock.chains`, `src/account/model.ts`).

## Режим «слот» (`src/git/slot.ts`)

- `"slot": true` или число слотов у проекта в `even-keel.config.json` — пул постоянных worktree на репозиторий вместо нового на каждую задачу: `.claude/worktrees/even-keel`, дальше `even-keel-2`, `even-keel-3`… (`true` — один). Игнорируемые кэши (`Library` Unity, `node_modules`) переживают задачу, и первый запуск новой обрабатывает только разницу; лишний слот нужен, чтобы живая сессия отпущенной задачи (пропущенной, отложенной блокером) осталась в своём, а не была остановлена. Цепочка по-прежнему ведёт одну задачу за раз.
- Подготовка: слот уже на ветке задачи (`<ключ>-<номер>/…`) — он, как есть, даже грязный. Иначе по каждому слоту: грязный (`git status --porcelain` не пуст) или с сессией другой задачи посреди хода (`busy`/`waiting`, по журналу запусков, `src/sessions/occupants.ts`) — не годится. Из годных берётся, по порядку предпочтения: отцепленный от ветки без чужих живых сессий, на чужой ветке без них, ещё не созданный (`git worktree add --detach <слот> main`), с простаивающими сессиями других задач — им `claude stop` (пятое исключение инварианта 1); при равенстве — с меньшим номером. Ни один не годится — ошибка запуска, цепочка на паузе с путями и причинами, слоты не трогаются. Затем `git clean -fd` (без `-x`) и `git switch <ветка>` или `git switch -c <ветка> main`.
- После Done слот на ветке задачи — `git switch --detach main` (грязный — остаётся на ветке, ветка не удаляется, предупреждение), затем ветка, origin и `git sync`, как без слота; папка слота не удаляется. Слоты на чужих ветках (уборка отпущенной задачи) не трогаются, удаляется только ветка. `claude stop` после Done в слоте — только сессиям этой задачи по журналу запусков.
- Число слотов меняется после перезапуска; при уменьшении лишние папки Even Keel больше не берёт и не убирает. Свой worktree задачи, оставшийся с прежнего режима, берётся и убирается по-старому.

## Исключения инварианта 1 подробно

1. **Лимит** у сессии текущей задачи незапаузенной цепочки: после сброса лимита или смены аккаунта диспетчер продолжает её через `--resume`, если кэш ещё тёплый (тот же аккаунт, < 55 мин с последнего ответа), иначе останавливает её (`claude stop`, не `rm`) и запускает новую в её рабочей папке с передачей дел (`src/chain/relay.ts`). Лимит — это и ошибка `rate_limit`, и мягкое предупреждение CLI (`usageLimitNote: "wrap_up"`), после которого сессия сама сворачивает ход. Рабочую папку и ветку для передачи даёт git (корень worktree от последнего `cwd`), не транскрипт: его `gitBranch` — ветка папки запуска.
2. **«Новая сессия»** (`restart`): пользователь заменяет сессию текущей задачи, если она не посреди хода, — та же передача дел, в журнале `restart` со ссылкой на прежнюю сессию.
3. **Контрольная точка**, которую сессия поставила сама: сессия текущей задачи незапаузенной цепочки закончила ход, и последняя строка её последнего ответа — `CHECKPOINT: <путь>` (так просит хук плагина `checkpoint@even-keel`, `plugins/checkpoint`, когда контекст разросся). Диспетчер делает ту же передачу дел, в промте — путь к записке от корня worktree, в журнале `checkpoint` со ссылкой на прежнюю сессию. Метка после неё — вызов инструмента, новый ответ без метки или сообщение в сессию — гасит её. Передача повторяется, сколько сессии её просят; число передач по задаче видно на странице. Сессия с лимитом идёт по правилу лимита (её промт тоже указывает на записку), а пока лимит выбран или новые сессии не запускаются, метка ждёт.
4. **Задача в Done**: когда её сессия закончила ход и не ждёт ответа (не `busy`/`waiting`), диспетчер останавливает её (`claude stop`, не `rm`; транскрипт остаётся, `--resume` вручную возможен) и убирает worktree. После слияния сессии делают не больше пары проверок в том же ходе и кончают отчётом (замер по транскриптам, 2026-09-29).
5. **Слот переключают** на ветку другой задачи (только когда свободного слота в пуле нет): живые сессии отпущенных задач (пропущенных, отложенных блокером) в слоте диспетчер перед этим останавливает (`claude stop`, не `rm`), иначе ответ такой сессии через Remote Control лёг бы в ветку чужой задачи. Если такая сессия посреди хода (`busy`/`waiting`), слот не переключается, цепочка на паузе с её задачей.

Перестать ждать сессию (не трогая её) диспетчер может, если она не посреди хода (`busy`/`waiting`): текущая задача получила открытый блокер из той же цепочки (сессия отложила её сама, в журнале `postpone`) или пользователь нажал «Пропустить» (`skip`). Пропущенную задачу цепочка не берёт, пока пользователь её не вернёт или она не уйдёт из цепочки в трекере (закрыта, в Backlog).

## Режим без присмотра (`unattended`)

Переключатель в меню состояния (шестерня, `SystemMenu`) — на случай, когда отвечать некому, например ночью. Хранится в `state/chain.json` (`unattended`, команда `chain/unattended` с `{ on }`), включённый режим — баннер `UnattendedBanner`.

- К каждому промту — запуска, `--resume`, передачи дел — дописывается `PROMPTS.unattended` (`src/chain/prompts.ts`): вопросов не задавать, сделать всё, что вопрос не держит; вопрос с вариантом по умолчанию — как обычно (доделать и слить, вопрос задачей); задачу, которую без ответа не закончить, — закоммитить в её ветку до чистого `git status`, не сливать, вопрос с вариантами — комментарием, ярлык вопроса, последним шагом — Backlog (хук после коммита двигает статус вперёд, поэтому после коммита и с проверкой). Сессиям, запущенным до включения, текст не доходит — только с ближайшим `--resume` или передачей дел.
- Задача в Backlog выпадает из цепочки, как любая вернутая в неактивный статус: отпускается, worktree или слот с её веткой остаются. Чистое дерево важно в режиме «слот»: грязный слот не берётся, и пара припаркованных задач с мусором остановила бы цепочку.
- Подстраховка в диспетчере (`Dispatcher.unanswered`): сессия текущей задачи закончила ход или ждёт ответа (не `busy`), без лимита и контрольной точки, и 10 минут тихо — с последнего ответа, с того, как цепочка взяла задачу, и с `--resume` (`resumedAt`), что позже, — задача пропускается, как кнопкой «Пропустить» (`skip` в журнале). Сессию диспетчер не трогает. Так ночь не стоит, если сессия всё-таки спросила или хук вернул статус. Слитая задача уходит в Done за секунды, 10 минут её не задевают.
- Задачу в Done (`closing`) цепочка тоже не ждёт дольше 10 тихих минут (`Dispatcher.quietTooLong`, с последнего ответа сессии): задача переходит в `released`, её уборку сделает обход отпущенных, когда сессия не будет посреди хода, а цепочка идёт дальше. Сессию диспетчер не трогает.
- **Фоновая команда.** Статус `shell` CLI пишет в `sessions/<pid>.json`, когда ход окончен, а запущенная сессией фоновая команда (`run_in_background`) ещё работает; по её концу сессия получит уведомление и продолжит. Для цепочки такая сессия посреди хода (`turnStatus`, `src/sessions/agents.ts`): долгий прогон в 15–20 минут не пропускается и не убирается. Час без новой строки в транскрипте — команда считается зависшей, сессия простаивающей. Слот с сессией в `shell` всегда занят.
