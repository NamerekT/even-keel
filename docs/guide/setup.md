# Setting up Even Keel

The [README](../../README.md) has the quick start. This is the rest: the CLIs Even Keel depends on, projects, trackers and plugins, reaching the page, the service, updating and uninstalling. Every variable and key is in the [reference](reference.md).

## The CLIs it depends on

**Even Keel depends on undocumented behaviour of the Claude Code CLI**: `claude agents --json`, the `sessions/<pid>.json` records and the `jobs/<id>/state.json` job files, the background daemon (`claude --bg`, `--bg --resume`, `claude daemon`), the transcript format, the text of `/usage`, the layout of `~/.claude.json`, `.credentials.json` and `plugins/installed_plugins.json`. None of it is a public API.

A version becomes the checked one after one live session on it went through a launch, a question answered from the chat, the chat's feed, a checkpoint and a stop (`npm run cli-check`, [docs/releases.md](../releases.md)). So chain sessions run on that version, not on the one your CLI has updated itself to: Even Keel downloads it from Anthropic into `state/cli/claude/<version>/` (~270 MB a version, checked against Anthropic's sha256) at the first call, runs the installed CLI until the download ends, and turns the auto-updater off for those sessions so they never update your own install ([docs/sessions.md](../sessions.md#the-checked-cli-btn-250-srcagentpinnedts)). Settings → Models, "CLI version", `Installed` puts a provider back on your CLI; the page shows a banner while sessions would run on another version than the checked one. The pin has limits:

- A session runs on the version of its account folder's daemon. A daemon on another version is restarted only once no session of that folder is live, and a newer `claude --bg` or `claude agents` run in the same account folder replaces the pinned daemon with its own version: keep your own background sessions out of the chain's account folder. Whether a terminal reaches the service's daemon on Windows to do that has not been checked.
- Anthropic's servers may refuse an old version, and an old version may not know a new model's alias; Codex lists models by the client's version. Then the checked version is raised in a new release of Even Keel.
- The transcripts your own sessions write on a newer version are read as before: the pin covers how chain sessions are run, not those files.

**The same goes for the Codex CLI**: the events of `codex exec --json` (`thread.started`, `item.completed`, `turn.completed`, `turn.failed`), `-c` overrides of its config keys (`mcp_servers`, `marketplaces`, `plugins`, `hooks.state`), the rollout files `sessions/YYYY/MM/DD/rollout-*.jsonl` and their `session_meta`, `turn_context`, `event_msg` (`token_count` with the context fill and the rate limit windows, `task_complete`, errors) and `response_item` lines, the `plugin/install` and `hooks/list` calls of `codex app-server`, the `[plugins.*]` tables of `config.toml` and the `plugins/cache` layout, the claims of the ID token in `auth.json`, the text of `codex login status` and of its quota errors, and the layout of the npm package on Windows. Codex sessions run on the checked version the same way: Even Keel unpacks the platform's npm package `@openai/codex@<version>-<platform>` (Apache-2.0, checked against the registry's sha512) into `state/cli/codex/<version>/`.

Where Even Keel finds the CLIs: Claude Code's native install in `~/.local/bin` (`claude.exe` on Windows), then the binary of the VS Code extension, then `claude` on `PATH`; `EVEN_KEEL_CLAUDE_BIN` overrides. Codex's own folder is `CODEX_HOME` or `~/.codex`, the accounts added from the page live in `~/.codex-accounts`; `EVEN_KEEL_CODEX_BIN` overrides the binary.

**OpenCode too**: Even Keel relies on the JSON events of `opencode run --format json`, its `-s` and `--title`, `OPENCODE_CONFIG_CONTENT`, the XDG folders, `auth.json`, the tables `session`, `message` and `part` of `opencode.db`, and the text of `opencode providers login`. Its sessions run on the checked version: Even Keel unpacks the platform's npm package of its native binary (`opencode-windows-x64@<version>` and the like, MIT, checked against the registry's sha512, ~170 MB a version) into `state/cli/opencode/<version>/`, with self-update turned off. An x64 processor without AVX2 needs OpenCode's `-baseline` build, which Even Keel does not take: set its "CLI version" to `Installed` there. With `Installed`, or until the download ends, sessions run on the `opencode` you installed (`npm install -g opencode-ai`; on Windows Even Keel takes the native `opencode.exe` inside the global npm package); `EVEN_KEEL_OPENCODE_BIN` overrides both. Its accounts live only in `~/.opencode-accounts`: your own OpenCode's folders are not listed.

**GitHub Copilot too**: Even Keel relies on the JSONL of `copilot -p --output-format json`, its `--session-id`, `--resume`, `--no-ask-user`, `--add-dir`, `--additional-mcp-config`, `--disable-mcp-server` and `--plugin-dir`, `COPILOT_HOME` and `COPILOT_GITHUB_TOKEN`, and the events of `session-state/<id>/events.jsonl`. Its sessions run on the checked version: Even Keel unpacks the platform's npm package of its native binary (`@github/copilot-win32-x64@<version>` and the like, checked against the registry's sha512, ~155 MB a version) into `state/cli/copilot/<version>/`, with `--no-auto-update` and `COPILOT_AUTO_UPDATE=false`. With `Installed`, or until the download ends, sessions run on the `copilot` you installed (`winget install GitHub.Copilot` on Windows, which Even Keel finds by itself); `EVEN_KEEL_COPILOT_BIN` overrides both, and is needed for the npm package `@github/copilot` installed by hand. Sign in once with `copilot login`, or add accounts with tokens on the accounts page. Its accounts live only in `~/.copilot-accounts`: your own `~/.copilot` is not listed.

## Projects

The projects and the settings live in Even Keel's database and are edited on the page; there is no file to create. The first start walks a short setup, each choice saved as you make it and changed later in **Settings**: the languages of the page and of the session prompts; the agent all projects run on by default, its account (sign in, or add one in a dialog over the step) and, for Claude Code and Codex, whether sessions run on the CLI version Even Keel was checked on (downloaded at the first session, about 270 MB for Claude Code) or on the one installed; a tracker profile (or later); whether Even Keel may ask GitHub twice a day for a new release — nothing is asked until you answer; and the [statistics](features.md#statistics-optional). Then the page opens the wizard that adds a project. You pick the agent of the project (the shared one unless you choose another; the wizard says whether it has a CLI and a signed-in account, and **Add an account** opens a dialog over it), give it the repository folder, pick a tracker profile (or add one right there) and the project in that tracker, which it suggests from the tracker's list and, on GitHub, from the repository's remote. The wizard checks the repository and its main branch (it suggests the checkout's current branch), the project in the tracker (it shows how many open tasks it sees), Claude Code's trust in the folder for a project Claude Code may run (its agent, or any agent with run labels on) and where tasks run — **Own folder per task** (a git worktree made for the task and removed after Done) or **Permanent folders** (a few folders a task switches the branch in). All the steps are on one page, each marked once its check passes or with the reason under its field when it fails, and **What will be created** at the bottom sums the project up before **Add project**.

When you add the project, Even Keel checks the repository again before saving it. A folder inside a repository is saved as the repository's root folder.

The wizard shows a validation error under the field that needs correcting and marks its step in red. Empty required fields are named at the bottom of the form.

Each project needs:

- a git repository with a main branch — `main` unless the project names another in `branch`; with a remote, Even Keel pushes it after every task;
- on Claude Code, or on another agent with run labels on (a label can give a task to Claude), the repository trusted by it (the wizard and the project's **Sessions** settings show the command to run): open `claude` in it once as the user the service runs as and accept the trust prompt — from another user's terminal the second command does that through `runas` or `sudo -u`. Otherwise the first Claude launch pauses the chain with the same commands (accepting the trust in the repository covers its task worktrees); then press **Check again and resume**: the chain does not retry by itself.

The rule that a session commits and merges its branch into `main` when the task is done comes with the launch and handoff prompts, plugin or not (in PR mode the prompt says to end the turn for a pull request instead).

A session gets the project's `CLAUDE.md`, `AGENTS.md` and skills as they are committed on the main branch: its worktree is checked out from there, so a file you have not committed yet does not reach it. Which of them each agent reads is in [the project's instructions and skills](features.md#the-projects-instructions-and-skills).

A project is removed at the bottom of its **Settings** → **Repository**; the page refuses while its chain runs or waits in the queue, a session works for it or in its folders, or a task still holds a place, and says which. Removal does not touch the repository, its worktrees or branches.

## Trackers and plugins

### Minimum: the adapter only

Even Keel reads the tasks itself, puts the title and description of the task into the session's prompt, and closes the task when its branch lands in `main`. You add a **tracker profile** on `/settings` → **Trackers and CI** → **Add profile**, and nothing else: pick the tracker, fill in its fields, press **Check** — Even Keel signs in and shows whom as — then **Save**. A profile is saved only once the tracker took it; the page never shows a saved token or password again. Profiles live in Even Keel's state database on your machine, not in git.

- **Huly:** the server address, the workspace, and the e-mail and password of a separate Huly account with access to the projects — create one for Even Keel. A token instead only if your Huly shows an API tokens page in the account settings: released self-hosted Huly has none, and its sign-in token comes from the e-mail and password anyway ([plugins/huly/README.md](../../plugins/huly/README.md#credentials)). The project key is the Huly project identifier (`ABC` for `ABC-12`).
- **GitHub:** a [fine-grained token](https://github.com/settings/personal-access-tokens/new) on the repositories, with the rights in [Token permissions](#token-permissions). A fine-grained token covers one owner: a personal repository and an organization's need a profile each. The profile shows when its token expires. A project names its repository: `{ "repo": "…", "tracker": "github", "github": "octo-org/abc" }`. GitHub has no backlog, so keep entry to the chain on a label: `"chain": { "requiredLabels": ["ready"] }`. For a public repository the label is a must: anyone with a GitHub account can open an issue there, and without the label it would enter the chain and give its text to a session that runs commands on your machine; only collaborators can label an issue, and the wizard warns about a public repository. For the same reason Even Keel reads only the comments of the repository's owner, the members of its organization, its collaborators and the token's own account — as an answer to a question, and in PR mode as a review or a comment on a pull request. Anyone else's is skipped with a line in the service log; the task card on the page still shows it. Details and the mapping of statuses, blockers, sub-issues and priorities: [plugins/github/README.md](../../plugins/github/README.md).
- **Linear:** a [personal API key](https://linear.app/settings/account/security) ([Token permissions](#token-permissions)). The project key is the team key (`ENG` for `ENG-12`); `"linear": "Web app"` narrows the team down to one Linear project: `{ "repo": "…", "tracker": "linear", "linear": "Web app" }`, so two repositories of one team run as two projects, each on its Linear project. Details and the mapping: [plugins/linear/README.md](../../plugins/linear/README.md).
- **GitLab:** a personal access token with the `api` scope, and optionally your server's web address (default `https://gitlab.com`, without `/api/v4`; a server under a path prefix keeps it, such as `https://example.com/gitlab`). Use GitLab.com or a self-managed GitLab 19.5 or later: those are the versions Even Keel was checked on, and older ones may build parent and child issues differently, so the chain may miss a subtask or close a parent too early. The profile checks the account and shows the token expiry when the server exposes it. Pick the project including subgroups: `{ "key": "APP", "repo": "…", "tracker": "gitlab", "gitlab": "group/subgroup/project" }`; issue `iid` 12 becomes `APP-12`. Opened issues are ready, closed ones done; use **Required labels** to keep unread issues out, especially in public projects. Only members with Reporter access or above and the token owner can answer sessions through comments. **GitLab Free has only related links, so no blocking order**: the chain follows milestones and priority; Premium or Ultimate adds native blocking links. Text such as `blocked by #12` is ignored. Details: [plugins/gitlab/README.md](../../plugins/gitlab/README.md).
- **Jira Cloud:** the site address (`https://<site>.atlassian.net`), the e-mail of an Atlassian account that sees the projects and its [API token](https://id.atlassian.com/manage-profile/security/api-tokens), classic or with scopes ([Token permissions](#token-permissions)). The project key is the Jira project key (`ABC` for `ABC-12`): `{ "key": "ABC", "repo": "…", "tracker": "jira" }`. Statuses of the To Do category are ready and enter the chain, except one named Backlog; a board whose backlog is not a status needs **Required labels** or the project's own active statuses. The chain is ordered by the `Blocks` link type: if your site renamed or deleted it, the profile's projects do not start until a link type of that name is back. Details: [plugins/jira/README.md](../../plugins/jira/README.md); the live checks are in [verified.md](../verified.md#trackers).

A project can take tasks from a second tracker too: in the project's settings, **Tracker** → **Task feeds** → **Add a feed**, pick the profile (it names the tracker), the place (a repository, a team — the profile's projects are suggested as you type, as in the wizard) and a key for the ids ([Several trackers for one project](features.md#several-trackers-for-one-project)). The chain rules a feed's tasks go by are the project's own, then its profile's, then the shared ones: a GitHub feed on a public repository needs its label as much as a GitHub project does, so set `requiredLabels` on that GitHub profile (its tab under **Chain rules**, or **Rules** on its row in **Trackers and CI**) when the project's own rules do not set it — the wizard's warning does not cover feeds.

On this level the session does not write to the tracker. What you do not get:

- **Postponing on a blocker.** The session cannot file a blocker for its task, so it cannot hand the task back and let the blocker run first. Blockers you link yourself still order the chain.
- **Question tasks.** A session cannot file a `Question: …` task for a decision it took on its own; it can only tell you in its final message.
- **Comments and decisions.** Nothing is written back: no closing comment, no decisions folded into the description, no new tasks for bugs found on the way.
- **Attachments and discussion.** The session sees only the title and the description.

### With the plugin

On top of the adapter, a Claude Code plugin from this repository gives the sessions the tracker's MCP server and a skill for working a task: the session reads the task and its attachments, records decisions in the description, files blockers and question tasks, creates new tasks, leaves a closing comment and merges.

Even Keel offers its own plugins from this folder, with no marketplace to add first:

1. On the `/tools` page, press **Add a package** under Packages, choose **Plugin** and pick `huly@even-keel` (or `github@even-keel`, `linear@even-keel`, `gitlab@even-keel`, `jira@even-keel`) for every project or one. Even Keel copies the plugin, installs a pinned version of its MCP server and gives both to every chain session at launch; turn it off per project in the table. A plugin your projects already had enabled when you upgraded is in the table already. A shortcut for one project: **Go to Tools** beside **Task description in the prompt** in the project's settings, or **Open →** on its "What sessions get" plaque while that says the tracker's plugin is missing, opens the same dialog with the tracker's plugin and the project already picked.
2. The MCP server takes the credentials of the project's tracker profile: it runs behind a local gateway on `127.0.0.1:4748` (`EVEN_KEEL_MCP_PORT`), so the sessions never see them. Another key a package needs shows in **Keys** on the same page, and the project's chain waits until it is set.
3. Nothing to switch off: once a package of the project brings the tracker's MCP server, the prompt carries only the task ID and the session reads the task itself (`brief` left as auto). `brief: true` or `false` overrides that; with `false` the chain waits while no package of the project brings the server.

The GitLab plugin enables the `issues,milestones` toolsets: sessions read issues through REST `get_issue` on GitLab.com and self-managed servers, including CE/Free. Work-item tools are disabled because the pinned MCP version's GraphQL queries fail on CE/Free; native parent-child changes need a compatible work-item tool.

**MCP through OAuth.** The Jira, Linear and GitHub profiles have **Connect MCP through OAuth** in their dialog, on a new profile too: a window asks the tracker for consent, and Even Keel keeps the access and refreshes it; sessions still see only the gateway's address. Linear needs nothing else. Jira connects to Rovo MCP v2 and requests the permissions its server advertises; an older Jira MCP OAuth connection needs connecting again in the profile dialog. Jira uses [Atlassian's OAuth domain rules](https://support.atlassian.com/security-and-access-policies/docs/available-atlassian-mcp-server-domains/): `localhost` is supported by default. If the consent page asks an admin to authorize a redirect URL at another address, your Atlassian organization's admin adds the **callback domain of your Even Keel page** to the allowed domains, not the authorization server's `auth.atlassian.com` address. In the current Atlassian Administration this is **Connectors → Atlassian MCP server → Add domain**; older screens call it **Rovo → Rovo MCP server → Domain settings** ([Atlassian's instructions](https://support.atlassian.com/security-and-access-policies/docs/control-atlassian-mcp-server-settings/)). Requiring a new custom domain was checked with the older authorization server; it has not been checked again with v2. GitHub's MCP server does not register clients itself: [create a GitHub OAuth App](https://github.com/settings/applications/new) with the **Callback URL** the dialog shows and enter its Client ID and Client secret. Open the page through a local HTTPS proxy such as Tailscale Service, or on `localhost` of the machine Even Keel runs on: a plain HTTP address of another machine is refused as a callback. Direct network access currently fails at the OAuth callback because the browser does not send the access cookie after a cross-site redirect; use localhost or the local proxy ([check and limitation](../verified.md#trackers)). When the access is revoked or expires, the profile's row says **MCP access lost**; open the profile and press **Connect again**. The tokens below remain the other way, for a machine without a browser.

The Jira plugin is Atlassian's own Rovo MCP server and needs a separate token from the REST adapter (or the OAuth connection above). First ask your Atlassian organization's admin to enable **API token** authentication for the Atlassian MCP server in the organization's settings (Connectors → Atlassian MCP server → Authentication). Then [create an Atlassian MCP V2 token with all scopes](https://id.atlassian.com/manage-profile/security/api-tokens?autofillToken&appId=mcp-v2&selectedScopes=all) for the same e-mail and enter it in **Atlassian MCP V2 token (optional)** in the Jira profile. Leave it empty for projects without `jira@even-keel`. The profile check calls `getAccessibleAtlassianResources` and requires that it include the profile's site; if the list is empty or lacks the site, create the MCP token again after enabling API token authentication. A successful tool listing alone does not prove access. Details: [plugins/jira/README.md](../../plugins/jira/README.md#plugin).

Sessions you start by hand get none of this. For them, Claude Code needs this repository as a marketplace: `/tools` offers to add it with a button while your default config (no `CLAUDE_CONFIG_DIR` set) does not know it, or run `claude plugin marketplace add <git URL or local path of this repository>` yourself. Then `claude plugin install huly@even-keel --scope project` in the project and the credentials in the `env` of `~/.claude/settings.json` (`HULY_URL`, `HULY_WORKSPACE`, `HULY_TOKEN` or `HULY_EMAIL` and `HULY_PASSWORD`; `GITHUB_PERSONAL_ACCESS_TOKEN`; `LINEAR_API_KEY`; `GITLAB_PERSONAL_ACCESS_TOKEN` and optional `GITLAB_URL`; `JIRA_BASIC_AUTH`, the base64 of `e-mail:MCP-token`, using the separate Atlassian MCP V2 token). Even Keel writes each tracker's default profile there itself; the GitHub, Linear, GitLab and Jira MCP variables above use different names, so supply those explicitly for sessions started by hand. Such a session never gets another profile.

The GitHub skill sets "blocked by" links through the [GitHub CLI](https://cli.github.com/), so `gh auth login` once. Everything else — troubleshooting, what the skills do — is in [plugins/huly/README.md](../../plugins/huly/README.md), [plugins/github/README.md](../../plugins/github/README.md), [plugins/linear/README.md](../../plugins/linear/README.md), [plugins/gitlab/README.md](../../plugins/gitlab/README.md) and [plugins/jira/README.md](../../plugins/jira/README.md).

### Several trackers

Each project has its own tracker (`tracker` in the project's entry, GitHub when a file you write names none), and they work at the same time: project A on Huly, project B on GitHub. A tracker can have several profiles — two Huly workspaces, a personal GitHub token and an organization's — and each project picks one (the **Profile** field when you add it, or in its settings until its first task runs). One profile of each tracker is the default: projects without a choice run on it, it is the one sessions started by hand get, and it gives the GitHub Actions token to projects of other trackers. Making another profile the default does not move a project whose tasks have already run: it stays on the old profile, now as its own choice. A profile whose token is refused turns red on **Trackers and CI**, and the chains on it pause until it is fixed.

Git is not part of this: pushes go through your own git and its credentials (SSH, the credential manager), whatever the profiles are. A project on Huly with a remote on GitHub works as is, and its CI is found by the remote.

### CI and pull requests

The CI is read with a profile too. GitLab CI is found from a root `.gitlab-ci.yml` file on `gitlab.com` or a host named by a GitLab profile's address. Nested groups are supported. When several GitLab installations share a host, HTTP(S) remotes use the longest matching URL prefix from the profiles, falling back to a root profile. The token comes from the project's GitLab profile for that installation, otherwise its default profile, otherwise its first profile. A profile for another installation on the same host is excluded, even when explicitly chosen. SSH remotes have no installation prefix in their path: the first installation on the host is used, with a log entry when the choice is ambiguous. GitHub Actions on a `github.com` remote takes the token of the project's GitHub profile, or of the default GitHub profile for a project on another tracker. CI on a Forgejo remote takes a **Forgejo** profile (**Add profile** → Forgejo: the server's address and an access token) on the remote's host. Pull requests of PR mode take the same token as the remote's CI. What each token needs is in [Token permissions](#token-permissions). With several GitHub, Forgejo or GitLab profiles, a project can pick the one its CI and pull requests take in **Settings** → **Check and CI** (`remoteProfiles`); "Automatic" is the choice above. A CI that no profile reaches is not shown at all. CI supports GitHub, Forgejo (or Gitea) and GitLab. PR mode supports GitHub, Forgejo and GitLab (merge requests, on the same profile as the remote's GitLab CI). A remote on `bitbucket.org` has no CI and cannot use PR mode. An unknown host is taken for Forgejo until a GitLab profile identifies it; a Forgejo profile's check on GitLab asks you to add a GitLab profile instead. A `FORGEJO_TOKEN` left in `.env` from an older install becomes a Forgejo profile on the first start, one per host of the projects' Forgejo remotes; after that it is not read.

### Token permissions

What a profile's token needs, by what it is used for. The profile dialog lists the same for the kind you pick.

| Profile | Tracker | CI | Pull requests (PR mode) |
| --- | --- | --- | --- |
| Huly | a separate account with access to the projects: its e-mail and password, or a token | — | — |
| GitHub, a fine-grained token for the repositories' owner | **Issues: Read and write** | **Actions: Read** | **Pull requests: Read and write**, **Contents: Read**, **Actions: Read** |
| Linear, a personal API key | write access | — | — |
| GitLab, a personal access token | `api` scope (`read_api` cannot close issues or post comments) | `api` scope, with access to the project and its pipelines | `api` scope, Developer access or above in the project (pushing the branch, opening a merge request, reading its discussions and the members) |
| Jira Cloud, an Atlassian API token | Browse projects, Add comments, Transition issues and Edit issues in the projects; a token with scopes also needs `read:jira-work`, `write:jira-work` and `read:jira-user` | — | — |
| Jira plugin, a separate Atlassian MCP V2 token | All scopes of the Atlassian MCP V2 application; enable API token authentication for the Atlassian MCP server before creating it. The REST token cannot be reused | — | — |
| Forgejo, an access token | — | `read:repository` (the repositories and their Actions), `read:user` (the sign-in check) | `write:repository` (opening a pull request, reading its reviews), `read:issue` (comments in its conversation), `read:user` |

PR mode pushes the task's branch with `git push`, on the git credentials of the account the service runs as (its SSH keys or credential manager), not with a profile's token: without them PR mode stops at the push. A forge that refuses to open a pull request with the token marks the profile's row **PR refused** and names the right it lacks. If the chain pauses because a pull request could not be opened, fix the token or select a profile with access in the project's **Check and CI** settings, then press **Resume**. Even Keel retries the same pull request mark without sending anything to the task's session; another failure pauses the chain with its new cause. Changing the profile alone does not retry it. The Forgejo rights for pull requests follow from the API calls Even Keel makes and are not yet checked against a real server ([What has not been verified](../unverified.md)).

## The page

`http://localhost:4747` by default. The page can be installed as an app (the install button in the address bar of Chrome or Edge) and then opens in its own window; browsers offer this on `localhost` or over HTTPS only.

### Answering from the phone

Sessions can be answered from the page's chat or the tracker. To answer them in Claude's own app as well, turn on Remote Control at startup in `/config` of Claude Code; the page links each session's Remote Control. Codex sessions have no remote control: they run through `codex exec`, whose threads the Codex app and ChatGPT on the phone do not list, so they are answered only from the page's chat or the tracker ([docs/sessions.md](../sessions.md#codex-btn-168-srccodex)).

### Reaching the page from another machine

By default the page listens on `127.0.0.1` only, and nothing else on the network sees it. That is on purpose: the page starts sessions with automatic permissions, writes answers into waiting sessions and signs Claude accounts in and out, so whoever reaches it drives your machine. Every request is also checked whatever `EVEN_KEEL_HOST` is:

- its `Host` must be `localhost`, `127.0.0.1`, `[::1]`, `EVEN_KEEL_HOST` or a name in `allowedHosts`, otherwise it gets 403. This stops DNS rebinding — a foreign site whose name was pointed at `127.0.0.1`;
- an `Origin`, if the request has one, must be one of the same names, so another site open in your browser cannot post to the page. Requests without `Origin` (the plugins' hooks, `curl`) pass.

Two ways to reach it from elsewhere:

- **A proxy on the same machine** (recommended). For example a Tailscale Service, `tailscale serve --service=svc:even-keel --https=443 http://localhost:4747`, which also gives the page HTTPS, so it can be installed as an app. The proxy forwards the name it was reached by, so put that name into `allowedHosts`: `"allowedHosts": ["even-keel.example.ts.net"]`. Its requests come from loopback, so the page asks them for no token: who gets in is decided by the tailnet's access rules.
- **Listening on the network.** Set `EVEN_KEEL_HOST` in `.env` to `0.0.0.0` or the machine's address, put the names or addresses you open it by into `allowedHosts` (the configured address itself is let in), and set `EVEN_KEEL_TOKEN` in `.env`. Without the token the service does not start. A request from another machine then needs the token: open the page once as `http://<address>:4747/?token=<token>`, and the service keeps it in an `HttpOnly`, `SameSite=Strict` cookie and drops it from the address; scripts send `Authorization: Bearer <token>`. Plain HTTP shows the token to anyone on the way, so prefer a proxy with HTTPS.

## As a service

The service starts by itself and restarts Even Keel if it fails. Stopping the service does not kill running sessions: they belong to the CLI's daemon.

**Installed with npm.** `npx even-keel` installs the package globally (`npm install --global even-keel`) and runs `even-keel install`: on Windows the start at sign-in below, elsewhere the package's own install script; once installed, `even-keel install` and `even-keel uninstall` do it again. The service runs from the global install, never from npx's cache, which npm may clear. A package keeps nothing of yours in its folder, since npm replaces the folder at every update: `.env`, `state/` and `logs/` are in the data folder — `%LOCALAPPDATA%\even-keel` on Windows, `~/Library/Application Support/even-keel` on macOS, `$XDG_DATA_HOME/even-keel` (`~/.local/share/even-keel`) on Linux, or the folder `EVEN_KEEL_DATA` names. The install script does not build anything, and on Windows it puts the service host into the data folder too. The service must run as the user whose data folder it is; for another account, pass `-Data <folder>` to `install.ps1` (or set `EVEN_KEEL_DATA`). `even-keel` with no command runs Even Keel in the terminal, on the same data folder.

**A clone** keeps its data in its own folder and runs its sources.

**Windows: a start at sign-in.** `even-keel install` (a clone: `node dist/src/cli.js install` after `npm run build`), as your own user from any terminal, no administrator and no PowerShell 7: it installs the dependencies and builds the page (a clone only), compiles a small host `EvenKeel.exe` with the `csc.exe` that ships with Windows (.NET Framework 4) into the data folder's `service` (a clone: `service\bin`), adds it to your sign-in start (`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, the value `EvenKeel`; it shows in Settings → Apps → Startup, where it can be turned off) and starts it. The host keeps Even Keel running, restarts it if it fails and puts an icon in the tray: **Open the page** (or a double click), **Restart**, **Quit**. The dot on the icon and its tooltip say how it is: green — it runs, amber — a chain is paused, blue — a session waits for your answer, grey — starting or stopped for an update, red — it does not answer. **Quit** ends it until your next sign-in; `even-keel install` starts it again. Log: `logs\even-keel.log` (of the data folder when installed with npm).

It runs only while you are signed in. After a Windows Update restart at night Even Keel waits for you to sign in, unless Windows signs you back in to finish the update: Settings → Accounts → Sign-in options → "Use my sign-in info to automatically finish setting up after an update" (an organization's policy may turn that off). Signing out stops it; running sessions go on as they would after any stop.

**Windows: a service.** For a machine where Even Keel must run without anyone signed in, a clone can still be the Windows service `EvenKeel`: `service\install.ps1` from PowerShell 7 as administrator installs the dependencies, builds the page, compiles the service host the same way and registers the service under your account. The script never asks for your password: enter it in `services.msc` → EvenKeel → Properties → Log On, which also grants the "Log on as a service" right, then start the service. One of the two per machine: they would take the same port, so `even-keel install` refuses while the service is installed and `install.ps1` refuses while the start at sign-in is.

**Linux and macOS.** `service/install.sh` (installed with npm: `even-keel install`), as your own user, not with `sudo`. On Linux it installs a systemd user unit (`systemctl --user status even-keel`, log: `journalctl --user -u even-keel`). A user unit stops when you log out; to keep it running, `loginctl enable-linger $USER`. On macOS it installs a launchd agent `local.even-keel` (log: `logs/even-keel.log`), which runs while you are logged in. The script takes `PATH` and `node` from your shell; if `node` changes (nvm and the like), run it again.

## Updating

The gear menu in the header ends with the installed version. Even Keel asks GitHub for its latest release at start and every 12 hours (a request to `api.github.com` without a token; it names only the installed version); a newer one gets a mark next to the version and a notification in the corner of the page. Turn the check off on `/settings` → **Interface** or with `"updates": { "check": false }` in the config.

**From the page.** The mark and the notification open the update window: the installed version, the notes of every newer release, and **Update to <version>**. A release marked as a revert release (its notes have a **Reverted** section) says what of an earlier release it takes back. The update:

1. waits, up to 5 minutes, until no chain is starting a session, handing over or closing a task — a restart in that moment would pause the chain; the page shows which projects it waits for;
2. stops the service, checks out the release's tag (`git fetch --tags`, `git checkout`), runs `npm ci` and `npm run build`, and starts the service again; installed with npm, it runs `npm install --global even-keel@<version>` into the same global folder instead;
3. waits up to 2 minutes for the service to answer with the new version and keep running.

If any step fails, including no answer, it checks out the commit it started from, installs and builds it again (with npm: installs the version it started from) and starts the service: you are back on the version you had. Either way the page reloads by itself and says how it went; **Details** shows the failed step and its output, and the whole log is `logs/update.log` (the outcome itself is in `logs/update.json`). Running sessions are not touched.

The button is there only when Even Keel runs as a service and its folder is a clean git checkout on the tag of the installed version — a clone that you update with `git pull` on the main branch is one — or a global npm install. Otherwise the window says why and you update by hand. A checkout that was on a branch stays on it (moved to the new tag), so a later `git pull` still works.

After an update the window and the gear menu also offer **Revert to <previous version>**, the same process in the other direction, as long as the update did not change the format of the stored state. When it did, the older version cannot read the state any more: the window says so, and going back is the manual way below, losing what was written since. In that case it is better to wait for a revert release, which keeps the new format. After a revert the newer release is offered again; nothing updates by itself. Once the version is changed by hand (below), the window no longer shows how the last update from the page went, nor offers to revert it.

**By hand:**

- **installed with npm** — `even-keel update` stops the service, installs the latest release (`even-keel update 0.2.0` — that version) into the same global folder and starts the service again; unlike the button it does not wait for the chains, and a failed install leaves the version you had. Run from a terminal: stop Even Keel, `npm install --global even-keel@latest`, start it again;
- **a clone run from a terminal** — stop Even Keel, then `git pull`, `npm ci`, `npm run build` and `npm start`;
- **a clone as a service** — `git pull`, then run its install again (`node dist/src/cli.js install` on Windows, `service/install.sh` elsewhere, `service\install.ps1` for the Windows service): it installs the dependencies, builds the page and restarts the service.

On Windows a running Even Keel holds files in `node_modules`: `npm ci` next to it fails with `EPERM` and leaves the folder half-removed. Stop Even Keel and run `npm ci` again. Running sessions are not stopped by any of this: they belong to the CLI's daemon, and the restarted Even Keel picks them up.

### Plugins

The plugins come with the code. Chain sessions run the version of a package installed on `/tools`: its row shows the newer version the marketplace has and an **Update** button, or **Check** when it knows of none (for a git URL marketplace both run `claude plugin marketplace update` first). Even Keel's own plugins are read from this folder, so after an update their rows offer the new version at once. For sessions you start by hand, a marketplace added from the local path of this folder is read from the folder, so they get the new plugins by themselves; one added from a git URL keeps its own copy: `claude plugin marketplace update even-keel`, then `claude plugin update huly@even-keel` (or `github@…`, `linear@…`, `checkpoint@…`, `tally@…`) in each project repository that installed it.

### Stored state

A new version may store the files of `state/` in a newer format: at startup, before anything else, Even Keel rewrites them to it and keeps each old file next to it as `<file>.v<N>.bak` (the log names them). It rewrites all of them or none; a file it cannot read, or one written by a newer version, leaves the service with only the page, which shows the reason.

The projects, the settings, the chain's state, the questions posted to the tracker, the launch log and the handoff snapshots live in one database, the folder `state/even-keel/` (PGlite, the embedded Postgres the statistics use too). An Even Keel from before it kept them in a SQLite file `state/even-keel.db` or, earlier, in files: the first start of this version imports `even-keel.db`, or else `chain.json`, `questions.json`, `launches.jsonl` and `handoffs/`, in one go — all of it or nothing — and renames them to `<name>.imported`. The config file `even-keel.config.json` is imported the same way, once, and kept as `even-keel.config.json.imported`; a file put there later is not read (the log says so). A database written by a newer version leaves the service with only the page, like a newer file.

`npm run storage -- backup <new folder>` copies the database, also while Even Keel runs (to restore, stop Even Keel and put the folder in place of `state/even-keel`); with `.env` that is what a move to another machine needs.

The statistics database is versioned too: the collector brings its schema up to date on its first run after the update, step by step, each step in one transaction. Going back to an older version does not undo that: the older collector stops on a newer database (one line in the log) and `/stats` says so, until you update again or restore a backup of the database taken before the update (`<state>/tally/pgdata` for the embedded one). On your own Postgres the collector migrates as `tally_writer`; if it is not the owner of the tables, it changes nothing and logs the statements to run and the role to run them as.

### Going back

After an update from the page that kept the storage format, **Revert** in the update window does all of this. Otherwise, by hand: stop Even Keel (as a service — stop the service), check out the previous version's code (`git checkout <commit>`), put the `.bak` copies back in place of the rewritten files, then start it again (as a service — run its install script). Stop it first: a running Even Keel may write over the restored files. What the newer version wrote since the update — launches, the chain's state — goes with the `.bak`. The checkout leaves git on a detached commit, so the next update starts with `git checkout main` before `git pull`.

To go back to a version from before the database, stop Even Keel, run `npm run storage -- export <empty folder>` and put the files it writes into `state/`, and `npm run storage -- config-export even-keel.config.json` for its config, before starting the old version.

## Uninstall

`even-keel uninstall` (a clone: `node dist/src/cli.js uninstall`, or `service/uninstall.sh`) stops and removes the service and nothing else: on Windows the start at sign-in with its host, and the Windows service too if there is one (that part needs PowerShell 7 as administrator; a clone: `service\uninstall.ps1`). Sessions it started keep running: they belong to the CLI's daemon, so finish or stop them first (`claude agents` lists them). The rest stays where it is, for you to remove by hand:

- **Installed with npm** — the package (`npm uninstall --global even-keel`) and the data folder, which holds everything listed for a clone's folder below.
- **The Even Keel folder** of a clone — the code, `.env` with the tracker credentials, the config, `logs/` (Windows and macOS; on Linux the log is the journal), and `state/` (`EVEN_KEEL_STATE_DIR`) with the state database (`state/even-keel/`: the chain, the launch log, closed tasks), the installed packages (`state/packages`) and the embedded statistics database (`state/tally/pgdata`). Deleting the folder removes all of it. On your own Postgres the statistics stay in that database.
- **In each project's repository** — the worktrees of unfinished tasks in `.claude/worktrees/` with their branches `<key>-<number>/task` (`git worktree list`, then `git worktree remove` and `git branch -d`), the slots of a project with `slot`, and the lines `.claude/worktrees/` and `.temp/` Even Keel added to `.git/info/exclude`. With the plugin: `claude plugin uninstall huly@even-keel --scope project` (or `github@…`, `linear@…`) and commit `.claude/settings.json`.
- **In your Claude Code config** — the plugin credentials in the `env` of `~/.claude/settings.json`, the marketplace (`claude plugin marketplace remove even-keel`), and the extra account folders in `~/.claude-accounts` (`EVEN_KEEL_ACCOUNTS_DIR`), each still signed in until you run `claude auth logout` with its `CLAUDE_CONFIG_DIR`; the Codex ones in `~/.codex-accounts` (`EVEN_KEEL_CODEX_ACCOUNTS_DIR`) the same, with `codex logout` and its `CODEX_HOME`. The OpenCode ones in `~/.opencode-accounts` (`EVEN_KEEL_OPENCODE_ACCOUNTS_DIR`) hold their credentials in `data/opencode/auth.json`: deleting a folder signs it out. Project memory moved to `~/.claude-memory/<project>`, with `~/.claude/projects/<project>/memory` linking to it: Claude Code keeps using it through the link, so leave it unless you want the memory gone too. Your skills in `~/.claude/skills` moved to `~/.claude-skills/<name>` the same way, each leaving a link behind, and so did `~/.claude/agents`, `commands`, `hooks` and `output-styles`, to `~/.claude-agents` and the like: leave them, or move the folders back in place of the links.
