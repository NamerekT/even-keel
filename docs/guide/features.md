# What Even Keel does

## CLI copies

During first-run setup, CLI downloads and sign-in state appear on the agent cards. System warnings about CLI versions and usage limits appear after setup. Usage warnings name each affected account in a shared or project account pool, including accounts of other providers; accounts that need sign-in show that on their card instead.

**CLI version → Checked** runs sessions on Even Keel's own checked copy. A missing copy asks for consent with its version and approximate size when you choose a provider or add an account. Cancel keeps the choice; the chain waits. Blue progress bands under the header and on the agent card show downloaded bytes. **Installed** uses the CLI you manage. A failed download switches that provider to Installed and offers a retry; without a CLI, the card shows a copyable installation command and **Check again**. See [setup](setup.md#the-clis-it-depends-on).

## Project page legend

Open **?** above the side panel for a legend grouped by location: the header, project row, tabs, task card and session strip. Its queue and account samples match the header. It explains task states separately from priority numbers, dependency counters, the cache ring, release-carry agents and context usage. State marks have different shapes as well as colours. Fix and release-carry rows show their state beside the row key.

## Protection

**Sessions → Protection**, in shared settings or a project's settings, enables default groups of destructive-action
deny rules. They start enabled. A project can turn a group off, add native rules, or use shared protection. Changes
apply when a session starts; running sessions keep their existing settings.

Claude Code receives permission deny rules; Copilot receives tool deny rules. Codex receives command-prefix rules,
which also work in its full-access mode. Codex and Copilot match literal command prefixes only: defaults cover common
push flag orders (`git push -f`, `git push origin -f` for each of the project's remotes) and literal recursive-delete
targets. On Codex they also cover the refspecs that force-push or delete the project's main branch on each remote
(`git push origin +main`, `+HEAD:main`, `+main:main`, `+HEAD:refs/heads/main`, `:main`, `:refs/heads/main`) and the
other spellings of those targets (`C:\`, `C:/`, `~/`, `~/*`, `$HOME/`, `../`, `../*`, `/*`). Other argument orders, refspecs, shell expansions and, on Codex, MCP calls are outside those rules: on Copilot
`git push origin main --force`, a `+main` refspec and a push wrapped in `pwsh -Command` still run, and only denying every `git push` would stop the first two. A
Copilot rule of your own is written `shell(<command>:*)` for a prefix; a `*` anywhere else in it matches nothing. What does not hold on Codex, as seen live: a command with a redirection (`2>&1`, `> file`),
a variable or a substitution is checked as one whole command, so a forbidden push inside it runs; so does one wrapped
in `bash -lc`, `sh -c`, `pwsh -Command` or `cmd /c`, a flag after the branch (`git push origin main --force`), a
refspec of another branch, merged flags (`-uf`, `-Rf`, `-r -f`) and `git -C <dir> push`. Chains joined by `;`, `&&` or `|` are
checked command by command. Huly deletion rules apply to Claude, Copilot and OpenCode. OpenCode receives command
glob denies and tracker tool denies in its session configuration. Its additional rules are command patterns, one
per line: `*` matches any text and `?` one character (for example, `git reset --hard*`). Its default patterns cover
the same push and recursive-delete spellings as Claude's groups. Other spellings and shell wrappers may escape
them; the last matching OpenCode permission wins. Even Keel's built-in config hook appends active Protection denies
after the account's and project's permissions, including `agent.build.permission`, so their broad or explicit
allows do not override Protection. No extra package is needed. Keep server-side branch protection enabled.
The page explains coverage in a help tip and warns when an agent runs without a sandbox and without Even Keel rules.
Rules can reduce accidental actions; they are not an OS sandbox.

The agent reads your own deny files alongside Protection. Claude Code and Codex let a deny outweigh an allow;
OpenCode uses the permission order described above. Even Keel does not copy them; the `/tools` page shows what reaches a chain session. A `deny` or
`ask` only in the main checkout's `.claude/settings.local.json` does not — a task worktree does not read that file —
and the page marks it with where to move it. Codex's own `.rules` files of the project's Codex account and the
`.codex/rules/` committed on the branch are listed under **Codex rules**.

Before launching a project's session, Even Keel reads the main branch's protection on GitHub and Forgejo, using the
configured branch name and remote profiles. Missing protection, failed verification and potential administrator
bypasses appear on the project page beside a link to the server's branch rules. Enable rules blocking force pushes
and branch deletion there, including enforcement for administrators where appropriate. Even Keel does not change
server rules. GitHub rulesets with no bypass actors do not show a bypass warning; if the profile cannot read the
bypass list, the warning remains. Older Forgejo rules without a force-push switch are recognized as protection too.
Checks are cached for five minutes. No protection check is available for GitLab yet.

The [README](../../README.md) has the short version. This is every feature in full; the keys named here are in the [reference](reference.md).

## The chain

Tasks enter the chain by status (by default: ready and in-progress tasks — not the backlog, not closed ones) and by labels you choose; a task labelled `Manual` or `Вручную` never enters it, it is yours to run. Order: open blockers first, then the order you set by dragging on the page, then milestone, priority, task number. A task with an open blocker waits, and the blocker may be a task of another project in the same tracker: a client change blocked by its API change starts only once the API task is closed, against the merged API, while the client's chain runs its other tasks meanwhile. A task with subtasks never runs itself — its subtasks do, and on Huly Even Keel closes it once they are all closed. A project with nothing to run says so and opens the project in its tracker, where you file or ready the next tasks.

The rules of which statuses are in work, which are closed and which labels a task needs or must not have are set in **Settings → Chain** for all projects, on a tracker profile for the projects on it (each tracker names its statuses differently), and on a project's **Tracker** tab, the narrowest winning key by key. They are one form on all three: a table of the tracker's statuses, each in the chain, out of it or closed — by its category until you move it —, and a table of labels, each required or not taken, with "Take any" or "Only with a required label" under it. Even Keel's own labels are listed there too and do not change: `Manual`/`Вручную` keep a task out, `Question`/`Вопрос` only mark it, and with run labels on, `Claude | sonnet` and the like pick the model. The "From" column says where each row comes from — the category, the shared settings, the profile or the project; a row the level does not set is greyed but can be changed, and one it sets has a reset arrow. A level keeps each list whole: moving one status makes that level's list of in-chain (or closed) statuses its own. Which tasks of the tracker project are the project's at all is apart from the chain: **Project tasks** — all, only some milestones' or all but some milestones' — on the project's Tracker tab, and for all projects in **Settings → Chain**.

Errors above the chain always stay visible. Several cleanup and carry warnings share a folded row with their count and a short summary; open it for the individual actions. One warning stays open. When several closed tasks have cleanup warnings, **Done for all** dismisses them together; warnings on tasks still shown in the chain keep their own **Done** button.

If a task is merged but its tracker refuses to close it, the project page and card show the tracker's response and **Open in the tracker**. Fill the required field or close the task in the tracker yourself. Even Keel retries automatically every 30 seconds and continues the chain once the task closes. This wait is shown separately from a session waiting for your reply.

**Give the active milestone to tasks without one** assigns the current task's milestone to a task entering the chain without one, or the earliest milestone in the chain when the current task has none. The backlog's "will stand here" preview uses that milestone too. If the assignment would put a blocker after a task it holds, the task keeps no milestone. A successful assignment appears on the page in the same refresh; a milestone you later change or clear is left alone.

## Several trackers for one project

GitLab Issues works on GitLab.com and self-managed servers too. Opened issues enter by your required labels, closed issues are done, and native milestones and priority labels order the chain. On GitLab Free there is no blocking order; Premium and Ultimate provide native blocking links. Uploaded pictures and files from descriptions and comments appear on the task card, including in private projects; pictures appear in the text too. Files attached to a trusted answer in GitLab reach the session. The profile and optional `gitlab:task` plugin use the same personal token ([setup](setup.md#trackers-and-plugins)). GitLab CI pipelines and, in PR mode, merge requests are supported.

Jira Cloud works through the site's REST API with an Atlassian API token. Statuses go by their category: To Do is ready, In Progress is in progress, Done is done, and a status named Backlog stays out of the chain. A Scrum project has no such status: its backlog is a board view, every To Do issue is ready, so keep the chain to chosen issues with a required label. `Blocks` links order the chain, fix versions are its milestones (the earliest by release date) and priorities come from Highest…Lowest or your site's own scheme by its order. Descriptions and comments show as Markdown, attached pictures and files appear on the task card, and files attached to an answer reach the session. A task closes through the first transition its workflow offers to a Done status; a workflow without one leaves the task open and says so in the log. Jira has no CI of its own: the CI and PR mode come from the repository's remote. The optional `jira:task` plugin brings Atlassian's own MCP server on a separate MCP token or an OAuth connection ([setup](setup.md#trackers-and-plugins)). Jira Data Center is not supported.

A project's tasks can come from more than one tracker: its own, plus **task feeds** added in the project's settings, Tracker tab — say a private Huly project for your own work and the GitHub issues others file. Each feed is a tracker, an account (profile) on it, a place (a repository, a team) and a key; the tasks of all feeds make one chain in the one repository. A task keeps its tracker's id — Huly's, Linear's and Jira's own, GitHub's and GitLab's `<feed key>-<number>` — so each feed's key must give ids no other project or feed gives. Blockers work only within one tracker; across them it is the order you set, then milestone, priority and number. Each feed's task is judged by its own profile's rules, closed in its own tracker, and given to its session as text unless a package brings that tracker's MCP server signed in as the feed's account. A feed whose tasks the chain has run keeps its account; removed, its recently closed tasks stay on the page for a week, and the stats keep linking them where they lived.

**GitHub issues taken into your tracker.** If people report in your public GitHub repository while you keep the work in Huly or Linear, set **Take in GitHub issues with the label** in the project's settings, Tracker tab. Every open issue of the project's GitHub remote with that label becomes a task of the project's tracker with a link back; you put the label on once you have read the issue, and only those with triage rights can. The issue's text and its author's comments go in marked as information, not instructions; comments of the repository's collaborators go in as they are; nobody else's are copied, so a stranger cannot steer the work. When the task is done, the issue gets one line — "Fixed; it ships in v1.2.3", the version taken from the task's milestone and the repository's tags — and Even Keel closes it when that release is published. Two projects on one repository take different labels, for example the fixes of the released version and the next one. The GitHub profile's token needs **Issues: Read and write**.

Sequential within a project, not across them: `parallel` lets that many chains on different projects run at once (one by default). Other projects wait in a queue and start as soon as a chain ends. The usage limit stays shared: every running chain takes tasks until the window is used up, then they all wait for the reset.

Run labels in the chain and task card keep the provider's spelling and show only the model name after the last `/`: `OpenCode | opencode/deepseek-v4.1-flash-free` appears as `OpenCode | deepseek-v4.1-flash-free`. Hover for the full tracker label. If space is tight, only the model is shortened with an ellipsis.

## Sessions

If Copilot rejects an unavailable model before starting a normal transcript, the session shows the reason and a button to the project's session settings. Choose an available Model there (or change the task's model label), then choose **New session**. Even Keel does not switch models automatically.

For Claude background sessions, Even Keel checks process creation times to discard stale session records and leave another process that reused a session's or saved child's process number running. If the operating system cannot report a creation time, it keeps the previous process-number check.

Each task gets a background session (`claude --bg`) in its own git worktree `.claude/worktrees/<key>-<number>` on a branch `<key>-<number>/task`, made from `main` (or the project's `branch`; `main` below means that branch). The session does the task and merges its branch into `main`; Even Keel sees the merge, closes the task in the tracker, stops the session, removes the worktree and the branch, and syncs `main` with the remote. A sync that cannot reach the remote (no connection, a timeout, DNS) is tried again 30 s and 2 min later while the next task runs; only after the third failure does the project page show a warning to sync by hand.

A task that needs no change in the repository — done in `main` already, research, an answer — has nothing to merge. Its session ends the turn with the last line `NO CHANGES: <one line — why>`, and Even Keel checks the worktree: with no commits beyond `main` and nothing uncommitted it moves the task to Done, puts the line in a comment on it and cleans up as after a merge. With commits or uncommitted changes the session is told to merge them or drop them and mark again. In PR mode the `PULL REQUEST:` mark does the same.

What a session runs on — the provider, its model and its account — is set in the config, shared and per project; Claude sessions run on Opus by default, whatever `/model` last saved in the CLI settings. The model field takes any name and suggests the ones the row's account offers: OpenCode's own list, the models of the Codex account, Claude's aliases. With `modelLabels` on, a task's label `Claude | sonnet`, `Codex | gpt-6.1-sol` or a bare `Codex` picks it for that task; a label of a provider with no account set runs the task on the project's provider and says so in a toast.

Instructions for every session go into the **Prompt** of **Settings** → **Providers and models**, whatever project and agent it runs: Claude Code, Codex, OpenCode and Copilot each read their own global rules file, and Even Keel does not copy one into another. A project's own **Prompt** comes after it and adds to it rather than replaces it. Both are off until you write something, are passed as written (Markdown is fine) and go into every new session — the first start and every handoff; a resumed session already has them.

**Model prompts**, in the same settings tab, add instructions for sessions matching a provider and model: `Claude | sonnet*` covers Claude's Sonnet aliases, `* | *sonnet*` also covers full Sonnet ids through other agents. Only `*` is special (any string); case is ignored, and spaces around `|` are trimmed. A bare `Codex` covers every Codex session, including the CLI's default; an explicit model pattern needs a known model. Every matching row adds its prompt in table order. The field suggests names from the accounts' model catalogues, and each row lists its matches by provider. Claude and Codex lists are incomplete: a manually entered id may match too. No known matches is a warning and still allows saving. Older model-only keys are upgraded automatically, preserving their exact model match for every provider.

## Release branches

Fixes of a released version can run in a chain of their own while the next version goes on in another. Clone the repository a second time, check out the release branch there and add it as a project on the same tracker project, with the same key or one of its own (`huly` then names the tracker project; on Linear, `TEAM/Project`). Two projects of one key are told apart on the page by their name in brackets, `ABC (Release)`. The two split the tracker's tasks by milestone: the release project requires the release's milestone (`chain.requiredMilestones`), the main one excludes it (`chain.excludedMilestones`), and Even Keel refuses a pair that would both take one task. The "Add a project" form does this for you: on a tracker project another project already has, it asks for the milestones the new one takes ("Only tasks in milestones") and, as it adds the project, moves them into the other's **Project tasks** → "All except". They read the tracker once between them.

With `mergeInto` naming the main project, the release project is carried forward: Even Keel merges its branch into the main project's branch in the main project's checkout and pushes it, in batches, whenever the main chain stands — stopped, empty or paused — so a fix never lands in the middle of a task's merge. **Carry now** on the release project's page does it at once. A conflict is aborted and the carry waits, one line on the release project's page with the files and git's output under **Details**. Press **Resolve with the agent** and a session without a tracker task, `<KEY>-CARRY` of the release project, merges the release commit in the main project's own worktree after that project's current task, on its model and account, keeping the main branch's structure and putting the release fix's meaning on top; it shows as a row of the main chain, and once the main branch has the release commit the carry is done and the row closes as "Carry of <KEY>: N commits". A main project with no chain running gets one for this session alone. **Skip** on that row lets the session go and the conflict waits again. Turn on **Resolve a conflict with the agent by itself** under **Merges into**, or run unattended, and a conflict goes to that session at once, with no button to press; a session that did not land the carry gets no successor until the release branch moves, and then the carry is tried again. Or resolve it by merging by hand. A merge git refuses for another reason — the service's account has no git name and email, say — waits the same way, and the page shows git's message: fix that, then press **Carry now**. Nothing is ever merged into `main` of a released version; that moves by your release. The main project must be of the same repository — the two checkouts share a remote, or one is a clone of the other's folder: the settings offer only such projects, and a carry between two other repositories fetches nothing and says so.

If a carry merges but its push fails, the release project's page keeps the push error until Even Keel confirms that all remotes have the merge commit. It checks every minute, so a later push by hand or another task's sync clears the message automatically. A remote that cannot be reached leaves the message in place.

## Codex (preview)

Pictures Codex opens with `view_image`, including several returned by one tool call, appear as thumbnails in the session's chat and whole transcript. Click one to open the viewer and browse the session's pictures. They remain available from the transcript after the original files are removed.

The shared or a project's `provider` key (the shared one is also moved by giving the Even Keel role to the Codex account on the accounts page), or a `Codex` label on a task, runs the task's sessions on the OpenAI Codex CLI instead: one `codex exec --json` per turn, the transcript and context fill read from Codex's own session files, the project's packages passed on every turn. Limits (5-hour and weekly, or the free plan's 30-day one) are read from ChatGPT every five minutes, sharing a request with OpenCode on the same subscription; if the request fails, the latest limits in Codex's session files stand in. If ChatGPT revokes the sign-in before it expires (for example after a plan change), Even Keel asks Codex to renew it once and reads the limits again, without a model turn or spending the allowance. This waits until the folder has no live Even Keel sessions, including those between turns. A failed renewal is not repeated on every poll; renew the account's sign-in if needed. Codex has no question tool, so a turn that ends without the task done waits for your reply in the chat window.

For Codex, OpenCode and Copilot, Even Keel checks whether a turn's process number was reused by a newer process. The session then waits for your reply, and stopping it leaves the newer process running. A completed turn is also recognised when the CLI prints diagnostic lines after its final event. If the operating system cannot report the process creation time, process checks follow the previous behaviour.

Run it as a chain only on short test tasks. From the Windows service the Codex sandbox does not start (a Codex bug), so on Windows it needs `execution.codex` set to `bypass`, which runs Codex sessions with no sandbox at all ([What has not been verified](../unverified.md#codex)).

## OpenCode (preview)

Pictures returned by OpenCode tools, including images read from a file, appear as thumbnails beside the tool call in the session's chat and whole transcript. Click one to browse the transcript's pictures. They are read from OpenCode's database and remain available after the original files or worktree are removed.

`provider` set to `opencode`, or a label such as `OpenCode | opencode/big-pickle`, runs the task's sessions on [OpenCode](https://opencode.ai): one `opencode run` per turn, the transcript and context fill read from OpenCode's own database, the project's packages passed on every turn. The model is OpenCode's `<provider>/<model>` (`opencode/big-pickle`, `anthropic/claude-sonnet-4-5`, `openai/gpt-6.1-sol`); without one, OpenCode's default. A model the account's `opencode models` does not list is not launched: the chain pauses with a message and a button to the session settings. An error a turn ends on (a provider refusing, a server error) shows as an error line in the chat. The session reads the project's `AGENTS.md`, else its `CLAUDE.md`, and its skills ([below](#the-projects-instructions-and-skills)), but not your global `~/.claude/CLAUDE.md` or skills. Like Codex, it has no question tool: a turn that ends without the task done waits for your reply in the chat window. A turn that has written nothing for 30 minutes while its process lives on is taken for hung: the session shows as waiting with a note, and a message to it or "New session" stops the turn first; nothing stops it on its own.

The [checkpoint](../../plugins/checkpoint) plugin reaches it through an OpenCode plugin of its own: the handoff on a full context, chat messages delivered mid-turn, after the session's next tool call, and the check before the merge. Limits come from the provider you sign it in with: a ChatGPT sign-in shows its 5-hour and weekly windows (shared with a Codex account on the same ChatGPT subscription, and the cards say so), a Copilot one its monthly allowance; the free models and API keys have none, and the card says why. An account on the free models shows instead the tokens it used today and over 30 days (with Tally on) and when it was last refused by its limit; when the chain hits that limit, it tries again in 15 minutes, then waits longer each time it is refused again, up to 4 hours. It was checked as a chain under the Windows service on the free models only; a ChatGPT, Copilot or API-key account and Linux or macOS were never run ([What has not been verified](../unverified.md#opencode)): run them on test tasks first.

## GitHub Copilot (preview)

`provider` set to `copilot`, or a label such as `Copilot | gpt-6-luna` (a bare `Copilot` leaves the model to Copilot's `auto`), runs the task's sessions on the [GitHub Copilot CLI](https://github.com/github/copilot-cli): one `copilot -p` per turn, the transcript and context fill read from Copilot's own session files, the project's packages passed on every turn. The session reads the project's `CLAUDE.md` and `AGENTS.md`, both when both are there, and its skills ([below](#the-projects-instructions-and-skills)), not your global `~/.claude/CLAUDE.md` or skills. Like Codex, it has no question tool: a turn that ends without the task done waits for your reply in the chat window.

An account added with a token shows its monthly allowance, "N left, resets on the 1st", and a spent one waits for the 1st; give the token the "Plan" read permission too, or the card can only count what was spent, or nothing. A machine sign-in shows its monthly allowance when Copilot confirms that it uses GitHub CLI's sign-in; otherwise add an account with its own token to read its allowance. This fallback was checked in Windows session 0; Copilot's own saved OAuth sign-in and Linux/macOS remain [unverified](../unverified.md#copilots-machine-token-and-model-availability-btn-516). What it does not have yet: the handoff on a full context and chat messages delivered mid-turn rest on Copilot running Claude Code hooks, which was never seen. It was checked from a terminal only, never as a chain under the service ([What has not been verified](../unverified.md#copilot)): run it on test tasks first.

## The project's instructions and skills

A project written for one agent keeps its rules when its tasks move to another. A lone instruction file reaches every agent: Even Keel tells Codex to read a `CLAUDE.md` and gives Claude Code a lone `AGENTS.md`, which neither reads by itself. With both files, each agent reads its own one, and Copilot reads both:

| Agent | Only `CLAUDE.md` | Only `AGENTS.md` | Both | Skill folders |
| --- | --- | --- | --- | --- |
| Claude Code | `CLAUDE.md` | `AGENTS.md`, given by Even Keel | `CLAUDE.md` | `.claude/skills` |
| Codex | `CLAUDE.md`, given by Even Keel | `AGENTS.md` | `AGENTS.md` | `.agents/skills`, `.codex/skills` |
| OpenCode | `CLAUDE.md` | `AGENTS.md` | `AGENTS.md` | `.opencode/skills`, and `.claude/skills`, `.agents/skills` given by Even Keel |
| Copilot | `CLAUDE.md` | `AGENTS.md` | both | `.github/skills`, `.agents/skills`, `.claude/skills` |

To keep one set of rules for every agent, write them in `AGENTS.md` and make `CLAUDE.md` the single line `@AGENTS.md`: Claude Code reads the file it names, the others read `AGENTS.md`. Codex has no way to skills in `.claude/skills`; keep the ones it should see in `.agents/skills`, which Claude Code in turn does not read. Only what is committed on the main branch reaches a session.

**Settings** → **Sessions** of a project shows what a session of its agent gets: the instruction file, the shared and the project's prompt, the project's skills (and the ones the agent misses because of their folder), and the skills of the project's packages. When none of it is there, it says the project has no rules. The same table is under it.

## Standards

A rule that matters only for some files — how the screens look, how the API is written — need not sit in every session's instructions. Make it a standard: **Settings** → **Sessions** → **Standards** of a project ties a document of the repository to the files it guards, as masks from the repository's root (`**/*.tsx, web/**/*.css`), with exceptions (`**/*.test.*`). The document is picked from the Markdown files on the project's main branch; one that is not committed there is flagged, since sessions would not get it. **Add "Interface"** fills in the files a screen is made of — `.tsx`, `.jsx`, `.vue`, `.svelte`, `.css`, `.scss`, `.html`, tests excepted.

A session gets the document the first time it reads a guarded file. If it goes to edit one before that, the edit is refused once with the document, and the next one goes through. After a compaction of the context the document comes again.

With **Shots and answers before the merge** on, a task branch that changed the standard's files is not merged (in pull request mode, not handed to its pull request) until `.temp/shot/` holds screenshots taken after the last change and `.temp/<document>-check.md`, written after them, answers each question of the document's section "The check" — a list of questions under a heading of that name. The session is told what is missing and goes on.

Standards come with the [checkpoint](../../plugins/checkpoint) plugin and reach Claude Code, Codex, Copilot and OpenCode sessions; on OpenCode the pull request is not held back. A project has none until you add them.

## Slots

For repositories with heavy ignored caches (Unity's `Library`, big `node_modules`) a project can use a pool of permanent worktrees instead of a fresh one per task, so the next task rebuilds only the difference.

## Handoffs

A session that hit the usage limit is resumed a minute after the reset if its prompt cache is still warm, otherwise stopped and replaced by a new session in the same worktree with a handoff prompt. The service log records the task, account folder, reset time (or that it is unknown) and planned continuation once per limit, any update to the reset, and the successful resume or handoff with its session id.

The session panel groups the limit messages together, newest first, with earlier messages folded below. It names the affected account and provider and shows the reset in local time. Its settings button opens **Project settings → Sessions**: change that provider's account in the shared or own pool, or change the task's provider label. A task on a different provider from the active one does not change accounts when you switch the header's account.

The same handoff happens when a session ends its turn with a `CHECKPOINT: <path to a note>` line — the [checkpoint](../../plugins/checkpoint) plugin asks for it once the context grows past a threshold, 200k tokens until the project's own statistics give a better one, and stops asking below 300k after three handoffs of a task — and when you press **New session** on the page.

While a working turn writes nothing, the session card and **New session** tooltip show its last write and the times when replacement becomes available. After five quiet minutes you can interrupt it with confirmation. After thirty quiet minutes it is treated as hung: the session waits and **New session** needs no confirmation; a chat reply stops that hung turn before continuing, too. This applies to Claude Code (both transports), Codex, OpenCode and Copilot. New output resets the timer and invalidates an open confirmation. Streaming output counts even while Windows leaves a transcript's modification time unchanged. Nothing stops a silent turn automatically. A session waiting for an answer is not a silent working turn; Claude's background commands keep their separate one-hour check.

To leave a long session to the agent's own compaction instead, turn off **Handoffs by context size** in **Settings** → **Sessions**, for every project or in one project's settings: the plugin then never asks for a note because of the context, while the handoffs on a usage limit, **New session** and a note the session writes by itself work as before.

If the session writes `.temp/handoff.md` near the end of its turn but forgets the line, the plugin asks it to add it. This also covers Codex writing the note through a shell command with a literal file path. A path built in a variable or a write hidden inside another script still needs the session to add the line itself.

A task's row in the chain shows its live session: a ring for the prompt cache that drains until it goes cold, the context with its percent in blue, amber or red by its level, the account's initial when the session runs on an account other than the project's, and a counter of context resets — every handoff above plus every compaction of the agent's own — hidden while there are none. While the session works, the title has the first line to itself and the second is one field: what the session is doing right now, filled up to the context level with a clear edge, the percent, resets and initial at its end; on the current task's row the cache ring stands left of the lamp. A session that waits for a reply, rests or has stopped keeps the row on one line, with the context as a small bar. Point at a part for its figures: the minutes left in the cache, the tokens, the account's e-mail, the resets by kind.

What each lamp and shape of a row means, and each sign of the header that has no words on it — the limit rings, the account dot, the gear — is in the **?** tab after **Settings** at the right of the project page. It opens beside the chain, so you can check one against the other.

Notices under the header stay with it as you scroll, with a dividing line between them. The project settings panel leaves room for them and keeps its save button in view. When there are many notices, their area scrolls separately. Notices slide open and closed; reduced motion in your system settings disables that animation.

## Chat with the session

On a computer, Enter sends a reply and Shift+Enter starts a new line; Ctrl+Enter and Cmd+Enter also send. In a question's "Other" field, Enter goes to the next question or submits the last one, while Shift+Enter starts a new line. Selecting an option never advances by itself. Enter that confirms IME input does not send. On a phone or tablet, Enter starts a new line: use the buttons to send or go to the next question.

The **Chat** button of the current session opens its whole transcript with a reply box: the session's questions one at a time as a card with radio buttons or checkboxes, free text and files — picked with `+`, pasted with Ctrl+V (a screenshot straight from the clipboard) or dropped on the window — which land in the task's `.temp/inbox/`. Pictures the session read and the ones you sent show as thumbnails that open full-window, with a pager through all of them. Files the session sends you (Claude Code's `SendUserFile`) stand in the chat as a block of their own: a markdown file rendered in place, a picture as a thumbnail, anything else to download — as long as the file is still in the session's folder or its project's folder. The button turns amber while the session waits for you. Even Keel stops the session and resumes it with your answer. An unsent reply — its text and files — stays with each session's chat in your browser: close the window or reload the page and it is still there, until you send it.

If a turn stops on an API error, send a reply from the chat to resume the session. While the agent is still working or retrying the request, the usual rules for messages during a turn apply.

If OpenCode stays silent for 30 seconds, Even Keel also checks its account log for a stream error from that session. A usage limit then follows the usual limit wait; another stream error shows a translated message and lets you send a reply or choose **New session**. Without such an error, the existing hang check still applies.

If your reply cannot be delivered, Even Keel reports the failure and leaves the chain running. Send the reply again when the cause is resolved; Even Keel does not automatically retry a failed delivery.

You can also write to a session while it works ("not there", "mind X too"): a hook of the [checkpoint](../../plugins/checkpoint) plugin hands the message over at its next tool call or at the end of the turn, without stopping it, and the chat shows whether it waits, was delivered, or came back because the session asked a question meanwhile. If the hook times out before the service sends its response, the message stays queued for the next hook or resume. A Claude session on the Agent SDK transport needs no plugin for it: the message goes straight in and the session reads it once its current tool call ends.

If the turn ends before the hook takes your message, Even Keel resumes the same session with it, including when the chain stops after that turn. The message stays waiting until the resume succeeds; if it fails or another session takes over, the message comes back to the chat.

A Claude session that stops on a permission dialog — a command an `ask` rule in your settings holds, a call the `auto` classifier keeps refusing — puts the call to you as a question: "Allow the session to run Bash?" with the command under "Allow", and "Deny". Answer it from the chat, the question panel or the tracker comment, and the session goes on at once, without a stop: the call runs, or the session gets your refusal and your words. While the chain runs unattended such a call is refused at once. A session on `--bg` needs the [checkpoint](../../plugins/checkpoint) plugin for it (its hook holds the dialog), one on the Agent SDK transport does not; without the plugin the dialog is answered through Remote Control. Codex and OpenCode sessions never stop on such a dialog.

A question with options is also posted to the tracker as a numbered comment; reply with `2`, `1, 3` or text. Remote Control still works for Claude sessions: the page links each one's Remote Control ([setup](setup.md#answering-from-the-phone)).

## Task cards

A click on a task's title opens its card: the description and comments rendered from Markdown, labels with what each means to the chain, milestone, priority, and the tasks it blocks, waits for or relates to. A backlog task moves to Todo from its card, straight from the backlog panel or, when it holds a chain task, from its locked row in the chain, so the phone rarely needs the tracker's own page. On GitHub there is no backlog, so no Todo button.

The milestone on the card is a pick: choosing another one moves the task there in the tracker at once, and the chain reorders. Tracker changes reach the page on the next poll, every 30 seconds; the refresh button in the project head reads the tracker now.

## Changelog drafts

A button on a milestone's head in the chain has the agent write that milestone's changelog section in the Keep a Changelog format, from the titles and closing comments of its done tasks, in the language of your `CHANGELOG.md` (or `README.md`). It runs read-only, on the account and model the project's next session would get, and starts from the section already in your changelog file, so your own edits there stay.

You ask for changes in words and see them highlighted, with what each turn cost and on which account; "Write" puts the section into the file (the project setting `changelog`, `CHANGELOG.md` by default) and commits it to the main branch of your checkout; tasks closed later are added to the section with one button, and a released version's section is left alone. Tasks a user would not notice (refactoring, tests, process) are left out; when that leaves the section with no entry, the dialog says so and names the tasks instead of keeping an empty draft — say in a task's closing comment what it changes for users and write again.

## Hands off a stopped session

A session that asks a question or has a permanent failure is left alone: you answer it or move the task in the tracker yourself. A temporary model overload is retried automatically in the same session after 15 minutes, doubling up to four hours while it keeps failing and starting over after a successful answer. The page shows “waiting to retry” and the next attempt time. A chat answer or **New session** cancels that attempt; pausing the chain holds automatic retries. The provider variants and recovery through a real outage are [not yet verified](../unverified.md#temporary-model-errors-btn-498). You can skip a task, and a session that files a blocker for its task gets the task postponed until the blocker is done. When the blocker closes, or you undo Skip, a resting session is replaced with a new one carrying its handoff; the prompt names the closed blockers. A session working again, waiting on its own question, or given a message since the release is adopted and left to continue.

Work that sits in a task's folder but not in the main branch — files never committed, or commits never merged — is marked once the task is out of the chain: a red chip on its backlog row, or on its chain row when it was skipped or is closed, with the path, the branch and what to do on hover, a red dot on the **Backlog** tab, and a callout on its card. While the chain still leads the task, or is closing it and cleaning up, its uncommitted files are its session's and get no chip. So a task parked in the backlog with a finished change is not forgotten: answer it and move it back to Todo, and a new session picks the work up, or commit and merge it yourself. A closed task whose cleanup had to leave its folder behind stays in the chain list instead of going to the archive, with what the cleanup said in the chip's tip: commit and merge the work or delete the folder and it goes to the archive by itself, or press **Done** on its row. The mark follows the folder within about a minute, and at once after a cleanup.

## Keeping a waiting session warm

Off by default. A Claude Code session that waits for your reply keeps its prompt cache for an hour on a subscription, five minutes on an API key; an answer after that pays for reading the whole context again, and the chain hands a session over to a new one rather than resume it cold. With **Settings → Sessions → Keep the cache of a waiting session warm, hours** above 0, Even Keel asks a copy of the session for one word shortly before its cache would expire, so the next real turn reads it from the cache. The copy writes nothing: the session, its transcript and its question stay as they were, and the page and the statistics do not see the pings — the service log has a line for each.

It covers the current session of each running chain that is not paused and not on a limit, including a session waiting to retry a temporary model error, and in pull-request mode the sessions waiting on their open pull requests; never a session mid-turn or one whose cache has already gone cold. The pings stop after the hours you set, counted from the session's last answer, or once they would cost more than a cold start: 20 on an hour cache, 12 on a five-minute one. An overloaded ping is skipped and can be tried again while the cache remains warm. A ping that misses the cache or fails for another reason stops the pings for that session until the service restarts, and a restart forgets the pings, so a session waiting across one is let go cold. Each ping spends the account's limits.

## Unattended mode

For when nobody will answer — a switch in **Settings → Chain** (the gear in the header). Sessions are told to ask nothing, to do everything a question does not hold, and to park a task held by one: committed on its branch, unmerged, the question left in the task, the task moved to Backlog. A session that sits 10 minutes without the task done is skipped, and the session of a done task that stays busy for 10 quiet minutes is no longer waited for, so one stuck session does not stop the whole run.

## Lean sessions

Chain sessions start without claude.ai skills and plugins, and with niche bundled skills reachable only through `/name`, so their skill listing does not eat the context; the project's own settings still win. It is a switch in **Settings → Sessions**, and the settings files stay untouched. The `/tools` page shows what sessions get, for one project or several side by side: what will not reach them, settings by level, and the skills and tools the last session actually saw.

## Packages

Plugins and MCP servers are a set per project, kept by Even Keel and given to chain sessions by flags at every launch: a pinned version installed with one button, updated with another, while a running task stays on the version it started with. MCP servers run behind a local gateway, so the keys stay in Even Keel's `.env`.

Package settings on `/tools` can be changed for every project or for one project. Settings you leave at their inherited value follow the package's defaults after an update; your changes stay. Reset a value to inherit it again. A running task keeps the defaults of its pinned version.

A tracker's MCP server uses the project's chosen profile, or the last task feed's profile for another tracker, otherwise that tracker's default profile. The chosen profile supplies its whole set of connection fields: an optional address left blank uses the server's default, such as GitLab.com, even if the default profile points to a self-managed server. Jira, Linear and GitHub profiles can connect their MCP server through OAuth with one button instead of an MCP token; Even Keel keeps and refreshes that access, and the sessions never see it ([setup](setup.md#trackers-and-plugins)).

Codex sessions get the same set: the MCP servers, and of a plugin its skills and hooks (not its commands and agents), installed into each Codex folder on its first turn there and kept off for your own Codex sessions. OpenCode sessions get the MCP servers and a plugin's skills, plus hooks from plugins that bring OpenCode support: checkpoint and Huly do. Huly refuses descriptions and comments whose inline code is inside another formatting mark, and shows the estimate calibration when setting an estimate, with one refusal and a retry when the estimate disagrees with the data. The chain does not start a task while a package of its project is not installed, lacks a key or does not answer. Nor does it start a Codex task when Codex would not run a plugin's hooks (it checks that it trusts them first, and a new Codex version may change how): the session would go without the check before a merge and the context reminders. The page names the package; update Even Keel, or for now run the task on another provider.

Your own skills (`~/.claude/skills`, Codex's skills folder) reach only their own agent; **Add a package → My skills** on `/tools` wraps the ones you tick into one plugin package, so Codex, OpenCode and Copilot sessions get them too, and an edit of a skill shows as an update of the package. A skill that leans on Claude Code's own tools (Edit, `/rewind`, subagents) works poorly on another agent.

## Accounts

The account row's menu opens at the horizontal position you click, below the row (above it when space is short), and stays inside the window. Enter/Space opens it at the row's default position.

On a project's chain page, the header chip shows the account of its current session, or of the next task before it starts, including while the chain is paused or stopped. Hover or focus shows up to three distinct accounts in order: the task, the project's default and Even Keel's default. A coloured border and stack count mark a cascade; on phones the chip keeps the tightest usage window. Other pages show only Even Keel's account. Pressing the chip opens the full Accounts panel. Accounts without readable limits show token counts instead of empty limit rows.

Accounts appear only after you add them. In **Add account**, choose a provider: if its CLI already has a sign-in on this machine, the dialog offers that identity or signing in with another account. Otherwise it opens the usual sign-in choices. The first account added for a provider takes its unused shared pool entry. Removing an added global CLI account from Even Keel keeps its folder and CLI sign-in. An update keeps global accounts that were already visible; a new installation starts without them.

Your own Claude and Codex subscriptions — a personal and a work one, say — one config folder each. At most one Codex account may be on the free plan: OpenAI's terms do not allow several free accounts to get round the limits, so Even Keel refuses a second one ([docs/accounts.md](../accounts.md#the-codex-folders-btn-168-btn-176)).

OpenCode accounts are folders of their own too, signed in with ChatGPT or GitHub Copilot (a link and a one-time code), on an Anthropic or OpenAI API key, or with no sign-in for OpenCode's free models. There is no Claude subscription for OpenCode: Anthropic allows it only in Claude Code, so Claude in OpenCode is an API key ([docs/accounts.md](../accounts.md#the-opencode-folders-btn-214)).

GitHub Copilot accounts are folders too. One runs on the GitHub sign-in already on the machine (`copilot login`, which Copilot keeps for the whole machine, not per folder); for several GitHub accounts, add each with a fine-grained token that has the "Copilot Requests" permission. GitHub's terms allow one free account per person: several tokens are for several paid seats, not to stretch a free budget ([docs/accounts.md](../accounts.md#the-copilot-folders-btn-215)).

The `/accounts` page and the header\'s Accounts panel group accounts in bordered provider blocks, with accounts at work first. Each account is a row: its name, role chips and limits; the page also shows sessions (VS Code chats by tab title) and how they run. Click the row, or focus it and press Enter/Space, to move Even Keel or VS Code onto it, rename it or remove it. Unavailable actions say why. The Claude desktop app can be launched on a folder by hand ([account details](../accounts.md#the-claude-desktop-app)). Problems appear above the list with their fix. Shared limits and the source and age of readings are in tips. OpenCode and Copilot without a readable allowance share token counts for today and 30 days. At phone widths a row keeps the name, role and the tightest used percentage; the burger has one Accounts button with that percentage and an error dot.\n\nA provider\'s Add opens its sign-in choices; Add account at the top also offers providers with no accounts, whose empty blocks are omitted. Claude Code offers a subscription or API key; Codex a ChatGPT subscription or API key; OpenCode ChatGPT, GitHub Copilot, free models or API key; Copilot this machine\'s sign-in or a token. The dialog walks the sign-in steps, closes on success and highlights the added row. It opens over the current page, including setup and the project wizard. A missing CLI disables its provider with installation help. Until a provider has a registered shared account, its first added account takes that role. An account uses its given name, else e-mail, else provider (numbered for duplicates); Rename in the row menu changes only that name, and an empty name restores the default.

An account can also be an Anthropic API key, checked with Anthropic when added and then hourly: its sessions pay from the key, the page shows its spend today instead of usage windows (with statistics on), and it has no Remote Control. A session whose key runs out of credit is held, the key is checked every 5 minutes, and the chain goes on once it is topped up ([account details](../accounts.md#api-accounts-btn-99)). A spending cap also holds the current task: the account problem band and session panel show the reset date from the error, and the chain retries then, or sooner if a five-minute check succeeds after you raise the cap. You can switch accounts to continue immediately. Automatic recovery from a real spending cap and the workspace variant have [not yet been checked live](../unverified.md#api-spending-cap-recovery). A Codex account can be an OpenAI API key the same way, checked with OpenAI; a Codex session whose key runs out of money is held the same way. When a key is revoked or expires, the card says it isn't accepted: "Replace key" there or in its ⋯ menu takes a new one into the same account, so its name, roles and history stay. The new key is checked first and the old one stays if it is refused; a key of another organization is refused too, as it is another account to add on its own. Sessions already running finish on the old key, new ones start on the new one. A Copilot token is replaced the same way.

Claude sessions run one of two ways: `CLI --bg`, the CLI's own background sessions, or `Agent SDK`, where Even Keel holds each session's CLI in a small process of its own. Through the SDK a session outlives a restart of the service with its question still open, and an answer or a chat message goes straight into the running session instead of stopping and resuming it. A tool call the auto mode would put to you comes to the page as a question with "Allow" and "Deny" and waits for your answer, or is refused at once in unattended mode. Which one is Claude Code's "Execution" in Settings → Providers and models: `Auto`, the default, runs an API key account through the SDK and a subscription on `--bg`; `CLI --bg` or `Agent SDK` runs every Claude account that way. Each account's Runs through column says which way its sessions go. If you had picked the way per account before the update, the setting takes it over when every account agrees with `Auto` or every one was on the SDK; otherwise it is `Auto`, and the service log names each account whose way changed. Anthropic asks products built on the Agent SDK to sign in with an API key rather than a claude.ai subscription, so the SDK on a subscription is your call. The SDK needs the checked CLI (the "CLI version" next to it). Even Keel downloads the SDK alongside that CLI only after you approve the download; Checked sessions wait until both copies are ready. A change applies to new sessions, running ones keep their way ([docs/sessions.md](../sessions.md#the-agent-sdk-transport-btn-239-srcclaudesdk)).

## Limits

The windows of every subscription account are read every 5 minutes: Claude Code's 5-hour and weekly windows with its own `/usage` command (no quota spent), Codex and OpenCode's ChatGPT windows from ChatGPT, and Copilot's monthly allowance from GitHub. Between those reads a Claude session running through the Agent SDK keeps its windows fresh with the limits the CLI reports at each response. Even Keel stays inside them: while a window is exhausted the next task waits for its reset.

## Statistics (optional)

A built-in collector (Tally) reads the session transcripts every five minutes into an embedded Postgres ([PGlite](https://pglite.dev)) or your own: spend by day and project, cost and time per task, where sessions got stuck, slow commands, estimates against actual time, and before/after comparisons of changes to your rule files. All of it on the `/stats` page.

Statistics include history from existing account folders, including the global Claude and Codex folders even if you have not added those accounts in Even Keel. A folder left out of a scan keeps its reading progress while its files still exist, so changing the scan does not force that history to reload.

Task time includes Codex turns from its saved session files, including older sessions whose files are still available. Visible synchronous question waits are excluded from active time; waits the session file does not show remain included. OpenCode and Copilot currently contribute spend without turn times.

"Where the spend goes", the task table and rule comparisons group models by tier: Opus, Sonnet, Haiku and Fable for Claude; Sol, Luna, Astra and Terra for OpenAI. Versions within a tier count together; OpenAI models without a known tier appear as GPT. Other families, including DeepSeek, appear separately. Shares below 1% fold into "others".

"Rule changes" starts open and remembers your choice. Pick a chart mark to see "Before and after" and "By model" above the folded "What changed" details. Each side has its own model selection, saved in the URL; without a mark, "Side by side" compares models over the same page period. Account limit windows and checkpoint thresholds have separate folded sections; components show the 10 with most tasks, with "Show all" for the rest.

The last step of the first start's setup asks whether you want it — no stats, the local database or your own Postgres — and nothing is collected until you choose; the copy takes about a third of the transcripts' size. Switch it on or off any time in Settings → Stats: it applies at once, and turning it off deletes no data. Without stats the checkpoint threshold stays at 200k tokens.

A comparison is easier to judge when you know why a rule changed: add the hook `tally/bin/rule-hook.mjs` to `~/.claude/settings.json` and a session that edits a `CLAUDE.md`, skill, hook, agent or settings file is asked to log the reason in `<state>/rule-history.jsonl` (`ruleHistory` in `tally/tally.config.json`), which `/stats` attaches to the change:

```json
"hooks": {
  "PostToolUse": [{ "matcher": "Edit|MultiEdit|Write", "hooks": [{ "type": "command", "command": "node \"/path/to/even-keel/tally/bin/rule-hook.mjs\"" }] }],
  "Stop": [{ "hooks": [{ "type": "command", "command": "node \"/path/to/even-keel/tally/bin/rule-hook.mjs\"" }] }]
}
```

The page shows the numbers; the `tally` plugin draws conclusions from them. Its `tally:session-audit` skill answers "tasks got more expensive — why?" or "what changed after I edited CLAUDE.md?" from any project: it compares the period since your last rule edit (or the one you name) with the span before it — task cost and time, context per request, entry context, sessions per task, stuck spans, estimates — always cut by model, lists the rule edits, models and outlier tasks between them, digs into the tasks that show the cause and into handoffs and context compactions (what the next session re-read, what the ramp-up cost), and ends with proposals, each with the metric it should move. It only reads the database and changes no rule by itself. Install it in Claude Code with `claude plugin install tally@even-keel` once the marketplace is added ([setup](setup.md#with-the-plugin)); it finds Even Keel through the running service, or `EVEN_KEEL_HOME` set to the checkout ([plugins/tally](../../plugins/tally/README.md)). Estimates, statuses and components come from Huly: with another tracker the audit skips what needs them. Money is at API prices (`prices` in `tally/tally.config.json`), a ruler for comparing, not your subscription's bill.

## CI

A badge in the project's head shows the CI of each remote — Forgejo Actions, GitHub Actions or GitLab CI, found from `git remote` and the workflow folders or root `.gitlab-ci.yml` file: whether the API answers and a runner takes the runs, the current run with its tasks, jobs and steps against the usual length, and the recent runs. The current run, recent runs and usual length belong to the project's configured branch. The API is polled only while a run is unfinished or after a push. A failed CI outside the project's selection, or with the protection of main off, still gets a notification, which says that the chain does not use that CI to decide whether to continue.

After a task is merged and `main` is pushed, the next task waits for the CI's verdict (as long as the project allows) while its worktree is prepared. A red `main` is fixed first: Even Keel stops the session working on the current task, starts a session to fix `main` — with the failed jobs and the commits of the push in its prompt, without a task in the tracker — and, once the fix is merged, continues the stopped session with a note to merge `main` into its branch. A project can ask for a high-priority fix task in the tracker instead (`ci.fixTask`). If the fix is red too, the chain pauses instead of starting another.

If the CI turns red just as a session starts, Even Keel waits until it can tell whether the session is working or waiting before making room for the fix. A session waiting for an answer keeps its question and is set aside without being stopped.

OpenCode and Copilot accounts on the machine's sign-in can continue without an e-mail address. Continuing the same session requires the same account folder and a warm cache; a changed folder starts a new session with a handoff. An account that is signed out waits until it is ready again.

Several projects in separate clones of one repository, on the same main branch, share a red `main`: while one of them fixes it, the others start no new task and start no second fix of the same break; their sessions already at work go on. Once the fix is green, they all go on.

## A check without CI

A project with no CI, or whose CI does not answer, can name its own check commands, such as `npm run typecheck && npm test`. A session's merge into `main` waits until they pass in the task's worktree (a hook of the [checkpoint](../../plugins/checkpoint) plugin), and a failure goes back to the session to fix. If `main` moved while the task ran, Even Keel runs the check again on `main` in the next task's worktree before that task starts; a failure there is handled like a red CI.

## Pull requests (experimental)

With `pullRequests` on, a session does not merge its branch: Even Keel pushes it, opens a pull request on GitHub or Forgejo, or a merge request on GitLab, and takes the next task; review feedback and failed checks go back to the task's session, and a chain that ran out of tasks starts again for them by itself (one you stopped waits for **Start**). When the tasks are GitHub issues and the pull request is on GitHub, Even Keel ends its body with `Closes owner/repo#N`, so the issue shows the pull request and GitHub closes it at the merge; with GitLab Issues on the same GitLab server it ends a merge request with `Closes #N` (an issue of another project: `Closes group/name#N`). On GitLab every note of a member with Reporter access or above is feedback; approvals and other system notes, and bots, are not. A session that writes on its own pull request is told to put the hidden line `<!-- even-keel:session -->` into its text, and such a comment is not feedback, even when it is posted with your token. Use it at your own risk: on GitHub, opening, closing and merging a pull request, the owner's and collaborators' comments, reviews with line comments and failed runs reaching the session, `Closes owner/repo#N`, and the move to Done with the cleanup ran live, and Forgejo ran the same way with a conflict with the main branch; GitLab merge requests, their notes, line comments and failed pipelines ran live on GitLab.com and a self-managed server. In full — the `projects[].pullRequests` row of the [reference](reference.md#configuration).

## Status

The gear in the header has a dot when something is wrong and a **Status** row leading to `/status`, one screen: a line on top that says all is well or names the problems with a button for the first, a tile each for the service itself, the reading of the limits, the settings and the statistics collector, and a card per tracker account in use — whether it answers and when it last did, its error in plain words, the projects and task feeds it reads (those not read for a while marked), a **Check** button that reads them now and **Open profile**.

What waits for you also gets a notification in the corner while the page is open — a chain stopped on the usage limit, a red main, a session's question, a release carry that hit a conflict, a task that left the chain with its work not committed or not merged — with **Open** to the project. CI failures give one notification per project and commit, naming the failed CIs and updating in place when another fails. A closed notification returns only if a newly failed CI now holds the chain; an optional CI failure alone does not bring it back. An error on a card says what to do, and where a setting, an access profile or an account fixes it, a button under it opens that place.

In a session's usage-limit notice, press the **?** attached to the project settings button for the account and instructions on starting sooner. Press it again, press Escape or click outside to close the tip. Earlier messages expand below the button.

A carry conflict's notification goes away once an agent is assigned, and a conflict assigned automatically gets no notification. If you **Skip** the agent's session while the conflict remains, the notification returns.

## In the tray (Windows)

On Windows `even-keel install` makes Even Keel start at your sign-in, with no administrator, and puts its icon in the tray: a dot says whether it runs, a chain is paused or a session waits for your answer, and the menu opens the page, restarts Even Keel or quits it. It runs while you are signed in; for a machine nobody signs in to, a clone can still be a Windows service. In full — [As a service](setup.md#as-a-service).

## Updating from the page

A newer release gets a mark next to the version in the gear menu and a notification. Both open the update window: the notes of every release since yours, a mark on a release that takes back part of an earlier one, and **Update**. Even Keel waits for the chains to settle, checks out the release, builds it and restarts the service; if the new version does not come up, the old one comes back, and the page says what failed. After an update, **Revert** goes back to the previous version the same way, unless the update changed the format of the stored state. The button needs Even Keel running as a service from a clean clone; otherwise the window says why and you update by hand. Even Keel asks GitHub for releases only once you allow it: the first start's setup asks, and **Settings** → **Interface** changes it. In full — [Updating](setup.md#updating).
