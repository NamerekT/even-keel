# Sessions, models, prompts, limits

Reference for sessions: how Even Keel launches `claude` and watches it.

## Agent adapters (BTN-167, `src/agent/`)

The seam for a second agent (BTN-116: Codex), on the pattern of `src/tracker/`. The chain, the page, the accounts and the limits reach an agent only through `Agent` (`src/agent/contract.ts`); Claude Code is the one implementation (`src/claude/adapter.ts` over `ClaudeCli` in `src/claude/cli.ts`), registered by name in `AGENTS` (`src/agent/adapters.ts`) and set up once in `src/service.ts`.

- Every account folder carries its agent (`AccountHome.agent`, `AccountEntry.agent`), and a session runs on the agent of its account: `agentOf(home)` in `src/service.ts` picks the runtime for a launch (the account of the run profile, below), a resume, a stop, the monitor and the transcript routes. A session shows it as `SessionView.agent`. Nothing about the agent is written to the config or `state/`: an account folder is Claude's because `AccountHomes` makes Claude's.
- The contract: `launch`, `resume` (a limit resume, a reply and a checkpoint go on this way; a handoff is a `launch` in the same place), `stop`, `sessions` (the folder's sessions as `AgentEntry`), `tail` (a transcript read as it grows, `summary()` is the `TranscriptSummary` the page and the chain read: stage, action, context fill, the question, the API error), `record`, `feed`, `transcripts` (which sessions a folder holds, for `TranscriptOwners`), `authStatus`, `login`, `logout`, `env` (the session's environment: `sessionBase` without the trackers' and CIs' credentials plus `CLAUDE_CONFIG_DIR` for a folder other than the global one).
- Optional, because only Claude has them: `usage` (`claude -p /usage`, parsed by `parseUsage` in the adapter; without it the account is not polled), `stopDaemon`, `liveRecords` (the apps panel), `remote` (Remote Control). `SessionStart.settings` is Claude's `--settings`; `model` is the model name as the CLI takes it, `null` — the CLI's own default. The cache lifetime, `AskUserQuestion` and the job files stay inside the Claude adapter and the transcript fold.
- The contract does not need a live process between turns: a session is its id and its transcript, `resume` may start a process per turn (`codex exec resume`).
- The agent of a new session (BTN-168, BTN-173): see "Run profiles" below. `choiceFor(project, task)` in `src/service.ts` picks the account folder a launch, a handoff (`relay`) and a fix session (`launchFix`) start in. The chain judges a launch block, the limits and the relay account by that same folder (`blocked`, `limitReset`, `account` in `src/chain/model.ts` take the project and the task). `agentExtras` adds what only Codex takes: the bypass (`execution.codex`) and the tracker's MCP server. Still Claude's and left for the accounts page: `AccountHomes` (folders, `.claude.json`, `.credentials.json`, sharing), `parseAuthStatus`, `parseCredentialTimes`, the statusline's `rate-limits.json`.

## CLI and transcripts

- Sessions are the `claude` CLI (`--bg`, `agents --json`). The binary: `EVEN_KEEL_CLAUDE_BIN`, otherwise the standalone CLI `~/.local/bin/claude.exe` (outside Windows — `claude`), otherwise the binary of the newest VS Code extension version (an extension update deletes its folder).
- Transcripts are in `<account folder>/projects`. `claude agents`, transcripts, `sessions/<pid>.json` and `settings.json` are read for each account folder.
- `claude agents --json` (2.1.284) prints neither `pid` nor `status`, and `state: done` stays both for a live session after a turn and for a stopped one: a live process, `pid` and `busy`/`idle` come from `sessions/<pid>.json` entries with a live `pid` (`withLiveRecords`).
- Prompt cache freshness comes from the transcript: the lifetime (5 min or 1 h) by `usage.cache_creation` of the last response that wrote the cache (if both are present, 5 min is taken), counted from the first line of the last response.
- The progress feed on the page is the last 30 lines of the fold (`TranscriptFold`): texts and tool calls, API errors and human requests (`kind: 'prompt'`; without `isMeta`, tool results, `origin.kind` other than `human`, and client context blocks like `<ide_selection>`, `<pasted_content>` stays). The "Whole transcript" button is `GET /api/sessions/<id>/transcript`: the same fold without truncation (`whole`), with the full command in `detail` for Bash and PowerShell. For a live session the window reads further every 3 s with `?after=<how many lines it already has>`: fold lines are only appended, and the service folds the file anew each time (14 MB — ~150 ms). Requests do not go into the handoff on a limit.
- Questions and answers (BTN-101, `src/sessions/ask.ts`): a pending `AskUserQuestion` call is the session's open question, `SessionView.ask` (`tool_use` id and its questions); in the whole fold the call's line carries it as `line.ask`. Its `tool_result` with `toolUseResult.answers` becomes an `answer` line with `answers` (the question it answers and the answers by question text). A result without answers (the call was interrupted or failed when the session was stopped) leaves the question stray, and the next human prompt answers it: that prompt is an `answer` line too, its answers read back by `answersIn` from its `- "question" → answer` lines. Any new prompt clears the open question.
- A pending `AskUserQuestion` is not in the transcript (verified on CLI 2.1.296, 2026-10-12): the CLI writes the whole last message — the text before the call and the call — only together with the answer. Until then the session record says `status: waiting`, `waitingFor: "input needed"`, and the question is only in `block.questions` of `jobs/<id>/state.json` (`needs` is `answer: <question> (<labels>)`): the question text and the options with descriptions, without `header`, `multiSelect` or `preview`. `withJobFiles` reads it for a live waiting session (`blockedAsk`) and the monitor gives it as `SessionView.ask` when the transcript has none: the id is `job:<job id>:<hash of the questions>`, `unsaved: true`, every question is a single choice without a header — several options go through "Other" on the page, and `1, 3` in a tracker comment stays text. `claude stop` loses that message for good: after `--resume` the transcript has a synthetic `No response requested.` in its place, and the session sees neither its text nor its question.
- The reply prompt (`replyPrompt`, in `promptLanguage`, BTN-182) is what the user sent and nothing more, since the chat shows it as the user's message: the `- "question" → answer` lines, the user's text, then `Files from the user:` and the paths. For an `unsaved` question one service line goes first, that the question was lost when the session restarted, and each question gets its answer line (or `- "question"` alone when skipped) with the chosen options' descriptions indented under it. Where the answer came from (the page or the tracker) goes only to the service log (`Reply.from`). `replyParts` takes a prompt apart again for the chat — the answers, the user's own words and the files — and also strips the service lines of older prompts (`LEGACY`: the source intro, the "call above" paragraph, the comment label, the numbered lost block). An empty reply is `answer.empty`. Files are saved first into `.temp/inbox/` of the task's folder (`src/sessions/inbox.ts`: safe names, no overwriting, a `.zip` unpacked with `tar -xf`, `unzip` as a fallback); the folder has its own `.gitignore` with `*`, so the worktree stays clean and cleanup after Done does not stall. How `--resume` treats an unanswered `AskUserQuestion` that did reach the transcript is not verified, so the prompt does not depend on it.
- `claude --bg --resume <id>` starts a copy under a new session id (the page shows it as a new chat with the whole history again) when the session is still running or, if its job `jobs/<job id>/state.json` is saved, when any flag is passed: such a session keeps its own options (model, permission mode, name, settings), and the CLI prints `note: … keeps its own saved options, so the flags you passed started a copy` (reason `own-options`, read from the 2.1.302 binary). So a reply or a limit resume passes only `--bg --resume <id> <prompt>` when the job is saved (`resumeArgs`): the session goes on in place with the options of its launch (verified live on 2.1.302, 2026-10-17), and a run label or model changed meanwhile applies only from the next launch. Without a saved job the flags are passed as at a launch. The dispatcher still looks for the resumed session by that id or, like after a launch, by the task name, the folder and the start time (`resumedAs`) — the latter only for another job than the resumed one. Resuming in place, the daemon kills the job's process and spawns a new one, and for under a second that process shows a fresh session id (in `claude agents` and `history.jsonl`) before it loads the session and takes the old id (2.1.302, 2026-10-18): taking that fresh id gave the chain a session with no transcript — "transcript not found" in the chat and "Session booting" for 5 minutes.
- `claude --bg` goes through the supervisor daemon (`claude daemon run`, on Windows the pipe `\\.\pipe\cc-daemon-…`). Stopping the service does not kill background sessions — they are children of the daemon.

## Codex (BTN-168, `src/codex/`)

Checked on codex-cli 0.162.1. The binary: `EVEN_KEEL_CODEX_BIN`, otherwise on Windows the native `codex.exe` of the global npm package `@openai/codex` (its `codex.cmd` needs a console), otherwise `codex`.

- A turn is `codex exec --json … [resume <id>] <prompt>`, a detached process with its stdout written to a file (`state/codex/turns/<name>-<ms>.jsonl`), not a pipe: it outlives the service. Every flag goes before `resume` — the subcommand takes none of its own. The thread id is the first event (`thread.started`); the turn is over at `turn.completed`/`turn.failed`.
- Codex has no list of background sessions, so Even Keel keeps its own registry: `state/codex/sessions/<id>.json` (`sessionId`, `name`, `cwd`, `account`, `startedAt`, the `pid` and output file of the last turn, `stopped`). Between turns there is no process: the session is `idle` with `resting: true`, and liveness checks go through `isLive` (a live pid or `resting`). `stop` kills the turn's process tree (`taskkill /T /F`, elsewhere `process.kill(-pid)`) and marks the session `stopped`.
- The transcript is the rollout `<CODEX_HOME>/sessions/YYYY/MM/DD/rollout-<time>-<id>.jsonl`; a resume appends to the same file. The fold (`RolloutFold`) reads `session_meta`, `turn_context` and `event_msg` lines; the context fill is `info.last_token_usage.input_tokens` of `token_count` against `model_context_window`. An `event_msg` of type `error`, or the `error` of a failed turn's `task_complete` (how 0.162.1 writes a rejected request, e.g. a model the plan does not have), is the API error, a limit when its text says so; a message that is the API's JSON answer shows its inner `error.message`. Codex has no Remote Control: its sessions get neither a link nor the "Remote Control is off" note.
- Limits come from `rate_limits` of the newest `token_count` in the account's latest rollouts (`usage` of the adapter): the 300-minute window is the five-hour one, the 10080-minute window the weekly one, the 43200-minute window the month (`RateLimits.month`; the free plan has only that one, `plan_type: "free"`, seen on 0.162.1), a window of another length is not shown. A plan with a month shows it in place of the windows it lacks (`limitSpans`), the chain counts a spent month like a spent week, and a limit hit on it waits for the month's reset. No rollout — no data. Tally does not snapshot the month (`span` is `5h`/`7d` only).
- Flags: `--approve-for-me` (chain sessions run without a human: Codex's automatic reviewer approves inside its sandbox), or `--dangerously-bypass-approvals-and-sandbox` instead when the shared `execution.codex` is `bypass` (below), `-m <model>` when the run profile has a Codex model (below), the MCP servers of the project's packages as `-c mcp_servers.<name>.url=<gateway address>` overrides (`src/codex/mcp.ts`, `docs/packages.md`): Codex's `config.toml` is never written, and the turn holds no credentials — the gateway adds them.
- The Codex sandbox does not start under the Windows service (BTN-171, checked on 0.162.1 and 0.163.0). Codex creates its private desktop on the window station of the calling process and starts the command on `Winsta0\<that desktop>`; in session 0 the service's station is `Service-0x0-…$`, so every program that loads `USER32.dll` (`git`, `node`, `pwsh`) dies with `0xC0000142` (`unelevated`), and the elevated runner never connects ("timed out … connecting runner pipe-in"). `cmd /c echo` still works, which hides it. Upstream: openai/codex#46412, #37722; no admin setup fixes it. On 0.162.1 the elevated sandbox fails even earlier with "setup refresh had errors" while the Codex desktop app runs (openai/codex#51601, fixed in 0.163.0). Hence the shared key `execution.codex` (BTN-173; before it the project key `codexBypassSandbox`): `sandbox` by default, `bypass` — sessions run with no sandbox and no reviewer. It is shared only, since the sandbox fails for every project alike; Claude has no modes, and `execution.claude` is a config error.
- There is no `AskUserQuestion`: a turn that ends without Done leaves the session resting, it is answered from the page's chat window (`resume`), and nothing is posted to the tracker (BTN-166). The prompts stay Claude's; the unattended line about `AskUserQuestion` is harmless here.

## Run profiles (BTN-173, `src/sessions/launch.ts`)

What a session runs on is three dictionaries keyed by provider (`claude`, `codex`; `src/agent/providers.ts`), at two levels, plus the provider itself:

- `provider` — shared and per project (`claude` by default). Formerly the project's `agent`.
- `models: { <provider>: <model> }` — shared and per project; a project's entry overrides the shared one of that provider, other providers come from the shared. The shared `models.claude` is `opus` by default: a Claude session is never launched without `--model`, since the CLI would take the model from `settings.json`, which `/model` rewrites in any editor on the same account. Codex has no built-in default — `null`, the model of its own `config.toml`.
- `accounts: { <provider>: <account key> }` — the pool, shared and per project, merged the same way; an account key from `/accounts` (BTN-169) fixes the provider. Defaults: `global` (`~/.claude`) and `codex` (`~/.codex`); a Codex account added from the page is a folder under `~/.codex-accounts` (`docs/accounts.md`). The active account of the header is the shared provider's entry, and moving the "Even Keel" role moves the shared provider (`docs/accounts.md`). One account per provider: a spent limit is not rotated — the chain waits for the reset or an edit of the pool entry the project uses, and a new account means a new session with a handoff.
- `modelLabels` — shared and per project, off by default: whether the tasks' run labels are read.

`runSettings(config, project)` in `src/config.ts` fills a project's values over the shared ones. `runChoice` picks: with labels on, the task's run label (`Task.runLabels`, `runLabelOf` in `src/tracker/model.ts`) — `<provider> | <model>` such as `Claude | opus`, `Codex | gpt-6.1-sol`, or a bare provider (`Codex`, the label of BTN-168) that takes the model from the dictionaries; the provider is compared case-insensitively, whitespace around `|` is trimmed, the model goes to the CLI as written (a typo is the session's error on its first turn). Otherwise, and when a task carries more than one run label (a warning in the service log), the project's provider and model. The old `Sonnet`/`Opus`/`Haiku` labels are not read any more. A label whose provider has no account in the pool (`hasAccount`: the key names a folder of that provider) does not pause the chain: the task runs on the project's provider with the project's model, the launch log entry gets `fallback` and the page a toast (`chain.noAccountFor`, `docs/web.md`).

The choice is the task's and the project's, not the previous session's: a handoff (limit, checkpoint, "New session", reply) stays on the same provider. `launchPlan` appends `modelPrompts.<model>` to the prompt: the key is any model name as the CLI gets it (`opus`, `gpt-6.1-sol`), compared case-insensitively; a model left to the CLI has none. The model goes on every launch — first, `--resume` without a saved job, handoff, "New session".

## Extra tools (BTN-74, `src/tools/`)

Plugins and MCP servers are the project's packages, given by flags at every launch (`docs/packages.md`). What stays here is the rest of `--settings` and the "What sessions get" page.

- The "Trim the tools" switch on `/settings`, the Sessions group (`chain/trim`, `ChainState.trimTools`, on by default): chain sessions are launched with `--settings <JSON>` (`chainSettings`) — `syncClaudeAiSkills` and `syncClaudeAiPlugins` are off, skills from the config's `hiddenSkills` (default `DEFAULT_HIDDEN_SKILLS`) are `user-invocable-only`, that is, only through `/name`. It applies on every launch: first, `--resume`, handoff. The settings files are not changed, `--settings` affects only that launch (verified on CLI 2.1.290: `--bg` passes it through, claude.ai skills do not go to `.trash`).
- With the switch off, `--settings` still goes: it carries `autoMemoryDirectory`, the shared memory folder (`docs/accounts.md`), and `enabledPlugins: false` for the enabled plugins outside the task's set (`docs/packages.md`).
- The CLI looks for `.mcp.json` in the parent folders as well, so a session in a worktree inside the main checkout would see the servers of the main checkout's `.mcp.json`, even an untracked one, and hang on their approval dialog (BTN-86). `--strict-mcp-config` of the packages cuts them off: no `disabledMcpjsonServers` any more.
- A stdio MCP server of a plugin that failed to start is cached by the CLI in `<account folder>/mcp-needs-auth-cache.json` for 15 minutes (BTN-159, CLI 2.1.302). Chain sessions no longer run plugin servers themselves — the gateway does — so Even Keel does not read that file.
- A session that hangs on any startup dialog is visible only in its job file: `claude agents --json` shows `state: blocked`, as for a question, while `<account folder>/jobs/<id>/state.json` gets `tempo: blocked` and in `needs` what the dialog asks for: for a known one, e.g. `approve 1 new project MCP server (strata) — attach to respond`, otherwise `open this session to continue setup` with `detail: "stuck on a startup dialog"` from the CLI's 45 s watchdog (2.1.296). A blocked session without a live `sessions/<pid>.json` has not begun its first turn, so Even Keel reads that file for such sessions (`withJobFiles`, `blockedOn`), puts `needs` into `SessionView.startupDialog`, the panel says why the session stands and the service log has a `sessions: … hangs on a Claude Code dialog` line. Such a session is not mid-turn: "New session" and "Skip" stay available. The dialog itself cannot be seen from a terminal: the service's daemon is in session 0.
- `skillOverrides` of the project (`.claude/settings.json`) and of the main checkout (`.claude/settings.local.json`, which overrides the project one, as in the CLI) override the list. A session in a worktree does not read the main checkout's `settings.local.json` — its `skillOverrides` reach it only through `--settings`.
- The "What sessions get" page is `/tools?projects=A,B&diff=1` (`web/src/tools/`); without `projects` the first two chain projects are selected, so the matrix is not squeezed. The project page has a line with the number of problems and a link. The project choice is the same list as on `/stats` (`web/src/ui/ProjectList.tsx`); at the top is the packages table (`docs/packages.md`), then the problems merged across projects (won't reach the session, claude.ai skills, MCP servers the last session failed to connect, accounts), below is a "setting × project" matrix by section with the result for the session and level marks; `diff=1` ("Only differences") shows only the rows where projects differ; the logic is `web/src/tools/matrix.ts`. Per-project data is `GET /api/projects/<key>/tools` (`readToolsView`): a table of settings by level (user, project, local, Even Keel) with the result for the session, the difference between the accounts' `settings.json` and the global one (key names only — `env` holds secrets) and what the project's last session received: the start of its transcript (first 400 lines; the worktree folders `<repo>--claude-worktrees-*` first) — `skill_listing`, `prompt_snapshot.tools`, `deferred_tools_delta`.

## Checkpoint threshold (BTN-86)

The `checkpoint` plugin's hook (`plugins/checkpoint/hooks/context-checkpoint.mjs`, the rules in `nudges.mjs`) asks a session for a handoff by context size. The first nudge is at 200k, the next every 50k up to 250k and every 25k past it. The hook reads no transcript, so it works the same for Claude Code and Codex: on every tool call it asks the service about its session, `GET /api/sessions/<id>/checkpoint` → `{ project, task, handoffs, first, source, context }`, 404 for a session the chain did not start. `context` is the session's context fill as the service's monitor last read it from the transcript (`SessionMonitor.contextOf`), `null` while it has not; with no answer, a 404 or a `null` the hook is silent, so a session started by hand gets no nudges. The `CHECKPOINT_*` variables still override the steps. Environment variables are not used to pass the answer: whether they reach a session through `claude --bg` and the daemon was not checked.

The plugin's `Stop` hook (`checkpoint-mark.mjs`) sends back a turn that wrote `.temp/handoff.md` among its last three tool calls but ended without the `CHECKPOINT:` line. Whether it did comes from `GET /api/sessions/<id>/note` → `{ note }` (`noteAtEnd` in `src/sessions/note.ts` over the agent's `feed`; a Codex file change is an `Edit` line).

- `handoffs` (`handoffsOf` in `src/chain/launches.ts`) is the number of the task's sessions started by `checkpoint`, `restart` or `relay`, up to and including this one. From the third on the hook is silent below the hard threshold of 300k: on tasks with many handoffs most of them lost money (CBL-596: 12 handoffs, $17.5 spent, $5.3 saved).
- `first` with `source: "calibrated"` or `"config"` replaces the hook's own first threshold; `"default"` leaves it alone.
- Calibration (`src/stats/checkpoint.ts`, the query `CHECKPOINT` in `src/stats/reader.ts`): `first = base + (note + recovery) / (cache read price × 40 requests)`, rounded to 1k and kept within 150–250k. `base` is the median context of the project's checkpoint successors at their 15th main-thread request, `note` the median spend of a session from its first write of `.temp/handoff.md` to its end, `recovery` the median spend of a successor before its first edit, the price is that of the successors' most frequent model in Tally's `model_prices`. The work left, 40 requests, is a constant, about the lower quartile of what was measured: a measured remainder depends on the threshold itself (a higher one shortens it and pulls the threshold up, the successors' recovery requests inflate it and pull down). The hard threshold and the limit of handoffs are not calibrated.
- It applies once the project has 20 checkpoint successors and 50 sessions that went over 150k; until then, and without statistics, the threshold is 200k. `stats.checkpointTokens` in the config pins it for all projects and switches the calibration off.
- Measured on 2026-10-10: CBL — base 73k, note $0.18, recovery $0.64, 168 successors → 176k; BTN — 79k, $0.18, $0.69, 32 successors → 187k. Why 150k was too early: with a 1 h cache write at $8/M against a read at $0.2/M, rebuilding the context costs as much as re-reading it 40 times, and of 163 CBL handoffs at 150k 93 lost money ($177 spent, $132 saved).

## Prompts (`src/sessions/prompt.ts`)

Assembled strictly: a value in the launch and handoff prompt goes through `fill`, and an empty or non-string one is an assembly error — the chain pauses with it instead of going into a session with a blank space. `modelPrompts` is passed as is, with no substitutions: `{name}`, `{{name}}`, `${name}` is a config error. A project whose tracker has a project key in the config (`github`, `linear`) gets the line "Tracker: GitHub, project octo-org/abc." after the launch or handoff text, brief or not (`withTracker`): with the brief off the prompt otherwise carries only the task id, and the GitHub skill fell back to `origin`, which may be missing or point elsewhere (BTN-143). A project's `prompt` (BTN-97, `withProjectPrompt`) goes under the heading "Instructions for this project:" after the brief and before the unattended rules and the model prompt, into the prompt of a new session only — the first launch and a handoff; `--resume` and a reply continue a session that already has it. It is free text and is not checked for substitutions; an empty one is no prompt. The session that fixes a red `main` without a task (BTN-115, `docs/chain.md`) has no brief: its prompt is `fixPrompt` — the report of what broke, the worktree, the branch and its rules — with the project's `prompt` after it, and a handoff of it carries the report again (`withReport`). The prompt language is `promptLanguage` (`src/chain/prompts.ts`, see `docs/web.md`).

## Limits

- Each account has its own: `claude -p /usage --output-format json --no-session-persistence` in its folder every 5 minutes (a local command, spends no quota) and a statusline snapshot (marked with the session's `configDir`; without the mark — the global account); the fresher one is taken.
- Do not poll more often: the server answers `/api/oauth/usage` with 429, the VS Code extension panel polls it with the same token, and after a 429 the CLI (2.1.286) does not query this token for ~45 min.
- With an expired access token or after a 429, `/usage` returns no limits (the subscription line is there, the window lines are not) — that is "no data" (`stale`), not an error. A `/usage` answer is accepted whole or not at all: both window lines with a percentage and a reset (`0% used` without a reset — the window has not started).
- Polling continues only if the answer says outright `num_turns: 0` and `total_cost_usd: 0`, otherwise it is switched off until restart. An unreadable answer or switched-off polling is shown by the page as a banner (`UsageBanner`).
- While a window is used up, the next task is not started: the chain waits for the reset (`limitUntil`) and continues by itself.
- A limit on a running session whose text gives no reset time (the `wrap_up` warning) takes it from these limits once they are newer than the limit (`docs/chain.md`, exception 1).
- An API account (`docs/accounts.md`) has no windows: `/usage` is not polled for it (in its folder it answers free with no window lines), and exception 1 does not apply to its sessions.

## Prompt cache lifetime (BTN-99)

What the CLI 2.1.302 binary does, in order of precedence: the `FORCE_PROMPT_CACHING_5M` variable → 5 minutes; the variables `CLAUDE_CODE_PROMPT_CACHE_TTL` / `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`; the settings `promptCacheTtl` / `subagentPromptCacheTtl` (`"5m"` | `"1h"`), whatever the sign-in; the `ENABLE_PROMPT_CACHING_1H` variable → 1 hour. Without any of them: 1 hour on a subscription within its limits (5 minutes in overage), 5 minutes on an API key, Bedrock or Vertex. A 1-hour cache write is billed higher than a 5-minute one.

The `cacheTtl` config key (`"5m"` | `"1h"`, absent or `null` — the CLI decides; `/settings`, the Claude Code group) goes into the chain sessions' `--settings` as `promptCacheTtl` (`chainSettings` in `src/tools/panel.ts`), on every launch. It is live: the next launch takes the new value. It matters mostly on a key, where a chain waiting for a reply longer than 5 minutes otherwise writes the whole context again.

## Agent SDK and API keys (BTN-136, research)

Not used by Even Keel: a check of whether sessions could run through the Agent SDK (`@anthropic-ai/claude-agent-sdk`) or on an API key and survive a restart of the service. Checked live on 2026-10-17 with SDK 0.3.302 (it bundles CLI 2.1.302 in `@anthropic-ai/claude-agent-sdk-<os>-<arch>`, so pinning the SDK pins the CLI unless `pathToClaudeCodeExecutable` is set), the standalone CLI 2.1.302, Haiku, the sandbox repository, a Pro subscription; the scripts were throwaway.

The SDK on an API key was not run (the key was spent only on the CLI check); its rows follow from the SDK runs on a subscription and the CLI run on the key.

- **The host dies with the default spawn.** The CLI is a child of the host's node and reads stdin; a non-detached child of node sits in libuv's kill-on-close job object, so a `TerminateProcess` of node (what the service host's `Process.Kill()` does) kills it at once. Its `sessions/<pid>.json` stays with a dead pid and `status: waiting`.
- **`resume` after the host died.** In an SDK session the `AskUserQuestion` call reaches the transcript at once, unlike `--bg`. `query({ resume })` keeps the whole history with the call; the call gets a synthetic `tool_result` with `is_error` — `[Tool call interrupted: the session ended before this call's result was recorded, so its outcome is unknown. …]` — and an assistant `No response requested.`; the answer comes as the next prompt, and the session took it. With a warm cache it cost 18.9k tokens read and ~230 written ($0.00024 on Haiku); with a cold one the whole context is written again (~19k tokens here, at the 1 h write price), not measured. Mid-turn: a running Bash command outlived the CLI and finished (its file appeared 20 s later), and after `resume` the model ran it again — a side effect may happen twice.
- **A detached executor.** `spawnClaudeCodeProcess` returns any `SpawnedProcess` (`stdin`, `stdout`, `kill`, `exit`). A separate node process started with `detached: true` spawns the CLI and pipes its stdio to a named pipe; the host's `SpawnedProcess` is a socket to it. The executor must not end the CLI's stdin when the host disconnects (a deliberate close sends its own message) and buffers the CLI's stdout until the next host. The host was killed while a question was pending: the executor and the CLI went on. A new `query()` whose spawn function attaches to the same pipe sends `initialize`, the running CLI answers it with the request it is still blocked on, and the SDK redelivers the question to `canUseTool` (`reinitialize()` documents this); the answer went in as a proper `tool_result` and the turn finished in place, without `resume`. A `detached` child survives a `TerminateProcess` of its parent and a non-detached one does not (checked); the executor was not started by the real service, so its surviving a `Restart-Service EvenKeel` rests on that and on the CLI daemon, a detached grandchild of the service's node, which does survive one.
- **Remote Control.** `enableRemoteControl(enabled, name?, { reattachSessionId, keepSessionOnExit })` on the `query()` object sends the CLI a `remote_control` control request and returns `{ session_url, bridge_session_id: "cse_…" }`; `initializationResult()` reports `remote_control_available`. The CLI turns `keep_session_on_exit` into `neverArchive`. Checked from the phone: an answer from the claude.ai app aborts the host's pending `canUseTool` (its `signal`) and the session goes on with it; with the host dead and the CLI in the executor the answer from the phone finished the turn and the next host got the buffered output; after the CLI exited (`keepSessionOnExit: true`), `resume` plus `enableRemoteControl(true, name, { reattachSessionId: "cse_…" })` in a new CLI came back into the same chat with the same `bridge_session_id`, and a new question was answered there. The `@anthropic-ai/claude-agent-sdk/bridge` module (`@alpha`) wants the account's OAuth token from the host — not to be used: Anthropic forbids third parties to collect Claude.ai tokens.
- **The CLI on an API key.** `claude --bg --model haiku` with `ANTHROPIC_API_KEY` in its environment, in a fresh account folder (its `.claude.json` with `hasCompletedOnboarding`, the folder trusted and the key pre-approved in `customApiKeyResponses.approved` by its last 20 characters, otherwise an interactive session asks), started a daemon and the session answered. The key is not in the job's `providerEnv` (only `CLAUDE_CONFIG_DIR`), so a session the daemon respawns may come back without it: for real use the key belongs in the account folder's `settings.json` `env` or an `apiKeyHelper` (not checked). The cache was written with a 5-minute lifetime (a subscription writes 1 h). A key not scoped to a workspace fails with `400 … must include the anthropic-workspace-id header`. `--max-budget-usd` works only with `--print`. Spent on the key: $0 (the 400) and ~$0.004 (28.5k tokens written, by the SDK's prices).
