# Sessions, models, prompts, limits

Reference for sessions: how Even Keel launches `claude` and watches it.

## CLI and transcripts

- Sessions are the `claude` CLI (`--bg`, `agents --json`). The binary: `EVEN_KEEL_CLAUDE_BIN`, otherwise the standalone CLI `~/.local/bin/claude.exe` (outside Windows — `claude`), otherwise the binary of the newest VS Code extension version (an extension update deletes its folder).
- Transcripts are in `<account folder>/projects`. `claude agents`, transcripts, `sessions/<pid>.json` and `settings.json` are read for each account folder.
- `claude agents --json` (2.1.284) prints neither `pid` nor `status`, and `state: done` stays both for a live session after a turn and for a stopped one: a live process, `pid` and `busy`/`idle` come from `sessions/<pid>.json` entries with a live `pid` (`withLiveRecords`).
- Prompt cache freshness comes from the transcript: the lifetime (5 min or 1 h) by `usage.cache_creation` of the last response that wrote the cache (if both are present, 5 min is taken), counted from the first line of the last response.
- The progress feed on the page is the last 30 lines of the fold (`TranscriptFold`): texts and tool calls, API errors and human requests (`kind: 'prompt'`; without `isMeta`, tool results, `origin.kind` other than `human`, and client context blocks like `<ide_selection>`, `<pasted_content>` stays). The "Whole transcript" button is `GET /api/sessions/<id>/transcript`: the same fold without truncation (`whole`), with the full command in `detail` for Bash and PowerShell. For a live session the window reads further every 3 s with `?after=<how many lines it already has>`: fold lines are only appended, and the service folds the file anew each time (14 MB — ~150 ms). Requests do not go into the handoff on a limit.
- `claude --bg --resume <id>` may bring the session up under a new session id (2.1.296), so after a resume the dispatcher looks for it by that id or, like after a launch, by the task name, the folder and the start time (`resumedAs`).
- `claude --bg` goes through the supervisor daemon (`claude daemon run`, on Windows the pipe `\\.\pipe\cc-daemon-…`). Stopping the service does not kill background sessions — they are children of the daemon.

## Model (`src/sessions/launch.ts`)

By the task label `Sonnet`/`Opus`/`Haiku` (case-insensitive, whitespace trimmed): `--model <alias>` on every launch — first, `--resume`, handoff, "New session"; `modelPrompts.<alias>` from `even-keel.config.json` is appended to the prompt if present. No label or two different ones — the model from the `model` config key (default `opus`; the second case logs a warning) and its prompt from `modelPrompts`. A session is never launched without `--model`: the CLI would take the model from `settings.json`, which `/model` rewrites in any editor on the same account.

## Extra tools (BTN-74, `src/tools/`)

- The "Trim the tools" switch in the status menu (the gear, `chain/trim`, `ChainState.trimTools`, on by default): chain sessions are launched with `--settings <JSON>` (`chainSettings`) — `syncClaudeAiSkills` and `syncClaudeAiPlugins` are off, skills from the config's `hiddenSkills` (default `DEFAULT_HIDDEN_SKILLS`) are `user-invocable-only`, that is, only through `/name`. It applies on every launch: first, `--resume`, handoff. The settings files are not changed, `--settings` affects only that launch (verified on CLI 2.1.290: `--bg` passes it through, claude.ai skills do not go to `.trash`).
- With the switch off, `--settings` still goes: it carries `autoMemoryDirectory`, the shared memory folder (`docs/accounts.md`), and `disabledMcpjsonServers` (below).
- The CLI looks for `.mcp.json` in the parent folders as well, so a session in a worktree inside the main checkout sees the servers of the main checkout's `.mcp.json`, even an untracked one, but not their approval in `settings.local.json`. Such a server is "Pending approval", and a `--bg` session hangs on the approval dialog before its first turn (BTN-86, 2026-10-10). So every chain session in a worktree gets the servers of `<repo>/.mcp.json` that its own `.mcp.json` lacks in `disabledMcpjsonServers` (`strayMcpServers`, whatever the switch). Verified on CLI 2.1.296: `claude --settings <file> mcp get <name>` in the worktree shows "Rejected" instead of "Pending approval".
- A session that hangs on any startup dialog is visible only in its job file: `claude agents --json` shows `state: blocked`, as for a question, while `<account folder>/jobs/<id>/state.json` gets `tempo: blocked`, `detail: "stuck on a startup dialog"` from the CLI's 45 s watchdog. Even Keel reads that file for `blocked` sessions without a live record (`withStartupDialogs`), sets `SessionView.startupDialog`, the panel says why the session stands and the service log has a `sessions: … hangs on a Claude Code dialog` line. Such a session is not mid-turn: "New session" and "Skip" stay available. The dialog itself cannot be seen from a terminal: the service's daemon is in session 0.
- `skillOverrides` of the project (`.claude/settings.json`) and of the main checkout (`.claude/settings.local.json`, which overrides the project one, as in the CLI) override the list. A session in a worktree does not read the main checkout's `settings.local.json` — its `skillOverrides` reach it only through `--settings`.
- The "What sessions get" page is `/tools?projects=A,B&diff=1` (`web/src/tools/`); without `projects` the first two chain projects are selected, so the matrix is not squeezed. The project page has a line with the number of problems and a link. The project choice is the same list as on `/stats` (`web/src/ui/ProjectList.tsx`); at the top are the problems merged across projects (won't reach the session, claude.ai skills, MCP servers that failed or don't make it into the worktree, accounts), below is a "setting × project" matrix by section with the result for the session and level marks; `diff=1` ("Only differences") shows only the rows where projects differ; the logic is `web/src/tools/matrix.ts`. Per-project data is `GET /api/projects/<key>/tools` (`readToolsView`): a table of settings by level (user, project, local, Even Keel) with the result for the session, MCP servers from settings (`.claude.json`, `.mcp.json`, plugins) marked "not in worktree", the difference between the accounts' `settings.json` and the global one (key names only — `env` holds secrets) and what the project's last session received: the start of its transcript (first 400 lines; the worktree folders `<repo>--claude-worktrees-*` first) — `skill_listing`, `prompt_snapshot.tools`, `deferred_tools_delta`.

## Prompts (`src/sessions/prompt.ts`)

Assembled strictly: a value in the launch and handoff prompt goes through `fill`, and an empty or non-string one is an assembly error — the chain pauses with it instead of going into a session with a blank space. `modelPrompts` is passed as is, with no substitutions: `{name}`, `{{name}}`, `${name}` is a config error. The prompt language is `promptLanguage` (`src/chain/prompts.ts`, see `docs/web.md`).

## Limits

- Each account has its own: `claude -p /usage --output-format json --no-session-persistence` in its folder every 5 minutes (a local command, spends no quota) and a statusline snapshot (marked with the session's `configDir`; without the mark — the global account); the fresher one is taken.
- Do not poll more often: the server answers `/api/oauth/usage` with 429, the VS Code extension panel polls it with the same token, and after a 429 the CLI (2.1.286) does not query this token for ~45 min.
- With an expired access token or after a 429, `/usage` returns no limits (the subscription line is there, the window lines are not) — that is "no data" (`stale`), not an error. A `/usage` answer is accepted whole or not at all: both window lines with a percentage and a reset (`0% used` without a reset — the window has not started).
- Polling continues only if the answer says outright `num_turns: 0` and `total_cost_usd: 0`, otherwise it is switched off until restart. An unreadable answer or switched-off polling is shown by the page as a banner (`UsageBanner`).
- While a window is used up, the next task is not started: the chain waits for the reset (`limitUntil`) and continues by itself.
