# Sessions, models, prompts, limits

Reference for sessions: how Even Keel launches `claude` and watches it.

## Agent adapters (BTN-167, `src/agent/`)

The seam for a second agent (BTN-116: Codex), on the pattern of `src/tracker/`. The chain, the page, the accounts and the limits reach an agent only through `Agent` (`src/agent/contract.ts`); Claude Code is the one implementation (`src/claude/adapter.ts` over `ClaudeCli` in `src/claude/cli.ts`), registered by name in `AGENTS` (`src/agent/adapters.ts`) and set up once in `src/service.ts`.

- Every account folder carries its agent (`AccountHome.agent`, `AccountEntry.agent`), and a session runs on the agent of its account: `agentOf(home)` in `src/service.ts` picks the runtime for a launch (the account of the run profile, below), a resume, a stop, the monitor and the transcript routes. A session shows it as `SessionView.agent`. Nothing about the agent is written to the config or `state/`: an account folder is Claude's because `AccountHomes` makes Claude's.
- The contract: `launch`, `resume` (a limit resume, a reply and a checkpoint go on this way; a handoff is a `launch` in the same place), `stop`, `sessions` (the folder's sessions as `AgentEntry`), `tail` (a transcript read as it grows, `summary()` is the `TranscriptSummary` the page and the chain read: stage, action, context fill, the question, the API error), `record`, `feed`, `transcripts` (which sessions a folder holds, for `TranscriptOwners`), `authStatus`, `login`, `logout`, `env` (the session's environment: `sessionBase` without the trackers' and CIs' credentials plus `CLAUDE_CONFIG_DIR` for a folder other than the global one).
- Optional, because only Claude has them: `usage` (`claude -p /usage`, parsed by `parseUsage` in the adapter; without it the account is not polled; Codex, OpenCode and Copilot have one too, "Limits" below, and Copilot's `keyUsage` has its token accounts polled), `contextWindow` and `windowStamp` (`claude -p /context`, "Context window" below; Codex has the window in its rollout), `stopDaemon`, `liveRecords` (the apps panel), `remote` (Remote Control). `models` is optional too, for another reason: Copilot has no list ("Model lists" below). `SessionStart.settings` is Claude's `--settings`; `model` is the model name as the CLI takes it, `null` — the CLI's own default. The cache lifetime, `AskUserQuestion` and the job files stay inside the Claude adapter and the transcript fold.
- The contract does not need a live process between turns: a session is its id and its transcript, `resume` may start a process per turn (`codex exec resume`).
- The agent of a new session (BTN-168, BTN-173): see "Run profiles" below. `choiceFor(project, task)` in `src/service.ts` picks the account folder a launch, a handoff (`relay`) and a fix session (`launchFix`) start in. The chain judges a launch block, the limits and the relay account by that same folder (`blocked`, `limitReset`, `account` in `src/chain/model.ts` take the project and the task). `agentExtras` adds what only Codex takes: the bypass (`execution.codex`) and the tracker's MCP server. Still Claude's and left for the accounts page: `AccountHomes` (folders, `.claude.json`, `.credentials.json`, sharing), `parseAuthStatus`, `parseCredentialTimes`, the statusline's `rate-limits.json`.

## CLI and transcripts

- Sessions are the `claude` CLI (`--bg`, `agents --json`), or the same CLI through the Agent SDK for an account folder whose transport is `sdk` ("The Agent SDK transport" below); the rest of this section is `--bg`. The binary: `EVEN_KEEL_CLAUDE_BIN`, otherwise Even Keel's own copy of the checked version while `cli.claude` is `checked` and the copy is downloaded ("The checked CLI" below), otherwise the standalone CLI `~/.local/bin/claude.exe` (outside Windows — `claude`), otherwise the binary of the newest VS Code extension version (an extension update deletes its folder).
- Transcripts are in `<account folder>/projects`. `claude agents`, transcripts, `sessions/<pid>.json` and `settings.json` are read for each account folder.
- `claude agents --json` (2.1.284) prints neither `pid` nor `status`, and `state: done` stays both for a live session after a turn and for a stopped one: a live process, `pid` and `busy`/`idle` come from `sessions/<pid>.json` entries with a live `pid` (`withLiveRecords`).
- Prompt cache freshness comes from the transcript: the lifetime (5 min or 1 h) by `usage.cache_creation` of the last response that wrote the cache (if both are present, 5 min is taken), counted from the first line of the last response.
- The progress feed on the page is the last 30 lines of the fold (`TranscriptFold`): texts and tool calls, API errors and human requests (`kind: 'prompt'`; without `isMeta`, tool results, `origin.kind` other than `human`, and client context blocks like `<ide_selection>`, `<pasted_content>` stays). A message from Remote Control or the terminal that came mid-turn has no `user` line: the CLI writes it as an `attachment` of type `queued_command` (the prompt in `prompt`, `origin.kind: "human"`; the session's own task notifications carry another kind) next to a `queue-operation` `remove` with `absorbed_mid_turn`, and the feed shows it as a prompt without starting a turn. `thinking` blocks never reach the feed, even with text (`thinking.display: "updates"`): the model's thinking is not read out of transcripts. The "Whole transcript" button is `GET /api/sessions/<id>/transcript`: the same fold without truncation (`whole`), with the full command in `detail` for Bash and PowerShell. For a live session the window reads further every 3 s with `?after=<how many lines it already has>`: fold lines are only appended, and the service folds the file anew each time (14 MB — ~150 ms). Requests do not go into the handoff on a limit.
- Questions and answers (BTN-101, `src/sessions/ask.ts`): a pending `AskUserQuestion` call is the session's open question, `SessionView.ask` (`tool_use` id and its questions); in the whole fold the call's line carries it as `line.ask`. Its `tool_result` with `toolUseResult.answers` becomes an `answer` line with `answers` (the question it answers and the answers by question text). A result without answers (the call was interrupted or failed when the session was stopped) leaves the question stray, and the next human prompt answers it: that prompt is an `answer` line too, its answers read back by `answersIn` from its `- "question" → answer` lines. Any new prompt clears the open question.
- A pending `AskUserQuestion` is in the transcript at once from CLI 2.1.302: the response line with the call, its `model` and `usage`, is written while the job still waits. Checked live on 2.1.303 (EKR-3, 2026-10-21): a `--bg` Haiku session whose very first action was the question had that line 0.2 s after the API reply, with `tempo: blocked` in its job file, and the fold gave the model, the context and a 1 h cache from it — so a session that starts with a question shows them like any other. The job file's `updatedAt` was set as the job went `blocked` and not touched for the 4 minutes it waited; nothing reads it, since the transcript dates the cache. On CLI 2.1.296 (verified 2026-10-12) it was not in the transcript: the CLI wrote the whole last message — the text before the call and the call — only together with the answer. Until then the session record says `status: waiting`, `waitingFor: "input needed"`, and the question was only in `block.questions` of `jobs/<id>/state.json` (`needs` is `answer: <question> (<labels>)`): the question text and the options with descriptions, without `header`, `multiSelect` or `preview`. `withJobFiles` reads it for a live waiting session (`blockedAsk`) and the monitor gives it as `SessionView.ask` when the transcript has none: the id is `job:<job id>:<hash of the questions>`, `unsaved: true`, every question is a single choice without a header — several options go through "Other" on the page, and `1, 3` in a tracker comment stays text. There `claude stop` lost that message for good: after `--resume` the transcript had a synthetic `No response requested.` in its place, and the session saw neither its text nor its question. On 2.1.302 the call was seen in the transcript of a `--bg` chain session, and `claude --bg --resume` with the answer gave it the same synthetic error result as an SDK session (`[Tool call interrupted: …]`, then `No response requested.`), with the answer as the next prompt (BTN-189, 2026-10-18).
- The reply prompt (`replyPrompt`, in `promptLanguage`, BTN-182) is what the user sent and nothing more, since the chat shows it as the user's message: the `- "question" → answer` lines, the user's text, then `Files from the user:` and the paths. For an `unsaved` question one service line goes first, that the question was lost when the session restarted, and each question gets its answer line (or `- "question"` alone when skipped) with the chosen options' descriptions indented under it. Where the answer came from (the page or the tracker) goes only to the service log (`Reply.from`). `replyParts` takes a prompt apart again for the chat — the answers, the user's own words and the files — and also strips the service lines of older prompts (`LEGACY`: the source intro, the "call above" paragraph, the comment label, the numbered lost block). An empty reply is `answer.empty`. Files are saved first into `.temp/inbox/` of the task's folder (`src/sessions/inbox.ts`: safe names, no overwriting, a `.zip` unpacked with `tar -xf`, `unzip` as a fallback); the folder has its own `.gitignore` with `*`, so the worktree stays clean and cleanup after Done does not stall. How `--resume` treats an unanswered `AskUserQuestion` that did reach the transcript is not verified, so the prompt does not depend on it.
- `claude --bg --resume <id>` starts a copy under a new session id (the page shows it as a new chat with the whole history again) when the session is still running or, if its job `jobs/<job id>/state.json` is saved, when any flag is passed: such a session keeps its own options (model, permission mode, name, settings), and the CLI prints `note: … keeps its own saved options, so the flags you passed started a copy` (reason `own-options`, read from the 2.1.302 binary). So a reply or a limit resume passes only `--bg --resume <id> <prompt>` when the job is saved (`resumeArgs`): the session goes on in place with the options of its launch (verified live on 2.1.302, 2026-10-17), and a run label or model changed meanwhile applies only from the next launch. Without a saved job the flags are passed as at a launch. The dispatcher still looks for the resumed session by that id or, like after a launch, by the task name, the folder and the start time (`resumedAs`) — the latter only for another job than the resumed one. Resuming in place, the daemon kills the job's process and spawns a new one, and for under a second that process shows a fresh session id (in `claude agents` and `history.jsonl`) before it loads the session and takes the old id (2.1.302, 2026-10-18): taking that fresh id gave the chain a session with no transcript — "transcript not found" in the chat and "Session booting" for 5 minutes. The monitor takes a job's new session id only once two polls in a row show it, and keeps the earliest `startedAt` it saw for a job (`steadyJobs`): while a process lives, `claude agents` gives that process's start. A reply or a limit resume stops the session first, so for several seconds `claude agents` calls it `stopped` and then `working` with no process, and its `startedAt` becomes the new process's: the monitor shows a session the service is resuming as working until it is live again (`ResumeHolds`), and the page shows no start banner for a session that already had an answer or a resume. Its `busy` status lags further, 8–20 s after the resume (CLI 2.1.308, 2026-10-22), and a chat message in that window stopped the fresh turn and resumed it again: a session counts as mid-turn from the start of its resume until a poll shows it `busy`, it shows a question other than the one it had, or 45 s pass (`ResumeHolds.turning`, BTN-307), so such a message goes into the mailbox or gets `answer.busy`. `state: done` is the CLI's guess that a job did its work, given to a turn that ends on a question in plain text too: with a live process such a session waits for a reply, it is finished only once its process is gone.
- How long a reply takes to reach a session (BTN-203, CLI 2.1.302 on Windows, a Haiku session, 2026-10-18). `claude stop` returns in 0.6–0.8 s and the process is gone 0.3–0.9 s later; `claude agents` takes 0.2–0.4 s. `claude --bg --resume` takes 3.5–3.9 s until the job shows as `working` in `claude agents` (the command itself returns 0.1–0.4 s later), and the prompt is in the transcript ~1 s after that: about 5 s from the stop is the CLI's floor. On top of it the service used to spend 2–5 s in `ClaudeCli.stop`: the Windows process listing before the stop (`powershell.exe` with `Get-CimInstance`, 0.6–2.6 s), polls of `claude agents` a second apart, and a `taskkill` per descendant one by one, ~0.6 s each even on a dead pid (8 of them took 5 s). Now the listing runs alongside the stop, the exit is watched by the pid every 100 ms and confirmed by one `claude agents`, only live descendants are killed and all at once, and `appear` polls every 250 ms: a stop and a resume went from 7.2–9.2 s to 6.1–6.7 s, the stop itself from 3.2–5.1 s to 1.5–2.1 s. The service logs each reply or limit resume in one line, `sessions: <task> resumed in <ms> ms (stop <ms> ms)`. A `--resume` sent right after `claude stop` returns, before the old process exits, went on in place too (two rounds, no copy, the transcript intact: the daemon has already marked the job `stopped`) and would save another 0.3–0.9 s; it is not used, since `stop` is also the one that kills the leftovers before a worktree is removed.
- A prompt that starts with a dash — a reply begins with its `- "question" → answer` line — passes `claude --bg`, but the process the daemon spawns for the job reads it as an unknown option and exits before init: the job is `failed` with `error: unknown option '- …'`, and the chain pauses on "did not show up in claude agents" (2.1.302, 2026-10-18). `promptArg` puts a line break before such a prompt.
- `claude --bg` goes through the supervisor daemon (`claude daemon run`, on Windows the pipe `\\.\pipe\cc-daemon-…`). Stopping the service does not kill background sessions — they are children of the daemon.

## Codex (BTN-168, `src/codex/`)

Checked on codex-cli 0.162.1. The binary: `EVEN_KEEL_CODEX_BIN`, otherwise Even Keel's own copy of the checked version while `cli.codex` is `checked` and the copy is downloaded ("The checked CLI" below), otherwise on Windows the native `codex.exe` of the global npm package `@openai/codex` (its `codex.cmd` needs a console), otherwise `codex`.

- A turn is `codex exec --json … [resume <id>] <prompt>`, a detached process with its stdout written to a file (`state/codex/turns/<name>-<ms>.jsonl`), not a pipe: it outlives the service. Every flag goes before `resume` — the subcommand takes none of its own. The thread id is the first event (`thread.started`); the turn is over at `turn.completed`/`turn.failed`.
- Codex has no list of background sessions, so Even Keel keeps its own registry: `state/codex/sessions/<id>.json` (`sessionId`, `name`, `cwd`, `account`, `startedAt`, the `pid` and output file of the last turn, `stopped`). Between turns there is no process: the session is `idle` with `resting: true`, and liveness checks go through `isLive` (a live pid or `resting`). `stop` kills the turn's process tree (`taskkill /T /F`, elsewhere `process.kill(-pid)`) and marks the session `stopped`.
- The transcript is the rollout `<CODEX_HOME>/sessions/YYYY/MM/DD/rollout-<time>-<id>.jsonl`; a resume appends to the same file. The fold (`RolloutFold`) reads `session_meta`, `turn_context` and `event_msg` lines; the context fill is `info.last_token_usage.input_tokens` of `token_count` against `model_context_window`. An `event_msg` of type `error`, or the `error` of a failed turn's `task_complete` (how 0.162.1 writes a rejected request, e.g. a model the plan does not have), is the API error, a limit when its text says so; a message that is the API's JSON answer shows its inner `error.message`. A call whose item is `status: failed` gets a failed line: a command's starts with `Exit code N`, as Claude's does, since Codex fails a whole joined command on its last exit code and the output may be an ordinary one — its first look round is `git status …; rg --files -g AGENTS.md …`, and `rg` finding no `AGENTS.md` exits 1 (BTN-233). Codex has no Remote Control: its sessions get neither a link nor the "Remote Control is off" note.
- No remote control of chain sessions (BTN-178, checked on 0.162.1 on 2026-10-18). Codex's own one is `codex remote-control` (experimental): the phone's ChatGPT app reaches threads through an app-server — the daemon or the Codex desktop app as the host. The chain's threads are not among them: a `codex exec` thread is recorded with `source = exec`, and `thread/list` without `sourceKinds` returns only interactive sources (100 `vscode` threads and no `exec` one on this machine; all 23 chain threads with `sourceKinds: ["exec"]`). A thread made through `codex app-server` (`thread/start`) gets `vscode` and would be listed. The daemon cannot be run from the service: the service is elevated, and `codex app-server daemon start` refuses ("start the Windows daemon from a non-elevated terminal; shared clients must not inherit administrator privileges"); `codex remote-control --no-daemon` does start in the service's process, but would hand the phone an administrator's process. The daemon's control socket path is capped at `SUN_LEN`, so a long `CODEX_HOME` cannot hold one. The Codex SDK (`@openai/codex-sdk` 0.163.0) runs the same `codex exec --experimental-json` with its turn piped to the caller, so a service restart would kill it; its `threadSource` is an analytics tag and leaves `source` as `exec` (BTN-193, v0.2). Moving the turns to an app-server was left for later (BTN-194): v0.1 keeps `codex exec`, and a daemon in the user's own session with Even Keel as its client is BTN-196 (v0.2) — once [openai/codex#52675](https://github.com/openai/codex/issues/52675) (a second app-server on the same `CODEX_HOME` fights the desktop app's remote control: 409s and "active writer" on an idle thread) is fixed and the Windows daemon is no longer experimental.
- Limits come from `rate_limits` of the newest `token_count` in the account's latest rollouts (`usage` of the adapter): the 300-minute window is the five-hour one, the 10080-minute window the weekly one, the 43200-minute window the month (`RateLimits.month`; the free plan has only that one, `plan_type: "free"`, seen on 0.162.1), a window of another length is not shown. A plan with a month shows it in place of the windows it lacks (`limitSpans`), the chain counts a spent month like a spent week, and a limit hit on it waits for the month's reset. No rollout — no data. Tally does not snapshot the month (`span` is `5h`/`7d` only).
- Flags: `--approve-for-me` (chain sessions run without a human: Codex's automatic reviewer approves inside its sandbox), or `--dangerously-bypass-approvals-and-sandbox` instead when the shared `execution.codex` is `bypass` (below), `-m <model>` when the run profile has a Codex model (below), the MCP servers of the project's packages as `-c mcp_servers.<name>.url=<gateway address>` overrides (`src/codex/mcp.ts`, `docs/packages.md`): Codex's `config.toml` is never written, and the turn holds no credentials — the gateway adds them.
- The Codex sandbox does not start under the Windows service (BTN-171, checked on 0.162.1 and 0.163.0). Codex creates its private desktop on the window station of the calling process and starts the command on `Winsta0\<that desktop>`; in session 0 the service's station is `Service-0x0-…$`, so every program that loads `USER32.dll` (`git`, `node`, `pwsh`) dies with `0xC0000142` (`unelevated`), and the elevated runner never connects ("timed out … connecting runner pipe-in"). `cmd /c echo` still works, which hides it. Upstream: openai/codex#46412, #37722; no admin setup fixes it. On 0.162.1 the elevated sandbox fails even earlier with "setup refresh had errors" while the Codex desktop app runs (openai/codex#51601, fixed in 0.163.0). What `--approve-for-me` does there (BTN-233, 0.162.1, `codex exec` from the service's daemon in session 0, 19.10.2026): the turn runs `on-request` with the `auto_review` reviewer in `workspace-write`, every command fails at once with exit code `-1` and "Failed to create unified exec process: helper_unknown_error: setup refresh had errors", while `apply_patch` edits still land. The model may rerun the command with `sandbox_permissions: require_escalated`, the reviewer approves it, and it runs with no sandbox — that is how a session commits under the service without the bypass, with a failed line before each such step. Whether it asks is the model's choice: told nothing, it gave up on the commit after five refused commands; told to escalate, it committed on the second try. Hence the shared key `execution.codex` (BTN-173; before it the project key `codexBypassSandbox`): `sandbox` by default, `bypass` — sessions run with no sandbox and no reviewer. It is shared only, since the sandbox fails for every project alike. Claude's modes are another matter, its transport (`execution.claude`, "The Agent SDK transport" below); `execution.opencode` and `execution.copilot` are config errors.
- There is no `AskUserQuestion`: a turn that ends without Done leaves the session resting, it is answered from the page's chat window (`resume`), and nothing is posted to the tracker (BTN-166). The prompts stay Claude's; the unattended line about `AskUserQuestion` is harmless here.

## OpenCode (BTN-214, `src/opencode/`)

Checked on OpenCode 1.18.25 on Windows with the free model `opencode/big-pickle`, from a script driving the adapter (launch, a reply, the transcript, Tally), not yet as a chain session under the service. The binary: `EVEN_KEEL_OPENCODE_BIN`, otherwise Even Keel's own copy of the checked version while `cli.opencode` is `checked` and the copy is downloaded ("The checked CLI" below, BTN-347), otherwise on Windows the native `opencode.exe` of the global npm package `opencode-ai` (its `opencode` on the PATH is an npm wrapper), otherwise `opencode`; self-update is off on any of them.

- A turn is `opencode run --format json [-m <provider>/<model>] (--title <task> | -s <session>) -- <prompt>`, a detached process with its JSON events in a file, as Codex's (`TurnRegistry` of `src/codex/turns.ts`, kept in `state/opencode/`). The prompt goes after `--`: `run` reads a reply's leading `- "question" → answer` as an option and prints its help. Every event carries `sessionID`; a turn that sends none yet is found in the account's database by its title, folder and start. The turn is over when its last event is an `error` or a `step_finish` whose `reason` is not `tool-calls`. Liveness, `resting` and `stop` are Codex's.
- **OpenCode takes its working folder from `PWD`** before the process's own: a spawn with `cwd` alone ran in the service's folder. Every turn sets `PWD`.
- The account's environment (`openCodeEnv`): the four XDG folders, `OPENCODE_DISABLE_AUTOUPDATE`, `OPENCODE_DISABLE_EXTERNAL_SKILLS` and `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS` (no `~/.claude/skills`, `~/.agents/skills`). Not `OPENCODE_DISABLE_CLAUDE_CODE`: it drops the project's `CLAUDE.md` too. The global instructions are the account's empty `config/opencode/AGENTS.md`, which OpenCode takes before `~/.claude/CLAUDE.md`; the project's `AGENTS.md`, else `CLAUDE.md`, still reaches the session.
- The session's config on top of the account's and the project's is `OPENCODE_CONFIG_CONTENT` (`sessionConfig`): `permission.external_directory: allow` (a merge into the main checkout from a worktree is outside the folder, and an `ask` in `run` is rejected on its own), the gateway's MCP servers with the project's own `opencode.json(c)` servers turned off by name, and as `skills.paths` the plugin packages' `skills/` (`docs/packages.md`) and the project's own `.claude/skills` and `.agents/skills`, which the skill flags above drop too (`skillDirs`, "Project rules for every agent" below). No `--auto`: every other `ask` is rejected, and there is no `execution.opencode`, since OpenCode has no OS sandbox to bypass.
- The transcript is rows of `data/opencode/opencode.db` (`src/opencode/db.ts`: read-only, opened and closed per read, a tool's output left out). `foldSession` gives the same `TranscriptSummary` as the other folds: the feed, the stage, the model as `<provider>/<model>`, the context (the last step's input with the cache) and the totals, an API error from the message's `error`. An error a turn ended on leaves no row (a model the account does not have: `UnknownError`, "Unexpected server error", seen on 1.18.25 with `-m deepseek-v4.1`), so the fold also takes the `error` event that ends a turn's output — the last line of each of the session's turn files, `<task>-<ms>.jsonl` since its start (`turnError`, `OpenCodeCli.turnErrors`, BTN-336) — as an error line and the API error in its place by time, unless a step holds the same text. A tail reads again only when the session's newest `time_updated` moved or a turn ended on another error. A handoff has no transcript path to point at (`tail.path` is `undefined`).
- The context window comes from OpenCode's copy of the models.dev catalogue, `<account>/cache/opencode/models.json` (`windowOf`).
- The models are `opencode models` in the account's folders (`parseModels`): one `<provider>/<model>` a line, only those of the providers the account is signed in to (`opencode/big-pickle`, `opencode/deepseek-v4.1-flash-free` on a fresh account), ~2 s. `run -m` takes nothing else, so the list is complete ("Model lists" below).
- Usage limits only from the provider (BTN-341): OpenCode shows none, so a ChatGPT sign-in has its 5-hour and weekly windows and a Copilot one its month read from their APIs ("Limits of OpenCode and Copilot" below); OpenCode Zen and API keys have none. A turn's error is a limit by its text (`LIMIT_TEXT` in `src/opencode/transcript.ts`), a 429 `statusCode` or a `FreeUsageLimitError` anywhere in the answer, Zen's spent free allowance (BTN-342); on Zen the chain tries such a limit again with a growing wait (`docs/chain.md`, exception 1), never seen live (`docs/unverified.md`).
- **A hung turn** (BTN-273, `hungEntry`): a live turn whose session rows in `opencode.db` and whose output file have not changed for 30 minutes (`TURN_HANG_MS`) is taken for hung — a request OpenCode retries for good, a tool that never returns. Its entry turns `idle` with `hungSince` and keeps its `pid`: the chain treats the session as not mid-turn, the page says so (`SessionView.hungSince`), the service log warns once, and the user may write to it or press "New session"; `resume` and `stop` both kill a live turn first, so two processes never write one session. Nothing stops it on its own (invariant 1); unattended, it is an idle session like any other. A failed read of the database does not count as silence. A killed turn's `running` tool part and its message without `time.completed` do not matter: liveness is the process and the output's last event, not the rows.
- The checkpoint threshold and the chat mailbox (BTN-274) come from the `checkpoint` package's OpenCode plugin, `plugins/checkpoint/opencode/checkpoint.mjs`: `pluginFiles` puts every script of a plugin package's `opencode/` folder into the session config's `plugin` as a file URL, which OpenCode loads into its process. On `tool.execute.after` it asks the service what the hook commands ask (`hooks/evenkeel.mjs`, "Checkpoint threshold" and "Chat mailbox" below) and appends the nudge and the messages to the tool's `output`, each in a `<system-reminder>` block: a plugin has no other way into the context mid-turn (a `client.session.prompt` with `noReply` from inside the hook hung the turn, 1.18.25). A delivered message also goes into the call's `metadata.evenKeel.mail`, which the feed reads (`SessionFold.pushPart`); the output itself is never read. A subagent's calls carry its own session id, which the service does not know. The merge check (BTN-288) is `tool.execute.before` of `bash`: `mergeRefusal` (`hooks/merges.mjs`, shared with `merge-check.mjs`) in the plugin's `directory`, the commands run asynchronously, and the refusal thrown as an `Error`, which OpenCode turns into the call's error without running it (seen live on 1.18.25). The `Stop` guard cannot block: `run` ends on the session's first `session.status` idle. Instead `experimental.text.complete`, which may rewrite a text part before it is stored, adds `CHECKPOINT: .temp/handoff.md` to a text without the mark when the plugin saw a `write`/`edit` of the note among the last three tool calls and `/note` says yes (seen live: the line is in the run's events and in `opencode.db`). Not ported: mail at a stop or before a question.
- `Agent.write` (the changelog): `opencode run --pure` with the prompt on stdin and a config that denies every tool but Read, Grep and Glob and turns the project's own MCP servers off (`writeArgs`, `writeConfig`); the answer is the last step's text, the tokens and the cost those of every step (`parseWriteAnswer`). The session it leaves is deleted afterwards (`opencode session delete`), so the account's database holds no transcript of it.
- There is no question tool in `run`: a question is the text a turn ends with, answered from the chat window, as with Codex.

## GitHub Copilot (BTN-215, `src/copilot/`)

Built on the research below (BTN-213) and checked on Copilot CLI 1.0.98 on Windows from a terminal: a launch with `--session-id`, a resume, the transcript fold against the CLI's own `session.shutdown` totals, the Tally rows. Never yet as a chain session under the service (`docs/unverified.md`). The binary: `EVEN_KEEL_COPILOT_BIN`, otherwise Even Keel's own copy of the checked version while `cli.copilot` is `checked` and the copy is downloaded ("The checked CLI" below, BTN-347), otherwise on Windows the `copilot.exe` winget installed (`%LOCALAPPDATA%\Microsoft\WinGet\Links`, else the package folder under `WinGet\Packages\GitHub.Copilot_*`), otherwise `copilot`; any of them with `--no-auto-update` and `COPILOT_AUTO_UPDATE=false`.

- A turn is `copilot -C <dir> --output-format json --no-auto-update --no-ask-user --allow-all-tools (--session-id <uuid> --name <task> | --resume=<id>) [--model <model>] [--add-dir <main checkout>] [MCP flags] [--plugin-dir <dir>…] --prompt=<prompt>`, a detached process with its JSONL in a file (`TurnRegistry`, `state/copilot/`), as Codex's. Even Keel gives a new session its id, so the session is known before the first event; the prompt goes as `--prompt=`, since a reply starts with `-`. The turn is over at the `result` line, the last of `--output-format json`. Liveness, `resting` and `stop` are Codex's.
- `--no-ask-user` takes the question tool away: a question is the text a turn ends with, answered from the chat window, as with Codex. `--add-dir` lets a worktree's session merge into the main checkout; there is no `execution.copilot`, since Copilot has no OS sandbox to bypass.
- The account's environment (`copilotEnv`): `COPILOT_HOME` is the account folder, `COPILOT_GITHUB_TOKEN` its token when it has one (`GH_TOKEN` and `GITHUB_TOKEN` are removed, since the CLI would take them), `COPILOT_AUTO_UPDATE=false`. A folder without a token runs on the machine's own `copilot login` (`docs/accounts.md`).
- The transcript is `<COPILOT_HOME>/session-state/<id>/events.jsonl` (`CopilotFold`): the feed from `user.message`, `assistant.message` and its `toolRequests`, tool names mapped to Claude's (`powershell`/`bash` → `Shell`, `view` → `Read`, `edit` → `Edit`, `create` → `Write`, an MCP tool `<server>-<tool>` → `mcp__<server>__<tool>`); the context is `inputTokens` of the last main-thread `session.usage_record` (the cache included), the window its `maxPromptTokens`, the model its `model` (`auto` resolves to a real model there). A `session.error` is the API error: `rate_limit`/`quota` or a text about a limit is a limit, `billing_not_configured` or a text about billing or AI credits is spent credit.
- The MCP servers of the project's packages go through the gateway as `--additional-mcp-config`; Copilot has no strict mode, so `--disable-builtin-mcps` drops its GitHub server and `--disable-mcp-server` each server of the project's `.mcp.json`, `.github/mcp.json`, `.vscode/mcp.json`, the account's `mcp-config.json` and the packages' plugins (`ownServers`). Plugin packages go as `--plugin-dir` (`docs/packages.md`).
- The monthly allowance and no prompt cache countdown: the transcript has what a session spent, not what is left, so a folder with a token has its month read from GitHub's API (BTN-341, "Limits of OpenCode and Copilot" below) and one on the machine's sign-in has no limit bars; its cache lives 1800 s, which `CacheTtl` (5 min or 1 h) cannot carry, so the page shows none, as for Codex and OpenCode.
- One transport only: the Agent SDK (BTN-239) is Claude's, so a Copilot folder, a token one too, has no transport (`transportOf` is `null`, its card says none), and the adapter has no `Agent.reply` and its entries do not steer. An answer or a limit resume is a new turn with `--resume` once the last one is over, as for Codex and OpenCode, and a chat message mid-turn waits for the mailbox or the turn's end.
- What Copilot does not get yet: the checkpoint threshold and the chat mailbox work only if Copilot runs the project's `.claude/settings.json` hooks, which the docs say and nobody saw (`docs/unverified.md`); a stall watchdog, `Agent.write`.

## Run profiles (BTN-173, `src/sessions/launch.ts`)

What a session runs on is three dictionaries keyed by provider (`claude`, `codex`, `opencode`, `copilot`; `src/agent/providers.ts`), at two levels, plus the provider itself:

- `provider` — shared and per project (`claude` by default). Formerly the project's `agent`.
- `models: { <provider>: <model> }` — shared and per project; a project's entry overrides the shared one of that provider, other providers come from the shared. The shared `models.claude` is `opus` by default: a Claude session is never launched without `--model`, since the CLI would take the model from `settings.json`, which `/model` rewrites in any editor on the same account. Codex has no built-in default — `null`, the model of its own `config.toml`; neither has OpenCode, whose model is `<provider>/<model>` (`opencode/big-pickle`, `openai/gpt-6.1-sol`), as `opencode models` lists it; nor Copilot, whose own default is `auto` (the CLI picks a model per session, `gpt-6-luna` in the check).
- `accounts: { <provider>: <account key> }` — the pool, shared and per project, merged the same way; an account key from `/accounts` (BTN-169) fixes the provider. Defaults: `global` (`~/.claude`) and `codex` (`~/.codex`); a Codex account added from the page is a folder under `~/.codex-accounts`, an OpenCode one under `~/.opencode-accounts`, a Copilot one under `~/.copilot-accounts` — OpenCode and Copilot have no default account (`docs/accounts.md`). The active account of the header is the shared provider's entry, and moving the "Even Keel" role moves the shared provider (`docs/accounts.md`). One account per provider: a spent limit is not rotated — the chain waits for the reset or an edit of the pool entry the project uses, and a new account means a new session with a handoff.
- `modelLabels` — shared and per project, off by default: whether the tasks' run labels are read.

`runSettings(config, project)` in `src/config.ts` fills a project's values over the shared ones. `runChoice` picks: with labels on, the task's run label (`Task.runLabels`, `runLabelOf` in `src/tracker/model.ts`) — `<provider> | <model>` such as `Claude | opus`, `Codex | gpt-6.1-sol`, or a bare provider (`Codex`, the label of BTN-168) that takes the model from the dictionaries; the provider is compared case-insensitively, whitespace around `|` is trimmed, the model goes to the CLI as written (a typo is the session's error on its first turn, unless the account's list refuses it first, "Model lists" below). Otherwise, and when a task carries more than one run label (a warning in the service log), the project's provider and model. The old `Sonnet`/`Opus`/`Haiku` labels are not read any more. A label whose provider has no account in the pool (`hasAccount`: the key names a folder of that provider) does not pause the chain: the task runs on the project's provider with the project's model, the launch log entry gets `fallback` and the page a toast (`chain.noAccountFor`, `docs/web.md`).

The choice is the task's and the project's, not the previous session's: a handoff (limit, checkpoint, "New session", reply) stays on the same provider. `launchPlan` appends `modelPrompts.<model>` to the prompt: the key is any model name as the CLI gets it (`opus`, `gpt-6.1-sol`), compared case-insensitively; a model left to the CLI has none. The model goes on every launch — first, `--resume` without a saved job, handoff, "New session".

## Checkpoint threshold (BTN-86)

The `checkpoint` plugin's hook (`plugins/checkpoint/hooks/context-checkpoint.mjs`, the rules in `nudges.mjs`) asks a session for a handoff by context size. The first nudge is at 200k, the next every 50k up to 250k and every 25k past it. The hook reads no transcript, so it works the same for Claude Code and Codex, and for OpenCode through the package's OpenCode plugin ("OpenCode" above): on every tool call it asks the service about its session, `GET /api/sessions/<id>/checkpoint` → `{ project, task, handoffs, first, source, context }`, 404 for a session the chain did not start. `context` is the session's context fill as the service's monitor last read it from the transcript (`SessionMonitor.contextOf`), `null` while it has not; with no answer, a 404 or a `null` the hook is silent, so a session started by hand gets no nudges. The `CHECKPOINT_*` variables still override the steps. Environment variables are not used to pass the answer: the environment of a `claude --bg` does not reach its session while the daemon runs (`docs/accounts.md`).

The plugin's `Stop` hook (`checkpoint-mark.mjs`) sends back a turn that wrote `.temp/handoff.md` among its last three tool calls but ended without the `CHECKPOINT:` line. Whether it did comes from `GET /api/sessions/<id>/note` → `{ note }` (`noteAtEnd` in `src/sessions/note.ts` over the agent's `feed`; a Codex file change is an `Edit` line).

- `handoffs` (`handoffsOf` in `src/chain/launches.ts`) is the number of the task's sessions started by `checkpoint`, `restart` or `relay`, up to and including this one. From the third on the hook is silent below the hard threshold of 300k: on tasks with many handoffs most of them lost money (CBL-596: 12 handoffs, $17.5 spent, $5.3 saved).
- `first` with `source: "calibrated"` or `"config"` replaces the hook's own first threshold; `"default"` leaves it alone.
- A default or calibrated threshold over the first share of the session's context window, 72 % unless set (`stats.checkpointShares.first`; `withinWindow` in `src/stats/checkpoint.ts`; the window is the session's, else `context.window`) comes down to it, rounded down to 1k, with `source: "window"`, which the hook takes like `"calibrated"`: past it the agent's own compaction may come first (below). A threshold pinned by `stats.checkpointTokens` (`"config"`) stays as it is, past the window too, and the shares do not apply.
- `late` and `hard` (BTN-259) are the late and hard shares of the same window, 85 % and 95 % unless set (`stats.checkpointShares.late`, `.hard`), rounded down to 1k; the hook takes the lower of each and its own (the default 250k and 300k or `CHECKPOINT_LATE_TOKENS`/`CHECKPOINT_HARD_TOKENS`), so a small window brings the late nudges and the hold of a task with many handoffs inside it and a large one changes nothing. A share therefore only lowers a step of the hook: raising it lifts the step at most to the hook's own value. For a Claude session (`SessionView.agent`) both are also kept before its compaction, below: at most the window less 32k less 30k for `late` and less 15k for `hard` (`COMPACTION_GAP`, `BEFORE_COMPACTION`), room for a large tool result and the note, so a share above that point no longer lifts them. On a 250k window a Claude session's nudges come at 180k, 188k and 213k, a held task is asked from 203k; on a 200k one `late` (138k) falls under the first, so the nudges come at 144k and 163k, held from 153k; on a 400k one the late share 340k is cut to 338k and the hard 380k to 353k. Other agents, and a session the service does not see, keep the shares alone: their point is not measured. Without a window, or with a pinned `first`, both are `null` and the hook keeps its own — a pin of 999999 still switches the nudges off.
- Where Claude Code compacts (measured 2026-10-24, the week of BTN-254 with the nudges off): not at a share of the window but about 32k short of it — 56 auto-compactions in 37 chain sessions on a 250k window came at 216–227k (median 218k), hand sessions on a 400k window at a median 369k. Each session went on from its summary to the task's end. So on a 250k window the late share at 212k came ~5k before the compaction and the hard one at 237k never, and on a 200k window the compaction (~167k) came before the late 85 %; hence the cap of a Claude session's `late` and `hard` above (BTN-377). Codex's point is not measured (`docs/unverified.md`).
- The shares (BTN-261) are whole percents, `first < late < hard`, set for Even Keel and per project (`docs/settings.md`); `DEFAULT_SHARES` holds the built-in ones. The handler of `/checkpoint` reads the project's current values on every request, so a change applies to the next tool call of a running session.
- Calibration (`src/stats/checkpoint.ts`, the query `CHECKPOINT` in `src/stats/reader.ts`): `first = base + (note + recovery) / (cache read price × 40 requests)`, rounded to 1k and kept within 150–250k. `base` is the median context of the project's checkpoint successors at their 15th main-thread request, `note` the median spend of a session from its first write of `.temp/handoff.md` to its end, `recovery` the median spend of a successor before its first edit, the price is that of the successors' most frequent model in Tally's `model_prices`. The work left, 40 requests, is a constant, about the lower quartile of what was measured: a measured remainder depends on the threshold itself (a higher one shortens it and pulls the threshold up, the successors' recovery requests inflate it and pull down). The hard threshold and the limit of handoffs are not calibrated.
- It applies once the project has 20 checkpoint successors and 50 sessions that went over 150k; until then, and without statistics, the threshold is 200k. `stats.checkpointTokens` in the config pins it for all projects and switches the calibration off.
- Measured on 2026-10-10: CBL — base 73k, note $0.18, recovery $0.64, 168 successors → 176k; BTN — 79k, $0.18, $0.69, 32 successors → 187k. Why 150k was too early: with a 1 h cache write at $8/M against a read at $0.2/M, rebuilding the context costs as much as re-reading it 40 times, and of 163 CBL handoffs at 150k 93 lost money ($177 spent, $132 saved).

## Chat mailbox (BTN-181)

A session that steers — an SDK session, `AgentEntry.steers` — needs no mailbox: a chat message mid-turn goes straight into its live CLI (BTN-291, "The Agent SDK transport" below), and only when that finds the session not live here after all does the message fall back to the mailbox, if its hooks listen. Any other chat message to a working session (invariant 1, `docs/chain.md`) waits in the `mailbox` table of the state database (`Mailbox` in `src/sessions/mailbox.ts`) until a hook of the `checkpoint` plugin takes it (`plugins/checkpoint/hooks/mailbox.mjs`, from plugin 0.7.0, on `PreToolUse`, `PostToolUse` and `Stop` of every tool). The hook calls `POST /api/sessions/<id>/mail` with `{ event }` — `PreToolUse`, `PostToolUse`, `Stop`, or `AskUserQuestion` for a `PreToolUse` of that tool — and gets `{ message }`: `null` when nothing waits, 404 for a session the chain did not start, 400 without a known event. A message hands everything that waited at once, marked delivered on that event (`mailFor` in `src/sessions/mailRelay.ts`):

- before or after a tool call — `hookSpecificOutput.additionalContext`, the turn goes on;
- at `Stop` — `{ decision: "block", reason }`, so the session carries on instead of ending its turn;
- before `AskUserQuestion` — `permissionDecision: "deny"` with the message as the reason: the question does not go out next to an unread message, and the session asks again only if it still needs to.

A subagent's call (`agent_id` in the hook's input) is left alone, so the message waits for the main thread. With no service or no answer in time (2 s, 5 s at `Stop`) the hook prints nothing and the tool call goes on.

The text (`mailMessage` in `src/sessions/mail.ts`) is a lead for the event in the prompt language — "the user wrote to you from Even Keel's chat while you were working", "so your turn is not over yet" at `Stop`, "your question did not go out" before a question — then each message as `<even-keel-message id="N">` around its `replyPrompt` (the words and the paths of files saved into `.temp/inbox/`). The mark is how the feed finds the message again (`mailIn`, `pushMail` in `src/sessions/transcript.ts`): in a hook attachment (`attachment.type` `hook_*`; at `PreToolUse`/`PostToolUse` it is `hook_additional_context` with the text in `content`), in a user prompt, meta ones included (the `Stop` feedback: an `isMeta` user prompt `Stop hook feedback:\n<reason>` next to a `hook_blocking_error` attachment), and in the error result of the open `AskUserQuestion` (`PreToolUse:AskUserQuestion hook error: <reason>`) — which then closes that question instead of leaving it astray. All three seen live on 22.10.2026, CLI 2.1.308. The Codex feed (`RolloutFold` in `src/codex/rollout.ts`) reads it in a `response_item` message of role `developer` — the only trace a hook's `additionalContext` leaves in a rollout, seen live on 18.10.2026 — and in a `UserMessage`. The OpenCode feed reads it in a tool call's `metadata.evenKeel.mail`, where the package's OpenCode plugin keeps what it appended to the output (on `PostToolUse` only). Other tool results are never read, so a session that prints the mark from a file does not fake a message. Tally does not count mail as a turn start.

Whether a session's hooks listen is known only from the hooks themselves: `Mailbox.listens` is true once they have asked at least once since the service started. A session with an older plugin, without the `checkpoint` package, or a new one before its first tool call does not listen, and the chat refuses it mid-turn with `answer.busy`, as before. After a service restart a working session listens again at its next tool call.

The race with the end of a turn is settled by `settleMail` on every change the session monitor reports and every 15 s: a message still waiting for a session that is no longer mid-turn, 10 s or more after it was posted (`mailOutcome`), goes by a resume as an answer would (`resume` as its event), or comes back to the chat (`returned`) when the session waits on a question or is gone, or the resume is refused. A returned message leaves the chat window when the user answers the session from it or presses "Dismiss" (`session/mail/dismiss`). Settled rows are deleted a week after they settled, at the next post.

## Permission dialogs (BTN-269)

A `--bg` session in `auto` mode still stops on a permission dialog: an `ask` rule of the settings, the classifier refusing a call several times. Seen live on CLI 2.1.308 (2026-10-23, Haiku, an `ask` rule on `Bash(echo:*)`): the session record says `status: waiting`, `waitingFor: "permission prompt"`; the job file has `tempo: blocked` and only one line, `needs: "approve Bash: echo …"`, no structure like `block.questions`; the pending `tool_use` is in the transcript at once. A stop and `--resume` lose the call (`[Tool call interrupted: …]`, then `No response requested.`), and the resumed model makes it again and meets the same dialog, since the rule stays: no way to allow a call.

What works is a `PermissionRequest` hook (`plugins/checkpoint/hooks/permission.mjs`, from plugin 0.10.0). Seen live on the same CLI: the hook gets `session_id`, `tool_name`, `tool_input` and `permission_mode`, no `tool_use_id`, one hook per call (two parallel calls — two hooks); the CLI shows the dialog at once and runs the hook beside it, so the session stays `waiting` while the hook waits; a decision the hook prints later is taken in the middle of the open dialog — `allow` runs the call, `deny` with `message` gives the model an error result with that text and the turn goes on — and the transcript gets a `hook_permission_decision` attachment with `decision` and `toolUseID`. A hook that prints nothing leaves the dialog. A dialog answered by something else (another hook's decision, so presumably Remote Control too) does not end a hook still waiting: it runs on to its timeout.

So the hook asks Even Keel every second, `POST /api/sessions/<id>/permission` with `{ tool, input, since }` (`since` — the hook's start, ms), until the answer is `{ decision }` other than `null`, and prints it as `hookSpecificOutput.decision`. A 404 — a session the chain did not start, or a call closed after the hook began — ends it with no output; no Even Keel at the first request ends it too, while a failed request after an answer is taken for a restart of the service and the hook asks on. It gives up after 29 minutes (its `timeout` is 1800 s, as `merge-check`'s). Codex 0.162.1 has the same hook event and runs it (its input carries `turn_id`), but its approvals belong to its reviewer (`--approve-for-me`), so the hook leaves them alone. `AskUserQuestion` gets a `PermissionRequest` too, its dialog being the question itself: the hook leaves it (from 0.11.2), and the service answers a 404 to an older hook that still asks, so the question stays one of the transcript, not a call to allow.

The service's side is `Approvals` (`src/sessions/approvals.ts`), in memory: a call by the session and a hash of `[tool, input]`, put to the user by `permissionAsk` (`src/sessions/permission.ts`, shared with the SDK host, BTN-303) with the id `perm:<session id>:<hash>`. While the session is `waiting`, the oldest call not yet decided is its `SessionView.ask` (the monitor's `approval`, ahead of a question of the transcript), so the question panel, the chat and a tracker comment answer it like any question; `resumeWith` settles it first (`approved` in `src/service.ts`) by `permissionMove` and returns the same session id, with no stop and no resume — words that came with "Allow" wait in the session's mailbox. While the chain runs unattended a call is refused at once with `NO_APPROVAL`. A call whose hook has not asked for 10 s is dropped; on every read of the sessions (`settle`) the calls of a session not `waiting` and older than 10 s are closed — the dialog was answered elsewhere — and their hooks get a 404 on their next poll, while a later hook for the same call (`since` after the close) is asked anew. After a restart of the service the hooks ask again and the calls are back.

## Project standards (BTN-359)

A standard is a document of the project's repository and the files it guards: the project setting `standards`, a list of `{ doc, files, except, shots }` (`Standard` in `src/state.ts`, checked by `standardsOf` in `src/projects/standards.ts`; `docs/settings.md`). The masks are globs from the repository's root: `**/` any folders, `*` and `?` within one path part, an exception wins. The page edits it in the project's Sessions tab (`ProjectStandards.tsx`), the document picked from the Markdown files committed on the project's branch (`ToolsView.docs`, `readBranchDocs` in `src/tools/panel.ts`), one the branch lacks is warned about; "Add "Interface"" adds `INTERFACE_FILES` with `DEFAULT_EXCEPT` and the merge's check on, `docs/design.md` when the branch has it. "What the session gets" lists the documents.

The `checkpoint` plugin holds them, from 0.12.0 (`plugins/checkpoint/hooks/standards.mjs`, the hook command `standard-gate.mjs`). The hook asks `GET /api/sessions/<id>/standards` (`{ standards }`, the same answer as `/check` has; 404 for a session the chain did not start, and then it says nothing):

- `PostToolUse` of a read (`Read`, Copilot's `view`, `read_file`) of a guarded file adds the document, whole, in `additionalContext` inside `<standard path="…">`, with a line on what the merge will want when `shots` is on.
- `PreToolUse` of an edit (`Edit`, `Write`, `MultiEdit`, `NotebookEdit`, Codex's `apply_patch` — its paths from the patch's `*** Update File:` lines —, Copilot's `edit`/`create`/`str_replace`) of a guarded file whose document the session has not had is denied with the document as the reason; the edit after it goes through.
- What was given is kept per session (and per subagent: `agent_id`) in `<session>.standards.json` of the temp folder's `claude-context-checkpoint/`, beside the threshold's marks; `SessionStart` with `compact` or `clear` drops the session's own, so the document comes again after a compaction.
- The merge: `mergeRefusal` (`hooks/merges.mjs`, shared by `merge-check.mjs` and the OpenCode plugin) runs `standardsRefusal` before the project's check commands. For each standard with `shots` whose files `git diff --name-only <main>...HEAD` names, it wants pictures in `.temp/shot/` (any depth) newer than the newest mtime of those files, then `.temp/<document's name>-check.md` newer than the pictures, holding each question of the document's section "The check" (its list items ending with "?", up to the next heading of the same level) with words after it before the next question. Committed changes only: the diff is of the branch, not of the worktree. A git that cannot tell lets the merge go.
- PR mode has no merge: the `Stop` hook refuses a turn whose last line is the `PULL REQUEST` mark with the same text (`decision: block`), once — a turn already stopped by a hook (`stop_hook_active`) goes.

OpenCode gets the same from `opencode/checkpoint.mjs`: the read on `tool.execute.after` (appended to the output), the edit on `tool.execute.before` (thrown), the marks dropped on the `session.compacted` event, the merge with the merge check. Its turn's end cannot be blocked, so PR mode's mark is not held there.

## One-off turns (BTN-142, `Agent.write`)

The optional `Agent.write(home, turn)` (`OneTurn`: `cwd`, `prompt`, `model`, `timeoutMs`) runs one turn that keeps no session and answers with its text; `runWithInput` (`src/agent/oneturn.ts`) feeds the prompt on stdin, so a long one never meets the Windows command-line limit, and kills the process tree on the timeout. Only reading tools, no MCP, nothing to approve:

- Claude: `claude -p --output-format json --no-session-persistence --strict-mcp-config --disable-slash-commands --tools Read,Glob,Grep [--model <m>]` (`writeArgs` in `src/claude/cli.ts`); `parseWriteAnswer` takes `result` and throws with the CLI's own words when `is_error` is set or there is no result. The cost is `total_cost_usd`, the tokens the sum of `modelUsage` (every call of the turn by model; the top `usage` counts only the last call), the model the costliest key of `modelUsage`.
- Codex: `codex exec --json --sandbox read-only --ephemeral --color never [-m <m>] -` (`writeArgs` in `src/codex/cli.ts`): the answer is the last `agent_message` item, the tokens are the `usage` of `turn.completed` (`input_tokens` holds `cached_input_tokens`), a `turn.failed` throws its message. Codex counts no cost and its events name no model: the cost is null and the model the one asked for. Without a model Codex takes the one of its own config, which a ChatGPT account may refuse.

Both checked live on 2026-10-18, Codex before `--json` (`docs/unverified.md`).

`Agent.write` returns the text with the turn's `TurnSpend`; the changelog keeps it with the version under the account folder it ran on (`ChangelogSpend`), and the dialog shows it (`docs/web.md`). A turn with `--no-session-persistence` or `--ephemeral` leaves no transcript or rollout, so Tally and `/stats` never count it. The turn cannot ask: neither tool list holds `AskUserQuestion`, `Edit`, `Write` or `Bash` (a test of `writeArgs` keeps it so), and the prompt says no one will answer a question.

The one user is the changelog of a milestone (`src/changelog/`, BTN-142, BTN-209): `ChangelogDrafts` (`drafts.ts`) takes the account and model a new chain session of the project would get (`choiceFor` in `src/service.ts`) and runs in the project's main checkout with a 10-minute timeout; one operation per milestone at a time, a second ask gets the running one's result. The source is the changelog file in the main checkout (the project's `changelog` setting, `CHANGELOG.md` by default), read anew on every turn so the user's own edits there are kept; `changelogPlan` (`file.ts`) finds the milestone's section: a milestone named by a version (`v0.1`) owns `[0.1.0]`, its patches and, until its first tag, `Unreleased`; a tagged section is frozen and new tasks go into the next patch's section, which Even Keel heads itself (`docs/releases.md`). The prompt (`changelogPrompt`, `draft.ts`) has three modes: `fresh` — the section from the milestone's `Won` tasks with their last comments (`milestoneTasks`, `docs/trackers.md`, each comment cut to `MAX_COMMENT_CHARS`); `update` — the file's section with only the tasks it lacks, worked into it without rewriting the rest, a task the user already described is not repeated; `edit` — the section and the user's words, no tasks. Every mode gets the tags and the frozen sections as "already released, do not repeat", and asks for Keep a Changelog groups in the language of the changelog file, else of `README.md`. The answer is cut to its section (`answerSection`) and kept as a version in the database (`changelog_versions`, `docs/storage.md`) with the tasks it accounts for and the text its changes are shown against. "Write" puts the newest version into the file — the milestone's section replaced, or a new one put above the older versions — and commits only that file to the project's main branch of the main checkout without a task id (`commitChangelog`, `src/git/changelog.ts`): refused when the checkout is on another branch or the file has uncommitted changes, the CRLF line ends of the file kept; the next `git sync` pushes it. Measured on BTN `v0.1`: 172 tasks, a 183 000-character prompt (~200 000 tokens with the reads), 29 s and $0.42 on Sonnet. The routes are `POST /api/changelog/open|again|add|edit|write` `{ project, milestone, instruction? }` (`docs/web.md`).

## Prompts (`src/sessions/prompt.ts`)

Assembled strictly: a value in the launch and handoff prompt goes through `fill`, and an empty or non-string one is an assembly error — the chain pauses with it instead of going into a session with a blank space. `modelPrompts` is passed as is, with no substitutions: `{name}`, `{{name}}`, `${name}` is a config error. A project whose tracker has a project key in the config (`github`, `linear`) gets the line "Tracker: GitHub, project octo-org/abc." after the launch or handoff text, brief or not (`withTracker`): with the brief off the prompt otherwise carries only the task id, and the GitHub skill fell back to `origin`, which may be missing or point elsewhere (BTN-143). The `prompt` setting (`withPrompts`) goes after the brief and before the unattended rules and the model prompt: Even Keel's own (BTN-338) under the heading "Instructions for every project:", then the project's (BTN-97) under "Instructions for this project:" — the two add up, a project's empty one leaves Even Keel's in place. They go into the prompt of a new session only — the first launch and every handoff (`relay`: the limit, the checkpoint, "New session", a fixed `main`, PR feedback, a task back from an inactive status — every `HandoffReason`); `--resume` and a reply continue a session that already has them. They are free text, not checked for substitutions; an empty one is no prompt. The session that fixes a red `main` without a task (BTN-115, `docs/chain.md`) has no brief: its prompt is `fixPrompt` — the report of what broke, the worktree, the branch and its rules — with the two prompts after it, and a handoff of it carries the report again (`withReport`). The prompt language is `promptLanguage` (`src/chain/prompts.ts`, see `docs/web.md`).

## Limits

- Each account has its own: `claude -p /usage --output-format json --no-session-persistence` in its folder every 5 minutes (a local command, spends no quota) and a statusline snapshot (marked with the session's `configDir`; without the mark — the global account); the fresher one is taken.
- Do not poll more often: the server answers `/api/oauth/usage` with 429, the VS Code extension panel polls it with the same token, and after a 429 the CLI (2.1.286) does not query this token for ~45 min.
- With an expired access token or after a 429, `/usage` returns no limits (the subscription line is there, the window lines are not) — that is "no data" (`stale`), not an error. A `/usage` answer is accepted whole or not at all: both window lines with a percentage and a reset (`0% used` without a reset — the window has not started).
- Polling continues only if the answer says outright `num_turns: 0` and `total_cost_usd: 0`, otherwise it is switched off until restart. An unreadable answer or switched-off polling is shown by the page as a banner (`UsageBanner`). A call that fails (an exit code, a timeout) goes to the banner only when the next poll fails too: a lone one is usually the network, and it is only logged. The call closes its stdin, otherwise `-p` waits 3 s for input and prints a warning that used to be the only "reason" the banner showed.
- While a window is used up, the next task is not started: the chain waits for the reset (`limitUntil`) and continues by itself.
- A limit on a running session whose text gives no reset time (the `wrap_up` warning) takes it from these limits once they are newer than the limit (`docs/chain.md`, exception 1).
- An API account (`docs/accounts.md`) has no windows: `/usage` is not polled for it (in its folder it answers free with no window lines), and exception 1 does not apply to its sessions. Which accounts are API ones is known only once the account folders are read, so the first poll after a start waits for that (`LimitsWatcher.deferred`). The exception is an agent with `keyUsage` (Copilot): its token account is polled and waits on its limits like a subscription (`spendsByKey` in `src/service.ts`, `keyLimits` of `SessionMonitor`).

## Prompt cache lifetime (BTN-99)

What the CLI 2.1.302 binary does, in order of precedence: the `FORCE_PROMPT_CACHING_5M` variable → 5 minutes; the variables `CLAUDE_CODE_PROMPT_CACHE_TTL` / `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`; the settings `promptCacheTtl` / `subagentPromptCacheTtl` (`"5m"` | `"1h"`), whatever the sign-in; the `ENABLE_PROMPT_CACHING_1H` variable → 1 hour. Without any of them: 1 hour on a subscription within its limits (5 minutes in overage), 5 minutes on an API key, Bedrock or Vertex. A 1-hour cache write is billed higher than a 5-minute one.

The `cacheTtl` key (`"5m"` | `"1h"`, absent or `null` — the CLI decides; `/settings`, the Claude Code group, and a project's own value in its panel, BTN-187) goes into the chain sessions' `--settings` as `promptCacheTtl` (`chainSettings` in `src/tools/panel.ts`), on every launch. It is live: the next launch takes the new value. It matters mostly on a key, where a chain waiting for a reply longer than 5 minutes otherwise writes the whole context again. Seen live on a key with `1h` (CLI 2.1.310, Haiku, a `--bg` and an SDK chain session, 2026-10-25): every cache write of both was `ephemeral_1h_input_tokens`, none 5-minute.

## The Agent SDK transport (BTN-239, `src/claude/sdk/`)

A second way to run Claude sessions, beside `--bg`, chosen per account folder; the research behind it is the two sections below.

- **The choice.** The shared setting `execution.claude` (BTN-353; before it each folder's `transport` in `state/account.json`, `docs/accounts.md`): `auto` by default — an API-key folder takes `sdk` (the path Anthropic recommends for keys) and a subscription `bg` —, or `bg` or `sdk` for every folder (`transportOf` in `src/account/transport.ts`). /settings → Providers and models has it in the Execution column, its hint carrying what the SDK gives, that it needs the checked CLI and Anthropic's rule on SDK products; the Accounts card only says where a folder's sessions go. It applies live to the next launch: a session keeps the transport it started on, since the adapter routes a resume, a reply and a stop by whether the SDK registry knows the session id, never by the setting. Only Claude folders have it.
- **When it is used.** `viaSdk` in `src/claude/adapter.ts`: the folder's transport is `sdk`, the CLI is Even Keel's checked copy (`cli.claude: checked`, no `EVEN_KEEL_CLAUDE_BIN`) and the SDK of that version is downloaded. The SDK talks its own CLI version's protocol, so its version is pinned to the CLI's: CLI `2.1.N` goes with SDK `0.3.N` (`sdkVersionOf`). Its copy is a `PinnedCli` in `state/cli/claude-sdk/<version>/`, fetched from npm by `fetchNpmPackage` (`src/agent/npm.ts`, shared with Codex) at the first launch that wants it, without the platform package: `pathToClaudeCodeExecutable` is the checked CLI. Until the copy is there, the launch goes by `--bg` and the log says so.
- **The executor** (`executor.ts`). A detached node process per session runs the CLI with piped stdio and holds a named pipe (`\\.\pipe\even-keel-sdk-<uuid>`; `<tmpdir>/ek-sdk-<hex>.sock` elsewhere). It runs under Node's own type stripping, not tsx — tsx's esbuild child would hold `node_modules` — so it imports only `node:` modules and uses erasable syntax only. The protocol is JSON lines: the host's first line is `{"executor":"spawn",command,args,cwd,env}` or `{"executor":"attach"}`, the executor answers `{"executor":"hello",pid,turn}`, then every line is the CLI's stdin one way and its stdout the other; `{"executor":"exit",code}` once the CLI is gone. One host at a time, a new one replaces the old; the CLI's stdin is never ended. Without a host the CLI's output is buffered: 1 MB in memory, then a spill file of up to 256 MB, and the next host gets it. It exits when no first host came within 60 s, or 10 minutes after the CLI ended with no host back. Its log and spill file are `state/claude-sdk/executors/<session id>-<start>.log` and `.spill.jsonl`. A stop kills its process tree (`killTree`) and waits up to 30 s for the executor and the CLI to die (`claude.stillRunning` otherwise).
- **The host** (`host.ts`, `SdkSessions`). A `query()` whose `spawnClaudeCodeProcess` returns an `ExecutorProcess` (`pipe.ts`), a socket to the executor; the input is an inbox that never ends, so the CLI waits for the next message. The options: `systemPrompt` is the `claude_code` preset (omitted, the SDK sends an empty system prompt), `permissionMode` the chain's `auto`, the session's name as `title`, its model, `--settings`, the packages' MCP servers behind the gateway with `strictMcpConfig`, and its plugins as `local` plugins. `canUseTool` keeps an `AskUserQuestion` call pending as the session's question. Any other tool the CLI wants approved (BTN-303) is refused while the chain is unattended (`AgentOptions.unattended`, read at each call, so the switch applies live; `NO_APPROVAL` is the message); otherwise it waits as a question too, built by `permissionAsk` (`src/sessions/permission.ts`, shared with the `--bg` path, "Permission dialogs" above) in the page's language: "Allow the session to run <tool>?" with "Allow" (the command, or the input as JSON, in its preview) and "Deny", so the page's question panel, the chat and a tracker comment answer it as any question, and it is the turn's `waiting` state, not `waitingFor`. An approval that already waits when unattended mode goes on is refused at the next poll of the session's account (`refuseApprovals` in `sessions()`, every 3 s), or the chain would stand on it all night. After a restart of the service the host connects again on the first poll of the session (`connected`): a new `query()` attaches to the same executor, the CLI answers the SDK's `initialize` and asks the question it is still blocked on again, so the page has it back. The live view is an `AgentEntry` of kind `sdk`: alive while the executor's pid lives and its pipe answers (a reused pid does not), busy/idle from the SDK's `assistant` and `result` messages and the executor's `hello`, `waiting` with the question while a call is pending.
- **A reply goes into the live CLI** (`Agent.reply`, tried first by `resumeWith` in `src/service.ts`): all answers and no words of the user's own — the pending call is allowed with `updatedInput.answers`, a real `tool_result`; words or files with an open question — the call is refused with the whole reply as its message; no question — a new user message on stdin, which a busy session takes in the same turn. A pending tool approval is answered by `permissionMove`: the first option alone allows the call with its own input, any words that came with it following as the next message; "Deny" alone refuses it with "The user denied this call"; words of the user's own without "Allow" refuse it with the whole reply. Checked live from a terminal (2026-10-22, CLI 2.1.306, Haiku): such a message mid-turn is written as a `queue-operation` `enqueue`, then after the running tool's result an `attachment` `queued_command` and a `remove`, and the model answered it in that turn — the same shape the feed already reads for Remote Control. So a live SDK entry `steers` (`sdkEntryOf`), and a chat message to it while it works goes this way at once (`steer` in `answerSession`, `src/service.ts`, BTN-291), not into the mailbox; the page keeps its chat open mid-turn (`SessionMail.steers`). A reply to a session whose executor is gone is a new executor with `resume` and the same session id.
- **Remote Control** goes through `enableRemoteControl(true, name, { keepSessionOnExit: true, reattachSessionId })` while the folder starts sessions with it (`remoteControlAtStartup` in its `settings.json`, `remoteAtStartup`), the `cse_…` id kept in the record so a resume returns to the same chat on claude.ai; with no answer in 15 s the session runs without it. The method is not in the SDK's types (only in `sdk.mjs`), so it is optional in `src/claude/sdk/types.ts`. The `bridge` module stays unused (BTN-136).
- **The registry** (`registry.ts`): `state/claude-sdk/sessions/<session id>.json` with the name, folder, account, start, executor and CLI pids, pipe, model, Remote Control id and `stopped`, stamped with `SCHEMA_VERSION`. SDK sessions are not jobs of the daemon: `claude agents` and the desktop app do not list them; the transcript is the usual file, so the feed, Tally and handoffs read it as before.
- **Limits** (BTN-290): the `/usage` poll stays, and between its polls each `rate_limit_event` of the session (the CLI sends one per response) puts its windows over the newest that is known of the account (`limitsOfRateLimitInfo`, `LimitsWatcher.report`, source `sdk`, "from an SDK session" on the page). The utilization is a share and the reset in seconds; `unifiedWindows` holds both the five-hour and the weekly window, though it is not in `sdk.d.ts` — seen live on CLI 2.1.308 with SDK 0.3.308 (`{"status":"allowed_warning","rateLimitType":"seven_day","utilization":0.45,…,"unifiedWindows":{"five_hour":{"utilization":0.6,"resetsAt":…},"seven_day":{…}}}`). Without it only the documented `rateLimitType` window is read, and a `rejected` one without utilization counts as spent; the models' (`seven_day_opus`, `seven_day_sonnet`) and overage windows are not shown.
- **Checked live from the service** (BTN-292, 2026-10-22, Windows, CLI 2.1.308, SDK 0.3.308, Haiku, a subscription folder with `remoteControlAtStartup`). The first launch after the switch logged `the SDK 0.3.308 is not downloaded yet`, fetched it within a second and ran on `--bg`; the next ones ran through the SDK. `Restart-Service EvenKeel` while a session waited on its `AskUserQuestion`: the executor and the CLI lived on (their parent, the old node, gone), a new host attached 2 s after the start, the page had the question back, and the answer from the chat window went into the live CLI (`the reply went into the live SDK session … (answer)`, no `--resume`). Three restarts in one turn of a 4-minute command, the last a 28 s stop over the command's end: the executor kept the CLI, the turn wrote the command's result and two more steps with no host, then ran to its end under the host that attached, merged its branch, and the cleanup after Done stopped the session with no process left. Each session got its Remote Control id (`bridge`). Not run yet: a night of the chain against `--bg`, an answer from the phone and the reattach after a resume (BTN-296).

## Agent SDK and API keys (BTN-136, research)

Before BTN-239: a check of whether sessions could run through the Agent SDK (`@anthropic-ai/claude-agent-sdk`) or on an API key and survive a restart of the service. Checked live on 2026-10-17 with SDK 0.3.302 (it bundles CLI 2.1.302 in `@anthropic-ai/claude-agent-sdk-<os>-<arch>`, so pinning the SDK pins the CLI unless `pathToClaudeCodeExecutable` is set), the standalone CLI 2.1.302, Haiku, the sandbox repository, a Pro subscription; the scripts were throwaway.

| | CLI `--bg`, subscription (today) | CLI `--bg`, API key | SDK, subscription | SDK, API key |
| --- | --- | --- | --- | --- |
| Survives a service restart | yes, the daemon owns the sessions | yes, the same daemon | only through a detached executor or `resume` (below) | as SDK on a subscription |
| A pending question | only in `jobs/<id>/state.json`, lost on `claude stop` | as on a subscription | the `canUseTool` callback; the call is in the transcript at once | as SDK on a subscription |
| Remote Control | yes | no (needs a claude.ai sign-in) | yes, `enableRemoteControl` (undocumented) | no |
| Limits | 5h/7d windows, `/usage` | the organization's budget and rate limits, no windows | 5h/7d windows | the organization's |
| Fragility | undocumented `sessions/`, `jobs/`, `agents --json` | as on a subscription | documented API, except `enableRemoteControl`; an executor of our own to maintain | as SDK on a subscription |
| Anthropic's rules | the user signs in to the unmodified binary: allowed | allowed | open source only: SDK products "should use API key authentication" | allowed, the recommended path |

The SDK on an API key was not run (the key was spent only on the CLI check); its rows follow from the SDK runs on a subscription and the CLI run on the key.

- **The host dies with the default spawn.** The CLI is a child of the host's node and reads stdin; a non-detached child of node sits in libuv's kill-on-close job object, so a `TerminateProcess` of node (what the service host's `Process.Kill()` does) kills it at once. Its `sessions/<pid>.json` stays with a dead pid and `status: waiting`.
- **`resume` after the host died.** In an SDK session the `AskUserQuestion` call reaches the transcript at once, unlike `--bg`. `query({ resume })` keeps the whole history with the call; the call gets a synthetic `tool_result` with `is_error` — `[Tool call interrupted: the session ended before this call's result was recorded, so its outcome is unknown. …]` — and an assistant `No response requested.`; the answer comes as the next prompt, and the session took it. With a warm cache it cost 18.9k tokens read and ~230 written ($0.00024 on Haiku); with a cold one the whole context is written again (~19k tokens here, at the 1 h write price), not measured. Mid-turn: a running Bash command outlived the CLI and finished (its file appeared 20 s later), and after `resume` the model ran it again — a side effect may happen twice.
- **A detached executor.** `spawnClaudeCodeProcess` returns any `SpawnedProcess` (`stdin`, `stdout`, `kill`, `exit`). A separate node process started with `detached: true` spawns the CLI and pipes its stdio to a named pipe; the host's `SpawnedProcess` is a socket to it. The executor must not end the CLI's stdin when the host disconnects (a deliberate close sends its own message) and buffers the CLI's stdout until the next host. The host was killed while a question was pending: the executor and the CLI went on. A new `query()` whose spawn function attaches to the same pipe sends `initialize`, the running CLI answers it with the request it is still blocked on, and the SDK redelivers the question to `canUseTool` (`reinitialize()` documents this); the answer went in as a proper `tool_result` and the turn finished in place, without `resume`. A `detached` child survives a `TerminateProcess` of its parent and a non-detached one does not (checked); the executor was not started by the real service, so its surviving a `Restart-Service EvenKeel` rests on that and on the CLI daemon, a detached grandchild of the service's node, which does survive one.
- **Remote Control.** `enableRemoteControl(enabled, name?, { reattachSessionId, keepSessionOnExit })` on the `query()` object sends the CLI a `remote_control` control request and returns `{ session_url, bridge_session_id: "cse_…" }`; `initializationResult()` reports `remote_control_available`. The CLI turns `keep_session_on_exit` into `neverArchive`. Checked from the phone: an answer from the claude.ai app aborts the host's pending `canUseTool` (its `signal`) and the session goes on with it; with the host dead and the CLI in the executor the answer from the phone finished the turn and the next host got the buffered output; after the CLI exited (`keepSessionOnExit: true`), `resume` plus `enableRemoteControl(true, name, { reattachSessionId: "cse_…" })` in a new CLI came back into the same chat with the same `bridge_session_id`, and a new question was answered there. The `@anthropic-ai/claude-agent-sdk/bridge` module (`@alpha`) wants the account's OAuth token from the host — not to be used: Anthropic forbids third parties to collect Claude.ai tokens.
- **The CLI on an API key.** `claude --bg --model haiku` with `ANTHROPIC_API_KEY` in its environment, in a fresh account folder (its `.claude.json` with `hasCompletedOnboarding`, the folder trusted and the key pre-approved in `customApiKeyResponses.approved` by its last 20 characters, otherwise an interactive session asks), started a daemon and the session answered. The key is not in the job's `providerEnv` (only `CLAUDE_CONFIG_DIR`): it reached the session only because that `claude --bg` started the daemon, and sessions inherit the daemon's environment, respawned ones too; through a running daemon it would not arrive (BTN-129, `docs/accounts.md`). So for real use the key belongs in the account folder's `settings.json` `env`, which every session reads at its start, or an `apiKeyHelper`. The cache was written with a 5-minute lifetime (a subscription writes 1 h). A key not scoped to a workspace fails with `400 … must include the anthropic-workspace-id header`. `--max-budget-usd` works only with `--print`. Spent on the key: $0 (the 400) and ~$0.004 (28.5k tokens written, by the SDK's prices).

## Agent SDK against `--bg` (BTN-238, research)

How much steadier sessions through the Agent SDK would be than the `--bg` path, for the implementation (BTN-239, whose description holds the scope). Done on 2026-10-22 from the traps, `git log` and SDK 0.3.250–0.3.307; the live parts BTN-136 left unrun need the SDK transport inside the service and moved to BTN-239.

**The traps.** Of the CLAUDE.md "Traps", this file and `docs/unverified.md`, the ones the transport touches:

| Trap | With the SDK |
| --- | --- |
| `claude agents --json` has no `pid`/`status`, `state` lies; liveness from `sessions/<pid>.json` | gone: the host owns the CLI process and reads the turn's end from `result`; a registry of our own instead, as for Codex |
| a pending question only in `jobs/<id>/state.json`, lost on `claude stop` | gone: `canUseTool` gets it at once (`--bg` has had it in the transcript since 2.1.302 too) |
| an answer is `claude stop` + `--resume`: ~5 s floor, the synthetic "Tool call interrupted" | gone: the answer is the `canUseTool` result, a reply after a text turn a line into the live CLI's stdin (`streamInput`) |
| `--bg --resume` with flags starts a copy (`own-options`) | gone: `resume` keeps the session id (seen in BTN-136) |
| the respawned job shows a fresh session id for under a second; `steadyJobs`, `ResumeHolds`, `resumedAs` | gone: no daemon respawns anything |
| a prompt starting with a dash kills the job before init | gone: the prompt goes as JSON on stdin |
| `claude stop`/`agents` from a terminal do not reach the service's daemon | gone, and so does any terminal control: the user stops a chain session through Even Keel or by its pid, as today |
| the daemon's environment frozen at its start (BTN-129), the daemon restart on a shared config change (BTN-31) | gone: every launch is a new process with the environment the host gives it |
| the daemon's version: self-restart on upgrade, a terminal `--bg` replacing a pinned daemon, `DaemonRefresh` (BTN-248, BTN-250) | gone: each launch runs the binary named in `pathToClaudeCodeExecutable` |
| a startup dialog visible only in the job file | gone, presumably: stream-json mode shows no dialogs; not run |
| `state: done` given to a turn that ended on a plain-text question | gone: the host sees `result` and the CLI waiting on stdin |
| from 2.1.306 a background session's file tools are refused in a main checkout (EKR-16) | unknown: whether it is `--bg` only was not checked; chain sessions run in linked worktrees anyway |
| short CLI calls killed mid-renewal burn the refresh token (EKR-15) | partly: `claude agents` goes; `auth status`, `/usage`, `/context` stay, though `getContextUsage()` and the per-turn `rate_limit_event` could replace the last two (the SDK's own `/usage` call is marked experimental) |
| several `.claude.json` keys per folder, the desktop app's profile, plugin `version` bumps, `--strict-mcp-config`/`--plugin-dir`, `settings.local.json` of the main checkout, the failed-MCP cache (BTN-159), `bash.exe` outliving a stopped session (BTN-202), `/usage` 429 | stay: they are the CLI's, and the SDK runs the same CLI (the flags become `Options`) |

**How often `--bg` broke Even Keel.** Of 638 commits from 2026-09-01 to 2026-10-21, 23 fixed behaviour of the session transport (read from subjects and bodies, features left out). 17 would not have happened with the SDK: the daemon's config and environment (`e997d2c2`, `07be72a0`), liveness from `agents --json` (`40f66f47`, `009d3e1f`, part of `0c44af7e`), a terminal `claude stop` (`97eca325`), startup dialogs in job files (`3b04bdcd`, `49ce3bb5`), the question in the job file (`40293a78`), and eight about stop + resume: the copy under a new id (`c6f97863` and its test `7288bbdf`), flags starting a copy (`8e08a70a`), the respawn's fresh id (`f36a9c2e`), holds and steady jobs (`90f4419b`), the feed during delivery (`be25d75b`), the dash (`6b0583fd`), the latency (`d66532d2`). 4 partly (`c9230060` the MCP approval hang, `2bb62f3f` the delivery line, `0ec868e4` EKR-15, `57baf2d7` EKR-16), 2 stay (`55cad0ca` BTN-159, `9e5f0f20` BTN-202). Two came in September, 21 in October, 18 of them between 10 and 18 October, when resumes after a question or a limit and replies from the chat were built: the reply path is where `--bg` cost most. Since BTN-250 and BTN-253 a new CLI reaches the chain only after the CLI check, so the rate after 10-21 says little yet.

**What comes instead.**

- **An executor of our own** per session (BTN-136's `executor.mjs`): a detached node process holding the CLI and a named pipe (a Unix socket elsewhere). Ours to get right: the reattach handshake, the stdout buffer while no host is attached (bounded, spilled to a file), an executor whose CLI exited and whose host never came back (it must exit), the registry that maps a session to its pipe, killing the CLI's process tree. If the executor dies the CLI loses its stdin and ends; the session goes on by `resume` from the transcript, with the risk BTN-136 saw mid-turn — a command run twice. Survival of a service restart rests on mechanics, not a run: the host's `Process.Kill()` (`service/EvenKeelService.cs`) is a `TerminateProcess` of node, which kills only children in libuv's job object, and a `detached` child is not in it (checked in BTN-136); on Linux `KillMode=process` (`service/install.sh`) already leaves the daemon alive.
- **`enableRemoteControl`** is still only in `sdk.mjs`, not in `sdk.d.ts` (0.3.307): it may change without notice. The `bridge` module (`@alpha`) stays out (BTN-136).
- **The release pace.** The SDK is published with every CLI build, its version mirroring the CLI's (0.3.307 bundles 2.1.307), daily. It is 0.x: the minor went 0.1 → 0.2 in January 2026 and 0.2 → 0.3 in May. From 0.3.250 to 0.3.307 the `Query` interface (29 methods) and `Options` (69 fields) lost nothing, only gained (`readMcpResource`, `reloadOutputStyles`, `updateSettings`, four options); 0.3.290 → 0.3.307 added two exported constants. So the pin of BTN-250 and the CLI check cover it, the SDK's own pin being a `package.json` line.
- **Size.** The package is ~4.7 MB; the CLI comes as an optional dependency per platform, 274–292 MB (`manifest.json` of 0.3.307). Even Keel already downloads the checked CLI (BTN-250), so with `pathToClaudeCodeExecutable` pointing at that copy the install skips the platform package (`--omit=optional`) and nothing is fetched twice; an update changes the pin of both together.
- **Visibility.** SDK sessions are not jobs of the daemon: the user's `claude agents` and the desktop app do not list them; the transcript is the same file, so the page's feed, Tally and the handoffs read it unchanged. The cache on a subscription is 1 h as with `--bg` (BTN-136 runs).

**Anthropic's rules, re-read on 2026-10-22** (`code.claude.com/docs/en/legal-and-compliance`): "Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication", and third-party developers may not "route requests through Free, Pro, or Max plan credentials on behalf of their users"; while signing in "to the unmodified Claude Code binary with their own Claude subscription" is expressly not restricted. So `--bg` on the user's subscription is the allowed path, and the SDK on a subscription stays what the user decided after BTN-136: the open source build only, off by default in a paid one. The page also has a section on offering Claude Code in products (whether it is new since BTN-136 is not known) (unmodified binary, each end user on their own credentials, under the Commercial Terms).

**Conclusion: keep both transports, `--bg` the default.** The SDK removes most of what broke (17 of 23 fixes) and the reply path's restart, but `--bg` is the path the rules name as allowed on a subscription, which is how nearly every user runs; its traps are paid for and now gated by the CLI check; and the SDK brings an executor whose failures are ours, unproven under the service. BTN-239 builds the SDK as a second transport chosen per account folder, the default for API-key accounts (the path Anthropic recommends there) and opt-in on a subscription, with the live checks of this task as its acceptance: `Restart-Service EvenKeel` with a pending question and mid-turn, then a night of the TSK chain on the SDK against the same set on `--bg`. Dropping `--bg` is decided only after that night.

## Pinning the CLI versions (BTN-248, research)

Whether chain sessions can run on a checked CLI version instead of the one the CLI updated itself to; the implementation is BTN-250. Checked on Windows on 2026-10-19 with Claude Code 2.1.301–2.1.303 and codex-cli 0.162.1; the daemon runs below were in a scratch `CLAUDE_CONFIG_DIR`, not signed in, so no session spent a token. What Even Keel depends on in each CLI is listed in the README ("Before you run it").

**Claude Code today follows the newest version.** The native installer keeps whole binaries in `~/.local/share/claude/versions/<version>` (three were there: 2.1.301, 2.1.302, 2.1.303) and a copy of the current one at `~/.local/bin/claude.exe`, the path `resolveClaudeBinary` takes. Each account folder has its own daemon (the pipe `cc-daemon-<16 hex>` is keyed by the config folder; the service's daemon runs in Windows session 0). The daemon spawns its pty hosts and sessions from its own binary, and restarts itself on a newer build once its binary file changes (`tengu_daemon_self_restart_on_upgrade`, deferred while busy; it refuses an older build: "binary … changed to an OLDER build … refusing self-restart"). So when the user's own CLI updates the launcher, the service's daemon moves to the new build and the chain's next sessions run on it. Release cadence: 2.1.301 on 10-15, 2.1.302 on 10-17, 2.1.303 on 10-18; the `stable` channel was at 2.1.292.

- **A version by path.** `versions/<version>` runs as is, from a shell and from Node's `execFile` alike, though it has no `.exe` extension. But a binary under `versions/` starts the daemon through the launcher (`mUe` in the binary: inside the versions folder → `~/.local/bin/claude.exe`): a `--bg` from `versions/2.1.302` got a daemon and a session on 2.1.303. A copy of the same binary outside that folder starts the daemon, its pty hosts and its sessions from itself: all on 2.1.302.
- **The daemon decides the version, not the client.** A `--bg` from the pinned 2.1.302 copy to a running 2.1.303 daemon got a 2.1.303 session. A `--bg` from the 2.1.303 launcher to a running 2.1.302 daemon replaced that daemon with a 2.1.303 one; the old session's pty host lived on, orphaned. So a pin holds only while nothing newer starts a background session or asks `claude agents` in that account folder. Whether a terminal client in session 1 replaces the service's daemon in session 0 was not checked.
- **Getting a version.** `claude install <version>` (or `stable`/`latest`) installs into `versions/` and moves the launcher, so it changes the user's own CLI. Every build is published as `https://downloads.claude.ai/claude-code-releases/<version>/<platform>/claude(.exe)` with a `manifest.json` beside it (size and sha256 per platform; the local 2.1.301 matched it); `…/claude-code-releases/stable` and `…/latest` name the channels' versions. The npm package `@anthropic-ai/claude-code@<version>` is a wrapper over `@anthropic-ai/claude-code-<platform>` with the same binary (272 MB unpacked).
- **Auto-update.** `DISABLE_AUTOUPDATER=1` turns it off for a process (`DISABLE_UPDATES` also blocks `claude update`); `autoUpdates: false` in the global config counts only for non-native installs. `autoUpdatesChannel` (`latest`/`stable`/`rc`) and `minimumVersion` are settings of the config folder, so they would move the user's sessions in that folder too. A session started from a pinned copy without the variable would still update the user's native install. The VS Code extension runs its own bundled binary (2.1.301 here) and no daemon.
- **Shared state.** The account folder — `.claude.json`, `settings.json`, transcripts, `sessions/`, `jobs/`, `daemon.json`, the plugins — is shared by every version that runs in it, and Even Keel and Tally read transcripts the user's own sessions write on whatever version they run. A pin protects the control path of chain sessions (`--bg`, `agents --json`, the records, `/usage`), not the reading of other sessions' files.
- **Server side.** The CLI refuses to start below the remote `tengu_version_config.minVersion` ("It looks like your version of Claude Code (…) needs an update"); the value cached in every account folder here was `1.0.24`. `tengu_max_version_config` can force a downgrade. `requiredMinimumVersion`/`requiredMaximumVersion` are managed-policy settings only. Model aliases (`opus`, `sonnet`) are resolved by the binary, so an old pin may not know a new model's alias. Limits come from the server (`/api/oauth/usage`); a pin keeps the text of `/usage` the same.
- **Licence.** Claude Code is proprietary ("© Anthropic PBC. All rights reserved", the npm package's `LICENSE.md`): its binary cannot go into this repository or a release of Even Keel; Even Keel may only fetch it from Anthropic onto the user's machine, as the installer does.

**Codex has no daemon in the chain's path.** A turn is one `codex exec` process from the binary `resolveCodexBinary` finds, so the version of a turn is the version of that binary. The npm package `@openai/codex@<version>` takes its native binary from `@openai/codex@<version>-<platform>` (457 MB unpacked on win32-x64); GitHub releases carry the same binaries. Codex does not update itself: `check_for_update_on_startup` only shows a notice in the interactive TUI, and `codex update` runs when asked. The global npm binary changes only when the user updates it, and on Windows that update cannot replace a `codex.exe` a chain turn is running from. The Codex desktop app ships its own build and shares `~/.codex`.

- **Shared state.** `CODEX_HOME` holds versioned SQLite files (`state_5`, `logs_2`, `thread_history_1`), so a newer schema gets a new file rather than rewriting the old one. `codex migrate-rollouts --apply` (0.162.1, manual) moves legacy sessions to "paginated thread history"; a version that does that by itself would break the rollout reader whatever the chain runs on.
- **Server side.** The model list is fetched with the client's version (`client_version` in `models_cache.json`), and models carry a minimal client version, so an old pin does not see new models.
- **Licence.** Apache-2.0: the binary may be redistributed with its licence and notice, so Even Keel could depend on the npm package or fetch it.

**Conclusion.** Pinning is worth it for both CLIs. Codex is a binary path and nothing else. Claude needs Even Keel's own copy outside `versions/`, a folder per version (a running exe cannot be replaced on Windows), `DISABLE_AUTOUPDATER=1` for the sessions, a check of `claude daemon status` against the pin, and a daemon restart while no session of the folder is mid-turn to change versions. It holds only while the user starts no background sessions on another version in the chain's account folder. Built in BTN-250, below.

## The checked CLI (BTN-250, `src/agent/pinned.ts`)

Chain sessions run on the CLI version Even Keel was last checked against (`AgentAdapter.checked`, the README's "Last checked against"), not on the one the installed CLI updated itself to. The global setting `cli.<provider>` chooses: `checked` (the default) or `system`, the installed CLI as before; it applies from the next call of the CLI. `EVEN_KEEL_<AGENT>_BIN` beats both. All four agents are pinned since BTN-347; before it OpenCode and Copilot ran on the installed CLI only, for no reason but that it was not done yet.

- **Even Keel's own copy.** `PinnedCli` keeps a folder per version under `state/cli/<agent>/<version>/`. The first call of the agent's CLI while the copy is missing starts the download in the background, and until it ends that call and the next ones run on the installed CLI; a failed download is one log line and is tried again 15 minutes later. It downloads into `<version>.partial` and renames the folder when done, and after that keeps the newest other version and removes the rest; a folder still in use (a running exe on Windows) stays until the next download. When the copy is ready the version watcher asks again at once (`onCliChange`), so the page's banner goes.
- **Claude Code** (`src/claude/release.ts`): `manifest.json` of the version gives the binary's size and sha256 for the platform (`win32-x64`, `darwin-arm64`, `linux-x64`, `linux-x64-musl` on a Linux without glibc, …), the binary is `…/claude-code-releases/<version>/<platform>/claude(.exe)` from Anthropic's site, checked against both before it is used; ~270 MB per version. Nothing of it goes into the repository: the licence is proprietary.
- **Codex** (`src/codex/release.ts`): the platform's npm package `@openai/codex@<version>-<platform>` (Apache-2.0), its tarball only from `registry.npmjs.org` and checked against the registry's sha512, unpacked by `tar` (on Windows `System32\tar.exe`) into the version's folder; the binary is `vendor/<triple>/bin/codex(.exe)`, with `codex-path` and `codex-resources` beside it as in the global package. A turn is a process of that binary, so the next turn runs on the copy.
- **OpenCode** (`src/opencode/release.ts`): the npm package of the platform's native binary that `opencode-ai` lists as an optional dependency, `opencode-<windows|linux|darwin>-<x64|arm64>` with `-musl` on a Linux without glibc (MIT), fetched and checked as Codex's; the binary is `bin/opencode(.exe)`, ~170 MB per version. The `-baseline` builds `opencode-ai`'s `postinstall.mjs` takes on an x64 without AVX2 are not: such a machine runs on `system`. The npm versions are OpenCode's own releases, the ones `npm install -g opencode-ai` installs.
- **Copilot** (`src/copilot/release.ts`): the npm package of the platform's native binary that `@github/copilot`'s `npm-loader.js` runs, `@github/copilot-<win32|linux|linuxmusl|darwin>-<x64|arm64>`, fetched and checked as Codex's; the binary is `copilot(.exe)` at its root, the whole CLI without Node, ~155 MB per version. Its versions are the ones winget installs (both 1.0.103 on 2026-10-24). A Copilot binary runs the newest version it has updated itself to (`%LOCALAPPDATA%\copilot\pkg\<platform>\<version>` on Windows) unless `COPILOT_AUTO_UPDATE=false`, so the copy 1.0.98 answered `--version` with 1.0.103: the variable goes to every Copilot call, `--version` included.
- **No auto-update.** A Claude session on the copy gets `DISABLE_AUTOUPDATER=1` (`claudeEnv`), so it never updates the user's own install; the daemon the copy starts keeps the variable for its sessions. OpenCode gets `OPENCODE_DISABLE_AUTOUPDATE=1` and Copilot `--no-auto-update` with `COPILOT_AUTO_UPDATE=false` on whichever binary they run.
- **The daemon.** A Claude session runs on its folder's daemon's version, not on the client's. Before each launch, relay and resume, `DaemonRefresh.prepare` asks `claude daemon status` for the daemon's `version:` (`Agent.daemonVersion`; with no daemon CLI 2.1.308 prints `not running` and exits with code 1, which is "none runs", not an error — BTN-333) and compares it with the pin (`Agent.pinned`): a daemon on another version is stopped (`claude daemon stop --any`) once no session of the folder is live — the same rule as for a shared key, so a waiting or resting session is never stopped for it (invariant 1) — and the launch then starts a new daemon from the copy. Until then the folder is in `EvenKeelState.cliVersions` with its account and the `agent.daemonVersion` notice, and its sessions run on the daemon's version. A newer `claude --bg` or `claude agents` in the same folder replaces a pinned daemon with its own version again (BTN-248), so the pin holds only while nothing else starts background sessions there on another version.
- **What the pin does not cover.** The server may refuse an old version (`tengu_version_config.minVersion`) or force a newer one (`tengu_max_version_config`); an old version may not know a new model's alias, and Codex lists models by the client's version: then the checked version is raised. Transcripts the user's own sessions write on a newer version are read as before.

## OpenCode (BTN-212, research)

What OpenCode gives against the `Agent` contract, the research behind its adapter ("OpenCode" above; BTN-214 holds the full table and the decisions). Checked live on 2026-10-19 with OpenCode 1.18.25 on Windows, the free model `opencode/big-pickle` with no sign-in, from a terminal, not from the service.

- **A turn is a process**, as with Codex: `opencode run --format json -m <provider>/<model> "<prompt>"` prints JSON events (`step_start`, `tool_use`, `text`, `step_finish` with `tokens` and `cost`), every one carrying `sessionID`; `opencode run -s <sessionID>` goes on in the same session, after a killed turn too. A killed turn leaves its tool part `running` and its message without `time.completed` for good. `opencode serve` has an HTTP API (`prompt_async`, `abort`, `session/status`, questions, permissions) but is a server of its own to keep alive. On Windows `opencode` on the PATH is an npm wrapper; the native binary is `node_modules/opencode-ai/node_modules/opencode-windows-<arch>/bin/opencode.exe` under the global npm folder.
- **The account is four XDG folders**: `XDG_DATA_HOME` (`auth.json`, the transcripts in `opencode/opencode.db`), `XDG_CONFIG_HOME` (config, JS plugins in `opencode/plugins/`), `XDG_STATE_HOME`, `XDG_CACHE_HOME`. They do not hide `~/.claude/CLAUDE.md`, `~/.claude/skills` and `~/.agents/skills`, which OpenCode reads from the home folder: `OPENCODE_DISABLE_CLAUDE_CODE`/`OPENCODE_DISABLE_EXTERNAL_SKILLS` switch them off, and the account's `opencode/AGENTS.md` takes the place of `~/.claude/CLAUDE.md`. In a project it reads one file: `AGENTS.md`, else `CLAUDE.md`.
- **The transcript is SQLite**, tables `session`, `message` (role, `modelID`/`providerID`, `tokens`, `cost`, `finish`, `time.completed`, `error`) and `part` (text, tool calls with `state.status`); `opencode export <id>` gives the same as JSON in ~1.2 s. Context windows are in `opencode models <provider> --verbose` (`limit.context`).
- **No usage windows**: neither the ChatGPT nor the Copilot sign-in shows limits; only tokens and cost per answer.
- **MCP of the packages only**: `OPENCODE_CONFIG_CONTENT` with the gateway's servers, and `{"enabled": false}` by name for the servers of the project's own `opencode.json(c)`. `OPENCODE_DISABLE_PROJECT_CONFIG` is no way out: it drops the project's `AGENTS.md`/`CLAUDE.md` too. Package skills go in `skills.paths`.
- **Hooks are JS plugins**, not Claude's `hooks.json`: `tool.execute.before` (throwing blocks the call), `tool.execute.after` (may extend the output), `event` (`message.updated` carries the tokens). A note appended to a tool's output was taken by the model for an injection and ignored.
- **Permissions**: tools are allowed by default; an `ask` (such as `external_directory`, which a merge into the main checkout from a worktree is) is rejected on its own in `run`, so a session does not hang on it; `--auto` approves every `ask`. There is no OS sandbox. `run` has no question tool, even with `OPENCODE_ENABLE_QUESTION_TOOL`: a question is the text the turn ends with.
- **Sign-in**: `opencode providers login -p <provider> -m "<method>"` works through a pipe. Anthropic takes only a key (the Pro/Max sign-in is gone); `-p openai -m "ChatGPT Pro/Plus (headless)"` prints a device link and code, as Codex does; Copilot is a GitHub device sign-in; GitLab — OAuth or a token; the free models need none. One account folder may hold several providers at once.

## GitHub Copilot CLI (BTN-213, research)

The research behind the adapter above: what the Copilot CLI gives against the `Agent` contract and how it differs from OpenCode signed in with Copilot (BTN-215's description holds the full table, the comparison and what was not checked). Checked live on 2026-10-19 with Copilot CLI 1.0.98 on Windows (`winget install GitHub.Copilot`), a scratch `COPILOT_HOME`, model `auto`, two turns at 1 premium request each, from a terminal, not from the service.

- **A turn is a process**, as with Codex and OpenCode: `copilot -C <dir> -p "<prompt>" --output-format json` prints JSONL events and exits; the last line is `{"type":"result","sessionId":…,"exitCode":…,"usage":{"premiumRequests":…}}`. `--resume=<id>` (or `--session-id <uuid>`, which also sets the id of a new session) goes on in the same session and appends to the same transcript. Non-interactive runs need `--allow-all-tools` (or `--allow-all`/`--yolo`) for any tool; `--no-ask-user` drops the `ask_user` tool, so a question is the text the turn ends with; `--no-auto-update` pins the binary.
- **The transcript is JSONL**: `<COPILOT_HOME>/session-state/<uuid>/events.jsonl`, next to `workspace.yaml` (`id`, `cwd`, `name`, timestamps). Persisted events: `session.start`, `session.model_change`, `user.message`, `assistant.turn_start`, `assistant.message` (`model`, `content`, `toolRequests`), `assistant.turn_end`, `session.usage_record` per model call (`inputTokens`, `outputTokens`, `cacheReadTokens`, `cacheWriteTokens`, `reasoningTokens`, `cost` in premium requests), `session.shutdown` (`accountingSnapshot` with `totalNanoAiu` and `totalPremiumRequestCost` for the whole session). Deltas and MCP status are `ephemeral` and only on stdout. A model call reported a prompt cache lifetime of 1800 s.
- **Usage, not limits**: the transcript carries what a session spent (AI credits as `totalNanoAiu`, premium requests), not what is left of the plan; the remaining budget is only in the interactive footer and `/usage`. `--max-ai-credits` caps a session.
- **The account folder is `COPILOT_HOME`** (config, `session-state/`, `session-store.db`, `hooks/`, `mcp-config.json`, plugins, logs), but not the sign-in: the OAuth token sits in the OS keychain under `copilot-cli`, and `gh auth token` is the last fallback, so a fresh `COPILOT_HOME` ran under the sign-in already on the machine. One identity per session needs `COPILOT_GITHUB_TOKEN` (a fine-grained PAT with the "Copilot Requests" permission or an OAuth token; classic `ghp_` tokens are refused), which beats every stored sign-in.
- **Instructions and skills**: with a scratch `COPILOT_HOME`, `copilot instruction list` in this repository showed only its `CLAUDE.md`, and `copilot skill list` only the built-in skills: `~/.claude/CLAUDE.md` and `~/.claude/skills` were not picked up. `--no-custom-instructions` drops the repository's files too.
The three points below are from `--help` and GitHub's docs, not run.

- **Hooks take the Claude format**: PascalCase events (`PreToolUse`, `PostToolUse`, `Stop`, `SessionStart`, …) with snake_case payloads and Claude tool names in matchers, from `<COPILOT_HOME>/hooks/*.json`, `.github/hooks/*.json`, a plugin's `hooks.json` and also the repository's `.claude/settings.json`/`settings.local.json`; `--plugin-dir` loads a plugin in the Claude Code format. `PostToolUse` and `SessionStart` can return `additionalContext`, `Stop` can block with a `reason` that becomes the next prompt.
- **MCP**: `--additional-mcp-config <json|@file>` adds servers for a run on top of `<COPILOT_HOME>/mcp-config.json` and the project's `.mcp.json`/`.github/mcp.json`; there is no strict mode, so the project's servers go off one by one with `--disable-mcp-server <name>`, and the built-in GitHub server with `--disable-builtin-mcps`.
- **Paths**: file access is limited to the working folder and the temp folder; a merge into the main checkout from a worktree needs `--add-dir <main checkout>` or `--allow-all-paths`.
