# Sessions, models, prompts, limits

Reference for sessions: how Even Keel launches `claude` and watches it.

## CLI and transcripts

- Sessions are the `claude` CLI (`--bg`, `agents --json`). The binary: `EVEN_KEEL_CLAUDE_BIN`, otherwise the standalone CLI `~/.local/bin/claude.exe` (outside Windows — `claude`), otherwise the binary of the newest VS Code extension version (an extension update deletes its folder).
- Transcripts are in `<account folder>/projects`. `claude agents`, transcripts, `sessions/<pid>.json` and `settings.json` are read for each account folder.
- `claude agents --json` (2.1.284) prints neither `pid` nor `status`, and `state: done` stays both for a live session after a turn and for a stopped one: a live process, `pid` and `busy`/`idle` come from `sessions/<pid>.json` entries with a live `pid` (`withLiveRecords`).
- Prompt cache freshness comes from the transcript: the lifetime (5 min or 1 h) by `usage.cache_creation` of the last response that wrote the cache (if both are present, 5 min is taken), counted from the first line of the last response.
- The progress feed on the page is the last 30 lines of the fold (`TranscriptFold`): texts and tool calls, API errors and human requests (`kind: 'prompt'`; without `isMeta`, tool results, `origin.kind` other than `human`, and client context blocks like `<ide_selection>`, `<pasted_content>` stays). The "Whole transcript" button is `GET /api/sessions/<id>/transcript`: the same fold without truncation (`whole`), with the full command in `detail` for Bash and PowerShell. For a live session the window reads further every 3 s with `?after=<how many lines it already has>`: fold lines are only appended, and the service folds the file anew each time (14 MB — ~150 ms). Requests do not go into the handoff on a limit.
- Questions and answers (BTN-101, `src/sessions/ask.ts`): a pending `AskUserQuestion` call is the session's open question, `SessionView.ask` (`tool_use` id and its questions); in the whole fold the call's line carries it as `line.ask`. Its `tool_result` with `toolUseResult.answers` becomes an `answer` line with `answers` (the question it answers and the answers by question text). A result without answers (the call was interrupted or failed when the session was stopped) leaves the question stray, and the next human prompt answers it: that prompt is an `answer` line too, its answers read back by `answersIn` from its `- "question" → answer` lines. Any new prompt clears the open question.
- A pending `AskUserQuestion` is not in the transcript (verified on CLI 2.1.296, 2026-10-12): the CLI writes the whole last message — the text before the call and the call — only together with the answer. Until then the session record says `status: waiting`, `waitingFor: "input needed"`, and the question is only in `block.questions` of `jobs/<id>/state.json` (`needs` is `answer: <question> (<labels>)`): the question text and the options with descriptions, without `header`, `multiSelect` or `preview`. `withJobFiles` reads it for a live waiting session (`blockedAsk`) and the monitor gives it as `SessionView.ask` when the transcript has none: the id is `job:<job id>:<hash of the questions>`, `unsaved: true`, every question is a single choice without a header — several options go through "Other" on the page, and `1, 3` in a tracker comment stays text. `claude stop` loses that message for good: after `--resume` the transcript has a synthetic `No response requested.` in its place, and the session sees neither its text nor its question.
- The reply prompt (`replyPrompt`, in `promptLanguage`) says where the answer came from (the page or the tracker), that the `AskUserQuestion` above was left without an answer and may have ended in an error or an interruption from the stop, then the `- "question" → answer` lines, the user's text and the list of files. For an `unsaved` question it says instead that the message with the call was lost and repeats the questions with numbered options before the answers. An empty reply is `answer.empty`. Files are saved first into `.temp/inbox/` of the task's folder (`src/sessions/inbox.ts`: safe names, no overwriting, a `.zip` unpacked with `tar -xf`, `unzip` as a fallback); the folder has its own `.gitignore` with `*`, so the worktree stays clean and cleanup after Done does not stall. How `--resume` treats an unanswered `AskUserQuestion` that did reach the transcript is not verified, so the prompt does not depend on it.
- `claude --bg --resume <id>` starts a copy under a new session id (the page shows it as a new chat with the whole history again) when the session is still running or, if its job `jobs/<job id>/state.json` is saved, when any flag is passed: such a session keeps its own options (model, permission mode, name, settings), and the CLI prints `note: … keeps its own saved options, so the flags you passed started a copy` (reason `own-options`, read from the 2.1.302 binary). So a reply or a limit resume passes only `--bg --resume <id> <prompt>` when the job is saved (`resumeArgs`): the session goes on in place with the options of its launch (verified live on 2.1.302, 2026-10-17), and a model label changed meanwhile applies only from the next launch. Without a saved job the flags are passed as at a launch. The dispatcher still looks for the resumed session by that id or, like after a launch, by the task name, the folder and the start time (`resumedAs`).
- `claude --bg` goes through the supervisor daemon (`claude daemon run`, on Windows the pipe `\\.\pipe\cc-daemon-…`). Stopping the service does not kill background sessions — they are children of the daemon.

## Model (`src/sessions/launch.ts`)

By the task label `Sonnet`/`Opus`/`Haiku` (case-insensitive, whitespace trimmed): `--model <alias>` on every launch — first, `--resume`, handoff, "New session"; `modelPrompts.<alias>` from `even-keel.config.json` is appended to the prompt if present. No label or two different ones — the model from the `model` config key (default `opus`; the second case logs a warning) and its prompt from `modelPrompts`. A session is never launched without `--model`: the CLI would take the model from `settings.json`, which `/model` rewrites in any editor on the same account.

## Extra tools (BTN-74, `src/tools/`)

- The "Trim the tools" switch on `/settings`, the Sessions group (`chain/trim`, `ChainState.trimTools`, on by default): chain sessions are launched with `--settings <JSON>` (`chainSettings`) — `syncClaudeAiSkills` and `syncClaudeAiPlugins` are off, skills from the config's `hiddenSkills` (default `DEFAULT_HIDDEN_SKILLS`) are `user-invocable-only`, that is, only through `/name`. It applies on every launch: first, `--resume`, handoff. The settings files are not changed, `--settings` affects only that launch (verified on CLI 2.1.290: `--bg` passes it through, claude.ai skills do not go to `.trash`).
- With the switch off, `--settings` still goes: it carries `autoMemoryDirectory`, the shared memory folder (`docs/accounts.md`), and `disabledMcpjsonServers` (below).
- The CLI looks for `.mcp.json` in the parent folders as well, so a session in a worktree inside the main checkout sees the servers of the main checkout's `.mcp.json`, even an untracked one, but not their approval in `settings.local.json`. Such a server is "Pending approval", and a `--bg` session hangs on the approval dialog before its first turn (BTN-86, 2026-10-10). So every chain session in a worktree gets the servers of `<repo>/.mcp.json` that its own `.mcp.json` lacks in `disabledMcpjsonServers` (`strayMcpServers`, whatever the switch). Verified on CLI 2.1.296: `claude --settings <file> mcp get <name>` in the worktree shows "Rejected" instead of "Pending approval".
- A stdio MCP server of a plugin that failed to start is written by the CLI to `<account folder>/mcp-needs-auth-cache.json`, and sessions skip it without trying until the entry expires: `"Skipping connection (recent failure cached; retries automatically in 15 min, or edit the plugin config to retry now)"` (BTN-159, CLI 2.1.302). The entry is `"plugin:<plugin>:<server>": { "timestamp": <ms>, "id": "<16 hex>" }`, optionally with `ttlMs`; without it the wait is 15 minutes, an entry up to a minute in the future counts too. `id` is a hash of the server's normalized config (command, args, the plugin's own `env`, not the session's environment), so an edit of the plugin's `.mcp.json` lifts the wait while a fix of the credentials in `settings.json` does not. The same file holds the claude.ai and HTTP servers awaiting sign-in (`"claude.ai Linear": { "timestamp", "id": "mcpsrv_…" }`, 4 hours); Even Keel reads only the plugin entries. `claude mcp list` tries the server again whatever the entry and rewrites it on a failure. Even Keel reads the file of the active account (`readFailures`, `failedUntil` in `src/tracker/mcp.ts`) on every check of `McpCheck`, and before each launch of a chain task: while the project's tracker server is cached as failed, the chain launches nothing and waits, and the state has `mcpFailed` with the end of the wait for the `McpBanner` banner. A fix session of a red main does not wait: it needs no tracker.
- A session that hangs on any startup dialog is visible only in its job file: `claude agents --json` shows `state: blocked`, as for a question, while `<account folder>/jobs/<id>/state.json` gets `tempo: blocked` and in `needs` what the dialog asks for: for a known one, e.g. `approve 1 new project MCP server (strata) — attach to respond`, otherwise `open this session to continue setup` with `detail: "stuck on a startup dialog"` from the CLI's 45 s watchdog (2.1.296). A blocked session without a live `sessions/<pid>.json` has not begun its first turn, so Even Keel reads that file for such sessions (`withJobFiles`, `blockedOn`), puts `needs` into `SessionView.startupDialog`, the panel says why the session stands and the service log has a `sessions: … hangs on a Claude Code dialog` line. Such a session is not mid-turn: "New session" and "Skip" stay available. The dialog itself cannot be seen from a terminal: the service's daemon is in session 0.
- `skillOverrides` of the project (`.claude/settings.json`) and of the main checkout (`.claude/settings.local.json`, which overrides the project one, as in the CLI) override the list. A session in a worktree does not read the main checkout's `settings.local.json` — its `skillOverrides` reach it only through `--settings`.
- The "What sessions get" page is `/tools?projects=A,B&diff=1` (`web/src/tools/`); without `projects` the first two chain projects are selected, so the matrix is not squeezed. The project page has a line with the number of problems and a link. The project choice is the same list as on `/stats` (`web/src/ui/ProjectList.tsx`); at the top are the problems merged across projects (won't reach the session, claude.ai skills, MCP servers that failed or don't make it into the worktree, accounts), below is a "setting × project" matrix by section with the result for the session and level marks; `diff=1` ("Only differences") shows only the rows where projects differ; the logic is `web/src/tools/matrix.ts`. Per-project data is `GET /api/projects/<key>/tools` (`readToolsView`): a table of settings by level (user, project, local, Even Keel) with the result for the session, MCP servers from settings (`.claude.json`, `.mcp.json`, plugins) marked "not in worktree", the difference between the accounts' `settings.json` and the global one (key names only — `env` holds secrets) and what the project's last session received: the start of its transcript (first 400 lines; the worktree folders `<repo>--claude-worktrees-*` first) — `skill_listing`, `prompt_snapshot.tools`, `deferred_tools_delta`.

## Checkpoint threshold (BTN-86)

The `checkpoint` plugin's hook (`plugins/checkpoint/hooks/context-checkpoint.mjs`, the rules in `nudges.mjs`) asks a session for a handoff by context size. The first nudge is at 200k, the next every 50k up to 250k and every 25k past it. From 100k of context on, the hook asks the service about its session: `GET /api/sessions/<id>/checkpoint` → `{ project, task, handoffs, first, source }`, 404 for a session the chain did not start. An answer is kept for an hour in the hook's state file, a failure is retried in 5 minutes, and without an answer the hook runs on its constants and `CHECKPOINT_*` variables. Environment variables are not used to pass the answer: whether they reach a session through `claude --bg` and the daemon was not checked.

- `handoffs` (`handoffsOf` in `src/chain/launches.ts`) is the number of the task's sessions started by `checkpoint`, `restart` or `relay`, up to and including this one. From the third on the hook is silent below the hard threshold of 300k: on tasks with many handoffs most of them lost money (CBL-596: 12 handoffs, $17.5 spent, $5.3 saved).
- `first` with `source: "calibrated"` or `"config"` replaces the hook's own first threshold; `"default"` leaves it alone.
- Calibration (`src/stats/checkpoint.ts`, the query `CHECKPOINT` in `src/stats/reader.ts`): `first = base + (note + recovery) / (cache read price × 40 requests)`, rounded to 1k and kept within 150–250k. `base` is the median context of the project's checkpoint successors at their 15th main-thread request, `note` the median spend of a session from its first write of `.temp/handoff.md` to its end, `recovery` the median spend of a successor before its first edit, the price is that of the successors' most frequent model in Tally's `model_prices`. The work left, 40 requests, is a constant, about the lower quartile of what was measured: a measured remainder depends on the threshold itself (a higher one shortens it and pulls the threshold up, the successors' recovery requests inflate it and pull down). The hard threshold and the limit of handoffs are not calibrated.
- It applies once the project has 20 checkpoint successors and 50 sessions that went over 150k; until then, and without statistics, the threshold is 200k. `stats.checkpointTokens` in the config pins it for all projects and switches the calibration off.
- Measured on 2026-10-10: CBL — base 73k, note $0.18, recovery $0.64, 168 successors → 176k; BTN — 79k, $0.18, $0.69, 32 successors → 187k. Why 150k was too early: with a 1 h cache write at $8/M against a read at $0.2/M, rebuilding the context costs as much as re-reading it 40 times, and of 163 CBL handoffs at 150k 93 lost money ($177 spent, $132 saved).

## Prompts (`src/sessions/prompt.ts`)

Assembled strictly: a value in the launch and handoff prompt goes through `fill`, and an empty or non-string one is an assembly error — the chain pauses with it instead of going into a session with a blank space. `modelPrompts` is passed as is, with no substitutions: `{name}`, `{{name}}`, `${name}` is a config error. A project whose tracker has a project key in the config (`github`, `linear`) gets the line "Tracker: GitHub, project octo-org/abc." after the launch or handoff text, brief or not (`withTracker`): with the brief off the prompt otherwise carries only the task id, and the GitHub skill fell back to `origin`, which may be missing or point elsewhere (BTN-143). A project's `prompt` (BTN-97, `withProjectPrompt`) goes under the heading "Instructions for this project:" after the brief and before the unattended rules and the model prompt, into the prompt of a new session only — the first launch and a handoff; `--resume` and a reply continue a session that already has it. It is free text and is not checked for substitutions; an empty one is no prompt. The session that fixes a red `main` without a task (BTN-115, `docs/chain.md`) has no brief: its prompt is `fixPrompt` — the report of what broke, the worktree, the branch and its rules — with the project's `prompt` after it, and a handoff of it carries the report again (`withReport`). The prompt language is `promptLanguage` (`src/chain/prompts.ts`, see `docs/web.md`).

## Limits

- Each account has its own: `claude -p /usage --output-format json --no-session-persistence` in its folder every 5 minutes (a local command, spends no quota) and a statusline snapshot (marked with the session's `configDir`; without the mark — the global account); the fresher one is taken.
- Do not poll more often: the server answers `/api/oauth/usage` with 429, the VS Code extension panel polls it with the same token, and after a 429 the CLI (2.1.286) does not query this token for ~45 min.
- With an expired access token or after a 429, `/usage` returns no limits (the subscription line is there, the window lines are not) — that is "no data" (`stale`), not an error. A `/usage` answer is accepted whole or not at all: both window lines with a percentage and a reset (`0% used` without a reset — the window has not started).
- Polling continues only if the answer says outright `num_turns: 0` and `total_cost_usd: 0`, otherwise it is switched off until restart. An unreadable answer or switched-off polling is shown by the page as a banner (`UsageBanner`).
- While a window is used up, the next task is not started: the chain waits for the reset (`limitUntil`) and continues by itself.
- A limit on a running session whose text gives no reset time (the `wrap_up` warning) takes it from these limits once they are newer than the limit (`docs/chain.md`, exception 1).
