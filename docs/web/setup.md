# Page: the first run's setup and the project wizard

The Repository step shows whether Claude Code already trusts the checkout, or that trust will be saved before the session starts. There is no trust control in the wizard or the Sessions tab. Launch/resume integration is in [sessions](../sessions/agents.md#claude-folder-trust-ekr-59).

The first run's setup (BTN-310): `/setup?step=<step>` (`web/src/pages/Setup.tsx`, the steps and their addresses in `setupSteps.ts`), where `/` sends the page while `firstRun` holds (`src/setup.ts`: `tally` is `null` and there is no project; with projects and no stats it sends to the stats step alone). The steps, each written at once as the shared settings (`settings` with the form in force as `base`), never held in a draft: Language — `language` and `promptLanguage` as two rows, "Page" and "Session prompts", each an `English | Русский` pick (a page language picked sets both and the page turns at once; "Next" writes the language shown when `language` is still `null`); Git (`SetupGit.tsx`, BTN-731, BTN-886) — first "Use git?", two cards, Yes and No, each with a line of what it gives, the pick written at once as `defaultGit` (`gitChoice` in `setupSteps.ts`: the setting once given, before that Yes where git starts and nothing where it does not; "Next" writes the Yes shown when `defaultGit` is still `null`); No goes on to the next step at once and shows nothing of git, the dot's summary "Without git". Yes adds two sections in the Agent step's look: "Git", the installed version (`EvenKeelState.git`, `GitSetupView` from `gitSetup` in `src/git/setup.ts`, read at the service's start and on `git/check`) or, when `git --version` does not start (`GitResult.missing`, an ENOENT of `execFile` or, on macOS only, a nonzero exit containing `xcrun: error: invalid active developer path`), the install command of the package manager the service finds on its own `PATH` without starting it (`GitSetupView.install` from `gitInstallCommand` and `onPath`, EKR-54: winget on Windows; always `xcode-select --install` on macOS, regardless of Homebrew; the first of apt-get, dnf, pacman, zypper, apk on Linux; none found — no command), always the git-scm.com download page of the platform under it (`gitDownload`), alone when there is no command, and "Check again" beside the first of the two. On Windows a line above them says what makes Even Keel see a git installed since (`GitSetupView.restart`, `windowsStart` in `src/updates/control.ts` from the parent process): the tray's Restart or a restart of the Windows service by its name, after which node starts with `PATH` read anew (EKR-57) and checks git by itself, or, for node started in a terminal, a start from a new terminal, since the old one keeps its `PATH`. Linux and macOS have no such line: their package managers install into a folder already on the service's `PATH`, and "Check again" sees it. On macOS a note next to the command says that only Command Line Tools are installed, Xcode from the App Store is not needed, and full Xcode with an unaccepted license needs `sudo xcodebuild -license accept`; that license failure remains an ordinary git error. Even Keel never installs git itself. "Name and e-mail for commits", shown once git starts, two fields filled with `user.name`/`user.email` as git reads them in the service's home folder, and "Save", open once both are filled and one changed, which sends `git/identity` (`git config --global`, as the user the service runs as). "Next" waits for `gitStepReady`: No, or Yes with `gitReady` — a version, a name and an e-mail; Agent (`SetupAgent.tsx`, BTN-603) — three sections in the project wizard's look (`project-add__step`, each with a `StepDot`): "What runs the sessions", a card per provider with its icon (`AgentIcon`) and one line, "installed <version>" or "not installed" (`CliCopyView.installed`, `VersionWatcher.installedOf`), no buttons, the card a pick stretched over it; "<Agent> version", `CliSourceChoice` (`web/src/layout/CliSource.tsx`) — `Yours | Checked` radios for the chosen provider's `cli`, Checked through the consent dialog and `cli/download` with `CliProgress` under it, without the CLI the install `CommandBlock` and "Check again"; "<Agent> account", "+ Add" in the heading's aside (opens the add dialog over the step, `useOpenAdd`, `docs/accounts.md`, "Adding") and the provider's accounts as a table: a radio mark that writes `accounts.<provider>`, the name, and on the right "needs a sign-in" with "Sign in" (sends `account/renew`), "checking…" or Copilot's note. Without a CLI or a copy there is no "+ Add", only a note that the sign-in goes through the CLI; a copy that ends downloading with no account opens the add dialog by itself (BTN-542). "Next" waits for `agentReady` (`setupSteps.ts`): something to run on (`cliRunnable`: the CLI on Yours, the copy on Checked, even downloading) and an account. Tracker (`SetupTracker.tsx`) — first the built-in tracker's card, with nothing to connect (BTN-769), then a card per tracker kind (Huly, GitHub, Linear), its profiles by the name after the kind's (`profileShortName`) with their state, "Edit" on a refused or unreachable one, and "Connect" or "Add another", which opens `ProfileDialog` fixed on that kind; Updates — `updates.check` on or off as cards, the service holding the check while `firstRun` holds (`UpdateWatcher.enabled` in `src/service.ts`), so it is asked, not on by default; Stats — `StatsStep` (`docs/stats.md`), the picture beside the lead, the facts under both, whose choice ends the first run and opens the project wizard. There is no mark of a setup done: the stats go last because choosing them is the end.

The setup walks in the wizard's own frame (BTN-346, `WizardFrame` and `WizardFoot` in `web/src/pages/WizardFrame.tsx`, `wizard.css`; the pure part — `stepMarks`, `filledShare`, `listSummary` — in `wizard.ts`), meant for the project wizard too: one column of at most 760 px in the middle of the page, its head ("Set up Even Keel" and that anything can be changed in Settings), then the steps as dots on a line, each a link — a done one filled with a check and, under its label, what it holds (`summaryOf`: the languages, "Git 2.47 · John Doe", "Claude Code · john" with the e-mail cut at `@` by `accountShortName`, the first tracker profile and how many more, the update choice, the stats mode), the current one a ring, one without its answer empty wherever it stands; the line is filled up to the current dot, and the last dot, "First project", leads to the project wizard. Under the line the step is one card with its title, and its foot: "← Back" a quiet link at the left, at the right the primary button named after the next step ("Next: Tracker →"); an optional step (`OPTIONAL_STEPS`: Tracker, Stats) has "Skip for now" instead when there is nothing to go on with — the tracker without a profile, the stats (to the project wizard; not offered once there is a project, whose `/` would send back to the stats). Enter presses the primary button unless the focus is on a control or a link or a dialog is open. A step slides in (`--motion-appear`), the dots and the line move with it, choice cards rise under the pointer and the picked one has the accent's edge and a check in its corner; none of it with reduced motion. Up to 760 px the dots lose their labels and the current step's name stands under the line, the cards go one a column. A dot is the shared `StepDot` (`DotMark`): the line's done/current/future, and the project wizard's card dots, which add passed (green with a check) and failed (red with "!"). While `/setup` is open the header shows only the logo and the gear: no Stats link, chain, account or limits (`Header.tsx`).

Where the setup stopped (BTN-1023): a step is done by its answer, not by its place, and one function says so for both the line's checks (`setupLine` → `WizardStep.done` → `stepMarks`) and the step to come back to (`stepAnswered` and `setupStop` in `setupSteps.ts`). Language — `language` set; Git — No, or Yes with `gitStepReady` (the Yes shown before a pick is no answer), or a skip; Agent — `agentReady` only, so a provider without an account has no check; Tracker — a profile or a skip; Updates — gone past, since `updates.check` is on by default; Stats — `tally` set or a skip. A skip and the update step are kept in the global setting `setupPassed` (`docs/settings.md`), written by "Skip for now" and by the update step's pick or "Next", so a skipped step is not offered again. While `firstRun` holds and some step has no answer (`unfinishedStep` in `web/src/pages/SetupAsk.tsx`), every way into adding a project asks "Set Even Keel up?" first (`AddProjectLink`: Home's "+ Add project" and its empty state, the demo's three "Connect your own"; `SetupGate` on `/projects/add` opened by its address): Yes goes to the first step without an answer, No closes the question and leaves the person where they were — on the wizard when they came by its address. The setup's own ways into the wizard (the line's last dot, the stats step's end) carry `FROM_SETUP` and are not asked. Every step answered — the links go straight to the wizard.

A project without git (BTN-883, `docs/chain/worktrees.md`): the wizard's Repository step starts with a `Segmented` "In a git repository / Without git" (`WizardFields.git`; it starts on `defaultGit`, the setup's answer, and before one on "Without git" when git does not start). Without git the step is titled "Folder", its field may be blank or name a folder that does not exist, and `checkRepo` asks git nothing: a blank folder passes with `repo.root` = the `projects` folder Even Keel will make the project's own in (the id is not known before the add, and `trusted` is `null`), a typed one is refused only when it is another project's (`wizard.folderTaken`). Tasks' folders is then one line with no choice, and the summary shows the folder and "One folder for all tasks". The setup's Git step gets "Skip for now" while it is held — nothing picked, or Yes with git not ready (`gitHeld` in `Setup.tsx`, `git` in `OPTIONAL_STEPS`). `git.missing` and `git.noIdentity` come only from git calls, which a project without git never makes: with No and no git project nothing on the page asks for git. In the project's settings the Repository tab is `PlainRepoTab` and "Check and CI" one line.

Adding and removing a project (BTN-118): the wizard is `/projects/add` (`web/src/pages/ProjectAdd.tsx`, pure logic in `projectWizard.ts`); the home page sends there by itself when the config has no projects and no `configError`, otherwise it opens by "+ Add project" next to the title. The steps (BTN-197) are Agent (BTN-310) → Repository → Tracker → Project → Tasks' folders, all shown at once. Since BTN-344 it walks in the setup's `WizardFrame`: in the first run (no project yet) under the setup's head and step line, as its last step "First project", with "← Back" to the stats; standalone, with its own head and no line. Each step is a settings `Section` card (short fields as `Row`s, the folder full width, no lines between cards) whose head leads with a `StepDot` (`stepChecks` in `projectWizard.ts` over `checkMarks` in `wizard.ts`): empty — not filled in, an accent ring — the first such step, green — its check passed, red — it failed, the reason under its field (an entry's refusal on the card of the field it names: the key on Tracker for Huly, on Project for the others; `wizard.trackerShared` under the milestones). Tasks' folders is a `Segmented` "Own folder per task | Permanent folders" with a line saying what the pick means and, for permanent ones, their count. Under the cards "What will be created" (`ProjectSummary.tsx`, a `Card` with a `FactList`, standalone so it can go) shows the name and key, the tracker and its place (`trackerPlace`), the main branch, the folder, a task and its branch (`taskExample`: `KEY-12 → key-12/task`) and the folders, live; then the foot: what the add still misses (`missingOf`, the first reason in the order of the steps, naming its card) with "Check again", and "Add project". Agent: a `Select` of the providers, the shared one first in force and labelled so; the project's `provider` is written only when another one is picked (`withNewProject`), and under it the same readiness as the setup's (`AgentReady`) — its "Add an account" opens the add dialog over the wizard, which stays as it is; the wizard's fields live in the module (`kept` in `ProjectAdd.tsx`) until a project is added, so leaving the page loses nothing typed. The readiness does not hold the add. Repository: the folder; once found, its line says the main branch with a `[change]` link that opens the branch field (it opens by itself for a checkout with no current branch and for a branch the repository lacks, and stays open while that branch is retyped). Tracker (`web/src/pages/WizardTracker.tsx` over the shared `TrackerFields.tsx`): a `Select` of the tracker profiles from Access, each with its kind's icon, and "Add profile" as its last option, which opens `ProfileDialog` and picks the saved profile; first in it "Built-in (no account)" (BTN-769, `switchBuiltin`): no profile and no place, only the project's own key, and it is picked at the start when there is no tracker profile (`firstFields`); a single tracker profile is picked at the start otherwise. Under it, in its strip, the profile's state (signed in as whom, refused), then the fields of the profile's kind by its shape (`shapeOf`: `key` — Huly's project identifier, `place` — GitHub's `owner/name` with a free task prefix, `within` — Linear's team key and an optional project). The fields suggest the tracker's projects (`profiles/projects` with the typed text, 300 ms after the last keystroke, a `SuggestField` listing each key with its name), and an exact match fills the key, the value and the name (`pickProject`); the tracker's answer, the check's open tasks included, is the strip under the tracker project, its room kept while empty. Project: the name always, the key (Linear's team key, GitHub's task prefix) where the tracker does not give it. A field the user typed is not overwritten by a suggestion (`WizardFields.typed`, `typedIn`); switching the profile clears only the suggestions of the last kind (`switchProfile`). Switching the profile must not move the fields below: the empty `Select` keeps a line's height, a field head is as tall without its "?" as with it, and the folder's lines stay through a check of other fields (they depend on the folder and the branch only). 600 ms after the last keystroke, and on "Check again", the page sends the draft (`ProjectDraft`: repo, branch, key, name, tracker, tracker project, profile — `null` for the kind's default profile, slot count — 0 is a worktree per task, milestones, provider — `null` for the shared one) to `POST /api/project/check` (`checkDraft` in `src/projects/check.ts`): the folder is a git repository and not another project's, the branch exists, the entry passes `parseConfig` as the project would be added, the tracker answers `chainTasks` for the tracker project (its open tasks are counted; missing variables are named), and — for a project on any agent, since a task's run can give it to Claude (BTN-429, BTN-983) — the folder is trusted in the global `.claude.json` or in that of the shared Claude account's folder, the only one `claude` started with its `CLAUDE_CONFIG_DIR` writes the dialog to (`isTrusted`, BTN-300; the answer retains the service machine's platform and user for compatibility). The Repository card shows `wizard.trusted` when trusted and `trustTexts().pending` otherwise. Even Keel automatically marks the project's checkout as trusted in Claude Code before each background launch or resume, using the selected account. There is no trust switch, warning or command block in the wizard or the project's Sessions settings. A chain paused on `claude.untrusted` or `claude.trustWriteFailed` offers Check again and resume; retry saves trust again, after any damaged or unwritable account configuration is fixed.

The wizard's kept draft contains only changes made through its controls (BTN-1024, `projectWizardDraft.ts`). Each
visit overlays them on `firstFields` from the current state, so untouched Git and tracker-profile defaults follow
the setup again. A manual profile choice keeps both its id and tracker kind together, including Built-in. Repository
suggestions are recomputed rather than saved as manual edits. Failed checks or adds retain the draft; only a successful
add clears it. A browser reload clears the module's memory.

A blank branch is filled from the checkout's current one; for `place` the tracker's value comes from the repository's remotes (`repo.suggested`: the first remote the adapter's optional `projectOfRemote` recognises — GitHub, a github.com remote), the key and the name from the repository's name (`keyOfFolder`, `suggestOfRepo`). A tracker project another project reads is refused as `wizard.trackerShared` until the two split it by milestone (BTN-306): the refusal opens "Only tasks in milestones" under the Project step (it stays open while the milestones are typed), the draft's `milestones` become the new entry's `chain.requiredMilestones`, and `yieldedMilestones` (`src/config-form.ts`) takes them out of each other project's required ones or, when it requires none, adds them to its excluded ones — `withNewProject` writes that into their entries, and the check names those projects (`ProjectCheck.yields`) in a line under the field. "Add" is open once the repository, the entry and the tracker pass (`readyToAdd`) — trust is informational and does not block adding the project; it sends `project/add`, which starts the creation job (below), and the job's window opens the project once it is made. Removal is `ProjectRemove.tsx` at the bottom of the project settings' Repository tab: a confirm, then `project/remove`; `removalBlock` (`src/projects/removal.ts`) refuses while the project's chain runs or waits in the queue, a live session was launched for its tasks or works in its folders, a task holds a place (`held`) or cleanup leftovers remain, and the notice lists each reason. A first start without a config file starts with no projects, and the page opens the wizard.

Entry refusals are routed by code (`entryField` in `projectWizard.ts`), shared by the field messages and step dots. Only `wizard.keyShape` and `wizard.keyTaken` belong to the key (Tracker for the `key` shape, Project otherwise); `wizard.trackerPlace` belongs under the tracker project's field, and `wizard.trackerShared` under milestones. Blank required keys and tracker projects remain neutral: the footer's `missingOf` names what is missing.

Each card changes only with what it depends on (BTN-737). The folder's lines hold while the folder and the branch do (`repoCheck`); the tracker's answer holds while its `trackerBasis` (`projectWizard.ts`) does — the tracker, the profile, the tracker project as the adapter reads it (Linear: the team from the value or else the key) and the milestones; the key counts only for the `key` shape, where it is the tracker project. While it holds, the page sends the next check with `askTracker: false`, `checkDraft` gets `{ tracker: false }` and does not reach the tracker, and the page keeps the answer it has, its dot and its strip included. So the name, a free prefix, the folder, the branch, the agent and the slots never re-ask the tracker. "Check again" drops the held answer and asks it anew; a return to the page does not. The Project card still waits for the fresh check: its entry depends on the key and the name.

`project/add` rechecks the repository through the same `checkRepo` as `project/check` before writing anything
(`src/projects/add.ts`). A repository refusal returns its notice and leaves the config and profile links unchanged;
a folder inside a repository is stored as the repository root. Config validation still checks the key and tracker
fields; adding does not repeat the tracker's network check.

The folder field (BTN-744): `checkRepo` expands a leading `~` (`~/…`, on Windows also `~\…`) to the service user's home
(`expandHome`, `src/projects/folder.ts`; `~user` and `$HOME` stay as typed), refuses a relative path (`wizard.relativePath`)
and a folder that does not exist (`wizard.noFolder`, no git output, no button) before it asks git. The config gets git's
absolute root.

On Windows `expandFolder` also expands `%NAME%` from the service process's environment, case-insensitively, for
checking, adding and the repository-creation button. Tracker-profile variables do not override these values.
Expansion is a single pass after `~`; unknown or empty variables stay literal, and an unresolved leading variable
gets `wizard.noFolder` rather than the relative-path notice. Linux/macOS treat percent signs literally; `$NAME` and
`$env:NAME` are never expanded. Saved absolute roots are independent of later environment changes.

Git in the wizard (BTN-731). A folder that is not a repository (`wizard.notRepo`) gets "Make it a repository" under its
refusal, a repository with no commits (`wizard.noCommits`) "Make the first commit"; both send `git/init` with the folder
and the branch field (blank — `DEFAULT_BRANCH`), then check the draft again. `initRepository` (`src/git/setup.ts`)
refuses a missing folder (`wizard.noFolder`), a branch git would not take (`wizard.branchName`) and git without a name
or e-mail (`git.noIdentity`, whose fix opens the setup's Git step) before touching anything; then `git init -b <branch>`,
or for an unborn branch `git symbolic-ref HEAD refs/heads/<branch>`, and `git commit --allow-empty -m "Initial commit"`.
A repository with commits is left as it is. When git does not start at all, `checkRepo` answers `git.missing` instead
of `wizard.notRepo`, and so does any git call of the chain through `requireStarted` (`requireBranch`, the worktree
steps): the chain pauses on that notice, whose fix is "Check again and resume".

## Where the repository comes from (BTN-1048)

The Repository card (`web/src/pages/WizardRepo.tsx`, `RepoStep`) has, under the git mode, a `Segmented` "Source":
Clone | New repository | Existing (`WizardFields.source`, `ProjectDraft.source`). The draft starts on Clone, on
Existing while git has no name or e-mail (`firstFields`). Git that does not start closes "In a git repository" with the
reason and a link to the setup's Git step; git without a name and e-mail closes Clone and New repository with
`NoticeFixButton` of `git.noIdentity`. Existing is the old folder field with its "Make it a repository".

- **Clone** — "Remote address" (`ProjectDraft.remote`). The check asks the remote first (`git ls-remote --symref`,
  `sharedRemoteReader` in `src/git/remote-run.ts`, held for a minute per address); a text that is no address
  (`remoteShaped`: a URL, `[user@]host:path` or a full local path) is refused as `git.remoteShape` without asking git
  (BTN-1087). A refusal is `git.remoteShape|remoteDenied|remoteNotFound|remoteNetwork|remoteFailed` in one line under the
  field (`remoteRefusal` in `web/src/pages/remoteRefusal.ts`): the address cut to 48 characters, git's own words behind a
  `HelpTip`. An answer is "The remote answered" with the main branch and `[change]`, which opens the branch field right
  under the remote (under the path or the folder for the other sources). A branch the remote lacks is no refusal: the default branch is cloned and the wanted one is
  made when the entry is written.
- **Folder** (Clone, New repository and "Without git") — Even Keel's projects folder (`projectsDir()`, the data
  folder's fixed `projects/`, no setting) as muted text cut from the left, then the name's field; blank, the name
  suggested (`checkPlace` in `src/projects/place.ts`: the remote's name, else the project's name or key; a taken one
  gets the branch, then `-2`…). "another folder…" turns it into a full path (`ProjectDraft.repo`). Under it the
  folder's state (`FolderPlace`): free — made on creation, empty, or filled; a clone refuses a filled folder
  (`wizard.folderFilled`), a new repository says what goes into its first commit (files and size, counted up to a
  ceiling; `measureFolder` asks `git ls-files --others --exclude-standard` against an empty temporary repository, so
  every `.gitignore`, `info/exclude` and `core.excludesFile` leaves out what `git add -A` would), a folder that is a repository already is `wizard.alreadyRepo`. A clone of the same remote and branch already
  in the projects folder, which no project has, is offered with "Use it", which switches the source to Existing on it.
  The page sends `folder` only while no path is typed, and `checkDraft` routes a draft "Without git" to `checkPlace`
  only when it has `folder`: an older page keeps the own folder by id.

"Add project" sends `project/add`, and `settings.add` (`src/service/hosting.ts`) builds the steps
(`creationPlan`, `src/projects/creation.ts`) and starts them as a job (`stepJobs`, `src/jobs/runner.ts`; one live job
of a kind; `EvenKeelState.jobs`). The steps: the folder, the clone (`cloner`, `git clone --progress`, its stage,
percent, size and speed parsed by `parseProgress`) with its LFS files shown once a clone starts filtering them, or the
new repository's first commit (`git init -b <branch>`, `git add -A`, the commit), the project's entry, Claude Code's
trust for a folder Even Keel made, and the wait for the project's packages. A refused draft starts no job: the check is
repeated first.

The window (`JobWindow.tsx`, the add-package dialog's frame, not tied to the wizard: the job's `kind` names its steps,
and adding a machine to a project takes it too, BTN-993) shows each step's state, a clone's progress bar and figures,
the failure with its fix and "Retry" (`job/retry` runs the failed step again, the done ones are not repeated), and
"Cancel" (`job/cancel`): until the entry is written it aborts the step and removes only what the job made — the folder
it created, the contents of an empty folder it filled, the `.git` it made in a filled one. Once the entry is written
(`keptAfter`) the project stays: the note says so, and the button is "Open the project", which drops the job without
undoing anything. Esc does not close the window. A finished job keeps its window until "Open the project"
(`job/close`), which also removes the demo when asked and clears the kept fields.
