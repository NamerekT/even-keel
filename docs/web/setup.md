# Page: the first run's setup and the project wizard

The first run's setup (BTN-310): `/setup?step=<step>` (`web/src/pages/Setup.tsx`, the steps and their addresses in `setupSteps.ts`), where `/` sends the page while `firstRun` holds (`src/setup.ts`: `tally` is `null` and there is no project; with projects and no stats it sends to the stats step alone). The steps, each written at once as the shared settings (`settings` with the form in force as `base`), never held in a draft: Language — `language` and `promptLanguage` as two rows, "Page" and "Session prompts", each an `English | Русский` pick (a page language picked sets both and the page turns at once; "Next" writes the language shown when `language` is still `null`); Git (`SetupGit.tsx`, BTN-731) — two sections in the Agent step's look: "Git", the installed version (`EvenKeelState.git`, `GitSetupView` from `gitSetup` in `src/git/setup.ts`, read at the service's start and on `git/check`) or, when `git --version` does not start (`GitResult.missing`, an ENOENT of `execFile`), the install command of the package manager the service finds on its own `PATH` without starting it (`GitSetupView.install` from `gitInstallCommand` and `onPath`, EKR-54: winget on Windows; brew, otherwise `xcode-select --install` on macOS; the first of apt-get, dnf, pacman, zypper, apk on Linux; none found — no command), always the git-scm.com download page of the platform under it (`gitDownload`), alone when there is no command, and "Check again" beside the first of the two. On Windows a line above them says what makes Even Keel see a git installed since (`GitSetupView.restart`, `windowsStart` in `src/updates/control.ts` from the parent process): the tray's Restart or a restart of the Windows service by its name, after which node starts with `PATH` read anew (EKR-57) and checks git by itself, or, for node started in a terminal, a start from a new terminal, since the old one keeps its `PATH`. Linux and macOS have no such line: their package managers install into a folder already on the service's `PATH`, and "Check again" sees it. Even Keel never installs git itself. "Name and e-mail for commits", shown once git starts, two fields filled with `user.name`/`user.email` as git reads them in the service's home folder, and "Save", open once both are filled and one changed, which sends `git/identity` (`git config --global`, as the user the service runs as). "Next" waits for `gitReady`: a version, a name and an e-mail; Agent (`SetupAgent.tsx`, BTN-603) — three sections in the project wizard's look (`project-add__step`, each with a `StepDot`): "What runs the sessions", a card per provider with its icon (`AgentIcon`) and one line, "installed <version>" or "not installed" (`CliCopyView.installed`, `VersionWatcher.installedOf`), no buttons, the card a pick stretched over it; "<Agent> version", `CliSourceChoice` (`web/src/layout/CliSource.tsx`) — `Yours | Checked` radios for the chosen provider's `cli`, Checked through the consent dialog and `cli/download` with `CliProgress` under it, without the CLI the install `CommandBlock` and "Check again"; "<Agent> account", "+ Add" in the heading's aside (opens the add dialog over the step, `useOpenAdd`, `docs/accounts.md`, "Adding") and the provider's accounts as a table: a radio mark that writes `accounts.<provider>`, the name, and on the right "needs a sign-in" with "Sign in" (sends `account/renew`), "checking…" or Copilot's note. Without a CLI or a copy there is no "+ Add", only a note that the sign-in goes through the CLI; a copy that ends downloading with no account opens the add dialog by itself (BTN-542). "Next" waits for `agentReady` (`setupSteps.ts`): something to run on (`cliRunnable`: the CLI on Yours, the copy on Checked, even downloading) and an account. Tracker (`SetupTracker.tsx`) — a card per tracker kind (Huly, GitHub, Linear), its profiles by the name after the kind's (`profileShortName`) with their state, "Edit" on a refused or unreachable one, and "Connect" or "Add another", which opens `ProfileDialog` fixed on that kind; Updates — `updates.check` on or off as cards, the service holding the check while `firstRun` holds (`UpdateWatcher.enabled` in `src/service.ts`), so it is asked, not on by default; Stats — `StatsStep` (`docs/stats.md`), the picture beside the lead, the facts under both, whose choice ends the first run and opens the project wizard. There is no mark of a setup done: the stats go last because choosing them is the end.

The setup walks in the wizard's own frame (BTN-346, `WizardFrame` and `WizardFoot` in `web/src/pages/WizardFrame.tsx`, `wizard.css`; the pure part — `stepMarks`, `filledShare`, `listSummary` — in `wizard.ts`), meant for the project wizard too: one column of at most 760 px in the middle of the page, its head ("Set up Even Keel" and that anything can be changed in Settings), then the steps as dots on a line, each a link — a done one filled with a check and, under its label, what it holds (`summaryOf`: the languages, "Git 2.47 · John Doe", "Claude Code · john" with the e-mail cut at `@` by `accountShortName`, the first tracker profile and how many more, the update choice, the stats mode), the current one a ring, those ahead empty; the line is filled up to the current dot, and the last dot, "First project", leads to the project wizard. Under the line the step is one card with its title, and its foot: "← Back" a quiet link at the left, at the right the primary button named after the next step ("Next: Tracker →"); an optional step (`OPTIONAL_STEPS`: Tracker, Stats) has "Skip for now" instead when there is nothing to go on with — the tracker without a profile, the stats (to the project wizard; not offered once there is a project, whose `/` would send back to the stats). Enter presses the primary button unless the focus is on a control or a link or a dialog is open. A step slides in (`--motion-appear`), the dots and the line move with it, choice cards rise under the pointer and the picked one has the accent's edge and a check in its corner; none of it with reduced motion. Up to 760 px the dots lose their labels and the current step's name stands under the line, the cards go one a column. A dot is the shared `StepDot` (`DotMark`): the line's done/current/future, and the project wizard's card dots, which add passed (green with a check) and failed (red with "!"). While `/setup` is open the header shows only the logo and the gear: no Stats link, chain, account or limits (`Header.tsx`).

Adding and removing a project (BTN-118): the wizard is `/projects/add` (`web/src/pages/ProjectAdd.tsx`, pure logic in `projectWizard.ts`); the home page sends there by itself when the config has no projects and no `configError`, otherwise it opens by "+ Add project" next to the title. The steps (BTN-197) are Agent (BTN-310) → Repository → Tracker → Project → Tasks' folders, all shown at once. Since BTN-344 it walks in the setup's `WizardFrame`: in the first run (no project yet) under the setup's head and step line, as its last step "First project", with "← Back" to the stats; standalone, with its own head and no line. Each step is a settings `Section` card (short fields as `Row`s, the folder full width, no lines between cards) whose head leads with a `StepDot` (`stepChecks` in `projectWizard.ts` over `checkMarks` in `wizard.ts`): empty — not filled in, an accent ring — the first such step, green — its check passed, red — it failed, the reason under its field (an entry's refusal on the card of the field it names: the key on Tracker for Huly, on Project for the others; `wizard.trackerShared` under the milestones). Tasks' folders is a `Segmented` "Own folder per task | Permanent folders" with a line saying what the pick means and, for permanent ones, their count. Under the cards "What will be created" (`ProjectSummary.tsx`, a `Card` with a `FactList`, standalone so it can go) shows the name and key, the tracker and its place (`trackerPlace`), the main branch, the folder, a task and its branch (`taskExample`: `KEY-12 → key-12/task`) and the folders, live; then the foot: what the add still misses (`missingOf`, the first reason in the order of the steps, naming its card) with "Check again", and "Add project". Agent: a `Select` of the providers, the shared one first in force and labelled so; the project's `provider` is written only when another one is picked (`withNewProject`), and under it the same readiness as the setup's (`AgentReady`) — its "Add an account" opens the add dialog over the wizard, which stays as it is; the wizard's fields live in the module (`kept` in `ProjectAdd.tsx`) until a project is added, so leaving the page loses nothing typed. The readiness does not hold the add. Repository: the folder; once found, its line says the main branch with a `[change]` link that opens the branch field (it opens by itself for a checkout with no current branch and for a branch the repository lacks, and stays open while that branch is retyped). Tracker (`web/src/pages/WizardTracker.tsx` over the shared `TrackerFields.tsx`): a `Select` of the tracker profiles from Access, each with its kind's icon, and "Add profile" as its last option, which opens `ProfileDialog` and picks the saved profile; with no tracker profile at all an "Add profile" button stands in the list's place, as wide; a single tracker profile is picked at the start. Under it, in its strip, the profile's state (signed in as whom, refused), then the fields of the profile's kind by its shape (`shapeOf`: `key` — Huly's project identifier, `place` — GitHub's `owner/name` with a free task prefix, `within` — Linear's team key and an optional project). The fields suggest the tracker's projects (`profiles/projects` with the typed text, 300 ms after the last keystroke, a `SuggestField` listing each key with its name), and an exact match fills the key, the value and the name (`pickProject`); the tracker's answer, the check's open tasks included, is the strip under the tracker project, its room kept while empty. Project: the name always, the key (Linear's team key, GitHub's task prefix) where the tracker does not give it. A field the user typed is not overwritten by a suggestion (`WizardFields.typed`, `typedIn`); switching the profile clears only the suggestions of the last kind (`switchProfile`). Switching the profile must not move the fields below: the empty `Select` keeps a line's height, a field head is as tall without its "?" as with it, and the folder's lines stay through a check of other fields (they depend on the folder and the branch only). 600 ms after the last keystroke, and on "Check again", the page sends the draft (`ProjectDraft`: repo, branch, key, name, tracker, tracker project, profile — `null` for the kind's default profile, slot count — 0 is a worktree per task, milestones, provider — `null` for the shared one) to `POST /api/project/check` (`checkDraft` in `src/projects/check.ts`): the folder is a git repository and not another project's, the branch exists, the entry passes `parseConfig` as the project would be added, the tracker answers `chainTasks` for the tracker project (its open tasks are counted; missing variables are named), and, for a project Claude may run — on Claude, or with run labels on (BTN-429; `trusted` is `null` otherwise) — the folder is trusted in the global `.claude.json` or in that of the shared Claude account's folder, the only one `claude` started with its `CLAUDE_CONFIG_DIR` writes the dialog to (`isTrusted`, BTN-300; the answer carries the service machine's `platform` and the service's `user`: an untrusted folder shows `trustCommand` — `pushd "<folder>" && claude` on Windows, `cd '<folder>' && claude` elsewhere, under a line that on Windows says to run it in cmd, not PowerShell (`wizard.untrustedWin`, `settings.untrustedWin`, EKR-55: Windows PowerShell 5.1 does not parse `&&`, and an npm-installed `claude` is a `claude.ps1` the default execution policy blocks; no PowerShell variant, since it would depend on how `claude` was installed) — and, only while Even Keel runs as a system service (the answer's `service`, `runsAsService` in `src/updates/control.ts`: a Windows service, a systemd system unit, a launchd daemon; `npm start`, the tray and `install.sh`'s user unit run as the user at the terminal, BTN-687; `trustCommandsOf`), for a terminal of another user, `trustCommandAs`, the same as the service's user — `runas /user:<user> "cmd /k cd /d <folder> && claude"` on Windows, `cd '<folder>' && sudo -u '<user>' -H claude` elsewhere — each with a copy button where the page has the clipboard, and the page asks again on the window's `focus` or `visibilitychange`, not on a timer; the commands are `TrustCommands.tsx`). The same block warns on the Sessions tab of a project's settings while the form's agent is Claude or its run labels are on (`TrustWarning`, the query `project/trust` with the form's Claude account), and stands under a chain paused on `claude.untrusted` — `claude --bg` refused the worktree, and `launchIn` in `src/service.ts` turns that `claude.startFailed` into a notice naming the project's checkout (`untrustedStart`), whose fix (`noticeFixOf`, `{ to: 'resume' }`) is "Check again and resume": the next launch is the check. A blank branch is filled from the checkout's current one; for `place` the tracker's value comes from the repository's remotes (`repo.suggested`: the first remote the adapter's optional `projectOfRemote` recognises — GitHub, a github.com remote), the key and the name from the repository's name (`keyOfFolder`, `suggestOfRepo`). A tracker project another project reads is refused as `wizard.trackerShared` until the two split it by milestone (BTN-306): the refusal opens "Only tasks in milestones" under the Project step (it stays open while the milestones are typed), the draft's `milestones` become the new entry's `chain.requiredMilestones`, and `yieldedMilestones` (`src/config-form.ts`) takes them out of each other project's required ones or, when it requires none, adds them to its excluded ones — `withNewProject` writes that into their entries, and the check names those projects (`ProjectCheck.yields`) in a line under the field. "Add" is open once the repository, the entry and the tracker pass (`readyToAdd`) — trust is only a warning with what to do; it sends `project/add`, which writes the record through `ConfigStore`, and the page goes to `/p/<id>` once the state has a project of the key it did not have before (another one may share the key). Removal is `ProjectRemove.tsx` at the bottom of the project settings' Repository tab: a confirm, then `project/remove`; `removalBlock` (`src/projects/removal.ts`) refuses while the project's chain runs or waits in the queue, a live session was launched for its tasks or works in its folders, a task holds a place (`held`) or cleanup leftovers remain, and the notice lists each reason. A first start without a config file starts with no projects, and the page opens the wizard.

Entry refusals are routed by code (`entryField` in `projectWizard.ts`), shared by the field messages and step dots. Only `wizard.keyShape` and `wizard.keyTaken` belong to the key (Tracker for the `key` shape, Project otherwise); `wizard.trackerPlace` belongs under the tracker project's field, and `wizard.trackerShared` under milestones. Blank required keys and tracker projects remain neutral: the footer's `missingOf` names what is missing.

Each card changes only with what it depends on (BTN-737). The folder's lines hold while the folder and the branch do (`repoCheck`); the tracker's answer holds while its `trackerBasis` (`projectWizard.ts`) does — the tracker, the profile, the tracker project as the adapter reads it (Linear: the team from the value or else the key) and the milestones; the key counts only for the `key` shape, where it is the tracker project. While it holds, the page sends the next check with `askTracker: false`, `checkDraft` gets `{ tracker: false }` and does not reach the tracker, and the page keeps the answer it has, its dot and its strip included. So the name, a free prefix, the folder, the branch, the agent and the slots never re-ask the tracker. "Check again" drops the held answer and asks it anew; a return from the trust terminal does not. The Project card still waits for the fresh check: its entry depends on the key and the name.

`project/add` rechecks the repository through the same `checkRepo` as `project/check` before writing anything
(`src/projects/add.ts`). A repository refusal returns its notice and leaves the config and profile links unchanged;
a folder inside a repository is stored as the repository root. Config validation still checks the key and tracker
fields; adding does not repeat the tracker's network check.

The folder field (BTN-744): `checkRepo` expands a leading `~` (`~/…`, on Windows also `~\…`) to the service user's home
(`expandHome`, `src/projects/folder.ts`; `~user` and `$HOME` stay as typed), refuses a relative path (`wizard.relativePath`)
and a folder that does not exist (`wizard.noFolder`, no git output, no button) before it asks git. The config gets git's
absolute root.

Git in the wizard (BTN-731). A folder that is not a repository (`wizard.notRepo`) gets "Make it a repository" under its
refusal, a repository with no commits (`wizard.noCommits`) "Make the first commit"; both send `git/init` with the folder
and the branch field (blank — `DEFAULT_BRANCH`), then check the draft again. `initRepository` (`src/git/setup.ts`)
refuses a missing folder (`wizard.noFolder`), a branch git would not take (`wizard.branchName`) and git without a name
or e-mail (`git.noIdentity`, whose fix opens the setup's Git step) before touching anything; then `git init -b <branch>`,
or for an unborn branch `git symbolic-ref HEAD refs/heads/<branch>`, and `git commit --allow-empty -m "Initial commit"`.
A repository with commits is left as it is. When git does not start at all, `checkRepo` answers `git.missing` instead
of `wizard.notRepo`, and so does any git call of the chain through `requireStarted` (`requireBranch`, the worktree
steps): the chain pauses on that notice, whose fix is "Check again and resume".
