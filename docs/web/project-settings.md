# Page: project settings

Project settings (BTN-97, BTN-117): the "Settings" tab over the side column (a tag in the project head where there is no column) opens a side panel at `#settings` (`web/src/pages/SettingsPanel.tsx`): `repo`, `branch`, the tracker with the project key it needs, `brief`, `slot`, `prompt`, `commands.beforeStart`, `commands.check` and `commands.afterGreen` (one command per line, textareas), `ci` (BTN-103: a checkbox per CI kind and "wait no longer than, min", empty — `null`; `recheckMain`, `fixTask`), `fillMilestone` (BTN-107) and the chain rules. That the settings apply at once, with no restart, is said once, in the legend's line for the Settings tab (`t.help.signs.settings`); the panel's head has no "?" of its own (EKR-2 put one there, BTN-613 took it out as a second "?" beside the legend's). The panel is split into groups, tabs in its head (BTN-128): Repository (`repo`, `branch`, `slot`, then "Remove project" as a red-framed card of its own), Tracker (the tracker, its project key, `intakeLabel` — hidden for a GitHub tracker, BTN-262 —, `fillMilestone`, then "Task sources" — the main tracker's line and the feeds', each opening its rules in a window, BTN-553 — together, so that one save cannot set a tracker apart from its statuses), Sessions (BTN-173: `provider`, `models.<provider>` and `accounts.<provider>` for each provider, `modelLabels` — '' in each is "as shared"; a model field, here and on `/settings`, stays free text suggesting the row's account's models (`SuggestField`, `useModelCatalog` → `POST /api/models/list`, BTN-336, BTN-583; `docs/sessions/models.md`, "Model lists"), none when the account lists nothing, and cleared when an account switched in the form lists everything but the model (`useModelReset`, BTN-582); then `brief` with "Go to Tools" beside it (EKR-5, the tracker's package on `/tools`, `docs/packages.md`), `prompt`, `commands.beforeStart`, and since BTN-187 `promptLanguage` and `stats.checkpointTokens` (since BTN-255 the `contextHandoffs` switch before it, which disables the threshold and the shares while off), since BTN-261 the three `stats.checkpointShares`, then `cacheTtl`, and since BTN-359 the section "Standards", `ProjectStandards.tsx`, before "What the session gets", `docs/sessions/protection.md`, "Project standards"), Check and CI (`ci.guard` first, then `commands.check`, `commands.afterGreen`, the rest of `ci`; then `pullRequests` with "Add profile" in its block and a select per CI kind of `remoteProfiles` — "Automatic" and the profiles that could serve it, shown with two of them or a choice made, a removed one as "removed profile", BTN-231; with the guard off the rest is greyed out and disabled, its values kept — `.settings__guarded--off`). The keys set on both levels (`OWN_KEYS`, BTN-187: the five of `ci`, `fillMilestone`, `promptLanguage`, `cacheTtl`, `stats.checkpointTokens`, since BTN-255 `contextHandoffs`, and since BTN-261 the three `stats.checkpointShares`) go into the form as `own`, only the project's own values, a key left out being "as shared". Layout (BTN-337, both settings pages, parts in `settingsParts.tsx`, styles in `settings.css`): a tab's fields are grouped into section cards (`Section`: a title, its "?", an optional `aside` at the right, `danger` for the red frame), 24 px apart, 12 px inside, the fields parted by thin lines; the card's head is a band across its top (BTN-343), a tone lighter than the card with a line under it (reddish on a `danger` card), the title 15 px 600, while a row's name is 400 in a muted colour, so head, name and value read as three levels; a short field is a `Row` — the name at the left, the control at the right, every control `--control-width` wide so the right edges line up (16em on `/settings`, 11.5em in the panel; under 340 px of form the control goes under its name, a switch takes only its own width) — and a text field, a table or a grid goes full width under its name. An on/off setting is a `Switch` (`role="switch"`, `SwitchField`), not a select or a checkbox; `brief` stays a select, its third value being "auto". Inheritance has one mark (`Inherit`, in the field's head or under a grid cell): the control always shows the value in force; an inherited one has a dashed "shared" chip, an own one an "own" chip with `InheritIcon` that goes back to the shared value (it names that value in its tip; unlike the "was … ↺" undo of an unsaved change). Editing an inherited field makes it own: a select or switch writes its value, a field kept by an `own*` flag (`ci.kinds`, `ci.waitMinutes`, `stats.checkpointTokens`, the three shares as one) is copied from the shared values first (`ownEdit`), so the fields are never greyed out. Edited back to the value it inherited, a field that started inherited inherits again, unchanged: a select, a switch, the provider and the protection go back to '' (`inheritedEdit`), an `own*` flag back to off (`ownEdited`, both in `settingsDraft.ts`); one that started own stays own. The protection compares by its rules, not its text (`sameProtection`), so groups switched back in another order are no change. The changed-field stripe is a `::before` 12 px out to the left, inside the card's padding. A field's explanation is not a line under it but a "?" after its name (`FieldHead`, `HelpTip`), opened and closed by a press, not by pointing, with the same tip as the facts (`useTip`); pale until its row or heading is pointed at (`@media (hover: hover)`); the "?" is out of the Tab order, so Tab goes from field to field. Neither is a tab's or a block's (BTN-324), on both settings pages: Check and CI of `/settings` has a "?" by the tab's title, the profiles one by their heading, "Remove project" one by its name, and why a tracker or a feed's profile is locked (`trackerLocked`, `feedLocked`) is in the "?" of that field. Only an error, a warning or an empty state stays a line of text; the `.env` rows of Access keep their short description beside the name. A list field is an editable table (`web/src/pages/settingsTable.tsx`): `ListTable` for one column, `RowsTable` for several — a cell edits in place, long text wraps, the trash removes a row, the last row adds one once its cells are filled (Enter, or Ctrl+Enter in a multiline cell; Enter never submits the form). A column takes `suggest` (a `SuggestField`, free input still allowed, the values other rows took left out) or `options` (a select); the first column is the key and cannot repeat. A select across the page is `web/src/ui/Select.tsx`, not a native `<select>`: a combobox button with a listbox in a `popover` portalled to the button's closest `<dialog>`, else to `document.body` (inside a `<label>` a press on an option would click the button again; a modal dialog makes everything outside it inert, so a list in the body would show over the task card but take no clicks), keys in `selectKeys.ts`; Escape closes only the list. An option may carry an `icon` before its label and an `aside` after it (a muted `.select__note`, the unsaved dot), both shown in the button too. A long list takes `search` (the plugin pick of "Add a package", hundreds of plugins of the official marketplaces): a field atop the open list takes the typing, a printable key on the closed button opens it with that key; the list keeps the labels holding every word (`filterOf`), those starting with the query first, then those with a word starting so — "fi" puts figma before every plugin of `claude-plugins-official`; arrows and Enter pick, Escape and Tab go back to the button. Checkboxes and radios stay native inputs, drawn by the global rules in `web/src/styles.css`. The field values stay '\n' texts in the draft (`rowsOf`, `linesText`, `pairOf` in `settingsRows.ts`). The chain rules' statuses, labels and milestones come from the tasks the page knows and from what the trackers name (`knownStatuses`, `ruleChoicesOf`, EVK-1): the project's in its panel, all projects' on `/settings`, a profile's projects' in its group, a name once whatever its case. What a tracker names — every status (with its category) and label a task of the project can have, whether or not a task has it now — is `GET /api/projects/<id>/vocabulary` (the adapter's optional `vocabulary`, `docs/trackers.md`), read by `useVocabularies` as the panel or the page opens; the service keeps an answer five minutes (`src/tracker/vocabulary.ts`). So a project whose chain is empty still gets suggestions. A tracker without it, off or not answering (404, an error) adds nothing and shows no error: nothing waits on it. A milestone the opposite list has is not offered (`withoutListed`), since the config refuses it in both. The save sends `POST /api/project/settings` with `{project, base, ...ProjectForm}` (`projectFormOf` checks only the shape; `ConfigStore.saveProject`). Once the chain has launched a task of a project (`launchedProjects` in `src/chain/launches.ts`: a launch that is not a release or a `-FIX` session), the page does not switch its tracker or tracker project: `ConfigView.trackerLocked` disables both with a "v0.2" badge and gives the profile field a "?" saying why, and a save that changes them anyway is refused with `config.trackerLocked`. A project with tasks in the built-in tracker cannot leave it either (`ProjectTracker.tsx` `hasTasks`, `config.builtinLocked`, BTN-769), and a project with tasks of another tracker is not offered the built-in one: that is an export, not built yet. A `config-import` is not checked for it. Another tracker for a live project is a task feed (BTN-66): the Tracker tab has "Task sources" (`FeedList.tsx`, BTN-553) under the tracker block, an "Add a feed" button at the heading's right, the main tracker's line first, then a row per feed — the line, then the tracker block with its place fixed — or one line saying where the chain takes tasks from without them; each source is a box of its own (`--surface-muted`, `--border`, `--radius-control`), so where one ends shows. The form that adds a feed opens only from the button, at the top of the list in an accent box titled "New feed" (marked as a chosen provider is), scrolled into view with its first field focused, so the press shows wherever the list was scrolled (the block, then the key, only where the tracker's ids do not carry their own, the primary "Add a feed" and "Cancel"); a feed is added and removed (its "⋯" menu, then a confirmation) at once, outside the draft and the bar (`docs/chain/entry.md`, "Task feeds"). A source's line (`SourceLine`, `SourceDialog.tsx`) is its tracker's icon, key and tracker, "Rules: its own / as in the profile", the unsaved dot and "Configure", which opens the source's window (`SourceDialog`): the parts as tabs — "Chain rules" (`RuleForm`) and "Project tasks" (`MilestoneFields`), a new part being one more `SourceTab` — and one "Save" for all of them at the bottom, the window 880 px wide and full screen under 760 px. A project on the built-in tracker has only "Project tasks" and no tab strip (BTN-769): its statuses and labels are fixed (BTN-767); its milestones are the built-in tracker's, "Only milestones" is unavailable with a note while it has none, and a save first creates each milestone the rules name that it lacks (`newMilestones`, `builtin/milestone`). The tabs differ in height, so the window stands at a fixed distance from the top, not in the middle: the head and the tabs stay put on a switch, and the bottom edge with the foot glides to the new height (`useHeightGlide` in `web/src/ui/useHeightGlide.ts`, `--motion-appear`). Closing keeps the edits: the row keeps its dot. The main tracker's window edits the panel's draft and saves through the panel's save, so the tracker and its statuses still go in one save; its rules inherit from the profile of the tracker the draft names, and switching the tracker in the draft puts the project's own `active` and `terminal` back to what the new one inherits (switching back restores them), with a warning band and "Configure" on the main line. A feed's window keeps its own draft (scope `feed:<project>:<feed>`, `FeedDialog.tsx`) and saves through `POST /api/project/feed/rules` with the keys it sets itself (`ownRulesOf`); it inherits from the feed's profile over the shared rules, not from the project (`feedRulesOf`), suggests only the feed's own tracker's vocabulary and tasks (`sourceTasks` by `FeedView.prefix`), and "From" says "feed" for its own rows. In `dev:fake` ABC's Linear feed has a `terminal` of its own, and XYZ too, so switching XYZ's tracker shows the warning. The tracker block (BTN-322, `TrackerFields.tsx`) is the wizard's, one component for the wizard, the Tracker tab and each feed: the profile `Select` with its kind's icon and "Add profile", on its row the fields of the kind's shape with the profile's projects suggested; a strip glued under each field (`FieldStrip`, `docs/design.md`) says the profile's state under the profile (`profileLine`: signed in as whom, refused) and the tracker's answer under the tracker project (`projectLine`: no such project or a failed list, the wizard's check, the name of an exact match). With the key fixed and no project field (Huly in the settings) a project error goes under the profile. In the settings (`ProjectTracker.tsx`, `keyFixed`) there is no tracker field: the profiles of every tracker are offered and the chosen one's kind is the tracker. A profile of the saved tracker is linked at once (`profiles/link`) while the tracker project goes into the draft, a Linear value split into a team and a project field (`placeFields`, joined back by `placeOf`), a blank one standing for the key. A profile of another tracker puts that tracker into the draft with an empty tracker project (one of the saved tracker puts both back as saved) and is linked once the save lands, since a profile is linked only to its project's saved tracker.

"What the session gets" (BTN-340, `web/src/pages/SessionGets.tsx`, the facts pure in `sessionRules.ts` with tests) is a section of the Sessions tab after `prompt`, for the agent the form names (the project's `provider`, else the shared one, unsaved edits included): the instruction files a session of it reads (a note when Even Keel passes the lone one, when it reads both, or which file it leaves unread), whether the shared and the project's `prompt` are set, the project's skills it reads and those it misses with their folder, and the skills of the project's enabled plugin packages (a note when the agent takes no hooks, `pluginReach`). With no instruction file, prompt or skill it reached, a warning says the project has no rules. Under it a `<details>` holds the table of every agent from `src/agent/projectRules.ts`, the same as in the guide. The rules come from `ToolsView.rules` of `GET /api/projects/<id>/tools` (`useToolsViews`): `git ls-tree` of the project's branch, so an uncommitted file does not count (`docs/sessions/protection.md`, "Project rules for every agent"); `null` there — git could not read the branch — gives a line saying it is unknown. `?tools=` of `dev:fake` varies them: `empty` has none, odd-letter projects only `AGENTS.md` and `.agents/skills`, the rest both files and `.claude/skills`.

The chain rules by what they are about (BTN-334, `RuleForm.tsx`, the row logic pure in `ruleRows.ts` with tests) are one form on the four levels — `/settings`, a tracker profile's group, the window of a project's main tracker and the window of a feed (both from the Tracker tab, BTN-553). Statuses are a table, a row per known status with a radio "in the chain / out of it / closed"; a label is a row with one rule, "Required" or "Don't take", added from a field suggesting the trackers' labels, and under the table "Take any / Only with a required label" ("any" drops the required ones). `Manual` is an ordinary "Don't take" row of the shared default (BTN-758), removable, and a level adding a label starts from the inherited list, `Manual` with it (`withLabel`). Even Keel's own labels head the table, not editable: `Question`/`Вопрос` only a mark, the run labels the tasks carry while `modelLabels` is on pick the model. Each row's "From" says where its value comes from — by category, built in, shared, `profile <name>`, project or feed; a row of another level is muted but whole and still editable, the level's own gets a reset that puts back what it inherits. The values stay the lists of the config, inherited key by key, each list whole: a radio rewrites only the lists the status leaves or enters (`withPlace`), so moving a status in or out of the chain leaves an inherited `terminal` inherited, and a level back where the categories put every status writes `null`. A profile cannot keep `null` or `[]` over a shared list, so there "by the categories" is the list spelled out and a value equal to the inherited one is the key unset (`settled`). The milestone rules are not chain rules: "Project tasks — all / only milestones [..] / all except [..]" (`MilestoneFields`), in a source's window and in a section of their own on `/settings`. The project's form carries `ownRules`, the rule keys it sets itself, so the panel shows the profile's value for the rest (`effectiveRules`); a key is the project's own while its value differs from what it inherits (`ruleOrigins`), and the save writes it only then — `withProjectForm` compares each rule key with the profile's value over the shared one.

Status moves (BTN-554, `MoveFields.tsx`, the option logic pure in `statusMoves.ts` with tests) are a section "Statuses on actions" of three picks — on task start, on pull request (with the hint that it works once PR mode is on), on task completion — in a profile's tab of Chain rules (not on "All trackers"), in one form and one save bar with its rules (`ProfileRules.tsx`), and a third tab of a source's window, the main tracker's and a feed's (`SourceMoves.tsx`). Only for a kind that moves statuses (`ProfileKindView.moves`). The picks offer what `profiles/statuses` lists for the profile, filtered by the rules as drafted: start and review the statuses in the chain, completion the done ones; a saved name the tracker no longer lists stays a choice. On the profile level the first choice is "leave as is" or "automatic", on the source level "as in the profile (<its value>)", and start and review add "leave as is". A new profile of such a kind gets one more step in the add dialog, "Task statuses" (`ProfileMovesStep.tsx`), filled with `defaultMoves`; without statuses read it says so and keeps only "Skip". The commands are `profiles/moves` (`{id, moves}`) and `project/moves` (`{project, feed: id | null, moves}`); the query `profiles/statuses` (`{id}`) answers the statuses or `null`. A move refused or out of the chain (`statusMove.*`, `TrackerView.moveFailures`) is a red band on the project page with "Open the statuses on actions", which opens the profile's tab or the project's Tracker tab by the notice's `level`; so does a refused close with a chosen status.
