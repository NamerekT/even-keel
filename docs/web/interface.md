# Page: the stack, the state stream, routes and the theme

The header, the banners and `/status` are in [`header.md`](header.md); the home page in [`home.md`](home.md). How the page looks — tokens, blocks, plaques, tips, motion, modals and the check before a merge — is `docs/design.md`.

## The stack

- React + Vite in `web/`, built into `dist/web`, which the server serves; a client route gets `index.html`. `npm run dev:web` is Vite with an `/api` proxy to `EVEN_KEEL_URL` (`:4747` by default).
- The client takes state types from `src/state.ts`; settings and form types are in `src/state/settings.ts`, re-exported through it. Both hold only types. Nothing the page imports as a value may reach `node:*`, through `src/` either: the browser build leaves the whole page blank. `web/src/node-free.test.ts` walks the page's value imports and names the chain that brings one in; a server-only step goes in as a parameter (as `TranscriptFold` takes `expandPromptFile` from `history.ts` and `tail.ts`).
- The response headers (CSP, frames, referrer, `nosniff`) are in [`sign-in.md`](sign-in.md#the-checks-on-every-request).
- `src/server-response.ts` gzips JSON of at least 1024 UTF-8 bytes when `Accept-Encoding` allows it and varies on that header. SSE is gzipped too, at the fastest level, with `Z_SYNC_FLUSH` after every event; a disconnect releases its compressor. Clients without gzip get the plain protocol.

## The state stream

- **The first frame.** The initial state comes only from the first `/api/events` frame: the whole `EvenKeelState`. There is no parallel `/api/state` download; `GET /api/state` stays for scripts and update checks, and a closed stream still probes it for a refused sign-in.
- **Commands.** A command answers `{ok:true}` or an error with its notice, never the state; the page keeps its data until the stream brings the change. A successful command schedules `broadcastSoon` after its answer, even one with no notification of its own. No command is retried automatically.
- **Building a frame.** A change asks for the state through `EventHub.broadcastSoon('state', getState)` (`src/events.ts`), never `broadcast('state', getState())`: the state is built at most once per 200 ms, a burst builds once, and nothing is built while no page listens. At a start the trackers, profiles and CI answer many times a second, and each used to build the whole state. A frame equal to the last one is not sent.
- **Patches.** After the whole state the stream sends `statePatch` (`src/patch.ts`): the top-level keys that changed, those gone, and keyed parts by their key — `sessions` by `sessionId`, `eventLog` by `id`, `trackers` by `name`, and `ci` by its own keys (`OWN_KEYS`, sent as `byKey`), each with the order only when it changed. So a CI poll sends one project's CI, not every project's, and a frame is 4–70 KB instead of ~2 MB. A new keyed part is one more entry in the hub's map; an array whose entries lack a unique id goes whole.
- **Where a patch lands.** The page lays a patch over the last state the stream sent, never over a command's answer (`applyPatch`, `web/src/live/patch.ts`). A new page joins through `EventHub.join`: it gets the whole state, and the pages already there first get a patch to the same data, so every page's base is what the hub last sent. Reconnection gets a whole frame before any patch.
- **The blocked service.** When `src/start.ts` could not migrate the storage, the service serves only the page: `/api/events` sends one `blocked` event with the reason (`LiveSnapshot.blocked`) and the page shows only the banner `app.blocked` (`docs/chain/state.md`, "State files and the schema version").

## What the state holds

- **A finished session.** One the chain does not wait on goes with an empty `feed` and `action` (`wireGetState`), and the page shows neither (`showsAction`). The rest stays: the card of a closed task shows its last session.
- **Recent history only** (`recentHistory`, `src/service/page-history.ts`). The sessions not finished, those a chain waits on, those of an open task or an open fix of main, and those that moved within `HISTORY_SHOWN_MS` (3 days); `taskSessions` of those tasks only, with the newest launch of each task kept in `ranAt`, by which the chain orders closed tasks; the newest `EVENT_LOG_SHOWN` (200) log entries. The whole history made the state ~3 MB, most of it finished sessions.
- **The rest on demand.** `history/task` (`{ task }` → every run and its sessions, `TaskHistory`) when the session panel opens on a task named in `ranAt` or one with runs and no session (`useTaskHistory`; another machine's sessions are asked of it); `history/events` (the whole log) when `/log` opens, laid under the state's newest entries (`withOlder`). Until it answers, the chain row of such a task has no resets badge. The state's watchers (the event log, the badges, the demo) see the same trimmed state.
- **`tasks`** is the tasks of every project: the header's waiting count, the home cards and the chat drafts read all projects at once. It goes whole in a patch on any task change: keying it needs an id unique across projects, which a task of a tracker project two projects share lacks.
- **A machine's part.** `sessions`, `mailbox`, `taskSessions` with their accounts and compactions, `limits`, `usage`, the `account` panel and its `headerLevels` — and the tray's count of asking sessions — come from the hub's mirror of the machine (`LinkedMachine.page`, `src/machine/page.ts`; `docs/machines/pool.md`, "The mirror"), never from the session monitor or the account folders. They are as fresh as the machine's last post. The panel's `active` is the hub's own setting; before the machine's first snapshot the panel has no accounts.

## Routes and project names

- **A project page** is `/p/<id>`, the project's GUID: links come from `projectPath(project)`, the route is read back by `projectOfPath(state, param)` (`web/src/state.ts`). An older `/p/<KEY>` link is replaced by the id route of the first project with the key, keeping its search and hash (`ProjectRoute` in `web/src/App.tsx`).
- **Ids in the state.** The state names every project by its id, as the service does: `projects`, the chain, every per-project map and `tasks` (each with its `project`, since two projects may read one tracker project). `projectKeys` gives the key (stats, old links, the fix name), `taskPrefixes` the prefix of task ids, `projectLabels` what to show — the key, with a distinguisher where another project has it (`projectLabel` in `src/config.ts`, `useProjectLabel`/`ProjectLabel` in `web/src/ui/ProjectLabel.tsx`). A task's project is `taskProject(state, task)`.
- **Notices.** A server notice that names a project by id shows its label: `say()` runs `withLabels` (`src/notice/notice.ts`) with the labels `App` sets (`setProjectLabels`); the service log does the same to every line.
- **Links to projects.** Where a page text names another project it is a link to its page: `ProjectLinks` (`web/src/ui/ProjectLinks.tsx`) takes a text with project ids — `sayIds()` of a notice (`<Said>`), or a page text given ids — and links each by its label, the page's own project staying text; an id inside a task id (`ABC-5`) is not taken (`piecesOf`). It is used on the plaques of the project page and the card, the packages banner, the event and update toasts and the launch chart's legend. A link inside a card stands above the card's stretched link (`.project-link`); a toast with an `href` must not get one in its title.

## Modals and busy marks

- **Closing from the backdrop.** A modal closes from its backdrop only when the left button went both down and up on it (`useBackdropClose`, `web/src/ui/backdrop.ts`): a `click` goes to the common ancestor of the press and the release, the `<dialog>` itself, so a text selection dragged out of the window used to close it. A press on the backdrop starts no selection. Every modal uses it but the sign-in, which never closes from its backdrop; the media viewer counts its stage as backdrop.
- **The activity bar** (`ActivityBar`) at the top of the window is only for what a person did and waits on: commands, a session's read, the task card, `checkProject`, `query` (the whole `/log`, a closed task's runs) and `attach` go through `activity.track` (`web/src/live/activity.ts`).
- **Background reads** stay off the bar and show where they land: Tally's answers (`useStatsAnswer` — the strip under the chain keeps its skeleton, the header says "today: …"/"Tokens: …"), the tools' views (`useToolsViews`), the tracker's vocabulary (`useVocabularies`, its `reading` passed down through `VocabularyReading`) and the untracked `read` of `useLive` (an account's models, a repository's branches, the hub's addresses, a profile's statuses). A field fed by one shows a small loader in its list while it reads (`loading` of `SuggestField` and `Select`, `docs/design.md`).
- **Buttons.** `useCommand` marks the pressed button `aria-busy` while its command runs, so a new command button needs nothing for its spinner. A command the service carries out later (`chain/restart`) keeps the button busy with `useHold` until the state changes.
- **`useLanding`** (a command "landing" in the state, not a merge's landing): for a command whose result only the next state or a read shows — a settings save, the card's "Into the chain"/"To the backlog". Its control stays off from the press until the watched value changes, so the gap between the answer and the new state neither lets a second press through nor flashes the button. The time limit counts from the answer; past it the control is on again with `late` set.
- A block that reloads with its previous data on screen sets `aria-busy` on itself and is dimmed.

## A page open over an update

`web/src/live/reload.ts`: when a state brings another `startedAt`, the page fetches `/` and compares the `/assets/` files it names with those it loaded. Another build reloads the page at once, or, while a modal is open or a text field has focus, every 2 s once neither holds (chat drafts survive in IndexedDB). The task card does not hold it (`data-restorable`): its `card` parameter reopens it. A restart on the same build keeps the page. A lazy chunk gone from the new build (`vite:preloadError`: the build empties `dist/web`) reloads it too, at most once per 10 s; otherwise opening the task card on a stale page blanks it.

## The app

The page installs as an app (`web/public/manifest.webmanifest`). The `icon-*.png` files are renders of `favicon.svg` in its light colours, made by hand in a browser — there is no generator: `icon-192`/`icon-512` the tile on transparency, `apple-touch-icon.png` (180) and `icon-maskable-512.png` a full-bleed `#1c1c1a` square with the mark at 0.725 of the side for the platform's crop. The tray icon (`service/EvenKeelTray.cs`) draws `dist/web/icon-192.png`. There is no service worker: the service serves a fresh `dist/web` anyway. Chrome offers the install only in a secure context — `localhost` or HTTPS, not a bare `http://<IP>`.

## Theme

- The choice is System (the default), Light or Dark, kept per browser in `localStorage` under `even-keel.theme` (`web/src/theme.ts`): no config key, so a phone and a desktop may differ. It is picked in Settings → Interface, in the gear menu and in the burger's sheet (`ThemeSwitch`, `web/src/ui/ThemeSwitch.tsx`).
- The page's theme is `<html data-theme="light|dark">`, always resolved, never `system`; the dark tokens are one `:root[data-theme='dark']` block in `web/src/styles.css`, and no stylesheet asks `prefers-color-scheme` (`docs/design.md`).
- `web/public/theme.js` sets the attribute before the first paint, loaded blocking from the head of `web/index.html`, so a dark choice never flashes light. It is a file, not an inline script, because the CSP refuses inline code. It repeats `themeOf` in plain JS; `web/src/theme.test.ts` runs it against `themeOf` for every stored value and system theme.
- `watchTheme()` (in `web/src/main.tsx` before the render) follows `prefers-color-scheme` while the choice is System, takes a choice made in another tab through the `storage` event and sets the `media` of the two `theme-color` metas (`themeColorMedia`), so a phone's browser bar follows a manual choice.
- `npm run shot -- --theme <system|light|dark>` writes the choice before the page loads (`screenshots.md`).
