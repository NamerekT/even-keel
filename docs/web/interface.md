# Page: the stack, the state stream, routes, the header and the home page

## Interface

- The header account chip on `/p/<id>` follows the current session's saved account, otherwise the next launch choice even while stopped or paused. The server builds `AccountView.headerLevels` (`src/account/header-levels.ts`) through `runChoice`, with skipped and held tasks passed over by `nextTask`. It sends at most three distinct accounts: the task's override, the project's default and the shared default. An inherited default is labelled Even Keel. Every other route shows only the shared account. `AccountLevels` is read-only, uses one expanded card and two compact rows, and has no links, buttons or nested tips. A cascade adds an account-coloured chip border and stack count. A phone has no chip: the limits of the chip's account are thin bars along the header's bottom edge, one per window — a monthly or a single window is one bar across — and none for an account without windows (BTN-600). The full accounts drawer is unchanged.

- React + Vite in `web/`, built into `dist/web`, which the server serves; for client routes the server answers `index.html`.
- A page open over an update reloads itself (`web/src/live/reload.ts`). When a state brings another `startedAt`, the page fetches `/` and compares the `/assets/` files it names with those it was loaded with; another build reloads it at once, or, while a modal is open or a text field has focus, every 2 s once neither holds (chat drafts survive in IndexedDB). The task card does not hold it (`data-restorable`): its `card` parameter reopens it. A restart on the same build keeps the page. A lazy chunk gone from the new build (`vite:preloadError`, the build empties `dist/web`) reloads the page too, at most once per 10 s; before this, opening the task card on a stale page blanked it.
- The client takes state types from `src/state.ts` — only types there, no `node:*`.
- The state reaches the page over `/api/events`: the whole `EvenKeelState` when the stream opens, then on every change. A change asks for it through `EventHub.broadcastSoon('state', getState)` (`src/events.ts`, BTN-691), never `broadcast('state', getState())`: the state is built at most once per 200 ms, a request inside the window waits for its end and a burst of them builds once, with nothing built while no page listens. At a start the trackers, profiles and CI answer many times a second, and each built the whole state anew. A frame equal to the last one is not sent.
- After the whole state the stream sends only what changed, as `statePatch` (BTN-695): the top-level keys that changed, those gone, and `sessions` by `sessionId` — the changed sessions, with the order only when it changed (`EventHub` built with `{ state: { sessions: 'sessionId' } }`, the patch type in `src/patch.ts`). Between two frames 1–4 small keys and one session of ~750 change, so a frame is 4–70 KB instead of ~2 MB. The page lays a patch over the last state the stream sent, never over a command's answer (`applyPatch`, `web/src/live/patch.ts`). A new page joins through `EventHub.join`: it gets the whole state, and the pages already there get a patch to the same data first, so every page's base is what the hub last sent. A new keyed part is one more entry in that map; an array whose entries lack a unique id goes whole.
- A finished session the chain does not wait on goes with an empty `feed` and `action` (`wireGetState`): the page shows neither (`showsAction`). The rest of a finished session stays: the card of a closed task shows its last session.
- A project page is `/p/<id>`, the project's GUID (BTN-132): links are built by `projectPath(project)` and the route is read back by `projectOfPath(state, param)` (`web/src/state.ts`). An older `/p/<KEY>` link is replaced by the id route of the first project of the key, with its search and hash (`ProjectRoute` in `web/src/App.tsx`).
- The state names every project by its id, as the service does (BTN-271): `projects`, the chain, every per-project map and `tasks` (each with its `project`, since two projects may read one tracker project). `projectKeys` gives the key (stats, old links, the fix name), `taskPrefixes` the prefix of the task ids, `projectLabels` what to show: the key, with a distinguisher where another project has it (`projectLabel` in `src/config.ts`, `useProjectLabel`/`ProjectLabel` in `web/src/ui/ProjectLabel.tsx`). A task's project is `taskProject(state, task)`. Server notices that name a project by id are shown by its label: `say()` runs `withLabels` (`src/notice/notice.ts`) with the labels `App` sets (`setProjectLabels`), and the service log does the same to every line. Where the page's text names another project it is a link to its page (BTN-319): `ProjectLinks` (`web/src/ui/ProjectLinks.tsx`) takes a text with the projects by their ids — `sayIds()` of a notice (`<Said>`), or a page text given ids — and makes each one a link by its label, the page's own project staying text; an id inside a task id (`ABC-5`) is not taken (`piecesOf`). It is used on the plaques of the project page and the card (the chain's error, a slot, CI or release-carry wait, cleanup warnings), the packages banner and the event and update toasts; the launch chart's legend links its projects too. A link inside a card stands above the card's stretched link (`.project-link`), and a toast with an `href` must not get one in its title. A project card selects no text: a press anywhere on it but its buttons and links opens the project, the task title cut short too — it stands above the stretched link for its tip, so it is a link to the project itself (`TaskTitle` in `ProjectCard.tsx`).
- When `src/main.ts` could not migrate the storage, the service serves only the page: `/api/events` sends one `blocked` event with the reason (`LiveSnapshot.blocked`), and the page shows nothing but the error banner `app.blocked` (`docs/chain/state.md`, "State files and the schema version").
- `npm run dev:web` — Vite with a `/api` proxy to `EVEN_KEEL_URL` (`:4747` by default).
- How the page looks — tokens, blocks, layout, the plaques, tips, motion, modals and the check before a merge — is `docs/design.md`.
- The header and all six global banners share one sticky stack (`AppHeader.tsx`). Its `ResizeObserver` writes the full height to `--header-height` on `.app`, including wrapping, expanded details and motion; `--header-row-height` is only the header row's minimum height. Viewport-bound panels and sticky columns use the measured height. The banners scroll separately beyond 40dvh, leaving room for page content. `Banner.tsx` keeps the last content through its exit transition, makes it inert and hidden from accessibility as soon as it starts closing, then removes it; `banners.css` gives each banner a dividing line and 0.2 s entry/exit motion, disabled by `prefers-reduced-motion`. The browser check is logged in `verified.md`, BTN-480.
- A modal closes from its backdrop only when the left button went both down and up on it (EKR-23, `useBackdropClose` in `web/src/ui/backdrop.ts`): a `click` goes to the common ancestor of the press and the release, the `<dialog>` itself, so a text selection dragged out of the window used to close it. A press on the backdrop does not start a selection. Every modal but the sign-in, which does not close from its backdrop at all, uses it; the media viewer counts its stage as backdrop too.
- The home page has memes too (`web/src/ui/memes.ts`). Under the title, `harborMemes` builds lines from the user's own numbers — the busiest of the 14 days from 50 launches, a project with ¾ of at least 50 launches, 3+ open questions, the five-hour limit from 50 % — plus the line about Even Keel itself; one draw per visit picks among them, and the numbers follow the state. A project with no task to show says why through `emptyCard`: everything done, a project with no tasks, or an empty chain with a backlog — these are quiet rows, the line in their tip; open tasks that are only held back keep the plain "No open tasks" on a full card. The same three kinds add a call to file tasks or ready them in the tracker (`emptyCall`, EKR-13): under the joke in the tip, at the top of the project page in place of "No tasks in the chain", and under the joke of a card (queued, paused or with a question), with an "Open in <tracker>" button when the tracker gives the project's page (`trackerUrls.pages`, `TrackerSetup.projectUrl`) and one more for each task feed whose tracker gives its page, the project's first (`projectPages`, BTN-329); two buttons of one tracker add their keys ("Open in Huly · OPS"). In `dev:fake` XYZ is the empty project, each project's page a made-up Huly address, ABC's feeds a GitHub and a Linear one. A card's line stands still, so several cards do not type at once: a quote in the project's colour, the first part muted as the setup and the rest in full ink as the punchline. The line under the title, in the main font, is an array of parts typed by `Typed` (`web/src/ui/Typed.tsx`) with a 3 s hold between parts; it types once per mount, a changed number in it is taken over without retyping, and with reduced motion it is shown whole. It queues up like the chains do (`Typists`, `book`): as many lines type at once as `parallel`.
- The order of the home cards (BTN-207, BTN-244, `web/src/pages/homeGroups.ts`). A switch of four icons in the head (`GroupingSwitch`, kept in `localStorage` under `even-keel.home.grouping`, without groups until chosen) shows one plain grid (`none`) or groups the projects by repository, by tracker connection (`state.trackers`, titled by its `title`) or both — remote blocks, with tracker subheads inside a block only when it holds two trackers. A remote group is the projects whose checkouts share a remote, transitively; the service reads each checkout's remotes into `state.remotes` (`ProjectRemotes`, `src/projects/remotes.ts`, on a config change and every minute with the CI targets), and `remoteRef` makes one id of every url of a repository — host and path in lower case, without credentials, port, `.git` or the remote's name, a local bare repository by its resolved path. The group is titled by the `owner/repo` most of its projects share (a local one by its folder). A project left alone in its group, or without remotes, goes into one block after the groups, titled "Other". When there is at least one group, every block is a framed panel titled with its project count; otherwise the one block is the plain grid. Inside a section the full cards come working first (the chain runs, is queued or paused, or a question is open — `zoneOf`), then the rest, each in config order; the block's quiet projects (`ghost`, `finished`, `shelved`) leave the grid for one wrapping strip at its bottom (`laidOut`, `QuietRow`: colour, key, done/total, a link to the project; the name and the joke in a tip), and a tracker section left without cards drops its subhead. The punchlines' turns (`emptyTurns`) go by this page order. A card's task title is clamped to two lines, the whole of it in a tip only when cut. When every open task is held (skipped, or behind a blocker the chain does not take), the card and the queue show the first of the chain marked "Skipped" or "Blocked" (`CardTask.held`), not "No open tasks". In `dev:fake` ABC and XYZ share `john/app` (`FAKE_REMOTES`), so the page shows one group; the fake has one tracker, so "by tracker" is one group of four.
- `/stats` and `/tools` end with a basement (`web/src/layout/Basement.tsx`; the page renders it, a portal puts it into `BasementSlot` below `main`, so it spans the whole window; it comes once the page's data has answered and stays through filter changes): a wall, a floor in perspective, six caution tapes at three depths — some torn with the pieces hanging and swaying, some worn — and a sign on legs with the page's line (`t.basement`). The tapes are a fixed layout, not random; with reduced motion the pieces do not sway.
- The 404 (an unknown route or a project not in the config) is the whole page as a basement: `tall` makes the scene take the rest of the window, `idle` turns the "work in progress" tape into bare stripes (nothing is being built there), and the sign carries `t.notFound` with the link up. The home and project pages get no basement: they are opened many times a day and have jokes of their own.
- While none of the chosen projects has answered, `/tools` shows the outline of the matrix (`web/src/tools/ToolsLoading.tsx`): the real section titles and project columns, a lamp per project (blue — reading, green — answered), pulsing bars and a barcode scanner by the caption. It comes after 0.15 s, so a fast answer does not flash it; with reduced motion nothing moves.
- Updates (BTN-134, `src/updates/`): the service reads its version from `package.json` and, while `updates.check` is on, asks `api.github.com/repos/<repository>/releases?per_page=30` (no token) at start and every 12 h (`UpdateWatcher`, `releasesOf`) — not during the first run (`firstRun`, BTN-310): the setup asks whether to, and the first ask comes once the run ends (a config change calls `configChanged`); drafts, prereleases and tags that are not a version are ignored, and a failed request is one log line. The page gets `EvenKeelState.updates` (`updatesView` for the releases, `Updater.view()` for the rest): the last row of the gear menu and of the burger's sheet is "Even Keel <version>", with a button "<version> available" when a release is newer, or "back to <version>" when this version came by an update (`VersionRow` in `web/src/layout/Updates.tsx`). Both open the update window (`UpdateWindow`, BTN-163). A newer release also gets a toast in the window's corner (`UpdateToast`, built on the generic `web/src/ui/Toast.tsx`) unless `updates.notify` is off or `updates.dismissed` is that version: "Update…" opens the window, "Close" sends `updates/dismiss {version}` (a later release shows it again), "Don't show again" sends `updates/mute` (writes `notify: false`); both are written to the config, so every device stops showing it.
- The update window (BTN-163): the installed and the latest version, the notes of every release newer than the installed one (`notes`, newest first, markdown sanitized), an amber mark over a note with a `### Reverted` section (`revertedOf`: its text up to the next heading of level 3 or above), and "Update to <version>" (`updates/install`) or why there is none (`blocked`: not a service, not a git checkout, uncommitted changes, HEAD not on the installed version's tag; an npm install that is not global). The text under the button follows `source`: a checkout and a build, or an npm install. Under it the previous version (`previous`) with "Revert to <version>" (`updates/revert`) or why not — `storage` when the storage versions differ, with the way back from the `.bak` copies. An update under way is a toast (`UpdateProgressToast`, `progress`: "waiting for <projects>" while the chains settle, then "updating…"), and the page calls `location.reload()` once the service answers with another version. How it ended is a toast after the restart (`UpdateResultToast`, `result`): "Details" opens the window with the step, the rollback and the output, "Close" sends `updates/seen`. The process itself is in `docs/service.md`, "Updating from the page".
- Run label fallbacks (BTN-173): a launch whose run label named a provider without an account in the pool (`docs/sessions/models.md`, "Run profiles") is in `EvenKeelState.fallbacks` for 24 hours, from the launch log; each gets a toast (`FallbackToasts`, `web/src/layout/Fallbacks.tsx`) with the `chain.noAccountFor` notice. "Close" is per device: the closed ones are kept in `localStorage` (`even-keel.fallbacks.dismissed`, `<at>|<task>`).
- Unchecked CLI versions (BTN-249, `src/agent/versions.ts`): each agent adapter names the CLI version Even Keel was last checked against (`AgentAdapter.checked`, the same as the README's "Last checked against"), and the service asks each agent's CLI on the machine its `--version` at start, every 15 minutes and once its own copy of the checked version is downloaded (`VersionWatcher`; a failed call is one log line and keeps what was known). It is the machine's CLI whatever sessions run on (`Agent.system`, BTN-622), so "Yours, X" and the setup's "installed X" keep its version after a switch to Checked; the CLI check (`src/cli-check/run.ts`) asks `Agent.version`, the copy sessions run on. The warning is only for a CLI sessions run on (BTN-593, `VersionedAgent.runsOnInstalled`): its provider is in use — the shared one or a project's own (`providersInUse`) — and its `cli` setting is `system` (Yours, the default since BTN-603) or its `EVEN_KEEL_<AGENT>_BIN` is set. With `checked` (BTN-250) sessions run on Even Keel's own copy or wait for it, so a CLI merely installed on the machine, or a provider nobody picked, warns of nothing; the copy's progress is in separate blue header/card bands (`CliCopies`). Missing copies wait for explicit download consent, and download failure saves Yours for that provider. Such a CLI on any other version, newer or older, is in `EvenKeelState.cliVersions` with the `agent.uncheckedVersion` notice and goes into the warning banner under the header (`CliVersionBanner`); an unchecked Yours version does not hold the chain; a missing Checked copy does. An account whose Claude Code daemon runs another version than the pin joins the same list with its `account` and the `agent.daemonVersion` notice (`DaemonRefresh.outdated`, `docs/sessions.md`). The banner is one folded line (BTN-349, `cliSummary`): the one CLI with its versions ("Claude Code 2.1.309 · checked 2.1.310") or how many there are ("2 CLIs on versions…"); "Details" unfolds each one's notice and stays open until a reload; an installed CLI's entry (no `account`, source `system`) has "Switch to checked" (`CheckedSwitch`, BTN-603), the same consent dialog as the settings. "Hide" is per device and per version: `localStorage` `even-keel.cliVersions.dismissed` keeps the closed version by agent (by agent and account for a daemon), so the next update shows the banner again.
- The tab badge (`web/src/layout/tabBadge.ts`): a red dot — a check of `/status` fails (including a lost connection to the service), a yellow one — sessions are waiting for a reply; their count is in the title, `(2) Even Keel`. The badge without a dot is `web/public/favicon.svg`, and the dot is drawn onto it in a data URL.
- The content column is `--column` in `web/src/styles.css`: 94 % of the window, the header and the banners use the same variable.
- The wide header (`web/src/layout/Header.tsx`, styles in `header.css`) is the brand with the project key and the Stats link, then three blocks of one height and border. The work block: the chain toggle (`QueueMenu`, its queue panel hanging under the block from `.work-anchor`, outside the block so that its `overflow` does not clip it) and, only while sessions wait, the amber "N waiting for a reply" leading to the first of them. The account block (`AccountBlock.tsx`): the active account and a ring per limit window with its percentage and the time to the reset (`formatSpan`, the one compact duration format of the page: "4h 59m", "2d 23h"), its dot in the account's colour; then, when projects run on other accounts too (`AccountEntry.projects`, BTN-175), one segment of small rings, one per such account (`headerAccounts` in `web/src/state.ts`): each filled to its fullest window in the same amber/red heat, the account's colour as a dot in its middle. A click opens the accounts drawer (`docs/accounts.md`; the full list is the `/accounts` page), a hover or keyboard focus shows the card with a part per account of the header: the email, the plan, the projects running on it, every window with the reset moment, where the limits came from and when, and the sign-in left. The gear (`GearMenu` in `Status.tsx`) is a menu of Settings, Status and Tools; the Status row carries the worst level of the checks and leads to `/status` (below), and the gear's dot shows only when a check warns (amber) or fails (red). Below 1000 px the waiting block drops "for a reply", below 880 px the rings drop the reset time.
- On a narrow screen (≤760 px, `useNarrow`) the header is one row: the brand with the project key, the waiting count and a burger (`web/src/layout/Menu.tsx`) whose dot is the worst of the checks and the account. The burger's sheet is the wide header's blocks in one column, a line between them: the Stats row; the work block (chains and, while someone waits, the questions segment; the queue panel unfolds under it); the account card laid out in place (`AccountSheet`: the name opens the accounts drawer, then both limits with their resets, then the other accounts projects run on, a part each); and the gear's items as rows (`GearRows`: Status with its level, Settings, Tools).
- The status page `/status` (BTN-66, BTN-357, `web/src/pages/StatusPage.tsx`, the pure part in `status.ts`) is one centred column of at most 1100 px, everything at once. On top a band: "All is well", or the count of the checks that warn or fail (`problemsOf`, the failing first) with the first of them and its action. Then a tile per check of `systemChecks` (`web/src/layout/system.ts`: the server, the limits, the settings, Tally) in a `TileGrid`, two in a row up to 760 px: its dot and word, one line of `note` (when the limits shown were read — `RateLimits.updatedAt`, when Tally last ran), the `details` in a "?" tip, and the button of its `fix` (`CheckFix`: "Retry" for a lost server, otherwise the settings tab that fixes it — the config error's field by `configFixOf`, which the config banner uses too, Stats for a failing collector). Under them a card per tracker connection, one per profile in use (`EvenKeelState.trackers`, `docs/trackers.md`): its icon and name, at the right the state with the last good poll, a down one's error as a sentence (`trackerProblem`: a refused key, a timeout, an unreachable address, other; the raw error in the tip), the projects and task feeds it reads as tags by their labels — only those of a live connection not read for over 3 minutes (`staleReaders`, `STALE_READ_MS`) carry when they were — "Check", which reads its projects now (`chain/refresh` for each, a feed through its project, `refreshedProjects`), and "Open profile" (Settings → Trackers and CI, the primary button of a down one). A profile no project reads (the links' default) says so with "Add project". `?item=<key>` — a check's key or a profile's id — scrolls to that tile or card and lights it once (`block-glow`). The Tally check reads `EvenKeelState.tallyHealth` (`TallyService.health`, `src/stats/tally.ts`): stats not set up or turned off are neutral, waiting for the first run or a good last run are fine, a failed run warns, a collector halted until a restart or one meant to collect that does not run fails. The limits themselves stay in the header as two 2 px bars along its bottom edge, 5 hours on the left and the week on the right.
- What the page is busy with: every request except polling goes through `activity.track` (`web/src/live/activity.ts`) and shows the bar at the top of the window (`ActivityBar`). `useCommand` marks the pressed button `aria-busy` for the duration of its command, so a new command button needs nothing for its spinner. A command the service accepts at once and carries out later (`chain/restart`) keeps its button busy with `useHold` until the state changes; a block that reloads with its previous data on screen sets `aria-busy` on itself and is dimmed.
- The page installs as an app (`web/public/manifest.webmanifest`, `icon-*.png` icons are renders of `favicon.svg`, the `maskable` one has the mark with a margin for cropping). There is no service worker: the service serves a fresh `dist/web` anyway. The install button in Chrome appears only in a secure context: `localhost` or HTTPS; not on a bare `http://<IP>`.
