# Page: language

## Language (BTN-57, `src/language.ts`: `en`, `ru`)

- On the project page, `ProjectNotices` shows pause and ordering errors once per distinct notice (`projectErrors`, `sameNotice`), with settings and PR-mode fixes in the same band. A failed chain-control command stays by its controls.
- The `language` setting is the page language (`null` or no key — the browser language, English if it is unfamiliar), `promptLanguage` is the language of session prompts (absent — `language`, then English; `src/chain/prompts.ts`).
- The page translates its own chrome (`web/src/i18n/`, `ru.ts` is the source of the type, `en.ts` equals it) and server messages (BTN-62): pause reasons, cleanup, config, sign-in and command errors arrive as a code with values (`{ code, params, detail, cause, items }`, `src/notice/notice.ts`); the English text and the list of codes are in `src/notice/en.ts`, the Russian in `web/src/i18n/notices-ru.ts`, and the page builds the text with `say()`. A new code is an entry in both files; the type checks that the sets are equal.
- Errors in the page's words (BTN-297): a message a person reads names a setting by its label on the page, says what to do and, where the page has a place for it, gives a button there; paths of the config (`projects[0].branch`, `ABC.chain.active`) stay in the log and `config-import`. A setting refused at its field (an `ErrorStrip` under one field, `FieldNote` under a setting of several controls; `docs/design.md`, "Field strip") is said by `sayAtField`: the texts of `web/src/i18n/fields-en.ts`/`fields-ru.ts`, by the value; a code they lack falls back to `say()`. A test keeps paths out of them and out of the `wizard.*` texts. In `dev:fake` a project saved with an empty repository path is refused at that field (`config.repoEmpty`).
- Short messages (EKR-87): a message is one or two sentences — what happened and what to do. Its text, the labels over its commands and its buttons do not repeat each other: an instruction the text gives has no label over the command, or one word such as the shell. It shows one command, the one this installation needs; a second only when Even Keel cannot pick (a trust pause saved before it knew whether it runs as a service). A command reads by eye: no base64, no `-EncodedCommand`, no line quoted for two levels of process arguments; where `runas` needs that, Even Keel writes a short script into its state folder and the command runs the file (`state/trust/<task>.ps1`, `docs/sessions/agents.md`). The why — which user the service runs as, what a retry does — goes into a `?` tip or the log, not the text. The test `web/src/i18n/noticeLength.test.ts` measures every text of `src/notice/en.ts` (as the page shows it) and `web/src/i18n/notices-ru.ts`, each parameter counted as one character, against `NOTICE_LIMITS` (`web/src/i18n/noticeLength.ts`: 200 English, 220 Russian). The texts longer than that when the rule came are in `web/src/i18n/notice-lengths.json`, and a length there may only go down: the test fails on a text past its limit and asks for `npm run notice-lengths` (it rewrites the file) when one got shorter. A new code starts at the limit.
- The way to a fix (`web/src/pages/noticeFix.ts`, `FixButtons.tsx`): `noticeFixOf` maps a notice — or the first of its items, then its cause — to a tab of the project's settings (`git.noBranch`, `chain.emptyLabels`, `prompt.empty`, `forward.foreign`, `chain.limitSpent`), Settings → Trackers and CI (`ci.noToken`, `ci.denied`, `review.denied`, `profiles.paused`), Settings → Interface (`config.token`, `config.tokenShape`) or Accounts (`account.*`); `NoticeFixButton` sits under the error of a card, of a project's page, of its carry and of its CI. The config banner opens the tab of the refused field (`fieldOf`, then `fieldFixOf`). A new code that a setting, a profile or an account fixes gets an entry in `BY_CODE`.
- A session's limit is one `Band` (`LimitNotice.tsx`, `limitMessages.ts`): only the newest of the command refusal, the agent's report and the continuation plan. The older ones are not shown (BTN-579): the agent's report is the last line of the activity feed anyway, and a refusal already names the reset. Its full-width `ButtonWithTip` opens Project settings → Sessions; the attached `?` button holds the account and recovery instructions in a press-only tip, using the same `useTip` toggle as `HelpTip`. The refusal belongs to that session and goes away when it resumes. The account and provider in `chain.limitSpent` come from the task's run choice through `currentAccount` and `requireLimit`; older notices without these optional fields still render. `say` and `sayIds` format its reset in local time, including nested notices, while the log retains ISO. The provider's shared or own pool can be changed in Sessions; changing the task's provider label is another option. Neither the panel nor the event toast promises the header's account switch will change a task on another provider.
- Event toasts (`EventToasts`, `web/src/layout/pageEvents.ts`): a chain held by the usage limit, a red main (a failed run of main, an open fix of it or a paused `ci.*`/`check.*` with its commit — one toast per commit), a session waiting on `AskUserQuestion`, a carry held by `forward.conflict`, work left in the folder of a task out of the chain (`EvenKeelState.works`; not one with a pull request and nothing uncommitted, not one a session is working in, and a closed task's only once its cleanup left a warning in `leftovers`; the service itself never gives work read before the task's session last acted, `docs/chain.md`). Only what comes while the page is open gets a toast (`freshEvents`; the first state is old news), "Open" goes to the project (the CI tab, the task's session, the backlog or the task's card), and a toast goes once its event is over; the state itself stays on the card.
- Work no commit of main holds (BTN-298, `EvenKeelState.works`, `docs/chain.md`): a chip with a red outline — "uncommitted · N" (files) or "not merged · N commits" — on the chain row next to "question" and in the session panel's status line, and on the backlog row after the milestone. One rule decides it for the chain row, the backlog, the task card and the toasts (`shownWork`, `web/src/work.ts`, BTN-365): only once the task is out of the chain and no session of it is mid-turn — in the backlog or out of the chain, skipped, waiting on its pull request with uncommitted files (its commits are the pull request's), or closed with a cleanup warning in `leftovers` (BTN-332). A task the chain leads — mid-turn, between turns, asking — or one in Done whose cleanup is still under way has no chip, callout or toast: its files are its session's, and the server's read of them may catch a long turn before its commit. A closed task with the chip keeps its row out of the archive (`archiveView` skips a block with `work` and does not count it), in its milestone, and carries the cleanup's warnings (`ChainBlock.leftovers`) into the chip's tip with a "Done" button on the row (`chain/dismiss`); the project head's cleanup warnings leave such a task out, so it is told of in one place. Once the work is committed and merged or the folder is deleted, the chip goes and the row goes to the archive; the warning, if not dismissed, comes back to the head. `WorkChip` (`web/src/ui/WorkChip.tsx`), its `Tipped` tip the counts, the path, the branch, a closed task's cleanup warnings and what to do. The "Backlog · N" tab gets a red dot when one of its tasks has some (`backlogWork`), and the task card a red callout above the description with the same lines and the two ways out: answer and move the task back to Todo (exception 9 starts a new session with a handoff), or commit and merge by hand.
- The carry of a release project (`Forward` in `web/src/pages/Project.tsx`, `ForwardView`, `docs/chain.md`) is a band on the release project's page. A held `forward.conflict` (BTN-369) is one red line — "1 commit of EKR conflicts with BTN in 2 files" — with "Resolve with the agent" (`forward/resolve`) at its right and "Details" folding the files and git's output (`.forward__more`) under it; "Carry now" is not offered for it. While the carry session is asked for or at work (`ForwardView.agent`) the band is a note marked with the working lamp's colour — "The agent resolves the conflict after the current task of BTN" or "… in the chain of BTN" — with "Open" to the session's row in the main project's chain (`/p/<id>#<KEY>-CARRY`). Any other hold, `forward.failed` among them, keeps the old band with "Carry now". The carry's rows in the main project's chain are told in `docs/chain/projects.md`, "The carry session"; `ChainList`, the session panel and the drag treat a carry like a fix (`isOwnName`), without the CI button.
- The Russian page speaks to the user on «вы», the pronoun in lowercase («ждёт вас», never «Вы»); the CLI version option is «Своя», not «Твоя». Jokes and dialogues (`project.idle`, `home.memes`, `basement` in `ru.ts`) keep «ты»: a character's voice. A test in `web/src/i18n/i18n.test.ts` walks every Russian text, templates by their source and by a call with a stub, and allows «ты» only under those keys.
- The service log is in English; git and CLI output (`detail`) and strings saved before BTN-62 (the old `state/chain.json`) are shown as is. Data (transcripts, labels, tasks) is not translated.

CI failure events share one key per project and commit and list every failed CI kind once. The project's effective CI settings decide whether it is `red` (at least one counted kind with the guard on) or `ciRed` (only uncounted failures). Both name the failed CIs and open the CI panel; only `red` promises that the next task waits. Open fixes and failed local checks still give `red` independently of the CI views. `toastEvents` refreshes an open toast in place as CIs fail or recover. `freshEvents` compares the previous events, so a closed toast stays closed when only another optional CI fails, but returns when `ciRed` becomes `red` and the chain now waits. Once the event disappears, its next occurrence is new again. `?event=redBoth` fails Forgejo Actions and GitHub Actions on the same commit after the first fake state; only Forgejo counts, as in `?event=ciRed`.

Conflict events require an unassigned carry (`ForwardView.agent` absent). Assigning an agent removes the event and its toast; skipping that session while the conflict remains brings the same event key back, which `freshEvents` sees as new after the intervening state without it.
