# Sign-in to the page

One owner signs in to the page (BTN-1619), with no passwords: a passkey in one press, or the owner key. Each sign-in gives the browser a token of its own, listed and revoked in the settings group "Sign-in and devices". The tables are `people`, `access_tokens` and `passkeys` (`docs/storage.md`); the code is `src/guard.ts` (who is asked), `src/access/` (the book of tokens, the passkey ceremonies, the routes) and `web/src/pages/SignIn.tsx`, `SignInSettings.tsx`, `passkey.ts`.

## Who is asked

The guard (`guard()` in `src/guard.ts`) runs before every route and gives one verdict:

| Request | Verdict |
| --- | --- |
| From this machine by a loopback name (`localhost`, `127.0.0.1`, `[::1]`) | pass, no sign-in: the sessions' hooks (`EVEN_KEEL_URL`) and the browser on the machine itself |
| From this machine by any other name — a proxy such as `tailscale serve` or a Tailscale Service — when the owner key is set or an invitation turned the sign-in on | asked to sign in, as from the network; the hook routes (`hookRouteOf`) still pass |
| No owner key set and the sign-in not turned on | from this machine by any name — a proxy on it included — pass, no sign-in; from elsewhere 401, `/invite` too; the settings group shows a band "Sign-in is not set up" whose button invites a device |
| `Authorization: Bearer <owner key>` | pass: scripts keep the key |
| A device token in the cookie (or as a Bearer) | pass, with the device: its `seen_at`/`seen_from` are noted (written at most once a minute) |
| `?token=<owner key>` in the address (an old link) | the device is signed in with the key and sent with 303 to the address without it |
| Not signed in, a page file (`GET` outside `/api/`) or `/api/auth/*` | a visit: the page loads and draws its sign-in screen |
| Anything else | 401 |

In Docker the host's browser reaches the hub through the container's gateway, not loopback: with the owner key set, `localhost` on the host is asked to sign in too, and the devices list shows the gateway's address for every device.

**Without the key** (BTN-1656) a hub takes devices by invitation alone. The first "Let in" turns the sign-in on: the mark `sign_in_on` (step 83, `AccessBook.signInOn`, `DeviceBook.signInOn` for the guard) makes a proxy's name ask as the key does. It is a mark of its own, not "a live token is there", so "Sign out everywhere" or signing the last device out never opens the page again. The browser that pressed that first "Let in" by a proxy's name and had no token of its own gets one with the answer (`invites/admit`), else it would shut itself out; on a loopback name it needs none. Open pages of other browsers by the proxy's name get 401 from then and land on the sign-in screen, which without the key has no key field, only the passkey and the line about an invitation. The key stays the spare way in: set later, it signs in as before, and the mark stays. "Turn sign-in off" in the "Sign-in by key" card (`POST sign-in/off`, only without the key, behind a confirmation) drops the mark and signs every device out, so a later invitation revives no old token; with the key set it answers `auth.signInKeepsKey`. Without the key the OAuth callback's cookie is signed with a secret of the process instead (`oauthCallbackCookie`).

**The first invitation through a proxy** (BTN-1667). Before that "Let in" the phone that scans the QR comes through the same proxy on this machine as the PC, so the guard lets it in unasked too. `/invite` must still take the link, so `GET /api/auth/state` answers `takesInvite` apart from `signedIn`: true for a browser not signed in and for one let in unasked — no key, no mark, no device token, a name that is not loopback; false for a browser with its own token and for a loopback name, which keep the "signed in already" screen. Nothing else reads it: such a browser stays in for the page and the routes for a signed-in browser (it may make the invitation itself) until the "Let in" turns the sign-in on. A proxy on another machine is no way to the first invitation: its requests come from elsewhere and get 401 before any route.

The address of a request behind a proxy on this machine is the first `X-Forwarded-For` (`addressOf`); from elsewhere the socket's, which a header cannot fake. The machines' link, the MCP gateway and the hooks are not touched by the sign-in.

A blocked service (a broken config) has no book: there the cookie holds the key itself and the server's form asks for it, as before BTN-1619.

## The routes

`accessRoute` (`src/access/routes.ts`) answers `/api/auth/*`; an error is 400 `{ error, notice }` with an `auth.*` code.

- Open to a visit: `GET state` (`AuthState`: signed in, key set, a passkey made on this request's host name, this device), `POST key { key }`, `POST passkey/options`, `POST passkey { response }`, `POST invite/open { link }` and `POST invite/wait` (`JoinView`, [Invitations](#invitations)).
- Only signed in (else 401 `auth.signInFirst`): `POST passkey/register/options`, `POST passkey/register { response }`, `POST passkey/remove { id }`, `POST devices` (`DevicesView`; a POST as the page's other queries), `POST devices/revoke { id }`, `POST devices/revoke-others`, `POST invites/create` (`InviteMade`, with the known outside `origins`), `POST invites/origin { origin }` (`{ origin, origins }`), `POST invites/admit|decline|cancel { id }`, `POST sign-in/off`, `POST sign-out`. `DevicesView.signInOn` says an invitation turned the sign-in on.

A sign-in sets the cookie (`HttpOnly`, `SameSite=Strict`, a year) and revokes the token the browser held before, so one browser is one row.

## Passkeys

WebAuthn through `@simplewebauthn/server` and `@simplewebauthn/browser`. The RP ID is the host name the page was opened by (`hostnameOf` of `Host`, which `allowedHosts` already admitted), the origin the browser's `Origin`: a passkey works only on the name it was made on, and its row in the settings shows that name. Attestation `none`, discoverable credentials, user verification preferred. A challenge lives 5 minutes, is used once and is bound to its kind and host; at most 200 wait at once, since the routes are open.

A passkey needs a secure context — HTTPS or `localhost`: on plain `http://<address>` the screen has no passkey button, only the key with a line saying why. It also needs a name: WebAuthn refuses an IP address as an RP ID, so on `http://127.0.0.1` or any v4/v6 address (`passkeyHost` in `src/access/passkey-host.ts`, shared with the page) neither the sign-in screen nor "Sign-in and devices" shows a passkey button, a line says to open `localhost` or an HTTPS name instead, and the server answers both options calls with `auth.passkeyByName` (BTN-1632). Where passkeys work but the hub has none made on this name (`AuthState.passkeyHere`, BTN-1631), the button gives way to a line too: the browser's dialog would list only the phone and security keys. After a sign-in with the key, where passkeys work, the screen offers to add one on this device.

A device signed in with a passkey keeps that passkey's host name (`access_tokens.passkey_host`): its row in the devices list tags it "passkey on `name`" instead of a bare "passkey", so two "Chrome on Windows" tell apart. Tokens made before BTN-1631 have none.

A browser answers `NotAllowedError` both when the person closes its dialog and when it refuses with no dialog at all — Telegram's in-app browser on iOS has `PublicKeyCredential` and refuses at once (BTN-1630). `ceremony` in `web/src/pages/passkey.ts` tells them apart: a refusal within `NO_DIALOG_MS` (1 s) with the page never losing focus or visibility is the browser's, and the screen and the settings group say the browser cannot use passkeys and to open the page in Safari or Chrome; a slower one, or one after the page lost focus, is "No passkey was picked".

## The owner key

The owner key is `EVEN_KEEL_TOKEN` in the hub's `.env` (the "Owner key" row of the group, `PageToken`). A token signed in with it keeps the key's mark (`key_mark`, an HMAC of the key, never the key): when the key changes, live, `AccessBook.keyIs` revokes every token signed in with another key; passkey sign-ins stay. Whoever can open the `.env` on the server can always sign in: there is no reset by mail.

## Invitations

A new device can sign in without the key: a device signed in invites it (BTN-1655, `InviteDesk` in `src/access/invites.ts`), as a Tailscale invitation does. "Invite a device" at the bottom of the "Devices" card posts `invites/create` and opens `InviteDialog`: the QR (`QrCode`, `web/src/ui/Qr.tsx`, drawn on the page by `uqr`, no network) and the link `<page origin>/invite#<secret>` with a copy button, a countdown, and "Waiting for the link to be opened". The secret is in the fragment, so loading the page never sends it to the server or a proxy's log.

**The link's origin** (BTN-1661, `web/src/pages/inviteOrigin.ts`) is never a loopback name: the PC that makes the link is signed in already, and another device cannot open `localhost`.

- A page open by an outside name links to its own origin, with no choice.
- A page open by a loopback name (`loopbackName`) takes the hub's known outside origins from `InviteMade.origins`, the last seen first. Two or more — an "Address" select, the last seen by default, the QR and the link redrawn for the pick; one — the link to it at once; none — instead of the QR a band "Another device cannot open localhost…" with the guide's button to the proxy and Tailscale section, and an "Outside address" field. With known origins a quiet "Another address" button opens the same field, so one mistyped address never becomes the only way out.
- **Known origins** are `PageOrigins` (`src/access/origins.ts`), the table `page_origins` (step 84, `origin` the key, `seen_at`). The guard notes the `Origin` header of a request it let in (`GuardSettings.origins`, `src/server-guard.ts`, verdict `pass` only) when its host is not a loopback name: a browser sends `Origin` with every POST, and nearly every query of the page is one. The scheme and port are what the browser's address bar has, not what the hub sees behind a proxy: Tailscale ends TLS, the hub gets http, and `Origin` says `https://<name>:8443`. A forged one never lands, since the request had to pass the guard (the name in "Other page names", and the sign-in where it asks). Written to the database at most once a minute per origin (`ORIGIN_WRITE_MS`), as a device's `seen_at`; the dialog lists those seen within 90 days (`ORIGIN_KEPT_MS`).
- **A typed origin** goes to `invites/origin { origin }` (`typedOrigin`): no scheme means `https://`, only http and https, the origin of what is typed is kept; a loopback name is `auth.inviteOriginLocal`, anything unreadable `auth.inviteOriginBad`. The answer is the origin and the new list, and the origin is remembered as seen now. The hub does not try to open it: from Docker it may not see its own Tailscale name, and a wrong address shows at once on the phone.

- **Table** `device_invites` (step 82): the link and the claim only as SHA-256; `waiting` (unopened) → `opened` (claimed, with the digits) → `admitted` / `declined` / `cancelled` → `used` (the token collected). An expired one is dropped from the table a day later. The same step adds `access_tokens.invite_id`: the device's row is tagged "by invitation".
- **Open.** `invite/open { link }` from the new device: the first browser to open a live link claims it — a claim secret in the cookie `even-keel-invite` (`HttpOnly`, `SameSite=Strict`, `Path=/api/auth/invite/`, never on screen) — and two random digits (00–99) are drawn. The same browser opening it again gets its own claim back; any other gets `used` and the owner hears nothing, so a link cannot be flooded with requests. A wrong, expired or cancelled-before-opening link is one answer, `gone`.
- **Wait.** `invite/wait` is a long request: it answers at once when the invitation is decided, else after `WAIT_MS` (25 s) with `waiting`, and the page asks again. `admitted` comes with the device's own token in the sign-in cookie, the same as after the key; only the claiming browser can collect it, since the claim is the cookie, not the link or the digits. That answer can be lost: a phone's screen goes dark while it waits, the hub issues the token into a dead connection and the invitation is `used` (BTN-1664). So while no request has presented that token (`AccessBook.isUnpresented`, memory only: after a restart every token counts as presented), the same claim asking again — `invite/wait` or `invite/open` — gets `admitted` with a new token and the old one is revoked, so "Devices" keeps one row. The window is the invitation's life, or `REISSUE_MS` (2 minutes) after "Let in" when it ends sooner; after it, after the token was presented or the device was signed out from "Devices", the claim gets `gone`.
- **Decide.** The dialog and the card read "Sign-in and devices" anew on the event `devices` of the stream (`InviteDesk.changed` → `EventHub.broadcast`, `LiveSource.onDevices`), so "Waiting…" turns into "<device> opened the link at <time>", the digits large, "Let in" and "Decline". "Let in" is for a person who saw the same digits on the new device: a link that leaked and was opened first by someone else shows other digits. Any device signed in can decide. A closed dialog leaves the invitation as a row of the "Devices" card with "Let in" and "Decline" once opened, and "Cancel"; nothing else on the page tells about it, so it is never approved by habit.
- **Limits.** A link lives `INVITE_MS` (10 minutes), is used once and dies on cancel; at most `MAX_INVITES` (5) wait at once (`auth.invitesFull`). The open routes take `INVITE_CALLS` (30) calls a minute per address (`RateLimit`, `src/access/rate.ts`), the next is 429 `auth.inviteSlowDown`.
- **Without the key** the invitation works the same, and its first "Let in" turns the sign-in on ([Who is asked](#who-is-asked)); the band "Sign-in is not set up" offers it.
- **The new device** (`web/src/pages/InviteJoin.tsx`, drawn by `main.tsx` on `/invite` before the page) shows the digits and "Waiting for approval where the link was made", then its own screen for each end — declined, expired, cancelled, used by another device, gone — or, let in, the passkey offer of the key's sign-in and the page. A lost link is no end (BTN-1663, `inviteFollow.ts`): `invite/wait` holds up to 25 s, and a phone drops it when its screen goes off or the tab goes to the background, while the claim cookie keeps the place and the hub gives the outcome at the next ask. So a failed fetch, or an answer with no notice of ours (a proxy's 502), keeps the screen with "Connection lost, trying again…" under it and asks the same again — `invite/open` until the hub took the link, `invite/wait` after — in 1, 2, 4, then every 8 s (the hub allows 30 calls a minute), and at once when the tab comes into view or the network comes back. Only 60 s of a lost link on a page in view ends it with `auth.inviteNoAnswer` and "Try again"; a refusal of the hub (`auth.inviteSlowDown`) ends it at once with its notice. A browser signed in already does not take the link: the screen says so and leads to the page, since the link may be meant for another device. "Signed in already" is the state's `takesInvite` false: a browser a hub without the key let in unasked by a proxy's name takes it ("Who is asked").
- The sign-in screen says under the key field where to get an invitation, with a link to the guide.
- **Scan a QR** (BTN-1657) under that line, only where the browser has a camera (`cameraHere`, `web/src/pages/qrScan.ts`: a secure page, `getUserMedia` and a `videoinput` among `enumerateDevices`, which lists kinds before any permission). It is for an installed app: on an iPhone the app keeps its cookies apart from Safari's, and the system camera opens the link in Safari. `QrScanDialog` (lazy, with its decoder) shows the back camera (`facingMode: environment`, `playsInline` and `muted` or iOS goes full screen) and reads a frame every 200 ms at 720 px at most with jsQR (`qrRead.ts`: plain JS bundled into the page, no network; Safari on iOS has no `BarcodeDetector`). Only a link of this page's own origin with `/invite#<secret>` is opened, by `location.assign` in the same window; an invitation of another address names its host, any other code says it is no invitation, and scanning goes on. A refused or missing camera is the dialog's error band.

## Revoking

`AccessBook` keeps the live tokens in memory, so the guard stays synchronous, and writes every change through. A revoke — "Sign out" of a device, "Sign out everywhere but here", a new key, a sign-in over an old token — closes the open event streams of those devices (`EventHub.closeTagged`, each stream tagged by its device's token id), and the page loads the sign-in screen.

A stream the service ended after its 200 is reopened by the browser itself, and EventSource never says why a stream failed, so the page does not wait for a refused reconnect: on every failed stream, whether the browser retries or gave up, and each time the tab comes back into view (`visibilitychange`, where Safari may hold a dead stream with no error yet) `LiveConnection` asks `GET /api/auth/state` (BTN-1629). A 401 (a hub without sign-ins whose token changed) or `signedIn: false` stops the connection and reloads the page into the sign-in screen; a failed request or another status is a lost link, and the reconnecting banner stays. One question is in flight at a time.

## The checks on every request

Every request is checked whatever `EVEN_KEEL_HOST` is:

- its `Host` must be `localhost`, `127.0.0.1`, `[::1]`, `EVEN_KEEL_HOST` or a name in `allowedHosts`, otherwise it gets 403. This stops DNS rebinding — a foreign site whose name was pointed at `127.0.0.1`;
- an `Origin`, if the request has one, must be the page's own: the same name and port as its `Host` (`https://name` matches a `Host` of `name` without a port, as an HTTPS proxy sends it). So neither another site open in your browser nor another app on the same name — a dev server on `localhost:5173`, a service on another port of your tailnet name — can post to the page. Requests without `Origin` (the plugins' hooks, `curl`) pass;
- a `POST` to `/api/` must be `Content-Type: application/json`, otherwise it gets 415: a browser cannot send that type to another site without asking it first. A script posting to the API sends the header, as `curl -H 'Content-Type: application/json'` does.

The page and its sign-in screen cannot be embedded in a frame, even on the same site.

Its content security policy permits scripts and connections only from its own origin, with inline styles and local/data/blob images and media. The page sends no referrer. A reverse proxy must preserve these response headers. An already open tab receives a new policy when reloaded.

Each sign-in gives the browser a token of its own in an `HttpOnly`, `SameSite=Strict` cookie. Starting MCP OAuth also sets a separate ten-minute `HttpOnly`, `SameSite=Lax` cookie for the callback alone, so the browser can return from the provider. The page's access cookie stays `SameSite=Strict`; the callback cookie cannot open other pages or API routes.

## dev:fake

`/?signIn` draws the screen (`?signIn=nokey` — no owner key on the hub, `?signIn=elsewhere` — passkeys made only on other names): the key is `owner-key`, a passkey always passes without the browser's dialog (`?signIn=nopasskeys` — refused at once, as by a browser without passkeys), and signing in drops the parameter. The settings group reads `web/src/live/fakeAuth.ts`: three passkeys on two names and four devices, two of them "Chrome on Windows", one by invitation, this browser one of them; its band follows the fake `EVEN_KEEL_TOKEN` (unset by default), `&signInOn` starts with the sign-in an invitation turned on (in the page state too, so the setup's Phone access step is checked: `/setup?step=phone&signInOn`), and a fake "Let in" turns it on in the settings group alone. `&invites` starts with two invitations waiting, one opened; an invitation made in the dialog is opened by a fake phone 3 s later, digits 47. dev:fake is open by localhost, so the dialog shows the loopback cases: two known origins by default (`https://hub.example.ts.net:8443` seen last, `http://192.0.2.10:4747`), `&origins=1` the first alone, `&origins=0` none and the address field; a typed address is checked as the hub's `typedOrigin` does. `/invite` is a browser signed in already, `/invite?signIn` the new device: let in 3 s after opening, or `&invite=declined|expired|cancelled|waiting|used|gone`, or `&invite=lost` — every wait fails as a dropped connection.
