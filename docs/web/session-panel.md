# Page: the session panel and the chat

Session account pills (`AccountTag`, `accountOf`) resolve a folder key first, then an e-mail within the session's agent when known. Every caller uses the session id to find its agent in the current session list; the chat can also take it directly from its target session. Without an agent, old records keep the first e-mail match. An e-mail belonging only to another agent leaves a neutral pill with the recorded address's name part. Stats and received-tools records use the same lookup; their own response formats carry no agent.

- The chat window carries the same ↗ link to the session on claude.ai as the session panel, while the session has one.
- A session that is starting (`sessionStart` in `web/src/state.ts`, `web/src/ui/SessionStart.tsx`): the current task's row shows a pill with the phase and the time since the start began, the row shimmers and its lamp is a blinking ring; the session panel shows a loading card with three steps instead of the session's facts. The phases: `launch`, `handover` and `resume` while `CurrentTask.starting` is set (the dispatcher is preparing the worktree, handing over, or — `CurrentTask.move` is `resume` — continuing the same session after a limit or a temporary error, EKR-120), `boot` while the page does not see the new session id yet, and while it sees it idle before its prompt lands (`idleBeforePrompt`: the CLI's idle reads as `waiting`, but with an empty context and feed, no question, no startup dialog and no API error it is no wait for a reply — the row, the header's "waiting for a reply" and the tab badge leave it out too, until the 5 minutes below are over), `answer` while that session works and its context is still empty (its feed is shown under the card). The time counts from the journal row of the new session; after 5 minutes the page stops calling it a start. Delivering the user's answer is no start: while the dispatcher stops the session and resumes it in place (`CurrentTask.answering` next to `starting`), the page shows that session at work (`working`, no open question) instead of a stopped one, so the chat does not say it has finished. Nor is what follows a start: a session whose journal run has an answer or a resume gets no phase, though its respawned process is fresh and its context may still be empty (a first turn that ended on `AskUserQuestion` has no assistant message in the transcript yet).
- The session's facts (`SessionBody` in `web/src/pages/SessionPanel.tsx`, fact components and `TipValue` in `web/src/pages/SessionFacts.tsx`, styles in `web/src/pages/facts.css`) are quiet until they need attention: Time, Cache, Context and Tokens are small muted figures, and only the session state is always loud. A tile turns loud by the `tone` of its `Fact` (`web/src/ui/blocks.tsx`), `warn` or `danger`: Context from the `warn` and `danger` thresholds of the scale against the session's own window (`contextFill`, `SessionView.contextWindow`; tokens alone until the agent reports a window; BTN-187, `docs/sessions.md`), Cache in the last fifth of its lifetime and once it is cold (`cacheTone`; a finished session stays quiet), Time and Tokens never. A fact is its figure alone; the details are a tip opened by pointing at the figure or pressing it (`TipValue`, `web/src/ui/useTip.ts`, the same tip as the chain blocks' counters): Time the session's start, Cache its lifetime, Model the provider, the model and the effort, Tokens the split by kind. Model (`ModelFact`, BTN-1098) is the model and the effort of the last answer from the transcript (`SessionView.model`, `effort`), the model's short name — "Opus 5.5", "GPT-5.1", the catalogue's name of an OpenCode model (`SessionView.modelTitle`), with a `free` badge for OpenRouter's `:free` (`ModelName`, `shortModel` in `web/src/ui/modelLabel.ts`, BTN-1348) — and the effort's bar scale as a task's run tag (`EffortBars`, BTN-1369); the tip has the full name with the id and the effort's word: only the model's tail is cut, the badge and the scale stay whole, and an agent that writes no effort shows the model alone. Context is one line (`ContextFact`, BTN-613): the label, a full-height divider, the bar, a short divider, "38%", another short divider and "96k / 250k" (BTN-1374), as the CLI download meter; the chain row's and the chat's tips read "96k of 250k (38%)"; it takes the whole row, Model (two columns) and Tokens under it. The window of a past session from "Sessions of the task" (`SessionWindow`) has the same rows — Started, Last turn and Worked, then "Context at the end", Model and Tokens, then separate Branch and Folder facts when recorded — from its record (`SessionRecord.agent`, `model`, `modelTitle`, `effort`; the agent is the account folder's the record was found in). For other agents the model value starts with the provider and a vertical bar, as in the task's run tag. In that window every fact is quiet. The Activity feed under the facts has no title: the feed itself is the press that opens the whole transcript, or the chat of the session the panel answers (`Feed.onChat`); a press that leaves selected text opens nothing, and from the keyboard the feed is a Tab stop opened by Enter or Space. A line's time is short, by the rule of [docs/design.md](../design.md) ("Time").
- In the task’s session list, the launch reason comes first. Resumes, answers and context compactions each have an icon and a count when positive. Their tooltips explain the events. Postponement, skipping and replacement each occupy a separate line.
- The chat with the current session (BTN-101; invariant 1, exception 6). The session panel of the chain's current task has a "Chat" button instead of "Open"; it is amber (`panel__chat--waiting`, the colour of `--lamp-waiting`) while the session waits for a reply. The claude.ai link is the `↗` icon `.panel__remote` in the panel head. A press on the Activity feed opens the chat too; the read-only whole transcript is what the feed opens only where there is no chat: past sessions (`SessionWindow`) and blocks other than the current one — writing to a past session would fork the work. The chat is `TranscriptWindow` with a `chat` target (BTN-182), laid out like the Claude app: no PROMPT/ANSWER labels, the feed a centred column of 800 px with no time column — the HH:MM of a line shows in the left margin while it is pointed at, the full date and seconds in its tip (`LineTime`); the calls are grouped (BTN-185, below). A user line shows only what the user sent (`replyParts`, `docs/sessions.md`): the answers as a compact card on the left (`AnswerCard` in `web/src/pages/AskPanel.tsx`: each question bold with its answer under it; when the call is in the transcript the card opens into `AskCard`, the read-only question with the chosen options ✓ green, the rest dimmed), then the user's own words and files as a right-aligned bubble (`UserBubble`), folded past 8 lines or 600 characters with "Show more". A tool line of an `AskUserQuestion` that was answered or is open in the chat is not shown, since the answer card or the bottom stands for it; neither is the error result through which a stop or a resume delivers its answer (`[Tool call interrupted: …]`, not a failed line) nor the synthetic `No response requested.` after it. The open question is `AskPanel` at the bottom: a card whose head holds the question and a pager "1 of 3" (BTN-900: a box on `--surface` with the position in 14 px 600 between two 28 px chevron buttons, 36 px on a coarse pointer; it is the only count of the questions, a skipped one is reached by its arrows), option rows with radio buttons or checkboxes (`multiSelect`), the label bold and the description muted, "Other" with a multiline field, a `preview` as a mono block beside the options, and "Skip" and "Next" — "Submit" on the last question (Enter in "Other"; Shift+Enter inserts a line). The head and the options scroll as one area (`.ask__scroll`, EKR-117: up to 50dvh, 40dvh on a screen up to 760 px), so a long question never pushes the options or the buttons off a phone; "Skip" and "Next" stay under it, and another question starts it from the top. On a screen up to 760 px the pager floats into the head's top right corner and the question flows around it, its first line centred on the pager; a wider screen keeps the question and the pager in one row. The pager sits in the fieldset's legend, so it still turns the questions while the reply is locked. A pick does not advance by itself, and a reply may skip questions — "Send" waits for any answer, text or file. A question known only from the job file (`ask.unsaved`, `docs/sessions.md`) gets a line under the panel saying that a reply from here resumes the session without its last message, while Remote Control keeps it. The session card's Activity feed shows the same parts of a user line in one row, joined with ` · ` (`feedText` in `web/src/pages/feedLine.ts`). A question asked in plain text gets `ChatComposer`: text, files and "Send". In both reply fields Enter sends or advances, Shift+Enter inserts a line, and Ctrl+Enter / Cmd+Enter also sends. `sendsReply` (`web/src/pages/chatKeys.ts`) leaves IME confirmation alone (`isComposing` or key code 229). On a coarse pointer (`useCoarsePointer`, `matchMedia('(pointer: coarse)')`) Enter only inserts a line: the buttons send or advance, and keyboard hints are hidden. Enter on a question's radio or checkbox neither submits nor advances. Sending immediately clears the text and files and leaves the field available for the next draft; "Send" and the options of a question are locked unless `lamp` is `waiting` or `error` and the session waits on no startup dialog (`waitingFor` is `null` or it is asking); an idle API error says in the send button's tip that a reply resumes the session, while a retry still reported as `working` follows the usual mid-turn rules; after sending they stay locked (`useHold`, 90 s or until the lamp, the open question or the session's last transcript line changes — `holdKey` in `web/src/pages/composerHold.ts`: a turn short enough to end between two updates of the state leaves the lamp `waiting` and the question as they were, BTN-220). The composer never offers a question the feed already holds an answer to (BTN-921, `shownAsk` over `answeredAsks` in `composerHold.ts`: an `answer` line of the transcript or a reply sent from this window), not out of its own memory, so a rebuilt chat, a reload or a late view of the session stopped and resumed to take the answer does not bring the panel back. One chat window per task (BTN-948): neither the window nor its composer is keyed by the session, so a handoff to a new session swaps only the feed (`TranscriptWindow` resets its lines, sent lines and viewer on a new `sessionId`, the composer its pending question and cold-cache dialog) without closing and reopening the dialog; a draft outlives a new question and a handoff; the picks reset when the question's id changes. The draft's text and files are also kept per task in the browser's IndexedDB (EKR-24, BTN-948, `web/src/pages/chatDraft.ts`, database `even-keel` v2, store `taskDrafts`, keyed by `draftKey(project, row id)` since a task key is not unique across projects; `localStorage` cannot hold a `File`): `useChatDraft` in `useChatDraft.ts` reads it as the composer opens — what was typed before the read finished wins — and writes it 400 ms after a change and as the window closes, so it outlives closing the chat, a handoff, the task's close and reloading the page. A draft of the old store `chatDrafts`, kept by `sessionId` before BTN-948, is read when the task has none and moved to the task. Starting a send clears the saved draft. A failed send prepends its text and files to the current draft and saves the reason, including when the window is closed. The picks are not part of it. Once per page load `App` prunes the task drafts of tasks the state no longer knows (`knownTasks`: `tasks`, closed ones too, and the keys of `taskSessions`) and the old session drafts of sessions it no longer knows (`knownSessions`), leaving any written in the last 24 h, since right after a start the service may not have read it yet (`staleDrafts`). Where the browser refuses IndexedDB (a private window may), the draft lives only while the window is open. Every transcript window of a task has the field, not only the chat: one opened from the feed of a block without a chat or from the session list gets `ShutComposer` — the same `ComposerBox` with the task's draft, "Send" off and the reason in its placeholder and the send button's tip (the task is closed; the session has finished; otherwise sessions are answered in the task's chat). A reply stops the session and resumes it, so for a few seconds it drops out of the state: the open chat keeps its last session (`lastTalking` in `SessionPanel.tsx`) instead of closing and reopening; so does a handoff until the new session is up. The task going to Done does not close an open chat (BTN-948): it stays on the last session with the field kept and shut by "the task is closed" (`closed` on the composer; BTN-558 refuses a message after the merge anyway). That session is taken from the state as it is now, not as the chat last saw it (`chatSessionOf` in `web/src/pages/chatSession.ts`, BTN-1018): the merge lands before the session writes its closing message, so the window reads the transcript to the end of the turn — the message shows and the turn line goes out with the `working` lamp — and stops reading once the session is `finished` or gone from the state. The project page holds the panel on the closed task while the chat is open — the move to the next open task (`focusAfterClose`) waits until the chat closes (`nextOpenAfter`, `onChatting` of `SessionPanel`). While the fix session of a red main leads the chain (BTN-119), the task the chain takes next keeps the "Chat" button for its live session (`ChainBlock.aside`, `chainBlocks`), not amber, and the chat is locked with the hint that the reply waits for the fix: `Dispatcher.answerable` takes answers only for the current task, and the session is not answered from the page before the chain is back to it. A sent answer shows at once as an optimistic line, kept until a prompt or answer line appears after it in the transcript: Submit puts it in the feed and takes the question's panel away before the server answers (`sendAhead`), and a refusal marks the line as not delivered (its answer card goes, the delivery mark below) and brings the panel back with its picks and the command's error; while the answer is delivered the feed holds only its answer card, never the open question's card. The panel slides up out of the field through `appear` and leaves sliding down through `fold`, in a `FoldPresence` (`.chat__ask`) whose height moves with it, so the feed above glides; with reduced motion it shows and goes at once. The question's styles are in `web/src/pages/ask.css`, the feed's, the calls' and the composer's in `web/src/pages/transcript.css`.
- The chat's task panel (BTN-891, `ChatTaskPanel` in `web/src/pages/ChatTaskPanel.tsx`, styles in `chatTask.css`): the task's description, attachments and comments beside the session, so that a reply does not need the card closed and reopened. A chat of a session with a task (not an own-named block such as `ABC-FIX`) has a sidebar switch at the left of its head (`TaskToggle`, `SidebarIcon`), pressed while the panel is open; the task key after it is a link-styled button doing the same, the title is not. The hotkey is `chatTask` (`Mod+B`, `docs/web/hotkeys.md`), handled on the chat dialog's `onKeyDown` so it works in the reply field too. Whether the panel is open is kept in `localStorage` (`even-keel.chat.taskPanel`), and the chat opens as it was last left. The panel is a column of 380 px (`--chat-task-width`) at the left of the feed, the window wider by it; below 1180 px of screen it lies over the feed under the head, with a shadow, instead of squeezing it. A press slides it in and out through `appear`: its width and the window's change together, so the feed keeps its width, and its content, held at the panel's right edge, comes from under the window's left edge (`@starting-style` for `chat-task--slide`; `chat-task--leaving` keeps it on the page until its width transition ends, at once with reduced motion). A chat that opens with the panel shows it without the slide. It is read only: the status pill, the title, the description, `Attachments` and `CardJournal` without an editor, in the card's own components (`CardText.tsx`: `cardMarkdown` and `StatusPill`), and at the bottom "Open the card", which closes the chat and opens the full card, where the task is edited and commented on; a task link in the text does the same for its task. It reads the card through the same cache as the card (`recallCard`/`rememberCard`) and reads it anew when the state's row of the task changes and when the session's lamp does; an unreadable card is the card's notice, a tracker without one the card's line, and the chat goes on working. On a narrow screen (`useNarrow`) the switch and the key open the full card over the chat instead; closing it shows the same chat again, the draft in the field kept. Escape in a dialog over the session panel closes only that dialog: the panel's own Escape listener skips a key from inside an open `dialog`.
- The window's frame (BTN-1356, `transcript.css`): the head is a band of its own, flush with the window's top and sides, on `--surface-muted` with a `--border` line under it, `--chat-head` (45 px) high, which the task panel lying over the feed starts under; its buttons (the panel switch, ↗, the cross as `CloseIcon`) are 28 px framed boxes on `--surface`. In the reply field the attached files (`FileStrip`) are a shelf at the field's top, flush with its edges, on `--surface` with a line under it, so the text reads apart from the files.
- Pictures in the transcript and the chat (BTN-184, BTN-396). Claude keeps a picture of a tool result whole in the transcript, base64 in an `image` block of the `tool_result` (checked on 2026-10-18); Codex keeps `input_image` data URLs in its rollout's tool outputs (`docs/sessions/codex.md`, "Codex"). The whole fold gives tool lines the call's id (`FeedLine.tool`) and, after a result with pictures, an `image` line with the call's id, their count and, for a `Read` or a statically named `view_image`, the file name; the data never goes into the state, SSE or the lines. It is a line of its own, not a mark on the tool line, because the page reads lines once and the result comes after the call. `GET /api/sessions/<id>/images/<tool>/<n>` decodes the picture from the transcript (the optional `Agent.image`: Claude's `readTranscriptImage`, Codex's `readRolloutImage`), even after the original file is gone. `GET /api/sessions/<id>/files/<name>` gives a picture the user sent: one the transcript names inside `.temp/inbox/` (`inboxImage`), else one in `.temp/inbox/` of the session's own folder (the record's `workdir`, `inboxImageIn`), before the transcript names it — a bare name `inboxName` leaves as it is and a picture type only, so no other folder is reached (BTN-1360) — and 404 once the worktree is cleaned up. `TranscriptWindow` puts the thumbnails (`Thumbs`) right of a matching tool line, or on their own when the call has no tool line; a row that does not fit beside the line's text wraps under it, never squeezing the text or the edit size (BTN-1103). A folded group of calls with two pictures or more shows them as one stack (`ThumbStack`): the first on top and the stepped edges of at most two more, no count drawn, the click opens the viewer on the first, and `aria-label` names it and the total; a picture that will not load leaves the stack, one left is a plain thumbnail, none — nothing. The opened group shows each picture at its call. A picture the user sends shows at once from the chosen file (`useLocalPictures`: object URLs of the window, revoked when it closes, turns to another session or the send fails; a new project chat's first session is no other session, as its start may take minutes after the message went out, BTN-1387), until the transcript has the reply; then from the service, falling back to the browser's copy when it does not load (`Media.fallback`, BTN-1360). Each turn of its address — the chosen file, the service's copy, the transcript's — keeps the picture on screen until the next address has loaded unseen under it (`InboxThumb`, `.thumb__next`), and for good when that one fails, so delivery draws no chip for a moment (BTN-1390); the bubble's file rows are keyed by place, as the sent line names a file by its name and the transcript by its path. Any other picture the user sent shows its 📎 name until the thumbnail loads. Pressing either opens the viewer. Both retry a temporarily missing inbox image with increasing delays because a new message may reach the page before its file appears in the transcript. `transcriptMedia` lists every picture of the transcript in order, and a click opens `MediaViewer` on all of them, with its pager and Esc. A picture the user sent and the agent's read of it are one frame (BTN-1361), so the pager counts pictures, not the places they show: a single-picture result whose file is in `.temp/inbox/` or known only by name (Claude's `image` line has the name, its tool line's `subject` the full path) is matched to the sent file by the full path where both know it, else by the name — a read of another worktree's inbox is another picture. The frame stands where it first shows, the user's bubble as a rule, and once the agent read it its address is the transcript's copy, which outlives the worktree's cleanup; until then the inbox address. The read's thumbnail opens the same frame, and a stack counts it once. In `dev:fake` the transcript has a read of the past answer's `order.png`, two `Read` screenshots and a browser shot (`fakeShots`), and `?shots=many|gone` adds a group of 18 (`fakeManyShots`).
- Files a session sends the user (BTN-305). A `SendUserFile` call (`input.files`, `input.caption`) gets `FeedLine.share` in the whole fold — the caption, the files as named and the call's `cwd` (`shareOf`, `src/sessions/share.ts`, free of `node:*` since the page type-checks the fold). `GET /api/sessions/<id>/shared/<tool>/<n>` resolves file `n` against that folder and gives it only inside the folder or its main checkout (`sharedFile`/`checkoutOf` in `src/sessions/shareFile.ts`: the part before `/.claude/worktrees/<name>`), since a session in a worktree writes to the main checkout's `.temp/` too; anything else, or a file that is gone, is a 404. The share line breaks a group of calls and is a `ShareCard` (`web/src/pages/ShareCard.tsx`): the caption, a `.md` fetched and rendered in place (folded past 24 lines or 2000 characters), a picture as a thumbnail in the viewer's list (`TranscriptMedia.byShare`), anything else a download link; a file the page cannot get — the worktree is cleaned up — is its name crossed out and muted after a ⊘, with "The file is no longer there" and why in the tip (`Gone`, BTN-1377). The page does not keep a copy: once the folder is gone, so is the file. In `dev:fake` the chat of ABC-5 has a share of a markdown, a picture, an archive and a gone file (`fakeShare`).
- Calls in the chat (BTN-185), read like Claude Code: the text comes first and the calls between two texts fold into one line, "Edited 2 files, read a file, ran 2 commands +31 −4 (1 failed) ›" (`feedEntries`, `summarize` and `toolKind` in `web/src/pages/toolGroups.ts`); a question breaks a group, a pause of over 5 minutes gets a time mark across the column, and a lone call stands as its own row. The group opens into `CallRow`s (`web/src/pages/ToolCalls.tsx`): the verb and the subject — the file name with its path in a tip, a command's description, a search's pattern — and a call with a command or an error opens under itself to show it; mono is only there. The fold gives a tool line its `name`, `subject` (`subjectOf`) and, for an edit, `added`/`removed` (`callFacts` in `src/sessions/transcript.ts`), and after a result with `is_error` a `failed` line with the error, which the page folds into its call as a red "failed". Codex does the same from the rollout (`status: 'failed'`, a `FileChange`'s `content` or `unified_diff`, `docs/unverified.md`). The window's head names only the task (BTN-890): its key and title on one line, cut by an ellipsis (`TranscriptWindow`'s `task`, the panel's `block.id` and `block.title`; without a task the session's id and "Chat"/"Transcript"); the title's tip holds the full title and the session's id, and a press on the title copies the id. At its right stay the PR button, `↗` and the close button; the window opens with the focus on the close button, since focusing the title would open its tip. What the session is at goes into the status line under the field (`ChatStatus` in `web/src/pages/ChatStatus.tsx`): the branch (`SessionView.branch`, the transcript's `gitBranch`; it gives up its room first) and the session's edits (`editTotals`) at the left, the account's tag, the model of the last answer by its short name as in the Model fact ("Opus 5.5", the `free` badge after it, `ModelName`) and its effort's bar scale, only the model's tail cut and a tip naming the model's full name with its id and the effort (a task's run or the launch profile sets them, the chat never does), and the context ring at the right. The ring (`ringFacts` in `web/src/pages/contextRing.ts`) fills by the context's share in the colours of the context meter and is dashed while the window's size is unknown; a press or Enter/Space opens a popover above it with the context's figures and bar — a mark where the session hands off (`GET /api/sessions/<id>/checkpoint`, unless its source is `off`) — and the account's card with its windows as the header shows them (`AccountCard` in `web/src/layout/AccountLevels.tsx`). A press outside or Escape closes it; that Escape does not close the chat. The read-only transcript (no `chat`) keeps the same head and status line at its bottom, from the state's session or, for a past one, its record (`useStatusFacts`). The composer is one rounded box with `+` for files and `/` for a command on the left and the send icon on the right; `/` puts a slash into an empty field and opens the commands menu (`CommandTextHandle.startCommand`), and is off while the field holds text. Between the field and Send stands the microphone (BTN-1343, `DictateButton` in `web/src/pages/DictateButton.tsx`, the pure parts in `dictation.ts`): the browser's `SpeechRecognition` or `webkitSpeechRecognition` in the page's language, no server part. A press keeps the field's text and writes after it, a space between, every result as it comes, interim ones included (`saidText`, `dictatedText`); a second press, the recognizer's own end, typing into the field, sending and closing the chat stop it. A fine pointer listens continuously, a touch screen stops at the first pause (Chrome on Android repeats phrases in a continuous session). While it listens the button is `aria-pressed`, lit in `--accent` with a breathing icon; an error leaves it amber with the reason and what to do in its tip (`dictationProblem`). No button where the browser has no recognition (Firefox) or the page is not a secure context (`speechRecognitionOf`). With a mouse `+` opens the file picker at once; on a touch screen (`useCoarsePointer`) it opens a sheet from the bottom with Camera, Photos and Files (BTN-1342, `AttachButton` in `web/src/pages/ComposerFiles.tsx`), each a file input of its own (`ATTACH_SOURCES` in `fileTiles.ts`): Camera takes `capture="environment"`, Photos takes pictures and videos without `capture`, which Android answers with its photo picker and iOS with Photos, where a bare input offered only the camera and the file manager; a pick closes the sheet. The files wait above the field in one strip of 64 px tiles that scrolls sideways, a mouse wheel scrolling it too (`FileStrip`): a picture or a video by its preview (an object URL made once per file and revoked when the file leaves the field or the field goes, `syncUrls`), any other file by its extension and its name cut in the middle (`tileOf`, `shortStem`), each with a round cross in its corner. A preview is a button (`.chat__view`) that opens `MediaViewer` on its file from the same object URL, no request to the service, paging through the strip's pictures and videos; the cross only removes, and a plain file's tile does not open (BTN-1388). The placeholder is short ("Reply to the session…"); the keys are in the hotkeys window. No hint line stands under the box (BTN-1347): why sending is off — locked, being sent, just sent — is the placeholder of the empty field and the tip of the send button, which is then `aria-disabled` rather than `disabled` so the tip opens on it (`ComposerBox`'s `reason`; `sendTip` for a tip while sending is on, mid-turn or after an API error). The field grows to 5 lines and scrolls inside after that. Up to 760 px it is tighter for the phone's keyboard: 4 lines with 16 px text (iOS zooms into smaller), thinner paddings round the box and the window's body; while the field has the focus the status line and the accept bar hide, and a draft left unfocused folds to its first line until a tap (`.chat__text:not(:focus)`; a press on `+`, `/` or Send keeps the focus so the box does not fold under the finger). The window follows the visual viewport (`useChatViewport`: `--chat-visible-height`/`--chat-visible-top` from `visualViewport`), so a keyboard that pans the page rather than resizing it leaves the head on screen; Android's Back, which closes the keyboard but keeps the focus, brings the status line back (`data-keyboard-closed`). Files also come by Ctrl+V into the reply box and by a drop anywhere on the chat window (BTN-204), in the same states as `+` — any time but while a reply is being sent (`ComposerHandle.attach`). A paste leaves text to the box as usual and takes the files of `clipboardData.items`; a picture the clipboard calls `image.png` becomes `paste-YYYYMMDD-HHMMSS.<ext>` by the local clock and its MIME type, so pastes do not merge into `image (2).png` (`takenFiles`, `pastedName` in `web/src/pages/chatFiles.ts`). A drop (`useFileDrop`) keeps the files' names and skips folders and anything that is not a file, such as a link or a picture from another page that brings no file; while files are dragged over the window, `.chat__drop` covers it with a dashed frame and a line. While the chat is open a file dropped elsewhere on the page — the backdrop — is refused rather than opened by the browser. The chain's cards are moved by pointer events, not HTML drag, so a file drag never starts `useChainDrag`. Files copied in Explorer are not checked live (`docs/unverified.md`). In `dev:fake` the chat of ABC-5 has a long run of calls with edits and a failed command (`fakeCalls`).
- The turn line of the chat (BTN-183): while the session's lamp is `working`, a line under the feed shows the time since the turn began (`formatElapsed`, ticking every second on the page) and what the session does — "Running: " and the running call's tool line, or "Thinking". It comes with the window's own reads (`Feed.turn` of `GET /api/sessions/<id>/transcript`), not with the state, so a call starting or ending broadcasts no state: a Claude turn begins at the last prompt that is not a meta line (task notifications too), and a call is running from its `tool_use` until its `tool_result`. The line shows no token count: the transcript writes an answer's `output_tokens` only once the answer is done, so a count would stand still while the model thinks and then jump. A Claude turn is mostly "Thinking": a `Read` or a `grep` returns in milliseconds, and the seconds between calls are the model generating. A Codex turn begins at `task_started`, and the rollout writes a call only once it has finished, so Codex always shows "Thinking". In `dev:fake` ABC-5 runs a shell command, the rest think (`?parallel=2`, the chat of DEMO).

- The delivery phase of the turn line (BTN-188). An answer stops the session and resumes it with the answer (7–10 s), and the transcript still ends in the turn before: from the send until the answer lands, the line is empty (BTN-1362; before it, "Delivering the answer, the session is starting up"), with no tool of the old turn — the clock of the message's delivery mark (below) tells it. One pure function, `turnPhase` (`web/src/pages/turnPhase.ts`), makes the phase from what the window knows: the last reply sent from this window (browser clock), the chain's delivery in progress (`ChainBlock.answering`, the `starting` of a `CurrentTask` that is `answering`) and the journal's last answer to the session (`TaskSession.answeredAt`, also written for a session answered after its chain stopped, `deliverLoose`, and for a tracker comment's answer). The answer has landed once the transcript has a turn begun at or after it, or a prompt or an answer line written after it, or three minutes passed (the hold of `ResumeHolds`); while the chain still delivers it, it has not. The clock runs from the send, and the turn the answer began goes on counting from it — "Thinking" with the same count, no jump back when the prompt lands; a turn begun more than three minutes after the answer counts from its own prompt. Codex is the same: its answer is a new `codex exec resume`, the new turn begins at its `task_started`. In `dev:fake` an answer from the chat stays in the delivery phase for three minutes: the fake transcript gets no new prompt.
- The delivery mark of the user's message (BTN-1362, `DeliveryMark` in `web/src/pages/DeliveryMark.tsx`, `sentFeed` in `web/src/pages/sentLines.ts`), in the task's chat and the project chat alike. Under every user bubble, left of its time, an icon: a muted clock while a line sent from this window is not in the transcript yet ("Delivering"; its hands turn, the minute one in `--motion-tick`, the hour one twelve times slower, and stand with reduced motion; the send itself — `deliver` of `useLive`, `web/src/live/actions.ts` — stays off the top bar, which a delivery of minutes would leave running, BTN-1393), two green checks once the transcript holds it ("Delivered at HH:MM", the transcript line's time; every user line of the transcript shows them), a red sign when the server refused it ("Not delivered"). The words are the icon's tip (`Tipped`), never a `title`. A refused line stays in the feed without its answer card, while its text and files go back into the draft as before; it counts as no answer to its question, and the next send takes it out. A sent line and the transcript line that lands for it share one React key (`sent-<id>`, the first reply after the line the send was made at, one per send), so the bubble is the same element through the landing however many lines arrive before it: no blink, no jump of the scroll, only the icon changes. A message mid-turn is a letter of `ChatMail` (below) with its own fate and gets no mark until the transcript holds it.
- Banners over the field (BTN-1363, `ComposerBanner` in `web/src/pages/ComposerBanner.tsx`, a `Band` with `chat-banner`). Under the field stands only the status line; everything else the composer says is a banner between the question's panel and the field, a few words at the left, its buttons and ✕ at the right, each in its own `FoldPresence` (`chat__banner`, the question panel's slide). A refused send or accept is `error` (`role="alert"`): its ✕ drops the refusal from the draft (`dismissFailure` of `useChatDraft`, so a reload does not bring it back; an accept's refusal is hidden in the composer) and a refused accept has "Try again". A question the CLI has not saved (`ask.unsaved`) is `warn`, the explanation in the tip of its line, closed per question. "Accept as answer" (`offersAccept`) is `note`: "Close the task with this answer?" and the button, the explanation in the button's tip; its ✕ closes it for the session's current turn, kept in `localStorage` (`acceptClosed.ts`: a session's id → the time of its feed's last line, the latest 200 sessions), so the next turn without a mark shows it again. On a phone the accept banner waits out the keyboard, as the status line. The project chat has the error banner only.
- The menu of the agent's last message (BTN-1363, `MessageMenu` in `web/src/pages/MessageMenu.tsx`, the look of `MoreMenu`'s list): the last text line of the feed opens it on a right click, and on a long press of a finger (500 ms, cancelled by a move of 10 px; Android's own `contextmenu` and the timer for Safari open it once). Its items: "Accept as answer" while `ChatTarget.accepts` (it goes through the composer's handle, so a refusal is the same banner) and "Copy text" where the page has a clipboard. - Mail to a working session (BTN-181, `docs/sessions/chat.md`, "Chat mailbox"). While the lamp is `working` and the session's hooks listen (`state.mailbox[<session>].listens`, `ChatTarget.mail`), `ChatComposer` stays unlocked, and the tip of its send button says that the message reaches the session at its next tool call or at the end of the turn (no standing hint under the field; mid-turn the button is `aria-disabled` rather than `disabled`, so the tip opens on it); a send is not held and has no optimistic line, since the message shows in the list instead. `ChatMail` (`web/src/pages/ChatMail.tsx`) lists the session's mail at the end of the feed, each letter a user's bubble with its fate under the text (BTN-1347; before it, a list above the composer): waiting for the hook, delivered with the time and the event, and returned — an amber card saying why (`Mail.reason`: the session asked a question while the message was on its way, stopped before it took it, or the task is already closed, BTN-558), with "As the answer" (it goes into the composer; not for a closed task, whose message is a new task) and "Dismiss". A delivered message then shows in the feed as the user's bubble, read from its mark in the transcript, so its line stays 3 s after the delivery and then fades and folds in 0.3 s (`letterPhase` in `web/src/pages/letterPhase.ts`; with reduced motion it just goes); a waiting or returned one stays until its fate changes. A feed scrolled to its end stays there when a letter or the composer takes room from it (a `ResizeObserver` in `TranscriptWindow`). The chat and the Activity feed keep to their end through `useFeedPin` (`web/src/pages/feedPin.ts`, BTN-1372): a pinned feed lets go only when the reader moves it — the wheel, a touch, a press on the box or its scrollbar, a scroll key or Tab, counted for 800 ms — so a scroll event raised by late layout (folds and images laid out after the first scroll, the window's foot laid out late and the browser clamping the position) puts it back at its end instead of leaving it short, as a phone's narrow column did by ~440 px. A folded message (`FoldBody` with `preview`) that was never opened does not scroll its toggle into view as it mounts. The letters' styles are `.chat__letter*` over `.bubble`, in `web/src/pages/transcript.css`. A session that steers (`state.mailbox[<session>].steers`, BTN-291) is open mid-turn too, with its own tip on the send button: the message goes straight into it and is not held, and the turn line does not take it for an answer being delivered (`SentLine.steered` in `TranscriptWindow`). Until the session takes it after its running tool call, the message is a waiting letter of `ChatMail` ("In the session · it reads it once the current tool call ends"), not a bubble: the list is read from the CLI's `queue-operation` lines in the transcript (`Turn.queued`, an `enqueue` not yet followed by its `remove` or a `dequeue`), so it outlives closing the window and shows a message sent mid-turn through Remote Control too; the window's own send fills the gap until the transcript has it. Once taken, it is the user's bubble from the `queued_command` line. A working session that neither listens nor steers keeps the composer shut until it stops, and the hint only says to wait: the agent-bridge plugin is built in (`docs/packages.md`), so a deaf session is one started before its install or before the service, and the page no longer offers to add the plugin (BTN-879's offer removed by BTN-986).
- Commands in the chat (BTN-557, `docs/sessions/agents.md`, "CLI and transcripts"). `ChatComposer`'s field is `CommandText` (`web/src/pages/CommandText.tsx`, styles in `chatCommands.css`), modelled on the commands of Claude Desktop. A `/` at the start of the message opens a menu above the field (`menuQuery`, `matchingCommands`): ↑/↓ move, Tab or Enter put the command in (`withCommand`), Esc closes, a click only puts it in; the row under the pointer shows its description beside the menu at once, over the menu below 760 px. A known command in the field is drawn in `--accent` by a mirror behind the textarea (the textarea's own text goes transparent while a command is in it, its caret stays), with its arguments hint muted after it until the user types them (`ghostOf`); the pointer resting on it shows a card with the name and the description. The command acts as one token: a caret stepping into it selects it whole (`snappedSelection`), Backspace right after it or Delete right before it removes it whole (`tokenCut`). The pure parts are in `web/src/pages/chatCommands.ts` with their tests; the labels are `commands.menu` and `commands.filter` of the composer's i18n.
- How a live transcript window reads. The window reads its session's transcript when the service says the file changed, and every 5 s besides in case a word was missed. Reading registers the file with `TranscriptWatch` (`src/sessions/watch.ts`, the file from the optional `Agent.feedFile`): an `fs.watch` on it, whose events settle for 100 ms into one SSE `transcript` event `{sessionId}` (`EventHub.signal`: `broadcast` drops a frame equal to the last one, and this one always is); a file nobody read for 30 s is dropped, and a watcher that fails is dropped and logged while the poll goes on. Each read folds the whole file again. Checked on 2026-10-18 on a live Claude session on Windows: 31 writes in 4 min, every one followed by an event, the latest 260 ms after. The session cards and the chain keep `SESSION_POLL_MS` (3 s), since each tick starts `claude agents` once per account folder (~260 ms each).
- `POST /api/session/answer` takes `{project, task, sessionId, ask, answers, text, files: [{name, data}]}`: `ask` is the open question's `tool_use` id or `null` for a plain-text question, `answers` maps the question text to the answer (labels joined with `, ` for `multiSelect`, the Other text as is), `data` is base64. The route alone accepts a body up to 64 MB. Refusals are the codes of `Dispatcher.answerable` (`docs/chain.md`).
