# The chat: pictures, files and calls

- Pictures in the transcript and the chat (BTN-184, BTN-396). Claude keeps a picture of a tool result whole in the transcript, base64 in an `image` block of the `tool_result` (checked on 2026-10-18); Codex keeps `input_image` data URLs in its rollout's tool outputs (`docs/sessions/codex.md`, "Codex"). The whole fold gives tool lines the call's id (`FeedLine.tool`) and, after a result with pictures, an `image` line with the call's id, their count and, for a `Read` or a statically named `view_image`, the file name; the data never goes into the state, SSE or the lines. It is a line of its own, not a mark on the tool line, because the page reads lines once and the result comes after the call. `GET /api/sessions/<id>/images/<tool>/<n>` decodes the picture from the transcript (the optional `Agent.image`: Claude's `readTranscriptImage`, Codex's `readRolloutImage`), even after the original file is gone. `GET /api/sessions/<id>/files/<name>` gives a picture the user sent: one the transcript names inside `.temp/inbox/` (`inboxImage`), else one in `.temp/inbox/` of the session's own folder (the record's `workdir`, `inboxImageIn`), before the transcript names it — a bare name `inboxName` leaves as it is and a picture type only, so no other folder is reached (BTN-1360) — and 404 once the worktree is cleaned up. `TranscriptWindow` puts the thumbnails (`Thumbs`) right of a matching tool line, or on their own when the call has no tool line; a row that does not fit beside the line's text wraps under it, never squeezing the text or the edit size (BTN-1103). A folded group of calls with two pictures or more shows them as one stack (`ThumbStack`): the first on top and the stepped edges of at most two more, no count drawn, the click opens the viewer on the first, and `aria-label` names it and the total; a picture that will not load leaves the stack, one left is a plain thumbnail, none — nothing. The opened group shows each picture at its call. A picture the user sends shows at once from the chosen file (`useLocalPictures`: object URLs of the window, revoked when it closes, turns to another session or the send fails; a new project chat's first session is no other session, as its start may take minutes after the message went out, BTN-1387), and keeps that address at every stage after — the transcript has the reply, the agent read it — since the same bytes under a new address would load again and blink (BTN-1425). Without the browser's copy (the chat opened on another device) the address turns — the service's copy, then the transcript's — and each turn keeps the picture on screen until the next address has loaded unseen under it, in the bubble (`InboxThumb`, `.thumb__next`) as in the viewer (`.viewer__next`, a picture of the same name only; a neighbour shows at once), and for good when that one fails, so delivery draws no chip for a moment (BTN-1390, BTN-1425); the bubble's file rows are keyed by place, as the sent line names a file by its name and the transcript by its path. Any other picture the user sent shows its 📎 name until the thumbnail loads. Pressing either opens the viewer. Both retry a temporarily missing inbox image with increasing delays because a new message may reach the page before its file appears in the transcript. `transcriptMedia` lists every picture of the transcript in order, and a click opens `MediaViewer` on all of them, with its pager and Esc. A picture is named by its file's name; pictures of one name from different folders (`npm run shot` puts each run into its own folder) are named by as many of their folders as tell each from the rest, `mock-a/1-chain.png` (`distinguish`, BTN-1685), while the same file and a bare name with no folder stay as they are. The window holds the picture on view by its key (`TranscriptMedia.keys`: a sent picture by its file's name from the send to the read, the rest by the call, a repeated name `#2`), not its place, so the list built again on delivery never puts a neighbour on view; the viewer closes by itself only when that picture left the chat, or on a handoff — not at a project chat's first session (BTN-1425). A picture the user sent and the agent's read of it are one frame (BTN-1361), so the pager counts pictures, not the places they show: a single-picture result whose file is in `.temp/inbox/` or known only by name (Claude's `image` line has the name, its tool line's `subject` the full path) is matched to the sent file by the full path where both know it, else by the name — a read of another worktree's inbox is another picture. The frame stands where it first shows, the user's bubble as a rule, and once the agent read it its address is the transcript's copy, which outlives the worktree's cleanup; until then the inbox address — either only where the browser holds no copy of it. The read's thumbnail opens the same frame, and a stack counts it once. In `dev:fake` the transcript has a read of the past answer's `order.png`, two `Read` screenshots and a browser shot (`fakeShots`), and `?shots=many|gone` adds a group of 18 (`fakeManyShots`).
- Files a session sends the user (BTN-305). A `SendUserFile` call (`input.files`, `input.caption`) gets `FeedLine.share` in the whole fold — the caption, the files as named and the call's `cwd` (`shareOf`, `src/sessions/share.ts`, free of `node:*` since the page type-checks the fold). `GET /api/sessions/<id>/shared/<tool>/<n>` resolves file `n` against that folder and gives it only inside the folder or its main checkout (`sharedFile`/`checkoutOf` in `src/sessions/shareFile.ts`: the part before `/.claude/worktrees/<name>`), since a session in a worktree writes to the main checkout's `.temp/` too; anything else, or a file that is gone, is a 404. The share line breaks a group of calls and is a `ShareCard` (`web/src/pages/ShareCard.tsx`): the caption, a `.md` fetched and rendered in place (folded past 24 lines or 2000 characters), a picture as a thumbnail in the viewer's list (`TranscriptMedia.byShare`), anything else a download link; a file the page cannot get — the worktree is cleaned up — is its name crossed out and muted after a ⊘, with "The file is no longer there" and why in the tip (`Gone`, BTN-1377). The page does not keep a copy: once the folder is gone, so is the file. In `dev:fake` the chat of ABC-5 has a share of a markdown, a picture, an archive and a gone file (`fakeShare`).
- Calls in the chat (BTN-185), read like Claude Code: the text comes first and the calls between two texts fold into one line, "Edited 2 files, read a file, ran 2 commands +31 −4 (1 failed) ›" (`feedEntries`, `summarize` and `toolKind` in `web/src/pages/toolGroups.ts`); a question breaks a group, a pause of over 5 minutes gets a time mark across the column, and a lone call stands as its own row. The group opens into `CallRow`s (`web/src/pages/ToolCalls.tsx`): the verb and the subject — the file name with its path in a tip, a command's description, a search's pattern — and a call with a command or an error opens under itself to show it; mono is only there. The fold gives a tool line its `name`, `subject` (`subjectOf`) and, for an edit, `added`/`removed` (`callFacts` in `src/sessions/transcript.ts`), and after a result with `is_error` a `failed` line with the error, which the page folds into its call as a red "failed". Codex does the same from the rollout (`status: 'failed'`, a `FileChange`'s `content` or `unified_diff`, `docs/unverified.md`). The window's head names only the task (BTN-890): its key and title on one line, cut by an ellipsis (`TranscriptWindow`'s `task`, the panel's `block.id` and `block.title`; without a task the session's id and "Chat"/"Transcript"); the title's tip holds the full title and the session's id, and a press on the title copies the id. At its right stay the PR button, `↗` and the close button; the window opens with the focus on the close button, since focusing the title would open its tip. What the session is at goes into the status line under the field (`ChatStatus` in `web/src/pages/ChatStatus.tsx`): the branch (`SessionView.branch`, the transcript's `gitBranch`; it gives up its room first) and the lines changed at the left (`chatEdits` in `web/src/pages/chatEdits.ts`, BTN-1424) — in a tracker task's window the task's branch against the main branch as the service last read its folder (`EvenKeelState.diffs`, tip "Changes of the branch"), the same for every session of the task, so a handoff does not empty it, and nothing for a branch with no change; in a project chat, a fix of main or a task whose folder is not read (gone, no git, an older service) the session's own edits (`editTotals`, tip "Edits of the session") — the account's tag, the model of the last answer by its short name as in the Model fact ("Opus 5.5", the `free` badge after it, `ModelName`) and its effort's bar scale, only the model's tail cut and a tip naming the model's full name with its id and the effort (a task's run or the launch profile sets them, the chat never does), and the context ring at the right. The ring (`ringFacts` in `web/src/pages/contextRing.ts`) fills by the context's share in the colours of the context meter and is dashed while the window's size is unknown; a press or Enter/Space opens a popover above it with the context's figures and bar — a mark where the session hands off (`GET /api/sessions/<id>/checkpoint`, unless its source is `off`) — and the account's card with its windows as the header shows them (`AccountCard` in `web/src/layout/AccountLevels.tsx`). A press outside or Escape closes it; that Escape does not close the chat. The read-only transcript (no `chat`) keeps the same head and status line at its bottom, from the state's session or, for a past one, its record (`useStatusFacts`). The composer is one rounded box with `+` for files and `/` for a command on the left and the send icon on the right; `/` puts a slash into an empty field and opens the commands menu (`CommandTextHandle.startCommand`), and is off while the field holds text. Between the field and Send stands the microphone (BTN-1343, `DictateButton` in `web/src/pages/DictateButton.tsx`, the pure parts in `dictation.ts`): the browser's `SpeechRecognition` or `webkitSpeechRecognition` in the page's language, no server part. A press keeps the field's text and writes after it, a space between, every result as it comes, interim ones included (`saidText`, `dictatedText`); a second press, the recognizer's own end, typing into the field, sending and closing the chat stop it. A fine pointer listens continuously, a touch screen stops at the first pause (Chrome on Android repeats phrases in a continuous session). While it listens the button is `aria-pressed`, lit in `--accent` with a breathing icon; an error leaves it amber with the reason and what to do in its tip (`dictationProblem`). No button where the browser has no recognition (Firefox) or the page is not a secure context (`speechRecognitionOf`). With the classifier's LiteLLM set (BTN-1391; the state's `dictation`, `dictationSettings` read live) a press records instead (`useRecording` in `web/src/pages/useRecording.ts`, the pure parts in `recording.ts`): `MediaRecorder` in `audio/webm;codecs=opus` or `audio/mp4` (Safari), the button widens into a pill with the microphone in `--lamp-error` and the time (`chat__dictate--recording`); a second press, two minutes (`MAX_RECORDING_MS`), sending or closing the chat stops it, and the sound goes in base64 to `POST /api/dictation/transcribe` (`Dictation` in `src/dictation/transcribe.ts`, `docs/tally.md`) while a spinner stands in the icon's place (`chat__dictate--waiting`, disabled); the text is added after the field's like the browser's. A refusal is a notice code in the button's tip (`dictation.*`) and, for the quota, an hour of the browser's recognition, five minutes after another failure (`fallbackUntil`); an empty or too long recording keeps the model. Firefox gets the button in this mode, since it records. In `dev:fake` `?dictation=on` sets it, `slow`, `quota` and `failed` answer late or refuse (`fakeDictation`); `npm run shot` gives Chromium a fake microphone. With a mouse `+` opens the file picker at once; on a touch screen (`useCoarsePointer`) it opens a sheet from the bottom with Camera, Photos and Files (BTN-1342, `AttachButton` in `web/src/pages/ComposerFiles.tsx`), each a file input of its own (`ATTACH_SOURCES` in `fileTiles.ts`): Camera takes `capture="environment"`, Photos takes pictures and videos without `capture`, which Android answers with its photo picker and iOS with Photos, where a bare input offered only the camera and the file manager; a pick closes the sheet. The files wait above the field in one strip of 64 px tiles that scrolls sideways, a mouse wheel scrolling it too (`FileStrip`): a picture or a video by its preview (an object URL made once per file and revoked when the file leaves the field or the field goes, `syncUrls`), any other file by its extension and its name cut in the middle (`tileOf`, `shortStem`), each with a round cross in its corner. A preview is a button (`.chat__view`) that opens `MediaViewer` on its file from the same object URL, no request to the service, paging through the strip's pictures and videos; the cross only removes, and a plain file's tile does not open (BTN-1388). The placeholder is short ("Reply to the session…"); the keys are in the hotkeys window. No hint line stands under the box (BTN-1347): why sending is off — locked, being sent, just sent — is the placeholder of the empty field and the tip of the send button, which is then `aria-disabled` rather than `disabled` so the tip opens on it (`ComposerBox`'s `reason`; `sendTip` for a tip while sending is on, mid-turn or after an API error). The field grows to 5 lines and scrolls inside after that. Up to 760 px it is tighter for the phone's keyboard: 16 px text (iOS zooms into smaller), thinner paddings round the box and the window's body; while the field has the focus the status line and the accept bar hide. A draft shows up to 5 lines focused or not (BTN-1700); unfocused, it shows its start with no scroll and folds to 2 lines while the reader is up the feed (`data-feed-raised` on the window's body, `feedRaised` in `web/src/pages/feedPin.ts`), gliding through `fold`. Against a loop of the field's height moving the feed's end, it rises only when the reader took a free feed more than 120 px above its end — more than the three lines it gives back plus the pin's slack — and comes down only when the feed is pinned again; growing at the end keeps the feed pinned, as the pin's `ResizeObserver` follows the box. A press on `+`, `/` or Send keeps the focus so the box does not fold under the finger. The tap that focuses the field puts the caret at the end of the draft and scrolls the field there, whatever line the finger met; later taps place it as usual (BTN-1701: `CommandText` marks a pointer press on an unfocused field and moves the caret on its click, after the browser has placed it). A message sent with success takes the focus away (`CommandTextHandle.sent`), so the keyboard folds and the feed shows whole; a failed send keeps the focus and the text. Wider, a click places the caret where it lands and the focus stays after a send. The window follows the visual viewport (`useChatViewport`: `--chat-visible-height`/`--chat-visible-top` from `visualViewport`), so a keyboard that pans the page rather than resizing it leaves the head on screen; Android's Back, which closes the keyboard but keeps the focus, brings the status line back (`data-keyboard-closed`). Files also come by Ctrl+V into the reply box and by a drop anywhere on the chat window (BTN-204), in the same states as `+` — any time but while a reply is being sent (`ComposerHandle.attach`). A paste leaves text to the box as usual and takes the files of `clipboardData.items`; a picture the clipboard calls `image.png` becomes `paste-YYYYMMDD-HHMMSS.<ext>` by the local clock and its MIME type, so pastes do not merge into `image (2).png` (`takenFiles`, `pastedName` in `web/src/pages/chatFiles.ts`). A drop (`useFileDrop`) keeps the files' names and skips folders and anything that is not a file, such as a link or a picture from another page that brings no file; while files are dragged over the window, `.chat__drop` covers it with a dashed frame and a line. While the chat is open a file dropped elsewhere on the page — the backdrop — is refused rather than opened by the browser. The chain's cards are moved by pointer events, not HTML drag, so a file drag never starts `useChainDrag`. Files copied in Explorer are not checked live (`docs/unverified.md`). In `dev:fake` the chat of ABC-5 has a long run of calls with edits and a failed command (`fakeCalls`).
