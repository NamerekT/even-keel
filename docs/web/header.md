# Page: the header, the banners, the status page and updates

## The wide header

`web/src/layout/Header.tsx`. The brand with the project key, the Stats link, the Log link to `/log` with its count of unread warnings and errors (`LogLink`, [`event-log.md`](event-log.md)), then three blocks: work, account, gear.

- **The work block** holds signs and numbers, no words. The chain toggle (`QueueMenu`): the state lamp, the projects icon and the count of projects with a chain started — each once, however many lanes it runs (`activeProjects`, `web/src/layout/queueRows.ts`); the names and the queue length are in its tip. Its queue panel hangs from `.work-anchor`, outside the block so the block's `overflow` does not clip it, and is narrowed to the room left (`usePopoverRoom`), so it never scrolls the page. Its "Now" has a row per running project and, a line each, the current task of every lane (`queueRows`). While sessions wait, the amber question sign with their count (`Waiting`) leads to the first of them.
- **The account block** (`AccountBlock.tsx`): the active account and a ring per limit window with its percentage and the time to the reset (`formatSpan`, the page's one compact duration: "4h 59m", "2d 23h"). When projects run on other accounts too (`AccountEntry.projects`), a segment of small rings follows, one per such account (`headerAccounts` in `web/src/state.ts`), each filled to its fullest window. A click opens the accounts drawer (`docs/accounts.md`; the full list is `/accounts`); a hover or focus shows a card per account: email, plan, its projects, every window with its reset, where the limits came from and when, the sign-in left. On a narrow window the rings drop the reset time.
- **The gear** (`GearMenu` in `Status.tsx`): Settings, Status, Tools, Hotkeys, the theme, "Report a problem" and the version. The Status row carries the worst level of the checks; the gear's dot shows only when a check warns or fails.
- **"Report a problem"** (`ReportItem`, `web/src/layout/Report.tsx`) opens a list beside the menu: Bug, Broke after a CLI update, Can't get it installed (the three forms of `.github/ISSUE_TEMPLATE/`), Question or idea (Discussions), each a link to a new tab, then "A vulnerability — privately only" to a private security advisory. The repository is `repository.url` of `package.json`; the forms get `version` and the agents' CLI versions (`cli`, `cli-now`) from the address (`reportLinks`, `cliLine`), the dropdowns nothing: GitHub's form takes no dropdown from the address (`docs/verified/page.md`).

## The account chip

On `/p/<id>` the header's account follows the current session's saved account, otherwise the next launch's choice, even while the chain is stopped or paused. The server builds `AccountView.headerLevels` (`src/account/header-levels.ts`) through `runChoice`, passing over skipped and held tasks as `nextTask` does, and sends at most three distinct accounts: the task's override, the project's default and the shared default (an inherited default is labelled Even Keel). Every other route shows only the shared account. `AccountLevels` is read-only: one expanded card and two compact rows, no links, buttons or nested tips; a cascade adds an account-coloured border and a stack count. A phone has no chip: the limits of its account are thin bars along the header's bottom edge, one per window, none for an account without windows.

## The narrow header

At ≤760 px (`useNarrow`) the header is one row: the brand with the project key, the waiting sign with its count and a burger (`web/src/layout/Menu.tsx`) whose dot is the worst of the checks and the account. Its sheet is the wide header's blocks in one column: the Stats and Log rows; the work block as rows (Chains with the running count, the queue panel unfolding under it; Questions with its count while someone waits); the account card in place (`AccountSheet`); the gear's items as rows (`GearRows`, "Report a problem" unfolding inside the sheet, `ReportRows`). A row's value sits at its right edge.

## The banners

- **One sticky stack.** The header and every global banner share one stack (`AppHeader.tsx`). Its `ResizeObserver` writes the full height to `--header-height` on `.app`, wrapping and motion included; viewport-bound panels and sticky columns use it. `--header-row-height` is only the header row's minimum. The banners scroll on their own beyond 40dvh, leaving room for the page. `Banner.tsx` keeps the last content through its exit, inert and hidden from accessibility from the moment it starts closing (`docs/verified/page.md`). The content column, header included, is `--column` in `web/src/styles.css`.
- **"Got it"** (`NoticeButtons`, `web/src/layout/NoticeButtons.tsx`) on each banner and project band sends `notices/dismiss` with the band's ids (`noticeId`, `name@project` for a project's) and a stamp of what it says now — the remotes' verdicts, the CLI's version, a check's code and moment, the error's JSON. The stamps are kept in `service_state` `notices.dismissed` (`withDismissed`, the newest 300) and come back as `EvenKeelState.noticesDismissed`. A band returns once its stamp changes (`notDismissed`), not at the next read, since branch protection is read every 5 minutes.
- **"Don't show again"** is for a warning of a kind (`NOTICE_KINDS`, `src/notice/kinds.ts`): `notices/mute` writes `notices.<kind>` (`docs/settings.md`) — for the project of a project's band, for Even Keel for a shared one (`kindShown`). Errors that hold a chain — the config, the MCP gateway, a project's chain error — are no kind and take only "Got it"; so do a failed CLI check and an account whose limits are not read at all (red).
- **The kinds.** A project's bands are the project kinds (`PROJECT_KINDS`: `protection.noRules`, `protection.remote`, `branch.drift`), which a project may hold over Even Keel's; Even Keel's also holds the shared ones (`cli.check`, `usage.unread`, `unattended`, `config.conflict`). `cli.versions` is still accepted but turns nothing off: it has no banner since BTN-780 and is not listed. Any other key is `config.noticeKind`.
- **Settings → Notices** (`NoticeSettings.tsx`) lists the kinds: on `/settings` a switch each, the project kinds as every project's default; in a project's panel "As shared", Show or Hide per project kind.
- **Alike bands are one band**: a project's remotes with protection warnings are lines of one band, each with its "Open branch rules"; the agents without rules one line; the accounts with unread limits for one reason one banner, each named with its detail in a tip (`usageGroups`).
- **Run fallbacks.** A launch whose task's run named a provider with no account in the pool (`docs/sessions/models.md`, "Run profiles") is in `EvenKeelState.fallbacks` for 24 hours, from the launch log; each gets a toast (`FallbackToasts`, `web/src/layout/Fallbacks.tsx`) with `chain.noAccountFor`. "Close" is per device, kept in `localStorage` (`even-keel.fallbacks.dismissed`, `<at>|<task>`).

## The tab badge

`web/src/layout/tabBadge.ts`: a red dot — a check of `/status` fails (a lost connection to the service included); a yellow one — sessions wait for a reply, their count in the title, `(2) Even Keel`. The badge without a dot is `web/public/favicon.svg`; the dot is drawn onto it in a data URL.

## The status page

`/status` (`web/src/pages/StatusPage.tsx`, the pure part in `status.ts`), everything in one column.

- **The band** on top: "All is well", or the count of checks that warn or fail (`problemsOf`, failing first) with the first of them and its action.
- **A tile per check** of `systemChecks` (`web/src/layout/system.ts`: the server, the limits, the settings, Tally): its dot and word, one line of `note` (when the limits were read, when Tally last ran), the `details` in a "?" tip and the button of its `fix` (`CheckFix`: "Retry" for a lost server, otherwise the settings tab that fixes it — a config error's field by `configFixOf`, which the config banner uses too; Stats for a failing collector).
- **The Tally check** reads `EvenKeelState.tallyHealth` (`TallyService.health`, `src/stats/tally.ts`): not set up or off — neutral; waiting for the first run or a good last run — fine; a failed run — warns; halted until a restart, or meant to collect and not running — fails.
- **A card per tracker connection**, one per profile in use (`EvenKeelState.trackers`, `docs/trackers.md`). At the right the state's dot and word, the last good poll in its tip (`LinkState`, `web/src/pages/statusLink.tsx`). A down one's error as a sentence (`trackerProblem`: a refused key, a timeout, an unreachable address, other; the raw error in the tip). The projects and task feeds it reads as tags (a feed by its key, `readerName`); a reader of a live connection not read for over 3 minutes (`staleReaders`, `STALE_READ_MS`) is marked with when it was read. "Check" reads its projects now (`chain/refresh` each, a feed through its project); "Open profile" opens Settings → Trackers and CI. A profile no project reads says so with "Add project".
- **The built-in tracker's card** is always first, even with no project on it (`idleBuiltin`), so a newcomer never sees an empty list: "database available" with "N open tasks" in its tip, its projects as tags, no "Check" or "Open profile".
- **`?item=<key>`** — a check's key or a profile's id — scrolls to that tile or card and lights it once (`block-glow`).

## Updates

`src/updates/`. What a person sees and does is the guide's [Updating from the page](../guide/page.md#updating-from-the-page); this is how it is built.

- **The check.** The service reads its version from `package.json` and, while `updates.check` is on, asks `api.github.com/repos/<repository>/releases?per_page=30` (no token) at start and every 12 h (`UpdateWatcher`, `releasesOf`). Not during the first run (`firstRun`): the setup asks whether to, and the first ask comes once the run ends (a config change calls `configChanged`). Drafts, prereleases and tags that are no version are ignored; a failed request is one log line.
- **The version row.** `EvenKeelState.updates` (`updatesView` for the releases, `Updater.view()` for the rest) makes the last row of the gear menu and the burger's sheet "Even Keel <version>", with "<version> available" when a release is newer or "back to <version>" when this version came by an update (`VersionRow`, `web/src/layout/Updates.tsx`). Both open the update window (`UpdateWindow`).
- **The toast.** A newer release gets a toast (`UpdateToast`, on `web/src/ui/Toast.tsx`) unless `updates.notify` is off or `updates.dismissed` is that version: "Update…" opens the window, "Close" sends `updates/dismiss {version}` (a later release shows it again), "Don't show again" sends `updates/mute` (`notify: false`). Both are written to the config, so every device stops showing it.
- **The window.** The installed and latest versions; the notes of every newer release (`notes`, newest first, markdown sanitized), with an amber mark over a note that has a `### Reverted` section (`revertedOf`: its text up to the next heading of level 3 or above); "Update to <version>" (`updates/install`) or why there is none (`blocked`: not a service, not a git checkout, uncommitted changes, HEAD not on the installed version's tag; an npm install that is not global). The text under the button follows `source`: a checkout and a build, or npm. Under it the previous version (`previous`) with "Revert to <version>" (`updates/revert`) or why not — `storage` when the storage versions differ, with the way back from the `.bak` copies.
- **Under way and after.** `UpdateProgressToast` (`progress`: "waiting for <projects>" while the chains settle, then "updating…"); the page calls `location.reload()` once the service answers with another version. After the restart `UpdateResultToast` (`result`): "Details" opens the window with the step, the rollback and the output, "Close" sends `updates/seen`.
