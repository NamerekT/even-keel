# Service

Reference for sessions: installing and running the service on different systems. Without the service, on any system: `npm install`, `npm run build`, `npm start` in the repository root. The npm package is the other install: "An npm install" below.

The Tally stats collector runs inside the service (every 5 minutes, in its own thread), so no separate scheduler or cron task is needed.

## What applies on the fly

A restart is needed only for a new version of Even Keel (BTN-130). The service looks at the settings in its database (`ConfigStore`, `src/config-store.ts`) and at `.env` (`EnvFile`, `src/env-file.ts`), each every 2 s, and applies a change at once:

- **The config.** Every key (`docs/settings.md`), whether the page saved it or `npm run storage -- config-import` replaced the settings (`docs/storage.md`). A project added gets its tracker, CI watches and packages; a removed one has its chain let go (`Dispatcher.forget`) while its sessions are left as they are; a key renamed under the same `id` carries its chain state, launches and packages (`rekeyed`, `Dispatcher.rekey`). A changed `repo` or tracker rebuilds that project's tracker link (`Trackers.apply`) and CI watches (`CiWatches.apply`). A remote or a first workflow added to the same checkout gets its CI watch within a minute (`docs/ci.md`). A smaller `slot` keeps finding the slots busy tasks are in: the pool spans the most slots it had since the start (`slotSpan`).
- **`.env`.** A variable the process got from outside the file stays as it was, as at the start. `envTargets` says who reads a changed one: a tracker's variables rebuild that tracker's links (the CI tokens are profiles', not `.env`'s: a changed profile gives every CI watch a new source, `docs/ci.md`); `EVEN_KEEL_ACCOUNTS_DIR`/`EVEN_KEEL_CODEX_ACCOUNTS_DIR` move the account roots; `EVEN_KEEL_TOKEN` changes the page guard and closes the open event streams, so pages ask for the token again; `EVEN_KEEL_HOST`/`EVEN_KEEL_PORT` move the page to a new server (the old one closes once the new one listens; a refusal keeps the old address and shows `server.rebindFailed` in the config banner); `TALLY_DB_*`/`TALLY_READER_*`/`TALLY_WRITER_*` restart the collector against the new database. The sessions' environment is built at each launch (`AgentOptions.env`), so a removed key never reaches a new session.
- **Start-only.** `EVEN_KEEL_MCP_PORT` (live sessions have the gateway's address in their flags), `EVEN_KEEL_STATE_DIR` (the files and the database the service has open), `EVEN_KEEL_CONFIG` (the config file imported once at the first start, `docs/storage.md`), `CLAUDE_CONFIG_DIR` and `CODEX_HOME` (the `global`/`codex` account folders). These are read once; change them with a restart.

## Windows

- The service host is `service/EvenKeelService.cs`, compiled during installation by the stock `csc.exe` from .NET Framework; there are no third-party wrappers. It keeps `node --import tsx src/main.ts` running in the repository root (`node dist/src/main.js` in a package, which has no `src/main.ts`), restarts it on a crash and writes the output to `logs/even-keel.log`. A third argument is the data folder of a package: the log goes there and the child gets it as `EVEN_KEEL_DATA`. To debug without the service: `EvenKeelService.exe <root> <node.exe> [<data folder>] --console`.
- `service/install.ps1` and `service/uninstall.ps1` — from PowerShell 7 as administrator. The script does not ask for the account password: the user enters it on the "Log On" tab in services.msc, which also grants the "Log on as a service" right.
- The service reads `.env` from the repository root (a package: from its data folder), and at its first start imports `even-keel.config.json` from there, if there is one; the address and port are `EVEN_KEEL_HOST` and `EVEN_KEEL_PORT` in `.env` (`127.0.0.1:4747` without them), and the port must not be occupied by a manual run.
- The service serves the built `dist/web`: `install.ps1` runs `npm run build`. After a code update, run `install.ps1` again (or `npm run build` and restart the service), otherwise the page is stale or returns 503.
- `install.ps1` stops a running service before `npm install`: the service holds `node_modules/@esbuild/win32-x64/esbuild.exe` (tsx's esbuild child), and npm fails on it with `EPERM`. `npm ci` next to a running Even Keel fails the same way and leaves `node_modules` half-removed (BTN-157: 33 of ~350 packages left); after a stop, `npm ci` again restores it. The binary is held only while the esbuild child runs, that is on a miss of tsx's cache; an update changes the sources, so right after one it is likely, and with a warm cache `npm ci` passed next to a running Even Keel. The service host stops node with `Process.Kill()`, node only, and esbuild exits with it within 2 s (checked with `TSX_DISABLE_CACHE=1`), so stopping the service is enough.
- Stopping the service does not kill background sessions — they are children of the `claude daemon run` daemon.
- **Rebuild after a green main.** `service/rebuild.ps1 -Commit <sha>` builds the checkout it lives in and restarts the service, only if the checkout's HEAD is that commit. It compiles `dist/` (`npx tsc`) and hands the rest to the update process in rebuild mode (`node dist/src/updates/run.js rebuild`, "Updating from the page" below), so the wait for the chains and the step order are one code with the page's button: when `package-lock.json` is newer than the installed one — wait, stop, `npm install`, build, start (the running service holds esbuild's binary); otherwise build, wait, stop, start. A rebuild never touches git: on a failure it only starts the service again, and the output goes to the SSH call as well as `logs/update.log`. The Forgejo workflow calls it as its last step over SSH, with `continue-on-error` so a workstation that is off does not turn `main` red. That step runs only on a push and only when the repository has the variables `DEPLOY_SSH_HOST`, `DEPLOY_SSH_USER`, `DEPLOY_SSH_KNOWN_HOSTS` and the secret `DEPLOY_SSH_KEY`. The key's line in the workstation's `authorized_keys` (for an administrator — `C:\ProgramData\ssh\administrators_authorized_keys`) forces the script: `from="<runner host>",restrict,command="pwsh -NoProfile -NonInteractive -File <root>\service\rebuild.ps1" ssh-ed25519 …`; the commit arrives in `SSH_ORIGINAL_COMMAND`.

## Linux and macOS

- `service/install.sh` as your own user (not via `sudo`): `npm install`, `npm run build`, then on Linux the unit `~/.config/systemd/user/even-keel.service` (`systemctl --user`, log — `journalctl --user -u even-keel`), on macOS the agent `~/Library/LaunchAgents/local.even-keel.plist` (`launchctl`, log — `logs/even-keel.log`, no rotation). Running it again rebuilds and restarts. `service/uninstall.sh` removes it.
- `PATH` and the path to `node` are taken from the installer's shell: if `node` changed (nvm and the like), run `install.sh` again.
- The unit has `KillMode=process`, so a restart leaves the CLI daemon of live sessions running. systemd says so in the journal — `Unit process … (claude) remains running after unit stopped` and `Found left-over process … This usually indicates unclean termination` — one pair per process; that is the intended behaviour, not a failure (seen in the BTN-143 trial, Ubuntu 26.04, systemd 259).
- Stopping the service does not kill background sessions: `KillMode=process` in the unit, `AbandonProcessGroup` in the agent. A `--user` unit lives while the user is logged in; to keep it running without a login, use `loginctl enable-linger <user>` (the installer reminds you). The macOS agent works only while logged in.
- **The update process** (next section) stops and starts the unit with `systemctl --user stop|start <unit>`, the unit read from `/proc/self/cgroup` (`user@….service/…/<unit>.service`; a system unit gets no button), and the agent with `launchctl bootout gui/<uid>/<label>`, waiting until `launchctl print` no longer finds it, then `launchctl bootstrap gui/<uid> <plist>`; the label is `XPC_SERVICE_NAME` of the service's environment, the plist `~/Library/LaunchAgents/<label>.plist`.
- Linux was verified live in WSL (Ubuntu 26.04, 2026-10-04): tests and type check, `install.sh` and `uninstall.sh`, signing in to `claude` from the page, `/usage` limits, starting a session in a task worktree, and after Done — stopping the session, cleaning up the worktree and branch, its own `main` sync with a push to origin. The CLI must know a new repository as trusted: otherwise the launch pauses and asks you to open `claude` in it once. A native Ubuntu 26.04 server was gone through by README in BTN-143 (installation) and BTN-157 (updating). macOS was not verified.

## An npm install (BTN-265)

The package `even-keel` (`docs/releases.md`, "Publishing to npm") is the built Even Keel: `dist/src`, `dist/tally`, `dist/web`, with the plugins, the status line and the service scripts next to them. Node does not strip types inside `node_modules`, so nothing there runs through tsx; whatever starts a module by its file (the Tally workers, the SDK executor) picks `.js` when its own file is `.js`.

- **Which install.** `src/locations.ts`: `root` is the folder with the nearest `package.json`, `source` is `git` when it has `src/main.ts`, otherwise `npm`. `home` — where `.env`, `state/` and `logs/` are — is `EVEN_KEEL_DATA`, else a checkout's own folder, else the data folder of the platform: `%LOCALAPPDATA%\even-keel`, `~/Library/Application Support/even-keel`, `$XDG_DATA_HOME/even-keel` (`~/.local/share/even-keel`). npm replaces the package's folder at every update, so nothing of the user's lives there. The variable is not `EVEN_KEEL_HOME`: the `tally` plugin finds the code by that one. `tally/bin/sql.mjs` finds the data the same way.
- **The command** `even-keel` (`src/cli.ts`, `bin` of `package.json`): none — run in the terminal; `install`/`uninstall` — `service/install.*`/`uninstall.*` of the package; `update [version]` — stop the service this package runs, `npm install --global --prefix <its prefix> even-keel@<version>`, start it, with no wait for the chains (the page's button waits). Run from the npx cache (`_npx` in its path), with no command or `install`, it first installs its own version globally and runs `install` from there: the service and the plugins' paths need a folder npx will not clear.
- **The scripts** tell a package by the missing `src/main.ts`: no `npm install` or build; the log in `<data>/logs`; on Windows the host compiled into `<data>\service` (the package's folder is replaced on update) and registered with the data folder as its third argument; the unit and the agent run `node dist/src/main.js` with `EVEN_KEEL_DATA`. `install.ps1 -Data <dir>` and `EVEN_KEEL_DATA` choose another data folder; the service must run as the user whose data folder it is.

## Updating from the page (BTN-163, `src/updates/`)

The update window on the page (`docs/web.md`) sends `updates/install` or `updates/revert`; the service side is `Updater` (`updater.ts`), the process that does the work is `run.ts` over `runner.ts`.

- **Who may.** `updateBlock` (`model.ts`) gives the reason there is no button, in this order: the checkout is still being read, it is not a git checkout (`readCheckout`, `checkout.ts`), Even Keel does not run under a service manager it can drive (`serviceControl`, `control.ts`: the parent process is a Windows service in `tasklist /svc`, a systemd user unit, a launchd agent), the checkout has tracked changes (`git status --porcelain --untracked-files=no`), HEAD is not on the tag of the installed version. The last one keeps a developer's checkout (`dev`, a task branch) and the CI-built one out: they update by `rebuild.ps1`. The checkout is read at the start and every 10 min. A package has no checkout (`packageBlock`): it needs a global install whose `--prefix` is known (`globalPrefixOf`, `prefix.ts`; `global` otherwise — a local install, the npx cache) and a service manager.
- **Revert.** `logs/update.json` is the record of the last run (`UpdateRecord`). "Revert" is offered only after an update that went through, to the version it came from (`previousOf`), and only when the storage versions it recorded equal the running ones: `{schema: SCHEMA_VERSION, database: SQLITE_VERSIONS + STEPS.length, tally: TALLY_SCHEMA_VERSION}`. Otherwise `previous.blocked` is `storage` and the page explains the manual way back. A revert release (a release that takes back an earlier one, `### Reverted` in its notes) is an update like any other, so it may come after a storage change; the rule is in `docs/releases.md`.
- **Settling.** Before the process starts, the service waits up to 5 min (`SETTLE_MS`) until `busyChains` (`settle.ts`) is empty: no unpaused chain is launching, handing over or closing a task. A chain waiting for the CI of main does not count — for a rebuild that CI is the run calling it, and the wait survives a restart (`state/`); the project's own check (`ciWait.local`) does. A chain that never settles is not waited for past the 5 min. The page shows the projects waited for (`progress.waiting`).
- **The process.** The service cannot update itself: `git checkout`, `npm ci` and the build replace its own code, and stopping it kills its children on systemd and launchd unless they are detached. So `launchRunner` (`launch.ts`) copies the compiled `dist/src/updates/` to a fresh folder in the OS temp folder (with a `package.json` of `"type": "module"` and the mark `.even-keel-update`), writes the plan there and starts `node run.js plan.json` detached (`detached`, `stdio: 'ignore'`), and the service goes on answering. The modules of the runner import only `node:*` and each other, so the copy runs alone. It survives the stop: the Windows host kills only its node child (`Process.Kill`), the unit has `KillMode=process`, the agent `AbandonProcessGroup`. It deletes its folder when done.
- **Steps** (`stepsOf`, `steps.ts`): update — stop, `git fetch --tags`, checkout, `npm ci`, `npm run build`, start, answer; revert — the same without the fetch. The checkout keeps the branch the checkout was on (`git checkout -B <branch> <tag>`, so a `git pull` by hand still works) or stays detached. npm runs through the node of the process (`npm-cli.js` next to it), since the service's `PATH` may lack it. "Answer" polls `GET /api/state` (loopback, no token; `stateUrlOf`) for 2 min (`ANSWER_MS`) until a start later than the one before the update answers with the target version, and the same start still answers 10 s on (`STEADY_MS`), so a service crashing in a loop does not pass. A package's update is stop, `npm install --global --prefix <prefix> even-keel@<version>` (`install`), start, answer, run from the data folder: a working folder inside the package would hold it on Windows while npm replaces it (`workingDir`, `runner.ts`).
- **Rollback** (`rollbackOf`, `runSteps`): a failure at stop or fetch only starts the service again and waits for its answer; at any later step — stop, check out the commit it started from, install, build, start, answer; a package's — stop, install the version it started from (`restore`), start, answer. A failed stop in the rollback is ignored (the service may be down already); any other failed rollback step ends it, recorded as `rollback.failed`.
- **The outcome** is written to `logs/update.json` of the data folder (a temporary file and a rename: the new service reads it at its start), the log of every step and its output to `logs/update.log` (appended). Neither is under `state/`, so they are no state format. The service reads the record at its start and again whenever the file changes (`watchFile`, every 5 s): the process writes it only after its answer step, so after the new service has started (found live in BTN-272). It logs it, and the page shows it as a toast until `updates/seen`. A process that could not even be started (no `dist/src/updates/run.js`) is a `launch` failure, kept in memory.
- **Rebuild mode.** `service/rebuild.ps1` runs the same code: `node dist/src/updates/run.js rebuild --root <dir> --state <url> --service <name> [--wait <s>]` copies itself to the temp folder like the button does, then runs in the foreground with the log echoed. Its steps have no git and its rollback only starts the service (section "Windows" above).
