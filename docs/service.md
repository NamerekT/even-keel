# Service

Reference for sessions: installing and running the service on different systems. Without the service, on any system: `npm install`, `npm run build`, `npm start` in the repository root. The npm package is the other install: "An npm install" below.

The Tally stats collector runs inside the service (every 5 minutes, in its own thread), so no separate scheduler or cron task is needed.

`src/service.ts` owns initialization order and live state. Its `service/` modules wire accounts and agents, chains and worktrees, trackers and intake, the HTTP/state view, stats and lifecycle. Their context uses live getters (and setters for mutable state), so callbacks see later-initialized components and the latest sessions, config and listening address; the modules import the context type only.

## What applies on the fly

A restart is needed only for a new version of Even Keel (BTN-130). The service looks at the settings in its database (`ConfigStore`, `src/config-store.ts`) and at `.env` (`EnvFile`, `src/env-file.ts`), each every 2 s, and applies a change at once:

- **The config.** Every key (`docs/settings.md`), whether the page saved it or `npm run storage -- config-import` replaced the settings (`docs/storage.md`). A project added gets its tracker, CI watches and packages; a removed one has its chain let go (`Dispatcher.forget`) while its sessions are left as they are; a key renamed under the same `id` carries its chain state, launches and packages (`rekeyed`, `Dispatcher.rekey`). A changed `repo` or tracker rebuilds that project's tracker link (`Trackers.apply`) and CI watches (`CiWatches.apply`). A remote or a first workflow added to the same checkout gets its CI watch within a minute (`docs/ci.md`). A smaller `slot` keeps finding the slots busy tasks are in: the pool spans the most slots it had since the start (`slotSpan`).
- **`.env`.** A variable the process got from outside the file stays as it was, as at the start. `envTargets` says who reads a changed one: a tracker's variables rebuild that tracker's links (the CI tokens are profiles', not `.env`'s: a changed profile gives every CI watch a new source, `docs/ci.md`); `EVEN_KEEL_ACCOUNTS_DIR`/`EVEN_KEEL_CODEX_ACCOUNTS_DIR` move the account roots; `EVEN_KEEL_TOKEN` changes the page guard and closes the open event streams, so pages ask for the token again; `EVEN_KEEL_HOST`/`EVEN_KEEL_PORT` move the page to a new server (the old one closes once the new one listens; a refusal keeps the old address and shows `server.rebindFailed` in the config banner); `TALLY_DB_*`/`TALLY_READER_*`/`TALLY_WRITER_*` restart the collector against the new database. The sessions' environment is built at each launch (`AgentOptions.env`), so a removed key never reaches a new session.
- **Start-only.** `EVEN_KEEL_MCP_PORT` (live sessions have the gateway's address in their flags), `EVEN_KEEL_STATE_DIR` (the files and the database the service has open), `EVEN_KEEL_CONFIG` (the config file imported once at the first start, `docs/storage.md`), `CLAUDE_CONFIG_DIR` and `CODEX_HOME` (the `global`/`codex` account folders), `EVEN_KEEL_CPU_PROFILE` (below). These are read once; change them with a restart.

## A slow start (BTN-680)

`src/diagnostics/start-watch.ts`, started by `src/main.ts` right after `.env` is read:

- **`start: modules … s, storage … s, service … s`** — once the service's top level is done: the time from the process start to `main.ts`'s own modules loaded, then opening and upgrading the storage, then `service.ts` (its imports and its wiring up to the timers).
- **`event loop: blocked up to N ms in the last 5 s (p99 M ms)`** — for the first 3 min, only for a 5-second window whose longest delay of the event loop (`perf_hooks.monitorEventLoopDelay`) reached 1 s, and a summary at the end when any did. A blocked loop makes every timeout in the process fire late: network probes report `does not answer`, tracker calls `call timed out` with a short longest HTTP request. A stall before the loop's first turn (the synchronous part of the imports) is not in the histogram — the `start:` line has it.
- **`EVEN_KEEL_CPU_PROFILE=<seconds>`** in `.env` — the process profiles its own CPU through an in-process inspector session (no port opens) for that many seconds of the start, at most 600, sampling every 1 ms, and writes `logs/start-<time>.cpuprofile`. Remove the variable after the run.

**Measured on 2026-11-01** (BTN-680; two profiles of the live service, 150 s from the node start, 1 ms sampling). Before: the loop was busy 98–100% for the first ~60 s and ~55% after, 109 s of 150; `AccountHomes.list` alone took 27.7 s (`readdirSync` 18 s, `existsSync` 5.8 s — every account's limits and view listed all account folders again, O(accounts²)), the session registries' `readFileSync` 16 s (`TurnRegistry` 10 s, `SdkRegistry` 6 s, on every sessions tick); the loop stalled for 1.1–2.8 s at a time, and every tracker call timed out after 15 s. Now the account folders are read once per synchronous pass and the registries at most once a second. After: 78.5 s of 150, ~100% for the first 40 s and 20–35% after. What was left:

- 9.6 s before `listening`: tsx compiling the `.ts` files changed since the last start on the main thread (esbuild `transformSync` 3.3 s, the synchronous pipe read 3.7 s) and opening PGlite (0.8 s). No call is made yet, so it times nothing out; it is only the price of running `node --import tsx src/main.ts` from the checkout after a pull.
- +15…+30 s: the sessions monitor catching up on transcripts — `readLines` 3.1 s in one go, then folding with stalls of 1.6–2.6 s; this is the window where the trackers timed out. Since BTN-690 transcripts are folded in small slices under one budget per turn of the loop for all readers ([`sessions/agents.md`](sessions/agents.md)); measured the same day: the longest delay of the loop in the first 180 s went from 6044 ms to 1121 ms (the first 4 s, before the catch-up), no tracker call timed out, the CPU busy 41.8 s of 150, 20–30% from +20 s on. A slice yielding per tail alone was not enough — 735 tails read at once still ran their slices back to back for up to 3.1 s.
- `getState` — 22.4 s of 78.5 (29%): the whole state rebuilt for every broadcast, with stalls of 3.0 and 1.7 s (`launchDays` 1.5 s, `readerOf` 1.2 s in one go). After BTN-690 alone it was 9.6 s of 39.3, the longest 505 ms: those stalls were the loop held by the catch-up, and the two functions took at most 32 and 3 ms at a time. Since BTN-691 the state is built at most once per 200 ms ([`web/interface.md`](web/interface.md)); measured the same day with a page listening: 8.9 s of 38.9 busy, ~180 builds in 150 s, ~50 ms each once settled, 250–450 ms in the six builds of +16…+30 s, none of whose parts reaches 200 ms alone. What was left is the state's own size — ~2 MB a frame, 736 sessions and 1170 tasks: since BTN-695 only the first frame is whole (~1.6 MB), the rest are patches of 4–70 KB ([`web/interface.md`](web/interface.md)). Building the state is still whole each time.
- Spawning processes (`execFile`, a synchronous CreateProcess on Windows) — ~6 s per start, git and CLI calls.

## Windows

Two ways to run it: the start at sign-in with a tray icon (BTN-372, `even-keel install`, no administrator — the default) and the Windows service `EvenKeel` (`install.ps1`, runs without a sign-in). One per machine, they share the port: `even-keel install` refuses while the service is registered, `install.ps1` while the `Run` value is.

### The start at sign-in (BTN-372)

- **The host** is the same code as the service's (`service/EvenKeelService.cs` with `EvenKeelHost.cs` and `EvenKeelTray.cs`), compiled by `src/autostart.ts` as `EvenKeel.exe` with `-target:winexe`, so no console window: into `<data>\service` for a package, `service\bin` for a checkout (`hostDirOf`). `installAutostart` ends a running host first (it holds the exe), compiles, writes `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` → `EvenKeel` = `"<exe>" "<root>" "<node>" ["<data>"] --tray` with `reg.exe` and starts it. A value, not a Startup shortcut: a shortcut needs COM through PowerShell, and Settings → Apps → Startup turns either off. `even-keel install` from a checkout ends the host, runs `npm install` and `npm run build` first, as `install.ps1` does; `uninstall` ends the host, deletes the value and the exe (the folder too once empty: the service's host may share it).
- **Modes** (the last argument): `--tray` — the host with the icon, one per machine (the mutex `Global\EvenKeel.Host`; a second one exits at once); `--start` — tells a running host to start node, or starts a host with the same arguments and `--tray` through a shell start, which inherits no handles, so a caller reading its output does not wait for the host; `--stop` — the host stops node and keeps it stopped, the call returns once node is down (30 s at most); `--quit` — the host stops node and exits. The commands are the events `Global\EvenKeel.Stop|Start|Quit` and `Stopped`: global, so `rebuild.ps1` over SSH, in another Windows session of the same user, reaches the host on the desktop. A stop for an update keeps the host and its icon for that reason: a host started from SSH would have no tray and end with the SSH session. Node held stopped, or started again by a start or **Restart**, begins its crash backoff anew.
- **The icon**: the page's `dist/web/icon-192.png` with a dot — green running, amber a chain paused (`chain.active[].paused`), blue a session waiting on its question (`sessions[].asking`), grey starting (no answer in the first 2 min after node started) or stopped for an update, red no answer. It reads `GET /api/state` every 10 s at the address of `EVEN_KEEL_HOST`/`EVEN_KEEL_PORT` from its environment over `.env` of the data folder, the wildcard on loopback as `stateUrlOf` does; the menu and tooltip follow the state's `language`, otherwise the Windows display language. **Restart** kills node and starts it at once; **Quit** ends the host until the next sign-in or `even-keel install`. The log lines are `tray: …` in `logs/even-keel.log`.
- **Under the host** node gets `EVEN_KEEL_LAUNCHER` (the host's exe). `serviceControl` takes it only when the parent process is `EvenKeel.exe` too (`launcherOf`): the sessions inherit the variable, not the parent. The control is `autostart`: stop `EvenKeel.exe --stop`, start `EvenKeel.exe <root> <node> [<data>] --start` (`autostartControl`); `even-keel update` finds it from the `Run` value (`registeredAutostart`), `rebuild.ps1` passes `--autostart <exe>` when no service `EvenKeel` is installed and the value is.

### The service

- The service host is `service/EvenKeelService.cs`, compiled during installation by the stock `csc.exe` from .NET Framework; there are no third-party wrappers. It keeps `node --import tsx src/main.ts` running in the repository root (`node dist/src/main.js` in a package, which has no `src/main.ts`), restarts it on a crash and writes the output to `logs/even-keel.log`. A third argument is the data folder of a package: the log goes there and the child gets it as `EVEN_KEEL_DATA`. To debug without the service: `EvenKeelService.exe <root> <node.exe> [<data folder>] --console`.
- `service/install.ps1` and `service/uninstall.ps1` — from PowerShell 7 as administrator. The script does not ask for the account password: the user enters it on the "Log On" tab in services.msc, which also grants the "Log on as a service" right.
- The service reads `.env` from the repository root (a package: from its data folder), and at its first start imports `even-keel.config.json` from there, if there is one; the address and port are `EVEN_KEEL_HOST` and `EVEN_KEEL_PORT` in `.env` (`127.0.0.1:4747` without them), and the port must not be occupied by a manual run.
- The service serves the built `dist/web`: `install.ps1` runs `npm run build`. After a code update, run `install.ps1` again (or `npm run build` and restart the service), otherwise the page is stale or returns 503.
- `install.ps1` stops a running service before `npm install`: the service holds `node_modules/@esbuild/win32-x64/esbuild.exe` (tsx's esbuild child), and npm fails on it with `EPERM`. `npm ci` next to a running Even Keel fails the same way and leaves `node_modules` half-removed (BTN-157: 33 of ~350 packages left); after a stop, `npm ci` again restores it. The binary is held only while the esbuild child runs, that is on a miss of tsx's cache; an update changes the sources, so right after one it is likely, and with a warm cache `npm ci` passed next to a running Even Keel. The service host stops node with `Process.Kill()`, node only, and esbuild exits with it within 2 s (checked with `TSX_DISABLE_CACHE=1`), so stopping the service is enough.
- Stopping the service does not kill background sessions — they are children of the `claude daemon run` daemon.
- **Rebuild after a green main.** `service/rebuild.ps1 -Commit <sha>` builds the checkout it lives in and restarts the service, only if the checkout's HEAD is that commit. With no service `EvenKeel` installed and a `Run` value `EvenKeel` there, it restarts node in the tray host instead (`--autostart`, "The start at sign-in" above). It compiles `dist/` (`npx tsc`) and hands the rest to the update process in rebuild mode (`node dist/src/updates/run.js rebuild`, "Updating from the page" below), so the wait for the chains and the step order are one code with the page's button: when `package-lock.json` is newer than the installed one — wait, stop, `npm install`, build, start (the running service holds esbuild's binary); otherwise build, wait, stop, start. A rebuild never touches git: on a failure it only starts the service again, and the output goes to the caller as well as `logs/update.log`. On the author's workstation it is the last line of Even Keel's own `commands.afterGreen` (`docs/ci.md`), run once GitHub's check of the pushed `dev` is green, whether the chain pushed it or a `git sync` by hand did (BTN-707): `pwsh -NoProfile -Command "& ./service/rebuild.ps1 -Commit (git rev-parse HEAD) *> logs/rebuild.log"`. The `afterGreen` guard has already made sure HEAD is the green commit; `pwsh` is the one process that outlives node's stop (`cmd.exe` running the line dies with it), and its output goes to a file, since the pipe to the service closes when the service stops. Until 2026-11-02 a Forgejo job called it over SSH after the tests; the SSH way below still works for a CI that can reach the workstation. The key's line in the workstation's `authorized_keys` (for an administrator — `C:\ProgramData\ssh\administrators_authorized_keys`) forces the script: `from="<runner host>",restrict,command="pwsh -NoProfile -NonInteractive -File <root>\service\rebuild.ps1" ssh-ed25519 …`; the commit arrives in `SSH_ORIGINAL_COMMAND`.

## Linux and macOS

- `service/install.sh` as your own user (not via `sudo`): `npm install`, `npm run build`, then on Linux the unit `~/.config/systemd/user/even-keel.service` (`systemctl --user`, log — `journalctl --user -u even-keel`), on macOS the agent `~/Library/LaunchAgents/local.even-keel.plist` (`launchctl`, log — `logs/even-keel.log`, no rotation). Running it again rebuilds and restarts. `service/uninstall.sh` removes it.
- `PATH` and the path to `node` are taken from the installer's shell: if `node` changed (nvm and the like), run `install.sh` again.
- The unit has `KillMode=process`, so a restart leaves the CLI daemon of live sessions running. systemd says so in the journal — `Unit process … (claude) remains running after unit stopped` and `Found left-over process … This usually indicates unclean termination` — one pair per process; that is the intended behaviour, not a failure (seen in the BTN-143 trial, Ubuntu 26.04, systemd 259). The MCP gateway's servers are not meant to survive: the service kills them itself on `SIGTERM` (BTN-720), since a left-over one keeps the tracker credentials of its start, and waits for each to exit before node does — `SIGKILL` after 5 s (BTN-723) — so a `huly-mcp` line in that pair means a bug.
- Stopping the service does not kill background sessions: `KillMode=process` in the unit, `AbandonProcessGroup` in the agent. A `--user` unit lives while the user is logged in; to keep it running without a login, use `loginctl enable-linger <user>` (the installer reminds you). The macOS agent lives in the desktop session's domain `gui/<uid>` and works only while the user is signed in to the desktop, at the screen or through Screen Sharing: an SSH login alone has no such domain. `install.sh` checks `launchctl print gui/<uid>` before the build and stops with a message saying so, instead of `Bootstrap failed: 125` at the end (BTN-735). There is no fallback to the background domain `user/<uid>`, without the desktop: Claude Code keeps its sign-in in the login keychain, which only a desktop sign-in unlocks, so sessions started there would not be signed in (assumed, [unverified](unverified/platforms.md#macos)). A Mac without a screen keeps its session through automatic login (System Settings → Users & Groups; needs FileVault off).
- **The update process** (next section) stops and starts the unit with `systemctl --user stop|start <unit>`, the unit read from `/proc/self/cgroup` (`user@….service/…/<unit>.service`; a system unit gets no button), and the agent with `launchctl bootout gui/<uid>/<label>`, waiting until `launchctl print` no longer finds it, then `launchctl bootstrap gui/<uid> <plist>` after the same check of the domain as `install.sh` (`even-keel update` from SSH on a Mac nobody is signed in to says to sign in, not 125); the label is `XPC_SERVICE_NAME` of the service's environment, the plist `~/Library/LaunchAgents/<label>.plist`.
- Linux was verified live in WSL (Ubuntu 26.04, 2026-10-04): tests and type check, `install.sh` and `uninstall.sh`, signing in to `claude` from the page, `/usage` limits, starting a session in a task worktree, and after Done — stopping the session, cleaning up the worktree and branch, its own `main` sync with a push to origin. The CLI must know a new repository as trusted: otherwise the launch pauses and asks you to open `claude` in it once. A native Ubuntu 26.04 server was gone through by README in BTN-143 (installation) and BTN-157 (updating). macOS was not verified; a smoke of the agent on GitHub's macOS runner, `install.sh` to `uninstall.sh`, runs at every push (`docs/ci.md`, "macOS").

## An npm install (BTN-265)

The package `even-keel` (`docs/releases.md`, "Publishing to npm") is the built Even Keel: `dist/src`, `dist/tally`, `dist/web`, with the plugins, the status line and the service scripts next to them. Node does not strip types inside `node_modules`, so nothing there runs through tsx; whatever starts a module by its file (the Tally workers, the SDK executor) picks `.js` when its own file is `.js`.

- **Which install.** `src/locations.ts`: `root` is the folder with the nearest `package.json`, `source` is `git` when it has `src/main.ts`, otherwise `npm`. `home` — where `.env`, `state/` and `logs/` are — is `EVEN_KEEL_DATA`, else a checkout's own folder, else the data folder of the platform: `%LOCALAPPDATA%\even-keel`, `~/Library/Application Support/even-keel`, `$XDG_DATA_HOME/even-keel` (`~/.local/share/even-keel`). npm replaces the package's folder at every update, so nothing of the user's lives there. The variable is not `EVEN_KEEL_HOME`: the `tally` plugin finds the code by that one. `tally/bin/sql.mjs` finds the data the same way.
- **The command** `even-keel` (`src/cli.ts`, `bin` of `package.json`): none — run in the terminal; `install`/`uninstall` — `service/install.*`/`uninstall.*` of the package; `update [version]` — stop the service this package runs, `npm install --global --prefix <its prefix> even-keel@<version>`, start it, with no wait for the chains (the page's button waits). Run from the npx cache (`_npx` in its path), with no command or `install`, it first installs its own version globally and runs `install` from there: the service and the plugins' paths need a folder npx will not clear.
- **The scripts** tell a package by the missing `src/main.ts`: no `npm install` or build; the log in `<data>/logs`; on Windows the host compiled into `<data>\service` (the package's folder is replaced on update) and registered with the data folder as its third argument; the unit and the agent run `node dist/src/main.js` with `EVEN_KEEL_DATA`. `install.ps1 -Data <dir>` and `EVEN_KEEL_DATA` choose another data folder; the service must run as the user whose data folder it is.

## Updating from the page (BTN-163, `src/updates/`)

The update window on the page (`docs/web/interface.md`) sends `updates/install` or `updates/revert`; the service side is `Updater` (`updater.ts`), the process that does the work is `run.ts` over `runner.ts`.

- **Who may.** `updateBlock` (`model.ts`) gives the reason there is no button, in this order: the checkout is still being read, it is not a git checkout (`readCheckout`, `checkout.ts`), Even Keel does not run under a service manager it can drive (`serviceControl`, `control.ts`: the parent process is the tray host of the start at sign-in or a Windows service in `tasklist /svc`, a systemd user unit, a launchd agent), the checkout has tracked changes (`git status --porcelain --untracked-files=no`), HEAD is not on the tag of the installed version. The last one keeps a developer's checkout (`dev`, a task branch) and the CI-built one out: they update by `rebuild.ps1`. The checkout is read at the start and every 10 min. A package has no checkout (`packageBlock`): it needs a global install whose `--prefix` is known (`globalPrefixOf`, `prefix.ts`; `global` otherwise — a local install, the npx cache) and a service manager.
- **Revert.** `logs/update.json` is the record of the last run (`UpdateRecord`). "Revert" is offered only after an update that went through, to the version it came from (`previousOf`), and only when the storage versions it recorded equal the running ones: `{schema: SCHEMA_VERSION, database: SQLITE_VERSIONS + STEPS.length, tally: TALLY_SCHEMA_VERSION}`. Otherwise `previous.blocked` is `storage` and the page explains the manual way back. A revert release (a release that takes back an earlier one, `### Reverted` in its notes) is an update like any other, so it may come after a storage change; the rule is in `docs/releases.md`.
- **Settling.** Before the process starts, the service waits up to 5 min (`SETTLE_MS`) until `busyChains` (`settle.ts`) is empty: no unpaused chain is launching, handing over or closing a task. A chain waiting for the CI of main does not count — for a rebuild that CI is the run calling it, and the wait survives a restart (`state/`); the project's own check (`ciWait.local`) does. A chain that never settles is not waited for past the 5 min. The page shows the projects waited for (`progress.waiting`).
- **The process.** The service cannot update itself: `git checkout`, `npm ci` and the build replace its own code, and stopping it kills its children on systemd and launchd unless they are detached. So `launchRunner` (`launch.ts`) copies the compiled `dist/src/updates/` to a fresh folder in the OS temp folder (with a `package.json` of `"type": "module"` and the mark `.even-keel-update`), writes the plan there and starts `node run.js plan.json` detached (`detached`, `stdio: 'ignore'`), and the service goes on answering. The modules of the runner import only `node:*` and each other, so the copy runs alone. It survives the stop: the Windows host kills only its node child (`Process.Kill`), the unit has `KillMode=process`, the agent `AbandonProcessGroup`. It deletes its folder when done.
- **Steps** (`stepsOf`, `steps.ts`): update — stop, `git fetch --tags`, checkout, `npm ci`, `npm run build`, start, answer; revert — the same without the fetch. The checkout keeps the branch the checkout was on (`git checkout -B <branch> <tag>`, so a `git pull` by hand still works) or stays detached. npm runs through the node of the process (`npm-cli.js` next to it), since the service's `PATH` may lack it. "Answer" polls `GET /api/state` (loopback, no token; `stateUrlOf`) for 2 min (`ANSWER_MS`) until a start later than the one before the update answers with the target version, and the same start still answers 10 s on (`STEADY_MS`), so a service crashing in a loop does not pass. A package's update is stop, `npm install --global --prefix <prefix> even-keel@<version>` (`install`), start, answer, run from the data folder: a working folder inside the package would hold it on Windows while npm replaces it (`workingDir`, `runner.ts`).
- **Rollback** (`rollbackOf`, `runSteps`): a failure at stop or fetch only starts the service again and waits for its answer; at any later step — stop, check out the commit it started from, install, build, start, answer; a package's — stop, install the version it started from (`restore`), start, answer. A failed stop in the rollback is ignored (the service may be down already); any other failed rollback step ends it, recorded as `rollback.failed`.
- **The outcome** is written to `logs/update.json` of the data folder (a temporary file and a rename: the new service reads it at its start), the log of every step and its output to `logs/update.log` (appended). Neither is under `state/`, so they are no state format. The service reads the record at its start and again whenever the file changes (`watchFile`, every 5 s): the process writes it only after its answer step, so after the new service has started (found live in BTN-272). It logs it, and the page shows it as a toast until `updates/seen`. A record that does not end on the running version (`leftRunning`: one that went through ends on its target, a failed one on the version it came from, a failed rollback on either) is left out — no result and no "Revert" — since `even-keel update` from a terminal or a `git pull` by hand moved the install after it; the file stays, the log says so (BTN-315). After a revert the newer release is offered again as "Update": the button is an offer, nothing updates by itself. A process that could not even be started (no `dist/src/updates/run.js`) is a `launch` failure, kept in memory.
- **Rebuild mode.** `service/rebuild.ps1` runs the same code: `node dist/src/updates/run.js rebuild --root <dir> --state <url> --service <name>|--autostart <exe> [--wait <s>]` copies itself to the temp folder like the button does, then runs in the foreground with the log echoed. Its steps have no git and its rollback only starts the service (section "Windows" above).
