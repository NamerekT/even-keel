# Storage

Even Keel's state is one PGlite database, the folder `state/even-keel/` (`EVEN_KEEL_STATE_DIR`): since BTN-147 a database, since BTN-198 PGlite instead of the `node:sqlite` file `state/even-keel.db`, since BTN-199 with the settings and the project records instead of the file `even-keel.config.json` (imported once, below). `account.json`, `packages.json` (and its cache `packages/`), `rate-limits.json`, `codex/`, `claude-sdk/` (BTN-239, `docs/sessions/sdk.md`) and `rule-history.jsonl` stay files of `state/`; Tally's database is its own (`docs/stats.md`).

The remaining JSON files written through `writeAtomic` (`src/storage/atomic.ts`) replace the destination with a temporary sibling file. On Windows, `rename` retries `EPERM`, `EACCES` and `EBUSY` for up to 3 seconds, with synchronous pauses growing from 10 to 100 ms; this keeps each write whole while an external reader or virus scanner briefly holds the destination. In-process readers of these files must use synchronous fs calls: an asynchronous read can leave a descriptor open until the event loop resumes, while the synchronous rename retries prevent that close for the entire retry window (BTN-499). The Codex and SDK registries read and list their session JSON synchronously while keeping their Promise interfaces. Other errors fail immediately. A failed write removes its temporary file. Off Windows the replaced file keeps its permissions (the temporary file is created owner-only and then given the old mode), so a `600` file does not turn `644` under the umask (EKR-95); a caller may name the mode instead, as `state/packages.json` does with `600` because a package's settings may hold a token. This covers the Codex and Claude SDK session registries, the account ledger, package state, file migrations and state exports; database transactions use their own storage path. The Windows reproduction and registry stress check are recorded in [verified.md](verified/sessions.md).

## The database (`src/storage/database.ts`, `src/storage/owner.ts`)

- The engine is PGlite (Postgres in WASM, the one Tally embeds): the folder holds `pgdata/` and, while a process holds it, `owner.json`.
- A PGlite folder has one session in one process. The service's main thread owns it: `src/main.ts` opens it before the service module loads (`prepareDatabase` → `keepDatabase`), `src/service.ts` takes it (`keptDatabase`) and closes it last on shutdown. The owner serves the database to `pg` clients on a loopback port of its own (`@electric-sql/pglite-socket`) and writes `{ pid, port }` into `owner.json`; an owner is live only when its pid runs and its port answers, so a file left by a crash is no owner.
- The folder is claimed before PGlite opens it (BTN-301; `src/storage/claim.ts`, which Tally's local database uses too, BTN-320): `owner.json` with `{ pid, since }` and no port yet is put in place as a hard link, which fails while one is there, so of two processes starting together one gets it and the other sees the claim. The port is written over it (a rename) once the server listens; the claim goes when the open fails or the database closes. A claim without a port is an open in progress while its pid runs, for at most 10 minutes; a stale claim is removed and taken again. An open refused because another process holds the folder leaves the service with the page's "process … holds the database" and the API at 503 until a restart, even after the holder closes.
- Queries are small: no worker thread. Readers through the port see whole transactions: the server gets a proxy of the database whose `runExclusive` also takes the transaction lock (`wholeTransactions`), so a read never lands between the statements of the service's transaction.
- Writes are not awaited by the service: `Writes` tracks them, logs a failure (`storage: … not saved`) and is settled on shutdown before the database closes. Order holds because PGlite runs queries and transactions in the order they were called, and every write starts its first query at the call. Writes of several rows go through `inTransaction` (a call inside another joins it).
- `Mailbox` keeps its rows in memory (`Mailbox.open`) and writes behind, so `settle` stays atomic in one thread and `getState` stays synchronous; the posted questions are loaded at start (`loadQuestions`) and saved behind.
- A project is named by its id (`projects.id`) in every `project_id`, as the running service names it (BTN-271): `src/chain/store.ts` reads and writes the ids as they are (`docs/chain/state.md`). Only `setting_values` has a foreign key to `projects`: the chain's tables keep the rows of a removed project as they did.
- Tests use `memoryDatabase()` (`src/storage/memory.ts`): an independent copy of a database migrated once per run. `test/pglite-template.ts` builds a fresh cluster, the SQLite import's v3 schema and the current schema with the real steps, then saves each closed folder and its `dumpDataDir` dump. `test/pglite.ts` starts raw PGlite clusters from the fresh copy; its test-only `openDatabase` wrapper uses a migrated template only for a new database and the exact standard steps for v3 or the current schema. In-memory copies use `loadDataDir`; disk copies use `test/copy-template.ts`, which scans each template once and copies its files asynchronously without repeating the directory traversal and metadata checks. Copies request a filesystem reflink when supported, falling back to ordinary file copies; there are no hard links. Existing databases, every frozen SQL sample and custom steps use the original migration path. `memoryDatabase()` closes each copy when its test ends.

- Versions 1 and 2 were the SQLite file (`PRAGMA user_version`); the numbering goes on in PGlite from 3. The version is the one row of `schema_version`. `STEPS[n]` takes the database from version `2 + n` to the next one in one transaction together with the new version, so a step that fails leaves the old version and none of its tables. ## Settings at the first start (`src/settings/import.ts`)

After `prepareDatabase`, `src/main.ts` runs `prepareSettings`: it mirrors the definitions and, the first time (no `config.imported` in `service_state`), imports the config file (`EVEN_KEEL_CONFIG`, `even-keel.config.json` of the root by default) whole in one transaction: brought to the current schema (`currentConfig`), entries without an id given one, checked as the service would run it, `updates.dismissed` taken out into `service_state`. The switches step 4 moved from `chain_flags` stay unless the file sets them. The file is renamed to `even-keel.config.json.imported`; the log line counts projects and settings. A file that does not parse stops the start with its notice (the blocked page) and stays as it is; no file — an empty start, marked imported too.

Later starts never read the file: one found there is logged as not read. `upgradeStorage` still runs first, so a pre-v9 config file of an old install is migrated together with the state files before the import.

## Import at the first start (`src/storage/state-files.ts`)

`src/main.ts` runs `upgradeStorage` (the files to their current schema, `docs/chain/state.md`) and then `prepareDatabase`:

- With a database: it is opened as its owner and brought to the current step. A v0.1 state file (`chain.json`, `questions.json`, `launches.jsonl`, `handoffs/`) or `even-keel.db` still next to it is not read; the log says so once per start.
- Without one, but with the SQLite file `even-keel.db` (versions 1–2): its rows are read whole (`sqliteRows`; the journal is switched to `DELETE` first, so a WAL the old service left folds into the file), written into a new database `state/even-keel.import/` in one transaction (`insertRows`, which also moves the id counters past the rows), and that folder is renamed to `state/even-keel` only once complete. The file is renamed to `even-keel.db.imported`; the log line counts the rows per table.
- Without either: the v0.1 files are read and checked whole (`readStateFiles`; a damaged or newer file is `storage.damaged` / `storage.newer` and nothing is written) and imported the same way; then each file or folder is renamed to `<name>.imported`. A handoff snapshot that does not parse is left out and logged.
- A failed import removes `even-keel.import` and leaves everything as it was (`storage.importFailed`). Nothing at all: an empty database.
- The rename of `even-keel.import` is retried for up to three seconds on Windows when it fails with `EPERM`, `EACCES` or `EBUSY` (`renameOver`, `src/storage/atomic.ts`): a virus scanner or the indexer may hold the folder just closed (BTN-674).
- A blocked start shows the error under the notice — an fs or database error, not a notice of its own — as the notice's detail on the page and as a `cause: …` log line after the main one, with its `code` and path when the message lacks them (`noticeWithCause`, `causeLine`, `src/notice/notice.ts`).

Tested on every frozen sample `test/fixtures/schema-v2` … `v9` and `database-v1`, `v2` (`src/storage/state-files.test.ts`, `database.test.ts`). The SQLite import was run on a copy of the live state on 2026-10-18 (889 launches, 93 snapshots, 10 closed tasks: every table came over with the same row count, in about 2.5 s).

## Backup, export, rollback

- `npm run storage -- backup <dir>` — a copy into a new folder laid out like `state/even-keel` (`<dir>/pgdata`), also while the service runs: all tables read in one statement (`rowsOf`), so the copy is consistent, then written into a fresh database (`backupDatabase` in `src/storage/copy.ts`); then the attachments' bytes `files/` are copied, without half-written uploads, so every record of the copy finds its file. To restore, stop the service and put the folder in place of `state/even-keel`. It holds the settings and projects too, and the trackers' profiles with their secrets and the OpenRouter management keys in the clear: keep a backup as private as `.env`. With `.env` it is everything a move to another machine needs.
- `npm run storage -- export <dir>` — the state as the v0.1 files, into an empty folder. A v0.1 Even Keel reads them, and so does the import: to roll back, stop the service, export, put the files into `state/` of the old version, and the settings as its `even-keel.config.json` (`config-export`).
- `npm run storage -- config-export <file>` — the settings and projects as a file of the config's format, into a new file (`exportConfig`). No profile and no secret goes into it; `config-import` leaves the profiles and `projects.profile_id` as they are.
- `npm run storage -- config-import <file>` — such a file (of any schema version) in place of the settings and projects, whole: a key it lacks goes back to its default, a project it lacks goes with its setting rows (`importConfig`, writer `hand`). The file is read and checked before anything is written. Through the port of a running service; the service picks it up at its next look (`ConfigStore`, every 2 s). It is the way to edit the settings by hand: export, edit, import.
- Both read the database of `EVEN_KEEL_STATE_DIR` (the checkout's `state/` by default; `.env` is loaded) through `readStateDatabase`. `closed_tasks` has no file: only the backup keeps it.

## Readers outside the service

`readStateDatabase` (`src/storage/owner.ts`) neither migrates nor reads a database of another version (`checkVersion`). With a live owner it connects to its port; a live owner always means "connect", even with the reader's own pid, because Tally's collector runs in a worker thread of the service. With no owner it opens the folder itself and, while open, owns it the same way: `owner.json` and a port, so a second reader connects to it. A claim without a port is waited for, up to 30 seconds, and then connected to: a reader started together with the service reads through it instead of failing.

Tally's collector (`evenKeelState` in `tally/src/collect.ts`) reads the launch log, the snapshots and the projects' folders and branches (`select repo, branch from projects`) this way; the config file only when there is no database yet. Without a database it reads the SQLite file (`sqliteInMemory`: its rows in a database in memory) or else the v0.1 files: a merge reaches the collector before the restarted service has imported them.
