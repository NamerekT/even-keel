# Storage

Even Keel's state is one PGlite database, the folder `state/even-keel/` (`EVEN_KEEL_STATE_DIR`): since BTN-147 a database, since BTN-198 PGlite instead of the `node:sqlite` file `state/even-keel.db`, since BTN-199 with the settings and the project records instead of the file `even-keel.config.json` (imported once, below). `account.json`, `packages.json` (and its cache `packages/`), `rate-limits.json`, `codex/`, `claude-sdk/` (BTN-239, `docs/sessions/sdk.md`) and `rule-history.jsonl` stay files of `state/`; Tally's database is its own (`docs/stats.md`).

The remaining JSON files written through `writeAtomic` (`src/storage/atomic.ts`) replace the destination with a temporary sibling file. On Windows, `rename` retries `EPERM`, `EACCES` and `EBUSY` for up to 3 seconds, with synchronous pauses growing from 10 to 100 ms; this keeps each write whole while an external reader or virus scanner briefly holds the destination. In-process readers of these files must use synchronous fs calls: an asynchronous read can leave a descriptor open until the event loop resumes, while the synchronous rename retries prevent that close for the entire retry window (BTN-499). The Codex and SDK registries read and list their session JSON synchronously while keeping their Promise interfaces. Other errors fail immediately. A failed write removes its temporary file. Off Windows the replaced file keeps its permissions (the temporary file is created owner-only and then given the old mode), so a `600` file does not turn `644` under the umask (EKR-95); a caller may name the mode instead, as `state/packages.json` does with `600` because a package's settings may hold a token. This covers the Codex and Claude SDK session registries, the account ledger, package state, file migrations and state exports; database transactions use their own storage path. The Windows reproduction and registry stress check are recorded in [verified.md](verified/sessions.md).

## The database (`src/storage/database.ts`, `src/storage/owner.ts`)

Step 45 adds the README badge's `badge_translations` cache (tracker source, task, title hash, attempt time and English
title) and `badge_translation_spend`, its retained usage ledger. Translation attempts are claimed before the request,
so a restart keeps the 30-minute retry interval; Tally reads the ledger through the owner and imports it by message id
without duplicates. See [English titles](badge.md#english-titles).

- The engine is PGlite (Postgres in WASM, the one Tally embeds): the folder holds `pgdata/` and, while a process holds it, `owner.json`.
- A PGlite folder has one session in one process. The service's main thread owns it: `src/start.ts` opens it before the service module loads (`prepareDatabase` → `keepDatabase`), `src/service.ts` takes it (`keptDatabase`) and closes it last on shutdown. The owner serves the database to `pg` clients on a loopback port of its own (`@electric-sql/pglite-socket`) and writes `{ pid, port }` into `owner.json`; an owner is live only when its pid runs and its port answers, so a file left by a crash is no owner.
- The folder is claimed before PGlite opens it (BTN-301; `src/storage/claim.ts`, which Tally's local database uses too, BTN-320): `owner.json` with `{ pid, since }` and no port yet is put in place as a hard link, which fails while one is there, so of two processes starting together one gets it and the other sees the claim. The port is written over it (a rename) once the server listens; the claim goes when the open fails or the database closes. A claim without a port is an open in progress while its pid runs, for at most 10 minutes; a stale claim is removed and taken again. An open refused because another process holds the folder leaves the service with the page's `storage.held` notice and the API at 503. The service retries every 3 seconds, indefinitely, using the same claim rules; it never displaces a live holder. The page names the current holder if it changes. Once the folder opens, the blocked server closes its connections and the full service starts normally; an open page reconnects automatically. Only the first refusal and successful recovery are logged. A different startup error replaces the reason and stops retries until a restart (BTN-1069; `src/storage/startup.ts`).
- Queries are small: no worker thread. Readers through the port see whole transactions: the server gets a proxy of the database whose `runExclusive` also takes the transaction lock (`wholeTransactions`), so a read never lands between the statements of the service's transaction.
- Writes are not awaited by the service: `Writes` tracks them, logs a failure (`storage: … not saved`) and is settled on shutdown before the database closes. Order holds because PGlite runs queries and transactions in the order they were called, and every write starts its first query at the call. Writes of several rows go through `inTransaction` (a call inside another joins it).
- `Mailbox` keeps its rows in memory (`Mailbox.open`) and writes behind, so `settle` stays atomic in one thread and `getState` stays synchronous; the posted questions are loaded at start (`loadQuestions`) and saved behind.
- A project is named by its id (`projects.id`) in every `project_id`, as the running service names it (BTN-271): `src/chain/store.ts` reads and writes the ids as they are (`docs/chain/state.md`). Only `setting_values` has a foreign key to `projects`: the chain's tables keep the rows of a removed project as they did.
- Tests use `memoryDatabase()` (`src/storage/memory.ts`): an independent copy of a database migrated once per run. `test/pglite-template.ts` builds a fresh cluster, the SQLite import's v3 schema and the current schema with the real steps, then saves each closed folder and its `dumpDataDir` dump. `test/pglite.ts` starts raw PGlite clusters from the fresh copy; its test-only `openDatabase` wrapper uses a migrated template only for a new database and the exact standard steps for v3 or the current schema. In-memory copies use `loadDataDir`; disk copies use `test/copy-template.ts`, which scans each template once and copies its files asynchronously without repeating the directory traversal and metadata checks. Copies request a filesystem reflink when supported, falling back to ordinary file copies; there are no hard links. Existing databases, every frozen SQL sample and custom steps use the original migration path. `memoryDatabase()` closes each copy when its test ends.
- A vitest run has its own temp folder, so tests that never delete what they create in `os.tmpdir()` leave nothing in the OS one (BTN-1316: ~20 GB a day on the workstation). `test/temp-setup.ts`, the first global setup, creates `<OS temp>/even-keel-tests/<pid>-<6 chars>/` with `run.json` (pid and start time) and points `TEMP`, `TMP` and `TMPDIR` of `process.env` at it before the pool starts: the workers, their child processes (the e2e service, git, CLI stubs) and the PGlite templates all write there. The root stays in the OS temp, not the checkout's `.temp/` — tests create git repositories and folders outside any repository — and the names are short for Windows' MAX_PATH. The workstation's Defender exclusion names exactly `%LOCALAPPDATA%\Temp\even-keel-tests`: keep the folder's name and place. The teardown removes the root; what a live child process still holds stays, with one warning line and the count of entries left, and the run does not fail. At its start each run sweeps what interrupted runs (Ctrl+C, a killed session) left: another run's folder goes when its pid is not alive or it started more than 24 h ago (a pid may be reused), a folder without `run.json` by its own age over 24 h; a live run in another worktree is never touched (`isStale`, `test/temp-root.ts`). A test that spawns a process with an environment of its own, without `...process.env`, passes `TEMP`, `TMP` and `TMPDIR` on (`src/packages/gateway.test.ts`). Folders left in the OS temp before this are not swept: some share common names with other programs.
- A git repository a test builds the same way every time (`init`, its config, a first commit, a bare remote with clones) is built once per run and copied whole (BTN-1483): on Windows each git process is costly, and Defender checks every one whatever the exclusions. `copyRepository(name, folder, build)` (`src/git/template.fixture.ts`) runs `build` once in a folder of its own under `<run root>/git-templates/`, renamed into place whole, so the workers of one run share it; each call copies it with `cpSync` and turns the build folder's paths in git's `config`, `.git` and `gitdir` files into the copy's (`retarget`: plain, doubled backslashes, forward slashes). One `name` means one build: the e2e `Harness` names its kind by the checkouts it asks for (`e2e-forge-second`). What a test checks — git's own behaviour, a history of its own — stays on git. To count git processes, set `GIT_TRACE2_EVENT` to a folder per test file from a setup file (`expect.getState().testPath`): git writes a file per process there, children's `sid` with a `/`; a wrapper on `PATH` is no way, `execFile` does not find one without `.exe`.

## Vacuum (`src/storage/vacuum.ts`)

PGlite is one session: `show autovacuum` says `on`, but no autovacuum worker runs, so a row an update or a delete leaves dead is never reclaimed unless the owner asks (BTN-952). The service asks twice:

- **At the start**, right after the database is opened and before the service module loads (`compactDatabase` in `src/start.ts`): `VACUUM FULL`, then `ANALYZE`. It rewrites every table without its dead rows, so the files shrink, and gives the planner its row counts. Nothing reads the database yet, so its table locks and its time hold nobody. The log gets `storage: the database was compacted in N ms`.
- **Every hour** while running (`VACUUM_EVERY_MS`, `vacuumDatabase` in `src/service.ts`, through `Writes`): a plain `VACUUM` of the whole database, which makes the dead rows reusable without shrinking the files. No table list: a new often-rewritten table is covered without a change here. No `ANALYZE` in it — it is most of the cost and the row counts of the start are enough for tables this small.

A failure of either is one log line (`storage: the vacuum failed: …`) and nothing else: the service starts and runs without it. Readers that open the folder themselves (`readStateDatabase` with no owner) and the tests do neither.

Measured on a copy of the live `pgdata` (2026-11-10, 21 projects, the database 41 MB, `session_windows` 16 MB for 816 rows, `chain_lists` 9.8 MB for 44): `VACUUM FULL` 0.85 s and the database 15 MB after it; the first plain `VACUUM (ANALYZE)` of the bloated database 0.6 s; on the compacted one a plain `VACUUM` 42 ms, with `ANALYZE` 220 ms. PGlite is synchronous: these are the times the event loop is held.

## Import at the first start (`src/storage/state-files.ts`)

`src/start.ts` runs `upgradeStorage` (the files to their current schema, `docs/chain/state.md`) and then `prepareDatabase`:

- With a database: it is opened as its owner and brought to the current step. A v0.1 state file (`chain.json`, `questions.json`, `launches.jsonl`, `handoffs/`) or `even-keel.db` still next to it is not read; the log says so once per start.
- Without one, but with the SQLite file `even-keel.db` (versions 1–2): its rows are read whole (`sqliteRows`; the journal is switched to `DELETE` first, so a WAL the old service left folds into the file), written into a new database `state/even-keel.import/` in one transaction (`insertRows`, which also moves the id counters past the rows), and that folder is renamed to `state/even-keel` only once complete. The file is renamed to `even-keel.db.imported`; the log line counts the rows per table.
- Without either: the v0.1 files are read and checked whole (`readStateFiles`; a damaged or newer file is `storage.damaged` / `storage.newer` and nothing is written) and imported the same way; then each file or folder is renamed to `<name>.imported`. A handoff snapshot that does not parse is left out and logged.
- A failed import removes `even-keel.import` and leaves everything as it was (`storage.importFailed`). Nothing at all: an empty database.
- The rename of `even-keel.import` is retried for up to three seconds on Windows when it fails with `EPERM`, `EACCES` or `EBUSY` (`renameOver`, `src/storage/atomic.ts`): a virus scanner or the indexer may hold the folder just closed (BTN-674).
- A blocked start shows the error under the notice — an fs or database error, not a notice of its own — as the notice's detail on the page and as a `cause: …` log line after the main one, with its `code` and path when the message lacks them (`noticeWithCause`, `causeLine`, `src/notice/notice.ts`).

The SQLite import was run on a copy of the live state on 2026-10-18 (889 launches, 93 snapshots, 10 closed tasks: every table came over with the same row count, in about 2.5 s).

## Backup, export, rollback

- `npm run storage -- backup <dir>` — a copy into a new folder laid out like `state/even-keel` (`<dir>/pgdata`), also while the service runs: all tables read in one statement (`rowsOf`), so the copy is consistent, then written into a fresh database (`backupDatabase` in `src/storage/copy.ts`); then the attachments' bytes `files/` are copied, without half-written uploads, so every record of the copy finds its file, and the memory repositories `memory/`, without git's `*.lock` files. To restore, stop the service and put the folder in place of `state/even-keel`. It holds the settings and projects too, and the trackers' profiles with their secrets and the OpenRouter management keys in the clear: keep a backup as private as `.env`. For a move also keep `state/machine/` with the service stopped and the agent account folders; the hub backup retains machine rows only as they were at their original migration. The hub's memory folders need not move as long as `memory/` does ("The memory repositories" below).
- **The automatic copies** (BTN-1083, `src/storage/backup.ts`, `backup-schedule.ts`). The service looks 5 min after its start and then every 10 min; when the newest checked copy of the folder is older than a day (`BACKUP_EVERY_MS`) it makes one, and a failed one is tried again after an hour. The rows are read in the service's thread (`rowsTextOf`, one statement, as the hand backup) and handed to a worker thread (`backup-worker.ts`; run from the sources, it gets tsx's loader as its only flag, since under vitest, as in e2e, it inherits none, BTN-1259), which writes the copy into `even-keel-auto-<YYYYMMDD>-<HHMMSS>-v<schema>` and checks it: a trial restore copies it whole into a temporary folder, opens it, compares the schema version and each table's row count with what was read, and hashes every attachment `builtin_files` names. Only then `check.json` (`CopyCheck`: time, version, rows per table, files) is written into the copy: a folder without it is no checked copy. A failed write or check removes the copy and leaves the older ones. Rotation (`rotate`) keeps the newest `backup.keep` checked copies, removes older checked ones and unchecked ones older than the newest checked, and touches no folder of another name, so a hand backup next to them stays. The folder is `backup.dir`, or `backups/` in the state folder (`backupDirOf`); both settings are read at each copy, so a change applies at the next one. The page's save refuses a `backup.dir` that names an existing file (`checkCopiesDir`, `config.backupDirFile`); a folder that later turns into a file or cannot be read has no copies (`ownCopies`), so the page's state still builds and shows the failed copy's banner (BTN-1179). The copy is a hand backup's layout: restored the same way, and as private as one.
- **Before schema steps.** At the start, when an existing database is about to take new steps (an update), `openDatabase` calls `copyBeforeSteps` first: the copy is made and checked in the start's own thread on the old schema, named with the old version, and rotated with the rest (the settings read from their rows as they are). A failure is logged and does not stop the start; the service shows it until a copy succeeds.
- **What the page gets.** `backup` of the state (`BackupView`: the folder, the newest checked copy's time, whether one runs, the failure as `storage.backupFailed` or `storage.backupCheckFailed`); the command `storage/backup` starts one at once (refused with `storage.backupRunning` while one runs). The page shows them on the "Backups" tab of Shared settings and the failure in a banner over every page (`BackupBanner`). The service's stop aborts a copy under way: the worker is terminated and its half-written folder removed, with no failure shown; a crash mid-copy leaves an unchecked folder that the rotation after the next copy removes.
- `npm run storage -- export <dir>` — the state as the v0.1 files, into an empty folder. A v0.1 Even Keel reads them, and so does the import: to roll back, stop the service, export, put the files into `state/` of the old version, and the settings as its `even-keel.config.json` (`config-export`).
- `npm run storage -- config-export <file>` — the settings and projects as a file of the config's format, into a new file (`exportConfig`). No profile and no secret goes into it; `config-import` leaves the profiles and `projects.profile_id` as they are.
- `npm run storage -- config-import <file>` — such a file (of any schema version) in place of the settings and projects, whole: a key it lacks goes back to its default, a project it lacks goes with its setting rows (`importConfig`, writer `hand`). The file is read and checked before anything is written. Through the port of a running service; the service picks it up at its next look (`ConfigStore`, every 2 s). It is the way to edit the settings by hand: export, edit, import.
- Both read the database of `EVEN_KEEL_STATE_DIR` (the checkout's `state/` by default; `.env` is loaded) through `readStateDatabase`. `closed_tasks` has no file: only the backup keeps it.

## The memory repositories (BTN-1646)

`state/even-keel/memory/<project id>.git` — the bare git repository of each project's memory (`memoryDirOf`, `MemoryHub` in `src/memory/git/hub.ts`, `docs/sessions/memory.md`, "The hub's repositories"). The service owns them, as it owns the database beside them: only its working copies push into them, nothing else writes there. A repository is made at a project's first working copy and stays after the project is removed.

- **Backup.** The automatic copies, the copy before schema steps and `npm run storage -- backup` copy `memory/` after the rows, leaving out `*.lock`. A copy taken while a sync pushes may miss that push; the working copies hold their whole history and push it again at their next sync.
- **Restore on another host.** `memory/` moves with `state/even-keel`. A project whose repository is missing gets an empty one and its working copy on the hub pushes its history into it; with neither the repository nor the old hub's memory folder, the memory starts empty: the transfer from `memory_records` is not repeated (`memory.transferred`).

## Readers outside the service

`readStateDatabase` (`src/storage/owner.ts`) neither migrates nor reads a database of another version (`checkVersion`). With a live owner it connects to its port; a live owner always means "connect", even with the reader's own pid, because Tally's collector runs in a worker thread of the service. With no owner it opens the folder itself and, while open, owns it the same way: `owner.json` and a port, so a second reader connects to it. A claim without a port is waited for, up to 30 seconds, and then connected to: a reader started together with the service reads through it instead of failing.

The port needs PGlite 0.5.17 or later (BTN-1437). The socket server hands PGlite a client's extended-protocol messages one by one, and an older PGlite answered a failed one with a ReadyForQuery of its own and then the Sync with another. A reader in another process got the second one as the empty answer of its next query, every answer after that went one query late, and the connection broke with `Received unexpected parseComplete message`. Inside one process both usually came in one chunk and `pg.Client` dropped the extra one, so the test (`state-reader-errors.test.ts`) reads the port message by message, not through `pg`.

Tally's collector (`evenKeelState` in `tally/src/collect.ts`) reads the launch log, the snapshots and the projects' folders and branches (`select repo, branch from projects`) this way; the config file only when there is no database yet. Without a database it reads the SQLite file (`sqliteInMemory`: its rows in a database in memory) or else the v0.1 files: a merge reaches the collector before the restarted service has imported them.
