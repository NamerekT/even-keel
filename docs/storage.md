# Storage

Even Keel's state is one PGlite database, the folder `state/even-keel/` (`EVEN_KEEL_STATE_DIR`): since BTN-147 a database, since BTN-198 PGlite instead of the `node:sqlite` file `state/even-keel.db`, since BTN-199 with the settings and the project records instead of the file `even-keel.config.json` (imported once, below). `account.json`, `packages.json` (and its cache `packages/`), `rate-limits.json`, `codex/`, `claude-sdk/` (BTN-239, `docs/sessions.md`) and `rule-history.jsonl` stay files of `state/`; Tally's database is its own (`docs/stats.md`).

The remaining JSON files written through `writeAtomic` (`src/storage/atomic.ts`) replace the destination with a temporary sibling file. On Windows, `rename` retries `EPERM`, `EACCES` and `EBUSY` for up to 3 seconds, with synchronous pauses growing from 10 to 100 ms; this keeps each write whole while an external reader or virus scanner briefly holds the destination. In-process readers of these files must use synchronous fs calls: an asynchronous read can leave a descriptor open until the event loop resumes, while the synchronous rename retries prevent that close for the entire retry window (BTN-499). The Codex and SDK registries read and list their session JSON synchronously while keeping their Promise interfaces. Other errors fail immediately. A failed write removes its temporary file. This covers the Codex and Claude SDK session registries, the account ledger, package state, file migrations and state exports; database transactions use their own storage path. The Windows reproduction and registry stress check are recorded in [verified.md](verified.md#sessions).

## The database (`src/storage/database.ts`, `src/storage/owner.ts`)

- The engine is PGlite (Postgres in WASM, the one Tally embeds): the folder holds `pgdata/` and, while a process holds it, `owner.json`.
- A PGlite folder has one session in one process. The service's main thread owns it: `src/main.ts` opens it before the service module loads (`prepareDatabase` → `keepDatabase`), `src/service.ts` takes it (`keptDatabase`) and closes it last on shutdown. The owner serves the database to `pg` clients on a loopback port of its own (`@electric-sql/pglite-socket`) and writes `{ pid, port }` into `owner.json`; an owner is live only when its pid runs and its port answers, so a file left by a crash is no owner.
- The folder is claimed before PGlite opens it (BTN-301; `src/storage/claim.ts`, which Tally's local database uses too, BTN-320): `owner.json` with `{ pid, since }` and no port yet is put in place as a hard link, which fails while one is there, so of two processes starting together one gets it and the other sees the claim. The port is written over it (a rename) once the server listens; the claim goes when the open fails or the database closes. A claim without a port is an open in progress while its pid runs, for at most 10 minutes; a stale claim is removed and taken again. An open refused because another process holds the folder leaves the service with the page's "process … holds the database" and the API at 503 until a restart, even after the holder closes.
- Queries are small: no worker thread. Readers through the port see whole transactions: the server gets a proxy of the database whose `runExclusive` also takes the transaction lock (`wholeTransactions`), so a read never lands between the statements of the service's transaction.
- Writes are not awaited by the service: `Writes` tracks them, logs a failure (`storage: … not saved`) and is settled on shutdown before the database closes. Order holds because PGlite runs queries and transactions in the order they were called, and every write starts its first query at the call. Writes of several rows go through `inTransaction` (a call inside another joins it).
- `Mailbox` keeps its rows in memory (`Mailbox.open`) and writes behind, so `settle` stays atomic in one thread and `getState` stays synchronous; the posted questions are loaded at start (`loadQuestions`) and saved behind.
- A project is named by its id (`projects.id`) in every `project_id`, as the running service names it (BTN-271): `src/chain/store.ts` reads and writes the ids as they are (`docs/chain.md`). Only `setting_values` has a foreign key to `projects`: the chain's tables keep the rows of a removed project as they did.
- Tests use `memoryDatabase()` (`src/storage/memory.ts`): an independent copy of a database migrated once per run. `test/pglite-template.ts` builds a fresh cluster, the SQLite import's v3 schema and the current schema with the real steps, then saves each closed folder and its `dumpDataDir` dump. `test/pglite.ts` starts raw PGlite clusters from the fresh copy; its test-only `openDatabase` wrapper uses a migrated template only for a new database and the exact standard steps for v3 or the current schema. In-memory copies use `loadDataDir`; disk copies use `test/copy-template.ts`, which scans each template once and copies its files asynchronously without repeating the directory traversal and metadata checks. Copies request a filesystem reflink when supported, falling back to ordinary file copies; there are no hard links. Existing databases, every frozen SQL sample and custom steps use the original migration path. `memoryDatabase()` closes each copy when its test ends.

## Schema steps

- Step 19 and file schema v20 (BTN-541) split Protection's one tracker group `deleteTracker` into a group per tracker (`deleteHuly`, `deleteGithub`, `deleteGitlab`, `deleteLinear`, `deleteJira`): a disabled `deleteTracker` disables all five, at the shared and the project level. The step rewrites the `protection` rows of `setting_values`; the file migration (`trackerGroupsOwned`) does the same on import. The frozen v19 sample holds a shared and a project row with the old group; `database-protection.test.ts` checks both paths.
- Step 20 and file schema v21 (BTN-603): the default of `cli.<provider>` became `system`. An existing database (`even_keel.migration_from` above 0) gets a shared `checked` row for each provider it left out, and the `cli` definition if it had none, so its sessions stay on the copy; a fresh one passes the step with nothing written. The file migration (`cliChecked`) fills the same providers with `checked` on import. The frozen sample is `test/fixtures/database-v20/`; `database-cli.test.ts` checks both paths.
- Step 21 and file schema v22 (BTN-610): the Agent SDK of Claude runs only on the checked CLI. A shared `execution.claude` row `"sdk"` writes the shared `cli.claude` row `"checked"` (by `service`), over `"system"` or where none was and the default `system` applied, with the `cli` definition if it had none; any other execution is left alone. The file migration (`sdkChecked`) writes the same into a v21 file. The frozen samples are `test/fixtures/database-v21/` and `test/fixtures/schema-v22/`; `database-sdk-cli.test.ts` checks both paths.
- Step 22 (BTN-558): `mailbox.reason`, why a returned message came back — `asked`, `gone` or `closed` (the task was over for the chain); `null` on rows returned before it, which the page reads as `asked`. No file schema change: the mailbox is not in the config. The frozen sample is `test/fixtures/database-v22/`; `database-mail-reason.test.ts` checks it and the step over v21.
- Step 23 and file schema v23 (BTN-553): a feed keeps its own chain rules (`chain` in its entry of the `projects.feeds` JSON) and the project's no longer reach its tasks. So that a feed takes the same tasks as before, the step copies a project's own rule rows of `setting_values` (the four chain rules and the two milestone rules) into each of its feeds that has no `chain` yet; the file migration (`feedsRuled`) does the same with `projects[].chain` on import. The frozen samples are `test/fixtures/database-v23/` and `test/fixtures/schema-v23/`; `database-feed-rules.test.ts` checks the step.
- Step 24 and file schema v24 (BTN-554): `tracker_profiles.moves`, the profile's status moves as JSON (`{}` on every row before it — nothing moves). A project's own are the `statusMoves` row of `setting_values`, a feed's `moves` in its entry of the `projects.feeds` JSON; both optional, so the file migration only restamps the version. The frozen samples are `test/fixtures/database-v24/` and `test/fixtures/schema-v24/`; `database-profile-moves.test.ts` checks the step and the round trip.

- Step 18 (BTN-577) reserves the new `LimitHold.overage` JSON in `chains`: the retained session snapshot and successful-stop marker let a paid subscription usage stop survive a restart. Tables are unchanged; the version prevents older code from dropping the wait and relaunching. The frozen v18 sample includes an unknown-reset paid hold; `database-overage.test.ts` checks its schema, full read and save/load roundtrip, and preservation of v17 state.

- File schema v19 (BTN-394) adds nullable `autoCompactWindow` at the shared and project levels and optional launch `settings` to SDK session records. Migration only restamps older files, preserving account-window inheritance. The settings definition is mirrored from the registry at startup; existing settings rows and SDK files need no database step.

- Step 17 (BTN-543) adds `global_accounts` (`account` primary key), the explicit registrations of the global Claude and Codex folders. `openAccountHomes` reads and writes it. The migration sets `accounts.adoptLegacy` in `service_state` only for an existing database; the runner exposes the version from before the entire migration as transaction-local `even_keel.migration_from`, so a fresh database passing through all steps stays fresh. Importing old state files, or finding an old account ledger without chain history, sets the same marker; SQLite already passes through the upgrade path. At the first account initialization the marker is consumed in the transaction that registers the global folders present then. Backups carry registrations; config export does not.
- Versions 1 and 2 were the SQLite file (`PRAGMA user_version`); the numbering goes on in PGlite from 3. The version is the one row of `schema_version`. `STEPS[n]` takes the database from version `2 + n` to the next one in one transaction together with the new version, so a step that fails leaves the old version and none of its tables. Step 3 is the tables of the SQLite versions in Postgres; step 4 (BTN-199) adds `projects`, `setting_definitions`, `setting_values` and `service_state` and moves the rows of `chain_flags` into setting rows (with their two definitions, only when it had rows) before dropping it; step 5 (BTN-200) adds `tracker_profiles` and `projects.profile_id`; step 6 (BTN-209) adds `changelog_versions`; step 7 adds `changelog_versions.spend`; step 8 (BTN-205) lets `chain_lists` hold the list `reviews` (the pull requests of PR mode, `docs/chain.md`); step 9 (BTN-207) adds the `color` definition and writes each project at a position under 8 the color of its position (`position + 1`), so nothing is repainted (`docs/settings.md`); step 10 (BTN-245) lets `chain_lists` hold the list `shelved` (tasks that left the chain for an inactive status after their session's turn, `docs/chain.md`); step 11 (BTN-271) drops the uniqueness of `projects.key`; step 12 (BTN-66) adds `tracker_profiles.rules`, `projects.feeds`, `feed_profiles` and the profile and status of `closed_tasks`; step 13 (BTN-345) makes the tracker a project's own: each project without a `tracker` row gets the shared row's value, or `huly` without one, and the shared row goes (the SQLite and v0.1 imports pass through it; an imported config file gets the same from schema v13, `trackersOwned`); step 14 (BTN-418) adds `key_organizations`; step 15 (BTN-475) adds `tracker_profiles.mcp_oauth`; `DATABASE_VERSION` is `2 + STEPS.length`.
- A database newer than the code is refused before anything is written: `storage.newerDatabase`, the blocked page (`src/main.ts`). So is a SQLite file of a version above 2.
- A step is never edited or removed once merged. A schema change is a new step and a new frozen sample `test/fixtures/database-v<N>/even-keel.sql` (the SQL of the tables and rows of that version). Four test files run in parallel: `src/storage/database-schema.test.ts` compares every schema with its frozen sample (columns, indexes, constraints); `database-settings.test.ts` and `database.test.ts` migrate and read every PGlite sample whole (the settings and profiles also through a backup); `database-sqlite.test.ts` imports the SQLite samples `database-v1/`, `database-v2/` whole. They share readers in `database.fixture.ts`; merged steps and samples stay unchanged. The state-file import and the owner's locking, readers and backup tests also run in separate files (`state-files.test.ts`, `state-owner.test.ts`), all on disk.
- Step 16 (BTN-461) changes each stored `modelPrompts` model key into `* | <model>`, preserving JSON entry order and the setting's writer metadata. The config's schema v17 makes the same conversion on file import.
- File schema v18 (BTN-547) adds optional `reason` (`postpone` or `skip`) and `blockers` to the JSON entries of `shelved`, and handover causes `unblocked` and `unskipped`. Older entries without a reason keep the inactive-status behaviour. The file migration only restamps; the existing `chain_lists` JSON and `handoffs.reason` text columns need no database step.

- The database's version is separate from `SCHEMA_VERSION` of the files (`src/storage/schema.ts`), which still versions the config's format (the imported file, `config-export`/`config-import`) and the files that stay.

## Settings at the first start (`src/settings/import.ts`)

After `prepareDatabase`, `src/main.ts` runs `prepareSettings`: it mirrors the definitions and, the first time (no `config.imported` in `service_state`), imports the config file (`EVEN_KEEL_CONFIG`, `even-keel.config.json` of the root by default) whole in one transaction: brought to the current schema (`currentConfig`), entries without an id given one, checked as the service would run it, `updates.dismissed` taken out into `service_state`. The switches step 4 moved from `chain_flags` stay unless the file sets them. The file is renamed to `even-keel.config.json.imported`; the log line counts projects and settings. A file that does not parse stops the start with its notice (the blocked page) and stays as it is; no file — an empty start, marked imported too.

Later starts never read the file: one found there is logged as not read. `upgradeStorage` still runs first, so a pre-v9 config file of an old install is migrated together with the state files before the import.

## Import at the first start (`src/storage/state-files.ts`)

`src/main.ts` runs `upgradeStorage` (the files to their current schema, `docs/chain.md`) and then `prepareDatabase`:

- With a database: it is opened as its owner and brought to the current step. A v0.1 state file (`chain.json`, `questions.json`, `launches.jsonl`, `handoffs/`) or `even-keel.db` still next to it is not read; the log says so once per start.
- Without one, but with the SQLite file `even-keel.db` (versions 1–2): its rows are read whole (`sqliteRows`; the journal is switched to `DELETE` first, so a WAL the old service left folds into the file), written into a new database `state/even-keel.import/` in one transaction (`insertRows`, which also moves the id counters past the rows), and that folder is renamed to `state/even-keel` only once complete. The file is renamed to `even-keel.db.imported`; the log line counts the rows per table.
- Without either: the v0.1 files are read and checked whole (`readStateFiles`; a damaged or newer file is `storage.damaged` / `storage.newer` and nothing is written) and imported the same way; then each file or folder is renamed to `<name>.imported`. A handoff snapshot that does not parse is left out and logged.
- A failed import removes `even-keel.import` and leaves everything as it was (`storage.importFailed`). Nothing at all: an empty database.

Tested on every frozen sample `test/fixtures/schema-v2` … `v9` and `database-v1`, `v2` (`src/storage/state-files.test.ts`, `database.test.ts`). The SQLite import was run on a copy of the live state on 2026-10-18 (889 launches, 93 snapshots, 10 closed tasks: every table came over with the same row count, in about 2.5 s).

## Backup, export, rollback

- `npm run storage -- backup <dir>` — a copy into a new folder laid out like `state/even-keel` (`<dir>/pgdata`), also while the service runs: all tables read in one statement (`rowsOf`), so the copy is consistent, then written into a fresh database (`backupDatabase` in `src/storage/copy.ts`). To restore, stop the service and put the folder in place of `state/even-keel`. It holds the settings and projects too, and the trackers' profiles with their secrets in the clear: keep a backup as private as `.env`. With `.env` it is everything a move to another machine needs.
- `npm run storage -- export <dir>` — the state as the v0.1 files, into an empty folder. A v0.1 Even Keel reads them, and so does the import: to roll back, stop the service, export, put the files into `state/` of the old version, and the settings as its `even-keel.config.json` (`config-export`).
- `npm run storage -- config-export <file>` — the settings and projects as a file of the config's format, into a new file (`exportConfig`). No profile and no secret goes into it; `config-import` leaves the profiles and `projects.profile_id` as they are.
- `npm run storage -- config-import <file>` — such a file (of any schema version) in place of the settings and projects, whole: a key it lacks goes back to its default, a project it lacks goes with its setting rows (`importConfig`, writer `hand`). The file is read and checked before anything is written. Through the port of a running service; the service picks it up at its next look (`ConfigStore`, every 2 s). It is the way to edit the settings by hand: export, edit, import.
- Both read the database of `EVEN_KEEL_STATE_DIR` (the checkout's `state/` by default; `.env` is loaded) through `readStateDatabase`. `closed_tasks` has no file: only the backup keeps it.

## Readers outside the service

`readStateDatabase` (`src/storage/owner.ts`) neither migrates nor reads a database of another version (`checkVersion`). With a live owner it connects to its port; a live owner always means "connect", even with the reader's own pid, because Tally's collector runs in a worker thread of the service. With no owner it opens the folder itself and, while open, owns it the same way: `owner.json` and a port, so a second reader connects to it. A claim without a port is waited for, up to 30 seconds, and then connected to: a reader started together with the service reads through it instead of failing.

Tally's collector (`evenKeelState` in `tally/src/collect.ts`) reads the launch log, the snapshots and the projects' folders and branches (`select repo, branch from projects`) this way; the config file only when there is no database yet. Without a database it reads the SQLite file (`sqliteInMemory`: its rows in a database in memory) or else the v0.1 files: a merge reaches the collector before the restarted service has imported them.
