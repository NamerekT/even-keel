# Sessions: the checkpoint threshold

## Checkpoint threshold (BTN-86)

The `agent-bridge` plugin's hook (`plugins/agent-bridge/hooks/context-checkpoint.mjs`, the rules in `nudges.mjs`) asks a session for a handoff by context size. The first nudge is at 200k, the next every 50k up to 250k and every 25k past it. The hook reads no transcript, so it works the same for Claude Code and Codex, and for OpenCode through the package's OpenCode plugin ([`opencode.md`](opencode.md), "The `agent-bridge` plugin"): on every tool call it asks the service about its session, `GET /api/sessions/<id>/checkpoint` → `{ project, task, handoffs, first, source, context, note }`, 404 for a session the chain did not start. `context` is the session's context fill as the service's monitor last read it from the transcript (`SessionMonitor.contextOf`), `null` while it has not; with no answer, a 404 or a `null` the hook is silent, so a session started by hand gets no nudges. The `CHECKPOINT_*` variables still override the steps. Environment variables are not used to pass the answer: the environment of a `claude --bg` does not reach its session while the daemon runs (`docs/accounts.md`).

The plugin is built in and follows Even Keel's version by itself (`docs/packages/files.md`), so a session never runs a plugin older than its service.

### The note and the mark

`note` (BTN-964) is the task's handoff note relative to the working folder, `noteFileOf` in `src/sessions/note.ts`: `.temp/handoff.md` in a git project, where each task has its own worktree, and `.temp/handoff-<task>.md` in a project without git, where every task shares the project's folder and one note would overwrite another's (characters of the task outside `[A-Za-z0-9._-]` become `-`). The nudge, the `Stop` hook's request, the handoff prompt (`handoff(extra, note)` in `src/chain/prompts.ts`), the chat's `/handoff` and the mail's checkpoint request all name that file.

The plugin's `Stop` hook (`checkpoint-mark.mjs`) sends back a turn that wrote the note among its last three tool calls but ended without the `CHECKPOINT:` line.

- Whether it did comes from `GET /api/sessions/<id>/note` → `{ note: false }` or `{ note: true, path }` (`noteWritten` in `src/sessions/note.ts` over the agent's whole `feed`; either name counts, and `path` is the one written, so the mark names it).
- The turn starts at its prompt: a chat message the running turn took in (through the inbox socket's `queued_command`, a mailbox hook or a refused `AskUserQuestion`) is a feed line marked `midTurn` and does not cut the note off, so a turn that wrote the note, then replied to such a message without the mark, is still sent back (BTN-1718).
- It recognizes file tools (`Write`, `Edit`, `MultiEdit`) and literal shell write targets: .NET `WriteAllText`/`WriteAllLines`/`AppendAllText`, `Set-Content`/`Add-Content`/`Out-File` with the path first or immediately after a path parameter, and `>`/`>>`. Reads and quoted text mentioning the note do not count. A path built in a variable or a write hidden in another script is not inferred; the session must end with the mark itself.

### The thresholds

- **The shares** (BTN-261): `first`, `late` and `hard` are shares of the session's context window, whole percents, `first < late < hard`, 72, 85 and 95 unless set (`stats.checkpointShares`, for Even Keel and per project, `docs/settings.md`; `DEFAULT_SHARES` in `src/stats/checkpoint.ts`). They apply only once the agent reports the session's window. The handler of `/checkpoint` reads the project's current values on every request, so a change applies to the next tool call of a running session.
- **`first`** with `source: "calibrated"` or `"config"` replaces the hook's own first threshold; `"default"` leaves it alone. A default or calibrated threshold over the first share comes down to it, rounded down to 1k, with `source: "window"`, which the hook takes like `"calibrated"`: past it the agent's own compaction may come first. A threshold pinned by `stats.checkpointTokens` (`"config"`) stays as it is, past the window too, and the shares do not apply (`withinWindow`).
- **`late` and `hard`** (BTN-259) are the late and hard shares, rounded down to 1k; the hook takes the lower of each and its own (the default 250k and 300k or `CHECKPOINT_LATE_TOKENS`/`CHECKPOINT_HARD_TOKENS`), so a small window brings the late nudges and the hold of a task with many handoffs inside it and a large one changes nothing. A share therefore only lowers a step of the hook. Without a window, or with a pinned `first`, both are `null` and the hook keeps its own — a pin of 999999 still silences the nudges below it, though `contextHandoffs` is the switch for that.
- **Before the compaction.** Where the session's compaction point is known, every share is also kept before it: Claude compacts about 32k short of its window (`CLAUDE_COMPACTION_GAP`), and a Codex or OpenCode session with an auto-compaction window compacts at its `compactAt` (`models.md`, "The auto-compaction window"). `first` and `late` stay at most 30k before that point and `hard` 15k (`BEFORE_COMPACTION`): room for a large tool result and the note. So a share above that point no longer lifts them (BTN-506). Other agents, and a session the service does not see, keep the shares alone. A Claude session's answer, before the hook takes the lower of it and its own:

  | Window | `first` at most | `late` | `hard` |
  | --- | --- | --- | --- |
  | 250k | 180k (the share) | 188k (point − 30k) | 203k (point − 15k) |
  | 200k | 138k (point − 30k) | 138k (point − 30k) | 153k (point − 15k) |
  | 400k | 288k (the share) | 338k (point − 30k) | 353k (point − 15k) |

  On a 250k window the nudges come at 180k, 188k and 213k and a held task is asked from 203k; on a 200k one `first` and `late` meet, so the nudges come every 25k from 138k.
- **Why the cap** (BTN-377): Claude Code compacts not at a share of the window but about 32k short of it — measured on 2026-10-24 with the nudges off, 56 auto-compactions in 37 chain sessions on a 250k window came at 216–227k (median 218k), hand sessions on a 400k window at a median 369k. With the shares alone the late share came ~5k before the compaction on 250k and the hard one never, and on 200k the compaction came before the late share. Codex's own point without a window set is not measured (`docs/unverified.md`).
- **`handoffs`** (`handoffsOf` in `src/chain/launches.ts`) is the number of the task's sessions started by `checkpoint`, `restart` or `relay`, up to and including this one. From the third on the hook is silent below the hard threshold of 300k: on tasks with many handoffs most of them lost money (on another project: 12 handoffs, $17.5 spent, $5.3 saved).
- **`source: "off"`** (BTN-255) — the project's `contextHandoffs` is off, its own or the shared one (`docs/settings.md`): the hook marks no context at any size, the hard threshold of a held task included, and the agent's own compaction keeps the context. The rest of the plugin stays on — the mark of a note the session wrote by itself, the chat's mail, the standards, the check before the merge — and so do the handoffs on a limit, "New session" and the answers: the note stays the way of every move between sessions. The other fields are filled as usual, so the page still sees the threshold.
- **The task labels** `Break | compaction` and `Break | handoff` are a task-label setting (`LABEL_PARSERS.checkpoint` in `src/settings/registry.ts`, `docs/settings.md`), read on every request from the latest task list — unlike run labels, which are no longer read (`models.md`). `Break | compaction` pins `first` to 999999, so the shares and the late and hard caps do not apply; `Break | handoff` or no label uses the project's threshold, and so do conflicting labels. `/stats` still shows the project threshold.

### Calibration

- `first = base + (note + recovery) / (cache read price × 40 requests)`, rounded to 1k and kept within 150–250k (`src/stats/checkpoint.ts`, the query `CHECKPOINT` in `src/stats/reader.ts`).
  - `base` is the median context of the project's checkpoint successors at their 15th main-thread request;
  - `note` the median spend of a session from its first note to its end — a write of `.temp/handoff….md` or a call of the tasks server's `handoff_write` (below);
  - `recovery` the median spend of a successor before its first edit;
  - the price is that of the successors' most frequent model in Tally's `model_prices`;
  - the work left, 40 requests, is a constant, about the lower quartile of what was measured: a measured remainder depends on the threshold itself (a higher one shortens it and pulls the threshold up, the successors' recovery requests inflate it and pull down).
- The hard threshold and the limit of handoffs are not calibrated.
- It applies once the project has 20 checkpoint successors and 50 sessions that went over 150k; until then, and without statistics, the threshold is 200k. `stats.checkpointTokens` in the config pins it for all projects and switches the calibration off.
- The calibration comes from Tally, cached for a minute (`StatsReader.checkpoint`). A read slower than `CHECKPOINT_WAIT_MS` (300 ms) is not waited for: the answer takes the last measures read, none before the first, and the read goes on into the cache — a wait past the hook's 2 s, or the link's 1.8 s for a machine elsewhere, would drop the answer (BTN-1634).
- Measured on 2026-10-10: one project — base 73k, note $0.18, recovery $0.64, 168 successors → 176k; BTN — 79k, $0.18, $0.69, 32 successors → 187k. Why 150k was too early: with a 1 h cache write at $8/M against a read at $0.2/M, rebuilding the context costs as much as re-reading it 40 times, and of 163 handoffs at 150k on that project 93 lost money ($177 spent, $132 saved).

## The note kept with Even Keel (BTN-1046)

A session whose project's set brings the tasks server writes no note file: it calls the server's `handoff_write(text)` and ends its turn with a bare `CHECKPOINT:` line. The tool has no task or session parameter; it is listed only on a server address with `?task=` (`toolSpecs`, `src/taskmcp/tools.ts`).

- **Who wrote it.** The machine's tasks server (`MachineTasks`, `src/taskmcp/machine.ts`) stamps the writer into the call's `_meta` (`even-keel/session`, `writer: { session, branch, at }`): the task's live session on that machine at the time of the call, the working one first, else the newest one not finished (`writerOf`, `src/service/hub-mcp.ts`). The hub's link adds the machine as the header `x-even-keel-machine`, which only the hub's own gateway reads. A call without a writer is refused with a text, nothing kept.
- **Kept only from the current session.** The hub (`writeHandoffNote`, `src/chain/handoff-notes.ts`) compares the writer with the newest row of `launches` for the task: another session gets "no longer the current session … not kept", a task never launched another refusal. So a late write of a session already handed over — one kept in the machine's outbox while the hub was away (`docs/machines.md`, "The hub away") — never replaces the note of the session after it. The text is cut at 512 KiB. Rows go to the table `handoff_notes` (`docs/storage.md`), several per task: a later call is a newer row.
- **Into the prompt.** A move that may hand the task over carries the task's newest note in its context (`MoveContext.note`, `RemoteDeps.note` → `lastHandoffNote`). `Handovers.handOver` puts its text whole into the new session's prompt (`PromptTexts.noteText`, `handoffPrompt(…, kept)`) only when the session handed over wrote it (`noteFrom`), so a note of an earlier session never comes back. After a checkpoint the note stands alone; on a limit, "New session" or a crash the last steps and the last message follow it, as without a note.
- **The checkpoint answer.** `note` in `GET /api/sessions/<id>/checkpoint` is `handoff_write` instead of a path for such a project (`handoffNoteOf`), and so is the `/handoff` command's request; `noteWritten` counts a call of the tool under any agent name of it (`mcp__…__handoff_write`, `tasks_handoff_write`, `tasks.handoff_write`), and the `Stop` hook then asks for the bare line.
- **A note file still works.** A session that writes a file and ends with `CHECKPOINT: <path>` (an agent without the server) is handed over as before; the machine reads the file for the snapshot, and the hub keeps that text as the session's note too (`fileNote` in the snapshot's save, `src/service/machine-link.ts`), so it is not lost with the worktree.
- `checkpointOf` (`src/sessions/transcript.ts`) gives `''` for the bare line, `null` for none; `noteOf` points at no file for `''`.
- Tally's calibration above (BTN-1240) starts `note` at the first call of the tool too, under any of its agent names as `noteWritten` counts them (a regular expression over `tool_calls.name` in `CHECKPOINT`); the call is no edit for `recovery`.
