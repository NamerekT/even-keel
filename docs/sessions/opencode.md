# Sessions: OpenCode

## OpenCode (BTN-214, `src/opencode/`)

First checked on OpenCode 1.18.25 on Windows with the free model `opencode/big-pickle`, from a script driving the adapter; since then it runs chain sessions under the service, on 1.19.5 too ([verified](../verified/opencode.md)). The research behind the adapter (BTN-212, OpenCode 1.18.25, 2026-10-19) is in the same journal; what of it is not the adapter's behaviour is at the end of this file.

The binary: `EVEN_KEEL_OPENCODE_BIN`, otherwise Even Keel's own copy of the checked version while `cli.opencode` is `checked` and the copy is downloaded (`cli-versions.md`, "The checked CLI"), otherwise on Windows the native binary of the global npm package `opencode-ai` (its `opencode` on the PATH is an npm wrapper), otherwise `opencode`; self-update is off on any of them. The package's `bin/opencode.exe` is a placeholder until its postinstall puts the build for the CPU there, which a newer npm skips unless allowed: `resolveOpenCodeBinary` takes that `bin` once it is real, else the platform package's (`opencode-windows-<arch>`: plain, `-baseline`, `-musl`, in that order; `npmCliBinary`, `agents.md`).

### Turns

- **A turn** is `opencode run --format json [-m <provider>/<model>] (--title <task> | -s <session>)`, a detached process with its JSON events in a file, as Codex's (`TurnRegistry` of `src/codex/turns.ts`, kept in `state/opencode/`). Liveness, `resting` and `stop` are Codex's (`codex.md`).
- **The prompt** is no argument: Even Keel writes it, UTF-8, to the turn's stdin and closes it, and `run` with no message takes stdin as the message, unchanged (BTN-1337, OpenCode 1.19.5). So a task description past Windows' 32,767-character command line fits, and a reply's leading `- "question" → answer`, which `run` would read as an option, never reaches argv.
- **The session id.** Every event carries `sessionID`; a turn that sends none yet is found in the account's database by its title, folder and start. A new turn waits 120 s for its first event. A resume (`-s`) waits for none (BTN-1678): once its process outlives 5 s (`RESUME_GRACE_MS`) it is the session's turn, since OpenCode 1.19.6 retries a Zen limit that is still on without writing a line, and the silence goes to the log check and the hang rule below; only an exit before that fails the resume. A turn that fails with nothing in its file says in the notice's `detail` whether the process exited or lived on silent (`silentTurnDetail`).
- **The end.** The turn is over when its last event is an `error` or a `step_finish` whose `reason` is not `tool-calls`.
- **OpenCode takes its working folder from `PWD`** before the process's own: a spawn with `cwd` alone ran in the service's folder. Every turn sets `PWD`.
- There is no question tool in `run`, even with `OPENCODE_ENABLE_QUESTION_TOOL`: a question is the text a turn ends with, answered from the chat window, as with Codex.

### The account and the config

- **The account is four XDG folders** (`openCodeEnv`): `XDG_DATA_HOME` (`auth.json`, the transcripts in `opencode/opencode.db`), `XDG_CONFIG_HOME` (config, JS plugins in `opencode/plugins/`), `XDG_STATE_HOME`, `XDG_CACHE_HOME`; with them `OPENCODE_DISABLE_AUTOUPDATE`, `OPENCODE_DISABLE_EXTERNAL_SKILLS` and `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS` (no `~/.claude/skills`, `~/.agents/skills`, which the XDG folders do not hide). Not `OPENCODE_DISABLE_CLAUDE_CODE`: it drops the project's `CLAUDE.md` too. The global instructions are the account's empty `config/opencode/AGENTS.md`, which OpenCode takes before `~/.claude/CLAUDE.md`; the project's `AGENTS.md`, else `CLAUDE.md`, still reaches the session. One account folder may hold several providers at once.
- **The session's config** on top of the account's and the project's is `OPENCODE_CONFIG_CONTENT` (`sessionConfig`):
  - `permission.external_directory: allow`: a merge into the main checkout from a worktree is outside the folder;
  - `experimental.continue_loop_on_deny: true` (the next bullet);
  - the gateway's MCP servers, with the project's own `opencode.json(c)` servers turned off by name (`{"enabled": false}`). `OPENCODE_DISABLE_PROJECT_CONFIG` is no way out: it drops the project's `AGENTS.md`/`CLAUDE.md` too;
  - as `skills.paths` the plugin packages' `skills/` (`docs/packages.md`) and the project's own `.claude/skills` and `.agents/skills`, which the skill flags above drop too (`skillDirs`, `protection.md`, "Project rules for every agent").
- **Permissions.** Tools are allowed by default; an `ask` is rejected on its own in `run`, so a session does not hang on it. The default `read` rules ask for `*.env` and `*.env.*` (`*.env.example` is allowed). A rejected `ask` (`PermissionRejectedError`) ends the turn at once unless `experimental.continue_loop_on_deny` is `true`: the model is never asked again, and a chain session would stand waiting with no question (EKR-119). Every config of Even Keel's turns sets it (`CONTINUE_ON_DENY`), so the model gets the rejection as the tool's error and goes on. A `deny` rule (`PermissionDeniedError`, Protection's) never ends the turn: the model gets "The user has specified a rule which prevents you…" and goes on, with the flag or without it (OpenCode 1.19.5, `SessionProcessor.failToolCall`). No `--auto` (it approves every `ask`), and there is no `execution.opencode`, since OpenCode has no OS sandbox to bypass.
- **Sign-in** is `opencode providers login -p <provider> -m "<method>"`, which works through a pipe: `-p openai -m "ChatGPT Pro/Plus (headless)"` prints a device link and code, as Codex does; Anthropic takes only a key; Copilot is a GitHub device sign-in; GitLab — OAuth or a token; the free models need none (`docs/accounts.md`).

### The transcript, the models and the limits

- **The transcript** is rows of `data/opencode/opencode.db` (`src/opencode/db.ts`: read-only, opened and closed per read, a tool's output left out), tables `session`, `message` and `part`. `foldSession` gives the same `TranscriptSummary` as the other folds: the feed, the stage, the model as `<provider>/<model>`, the context (the last step's input with the cache) and the totals, an API error from the message's `error`. A tail reads again only when the session's newest `time_updated` moved or a turn ended on another error. A handoff has no transcript path to point at (`tail.path` is `undefined`).
- **Errors with no row.** An error a turn ended on leaves no row (a model the account does not have: `UnknownError`, "Unexpected server error", seen on 1.18.25 with `-m deepseek-v4.1`), so the fold also takes the `error` event that ends a turn's output — the last line of each of the session's turn files, `<task>-<ms>.jsonl` since its start (`turnError`, `OpenCodeCli.turnErrors`, BTN-336) — as an error line and the API error in its place by time, unless a step holds the same text.
- **Anthropic spending caps** (`isSpendingLimit`, BTN-586) are `apiError.kind: spend`, checked in both the displayed message and the full error JSON before limits or transient errors. An API account holds the task on this refusal, reads its explicit UTC reset through `spendingReset`, and keeps five-minute key checks active through `limitRecovery`, as Claude does. Recovery through a real cap remains [unverified](../unverified/sessions.md#api-spending-cap-recovery).
- **Tool-result pictures** (BTN-481) are `file` attachments in `state.attachments`, with an image `mime` and a base64 data URL (`read`, OpenCode 1.18.25, checked against a saved real session). `sessionRows` projects only their count into `PartRow.images`; the whole fold emits an `image` line under the call's `callID`, with the file path for `read`. `Agent.image` reads the selected attachment through `sessionImage`, scoped to the session and call, even after the source file is gone. Neither the feed nor a normal database read returns the picture data.
- **The models** are `opencode models` in the account's folders (`parseModels`): one `<provider>/<model>` a line, only those of the providers the account is signed in to (`opencode/big-pickle`, `opencode/deepseek-v4.1-flash-free` on a fresh account), ~2 s. `run -m` takes nothing else. For an OpenAI OAuth sign-in the OpenAI part is intersected with the subscription's visible models (`models.md`); the other providers stay unchanged.
- **The context window** comes from OpenCode's copy of the models.dev catalogue, `<account>/cache/opencode/models.json` (`windowOf`).
- **The auto-compaction window** (`openCodeAutoCompactWindow`, BTN-856, `src/opencode/window.ts`). OpenCode 1.19.5 compacts (`SessionCompaction.isOverflow`) once the last step's tokens reach `usable`: `limit.input − (compaction.reserved ?? min(20000, maxOutput))` for a model with an input limit, else `limit.context − min(limit.output, 32000)`. A config overrides a model's limit by field (`provider.<id>.models.<model>.limit` over the catalogue), but its schema wants both `context` and `output` in `limit`, and many catalogue models have `limit.input`, so `context` alone does nothing. With a window `W` below the chosen model's `limit.context`, `windowConfig` adds `provider.<p>.models.<m>.limit = { context: W, input: W, output: <the catalogue's output> }` and `compaction.reserved = 32000` to `OPENCODE_CONFIG_CONTENT`: the session compacts at `W − 32000`, where Claude's and Codex's do (`compactionLimit`). `W` is the record's `contextWindow`; `resume` takes it and the model (`start.model`, else the transcript's) from there. `opencode models opencode --verbose` with such a config showed `big-pickle` at `150000/150000/32000` in place of `200000/160000/32000`; a compaction at that point in a live session is [unverified](../unverified/opencode.md#the-opencode-auto-compaction-window-btn-856).
- **Limits** only from the provider (BTN-341): OpenCode shows none, so a ChatGPT sign-in has its 5-hour and weekly windows and a Copilot one its month read from their APIs (`limits.md`, "ChatGPT (Codex and OpenCode)" and "Other agents' limits"); OpenCode Zen and API keys have none. A turn's error is a limit by its text (`LIMIT_TEXT` in `src/opencode/transcript.ts`), a 429 `statusCode` or a `FreeUsageLimitError` anywhere in the answer, Zen's spent free allowance (BTN-342); on Zen the chain tries such a limit again with a growing wait (`docs/chain/exceptions.md`, exception 1), never seen live (`docs/unverified.md`). Credit exhaustion takes precedence over limits and transient errors: `CREDIT_TEXT` checks both the displayed message and the full error JSON, including `responseBody`, for quota and balance codes or "no credits remaining".

### A silent turn

The thresholds are the common rule (`agents.md`, "A silent turn"); what OpenCode adds:

- **Activity** is the session's rows in `opencode.db` and the turn's output file. A failed read of the database does not count as silence. A killed turn leaves its tool part `running` and its message without `time.completed` for good; that does not matter: liveness is the process and the output's last event, not the rows.
- **A hung turn** (BTN-273, `hungEntry`) keeps its `pid`, and `resume` and `stop` both kill a live turn first, so two processes never write one session.
- **The account log** (`LOG_SILENCE_MS`, BTN-497). After 30 seconds without a changed session row or turn event, the adapter checks `<account>/data/opencode/log/opencode.log`: some stream failures, "Free usage limit reached" among them, reach neither the JSON events nor SQLite and leave `opencode run` alive.
  - `OpenCodeLog` reads appended bytes in 64 KiB chunks from a per-account cursor, holding incomplete lines until their newline. Only `ERROR` entries with `message="stream error"`, the exact `session.id`, and a timestamp newer than both the last activity and the current turn's start qualify. Before recording a failure, the adapter rechecks activity and process ownership.
  - The failure becomes an `even_keel_stream_error` diagnostic in the service-owned turn output, so it survives a service restart and reaches `turnErrors` and the fold. It makes the session idle while keeping its live pid; unlike OpenCode's `error` event it does not mean the process exited, so stop and resume still end the owned turn.
  - Limits and spent credit use the usual classification; a free allowance with no known reset uses the 15-minute retry, doubling up to four hours. Other stream errors show the translated `opencode.streamError` notice with the reply/new-session actions, without the raw log line. With no matching error the 30-minute hang rule is unchanged. A real provider refusal remains [unverified](../unverified/opencode.md#opencode-stream-errors-in-the-account-log-btn-497).

### The `agent-bridge` plugin (BTN-274)

The checkpoint threshold, the chat mailbox and the merge check come from the `agent-bridge` package's OpenCode plugin, `plugins/agent-bridge/opencode/agent-bridge.mjs`: `pluginFiles` puts every script of a plugin package's `opencode/` folder into the session config's `plugin` as a file URL, which OpenCode loads into its process. Hooks there are JS plugins, not Claude's `hooks.json`: `tool.execute.before` (throwing blocks the call), `tool.execute.after` (may extend the output), `event`.

- **The threshold and the standards.** On `tool.execute.after` the plugin asks the service what the hook commands ask (`hooks/evenkeel.mjs`; `checkpoint.md`, "Checkpoint threshold"; `protection.md`, "Project standards") and appends the nudge to the tool's `output` in a `<system-reminder>` block. A `client.session.prompt` with `noReply` from inside the hook hung the turn (1.18.25).
- **Chat mail** (BTN-1323, `agent-bridge` 1.5.0). A note appended to a tool's output was taken by the model for an injection and ignored, so a chat message goes as the user's own line:
  - `mailPost` (`hooks/mailpost.mjs`, outside `opencode/` since OpenCode loads every script there as a plugin) posts it by `client.session.promptAsync`, a text part with `metadata.evenKeel.mail`, after each tool call and every 2 s while the session's `session.status` is busy; one poll per session, its requests one at a time, stopped on idle.
  - The running `opencode run` takes the line on its next step, a text step included: its loop goes on while the last user row is newer than the last answer (seen live on 1.19.5; an awaited post from `tool.execute.after` does not hang).
  - A labelled line with no answer after it is the fold's `unansweredMail`: the turn ended before the model took it, and `settleMail` resumes the session with the same text. How the feed shows the line is in `chat.md`, "Chat mailbox".
  - A subagent's calls carry its own session id, which the service does not know. Not ported: mail at a stop or before a question.
- **The merge check** (BTN-288) is `tool.execute.before` of `bash`: `mergeRefusal` (`hooks/merges.mjs`, shared with `merge-check.mjs`) in the plugin's `directory`, the commands run asynchronously, and the refusal thrown as an `Error`, which OpenCode turns into the call's error without running it (seen live on 1.18.25).
- **The `CHECKPOINT:` line.** The `Stop` guard cannot block: `run` ends on the session's first `session.status` idle. Instead `experimental.text.complete`, which may rewrite a text part before it is stored, adds `CHECKPOINT: .temp/handoff.md` to a text without that line when the plugin saw a `write`/`edit` of the note among the last three tool calls and `/note` says yes (seen live: the line is in the run's events and in `opencode.db`).

### One-off writing

`Agent.write` (the changelog): `opencode run --pure` with the prompt on stdin and a config that denies every tool but Read, Grep and Glob and turns the project's own MCP servers off (`writeArgs`, `writeConfig`); the answer is the last step's text, the tokens and the cost those of every step (`parseWriteAnswer`). The session it leaves is deleted afterwards (`opencode session delete`), so the account's database holds no transcript of it.

### OpenCode on Copilot is blocked (BTN-573)

Until a separate live check enables it. Copilot Free's automatic model selection does not match OpenCode's named-model calls, which failed on the checked CLI.

- `ModelCatalog.refusal` rejects `github-copilot/*` before consulting the catalogue, including a task's run; its offered lists omit those models. `OpenCodeCli` also checks the actual credentials before launch, resume and one-turn writing. A resume with no selected model checks the saved session's model before stopping its old turn.
- Copilot-only folders are blocked by `launchBlock` and `switchProblem`; mixed folders keep their other providers. Every generated turn config contains `disabled_providers: ['github-copilot']` to prevent an implicit default from selecting it.
- The chain pauses with `chain.opencodeCopilot`, linked to session settings: choose another Model or Account and update a Copilot run label before resuming. Status and allowance reads remain enabled.

### Left from the research (BTN-212)

What the research found that the adapter does not use:

- `opencode serve` has an HTTP API (`prompt_async`, `abort`, `session/status`, questions, permissions), but is a server of its own to keep alive; the adapter runs `opencode run` per turn.
- `opencode export <id>` gives a session as JSON in ~1.2 s; the adapter reads the database instead. `opencode models <provider> --verbose` lists the windows (`limit.context`).
- The `event` hook's `message.updated` carries the tokens.
