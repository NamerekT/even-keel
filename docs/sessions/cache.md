# Sessions: the prompt cache and keep-warm

## Prompt cache lifetime (BTN-99)

What the CLI 2.1.302 binary does, in order of precedence: the `FORCE_PROMPT_CACHING_5M` variable → 5 minutes; the variables `CLAUDE_CODE_PROMPT_CACHE_TTL` / `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`; the settings `promptCacheTtl` / `subagentPromptCacheTtl` (`"5m"` | `"1h"`), whatever the sign-in; the `ENABLE_PROMPT_CACHING_1H` variable → 1 hour. Without any of them: 1 hour on a subscription within its limits (5 minutes in overage), 5 minutes on an API key, Bedrock or Vertex. A 1-hour cache write is billed higher than a 5-minute one.

The `cacheTtl` key (`"5m"` | `"1h"`, `null` — the CLI decides; `/settings`, the Claude Code group, and a project's own value in its panel, BTN-187) goes into the chain sessions' `--settings` as `promptCacheTtl` (`chainSettings` in `src/tools/panel.ts`), on every launch. It is live: the next launch takes the new value. It matters mostly on a key, where a chain waiting for a reply longer than 5 minutes otherwise writes the whole context again. Seen live on a key with `1h` (CLI 2.1.310, Haiku, a `--bg` and an SDK chain session, 2026-10-25): every cache write of both was `ephemeral_1h_input_tokens`, none 5-minute.

The default is `"5m"` with `keepWarm` 2 (BTN-1401; before, `null` and 0). Measured on Tally from 2026-11-17 15:25 UTC to 2026-11-20 on the project even-keel, already on `5m` with `keepWarm` 2: 10.3k main-thread answers cost $432 at API prices, the same on an hour-long cache ~$490 (−12%), almost all of it the write price (Opus 5.5: $5/M for 5 minutes, $8/M for an hour; writes are ~35% of the chain's cost). Cold rebuilds after 5–55-minute pauses: 11 of 82, $6; of 58 pauses of 5–10 minutes 8 were rebuilt; ~80 pings, ~$2. Without keep-warm `5m` is still cheaper ($66 less than the hour, ~$21 to rebuild every pause the pings held), but each question waiting over 5 minutes would wake a cold session. The guide's table (`docs/guide/sessions.md`, "Which cache lifetime") gives the cost of an answer by its delay at ~108k of context. Whether a subscription's limit counts the two lifetimes differently is not published and our data does not tell (the switch coincided with the kind of sessions and the date), so the guide promises API prices only. A changed default reaches every install that never stored the key: a page save writes no row equal to the default (`changesOf`), so a stored `1h` or `null` stays.

Project chats (`MachineChats`, `src/service/machine-chats.ts`) are always on the hour: a Claude chat is launched and resumed with `promptCacheTtl: 1h` in its `--settings` (`createChatSettings`, BTN-1694), `--bg` and SDK alike, whatever `cacheTtl` says. Keep-warm does not ping a chat, and a person in a chat leaves for longer than five minutes. As a flag it outranks `promptCacheTtl` of the account's and the project's settings files; the environment variables above still outrank it.

### The cache trial (BTN-1412)

The measure of 2026-11-20 could not tell whether a subscription's limit counts the two lifetimes differently: `5m` came with a change of session kinds and a date. The trial makes the lifetime vary on its own. `cacheTrial` (G, off, written by hand through `config-import`; no field on the page) on, a chain session's `promptCacheTtl` is `trialTtl(task)` (`src/sessions/cache.ts`) over the project's and the shared `cacheTtl`: the task's number mod 4 is 0 or 1 — `5m`, 2 or 3 — `1h`. It is the number's second bit, so it crosses the compaction trial's parity (BTN-505) in all four ways. It is worked out at every launch from the number (`createSessionSettings`), with no labels to hand out or forget: handoffs, keep-warm pings and resumes of the task get the same lifetime while the trial is on. A session named without a number (`<KEY>-FIX`, `<KEY>-CARRY`) keeps the project's lifetime; project chats stay on the hour; Codex, Copilot and OpenCode take no `--settings` lifetime. Keep-warm needs no change: its window is the lifetime the transcript wrote (EKR-122).

The page marks such a session: `SessionView.cacheTrial` (`byTrial`, set in `machine-side.ts`) is on while the trial is on and a Claude chain session's transcript wrote its number's lifetime, and the Cache tip of the session panel says the trial set it (`?cache=trial` in `dev:fake`). A lifetime the transcript wrote otherwise (an environment variable outranking `--settings`, overage) gets no mark, nor does a session after the trial is turned off.

### Every agent's cache (BTN-560, research)

The chain takes a session's cache for warm by its agent's window (`Agent.warmMs`, BTN-563; below the table). How long each agent's cache really lives, by the providers' documentation and by Tally: the share of the prompt read from the cache by the first request after a pause, counted over every response in Tally up to 2026-10-29. Short of 3 minutes every agent reads 95–98%; the base an agent reads after any pause is its system prompt and tools, cached across sessions (8–12k tokens for Codex).

What follows for the chain (BTN-563). Each lifetime is taken less a margin (`warmCacheMs`, `src/sessions/cache.ts`): an hour is 55 minutes, half an hour 25, five minutes 4. The adapter's `warmMs` gives the window from the cache the transcript last wrote and whether the account is on a key; `SessionMonitor.handoff` puts it into `HandoffSession.warmMs`, and every warm check reads it there — a limit or credit resume (`holdOf`, `relayStep`), the fixed-`main` resume and the pull request feedback (`warmSince` in `src/chain/mainfix.ts` and `src/chain/reviews.ts`). A session the monitor no longer sees, and an agent without `warmMs`, get `WARM_CACHE_MS`, 55 minutes.

- Claude: by the transcript's `ttl` on any sign-in, so a subscription's `cacheTtl: "5m"` or overage gets 4 minutes (EKR-122); before the transcript writes a cache, 55 minutes on a subscription and 4 on a key.
- Codex: 25 minutes on any account; the rollout does not say, so it is known in advance. The fold takes the cache as written at the last model call (the rollout's last `token_count` with a `last_token_usage`) and living 30 minutes (`CODEX_TTL`, BTN-564): that is the cache keep-warm reads and the page's cache clock shows for a Codex session.
- Copilot: by `usage.cacheExpiresAt` of the session's last own `session.usage_record`, its lifetime counted from the call's start (`timestamp` less `duration`) and named by the longest of `5m`, `30m`, `1h` it outlives (`ttlWithin`). A last call without the field leaves `cache` empty and the window 25 minutes. The cache is also what the page's cache clock shows for a Copilot session.
- OpenCode: 55 minutes: DeepSeek outlives it, so it only errs on the safe side. Its ChatGPT, Copilot and Anthropic providers are not told apart; they wait for sessions of their own.

Keep-warm (below) is Claude's and Codex's. Codex's is `codex exec --ephemeral fork <id> <prompt>`, which forks a session and keeps no files. Probed on 0.164.0 (BTN-677, 2026-11-01, `gpt-6-luna` on a free ChatGPT account; `docs/verified.md`, "Codex"): the `exec` flags go before `fork`; the fork gets a thread id of its own and still reads its prompt from the source session's cache, 96.9–99.6% of it 1–4 minutes after the source's turn, with the project's packages through `CodexPlugins` args too. Its `turn.completed.usage` and `total_token_usage` add the source session's whole total to its own request, so a ping's hit is its usage less the session's last `total_token_usage`; a fork without `--ephemeral` shows its own in `last_token_usage`. `--ephemeral` writes no rollout and leaves the source's alone; `-s read-only` turns a tool call down by policy; `--disable hooks` keeps every package hook quiet, while without it the Stop hooks run under the fork's own thread id. OpenCode's `run --fork` writes a session of its own, to be deleted afterwards as `Agent.write` does, and DeepSeek does not need one. Copilot 1.0.98 has no fork, so a ping would write into the waiting session itself.

### Keep-warm (BTN-437, `src/sessions/keepwarm.ts`, `Agent.warm`)

Modelled on Flow's `/keepwarm` (MIT). When to ping and what keeps it safe is in `docs/chain/exceptions.md` ("A keep-warm ping"); here — what the ping is. It is a fork of the session that writes nothing: the session's transcript, process and question stay as they are. Besides the sessions a chain waits for, it keeps warm the session a red main stopped mid-turn while the fix runs (`chain.interrupted`, BTN-1616), the one `MainFix.resume` continues by `--resume` only while its cache is warm: on Claude Code, whose fork reads a transcript ending on an open tool call; a Codex one is left alone.

The page learns of the pings from the machine, not from the transcript (EKR-143): the session views the machine sends the hub (`sessions` of `src/service/machine-side.ts`) get `warm` (`KeptWarm`: the last ping that read the cache and the count) from `KeepWarm.kept`, only for the stretch of idleness its `cache` names, and each such ping tells the hub the machine's facts changed (`onWarm` → `tell.changed`). `sessionCache` in `web/src/state.ts` counts the cache warm until a lifetime after that ping; the cache clock, its tone, the chain row's ring and the cold-reply dialog all read it. The session panel's Cache fact (`CacheFact`) has one tip, its own, opening with that time ("warm until"/"cold at"); `CacheClock` carries no `title`, which the browser drew over it (EKR-145). The memory lives in the machine's process and is taken again after a restart (BTN-1507): the hub's `records.restore` gives the machine its `warm_pings` of the last 25 hours (`readWarmPings(db, since)`, `RetainedRecords.warm`), `KeepWarm.restore` keeps them by session, and the first check that knows a session's cache (`seed`) builds its series from those of the current stretch — the hits are the count, the last hit is `warmedAt`, a last miss keeps the session off. Before, BTN-1337's ping at +4.4 min and a restart at +6.5 left the new process counting from the session's answer: cold, let go.

Timing (BTN-1507, BTN-1527). The check runs every 5 s (`KEEP_WARM_TICK_MS`, it reads only facts in memory) and a five-minute cache is pinged 90 s before it ends, an hour or a half-hour one 5 minutes before (`MARGIN_MS`). With the old 30 s tick and 60 s margin a restart inside the window left no check in time: BTN-1292 and BTN-1443 came back at +4.0 min and were never pinged. The 90 s do not cover every restart. By the logs of 20.11 00:18–22.11 21:39, 103 restarts: most are 5–20 s from `stopped` to `listening`, 11 took 74–173 s, every one with a build under the stopped service — 8 a rebuild whose checkout a chain or a hand commit moved on (`building again`, `building it instead of the commit before`), 3 a plain `stop → install → build → start` (97–112 s). After `listening` the facts of a session take 30–52 s more (series restored at +30 s and +52 s; in the second, 79 s from the stop with 27 s down). A stop just before a ping went past the margin from 104 s down on.

So a planned stop asks first (BTN-1527, `docs/service.md`, "Keep-warm ahead of the stop"): `KeepWarm.ahead(ms)` runs the check with the window `ms` (240 s from the update process, at most the five-minute lifetime less a tick) in place of the margin wherever it is longer, so every session whose cache would go cold within the stop and the facts after it is pinged now, under the same conditions as any ping (`warmStep`'s `aheadMs`); it resolves once those and the pings in flight are answered, so their `warm.ping` records reach `warm_pings` before the stop and the next start's `seed` counts the cache warm from them. A rebuild whose checkout moved on builds the new commit before the stop, the service still up (`stopRebuild`), so only a changed `package-lock.json` keeps a build under the stopped service. A series still cut leaves one line (`reportCut`): `warmStep` says `cold` — the cache is cold while the session is otherwise one to ping — and the first check of this process that knew the session's cache came after its ping was due and within 3 minutes of the first check (`STARTUP_MS`), so a session a check knew in time, or one that came later (a chain resumed), says nothing: `keepwarm: <task>: the cache of <session> went cold at … unpinged: its ping was due from …, and the first check that knew the session came at …, the checks having begun at …: the series ends`.

A turn ended on a background job (BTN-1507). Claude lists a session whose turn ended while a background command runs as `shell`, which `turnStatus` turns into `busy` for the chain; with no open call `warmStep` used to wait, and the cache went cold until the job's notice came (BTN-1323, BTN-1475, BTN-1441, PPF-14). The transcript closes a turn with a `system` line `subtype: "turn_duration"` (after `stop_hook_summary`; PPF-14: the turn ended 16:06:40, the next line, the task notification, came 16:23:13). The fold sets `Turn.ended` on it, `startTurn` clears it; `SessionView.turnEnded` carries it, and `wireKeepWarm` sets `WarmFacts.ended` from it or the `shell` status. A turn ended on a background agent gets the same mark; on CLI 2.1.330 its process was `shell` too, though the names read in the CLI (`isLoading || delegatedActive`) allow plain `busy`. The ping warms only the session's own cache: an agent resumed after more than 5 minutes writes its context again.

An agent's own cache is not pinged (BTN-1530): CLI 2.1.330 has no way to fork an agent without writing into it. An agent lives inside its session's process with its transcript `<session>/subagents/agent-<id>.jsonl` and a `.meta.json` (`agentType`, `description`, `toolUseId`); `--resume` takes a session id or a `.jsonl` path, and a path is loaded as a main thread, with the main thread's tools and system prompt (only a main-thread `--agent` is restored), while an agent's request starts with its own: BTN-1511's agent read 0 tokens after its wait while the pinged session beside it read 98%, so not even the tools and system prefix were shared. The CLI resumes an agent only from inside its session (`SendMessage`, `resumeAgentBackground`), which is a new turn of the agent with its tools, not a read-only fork. So keep-warm stays the session's, and `/stats` counts what a cold agent costs instead: the cost tip of a task and of its session (`agentMisses`, `agentMissCost`, `agentRequests` and `AGENT_MISS` in `src/stats/reader.ts`) gives the agents' requests that came after a pause longer than the agent's lifetime (an hour when the agent ever wrote an hour's cache, five minutes otherwise) and wrote more of their prompt than they read, and their price. Not probed with a live agent here: every account folder on the workstation denies the Agent tool.

Failures (BTN-1507). A fork that answered with a tool call ends `error_max_turns` and exits 1 (BTN-1365): `runWithInput` keeps the run's `stdout` on the error (`stdoutOf`), `ClaudeCli.warm` reads the printed result from it, and `warmSpend` takes `error_max_turns` when its usage read or wrote any prompt — that ping counts by its usage. Any other non-transient failure is tried again on the next checks, and three in a row (`MAX_FAILURES`) turn the session off until a restart.

- `--bg` (`ClaudeCli.warm`, `warmArgs`): `claude -p --resume <id> --fork-session --no-session-persistence --output-format json --max-turns 1`, the session's `--mcp-config`/`--plugin-dir`, `--permission-mode dontAsk`, `--model` of the session's last answer (`SessionView.model`), the chain's `--settings` with `disableAllHooks: true` (`hooksOff`) and `--append-system-prompt-file` when the session has one (`agentsFallback`); the prompt `Reply with the single word ok.` on stdin, 3 minutes at most.
- SDK (`SdkSessions.warm`): `query` with a string prompt, `resume`, `forkSession: true`, `persistSession: false`, `maxTurns: 1`, `permissionMode: 'dontAsk'`, a `canUseTool` that denies, the session's own `sessionOptions` with the hooks off.
- What it spent is the top `usage` of the result (`warmSpend`): a fork's `modelUsage` and `total_cost_usd` add up the turns it resumed, so its cost is left `null`.
- Codex (`CodexCli.warm`, `warmArgs` in `src/codex/cli.ts`, BTN-564): `codex exec --json --ephemeral --sandbox read-only --disable hooks -c project_doc_fallback_filenames=["CLAUDE.md"]`, the model of the session's last turn, the gateway's servers (`mcpArgs`) and the packages' `CodexPlugins` args as its turns have them, then `fork <id> -` with the same prompt on stdin, 3 minutes at most, in the folder the registry gives the session. Read-only in place of `--approve-for-me` or the bypass: the probe forked an `--approve-for-me` session that way and read 97–99.6% (BTN-677). What it spent is `turn.completed.usage` (`parseWriteAnswer`) less the session's total as its rollout last wrote it (`forkSpend`), read just before the fork: the fork's usage adds that total to its own request. The fork writes no rollout and runs outside `TurnRegistry`, so neither the registry nor the page sees it.
- Every answered ping, a miss too, is recorded for Tally (BTN-1413): `wireKeepWarm` (`src/service/machine-chain.ts`) sends the link record `warm.ping` (`warmPingOf`, `src/sessions/warm-pings.ts`) with the session, task, project, account, model and the tokens by kind; the agents give the cache write as one number, which goes to the 5-minute or the hour column by the session's lifetime. The hub keeps it in `warm_pings` (step 70, `docs/storage.md`), and Tally copies it into its own `warm_pings` and prices it (`docs/tally.md`, step 20): the task's cost on `/stats` and the limit shares count the pings, apart from its responses. A ping that threw is not recorded.
- Every ping logs, as it starts, one `keepwarm: <task>: the ping <n> of <session> starts at …` line with the inputs of `warmStep`'s decision (BTN-1394, `pingLine`): the cache's lifetime and end and the request it is counted from, `busy`, `onTool`, `ended`, `held`, `limited`, the series memory (`stretch`, `pings`, `warmedAt`; `none` — no memory) and the transcript file's size, mtime and the last line the service folded from it (`KeepWarmDeps.transcript`; `unknown` — no file or a failed `stat`). The line after the answer says how it went. It is there to explain the few pings that went out early (EKR-144's count): an mtime well past the last entry means the service read the transcript late.

Probed on CLI 2.1.310 with Haiku (2026-10-26): without `--no-session-persistence` the fork writes a transcript of its own, with it none. Forks of a multi-turn `-p` session read 99.5% and 100% of their prompt from the cache; a single-turn `--bg` one 91.5%, a single-turn `-p` one 88% (the tool list and the system prompt of a first turn differ a little). `plan` mode reads nothing from the cache (it changes the system prompt), `auto`, `default` and `dontAsk` read the same; `--max-turns 1` does not stop a tool call in `auto` (a Write went through), `default` and `dontAsk` refuse it — so the fork runs in `dontAsk`. `disableAllHooks` keeps the cache. What was not seen live is in `docs/unverified.md`.

Mid-turn, on a long tool call (EKR-142). A session whose turn waits on a tool's result has a transcript that ends with the call and no result, and its cache goes cold under a build or test run longer than the cache's lifetime: the next request writes the whole context again (BTN-1251: a 5-minute cache, a six-minute `vitest`, ~122k written). Probed on 2026-11-18 with Haiku and `promptCacheTtl: "5m"`, the session running one foreground Bash call of 400 s. A `-p` session on CLI 2.1.327: its fork (`warmArgs`'s flags, no packages) resumed it 30 s into the call, answered and read 18,590 of 19,946 tokens (93.2%), writing 1,354 — the open call and a closing result of its own; a second fork at 230 s read 18,802 of 18,829 (99.9%). Neither wrote a transcript, and the session's own did not change. When the call returned, 6 min 40 s after the request that made it, the session's next request read 18,590 — its whole earlier prompt — and wrote 963. The control beside it, the same session without forks, read 15,694 and wrote 3,545: its own messages had gone cold, and the part it read was the prefix it shared with the pinged run. An SDK session (the SDK 0.3.319 with CLI 2.1.319, `SdkSessions.warm`'s options): forks at 30 s and 230 s read 19,283 of 20,059 (96.1%) and 20,057 of 20,057, wrote no transcript, and the session's request after the call read its whole earlier prompt, 19,283, and wrote 1,543. So `warmStep` pings such a turn like a waiting session (`WarmFacts.onTool`, `Agent.warmsOnTool`); a model request in flight, a resume or handoff hold and a starting task still stop it. Codex is not probed mid-turn and keeps waiting for the turn's end.
