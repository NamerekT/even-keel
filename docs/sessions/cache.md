# Sessions: the prompt cache and keep-warm

## Prompt cache lifetime (BTN-99)

What the CLI 2.1.302 binary does, in order of precedence: the `FORCE_PROMPT_CACHING_5M` variable → 5 minutes; the variables `CLAUDE_CODE_PROMPT_CACHE_TTL` / `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`; the settings `promptCacheTtl` / `subagentPromptCacheTtl` (`"5m"` | `"1h"`), whatever the sign-in; the `ENABLE_PROMPT_CACHING_1H` variable → 1 hour. Without any of them: 1 hour on a subscription within its limits (5 minutes in overage), 5 minutes on an API key, Bedrock or Vertex. A 1-hour cache write is billed higher than a 5-minute one.

The `cacheTtl` key (`"5m"` | `"1h"`, absent or `null` — the CLI decides; `/settings`, the Claude Code group, and a project's own value in its panel, BTN-187) goes into the chain sessions' `--settings` as `promptCacheTtl` (`chainSettings` in `src/tools/panel.ts`), on every launch. It is live: the next launch takes the new value. It matters mostly on a key, where a chain waiting for a reply longer than 5 minutes otherwise writes the whole context again. Seen live on a key with `1h` (CLI 2.1.310, Haiku, a `--bg` and an SDK chain session, 2026-10-25): every cache write of both was `ephemeral_1h_input_tokens`, none 5-minute.

### Every agent's cache (BTN-560, research)

The chain takes a session's cache for warm by its agent's window (`Agent.warmMs`, BTN-563; below the table). How long each agent's cache really lives, by the providers' documentation and by Tally: the share of the prompt read from the cache by the first request after a pause, counted over every response in Tally up to 2026-10-29. Short of 3 minutes every agent reads 95–98%; the base an agent reads after any pause is its system prompt and tools, cached across sessions (8–12k tokens for Codex).

| Claude `--bg` on an API key | 5 minutes, 1 hour with `cacheTtl: 1h` | the CLI binary; seen live with `1h` (above) | yes | yes: `cacheTtl` |

What follows for the chain (BTN-563). Each lifetime is taken less a margin (`warmCacheMs`, `src/sessions/cache.ts`): an hour is 55 minutes, half an hour 25, five minutes 4. The adapter's `warmMs` gives the window from the cache the transcript last wrote and whether the account is on a key; `SessionMonitor.handoff` puts it into `HandoffSession.warmMs`, and every warm check reads it there — a limit or credit resume (`holdOf`, `relayStep`), the fixed-`main` resume and the pull request feedback (`warmSince` in `src/chain/mainfix.ts` and `src/chain/reviews.ts`). A session the monitor no longer sees, and an agent without `warmMs`, get `WARM_CACHE_MS`, 55 minutes.

- Claude: 55 minutes on a subscription, as before (the overage's five minutes are not told apart); on a key by the transcript's `ttl`, 4 minutes when none is written yet.
- Codex: 25 minutes on any account; the rollout does not say, so it is known in advance. The fold takes the cache as written at the last model call (the rollout's last `token_count` with a `last_token_usage`) and living 30 minutes (`CODEX_TTL`, BTN-564): that is the cache keep-warm reads and the page's cache clock shows for a Codex session.
- Copilot: by `usage.cacheExpiresAt` of the session's last own `session.usage_record`, its lifetime counted from the call's start (`timestamp` less `duration`) and named by the longest of `5m`, `30m`, `1h` it outlives (`ttlWithin`). A last call without the field leaves `cache` empty and the window 25 minutes. The cache is also what the page's cache clock shows for a Copilot session.
- OpenCode: 55 minutes: DeepSeek outlives it, so it only errs on the safe side. Its ChatGPT, Copilot and Anthropic providers are not told apart; they wait for sessions of their own.

Keep-warm (below) is Claude's and Codex's. Codex's is `codex exec --ephemeral fork <id> <prompt>`, which forks a session and keeps no files. Probed on 0.164.0 (BTN-677, 2026-11-01, `gpt-6-luna` on a free ChatGPT account; `docs/verified.md`, "Codex"): the `exec` flags go before `fork`; the fork gets a thread id of its own and still reads its prompt from the source session's cache, 96.9–99.6% of it 1–4 minutes after the source's turn, with the project's packages through `CodexPlugins` args too. Its `turn.completed.usage` and `total_token_usage` add the source session's whole total to its own request, so a ping's hit is its usage less the session's last `total_token_usage`; a fork without `--ephemeral` shows its own in `last_token_usage`. `--ephemeral` writes no rollout and leaves the source's alone; `-s read-only` turns a tool call down by policy; `--disable hooks` keeps every package hook quiet, while without it the Stop hooks run under the fork's own thread id. OpenCode's `run --fork` writes a session of its own, to be deleted afterwards as `Agent.write` does, and DeepSeek does not need one. Copilot 1.0.98 has no fork, so a ping would write into the waiting session itself.

### Keep-warm (BTN-437, `src/sessions/keepwarm.ts`, `Agent.warm`)

Modelled on Flow's `/keepwarm` (MIT). When to ping and what keeps it safe is in `docs/chain/exceptions.md` ("A keep-warm ping"); here — what the ping is. It is a fork of the session that writes nothing: the session's transcript, process and question stay as they are.

- `--bg` (`ClaudeCli.warm`, `warmArgs`): `claude -p --resume <id> --fork-session --no-session-persistence --output-format json --max-turns 1`, the session's `--mcp-config`/`--plugin-dir`, `--permission-mode dontAsk`, `--model` of the session's last answer (`SessionView.model`), the chain's `--settings` with `disableAllHooks: true` (`hooksOff`); the prompt `Reply with the single word ok.` on stdin, 3 minutes at most.
- SDK (`SdkSessions.warm`): `query` with a string prompt, `resume`, `forkSession: true`, `persistSession: false`, `maxTurns: 1`, `permissionMode: 'dontAsk'`, a `canUseTool` that denies, the session's own `sessionOptions` with the hooks off.
- What it spent is the top `usage` of the result (`warmSpend`): a fork's `modelUsage` and `total_cost_usd` add up the turns it resumed, so its cost is left `null`.
- Codex (`CodexCli.warm`, `warmArgs` in `src/codex/cli.ts`, BTN-564): `codex exec --json --ephemeral --sandbox read-only --disable hooks -c project_doc_fallback_filenames=["CLAUDE.md"]`, the model of the session's last turn, the gateway's servers (`mcpArgs`) and the packages' `CodexPlugins` args as its turns have them, then `fork <id> -` with the same prompt on stdin, 3 minutes at most, in the folder the registry gives the session. Read-only in place of `--approve-for-me` or the bypass: the probe forked an `--approve-for-me` session that way and read 97–99.6% (BTN-677). What it spent is `turn.completed.usage` (`parseWriteAnswer`) less the session's total as its rollout last wrote it (`forkSpend`), read just before the fork: the fork's usage adds that total to its own request. The fork writes no rollout and runs outside `TurnRegistry`, so neither the registry, the page nor Tally sees it.

Probed on CLI 2.1.310 with Haiku (2026-10-26): without `--no-session-persistence` the fork writes a transcript of its own, with it none. Forks of a multi-turn `-p` session read 99.5% and 100% of their prompt from the cache; a single-turn `--bg` one 91.5%, a single-turn `-p` one 88% (the tool list and the system prompt of a first turn differ a little). `plan` mode reads nothing from the cache (it changes the system prompt), `auto`, `default` and `dontAsk` read the same; `--max-turns 1` does not stop a tool call in `auto` (a Write went through), `default` and `dontAsk` refuse it — so the fork runs in `dontAsk`. `disableAllHooks` keeps the cache. What was not seen live is in `docs/unverified.md`.
