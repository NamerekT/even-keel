# Sessions: the chat mailbox, permission dialogs and one-off turns

## Chat mailbox (BTN-181)

A failed user-answer delivery (`Handovers.deliver`, BTN-499) returns false, clears the temporary delivery marks and logs the refusal without pausing the chain or retrying the answer on its next tick. The user can send it again. Pull request feedback failures still pause the chain. Tests cover the refusal, the absence of an automatic replay and a successful explicit retry; this failure path has not been checked with a live CLI ([unverified.md](../unverified/sessions.md#mail-resumed-while-a-chain-stops-btn-427)).

A session that steers — an SDK session, `AgentEntry.steers` — needs no mailbox: a chat message mid-turn goes straight into its live CLI (BTN-291, "The Agent SDK transport" below), and only when that finds the session not live here after all does the message fall back to the mailbox, if its hooks listen. Any other chat message to a working session (invariant 1, `docs/chain.md`) waits in the `mailbox` table of the state database (`Mailbox` in `src/sessions/mailbox.ts`) until a hook of the `checkpoint` plugin takes it (`plugins/checkpoint/hooks/mailbox.mjs`, from plugin 0.7.0, on `PreToolUse`, `PostToolUse` and `Stop` of every tool). The hook calls `POST /api/sessions/<id>/mail` with `{ event }` — `PreToolUse`, `PostToolUse`, `Stop`, or `AskUserQuestion` for a `PreToolUse` of that tool — and gets `{ message }`: `null` when nothing waits, 404 for a session the chain did not start, 400 without a known event. A message hands everything that waited at once, marked delivered on that event (`mailFor` in `src/sessions/mailRelay.ts`):

- before or after a tool call — `hookSpecificOutput.additionalContext`, the turn goes on; in a Copilot session (`EVEN_KEEL_AGENT=copilot`) a top-level `additionalContext` (`contextOutput` in `plugins/checkpoint/hooks/evenkeel.mjs`), as for the context nudge and a standard's document, since Copilot drops the former on `PostToolUse` (BTN-467);
- at `Stop` — `{ decision: "block", reason }`, so the session carries on instead of ending its turn;
- before `AskUserQuestion` — `permissionDecision: "deny"` with the message as the reason: the question does not go out next to an unread message, and the session asks again only if it still needs to.

The same answer may carry `context`, a note of the service's own that the hook (from plugin 0.15.0) adds to `additionalContext` after the mail on `PreToolUse` and `PostToolUse` only — never at `Stop` or before a question, so it neither keeps a turn going nor turns a question down. Its one user is the request for the README badge's status line (`mailContext` in `src/server.ts`, `docs/badge.md`, BTN-932).

A subagent's call (`agent_id` in the hook's input) is left alone, so the message waits for the main thread. With no service or no answer in time (5 s for every event, within the hook's 10 s budget) the hook prints nothing and the tool call goes on.

The HTTP handler reserves mail in memory (`Mailbox.take`, BTN-522) while the stored rows remain `waiting`, excluded from other hooks and settlement timers. It marks them `delivered` and publishes the change only on the response's `finish`. A connection closed or failed before `finish` releases the reservation for the next hook or resume; a service restart also releases it. This acknowledges sending the HTTP response, not the CLI applying its contents. Checked with the real mailbox hook and delayed HTTP responses on Windows ([verified.md](../verified/sessions.md)).

The text (`mailMessage` in `src/sessions/mail.ts`) is a lead for the event in the prompt language — "the user wrote to you from Even Keel's chat while you were working", "so your turn is not over yet" at `Stop`, "your question did not go out" before a question — then each message as `<even-keel-message id="N">` around its `replyPrompt` (the words and the paths of files saved into `.temp/inbox/`). The `Stop` lead also asks the session to repeat its previous final `NO CHANGES:`, `CHECKPOINT:` or `PULL REQUEST:` line after answering, if the message has not changed the task's outcome. The folds still take the mark from the latest response: an old mark cannot override a new outcome.

The mark around each message is how the feed finds it again (`mailIn`, `pushMail` in `src/sessions/transcript.ts`): in a hook attachment (`attachment.type` `hook_*`; at `PreToolUse`/`PostToolUse` it is `hook_additional_context` with the text in `content`), in a user prompt, meta ones included (the `Stop` feedback: an `isMeta` user prompt `Stop hook feedback:\n<reason>` next to a `hook_blocking_error` attachment), and in the error result of the open `AskUserQuestion` (`PreToolUse:AskUserQuestion hook error: <reason>`) — which then closes that question instead of leaving it astray. All three seen live on 22.10.2026, CLI 2.1.308. The Codex feed (`RolloutFold` in `src/codex/rollout.ts`) reads it in a `response_item` message of role `developer` — the only trace a hook's `additionalContext` leaves in a rollout, seen live on 18.10.2026 — and in a `UserMessage`. At `Stop` it reads `HookPrompt.fragments[].text`; the escaped `<hook_prompt>` user response item is ignored. A `HookPrompt` does not clear final marks or count as an assistant reply, and mail ids are deduplicated across hook representations. The OpenCode feed reads it in a tool call's `metadata.evenKeel.mail`, where the package's OpenCode plugin keeps what it appended to the output (on `PostToolUse` only). The Copilot feed (`CopilotFold` in `src/copilot/transcript.ts`) reads it in `hook.end`'s `data.output.additionalContext`, which Copilot 1.0.105 writes on `postToolUse` but not on `preToolUse` (`hook.end` holds only `hookType` and `success`, BTN-516). For that gap the chat window's feed also gets the mailbox's delivered hook messages (`Mailbox.delivered`, `deliveredMail`), each fed as the user's prompt at its `settledAt` unless the transcript showed its id first; the mailbox keeps them a week, so an older Copilot session's chat loses its `preToolUse` messages (BTN-519). Other tool results are never read, so a session that prints the mark from a file does not fake a message. Tally does not count mail as a turn start.

Whether a session's hooks listen is known only from the hooks themselves: `Mailbox.listens` is true once they have asked at least once since the service started. A session with an older plugin, without the `checkpoint` package, or a new one before its first tool call does not listen, and the chat refuses it mid-turn with `answer.busy`, as before. After a service restart a working session listens again at its next tool call.

The race with the end of a turn is settled by `settleMail` on every change the session monitor reports and every 15 s: a message still waiting for a session that is no longer mid-turn, 10 s or more after it was posted (`mailOutcome`), goes by a resume as an answer would (`resume` as its event), or comes back to the chat (`returned`) when the session waits on a question or is gone, or the resume is refused. `Dispatcher.answer` returns the result of delivery from its queue; mail stays `waiting` until the transport accepts the reply, then becomes `delivered`/`resume`, or `returned` if delivery fails. `Mailbox.claim` holds those rows in memory while delivery waits, excluding them from hooks and further settlement passes without changing the stored fate. A service restart releases these claims. If the chain stops before the queued delivery, `Handovers.deliver` uses `deliverLoose` while `handoff(task)` still names the same session and no new chain has started; a changed session or a refused delivery is logged and returns failure. The same fallback serves answers from the page and tracker. A returned message leaves the chat window when the user answers the session from it or presses "Dismiss" (`session/mail/dismiss`). Settled rows are deleted a week after they settled, at the next post.

## A reply to a cold session (BTN-757)

A reply to a session that is not mid-turn and whose prompt cache went cold (`coldReply` in `web/src/pages/coldReply.ts`: the level `cold` of `cacheFreshness`; an unknown cache sends as before) first opens `ColdReplyDialog`: when the cache went cold, how many tokens of context a resume rereads at the cache write price, and three buttons — "New session with this message" (primary, focused), "Reply to this session", "Cancel" (the text and the files stay in the box). A loose session (its chain stopped, `ChatTarget.renews` false) gets only the reply and the cancel: no chain to hand it over. A reply mid-turn — the mailbox or steering — never asks: the turn's cache is warm.

The choice goes as `renew: true` in `POST /api/session/answer` (`answerOf` in `src/server-request.ts`). `answerSession` (`src/sessions/chat.ts`) saves the files into `.temp/inbox/` and builds the same `replyPrompt`; a session that turned out to be mid-turn takes it as usual, otherwise `Dispatcher.renew` checks as `answerable` does (`answer.moved`, `chain.limitSpent`, `chain.launching`), refuses a loose session with `chain.notCurrent`, and queues `Handovers.renew`: the handoff of "New session" (`handOverCurrent` with the reason `message`) whose prompt has its own `why.message` line and ends with `userMessage` ("The user's message:") and the reply. The launch log says `restart` with cause `message`, the page's session list "New with your message"; the snapshot's reason is `restart` (Tally's reasons are unchanged), told apart by its prompt. The page does not echo the reply into the old transcript: the panel turns to the new session. A service restart mid-move repeats it with the same reply (`move: 'message'`, `Handovers.recover`). The old session is stopped as on "New session" — invariant 1's exception 2 (`docs/chain/exceptions.md`). Never run live ([unverified](../unverified/sessions.md#a-reply-to-a-cold-session-btn-757)).

## Permission dialogs (BTN-269)

A `--bg` session in `auto` mode still stops on a permission dialog: an `ask` rule of the settings, the classifier refusing a call several times. Seen live on CLI 2.1.308 (2026-10-23, Haiku, an `ask` rule on `Bash(echo:*)`): the session record says `status: waiting`, `waitingFor: "permission prompt"`; the job file has `tempo: blocked` and only one line, `needs: "approve Bash: echo …"`, no structure like `block.questions`; the pending `tool_use` is in the transcript at once. A stop and `--resume` lose the call (`[Tool call interrupted: …]`, then `No response requested.`), and the resumed model makes it again and meets the same dialog, since the rule stays: no way to allow a call.

What works is a `PermissionRequest` hook (`plugins/checkpoint/hooks/permission.mjs`, from plugin 0.10.0). Seen live on the same CLI: the hook gets `session_id`, `tool_name`, `tool_input` and `permission_mode`, no `tool_use_id`, one hook per call (two parallel calls — two hooks); the CLI shows the dialog at once and runs the hook beside it, so the session stays `waiting` while the hook waits; a decision the hook prints later is taken in the middle of the open dialog — `allow` runs the call, `deny` with `message` gives the model an error result with that text and the turn goes on — and the transcript gets a `hook_permission_decision` attachment with `decision` and `toolUseID`. A hook that prints nothing leaves the dialog. A dialog answered by something else (another hook's decision, so presumably Remote Control too) does not end a hook still waiting: it runs on to its timeout.

So the hook asks Even Keel every second, `POST /api/sessions/<id>/permission` with `{ tool, input, since }` (`since` — the hook's start, ms), until the answer is `{ decision }` other than `null`, and prints it as `hookSpecificOutput.decision`. A 404 — a session the chain did not start, or a call closed after the hook began — ends it with no output; no Even Keel at the first request ends it too, while a failed request after an answer is taken for a restart of the service and the hook asks on. It gives up after 29 minutes (its `timeout` is 1800 s, as `merge-check`'s). Codex 0.162.1 has the same hook event and runs it (its input carries `turn_id`), but its approvals belong to its reviewer (`--approve-for-me`), so the hook leaves them alone. `AskUserQuestion` gets a `PermissionRequest` too, its dialog being the question itself: the hook leaves it (from 0.11.2), and the service answers a 404 to an older hook that still asks, so the question stays one of the transcript, not a call to allow.

The service's side is `Approvals` (`src/sessions/approvals.ts`), in memory: a call by the session and a hash of `[tool, input]`, put to the user by `permissionAsk` (`src/sessions/permission.ts`, shared with the SDK host, BTN-303) with the id `perm:<session id>:<hash>`. While the session is `waiting`, the oldest call not yet decided is its `SessionView.ask` (the monitor's `approval`, ahead of a question of the transcript), so the question panel, the chat and a tracker comment answer it like any question; `resumeWith` settles it first (`approved` in `src/service.ts`) by `permissionMove` and returns the same session id, with no stop and no resume — words that came with "Allow" wait in the session's mailbox. While the chain runs unattended a call is refused at once with `NO_APPROVAL`. A call whose hook has not asked for 10 s is dropped; on every read of the sessions (`settle`) the calls of a session not `waiting` and older than 10 s are closed — the dialog was answered elsewhere — and their hooks get a 404 on their next poll, while a later hook for the same call (`since` after the close) is asked anew. After a restart of the service the hooks ask again and the calls are back.

## One-off turns (BTN-142, `Agent.write`)

The optional `Agent.write(home, turn)` (`OneTurn`: `cwd`, `prompt`, `model`, `timeoutMs`) runs one turn that keeps no session and answers with its text; `runWithInput` (`src/agent/oneturn.ts`) feeds the prompt on stdin, so a long one never meets the Windows command-line limit, and kills the process tree on the timeout. Only reading tools, no MCP, nothing to approve:

- Claude: `claude -p --output-format json --no-session-persistence --strict-mcp-config --disable-slash-commands --tools Read,Glob,Grep [--model <m>]` (`writeArgs` in `src/claude/cli.ts`); `parseWriteAnswer` takes `result` and throws with the CLI's own words when `is_error` is set or there is no result. The cost is `total_cost_usd`, the tokens the sum of `modelUsage` (every call of the turn by model; the top `usage` counts only the last call), the model the costliest key of `modelUsage`.
- Codex: `codex exec --json --sandbox read-only --ephemeral --color never [-m <m>] -` (`writeArgs` in `src/codex/cli.ts`): the answer is the last `agent_message` item, the tokens are the `usage` of `turn.completed` (`input_tokens` holds `cached_input_tokens`), a `turn.failed` throws its message. Codex counts no cost and its events name no model: the cost is null and the model the one asked for. Without a model Codex takes the one of its own config, which a ChatGPT account may refuse.

Both checked live on 2026-10-18, Codex before `--json` (`docs/unverified.md`).

`Agent.write` returns the text with the turn's `TurnSpend`; the changelog keeps it with the version under the account folder it ran on (`ChangelogSpend`), and the dialog shows it (`docs/web.md`). A turn with `--no-session-persistence` or `--ephemeral` leaves no transcript or rollout, so Tally and `/stats` never count it. The turn cannot ask: neither tool list holds `AskUserQuestion`, `Edit`, `Write` or `Bash` (a test of `writeArgs` keeps it so), and the prompt says no one will answer a question.

The one user is the changelog of a milestone (`src/changelog/`, BTN-142, BTN-209): `ChangelogDrafts` (`drafts.ts`) takes the account and model a new chain session of the project would get (`choiceFor` in `src/service.ts`) and runs in the project's main checkout with a 10-minute timeout; one operation per milestone at a time, a second ask gets the running one's result. The source is the changelog file in the main checkout (the project's `changelog` setting, `CHANGELOG.md` by default), read anew on every turn so the user's own edits there are kept; `changelogPlan` (`file.ts`) finds the milestone's section: a milestone named by a version (`v0.1`) owns `[0.1.0]`, its patches and, until its first tag, `Unreleased`; a tagged section is frozen and new tasks go into the next patch's section, which Even Keel heads itself (`docs/releases.md`). The prompt (`changelogPrompt`, `draft.ts`) has three modes: `fresh` — the section from the milestone's `Won` tasks with their last comments (`milestoneTasks`, `docs/trackers.md`, each comment cut to `MAX_COMMENT_CHARS`); `update` — the file's section with only the tasks it lacks, worked into it without rewriting the rest, a task the user already described is not repeated; `edit` — the section and the user's words, no tasks. Every mode gets the tags and the frozen sections as "already released, do not repeat", and asks for Keep a Changelog groups in the language of the changelog file, else of `README.md`. It also gets the sections of the version line before the milestone's (`changelogPlan`'s `previous`: `0.1.x` for `v0.2`, for a milestone that is not a version the newest line of the file) as what the reader upgrades from: a fix, change or removal of something the section adds is folded into that entry or left out, and Changed, Removed and Fixed hold only what that release already had. Without the rule the v0.2 draft listed fixes of OpenCode, Copilot, GitLab and Jira, all new in v0.2, under Fixed. The answer is cut to its section (`answerSection`) and kept as a version in the database (`changelog_versions`, `docs/storage.md`) with the tasks it accounts for and the text its changes are shown against. "Write" puts the newest version into the file — the milestone's section replaced, or a new one put above the older versions — and commits only that file to the project's main branch of the main checkout without a task id (`commitChangelog`, `src/git/changelog.ts`): refused when the checkout is on another branch or the file has uncommitted changes, the CRLF line ends of the file kept; the next `git sync` pushes it. Measured on BTN `v0.1`: 172 tasks, a 183 000-character prompt (~200 000 tokens with the reads), 29 s and $0.42 on Sonnet. The routes are `POST /api/changelog/open|draft|again|add|edit|write` `{ project, milestone, instruction? }` (`docs/web.md`); `open` runs no turn — without a version it gives the task counts and the file's section (`ChangelogView.start`), and only `draft` writes the first one (BTN-747).
