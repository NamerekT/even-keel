# Sessions: pinned, checked and latest CLI versions

## Pinning the CLI versions (BTN-248, research)

Whether chain sessions can run on a checked CLI version instead of the one the CLI updated itself to; the implementation is BTN-250, the next section, which holds what was built (the download, the daemon check, what a pin does not cover). Checked on Windows on 2026-10-19 with Claude Code 2.1.301–2.1.303 and codex-cli 0.162.1, in a scratch `CLAUDE_CONFIG_DIR`, not signed in. What Even Keel depends on in each CLI is listed in the README ("Before you run it"). Why the copy is built as it is:

- **Claude Code follows the newest version by itself.** The native installer keeps whole binaries in `~/.local/share/claude/versions/<version>` and a copy of the current one at `~/.local/bin/claude.exe`, the path `resolveClaudeBinary` takes. Each account folder has its own daemon (the pipe `cc-daemon-<16 hex>` is keyed by the config folder); the daemon spawns its pty hosts and sessions from its own binary and restarts itself on a newer build once its binary file changes (`tengu_daemon_self_restart_on_upgrade`, deferred while busy; it refuses an older build). So when the user's own CLI updates, the service's daemon moves to the new build and the chain's next sessions run on it. Builds came every day or two (2.1.301 on 10-15, 2.1.303 on 10-18).
- **So the copy lives outside `versions/`.** A binary under `versions/` starts the daemon through the launcher `~/.local/bin/claude.exe`: a `--bg` from `versions/2.1.302` got a daemon and a session on 2.1.303. A copy of the same binary outside that folder starts the daemon, its pty hosts and its sessions from itself. A folder per version, as a running exe cannot be replaced on Windows.
- **The daemon decides the version, not the client.** A `--bg` from a 2.1.302 copy to a running 2.1.303 daemon got a 2.1.303 session; a `--bg` from the 2.1.303 launcher to a running 2.1.302 daemon replaced that daemon, the old session's pty host living on, orphaned. Hence the daemon check of the next section, and the limit that a pin holds only while nothing newer starts a background session or asks `claude agents` in that account folder.
- **Auto-update off per process.** `DISABLE_AUTOUPDATER=1` turns it off for a process (`DISABLE_UPDATES` also blocks `claude update`); `autoUpdates: false` in the global config counts only for non-native installs, and `autoUpdatesChannel`/`minimumVersion` are settings of the config folder, so they would move the user's own sessions there too. `claude install <version>` moves the launcher, so it would change the user's own CLI. The VS Code extension runs its own bundled binary and no daemon.
- **Shared state.** The account folder — `.claude.json`, `settings.json`, transcripts, `sessions/`, `jobs/`, `daemon.json`, the plugins — is shared by every version that runs in it. A pin protects the control path of chain sessions (`--bg`, `agents --json`, the records, `/usage`), not the reading of the files other sessions write on their versions.
- **Codex has no daemon in the chain's path.** A turn is one `codex exec` process, so the version of a turn is that of its binary. Codex does not update itself (`check_for_update_on_startup` only shows a notice in the TUI), and on Windows an npm update cannot replace a `codex.exe` a turn is running from. The Codex desktop app ships its own build and shares `~/.codex`. `CODEX_HOME` holds versioned SQLite files (`state_5`, `logs_2`, `thread_history_1`), so a newer schema gets a new file; `codex migrate-rollouts --apply` (manual in 0.162.1) moves legacy sessions to "paginated thread history", and a version that did that by itself would break the rollout reader whatever the chain runs on.
- **Licences.** Claude Code is proprietary ("© Anthropic PBC. All rights reserved"): its binary cannot go into this repository or a release of Even Keel, which may only fetch it from Anthropic onto the user's machine, as the installer does. Codex is Apache-2.0.

## The checked CLI (BTN-250, `src/agent/pinned.ts`)

Chain sessions can run on the CLI version Even Keel was last checked against (`AgentAdapter.checked`, the README's "Last checked against") rather than the one the installed CLI updated itself to. The global setting `cli.<provider>` chooses, for all four agents (BTN-347): `system` ("Yours" on the page, the default), the installed CLI, or `checked`, Even Keel's copy; it applies from the next call of the CLI. `EVEN_KEEL_<AGENT>_BIN` beats both. Yours is the default (BTN-603) because a copy is roughly 80–340 MB to download per agent (Codex's unpacks to ~500 MB), and the unchecked-version warning (BTN-593, an entry of the event log) keeps Yours honest; databases and config files from before keep `checked` written (DB step 20, config v21, `docs/storage.md`).

### Even Keel's own copy

- **Never downloaded unasked.** `PinnedCli.path()` is passive: startup, availability, version checks, sign-in and SDK probes never download.
- **Consent.** Choosing Checked (`CliSourceChoice` in the setup's Agent step and Settings → Providers and models, through `useCheckedSwitch` in `web/src/layout/CliSource.tsx`) offers consent with the version and the approximate size of the download (the last argument of `cliCopy`, not the space on disk); so do selecting a provider already on Checked without a copy and adding its account. Closing it keeps the choice without downloading.
- **Once per provider** (BTN-1175). A download that ends ready adds the provider to `cli.downloaded` in `service_state`, and so does a whole version folder found at the start (`PinnedCli.hadCopy`, the old version the first sweep then removes included, so installs from before the record count). A provider in it, on Checked, with its copy `missing` (not `failed`) fetches by itself: at the start (`copies().resume()` in `src/service/lifecycle.ts`) and whenever `blocked` is asked, so a raised pin after an update downloads with no click and the chain waits only for the bytes. The first choice of Checked and a provider whose copy was never downloaded still ask.
- **The download.** `cli/download` fetches into `<version>.partial`, verifies the binary and atomically renames it. After a download all other versions are pruned; locked folders are retried at service startup and each version sweep, including `claude-sdk`.
- **Progress.** The header's and agent card's blue bands show the byte progress (Claude's manifest size, npm's response Content-Length) of one package only: the CLI, or Claude's Agent SDK when the CLI is already in place. Once that package is in, the band reads "Checking and unpacking…" until the copy is ready, however the second package's bytes go: summing both sent it back to bytes several times (BTN-681).
- **The chain waits** on `agent.copyMissing` while Checked has no ready copy, even if a system CLI exists; it resumes when the copy is ready.
- **A failed download** persists only that provider's source as `system`, shows `agent.copyFailed` and waits for the explicit retry.
- **Yours never installs anything globally:** a missing binary has a command block, Check again and Checked to choose.
- All Claude calls, including marketplace operations, use the adapter's resolved binary.

### Per agent

- **Claude Code** (`src/claude/release.ts`): `manifest.json` of the version gives the binary's size and sha256 for the platform (`win32-x64`, `darwin-arm64`, `linux-x64`, `linux-x64-musl` on a Linux without glibc, …), the binary is `https://downloads.claude.ai/claude-code-releases/<version>/<platform>/claude(.exe)`, with the manifest beside it, checked against both before it is used; ~340 MB per version. Nothing of it goes into the repository: the licence is proprietary.
- **Codex** (`src/codex/release.ts`): the platform's npm package `@openai/codex@<version>-<platform>` (Apache-2.0), its tarball only from `registry.npmjs.org` and checked against the registry's sha512, unpacked by `tar` (on Windows `System32\tar.exe`) into the version's folder; the binary is `vendor/<triple>/bin/codex(.exe)`, with `codex-path` and `codex-resources` beside it as in the global package; ~180 MB to download (180.7 MB for 0.166.0 on win32-x64), ~500 MB unpacked. A turn is a process of that binary, so the next turn runs on the copy.
- **OpenCode** (`src/opencode/release.ts`): the npm package of the platform's native binary that `opencode-ai` lists as an optional dependency, `opencode-<windows|linux|darwin>-<x64|arm64>` with `-musl` on a Linux without glibc (MIT), fetched and checked as Codex's; the binary is `bin/opencode(.exe)`, ~80 MB per version. The `-baseline` builds `opencode-ai`'s `postinstall.mjs` takes on an x64 without AVX2 are not: such a machine runs on `system`. The npm versions are OpenCode's own releases, the ones `npm install -g opencode-ai` installs.
- **Copilot** (`src/copilot/release.ts`): the npm package of the platform's native binary that `@github/copilot`'s `npm-loader.js` runs, `@github/copilot-<win32|linux|linuxmusl|darwin>-<x64|arm64>`, fetched and checked as Codex's; the binary is `copilot(.exe)` at its root, the whole CLI without Node, ~155 MB per version. Its versions are the ones winget installs (both 1.0.103 on 2026-10-24). A Copilot binary runs the newest version it has updated itself to (`%LOCALAPPDATA%\copilot\pkg\<platform>\<version>` on Windows) unless `COPILOT_AUTO_UPDATE=false`, so the copy 1.0.98 answered `--version` with 1.0.103: the variable goes to every Copilot call, `--version` included.

### What keeps the version

- **No auto-update.** A Claude session on the copy gets `DISABLE_AUTOUPDATER=1` (`claudeEnv`), so it never updates the user's own install; the daemon the copy starts keeps the variable for its sessions. OpenCode gets `OPENCODE_DISABLE_AUTOUPDATE=1` and Copilot `--no-auto-update` with `COPILOT_AUTO_UPDATE=false` on whichever binary they run.
- **The daemon.** A Claude session runs on its folder's daemon's version, not on the client's. Before each launch, relay and resume, `DaemonRefresh.prepare` asks `claude daemon status` for the daemon's `version:` (`Agent.daemonVersion`; with no daemon CLI 2.1.308 prints `not running` and exits with code 1, which is "none runs", not an error — BTN-333) and compares it with the pin (`Agent.pinned`): a daemon on another version is stopped (`claude daemon stop --any`) once no session of the folder is live — the same rule as for a shared key, so a waiting or resting session is never stopped for it (invariant 1) — and the launch then starts a new daemon from the copy. Until then the folder is in `EvenKeelState.cliVersions` with its account and the `agent.daemonVersion` notice, and its sessions run on the daemon's version. A newer `claude --bg` or `claude agents` in the same folder replaces a pinned daemon with its own version again (BTN-248), so the pin holds only while nothing else starts background sessions there on another version.
- **What the pin does not cover.** The server may refuse an old version (`tengu_version_config.minVersion`) or force a newer one (`tengu_max_version_config`); model aliases are resolved by the binary, so an old version may not know a new model's alias, and Codex lists models by the client's version (models carry a minimal client version): then the checked version is raised. Limits come from the server, and transcripts the user's own sessions write on a newer version are read as before.

## The newest release (BTN-1539, `src/agent/latest.ts`)

A third value of `cli.<provider>`, `latest` ("Latest" on the page): Even Keel's own copy of the agent's newest release, for a place where a person cannot install the CLI. The page offers it only where `installableClis` (`src/agent/installable.ts`) leaves the provider out: in a container (`inContainer`) nobody, since the service user writes nothing outside its volumes; elsewhere Claude Code is always installable (its installer writes into the home folder) and an npm CLI only when npm's global folder (`npm_config_prefix`, else the one of the running node) or the nearest existing folder above it is writable. On Windows `accessSync(W_OK)` on a folder is nearly always true, so a Windows host practically never sees Latest. The flag goes to the page as `CliCopyView.installable`; without it the copy window has no `npm install -g`, its main button is **Switch to checked** with **Download the latest** beside it, and the CLI version choice gets the third radio. A provider already on `latest` keeps the radio wherever it runs.

- **The copy.** `LatestCli` keeps whole version folders in `state/cli/<agent>-latest/<version>`, beside the checked copy's `state/cli/<agent>`, each fetched and verified by an inner `PinnedCli` exactly as that version's checked copy would be (the same `fetch` of the agent's `release.ts`). The version sessions run on is the newest whole folder on disk; nothing else is stored. The newest version comes from the agent's `latest` (`AgentAdapter.latest`): Claude Code's `…/claude-code-releases/latest`, the npm `latest` tag of `@openai/codex`, `opencode-ai` and `@github/copilot` (`npmLatest`).
- **Updating.** Each version sweep (`wireCliVersions`, every 15 minutes and on `cli/check`) calls `cli.update()`, which on `latest` with a ready copy runs `LatestCli.ensure()` in the background: a newer release downloads beside the old one, which stays ready and is what sessions run on until the new folder is whole; then the next call of the CLI takes it, and the sweep removes the old folder. `prune` is skipped while a download runs, or the old version's sweep would remove the new folder. A failed registry read or download with a copy in place only logs; without one it is the `failed` status and `onCliFailure`, the same `ConfigStore.fallBackCli` to `system` as Checked's.
- **Consent and the chain.** Choosing Latest (`cli/download` with `source: 'latest'`, `copies().download`) is consent to each newer release too; the provider joins `cli.downloaded` as on Checked, so a missing copy fetches by itself at the start and on `blocked`, and a machine follows the hub's consent the same way, asking the registry itself (its version may differ from the hub's for a sweep). The chain waits on `agent.copyMissing` with `latest: true` while no copy is ready; a newer release downloading beside a ready copy is no wait (`LatestCli.downloading` counts only the first download).
- **Claude.** `Agent.pinned` gives the latest copy's version, so `DaemonRefresh` moves a folder's daemon to a new release once none of its sessions is live, as for a raised checked version. The Agent SDK is bound to the checked version, so a Claude account on `latest` runs on `--bg` (`viaSdk` false) and `execution.claude: sdk` still needs `cli.claude: checked` (`config.executionCli`).
- **`EVEN_KEEL_<AGENT>_BIN`** beats `latest` as it beats Checked.
