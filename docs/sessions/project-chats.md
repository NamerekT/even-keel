# Sessions: project chats

A project chat (BTN-1229, the server side BTN-1230) is a session without a task that the user starts from the page to talk about the project. It runs like a hand session, not like a chain one; the chain never sees it. The page's chat list, its window and the handover to a new session are BTN-1231…1234.

## A chat and its session

- **The record.** `ProjectChats.create` (`src/chats/chats.ts`) makes a chat of a project with the user's choice: the account folder, the model and the effort. They never change: another choice is another chat, so its prompt cache stays the same. The choice becomes the project's offer for the next chat (`chat_choices`). A chat's id is `chat-<12 hex>`; it is also the name its sessions start under, so the session monitor finds them as it finds a task's (`sessionsByTask` takes a name `isChatName` gives) and the views carry it as `task`.
- **No process before the first message.** A created chat holds no session. The user's first message (`ProjectChats.send`) launches it through the machine of the project's folder; each later one goes into the same session.
- **The machine.** The "New session" window lets the user pick it (BTN-1614) among the project's candidates (`placesOf`, `src/chats/places.ts`): the pool's turned-on machines, the own one first; with an empty pool the own machine and every machine elsewhere with a folder of the project. Each candidate says why it cannot take a chat now: `offline` (off the link) or `noFolder`. A chat created without a machine goes where it went before: the own machine when the pool has it or is empty, else the first connected machine of the pool (`pickedOf`). `placeOf` (deps in `src/service/chats.ts`) checks a machine named: outside the pool `chats.notInPool`, no folder `chats.noFolder`, off the link `chats.noMachine`; the folder is the one that machine has for the project. The chat keeps that machine (`chats.machine_id`, `ChatCard.machine`): the first message, a deferred relaunch and `renew` all go to it, so its history and `past` stay where they are, and an offline machine refuses the message (`chats.noMachine`).
- **The launch** (`MachineChats.launch`, `src/service/machine-chats.ts`) is the chain's `launchIn` with nothing of the chain: the project's main checkout as the folder, not the chain's `--settings` (a Claude chat's only one is `{"promptCacheTtl":"1h"}`, BTN-1401, `docs/sessions/cache.md`), no packages, no "Trim the tools", no handoff note. So the session has the account folder's own plugins and MCP servers and the checkout's `.claude/settings*.json` and `.mcp.json`, as a session started by hand there. The one addition is the built-in package's plugin (`agent-bridge`) alone, its current install (`Packages.chatPlugins`, `bridgePlugins` in `src/packages/launch.ts`), for its hooks: the mail mid-turn (BTN-1346) and a Claude session's inbox socket (BTN-1371); its MCP servers stay off (Copilot's `--disable-mcp-server`, Codex's per-server `enabled = false`; OpenCode takes only the plugin's `opencode/` script), and the account's own plugins stay on (`SessionStart.ownPlugins`: Codex keeps `config.toml`'s plugins; a failed plugin setup there only warns in the log and the chat goes on without it). Claude Code starts a `--plugin-dir` plugin's servers and turns them off only by `--strict-mcp-config`, which would drop the account's and the checkout's own servers too, so a Claude chat (`--bg` and SDK) gets a copy of the install without `.mcp.json` and the manifest's `mcpServers` (`ensureServerless`, `<cache>/<package>/<install>/serverless`, made once per install) as its one `--plugin-dir`, still without the chain's `--settings`: the account's own plugins stay on. `daemons.prepare` shares the common configuration into the account folder first (`src/account/share.ts`), as before any launch. The project's protection, its main branch and the agent's execution mode are the chain's. Remote Control is the account's own setting (`remoteControlAtStartup`), so a Claude chat is in the Claude app signed in to the same account when the chain's sessions are.
- **A later message** (`MachineChats.send`) goes the way a task chat's message to a live session goes, and a turn is never cut for it (BTN-1345). In order: into the live session where its agent takes one (`Agent.reply`: a live SDK session, mid-turn too); into a Claude `--bg` session's inbox socket (`toldInbox`, `docs/sessions/chat.md`, "The inbox socket"), mid-turn or between turns, unless the session waits on a question or a permission dialog or is marked hung; mid-turn, into the mailbox when the session's hooks ask for mail (`Mailbox.listens`, the row under the chat's id; from the launch or resume on, before they first ask, BTN-1430, `docs/sessions/chat.md`) — an OpenCode, Copilot or Codex chat's do, through the built-in plugin of its launch (BTN-1346), and the hook route `/mail` answers for a project chat's session as for a chain's (`isChatSession`, `src/service/hosting.ts`); the letter is delivered and marked as in a task chat (`docs/sessions/chat.md`), and one the hooks missed at the end of the turn goes on through `settleMail`, whose resume of a chat is `ProjectChats.resume`, a later message with the letter's prompt; otherwise, with the session not mid-turn, the session is stopped and resumed with it; mid-turn it is refused (`chats.busy`). Neither the agent nor the inbox is tried for a hung session. Files go into `.temp/inbox/` of the folder first (`chat.saveInbox`), and the prompt is `replyPrompt`, an answer to the session's open question included. A message while the first session still starts is refused (`chats.starting`).
- **Every call carries the whole choice.** The machine keeps nothing of a chat; the hub's record is the only one.

## Its state for the page

`ProjectChats.list`/`card` give a `ChatCard` (`src/chats/model.ts`): the title — the one the CLI wrote into the transcript (`custom-title`, `ai-title`, read by `MachineChats.title`; Claude only), until then the first message —; the CLI writes the session's launch name, the chat id, as its `custom-title` and generates no `ai-title` under it, so a `custom-title` equal to the chat id is passed over and only a rename by the user replaces the first message (BTN-1339; a kept title equal to the id from before is dropped by `keptTitleOf`), the agent, account, model and effort, the state, the context fill, the last message and whose it is (`user`, `agent`, `ask`), the time of the last event, whether the user has read it, and, archived, its successor.

The state (`stateOf`): `new` (no message yet), `starting`, `working`, `waiting` (a question, a permission dialog, a startup dialog), `answered` (the turn ended and the cache is warm), `cold` (the cache window passed; without one, five minutes after the last event), `error` (a limit or an error that is not a temporary refusal), `archived`. The active list puts the waiting chats first, then by the last event, newest first. A chat is unread while its last message is the agent's and came after the user last opened it (`chats/read`).

The page's calls are `POST /api/chats/<name>` (`src/chats/routes.ts`): `list` (the project's active chats and its last choice), `archive` (a page of 20, newest first, `words` searched in the title, the first and last message and what the user wrote; `more` says an older page follows, no total), `chat` (an archived one too), `machines` (the window's machines and `picked`, the one a chat without a machine goes to; each with its account panel: a machine elsewhere's from its mirror with the hub's limits, `null` for the own one, whose the page has live), `create` (an optional `machine`), `send` (text, answers and files in base64, up to 64 MB), `renew` (the same with the new chat's account, model and effort), `read`, `hide`.

Before the machine reports a session, a card with a recent user message shows `starting` for the usual session boot grace. In the window, sending moves the draft into the feed immediately. The chat keeps that bubble through the session ID arriving, a missing transcript and an empty first read. The recorded prompt replaces it on the first successful read that contains it. The field stays editable during upload. Mid-turn it is open where the page's mailbox of the session says it listens (`EvenKeelState.mailbox`, `SessionMail.listens`: it steers, its inbox is known or its hooks ask for mail), with the task chat's tip on Send (`t.session.chat.steers` or `mailbox`). Each mid-turn message appears immediately as a user bubble. Its clock changes to checks when the transcript contains it. A returned message shows a red mark with the reason and its contents return to the draft. A session that cannot take a mid-turn message keeps the field shut until it stops. While the session's lamp is `working`, the task chat's turn line stands over the field — the clock's pill, then the action (`docs/web/session-panel.md`, BTN-1427): `ProjectChatWindow` gives the window the chat's session view. The saved draft also keeps attachments awaiting mailbox delivery. Reopening the chat shares its pending send. A failed send prepends the original text and files to the current draft and saves the reason even if the window has closed.

## Going on in a new session

A message to a chat whose cache went cold or whose account is at its limit may go to a new chat instead (BTN-1232). The page asks (`chatRenewal` in `web/src/pages/chatRenewal.ts`): cold is the session's `coldReply` (without the session's view, the chat's state `cold`); a limit is the account's tightest window spent or the session's lamp `limit`, and it comes first. Not for a chat that works or starts, nor for one without a session. The window offers the project's last choice; at a limit, when that is the same spent account, the next open account of the chat's agent, else of any agent (`renewalChoice`). The accounts, for the limit and for the offer, are those of the chat's machine (`useChatAccounts`): a machine elsewhere's are asked for through `machines` when the chat's window opens and again when the renewal window does; there is no pick of a machine there.

The model list of the "New session" and renewal windows is still the hub's `models/list` by account key: a machine elsewhere's own catalogue is not read, so an account the hub has no folder of offers only the CLI's default.

`ProjectChats.renew` (`chats/renew`):

1. The files go into the folder's inbox and the text becomes `replyPrompt`, an open question's answers included, as for `send`.
2. The machine gives the old session's past (`MachineChats.past`: the monitor's `handoff` of the chat — its transcript path and recent feed lines); a failure leaves it out.
3. The old session is stopped (exception 12). A failed stop refuses the step and nothing changes.
4. The new chat is kept with `previous` (the old one) and `pending`, its whole first prompt (`renewPrompt`, `src/chats/prompt.ts`): a lead, the last 10 turns of the old chat taken from its feed without a model (the user's words and the agent's texts, each cut to 600 characters), the old transcript's path with "grep it, do not read it whole", then the message under `USER_MESSAGE_HEAD`, so the page shows it as the user's (BTN-1281). The old chat goes to the archive with the new one as its successor, and the new one becomes the project's last choice.
5. The new chat's session is launched with `pending`; once it is, `pending` is cleared. A failed launch clears it too and returns the error: the new chat stays, without a session, and the user's next message there starts it as any first message.

A restart between 4 and 5 loses nothing: the sweep finds an active chat with `pending` and no session and launches it with the same prompt, unless the machine already knows a session of the chat (`past`), which it then takes. An offline machine keeps it pending until the machine is back. A chat with `pending` and no session is `starting` for the page.

## The archive

- A chat goes to the archive a day after its last message or its session's last action, **in any state** — mid-turn or waiting on a question too (`ARCHIVE_AFTER_MS`). The service's sweep runs once a minute (`CHATS_SWEEP_MS`): it also keeps the title, the last message and the time of the last event, so the archive has them once the session's view is gone.
- "Hide" is the same archive; there is no delete, and the transcript stays on disk.
- On its way to the archive the session is stopped through its agent (exception 11 in `docs/chain/exceptions.md`). A failed stop refuses "Hide"; the day-old sweep archives anyway and logs it.
- An archived chat is only read: a message to it is refused (`chats.archived`); going on is a new chat. The chat a new session replaces goes to the archive with its successor (BTN-1232, exception 12).
- A restart loses nothing: the active chats are read back from the database, and their sessions are found again by name as the chain's are.

## The page

The Chats tab of the project page (BTN-1231) polls `list` every 4 s while the page is open, for its list and its badge; `archive` is asked per search and page, `create` from the "New session" window, `send` and `read` from the chat's window. A chat's window is the session's transcript window with the chat's field, without the commands menu; one without a session yet shows an empty feed. How it looks is in `docs/web/project-page.md` ("The Chats tab").

## In the stats

Tally reads each chat's session from the `chats` table and keeps it in `chat_sessions` (BTN-1233): such a session belongs to no task, even when its title names one, and `/stats` shows the chats' count and spend per project under the task table (`docs/tally.md` step 18, `docs/stats.md`).

## Not covered

Uncommitted changes a chat leaves in the main checkout hold up a chain task's merge the way a hand session's do from an editor: no guard of its own.
