# Sessions: the Agent SDK

## The Agent SDK transport (BTN-239, `src/claude/sdk/`)

A second way to run Claude sessions, beside `--bg`, chosen per account folder; the research behind it is the two sections below.

- **The choice.** The shared setting `execution.claude` (BTN-353; before it each folder's `transport` in `state/account.json`, `docs/accounts.md`): `auto` by default — an API-key folder takes `sdk` (the path Anthropic recommends for keys), a cloud folder (BTN-822, `docs/accounts.md`) too, as it pays per token (`paysPerToken`), and a subscription `bg` —, or `bg` or `sdk` for every folder (`transportOf` in `src/account/transport.ts`). /settings → Providers and models has it in the Execution column, its hint carrying what the SDK gives, that it needs the checked CLI, Anthropic's rule on SDK products and that on a subscription the SDK spends the limits faster (about 2× the five-hour window, ~1.27× the week, "Agent SDK against `--bg`, measured" below); the Accounts card only says where a folder's sessions go. It applies live to the next launch: a session keeps the transport it started on, since the adapter routes a resume, a reply and a stop by whether the SDK registry knows the session id, never by the setting. Only Claude folders have it.
- **When it is used.** `viaSdk` in `src/claude/adapter.ts`: the folder's transport is `sdk`, the CLI is Even Keel's checked copy (`cli.claude: checked`, no `EVEN_KEEL_CLAUDE_BIN`) and the SDK of that version is downloaded. The SDK talks its own CLI version's protocol, so its version is pinned to the CLI's: CLI `2.1.N` goes with SDK `0.3.N` (`sdkVersionOf`). Its copy is a `PinnedCli` in `state/cli/claude-sdk/<version>/`, downloaded with explicit CLI consent from npm by `fetchNpmPackage` (`src/agent/npm.ts`, shared with Codex) alongside the checked CLI, without the platform package: `pathToClaudeCodeExecutable` is the checked CLI. Until the copy is there, the launch goes by `--bg` and the log says so.
- **`sdk` holds the checked CLI** (BTN-610). `execution.claude: sdk` with `cli.claude: system` once let sessions go on `--bg` quietly while the page said "Agent SDK". Now the pair is a config error, `config.executionCli` (`needsCheckedCli` in `src/agent/providers.ts`, checked in `parseConfig`, so the page, `config-import` and every write share it); picking Agent SDK on /settings switches the form's CLI version to Checked and locks Yours with a tip while the form holds Agent SDK (`cliLockOf`). On /settings the CLI version is a field of the form (BTN-682): it is saved with Execution, so the service judges the pair as the form holds it, and a copy that is not there is offered for download once the save lands (the consent dialog `useCommand` opens after a `settings` save that moves a provider to `checked`); the setup wizard and the copy bands still switch at once (the version banner did too until BTN-780) (`cli/system`, `cli/checked`, `cli/download`). Before BTN-682 the version switched at once and Execution only on save, so Yours stayed shut until a new Execution was saved (BTN-638); a failed download keeps `checked` (`ConfigStore.fallBackCli`), and the "Use installed" button of a waiting copy is hidden. A stored pair moves to `checked` by DB step 21 and config v22. `auto` is not locked: on Yours it runs every folder by `--bg`.
- **The executor** (`executor.ts`). A detached node process per session runs the CLI with piped stdio and holds a named pipe (`\\.\pipe\even-keel-sdk-<uuid>`; `<tmpdir>/ek-sdk-<hex>.sock` elsewhere). It runs under Node's own type stripping, not tsx — tsx's esbuild child would hold `node_modules` — so it imports only `node:` modules and uses erasable syntax only. The protocol is JSON lines: the host's first line is `{"executor":"spawn",command,args,cwd,env}` or `{"executor":"attach"}`, the executor answers `{"executor":"hello",pid,turn}`, then every line is the CLI's stdin one way and its stdout the other; `{"executor":"exit",code}` once the CLI is gone. One host at a time, a new one replaces the old; the CLI's stdin is never ended. Without a host the CLI's output is buffered: 1 MB in memory, then a spill file of up to 256 MB, and the next host gets it. It exits when no first host came within 60 s, or 10 minutes after the CLI ended with no host back. Its log and spill file are `state/claude-sdk/executors/<session id>-<start>.log` and `.spill.jsonl`. A stop kills its process tree (`killTree`) and waits up to 30 s for the executor and the CLI to die (`claude.stillRunning` otherwise).
- **The host** (`host.ts`, `SdkSessions`). A `query()` whose `spawnClaudeCodeProcess` returns an `ExecutorProcess` (`pipe.ts`), a socket to the executor; the input is an inbox that never ends, so the CLI waits for the next message. The options: `systemPrompt` is the `claude_code` preset, the CLI's own system prompt as a `--bg` session gets it (nothing is appended to it: the CLI reads a lone `AGENTS.md` by itself, BTN-833), `permissionMode` the chain's `auto`, the session's name as `title`, its model, `--settings`, the packages' MCP servers behind the gateway with `strictMcpConfig`, and its plugins as `local` plugins. `canUseTool` keeps an `AskUserQuestion` call pending as the session's question. Any other tool the CLI wants approved (BTN-303) is refused while the chain is unattended (`AgentOptions.unattended`, read at each call, so the switch applies live; `NO_APPROVAL` is the message); otherwise it waits as a question too, built by `permissionAsk` (`src/sessions/permission.ts`, shared with the `--bg` path, "Permission dialogs" above) in the page's language: "Allow the session to run <tool>?" with "Allow" (the command, or the input as JSON, in its preview) and "Deny", so the page's question panel, the chat and a tracker comment answer it as any question, and it is the turn's `waiting` state, not `waitingFor`. An approval that already waits when unattended mode goes on is refused at the next poll of the session's account (`refuseApprovals` in `sessions()`, every 3 s), or the chain would stand on it all night. After a restart of the service the host connects again on the first poll of the session (`connected`): a new `query()` attaches to the same executor, the CLI answers the SDK's `initialize` and asks the question it is still blocked on again, so the page has it back. The live view is an `AgentEntry` of kind `sdk`: alive while the executor's pid lives and its pipe answers (a reused pid does not), busy/idle from the SDK's `assistant` and `result` messages and the executor's `hello`, `waiting` with the question while a call is pending.
- **A reply goes into the live CLI** (`Agent.reply`, tried first by `resumeWith` in `src/service.ts`): all answers and no words of the user's own — the pending call is allowed with `updatedInput.answers`, a real `tool_result`; words or files with an open question — the call is refused with the whole reply as its message; no question — a new user message on stdin, which a busy session takes in the same turn. A pending tool approval is answered by `permissionMove`: the first option alone allows the call with its own input, any words that came with it following as the next message; "Deny" alone refuses it with "The user denied this call"; words of the user's own without "Allow" refuse it with the whole reply. Checked live from a terminal (2026-10-22, CLI 2.1.306, Haiku): such a message mid-turn is written as a `queue-operation` `enqueue`, then after the running tool's result an `attachment` `queued_command` and a `remove`, and the model answered it in that turn — the same shape the feed already reads for Remote Control. So a live SDK entry `steers` (`sdkEntryOf`), and a chat message to it while it works goes this way at once (`steer` in `answerSession`, `src/service.ts`, BTN-291), not into the mailbox; the page keeps its chat open mid-turn (`SessionMail.steers`). A reply to a session whose executor is gone is a new executor with `resume` and the same session id.
- **Remote Control** goes through `enableRemoteControl(true, name, { keepSessionOnExit: true, reattachSessionId })` while the folder starts sessions with it (`remoteControlAtStartup` in its `settings.json`, `remoteAtStartup`), the `cse_…` id kept in the record so a resume returns to the same chat on claude.ai; with no answer in 15 s the session runs without it. The method is not in the SDK's types (only in `sdk.mjs`), so it is optional in `src/claude/sdk/types.ts`. The `bridge` module stays unused (BTN-136).
- **The registry** (`registry.ts`): `state/claude-sdk/sessions/<session id>.json` with the name, folder, account, start, executor and CLI pids, pipe, model, Remote Control id and `stopped`, stamped with `SCHEMA_VERSION`. SDK sessions are not jobs of the daemon: `claude agents` and the desktop app do not list them; the transcript is the usual file, so the feed, Tally and handoffs read it as before.
- **Limits** (BTN-290): the `/usage` poll stays, and between its polls each `rate_limit_event` of the session (the CLI sends one per response) puts its windows over the newest that is known of the account (`limitsOfRateLimitInfo`, `LimitsWatcher.report`, source `sdk`, "from an SDK session" on the page). The utilization is a share and the reset in seconds; `unifiedWindows` holds both the five-hour and the weekly window, though it is not in `sdk.d.ts` — seen live on CLI 2.1.308 with SDK 0.3.308 (`{"status":"allowed_warning","rateLimitType":"seven_day","utilization":0.45,…,"unifiedWindows":{"five_hour":{"utilization":0.6,"resetsAt":…},"seven_day":{…}}}`). Without it only the documented `rateLimitType` window is read, and a `rejected` one without utilization counts as spent; the models' (`seven_day_opus`, `seven_day_sonnet`) and overage windows are not shown.
- **Checked live from the service** (BTN-292, 2026-10-22, Windows, CLI 2.1.308, SDK 0.3.308, Haiku, a subscription folder with `remoteControlAtStartup`). The first launch after the switch logged `the SDK 0.3.308 is not downloaded yet`, fetched it within a second and ran on `--bg`; the next ones ran through the SDK. `Restart-Service EvenKeel` while a session waited on its `AskUserQuestion`: the executor and the CLI lived on (their parent, the old node, gone), a new host attached 2 s after the start, the page had the question back, and the answer from the chat window went into the live CLI (`the reply went into the live SDK session … (answer)`, no `--resume`). Three restarts in one turn of a 4-minute command, the last a 28 s stop over the command's end: the executor kept the CLI, the turn wrote the command's result and two more steps with no host, then ran to its end under the host that attached, merged its branch, and the cleanup after Done stopped the session with no process left. Each session got its Remote Control id (`bridge`). Not run yet: an answer from the phone and the reattach after a resume (BTN-296); the chain against `--bg` is "Agent SDK against `--bg`, measured" below.

## Agent SDK and API keys (BTN-136, research)

Before BTN-239: a check of whether sessions could run through the Agent SDK (`@anthropic-ai/claude-agent-sdk`) or on an API key and survive a restart of the service. Checked live on 2026-10-17 with SDK 0.3.302 (it bundles CLI 2.1.302 in `@anthropic-ai/claude-agent-sdk-<os>-<arch>`, so pinning the SDK pins the CLI unless `pathToClaudeCodeExecutable` is set), the standalone CLI 2.1.302, Haiku, the sandbox repository, a Pro subscription; the scripts were throwaway.

| | CLI `--bg`, subscription (today) | CLI `--bg`, API key | SDK, subscription | SDK, API key |
| --- | --- | --- | --- | --- |
| Survives a service restart | yes, the daemon owns the sessions | yes, the same daemon | only through a detached executor or `resume` (below) | as SDK on a subscription |
| A pending question | only in `jobs/<id>/state.json`, lost on `claude stop` | as on a subscription | the `canUseTool` callback; the call is in the transcript at once | as SDK on a subscription |
| Remote Control | yes | no (needs a claude.ai sign-in) | yes, `enableRemoteControl` (undocumented) | no |
| Limits | 5h/7d windows, `/usage` | the organization's budget and rate limits, no windows | 5h/7d windows | the organization's |
| Fragility | undocumented `sessions/`, `jobs/`, `agents --json` | as on a subscription | documented API, except `enableRemoteControl`; an executor of our own to maintain | as SDK on a subscription |
| Anthropic's rules | the user signs in to the unmodified binary: allowed | allowed | open source only: SDK products "should use API key authentication" | allowed, the recommended path |

The SDK on an API key was not run (the key was spent only on the CLI check); its rows follow from the SDK runs on a subscription and the CLI run on the key.

- **The host dies with the default spawn.** The CLI is a child of the host's node and reads stdin; a non-detached child of node sits in libuv's kill-on-close job object, so a `TerminateProcess` of node (what the service host's `Process.Kill()` does) kills it at once. Its `sessions/<pid>.json` stays with a dead pid and `status: waiting`.
- **`resume` after the host died.** In an SDK session the `AskUserQuestion` call reaches the transcript at once, unlike `--bg`. `query({ resume })` keeps the whole history with the call; the call gets a synthetic `tool_result` with `is_error` — `[Tool call interrupted: the session ended before this call's result was recorded, so its outcome is unknown. …]` — and an assistant `No response requested.`; the answer comes as the next prompt, and the session took it. With a warm cache it cost 18.9k tokens read and ~230 written ($0.00024 on Haiku); with a cold one the whole context is written again (~19k tokens here, at the 1 h write price), not measured. Mid-turn: a running Bash command outlived the CLI and finished (its file appeared 20 s later), and after `resume` the model ran it again — a side effect may happen twice.
- **A detached executor.** `spawnClaudeCodeProcess` returns any `SpawnedProcess` (`stdin`, `stdout`, `kill`, `exit`). A separate node process started with `detached: true` spawns the CLI and pipes its stdio to a named pipe; the host's `SpawnedProcess` is a socket to it. The executor must not end the CLI's stdin when the host disconnects (a deliberate close sends its own message) and buffers the CLI's stdout until the next host. The host was killed while a question was pending: the executor and the CLI went on. A new `query()` whose spawn function attaches to the same pipe sends `initialize`, the running CLI answers it with the request it is still blocked on, and the SDK redelivers the question to `canUseTool` (`reinitialize()` documents this); the answer went in as a proper `tool_result` and the turn finished in place, without `resume`. A `detached` child survives a `TerminateProcess` of its parent and a non-detached one does not (checked); the executor was not started by the real service, so its surviving a `Restart-Service EvenKeel` rests on that and on the CLI daemon, a detached grandchild of the service's node, which does survive one.
- **Remote Control.** `enableRemoteControl(enabled, name?, { reattachSessionId, keepSessionOnExit })` on the `query()` object sends the CLI a `remote_control` control request and returns `{ session_url, bridge_session_id: "cse_…" }`; `initializationResult()` reports `remote_control_available`. The CLI turns `keep_session_on_exit` into `neverArchive`. Checked from the phone: an answer from the claude.ai app aborts the host's pending `canUseTool` (its `signal`) and the session goes on with it; with the host dead and the CLI in the executor the answer from the phone finished the turn and the next host got the buffered output; after the CLI exited (`keepSessionOnExit: true`), `resume` plus `enableRemoteControl(true, name, { reattachSessionId: "cse_…" })` in a new CLI came back into the same chat with the same `bridge_session_id`, and a new question was answered there. The `@anthropic-ai/claude-agent-sdk/bridge` module (`@alpha`) wants the account's OAuth token from the host — not to be used: Anthropic forbids third parties to collect Claude.ai tokens.
- **The CLI on an API key.** `claude --bg --model haiku` with `ANTHROPIC_API_KEY` in its environment, in a fresh account folder (its `.claude.json` with `hasCompletedOnboarding`, the folder trusted and the key pre-approved in `customApiKeyResponses.approved` by its last 20 characters, otherwise an interactive session asks), started a daemon and the session answered. The key is not in the job's `providerEnv` (only `CLAUDE_CONFIG_DIR`): it reached the session only because that `claude --bg` started the daemon, and sessions inherit the daemon's environment, respawned ones too; through a running daemon it would not arrive (BTN-129, `docs/accounts.md`). So for real use the key belongs in the account folder's `settings.json` `env`, which every session reads at its start, or an `apiKeyHelper`. The cache was written with a 5-minute lifetime (a subscription writes 1 h). A key not scoped to a workspace fails with `400 … must include the anthropic-workspace-id header`. `--max-budget-usd` works only with `--print`. Spent on the key: $0 (the 400) and ~$0.004 (28.5k tokens written, by the SDK's prices).

## Agent SDK against `--bg` (BTN-238, research)

How much steadier sessions through the Agent SDK would be than the `--bg` path, for the implementation (BTN-239, whose description holds the scope). Done on 2026-10-22 from the traps, `git log` and SDK 0.3.250–0.3.307; the live parts BTN-136 left unrun need the SDK transport inside the service and moved to BTN-239.

**The traps.** Of the CLAUDE.md "Traps", this file and `docs/unverified.md`, the ones the transport touches:

| Trap | With the SDK |
| --- | --- |
| `claude agents --json` has no `pid`/`status`, `state` lies; liveness from `sessions/<pid>.json` | gone: the host owns the CLI process and reads the turn's end from `result`; a registry of our own instead, as for Codex |
| a pending question only in `jobs/<id>/state.json`, lost on `claude stop` | gone: `canUseTool` gets it at once (`--bg` has had it in the transcript since 2.1.302 too) |
| an answer is `claude stop` + `--resume`: ~5 s floor, the synthetic "Tool call interrupted" | gone: the answer is the `canUseTool` result, a reply after a text turn a line into the live CLI's stdin (`streamInput`) |
| `--bg --resume` with flags starts a copy (`own-options`) | gone: `resume` keeps the session id (seen in BTN-136) |
| the respawned job shows a fresh session id for under a second; `steadyJobs`, `ResumeHolds`, `resumedAs` | gone: no daemon respawns anything |
| a prompt starting with a dash kills the job before init | gone: the prompt goes as JSON on stdin |
| `claude stop`/`agents` from a terminal do not reach the service's daemon | gone, and so does any terminal control: the user stops a chain session through Even Keel or by its pid, as today |
| the daemon's environment frozen at its start (BTN-129), the daemon restart on a shared config change (BTN-31) | gone: every launch is a new process with the environment the host gives it |
| the daemon's version: self-restart on upgrade, a terminal `--bg` replacing a pinned daemon, `DaemonRefresh` (BTN-248, BTN-250) | gone: each launch runs the binary named in `pathToClaudeCodeExecutable` |
| a startup dialog visible only in the job file | gone, presumably: stream-json mode shows no dialogs; not run |
| `state: done` given to a turn that ended on a plain-text question | gone: the host sees `result` and the CLI waiting on stdin |
| from 2.1.306 a background session's file tools are refused in a main checkout (EKR-16) | unknown: whether it is `--bg` only was not checked; chain sessions run in linked worktrees anyway |
| short CLI calls killed mid-renewal burn the refresh token (EKR-15) | partly: `claude agents` goes; `auth status`, `/usage`, `/context` stay, though `getContextUsage()` and the per-turn `rate_limit_event` could replace the last two (the SDK's own `/usage` call is marked experimental) |
| several `.claude.json` keys per folder, the desktop app's profile, plugin `version` bumps, `--strict-mcp-config`/`--plugin-dir`, `settings.local.json` of the main checkout, the failed-MCP cache (BTN-159), `bash.exe` outliving a stopped session (BTN-202), `/usage` 429 | stay: they are the CLI's, and the SDK runs the same CLI (the flags become `Options`) |

**How often `--bg` broke Even Keel.** Of 638 commits from 2026-09-01 to 2026-10-21, 23 fixed behaviour of the session transport (read from subjects and bodies, features left out). 17 would not have happened with the SDK: the daemon's config and environment (`e997d2c2`, `07be72a0`), liveness from `agents --json` (`40f66f47`, `009d3e1f`, part of `0c44af7e`), a terminal `claude stop` (`97eca325`), startup dialogs in job files (`3b04bdcd`, `49ce3bb5`), the question in the job file (`40293a78`), and eight about stop + resume: the copy under a new id (`c6f97863` and its test `7288bbdf`), flags starting a copy (`8e08a70a`), the respawn's fresh id (`f36a9c2e`), holds and steady jobs (`90f4419b`), the feed during delivery (`be25d75b`), the dash (`6b0583fd`), the latency (`d66532d2`). 4 partly (`c9230060` the MCP approval hang, `2bb62f3f` the delivery line, `0ec868e4` EKR-15, `57baf2d7` EKR-16), 2 stay (`55cad0ca` BTN-159, `9e5f0f20` BTN-202). Two came in September, 21 in October, 18 of them between 10 and 18 October, when resumes after a question or a limit and replies from the chat were built: the reply path is where `--bg` cost most. Since BTN-250 and BTN-253 a new CLI reaches the chain only after the CLI check, so the rate after 10-21 says little yet.

**What comes instead.**

- **An executor of our own** per session (BTN-136's `executor.mjs`): a detached node process holding the CLI and a named pipe (a Unix socket elsewhere). Ours to get right: the reattach handshake, the stdout buffer while no host is attached (bounded, spilled to a file), an executor whose CLI exited and whose host never came back (it must exit), the registry that maps a session to its pipe, killing the CLI's process tree. If the executor dies the CLI loses its stdin and ends; the session goes on by `resume` from the transcript, with the risk BTN-136 saw mid-turn — a command run twice. Survival of a service restart rests on mechanics, not a run: the host's `Process.Kill()` (`service/EvenKeelService.cs`) is a `TerminateProcess` of node, which kills only children in libuv's job object, and a `detached` child is not in it (checked in BTN-136); on Linux `KillMode=process` (`service/install.sh`) already leaves the daemon alive.
- **`enableRemoteControl`** is still only in `sdk.mjs`, not in `sdk.d.ts` (0.3.307): it may change without notice. The `bridge` module (`@alpha`) stays out (BTN-136).
- **The release pace.** The SDK is published with every CLI build, its version mirroring the CLI's (0.3.307 bundles 2.1.307), daily. It is 0.x: the minor went 0.1 → 0.2 in January 2026 and 0.2 → 0.3 in May. From 0.3.250 to 0.3.307 the `Query` interface (29 methods) and `Options` (69 fields) lost nothing, only gained (`readMcpResource`, `reloadOutputStyles`, `updateSettings`, four options); 0.3.290 → 0.3.307 added two exported constants. So the pin of BTN-250 and the CLI check cover it, the SDK's own pin being a `package.json` line.
- **Size.** The package is ~4.7 MB; the CLI comes as an optional dependency per platform, 274–292 MB (`manifest.json` of 0.3.307). Even Keel already downloads the checked CLI (BTN-250), so with `pathToClaudeCodeExecutable` pointing at that copy the install skips the platform package (`--omit=optional`) and nothing is fetched twice; an update changes the pin of both together.
- **Visibility.** SDK sessions are not jobs of the daemon: the user's `claude agents` and the desktop app do not list them; the transcript is the same file, so the page's feed, Tally and the handoffs read it unchanged. The cache on a subscription is 1 h as with `--bg` (BTN-136 runs).

**Anthropic's rules, re-read on 2026-10-22** (`code.claude.com/docs/en/legal-and-compliance`): "Developers building products or services that interact with Claude's capabilities, including those using the Agent SDK, should use API key authentication", and third-party developers may not "route requests through Free, Pro, or Max plan credentials on behalf of their users"; while signing in "to the unmodified Claude Code binary with their own Claude subscription" is expressly not restricted. So `--bg` on the user's subscription is the allowed path, and the SDK on a subscription stays what the user decided after BTN-136: the open source build only, off by default in a paid one. The page also has a section on offering Claude Code in products (whether it is new since BTN-136 is not known) (unmodified binary, each end user on their own credentials, under the Commercial Terms).

**Conclusion: keep both transports, `--bg` the default.** The SDK removes most of what broke (17 of 23 fixes) and the reply path's restart, but `--bg` is the path the rules name as allowed on a subscription, which is how nearly every user runs; its traps are paid for and now gated by the CLI check; and the SDK brings an executor whose failures are ours, unproven under the service. BTN-239 builds the SDK as a second transport chosen per account folder, the default for API-key accounts (the path Anthropic recommends there) and opt-in on a subscription, with the live checks of this task as its acceptance: `Restart-Service EvenKeel` with a pending question and mid-turn, then a night of the TSK chain on the SDK against the same set on `--bg`. Dropping `--bg` is decided only after that night.

### Agent SDK against `--bg`, measured (BTN-286, BTN-388)

The night became a run of 2026-10-28…11-01: four subscription folders on `execution.claude: sdk` (~$275 of work at API prices), compared with the tasks on `--bg` before it. The project even-keel, tasks whose first session started after 10-20, the transport read from the entrypoint of the task's sessions (`sdk-ts` against `cli`); Tally (`audit_sessions`, `stuck_spans`, `tasks`, `message_costs`, `limit_snapshots`) and the service log.

| | `--bg` | SDK |
| --- | --- | --- |
| tasks | 155 | 86 |
| sessions per task | 1.23 | 1.28 |
| "New session" by hand (`restart`) | 3 | 1 |
| limit handoffs (`relay`) | 10 (6%) | 9 (10%) |
| context handoffs (`checkpoint`) | 6 | 12 (not comparable: the auto-compact window changed on 10-28) |
| pauses of the BTN chain | 3, none from the Claude transport | 0 |

- **Steadiness.** No SDK errors in the log; the `--bg` daemon had `agents --json` and `daemon status` timeouts. The user recalls no Resume by hand and no session lost to a service restart; Remote Control on the SDK was checked on 10-30…10-31 (`docs/verified.md`). The SDK is no less steady than `--bg`, but the difference is too small to mark it steadier on the page.
- **Limits.** Dollars at API prices per 1% of a window, only windows where Opus is ≥ 90% of the cost. Five-hour windows with SDK sessions only: 0.201–0.206 $/% (11 windows on three folders, one at 0.146); with `--bg` or hand sessions only: 0.38–0.42 $/% on every folder — exactly 2×. Mixed windows add up (a window of $14 SDK and $13.5 by hand predicts 104%, it was 100%). Full weeks on `--bg` and by hand: $302–309 per 100% on every folder (3.02–3.09 $/%); the current weeks, 71–81% SDK, give ~2.42 $/% for the SDK, ~1.27× faster — an extrapolation from the mixed share, the weeks not over. Spending elsewhere (the desktop app) would scatter the numbers rather than give one 0.20 on three folders, and Tally losing SDK spend would show 2× on the week too.
- **So.** On the SDK a five-hour window ends after ~$20 of work instead of ~$41, and a full five-hour window is 8% of the week instead of 13%; the run overpaid ~24 points of one folder's week, spread over four. An earlier single pair on 10-25 (CLI 2.1.310, Sonnet, a Pro folder, the same load in the TUI and in `claude -p`) gave ~1.8×; `CLAUDE_CODE_ENTRYPOINT=cli` does not change the `sdk-cli` entrypoint of `-p`. Upstream: `anthropics/claude-code#97074`, headless sessions spending the five-hour window ~1.7–1.8× faster, open on 11-01 with reproductions up to 10-30 and no answer from Anthropic. `--bg` sessions write the entrypoint `cli`, as the TUI does, so `auto` on a subscription is not hit; the user put Claude back on `--bg` on 11-01. On an API key there are no windows, so no penalty.
