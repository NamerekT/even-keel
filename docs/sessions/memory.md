# The project memory

Part of [`docs/sessions.md`](../sessions.md).

## The memory server (BTN-1029)

The project memory is the files of the project's memory folder, `~/.claude-memory/<project>` (`sharedMemory`, `docs/accounts.md`), a working copy of the project's memory repository ("The hub's repositories" below). A Claude chain session works it as the CLI's own file memory, like a session started by hand; every other agent, which has no file memory of Claude's kind, through Even Keel's `memory` MCP server, on the hub and on a machine (BTN-137). The server works on the files of the hub's folder. Until BTN-1029 the memory was rows of `memory_records` mirrored into that folder; from BTN-1029 to BTN-1647 every chain session, Claude's too, had it only through the server; BTN-1646 moved it into git, and the table is no longer written.

- **Where the server comes from.** The built-in plugin `agent-bridge` brings it in its `.mcp.json` (`http://127.0.0.1:4748/memory`), so every project's set has it; it is not in the `tasks` plugin, since a project may have no tasks server. A session reaches it like any package server, through the MCP gateway (`docs/packages.md`), with `?task=<task>` on its address so that what it writes carries the task.
- **Who answers.** Only the hub's gateway (`McpGateway`, `isMemoryUrl`): a machine publishes no route of its own and relays the call to the hub over the link, as `hub.servers()` lists the memory routes among the hub-owned ones (`Packages.hubServers`, `docs/machines.md`). A machine's gateway asked directly answers 404.
- **What a session gets** (BTN-1647). Which way an agent goes is `readsFileMemory` (`src/memory/mcp.ts`): Claude Code alone.
  - **A Claude session** gets the folder as `autoMemoryDirectory` in its `--settings` (`chainSettings`, `src/tools/panel.ts`), whatever the "Trim the tools" switch: the CLI loads its `MEMORY.md`, brings up the records it finds relevant and writes new ones as files, which the folder's sync commits (`SETTLE_MS` after the edit). The folder is `sharedMemory` of the machine's own global account folder: the hub's on the hub, the machine's on a machine, which BTN-1648 makes a working copy too. It gets neither the memory server (`Packages.startOf` leaves it out of `--mcp-config`, the plugin with its hooks stays; `--strict-mcp-config` keeps the plugin's own `.mcp.json` off) nor the index in the prompt.
  - **Any other agent** (Codex, OpenCode, Copilot) gets the server and, in the prompt, its tools and the index of the hub folder's records (`name — description` from each file's frontmatter, `MemoryHub.index`; `withMemory`, `PROMPTS.memory`, `memoryEmpty` when there are none). The hub's `wireBriefed.prepare` writes that text into the brief's `memory`, beside its `prompt`, since the hub does not know which agent the machine starts; the machine's `launchBriefs.apply` adds it after the brief for an agent without file memory, at a launch and a handoff alike. A project whose set has no server gives no `memory` either.

## Tools

- `memory_list` — the index with each record's version.
- `memory_read(names)` — whole records with their versions.
- `memory_write(name, description, type, body, version?, distinct?)` — without `version` a new record, with the version `memory_read` gave a change of it. The type is the CLI's: `user`, `feedback`, `project`, `reference`.
- `memory_delete(name, version)`.

A record is a `.md` file of the folder (frontmatter `name`, `description`, `metadata.type`, then the body; `MEMORY.md` is the index, never a record); of two files with one `name` the first by file name counts. The tools read and write the files (`src/memory/files.ts`), and a call that wrote is committed and pushed at once, with no `SETTLE_MS` wait (`MemoryHub.within`): a write keeps the record's file, a new record gets `<name>.md` (`-2`, `-3` when taken), and its line in `MEMORY.md` gets the description; a delete removes the file and its line. The person's own lines and headings of `MEMORY.md` stay.

**A write carries the version the session read**, as the built-in tracker's edit does (`builtin/edit`). A record's version is a number drawn from its file's text (the first 32 bits of its SHA-256, `textVersion`), so any change of the file — a session's, a person's in the editor, another machine's brought by a sync — is a new version. The check of the version and the write run as one synchronous step between two syncs of the working copy (`MemoryHub.within`, `MemorySync.edit`), so two machines writing the same record at once never both win, and a sync follows every write. The refused one gets the record's current text and version in the answer of its own call, applies its change to it and writes again; nobody else is told and no other session is written to. A change of another record passes; a new record never conflicts, besides one under the name of a live record (refused with that record). A deleted record is gone from the folder: a write or delete with a version it had is refused with "there is no record".

**A new record close to an existing one** (two words of name and description in common, half of the shorter one's, `similarRecords`) is refused with the list of the close ones, so the session updates the old record instead of growing the index; `distinct: true` writes it anyway.

Free-text lines of the hub's `MEMORY.md` that are no record's do not reach chain sessions: the prompt indexes only records.

## The hub's repositories (BTN-1646)

`MemoryHub` (`src/memory/git/hub.ts`, wired in `src/service/account-packages.ts`) keeps the hub's side:

- **A bare repository per project**, `state/even-keel/memory/<project id>.git` (`memoryDirOf`, `docs/storage.md`): named by the project's GUID, never its key or folder. It is made with `git init --bare` as `<id>.git.new` and renamed, so a half-made one never stands. The service owns it, as it owns the rest of the folder.
- **The hub's memory folders are its working copies.** Each project's folder on the hub (`folders()`: `sharedMemory` of its `repo` in the global account folder) gets a `MemorySync` with the project's repository as its remote (next section). The copies follow the projects: `apply()` runs at the service's start and at every change of the settings, starts the copies of new folders and stops those of folders gone. A removed project's repository stays. Two projects whose folders are one folder (the same real path, `pathKey`) — one working copy, the first project's: the log says once `… gets no working copy there`, and the other's tools write into the same files.
- **The transfer** (`transferRecords`, `src/memory/git/transfer.ts`): before a project's first working copy starts, its live rows of `memory_records` are written into its folder as files, `MEMORY.md` is tidied (`reindex`) and `.gitattributes` laid, so the folder's first sync commits them all in one commit beside the files already there. The folder's own files win, as a hand edit won in the old mirror: a record whose name a file carries is left out, and so is one whose last file holds another record now; in a folder bearing the old mirror's `.even-keel-memory` mark of the project, a record whose file is gone was removed by a person and stays removed. It runs once per project (`memory.transferred` in `service_state`); a start that dies before the mark writes the same files again and skips what is there.
- **A move to another host**: `state/even-keel` carries `memory/` (the backup copies it too). A repository that is missing is made anew (BTN-1674): from the project's branch of the mirror when one is set and has it (`memory: <id> has a new repository …, its history taken from the mirror`), else empty. The working copies' sync then pushes their whole history into it as it is, with its hashes; an empty copy commits nothing into an empty repository, so no root commit of its own makes the others rebase onto it. The transfer is not repeated, since its mark moved with the database.
- **The memory tools** work in the project's first folder between its syncs (`within`); without a working copy (git failed for it) they work in the folder directly.

## The mirror (BTN-1649)

So that the memory outlives the hub, `RemoteMirror` (`src/memory/git/remote-mirror.ts`, built by `MemoryHub`) copies the hub's repositories to one remote repository, the setting `memoryMirror` (`docs/settings.md`; `null` — no mirror, the default).

- **One repository, a branch per project.** A project's `main` goes into the branch `refs/heads/<project id>`, named by its GUID like its repository on the hub; the mirror's own `main` is never written. One remote to make and to sign in to, whatever the number of projects.
- **When.** After every successful push of a working copy into the project's repository (`MemorySync`'s `pushed` dependency, `MemoryHub.pushed`), and for every project at the first `apply()` (the service's start) and at every new address. A push into the hub's repository that does not go through the hub's own working copy — a machine's, BTN-1648 — must call `MemoryHub.pushed(project)` too. Pushes of one project run one at a time and the calls meanwhile share the next; no session and no sync waits for them.
- **Never forced.** A branch with commits the hub's repository lacks (another hub pushed there, a hand commit, a hub that lost its repository before BTN-1674) is left as it is with one log line; the mirror follows the hub only forward. While a project's branch is left so, the state's `memoryMirror` is the notice `memory.mirrorBehind` (the projects and the address, a button to the setting) instead of the privacy one; a push that goes through again, or a new address, clears it.
- **Failure.** A failed push is logged once per distinct failure (`memory: <id> cannot push to the mirror, tried again at its next push: …`) and `memory: <id> reached the mirror again` when one goes through; the next push carries what was missed, there is no timer of its own.
- **Credentials stay out of the settings.** The check refuses an address with a password in it (`config.memoryMirrorPassword`); git signs in by an SSH key or its credential helper, and the push runs with `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never`, so it fails instead of waiting for a prompt nobody answers.
- **Privacy.** Even Keel cannot tell whether the remote is private: while the setting is set the state carries `memoryMirror` (notice `memory.mirrorPrivate`), and the page shows the banner `MemoryMirrorBanner` until the user dismisses it for that address, with a button to the setting.
- **Restoring** a lost hub: with the mirror set, a missing repository is made from its branch at the start (above, "A move to another host"); by hand, clone the mirror's branch of a project into `state/even-keel/memory/<id>.git` as a bare repository (`git clone --bare --branch <id> <mirror>` and rename the branch to `main`), or point a memory folder's working copy at it.

## The memory repository (BTN-1558)

The project memory moves from the records into git: a bare repository per project and a working copy in each machine's memory folder. `MemorySync` (`src/memory/git/sync.ts`, BTN-1645) keeps one working copy in step with its bare repository and serves the hub and the machines alike; the remote is a parameter (a path or any address git takes), so the hub's repositories and the link's transport are not its concern. The hub's copies run since BTN-1646, the machines' since BTN-1648 (next section but one).

- **A sync** commits every edit of the folder in one commit (`memory: N files from <machine>`), fetches, rebases the local commits onto `origin/main` of the memory repository (`MEMORY_BRANCH`: Even Keel's own repository, never a project's `branch`), tidies the index and pushes; a push refused because another copy pushed in between is retried up to three rounds. The commits run with their own identity, no hooks and no signing (`GIT_CONFIG_*` of the call), whatever the person's git config says.
- **When.** `start()` syncs at once, which commits what a hand session wrote while Even Keel was not running, then watches the folder: a sync comes `SETTLE_MS` (30 s) after the last edit. `sync()` is the call for the link's reconnection. One sync runs at a time; calls during one share the next.
- **Without the remote** the commits stay in the working copy and the log says `cannot reach its repository`; the next try comes `RETRY_MS` (5 min) later unless an edit or a call comes first.
- **An empty folder is never a deletion.** A folder that is missing, empty or not a repository is made one (`git init`, the remote as `origin`) and takes the remote's history: an empty one gets every file, one with old files commits them and rebases them onto the remote's, so both sides' files stay. An empty folder with an empty remote commits nothing, not even `.gitattributes`; the fetch prunes, so a remote made anew is seen empty and gets the copy's history. Only a commit of a deletion in a working copy removes a record from the repository.
- **A rebase is never left unfinished.** One found stopped in the folder (the service died in the middle) is aborted first, the local commits kept; one that fails for anything but a settled conflict is aborted and the next sync tries again.
- **`MEMORY.md`** merges by union: `.gitattributes` holds `MEMORY.md merge=union` and is committed into the repository, and `.git/info/attributes` repeats it for the first rebase of a copy. After every fetch the index is tidied (`reindex`, `src/memory/git/reindex.ts`): a repeated line goes, a line about a file that is not there goes, a file without a line gets `- [name](file.md) — description` at the end, and of several lines of one file the one whose description is the file's frontmatter stays, otherwise the first. Every other line is a person's and stays. The tidy is its own commit, `memory: index from <machine>`.
- **A record changed on two machines** between their syncs stops the rebase on that file. The copy that meets it keeps its own version in the file and writes the remote's beside it as `<stem>.conflict.md` (`-2`, `-3` when taken), named so in its frontmatter and described as `MERGE into <stem>.md, then delete this file: another machine's version of it — <its description>` (`settleConflicts`, `src/memory/git/conflicts.ts`). The mark is the description, so the next session meets it wherever it reads the index: in `MEMORY.md`, which the tidy gives the side file a line in, and in the index the memory tools build from frontmatter. Merging is that session's work: it edits the record and deletes the side file, and the sync commits both. The copy that pushed first gets the other's version in the file and the same side file at its next sync; git's history keeps both versions. A change against a deletion keeps the change.
- **Keys stay out.** Before a commit every added or changed file is scanned (`findSecrets`, `src/memory/git/secrets.ts`: private key blocks, the token formats of known providers, a password inside a URL, a long random-looking value assigned to a key-like name). A file with a hit is left out of the commit, stays in the folder as it is and gets a log line once per content (`… is not committed: it looks like it holds a key (GitHub token on line 8)`); the index gets no line for a new such file, so the other copies never see a line without its file. The scanner is Even Keel's own, as Even Keel installs through npm with no outside program.

## The machines' copies (BTN-1648)

A machine elsewhere keeps its memory folders as working copies of the hub's repositories, synced by the same `MemorySync`; the hub's own machine gets nothing new, its folders are the hub's copies.

- **Transport.** git goes over the link, as the hub's MCP servers do. A machine runs `MemoryRelay` (`src/memory/git/relay.ts`), a loopback HTTP server on `127.0.0.1` and a free port, the `origin` of its copies: `http://127.0.0.1:<port>/<project id>.git`. Each smart-HTTP request of git goes to the hub as the link's post `/link/git` (`{connection, project, request}`, the body base64, `docs/machines.md`); the hub answers through `git http-backend` over `state/even-keel/memory/<id>.git` (`gitBackend`, `src/memory/git/backend.ts`, `REMOTE_USER` the machine, so a push is taken). A machine's push into a repository brings the hub's own copies of that project a sync at once and goes on to the mirror, as a push of the hub's copies does ("The mirror" above).
- **The rights.** The hub serves a project's repository only to a machine with a row of the project in `project_machines`, turned on or not, or with a folder bound to the project (below); any other gets 403 and the log one line (`hubMemoryGit`, `src/memory/git/hub-git.ts`). A project without a repository yet is 404.
- **What a machine syncs** (`machineMemoryFolders`, `src/machine/memory.ts`): each project of its pool from the brief, `~/.claude-memory/<folder>` of the project's folder there (`sharedMemory`), then each folder bound to a project. Several folders of one project (`even-keel` and `even-keel-github`) are copies of one repository. A folder neither in the pool nor bound is never touched.
- **A folder outside the pool** — a hand session's clone, a project worked on by hand on a machine that does not run its tasks — syncs only once the hub's owner binds it on the machine's page, card "Other projects' memory" (a project and the folder's path on the machine). The bindings are `memory.folders` in `service_state` (`MemoryFolders`, `src/memory/git/folders.ts`), sent to the machine in its brief (`memory`). The hub decides, not the machine: the memory is the owner's data, and a machine gives itself no access.
- **Without the link** the relay answers 503: the commits stay in the copies, which go on from the brief kept from the last run. At each reconnection (`MachineMemory.online`) every copy syncs, so the commits made meanwhile go. While the link is up the copies also fetch every `PULL_EVERY_MS` (10 min), so another machine's edits come without an edit here.
- **The size.** A request travels in one link post, so the link's `MAX_BODY_BYTES` (8 MB) holds: a push whose body is over about 6 MB (base64 grows it by a third) gets git's 413, its commits stay on the machine, and the log says so once per project. Text memory stays far below it.

The privacy of the memory on machines (open question 1 of BTN-1029) is settled by the repository per project: a machine gets only the memory of the projects of its pool and of those a folder of it is bound to, never the rest of the hub's.
