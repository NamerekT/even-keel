# Sessions: Codex

## Codex (BTN-168, `src/codex/`)

Checked on codex-cli 0.162.1. The binary: `EVEN_KEEL_CODEX_BIN`, otherwise Even Keel's own copy of the checked version while `cli.codex` is `checked` and the copy is downloaded ("The checked CLI" below), otherwise on Windows the native `codex.exe` of the global npm package `@openai/codex` (its `codex.cmd` needs a console), otherwise `codex`.

- Tool pictures (BTN-396): a `response_item` with `custom_tool_call_output` (code mode) or `function_call_output` holds an `output` array with `input_image` blocks whose `image_url` is a base64 data URL. The whole `RolloutFold` adds one `image` line per result, keyed by `call_id`, with the count; `readRolloutImage` reads that same array for `Agent.image`, without needing the original file. The name comes from a direct `view_image` call's JSON `path`, or one static `tools.view_image({path: ...})` in an `exec` wrapper; computed paths and several calls leave the name empty. JavaScript is never evaluated. The ordinary progress feed stays unchanged. Checked against the BTN-381 rollout on 2026-10-25: three results holding 1, 9 and 10 pictures.

- A turn is `codex exec --json … [resume <id>] <prompt>`, a detached process with its stdout written to a file (`state/codex/turns/<name>-<ms>.jsonl`), not a pipe: it outlives the service. Every flag goes before `resume` — the subcommand takes none of its own. The thread id is the first event (`thread.started`); the turn is over at `turn.completed`/`turn.failed`.
- Codex has no list of background sessions, so Even Keel keeps its own registry: `state/codex/sessions/<id>.json` (`sessionId`, `name`, `cwd`, `account`, `startedAt`, the `pid` and output file of the last turn, `stopped`). Between turns there is no process: the session is `idle` with `resting: true`, and liveness checks go through `isLive` (a live pid or `resting`). `stop` kills the turn's process tree (`taskkill /T /F`, elsewhere `process.kill(-pid)`) and marks the session `stopped`. If saving a newly launched or resumed turn fails even after `writeAtomic`'s Windows retries (`docs/storage.md`), the CLI adapter kills that new process tree and waits for its exit before returning the save error; it leaves no running turn hidden behind an absent or old registry entry. Checked live on Windows on 2026-10-25 with a detached helper emitting `thread.started` and spawning a child: injected save failures at launch and resume killed both processes before returning, and a later resume saved normally. Real Windows file handles denying replacement also exercised both a released lock and the 3-second retry deadline.
- Codex, Copilot and OpenCode check process creation times both when polling a running turn and immediately before killing its tree (`src/codex/process.ts`). A process created later than the timestamp in the last turn's output filename plus the adapter's launch window (60 seconds for Codex, 120 for Copilot/OpenCode) has reused the pid: the session rests, and a stop leaves that tree alive and marks the session stopped. The session's original `startedAt` is not the last turn's start after a resume. Polls on Windows share one `Get-Process` snapshot across adapters and accounts, coalescing concurrent requests and caching it for one second; stops use a fresh lookup of that pid. Linux reads `/proc/<pid>/stat` plus boot time and `getconf CLK_TCK`, macOS uses `ps -o lstart=`. An unavailable creation time or unrecognised output filename preserves the previous behaviour. Checked on Windows on 2026-10-26 with owned parent/child processes for all three adapters: a newer process was shown resting and preserved, a current resumed turn was busy and its tree was killed by stop. Linux/macOS remain in `docs/unverified.md`.
- The three adapters' stdout and stderr share a turn file. End-of-turn detection reads the last JSON object with a string `type`, skipping trailing stderr and JSON without an event type; a later real event takes precedence over an earlier terminal one. OpenCode's turn-error reader uses the same rule. Checked with terminal events followed by stderr while an owned helper process stayed alive: all three adapters showed the session resting.
- The transcript is the rollout `<CODEX_HOME>/sessions/YYYY/MM/DD/rollout-<time>-<id>.jsonl`; a resume appends to the same file. The fold (`RolloutFold`) reads `session_meta`, `turn_context` and `event_msg` lines; the context fill is `info.last_token_usage.input_tokens` of `token_count` against `model_context_window`. An `event_msg` of type `error`, or the `error` of a failed turn's `task_complete` (how 0.162.1 writes a rejected request, e.g. a model the plan does not have), is the API error, a limit when its text says so; a message that is the API's JSON answer shows its inner `error.message`. The next item of the session clears it, as it clears the checkpoint, pull request and no changes marks, except an `item_completed` with the `turn_id` of a turn whose `task_complete` is already written: a command the turn's end killed completes after it (`status: failed`, `exit_code: -1`, 0.164.0) and must not erase the limit (BTN-421). A call whose item is `status: failed` gets a failed line: a command's starts with `Exit code N`, as Claude's does, since Codex fails a whole joined command on its last exit code and the output may be an ordinary one — its first look round is `git status …; rg --files -g AGENTS.md …`, and `rg` finding no `AGENTS.md` exits 1 (BTN-233). Codex has no Remote Control: its sessions get neither a link nor the "Remote Control is off" note.
- No remote control of chain sessions (BTN-178, checked on 0.162.1 on 2026-10-18). Codex's own one is `codex remote-control` (experimental): the phone's ChatGPT app reaches threads through an app-server — the daemon or the Codex desktop app as the host. The chain's threads are not among them: a `codex exec` thread is recorded with `source = exec`, and `thread/list` without `sourceKinds` returns only interactive sources (100 `vscode` threads and no `exec` one on this machine; all 23 chain threads with `sourceKinds: ["exec"]`). A thread made through `codex app-server` (`thread/start`) gets `vscode` and would be listed. The daemon cannot be run from the service: the service is elevated, and `codex app-server daemon start` refuses ("start the Windows daemon from a non-elevated terminal; shared clients must not inherit administrator privileges"); `codex remote-control --no-daemon` does start in the service's process, but would hand the phone an administrator's process. The daemon's control socket path is capped at `SUN_LEN`, so a long `CODEX_HOME` cannot hold one. The Codex SDK (`@openai/codex-sdk` 0.163.0) runs the same `codex exec --experimental-json` with its turn piped to the caller, so a service restart would kill it; its `threadSource` is an analytics tag and leaves `source` as `exec` (BTN-193, v0.2). Moving the turns to an app-server was left for later (BTN-194): v0.1 keeps `codex exec`, and a daemon in the user's own session with Even Keel as its client is BTN-196 (v0.2) — once [openai/codex#52675](https://github.com/openai/codex/issues/52675) (a second app-server on the same `CODEX_HOME` fights the desktop app's remote control: 409s and "active writer" on an idle thread) is fixed and the Windows daemon is no longer experimental.
- Limits on a ChatGPT sign-in come first from `GET chatgpt.com/backend-api/wham/usage`, with `tokens.access_token` and `tokens.account_id` from the folder's `auth.json` (`CodexUsage` in `src/codex/usage.ts`, `pollChatGpt` in `src/limits/chatgpt.ts`). Codex and OpenCode share a five-minute poll by `chatgpt:<account id>`, including an in-flight request; a refused token may be retried with another folder's sign-in. On a 401/403 before the access token's JWT `exp`, or with no known expiry, `CodexUsage` asks Codex's app-server for `account/read` with `refreshToken: true` once, rereads `auth.json` and retries with the replacement token. Codex alone writes the tokens; no thread or turn is started. Renewal waits while the folder has any live Even Keel session, resting ones included (`isLive`); launches and resumes wait for an ongoing renewal too. A failed renewal or a refused replacement is not renewed again by subsequent polls in that service run; a successful API answer clears that hold. A refused or unreadable answer or a network failure falls back to `rate_limits` of the newest `token_count` in the account's latest rollouts; without either source there is no data, preserving the expiry or revocation reason when known. API-key folders keep the rollout path (the watcher does not poll them). Both sources map the 300-minute window to five hours, 10080 minutes to a week, 43200 minutes to a month (`RateLimits.month`; the free plan has only that one, `plan_type: "free"`, seen on 0.162.1); a window of another length is not shown. A rollout's `token_count` whose `rate_limits` have no window is passed over: 0.164.0 writes one with `limit_id: "premium"` and `primary`/`secondary` both `null` right before a turn refused by the limit, and taken it would wipe the spent window. The refusal is the `error` of `task_complete` (`codex_error_info: "usage_limit_exceeded"`), and its "try again at Nov 16th, 2026 10:12 PM" (a bare "3:46 PM" for the same day, in the machine's zone) is the limit's reset (`resetTimeOf`), before any window says so. The time is formatted from the server's `resets_at` with `%-I:%M %p`, the seconds cut off: a bare time is the same local date as the refusal, and a passed one is the rounding of the current minute, not tomorrow (EKR-34: a session started at 12:55:06 for "12:55 PM" was refused with the same time, and the chain waited a day). The bare time of Claude's "resets 1am" still rolls over to the next day. The wait ends a minute after the reset, and a refusal naming a reset over a minute gone waits 10 minutes from the refusal (`releaseAt`, `src/chain/relay.ts`). An API answer after the refusal with `rate_limit.allowed: true` and `limit_reached: false` (`RateLimits.open`) ends the wait before the named reset, for an early reset of the limits (BTN-530, `docs/chain.md`); a rollout's limits carry no such flag and are judged by their windows, as Claude's `/usage` is. A plan with a month shows it in place of the windows it lacks (`limitSpans`), the chain counts a spent month like a spent week, and a limit hit on it waits for the month's reset. Tally does not snapshot the month (`span` is `5h`/`7d` only).
- Flags: `--approve-for-me` (chain sessions run without a human: Codex's automatic reviewer approves inside its sandbox), or `--dangerously-bypass-approvals-and-sandbox` instead when the shared `execution.codex` is `bypass` (below), `-m <model>` when the run profile has a Codex model (below), the MCP servers of the project's packages as `-c mcp_servers.<name>.url=<gateway address>` overrides (`src/codex/mcp.ts`, `docs/packages.md`): Codex's `config.toml` is never written, and the turn holds no credentials — the gateway adds them.
- The Codex sandbox does not start under the Windows service (BTN-171, checked on 0.162.1 and 0.163.0). Codex creates its private desktop on the window station of the calling process and starts the command on `Winsta0\<that desktop>`; in session 0 the service's station is `Service-0x0-…$`, so every program that loads `USER32.dll` (`git`, `node`, `pwsh`) dies with `0xC0000142` (`unelevated`), and the elevated runner never connects ("timed out … connecting runner pipe-in"). `cmd /c echo` still works, which hides it. Upstream: openai/codex#46412, #37722; no admin setup fixes it. On 0.162.1 the elevated sandbox fails even earlier with "setup refresh had errors" while the Codex desktop app runs (openai/codex#51601, fixed in 0.163.0). What `--approve-for-me` does there (BTN-233, 0.162.1, `codex exec` from the service's daemon in session 0, 19.10.2026): the turn runs `on-request` with the `auto_review` reviewer in `workspace-write`, every command fails at once with exit code `-1` and "Failed to create unified exec process: helper_unknown_error: setup refresh had errors", while `apply_patch` edits still land. The model may rerun the command with `sandbox_permissions: require_escalated`, the reviewer approves it, and it runs with no sandbox — that is how a session commits under the service without the bypass, with a failed line before each such step. Whether it asks is the model's choice: told nothing, it gave up on the commit after five refused commands; told to escalate, it committed on the second try. Hence the shared key `execution.codex` (BTN-173; before it the project key `codexBypassSandbox`): `sandbox` by default, `bypass` — sessions run with no sandbox and no reviewer. It is shared only, since the sandbox fails for every project alike. Claude's modes are another matter, its transport (`execution.claude`, "The Agent SDK transport" below); `execution.opencode` and `execution.copilot` are config errors.
- There is no `AskUserQuestion`: a turn that ends without Done leaves the session resting, it is answered from the page's chat window (`resume`), and nothing is posted to the tracker (BTN-166). The prompts stay Claude's; the unattended line about `AskUserQuestion` is harmless here.
