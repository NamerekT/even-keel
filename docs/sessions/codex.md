# Sessions: Codex

## Codex (BTN-168, `src/codex/`)

Checked on codex-cli 0.162.1. The binary: `EVEN_KEEL_CODEX_BIN`, otherwise Even Keel's own copy of the checked version while `cli.codex` is `checked` and the copy is downloaded (`cli-versions.md`, "The checked CLI"), otherwise on Windows the native `codex.exe` of the global npm package `@openai/codex` (its `codex.cmd` needs a console), otherwise `codex`.

- **A turn** is `codex exec --json … [resume <id>] -`. Even Keel writes the UTF-8 prompt to stdin and closes it, so long task descriptions and chat replies fit on Windows. The detached process writes stdout and stderr to `state/codex/turns/<name>-<ms>.jsonl` and can outlive the service. Every flag goes before `resume` — the subcommand takes none of its own. The thread id is the first event (`thread.started`); the turn is over at `turn.completed`/`turn.failed`. How the end is read from the turn file, and how a pid that the system has reused is told from the turn's, is common to Codex, Copilot and OpenCode: `agents.md`, "Stopping a turn".
- **A project without git** (BTN-883): the start carries `SessionStart.outsideRepo` and `turnArgs`/`warmArgs` add `--skip-git-repo-check` right after `--json`: `codex exec` refuses a folder outside a repository without it (the flag is in `codex exec --help` of 0.167.0). `writeProtection` then asks git nothing and writes no `info/exclude` entry — the folder may lie inside a repository that is not the project's.
- **The registry.** Codex has no list of background sessions, so Even Keel keeps its own: `state/codex/sessions/<id>.json` (`sessionId`, `name`, `cwd`, `account`, `startedAt`, the `pid` and output file of the last turn, `stopped`). Between turns there is no process: the session is `idle` with `resting: true`, and liveness checks go through `isLive` (a live pid or `resting`). `stop` kills the turn's process tree (`killTree`) and marks the session `stopped`. If saving a newly launched or resumed turn fails even after `writeAtomic`'s Windows retries (`docs/storage.md`), the adapter kills that new process tree and waits for its exit before returning the save error: no running turn is left hidden behind an absent or old registry entry. Checked live on Windows ([verified](../verified/codex.md)).
- **The transcript** is the rollout `<CODEX_HOME>/sessions/YYYY/MM/DD/rollout-<time>-<id>.jsonl`; a resume appends to the same file. The fold (`RolloutFold`) reads `session_meta`, `turn_context` and `event_msg` lines; the context fill is `info.last_token_usage.input_tokens` of `token_count` against `model_context_window`.
  - An `event_msg` of type `error`, or the `error` of a failed turn's `task_complete` (how 0.162.1 writes a rejected request, e.g. a model the plan does not have), is the API error, a limit when its text says so; a message that is the API's JSON answer shows its inner `error.message`.
  - The next item of the session clears that error, as it clears the session's last `CHECKPOINT:`, `PULL REQUEST` and `NO CHANGES:` lines, except an `item_completed` with the `turn_id` of a turn whose `task_complete` is already written: a command the turn's end killed completes after it (`status: failed`, `exit_code: -1`, 0.164.0) and must not erase the limit (BTN-421).
  - A call whose item is `status: failed` gets a failed line: a command's starts with `Exit code N`, as Claude's does, since Codex fails a whole joined command on its last exit code and the output may be an ordinary one — its first look round is `git status …; rg --files -g AGENTS.md …`, and `rg` finding no `AGENTS.md` exits 1 (BTN-233).
- **Tool pictures** (BTN-396): a `response_item` with `custom_tool_call_output` (code mode) or `function_call_output` holds an `output` array with `input_image` blocks whose `image_url` is a base64 data URL. The whole `RolloutFold` adds one `image` line per result, keyed by `call_id`, with the count; `readRolloutImage` reads that same array for `Agent.image`, without needing the original file. The name comes from a direct `view_image` call's JSON `path`, or one static `tools.view_image({path: ...})` in an `exec` wrapper; computed paths and several calls leave the name empty. JavaScript is never evaluated. The ordinary progress feed stays unchanged ([verified](../verified/codex.md)).
- **No Remote Control** (BTN-178): its sessions get neither a link nor the "Remote Control is off" note. Codex's own `codex remote-control` reaches threads through an app-server, and the chain's `codex exec` threads are not among them (`source = exec`, which `thread/list` leaves out by default); the daemon cannot run under the elevated service either. Moving the turns to an app-server in the user's own session waits for [openai/codex#52675](https://github.com/openai/codex/issues/52675): a second app-server on the same `CODEX_HOME` fights the desktop app's remote control. The findings are in [verified](../verified/codex.md).
- **Limits** on a ChatGPT sign-in — the `wham/usage` poll, token renewal, the windows, the reset read from a refusal, a live session's reports and a workspace seat — are shared with OpenCode: `limits.md`, "ChatGPT (Codex and OpenCode)".
- **Flags:** `--approve-for-me` (chain sessions run without a human: Codex's automatic reviewer approves inside its sandbox), or `--dangerously-bypass-approvals-and-sandbox` instead when the shared `execution.codex` is `bypass` (the next bullet); `-m <model>` when the run profile has a Codex model (`models.md`); the MCP servers of the project's packages as `-c mcp_servers.<name>.url=<gateway address>` overrides (`src/codex/mcp.ts`, `docs/packages.md`): Codex's `config.toml` is never written, and the turn holds no credentials — the gateway adds them.
- **The sandbox does not start under the Windows service** (BTN-171, BTN-233; [verified](../verified/codex.md)). Codex starts the command on a private desktop of the calling process's window station, and in session 0 every program that loads `USER32.dll` (`git`, `node`, `pwsh`) dies with `0xC0000142`; `cmd /c echo` still works, which hides it. Upstream: openai/codex#46412, #37722; no admin setup fixes it.
  - With `--approve-for-me` every command then fails at once with exit code `-1` ("helper_unknown_error: setup refresh had errors"), while `apply_patch` edits still land. The model may rerun a command with `sandbox_permissions: require_escalated`, the reviewer approves, and it runs unsandboxed — whether it asks is the model's choice, so a session may give up on its commit.
  - Hence the shared key `execution.codex` (BTN-173): `sandbox` by default, `bypass` — sessions run with no sandbox and no reviewer. It is shared only, since the sandbox fails for every project alike. Claude's transport is the separate key `execution.claude` (`sdk.md`); `execution.opencode` and `execution.copilot` are config errors.
- **No `AskUserQuestion`:** a turn that ends without Done leaves the session resting, it is answered from the page's chat window (`resume`), and nothing is posted to the tracker (BTN-166). Codex gets the same prompts as Claude; their unattended line about `AskUserQuestion` names a tool Codex lacks and is harmless.
