# Sessions: run profiles, models, prompts and the context window

## Run profiles (BTN-173, `src/sessions/launch.ts`)

What a session runs on is three dictionaries keyed by provider (`claude`, `codex`, `opencode`, `copilot`; `src/agent/providers.ts`), at two levels, plus the provider itself:

- `provider` — shared and per project (`claude` by default). Formerly the project's `agent`.
- `models: { <provider>: <model> }` — shared and per project; a project's entry overrides the shared one of that provider, other providers come from the shared. The shared `models.claude` is `opus` by default: a Claude session is never launched without `--model`, since the CLI would take the model from `settings.json`, which `/model` rewrites in any editor on the same account. Codex has no built-in default — `null`, the model of its own `config.toml`; neither has OpenCode, whose model is `<provider>/<model>` (`opencode/big-pickle`, `openai/gpt-6.1-sol`), as `opencode models` lists it; nor Copilot, whose own default is `auto` (the CLI picks a model per session, `gpt-6-luna` in the check).
- `accounts: { <provider>: <account key> }` — the pool, shared and per project, merged the same way; an account key from `/accounts` (BTN-169) fixes the provider. Defaults: `global` (`~/.claude`) and `codex` (`~/.codex`); a Codex account added from the page is a folder under `~/.codex-accounts`, an OpenCode one under `~/.opencode-accounts`, a Copilot one under `~/.copilot-accounts` — OpenCode and Copilot have no default account (`docs/accounts.md`). The active account of the header is the shared provider's entry, and moving the "Even Keel" role moves the shared provider (`docs/accounts.md`). One account per provider: a spent limit is not rotated — the chain waits for the reset or an edit of the pool entry the project uses, and a new account means a new session with a handoff.

`runSettings(config, project)` in `src/config.ts` fills a project's values over the shared ones. `runChoice` picks by the task's run, else the project's provider and model. A run whose provider has no account in the pool (`hasAccount`: the key names a folder of that provider) does not pause the chain: the task runs on the project's provider with the project's model, the launch log entry gets `fallback` and the page a toast (`chain.noAccountFor`, `docs/web.md`).

### The run of a task (BTN-983, `src/sessions/runs.ts`)

A task's run is Even Keel's own record, not the tracker's: `{ provider, model, effort }` by project id and task in the table `task_runs` (`docs/storage.md`), kept in memory by `TaskRuns` and written behind by `runs-store.ts`. Each field may be empty, "as the project says"; nothing set is no record.

- **The provider** is one of `PROVIDERS`, compared case-insensitively. **The model** needs its provider and goes to the CLI as written (a typo is the session's error on its first turn, unless the account's list refuses it first, "Model lists" below); a provider alone takes the model from the dictionaries. A change of the provider drops a model the change does not name (`patchedRun`).
- **The effort** needs no provider: it goes to whatever provider the task runs on, and only if that provider takes the level (`effortFor`), otherwise no flag is passed. The levels are `EFFORTS` in `src/agent/providers.ts`: Claude Code `low`, `medium`, `high`, `xhigh`, `max` (`--effort`, the Agent SDK through `extraArgs`); Codex `minimal`, `low`, `medium`, `high`, `xhigh` (`-c model_reasoning_effort="…"`). OpenCode and Copilot have none here: the page shows no effort field for them and `taskRunOf` refuses one. Levels of Even Keel and of a project for the effort are BTN-146.
- **Every launch path** passes it, as `--model`: the effort is `SessionStart.effort`, filled by `agentExtras` from `runChoice` on the first launch, `--resume` that starts a new job, a handoff, "New session" and the keep-warm fork. A live session keeps what it started on; a changed run applies from the next launch.
- **Who sets it**: the task card (`TaskRunPick`, the command `POST /api/task/run` with `{ task, provider, model, effort }` — the whole run, empty fields clear) and the tasks server's `run` field of `tasks_create` and `task_update` (`docs/trackers.md`). Both check through `taskRunOf` (`run.unknownProvider`, `run.modelWithoutProvider`, `run.unknownEffort`). The page reads `EvenKeelState.runs` (project id → task → run); chain rows and the backlog draw it with `RunLabelTag`.
- **Run labels are not read.** A tracker label `<Provider> | <model>` or a bare `<Provider>` was the run before BTN-983; now it is a plain label. The update moves them once: database step 47 marks in `run_label_imports` each project whose `modelLabels` was on (its own or inherited) and drops the setting; on the first list of such a project's tasks `TaskRuns.importLabels` turns the run label of each open task that has exactly one and no run yet into a run, and the mark goes. A task with several run labels ran as its project said and still does. The labels stay in the tracker. `runLabelOf` (`src/tracker/model.ts`) is kept for this import only.

The choice is the task's and the project's, not the previous session's: a handoff (limit, checkpoint, "New session", reply) stays on the same provider. For a new session, `launchPlan` appends every matching `modelPrompts` entry in table order. Keys use the run-label shape `provider | model`: `Claude | sonnet*`, `* | *sonnet*`; only `*` is special (any string), case is ignored and spaces around `|` are trimmed. A bare provider (`Codex`, or `*` for all providers) covers its sessions including an unknown CLI default; an explicit model pattern requires a known model. Matching uses the actual launch choice after account fallback. `modelPromptMatches` (`src/sessions/model-prompts.ts`) is shared with the page's preview. Schema v17 migrates each legacy model key to `* | <key>`; database step 16 does the same for stored settings, preserving entry order. The model prompt goes on every new session — first launch, handoff, "New session", fix and carry. Chat replies (resume and SDK steering) and automatic resumes use the original continuation text without model prompts or unattended instructions, even after a model change. `goOnWith` retains the plan's model and the existing account and launch settings.

The Model prompts table suggests run labels from every account's `ModelCatalog` list and shows each row's matching models grouped by provider. An incomplete catalogue (Claude/Codex aliases and suggestions, or an unavailable account list) also allows any manually entered id matching the pattern. No known match is a warning, not a save refusal. `ModelPrompts.tsx` and `modelPromptPreview.ts` hold this page section; `useModelCatalog` preserves the service's completeness flag.

### Model lists (BTN-336)

The optional `Agent.models(home)` gives the models a session of the account may run on, as `-m`/`--model` takes them, and whether the list is `complete`. `ModelCatalog` (`src/agent/models.ts`) keeps each account's answer for 10 minutes and a failure for one (logged as `models: <account> did not list its models`), and asks one agent once for callers that come together.

- **OpenCode** — `opencode models`, complete (an empty source answer is not: it says nothing). An OpenAI OAuth sign-in additionally filters `openai/*` by `GET https://chatgpt.com/backend-api/codex/models?client_version=<checked Codex version>` (`src/opencode/models.ts`, BTN-584): only `models[].slug` whose `visibility` is `list`, intersected with OpenCode's catalogue. A successful empty intersection remains complete. The access token and account header come from OpenCode's `auth.json`, falling back to the token's account claim. The token is only read, never renewed. An expired or missing token, non-200 response, malformed body or network failure leaves the source list unchanged and logs one sanitized line. API keys and other providers are unchanged. On 2026-10-29 the endpoint accepted the checked version `0.164.0` with a free ChatGPT sign-in and returned three visible slugs (`verified.md`, OpenCode).
- **Codex** — `model/list` of `codex app-server` in the account's `CODEX_HOME` (`listedModels`: `data[].model`, the `hidden` ones left out; `gpt-6-luna`, `gpt-5.6-terra`, `gpt-5.6-luna` on a free ChatGPT account, 0.162.1). Not complete: an API key reaches models it does not name.
- **Claude** — a fixed set of aliases (`opus`, `sonnet`, `haiku`, `opusplan`, `sonnet[1m]`), not complete: a full id is typed in.
- Copilot has no model list. A live request to `copilot_internal/v2/token` with the GitHub CLI token returned 403 without impersonating an editor, and the Copilot CLI's command surface exposes no signed-in identity to verify that token; the model endpoint was not called. Do not rely on an unverified model list (`docs/unverified.md`, "Copilot's machine token and model availability").

`launchIn` and `resumeIn` in `src/service.ts` ask `ModelCatalog.refusal` before the agent: a model a complete list lacks throws `chain.unknownModel` (the task, the model, the agent, the account by the page's name and its models — those of the asked model's provider first, the closest by name ahead, eight named and the rest counted, `nearest` in `src/agent/models.ts`), so the chain pauses with it and the page gives the button to the project's "Sessions" tab (`noticeFixOf`) instead of a session whose first turn dies. The pause lifts by itself (BTN-679): while the chain is paused on `chain.unknownModel`, each step of the dispatcher (a settings change, the 30-second tick) asks `refusal` again for the model the first task would start on (`modelBlock` in `wireDispatcher`, `cleared` in `src/chain/pauses.ts`), and the chain goes on once there is none and nothing else blocks a launch; Resume still works at once. A list kept without the model is read anew first, since the account may have signed in to another provider meanwhile; an agent that does not answer holds nothing. The page reads the lists by `POST /api/models/list` `{ account }` → `ModelList | null` (`docs/web.md`).

The settings forms keep such a pair from being saved in the first place (BTN-582, `useModelReset` in `web/src/pages/modelReset.ts`, the project's panel and `/settings`): when a provider's account is switched in the form and the new account's list comes back complete without the row's model, the model field is cleared back to the value it inherits (`modelAfterSwitch`). An incomplete list, no list, or a model edited before the answer leaves the field alone; a model saved earlier is not touched when the form opens.

The session panel shows the model a session actually answers with (BTN-229, `SessionView.model`), not the one it was launched with: the fold takes `message.model` of the last main-thread answer of a Claude transcript (not a subagent's, not `<synthetic>`) and `model` of the last `turn_context` of a Codex rollout. So it answers for a session started by hand too, and shows the full id (`claude-haiku-5-5` for `--model haiku`) and the model a launch without `--model` got from the CLI's settings. Until a Claude session's first answer it is `—`; Codex writes `turn_context` at the start of the turn.

If OpenCode still reports `is not supported when using Codex with a ChatGPT account` in a stored step, a terminal error or a log-derived stream error, the fold classifies it as `apiError.kind: model` with `chain.modelUnavailable` (BTN-584). It shows a waiting lamp and the translated Model/Account guidance; the monitor invalidates only that account's catalogue, including an in-flight read. The chain pauses while retaining its current session, before unattended skipping, without stopping or writing to it. Choose an available model/account, update a model label if present, use "New session" and resume the chain. This recovery under the service is still [unverified](../unverified/opencode.md#opencode-chatgpt-model-filtering-btn-584).

## Context window (BTN-187)

A session's context bar and the cap of its checkpoint threshold measure against the window its agent gives (`SessionView.contextWindow`); the `context.window` setting only stands in while there is none. `warn` and `danger` stay settings.

Finished session records keep their own window when present. Otherwise `sessionRecord` uses the last non-null
window `SessionMonitor` observed for that session, without a new CLI probe. The monitor retains up to 2000 sessions
(`SESSION_WINDOWS_KEPT`) in first-observed order and never drops one the page still shows; repeated observations
update the value without renewing its place. The new and changed values of a poll are written behind in one batch
into the state database's `session_windows` and read back at the start (BTN-946), so a restart keeps them; a
session older than the newest 2000 falls back to `context.window`. An unchanged poll writes nothing: with a
smaller memory than the sessions shown, every poll rewrote all of them (BTN-951).

`autoCompactWindow` sets a separate window in tokens for Claude chain sessions, shared and per project (project wins).
An omitted project value inherits the shared one; explicit `null` selects the account's window even over a shared
number. `chainSettings` sends a number as `autoCompactWindow` in `--settings`, and omits `null`. Live edits apply to
new launches only; manual sessions retain the account's settings. The CLI precedence was [checked live](../verified/sessions.md).
Window probes use the session's original launch settings: daemon jobs supply their `respawnFlags`, SDK records
retain `settings` across reconnects. The cache separates account, model and launch settings, so projects with different
windows cannot share a measurement. Old records without launch settings use the account's window. The measured
window feeds `withinWindow`: the checkpoint shares and the margins before Claude's own compaction move with it.

`codexAutoCompactWindow` (BTN-810) is the same setting for Codex chain sessions, shared and per project, with the same
inheritance; `null` keeps the model's own window. `wireAgentExtras` puts the number into `SessionStart.contextWindow`
of a Codex launch, and `windowArgs` (`src/codex/window.ts`) turns it into `-c model_context_window=<W>` and
`-c model_auto_compact_token_limit=<W − 32000>`: Codex then compacts where Claude does with the same window
(`CLAUDE_COMPACTION_GAP`). Codex has no process between turns, so the window is written into the session's record
(`CodexSession.contextWindow`) at launch; every `resume` and keep-warm `fork` takes it from there, never from the
current settings, and a running session keeps its window through a live edit. Hand sessions and `config.toml` are
not touched. The record's window gives `AgentEntry.compactAt`, which `withinWindow` takes as the compaction point
over the agent's measured gap: with a window set, Codex's late and hard thresholds stay before its compaction as
Claude's do; without one they are only shares of the window the rollout reports. The rollout reports less than `W`:
Codex's effective window, `W` × the model's `effective_context_window_percent` (95 for every model on 0.167.0), so
250000 shows as 237500 and the compaction point at 218000 sits at 92 % of it. That is the CLI's own number, not a
lost flag (BTN-812, `docs/verified/sessions.md`).

`openCodeAutoCompactWindow` (BTN-856) is the same setting for OpenCode chain sessions, with the same inheritance;
`null` keeps the model's own window. The models of one OpenCode account differ (1M for MiniMax, 200k for others), so
the setting is a ceiling: `sessionWindow` (`src/opencode/window.ts`) takes it only below the chosen model's
`limit.context` in the account's catalogue, and a session with no `-m` or a model the catalogue lacks keeps the
model's window. How OpenCode is told is in [OpenCode](opencode.md). The window is written into the session's record
at launch and every resume takes it from there, as Codex's; the record's window gives the page's window and
`AgentEntry.compactAt` (`W − 32000`), so the checkpoint thresholds stay before the compaction there too.

Copilot CLI has no such setting (1.0.106, [Copilot](copilot.md)): its card has no window field, and its window is the
transcript's `maxPromptTokens`, as before.

On the page the window is a column of the Agent card, beside Model and Account (`WINDOW_KEYS` of
`web/src/pages/settingsRun.ts`): shared settings, Models tab; a project's sessions tab, with the own flag of each key
(`ownAutoCompact`, `ownCodexCompact`, `ownOpenCodeCompact`, `WINDOW_FLAGS` of `projectForm.ts`). The «Claude Code»
block below keeps Cache TTL and keep-warm.

- **Codex** writes it into the rollout: `model_context_window` of `task_started` and of every `token_count` (`RolloutFold`, 258400 for `gpt-6.1-sol` on 0.163.0: 95 % of the model's 272000, `effective_context_window_percent`). A finished session's record carries it too.
- **Claude** gives it to `claude -p /context --output-format json --no-session-persistence --model <model>`, a local command with no turn: the `result` has the line `**Tokens:** 23.8k / 250k (10%)` (`parseContextWindow` in `src/claude/context.ts`). It answers the window the account's settings make, `autoCompactWindow` included: with 250k in `~/.claude/settings.json` every model answered 250k on 2.1.303, `opus[1m]` too. It runs spawned directly, never through Git Bash (`docs/accounts.md`), in the account's environment with the `--settings` of a chain session of the task's project.
- The model asked about is the `--model` the session was started with, from `respawnFlags` of its `jobs/<id>/state.json` (`launchedModel`): the transcript names `claude-opus-5-5` for an `opus[1m]` launch. A session without a job file or a `--model` is asked about the transcript's model.
- The answers are kept per account, model and original launch settings (`ContextWindows` in `src/agent/windows.ts`): the first session that needs one asks in the background and the bar shows the fallback window until the answer comes. Every 60 s the stamp is compared — the binary's path and change time and the account's `settings.json` change time (`windowStamp`); a new stamp asks again with the original launch settings, a failed question is asked again a minute later and keeps the last answer.
- The answers outlive a restart (BTN-946): each one is written behind with its stamp into the state database's `context_windows` and read back at the start, so the bar and the checkpoint threshold use the saved window at once; the first peek compares the stamp and asks again only if it changed, showing the saved window until the answer. The questions go one at a time: a folder's CLI calls queue (`FolderCalls`) and a call's timeout runs while it waits, so eight probes at once after a restart timed out together.
- `npm run cli-check` has a step for it: Claude's `/context`, Codex's window in the record of the check's session.

## Prompts (`src/sessions/prompt.ts`)

`wireBriefed` and `wireWithProject` in `src/service/chain-prompts.ts` connect tracker briefs, vocabulary and shared/project instructions to the service. `src/service/chain.ts` re-exports these entry points.

Assembled strictly: a value in the launch and handoff prompt goes through `fill`, and an empty or non-string one is an assembly error — the chain pauses with it instead of going into a session with a blank space. `modelPrompts` is passed as is, with no substitutions: `{name}`, `{{name}}`, `${name}` is a config error. A project whose tracker has a project key in the config (`github`, `linear`) gets the line "Tracker: GitHub, project octo-org/abc." after the launch or handoff text, brief or not (`withTracker`): with the brief off the prompt otherwise carries only the task id, and the GitHub skill fell back to `origin`, which may be missing or point elsewhere (BTN-143). After it come the roles lines of the project's trackers the tasks server serves (`withVocabulary`, `promptTrackers` in `src/service/vocabulary.ts`, BTN-893; `docs/trackers.md`, "The tasks server"): one `chain:` line for a project with one tracker; with feeds a `trackers:` list of prefixes and the full line of the task's tracker plus a short one (no milestones) of each other. A tracker that is off or fails to answer its vocabulary gets no line, and none read leaves the prompt as it was. The `prompt` setting (`withPrompts`) goes after the brief and before the unattended rules and the model prompt: Even Keel's own (BTN-338) under the heading "Instructions for every project:", then the project's (BTN-97) under "Instructions for this project:" — the two add up, a project's empty one leaves Even Keel's in place. They go into the prompt of a new session only — the first launch and every handoff (`relay`: the limit, the checkpoint, "New session", a fixed `main`, PR feedback, a task back from an inactive status — every `HandoffReason`); `--resume` and a reply continue a session that already has them. They are free text, not checked for substitutions; an empty one is no prompt. The session that fixes a red `main` without a task (BTN-115, `docs/chain.md`) has no brief: its prompt is `fixPrompt` — the report of what broke, the worktree, the branch and its rules — with the two prompts after it, and a handoff of it carries the report again (`withReport`). The prompt language is `promptLanguage` (`src/chain/prompts.ts`, see `docs/web.md`).
