# Sessions: agent adapters, the Claude CLI and transcripts

## Agent adapters (BTN-167, `src/agent/`)

The chain, the page, the accounts and the limits reach an agent only through `Agent` (`src/agent/contract.ts`), on the pattern of `src/tracker/`. Four adapters implement it: Claude Code (`src/claude/adapter.ts` over `ClaudeCli` in `src/claude/cli.ts`), Codex ([`codex.md`](codex.md)), OpenCode ([`opencode.md`](opencode.md)) and Copilot ([`copilot.md`](copilot.md)). They are registered by name in `AGENTS` (`src/agent/adapters.ts`) and set up once in `src/service.ts`. `AGENTS` also holds `demo`, the first run's scripted agent (`src/demo/agent.ts` over `src/agent/scripted.ts`): no CLI, no sign-in, no limits, run only on the demo's project and never offered on the page (`docs/chain/demo.md`).

- **An account folder's agent.** Every account folder carries its agent (`AccountHome.agent`, `AccountEntry.agent`), and a session runs on the agent of its account: `agentOf(home)` in `src/service.ts` picks the runtime for a launch, a resume, a stop, the monitor and the transcript routes. A session shows it as `SessionView.agent`. The agent is not stored anywhere: `AccountHomes` keeps a root folder per agent, and a folder belongs to the agent whose root it lies under (the global folders are `~/.claude` and `~/.codex`).
- **The contract.** `launch`; `resume` (a limit resume, a reply and a checkpoint go on this way; a handoff is a `launch` in the same place); `stop`; `sessions` (the folder's sessions as `AgentEntry`); `tail`; `record`; `feed`; `transcripts` (which sessions a folder holds, for `TranscriptOwners`); `authStatus`, `login`, `logout`; `env` (the session's environment: `sessionBase` without the trackers' and CIs' credentials, plus `CLAUDE_CONFIG_DIR` for a folder other than the global one).
  - `tail` is a transcript read as it grows; its `summary()` is the `TranscriptSummary` the page and the chain read: stage, action, context fill, the question, the API error.
  - How it reads (BTN-690): the file tails of Claude, Codex and Copilot read 1 MiB at a time and fold 64 KiB of lines at a time through `lineSlices` (`src/sessions/lines.ts`). All readers together hold one turn of the event loop for at most ~30 ms (`paced`, one budget for all), since the monitor reads every session of every account at once — 735 on the author's workstation. While a read is under way `summary()` stays the one from before it, so the catch-up after a restart neither holds the loop for seconds nor shows a half-folded transcript.
- **Optional methods**, and the adapters that have them:

  | Method | What it is | Claude | Codex | OpenCode | Copilot |
  | --- | --- | --- | --- | --- | --- |
  | `usage` | the account's limits; without it the account is not polled ([`limits.md`](limits.md)); Claude's is `claude -p /usage`, parsed by `parseUsage` | yes | yes | yes | yes |
  | `keyUsage` | its token accounts are polled too | | | | yes |
  | `contextWindow` | the window asked of the agent ([`models.md`](models.md), "Context window"); Codex and Copilot have it in the transcript | yes | | yes | |
  | `windowStamp` | when `contextWindow` must be asked again | yes | | | |
  | `models` | the model list ([`models.md`](models.md), "Model lists") | yes | yes | yes | |
  | `write` | a one-off turn ([`chat.md`](chat.md), "One-off turns") | yes | yes | yes | |
  | `warm` | the keep-warm ping ([`cache.md`](cache.md), "Keep-warm") | yes | yes | | |
  | `image` | a picture of a tool result | yes | yes | yes | |
  | `stopDaemon`, `liveRecords`, `remote` | the daemon, the apps panel, Remote Control | yes | | | |

- `SessionStart.settings` is Claude's `--settings`; `model` is the model name as the CLI takes it, `null` — the CLI's own default. The cache lifetime, `AskUserQuestion` and the job files stay inside the Claude adapter and the transcript fold.
- The contract does not need a live process between turns: a session is its id and its transcript, and `resume` may start a process per turn (`codex exec resume`).
- **Where a session starts** (BTN-168, BTN-173). The agent of a new session comes from the run profile ([`models.md`](models.md), "Run profiles"). `choiceFor(project, task)` in `src/service.ts` picks the account folder a launch, a handoff (`relay`) and a fix session (`launchFix`) start in. The chain judges a launch block, the limits and the relay account by that same folder (`blocked`, `limitReset`, `account` in `src/chain/model.ts` take the project and the task).
  - An answer, a letter or a reply that resumes the task's session is judged by the session's own folder instead (`MachinePort.sessionBlock`, BTN-1396): a task whose run was switched to a spent account still takes answers on the one it runs on. "New session" and "New session with this message" go by `choiceFor`.
  - `agentExtras` adds what only Codex takes: the bypass (`execution.codex`) and the tracker's MCP server.
  - Still Claude's and left for the accounts page: `AccountHomes` (folders, `.claude.json`, `.credentials.json`, sharing), `parseAuthStatus`, `parseCredentialTimes`, the statusline's `rate-limits.json`.

## Claude folder trust (EKR-59)

Before every Claude background launch and resume, `wireLaunchIn` and `wireResumeIn` (`src/service/accounts.ts`) pass the project's checkout as `SessionStart.trustedRepo`, inside the account's CLI lease. A changed account or checkout is taken on the next launch or resume without restarting the service. There is no consent setting (the project key `trustClaude` went in schema 26).

Only the Claude adapter writes trust, after choosing the transport: SDK launches and sessions known to `SdkSessions.knows` are left alone, even after the configured transport changes. For `--bg`, `trustFolder` reads the selected account's `.claude.json` (the service user's global file when no `CLAUDE_CONFIG_DIR` is set) right before the launch or resume, uses `isTrusted` and `samePath`, keeps other keys and projects, and writes atomically. The wizard and the project trust API use the same check.

Which key counts:

- The CLI looks trust up by its working folder's real path, links resolved: a symlink on Linux (`getcwd`, EKR-94) and a junction on Windows (EKR-96). So only a key spelled as the real path (`workingFolder`) counts. A folder under a symlink or a junction, or macOS `/tmp` and `/var`, gets its key under the real path, copying what an entry under the link path held; a folder that cannot be resolved is written as it is.
- On Windows the real path is `realpathSync.native`'s: the drive letter upper case and every part in its case on disk.
- On Windows only forward-slash keys count (EKR-92). The writer reuses one if present, otherwise creates one, copying an existing backslash entry without changing it; with both keys present it updates only the forward-slash entry.
- A Windows folder whose real path leaves its drive — a `subst` or mapped network drive (`realpath` turns them into the target drive or a UNC path), a `\\?\` path — is kept as written, unchecked.

The file: a missing one is created, `600` off Windows, and an existing one keeps its mode (EKR-95); empty, malformed, wrongly shaped or inaccessible data is not replaced; a file the CLI already reads as trusted is not rewritten. Trust enables the repository's `.claude/settings*.json` hooks too; chain sessions still disable `.mcp.json` servers. This does not accept Claude's separate bypass-permissions disclaimer.

**When it fails.** A write failure pauses with `claude.trustWriteFailed`, naming the file and the reason (`file`, `reason`: `access` for a file system error, `invalid` for a damaged file): fix the account file, then Check again and resume. A CLI trust refusal maps to `claude.untrusted` (also through nested causes and items), and its pause offers manual trust commands (EKR-85…87):

- The refused invocation records its absolute executable and account override in the notice (`params.recovery`); the service keeps that attempt's checkout too, and the commands keep this snapshot across settings changes and restarts.
- The pause shows one command: the service user's under a system service, the current user's otherwise. A managed account sets `CLAUDE_CONFIG_DIR` explicitly and a global one clears it, so the command is run as the user the notice names. The label over a command is only its shell (cmd, PowerShell; none in a Linux or macOS terminal); commands scroll horizontally inside their blocks.
- Windows without a service: one PowerShell line with literal paths. A Windows service: the refusal writes `<state>/trust/<task>.ps1` (`untrustedStart`, `src/claude/trust.ts`; UTF-8 with a BOM: stop on error, the checkout, the account override, the CLI), names it in `params.script`, and the command typed into cmd is `runas /user:<user> "powershell -NoExit -NoProfile -ExecutionPolicy Bypass -File <script>"`, so the user reads a file instead of a line quoted twice over.
- Linux and macOS: shell and sudo with the service user's home.
- Check again and resume writes trust again, and a new refusal records the new attempt.
- Older notices keep older commands: one whose script could not be written (logged) or saved before EKR-87 keeps the `Start-Process runas.exe -NoNewWindow -Wait` line; a saved one without the service flag shows both users' commands, the second labelled; one without a complete recovery snapshot keeps the PATH commands.

Checked live on Windows ([verified](../verified/sessions.md)); another service user and macOS/Linux are [open checks](../unverified/sessions.md#writing-claude-folder-trust-before-launch-ekr-59).

## Stopping a turn (`killTree`, BTN-643)

A Codex, Copilot or OpenCode turn and the SDK transport's executor are detached processes, each the leader of its own session and group; `killTree` (`src/agent/process.ts`) kills one with what it started. Claude's `--bg` jobs are stopped by `ClaudeCli.stop` ("CLI and transcripts" below).

- **Windows:** `taskkill /PID <pid> /T /F`, which follows parents and is forced already.
- **Linux and macOS:** one `ps -A -o pid=,ppid=,pgid=` right before the kill; the turn's descendants are found by parent in it, and `SIGTERM` goes to the turn's group and to the group of every descendant. A shell tool may run its command in a session and group of its own — OpenCode 1.18.25, Codex 0.166.0 and Copilot 1.0.105 on Linux do, Codex on macOS too — and such a command outlived a stop that signalled only `-pid` (2026-10-31). A descendant in the service's own group is signalled alone, never the group. Without `ps`, or with the turn missing from its table, only `-pid` is signalled. A command whose parent died before the snapshot is reparented away and not looked for.
- **`SIGTERM` first, `SIGKILL` after the wait** (`stopTree`, BTN-760): Codex, Copilot and OpenCode wait up to `STOP_TIMEOUT_MS` (30 s) for the turn's pid to go. A turn that outlives it — one frozen by `SIGSTOP` cannot run its own `SIGTERM` handler (EKR-64) — is checked against its creation time again and, only while it is still the turn, a fresh snapshot's groups get `SIGKILL`. A pid still alive 5 s later, or one no longer the turn's, throws `<agent>.stillRunning`, which pauses the chain without launching a second session. The SDK transport's executor gets `SIGTERM` alone: its pid check is its pipe answering, which a terminated executor no longer does.

**Not a stranger's process** (EKR-33, `src/codex/process.ts`). Codex, Copilot and OpenCode check the turn's process creation time both when polling a running turn and right before `killTree`; the tree is taken after that check, and a process is in it only through a parent chain from the turn at that moment.

- A process created later than the time in the last turn's output file name plus the adapter's launch window (60 s for Codex, 120 s for Copilot and OpenCode) has reused the pid: the session rests, and a stop leaves that tree alive and marks the session stopped. The session's original `startedAt` is not the last turn's start after a resume.
- On Windows the polls share one `Get-Process` snapshot across adapters and accounts, coalescing concurrent requests and caching it for a second; a stop uses a fresh lookup of that pid. Linux reads `/proc/<pid>/stat` with the boot time and `getconf CLK_TCK`, macOS uses `ps -o lstart=`.
- An unknown creation time or an unrecognised output file name keeps the check out.
- Checked live on Windows for all three adapters ([verified](../verified/sessions.md)); Linux and macOS are open (`docs/unverified/codex.md`, "Stopping a turn on macOS and Linux").

**The turn file.** The three adapters write a turn's stdout and stderr into one file. The end of a turn is read from the last JSON object with a string `type`, skipping trailing stderr and JSON without an event type; a later real event outranks an earlier terminal one. OpenCode's turn-error reader uses the same rule ([verified](../verified/codex.md)).

## CLI and transcripts

### The daemon and the binary

- `claude --bg` goes through the supervisor daemon (`claude daemon run`, on Windows the pipe `\\.\pipe\cc-daemon-…`). Background sessions are the daemon's children, so stopping the service does not kill them.
- Sessions are the `claude` CLI (`--bg`, `agents --json`), or the same CLI through the Agent SDK for an account folder whose transport is `sdk` ([`sdk.md`](sdk.md)). What follows in this section holds for `--bg`; the feed, the questions and the replies hold for both.
- The binary, the first found, in this order:
  - `EVEN_KEEL_CLAUDE_BIN`;
  - Even Keel's own copy of the checked version, while `cli.claude` is `checked` and the copy is downloaded ([`cli-versions.md`](cli-versions.md#the-checked-cli-btn-250-srcagentpinnedts));
  - the standalone CLI `~/.local/bin/claude.exe` (outside Windows `claude`);
  - a global npm install's native binary;
  - the binary of the newest VS Code extension version (an extension update deletes its folder).
- The npm install (`npmCliBinary`, `src/agent/npm-global.ts`, BTN-1196): the package's `bin/claude.exe` is a placeholder of ~500 bytes until its postinstall links the native binary of `@anthropic-ai/claude-code-<platform>-<arch>[-musl]` over it, and a newer npm skips that postinstall unless allowed. So Even Keel takes `bin/claude.exe` only when it is no placeholder, else the platform package's `claude(.exe)` inside the package or hoisted beside it. The global folders are `<PATH folder>\node_modules` and `%APPDATA%\npm\node_modules` on Windows, `<PATH folder>/../lib/node_modules` elsewhere. `findBinary` refuses any `.exe` under 4 KB after following links (`isRunnable`), so npm's link to the placeholder on a Linux PATH does not pass for an installed CLI. `opencode-ai` is laid out the same way (`resolveOpenCodeBinary`).

### Sessions, jobs and live processes

- Transcripts are in `<account folder>/projects`. `claude agents`, the transcripts, `sessions/<pid>.json` and `settings.json` are read for each account folder.
- `claude agents --json` (2.1.284) prints neither `pid` nor `status`, and `state: done` stays both for a live session after a turn and for a stopped one: a live process, `pid` and `busy`/`idle` come from `sessions/<pid>.json` entries with a live `pid` (`withLiveRecords`). `state: done` is the CLI's guess that a job did its work, given to a turn that ends on a question in plain text too: with a live process such a session waits for a reply, and it is finished only once its process is gone.
- **The listing is asked only on a change** (`FolderListings`, `src/claude/listing.ts`, BTN-1478). The monitor runs `claude agents` again only when what it prints from changes: the CLI binary, the live `sessions/<pid>.json` records, `daemon/roster.json` (by a hash of its text) and each job's `state.json` without the fields a turn moves on every step (`detail`, `tokens`, `updatedAt`…).
  - A file is read again only on a new inode, mtime or size, and on every tick while its mtime is under 2 s old (`FILE_SETTLE_MS`, BTN-1526): two writes within one tick of the file system's clock share an mtime, and `working` → `blocked` keeps the size.
  - A finished job the roster does not hold is not looked at again — a resume makes it a worker, which rewrites the roster.
  - An answer is kept at most 30 s; the chain's own listings (a launch, a resume, a stop) always ask.
  - Why: on a folder with 380 jobs the stamp costs ~0.5 ms a tick against tens of milliseconds of a spawn, which holds the event loop on Windows.
- **A job outlives its daemon** (BTN-648). A daemon that retires a job blocked on "Credit balance is too low" settles it `done` and exits, while its `state.json` stays `blocked` (2.1.310). So a blocked or working job without a live `sessions/<pid>.json` is taken as starting only while the folder's daemon holds it: `daemon/roster.json` lists it under `workers` (keyed by job id), and its `supervisorPid` lives and started before the roster's `updatedAt`. Otherwise the entry is `abandoned` (`daemonJobs`, `withJobFiles`): no startup dialog, and a stop returns at once without `claude stop`, which would answer "couldn't confirm … was stopped".
- **A session hung on a startup dialog** is visible only in its job file: `claude agents --json` shows `state: blocked`, as for a question, while `<account folder>/jobs/<id>/state.json` gets `tempo: blocked` and in `needs` what the dialog asks for — for a known one, e.g. `approve 1 new project MCP server (strata) — attach to respond`, otherwise `open this session to continue setup` with `detail: "stuck on a startup dialog"` from the CLI's 45 s watchdog (2.1.296). A blocked session without a live `sessions/<pid>.json` has not begun its first turn, so Even Keel reads that file for it (`withJobFiles`, `blockedOn`) and puts `needs` into `SessionView.startupDialog`: the panel says why the session stands, and the log has a `sessions: … hangs on a Claude Code dialog` line. Such a session is not mid-turn: "New session" and "Skip" stay available. The dialog cannot be seen from a terminal: the service's daemon is in session 0.
- **Whose process it is.** Claude records' `startedAt` is the process's initialization time in Unix milliseconds (CLI 2.1.310), not the original job's start after a resume. `liveRecords` rejects a pid whose OS creation time is later, sharing the Windows process-time snapshot with the other adapters (`src/codex/process.ts`). `ClaudeCli.stop` checks again with a fresh lookup before collecting descendants or calling the CLI, and checks ownership while waiting for the exit. The saved descendants carry their creation times: older children of a reused parent pid are left out, and each remaining process is checked against its saved identity right before it is killed. Windows kills each with its own `taskkill /F`, without `/T`, so unchecked descendants are not killed. An unknown creation time keeps the check out. Checked live on Windows ([verified](../verified/sessions.md)); Linux and macOS are in `docs/unverified.md`.

### A silent turn (BTN-496, `src/sessions/silence.ts`)

All four agents can keep a live working process with no error and no completed turn, so they share one rule.

- **Activity.** `TurnActivity` in the monitor dates Claude Code (CLI and SDK), Codex and Copilot by both the transcript's modification time and observed file-size changes, including streaming and thinking records the feed omits. Windows can keep Codex's rollout modification time frozen while its writer holds the file open (BTN-518), so a size change, a truncation too, or a changed path counts as activity at the time it is seen. The reader keeps that stamp between polls; its first sample uses the modification time without inventing recent activity, and removed sessions lose their cache. A process start, a new process or an observed idle-to-busy change bounds old transcript writes, so a resumed turn gets its own clock. OpenCode gives its database or output stamp in `AgentEntry.silentSince`; an unreadable source is unknown, never evidence of a hung turn.
- **Five minutes** (`TURN_RESTART_MS`). From then on "New session" may replace the working turn once the user confirms it; the confirmation carries the session id and the start of the silence, and `guardRestart` checks both at the request and again before the queued handoff (`chain.restartChanged` if either moved). Before that a busy session refuses it (`chain.silentTurn`). "Skip" keeps its ordinary busy guard.
- **Thirty minutes** (`TURN_HANG_MS`). `hungEntry` turns the silent entry idle with `hungSince`, keeping its pid; a chat reply then bypasses live SDK steering and stops the hung process before resuming it.
- Neither threshold stops anything on its own. The page shows the silence from two minutes on (`shownSilence`), timed by `SessionView.silentSince`, with both thresholds' moments.
- Left out: waiting sessions, a Codex session resting between turns (it has no process) and Claude's `shell` status — the turn has ended while a background command runs. `shell` keeps its own one-hour rule (`turnStatus`): such a session counts as busy for an hour after the transcript's last line, then idle. While its card's status light (the lamp) is `working` it carries `SessionView.background` (BTN-960, `backgroundWait`): the transcript's last background command (`TranscriptSummary.backgroundCommand`: a shell call with `run_in_background`, a `Monitor`) and `hangsAt`, that hour's end. The page shows it on the card's action line, the chat's turn line and the drawer's status instead of "working"/"Thinking".
- Recovery from a real stalled provider is [unverified](../unverified/sessions.md#silent-turn-recovery-btn-496).

### Temporary model errors (BTN-498, `src/sessions/transient.ts`)

`apiError.kind: transient`: `at capacity`, `overloaded`/`overloaded_error`, Codex's `server_is_overloaded`, and `service unavailable`/`service_unavailable`. A bare HTTP 503/529 without such a message is not enough. Claude's synthetic API error, Codex's error event or failed `task_complete` (with `codex_error_info`), OpenCode's step or turn error and Copilot's `session.error` keep the kind. An idle live session shows a waiting lamp; while the CLI retries mid-turn it stays working. Provider variants and recovery through a real outage are [unverified](../unverified/sessions.md#temporary-model-errors-btn-498); the chain's resume schedule is in [chain/exceptions.md](../chain/exceptions.md), exception 1.

### The feed

The progress feed on the page is the last 30 lines of the fold (`TranscriptFold`): texts and tool calls, API errors and the person's prompts (`kind: 'prompt'`). Requests do not go into the handoff on a limit.

- **A prompt line is shown for** a `user` record that has no `isMeta`, is no tool result and whose `origin.kind` is `human` or absent; client context blocks in it (`<ide_selection>`, `<pasted_content>`) stay in the text.
- **A message that came mid-turn** from Remote Control or the terminal has no `user` line: the CLI writes it as an `attachment` of type `queued_command` (the prompt in `prompt`, `origin.kind: "human"`) next to a `queue-operation` `remove` with `absorbed_mid_turn`. The feed shows it as a prompt without starting a turn.
- **Not shown** (BTN-1504): the session's own task notifications (another `origin.kind`) and the notice the CLI queues after a resume about the last process's background command (no `origin`, only `commandMode: "task-notification"`); their `enqueue` is no waiting message. `thinking` blocks never reach the feed, even with text (`thinking.display: "updates"`): the model's thinking is not read out of transcripts.
- **The whole transcript** ("Whole transcript") is `GET /api/sessions/<id>/transcript`: the same fold without truncation (`whole`), with the full command in `detail` for Bash and PowerShell. For a live session the window reads on every 3 s with `?after=<how many lines it already has>`: fold lines are only appended, and the service folds the file anew each time (14 MB — ~150 ms).

### Questions and answers (BTN-101, `src/sessions/ask.ts`)

- A pending `AskUserQuestion` call is the session's open question, `SessionView.ask` (`tool_use` id and its questions); in the whole fold the call's line carries it as `line.ask`. Its `tool_result` with `toolUseResult.answers` becomes an `answer` line with `answers` (the question it answers and the answers by question text). Any new prompt clears the open question.
- A result without answers (the call was interrupted or failed when the session was stopped) leaves the question stray, and the next human prompt answers it: that prompt is an `answer` line too, its answers read back by `answersIn` from its `- "question" → answer` lines. `claude --bg --resume` with the answer gives such a call the same synthetic error result as an SDK session (`[Tool call interrupted: …]`, then `No response requested.`), with the answer as the next prompt (2.1.302, BTN-189).
- From CLI 2.1.302 a pending call is in the transcript at once: the response line with the call, its `model` and `usage`, is written while the job still waits, so a session whose first action is a question shows its model, context and cache like any other (EKR-3).
- An older CLI (2.1.296) wrote that message only together with the answer, and `claude stop` lost it for good. There the question is only in `block.questions` of `jobs/<id>/state.json` (the record says `status: waiting`, `waitingFor: "input needed"`): the text and the options with descriptions, without `header`, `multiSelect` or `preview`. `withJobFiles` reads it for a live waiting session (`blockedAsk`), and the monitor gives it as `SessionView.ask` when the transcript has none: the id is `job:<job id>:<hash of the questions>`, `unsaved: true`, and every question is a single choice without a header.

### The reply (`replyPrompt`, BTN-182)

How a reply travels — the mailbox, the inbox socket, a resume — is [`chat.md`](chat.md); this is what it says.

- The reply prompt, in `promptLanguage`, is what the user sent and nothing more, since the chat shows it as the user's message: the `- "question" → answer` lines, the user's text, then `Files from the user:` and the paths. A reply that answers some of the questions lists all of them in order, a skipped one as `- "question"` alone, so the session knows it went unanswered (BTN-1778); a reply in words alone names none. For an `unsaved` question one service line goes first, that the question was lost when the session restarted, and each question gets its answer line (or `- "question"` alone when skipped) with the chosen options' descriptions indented under it. Where the answer came from (the page or the tracker) goes only to the log (`Reply.from`). An empty reply is `answer.empty`.
- The page's panel keeps its picks by question text while the call comes back under another id (the job file's, then the transcript's, as after a service restart) or vanishes for a moment (`carriedPicks`, `web/src/pages/askPick.ts`).
- `replyParts` takes a prompt apart again for the chat — the answers, the user's own words and the files — and strips the service lines of older prompts too (`LEGACY` in `ask.ts`).
- Files are saved first into `.temp/inbox/` of the task's folder (`src/sessions/inbox.ts`: safe names, no overwriting, a `.zip` unpacked with `tar -xf`, `unzip` as a fallback); the folder has its own `.gitignore` with `*`, so the worktree stays clean and the cleanup after Done does not stall.
- How `--resume` treats an unanswered `AskUserQuestion` that did reach the transcript is not verified, so the prompt does not depend on it.
- **Chat commands** (BTN-557). `CHAT_COMMANDS` (`src/sessions/commands.ts`, free of `node:*`, read by the page too) lists them; `commandIn` finds a known one at the start of a message. `replyPrompt` expands it through `commandPrompt` (`src/sessions/commandPrompt.ts`) only for `reply.from === 'page'`: a tracker comment that starts with `/handoff` reaches the session as written. Every page path goes through `replyPrompt` — a resume, an SDK steer and the mailbox (`mailPrompt`) — so a command means the same in every state of the session.
  - `/handoff [extra]` becomes `PromptTexts.handoff`: write `.temp/handoff.md` and end the turn with `CHECKPOINT: .temp/handoff.md`, the same note the `agent-bridge` plugin asks for on a full context, with the user's words after the command as an extra paragraph. The mark then hands the task over as any checkpoint does (invariant 1's exception).
  - `typedText` maps an expanded prompt in either language back to `/handoff extra`: `userLine` uses it, so every agent's feed shows the command as typed, and a mailbox message posted from a permission answer (`approved` in `src/service/machine-chain.ts`) is stored typed and expanded again when the hook delivers it.
  - A new command is an entry in `CHAT_COMMANDS` and its prompt in `TEXTS` of `commandPrompt.ts`.

### Resuming (`--resume`)

- **In place or a copy.** `claude --bg --resume <id>` starts a copy under a new session id (the page shows it as a new chat with the whole history again) when the session is still running or, if its job `jobs/<job id>/state.json` is saved, when any flag is passed: such a session keeps its own options (model, permission mode, name, settings), and the CLI prints `note: … keeps its own saved options, so the flags you passed started a copy` (reason `own-options`). So a reply or a limit resume of a saved job passes only `--bg --resume <id> <prompt>` (`resumeArgs`): the session goes on in place with its launch's options, and a task's run or a model changed meanwhile applies from the next launch. Without a saved job the flags are passed as at a launch.
- **Finding the resumed session** (`resumedAs`): by that id or, as after a launch, by the task name, the folder and the start time — the latter only for another job than the resumed one.
- **The id flicker** (`steadyJobs`). Resuming in place, the daemon kills the job's process and spawns a new one, and for under a second that process shows a fresh session id (in `claude agents` and `history.jsonl`) before it loads the session and takes the old id (2.1.302). Taking the fresh id gave the chain a session with no transcript. So the monitor takes a job's new session id only once two polls in a row show it, and keeps the earliest `startedAt` it saw for a job: while a process lives, `claude agents` gives that process's start.
- **The gap** (`ResumeHolds`). A reply or a limit resume stops the session first, so for several seconds `claude agents` calls it `stopped`, then `working` with no process, and its `startedAt` becomes the new process's. The monitor shows a session the service is resuming as working until it is live again, and the page shows no start banner for a session that already had an answer or a resume.
- **Mid-turn after a resume** (`ResumeHolds.turning`, BTN-307). The `busy` status lags 8–20 s behind the resume (2.1.308), and a chat message in that window stopped the fresh turn and resumed it again. So a session counts as mid-turn from the start of its resume until a poll shows it `busy`, it shows another question than the one it had, or 45 s pass; such a message goes into the mailbox or gets `answer.busy`.
- **How long it takes** (BTN-203). About 5 s from the stop is the CLI's floor: `claude stop` 0.6–0.8 s and the process gone 0.3–0.9 s later, `claude --bg --resume` 3.5–3.9 s until the job shows `working`, the prompt in the transcript ~1 s after. `ClaudeCli.stop` adds little to it: the Windows process listing runs alongside the stop, the exit is watched by the pid every 100 ms and confirmed by one `claude agents`, only live descendants are killed and all at once, and `appear` polls every 250 ms (a stop and a resume take 6.1–6.7 s). The log has one line per reply or limit resume, `sessions: <task> resumed in <ms> ms (stop <ms> ms)`. A `--resume` sent before the old process exits would go on in place too and save another 0.3–0.9 s; it is not used, since `stop` is also what kills the leftovers before a worktree is removed.

### The prompt on the command line

- **A leading dash.** A prompt that starts with a dash — a reply begins with its `- "question" → answer` line — passes `claude --bg`, but the process the daemon spawns reads it as an unknown option and exits before init: the job is `failed` with `error: unknown option '- …'`, and the chain pauses on "did not show up in claude agents" (2.1.302). `promptArg` puts a line break before such a prompt.
- **Too long** (BTN-1505). `claude --bg` reads a prompt from stdin, but its daemon spawns the session with the prompt on its own command line (`claude.exe --bg-pty-host <pipe> <cols> <rows> -- claude.exe --session-id <id> <flags> <prompt>`): a 50,039-character prompt left the job `crashed` with `ENAMETOOLONG: name too long, uv_spawn` (2.1.330), so stdin is no way around Windows' 32,767 characters, and a long task's handoff prompt reaches them. Elsewhere the limit is 128 KiB an argument.
  - `fittedArgs` (`src/claude/cli.ts`) counts the line the daemon will spawn — the binary twice, the flags, the prompt as libuv quotes it and 512 characters for the daemon's wrap (`commandLineFits`, `src/sessions/prompt-file.ts`); a resume of a saved job counts the launch's flags too, since the daemon puts them back.
  - When it does not fit, the prompt goes whole into `.temp/even-keel-prompts/prompt-<ms>-<hex>.md` of the session's folder (`writePromptFile`; `.temp/` is in `info/exclude`), and the session gets `promptPointer`: read that file whole and act on it as this message.
  - The chat feed (`userLine` in `src/sessions/transcript.ts`) and Tally's first prompt (`firstPrompt`) show the file's text in the pointer's place through `expandPromptFile`, which reads only a file of that folder and gives the pointer as it is once the worktree is gone; the handoff snapshot holds the whole prompt anyway.
  - A spawn that never ran prints nothing — Node 26 throws `spawn ENAMETOOLONG` at once — so every CLI call's failure `detail` is `callFailure`/`execFailure` (`src/agent/exec-failure.ts`): the exit code or the timeout with stderr and stdout, else the error's message. Codex and OpenCode turns keep the child's spawn error the same way.
