# Sessions: session settings and the "What sessions get" page

## Session settings (BTN-74, `src/tools/`)

Plugins and MCP servers are the project's packages, given by flags at every launch (`docs/packages.md`). What stays here is the rest of `--settings` and the "What sessions get" page. How a session gets stuck on a startup dialog, and a job file that outlives its daemon, are in `agents.md` ("Sessions, jobs and live processes").

- The "Trim the tools" switch on `/settings`, the Sessions group (`chain/trim`, `ChainState.trimTools`, on by default): chain sessions are launched with `--settings <JSON>` (`chainSettings`) — `syncClaudeAiSkills` and `syncClaudeAiPlugins` are off, skills from the config's `hiddenSkills` (default `DEFAULT_HIDDEN_SKILLS`) are `user-invocable-only`, that is, only through `/name`. It applies on every launch: first, `--resume`, handoff. The settings files are not changed, `--settings` affects only that launch (verified on CLI 2.1.290: `--bg` passes it through, claude.ai skills do not go to `.trash`).
- With the switch off, `--settings` still goes: it carries `autoMemoryDirectory`, the shared memory folder (`docs/accounts.md`), and `enabledPlugins: false` for the enabled plugins outside the task's set (`docs/packages.md`).
- The CLI looks for `.mcp.json` in the parent folders as well, so a session in a worktree inside the main checkout would see the servers of the main checkout's `.mcp.json`, even an untracked one, and hang on their approval dialog (BTN-86). `--strict-mcp-config` of the packages cuts them off.
- `skillOverrides` of the project (`.claude/settings.json`) and of the main checkout (`.claude/settings.local.json`, which overrides the project one, as in the CLI) override the list. A session in a worktree does not read the main checkout's `settings.local.json` — its `skillOverrides` reach it only through `--settings`. They are Claude Code's alone: Codex, Copilot and OpenCode sessions see every skill of `~/.agents/skills`, where Even Keel links the user's own skills (BTN-1691, `docs/packages/files.md`).

## The "What sessions get" page

Not to be confused with the "What the session gets" card on a project's settings (`docs/web/project-settings.md`): the page compares settings across projects, the card lists one project's instruction files, skills and documents.

- **Address and choice.** `/tools?projects=A,B&diff=1` (`web/src/tools/`); without `projects` the first two chain projects are selected, so the matrix is not squeezed. The project choice is the same list as on `/stats` (`web/src/ui/ProjectList.tsx`). The project page has a chip in its head with the number of problems, leading there (`docs/web.md`). Packages are not here (BTN-802): the catalog is on `/settings`, a project's set over its page (`docs/packages.md`).
- **Problems**, at the top, merged across projects: a deny or an ask only in `settings.local.json`, the rest that won't reach the session, the main checkout's `.claude/settings.json` the sessions do not get, claude.ai skills, MCP servers the last session failed to connect, accounts.
- **The matrix**, below: "setting × project" by section, with the result for the session and level marks; `diff=1` ("Only differences") shows only the rows where projects differ. The logic is `web/src/tools/matrix.ts`.
- **The data** is `GET /api/projects/<id>/tools` (`readToolsView`), per project:
  - a table of settings by level (user, project, local, Even Keel) with the result for the session;
  - the difference between the accounts' `settings.json` and the global one (key names only — `env` holds secrets);
  - what the project's last session received: the start of its transcript (first 400 lines; the worktree folders `<repo>--claude-worktrees-*` first) — `skill_listing`, `prompt_snapshot.tools`, `deferred_tools_delta`.
- The project level is `.claude/settings.json` committed on the project's branch (EKR-128, `readProjectSettings` in `src/tools/projectSettings.ts`), read with `git show <branch>:.claude/settings.json` as the Codex rules are: a task worktree starts from the branch, so a file in `.gitignore` or never committed never reaches a chain session, and neither do the main checkout's uncommitted edits. The page and the launch read the same version — `createSessionSettings` (`src/tools/sessionSettings.ts`) gives it to `otherPlugins` and to trimming. When the main checkout's file differs, `ToolsView.settingsDrift` names why: `ignored` (`git check-ignore`), `uncommitted` or `edited` (compared as parsed JSON, so CRLF is no edit); the page lists it as a problem of its own kind with what to commit. Nothing is carried over from the disk with `--settings`: that would hide a file missing from git, and a session started by hand in a worktree would still go without it. A project without git reads its folder (the last bullet).
- **Left out of the view**, so the problems hold only what a chain session misses (BTN-321); such a row is not in the matrix either:
  - A plugin or an MCP permission set only in `settings.local.json` for a package the project does not have on, or one not in the catalog. Sessions get plugins and MCP only as packages, so it is a setting for sessions started by hand in the main checkout (`forPackageOff` in `src/tools/settings.ts`, by `sessionReach` in `src/packages/launch.ts` — a `plugin` row by `<name>@<marketplace>`, `mcp__<server>__…` by the gateway's server name, `mcp__plugin_<plugin>_…` by the plugin).
  - A plugin set on in `settings.local.json` that the project does get as a package: the package turns it on for the sessions anyway (BTN-1709). One set off there stays in the view: it really has no effect.
  - An account folder no project runs on (`projectsByAccount`) is not compared with the global `settings.json`: the copy goes over it before its first launch anyway.
  - Even Keel's own settings guard in a folder's `PreToolUse` is no difference (`accountDrift` compares after `stripSettingsGuard`, `docs/accounts.md`; BTN-912): in a group beside a user's hook only that hook is compared, and an event list or `hooks` left empty counts as absent.
- The agents' own deny files are shown, never synced (BTN-466, decided 2026-10-27): they add up by themselves — the agent reads its files, Protection lies on top, and a deny outweighs an allow — so Even Keel keeps no second copy. A `deny` or `ask` only `settings.local.json` has gets its own problem and a "deny — not reached" chip with where to move it (`localDeny` in `web/src/tools/matrix.ts`); `chainSettings` still carries only `skillOverrides` from that file.
- The "Codex rules" section reads Codex's `.rules` files (`parseCodexRules` in `src/codex/rules.ts`, the `prefix_rule` calls only, not run): the `rules/` of the project's Codex account folder (`runSettings(...).accounts.codex`) as the user level and `.codex/rules/` committed on the branch as the project level, without Even Keel's `even-keel.generated.rules` (that is Protection). `forbidden` shows as `deny`, `prompt` as `ask`, a missing decision as `allow`; the session gets the strictest of a pattern's values, as Codex takes the most restrictive matching rule. Copilot CLI keeps no persistent tool deny rules (1.0.103: only `--deny-tool`, and `deniedUrls` for addresses), so it has no section.
- A project without git (BTN-883, BTN-963) runs its sessions in its folder itself, not a worktree, so `readToolsView` (`places.plain`) reads that folder instead of a branch: `settings.local.json` and the `.claude.json` entry reach the session, between Even Keel's level and the project's (`readsLocal` in `settingRows`, `scopeMarks(row, true)` on the page — L is marked as read, and its denies are no problem); the instruction files, skills and documents (the "What the session gets" card and the standards' document picker) come from a walk of the folder without `node_modules`, `.git` and `.temp`, at most 5,000 files; the project's Codex rules from its `.codex/rules/`. `ToolsView.plain` tells the page.
