# Sessions: extra tools

## Extra tools (BTN-74, `src/tools/`)

Plugins and MCP servers are the project's packages, given by flags at every launch (`docs/packages.md`). What stays here is the rest of `--settings` and the "What sessions get" page.

- The "Trim the tools" switch on `/settings`, the Sessions group (`chain/trim`, `ChainState.trimTools`, on by default): chain sessions are launched with `--settings <JSON>` (`chainSettings`) — `syncClaudeAiSkills` and `syncClaudeAiPlugins` are off, skills from the config's `hiddenSkills` (default `DEFAULT_HIDDEN_SKILLS`) are `user-invocable-only`, that is, only through `/name`. It applies on every launch: first, `--resume`, handoff. The settings files are not changed, `--settings` affects only that launch (verified on CLI 2.1.290: `--bg` passes it through, claude.ai skills do not go to `.trash`).
- With the switch off, `--settings` still goes: it carries `autoMemoryDirectory`, the shared memory folder (`docs/accounts.md`), and `enabledPlugins: false` for the enabled plugins outside the task's set (`docs/packages.md`).
- The CLI looks for `.mcp.json` in the parent folders as well, so a session in a worktree inside the main checkout would see the servers of the main checkout's `.mcp.json`, even an untracked one, and hang on their approval dialog (BTN-86). `--strict-mcp-config` of the packages cuts them off: no `disabledMcpjsonServers` any more.
- A stdio MCP server of a plugin that failed to start is cached by the CLI in `<account folder>/mcp-needs-auth-cache.json` for 15 minutes (BTN-159, CLI 2.1.302). Chain sessions no longer run plugin servers themselves — the gateway does — so Even Keel does not read that file.
- A session that hangs on any startup dialog is visible only in its job file: `claude agents --json` shows `state: blocked`, as for a question, while `<account folder>/jobs/<id>/state.json` gets `tempo: blocked` and in `needs` what the dialog asks for: for a known one, e.g. `approve 1 new project MCP server (strata) — attach to respond`, otherwise `open this session to continue setup` with `detail: "stuck on a startup dialog"` from the CLI's 45 s watchdog (2.1.296). A blocked session without a live `sessions/<pid>.json` has not begun its first turn, so Even Keel reads that file for such sessions (`withJobFiles`, `blockedOn`), puts `needs` into `SessionView.startupDialog`, the panel says why the session stands and the service log has a `sessions: … hangs on a Claude Code dialog` line. Such a session is not mid-turn: "New session" and "Skip" stay available. The dialog itself cannot be seen from a terminal: the service's daemon is in session 0.
- A job's `state.json` outlives its daemon: a daemon that retires a job blocked on "Credit balance is too low" settles it `done` and exits, while the file stays `blocked` (2.1.310, BTN-648). So a blocked or working job without a live `sessions/<pid>.json` is taken as starting only while the folder's daemon holds it: `daemon/roster.json` lists it under `workers` (keyed by job id) and its `supervisorPid` lives and started before the roster's `updatedAt`. Otherwise the entry is `abandoned` (`daemonJobs`, `withJobFiles`): no startup dialog, and a stop returns at once without `claude stop`, which would answer "couldn't confirm … was stopped".
- `skillOverrides` of the project (`.claude/settings.json`) and of the main checkout (`.claude/settings.local.json`, which overrides the project one, as in the CLI) override the list. A session in a worktree does not read the main checkout's `settings.local.json` — its `skillOverrides` reach it only through `--settings`.
- The "What sessions get" page is `/tools?projects=A,B&diff=1` (`web/src/tools/`); without `projects` the first two chain projects are selected, so the matrix is not squeezed. The project page has a chip in its head with the number of problems, leading there (`docs/web.md`). The project choice is the same list as on `/stats` (`web/src/ui/ProjectList.tsx`); the packages are not here since BTN-802 — the catalog is on `/settings`, a project's set over its page (`docs/packages.md`) —, at the top are the problems merged across projects (a deny or an ask only in `settings.local.json`, the rest that won't reach the session, claude.ai skills, MCP servers the last session failed to connect, accounts), below is a "setting × project" matrix by section with the result for the session and level marks; `diff=1` ("Only differences") shows only the rows where projects differ; the logic is `web/src/tools/matrix.ts`. Per-project data is `GET /api/projects/<key>/tools` (`readToolsView`): a table of settings by level (user, project, local, Even Keel) with the result for the session, the difference between the accounts' `settings.json` and the global one (key names only — `env` holds secrets) and what the project's last session received: the start of its transcript (first 400 lines; the worktree folders `<repo>--claude-worktrees-*` first) — `skill_listing`, `prompt_snapshot.tools`, `deferred_tools_delta`.
- Two kinds of rows stay out of the view, so the problems hold only what a chain session misses (BTN-321). A plugin or an MCP permission set only in `settings.local.json`, for a package the project does not have on (or one not in the catalog): sessions get plugins and MCP only as packages, so it is a setting for sessions started by hand in the main checkout (`forPackageOff` in `src/tools/settings.ts`, by `sessionReach` in `src/packages/launch.ts` — a `plugin` row by `<name>@<marketplace>`, `mcp__<server>__…` by the gateway's server name, `mcp__plugin_<plugin>_…` by the plugin). Such a row is not shown in the matrix either. And an account folder no project runs on (`projectsByAccount`) is not compared with the global `settings.json`: the copy goes over it before its first launch anyway. Nor is Even Keel's own settings guard in a folder's `PreToolUse` a difference (`accountDrift` compares after `stripSettingsGuard`, `docs/accounts.md`; BTN-912): in a group beside a user's hook only that hook is compared, and an event list or `hooks` left empty counts as absent.
- The agents' own deny files are shown, never synced (BTN-466, decided 27.10.2026): they add up by themselves — the agent reads its files, Protection lies on top, and a deny outweighs an allow — so Even Keel keeps no second copy. A `deny` or `ask` only `settings.local.json` has gets its own problem and a "deny — not reached" chip with where to move it (`localDeny` in `web/src/tools/matrix.ts`); `chainSettings` still carries only `skillOverrides` from that file. The "Codex rules" section reads Codex's `.rules` files (`parseCodexRules` in `src/codex/rules.ts`, the `prefix_rule` calls only, not run): the `rules/` of the project's Codex account folder (`runSettings(...).accounts.codex`) as the user level and `.codex/rules/` committed on the branch as the project level, without Even Keel's `even-keel.generated.rules` (that is Protection). `forbidden` shows as `deny`, `prompt` as `ask`, a missing decision as `allow`; the session gets the strictest of a pattern's values, as Codex takes the most restrictive matching rule. Copilot CLI keeps no persistent tool deny rules (1.0.103: only `--deny-tool`, and `deniedUrls` for addresses), so it has no section.
- A project without git (BTN-883, BTN-963) runs its sessions in its folder itself, not a worktree, so `readToolsView` (`places.plain`) reads that folder instead of a branch: `settings.local.json` and the `.claude.json` entry reach the session, between Even Keel's level and the project's (`readsLocal` in `settingRows`, `scopeMarks(row, true)` on the page — L is marked as read, and its denies are no problem); the instruction files, skills and documents (the "What the session gets" card and the standards' document picker) come from a walk of the folder without `node_modules`, `.git` and `.temp`, at most 5,000 files; the project's Codex rules from its `.codex/rules/`. `ToolsView.plain` tells the page.
