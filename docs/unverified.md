# What has not been verified

Even Keel is checked live on the author's machine with the author's accounts. Some behaviour could not be checked there: the situation never came up, or there was no way to create it. This page lists it, so you know where Even Keel works on an assumption. Each entry says what is assumed, what happens if the assumption is wrong and what to do about it.

If you run into one of these, please open an issue with what you saw: it is the only way the entry gets checked.

## Platforms

- **macOS.** `service/install.sh` installs a launchd agent there, but Even Keel has never run on a Mac: neither the agent nor finding the CLI and its folders.

## Updating

- **Plugins from a git URL marketplace.** A marketplace added from a local path is read from its folder, so an update of the code reaches the plugins by itself; that was checked. One added from a git URL (`owner/repo`, `https://…`) keeps a copy by version, and README tells you to run `claude plugin marketplace update even-keel` and `claude plugin update <plugin>@even-keel` in each project. The commands were run, but a copy that is actually behind was never brought up to date with them. If sessions still run the old plugin, `claude plugin uninstall … --scope project` and `claude plugin install … --scope project` in the project install the current one.
- **The first start with the PGlite state database (BTN-198).** The import of `state/even-keel.db` into `state/even-keel/` was tested on the frozen samples and run on a copy of the author's live state (889 launches, 93 handoff snapshots, 10 closed tasks: every table came over whole); backup and export through a live owner, a reader in a worker thread of the owner's process (the way Tally's collector reads) and a restore of the backup were checked on that copy. Not yet by the service itself after an update, with its page and a restart in the middle (`docs/storage.md`). If the start stops on the page with an import error, the file is untouched and nothing was written. **Workaround:** if the state looks wrong after the import, stop Even Keel, delete `state/even-keel/`, rename `even-keel.db.imported` back to `even-keel.db` and start the previous version.
- **A reader opening the state database while the service starts.** With no service running, `npm run storage` or a collector run outside the service opens the folder itself for the seconds it reads. A service started in those seconds refuses the folder ("process … holds the database") and stops on its start. Never seen; the window is a few seconds. **Workaround:** start the service again once the reader has finished.

## The page

- **A changed `EVEN_KEEL_TOKEN` seen from another machine (BTN-130).** Checked live: the service reads the new token from `.env` and logs it. Not checked: the open event streams closed on the change, and a browser on another machine with the old token's cookie getting the token form when its page reconnects, since every request from the author's machine, to any of its addresses, passes without a token. If the page keeps showing a dead connection instead, reload it; the form comes on the next page load.

- **Adding and removing a project on the running service (BTN-118).** The wizard, the removal and the start without a config file are covered by tests and were looked at on fake data, but not run on the author's live service: a project added by the wizard taking its first task, its tracker probe (`chainTasks` over a connection of its own, not the service's), and a removal refused by a real live session. If an added project does not show up, or a removal goes through while a session works there, **workaround:** `npm run storage -- config-export`, edit the file, `config-import` it — the service applies it on the fly.
- **The wizard's trust check.** It reads only the global `~/.claude.json` (where Claude Code records the trust and from where it is carried into the account folders), not the active account folder's copy, and it does not check Codex's trust at all. A folder trusted only in an account folder shows the warning although it is trusted; the warning does not hold the add. A folder that passes but is not trusted for the chain's account pauses the chain at its first launch, as before.
- **Pasting files copied in Explorer into the chat (BTN-204).** Ctrl+V in the chat's reply box attaches whatever files the browser hands the paste (`clipboardData.items`). A pasted picture and plain text were checked with a real Ctrl+V in Playwright's Chromium, a drop of one and several files with synthetic events. Files copied in Explorer were not: the headless browser the checks run in does not read the system clipboard at all, and the installed Chrome is not used for checks (`docs/web.md`, "Screenshots"). Chromium is assumed to hand them over as files; if it does not, the paste attaches nothing. **Workaround:** drop the files on the chat window or pick them with `+`.

## Claude limits

- **An early reset of a limit.** Anthropic sometimes resets a five-hour window or all limits of an account ahead of time. When a session hits a limit, the chain remembers the reset time from the error or from `/usage` and waits for it; what `/usage` shows right after an early reset has never been seen. If it shows a new window or no window, the remembered time is not updated and the chain keeps waiting until the original reset. **Workaround:** press "New session" on the task — it drops the remembered wait and starts a session at once; or switch the account.
- **Continuing a session after a limit.** A limit cannot be hit on demand, so neither path the chain takes after one has run live: `--resume` while the cache is warm and a new session with a handoff when it is cold (`docs/chain.md`, exception 1). Each shares its mechanics with paths that were checked on 17.10.2026: the resume with the user's answer from the page (`cli.resume`), the handoff with a checkpoint and "New session" (`relay`). What is left unchecked is the decision itself — reading the reset time, choosing warm or cold, the moment of the step. If the chain keeps waiting after the limit has reset, or resumes a session that then fails, **workaround:** press "New session" on the task.
- **Fast mode in statistics.** Responses in fast mode are recorded (`speed = fast`), but none have appeared in the data, so `/stats` prices them as normal responses and their cost is understated (`tally/CLAUDE.md`).

## Sessions

- **A resume that starts a copy.** A resumed session in place was seen to show a fresh session id for under a second before it takes its old one, and the chain now waits for the old id (`docs/sessions.md`). When the CLI starts a copy instead (a new job), the chain takes the first session of that new job; whether a copy also passes through a throwaway id first was not seen. If it does, the chain follows an id with no transcript: the chat says the transcript is not found and the card shows "Session booting" for 5 minutes. The workaround is "New session".
- **A chain session on an API account.** The CLI was seen to take a key from the account folder's `settings.json` (`claude auth status` says `api_key`, BTN-99) and a `--bg` session was seen to work on a key passed in its environment (BTN-136), but a chain session started from an API account folder with a real key was not run. Every session, a respawned one too, reads the folder's `settings.json` `env` at its start (BTN-129); if the CLI still does not authenticate a chain session with the key from there, the session fails at its first request with an authentication error and stops like any error. **Workaround:** set the key in that folder with `apiKeyHelper` or run the chain on a subscription account (`docs/accounts.md`).
- **The 1-hour cache on a key.** `cacheTtl: "1h"` goes to sessions as `promptCacheTtl`, which the CLI 2.1.302 binary honours whatever the sign-in; that a session on a key then really writes the 1-hour cache (`ephemeral_1h_input_tokens` in the transcript) was not checked with a real key. If it does not, sessions on a key keep the 5-minute cache and `/stats` shows more cache writes than expected; nothing breaks (`docs/sessions.md`).
- **A key refused after it was added.** The check of a key was seen live answering 200 for a working key and 401 for a made-up one; 403 (a disabled organization or a key without the permission) and a key revoked after it was added were never seen. If a revoked key still answers 200 on the models list, the account looks fine until its first session fails on authentication and stops like any error (`docs/accounts.md`). **Workaround:** remove the account and add a working key.
- **An API key out of credit (BTN-165).** Read from CLI 2.1.302, never seen with a key at zero: the API answers 400 "Your credit balance is too low…", and the CLI writes an error message with `error: "billing_error"` and the text "Credit balance is too low", which Even Keel takes as `credit` and waits out like a limit (`docs/chain.md`, exception 1). The check that the credit is back — one output token through `/v1/messages`, an answer of 2xx — was never run against a topped-up key either. If the CLI words it differently, the session stops like any error; if the check never says 2xx, the chain keeps waiting. **Workaround:** press "New session" on the task after the top-up, or switch the account.
- **The chat's turn line while an answer is delivered to Codex or after the chain stopped (BTN-188).** Seen live on a Claude chain session (BTN-189, CLI 2.1.302): a text answer and an `AskUserQuestion` answer were each in the transcript 8 s after the send, and the line went from "Delivering the answer" to "Thinking" then (`docs/web.md`). Not run on a Codex session nor on an answer to a session whose chain stopped (`deliverLoose`). It assumes the respawned session writes its prompt (or the answer's result) with a time after the moment the service began the delivery. If it does not, the line keeps saying the answer is on its way for up to three minutes while the session works; nothing else is affected.
- **Chat mail in a real session (BTN-181).** Checked by tests and in `dev:fake` only; the one live shape seen is a `PostToolUse` `additionalContext` in a transcript, an attachment `hook_additional_context` with the text in `content` (`docs/sessions.md`, "Chat mailbox"). Not seen:
  - how the model takes a message in `additionalContext` against a real user prompt — whether it acts on the correction at once. If it treats it as tool noise, the message is delivered but ignored until the user repeats it after the turn;
  - the transcript shape of a `Stop` hook's `decision: block` reason — the feed assumes a user prompt, possibly `isMeta` — and of the `permissionDecision: deny` result of an `AskUserQuestion` — assumed an error `tool_result` of that call carrying the reason. If either differs, the message is delivered but not shown in the feed as the user's bubble; the chat's list still says "delivered";
  - the mailbox's `Stop` block and `checkpoint-mark`'s in one turn: a turn that ends on `CHECKPOINT:` with mail waiting goes on, and its last line may no longer be the mark, so the handoff waits for the next turn's mark;
  - a long Bash call: the message waits for its end, the chat shows it waiting for the hook all that time.

  **Workaround:** if mail is not acted on or not shown, send the message after the turn ends; it then goes by resume, as before.
- **PR mode against a real forge (BTN-205).** The GitHub and Forgejo pull request clients (`src/review/`) were written from the API documentation and tested on recorded answer shapes only: opening a pull request or finding the open one, the poll's state, reviews, comments of the conversation (BTN-223: the issue comments endpoint with `since`, GitHub's `user.type` of a bot) and failed runs of the head commit, the merge and the close were never run against a real repository; that Forgejo refuses its author a request for changes on their own pull request is taken from its source, not tried; and neither was the push of a task branch from the service. If a pull request does not open, the chain halts with `review.notOpened` and its cause; the count of a branch's commits beyond `<remote>/<branch>` that keeps an empty pull request from opening (BTN-222) was tested on a fake git only: if it misreads a branch with commits as one with none and the worktree is clean, the task goes to Done without a pull request and the cleanup keeps the unmerged branch with a `cleanup.branchKept` warning (`git branch -d` refuses it), so the work stays; if it cannot count, the forge's own refusal halts the chain as before; if the poll misreads an answer, the log says `review: … was not polled` each minute and the task waits out of the chain. **Workaround:** turn `pullRequests` off for the project so that no new task goes out for review, merge the waiting pull requests by hand and move their tasks to Done in the tracker: the usual cleanup takes them and drops their records.
- **Background commands of a stopped session on Linux and macOS (BTN-202).** On Windows `claude stop` was seen to leave the `bash.exe` of a `run_in_background` command alive, and Even Keel now kills the session's process tree after the stop; that was checked there. On Linux and macOS it takes the tree from `ps` the same way and sends each process `SIGTERM`, but it never ran there, and whether the CLI already ends those commands itself was not seen. If a stopped session's command lives on, it holds the worktree and the cleanup leaves it in `leftovers`. **Workaround:** kill the command by hand and press "Done" on the warning; the next cleanup removes the folder.
- **VS Code chat titles.** A chat under "Working now" is named by the last `custom-title` of its transcript, else the last `ai-title` (`src/sessions/title.ts`); that this is the title on the VS Code tab was read from transcripts, not compared with the tabs. If VS Code titles a tab otherwise, the page shows a different name than the tab, nothing else breaks (`docs/accounts.md`).
- **The changelog commit from the service (BTN-209).** `commitChangelog` was tested on a temporary repository, not from the running service in a real main checkout. Assumed: the global git hooks (`core.hooksPath`) take a commit without a task id quietly, `core.autocrlf` does not turn the kept CRLF ends into a whole-file change, and git under the service account (Windows session 0) finds the user's identity and the repository's ownership (`safe.directory`). If one of them fails, "Write" shows `changelog.commitFailed` and the file is put back as it was. **Workaround:** "Copy", paste the section into the file and commit it by hand.
- **The Codex changelog turn with `--json`.** `codex exec` for a changelog draft was checked live only without `--json`; with it, a successful turn on 0.162.1 was not seen (only failed ones, on a model the plan refuses). Assumed: the answer is the `text` of the last `item.completed` of type `agent_message`, and `turn.completed` carries `usage` with `input_tokens` (the cached ones in it), `cached_input_tokens` and `output_tokens`. If the item type differs, the draft fails with "the turn ended with no message" (`changelog.failed`); if `usage` differs, the dialog shows 0 tokens. **Workaround:** the Claude provider for the project while it is checked.

## Codex

Checked live on codex-cli 0.162.1 (BTN-168): a detached turn outlives its parent killed hard, `exec resume <id>` goes on with the history, a resume of an unknown id fails instead of starting a new thread, `CODEX_HOME`, `rate_limits` and the context fill in the rollout. The rest:

- **The chain end to end on Codex.** From the service's Windows session 0 the Codex sandbox does not start, so a chain session runs commands there reliably only when `execution.codex` is `bypass` (`docs/sessions.md`, BTN-171, BTN-173, BTN-233). Bypassed chain sessions of the sandbox project ran commands, committed and merged their branch (TSK-19 on 17.10.2026, TSK-20 on 18.10.2026), but a chain of several Codex tasks one after another has not been run; the rest of the chain on Codex was checked by tests. **Workaround:** if a bypassed session still cannot run commands, run Codex tasks by hand in a terminal.
- **Chain sessions in the Codex app and on the phone (BTN-178).** That the Codex desktop app and the ChatGPT app on the phone do not list the chain's threads is read from the app-server protocol (`thread/list` without `sourceKinds` leaves `exec` threads out), not seen in either app. If an app lists them after all and the user writes there, that turn runs in the app's own app-server and appends to the same rollout: the page shows it in the feed, but Even Keel may `resume` the thread at the same time, and two turns on one thread is untested. **Workaround:** answer Codex sessions only from the page's chat or the tracker (`docs/sessions.md`).
- **Errors and limits in the rollout.** An API error is taken from an `event_msg` of type `error`, and a limit by its text (`usage limit`, `rate limit`, `quota`); neither was ever seen. If the shape differs, a session that hit a limit looks finished without Done and waits for the user. **Workaround:** press "New session" on the task after the reset.
- **Package MCP servers inside a real session.** The `-c mcp_servers.<name>.url=<gateway address>` overrides were checked against `codex exec` parsing, not with a session that called a server through the gateway. If Codex also has a server of the same name in its own `config.toml`, which one wins is unknown. **Workaround:** remove that server from Codex's config or give the tools through the package alone (`docs/packages.md`).
- **Sign-in from the page.** `codex login --device-auth` runs through the panel's sign-in flow, whose reading of the link was written for Claude's output; the one-time code is not parsed out, the window only shows the CLI output unfolded (`deviceLogin`), and the fake mode's output is a guess at Codex's wording. If the window shows no link, sign in with `codex login` in a terminal with the same `CODEX_HOME` (`docs/accounts.md`). Adding an account into a new folder under `~/.codex-accounts` (BTN-176) was checked only in the fake mode and in tests: that `codex login --device-auth` signs in a folder Even Keel made empty, and that the plan of a fresh sign-in is already in its `id_token` when the second free account is judged. If the plan is missing then, a second free account is added and only held afterwards, with the warning on its card.
- **Codex on an OpenAI API key (BTN-177).** Checked with a fake key only: `codex login --with-api-key` writes the `auth.json` Even Keel writes, `codex login status` reads it, a turn on it goes to the API and fails with 401, and OpenAI's models list answers 401 to a fake key. Never seen with a real key: that a turn runs on it, whether its rollout has `rate_limits` (the card shows the spend instead either way), the price of the model it runs on in Tally, and Codex's message when the key's money runs out (BTN-195). That message is read from the codex-cli 0.162.1 binary ("Quota exceeded. Check your plan and billing details.", its `QuotaExceeded` for OpenAI's 429 `insufficient_quota`), and the money check — `/v1/responses` on a `nano`/`mini` model with `max_output_tokens: 16`, waiting for 2xx or a 429 `insufficient_quota` — was never run against a real key, empty or topped up. If Codex words it otherwise, the session stops like on any error, or, if the text has `quota` in it, its lamp says "limit" while the chain does not hold it (on a key only `credit` is held); if the check never says 2xx (the key lists no such model, the request shape is refused), the chain keeps waiting and the log has the check's reason. **Workaround:** top the key up and press "New session" on the task.
- **A crashed turn and a service restart mid-turn.** Liveness is the pid of the last turn: a pid reused by another process after a crash would keep the session busy. A service restart mid-turn was checked with a parent process killed hard, not with the real service.
- **Stopping a turn on macOS and Linux.** The turn's process group is killed with `process.kill(-pid)`; it was run only on Windows (`taskkill /T`).
- **Edit sizes of a `FileChange` (BTN-185).** Only an `add` with the file's `content` was seen in a rollout (2026-10-18). A `delete` is assumed to carry `content` too, and an `update` a `unified_diff` whose `+`/`-` lines are counted (`src/codex/rollout.ts`). If the shape differs, the chat shows the edit with no `+N −M` and leaves it out of the session's edit total; nothing else changes.
- **Codex stats (BTN-170).** Checked on the rollouts on disk: 0.148 desktop sessions and 0.162 exec ones. Never seen: a non-zero `cache_write_input_tokens` — it is assumed to be inside `input_tokens` and is subtracted from it; a rollout in `archived_sessions/`; a 0.162 rollout that has `token_count` lines without a matching `token_usage_record` (the fallback was run only on 0.148 files). If one of these differs, a Codex response is counted twice or its input is off. **Workaround:** none needed for the chain; compare `/stats` with the `usage` in the rollout and fix `src/rollout.ts` (`tally/CLAUDE.md`).
- **Plugin hooks that block (BTN-180).** All five hook events of a plugin were seen running in Codex, and `additionalContext` reaching the model, but never a hook stopping anything: a `PreToolUse` exit code 2 refusing the call (`merge-check` holding a merge until the project's check, `check-marks` refusing a Huly description with bad marks), `permissionDecision: deny` (`show-calibration`), `decision: block` of a `Stop` hook (`checkpoint-mark`). If Codex ignores one, the call goes through: a merge before the check is green, a description with bad marks, a turn that wrote the handoff note without the `CHECKPOINT:` line waits for a reply. **Workaround:** for the last one, reply `CHECKPOINT: .temp/handoff.md` in the chat window or press "New session"; the others show in the tracker and on the CI.
- **Chat mail at a Codex `Stop` (BTN-181).** Seen live on 18.10.2026: messages sent during a command reach a Codex session through `PostToolUse`, and the chat shows them from the developer message the hook leaves in the rollout. Not seen: whether a `Stop` `decision: block` keeps the turn going (else the message is counted delivered at `Stop` while the turn ends without it; send it again from the chat), and where the rollout puts its text — the feed looks for the mark in a `UserMessage` too; if it lands elsewhere, the message works but has no bubble in the chat.
- **The handoff note of a Codex turn seen by the `Stop` hook.** `/api/sessions/<id>/note` reads the rollout when the hook asks; that Codex has written the turn's last `FileChange` by then was not seen. If it has not, the hook lets the turn end, as in the previous item.
- **Plugins in a Codex folder on Linux and macOS.** The install and the check that a plugin is already in a folder (`<CODEX_HOME>/plugins/cache/<marketplace>/<plugin>`) were run only on Windows. If the path differs, every first turn of a service run installs the plugin again, which costs a few seconds and changes nothing else.

## Packages

Checked live on 17.10.2026 (BTN-174) from a second instance in a terminal: plugins installed into Even Keel's state, a Claude chain session with `--strict-mcp-config` and `--plugin-dir` called the Huly server through the gateway, a plugin's hook ran. The rest:

- **The gateway from the Windows service.** The service runs in session 0; that the gateway's server processes (`node`, a `.cmd` through the shell) start there was not seen. If they do not, every project with such a package shows "no response" and its chain waits. **Workaround:** the page names the package; turn it off for the project and give the tracker brief to sessions (`brief`), or check the service's "Log On" account is the user who installed Node (`docs/service.md`).
- **"Add to Claude Code" on `/tools`** (BTN-226). The button runs `claude plugin marketplace add <checkout>` from the service in the default config; the config it was built on already knew the marketplace, so the banner never showed there and the button was seen only on the fake page. If the CLI fails from the service, the banner shows `packages.marketplaceAdd`; if it adds the marketplace to another folder than the one your terminal uses, the banner stays. **Workaround:** run the command the banner shows in your own terminal; chain sessions do not need it either way.
- **Linux and macOS.** Installing a package and the gateway's server processes were run only on Windows. If `npm` or a server does not start there, the cell shows "install failed" or "no response" and the chain waits.
- **Remote servers through the gateway.** Proxying an HTTP server with its headers filled from the pool (GitHub, Linear) is covered by tests, not by a session that called one. If a server answers the gateway otherwise than a session expects, the probe fails and the chain waits (`docs/trackers.md`). **Workaround:** turn the package off and give the tracker brief to sessions (`brief`).

## Trackers

- **A profile changed on `/settings` → Access (BTN-200).** Covered by tests, not run live (it would change the real keys): that the tracker of the profile's projects connects again with the new values, and that a new session finds the default profile's values in the `env` of the global `settings.json`. If the tracker does not connect again, its chips stay "does not answer". **Workaround:** restart the service.
- **Two profiles of one tracker (BTN-200).** Two projects on two profiles of the same tracker — each its own connection, its own gateway keys and its own GitHub Actions token — are covered by tests; the author has one account per tracker, so it never ran live. If a project reads another profile's tasks, **workaround:** keep one profile per tracker.
- **A project's own CI profile (BTN-231).** That a project's chosen GitHub or Forgejo profile (`remoteProfiles`) reads its CI and opens its pull requests is covered by tests; it never ran live, the author has one profile of each. If the CI or a pull request keeps the old profile after the choice, **workaround:** set the wanted profile as the default of its kind on Access.
- **The expiry of a fine-grained GitHub token.** The `github-authentication-token-expiration` header was seen with a classic token. If a fine-grained token's answer has no such header, its card shows no expiry; nothing else changes. A removed key also stops the global folder's daemon (`claude daemon stop --any` with the global `CLAUDE_CONFIG_DIR`, from the service); that stop was never run from the service — if it fails, the log has the error and the removed key stays with sessions of that folder until its daemon exits (`docs/accounts.md`). **Workaround:** stop the daemon by hand once no session of the folder is live.

- **GitHub attachments.** Downloading a file attached to an issue or comment with the token has not been tried live; if it fails, the page cannot open that file (`docs/trackers.md`).
- **Milestones on GitHub and Linear.** Filling the milestone of a task that entered the chain without one (`fillMilestone`) was checked only on Huly (`docs/trackers.md`).
- **Changing a milestone from the task card on GitHub and Linear.** Checked only on Huly. On GitHub, `updateIssue` with `milestoneId: null` is assumed to clear the milestone; on Linear, the choices are the project milestones of the issue's project and `projectMilestoneId: null` is assumed to clear it. If the tracker refuses, the card puts the old milestone back and shows the error; nothing else changes. **Workaround:** change the milestone in the tracker and press the refresh button in the project head (`docs/trackers.md`).
- **The tasks of a milestone on GitHub and Linear (BTN-142).** `milestoneTasks` was checked live only on Huly. On GitHub, `milestones(query:)` is assumed to search titles, so the exact title is found among its results; if it is not, the draft says the milestone has no done task (`changelog.empty`). On Linear the default order of `comments` is unknown, so both ends are read and the newer one is kept; if a page of comments holds neither end's newest, the draft gets an older comment for that task. **Workaround:** none needed for the release itself — the draft is a draft; edit it by hand.

## CI

- **When a CI run counts as stuck.** A queued run, or a push without a run, is called stuck after 2 minutes (`STUCK_MS`). The figure was chosen without live runs and may be too short for a slow runner queue (`docs/ci.md`).
- **A command after a green main that restarts Even Keel.** `commands.afterGreen` run as children of the service's node process. The service stops only that process, not its tree — the Windows wrapper (`service/EvenKeelService.cs`, `OnStop`), `KillMode=process` under systemd, `AbandonProcessGroup` under launchd — so a restart command is expected to outlive the stop and start the service again, but that was never run live. If it dies with the service, the service stays stopped, or the commands after the restart one never run. **Workaround:** make the restart the last command, hand it to something outside the service's process tree (a scheduled task, `systemd-run`), or restart by hand (`docs/ci.md`).
- **The first start with Forgejo profiles (BTN-201).** Checked live, read-only: a profile built from `FORGEJO_TOKEN` the way `importForgejo` builds it, on the host of this repository's Forgejo remote, signs in through `/api/v1/user` and is the one `ciToken` gives that remote, and the runs come with it; another host gets no token. The import itself, by the service on its own database after an update, is covered only by tests. If the Forgejo CI disappears from the page after the update, the import made no profile for that host (the log says why). **Workaround:** add a Forgejo profile on `/settings` → **Access** with the server's address and the token.
- **A remote added to a checkout on the running service (BTN-191).** Every minute the service rereads each project's remotes and workflow folders and adds or drops CI watches by the difference (`CiWatches.refresh`, `docs/ci.md`). The difference itself is covered by tests; the reading is the same as at the start. Not yet seen on the live service: a `git remote add` in a project's checkout giving `ci: <KEY> watches …` in the log within a minute. If the CI does not appear, **workaround:** change and restore the project's `repo` on `/settings`, or restart the service.
- **Chains of several projects on one remote (BTN-210).** The git side is checked on real clones of one remote (`docs/chain.md`, "Projects of one remote"): the fast-forward of `main` before a launch and the second try of a rejected sync. Not run as live chains on the service with a CI: two projects whose pushes race, a red push of one seen by the other. From the code, a red `main` holds and fixes only the project that pushed it, and another project of the remote may start a second fix of the same break once its own push carries the red commit (BTN-217). **Workaround:** put `ci.guard: false` on all projects of the remote but one: only that one judges and fixes `main`.
