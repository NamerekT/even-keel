# Trackers and plugins

Reference for sessions: how the tracker layer, the adapters and the Claude Code plugins are built. The working rules are in `CLAUDE.md`, the public description in `README.md` and `docs/guide/setup.md`.

## The `src/tracker/` layer (BTN-58)

- The neutral task model is `model.ts`: `TrackerTask` from the adapter, `Task` — plus the model and the question from the labels `Question` or `Вопрос`.
- The adapter contract is `source.ts`, `TaskSource`/`TrackerAdapter`; the description is in the JSDoc there, for those who write their own. The chain, the order, the rules and the page state know only these.
- The adapter is chosen by the project's `tracker` (`{ "key", "repo", "tracker" }`). Since BTN-345 it is the project's own only: the wizard, the project form and `config-import` always store it, and the shared one is gone (database step 13 and schema v13 gave each project the one it ran on). `DEFAULT_TRACKER` (`github`) meets only a project of a hand-written file of the current schema that names none. The registry is `src/tracker/adapters.ts`; the repository has Huly, GitHub, Linear, GitLab and Jira Cloud.
- For a tracker whose project is not named by a key, the adapter declares `projectKey` — a key in the project object (for GitHub `github`: `owner/name`); without it, or if malformed, it is a config error. With `optional` only a malformed one is an error (for Linear `linear` narrows the team to a project). With `alias` the value names the tracker's project instead of the key, which then is only Even Keel's (Huly `huly`, BTN-172). `placeOf(key, value)` gives the place in the tracker a project reads (`read`) and the prefix of its task ids (`ids`) when the ids are the tracker's own: projects with one place read it once and must split it by milestone (`docs/chain/projects.md`, "Several projects on one tracker project"); `readKeyOf`/`idPrefixOf` in `src/config.ts` fall back to the key. The values arrive in `setup` as the second argument. The optional `projectOfRemote` turns a git remote of the repository into that value (GitHub: a github.com remote's `owner/name`; GitLab: the full path on the profile's server, "GitLab Issues" below); it gets the parsed remote, the URL as git has it and the values of the profile the draft runs on, and the wizard fills the field with the first remote's answer (`repo.suggested` of `checkDraft`).
- A task ID is `<project key>-<number>`: the worktree, branch and stats go by it. What the tracker lacks, the adapter returns empty.
- The adapters know only the project key. Even Keel's own id of a project (`projects[].id`, a GUID) names it in `state/` and in the page's URLs and never reaches the tracker layer (`docs/chain/state.md`, "State files and the schema version").
- The optional `brief` and `complete` — Huly has both (BTN-63, `src/huly/source.ts`): the description is markdown, Done is a status of the `Won` category from the project type.
  - `brief` — the title and description are appended to the launch and handoff prompts.
  - `complete` — Even Keel closes the task once it sees its branch merged into `main`: `src/git/merged.ts` — the branch tip is in `main` and `main` has at least one commit made in the branch itself (by reflog: creation, `reset` and `Fast-forward` pulls of own commits do not count, so a branch that only pulled in `main` is not considered merged), `src/tracker/closer.ts`. A task reopened after such a close is closed again only by a new merge (BTN-689, `docs/chain/worktrees.md`, "Cleanup after Done"). `true` — the task was moved, already closed — `false`, nothing is written. It does not conflict with a git hook that also moves to Done: whoever is first closed it.
- The optional `children` — the direct subtasks of a task in any status; every adapter has it — Huly by `attachedTo`, GitHub by `subIssues`, Linear by the `parent` filter, GitLab by the work-item hierarchy, Jira by subtasks and the issues of an epic. With it and `complete`, Even Keel closes the parent (`src/tracker/parents.ts`): when tasks are refreshed, a parent that is open by the rules and has no open subtask among the known tasks is checked in the tracker — all subtasks closed and at least one in `Won` — `complete`. All cancelled — the parent is left to the user. In Huly `parents` goes from the root: the direct parent is the last.
- The optional `card`, `ready` and `unready` — the task card on the page; every adapter has `card` (BTN-76), Huly, Linear and Jira also `ready` and `unready`. `card` (`TrackerCard`, `src/tracker/card.ts`) — the description and comments in markdown, labels, milestone, priority, parent, "blocked by", "blocks", "related"; the server (`GET /api/tasks/<id>`) appends `cardOf`: what each label means to Even Keel (model, question, keeps out, required) and whether it can go into the chain or back to the backlog (`ready`, `unready`). `ready` moves a task of the `UnStarted` category to the first `ToDo` status of the project type and returns the new status; `unready` (BTN-509) mirrors it, a `ToDo` or `Active` task to the first `UnStarted` status, `null` for any other. Neither is called directly by the page: `POST /api/task/ready` ("Into the chain") and `POST /api/task/unready` ("To the backlog") also put on or take off the chain's required label through `relabel`, so a tracker with no backlog status (GitHub, GitLab) gets both buttons by label alone (`docs/chain/entry.md`, "Entry into the chain"); the service immediately substitutes the new state for the task in the chain without waiting for a poll. Whether the connected adapter has `ready`, `unready` and `relabel` is carried by the state in `trackers[]`: the buttons stand on this basis right in the backlog panel and the chain. Without `card` the page answers "the tracker doesn't provide a card" and gives a link.
- The card's `attachments` (`file`, `name`, MIME `type`, `size`, `url`) are the files of the task and of its comments. An adapter with its own public address gives `url`; with `url: null` the server puts its own `/api/tasks/<id>/files/<file>`, served by the optional `file(id, file)` (`TaskFile`: type, size, a byte stream). The Huly adapter answers it only for a file of that task or its comments and streams it from the workspace storage (`connectStorage`, connected lazily, reconnected once on failure). The route sends `nosniff` and `private, max-age=3600`; only raster images, video, audio and PDF go `inline`, everything else is `attachment` with `content-security-policy: sandbox`. No `Range`: a video plays, but seeking ahead waits for the download.
  - GitHub (`toCard` in `src/github/model.ts`): one GraphQL query — `body`, `parent`, `blockedBy`, `blocking` (with title and state of each), the first 100 comments (`author.login`); "related" is always empty and `ready`/`unready` are absent, since GitHub has no backlog status: its backlog is the open issues without a required label, and the buttons put that label on and take it off. No attachments on the card: files of comments are links in their text.
  - Linear (`toCard`, `readyState` in `src/linear/model.ts`): `blocks` is read both ways — `relations` (this task blocks) and `inverseRelations` (blocked by) — `related` from either side, other relation types are dropped; comments by `user.name`. `ready` moves a task in a `backlog`-type state to the team's first `unstarted` state by `position`; a task in `triage` or any other state is left alone (`null`). `unready` (`backlogState`) moves an `unstarted` or `started` task to the first `backlog`-type state.
  - Huly: "blocks" — tasks that have this one in `blockedBy` (the query passes `blockedBy: { _id, _class }` as a whole object: by `blockedBy._id` and `$elemMatch` Huly finds nothing); "related" — the task's own `relations`, Huly stores the link on both sides. Comments are `chunter:class:ChatMessage` by `attachedTo`, the markup converted to markdown with `@hcengineering/text-markdown`; the author is `createdBy` (social id) → `SocialIdentity.attachedTo` → `Person.name` in the form "Surname,Name".
  - GitLab (`GitlabUploads`, `src/gitlab/uploads.ts`): upload links in the description and human notes become distinct attachments with `url: null`; relative `/uploads/<secret>/<filename>`, project URLs and `/-/project/<id>/uploads/…` of this project are supported, including an installation prefix. The Markdown links are rewritten to the service's file route. The card renders inline images and download links only for those local attachment URLs. `file` checks that the task references the file, then streams the [REST download by secret and filename](https://docs.gitlab.com/api/project_markdown_uploads/#download-an-uploaded-file-by-secret-and-filename) with the profile token and redirects disabled. GitLab can return `application/octet-stream` for media: known image, audio, video and PDF extensions supply the inline type; other files remain downloads.
- Questions in the tracker (BTN-101, `src/tracker/questions.ts`): the optional `comment(id, body)` posts a Markdown comment and returns its id, `commentsAfter(id, after)` gives the comments posted after it, oldest first (`[]` once it is gone), each with its `files` by what `file(id, file)` serves. With both, `TrackerQuestions` polls every 15 s: when the session of a chain's current task waits on an `AskUserQuestion` (not on a question in plain text), it posts the question with numbered options (`questionComment`) and remembers it in the state database (`questions`, `docs/storage.md`), so a restart does not post it twice. A session that ended its turn without an `AskUserQuestion` (a question in plain text, or just waiting) gets nothing posted and no comment read: it is answered from the page's chat or Remote Control. That is a decision (BTN-166), not a gap: reading any comment as an answer would take a note to self or another person's comment for one, and posting every end of a turn would flood the tracker. Every comment after it is taken as the user's — a waiting session does not comment, and on GitHub Even Keel's token is often the user's own; only GitHub filters by author, since anyone can comment on a public repository (EKR-19, "GitHub Issues" below). The first comment answers by numbers (`2`, `1, 3`) or text, a line per question when there are several (`trackerAnswers`); the rest go along as text and their files are downloaded into `.temp/inbox/` (a file the tracker will not give stays a link). The reply goes through `Dispatcher.answer` (`docs/chain/exceptions.md`, exception 6); `answer.busy`, `chain.launching`, `chain.limitSpent` and `chain.notCurrent` are retried on the next tick, any other refusal closes the question (`done`). A question the session left (answered through the page or Remote Control, a new session) is forgotten. A question stays while its session lives and waits on it even when the task is no longer current (BTN-120: the chain is led by the fix of a red `main`, the task is postponed or skipped): its comments are not read then, and once the chain takes the task again they are read from the same question comment, so a reply written meanwhile reaches the session and the question is not posted twice.
  - Huly: `chunter:class:ChatMessage` with the markup from `markdownToMarkup`; comments after by `createdOn`, files are their `attachment`s. GitHub, Linear and GitLab: a comment's files are the upload links in its body (`github.com/user-attachments/…`, `private-user-images.githubusercontent.com/…`; `uploads.linear.app/…`; GitLab's `/uploads/…`), and `file` fetches only those with the token. GitLab collects files after checking the note author's membership. A GitHub upload of a public repository came back whole through the route (2026-10-24). A fine-grained token never gets a private repository's upload (404), so when the plain link fails GitHub's `file` reads the issue's comments over REST with `Accept: application/vnd.github.html+json`, finds in `body_html` the signed `private-user-images…?jwt=` link of the same upload id (`src/github/uploads.ts`) and fetches it with no token; the signature lives minutes, so it is taken at each download, never stored. A file still unavailable is a log line naming the upload id, never the signed link (checked live 2026-10-31, [verified log](verified/trackers.md)).
  - Replies in a comment's thread (BTN-897): an answer typed in the question's thread counts as a comment after it. Huly keeps such replies apart from the issue's comments and reads them separately ("Huly" below). Linear gives them in `issue.comments` with the rest, each with its `parent` (checked live 2026-11-09), so they are sorted in by time and the card lists them flat. GitLab's `/notes` lists every note of the issue, discussion replies included, by `created_at`, so the same holds (by the API's documentation, not checked live). GitHub, Forgejo and Jira have no threads under issue comments.
- The optional `create(task: NewTask)` (BTN-103) — a new task: project key, title, Markdown description, priority and the milestone of a given task (`milestoneOf`); it returns the new task's ID. With the project's `ci.fixTask` on, the chain files the fix of a red `main` with it (`docs/chain/main-ci.md`, "The CI of main"), and without it a red `main` pauses the chain with `ci.cannotCreate`; with `ci.fixTask` off, the default, the fix is a session without a task and `create` is not called. All three adapters have it, each in the first ready status of the project:
  - Huly: the number from the project's `sequence` (`$inc`), a rank after the last task (`makeRank`), the description through `uploadMarkup`, `addCollection` with `tracker.ids.NoParent`.
  - GitHub: GraphQL `createIssue`; the priority is the `priority: <level>` label only if the repository has it, the milestone is the given task's.
  - Linear: `issueCreate` in the team's first `unstarted` state, with the given task's project and project milestone.
- The optional `closingRef(id)` (BTN-295) — how a pull request names the task's issue; `null` for a task not of the tracker. The GitHub adapter gives `owner/repo#N` of the repository of the id's key, the GitLab one (BTN-414) the issue's address `<server>/<path>/-/issues/<iid>`, both with no request; the others have none. PR mode ends the body of a task's pull request on the same forge with `Closes <it>` (`closingOf`, `docs/chain/pr-mode.md`, "PR mode").
- The optional `setMilestone(id, milestoneOf)` (BTN-107) — puts a task without a milestone into the milestone of the task `milestoneOf`; `false` and no change when the task has a milestone by now or `milestoneOf` has none. The chain fills the milestone of a task that entered it without one with it (`fillMilestone`, `docs/chain/entry.md`, "Entry into the chain"). The milestone is named by a task that carries it because the neutral model has no milestone ID. All three adapters have it; GitHub's was verified live in a task feed (BTN-326, 2026-10-23), Linear's on 2026-10-25 (below):
  - Huly: `milestone` of the issue; a task of another project gives none.
  - GitHub: GraphQL `updateIssue` with `milestoneId`; a milestone belongs to a repository, so a task of another project gives none.
  - Linear: `issueUpdate` with `projectMilestoneId`; a milestone belongs to a project, so an issue without a project gets the project together with it, and an issue of another project is left alone. Checked live on 2026-10-25: the chain filled a Todo issue of a project narrowed to a Linear project, and the adapter, called from a script, gave an issue without a project both the project and the milestone in one `issueUpdate`.
- The optional `milestones(id)` and `moveMilestone(id, milestone)`, only as a pair (`trackerOf` drops one without the other) — the milestone pick on the task card. `milestones` gives `MilestonePick`: the tracker's id of the task's milestone (`null` — none) and the choices, each with its own id, label and target date; the card sorts them as the chain does (`compareMilestones`). `moveMilestone` puts the task into a choice's id, `null` into none. `POST /api/task/milestone` (`{task, milestone}`) calls it and then reads the project anew rather than patching the task, since the milestone changes the chain order; without the pair it is `task.cannotMoveMilestone`. All three adapters have it:
  - Huly: the milestones of the issue's project whose status is not Completed or Canceled, plus the issue's own when it is closed; a milestone of another project is refused.
  - GitHub: the repository's open milestones (GraphQL `milestones(states: OPEN)`), plus the issue's own when it is closed; `updateIssue` with `milestoneId`, `null` clears it.
  - Linear: every project milestone of the issue's project (Linear's have no closed state); an issue without a project has no choices. `issueUpdate` with `projectMilestoneId`, `null` clears it (checked live on 2026-10-25: another milestone, none and back).
- The optional `vocabulary(project)` (EVK-1) — `TrackerVocabulary`: the statuses with their categories (BTN-334: the rules' table places a status by its category until a list names it) and the labels a task of the project can have, whether or not a task has them now. The settings suggest them in the chain rules together with what the loaded tasks carry, so a project whose chain is empty still gets suggestions (`docs/web/project-settings.md`). `GET /api/projects/<id>/vocabulary` serves it by the project's id, 404 when the tracker is off or has no `vocabulary`; the service keeps an answer five minutes (`Vocabularies`, `src/tracker/vocabulary.ts`), a failure or a 404 is not kept. All three adapters have it:
  - Huly: the statuses of the project's type in its order (every status when the type is unknown) and the workspace's issue labels — `tags:class:TagElement` with `targetClass` `tracker:class:Issue` (`vocabularyOf`).
  - GitHub: its own four statuses (`GITHUB_STATUSES`) and every label of the repository (GraphQL `labels`, paged by 100).
  - Linear: the team's workflow states and the labels of the team and of the workspace (`issueLabels` with the team, or none — a workspace label has no team), paged by 50; a label group is left out, since it cannot go on an issue.
  - Checked live on 2026-10-18 on three projects with an empty chain, one per tracker: the route answered for each and the panel's rule lists offered the tracker's statuses and labels.
- The optional `milestoneTasks(project, milestone)` (BTN-142) — every task of a milestone named by its label, open and closed, each with the Markdown of its last comment (`MilestoneTask.lastComment`, the closing comment of its session as a rule); `[]` when the project has no such milestone. It feeds the changelog draft of a milestone (`src/changelog/`, `docs/sessions/chat.md`, "One-off turns"); without it the draft is `changelog.cannotList`. All three adapters have it:
  - Huly: the milestones of the project with that label, their issues and the newest `ChatMessage` of each (`latestMessages`), markup turned into Markdown. Checked live on 2026-10-18 on BTN `v0.1`: 178 tasks, 172 in `Won`.
  - GitHub: the milestone's number by `milestones(query:)` over open and closed ones, then an exact title match; its issues with `comments(last: 10)`, of which the newest by a trusted author (below).
  - Linear: the project milestones of the team with that name, their issues with both ends of `comments` (`newestBody` keeps the newer one). Seen live on 2026-10-25: Linear's default order is by `createdAt`, newest first, and an edit does not move a comment, so `first: 1` is the newest; a changelog draft of a Linear milestone took each task's closing comment.
- The optional `logTime(id, entry: TimeEntry)` with the adapter's `logsTime` (EKR-35) — the agent's active time on a done task written into the tracker's time tracking; Tally calls it once per task (`docs/tally.md`, "Task time"), through the profile of the task's project as `timeTrackers` gives it. `entryMinutes` makes whole minutes, at least one. `false` — the tracker refuses time in the project and the task needs no report; any other failure throws. Huly's report is Tally's own `TimeSpendReport`, not this operation; GitHub and Linear have no time tracking.
  - GitLab: `POST /projects/:path/issues/:iid/add_spent_time` with `duration` `<n>m` and the `summary` label; a 403 (below Reporter, or the project's time tracking off) is `false`.
  - Jira: `POST /issue/<key>/worklog?notifyUsers=false` with `timeSpentSeconds`, `started` — the last turn minus the time, as `…T10:13:00.000+0000` — and the label as an ADF `comment`; a 403, or a 400 whose `errors` name no field of the request (`JiraHttpError.fields`), is `false` — no "Work on issues" or tracking off; Jira words it in the account's language, so the text is never matched (EKR-91). A 400 naming a field is our request's fault and throws.
- The `brief` key (global and per project — `{ "key", "repo", "brief" }`, applied on the fly) decides whether the description goes into the prompt. Unset or `null` (BTN-225) it is auto, `briefOn` in `src/service.ts`: on exactly when no enabled package of the project brings the adapter's MCP server (`mcpServer`, for Huly `huly`) or, for a tracker the tasks server serves, `tasks` (BTN-882, "The tasks server" below), so a project with the tracker's plugin gets only the task id and one without it gets the task, with nothing to switch. `true` or `false` overrides it; with `false` the packages must bring the server: without it the set has the problem `noTrackerMcp`, the chain pauses with the reason and goes on by itself once it is gone (`chain.noTrackerMcp`, `docs/chain/pr-mode.md`). An adapter without `mcpServer` has the brief on under auto.
- Each profile in use has its own connection and poll (`src/tracker/link.ts`, `poller.ts`) and a card on the `/status` page (`TrackerView`: its state, last good poll, error and, per project and task feed it reads, when it last read it — `readAt`, `docs/web/project-page.md`). A failed call closes the connection and the next one connects again, except an answer that the project, team or issue asked for is not there (`TrackerNotFound`, BTN-317): closing would fail the calls of the profile's other projects under way on it ("Connection closed" in Huly), so a project deleted or renamed in the tracker would stall them all. A project's read that fails the same way on every refresh is logged once, and once more when it reads again. A project's task feeds (BTN-66, `docs/chain/entry.md`, "Task feeds") are read as projects of their own ids, each on its own profile. A task link goes by the tracker of its project or feed (`trackerUrls`, the `issueUrl` template with `{id}` or `{number}`), one of no known project by the default profile of the tracker most projects run on (`trackerUrls.default`, `linksTracker`: a tie goes to the first project's, no projects — no link); the stats link a task by the url its launch recorded, the template only without one. A project with nothing to run links to its page in the tracker and to each feed's in the feed's (`trackerUrls.pages`, by the project's or the feed's id, BTN-329; the optional `projectUrl`, checked live on 2026-10-21): GitHub — `https://github.com/<owner/repo>/issues`; Huly — `<url>/workbench/<workspace>/tracker/<project _id>/issues`, the `_id` learned on the first read of the project's tasks (`HulySource.projectIds`); Linear — the team's `https://linear.app/<urlKey>/team/<KEY>/all`, or for a key narrowed to a Linear project that project's `url` + `/issues`, again known after the first read (`LinearSource.projectUrls`). Until then the button is not shown.

- A tracker call that times out logs its operation, elapsed time and request count once until that read succeeds; recovery logs the count of the failures. Automatic task and chain reads pass a retry key to `TrackerLink.run`: the same read waits 20, 40, 80, 160, then at most 300 seconds after successive timeouts, without reconnecting during that delay. Other reads do not clear its count, and a profile reset clears the delay. A broken connection is the same reason for that delay as a timeout — the tracker did not answer either way (Node's `fetch failed` with the reason in `cause`, or the request's own timeout). The call's abort signal cancels outstanding HTTP work through `trackedFetch`. A successful call over half the timeout logs its measurements at most once per ten minutes per operation and profile. GitLab, GitHub, Linear and Jira count HTTP requests in each call separately and report the longest request's path without its query or upload secret; Huly reports the count as unavailable. The timeout error on the page is unchanged.
- **A tracker that did not answer (BTN-825).** The link remembers the error the tracker did not answer with — a timeout or a broken connection — and while it holds, every call the page asks for fails at once with that error instead of waiting the whole timeout again. Those calls go through `TrackerLink.page`: the card (`GET /api/tasks/<id>`), a file of a task, the task's actions ("Into the chain", "To the backlog", the labels, the milestone), the vocabulary (`GET /api/projects/<id>/vocabulary`) and the changelog's list of a milestone. The chain's own reads keep going through `TrackerLink.run`: they are what brings the tracker back, and they wait their own delay. Any call that answered — even that what was asked for is not there — clears the memory, and the page goes on as usual. The page's answer is the error itself: the same code and the same text it got after the timeout. `GET /api/projects/<id>/tools` reads no tracker — the project's own folder and the account folders — so it is never held by a tracker that does not answer.
- Status polling logs consecutive failures with the same error text (including its cause) once per profile; a changed error is logged again. The first successful poll after a failure logs `<profile title>: reads again`, even if no status changed. With no watched tasks, polling is skipped and does not count as recovery. Project refreshes keep their own failure state.

### Writing task labels (BTN-507)

The optional `TaskSource.relabel(id, { add, remove })` returns the saved label names. `trackerOf` forwards it only when present; a connected tracker publishes the capability as `trackers[].relabel` (absent in older snapshots means false). Remove first, then add; names are trimmed and compared with `toLocaleLowerCase`, as in `toTask`. Existing labels keep their spelling. Other labels stay attached. An empty add list can remove all labels.

| Adapter | Label definitions and write |
| --- | --- |
| Huly | Workspace issue `TagElement`s; creates a missing definition in `core.space.Workspace`, using the default issue category or `tracker.category.Other`. Removes and adds `TagReference`s through collection operations, preserving the issue's label counter; returns the references read back. |
| GitHub | Pages the issue and repository labels; creates missing repository labels with `createLabel`, then writes `updateIssue.labelIds` once and returns its labels, paging the remainder. |
| GitLab | Reads the issue and project labels (ancestor group labels included); creates missing project labels, then replaces `labels` in one issue update and returns the saved names. |
| Linear | Pages the issue labels and the team's available labels (workspace labels included, groups excluded); creates missing labels with the issue's `teamId`, then writes `issueUpdate.labelIds` once and returns its labels, paging the remainder. A mutation with `success: false` is a refusal. Adding the name of a label group (`isGroup`) that no usable label shares is refused with `task.labelGroup` before any write (BTN-668): Linear puts no group on an issue and creates no label under a group's name. |
| Jira | Labels are free strings: replaces `fields.labels` and reads the saved names back after Jira's empty update response. No definition is created. |
| Forgejo | Reads the issue's labels and the repository's plus its organization's (a user's repository answers 404 there, taken for none; a token without `read:organization` gets 403 first, and then the repository's `/teams` decides: 405 is a user's repository with no organization labels, anything else keeps the scope error); creates a missing repository label in grey, then replaces the issue's labels by id (`PUT …/labels`) and returns the saved names. |

`POST /api/task/labels` takes `{ task, add: string[], remove: string[] }`; both lists are required and an empty list is allowed. `taskControl` (`src/tracker/control.ts`) routes by the task's reader, including feeds. After a successful write it immediately refreshes the reader, as `ready` does: labels can admit a task to the chain, so `fillMilestone` must run before it enters. Without a refresher it patches the reader's task with `toTask`, updates the chain and broadcasts state, including the derived run labels and question flag. Neither path waits for the next tracker poll. The card itself is read afresh through its existing GET route. An unsupported adapter gives `task.cannotRelabel`; a failed read/create/write gives `task.relabelFailed`, with a fix link to tracker profiles; a refusal the adapter names itself (a `NoticeError`, such as `task.labelGroup`) reaches the page as it is. The underlying error remains the error's cause, not page text. Every refusal, of the label route and of "Into the chain" and "To the backlog" alike, logs a `relabel:` line with the task, the tracker and the cause. A failed operation can have created a definition or changed some Huly references before the refusal; there is no transaction across tracker requests. Refresh the task before retrying.

Fixtures cover all six adapters, case matching, missing definitions, pagination, clearing labels, failures, service state and HTTP validation. Every provider but Forgejo, its refusals included, was checked live by 2026-11-01 ([verified log](verified/trackers.md)); Forgejo's is in [unverified](unverified/trackers.md#forgejo-issues-btn-476).

### Assigning experiment break labels (BTN-505)

`npm run break-labels -- [--dry-run] <project key or GUID> ...` is a separate script, using the installation's database settings and profiles. A non-unique key is refused with the matching GUIDs. `src/stats/break-labels.ts` selects compaction for even task numbers and handoff for odd ones, including backlog and parents but excluding Won/Lost. It re-reads each task, preserves any existing break label (even both or a mismatch), and adds a missing label through `TaskSource.relabel`. JSON lines carry UTC time, project GUID, task ID/number, expected and actual labels and action. No page or service feature is added. The [preregistered protocol](posts/compaction-ab.md) defines analysis, deviations and an optional five-minute Windows schedule; the user registers it. The source checkout's dependencies are required.

### Moving a task to a chosen status (BTN-554)

The optional pair `TaskSource.moveTo(id, name)` and `statuses()`, and the optional `name` of `complete(id, name)`. `moveTo` moves a task to the status of that name (compared as `sameName` does) and answers the status it is in, `null` when the tracker has no way there; `statuses()` lists every status the profile's tracker has, a name once (`uniqueStatuses`). Only Huly, Linear and Jira have them; a kind's view carries `moves: true` for the page.

| Adapter | `moveTo`, `statuses`, `complete` with a name |
| --- | --- |
| Huly | The status of the name in the project type (`namedStatus`), written as any status change; every issue status of the workspace. `complete` takes the named one only of the `Won` category, another is an error. |
| Linear | The state of the name in the issue's team (`moveState`); `workflowStates` of every team the key sees, paged by 50. `complete` takes the named `completed` state of the team. |
| Jira | The workflow's transition into a status of the name; none — logged and `null`. `/rest/api/3/status` for the list. `complete` takes a transition into a Done-category status of that name, none is an error. |

`StatusMover` (`src/tracker/mover.ts`) moves a task when Even Keel starts it (`start`) and when it opens the task's pull request (`review`), by the profile's moves and the source's over them (`movesOf`, `src/chain/moves.ts`). Only forward (`moveVerdict`): on a start only a task of the `ToDo` category, on a pull request any open one, never one already there; a target the rules put out of the chain is not tried (`statusMove.outside`), since the chain would let the task go at once. A refusal or an error is logged, never stops the chain, and stays in memory by reader (`trackers[].moveFailures`) until a later move of the task goes through; the page shows those of open tasks. The close goes through the closer as before, with the chosen done status (`doneMove`): one the rules do not take for done is not tried (`statusMove.notDone`), a refused one is `tracker.completeRefused` with `status` and `level`, retried as any refused close. `level` (`profile`, `source`) leads the notice's button to the setting.

## Contract tests on live trackers (BTN-470, `src/e2e-trackers/`)

The adapters' unit tests run on recorded answers and do not see a live API change. `src/e2e-trackers/contract.test.ts` is one set of cases over `TaskSource` and `TrackerAdapter`, run against each stand in turn: sign in (`account`), list projects, `create` a task and read it back in a `ToDo` status (`tasks`), find it among `chainTasks`, `brief`, `unready` and `ready`, `moveTo` the stand's `active` status, `relabel` on and off, two comments and `commentsAfter`, the `card`, a `blocks` pair read from both sides, and `complete` — `true` once, then `false`. ## Profiles (BTN-200, `src/profiles/`)

The profile dialog's primary action is **Check and save**: it checks new or changed values, then saves in the same operation. **Check** alone remains available without saving. A fresh check is reused; a duplicate warning from an automatic check stops the first save, and a second press with unchanged values accepts it. Errors stay in the dialog. Fields are inert until the operation ends, and a suggested name is sent with the first save unless the user supplied one.

The profile dialog groups OAuth and the fallback token in one "MCP for sessions" box (BTN-491). Jira's separate `JIRA_MCP_TOKEN` goes inside it, below OAuth. Linear, GitHub and GitLab have no OAuth (BTN-604): their MCP servers take the tracker's own token (`mcpKeys`), so the kind's view says `mcpShared` and the box is one line pointing to the token above. The list and dialog show "MCP: connected through OAuth" or a reconnect state, without an access-token expiry. A completed unsaved grant explains Check → Save and the ten-minute deadline from starting consent; closing by any dialog control or backdrop asks before losing it. Changing the grant invalidates an earlier check.

Both `profiles/check` and `profiles/save` check the selected MCP OAuth grant in addition to REST (`Profiles.checkedAccount`, `McpOAuth.check`, `src/profiles/mcp.ts`): refresh on expiry or once after refusal, then call `getAccessibleAtlassianResources` and require the site's URL. A refused refresh or repeated authorization refusal requires reconnecting; transient errors remain retryable. A fresh draft keeps refreshed credentials in its flow until saving, under its original deadline. With OAuth selected, REST checks omit Jira's unused fallback MCP token, including the periodic REST recheck; saving retains that token for later use after disconnecting OAuth. The check's success shares the tracker result line; failures use its existing error area.

**The grant's person** (BTN-590). Atlassian gives a grant to whoever is signed in to Atlassian in the browser, perhaps not the person of the REST token, and then sessions write under another name with other rights. After the site check, a grant's probe also calls `atlassianUserInfo` (`checkJiraMcp` with an `authorization`; an API token's person is the profile's e-mail, so it is not asked), and its `account_id` and name ride on the grant as `OAuthRecord.user`, kept through refreshes; a failure there leaves the person unknown and the check passes. The REST side is `ProfileAccount.user` (Jira's `/myself` `accountId`), which `Profiles` remembers per profile from every save and periodic recheck. Different ids give `profiles.mcpOtherAccount` — a warning, never a refusal: `CheckResult.mcpWarning` in the dialog, which checks a new grant at once, and `ProfileView.mcpOAuth.warning` in the row, each a warn band with "Connect again". Unknown on either side is silence. Linear, GitHub and GitLab have no grant to compare (BTN-604). Live behaviour: [unverified](unverified/trackers.md#the-person-of-a-jira-mcp-grant-btn-590).

- A profile is one tracker account: id (GUID), kind (`huly`, `github`, `linear`, `gitlab`, `jira`, `forgejo`), name, values, default flag, whom it signs in as and when its token expires. A kind with projects but no profile is `none:<kind>`, and the wizard's check says to add a profile.
- The first profile of a kind is its default, and the only one stays so. A new default does not move the projects and feeds the chain has started on the old one (`trackerLocked`): `Profiles.setDefault` links them to the old profile by name (BTN-435); a profile's address stays while anything runs on it (`profiles.hostLocked`). The default profile's values are written into the `env` of the global `~/.claude/settings.json`: a session started by hand gets only the default profile of each kind, never another one — a limit, not a bug. It also gives the GitHub Actions token to projects of other trackers, unless a project names its own (`remoteProfiles`, `docs/ci.md`).

- A profile may set the chain rules of the projects and feeds on it (BTN-66): `active`, `terminal`, `requiredLabels`, `excludedLabels` in `tracker_profiles.rules`, between the shared rules and a project's own (`docs/chain/entry.md`, "Entry into the chain"). `/settings` has an option per tracker profile in the "Whose rules" pick of the Chain rules group, after "All trackers" (`web/src/pages/ProfileRules.tsx`), suggesting the statuses and labels of its projects' vocabularies; the save (`profiles/rules`) is refused when a project or feed on the profile would clash. A feed's profile is `feed_profiles`; a profile a feed runs on counts as in use.

The home page dims a project card of a turned-off profile, says so instead of red errors and offers "Turn on"; a Start a stale page still shows asks "Profile X is off — turn it on?" and only turns it on.

- Import at the first start: the tracker variables of `.env` become the default profile of their kind, and every project of that kind runs on it; the mark `profiles.imported` keeps a second start from importing again, and the log says so. - **MCP through OAuth** (BTN-475, BTN-485, `src/profiles/oauth.ts`, `oauth-protocol.ts`): Jira profiles have "Connect MCP through OAuth" in the profile dialog (`web/src/pages/ProfileMcp.tsx`), on a new profile too. Only Jira, because Rovo MCP v2 takes no REST token: Linear's and GitHub's MCP take the tracker's token, and OAuth there only added a second identity that nothing compared with the token's owner (and for GitHub a user's own OAuth App), so BTN-604 removed it; a stored Linear or GitHub grant is dropped when the profiles are read (`readProfiles`) and its row is cleared at the next save. The provider is fixed in `MCP_OAUTH` (Rovo `https://mcp.atlassian.com/v2/mcp`); another kind is refused as `profiles.oauthUnsupported`. Discovery takes protected-resource metadata from the MCP endpoint's 401 `WWW-Authenticate` `resource_metadata`, or `/.well-known/oauth-protected-resource<resource path>` without that parameter. The resource must match the configured MCP URL and its metadata must stay on that origin; `authorization_servers` selects an issuer from the provider's explicit authorization-origin allowlist (`https://auth.atlassian.com`). Its metadata comes from `/.well-known/oauth-authorization-server<issuer path>`; the issuer must match exactly, S256 must be supported, and every endpoint must pass the same allowlist before registration. Redirects, embedded credentials and non-HTTPS metadata or endpoints are refused. A public client is registered dynamically (`token_endpoint_auth_method: none`, ignoring any returned client secret). Registration and consent carry the challenge's `scope`, otherwise all resource `scopes_supported` (the set checked live in BTN-416). Discovery and registration on the live provider were checked in BTN-485 ([verified log](verified/trackers.md)). The server binds an attempt to the profile's fields and refuses blank ones only as `profiles.incomplete`, so the dialog stops a check, a save or a connection itself and names the blank fields by their labels (`unfilled`, `web/src/pages/profileForm.ts`, BTN-597). The flow is PKCE S256 with a one-use `state`; a callback's `iss` must match the discovered issuer including its path, and is required when the metadata advertises it. `profiles/oauth/start` answers the consent URL, the browser window ends at `GET /api/profiles/oauth/callback`, which exchanges the code with the MCP `resource` (the grant is checked with `getAccessibleAtlassianResources` against the profile's site) and redirects to `/settings#trackers` with no code or token in the URL; the dialog polls `profiles/oauth/status` and closes the window. An attempt is bound to the draft's id, kind and values and lives 10 minutes, at most 32 at once; `profiles/check` and `profiles/save` take its id as `oauth` (`null` drops a stored grant). A changed host or account field of a stored profile with a grant is refused (`profiles.oauthExpired`): a new identity never keeps the old MCP one.
- OAuth failures go through `Profiles`' logger as one English line with the profile kind, step (`registration`, `consent`, `code exchange`, `grant verification`, `refresh`) and HTTP status plus the provider's string `error`, or the exception message (`oauth-error.ts`, BTN-484). A callback carrying `error` or no `code` is the `consent` step: it logs only the provider's `error` (or `no code`) and the page gets `profiles.oauthDenied`; every later failure, including an HTTP 400 on the exchange or a 401 on the grant check, gets `profiles.oauthFailed` (BTN-588). Response bodies, `error_description` and stacks are omitted; known credentials, callback codes, state and verifiers are redacted, including URL-encoded forms, and whitespace is flattened. The page still gets only its notice code. Stored and unsaved refreshes share this diagnostic path. Checked over a local HTTP provider fixture, including the actual callback's clean redirect ([verified log](verified/trackers.md)); no live provider refusal was induced.
- The callback address is the page's own origin, which the request's `Origin` must match with `Host`: HTTPS, or `http` on a loopback host only (`profiles.oauthAddress`). A page opened on another machine over plain HTTP cannot connect; open it over HTTPS (Tailscale Service) or on localhost of the service machine.
- For direct network access, `server-guard.ts` issues an `even-keel-oauth` cookie only on an authenticated `POST /api/profiles/oauth/start`: `HttpOnly`, `SameSite=Lax`, callback path, ten minutes. Its value is an expiry signed with HMAC-SHA256 under the current access token and a callback-specific purpose. `guard.ts` accepts it only on the exact `GET /api/profiles/oauth/callback`, after Host/Origin checks; it cannot authorize another route, method or bearer request. The ordinary access cookie stays Strict, and the existing OAuth state, PKCE and draft binding still decide whether a code can be exchanged. On completion or guard refusal, `oauth-response.ts` serves a static page that replaces the history URL with `/settings#trackers` and reloads it, with `no-store`, `no-referrer` and a hash-restricted CSP. Committing that page first restores the Strict cookie for the settings request; an HTTP redirect would keep it absent across the cross-site navigation. Guard refusals keep 401/403 and never call `finish`. Checked in Chromium against isolated real server routes and a simulated provider ([verified log](verified/trackers.md)).
- The grant is `tracker_profiles.mcp_oauth` (step 15), never in the profile's values, the key pool, `settings.json` or a session's environment; the page sees only `mcpOAuth.state` (`connected`, `reconnect`) and the warning about the grant's person, never its tokens. The gateway refreshes it single-flight (compare-and-swap, so a late refresh cannot restore an edited profile's grant), 30 s before expiry or after a 401, saving a rotated refresh token and using it in the next exchange; a refused refresh or a second 401 sets `reconnect`, and the profile's row shows "MCP: reconnect needed" with the dialog's "Connect again". Refused is a 401, `invalid_grant`, `invalid_client`, or any 4xx of an OAuth endpoint with an OAuth `error` except 408, 429, `temporarily_unavailable`, `server_error` and `slow_down` (`oauthHttpError`, BTN-589): Atlassian answers a refresh of an app revoked in Connected apps with 403 `unauthorized_client`, which used to stay retryable and asked the token endpoint at every probe. With `reconnect` set nothing goes to the provider until a new grant. A stored grant's failing refresh is logged once per reason, and `MCP OAuth refresh works again` once it succeeds. Old Jira v1 grants need a new connection through the profile dialog. The Atlassian MCP V2 token (`JIRA_MCP_TOKEN`) stays the second way for a server without a browser.
- A tracker and a CI in one profile (BTN-201, BTN-476): Forgejo (`forgejo`) was a CI's kind only, with no `projects`; since BTN-476 it is the adapter `src/forgejo/adapter.ts`, and a stored profile serves the tracker as it is, with no schema step: the values are the same `FORGEJO_URL` and `FORGEJO_TOKEN`. `profileKinds` (`src/profiles/model.ts`) still takes CI-only kinds as a second argument (a kind without `projects`: no `settings.json`, its card shows the CIs instead of projects), but none is passed now. ## GitHub Issues (BTN-65, `src/github/`)

- GraphQL `api.github.com` with the profile's `GITHUB_TOKEN` (fine-grained, Issues: Read and write; Actions: Read for the CI). A fine-grained token covers one owner: a personal repository and an organization's need two profiles. The expiry comes from the `github-authentication-token-expiration` header (`2026-11-03 13:47:15 UTC`, `expirationOf`; checked live on 2026-10-18 with a classic token, a fine-grained one is in `docs/unverified.md`).
- An open issue is `Open` (`ToDo`), one closed as completed (or without a reason) is `Completed` (`Won`), not planned and duplicate are `Lost`.
- Blockers are the native "blocked by", the parent and subtasks are sub-issues, priority is the label `priority: <level>` (or `priority/<level>`), there is no estimate (0). A blocker, parent or sub-issue from a repository without a project has the ID `owner/name#number`. `children` reads the `subIssues` of an issue page by page (BTN-606).
- `complete` closes the issue as completed. GitHub has no backlog status — keep entry into the chain on a label (`requiredLabels`): an open issue without it waits in the page's backlog, and "Into the chain"/"To the backlog" put it on and take it off (BTN-509, `docs/chain/entry.md`). In a public repository that backlog holds outsiders' issues too; only people with triage rights can label one. A pull request is never a task.
- Outsiders (EKR-19, `src/github/trust.ts`): anyone can open an issue and comment in a public repository, and a session has Bash on the user's machine. Only comments of `OWNER`, `MEMBER`, `COLLABORATOR` (`authorAssociation`) and of the token's own login (`viewer`) reach a session: a reply to a question (`commentsAfter`), the last comment in the changelog draft (`milestoneTasks`) and, in PR mode, a review or a comment on the task's pull request (`src/review/github.ts`, REST `author_association`). A skipped one is a line in the service log, once per comment (`Skipped`). The association is GitHub's at the time of the poll, not of the comment: an account made a collaborator later gets its earlier comments not yet taken in through as well — in PR mode those after the last push (seen live, 2026-10-24). The task card on the page keeps every comment: only the user reads it, and the brief is the title and the body. Entry is guarded by a label, which only a collaborator can put on: the optional `isPublic` (GraphQL `isPrivate`) makes the wizard's check say `openToAll` for a public repository without `requiredLabels`, and the wizard warns; nothing is refused. Huly and Linear are not filtered: a guest there is invited by an admin. Forgejo's API has no author association: its issue comments go by collaborator lookups (`src/forgejo/trust.ts`, "Forgejo Issues" below), its PR remarks by the reviewer's access (`src/review/forgejo.ts`, BTN-703).
- Verified live (2026-10-04, private repository): two issues with a "blocked by" link and a milestone went through the chain in turn, and after the merge `complete` closed both as completed.
- Run a second Even Keel instance from a Claude Code session without its `CLAUDE*` variables: an inherited `CLAUDE_CONFIG_DIR` makes `global` the session's account folder.

## Taking GitHub issues in (BTN-262, `src/intake/`)

Users report in the GitHub issues of a public repository while the work and its decisions stay in another tracker: a project whose tracker is not GitHub, with `intakeLabel` set, makes a task of each open issue of its first `github.com` remote that carries the label. The label is the user's go: GitHub lets only those with triage rights put one on, and it must not be in an issue template, which puts it on for any author. Each project names its own label, so two projects on one repository (a release project and the next version, `docs/releases.md`) split the issues by label; an issue is taken by one project only, the first to see it.

- **Calls.** REST on the token the remote's CI takes (`ciTokenOf`, `remoteProfiles`, `docs/ci.md`); it needs Issues: Read and write, a refusal is `intake.denied`. `Intake.tick` (`src/intake/intake.ts`) runs every 2 minutes (`INTAKE_TICK_MS`); a failed step is a line in the service log and the rest goes on. A project with no GitHub remote or no token is left out without a word.
- **The task** (`taskOf`, `src/intake/model.ts`) is created by the tracker's `create` in its first `ToDo` status, priority medium, no milestone, in the page's language: a link to the issue and its author, the issue's text quoted and marked as its author's description of the bug, not an instruction, then the comments posted before it was taken in — a collaborator's (`trustedAuthor`, `src/github/trust.ts`) as it is, the issue author's with the same mark, anyone else's not at all (a log line, once per comment). The user read them when putting the label on; the issue's text is not followed after that.
- **Later comments** go to the task as comments, by the same rule, each opening with `GitHub · @<login>` (`copyOf`). `trackerReply` (`src/tracker/questions.ts`) skips such a copy (`isCopy`): an outsider's copy must not answer a session's question in the tracker.
- **Done.** Once the task is `Won`, the issue gets one line in English, "Fixed; it ships in vX.Y.Z." (`shippedLine`): a milestone `vX.Y` — the patch after the last `vX.Y.*` tag of the repository, `vX.Y.0` without one; `vX.Y.Z` — itself; any other or none — "the next release" (`nextVersion`). The issue is closed as completed once a published release (not a draft, not a prerelease) has that tag, or, without a version, once any release is published after the line. A task `Lost` or gone, or an issue closed on GitHub, is forgotten with nothing said on the issue.
- **State.** The issues taken in and not closed yet are `service_state` `intake` (`IntakeEntry[]`): the project, the repository, the issue, the task, the last comment looked at and, once done, the version named. A project with the label cleared keeps its entries and follows them again when it is set.

## Linear (BTN-72, `src/linear/`)

Milestones carry `sortOrder` and their parent project's id from `projectMilestone` on task and card reads, and from `projectMilestones` in the picker. The neutral `TaskMilestone.trackerOrder` scopes that position to `linear:<project id>`; cycles remain separate from milestones.

- GraphQL `api.linear.app` with the profile's personal key `LINEAR_TOKEN` — in `Authorization` without `Bearer`.
- The task ID is the Linear identifier as is (`NAM-12`): the branch, the commit and the MCP in the session name the task the same way. The optional `linear` in the project object narrows the team to a Linear project (its name, case-insensitive). Without a team in it the project key is the team key, as before. With one — `NAM/Web app`, or `NAM/` for the whole team (`linearPlace` in `src/linear/model.ts`, BTN-73) — the key is only Even Keel's, so several Even Keel projects work on one team, one per Linear project; the task IDs stay the team's. Two projects with the same `linear` place share a read and split it by milestone. A whole-team project (`NAM/` or the key `NAM`) next to a project of one of its Linear projects reads that project's tasks too, and the config does not catch the overlap: give them milestone rules that split them, or narrow both.
- The status goes by the team's workflow state type: `triage` and `backlog` — `UnStarted`, `unstarted` — `ToDo`, `started` — `Active`, `completed` — `Won`, `canceled` and `duplicate` — `Lost`, an unfamiliar type — `UnStarted`; the name is the state's name. Linear has its own backlog, entry into the chain is as in Huly.
- Blockers are the inverse `blocks` relations, the parent and subtasks are native, priority is native (1 Urgent … 4 Low, 0 — none), there is no estimate (0: Linear has points).
- The milestone is the project milestone (`projectMilestone`), not a cycle: Linear itself carries unfinished work over to the next cycle, so an order by cycles will not work.
- `complete` is the first state of type `completed` by `position` in the task's team; a closed task (`completed`, `canceled`, `duplicate`) — `false`. A team's own auto-close of parents does not conflict with Even Keel's: whoever is first closes it.
- `children` (BTN-606) reads the issues with the filter `parent` (team key and number) page by page, with `includeArchived: true`: Linear archives closed issues after a while, and a parent still counts them.
- The link is `linear.app/<urlKey>/issue/{id}`; the adapter learns the organization's `urlKey` on connecting, and there are no links before that.
- API traps: query complexity is up to 10000, a list without `first` counts as 50 — nested ones get an explicit `first`. `issue(id)` on a nonexistent task fails the whole response — tasks by ID are read with the filter `number: { in }` by the team key. Linear also merges fields of one object inside `or` through "or" — an explicit `and` is needed.
- Verified live (2026-10-04, a team narrowed to a Linear test project): two tasks of a project milestone with a "blocks" link went through the chain in turn — the blocker first despite the second's higher priority — and after the merge `complete` moved both to Done, the worktrees and branches were cleaned up.

## GitLab Issues (BTN-410, `src/gitlab/`)

The profile uses `/user` and `/personal_access_tokens/self`; missing expiry support (404) leaves `expiresAt` null, but a known token without `api` is refused. The registry supplies the profile kind, wizard and settings choices through the existing tracker-place mechanism, with no database schema change. Profile changes take the existing live path through `Profiles` and `TrackerLink`.
- A project names its full path (`gitlab: group/subgroup/name`), while task ids are `<Even Keel key>-<iid>`. The wizard suggests it from a remote on the profile's own server (`projectOfRemote`, BTN-607): the remote's host must be that of `GITLAB_URL` (`gitlab.com` without one), an HTTP remote must sit under its installation prefix, which is stripped, and nested groups are kept (`gitlabRepo`, as CI reads it); a remote of another server suggests nothing, since its path names no project the profile reads. REST path segments are URL encoded; ids and links keep subgroups. Opened is `ToDo`, closed is `Won`, priority comes from `priority::<level>` or `priority: <level>`, estimate is 0. Every REST page is read through `x-next-page`, with a full-page fallback when that header is absent.
- Task lists and status polls read hierarchy and linked-item widgets together through GraphQL in batches of up to 20 issue IIDs (`batch.ts`), with work-item pagination. Overflowing child connections are completed through the individual hierarchy reader; overflowing or absent link widgets use the paginated REST links endpoint. An older schema retries without the link fragment, then without GraphQL if hierarchy is unavailable. REST issue and relation reads have at most six workers; batches and projects are processed in order, with no relation cache across polls. Closed issues kept only for milestone progress need no relations; status polls also skip relations of closed issues outside active milestones.
- Native links supply `is_blocked_by`, `blocks` and `relates_to`. Only the first orders this task. Free has only related links; no text dependencies are parsed. The card keeps all three kinds and reads its links through REST. Work-item hierarchies are read through GraphQL, including child pagination, on Free too; an absent widget or an older schema leaves parent/children empty. Authentication and runtime failures propagate rather than appearing as empty relations.
- Milestones include inherited group milestones, the current closed choice, assignment/copy/clear and tasks of a named milestone for changelog drafts. Closed tasks sharing active milestones contribute progress. Cards show every human note, in time order; answers and last comments use only the token owner's id or a current membership from `/members/all/:user_id` with `access_level >= 20` (Reporter), including inherited membership. A 403/404 membership lookup excludes the author, and skipped notes are logged once. System notes are excluded. Uploads appear on the card and inline in its text; trusted answers carry their files to the session through the authenticated file route.
- Fixtures cover model mapping, hierarchy, API operations and trust decisions. The adapter and the MCP plugin were checked live on GitLab.com and a self-managed CE 19.5, at the root and under a path prefix: answers from a Reporter who is a member through a group, the plugin in Claude and OpenCode sessions, and a profile token revoked mid-chain (the tracker goes down, a new token saved in the profile is picked up live). The hierarchy of older versions was not checked; the guide recommends 19.5 or later. GitLab CI and merge requests use the same profile (`docs/ci.md`, `docs/chain/pr-mode.md`).

## Jira Cloud (BTN-417, `src/jira/`)

- The optional profile secret `JIRA_MCP_TOKEN` is only for `jira@even-keel`: `mcpValues.JIRA_BASIC_AUTH` is base64 of `JIRA_EMAIL:JIRA_MCP_TOKEN`, never the REST token. Enable API token authentication for the Atlassian MCP server in the organization's settings first, then [create an Atlassian MCP V2 application token with all scopes](https://id.atlassian.com/manage-profile/security/api-tokens?autofillToken&appId=mcp-v2&selectedScopes=all). A profile check with this field set signs in over REST and calls `getAccessibleAtlassianResources` through MCP v2 (`src/jira/mcp.ts`, JSON and SSE replies, session cleanup); the result must include the profile site's URL. Without the site, `jira.mcpSite` asks for a new token after the admin switch; an MCP refusal is `jira.mcpToken`. Both offer the creation link on the profile form. `tools/list` alone proves no access. The field uses the existing credentials JSON in `tracker_profiles`, with no schema or file format change. The gateway takes profile edits live; a profile without the field still works over REST, while its Jira package names `JIRA_MCP_TOKEN` as missing.

- REST v3 with Basic `JIRA_EMAIL:JIRA_TOKEN`; `JIRA_URL` is the site's origin only (`https://<site>.atlassian.net`, https, no path: `siteUrl`, else `jira.url`), a profile with only some of the three is `jira.incomplete`. `JiraApi.open` signs in through `/rest/api/3/myself` on the site; when the site refuses (a token with scopes works only through the gateway), it reads the cloud id from `<site>/_edge/tenant_info` and tries `https://api.atlassian.com/ex/jira/<cloudId>`, and every later call goes to the base that answered. Jira Data Center is out of scope; Jira has no CI, the remote's CI and PR mode apply as for any tracker.
- The Even Keel key is the Jira project key and the task id is the issue key as it is: no `projectKey`, no `closingRef`, no `isPublic` (a Jira site has no anonymous issue filing by default). Comments are not filtered by author, as in Huly and Linear.
- The status goes by its category: `new` — `ToDo`, `indeterminate` — `Active`, `done` — `Won`, an unfamiliar one — `UnStarted`. Jira has no status kind for the backlog: a Jira Software backlog is a board's view, not a status, and the API cannot tell its issues from ready ones. So a `new`-category status whose `untranslatedName ?? name` is `Backlog` (`sameName`) is `UnStarted` and stays out of the default rules; a board whose backlog is not such a status keeps unread issues out by `requiredLabels` or its own `active` list. Issue responses, including `search/jql`, omit `untranslatedName`: `resolveStatuses` fills it by status id from `/project/<key>/statuses` for task reads, cards (including links to other projects) and `ready`. Each call shares one catalog per project and fetches it afresh on the next call; `chainTasks` reuses the catalog it already read. The localized `name` is kept for display and explicit status rules. `ready` moves an `UnStarted` issue through its first transition to a ready `new`-category status; `unready` moves a `ToDo` or `Active` one through its first transition to an `UnStarted` status and, where the workflow has none, leaves it alone (`null`): "To the backlog" then only takes the required label off. `chainTasks` reads the project's statuses (every issue type), turns the open ones into ids and searches `status in (…)` through `POST /search/jql` with `nextPageToken`, plus the closed issues of the open ones' fix versions for the milestone progress.
- `complete` takes the first transition to a status of the `done` category; with none from the current status it logs which status had none and returns `false` — the task stays open, as `complete` with no change does. Tasks by id go through `POST /issue/bulkfetch` by 100; an id Jira does not have lands in `issueErrors` and is left out.
- Blockers are the issue links of the type named `Blocks` (`inwardIssue` — this issue is blocked by it, `outwardIssue` — it blocks), found by name at connect: without such a type `connectJira` throws `jira.blocksType` with the types the site has, so a renamed type stops the profile's projects instead of running them out of order. "Related" on the card is `Relates` either way; other link types are dropped. The parent is the `parent` field, children are subtasks and, for an issue above the base level (`issuetype.hierarchyLevel > 0`, an epic), the issues with `parent in (…)`, counted by a JQL search of 50 keys at a time.
- Priority: the built-in Highest, High, Medium, Low, Lowest by name (urgent, high, medium, low, low); a site's own scheme by its place in `/priority/search`, spread over urgent…low; `create` picks the built-in name for the level, else the place. The estimate is 0. The milestone is the first fix version in the chain's milestone order. `orderedVersionsOf` reads every page of `/project/<key>/version?orderBy=sequence`, including released and archived versions, and gives each its zero-based position scoped to `jira:<key>`. Task reads share one catalog per Jira project for that call, fetch it afresh on the next call, and fail through the normal tracker error path when the catalog fails. Cards and the picker use the same catalog; `create` and `setMilestone` consult it when choosing among several fix versions. A version absent from the catalog has no position and uses the fallback. `milestones` offers unreleased, unarchived versions plus the issue's own; `moveMilestone` replaces all fix versions with the one picked (`null` — none), `setMilestone` copies the first version of a task of the same project. Sprints are not milestones.
- Descriptions and comments are ADF: `adfToMarkdown` and `markdownToAdf` (`src/jira/adf.ts`) cover headings, lists (nested, ordered with a start, task lists), code, quotes and panels, tables, rules, hard breaks, mentions, emoji, cards, status lozenges, dates and media. Ordinary text nodes escape Markdown and HTML punctuation before their ADF marks are applied, so literal tags, emphasis and line-leading block markers stay text on the card. Inline code and code blocks keep their content; the reverse converter reads backslash escapes, including delimiters inside marks and link labels. Briefs use the same Markdown, leaving ordinary commands readable. A media node names its file by `alt`, matched to the issue's attachment by file name (`mediaLinks`); the card's attachments are the issue's, with `url: null`, and `file` serves only one of the issue's attachments, from `/attachment/content/<id>?redirect=false`. `commentsAfter` gives a comment's files by the same match.
- `create` takes the project's `Task` type by `untranslatedName ?? name`, else the first standard type of `/issue/createmeta/<key>/issuetypes` (`hierarchyLevel === 0`, not a subtask), then readies the issue. With no standard type it fails before creating anything. `vocabulary` gives the project's statuses, every label of the site (`/label`, paged) and the names of the open versions; `milestoneTasks` reads a version's issues with their newest comment (`orderBy=-created`).
- The page links `<site>/browse/{id}` and `<site>/browse/<key>`. Fixtures cover the ADF conversion, the model, the profile, the gateway fallback and every source operation (`src/jira/*.test.ts`). Localized status responses, task reads and creation were checked live on 2026-10-27 (BTN-473, [verified log](verified/trackers.md)); the remaining checks are in `docs/unverified.md`, "Jira Cloud" and "Jira MCP plugin".

One profile serves the tracker, the CI (`docs/ci.md`) and PR mode (`docs/chain/pr-mode.md`), so the token needs `write:issue` beside `read:repository` and `read:user`. A 403 whose body says `required scope(s): [...]` is `ForgejoScopeError`, a `NoticeError` with `forgejo.scope` naming the missing scopes (BTN-788): the token is alive, so it is no `CredentialsRefused`; `TrackerLink` keeps an error's notice in `TrackerHealth.notice`, and `/status` and the project page say it instead of the guess `trackerProblem` makes from the text. The wizard lists the account's repositories with issues on (`forgejoProjects`, `/user/repos`, ten pages of 50 at most) and suggests the key from a remote on the profile's host (`projectOfRemote`, as GitLab's). Lists are read page by page by `x-total-count`.

A repository may turn dependencies off; then `/dependencies` answers 404, taken for none (`dependenciesOf`), and the chain goes by milestone and priority alone. `/blocks` still answers 200 with the links stored before (Forgejo, seen live 2026-11-07), so after that 404 the card skips `/blocks` and shows both sides empty (BTN-789). Closed issues are read without their blockers: a closed task orders nothing. No subtasks: Forgejo has none.
- Priority comes from a label `priority: <level>`, `priority/<level>` or the scoped `priority::<level>`, the highest wins; `create` puts on the repository's label of that level when there is one, otherwise none. Each author is asked once per read. A skipped comment is a line in the service log, once per comment (`Skipped`). The card keeps every comment. `isPublic` is "not private": an internal repository is open to every account of the server.
- Comments carry no files (`files: []`): attachments of a Forgejo issue are not served yet; nor is `closingRef`, so PR mode's pull request does not close the issue by itself — Even Keel's `complete` does.
- The page links `<web>/<owner>/<name>/issues/<index>` and `<web>/<owner>/<name>/issues`. Fixtures cover the model, the profile's errors, the gateway's keys and every source operation (`src/forgejo/*.test.ts`); run live on own Forgejo, Codeberg and Gitea on 2026-11-07 ([verified](verified/trackers.md)), with what is still open in [unverified](unverified/trackers.md#forgejo-issues-btn-476).

## The built-in tracker (BTN-767, `src/builtin/`)

Even Keel's own tasks, in its state database (step 30, `docs/storage.md`): a project with `tracker: builtin` needs no account, profile or key. The adapter `builtin` (`adapter.ts`) is marked `own`, so the wizard's tracker list, the profile kinds and the "no profile" log leave it out; `attachBuiltin(db)` hands it the database at the service's start. Its status moves are fixed (`fixedMoves`): a start goes to In Progress, a pull request to In Review, a merge to Done, whatever the project's or a profile's moves say.

- **The model** (`model.ts`). Statuses are fixed: Backlog (`UnStarted`), Todo (`ToDo`), In Progress and In Review (`Active`), Done (`Won`), Canceled and Duplicate (`Lost`). Priorities are `none`, `low`, `medium`, `high`, `urgent`. Labels are a project's list, each with a color picked by its name; `Manual`, `Question`, `Bug` and `Rework` are offered everywhere. Milestones are a project's list with an optional date, ordered by date, the undated after, then by name with numbers as numbers (v0.10 after v0.9).
- **A task** (`store.ts`, `BuiltinStore`) is named by its project's GUID and its number; the number is one past the last of every project of the same key, so `<KEY>-<N>` stays one task (`BuiltinNames` in `source.ts` maps both ways). A parent is of the same project, any depth, a cycle refused (`builtin.parentCycle`). Links are `blocks` and `relates`, also between projects of the built-in tracker, never to another tracker's task. Comments carry an author: `person`, `agent` or `service` (Even Keel's own), and an agent's comment its model (`<Provider> | <model>`, step 31; filled by the tasks server from the live session of the task). Deleting a task drops its labels, links and comments and frees its subtasks; an agent never deletes.
- **No false conflicts.** An edit of a short field (title, status, priority, milestone, parent) carries the value its editor saw and the new one; it is refused (`builtin.conflict` with the current value) only when the field holds neither. The card's description editor edits the description the same way (BTN-772, `field: 'description'`, compared as is, the revision grown), so a change of another field meanwhile is no conflict. Labels and links are added and removed one by one, so nobody's addition is lost. The description has its own revision, grown only by a change of the description: a whole replacement names the revision it started from (`builtin.descriptionConflict`), a patch `old → new` needs none but `old` found exactly once (`builtin.patchMissing`). The task's `version` grows on every change, for a poll to compare; it refuses nothing.
- **The page** reaches it only through `builtin/*` POST commands (`routes.ts` over `BuiltinControl` of `control.ts`): `create`, `edit` (`field`, `from`, `to`; a parent by its id, the description as its whole text), `description` (`text`, `rev`), `patch` (`old`, `new`), `labels` (`add`, `remove`; a new name creates the label), `milestone` (`name`, `date`; created or redated), `relate`/`unrelate` (`other`, `kind`), `comment` (`text`, as `person`), `uncomment` (`comment`) and `delete`. Each answers with the task as the page shows it, every task named by its id, and refreshes the chain's read of the project; a refusal is a `builtin.*` notice. `search` (`text`, `project` or `null` for every built-in project) finds tasks by a key or a word of the title, for the card's link and parent fields.
- **Refusals of the card's edits** (BTN-771): a parent that is the task itself (`builtin.selfParent`) or its descendant (`builtin.parentCycle`); a link that already exists (`builtin.linkExists`); a `blocks` that would close a loop through other tasks (`builtin.blockLoop`, `closesLoop` in `links.ts`); a blocker in a later milestone than the task it holds (`builtin.blockerLater`, `laterBlocker`: the chain could not order them, `docs/chain/entry.md`); deleting the chain's current task or one with a live session (`builtin.removeBusy`, the service's `busy` hook in `src/service/hosting.ts`). The page checks the same before it asks (`web/src/pages/cardEdit.ts`), the service decides.
- **The task journal** (BTN-774): the comments are a journal, not a discussion — agent reports, Even Keel's `NO CHANGES:`, session questions with their answers, the person's notes. The source is marked `journal` (`TaskSource.journal`, `Tracker.journal`) and has no `commentsAfter`, so no comment ever answers a session: a session's question is posted with "answer in the session's chat" instead of "reply with a comment" (`questionComment(…, journal)`) and stored already read, and an answer given in the page's chat to a question (`ask` set) is written into the journal as the person's note "Answer to the session" (`answerComment`, `BuiltinControl.answered`, `journalAnswer` in `src/service/hosting.ts`); answers through Remote Control or a terminal are not. The person deletes only their own note: `uncomment` (`task`, `comment`) refuses any other with `builtin.noNote`. Each card comment carries `journal` (`id`, `by`, `model`), which only this adapter fills.
- **The card** (`TrackerCard.edit`, `CardEdit` in `src/tracker/card.ts`) carries what the editing needs and only this adapter gives it: the fixed statuses, the project's and the built-in labels (run labels left out), the ancestors and the subtasks; the page's side is in `docs/web/project-page.md`.
- **Attachments** (BTN-773, `files.ts`, `BuiltinFiles`): a record in `builtin_files` (step 32) and the bytes in `state/even-keel/files/<sha256>`, one copy for the same bytes, unique per task. The page uploads the raw body to `POST /api/builtin/attach?task=&name=` (the type from `content-type`), read up to the setting `attachmentLimit` (MB, live; past it `builtin.fileTooLarge`), and gets `{ file, name, type, size, url }`; `builtin/detach` (`task`, `file` — the record's id) deletes the record (`builtin.noFile` when there is none). The bytes are written before the record (via a `.upload-*.tmp` rename); the service sweeps, at start and hourly, bytes no record points at and half-written uploads older than a day, so a description edit undone within the day shows its picture again. The file route serves the bytes by hash whether or not a record is left, as a raster picture only by its first bytes (`sniffedType`), anything else as `application/octet-stream` — an SVG or HTML never runs as the page. The card's attachments carry `id`, the absolute `path` and `missing` when the record outlived its file (logged, shown as a "No file" tile). Sessions read them by path: `task_read` lists `## Attachments` with name, size and path, and the brief of a chain session ends with the same list (`PROMPTS[lang].files`, `withBrief` in `src/chain/relay.ts`).
- Tally reads the tasks from the state database each run and counts a rework by `Rework` as well as `Переделка`, on `/stats` and in its own views (`docs/tally.md`, "Tasks from Huly"). Not served yet: time logging, a closing reference, the page's own screens (BTN-769…BTN-772).
- **Sessions** edit its tasks through Even Keel's own tasks server (BTN-768, "The tasks server" below): the adapter's `mcpServer` is `tasks` and `keepsBrief` keeps the brief on, so a chain session gets its own task in the prompt and the server is for the others. Its writes are `builtinEditor` (`editor.ts`) over the store: a short field set against the value it holds now (never a false conflict), a whole description by its revision, patches through `BuiltinStore.rewriteDescription` in one transaction, comments as `agent` with the session's model.

## The tasks server (BTN-768, `src/taskmcp/`)

An MCP server of five tools over the tracker layer, not over any tracker's tables: a tracker gets it by giving `TaskSource.editor` (`TaskEditor` in `src/tracker/editor.ts`: `list`, `create`, `set`, `revision`, `describe`, `patch`, `link`, `relabel`, `comment`). Every tracker gives one: the built-in tracker, Huly (BTN-779), GitHub, Linear, Jira, GitLab and Forgejo (BTN-875). A tracker other than the built-in one sets `TrackerAdapter.editsTasks` besides its own `mcpServer` (`servesTasks` in `server.ts`). None of the outer trackers keeps a revision of a description alone (their `updated_at` grows with any field), so each takes `descriptionEdits` (`src/tracker/editor.ts`): `rev` is `revisionOf` the Markdown, a patch is a read, `patchText` and a whole write with no lock between them, so a change made in the tracker in that window is overwritten. Their comments carry no model (the author is the token's account), and what a tracker cannot hold is an `EditRefused` with what to do instead, never a quiet success. A write made after the task was created — labels, a parent, a status — that fails says the task was created and must not be created again.

- **Cheap by design.** `tasks_list` — a line per task (key · status · milestone · title), open ones unless `status` says otherwise, at most 200. `task_read` — Markdown: the title, a head line (status, priority, milestone, labels, parent, links, `rev N`), the description, comments only with `comments: true`. `tasks_create` — a batch with every field at once, links and an earlier parent inside the batch as `#N`, the answer `KEY-N Title` lines. `task_update` — any fields at once: labels and links by `add`/`remove`, the description by `replace: [{old, new}]`, `append` or a whole `description` with `rev`; the answer one line of what changed, `already so` when nothing did. `task_comment` — a journal entry by the agent (`by: 'agent'`) with the model of the chain session of the address's task (`<Provider> | <model>` of its live session, `TasksDeps.modelOf`), `null` for a hand session or before the session's first answer; Even Keel's own comments (`NO CHANGES:`, session questions) stay by `service` (BTN-786). No tool deletes. The schemas are short enough that Claude Code loads them at once, with no ToolSearch.
- **Names, never ids.** Tasks by key (any case), statuses, labels and milestones by name, ignoring case. An unknown status, label or milestone is refused with the list of the existing ones (`TrackerVocabulary`); run labels pass. Everything is checked before the first task of a batch is created.
- **The roles line** (BTN-893, `src/taskmcp/vocabulary.ts`). A tracker's `chain:` line names, in its own spelling, the status that puts a task into the chain (the active statuses of category `ToDo`, else every active one, with the required label if the rules have one), the skip labels (`excludedLabels`), the question label, the milestones, and whether it keeps a priority and an estimate: `chain: into it — Todo; skip — Manual; question — Question; milestones v0.3; priority: yes; estimate: no`. It is built from the chain rules the tracker's tasks are judged by (`TasksDeps.rulesOf`: the project's, or a feed's `feedRules`), so the skills carry no literal status or label. `task_read` puts it as the card head's second line (a vocabulary that fails to read leaves only the line out), and a refused status, label or milestone ends with it. A chain session gets it in the launch and handoff prompts (`docs/sessions/models.md`). A tracker that gives no `vocabulary` says so in the line, and a status, label or milestone sent to it is refused, never passed blind. Priority is `no` where the editor's `priorities(labels)` finds none: GitHub, GitLab and Forgejo keep it only as `priority: <level>` labels, so a repository without them has none.
- **Estimate** (BTN-893). `estimate` of `tasks_create` and `task_update` is whole minutes of the agent's active work; the editor's optional `estimate(id, minutes)` converts it into the tracker's unit. Only Huly has one so far (hours, `estimation` and `remainingTime` on a new issue, `toCard` reads it back in minutes); every other tracker refuses an estimate before anything is created. The `tasks` plugin's `PreToolUse` hook (`plugins/tasks/hooks/`, the same for OpenCode in `opencode/tasks.mjs`) shows the project's "estimate → actual" medians from Even Keel's statistics once a session and refuses once a step the closed tasks disagree with by more than 1.5 times, as the `huly` plugin does.
- **No false refusals.** A patch's `old` is found exactly once, compared as is but for line ends (`patchText`): none — refused with the current text; more — refused with the count. A batch of patches applies whole or not at all. A patch already applied (its `old` gone and its `new` there, or its `old` only inside its `new`) and an `append` already at the end are skipped, so a repeat is `already so`. A whole description needs the description's revision, which another field's change does not grow.
- **Retries.** `tasks_create` with `retry` keeps what the batch created in the state database (`task_retries`, step 39, BTN-896, `docs/storage.md`), scoped by the project's GUID and retry key: a repeat, including after a service restart, creates only what is missing and answers with every task. Each created ID is saved with an awaited write before creating the next task, and calls of the same key run in sequence. The newest 200 different keys across the service are kept by first use (repeats do not renew them), including partial batches; cleanup runs once active retry calls settle. An evicted key starts anew. With no `retry`, nothing is journalled. A tracker refusal in the middle says what was created and that the same `retry` creates the rest; a journal read failure creates nothing, and a failed save stops the batch and names the created tasks. There is no shared transaction with an external tracker, so the window between a create and the save of its ID is closed by an operation marker (BTN-905, `TaskEditor.markers`): before creating a position the journal saves it as started with a fresh random marker (`task_retries.started`, step 40), and the task is created carrying it; a repeat that meets a started position without an ID first looks the marker up in the tracker. Found — its ID is taken, the batch's labels are put on again (Huly and Linear add them after the create) and the answer marks the line "found in the tracker after an interrupted call"; not found — the task is created with the same marker, so a create that did land but was not seen is refused by the tracker as a second task with that id rather than duplicated. A failed write of the started mark creates nothing for that position. The marker is the new task's own id, chosen by Even Keel, which a person never sees: the built-in tracker's row id, Huly's `_id` (`generateId`), Linear's issue `id` (a UUID v4 `issueCreate` takes). GitHub, GitLab, Forgejo and Jira have no such place and no markers yet (BTN-907): on them a crash in that window can still duplicate the task, and a failed save asks the caller to check the tracker before repeating. Reuse a key only with the same batch in the same order; the journal has no payload fingerprint or tracker/profile identity, and links are reapplied on a repeat. BTN-899 settled this policy: the 200-key retention, refusal on a database failure and the project-plus-key scope stay as they are.
- **Scope.** The gateway answers it in the service (`TasksMcp`, `docs/packages.md`). A chain session reaches it through the project's package route with `?task=<id>` (`sessionPackages`): the route names the project, the task gives the comment its model. A session started by hand reaches `/tasks` (or `/tasks/<project GUID>`); without a project in the address `tasks_list` and `tasks_create` take `project` (the key), the others find the project by the task's key among the projects it serves (`servesTasks`), by the prefix of their task ids (`idPrefixOf`: a Huly project's `huly` identifier, not Even Keel's key). A hand session needs the service running: the address is the service's own. **Feeds** (BTN-892): the address limits the project, not the tracker. A project's trackers are its readers (`readerIds`: its own, then its feeds', `TasksDeps.readers`), each told by the prefix of its task keys; `task_read`, `task_update` and `task_comment` go to the reader of the key's prefix, and a key no reader of the address's project gives is refused with the prefixes it has. `tasks_create` creates in the reader `tracker` names (a prefix), else — in a hand session — the one the `project` key gives (a feed's prefix names its project and the feed), else the reader of the address's task, so a blocker lands beside the task it holds, else the project's own. `blocks`, `blockedBy`, `relates` and a parent naming a key of another reader are refused before the first task of the batch (and before any write of `task_update`): `blocks` does not cross trackers (`docs/chain/entry.md`, "Task feeds"). `tasks_list` asks every reader at once (`Promise.allSettled`) and joins the lines in reader order; `tracker` narrows it to one. A filter by a status, label or milestone a tracker lacks gives nothing from it, never a refusal. A reader that fails is named at the end, `GHI: unreachable, not searched (<reason>)`, since a quietly short list leads to duplicates; with only one reader searched its failure is the refusal. Retries are scoped by the reader's GUID; a write refreshes the owner project. `/tasks` has no separate access check: the gateway accepts it only from this machine without `Origin`; a hand session with shell access already has broader rights, so this route does not expand them, while a chain session is scoped to the project in its address. Every write refreshes the chain's read of the project, so the chain sees a new task or link at once.
- **Stands in for the tracker's server** (BTN-882). For a tracker it serves, an enabled package that brings `tasks` counts as the tracker's MCP server: the set has no `noTrackerMcp`, `ProjectPackages.tracker.brought` is true with `through: 'tasks'`, and the auto `brief` leaves the project's own task out of the prompt (`briefOn`), as with the tracker's own plugin. A feed's task too (BTN-892): the server reads the feed on the feed's own link, so `briefOn` with the feed's reader leaves its brief out when the feed's tracker is one the server serves, whatever profile a tracker server of the packages signs in as; `ProjectPackages.tracker` still speaks only of the main tracker. The adapter's `mcpServer` stays its own (`huly` for Huly), and so does the delete protection, which goes by it (`refuseDeletes`).
- **Errors** are short English lines for the agent (`EditRefused`, a `NoticeError` in its English text), as a tool result with `isError`.
- **On Huly** (`hulyEditor`, `src/huly/editor.ts`) the same tools have these limits. Huly keeps no revision of a description, so `rev` is a hash of its Markdown (`revisionOf`); a patch reads the Markdown, patches it and writes it whole, with no lock between the read and the write, so a change made in Huly in that window is overwritten. Once a description was opened, Huly's collaborator reads its own document of it and ignores a new blob the issue names, so `uploadMarkup` plus the issue's `description` left the text as it was while the answer said "patched" (BTN-906): an existing description is rewritten in place through the collaborator's `updateContent`, as Huly's editor does, and Huly then points `description` at it itself; only a task without a description gets a new blob that way. The public client keeps its collaborator private, so `src/huly/collab.ts` takes it from the pinned version's internals (`src/huly/collab.test.ts` fails when they move) and refuses the write without them. The text is read back after every write: one that still reads as before is an error, never "patched". A parent is set only on a new task, of the same Huly project; moving a task to another parent is refused, since Huly rewrites the subtree. A new task without a status lands in the project's first status of the `UnStarted` category (Backlog), not in Huly's project default, as on the built-in tracker. `relates` is written on both tasks' `relations`, `blocks` on the blocked task's `blockedBy`. A comment carries no model: a Huly comment has no field for it. The Markdown round trip keeps everything but tables, which come back as HTML; one more trip adds a blank line, then it holds (`src/huly/editor.test.ts`). Huly's editor cannot open inline code inside bold, italics, strikethrough or a link (`RangeError: Invalid collection of marks`), so every text these tools write — a new task's description, a whole one, a patch, a comment — is fixed first rather than refused (BTN-894, `fixCodeMarks` in `src/huly/marks.ts`): in Huly's markup of the Markdown such a text node loses the outer mark (`**text `code`**` becomes `**text** `code``), or inside a link its code mark, so the link stays one; a text with nothing to fix is written as given. The answer says so (`ABC-1: description patched; fixed 1 mark: code moved out of bold`). A patch's `new` and `append` are fixed before they are applied, so a repeated patch is still "already so". The `huly` plugin's hook (`plugins/huly/hooks/check-marks.mjs`) still refuses such input on the plugin's own server until the plugin moves to this one (BTN-874).
- **On GitHub** (`githubEditor`, `src/github/editor.ts`). A status is the state with its close reason (`Completed`, `Not planned`, `Duplicate`); another reason of a closed issue reopens it first. A priority is the repository's label `priority: <level>` (or `priority/<level>`), swapped by relabelling; a level the repository has no label for is refused, since only the user makes labels. A milestone is found by title. The parent is a sub-issue (`addSubIssue` with `replaceParent`, `parentIssueId` on a new one), `blocks` the native "blocked by" (`addBlockedBy`); there is no `relates`.
- **On Linear** (`linearEditor`, `src/linear/editor.ts`). Status, priority and parent are Linear's own. A milestone is a project milestone, found by name in the issue's own Linear project, or among all the team's projects when it has none; a name found in two projects is refused. Links are issue relations: `blocks` kept on the blocker, `related` on either side.
- **On Jira** (`jiraEditor`, `src/jira/editor.ts`). A status moves only by a transition of the issue's workflow; a status it cannot reach is refused with the ones it can. Every issue keeps a priority, so `none` is refused. A milestone is a fix version, set as the issue's only one. A parent is an epic over a standard issue; a new task under a standard issue takes the project's sub-task type, and a sub-task takes no children. Links are issue links of the site's `Blocks` (the blocker outward) and `Relates` types; a site without `Relates` refuses it. The description is ADF, edited through Markdown (`adf.ts`).
- **On GitLab** (`gitlabEditor`, `src/gitlab/editor.ts`). A status is the state (`Opened`, `Closed`). A priority is the project's label `priority::<level>` (or `priority: <level>`), refused where the project has none. A milestone is an active one of the project or its groups. The parent is the work item hierarchy (`workItemUpdate`): an issue takes tasks as children, so a new task under an issue is made of the `task` type, and whatever GitLab refuses comes back as its own reason. A link is an issue link; GitLab keeps one per pair, so a pair linked another way is refused, and blocking links exist only on Premium and Ultimate: where the instance makes a `relates_to` instead, it is removed and the link refused.
- **On Forgejo** (`forgejoEditor`, `src/forgejo/editor.ts`), so on Gitea and Codeberg too. A status is the state (`Open`, `Closed`). A priority is a repository or organization label `priority/<level>` (or `priority: <level>`, `priority::<level>`), refused where there is none. A milestone is an open one of the repository. `blocks` is a native dependency, kept on the blocked issue (`/dependencies`); a repository with dependencies off refuses it. Forgejo has no subtasks and no `relates`: both are refused.

## Claude Code plugins (BTN-64)

- The repository is the marketplace `even-keel` (`.claude-plugin/marketplace.json`), one plugin per tracker in `plugins/<tracker>/`: the tracker MCP (`.mcp.json`) and skills (`skills/<name>`, invoked as `<tracker>:<name>`). `task` — working a task; Huly also has `split` — splitting into subtasks and `setup` — putting a repository on the tracker. The skills are in English and carry no foreign names or measurements. There is one non-tracker plugin there — `checkpoint` (the checkpoint hook, `docs/chain.md`), installed with `--scope user`.
- Installed with the global configuration (without `CLAUDE_CONFIG_DIR`): `claude plugin marketplace add <repository>`. Chain sessions get a plugin as a package of the project (`docs/packages.md`): "Add a package" in the package catalog (`/settings` → Packages) copies it from the marketplace, whatever `enabledPlugins` says. For sessions started by hand, `claude plugin install huly@even-keel --scope project` in the project repository — `enabledPlugins` in the project's `.claude/settings.json`; `share.ts` transfers the plugin registry into account folders. With the plugin as a package, the auto `brief` leaves the description out of the prompt by itself.
- A plugin change comes with a new `version` in its `plugin.json`: the installed copy sits in the cache by version, and `claude plugin update` with the same version picks up nothing. A marketplace added from a local path is the exception (CLI 2.1.301): `claude plugin list --json` shows `readFromFolder` and `folderVersion` next to the cached `version`, and sessions load the plugin from that folder, so a `git pull` there reaches the next sessions without `claude plugin update` (BTN-157: a session loaded the folder's `huly` skill while the cache held 0.4.0).

### `huly` — the model

- The server is `@firfi/huly-mcp`. The credentials (`HULY_URL`, `HULY_WORKSPACE`, `HULY_TOKEN` or `HULY_EMAIL`/`HULY_PASSWORD`) are inherited from the session environment and are not in `.mcp.json`, which has only the constant `TOOLSETS` (the set for working a task).
- `${…}` substitutions in a plugin's `.mcp.json` are unsuitable for a session that runs the server itself: an unset variable, even with a `:-` default, makes the session consider the server failed and not start it (`claude mcp list` still says "Connected"), and the server does not accept an empty `HULY_TOKEN`.
- Chain sessions: the gateway runs the server in its HTTP mode with the `HULY_*` of the project's profile (`docs/packages.md`); the session sees only the gateway's address. `sessionBase` removes `HULY_*` from the sessions' environment.
- Sessions started by hand: the default Huly profile's credentials are in `env` of `~/.claude/settings.json`: the session applies it itself, and `share.ts` transfers the file into account folders.
- How to use it — `plugins/huly/README.md`.
- OpenCode gets both Huly guards from `plugins/huly/opencode/huly.mjs` (plugin 0.5.8): markdown writes are checked before execution; estimate calibration shares the command hook's request and once-per-session marks. For MCP calls, OpenCode 1.18.25 passes the raw result to `tool.execute.after`, so calibration is appended as a text block in `content`, before OpenCode assembles the output (the plugin also accepts the assembled `output` shape). Checked live on Windows on 2026-10-25 with OpenCode 1.18.25 and `opencode/deepseek-v4.1-flash-free`: the gateway tool is `plugin_huly_huly_update_issue`, malformed markdown was refused, a mismatched estimate was refused once, and a corrected retry reached Huly and was read back. A second session saw calibration on an allowed estimate's result and none on its next call.

### `github` (BTN-65)

- The remote GitHub server (`api.githubcopilot.com/mcp/`, toolsets `issues,labels`). An HTTP server needs the token in a header, so a `${GITHUB_PERSONAL_ACCESS_TOKEN}` substitution is used here — without the variable the server is useless anyway. For chain sessions the gateway fills it from the `GITHUB_TOKEN` of the project's profile (the adapter's `mcpKeys`) and adds the header itself; a session started by hand needs `GITHUB_PERSONAL_ACCESS_TOKEN` of its own.
- The MCP has no "blocked by" links — the skill sets them via `gh api …/dependencies/blocked_by`.
- How to use it — `plugins/github/README.md`.

### `linear` (BTN-72)

- The remote Linear server (`mcp.linear.app/mcp`). It accepts a personal key in a header — `Authorization: Bearer ${LINEAR_API_KEY}`; for chain sessions the gateway fills it from the `LINEAR_TOKEN` of the project's profile (`mcpKeys`), a session started by hand needs `LINEAR_API_KEY` of its own.
- The server sets "blocks" links itself: `save_issue` with `blockedBy`/`blocks`.
- How to use it — `plugins/linear/README.md`.

### `gitlab` (BTN-410)

- The stdio package `@zereight/mcp-gitlab@2.3.11`, with `GITLAB_TOOLSETS: "issues,milestones"`: REST issue tools are available from launch. Work-item tools are disabled because their GraphQL queries include `WorkItemWidgetStatus`, which CE/Free does not expose and rejects for the whole query. The task skill uses `get_issue` and does not offer work-item hierarchy changes through this package. The official MCP rejects a legacy `api` PAT and requires OAuth with `mcp` or a separate fine-grained MCP token, so the community server matches the adapter's credentials and works on self-managed hosts without OAuth.
- The gateway fills `${GITLAB_PERSONAL_ACCESS_TOKEN}` through `mcpKeys` from `GITLAB_TOKEN`, and `${GITLAB_URL:-https://gitlab.com}` into `GITLAB_API_URL`; the package normalizes the web root to `/api/v4`. The session only sees the local gateway.
- How to use it — `plugins/gitlab/README.md`.

### `jira` (BTN-417)

- The official Atlassian Rovo MCP server (`https://mcp.atlassian.com/v2/mcp`), which takes an API token in `Authorization: Basic base64(email:token)`. A community server was not taken: the official one accepts the same token as the adapter. Its limits come from Atlassian: the organization admin must turn on API token authentication for the server, and only a token with scopes gets Jira tools — a classic one gets Teamwork Graph tools only. Tools take the site's `cloudId`, which the skill gets from `getAccessibleAtlassianResources`.
- The header is built from two keys, which `mcpKeys` cannot do: the adapter's `mcpValues` declares `JIRA_BASIC_AUTH` as a value derived from `JIRA_EMAIL` and `JIRA_TOKEN` (`DerivedKey`, `src/tracker/source.ts`), `trackerKeyRules` hands them to `keysOf` as `derived`, and a missing source key is reported by its own name. A session started by hand needs `JIRA_BASIC_AUTH` of its own.
- How to use it — `plugins/jira/README.md`.

### `forgejo` (BTN-476)

- The official Gitea MCP server `gitea-mcp` (checked against v1.13.0), a Go binary started over stdio (`-t stdio`): it takes the token from the environment (`GITEA_ACCESS_TOKEN`) and the host from `GITEA_HOST`, so the gateway fills both from the profile (`mcpKeys` from `FORGEJO_TOKEN`, `mcpValues` from `FORGEJO_URL` with its prefix); its Gitea SDK reads Forgejo's version string. `GITEA_SCOPES: issue,label,milestone,user` keeps the tool list to what a task needs. The official server was taken first, as the task asked, and it fits: it has the dependency tools (`issue_write` `add_dependency`) the skill needs.
- The binary is not an npm package and Even Keel does not pin it: it must be on the service's `PATH` (`plugins/forgejo/README.md`). Its tools are method-style (`issue_write` with `method: delete_comment`), so `deletesRecord` reads a `method` field by its words and the protection group `deleteForgejo` refuses them at the gateway (`docs/sessions/protection.md`).
- How to use it — `plugins/forgejo/README.md`.

### `tasks` (BTN-768)

- Even Keel's own tasks server ("The tasks server" above) with the skills `tasks:task` and `tasks:split`: the common part of `huly:task`/`huly:split` in terms of the five tools, short since a skill sits in the context every turn. `.mcp.json` points at `http://127.0.0.1:4748/tasks`: for a package the gateway recognises the address (`isTasksUrl`, any port) and answers it itself; for a session started by hand it is the real address, with the project named by its key. It serves every tracker (Huly since BTN-779, the rest since BTN-875); the `huly` plugin keeps its own server until the live check of the Huly editor.
- How to use it — `plugins/tasks/README.md`.
