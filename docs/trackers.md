# Trackers and plugins

Reference for sessions: how the tracker layer, the adapters and the Claude Code plugins are built. The working rules are in `CLAUDE.md`, the public description in `README.md` and `docs/guide/setup.md`.

## The `src/tracker/` layer (BTN-58)

- The neutral task model is `model.ts`: `TrackerTask` from the adapter, `Task` — plus the model and the question from the labels `Question` or `Вопрос`.
- The adapter contract is `source.ts`, `TaskSource`/`TrackerAdapter`; the description is in the JSDoc there, for those who write their own. The chain, the order, the rules and the page state know only these.
- The adapter is chosen by the project's `tracker` (`{ "key", "repo", "tracker" }`). Since BTN-345 it is the project's own only: the wizard, the project form and `config-import` always store it, and the shared one is gone (database step 13 and schema v13 gave each project the one it ran on). `DEFAULT_TRACKER` (`github`) meets only a project of a hand-written file of the current schema that names none. The registry is `src/tracker/adapters.ts`; the repository has Huly, GitHub, Linear, GitLab and Jira Cloud.
- For a tracker whose project is not named by a key, the adapter declares `projectKey` — a key in the project object (for GitHub `github`: `owner/name`); without it, or if malformed, it is a config error. With `optional` only a malformed one is an error (for Linear `linear` narrows the team to a project). With `alias` the value names the tracker's project instead of the key, which then is only Even Keel's (Huly `huly`, BTN-172). `placeOf(key, value)` gives the place in the tracker a project reads (`read`) and the prefix of its task ids (`ids`) when the ids are the tracker's own: projects with one place read it once and must split it by milestone (`docs/chain.md`, "Several projects on one tracker project"); `readKeyOf`/`idPrefixOf` in `src/config.ts` fall back to the key. The values arrive in `setup` as the second argument. The optional `projectOfRemote` turns a git remote of the repository into that value (GitHub: a github.com remote's `owner/name`); the wizard fills the field with it (`repo.suggested` of `checkDraft`).
- A task ID is `<project key>-<number>`: the worktree, branch and stats go by it. What the tracker lacks, the adapter returns empty.
- The adapters know only the project key. Even Keel's own id of a project (`projects[].id`, a GUID) names it in `state/` and in the page's URLs and never reaches the tracker layer (`docs/chain.md`, "State files and the schema version").
- The optional `brief` and `complete` — Huly has both (BTN-63, `src/huly/source.ts`): the description is markdown, Done is a status of the `Won` category from the project type.
  - `brief` — the title and description are appended to the launch and handoff prompts.
  - `complete` — Even Keel closes the task once it sees its branch merged into `main`: `src/git/merged.ts` — the branch tip is in `main` and `main` has at least one commit made in the branch itself (by reflog: creation, `reset` and `Fast-forward` pulls of own commits do not count, so a branch that only pulled in `main` is not considered merged), `src/tracker/closer.ts`. `true` — the task was moved, already closed — `false`, nothing is written. It does not conflict with a git hook that also moves to Done: whoever is first closed it.
- The optional `children` — the direct subtasks of a task; only Huly has it (by `attachedTo`). With it and `complete`, Even Keel closes the parent (`src/tracker/parents.ts`): when tasks are refreshed, a parent that is open by the rules and has no open subtask among the known tasks is checked in the tracker — all subtasks closed and at least one in `Won` — `complete`. All cancelled — the parent is left to the user. In Huly `parents` goes from the root: the direct parent is the last.
- The optional `card` and `ready` — the task card on the page; Huly has both, GitHub and Linear have `card` (BTN-76), Linear also `ready`. `card` (`TrackerCard`, `src/tracker/card.ts`) — the description and comments in markdown, labels, milestone, priority, parent, "blocked by", "blocks", "related"; the server (`GET /api/tasks/<id>`) appends `cardOf`: what each label means to Even Keel (model, question, keeps out, required) and whether it can be moved to Todo. `ready` (`POST /api/task/ready`) moves a task of the `UnStarted` category to the first `ToDo` status of the project type and returns the new status; the service immediately substitutes it for the task in the chain without waiting for a poll. Whether the connected adapter has `ready` is carried by the state in `trackers[].ready`: the "Move to Todo" button stands on this basis right in the backlog panel, for tasks of the `UnStarted` category. Without `card` the page answers "the tracker doesn't provide a card" and gives a link.
- The card's `attachments` (`file`, `name`, MIME `type`, `size`, `url`) are the files of the task and of its comments. An adapter with its own public address gives `url`; with `url: null` the server puts its own `/api/tasks/<id>/files/<file>`, served by the optional `file(id, file)` (`TaskFile`: type, size, a byte stream). The Huly adapter answers it only for a file of that task or its comments and streams it from the workspace storage (`connectStorage`, connected lazily, reconnected once on failure). The route sends `nosniff` and `private, max-age=3600`; only raster images, video, audio and PDF go `inline`, everything else is `attachment` with `content-security-policy: sandbox`. No `Range`: a video plays, but seeking ahead waits for the download.
  - GitHub (`toCard` in `src/github/model.ts`): one GraphQL query — `body`, `parent`, `blockedBy`, `blocking` (with title and state of each), the first 100 comments (`author.login`); "related" is always empty and `ready` is absent, since GitHub has no backlog. No attachments on the card: files of comments are links in their text.
  - Linear (`toCard`, `readyState` in `src/linear/model.ts`): `blocks` is read both ways — `relations` (this task blocks) and `inverseRelations` (blocked by) — `related` from either side, other relation types are dropped; comments by `user.name`. `ready` moves a task in a `backlog`-type state to the team's first `unstarted` state by `position`; a task in `triage` or any other state is left alone (`null`).
  - Huly: "blocks" — tasks that have this one in `blockedBy` (the query passes `blockedBy: { _id, _class }` as a whole object: by `blockedBy._id` and `$elemMatch` Huly finds nothing); "related" — the task's own `relations`, Huly stores the link on both sides. Comments are `chunter:class:ChatMessage` by `attachedTo`, the markup converted to markdown with `@hcengineering/text-markdown`; the author is `createdBy` (social id) → `SocialIdentity.attachedTo` → `Person.name` in the form "Surname,Name".
  - GitLab (`GitlabUploads`, `src/gitlab/uploads.ts`): upload links in the description and human notes become distinct attachments with `url: null`; relative `/uploads/<secret>/<filename>`, project URLs and `/-/project/<id>/uploads/…` of this project are supported, including an installation prefix. The Markdown links are rewritten to the service's file route. The card renders inline images and download links only for those local attachment URLs. `file` checks that the task references the file, then streams the [REST download by secret and filename](https://docs.gitlab.com/api/project_markdown_uploads/#download-an-uploaded-file-by-secret-and-filename) with the profile token and redirects disabled. GitLab can return `application/octet-stream` for media: known image, audio, video and PDF extensions supply the inline type; other files remain downloads.
- Questions in the tracker (BTN-101, `src/tracker/questions.ts`): the optional `comment(id, body)` posts a Markdown comment and returns its id, `commentsAfter(id, after)` gives the comments posted after it, oldest first (`[]` once it is gone), each with its `files` by what `file(id, file)` serves. With both, `TrackerQuestions` polls every 15 s: when the session of a chain's current task waits on an `AskUserQuestion` (not on a question in plain text), it posts the question with numbered options (`questionComment`) and remembers it in the state database (`questions`, `docs/storage.md`), so a restart does not post it twice. A session that ended its turn without an `AskUserQuestion` (a question in plain text, or just waiting) gets nothing posted and no comment read: it is answered from the page's chat or Remote Control. That is a decision (BTN-166), not a gap: reading any comment as an answer would take a note to self or another person's comment for one, and posting every end of a turn would flood the tracker. Every comment after it is taken as the user's — a waiting session does not comment, and on GitHub Even Keel's token is often the user's own; only GitHub filters by author, since anyone can comment on a public repository (EKR-19, "GitHub Issues" below). The first comment answers by numbers (`2`, `1, 3`) or text, a line per question when there are several (`trackerAnswers`); the rest go along as text and their files are downloaded into `.temp/inbox/` (a file the tracker will not give stays a link). The reply goes through `Dispatcher.answer` (`docs/chain.md`, exception 6); `answer.busy`, `chain.launching`, `chain.limitSpent` and `chain.notCurrent` are retried on the next tick, any other refusal closes the question (`done`). A question the session left (answered through the page or Remote Control, a new session) is forgotten. A question stays while its session lives and waits on it even when the task is no longer current (BTN-120: the chain is led by the fix of a red `main`, the task is postponed or skipped): its comments are not read then, and once the chain takes the task again they are read from the same question comment, so a reply written meanwhile reaches the session and the question is not posted twice.
  - Huly: `chunter:class:ChatMessage` with the markup from `markdownToMarkup`; comments after by `createdOn`, files are their `attachment`s. GitHub, Linear and GitLab: a comment's files are the upload links in its body (`github.com/user-attachments/…`, `private-user-images.githubusercontent.com/…`; `uploads.linear.app/…`; GitLab's `/uploads/…`), and `file` fetches only those with the token. GitLab collects files after checking the note author's membership. A GitHub upload of a public repository came back whole through the route (2026-10-24); a private repository's is not verified live.
- The optional `create(task: NewTask)` (BTN-103) — a new task: project key, title, Markdown description, priority and the milestone of a given task (`milestoneOf`); it returns the new task's ID. With the project's `ci.fixTask` on, the chain files the fix of a red `main` with it (`docs/chain.md`, "The CI of main"), and without it a red `main` pauses the chain with `ci.cannotCreate`; with `ci.fixTask` off, the default, the fix is a session without a task and `create` is not called. All three adapters have it, each in the first ready status of the project:
  - Huly: the number from the project's `sequence` (`$inc`), a rank after the last task (`makeRank`), the description through `uploadMarkup`, `addCollection` with `tracker.ids.NoParent`.
  - GitHub: GraphQL `createIssue`; the priority is the `priority: <level>` label only if the repository has it, the milestone is the given task's.
  - Linear: `issueCreate` in the team's first `unstarted` state, with the given task's project and project milestone.
- The optional `closingRef(id)` (BTN-295) — how a pull request names the task's issue; `null` for a task not of the tracker. The GitHub adapter gives `owner/repo#N` of the repository of the id's key, the GitLab one (BTN-414) the issue's address `<server>/<path>/-/issues/<iid>`, both with no request; the others have none. PR mode ends the body of a task's pull request on the same forge with `Closes <it>` (`closingOf`, `docs/chain.md`, "PR mode").
- The optional `setMilestone(id, milestoneOf)` (BTN-107) — puts a task without a milestone into the milestone of the task `milestoneOf`; `false` and no change when the task has a milestone by now or `milestoneOf` has none. The chain fills the milestone of a task that entered it without one with it (`fillMilestone`, `docs/chain.md`, "Entry into the chain"). The milestone is named by a task that carries it because the neutral model has no milestone ID. All three adapters have it; GitHub's was verified live in a task feed (BTN-326, 2026-10-23), Linear's on 2026-10-25 (below):
  - Huly: `milestone` of the issue; a task of another project gives none.
  - GitHub: GraphQL `updateIssue` with `milestoneId`; a milestone belongs to a repository, so a task of another project gives none.
  - Linear: `issueUpdate` with `projectMilestoneId`; a milestone belongs to a project, so an issue without a project gets the project together with it, and an issue of another project is left alone. Checked live on 2026-10-25: the chain filled a Todo issue of a project narrowed to a Linear project, and the adapter, called from a script, gave an issue without a project both the project and the milestone in one `issueUpdate`.
- The optional `milestones(id)` and `moveMilestone(id, milestone)`, only as a pair (`trackerOf` drops one without the other) — the milestone pick on the task card. `milestones` gives `MilestonePick`: the tracker's id of the task's milestone (`null` — none) and the choices, each with its own id, label and target date; the card sorts them as the chain does (`compareMilestones`). `moveMilestone` puts the task into a choice's id, `null` into none. `POST /api/task/milestone` (`{task, milestone}`) calls it and then reads the project anew rather than patching the task, since the milestone changes the chain order; without the pair it is `task.cannotMoveMilestone`. All three adapters have it:
  - Huly: the milestones of the issue's project whose status is not Completed or Canceled, plus the issue's own when it is closed; a milestone of another project is refused.
  - GitHub: the repository's open milestones (GraphQL `milestones(states: OPEN)`), plus the issue's own when it is closed; `updateIssue` with `milestoneId`, `null` clears it.
  - Linear: every project milestone of the issue's project (Linear's have no closed state); an issue without a project has no choices. `issueUpdate` with `projectMilestoneId`, `null` clears it (checked live on 2026-10-25: another milestone, none and back).
- The optional `vocabulary(project)` (EVK-1) — `TrackerVocabulary`: the statuses with their categories (BTN-334: the rules' table places a status by its category until a list names it) and the labels a task of the project can have, whether or not a task has them now. The settings suggest them in the chain rules together with what the loaded tasks carry, so a project whose chain is empty still gets suggestions (`docs/web.md`). `GET /api/projects/<id>/vocabulary` serves it by the project's id, 404 when the tracker is off or has no `vocabulary`; the service keeps an answer five minutes (`Vocabularies`, `src/tracker/vocabulary.ts`), a failure or a 404 is not kept. All three adapters have it:
  - Huly: the statuses of the project's type in its order (every status when the type is unknown) and the workspace's issue labels — `tags:class:TagElement` with `targetClass` `tracker:class:Issue` (`vocabularyOf`).
  - GitHub: its own four statuses (`GITHUB_STATUSES`) and every label of the repository (GraphQL `labels`, paged by 100).
  - Linear: the team's workflow states and the labels of the team and of the workspace (`issueLabels` with the team, or none — a workspace label has no team), paged by 50; a label group is left out, since it cannot go on an issue.
  - Checked live on 2026-10-18 on three projects with an empty chain, one per tracker: the route answered for each and the panel's rule lists offered the tracker's statuses and labels.
- The optional `milestoneTasks(project, milestone)` (BTN-142) — every task of a milestone named by its label, open and closed, each with the Markdown of its last comment (`MilestoneTask.lastComment`, the closing comment of its session as a rule); `[]` when the project has no such milestone. It feeds the changelog draft of a milestone (`src/changelog/`, `docs/sessions.md`, "One-off turns"); without it the draft is `changelog.cannotList`. All three adapters have it:
  - Huly: the milestones of the project with that label, their issues and the newest `ChatMessage` of each (`latestMessages`), markup turned into Markdown. Checked live on 2026-10-18 on BTN `v0.1`: 178 tasks, 172 in `Won`.
  - GitHub: the milestone's number by `milestones(query:)` over open and closed ones, then an exact title match; its issues with `comments(last: 10)`, of which the newest by a trusted author (below).
  - Linear: the project milestones of the team with that name, their issues with both ends of `comments` (`newestBody` keeps the newer one). Seen live on 2026-10-25: Linear's default order is by `createdAt`, newest first, and an edit does not move a comment, so `first: 1` is the newest; a changelog draft of a Linear milestone took each task's closing comment.
- The `brief` key (global and per project — `{ "key", "repo", "brief" }`, applied on the fly) decides whether the description goes into the prompt. Unset or `null` (BTN-225) it is auto, `briefOn` in `src/service.ts`: on exactly when no enabled package of the project brings the adapter's MCP server (`mcpServer`, for Huly `huly`), so a project with the tracker's plugin gets only the task id and one without it gets the task, with nothing to switch. `true` or `false` overrides it; with `false` the packages must bring the server: without it the set has the problem `noTrackerMcp`, the chain waits and the banner names the project (`docs/packages.md`). An adapter without `mcpServer` has the brief on under auto.
- Each profile in use has its own connection and poll (`src/tracker/link.ts`, `poller.ts`) and a card on the `/status` page (`TrackerView`: its state, last good poll, error and, per project and task feed it reads, when it last read it — `readAt`, `docs/web.md`). A failed call closes the connection and the next one connects again, except an answer that the project, team or issue asked for is not there (`TrackerNotFound`, BTN-317): closing would fail the calls of the profile's other projects under way on it ("Connection closed" in Huly), so a project deleted or renamed in the tracker would stall them all. A project's read that fails the same way on every refresh is logged once, and once more when it reads again. A project's task feeds (BTN-66, `docs/chain.md`, "Task feeds") are read as projects of their own ids, each on its own profile. A task link goes by the tracker of its project or feed (`trackerUrls`, the `issueUrl` template with `{id}` or `{number}`), one of no known project by the default profile of the tracker most projects run on (`trackerUrls.default`, `linksTracker`: a tie goes to the first project's, no projects — no link); the stats link a task by the url its launch recorded, the template only without one. A project with nothing to run links to its page in the tracker and to each feed's in the feed's (`trackerUrls.pages`, by the project's or the feed's id, BTN-329; the optional `projectUrl`, checked live on 2026-10-21): GitHub — `https://github.com/<owner/repo>/issues`; Huly — `<url>/workbench/<workspace>/tracker/<project _id>/issues`, the `_id` learned on the first read of the project's tasks (`HulySource.projectIds`); Linear — the team's `https://linear.app/<urlKey>/team/<KEY>/all`, or for a key narrowed to a Linear project that project's `url` + `/issues`, again known after the first read (`LinearSource.projectUrls`). Until then the button is not shown.

- A tracker call that times out logs its operation, elapsed time and request count; a successful call over half the timeout logs the same at most once per ten minutes per operation and profile. GitLab, GitHub, Linear and Jira count HTTP requests in each call separately and report the longest request's path without its query or upload secret; Huly reports the count as unavailable. The timeout error on the page is unchanged.
- Status polling logs consecutive failures with the same error text (including its cause) once per profile; a changed error is logged again. The first successful poll after a failure logs `<profile title>: reads again`, even if no status changed. With no watched tasks, polling is skipped and does not count as recovery. Project refreshes keep their own failure state.

## Profiles (BTN-200, `src/profiles/`)

The profile dialog groups OAuth and the fallback token in one "MCP for sessions" box (BTN-491). Jira's separate `JIRA_MCP_TOKEN` goes inside it, below OAuth; GitHub and Linear reuse their REST token, so its input stays with REST sign-in and the MCP box points to it. The list and dialog show "MCP: connected through OAuth" or a reconnect state, without an access-token expiry. A completed unsaved grant explains Check → Save and the ten-minute deadline from starting consent; closing by any dialog control or backdrop asks before losing it. Changing the grant invalidates an earlier check.

Both `profiles/check` and `profiles/save` check the selected MCP OAuth grant in addition to REST (`Profiles.checkedAccount`, `McpOAuth.check`, `src/profiles/mcp.ts`): refresh on expiry or once after refusal, then initialize the remote server (GitHub/Linear) or call `getAccessibleAtlassianResources` and require the site's URL (Jira). A refused refresh or repeated authorization refusal requires reconnecting; transient errors remain retryable. A fresh draft keeps refreshed credentials in its flow until saving, under its original deadline. With OAuth selected, REST checks omit Jira's unused fallback MCP token, including the periodic REST recheck; saving retains that token for later use after disconnecting OAuth. The check's success shares the tracker result line; failures use its existing error area.

- A profile is one tracker account: id (GUID), kind (`huly`, `github`, `linear`, `gitlab`, `jira`), name, values, default flag, whom it signs in as and when its token expires. It lives in the state database (`tracker_profiles`, `docs/storage.md`); the values are kept under the adapter's variable names (`HULY_URL`, `GITHUB_TOKEN` …), so `setup`, the gateway and Tally take them as they are. The adapter's `variables`, `hostVariables`, `alternatives` (Huly: `HULY_TOKEN`, or `HULY_EMAIL` and `HULY_PASSWORD`), `help`, `profileName`, `account` and `projects` serve the profile's sign-in and its project list (`src/{huly,github,linear,gitlab,jira}/profile.ts`).
- A project runs on the profile in `projects.profile_id`; without one, or with one of another kind, on its kind's default profile. `Trackers` and `trackerPlans` go by profile id: two projects of one tracker on two profiles are two connections. A kind with projects but no profile is `none:<kind>`, and the wizard's check says to add a profile.
- The first profile of a kind is its default, and the only one stays so. A new default does not move the projects and feeds the chain has started on the old one (`trackerLocked`): `Profiles.setDefault` links them to the old profile by name (BTN-435); a profile's address stays while anything runs on it (`profiles.hostLocked`). The default profile's values are written into the `env` of the global `~/.claude/settings.json`: a session started by hand gets only the default profile of each kind, never another one — a limit, not a bug. It also gives the GitHub Actions token to projects of other trackers, unless a project names its own (`remoteProfiles`, `docs/ci.md`).
- `/settings` → Trackers and CI (BTN-355, before Chain rules): a row per profile and "Add profile" (`SettingsProfiles.tsx`, BTN-325); a tracker profile's row has "Rules", which opens its tab of Chain rules. A row is quiet while all is well — a lamp, the kind's icon, the name (whom it signs in as and its projects or CIs in the name's tip) and a muted "default" — and only what needs a look is coloured: a refusal or no answer, an expiry within 14 days, hidden CI, a refused pull request; Edit, Make default and Remove are text buttons at its end. A save goes only after the tracker took the values (`profiles/check`, then `profiles/save`); a same account on the same host (kind, host, workspace, login) is a warning. The page gets a secret as "set", never its value; an empty secret field of a stored profile keeps the stored value. While projects use a profile, its host fields stay and it cannot be removed (`profiles.hostLocked`, `profiles.inUse`); a project's profile is closed for change once the chain ran a task of it, like its tracker (`trackerLocked`).
- A profile may set the chain rules of the projects and feeds on it (BTN-66): `active`, `terminal`, `requiredLabels`, `excludedLabels` in `tracker_profiles.rules`, between the shared rules and a project's own (`docs/chain.md`, "Entry into the chain"). `/settings` has a tab per tracker profile in the Chain rules group, beside "All trackers" (`web/src/pages/ProfileRules.tsx`), suggesting the statuses and labels of its projects' vocabularies; the save (`profiles/rules`) is refused when a project or feed on the profile would clash. A feed's profile is `feed_profiles`; a profile a feed runs on counts as in use.
- Every profile is checked again every 15 minutes. A refusal by the tracker (`CredentialsRefused`) turns it red and pauses the chains on it with `profiles.paused`, which names the profile; a host that does not answer does not pause.
- Import at the first start: the tracker variables of `.env` become the default profile of their kind, and every project of that kind runs on it; the mark `profiles.imported` keeps a second start from importing again, and the log says so. After the import the tracker, the CI and Tally no longer read the tracker variables of `.env`.
- **MCP through OAuth** (BTN-475, BTN-485, `src/profiles/oauth.ts`, `oauth-protocol.ts`): Jira, Linear and GitHub profiles have "Connect MCP through OAuth" in the profile dialog (`web/src/pages/ProfileMcp.tsx`), on a new profile too. The providers are fixed in `MCP_OAUTH` (Rovo `https://mcp.atlassian.com/v2/mcp`, `https://mcp.linear.app/mcp`, `https://api.githubcopilot.com/mcp/`). Jira and Linear discover protected-resource metadata from the MCP endpoint's 401 `WWW-Authenticate` `resource_metadata`, or `/.well-known/oauth-protected-resource<resource path>` without that parameter. The resource must match the configured MCP URL and its metadata must stay on that origin; `authorization_servers` selects an issuer from the provider's explicit authorization-origin allowlist (Jira: `https://auth.atlassian.com`; Linear: `https://mcp.linear.app`). Its metadata comes from `/.well-known/oauth-authorization-server<issuer path>`; the issuer must match exactly, S256 must be supported, and every endpoint must pass the same allowlist before registration. Redirects, embedded credentials and non-HTTPS metadata or endpoints are refused. Jira and Linear register a public client dynamically (`token_endpoint_auth_method: none`, ignoring any returned client secret). Registration and consent carry the challenge's `scope`, otherwise the provider's scope (Linear: `read write`) or all resource `scopes_supported` (Jira: the set checked live in BTN-416). Discovery and registration on both live providers were checked in BTN-485 ([verified log](verified.md#trackers)). GitHub uses the user's own OAuth App: its Client ID, Client secret and the callback URL shown by the dialog. The flow is PKCE S256 with a one-use `state`; a callback's `iss` must match the discovered issuer including its path, and is required when the metadata advertises it (Linear). `profiles/oauth/start` answers the consent URL, the browser window ends at `GET /api/profiles/oauth/callback`, which exchanges the code with the MCP `resource` (a Jira grant is checked with `getAccessibleAtlassianResources` against the profile's site) and redirects to `/settings#trackers` with no code or token in the URL; the dialog polls `profiles/oauth/status` and closes the window. An attempt is bound to the draft's id, kind and values and lives 10 minutes, at most 32 at once; `profiles/check` and `profiles/save` take its id as `oauth` (`null` drops a stored grant). A changed host or account field of a stored profile with a grant is refused (`profiles.oauthExpired`): a new identity never keeps the old MCP one.
- OAuth failures go through `Profiles`' logger as one English line with the profile kind, step (`registration`, `code exchange`, `grant verification`, `refresh`) and HTTP status plus the provider's string `error`, or the exception message (`oauth-error.ts`, BTN-484). Response bodies, `error_description` and stacks are omitted; known credentials, callback codes, state and verifiers are redacted, including URL-encoded forms, and whitespace is flattened. The page still gets only its notice code. Stored and unsaved refreshes share this diagnostic path. Checked over a local HTTP provider fixture, including the actual callback's clean redirect ([verified log](verified.md#trackers)); no live provider refusal was induced.
- The callback address is the page's own origin, which the request's `Origin` must match with `Host`: HTTPS, or `http` on a loopback host only (`profiles.oauthAddress`). A page opened on another machine over plain HTTP cannot connect; open it over HTTPS (Tailscale Service) or on localhost of the service machine.
- For direct network access, `server-guard.ts` issues an `even-keel-oauth` cookie only on an authenticated `POST /api/profiles/oauth/start`: `HttpOnly`, `SameSite=Lax`, callback path, ten minutes. Its value is an expiry signed with HMAC-SHA256 under the current access token and a callback-specific purpose. `guard.ts` accepts it only on the exact `GET /api/profiles/oauth/callback`, after Host/Origin checks; it cannot authorize another route, method or bearer request. The ordinary access cookie stays Strict, and the existing OAuth state, PKCE and draft binding still decide whether a code can be exchanged. On completion or guard refusal, `oauth-response.ts` serves a static page that replaces the history URL with `/settings#trackers` and reloads it, with `no-store`, `no-referrer` and a hash-restricted CSP. Committing that page first restores the Strict cookie for the settings request; an HTTP redirect would keep it absent across the cross-site navigation. Guard refusals keep 401/403 and never call `finish`. Checked in Chromium against isolated real server routes and a simulated provider ([verified log](verified.md#trackers)).
- The grant is `tracker_profiles.mcp_oauth` (step 15), never in the profile's values, the key pool, `settings.json` or a session's environment; the page sees only `mcpOAuth.state` (`connected`, `reconnect`). The gateway refreshes it single-flight (compare-and-swap, so a late refresh cannot restore an edited profile's grant), 30 s before expiry or after a 401, saving a rotated refresh token and using it in the next exchange; a refused refresh or a second 401 sets `reconnect`, and the profile's row shows "MCP: reconnect needed" with the dialog's "Connect again". Old Jira v1 grants need a new connection through the profile dialog. The API token for MCP (`JIRA_MCP_TOKEN`, the GitHub and Linear tokens) stays the second way for a server without a browser.
- A CI kind (BTN-201): Forgejo (`forgejo`, `src/ci/forgejo-profile.ts`) is a profile kind that is not a tracker. The kinds are `profileKinds` (`src/profiles/model.ts`): the adapters plus `FORGEJO_PROFILE`, which has no `projects` and serves no project's tracker, so the wizard never offers it. Its card shows the CIs on its host instead of projects; its values go neither to `settings.json` nor to a session, only to packages that ask for `FORGEJO_TOKEN` (`keyPool`, `docs/packages.md`). Its own import is `profiles.forgejo.imported` (`docs/ci.md`).

## GitHub Issues (BTN-65, `src/github/`)

- GraphQL `api.github.com` with the profile's `GITHUB_TOKEN` (fine-grained, Issues: Read and write; Actions: Read for the CI). A fine-grained token covers one owner: a personal repository and an organization's need two profiles. The expiry comes from the `github-authentication-token-expiration` header (`2026-11-03 13:47:15 UTC`, `expirationOf`; checked live on 2026-10-18 with a classic token, a fine-grained one is in `docs/unverified.md`).
- An open issue is `Open` (`ToDo`), one closed as completed (or without a reason) is `Completed` (`Won`), not planned and duplicate are `Lost`.
- Blockers are the native "blocked by", the parent and subtasks are sub-issues, priority is the label `priority: <level>` (or `priority/<level>`), there is no estimate (0). A blocker or parent from a repository without a project has the ID `owner/name#number`.
- `complete` closes the issue as completed. GitHub has no backlog — keep entry into the chain on a label (`requiredLabels`). A pull request is never a task.
- Outsiders (EKR-19, `src/github/trust.ts`): anyone can open an issue and comment in a public repository, and a session has Bash on the user's machine. Only comments of `OWNER`, `MEMBER`, `COLLABORATOR` (`authorAssociation`) and of the token's own login (`viewer`) reach a session: a reply to a question (`commentsAfter`), the last comment in the changelog draft (`milestoneTasks`) and, in PR mode, a review or a comment on the task's pull request (`src/review/github.ts`, REST `author_association`). A skipped one is a line in the service log, once per comment (`Skipped`). The association is GitHub's at the time of the poll, not of the comment: an account made a collaborator later gets its earlier comments not yet taken in through as well — in PR mode those after the last push (seen live, 2026-10-24). The task card on the page keeps every comment: only the user reads it, and the brief is the title and the body. Entry is guarded by a label, which only a collaborator can put on: the optional `isPublic` (GraphQL `isPrivate`) makes the wizard's check say `openToAll` for a public repository without `requiredLabels`, and the wizard warns; nothing is refused. Huly and Linear are not filtered: a guest there is invited by an admin. Forgejo's API has no author association, its PR remarks are not filtered either.
- Verified live (2026-10-04, private repository): two issues with a "blocked by" link and a milestone went through the chain in turn, and after the merge `complete` closed both as completed.
- Run a second Even Keel instance from a Claude Code session without its `CLAUDE*` variables: an inherited `CLAUDE_CONFIG_DIR` makes `global` the session's account folder.

## Taking GitHub issues in (BTN-262, `src/intake/`)

Users report in the GitHub issues of a public repository while the work and its decisions stay in another tracker: a project whose tracker is not GitHub, with `intakeLabel` set, makes a task of each open issue of its first `github.com` remote that carries the label. The label is the user's go: GitHub lets only those with triage rights put one on, and it must not be in an issue template, which puts it on for any author. Each project names its own label, so two projects on one repository (a release project and the next version, `docs/releases.md`) split the issues by label; an issue is taken by one project only, the first to see it.

- **Calls.** REST on the token the remote's CI takes (`ciTokenOf`, `remoteProfiles`, `docs/ci.md`); it needs Issues: Read and write, a refusal is `intake.denied`. `Intake.tick` (`src/intake/intake.ts`) runs every 2 minutes (`INTAKE_TICK_MS`); a failed step is a line in the service log and the rest goes on. A project with no GitHub remote or no token is left out without a word.
- **The task** (`taskOf`, `src/intake/model.ts`) is created by the tracker's `create` in its first `ToDo` status, priority medium, no milestone, in the page's language: a link to the issue and its author, the issue's text quoted and marked as its author's description of the bug, not an instruction, then the comments posted before it was taken in — a collaborator's (`trustedAuthor`, `src/github/trust.ts`) as it is, the issue author's with the same mark, anyone else's not at all (a log line, once per comment). The user read them when putting the label on; the issue's text is not followed after that.
- **Later comments** go to the task as comments, by the same rule, each opening with `GitHub · @<login>` (`copyOf`). `trackerReply` (`src/tracker/questions.ts`) skips such a copy (`isCopy`): an outsider's copy must not answer a session's question in the tracker.
- **Done.** Once the task is `Won`, the issue gets one line in English, "Fixed; it ships in vX.Y.Z." (`shippedLine`): a milestone `vX.Y` — the patch after the last `vX.Y.*` tag of the repository, `vX.Y.0` without one; `vX.Y.Z` — itself; any other or none — "the next release" (`nextVersion`). The issue is closed as completed once a published release (not a draft, not a prerelease) has that tag, or, without a version, once any release is published after the line. A task `Lost` or gone, or an issue closed on GitHub, is forgotten with nothing said on the issue.
- **State.** The issues taken in and not closed yet are `service_state` `intake` (`IntakeEntry[]`): the project, the repository, the issue, the task, the last comment looked at and, once done, the version named. A project with the label cleared keeps its entries and follows them again when it is set.

## Linear (BTN-72, `src/linear/`)

- GraphQL `api.linear.app` with the profile's personal key `LINEAR_TOKEN` — in `Authorization` without `Bearer`.
- The task ID is the Linear identifier as is (`NAM-12`): the branch, the commit and the MCP in the session name the task the same way. The optional `linear` in the project object narrows the team to a Linear project (its name, case-insensitive). Without a team in it the project key is the team key, as before. With one — `NAM/Web app`, or `NAM/` for the whole team (`linearPlace` in `src/linear/model.ts`, BTN-73) — the key is only Even Keel's, so several Even Keel projects work on one team, one per Linear project; the task IDs stay the team's. Two projects with the same `linear` place share a read and split it by milestone. A whole-team project (`NAM/` or the key `NAM`) next to a project of one of its Linear projects reads that project's tasks too, and the config does not catch the overlap: give them milestone rules that split them, or narrow both.
- The status goes by the team's workflow state type: `triage` and `backlog` — `UnStarted`, `unstarted` — `ToDo`, `started` — `Active`, `completed` — `Won`, `canceled` and `duplicate` — `Lost`, an unfamiliar type — `UnStarted`; the name is the state's name. Linear has its own backlog, entry into the chain is as in Huly.
- Blockers are the inverse `blocks` relations, the parent and subtasks are native, priority is native (1 Urgent … 4 Low, 0 — none), there is no estimate (0: Linear has points).
- The milestone is the project milestone (`projectMilestone`), not a cycle: Linear itself carries unfinished work over to the next cycle, so an order by cycles will not work.
- `complete` is the first state of type `completed` by `position` in the task's team; a closed task (`completed`, `canceled`, `duplicate`) — `false`.
- The link is `linear.app/<urlKey>/issue/{id}`; the adapter learns the organization's `urlKey` on connecting, and there are no links before that.
- API traps: query complexity is up to 10000, a list without `first` counts as 50 — nested ones get an explicit `first`. `issue(id)` on a nonexistent task fails the whole response — tasks by ID are read with the filter `number: { in }` by the team key. Linear also merges fields of one object inside `or` through "or" — an explicit `and` is needed.
- Verified live (2026-10-04, a team narrowed to a Linear test project): two tasks of a project milestone with a "blocks" link went through the chain in turn — the blocker first despite the second's higher priority — and after the merge `complete` moved both to Done, the worktrees and branches were cleaned up.

## GitLab Issues (BTN-410, `src/gitlab/`)

- REST API v4 on `GITLAB_URL` (default `https://gitlab.com`) with `GITLAB_TOKEN`, a PAT with the `api` scope. Addresses are web roots, including an optional installation prefix, without `/api/v4`. The profile uses `/user` and `/personal_access_tokens/self`; missing expiry support (404) leaves `expiresAt` null, but a known token without `api` is refused. The registry supplies the profile kind, wizard and settings choices through the existing tracker-place mechanism, with no database schema change. Profile changes take the existing live path through `Profiles` and `TrackerLink`.
- A project names its full path (`gitlab: group/subgroup/name`), while task ids are `<Even Keel key>-<iid>`. REST path segments are URL encoded; ids and links keep subgroups. Opened is `ToDo`, closed is `Won`, priority comes from `priority::<level>` or `priority: <level>`, estimate is 0. Every REST page is read through `x-next-page`, with a full-page fallback when that header is absent.
- The links endpoint supplies `is_blocked_by`, `blocks` and `relates_to`. Only the first orders this task. Free has only related links; no text dependencies are parsed. The card keeps all three kinds. Work-item hierarchies are read through GraphQL, including child pagination, on Free too; an absent widget or an older schema leaves parent/children empty. Authentication and runtime failures propagate rather than appearing as an empty hierarchy.
- Milestones include inherited group milestones, the current closed choice, assignment/copy/clear and tasks of a named milestone for changelog drafts. Closed tasks sharing active milestones contribute progress. Cards show every human note, in time order; answers and last comments use only the token owner's id or a current membership from `/members/all/:user_id` with `access_level >= 20` (Reporter), including inherited membership. A 403/404 membership lookup excludes the author, and skipped notes are logged once. System notes are excluded. Uploads appear on the card and inline in its text; trusted answers carry their files to the session through the authenticated file route.
- Fixtures cover model mapping, hierarchy, API operations and trust decisions. The adapter and the MCP plugin were checked live on GitLab.com and a self-managed CE 19.5, at the root and under a path prefix: answers from a Reporter who is a member through a group, the plugin in Claude and OpenCode sessions, and a profile token revoked mid-chain (the tracker goes down, a new token saved in the profile is picked up live). The hierarchy of older versions was not checked; the guide recommends 19.5 or later. GitLab CI and merge requests use the same profile (`docs/ci.md`, `docs/chain.md`).

## Jira Cloud (BTN-417, `src/jira/`)

- The optional profile secret `JIRA_MCP_TOKEN` is only for `jira@even-keel`: `mcpValues.JIRA_BASIC_AUTH` is base64 of `JIRA_EMAIL:JIRA_MCP_TOKEN`, never the REST token. Enable API token authentication for the Atlassian MCP server in the organization's settings first, then [create an Atlassian MCP V2 application token with all scopes](https://id.atlassian.com/manage-profile/security/api-tokens?autofillToken&appId=mcp-v2&selectedScopes=all). A profile check with this field set signs in over REST and calls `getAccessibleAtlassianResources` through MCP v2 (`src/jira/mcp.ts`, JSON and SSE replies, session cleanup); the result must include the profile site's URL. Without the site, `jira.mcpSite` asks for a new token after the admin switch; an MCP refusal is `jira.mcpToken`. Both offer the creation link on the profile form. `tools/list` alone proves no access. The field uses the existing credentials JSON in `tracker_profiles`, with no schema or file format change. The gateway takes profile edits live; a profile without the field still works over REST, while its Jira package names `JIRA_MCP_TOKEN` as missing.

- REST v3 with Basic `JIRA_EMAIL:JIRA_TOKEN`; `JIRA_URL` is the site's origin only (`https://<site>.atlassian.net`, https, no path: `siteUrl`, else `jira.url`), a profile with only some of the three is `jira.incomplete`. `JiraApi.open` signs in through `/rest/api/3/myself` on the site; when the site refuses (a token with scopes works only through the gateway), it reads the cloud id from `<site>/_edge/tenant_info` and tries `https://api.atlassian.com/ex/jira/<cloudId>`, and every later call goes to the base that answered. Jira Data Center is out of scope; Jira has no CI, the remote's CI and PR mode apply as for any tracker.
- The Even Keel key is the Jira project key and the task id is the issue key as it is: no `projectKey`, no `closingRef`, no `isPublic` (a Jira site has no anonymous issue filing by default). Comments are not filtered by author, as in Huly and Linear.
- The status goes by its category: `new` — `ToDo`, `indeterminate` — `Active`, `done` — `Won`, an unfamiliar one — `UnStarted`. Jira has no status kind for the backlog: a Jira Software backlog is a board's view, not a status, and the API cannot tell its issues from ready ones. So a `new`-category status whose `untranslatedName ?? name` is `Backlog` (`sameName`) is `UnStarted` and stays out of the default rules; a board whose backlog is not such a status keeps unread issues out by `requiredLabels` or its own `active` list. Issue responses, including `search/jql`, omit `untranslatedName`: `resolveStatuses` fills it by status id from `/project/<key>/statuses` for task reads, cards (including links to other projects) and `ready`. Each call shares one catalog per project and fetches it afresh on the next call; `chainTasks` reuses the catalog it already read. The localized `name` is kept for display and explicit status rules. `ready` moves an `UnStarted` issue through its first transition to a ready `new`-category status. `chainTasks` reads the project's statuses (every issue type), turns the open ones into ids and searches `status in (…)` through `POST /search/jql` with `nextPageToken`, plus the closed issues of the open ones' fix versions for the milestone progress.
- `complete` takes the first transition to a status of the `done` category; with none from the current status it logs which status had none and returns `false` — the task stays open, as `complete` with no change does. Tasks by id go through `POST /issue/bulkfetch` by 100; an id Jira does not have lands in `issueErrors` and is left out.
- Blockers are the issue links of the type named `Blocks` (`inwardIssue` — this issue is blocked by it, `outwardIssue` — it blocks), found by name at connect: without such a type `connectJira` throws `jira.blocksType` with the types the site has, so a renamed type stops the profile's projects instead of running them out of order. "Related" on the card is `Relates` either way; other link types are dropped. The parent is the `parent` field, children are subtasks and, for an issue above the base level (`issuetype.hierarchyLevel > 0`, an epic), the issues with `parent in (…)`, counted by a JQL search of 50 keys at a time.
- Priority: the built-in Highest, High, Medium, Low, Lowest by name (urgent, high, medium, low, low); a site's own scheme by its place in `/priority/search`, spread over urgent…low; `create` picks the built-in name for the level, else the place. The estimate is 0. The milestone is the earliest fix version by release date (one without a date last); `milestones` offers the project's unreleased, unarchived versions plus the issue's own, `moveMilestone` replaces all the issue's fix versions with the one picked (`null` — none), `setMilestone` copies the earliest version of a task of the same project.
- Descriptions and comments are ADF: `adfToMarkdown` and `markdownToAdf` (`src/jira/adf.ts`) cover headings, lists (nested, ordered with a start, task lists), code, quotes and panels, tables, rules, hard breaks, mentions, emoji, cards, status lozenges, dates and media. Ordinary text nodes escape Markdown and HTML punctuation before their ADF marks are applied, so literal tags, emphasis and line-leading block markers stay text on the card. Inline code and code blocks keep their content; the reverse converter reads backslash escapes, including delimiters inside marks and link labels. Briefs use the same Markdown, leaving ordinary commands readable. A media node names its file by `alt`, matched to the issue's attachment by file name (`mediaLinks`); the card's attachments are the issue's, with `url: null`, and `file` serves only one of the issue's attachments, from `/attachment/content/<id>?redirect=false`. `commentsAfter` gives a comment's files by the same match.
- `create` takes the project's `Task` type by `untranslatedName ?? name`, else the first standard type of `/issue/createmeta/<key>/issuetypes` (`hierarchyLevel === 0`, not a subtask), then readies the issue. With no standard type it fails before creating anything. `vocabulary` gives the project's statuses, every label of the site (`/label`, paged) and the names of the open versions; `milestoneTasks` reads a version's issues with their newest comment (`orderBy=-created`).
- The page links `<site>/browse/{id}` and `<site>/browse/<key>`. Fixtures cover the ADF conversion, the model, the profile, the gateway fallback and every source operation (`src/jira/*.test.ts`). Localized status responses, task reads and creation were checked live on 2026-10-27 (BTN-473, [verified log](verified.md#trackers)); the remaining checks are in `docs/unverified.md`, "Jira Cloud" and "Jira MCP plugin".

### `huly` — the model

- The server is `@firfi/huly-mcp`. The credentials (`HULY_URL`, `HULY_WORKSPACE`, `HULY_TOKEN` or `HULY_EMAIL`/`HULY_PASSWORD`) are inherited from the session environment and are not in `.mcp.json`, which has only the constant `TOOLSETS` (the set for working a task).

- Sessions started by hand: the default Huly profile's credentials are in `env` of `~/.claude/settings.json`: the session applies it itself, and `share.ts` transfers the file into account folders.
- How to use it — `plugins/huly/README.md`.
- OpenCode gets both Huly guards from `plugins/huly/opencode/huly.mjs` (plugin 0.5.8): markdown writes are checked before execution; estimate calibration shares the command hook's request and once-per-session marks. For MCP calls, OpenCode 1.18.25 passes the raw result to `tool.execute.after`, so calibration is appended as a text block in `content`, before OpenCode assembles the output (the plugin also accepts the assembled `output` shape). Checked live on Windows on 2026-10-25 with OpenCode 1.18.25 and `opencode/deepseek-v4.1-flash-free`: the gateway tool is `plugin_huly_huly_update_issue`, malformed markdown was refused, a mismatched estimate was refused once, and a corrected retry reached Huly and was read back. A second session saw calibration on an allowed estimate's result and none on its next call.
