# The CI layer

The layer, which CIs the chain counts, the check without a CI, commands after a green main, which CI a project has, git over HTTPS.

## The layer

Before a project launches a session, `ProtectionAudit` reads its GitHub/Forgejo remotes independently of workflow
discovery, using the normal remote profiles. Results are cached for five minutes per repository, branch and profile
selection, in `EvenKeelState.protection`. It never changes server rules or blocks a launch. GitHub's active rulesets
and classic branch protection contribute separately to force-push and deletion protection. Each unique active GitHub
ruleset is read for `bypass_actors`: an empty list means no bypass, a nonempty, hidden or inaccessible list keeps the
possible-bypass warning without discarding the protection verdict. Classic protection contributes its administrator
bypass only when it exists. See the [GitHub rules API](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset).
Forgejo's rule list is paged; an exact rule wins over globs, and disagreeing globs yield unknown. Older Forgejo rules
with a boolean `enable_push` but no `enable_force_push` forbid force pushes; an explicit switch takes precedence,
and incomplete or malformed responses stay unknown. Checked live on 2026-10-26: Forgejo 16.0.3 returned these older
rules with `apply_to_admins: true`; GitHub returned an active ruleset with empty `bypass_actors` and no classic rule.
Both remotes reported protected without bypass warnings, using the project's selected profiles. API failures and
unsupported GitLab checks yield unknown. The project page links to branch settings for missing/unverified protection
and administrator bypasses.

A private GitHub repository on the free plan has no branch protection or rulesets at all (EKR-121, read live on
2026-11-16): `branches/<b>/protection` and `rules/branches/<b>` both answer 403 "Upgrade to GitHub Pro or make this
repository public to enable this feature.", `branches/<b>` 200 with `protected: false`. Only that triple, matched on
the 403 bodies' `message` already read, is `unavailable`; another wording falls back to `unknown`. The page gives it a
band of its own with no link and one "Don't show again" — a "Got it" mark per repository URL
(`protection.plan:<url>@<project>`) stamped with the branch, so later reads keep it closed (`planProtectionWarnings`).

`src/ci/` is separate from the tracker layer and knows nothing of tasks beyond the `[KEY-N]` ids in commit subjects.

| `adapters.ts` | `CI_TOKENS`, `ciVariables` (kept out of the sessions' environment by `sessionBase`), `CI_SOURCES` (the adapter of each kind; the end-to-end tests put their fake in place of Forgejo's), `ciSource`, `projectTargets` |

| `shared.ts` | `SharedSources`: shared API answers per repository and token, with runs scoped by branch and limit |
| `verdict.ts` | `verdictOf`: what the CIs say about a pushed commit — green, red, pending or unavailable |

The contract is two calls: `runs(limit, branch?)` — the latest runs, newest first, scoped to a branch when given; `jobs(run)` — the jobs of a run with their steps when the CI gives them. A project's watch always passes its branch, so its current run, history and median contain only that branch's runs. GitHub uses the `branch` query parameter; Forgejo uses `ref=refs/heads/<branch>` (`branch` is ignored by Forgejo). PR feedback omits the branch filter and selects the PR's head commit. The optional `log(job)` is a job's plain-text log (`getText` in `http.ts`): GitHub's `/actions/jobs/<id>/logs`, Forgejo's `/api/v1/repos/<owner>/<repo>/actions/jobs/<id>/logs`, GitLab's `/api/v4/projects/<id>/jobs/<id>/trace`. Forgejo and GitLab are asked with `accept: text/plain`; GitHub answers that with 415, so its log is asked with `application/vnd.github+json` and comes after a redirect to a signed address. `readFailure` (`src/ci/report.ts`) reads a failed run's jobs and the tail of its first failed job's log (`logTail`, 60 lines without the timestamps GitHub and Forgejo prefix): `CiWatch.failed(run)` for the fix's text, PR mode's `check` for a failed run of the pull request's head the session has not been told of. A log that cannot be read — an older CI, a refusal — leaves the run with its link alone.

The optional `rerun(run)` (BTN-846) reruns only a run's failed jobs, the run keeping its id and ending anew with a new `stoppedAt`: GitHub's `POST /actions/runs/<id>/rerun-failed-jobs` (the token needs `actions: write`), GitLab's `POST /projects/<id>/pipelines/<id>/retry`; `post` in `http.ts` turns 401/403 into `ci.rerunDenied`. Forgejo has none: 16.0.3 (gitea 1.22.0) has no rerun endpoint under `/repos/{owner}/{repo}/actions/`. `CiWatch.rerun` throws `ci.rerunUnsupported` without it and, after a rerun, polls the history at once and for `WANT_MS`; `SharedSources` passes `rerun` through and drops its cached runs and jobs of that repository after it. The chain's use of it is `ci.rerunFailed` below and `docs/chain/main-ci.md`, "The rerun before the red".

## Which CIs the chain counts

`projects[].ci` of the settings, read live, also set from the project's settings panel:

```json
"ci": { "guard": true, "kinds": ["forgejo", "github", "gitlab"], "waitMinutes": 30, "recheckMain": true, "fixTask": false, "rerunFailed": true }
```

- `guard` — the guard of `main` as a whole, `true` by default. `false`: no counted CI and no check (`hubMainDeps` gives the verdict `none`, `checking` no commands, `checkMain` is `skipped`, `mergeCheck` `[]`) — a push is not waited for, nothing is checked before the merge or on `main`, and no fix is made. The other keys are kept and apply again once it is back on. A wait from before it was turned off is released at the next settle; a fix session already running is left alone.
- `kinds` — the CIs whose verdict the chain waits for; without the key — all three (`DEFAULT_CI` in `src/settings/defaults.ts`); empty — none, and the project's own check takes over (below).
- `waitMinutes` — how long the next launch waits after the push: `null` or no key — as long as it takes, `0` — not at all (faster, but the next task may start on a broken `main`).
- `recheckMain` — `false` turns off the second run of the project's check on a `main` that moved (below); a merge whose check before it did not report is checked on `main` anyway.
- `fixTask` (BTN-115) — who fixes a red `main`, for a red CI and a failed check alike. `false`, the default — a session without a tracker task, started by the dispatcher, and the working session of the current task is stopped until it is done. The fix is over once its branch is in `main` and the session is not working or waiting: a turn that ended with a background command still running (`shell`, a loop waiting on a CI log) does not hold it, the cleanup stops the session and kills the command (`docs/chain/unattended.md`, "Background command"). `true` — a task created in the tracker, taken after the current one; the adapter then needs `create`. Read at the red verdict, so a change applies to the next one.
- `rerunFailed` (BTN-846) — `true`, the default: the first red verdict on a pushed `main` reruns its failed jobs once and waits up to an hour for them, so a flaky test or a runner failure starts no fix; red again — the fix as above, told it was a second red. `false` — the fix at the first red. Only a CI that can rerun through its API (GitHub, GitLab); with Forgejo among the failed runs nothing is rerun.
- The settings panel writes the key only when it differs from the default.
- In PR mode (`pullRequests`, `docs/chain/pr-mode.md`) Even Keel pushes task branches to the pull request's remote, so a workflow `on: push` without a branch filter runs on them too; the failed runs of a pull request's head commit are feedback to the task's session, not a verdict on `main`.

## The check without a CI (BTN-104)

`projects[].commands.check` — lines run in order, like `commands.beforeStart`; empty — no check. It is in effect when no counted CI will judge `main`: `kinds` is empty, the repository has none of them, or one is not `ok` (`mergeCheck` in `src/chain/mainci.ts`). With `ci.guard: false` it never runs.

- **On the branch, before the merge.** The `PreToolUse` hook of the `agent-bridge` plugin (`plugins/agent-bridge/hooks/merge-check.mjs`) sees a Bash command that merges the branch of the session's worktree, asks `GET /api/sessions/<id>/check` (404 — not a chain session; `{ commands: [] }` — no check) and runs the commands in the worktree. The first failure blocks the merge (exit 2) with the command, its code and the tail of its output; the session fixes it and merges again. Once every command passed on a worktree without changes to tracked files, the hook reports the tree of its `HEAD` and the commands with `POST /api/sessions/<id>/check` `{ tree, commands }` (EKR-103; OpenCode's plugin the same); the service keeps the latest report per project and task in memory (`CheckReports`, `src/chain/checkreports.ts`). The plugin is installed in user scope, so it reaches the sessions of every tracker.
- **On main, if it moved.** Only the hook's report shows the check ran: without the plugin, with an old one, a merge outside Bash, a report lost to the 2-second timeout or a service restart in between there is none. Before the cleanup the dispatcher takes the reported tree, if its commands are still the project's `commands.check` (`MainCheckDeps.reportedTree`); after the push, `MainCheck.pushed` compares it with the tree of `main` (`checked` on the push; no report — `unreported`, for a project with a check). When the CI cannot judge the push (`none` at once, `unavailable` after the wait), `withoutCi` decides: the reported tree — green, logged `is the tree the check before the merge reported`; no report — the push goes to `ci[<project>].local` whatever `recheckMain` says, logged `the check before the merge did not report`; another tree and `recheckMain` — the push goes to `ci[<project>].local` too, and before the next launch the dispatcher runs the check in that task's place (`checkMain`, a yellow line `ciWait.local` on the page): `TaskPlaces.readyAhead` brings the place to `main` and runs the commands before start, and the check runs only if the place is then on `main` (a task with its own commits is skipped with a log line). The check never touches the user's main checkout; only the commands after a green `main` (below) run there.
- **A failure on main** is a red `main` (`MainFailure.check`): the same fix — a session or, with `fixTask`, a task — with the command and the output tail in its text (`redReport`), the same single fix at a time, and a failure on the push of the fix stops the chain with `check.fixFailed`.

## Commands after a green main (BTN-156)

`projects[].commands.afterGreen` — lines run in order in the project's main checkout (`repo`) once a push of `main` is green: by the CI or by the project's own check, the same event (`MainCheck.passed`), whether or not `waitMinutes` ran out before the verdict. Without `ci.guard` there is no verdict, so they never run. The point is the project's own service on this machine — build it and restart it — when the CI runs elsewhere (a GitHub runner cannot reach the workstation) and agents do not build it.

- **Guard.** It is the only place the dispatcher touches the main checkout: the commands run only if it is on the project's `branch` and its `HEAD` is the green commit (`MainCheckDeps.runAfterGreen` in `src/chain/mainci.ts`); otherwise a log line `afterGreen: <KEY>: skipped after <commit>: …`.
- **Once per commit.** Pushes glued into one verdict give one run, for the latest commit. Before the commands start, `ci[<project>].afterGreen` of the chain state (`docs/storage.md`) is set to the commit and saved, so a command that restarts Even Keel itself does not run them again after the restart. One run at a time per project: a green push that comes meanwhile runs after it.
- **A failure is not a red main.** The code is green, the environment broke: no fix, the chain goes on; a `leftovers` entry `afterGreen.failed` under the last task of the push (the warning on the project page) and the output in the service log.
- **The chain waits.** While they run, the next launch of the project is held, `ciWait.after` (`docs/chain/main-ci.md`).
- **On the page** (BTN-829). The first card of the CI panel has an "After green" row under the push: a dot and how the last run went — running on a commit since a time (while `ciWait.after` holds, an "i" after it and "The next task waits for them" in the row's tip, BTN-1378), done, the command that failed with its exit code (the output stays in the log), skipped with the guard's reason (`afterGreen.offBranch`, `afterGreen.pastCommit`), or started with no end seen when the service restarted mid-run; a run that ended has when at the row's right, a cell of its own. The start and end are `ci[<project>].afterGreenRun` of the chain state (`AfterGreenRecord`), written by `MainCheck.afterGreen` and `afterGreenEnded`, so the row survives a restart; a project without `commands.afterGreen` has no row. The view is `MainCheck.view` → `state.mainCi[<project>]` (`MainCiView`, filled in `src/service/hosting.ts`).
- **A push by hand** (BTN-707). A move of the remote's `main` the chain did not make — `git sync` or `git push` from a terminal — is awaited too, by the counted CIs (`ci.kinds`, guard on) only. `MainCheck.settleOutside` reads the remote's `main` the counted watches agree on (`MainCheckDeps.remoteHeads`, each watch's `CiWatch.remoteHead`) at every settle, before the chain's own pushes are judged: a move to a commit that is not the chain's awaited push (`check`, `local`) or its last green is a push from outside, logged `ci: <KEY>: main of the remote is at <commit>, pushed outside the chain; waiting for the CI`. Green — `passed` as for a push of the chain: `ci[<project>].green`, the commands with the same guard and the same once per commit. Red or without a verdict — a log line only, no fix, nothing stopped; the CI panel shows the red run. The panel labels such a push "pushed by hand" and the chain's own "pushed by the chain" (BTN-829, "The page" below). It holds no launch (only the commands running hold one, as above), and a newer push replaces the one awaited. A push of the chain of the same commit takes it over (`MainCheck.pushed`). The awaited push is kept in memory only, and the first look after a start is no push: a push made just before a restart, or while the service was down, runs nothing. A failure of the commands after such a push stays in the log: a `leftovers` entry belongs to a task, and the push has none.

## Which CI a project has

Read from `git config --get-regexp ^remote\..*\.url$` and the workflow folders of the project's checkout when the project appears in the config or its `repo` changes (`CiWatches.apply`, `src/ci/watches.ts`), and again every minute for every project (`CiWatches.refresh`): a remote added or a first workflow in the same checkout gets its watch, a CI gone loses it, and a watch whose remote stays keeps its state. Only a change is logged (`ci: <KEY> watches …`, or `watches no CI` when the last one went); a checkout whose remotes cannot be read on a refresh keeps its watches. A changed profile gives every watch a new source at once (`CiWatches.tokensChanged`).

Every reader of a checkout's remote addresses (the CI watches, `ProtectionAudit`, `ProjectRemotes`, PR mode, the project and folder checks) goes through `remoteUrls` (`src/git/remote-urls.ts`, BTN-1484): git's answer is kept per git runner and folder while the inode, mtime and size of the checkout's `config` (the common one for a linked worktree, found from `.git`'s `gitdir:` and `commondir` without git) and of its `config.worktree` stay the same. A folder without a `.git` of its own asks git every time; remotes in a global or `include.path` file are seen only after the checkout's own config changes. On `src/e2e/` (36 files, 153 tests) this took the reads from 3,936 of 23,400 top-level git processes to 278 of 19,783; before, most came from `ProtectionAudit.check` asked by the machines (1,554), `CiWatches.refresh` (1,236 with `reconcile`) and `ProjectRemotes.apply` (1,023).

- A `github.com` remote with `.github/workflows` — GitHub Actions.
- A public host of a forge with no adapter (`bitbucket.org`; `UNSUPPORTED_HOSTS` in `src/ci/remote.ts`) — no CI, and no token is asked for (EKR-8). A new adapter takes its host out of that list.
- A `gitlab.com` remote, or a host named by `GITLAB_URL` of any GitLab profile, with a root `.gitlab-ci.yml` file — GitLab CI. Nested groups stay in the project path; a self-managed installation's prefix and web port come from its profile. HTTP(S) remotes take the longest configured prefix matching a whole path segment, regardless of profile order; a root profile is the fallback. With profiles on the host but no matching prefix or root, no target is returned. SSH paths carry no installation prefix, so the first base on the host still wins; several distinct bases log the selected one once per ordered set of installations. CI and merge requests share this selection. Profile changes recheck the watches live.
- Any other host — Forgejo, if the repository has `.forgejo/workflows`, or `.github/workflows` (Forgejo falls back to it when it has none of its own). An unknown host without a GitLab profile is taken for Forgejo too; the Forgejo profile's check (`forgejoAccount`) first asks `/api/v1/version` and says the server is not Forgejo or Gitea unless it answers `{ version }` in JSON (a JSON 401/403 there is a server that wants a sign-in for its API, left to the `/user` request).
- No remote or no CI configuration — no CI and no badge.

The token is chosen per remote (`ciToken`, `src/ci/adapters.ts`). The CI is a property of the remote, not of the tracker: a project on Huly with a `github.com` remote has GitHub Actions too (Even Keel itself).

- Forgejo: a Forgejo profile (`FORGEJO_URL`, `FORGEJO_TOKEN`; `src/ci/forgejo-profile.ts`) whose `FORGEJO_URL` has the remote's host — the default one when several do, else the first. Since BTN-476 the same profile is also a task tracker (`docs/trackers.md`, "Forgejo Issues"): one token for issues, CI and pull requests. `.env` is not read for it: at the first start `importForgejo` (`src/profiles/store.ts`) turns a `FORGEJO_TOKEN` of `.env` into one profile per host — the host of `FORGEJO_URL` when `.env` has it, then those of the projects' Forgejo remotes, never a second profile for one host (`docs/storage.md`).
- GitHub Actions: the project's tracker profile if it is a GitHub one, else the default GitHub profile (`docs/trackers.md`, "Profiles"); the token needs **Actions: Read**.
- GitLab CI: the project's GitLab profile for the selected installation (origin and prefix), otherwise the default GitLab profile for that installation, otherwise the first there. Profiles for other installations on the same host are excluded. An empty profile address means `https://gitlab.com`. The profile requires a personal token with `api` scope and project access. A Forgejo profile check identifies GitLab by its public host, API metadata, sign-in redirect or `/api/v4/version`, and asks for a GitLab profile instead.

A project can name the profile itself (BTN-231): `remoteProfiles: { github?: <profile id>, forgejo?: <profile id>, gitlab?: <profile id> }`, one per kind, not per remote. The chosen one wins while it exists, is of the target's kind and, for Forgejo, is on the remote's host, or for GitLab, names the selected installation; otherwise the automatic choice above holds, with no error — a profile removed later falls back by itself. PR mode takes the same token (`ciTokenOf` in `src/service.ts`), so the pull requests follow the choice too: checked live on 2026-10-25 with two Forgejo profiles of different users on one host, where the pull request's author followed the choice and a switch to a token without pull request rights refused the next one with `review.notOpened`. A GitHub CI followed the choice live on 2026-10-24. A change applies at once: `projectsChanged` calls `CiWatches.tokensChanged()`. The page offers the choice in the project's Check and CI tab (`remoteChoices`, `web/src/pages/remoteProfiles.ts`) only when the kind has two candidates or a choice is already made.

With no profile for it, or when the token does not reach the repository's runs (`ci.denied`, HTTP 404), the CI of that remote is not shown at all, with no error (`CiWatch.hidden`, all CIs); the log gets a line only when an error appears or changes and one when the CI answers again (BTN-333): the page and the main check take only `CiWatches.shown(project)`. On Trackers and CI of `/settings` a profile's row lists the CIs it serves (`ProfileView.ci`) and says in its tip which ones it does not reach (`ProfileView.hiddenCi`).

A Forgejo repository with Actions turned off answers `/actions/runs` with the same 404 as one the token does not see, and its checkout may still have `.github/workflows` (Forgejo falls back to them, so `ciTargets` takes the target). Only on that 404 `forgejoSource` asks `GET /api/v1/repos/<owner>/<repo>`: a repository seen with `has_actions: false` makes the runs fail with `ci.actionsOff` (BTN-1500); a repository not seen, a failed request or any other `has_actions` keeps the 404. Such a watch is `CiWatch.off`, not `hidden`: not shown, not judging a main and in neither `ProfileView.ci` nor `hiddenCi`, so the profile shows no warning. It is polled again every `ERROR_RETRY_MS` like any error, so Actions turned on later bring the CI back without a restart, and turned off at a working CI take it away just as quietly.

Projects in separate clones of one remote (BTN-210) each get their own watches of the same repository, and each waits for the verdict on its own pushes: a watch reads the pushes and the tasks of a run in its own clone. Their sources share API answers for `FRESH_MS` (10 s, below `POLL_MS`), a failure too (`SharedSources` in `src/ci/shared.ts`), keyed by forge, host, owner, repository and token. Runs are further keyed by branch and limit: two projects on different branches never share their run history, while two on the same branch share a poll regardless of their remote names. Jobs are shared by run and status across branches; a log is not shared. Projects whose tokens differ (another profile in `remoteProfiles`) poll apart, since the token decides whether the CI is seen at all. A branch changed live clears the watch's current run, history, median and awaited push and polls the new branch. The fix is shared (BTN-217): while one project of the remote and main branch fixes a red `main`, the others' launches wait and their red pushes start no second fix (`docs/chain/projects.md`, "Projects of one remote").

## Git over HTTPS

BTN-1541. The service's own git takes the token of the remote's profile, so a host without Git Credential Manager (Docker) needs no credential helper set up by hand. `withCredentials` (`src/git/credentials.ts`) wraps a `Git`: a call to a remote (`push`, `fetch`, `pull`, `ls-remote`, a `git sync` alias) reads the folder's remote addresses (`remoteUrls`), keeps the `https:` ones without their user (`credentialUrl`), asks `CredentialsOf` for them and runs git with `credentialEnv`. `credentialedRemote` does the same for `RemoteGit` (`ls-remote` and `clone` of the wizard and of a machine's connect), by the address among its arguments.

- **Nothing kept.** The credentials live only in the call's environment, through git's env-only config (`GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n`, git 2.31+; an older git ignores it and goes on its own helper): for each address `credential.<url>.helper` is reset and then set to a shell helper that prints `EVEN_KEEL_GIT_USERNAME_<i>`/`EVEN_KEEL_GIT_PASSWORD_<i>` of the same environment on `get` and ignores `store` and `erase`. Nothing reaches git's config, a file or a session's environment; a clone's `origin` is the address as typed. A credentialed call sets `core.hooksPath` to a path that cannot be a folder: a hook would see the token, and a session can point the repository's hooks anywhere.
- **Which profile.** `gitCredentials` (`src/ci/git-credentials.ts`) takes the CI's choice: `ciTargets` and `ciToken` with the project's `remoteProfiles`, then the default profile for the host ("Which CI a project has" above). The user name is the forge's: GitHub `x-access-token`, GitLab `oauth2`, Forgejo and Gitea the profile's login or `even-keel` (they read only the token). GitLab profile tokens are personal access tokens, read from the profile's values as the CI reads them: nothing is refreshed. An address with no profile, `http:`, SSH and local remotes are left to git.
- **Where it applies.** The chain's git on every machine (`MachineOwn.git`: task branch pushes, the main branch's sync, moves), the hub's PR-mode push (`reviewDeps`), the forward carry's fetch, the reassigner's `ls-remote`, the folder checks of a machine's connect ("Right to push") and the clones of the wizard (the host's default profiles, no project yet) and of a connect. The LFS restore after a failed checkout goes on git's own helper.
- **A token that may not write.** `deniedOf` reads the forges' refusals (GitHub "Write access to repository not granted" and "Permission to … denied", GitLab "not allowed to push", Forgejo "permission denied for writing", then curl's 403). Such a push is made once more on git's own credentials, so a read-only CI token never takes away a push a helper of the user's could make; refused again, the result carries `GitResult.denied`, and `syncMain` and `openPull` give `git.readOnly` with the profile's name and the address, its fix the profiles' page (`noticeFixOf`). The task branch push at the end of a turn only logs, as any failure of it.
- **Machines.** The token stays on the hub: a machine asks `POST /link/credentials` for each call (`docs/machines/link.md`, "The two directions").
