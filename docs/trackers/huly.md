# Huly

The adapter `src/huly/` through `@hcengineering/api-client` — the same client as the git hooks in `~/.githooks`. Its source gives the tasks server's editor (`editor.ts`, BTN-779; "The tasks server" below).

The `@hcengineering/*` packages are loaded on the first connection, never on import (`connectHuly`, `withClient` in `profile.ts`, Tally's `connect`): a service without a Huly profile does not load the client at all. `src/huly/lazy.test.ts` holds this in a fresh process.

The npm package does not carry the client either (BTN-666): it is ~19.5 MB in ~3,200 files, a third of the install. Every load goes through `hulyClient.require` (`src/huly/client.ts`): first the code's own resolution — a clone has the packages in `devDependencies` — then `state/huly-client/` of the data folder, taken only when every package of `HULY_CLIENT` is there at its pinned version, so an update of Even Keel that pins new ones installs anew. When neither has them, the service writes a `package.json` of `HULY_CLIENT` into that folder and runs `npm install --omit=dev` there (`installDependencies` in `src/packages/npm.ts`); the call that found nothing throws `huly.clientInstalling`. The install starts at the service's start and on every change of the profiles when a Huly profile exists (`installForProfiles`), and on the first load otherwise — the check of a new profile then answers `huly.clientInstalling` and is pressed again in a minute. While it runs or after it failed (`huly.clientFailed` with npm's error) the state carries the notice in `hulyClient`, and `/status` shows a "Huly client" tile with Retry (`huly/install`; off while installing). A failed install is not retried by itself. The chain needs nothing of its own for the wait: a Huly connection that throws is a tracker `down`, and the next poll connects again. Tally's worker thread only looks for the client (`install: false`) and leaves the install to the service. `src/dependencies.test.ts` keeps `@hcengineering/*` out of `dependencies` and `HULY_CLIENT` equal to their `devDependencies`, pinned exactly.

Tiptap is overridden (BTN-698): `@hcengineering/text` asks for Tiptap `^2`, which has no fix for GHSA-cp6q-959q-f8rh, so `HULY_CLIENT_OVERRIDES` pins every `@tiptap/*` package under it at a 3.x release. The same map is the `overrides` of Even Keel's `package.json` and of the data folder's `package.json`, and a data folder counts as installed only when the Tiptap packages are at that version too, so an install from before the override is redone. On Tiptap 3, `@hcengineering/text`'s HTML conversion (`htmlToJSON`, `jsonToHTML`, the `html` format of `fetchMarkup`/`uploadMarkup`) throws in Node; Even Keel uses only the `markdown` format, which goes through `text-core` and `text-markdown` and never reaches Tiptap. A new `@hcengineering/*` version is checked against this: `src/dependencies.test.ts` fails when its `@tiptap/*` list has a package the override lacks, and `src/huly/client.test.ts` runs the real markdown round trip. Drop the override once Huly moves to Tiptap 3.

- Threads under comments (BTN-897): a reply in a comment's thread is a `chunter:class:ThreadMessage` attached to the comment, not to the issue, so a query of the issue's `ChatMessage`s misses it. `card`, `file` and `commentsAfter` read the replies with `attachedTo` in the comments' ids (`repliesTo` in `source.ts`). The card nests them under their comment in the neutral `TaskComment.replies`, and `task_read` prints each one under its comment as `#### ↳ reply: …`; `commentsAfter` gives the later comments, the replies in the question's own thread and those in the later comments' threads in one list by time (`answersAfter`), so an answer typed in the question's thread reaches the session; `file` finds a reply's attachments too. A `findAll` of `ChatMessage` or `ThreadMessage` with any `projection` answers no documents (BTN-1019, checked live 2026-11-13; a projected `Milestone` query is fine), so these are always read whole: with `{ _id: 1 }` there `file` found only the issue's own attachments. The page's card does not show the replies yet (BTN-909).
- The project key is the Huly project identifier, unless the optional `huly` names another one (BTN-172): then the key is only Even Keel's (`BTNR` with `huly: BTN`), the task ids are Huly's (`BTN-300`), and `connectHuly` looks the space up by the named identifier (`spaceOf`). The wizard picks the Huly project and offers its identifier as the key; a second project on it may keep that key (BTN-271, the page tells them apart by `projectLabel`) or take its own.
