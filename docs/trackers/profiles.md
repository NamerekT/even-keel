# Tracker profiles

## Profiles (BTN-200, `src/profiles/`)

The profile dialog's primary action is **Check and save**: it checks new or changed values, then saves in the same operation. **Check** alone remains available without saving. A fresh check is reused; a duplicate warning from an automatic check stops the first save, and a second press with unchanged values accepts it. Errors stay in the dialog. Fields are inert until the operation ends, and a suggested name is sent with the first save unless the user supplied one.

The profile dialog groups OAuth and the fallback token in one "MCP for sessions" box (BTN-491). Jira's separate `JIRA_MCP_TOKEN` goes inside it, below OAuth. Linear, GitHub and GitLab have no OAuth (BTN-604): their MCP servers take the tracker's own token (`mcpKeys`), so the kind's view says `mcpShared` and the box is one line pointing to the token above. The list and dialog show "MCP: connected through OAuth" or a reconnect state, without an access-token expiry. A completed unsaved grant explains Check → Save and the ten-minute deadline from starting consent; closing by any dialog control or backdrop asks before losing it. Changing the grant invalidates an earlier check.

Both `profiles/check` and `profiles/save` check the selected MCP OAuth grant in addition to REST (`Profiles.checkedAccount`, `McpOAuth.check` in `src/profiles/oauth.ts`, the probe in `src/profiles/mcp.ts`): refresh on expiry or once after refusal, then call `getAccessibleAtlassianResources` and require the site's URL. A refused refresh or repeated authorization refusal requires reconnecting; transient errors remain retryable. A fresh draft keeps refreshed credentials in its flow until saving, under its original deadline. With OAuth selected, REST checks omit Jira's unused fallback MCP token, including the periodic REST recheck; saving retains that token for later use after disconnecting OAuth. The check's success shares the tracker result line; failures use its existing error area.

**The grant's person** (BTN-590). Atlassian gives a grant to whoever is signed in to Atlassian in the browser, perhaps not the person of the REST token, and then sessions write under another name with other rights. After the site check, a grant's probe also calls `atlassianUserInfo` (`checkJiraMcp` with an `authorization`; an API token's person is the profile's e-mail, so it is not asked), and its `account_id` and name ride on the grant as `OAuthRecord.user`, kept through refreshes; a failure there leaves the person unknown and the check passes. The REST side is `ProfileAccount.user` (Jira's `/myself` `accountId`), which `Profiles` remembers per profile from every save and periodic recheck. Different ids give `profiles.mcpOtherAccount` — a warning, never a refusal: `CheckResult.mcpWarning` in the dialog, which checks a new grant at once, and `ProfileView.mcpOAuth.warning` in the row, each a warn band with "Connect again". Unknown on either side is silence. Linear, GitHub and GitLab have no grant to compare (BTN-604). Live behaviour: [unverified](../unverified/trackers.md#the-person-of-a-jira-mcp-grant-btn-590).

- A profile is one tracker account: id (GUID), kind (`huly`, `github`, `linear`, `gitlab`, `jira`, `forgejo`), name, values, default flag, whom it signs in as and when its token expires. It lives in the state database (`tracker_profiles`, `docs/storage.md`); the values are kept under the adapter's variable names (`HULY_URL`, `GITHUB_TOKEN` …), so `setup`, the gateway and Tally take them as they are. The adapter's `variables`, `hostVariables`, `optionalVariables` (GitLab: `GITLAB_URL`, blank for GitLab.com; the profile dialog does not ask for them, EKR-123), `alternatives` (Huly: `HULY_TOKEN`, or `HULY_EMAIL` and `HULY_PASSWORD`), `help`, `profileName`, `account` and `projects` serve the profile's sign-in and its project list (`src/{huly,github,linear,gitlab,jira,forgejo}/profile.ts`). A new profile's default name is the account's own — the Huly workspace, the GitHub owner or login, the GitLab user, the Linear organization, the Jira site, the Forgejo host — without the tracker's name before it: the page draws the tracker as an icon beside the name (BTN-1382). Names saved before that keep their "Huly · " prefix; the setup's summary drops it (`profileShortName`). A feed in a server message is `ABC/WEB`, the project and the feed's key (`feedLabel`, `src/config.ts`).
- A project runs on the profile in `projects.profile_id`; without one, or with one of another kind, on its kind's default profile. `Trackers` and `trackerPlans` go by profile id: two projects of one tracker on two profiles are two connections. A kind with projects but no profile is `none:<kind>`, and the wizard's check says to add a profile.
- The first profile of a kind is its default, and the only one stays so. A new default does not move the projects and feeds the chain has started on the old one (`trackerLocked`): `Profiles.setDefault` links them to the old profile by name (BTN-435); a profile's address stays while anything runs on it (`profiles.hostLocked`). The default profile's values are written into the `env` of the global `~/.claude/settings.json`: a session started by hand gets only the default profile of each kind, never another one — a limit, not a bug. An edit of a default rewrites its kind's variables there; the service's start (`Profiles.start`, BTN-1167) only adds a default's variable the file lacks and leaves one already there, even set by hand, so a default stored before its kind reached the file (Forgejo before BTN-476) gets there without a new save. **Hidden from sessions started by hand** (BTN-1498, `tracker_profiles.hand_sessions`, `Profiles.setHandSessions`, route `profiles/handSessions`, "Hide from hand sessions" / "Give to hand sessions" on a tracker profile's row): as its kind's default such a profile writes nothing there and takes its kind's variables out (as no default does), and the start takes out each variable still holding its value instead of adding it, leaving one set by hand to another value; the flag is the profile's, so a new default brings its own, and it changes nothing for the service, the gateway's key pool and chain sessions. It is for a tracker only the service and the benches use (Huly after the move to the built-in tracker): hand sessions work through `tasks` and need no keys of it. `share.ts` copies the file into every account folder, so a chain session can read those keys from its own configuration folder: `chainSettings` blanks them only in its environment. This is accepted, as are `.env`, the state database and its backups, and the guide says so (`docs/guide/security.md`, BTN-1117). It also gives the GitHub Actions token to projects of other trackers, unless a project names its own (`remoteProfiles`, `docs/ci.md`).
- `/settings` → Trackers and CI (BTN-355, before Chain rules): a row per profile and "Add profile" (`SettingsProfiles.tsx`, BTN-325); a tracker profile's row has "Rules", which opens its tab of Chain rules. The built-in tracker's row is always first (`BuiltinRow`, BTN-769): a lamp, its icon and name, no buttons — it has no account, so nothing to connect or edit. A row is quiet while all is well — a lamp, the kind's icon, the name (whom it signs in as and its projects or CIs in the name's tip) and a muted "default" — and only what needs a look is coloured: a refusal or no answer, an expiry within 14 days, hidden CI, a refused pull request; Edit, Make default and Remove are text buttons at its end. A save goes only after the tracker took the values (`profiles/check`, then `profiles/save`); a same account on the same host (kind, host, workspace, login) is a warning. The page gets a secret as "set", never its value; an empty secret field of a stored profile keeps the stored value. While projects use a profile, its host fields stay and it cannot be removed (`profiles.hostLocked`, `profiles.inUse`); a project's profile is closed for change once the chain ran a task of it, like its tracker (`trackerLocked`).
- A profile may set the chain rules of the projects and feeds on it (BTN-66): `active`, `terminal`, `requiredLabels`, `excludedLabels` in `tracker_profiles.rules`, between the shared rules and a project's own (`docs/chain/entry.md`, "Entry into the chain"). `/settings` has an option per tracker profile in the "Whose rules" pick of the Chain rules group, after "All trackers" (`web/src/pages/ProfileRules.tsx`), suggesting the statuses and labels of its projects' vocabularies; the save (`profiles/rules`) is refused when a project or feed on the profile would clash. A feed's profile is `feed_profiles`; a profile a feed runs on counts as in use.
- A profile of a kind that moves statuses (Huly, Linear, Jira) keeps its status moves in `tracker_profiles.moves` (BTN-554, "Moving a task to a chosen status" above): `start`, `review` — a status name or `null` (leave the status), `done` — a done status name; no key — not set. Its tab of Chain rules has the section "Statuses on actions" in the same form as the rules, saved after them by `profiles/moves`; the picks offer the statuses `profiles/statuses` lists (`null` — the tracker named none, an error — not read), start and review only those in the chain, done only those the rules take for done, and a save that breaks this is refused (`statusMoves.outside`, `statusMoves.notDone`), as is a name the read list lacks (`statusMoves.unknown`, BTN-667; with no statuses read the save goes through, there is nothing to check against). A chosen value the read list lacks is marked "not in the tracker" in its pick and in a strip under the field (`missingMove`). Moves a `config-import` sets go past that check: once they apply, the service checks the changed ones against the statuses (`changedMoves`, `checkChangedMoves` in `src/service/trackers.ts`) and logs what a save would refuse, without undoing the import. Right after a new profile of such a kind is saved, the dialog asks for them in one more step, offered by `defaultMoves` (the first started status in the chain, the started one named for review); "Skip" leaves none.
- Every profile is checked again every 15 minutes. A refusal by the tracker (`CredentialsRefused`) turns it red and pauses the chains on it with `profiles.paused`, which names the profile; a host that does not answer does not pause.
- A check that got no answer (`unreachable`) is tried again in 1, 2 and 4 minutes, then left to the round; a refusal waits for the round. Such a profile is also checked again, at most once a minute, when its tracker's link turns live (`recovered` of `startTracker`) or a CI that takes its token answers again (`onRecovered` of `CiWatch`): the first check comes 15 s after the start, when every call of the service times out for about a minute, and used to keep the profile "not answering" for 15 minutes (BTN-678, `retryLater`, `recheckSoon` in `src/profiles/service.ts`).
- **A profile turned off** (BTN-830, `tracker_profiles.disabled`, `Profiles.setDisabled`, route `profiles/disable`): the switch at the end of its row in Trackers and CI. Off, the service reaches nothing of its host: `Trackers` builds no link for its plan (the view is `off` with `disabled`, no polling of its projects and feeds), the 15-minute recheck and the 1-2-4-minute retries skip it, `ciToken` gives no token for a CI that would take it (no other profile's token either), `timeTrackers` writes no time through it, and a task card, a tool, a vocabulary, a status list or a project list of it answers at once with `profiles.disabled` and a "Turn on" button (`noticeFixOf`), with no call. Its chains do not start: `profileBlock` holds unattended and auto-resume, Start answers `profiles.disabled` (`disabledBlock` in `src/service/accounts.ts`). Turning off is refused while a chain on a project or feed of it is running, paused or queued: `profiles.chainsRunning` names the chains and gives "Stop the chain". Turning on starts nothing: the profile is checked again at once, and Start waits for a fresh read (`chain.unread` below). The global `settings.json` keeps the default profile's values, so a session started by hand still gets them. The home page dims a project card of a turned-off profile, says so instead of red errors and offers "Turn on"; a Start a stale page still shows asks "Profile X is off — turn it on?" and only turns it on.
- **Start only by a fresh read** (BTN-830, `listBlock` of the dispatcher, `readFresh` in `src/tracker/health.ts`): a tracker view remembers when its link last turned live (`liveSince`); a reader whose last full read (`readAt`) is older was read before the tracker went down or the service started. Start reads such a project's tracker anew first and refuses with `chain.unread` while a reader stays stale: a new task the old list lacks might be first in the order. Before BTN-830 Start went by the old list whenever it had work in it, with the tracker down too. The home card shows "Reading tasks…" in Start's place until then.
- Import at the first start: the tracker variables of `.env` become the default profile of their kind, and every project of that kind runs on it; the mark `profiles.imported` keeps a second start from importing again, and the log says so. After the import the tracker, the CI and Tally no longer read the tracker variables of `.env`.
- **MCP through OAuth** (BTN-475, BTN-485, `src/profiles/oauth.ts`, `oauth-protocol.ts`): Jira profiles have "Connect MCP through OAuth" in the profile dialog (`web/src/pages/ProfileMcp.tsx`), on a new profile too. Only Jira, because Rovo MCP v2 takes no REST token: Linear's and GitHub's MCP take the tracker's token, and OAuth there only added a second identity that nothing compared with the token's owner (and for GitHub a user's own OAuth App), so BTN-604 removed it; a stored Linear or GitHub grant is dropped when the profiles are read (`readProfiles`) and its row is cleared at the next save. The provider is fixed in `MCP_OAUTH` (Rovo `https://mcp.atlassian.com/v2/mcp`); another kind is refused as `profiles.oauthUnsupported`. Discovery takes protected-resource metadata from the MCP endpoint's 401 `WWW-Authenticate` `resource_metadata`, or `/.well-known/oauth-protected-resource<resource path>` without that parameter. The resource must match the configured MCP URL and its metadata must stay on that origin; `authorization_servers` selects an issuer from the provider's explicit authorization-origin allowlist (`https://auth.atlassian.com`). Its metadata comes from `/.well-known/oauth-authorization-server<issuer path>`; the issuer must match exactly, S256 must be supported, and every endpoint must pass the same allowlist before registration. Redirects, embedded credentials and non-HTTPS metadata or endpoints are refused. A public client is registered dynamically (`token_endpoint_auth_method: none`, ignoring any returned client secret). Registration and consent carry the challenge's `scope`, otherwise all resource `scopes_supported` (the set checked live in BTN-416). Discovery and registration on the live provider were checked in BTN-485 ([verified log](../verified/trackers.md)). The server binds an attempt to the profile's fields and refuses blank ones only as `profiles.incomplete`, so the dialog stops a check, a save or a connection itself and names the blank fields by their labels (`unfilled`, `web/src/pages/profileForm.ts`, BTN-597). The flow is PKCE S256 with a one-use `state`; a callback's `iss` must match the discovered issuer including its path, and is required when the metadata advertises it. `profiles/oauth/start` answers the consent URL, the browser window ends at `GET /api/profiles/oauth/callback`, which exchanges the code with the MCP `resource` (the grant is checked with `getAccessibleAtlassianResources` against the profile's site) and redirects to `/settings#trackers` with no code or token in the URL; the dialog polls `profiles/oauth/status` and closes the window. An attempt is bound to the draft's id, kind and values and lives 10 minutes, at most 32 at once; `profiles/check` and `profiles/save` take its id as `oauth` (`null` drops a stored grant). A changed host or account field of a stored profile with a grant is refused (`profiles.oauthExpired`): a new identity never keeps the old MCP one.
- OAuth failures go through `Profiles`' logger as one English line with the profile kind, step (`registration`, `consent`, `code exchange`, `grant verification`, `refresh`) and HTTP status plus the provider's string `error`, or the exception message (`oauth-error.ts`, BTN-484). A callback carrying `error` or no `code` is the `consent` step: it logs only the provider's `error` (or `no code`) and the page gets `profiles.oauthDenied`; every later failure, including an HTTP 400 on the exchange or a 401 on the grant check, gets `profiles.oauthFailed` (BTN-588). Response bodies, `error_description` and stacks are omitted; known credentials, callback codes, state and verifiers are redacted, including URL-encoded forms, and whitespace is flattened. The page still gets only its notice code. Stored and unsaved refreshes share this diagnostic path. Checked over a local HTTP provider fixture, including the actual callback's clean redirect ([verified log](../verified/trackers.md)); no live provider refusal was induced.
- The callback address is the page's own origin, which the request's `Origin` must match with `Host`: HTTPS, or `http` on a loopback host only (`profiles.oauthAddress`). A page opened on another machine over plain HTTP cannot connect; open it over HTTPS (Tailscale Service) or on localhost of the service machine.
- For direct network access, `server-guard.ts` issues an `even-keel-oauth` cookie only on an authenticated `POST /api/profiles/oauth/start`: `HttpOnly`, `SameSite=Lax`, callback path, ten minutes. Its value is an expiry signed with HMAC-SHA256 under the current access token and a callback-specific purpose. `guard.ts` accepts it only on the exact `GET /api/profiles/oauth/callback`, after Host/Origin checks; it cannot authorize another route, method or bearer request. The ordinary access cookie stays Strict, and the existing OAuth state, PKCE and draft binding still decide whether a code can be exchanged. On completion or guard refusal, `oauth-response.ts` serves a static page that replaces the history URL with `/settings#trackers` and reloads it, with `no-store`, `no-referrer` and a hash-restricted CSP. Committing that page first restores the Strict cookie for the settings request; an HTTP redirect would keep it absent across the cross-site navigation. Guard refusals keep 401/403 and never call `finish`. Checked in Chromium against isolated real server routes and a simulated provider ([verified log](../verified/trackers.md)).
- The grant is `tracker_profiles.mcp_oauth` (step 15), never in the profile's values, the key pool, `settings.json` or a session's environment; the page sees only `mcpOAuth.state` (`connected`, `reconnect`) and the warning about the grant's person, never its tokens. The gateway refreshes it single-flight (compare-and-swap, so a late refresh cannot restore an edited profile's grant), 30 s before expiry or after a 401, saving a rotated refresh token and using it in the next exchange; a refused refresh or a second 401 sets `reconnect`, and the profile's row shows "MCP: reconnect needed" with the dialog's "Connect again". Refused is a 401, `invalid_grant`, `invalid_client`, or any 4xx of an OAuth endpoint with an OAuth `error` except 408, 429, `temporarily_unavailable`, `server_error` and `slow_down` (`oauthHttpError`, BTN-589): Atlassian answers a refresh of an app revoked in Connected apps with 403 `unauthorized_client`, which used to stay retryable and asked the token endpoint at every probe. With `reconnect` set nothing goes to the provider until a new grant. A stored grant's failing refresh is logged once per reason, and `MCP OAuth refresh works again` once it succeeds. Old Jira v1 grants need a new connection through the profile dialog. The Atlassian MCP V2 token (`JIRA_MCP_TOKEN`) stays the second way for a server without a browser.
- A tracker and a CI in one profile (BTN-201, BTN-476): Forgejo (`forgejo`) was a CI's kind only, with no `projects`; since BTN-476 it is the adapter `src/forgejo/adapter.ts`, and a stored profile serves the tracker as it is, with no schema step: the values are the same `FORGEJO_URL` and `FORGEJO_TOKEN`. `profileKinds` (`src/profiles/model.ts`) still takes CI-only kinds as a second argument (a kind without `projects`: no `settings.json`, its card shows the CIs instead of projects), but none is passed now. A Forgejo profile's tip names its projects and also the CIs on its host when there are some. As every tracker's, the default Forgejo profile's values go into the global `settings.json` (a session started by hand gets them; they did not before BTN-476), and never into a chain session's environment. Its first-start import stays `importForgejo` (`profiles.forgejo.imported`, `docs/ci.md`): the service passes the adapters to `importProfiles` without `forgejo`, since `FORGEJO_TOKEN` alone is the CI's older form; `FORGEJO_URL` beside it adds its host first, and a host that already has a Forgejo profile gets no second one.
