# The tracker layer: the link and contract tests

How a profile's connection and poll behave, and the live contract tests.

- Each profile in use has its own connection and poll (`src/tracker/link.ts`, `poller.ts`) and a card on the `/status` page (`TrackerView`: its state, last good poll, error and, per project and task feed it reads, when it last read it — `readAt`, `docs/web/project-page.md`). A failed call closes the connection and the next one connects again, except an answer that the project, team or issue asked for is not there (`TrackerNotFound`, BTN-317): closing would fail the calls of the profile's other projects under way on it ("Connection closed" in Huly), so a project deleted or renamed in the tracker would stall them all. A project's read that fails the same way on every refresh is logged once, and once more when it reads again. A project's task feeds (BTN-66, `docs/chain/entry.md`, "Task feeds") are read as projects of their own ids, each on its own profile. A task link goes by the tracker of its project or feed (`trackerUrls`, the `issueUrl` template with `{id}` or `{number}`), one of no known project by the default profile of the tracker most projects run on (`trackerUrls.default`, `linksTracker`: a tie goes to the first project's, no projects — no link); the stats link a task by the url its launch recorded, the template only without one. A project with nothing to run links to its page in the tracker and to each feed's in the feed's (`trackerUrls.pages`, by the project's or the feed's id, BTN-329; the optional `projectUrl`, checked live on 2026-10-21): GitHub — `https://github.com/<owner/repo>/issues`; Huly — `<url>/workbench/<workspace>/tracker/<project _id>/issues`, the `_id` learned on the first read of the project's tasks (`HulySource.projectIds`); Linear — the team's `https://linear.app/<urlKey>/team/<KEY>/all`, or for a key narrowed to a Linear project that project's `url` + `/issues`, again known after the first read (`LinearSource.projectUrls`). Until then the button is not shown.

- A tracker call that times out logs its operation, elapsed time and request count once until that read succeeds; recovery logs the count of the failures. Automatic task and chain reads pass a retry key to `TrackerLink.run`: the same read waits 20, 40, 80, 160, then at most 300 seconds after successive timeouts, without reconnecting during that delay. Other reads do not clear its count, and a profile reset clears the delay. A broken connection is the same reason for that delay as a timeout — the tracker did not answer either way (Node's `fetch failed` with the reason in `cause`, or the request's own timeout). The call's abort signal cancels outstanding HTTP work through `trackedFetch`. A successful call over half the timeout logs its measurements at most once per ten minutes per operation and profile. GitLab, GitHub, Linear and Jira count HTTP requests in each call separately and report the longest request's path without its query or upload secret; Huly reports the count as unavailable. The timeout error on the page is unchanged.
- **A tracker that did not answer (BTN-825).** The link remembers the error the tracker did not answer with — a timeout or a broken connection — and while it holds, every call the page asks for fails at once with that error instead of waiting the whole timeout again. Those calls go through `TrackerLink.page`: the card (`GET /api/tasks/<id>`), a file of a task, the task's actions ("Into the chain", "To the backlog", the labels, the milestone) and the changelog's list of a milestone. The vocabulary — the page's (`GET /api/projects/<id>/vocabulary`), a session prompt's lines of roles and the check below — goes through `TrackerLink.aside`, held the same way, but its refusal is its own: it neither puts the tracker down nor brings it back (EKR-106). The chain's own reads keep going through `TrackerLink.run`: they are what brings the tracker back, and they wait their own delay. Any call that answered — even that what was asked for is not there — clears the memory, and the page goes on as usual. The page's answer is the error itself: the same code and the same text it got after the timeout. `GET /api/projects/<id>/tools` reads no tracker — the project's own folder and the account folders — so it is never held by a tracker that does not answer.
- **A vocabulary refused while tasks are read (EKR-106).** A full read of a reader reads its vocabulary too, once each time the link turns live (a saved token resets the link). A refusal with a notice, such as Forgejo's `forgejo.scope` for `read:organization` on an organization's repository, goes into `TrackerView.termsRefused` by reader, and the project page names the project and its feeds it holds, with the notice and its fix; a refusal without one is retried on the next read. Each text is logged once. A session prompt that leaves out a tracker's line of roles says so in the log: `prompt: the <KEY> chain line is left out: <why>`.
- **Writes of the tasks server (BTN-929).** `tasks_create`, `task_update` and `task_comment` go through `TrackerLink.write` with the operation's name (`create`, `update`, `comment`), which the log uses instead of the last method called. The timeout bounds the tracker's silence, not the call: every answer — an HTTP request answered through `trackedFetch` (`CallDiagnostics.onAnswer`) or a settled call of the source, its `editor` or the editor's `files`/`markers` (so Huly, which counts no HTTP, too) — gives it the whole `timeoutMs` again, so a batch of tasks with files and links on a slow GitLab.com runs to its end. After a timeout every next call of the source inside that write throws, and the batch stops instead of going on behind the session's back. A write that timed out after an answer leaves the tracker's health as it was (`live`), keeps the connection and holds no page call; one without any answer is the tracker not answering, as a read. Writes are never delayed by the read back-off, and each of their failures is logged. A `tasks_create` the tracker broke off answers with the tasks created before it and tells the session to repeat with the same `retry` (without one, to read `tasks_list` first).
- Status polling logs consecutive failures with the same error text (including its cause) once per profile; a changed error is logged again. The first successful poll after a failure logs `<profile title>: reads again`, even if no status changed. With no watched tasks, polling is skipped and does not count as recovery. Project refreshes keep their own failure state.

### Writing task labels (BTN-507)

The optional `TaskSource.relabel(id, { add, remove })` returns the saved label names. `trackerOf` forwards it only when present; a connected tracker publishes the capability as `trackers[].relabel` (absent in older snapshots means false). Remove first, then add; names are trimmed and compared with `toLocaleLowerCase`, as in `toTask`. Existing labels keep their spelling. Other labels stay attached. An empty add list can remove all labels.

| Adapter | Label definitions and write |
| --- | --- |
| Huly | Workspace issue `TagElement`s; creates a missing definition in `core.space.Workspace`, using the default issue category or `tracker.category.Other`. Removes and adds `TagReference`s through collection operations, preserving the issue's label counter; returns the references read back. |
| GitHub | Pages the issue and repository labels; creates missing repository labels with `createLabel`, then writes `updateIssue.labelIds` once and returns its labels, paging the remainder. |
| GitLab | Reads the issue and project labels (ancestor group labels included); creates missing project labels, then replaces `labels` in one issue update and returns the saved names. |
| Linear | Pages the issue labels and the team's available labels (workspace labels included, groups excluded); creates missing labels with the issue's `teamId`, then writes `issueUpdate.labelIds` once and returns its labels, paging the remainder. A mutation with `success: false` is a refusal. Adding the name of a label group (`isGroup`) that no usable label shares is refused with `task.labelGroup` before any write (BTN-668): Linear puts no group on an issue and creates no label under a group's name. |
| Jira | Labels are free strings: replaces `fields.labels` and reads the saved names back after Jira's empty update response. No definition is created. |
| Forgejo | Reads the issue's labels and the repository's plus its organization's (a user's repository answers 404 there, taken for none; a token without `read:organization` gets 403 first, and then the repository's `/teams` decides: 405 is a user's repository with no organization labels, anything else keeps the scope error, never read as the repository's labels alone, so a relabel makes no repository twin of an organization's label; EKR-106); creates a missing repository label in grey, then replaces the issue's labels by id (`PUT …/labels`) and returns the saved names. |

`POST /api/task/labels` takes `{ task, add: string[], remove: string[] }`; both lists are required and an empty list is allowed. `taskControl` (`src/tracker/control.ts`) routes by the task's reader, including feeds. After a successful write it immediately refreshes the reader, as `ready` does: labels can admit a task to the chain, so `fillMilestone` must run before it enters. Without a refresher it patches the reader's task with `toTask`, updates the chain and broadcasts state, including the derived question flag. Neither path waits for the next tracker poll. The card itself is read afresh through its existing GET route. An unsupported adapter gives `task.cannotRelabel`; a failed read/create/write gives `task.relabelFailed`, with a fix link to tracker profiles; a refusal the adapter names itself (a `NoticeError`, such as `task.labelGroup`) reaches the page as it is. The underlying error remains the error's cause, not page text. Every refusal, of the label route and of "Into the chain" and "To the backlog" alike, logs a `relabel:` line with the task, the tracker and the cause. A failed operation can have created a definition or changed some Huly references before the refusal; there is no transaction across tracker requests. Refresh the task before retrying.

Fixtures cover all six adapters, case matching, missing definitions, pagination, clearing labels, failures, service state and HTTP validation. Every provider but Forgejo, its refusals included, was checked live by 2026-11-01, Forgejo's on 2026-11-14 ([verified log](../verified/trackers.md)).

### Moving a task to a chosen status (BTN-554)

The optional pair `TaskSource.moveTo(id, name)` and `statuses()`, and the optional `name` of `complete(id, name)`. `moveTo` moves a task to the status of that name (compared as `sameName` does) and answers the status it is in, `null` when the tracker has no way there; `statuses()` lists every status the profile's tracker has, a name once (`uniqueStatuses`). Only Huly, Linear, Jira and the built-in tracker have them; a kind's view carries `moves: true` for the page.

| Adapter | `moveTo`, `statuses`, `complete` with a name |
| --- | --- |
| Huly | The status of the name in the project type (`namedStatus`), written as any status change; every issue status of the workspace. `complete` takes the named one only of the `Won` category, another is an error. |
| Linear | The state of the name in the issue's team (`moveState`); `workflowStates` of every team the key sees, paged by 50. `complete` takes the named `completed` state of the team. |
| Jira | The workflow's transition into a status of the name; none — logged and `null`. `/rest/api/3/status` for the list. `complete` takes a transition into a Done-category status of that name, none is an error. |

`StatusMover` (`src/tracker/mover.ts`) moves a task when Even Keel starts it (`start`) and when it opens the task's pull request (`review`), by the profile's moves and the source's over them (`movesOf`, `src/chain/moves.ts`). Only forward (`moveVerdict`): on a start only a task of the `ToDo` category, on a pull request any open one, never one already there; a target the rules put out of the chain is not tried (`statusMove.outside`), since the chain would let the task go at once. A refusal or an error is logged, never stops the chain, and stays in memory by reader (`trackers[].moveFailures`) until a later move of the task goes through; the page shows those of open tasks. Every close takes the chosen done status (`doneMove`) through one piece, `closeInto` of `src/tracker/close.ts` (BTN-1163): one the rules do not take for done is not tried (`statusMove.notDone`), a refused one is `tracker.completeRefused` with `status` and `level`. The closes are four: a merge (`MergeCloser`, retried on each read), a merged pull request (`Reviews.apply`; a refusal goes into `PendingCloses`, which the reader's `MergeCloser` retries whatever main has of the branch and shows with its own), a pull request with nothing to open (`Reviews.doneWithout`), a `NO CHANGES:` or `TASK DONE` mark and "Accept as answer" (`UnchangedDeps`, wired in `src/service/closing.ts`). The last ones pause the chain or refuse the button with the notice as the cause, marked `held` (no "retries by itself"); "Accept as answer" checks the status before it comments. `level` (`profile`, `source`) leads the notice's button to the setting. A fifth way of closing goes through `closeInto` too.

## Contract tests on live trackers (BTN-470, `src/e2e-trackers/`)

The adapters' unit tests run on recorded answers and do not see a live API change. `src/e2e-trackers/contract.test.ts` is one set of cases over `TaskSource` and `TrackerAdapter`, run against each stand in turn: sign in (`account`), list projects, `create` a task and read it back in a `ToDo` status (`tasks`), find it among `chainTasks`, `brief`, `unready` and `ready`, `moveTo` the stand's `active` status, `relabel` on and off, two comments and `commentsAfter`, the `card`, a `blocks` pair read from both sides, and `complete` — `true` once, then `false`. A case the stand cannot run is skipped with its reason in the report — a method the adapter lacks (GitHub and GitLab have no `ready`/`moveTo`), no task created, no pair seeded — so a skip never passes as green. The contract writes no link and deletes nothing: each stand's `blocks` pair is seeded once by hand and stays open in the backlog, and the cases' own task is closed at the end, also after a failure. A new tracker is one more stand, not a new set; the CI adapters (`src/ci/`) are not in it yet.

- A stand (`Stand`, `stands.fixture.ts`) is a name, the adapter, a profile's values, the project's `place` (the key and the `projectKey` value), optionally `blocks: [blocker, blocked]`, `active` and `done`. `EVEN_KEEL_TRACKER_STANDS` holds the list — the JSON itself or the path of a file with it; empty, the set runs nothing, and on CI it fails, since a night without stands checks nothing. An adapter without a stand is listed as a skip. `EVEN_KEEL_TRACKER_STANDS_SKIP` and `EVEN_KEEL_TRACKER_STANDS_ONLY` (stand or adapter names, comma-separated; `selectStands`) pass over some stands or run only those, each skipped one listed with its reason; an `ONLY` name no stand has fails the run, and so does a CI run with every stand skipped.
- `npm run test:trackers` runs it; `npm test` and `test:all` leave it out. The stands are the maintainer's: test projects of their own on Huly (workspace `ekcheck`, EKW), GitHub, Linear, Jira Cloud, GitLab.com and Forgejo, the file built from the benches' tokens outside this repository.
- `.github/workflows/trackers-e2e.yml` ("Tracker contract") runs it every night at 03:00 UTC on `dev` and by hand, with the stands from the secret `TRACKER_STANDS`. The self-hosted stands are reached over the tailnet: with the secrets `TS_OAUTH_CLIENT_ID` and `TS_OAUTH_SECRET` (a Tailscale OAuth client for `tag:ci`) the job joins it first; without them `TRACKER_STANDS` holds only the stands on the internet. The task said Forgejo's runner; it is on GitHub because since 2026-11-02 the repository's CI is.
- **Huly is a step before a release, not a night** (BTN-1489). Since 2026-11-22 the self-hosted Huly is up only on demand, and a night against it was red on a connect timeout. The workflow's `ON_DEMAND` (`huly`) names the stands up only on demand: the night and a plain run by hand skip them (`EVEN_KEEL_TRACKER_STANDS_SKIP`), and a run by hand with the input `on_demand` runs only them (`EVEN_KEEL_TRACKER_STANDS_ONLY`), titled "Huly contract" instead of "Tracker contract" (`run-name`). One file rather than a second workflow, because GitHub dispatches only workflows already on the default branch. `scripts/huly-contract.sh` on the workstation does the step: it brings Huly up, runs `gh workflow run trackers-e2e.yml --ref dev -f on_demand=true`, finds the new run by its title, watches it and brings Huly down — also after a failure or Ctrl+C — and exits with the run's result. Its up and down commands are the host's: `EVEN_KEEL_HULY_UP` and `EVEN_KEEL_HULY_DOWN`, from the environment or from the file `EVEN_KEEL_HULY_STAND` names (`~/.config/even-keel/huly-stand` by default), the stand's address and ssh host never in the repository; the up command returns once Huly answers.
- **A red night holds every release, and so does the Huly contract.** `scripts/nights-green.sh` takes the latest finished run of each nightly workflow — this one, "Real CLIs" and "macOS" (`docs/ci.md`) — of the night or by hand on `dev` (for this one, not titled "Huly contract"), and fails unless it is a success; it takes the latest "Huly contract" on `dev` the same way, and with none yet it fails too, since nothing starts that run by itself. `publish.yml` runs it before `npm publish`, and the release's first step names it (`docs/releases.md`, "A release"). A red night is lifted by a fix on `dev` and a green run by hand (`gh workflow run trackers-e2e.yml --ref dev`), a red or missing Huly contract by a green `sh scripts/huly-contract.sh`. A nightly workflow with no run yet passes with a note: GitHub starts a schedule only once the workflow is on the default branch. "macOS" is the exception: it left the push check of `dev` for its night, so with no run on `dev` it holds the release (`docs/ci.md`, "macOS"). GitHub mails the failure of a scheduled run to whoever last changed its schedule.
