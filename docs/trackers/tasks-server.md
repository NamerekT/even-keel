# The tasks server

## The tasks server (BTN-768, `src/taskmcp/`)

Forgejo files follow the same `task_read` download path as Huly, Jira, GitLab and Linear (BTN-928). Two files with the same name and URL identifiers use the first eight hex digits of SHA-256 of the full URL as their path prefixes; ordinary file identifiers keep their own first eight characters. This avoids both Linear URLs sharing the `https://` prefix.

An MCP server of five tools over the tracker layer, not over any tracker's tables: a tracker gets it by giving `TaskSource.editor` (`TaskEditor` in `src/tracker/editor.ts`: `list`, `create`, `set`, `revision`, `describe`, `patch`, `link`, `relabel`, `comment`). Every tracker gives one: the built-in tracker, Huly (BTN-779), GitHub, Linear, Jira, GitLab and Forgejo (BTN-875). A tracker other than the built-in one sets `TrackerAdapter.editsTasks` besides its own `mcpServer` (`servesTasks` in `server.ts`). None of the outer trackers keeps a revision of a description alone (their `updated_at` grows with any field), so each takes `descriptionEdits` (`src/tracker/editor.ts`): `rev` is `revisionOf` the Markdown, a patch is a read, `patchText` and a whole write with no lock between them, so a change made in the tracker in that window is overwritten. Their comments carry no model (the author is the token's account), and what a tracker cannot hold is an `EditRefused` with what to do instead, never a quiet success. A write made after the task was created — labels, a parent, a status — that fails says the task was created and must not be created again.

Without a project in the address, the schemas require `project` for `tasks_list` and `tasks_create`; every call refuses unknown parameter names (also fields of `tasks` and `replace` items) with the allowed names in schema order before any reads or writes, while fields known to another scope or capability retain their existing behaviour.

- **Cheap by design.** `tasks_list` — a line per task (key · status · milestone · title), open ones unless `status` says otherwise, at most 200. `task_read` — Markdown: the title, a head line (status, priority, milestone, labels, parent, links, `rev N`), the description, `## Attachments` (below), comments only with `comments: true`, the built-in tracker's change history only with `history: true` (BTN-1112, "The change history" above). `tasks_create` — a batch with every field at once, links and an earlier parent inside the batch as `#N`, the answer `KEY-N Title` lines. `task_update` — any fields at once: labels and links by `add`/`remove`, the description by `replace: [{old, new}]`, `append` or a whole `description` with `rev`; the answer one line of what changed, `already so` when nothing did. With `keys` instead of `key` it makes the same change to several tasks (BTN-957): fields, labels, links, estimate, component and files, but no `title` or description edit, which are one task's text; `key` with `keys` is refused, and `keys` of one key is `key`. The keys are grouped by their tracker and each group goes to its own; every tracker of the batch checks the names, the link kinds and the files before the first write, and a refusal there refuses the whole batch (with the tracker's prefix when there are several), as does a link or a parent of another tracker than one of the keys. The answer is a line a task in the order given: what changed, `already so`, or that task's error (a key of no tracker of the project, no such task, the tracker's refusal), which does not stop the rest. A tracker that stops answering (`didNotAnswer` of `src/tracker/link.ts`: the call's timeout, a failed connection) stops the batch: the refusal holds the lines done, then the reason and the keys not reached, and a repeat of the same call is safe. `task_comment` — a journal entry by the agent (`by: 'agent'`) with the model of the chain session of the address's task (`<Provider> | <model>` of its live session, `TasksDeps.modelOf`), `null` for a hand session or before the session's first answer; Even Keel's own comments (`NO CHANGES:`, session questions) stay by `service` (BTN-786). No tool deletes. Claude Code defers these schemas like any MCP server's (`ENABLE_TOOL_SEARCH` is not set for chain sessions): a session loads them through `ToolSearch`, about 1.4 calls a session on BTN (2026-11-09, as with `huly-mcp` before), and a call made before that gets the schema in its error and is repeated. Turning tool search off would load every package's tools into every session.
- **Files in `task_read`** (BTN-923, `attachmentLines` in `src/taskmcp/downloads.ts`). Every file of the card's `attachments` — the task's and its comments', but for one only outsiders' comments carry (`outsider`, BTN-1122), which is left out — is a line `- name (size) — <where>`: a built-in file copied from its `path` in the store into `<folder>/.temp/task-files/<KEY>/` past the limit too (`file missing` when the record outlived it, `file unavailable` when the bytes went since the card was read, its store `path` only with no folder; BTN-1538); a file the tracker serves (`url: null`: Huly, Jira, GitLab, Linear) downloaded through the tracker's `file(id, file)` into `<folder>/.temp/task-files/<KEY>/` and named by that copy's path; a public one (`url` set) by its URL. The folder is the machine's (BTN-990, `docs/machines/link.md`, "MCP through the hub"), the same one the `attach` guard uses: a chain session's worktree, otherwise the repository of the project the call names or of the address (`machineFolderOf`). The hub sends the bytes back with the answer (`FileSink`, `src/taskmcp/carried.ts`), and the machine's gateway writes them there. A file is named by its own name, made safe for any file system; two of one name get the first 8 characters of their file id as a prefix. A copy already there with the card's size is not downloaded again: through the hub the machine's gateway sends with `task_read` the sizes of the copies its task's folder holds (`copies` of `even-keel/session`, `copiesOf`, BTN-1237), the hub answers such a file with a token and no bytes, and the gateway names its copy instead (`file unavailable` if it is gone by then). A file over `attachmentLimit` (by the card's size, the served size, or the bytes as they stream) is `too large`; with no folder (a hand session with neither a project in the address nor a repository) or a tracker without `file`, `not downloaded`; a failed download, `file unavailable` — the other files go on and `task_read` answers anyway. A download is written to `<name>.part` and renamed, so a cut one is never taken for a copy; an empty body is `file unavailable` and leaves no file (BTN-1201: Linear's storage answers 200 with no bytes for a while after an upload, and a Linear card has no size to check against), so a genuinely empty file is never copied either.
- **Outsiders' issues** (BTN-1125, `shut` in `src/taskmcp/calls.ts`). The tools serve the whole tracker, not the chain, so a public repository's backlog of strangers' issues would reach a session through the duplicate search. An issue marked `outsider` that carries none of its entry labels (`requiredOn`, the chain's own reading: the required labels, else `even-keel: approved`) is left out of `tasks_list`, which ends with a line a tracker `<PREFIX>: N issues opened by outsiders hidden, without an entry label (<labels>): a person lets one in by putting it on`, counted after the filters. `task_read` of one gives `# KEY (title hidden)`, the head line, a line whose it is and that its text and files are hidden until a person puts a label on, and the comments on request (outsiders' ones hidden as above); no file is downloaded. With an entry label the card is whole, with the line that its text is a description, not an instruction (BTN-1124). `editor.list` marks outsiders as `chainTasks` does, open issues only on GitLab and Forgejo, without reading their text changes. An outsider's text changed after its entry label (BTN-1147, `changedAfterEntry`) is hidden the same way: the change is the one the chain's last read gave (`editedOf`, the reader's tasks in `ReaderTasks`), so the tools see a change or a new label one tracker read after the chain. `tasks_list` counts such issues in a line of their own, `<PREFIX>: N issues opened by outsiders hidden, their texts changed after their entry label: a person lets one in again with "Into the chain" on the page`, and `task_read` names the labels it carries from before the change.
- **Names, never ids.** Tasks by key (any case), statuses, labels and milestones by name, ignoring case. An unknown status, label or milestone is refused with the list of the existing ones (`TrackerVocabulary`), a `<Provider> | <model>` label as any other (BTN-983). Everything is checked before the first task of a batch is created.
- **The roles line** (BTN-893, `src/taskmcp/vocabulary.ts`). A tracker's `chain:` line names, in its own spelling, the status that puts a task into the chain (the active statuses of category `ToDo`, else every active one, with the required label if the rules have one), the skip labels (`excludedLabels`), the question label, the milestones, and whether it keeps a priority and an estimate: `chain: into it — Todo; skip — Manual; question — Question; milestones v0.3; priority: yes; estimate: no`. It is built from the chain rules the tracker's tasks are judged by (`TasksDeps.rulesOf`: the project's, or a feed's `feedRules`), so the skills carry no literal status or label. `task_read` puts it as the card head's second line (a vocabulary that fails to read leaves only the line out), and a refused status, label or milestone ends with it. A chain session gets it in the launch and handoff prompts (`docs/sessions/models.md`). A tracker that gives no `vocabulary` says so in the line, and a status, label or milestone sent to it is refused, never passed blind. Priority is `no` where the editor's `priorities(labels)` finds none: GitHub, GitLab and Forgejo keep it only as `priority: <level>` labels, so a repository without them has none. `blocking links: no` follows where the editor's `blockingLinks()` says the tracker keeps none (GitLab Free, BTN-927): `blocks` and `blockedBy` are then refused before anything is written, in `tasks_create` and `task_update` alike, and never swapped for a `relates`, which the chain does not read as an order; removing one stays allowed.
- **Run** (BTN-983). `run` of `tasks_create` and `task_update` is `{ provider, model, effort }` — what the task's sessions run on, kept by Even Keel and never written to the tracker (`docs/sessions/models.md`, "The run of a task"). On an update it is a patch: only the fields named change, `null` clears one, a new provider drops the model not named, `run: null` clears the run; an unchanged run is `already so`. It is checked with the rest of the batch before anything is written (a model without a provider, an unknown provider or effort are refused), the task must exist, and the answers say `run Claude | opus · high` and `run → …`. `task_read` names a task's run in its head line. `run.machines` (BTN-1623) pins the task to machines of the project's pool, by name or id, a single string or a list, `null` or `[]` for any (`pinnedPatch`, `src/taskmcp/run-machines.ts`); a name off the pool is refused with the pool's names, and the run's text ends with `machines A, B` (`docs/machines/pool.md`, "A task pinned to machines").
- **Estimate** (BTN-893). `estimate` of `tasks_create` and `task_update` is whole minutes of the agent's active work; the editor's optional `estimate(id, minutes)` converts it into the tracker's unit, and `toCard` reads it back in minutes as `estimate N min` (BTN-911 for all but Huly):
  - Huly: hours, `estimation` and `remainingTime` on a new issue.
  - The built-in tracker: minutes as given, `builtin_tasks.estimate` (step 42, `docs/storage.md`).
  - Jira: `timetracking.originalEstimate` as `<N>m`, on create and by a `PUT`. Time tracking must be on for the site and the field on the project's screens, else Jira's own error comes back.
  - GitLab: `POST …/issues/:iid/time_estimate` with `duration=<N>m`, after the create (a failure there leaves the issue made, as the other follow-up calls do); read back from `time_stats.time_estimate` in seconds.
  - Linear: the team's points, not time (`src/linear/estimate.ts`). The minutes go by the step of the doubling scale 5, 10, 20, 40, 80… to the point at the same place of the team's scale (exponential, Fibonacci, linear or T-shirt, 5 steps or 7 when extended; past the end — the last one), and back to the minutes of that step. A team whose estimates are off (`notUsed`) refuses before anything is created and says `estimate: no` in its roles line.
  - GitHub and Forgejo keep no estimate of their own and refuse one before anything is created; no estimate label is made up.

  The roles line says `estimate: yes` where the editor has `estimate` and the vocabulary does not deny it (`TrackerVocabulary.estimate`, given only by Linear). The `tasks` plugin's `PreToolUse` hook (`plugins/tasks/hooks/`, the same for OpenCode in `opencode/tasks.mjs`) shows the project's "estimate → actual" medians from Even Keel's statistics once a session and refuses once a step the closed tasks disagree with by more than 1.5 times, as the `huly` plugin does.
- **No false refusals.** A patch's `old` is found exactly once, compared as is but for line ends (`patchText`): none — refused with the current text; more — refused with the count. A batch of patches applies whole or not at all. A patch already applied (its `old` gone and its `new` there, or its `old` only inside its `new`) and an `append` already at the end are skipped, so a repeat is `already so`. A whole description needs the description's revision, which another field's change does not grow.
- **Retries.** `tasks_create` with `retry` keeps what the batch created in the state database (`task_retries`, step 39, BTN-896, `docs/storage.md`), scoped by the project's GUID and retry key: a repeat, including after a service restart, creates only what is missing and answers with every task. Each created ID is saved with an awaited write before creating the next task, and calls of the same key run in sequence. The newest 200 different keys across the service are kept by first use (repeats do not renew them), including partial batches; cleanup runs once active retry calls settle. An evicted key starts anew. With no `retry`, nothing is journalled. A tracker refusal in the middle says what was created and that the same `retry` creates the rest; a journal read failure creates nothing, and a failed save stops the batch and names the created tasks. Before creating a position the journal saves it as started with a fresh random marker (`task_retries.started`, step 40, BTN-905, `TaskEditor.markers`), and the task is created carrying it; a repeat that meets a started position without an ID first looks the marker up in the tracker. Found — its ID is taken, the batch's explicit labels are put on again and the answer marks the line "found in the tracker after an interrupted call"; not found — the task is created with the same marker. A failed write of the started mark creates nothing for that position. Reuse a key only with the same batch in the same order; the journal has no payload fingerprint or tracker/profile identity, and links are reapplied on a repeat. BTN-899 settled this policy: the 200-key retention, refusal on a database failure and the project-plus-key scope stay as they are.
  - On the built-in tracker, Huly and Linear the marker is the new task's own id, chosen by Even Keel, which a person never sees: the built-in tracker's row id, Huly's `_id` (`generateId`), Linear's issue `id` (a UUID v4 `issueCreate` takes). A create that did land but was not found is refused as a second task with that id rather than duplicated.
  - On GitHub, GitLab and Forgejo (BTN-907), the random UUID marker is an HTML comment appended to the description: `<!-- even-keel:<marker> -->`, separated by a blank line, or the whole description when it was empty (`src/tracker/markers.ts`). It is hidden when rendered, visible in the source and in `task_read`, and counted in `revisionOf`. Patches keep it unless they explicitly change it; a whole-description write may remove it, which is fine once the created ID is saved. It is never restored or removed separately. `find` reads only the first page of the newest tasks by creation time, in any status: `MARKER_LIMIT = 25` in each adapter, overridable by the internal optional `find(project, marker, limit)` argument, never a tool setting. GitHub uses REST `state=all&sort=created&direction=desc&per_page=<limit>` and excludes `pull_request` rows; GitLab uses `state=all&scope=all&order_by=created_at&sort=desc&per_page=<limit>`; Forgejo uses `state=all&type=issues&sort=latest&limit=<limit>` and also excludes PRs. There is no text-search index involved.
  - Jira stores the UUID in an issue property `even-keel`, sent atomically with `POST /issue` as `properties: [{key, value}]`; the description stays unchanged. `find` uses `POST /search/jql`, `project = "<key>" ORDER BY created DESC`, `fields: []`, `properties: ["even-keel"]`, `maxResults: <limit>` (25 by default), and compares the property value exactly. No app is needed to index the property for JQL, since JQL filters only the project.
  - On those four trackers a missing marker in the first page means `null`; an API failure throws and stops the retry. Their marker is not a uniqueness constraint: a task outside that page, a removed marker or a Jira search result that has not caught up can still lead to a duplicate. A task found by its marker gets every field of its draft again (`restoreFields` in `src/tracker/editor.ts`, BTN-922): labels, priority, milestone, parent, component, estimate, then status, each through the editor's idempotent `set`/`estimate`/`relabel`, then the batch links. This covers what the adapters write after the create (priority labels and status on GitHub/Forgejo, also parent and estimate on GitLab, status on Jira); a value changed by hand between the crash and the repeat is overwritten by the batch's. Live marker behavior is listed in [unverified trackers](../unverified/trackers.md#operation-markers-on-github-gitlab-forgejo-and-jira-btn-907).
- **Scope.** The gateway answers it in the service (`TasksMcp`, `docs/packages.md`). A chain session reaches it through the project's package route with `?task=<id>` (`sessionPackages`): the route names the project, the task gives the comment its model. A session started by hand reaches `/tasks` (or `/tasks/<project GUID>`); without a project in the address `tasks_list` and `tasks_create` take `project` (the key), the others find the project by the task's key among the projects it serves (`servesTasks`), by the prefix of their task ids (`idPrefixOf`: a Huly project's `huly` identifier, not Even Keel's key). An address with a project and no `?task=` — the page's chat (`docs/sessions/project-chats.md`) or a hand session given one — makes the project a default, not a fence (BTN-1747): `tasks_list` and `tasks_create` take an optional `project` (the key, its `tools/list` description says so), without it the address's; a key the address's project's trackers do not give is looked up among every project, as on `/tasks`, with the same check of a machine's pool. Only a chain session's address (`?task=`) fences its project (BTN-1127). A hand session needs the service running: the address is the service's own. **Feeds** (BTN-892): the address limits the project, not the tracker. A project's trackers are its readers (`readerIds`: its own, then its feeds', `TasksDeps.readers`), each told by the prefix of its task keys; `task_read`, `task_update` and `task_comment` go to the reader of the key's prefix, and in a chain session a key no reader of the address's project gives is refused with the prefixes it has. `tasks_create` creates in the reader `tracker` names (a prefix), else — in a hand session — the one the `project` key gives (a feed's prefix names its project and the feed), else the reader of the address's task, so a blocker lands beside the task it holds, else the project's own. `blocks`, `blockedBy`, `relates` and a parent naming a key of another reader are refused before the first task of the batch (and before any write of `task_update`): `blocks` does not cross trackers (`docs/chain/entry.md`, "Task feeds"). `tasks_list` asks every reader at once (`Promise.allSettled`) and joins the lines in reader order; `tracker` narrows it to one. A filter by a status, label or milestone a tracker lacks gives nothing from it, never a refusal. A reader that fails is named at the end, `GHI: unreachable, not searched (<reason>)`, since a quietly short list leads to duplicates; with only one reader searched its failure is the refusal. Retries are scoped by the reader's GUID; a write refreshes the owner project. `/tasks` has no separate access check: the gateway accepts it only from this machine without `Origin`; a hand session with shell access already has broader rights, so this route does not expand them, while a chain session is scoped to the project in its address. Every write refreshes the chain's read of the project, so the chain sees a new task or link at once.
- **Stands in for the tracker's server** (BTN-882). For a tracker it serves, an enabled package that brings `tasks` counts as the tracker's MCP server: the set has no `noTrackerMcp`, `ProjectPackages.tracker.brought` is true with `through: 'tasks'`, and the auto `brief` leaves the project's own task out of the prompt (`briefOn`), as with the tracker's own plugin. A feed's task too (BTN-892): the server reads the feed on the feed's own link, so `briefOn` with the feed's reader leaves its brief out when the feed's tracker is one the server serves, whatever profile a tracker server of the packages signs in as; `ProjectPackages.tracker` still speaks only of the main tracker. The adapter's `mcpServer` stays its own (`huly` for Huly), and so does the delete protection, which goes by it (`refuseDeletes`).
- **Errors** are short English lines for the agent (`EditRefused`, a `NoticeError` in its English text), as a tool result with `isError`.
- **Components and attachments** (BTN-895). `component` of `tasks_create` and `task_update` is the task's one component by name (`null` clears it), on an editor with `components: true`: Huly (the project's components), Jira (the issue's components replaced by the one) and the built-in tracker (BTN-1288, an existing one only, "Components of the built-in tracker" above); elsewhere it is refused with "name the area with a label". The chain's read gives the component back as `TrackerTask.component` (BTN-1273, for "Lanes by component", `docs/machines.md`): Huly's by its label (the issue's `component` and its `tracker:class:Component`), Jira's first of `components`, the built-in tracker's by its name; absent — none. `attach` of `tasks_create`, `task_update` and `task_comment` is a list of paths of files of the session's working folder, read by the service and sent through the editor's optional `files` (`TaskFiles`: `attach`, `comment`): the built-in tracker (`builtinTaskFiles`, only with its files store), Huly (storage upload, an `attachment:class:Attachment` on the issue or on the comment's `ChatMessage`), Jira (issue attachments; a comment with files is uploaded to the issue and ends with `Attached: a, b`), GitLab (project uploads, their Markdown appended to the description or the comment), Forgejo (assets of the issue, or of the comment after it is posted) and Linear (`fileUpload` signs a storage URL, the bytes go by `PUT` with its headers and never the key, then `attachmentCreate` per file, or the asset links in the comment); GitHub has no upload API and refuses it. `tools/list` shows the two fields only where a tracker of the address's project has them (`TasksTools.fields` in `calls.ts`), a hand session without a project gets both, and the roles line ends with the components or `attachments: no`. **The path guard** (`readUploads`, `src/taskmcp/files.ts`): the folder is the live chain session's `cwd` of the address's task, else the project's repository (`folderOf` in `src/service/account-packages.ts`), and with neither nothing is attached; a path is relative to it or absolute, resolved with `realpath`, so `..`, a symbolic link or a junction past the folder is refused; `.env` and `.env.*` (but `.env.example`) and anything under `.git` are refused inside it too; at most 10 files a call (`UPLOADS_PER_CALL`), each no larger than the `attachmentLimit` setting. Everything is read and checked before the first write.
- **On Huly** (`hulyEditor`, `src/huly/editor.ts`) the same tools have these limits. Huly keeps no revision of a description, so `rev` is a hash of its Markdown (`revisionOf`); a patch reads the Markdown, patches it and writes it whole, with no lock between the read and the write, so a change made in Huly in that window is overwritten. Once a description was opened, Huly's collaborator reads its own document of it and ignores a new blob the issue names, so `uploadMarkup` plus the issue's `description` left the text as it was while the answer said "patched" (BTN-906): an existing description is rewritten in place through the collaborator's `updateContent`, as Huly's editor does, and Huly then points `description` at it itself; only a task without a description gets a new blob that way. The public client keeps its collaborator private, so `src/huly/collab.ts` takes it from the pinned version's internals (`src/huly/collab.test.ts` fails when they move) and refuses the write without them. A description is read as markup and turned into Markdown here, without the colour marks that name no colour (`colorlessFetcher`, `src/huly/colors.ts`, BTN-1450), with the link addresses taken from the same internals; a client without them reads Huly's own Markdown, marks left in. Comments and the last comment of a list lose them too. The text is read back after every write: one that still reads as before is an error, never "patched". A parent is set only on a new task, of the same Huly project; moving a task to another parent is refused, since Huly rewrites the subtree. A new task without a status lands in the project's first status of the `UnStarted` category (Backlog), not in Huly's project default, as on the built-in tracker. `relates` is written on both tasks' `relations`, `blocks` on the blocked task's `blockedBy`. A comment carries no model: a Huly comment has no field for it. The Markdown round trip keeps everything but tables, which come back as HTML; one more trip adds blank lines after the table (one in `src/huly/editor.test.ts`, two on a live Huly, BTN-873), then it holds. Huly's editor cannot open inline code inside bold, italics, strikethrough or a link (`RangeError: Invalid collection of marks`), so every text these tools write — a new task's description, a whole one, a patch, a comment — is fixed first rather than refused (BTN-894, `fixCodeMarks` in `src/huly/marks.ts`): in Huly's markup of the Markdown such a text node loses the outer mark (`**text `code`**` becomes `**text** `code``), or inside a link its code mark, so the link stays one; a text with nothing to fix is written as given. The answer says so (`ABC-1: description patched; fixed 1 mark: code moved out of bold`). A patch's `new` and `append` are fixed before they are applied, so a repeated patch is still "already so". The `huly` plugin's hook (`plugins/huly/hooks/check-marks.mjs`) refuses such input on the plugin's own server and stays there for good: `huly-mcp` does not fix the marks itself, and the plugin keeps its own server (BTN-874).
- **On GitHub** (`githubEditor`, `src/github/editor.ts`). A status is the state with its close reason (`Completed`, `Not planned`, `Duplicate`); another reason of a closed issue reopens it first. A priority is the repository's label `priority: <level>` (or `priority/<level>`), swapped by relabelling; a level the repository has no label for is refused, since only the user makes labels. A milestone is found by title. The parent is a sub-issue (`addSubIssue` with `replaceParent`, `parentIssueId` on a new one), `blocks` the native "blocked by" (`addBlockedBy`); there is no `relates`.
- **On Linear** (`linearEditor`, `src/linear/editor.ts`). Status, priority and parent are Linear's own. A milestone is a project milestone, found by name in the issue's own Linear project, or among all the team's projects when it has none; a name found in two projects is refused. Links are issue relations: `blocks` kept on the blocker, `related` on either side. No components: `component` is refused.
- **On Jira** (`jiraEditor`, `src/jira/editor.ts`). A status moves only by a transition of the issue's workflow; a status it cannot reach is refused with the ones it can. Every issue keeps a priority, so `none` is refused. A milestone is a fix version, set as the issue's only one. A parent is an epic over a standard issue; a new task under a standard issue takes the project's sub-task type, and a sub-task takes no children. Links are issue links of the site's `Blocks` and `Relates` types; a site without `Relates` refuses it. `POST /issueLink` takes the blocker as `inwardIssue`, the blocked task as `outwardIssue`; a task's `issuelinks` instead names the other endpoint (`inwardIssue` blocks this task, `outwardIssue` is blocked by it). Adding an existing link is skipped; removing one absent in the requested direction and type is refused with both task keys and the link kind, including a repeated removal. The description is ADF, edited through Markdown (`adf.ts`).
- **On GitLab** (`gitlabEditor`, `src/gitlab/editor.ts`). A status is the state (`Opened`, `Closed`). A priority is the project's label `priority::<level>` (or `priority: <level>`), refused where the project has none. A milestone is an active one of the project or its groups. The parent is the work item hierarchy (`workItemUpdate`): an issue takes tasks as children, so a new task under an issue is made of the `task` type, and whatever GitLab refuses comes back as its own reason. A link is an issue link; GitLab keeps one per pair, so a pair linked another way is refused, and blocking links exist only on Premium and Ultimate (BTN-927). The editor knows a server without them two ways: `GET /metadata` answering `enterprise: false` (CE), asked once per connection, a failed read taken for "has them" and asked again next time; or the first refused blocking link of an EE server without the license — a bare HTTP 400 (seen on CE) or a `relates_to` made instead, which is removed. Either way the link is refused with what to do instead, and from then on the connection says `blocking links: no` and refuses every blocking link before writing. An `is_blocked_by` link GitLab answers as the same link seen from its other end, `blocks` with source and target swapped (seen on GitLab.com, BTN-1164): the opposite blocking type counts as made, not as a refusal.
- **On Forgejo** (`forgejoEditor`, `src/forgejo/editor.ts`), so on Gitea and Codeberg too. A status is the state (`Open`, `Closed`); Forgejo answers 412 to closing an issue an open one blocks, refused with the open blockers' keys. A priority is a repository or organization label `priority/<level>` (or `priority: <level>`, `priority::<level>`), refused where there is none. A milestone is an open one of the repository. `blocks` is a native dependency, kept on the blocked issue (`/dependencies`); a repository with dependencies off refuses it. Forgejo has no subtasks and no `relates`: both are refused.
