# The built-in tracker: the copy and the switch

- **The copy into another tracker** (BTN-1073, part of BTN-956; `src/tracker/export.ts` over `src/builtin/export.ts`). One neutral code on the target's `TaskEditor` alone, so GitHub, Huly, Linear, Jira, GitLab and Forgejo need nothing of their own; the target is opened by `connectExportTarget` (`src/tracker/export-target.ts`) from a profile, a place and a key, as the wizard's tracker step names them. The project's switch to the new tracker is BTN-1074 (below), the page's window BTN-1075 (`docs/web/project-settings.md`), Tally BTN-1076. `ExportState` and `ExportTargetFields` live in `src/tracker/export.ts`, which the page may import; `src/builtin/export.ts` re-exports them.
  - **What is copied:** every open task of the project (status category not `Won`/`Lost`). Closed ones stay in the built-in tracker; the launch log keeps their title and address. A task copied once stays in the copy, even when it is closed before a repeat. Run labels are not written: a task's run is Even Keel's (`task_runs`).
  - **The closed tasks too** (BTN-1289): with `ExportTargetFields.closed` (the window's switch "Move the closed tasks too", off by default, kept in `tracker_exports.closed_tasks` and fixed for a started copy, as the history switch) the copy takes every task, Done, Canceled and Duplicate ones too (`takes`, `ExportSource.closed`). A closed task goes by the same stages, parents first, and gets the target's status of its category, so the target creates and closes it on the day of the copy: no tracker takes a back-dated task. Its journal starts with Even Keel's entry `Created <YYYY-MM-DD HH:MM> UTC, closed <YYYY-MM-DD HH:MM> UTC in the built-in tracker.` (`datesEntry`; the closing time is the task's last status change, else its last update), counted in the plan's journal entries. The plan counts them in every tile and status row, so its `parent` and `links` losses keep only links to other projects, and their labels and milestones enter the vocabulary losses. The old task gets "Moved to" and its `tracker_export_tasks` row like an open one, so the moved links and Tally's key map (BTN-1076) cover it.
  - **Status:** the target's status of the same `StatusCategory` — of the same name ignoring case, else the first of it (`statusFor`); In Review is `Active`. A target without the category gets the task with no status (its default), and the plan says so.
  - **The plan** (`exportPlan`) writes nothing: the tasks with their new status; `counts` of what moves (BTN-1290) — tasks, journal entries (`ExportTask.comments`), attachments, `blocks`, `relates` (a pair once) and subtasks between the copied tasks, the distinct milestones and labels the target has — each only where the target keeps it, so a kind it loses counts 0 here and stands in the losses; `statuses` — a row per status of the copied tasks, in the order of the categories, with how many have it and the target's status they get (`null` — its default); and the losses by kind — `priority` (the editor's `priorities` says no, e.g. no `priority: …` labels in a GitHub repository), `estimate`, `blocks` (`blockingLinks()` is `false` or no `blocks` in `linkTypes`), `relates`, `files`, `labels` and `milestones` the target's vocabulary (`src/tracker/vocabulary.ts`) does not have — named one by one: Even Keel never creates them, they are to be made in the tracker before the copy —, `status`, `parent` (a closed parent is not copied), `links` (to closed tasks or other built-in projects; they stay on the old tasks), `markers` (the target finds no task by a marker, so a repeat after a failure mid-create may make a second copy) and `history` (BTN-1112: tasks with a change history, which no target takes as its own events).
  - **The history summary** (BTN-1112): with `ExportTargetFields.history` (the window's switch, kept in `tracker_exports.history_summary` and fixed for a started copy) each task with a history gets one more journal entry, Even Keel's comment "Change history" with a table when (UTC), who, field, before → after (`historySummary`, `src/tracker/history-export.ts`), counted in the plan's journal entries. It is written from the token's account as every comment is: no tracker lets a personal token write as a bot, so a copy by a bot is a profile on the bot's token.
  - **The stages** (`runExport`), each task's last one kept in `tracker_export_tasks` (step 49, `docs/storage.md`): `pending` (the marker saved, the create may have happened) → `created` (parents first; a child's parent is the new key; `editor.markers.find` turns a `pending` row into its task instead of a second create, and that task gets every field of its draft again through `restoreFields`, as a `tasks_create` retry does, since the create may have stopped before its labels, priority, estimate or status, BTN-1192) → `linked` (`blocks`, `relates` between copied tasks; a repeat writes them again, a link already there is no error) → `attached` (`files.attach`, one by one) → `journaled` (each comment in order, starting "<who>, <YYYY-MM-DD HH:MM> UTC:" — `Person`, `Agent (<model>)` or `Even Keel` — because the target names the token's account as its author, `journalEntry`) → `marked` (Even Keel's `service` comment "Moved to [KEY](url)." in the old task, not written twice). `done` counts the files or comments already written of the next stage, so a repeat goes on after the last one; only the window between a post and its save can repeat one comment or file. A finished copy to the same target creates nothing, unless an open task was filed since: then only that one is copied (BTN-1074); another target is refused once a row exists (`export.otherTarget`).
  - **A failed write** stops the copy; the project stays on the built-in tracker, the log gets the English line, the state the code `export.failed`, kept in `tracker_exports.failed` (step 73) until the next run, over a restart too. A start repeats it from where it stopped. The notice says where it stopped as the import's does (below, "Where a transfer stopped"): `runExport` wraps each stage (`read`, `create`, `links`, `attach` with the file, `journal` with the comment, `mark`) and the copy's check (`check`, no task); a copy out has no link to the task (its source is the built-in tracker).
  - **The tracker's rate limit** (BTN-1190) is no failure. The adapters throw a refusal of it as `TrackerRateLimited` (`src/tracker/rate-limit.ts`) with the time it names (`untilOf`: `retry-after` in seconds or as a date, else `x-ratelimit-reset`, `ratelimit-reset` or `x-ratelimit-requests-reset`): GitHub, GitLab, Forgejo and Jira on HTTP 429 and on 403 with `retry-after`, `x-ratelimit-remaining: 0` or GitHub's text of its limits (`limitOfResponse`), GitHub's GraphQL `RATE_LIMITED` and Linear's `RATELIMITED` too; Huly has no known limit. A `CreatedThenRefused` keeps the refusal as its `cause`, so `rateLimitOf` finds it. The run (`throughLimits` in `src/builtin/export.ts`, for the start and "Repeat" alike) then waits until that time and a second, or, without one, a minute, doubled at each refusal in a row that moved nothing on, up to 30 minutes, and runs again: the stages are saved, so it goes on from the same place, a `pending` task found by its marker. Meanwhile the copy counts as running, the lock holds and `ExportState.waiting` is the time it waits until (in memory; the window says "waits until HH:MM"). The pace: an editor with `writes` (`WriteWindow[]`, `src/tracker/pace.ts`) gets each of the copy's writes held by `WritePace` so that no window gets more than its count; GitHub's `GITHUB_WRITES` are 60 a minute and 400 an hour, under the 80 and 500 of its secondary limits, so a large copy runs hours without a refusal. The other trackers have no pace and only wait out a refusal.
  - **A restart** of the service breaks a run off: at the start `BuiltinExports.resume` (called from `wireServer`) starts again each copy that is unfinished and has no `failed`, as "Continue" would; one stopped by a failure waits for "Continue" as before. A "Repeat" broken off goes on as a plain run, its check then counted again. A copy of a database before step 73 has no `failed`, so a copy stopped then goes on once at the first start.
  - **The lock** (`exporting.ts`): while a copy runs, every write of the project's tasks — the page's `builtin/*` commands (`answered` too) and the tasks server's (`builtinEditor`) — is refused with `builtin.exporting`. It holds only while the run goes on, in the service's memory: between a stopped run and its repeat edits are allowed, and an edit of a task already copied is not carried over.
  - **Routes** for the page (`routes.ts`, body `project`, `profile`, `place`, `key`, the switches `history` and `closed`): `builtin/export/plan` answers the plan; `builtin/export/start` answers the state at once and the copy runs on in the service, whatever the tab does; `builtin/export/state` (`project`) answers `target` (with the copy's switches), `running`, `startedAt`, `finishedAt`, `progress` (tasks per stage), `total` (the open tasks, every task with `closed`, and those copied and closed since: the page's "N of M"), `failed` and `waiting`.
  - **The old task's links** (BTN-1075): a card's parent, related and blocking refs and the page's task search (`builtin/search`) carry `moved` (`TaskRef.moved`: the new key and its address) for a task whose copy is through (`marked`), read from `tracker_export_tasks` by `movedTasks` (`export-store.ts`). The card shows "Moved to <key>" under such a link, the search adds it to the title.
  - **The prefix** (`checkPrefix`, `src/builtin/switch.ts`): the plan and the start refuse a target whose tasks would be named as the project's are now (`switch.samePrefix`) or as another project's or feed's (`switch.prefixTaken`), case aside, before anything is created, since the copy goes on only with the target it began with. Otherwise the old `ABC-5` and the new `ABC-5` would be one task in the launch log, the archive, the branches and Tally. On GitHub, GitLab and Forgejo the prefix is the key; on Huly it is the Huly project. The rest of the config's checks run on the moved project too.
  - **The check and the report** (BTN-1291, `checkExport`, `repairExport`, `checkMatched` in `src/tracker/transfer-check.ts`). At the end of each run and after "Repeat" the service counts both sides again, a row a kind the target keeps: tasks, comments, attachments, links (with the parent), milestones, labels, components — a loss the plan named is not counted. "Here" is what the copy was to take (copied tasks and open ones not yet copied; the journal without the "Moved to" notes), "there" is read from the target's cards (`ExportTarget.read` = the adapter's `TaskSource.card`). A task counts no more there than it was to get, and a label or milestone only when all its tasks have it, so an extra comment or label hides no missing one; each row names the source's tasks short of it. The check is kept in `tracker_exports.checked` with the plan (`plan`, saved at the start), both in `ExportState.check`; a check that cannot read the target keeps the copy finished with `export.checkFailed` and no check. `builtin/export/retry` (`project`) is "Repeat": a task the target lacks goes back to `pending` and is created again, the rest get their missing links and parent, attachments and comments from where the target's end, labels, milestone and component. At the switch the plan and the check are frozen into a `tracker_transfers` report (`TransferReports`, `src/builtin/transfer-store.ts`) while the source still lives; the event log gets `eventLog.transferMatched` or `transferMismatched` with a place on the Tracker tab and the report open. `builtin/transfers` (`project`) answers the project's reports, `builtin/transfer` (`id`) one report (`null` when gone).
- **The switch to the copy's target** (BTN-1074, `switchTracker` in `src/builtin/switch.ts`, route `builtin/export/switch` with `project`; answers `tracker`, `key` and `renamed`). The only way off the built-in tracker: `config.builtinLocked` and `config.trackerLocked` still refuse a change of the tracker in the settings. It needs a finished copy (`switch.noCopy`) with every open task at `marked`, every task when the copy takes the closed ones (`switch.notCopied` names the rest; a repeat of the copy brings them), then a check of it (`switch.noCheck`) that matched — or `anyway`, the page's "Switch without them" (`switch.mismatch`) —, and a project the chain does not work on — no running or queued chain, no task the chain holds, no released or shelved task, no open pull request (`switch.held`, each as an item): the copy gives its tasks new ids, so their branches, worktrees and records would name tasks the new tracker does not have. The window links each task id it names to the task's card (`web/src/pages/heldTasks.ts`). A switch with a live session is the question BTN-1078.
  - **What it writes:** the project's tracker, place (`trackerProject`) and key become the copy's target, through `ConfigStore.moveTracker` (`withTrackerMove`), and the project is linked to the copy's profile.
  - **What follows the tasks:** the dispatcher's saved order and skips (`Dispatcher.rename`) and the tasks' runs (`TaskRuns.rename`), by `tracker_export_tasks`: old id → new key. The history — launches, `closed_tasks`, `merge_closes`, handoffs, questions, mail — stays under the old ids; the same table links them. No worktree or branch is live then; folders of `left_folders` keep their old names and go as before.
  - **The old tasks** stay in the database with their "Moved to" note; the project reads them no more. The chain reads the new tracker in the same order: `blocks` and milestones came with the copy, the saved order with the switch (`src/e2e/builtin.test.ts`). A project without a saved order gets its computed one saved at the switch (BTN-1195): the target may keep no priority, and the copy numbers subtasks after their parents, so the same rules would order the new tasks otherwise. The saved order ranks the backlog too, by the same rules and after a hand-saved order (BTN-1199): a target without a Backlog status, such as GitHub, puts the former backlog into the chain, and unranked it would stand before the milestone as new tasks; a task the target keeps out of the chain drops out of the order at the next read.
