# The tracker layer: the contract

The neutral model and the optional capabilities an adapter offers.

## The `src/tracker/` layer (BTN-58)

- The neutral task model is `model.ts`: `TrackerTask` from the adapter, `Task` — plus the model and the question from the labels `Question` or `Вопрос`.
- The adapter contract is `source.ts`, `TaskSource`/`TrackerAdapter`; the description is in the JSDoc there, for those who write their own. The chain, the order, the rules and the page state know only these.
- The adapter is chosen by the project's `tracker` (`{ "key", "repo", "tracker" }`). Since BTN-345 it is the project's own only: the wizard, the project form and `config-import` always store it, and the shared one is gone (database step 13 and schema v13 gave each project the one it ran on). `DEFAULT_TRACKER` (`github`) meets only a project of a hand-written file of the current schema that names none. The registry is `src/tracker/adapters.ts`; the repository has Huly, GitHub, Linear, GitLab, Jira Cloud, Forgejo and the built-in tracker.
- For a tracker whose project is not named by a key, the adapter declares `projectKey` — a key in the project object (for GitHub `github`: `owner/name`); without it, or if malformed, it is a config error. With `optional` only a malformed one is an error (for Linear `linear` narrows the team to a project). With `alias` the value names the tracker's project instead of the key, which then is only Even Keel's (Huly `huly`, BTN-172). `placeOf(key, value)` gives the place in the tracker a project reads (`read`) and the prefix of its task ids (`ids`) when the ids are the tracker's own: projects with one place read it once and must split it by milestone (`docs/chain/projects.md`, "Several projects on one tracker project"); `readKeyOf`/`idPrefixOf` in `src/config.ts` fall back to the key. The values arrive in `setup` as the second argument. The optional `projectOfRemote` turns a git remote of the repository into that value (GitHub: a github.com remote's `owner/name`; GitLab: the full path on the profile's server, "GitLab Issues" below); it gets the parsed remote, the URL as git has it and the values of the profile the draft runs on, and the wizard fills the field with the first remote's answer (`repo.suggested` of `checkDraft`).
- A task ID is `<project key>-<number>`: the worktree, branch and stats go by it. What the tracker lacks, the adapter returns empty.
- The adapters know only the project key. Even Keel's own id of a project (`projects[].id`, a GUID) names it in `state/` and in the page's URLs and never reaches the tracker layer (`docs/chain/state.md`, "State files and the schema version").
- The optional `brief` and `complete` — every adapter has both; in Huly (BTN-63, `src/huly/source.ts`) the description is markdown, Done is a status of the `Won` category from the project type.
  - `brief` — the title and description are appended to the launch and handoff prompts; `trackerOf` adds the task's parents, root first, the same way for every adapter (BTN-1398, `docs/sessions/models.md`, "Prompts").
  - `complete` — Even Keel closes the task once it sees its branch merged into `main` of every remote of the checkout — landed, pushed by Even Keel itself (BTN-1581, `docs/chain/worktrees.md`, "Landing"); a checkout without a remote and PR mode go by the local `main`: `src/git/merged.ts` — the branch tip is in `main` and `main` has at least one commit made in the branch itself (by reflog: creation, `reset` and `Fast-forward` pulls of own commits do not count, so a branch that only pulled in `main` is not considered merged), `src/tracker/closer.ts`. A task reopened after such a close is closed again only by a new merge (BTN-689, `docs/chain/cleanup.md`, "Cleanup after Done"). `true` — the task was moved, already closed — `false`, nothing is written. It does not conflict with a git hook that also moves to Done: whoever is first closed it.
- The optional `children` — the direct subtasks of a task in any status; every adapter but Forgejo has it — Huly by `attachedTo`, GitHub by `subIssues`, Linear by the `parent` filter, GitLab by the work-item hierarchy, Jira by subtasks and the issues of an epic. With it and `complete`, Even Keel closes the parent (`src/tracker/parents.ts`): when tasks are refreshed, a parent that is open by the rules and has no open subtask among the known tasks is checked in the tracker — all subtasks closed and at least one in `Won` — `complete`. All cancelled — the parent is left to the user. The check runs before the chain is given the tasks — on a read and on the status poll that sees a subtask close — so a parent holding tasks with `blocks` is closed before the chain picks the next one and does not end it (BTN-1236). In Huly `parents` goes from the direct parent to the root: the direct parent is the first (BTN-1249; before it the root was taken, so a grandchild counted under the root). The subtask counts of the parents view (`parentRows`) take each open task once, even when a nested parent comes both among the parents and the tasks.
- The optional `card`, `ready` and `unready` — the task card on the page; every adapter has `card` (BTN-76), Huly, Linear, Jira and the built-in tracker also `ready` and `unready`. `card` (`TrackerCard`, `src/tracker/card.ts`) — the description and comments in markdown, labels, milestone, priority, parent, "blocked by", "blocks", "related"; the server (`GET /api/tasks/<id>`) appends `cardOf`: what each label means to Even Keel (model, question, keeps out, required) and whether it can go into the chain or back to the backlog (`ready`, `unready`). `ready` moves a task of the `UnStarted` category to the first `ToDo` status of the project type and returns the new status; `unready` (BTN-509) mirrors it, a `ToDo` or `Active` task to the first `UnStarted` status, `null` for any other. Neither is called directly by the page: `POST /api/task/ready` ("Into the chain") and `POST /api/task/unready` ("To the backlog") also put on or take off the chain's required label through `relabel`, so a tracker with no backlog status (GitHub, GitLab) gets both buttons by label alone (`docs/chain/entry.md`, "Entry into the chain"); the service immediately substitutes the new state for the task in the chain without waiting for a poll. Whether the connected adapter has `ready`, `unready` and `relabel` is carried by the state in `trackers[]`: the buttons stand on this basis right in the backlog panel and the chain. Without `card` the page answers "the tracker doesn't provide a card" and gives a link.
- The card's `subtasks` (BTN-1152, `SubtaskRef`: key, title, status, milestone label, made by `subtaskRef` from a `TrackerTask`) are the task's direct children in every status, read only for a task that has any. Huly asks the sub-issues (`attachedTo`) when the issue's `subIssues` count is above zero and resolves them as the list does (`HulyCardDocs.subIssues`); GitHub runs its `children` (`subIssues`, page by page) when `subIssuesSummary.total` is above zero; GitLab reads each child of the hierarchy the card already reads by its own issue, for its milestone, without the links and hierarchy `children` adds; Jira runs `children` (`parent = <key>`) for an epic (`hierarchyLevel` above zero) or an issue listing sub-tasks; Linear runs `children` (archived ones too) alongside the card query on every card, since the card's own `children` connection leaves the archived out; the built-in tracker gives the store's children. Forgejo has no subtasks and leaves the field out. The list is the card's one source of subtasks, the built-in card's editing included (`CardEdit` has none).
- The card's `attachments` (`file`, `name`, MIME `type`, `size`, `url`) are the files of the task and of its comments. An adapter with its own public address gives `url`; with `url: null` the server puts its own `/api/tasks/<id>/files/<file>`, served by the optional `file(id, file)` (`TaskFile`: type, size, a byte stream). The Huly adapter answers it only for a file of that task or its comments and streams it from the workspace storage (`connectStorage`, connected lazily, reconnected once on failure). The route sends `nosniff` and `private, max-age=3600`; only raster images, video, audio and PDF go `inline`, everything else is `attachment` with `content-security-policy: sandbox`. No `Range`: a video plays, but seeking ahead waits for the download.
  - GitHub (`toCard` in `src/github/model.ts`): one GraphQL query — `body`, `parent`, `blockedBy`, `blocking` (with title and state of each), the first 100 comments (`author.login`); "related" is always empty and `ready`/`unready` are absent, since GitHub has no backlog status: its backlog is the open issues without a required label, and the buttons put that label on and take it off. No attachments on the card: files of comments are links in their text.
  - Linear (`toCard`, `readyState` in `src/linear/model.ts`): `blocks` is read both ways — `relations` (this task blocks) and `inverseRelations` (blocked by) — `related` from either side, other relation types are dropped; comments by `user.name`. `ready` moves a task in a `backlog`-type state to the team's first `unstarted` state by `position`; a task in `triage` or any other state is left alone (`null`). `unready` (`backlogState`) moves an `unstarted` or `started` task to the first `backlog`-type state.
  - Huly: "blocks" — tasks that have this one in `blockedBy` (the query passes `blockedBy: { _id, _class }` as a whole object: by `blockedBy._id` and `$elemMatch` Huly finds nothing); "related" — the task's own `relations`, Huly stores the link on both sides. Comments are `chunter:class:ChatMessage` by `attachedTo`, the markup converted to markdown with `@hcengineering/text-markdown`; the author is `createdBy` (social id) → `SocialIdentity.attachedTo` → `Person.name` in the form "Surname,Name".
  - GitLab (`GitlabUploads`, `src/gitlab/uploads.ts`): upload links in the description and human notes become distinct attachments with `url: null`; relative `/uploads/<secret>/<filename>`, project URLs and `/-/project/<id>/uploads/…` of this project are supported, including an installation prefix. The Markdown links are rewritten to the service's file route. The card renders inline images and download links only for those local attachment URLs. `file` checks that the task references the file, then streams the [REST download by secret and filename](https://docs.gitlab.com/api/project_markdown_uploads/#download-an-uploaded-file-by-secret-and-filename) with the profile token and redirects disabled. GitLab can return `application/octet-stream` for media: known image, audio, video and PDF extensions supply the inline type; other files remain downloads.
- Questions in the tracker (BTN-101, `src/tracker/questions.ts`): the optional `comment(id, body)` posts a Markdown comment and returns its id, `commentsAfter(id, after)` gives the comments posted after it, oldest first (`[]` once it is gone), each with its `files` by what `file(id, file)` serves. With both, `TrackerQuestions` polls every 15 s: when the session of a chain's current task waits on an `AskUserQuestion` (not on a question in plain text), it posts the question with numbered options (`questionComment`) and remembers it in the state database (`questions`, `docs/storage.md`), so a restart does not post it twice. A session that ended its turn without an `AskUserQuestion` (a question in plain text, or just waiting) gets nothing posted and no comment read: it is answered from the page's chat or Remote Control. That is a decision (BTN-166), not a gap: reading any comment as an answer would take a note to self or another person's comment for one, and posting every end of a turn would flood the tracker. Every comment after it is taken as the user's — a waiting session does not comment, and on GitHub Even Keel's token is often the user's own; only GitHub filters by author, since anyone can comment on a public repository (EKR-19, "GitHub Issues" below). The first comment answers by numbers (`2`, `1, 3`) or text, a line per question when there are several (`trackerAnswers`); the rest go along as text and their files are downloaded into `.temp/inbox/` (a file the tracker will not give stays a link). A reply goes on only when a tick reads the same comments with the same files as the tick before (`seen`, in memory), so it waits 15–30 s: Huly writes a message and its attachments as separate documents though the user sends them with one button, and a poll between them took the answer without its file (BTN-1020); a reply still being written — a second comment, a file — waits again. The reply goes through `Dispatcher.answer` (`docs/chain/exceptions.md`, exception 6); `answer.busy`, `chain.launching`, `chain.limitSpent` and `chain.notCurrent` are retried on the next tick, any other refusal closes the question (`done`). A question the session left (answered through the page or Remote Control, a new session) is forgotten. A question stays while its session lives and waits on it even when the task is no longer current (BTN-120: the chain is led by the fix of a red `main`, the task is postponed or skipped): its comments are not read then, and once the chain takes the task again they are read from the same question comment, so a reply written meanwhile reaches the session and the question is not posted twice.
  - Huly: `chunter:class:ChatMessage` with the markup from `markdownToMarkup`; comments after by `createdOn`, files are their `attachment`s. GitHub, Linear and GitLab: a comment's files are the upload links in its body (`github.com/user-attachments/…`, `private-user-images.githubusercontent.com/…`; `uploads.linear.app/…`; GitLab's `/uploads/…`), and `file` fetches only those with the token. GitLab collects files after checking the note author's membership. A GitHub upload of a public repository came back whole through the route (2026-10-24). A fine-grained token never gets a private repository's upload (404), so when the plain link fails GitHub's `file` reads the issue's comments over REST with `Accept: application/vnd.github.html+json`, finds in `body_html` the signed `private-user-images…?jwt=` link of the same upload id (`src/github/uploads.ts`) and fetches it with no token; the signature lives minutes, so it is taken at each download, never stored. A file still unavailable is a log line naming the upload id, never the signed link (checked live 2026-10-31, [verified log](../verified/trackers.md)).
  - Replies in a comment's thread (BTN-897): an answer typed in the question's thread counts as a comment after it. Huly keeps such replies apart from the issue's comments and reads them separately ("Huly" below). Linear gives them in `issue.comments` with the rest, each with its `parent` (checked live 2026-11-09), so they are sorted in by time and the card lists them flat. GitLab's `/notes` lists every note of the issue, discussion replies included, by `created_at`, so the same holds (by the API's documentation, not checked live). GitHub, Forgejo and Jira have no threads under issue comments.
- The optional `create(task: NewTask)` (BTN-103) — a new task: project key, title, Markdown description, priority and the milestone of a given task (`milestoneOf`); it returns the new task's ID. With the project's `ci.fixTask` on, the chain files the fix of a red `main` with it (`docs/chain/main-ci.md`, "The CI of main"), and without it a red `main` pauses the chain with `ci.cannotCreate`; with `ci.fixTask` off, the default, the fix is a session without a task and `create` is not called. Every adapter has it; here Huly, GitHub and Linear, each in the first ready status of the project:
  - Huly: the number from the project's `sequence` (`$inc`), a rank after the last task (`makeRank`), the description through `uploadMarkup`, `addCollection` with `tracker.ids.NoParent`.
  - GitHub: GraphQL `createIssue`; the priority is the `priority: <level>` label only if the repository has it, the milestone is the given task's.
  - Linear: `issueCreate` in the team's first `unstarted` state, with the given task's project and project milestone.
- The optional `closingRef(id)` (BTN-295) — how a pull request names the task's issue; `null` for a task not of the tracker. The GitHub adapter gives `owner/repo#N` of the repository of the id's key, the GitLab one (BTN-414) the issue's address `<server>/<path>/-/issues/<iid>`, both with no request; the others have none. PR mode ends the body of a task's pull request on the same forge with `Closes <it>` (`closingOf`, `docs/chain/pr-mode.md`, "PR mode").
- The optional `setMilestone(id, milestoneOf)` (BTN-107) — puts a task without a milestone into the milestone of the task `milestoneOf`; `false` and no change when the task has a milestone by now or `milestoneOf` has none. The chain fills the milestone of a task that entered it without one with it (`fillMilestone`, `docs/chain/entry.md`, "Entry into the chain"). The milestone is named by a task that carries it because the neutral model has no milestone ID. Every adapter has it; here Huly, GitHub and Linear; GitHub's was verified live in a task feed (BTN-326, 2026-10-23), Linear's on 2026-10-25 (below):
  - Huly: `milestone` of the issue; a task of another project gives none.
  - GitHub: GraphQL `updateIssue` with `milestoneId`; a milestone belongs to a repository, so a task of another project gives none.
  - Linear: `issueUpdate` with `projectMilestoneId`; a milestone belongs to a project, so an issue without a project gets the project together with it, and an issue of another project is left alone. Checked live on 2026-10-25: the chain filled a Todo issue of a project narrowed to a Linear project, and the adapter, called from a script, gave an issue without a project both the project and the milestone in one `issueUpdate`.
- The optional `milestones(id)` and `moveMilestone(id, milestone)`, only as a pair (`trackerOf` drops one without the other) — the milestone pick on the task card. `milestones` gives `MilestonePick`: the tracker's id of the task's milestone (`null` — none) and the choices, each with its own id, label and target date; the card sorts them as the chain does (`compareMilestones`). `moveMilestone` puts the task into a choice's id, `null` into none. `POST /api/task/milestone` (`{task, milestone}`) calls it and then reads the project anew rather than patching the task, since the milestone changes the chain order; without the pair it is `task.cannotMoveMilestone`. Every adapter has it; here Huly, GitHub and Linear:
  - Huly: the milestones of the issue's project whose status is not Completed or Canceled, plus the issue's own when it is closed; a milestone of another project is refused.
  - GitHub: the repository's open milestones (GraphQL `milestones(states: OPEN)`), plus the issue's own when it is closed; `updateIssue` with `milestoneId`, `null` clears it.
  - Linear: every project milestone of the issue's project (Linear's have no closed state); an issue without a project has no choices. `issueUpdate` with `projectMilestoneId`, `null` clears it (checked live on 2026-10-25: another milestone, none and back).
- The optional `vocabulary(project)` (EVK-1) — `TrackerVocabulary`: the statuses with their categories (BTN-334: the rules' table places a status by its category until a list names it) and the labels a task of the project can have, whether or not a task has them now. The settings suggest them in the chain rules together with what the loaded tasks carry, so a project whose chain is empty still gets suggestions (`docs/web/project-settings.md`). `GET /api/projects/<id>/vocabulary` serves it by the project's id, 404 when the tracker is off or has no `vocabulary`; the service keeps an answer five minutes (`Vocabularies`, `src/tracker/vocabulary.ts`), a failure or a 404 is not kept. Every adapter has it; here Huly, GitHub and Linear:
  - Huly: the statuses of the project's type in its order (every status when the type is unknown) and the workspace's issue labels — `tags:class:TagElement` with `targetClass` `tracker:class:Issue` (`vocabularyOf`).
  - GitHub: its own four statuses (`GITHUB_STATUSES`) and every label of the repository (GraphQL `labels`, paged by 100).
  - Linear: the team's workflow states and the labels of the team and of the workspace (`issueLabels` with the team, or none — a workspace label has no team), paged by 50; a label group is left out, since it cannot go on an issue.
  - Checked live on 2026-10-18 on three projects with an empty chain, one per tracker: the route answered for each and the panel's rule lists offered the tracker's statuses and labels.
- The optional `milestoneTasks(project, milestone)` (BTN-142) — every task of a milestone named by its label, open and closed, each with the Markdown of its last comment (`MilestoneTask.lastComment`, the closing comment of its session as a rule); `[]` when the project has no such milestone. It feeds the changelog draft of a milestone (`src/changelog/`, `docs/sessions/chat.md`, "One-off turns"); without it the draft is `changelog.cannotList`. Every adapter has it; here Huly, GitHub and Linear:
  - Huly: the milestones of the project with that label, their issues and the newest `ChatMessage` of each (`latestMessages`), markup turned into Markdown. Checked live on 2026-10-18 on BTN `v0.1`: 178 tasks, 172 in `Won`.
  - GitHub: the milestone's number by `milestones(query:)` over open and closed ones, then an exact title match; its issues with `comments(last: 10)`, of which the newest by a trusted author (below).
  - Linear: the project milestones of the team with that name, their issues with both ends of `comments` (`newestBody` keeps the newer one). Seen live on 2026-10-25: Linear's default order is by `createdAt`, newest first, and an edit does not move a comment, so `first: 1` is the newest; a changelog draft of a Linear milestone took each task's closing comment.
- The optional `closedPage(project, open, { after, limit })` (BTN-1445) — a page of the project's closed tasks of any milestone and age, the last closed first, in one request: `{ total, tasks, next }` with an opaque cursor; `limit: 1` doubles as the count. It feeds the archive's older pages and its count (`docs/chain/entry.md`, "Entry into the chain"); without it the archive holds only what `chainTasks` reads. `trackerOf` turns `open` from the reader's chain rules (`isTerminal`). A page's tasks carry no labels and no `blockedBy`: an archive row shows neither.
  - The built-in tracker: one query (`readClosed`, `src/builtin/task-rows.ts`) with the count, ordered by the last change of the status in `builtin_history` (the task's `updated_at` when it never changed); the cursor is the offset.
  - Huly: no closing time and no offset, so the issues of the closed statuses go by `modifiedOn`, newest first, the cursor is the last row's `modifiedOn` (`$lt` it on the next page) and `total` comes from the find's `total`, so a later page counts only what is past its cursor. Issues changed in the same millisecond across a page's edge would be skipped (`docs/unverified/trackers.md`).
  - GitHub: GraphQL `issues(states: CLOSED, orderBy: UPDATED_AT DESC)` with `totalCount` and `endCursor`, up to 100 per page; GitHub has no order by closing time either.
  - Linear has none: its GraphQL gives no count of a filtered query. Jira, GitLab and Forgejo have none yet.
- The optional `logTime(id, entry: TimeEntry)` with the adapter's `logsTime` (EKR-35) — the agent's active time on a done task written into the tracker's time tracking; Tally calls it once per task (`docs/tally.md`, "Task time"), through the profile of the task's project as `timeTrackers` gives it. `entryMinutes` makes whole minutes, at least one. `false` — the tracker refuses time in the project and the task needs no report; any other failure throws. Huly's report is Tally's own `TimeSpendReport`, not this operation; GitHub and Linear have no time tracking.
  - GitLab: `POST /projects/:path/issues/:iid/add_spent_time` with `duration` `<n>m` and the `summary` label; a 403 (below Reporter, or the project's time tracking off) is `false`.
  - Jira: `POST /issue/<key>/worklog?notifyUsers=false` with `timeSpentSeconds`, `started` — the last turn minus the time, as `…T10:13:00.000+0000` — and the label as an ADF `comment`; a 403, or a 400 whose `errors` name no field of the request (`JiraHttpError.fields`), is `false` — no "Work on issues" or tracking off; Jira words it in the account's language, so the text is never matched (EKR-91). A 400 naming a field is our request's fault and throws.
- The `brief` key (global and per project — `{ "key", "repo", "brief" }`, applied on the fly) decides whether the description goes into the prompt. Unset or `null` (BTN-225) it is auto, `briefOn` in `src/service/account-packages.ts`: on exactly when no enabled package of the project brings the adapter's MCP server (`mcpServer`, for Huly `huly`) or, for a tracker the tasks server serves, `tasks` (BTN-882, "The tasks server" below), so a project with the tracker's plugin gets only the task id and one without it gets the task, with nothing to switch. `true` or `false` overrides it; with `false` the packages must bring the server: without it the set has the problem `noTrackerMcp`, the chain pauses with the reason and goes on by itself once it is gone (`chain.noTrackerMcp`, `docs/chain/pr-mode.md`). An adapter without `mcpServer` has the brief on under auto. A prompt without the brief (off, or none read) says in its place to read the task first (BTN-1202, `withUnbriefed` in `src/chain/relay.ts`): through `task_read(<key>, comments: true)` when a package brings `tasks`, otherwise through the tracker's tools — a weak agent may never open the skill that says it.
