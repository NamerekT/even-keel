# Linear, GitLab, Jira and Forgejo

How these four adapters fill the contract of [`layer.md`](layer.md). Their tasks server editors are in [`tasks-server.md`](tasks-server.md#each-trackers-editor), their imports — Linear's only, the others have none — in [`import.md`](import.md).

## Linear (BTN-72, `src/linear/`)

- **API.** GraphQL `api.linear.app` with the profile's personal key `LINEAR_TOKEN`, in `Authorization` without `Bearer`. An answer is read through `graphqlBody` (`src/linear/answer.ts`, BTN-1467): a 2xx body that broke off mid-read is "linear: the answer broke off: …" with the network's reason, one that is no JSON "the answer is no JSON: …"; "empty answer" is only a readable answer with neither `data` nor `errors`. Under another status an unreadable body leaves the HTTP status to name the failure.
- **API traps.** Query complexity is up to 10000, and a list without `first` counts as 50, so nested lists get an explicit `first`. `issue(id)` on a nonexistent task fails the whole response, so tasks by ID are read with the filter `number: { in }` by the team key. Linear merges fields of one object inside `or` through "or": an explicit `and` is needed.
- **IDs and places.** The task ID is the Linear identifier as is (`NAM-12`): the branch, the commit and the session's MCP name the task the same way. Without the optional `linear` the project key is the team key. `linear` narrows the team to a Linear project (its name, case-insensitive): `NAM/Web app`, or `NAM/` for the whole team (`linearPlace` in `src/linear/model.ts`, BTN-73). Then the key is only Even Keel's, so several Even Keel projects work on one team, one per Linear project; the task IDs stay the team's. Two projects with the same `linear` place share a read and split it by milestone. A whole-team project (`NAM/` or the key `NAM`) next to a project of one of its Linear projects reads that project's tasks too, and the config does not catch the overlap: give them milestone rules that split them, or narrow both.
- **Statuses** go by the workflow state's type: `triage` and `backlog` — `UnStarted`, `unstarted` — `ToDo`, `started` — `Active`, `completed` — `Won`, `canceled` and `duplicate` — `Lost`, an unfamiliar type — `UnStarted`; the name is the state's. Linear has its own backlog, so entry into the chain is as in Huly.
- **Fields.** Blockers are the inverse `blocks` relations, the parent and subtasks are native, priority is native (1 Urgent … 4 Low, 0 — none). The chain list's estimate is 0: Linear keeps points, which the tasks server maps ([`tasks-server.md`](tasks-server.md#estimate-btn-893)).
- **Milestones** are project milestones (`projectMilestone`), not cycles: Linear carries unfinished work over to the next cycle by itself, so an order by cycles would not hold. Milestones carry `sortOrder` and their project's id (`projectMilestone` on task and card reads, `projectMilestones` in the picker); `TaskMilestone.trackerOrder` scopes that position to `linear:<project id>`.
- **`complete`** is the first state of type `completed` by `position` in the task's team; a closed task (`completed`, `canceled`, `duplicate`) — `false`. A team's own auto-close of parents does not conflict with Even Keel's: whoever is first closes it.
- **`children`** (BTN-606) reads the issues with the filter `parent` (team key and number) page by page, with `includeArchived: true`: Linear archives closed issues after a while, and a parent still counts them.
- **Attachments** (BTN-928). The card includes the issue's `attachments` (`title`, `url`), read page by page, and private upload links from its description and first 100 comments; a URL appears once, the attachment's title over the link text. `uploads.linear.app` files have `url: null` and download through `file` with the profile key, a timeout and redirects off, as [Linear documents](https://linear.app/developers/file-storage-authentication); other URLs stay links. Linear gives no size or MIME type here: the card has 0 and an empty type, the download's headers and stream enforce the size limit, and a later `task_read` downloads the file again.
- **Links.** `linear.app/<urlKey>/issue/{id}`; the adapter learns the organization's `urlKey` on connecting, and there are no links before that.
- Checked live on a team narrowed to a test project: two tasks of a milestone with a "blocks" link went through the chain blocker first, despite the other's higher priority, and after the merge `complete` moved both to Done ([verified](../verified/trackers.md)).

## GitLab Issues (BTN-410, `src/gitlab/`)

- **API.** REST v4 on `GITLAB_URL` (default `https://gitlab.com`) with `GITLAB_TOKEN`, a PAT with the `api` scope. Addresses are web roots, an installation prefix included, without `/api/v4`. The profile uses `/user` and `/personal_access_tokens/self`: a server without expiry support (404) leaves `expiresAt` null, but a known token without `api` is refused. Every REST page is read through `x-next-page`, with a full-page fallback when that header is absent.
- **Projects.** A project names its full path (`gitlab: group/subgroup/name`); task ids are `<Even Keel key>-<iid>`. The wizard suggests the path from a remote on the profile's own server (`projectOfRemote`, BTN-607): the remote's host must be that of `GITLAB_URL` (`gitlab.com` without one), an HTTP remote must sit under its installation prefix, which is stripped, and nested groups are kept (`gitlabRepo`, as CI reads it); a remote of another server suggests nothing. REST path segments are URL-encoded; ids and links keep subgroups.
- **Fields.** Opened is `ToDo`, closed is `Won`. Priority comes from `priority::<level>` or `priority: <level>`; `create` puts the project's label of that level on when there is one. The estimate is `time_stats.time_estimate` in hours (0 — none). `vocabulary` gives the two states, the project's labels and its milestones.
- **Reading relations.** Task lists and status polls read the hierarchy and the linked items through GraphQL, up to 20 issues a batch (`batch.ts`); what overflows a batch's page is read issue by issue, the links through REST. An older GitLab without those GraphQL fields falls back step by step to REST. REST reads run at most six at once, batches and projects in order, with no relation cache across polls. Closed issues kept only for milestone progress are read without relations, and status polls skip relations of closed issues outside active milestones. Authentication and runtime failures propagate rather than appear as empty relations.
- **Links.** Native links give `is_blocked_by`, `blocks` and `relates_to`; only the first orders this task. GitLab Free has only related links, and no text dependencies are parsed. The card keeps all three kinds. The work-item hierarchy (parent, children) is read on Free too; an absent widget or an older schema leaves it empty.
- **Milestones** include inherited group milestones, with the issue's own closed one among the choices; they are assigned, copied and cleared, and `milestoneTasks` reads a named one's tasks for a changelog draft. Closed tasks of active milestones count in their progress.
- **Notes.** The card shows every human note, in time order; system notes are left out.
- **Members** (the outsider rule, [`github.md`](github.md#outsiders-on-public-repositories)): answers and last comments take only notes by the token's owner or a current member from `/members/all/:user_id` with `access_level >= 20` (Reporter), inherited membership included. A 403/404 lookup excludes the author, and a skipped note is logged once. The card marks an excluded author's note `outsider`, and an upload only such notes link to, for `task_read` to hide; a card asks after each note's author once. An open issue's author goes by the same rule for the entry gate (`authorTrust`, `markOutsiders` in `chainTasks`, and the card); the 5 s `tasks(ids)` poll reads statuses only and marks nothing. Members' answers carry their files to the session through the authenticated file route.
- **Checked live** on GitLab.com and a self-managed CE 19.5, at the root and under a path prefix ([verified](../verified/trackers.md)); the hierarchy of older versions was not checked, so the guide recommends 19.5 or later. GitLab CI and merge requests use the same profile (`docs/ci.md`, `docs/chain/pr-mode.md`).

## Jira Cloud (BTN-417, `src/jira/`)

- **API.** REST v3 with Basic `JIRA_EMAIL:JIRA_TOKEN`. `JIRA_URL` is the site's origin only (`https://<site>.atlassian.net`, https, no path: `siteUrl`, else `jira.url`); a profile with only some of the three is `jira.incomplete`. `JiraApi.open` signs in through `/rest/api/3/myself` on the site. When the site refuses (a token with scopes works only through the gateway), it reads the cloud id from `<site>/_edge/tenant_info` and tries `https://api.atlassian.com/ex/jira/<cloudId>`; every later call goes to the base that answered. Jira Data Center is out of scope. Jira has no CI: the remote's CI and PR mode apply as for any tracker.
- **Keys.** The Even Keel key is the Jira project key and the task id the issue key as it is: no `projectKey`, no `closingRef`, no `isPublic`. Comments are not filtered by author, as in Huly and Linear.
- **Statuses** go by category: `new` — `ToDo`, `indeterminate` — `Active`, `done` — `Won`, an unfamiliar one — `UnStarted`.
  - Jira has no status kind for the backlog: a Jira Software backlog is a board's view, and the API cannot tell its issues from ready ones. So a `new`-category status whose `untranslatedName ?? name` is `Backlog` (`sameName`) is `UnStarted` and stays out of the default rules; a board whose backlog is no such status keeps unready issues out by `requiredLabels` or its own `active` list.
  - Issue responses, `search/jql` included, omit `untranslatedName`: `resolveStatuses` fills it by status id from `/project/<key>/statuses` for task reads, cards (links to other projects included) and `ready`. Each call fetches that catalog once per project; `chainTasks` reuses the one it already read. The localized `name` is kept for display and explicit status rules.
  - `ready` moves an `UnStarted` issue through its first transition to a ready `new`-category status. `unready` moves a `ToDo` or `Active` one through its first transition to an `UnStarted` status and, where the workflow has none, leaves it alone (`null`): "To the backlog" then only takes the required label off.
- **Reads.** `chainTasks` reads the project's statuses (every issue type), turns the open ones into ids and searches `status in (…)` through `POST /search/jql` with `nextPageToken`, plus the closed issues of the open ones' fix versions for milestone progress. Tasks by id go through `POST /issue/bulkfetch` by 100; an id Jira does not have lands in `issueErrors` and is left out.
- **`complete`** takes the first transition to a status of the `done` category; with none from the current status it logs which status had none and returns `false`, the task left open.
- **Links.** Blockers are the issue links of the type named `Blocks` (`inwardIssue` — this issue is blocked by it, `outwardIssue` — it blocks), found by name at connect: without such a type `connectJira` throws `jira.blocksType` with the types the site has, so a renamed type stops the profile's projects instead of running them out of order. "Related" on the card is `Relates` either way; other types are dropped. The parent is the `parent` field; children are subtasks and, for an issue above the base level (`issuetype.hierarchyLevel > 0`, an epic), the issues with `parent in (…)`, counted by a JQL search of 50 keys at a time.
- **Priority.** The built-in Highest, High, Medium, Low, Lowest by name (urgent, high, medium, low, low); a site's own scheme by its place in `/priority/search`, spread over urgent…low; `create` picks the built-in name for the level, else the place. The estimate is `timetracking.originalEstimateSeconds` in hours (0 — none, or time tracking off).
- **Milestones** are fix versions: a task's milestone is the first of its `fixVersions` in the chain's milestone order (`earliestVersion`). Jira gives no tracker position (BTN-1021): the version catalog's `sequence` is in effect the creation order, the Releases page sorts by release date and has no drag, and a Kanban board shows no Versions panel. So versions go by release date, number and name, like those of a tracker without an order of its own, which matches the Releases page; a project that needs another order sets its own in Even Keel. `milestones` offers unreleased, unarchived versions of `/project/<key>/versions` plus the issue's own; `moveMilestone` replaces all fix versions with the one picked (`null` — none); `setMilestone` copies the first version of a task of the same project. Sprints are not milestones.
- **ADF.** Descriptions and comments are ADF: `adfToMarkdown` and `markdownToAdf` (`src/jira/adf.ts`) cover headings, lists (nested, ordered with a start, task lists), code, quotes and panels, tables, rules, hard breaks, mentions, emoji, cards, status lozenges, dates and media. Text nodes escape Markdown and HTML punctuation before their marks are applied, so literal tags, emphasis and line-leading block markers stay text on the card; code keeps its content, and the reverse converter reads backslash escapes, delimiters inside marks and link labels included. Briefs use the same Markdown.
- **Files.** A media node names its file by `alt`, matched to the issue's attachment by file name (`mediaLinks`). The card's attachments are the issue's, with `url: null`; `file` serves only one of them, from `/attachment/content/<id>?redirect=false`. `commentsAfter` gives a comment's files by the same match.
- **`create`** takes the project's `Task` type by `untranslatedName ?? name`, else the first standard type of `/issue/createmeta/<key>/issuetypes` (`hierarchyLevel === 0`, not a subtask), then readies the issue; with no standard type it fails before creating anything. `vocabulary` gives the project's statuses, every label of the site (`/label`, paged) and the names of the open versions; `milestoneTasks` reads a version's issues with their newest comment (`orderBy=-created`).
- **The MCP token.** The profile's optional `JIRA_MCP_TOKEN` is only for the `jira@even-keel` plugin ([`profiles.md`](profiles.md#jira-mcp-oauth-and-the-mcp-token), [`plugins.md`](plugins.md#jira-btn-417)); REST never uses it.
- **Links and checks.** The page links `<site>/browse/{id}` and `<site>/browse/<key>`. Fixtures cover the ADF conversion, the model, the profile, the gateway fallback and every source operation (`src/jira/*.test.ts`). Localized statuses, task reads and creation were checked live (BTN-473, [verified](../verified/trackers.md)).

## Forgejo Issues (BTN-476, `src/forgejo/`)

- **API.** The Gitea REST API (`/api/v1`, `ForgejoApi` in `api.ts`) on `FORGEJO_URL`, a web root with an optional installation prefix, and `FORGEJO_TOKEN` in `Authorization: token …`; Forgejo, Gitea and Codeberg answer alike. Lists are read page by page by `x-total-count`.
- **The token's scopes.** One profile serves the tracker, the CI (`docs/ci.md`) and PR mode (`docs/chain/pr-mode.md`), so the token needs `write:issue` beside `read:repository` and `read:user`. A 403 whose body says `required scope(s): [...]` is `ForgejoScopeError`, a `NoticeError` with `forgejo.scope` naming the missing scopes (BTN-788): the token is alive, so it is no `CredentialsRefused`. `TrackerLink` keeps an error's notice in `TrackerHealth.notice`, and `/status` and the project page say it instead of the guess `trackerProblem` makes from the text.
- **Projects.** The wizard lists the account's repositories with issues on (`forgejoProjects`, `/user/repos`, at most ten pages of 50) and suggests the key from a remote on the profile's host (`projectOfRemote`, as GitLab's). A project names `forgejo: owner/name`; a task id is `<Even Keel key>-<index>`, an issue of a repository without a project `owner/name#index` (`RepoMap`, as GitHub's). A pull request is never a task.
- **Statuses.** An open issue is `Open` (`ToDo`), a closed one `Closed` (`Won`), never `Lost`: Forgejo keeps no reason for closing. There is no backlog status: keep entry on a label (`requiredLabels`), as on GitHub. `complete` closes the issue.
- **Dependencies.** Blockers are the native dependencies (`/issues/{n}/dependencies` for "blocked by", `/blocks` for the card's other side); no text is parsed. A repository may turn dependencies off: then `/dependencies` answers 404, taken for none (`dependenciesOf`), and the chain goes by milestone and priority alone. `/blocks` still answers 200 with the links stored before (seen live), so after that 404 the card skips `/blocks` and shows both sides empty (BTN-789); each card read checks `/dependencies` again. Closed issues are read without their blockers: a closed task orders nothing. Forgejo has no subtasks.
- **Fields.** Priority comes from a label `priority: <level>`, `priority/<level>` or the scoped `priority::<level>`, the highest wins; `create` puts on the repository's label of that level when there is one. The estimate is 0. Milestones are native: the open ones and the issue's own to pick from, `0` clears, `setMilestone` copies one only within a repository, `milestoneTasks` finds it by title. `vocabulary` gives the two states, the labels of the repository and its organization, and the open milestones.
- **Members** (the outsider rule, [`github.md`](github.md#outsiders-on-public-repositories)): the API has no author association, so only comments of the token's account, the repository's owner by name and its collaborators reach a session (`src/forgejo/trust.ts`): `/collaborators/{user}` (204 or 404), then, for an organization's member who is no collaborator, `/collaborators/{user}/permission` with `write`, `admin` or `owner`. Forgejo tells that only to an admin of the repository; a refusal counts as an outsider. Each author is asked once per read and once per card. A skipped comment is a log line, once per comment (`Skipped`); the card marks it `outsider`. An open issue's author goes by the same rule for the entry gate. `isPublic` is "not private": an internal repository is open to every account of the server.
- **Files** (BTN-928). The card includes the `assets` of the issue and its comments (UUID, name, byte size), once per UUID, each with `url: null`. `file` rereads the task's assets, refuses a UUID outside them and streams `<web>/attachments/<uuid>` with the profile key, a timeout and redirects off, the installation prefix kept. The served size comes from the asset; known media extensions give the type when the server answers none or `application/octet-stream`. The metadata is the [API asset schema](https://raw.githubusercontent.com/go-gitea/gitea/main/modules/structs/attachment.go), the bytes the web attachment route. Markdown stays as it is. `commentsAfter` carries no files (`files: []`), and there is no `closingRef`, so PR mode's pull request does not close the issue by itself — Even Keel's `complete` does.
- **Links and checks.** The page links `<web>/<owner>/<name>/issues/<index>` and `<web>/<owner>/<name>/issues`. Fixtures cover the model, the profile's errors, the gateway's keys and every source operation (`src/forgejo/*.test.ts`); run live on Forgejo, Codeberg and Gitea, an organization member's answer included ([verified](../verified/trackers.md)).
