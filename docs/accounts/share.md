# Transferring the shared configuration (`src/account/share.ts`)

- **Guarding account settings (BTN-902, `src/account/settingsGuard.ts`, `settingsHook.ts`).** The transfer appends a `PreToolUse` command for `Edit|Write|MultiEdit` after the account's own settings layer. The command invokes this installation's absolute `dist/src/account/settingsHook.js` with the Node executable and separate arguments, without a shell or a plugin. Its `--even-keel-account-settings` marker lets the next transfer replace only its own commands, including one mixed into a user's group. User hooks stay; the guard is stripped before comparing or sharing settings through `AccountSettings`, so installing, updating or removing it is no user edit. Empty hook lists compare as absent. Only managed Claude folders get it, never the global folder or another provider's folder. A missing global settings file still allows installation while keeping the account's values; a broken existing account JSON is left intact.
  The script exits silently for other files, with no service request. For a candidate account `settings.json`, including relative paths from the event's `cwd` and `MultiEdit` targets, it compares paths through `src/paths.ts` and asks the local service's `/api/state` whether the folder's key is a listed, non-global Claude account. A denial tells the agent to edit shared settings in `~/.claude/settings.json` and use Accounts to resolve account-only changes. No answer within 1.5 s, a failed response or malformed input allows the edit; it emits no `allow` decision that could bypass normal permissions. The command has `onFailure: continue` so a missing installation or script does not hold edits. `even-keel uninstall` and both service uninstall scripts strip only marked commands from Claude account settings; removing an account removes its file with the folder. CLI configuration commands such as `/model`, shell writes and disabled hooks are outside this hook's coverage; the settings-edit band still handles those. Real CLI delivery and uninstall on each OS await [the live check](../unverified/accounts.md#account-settings-edit-hook-btn-902).
- Before every launch in an account folder, the following is transferred into it: `settings.json` (the global one on top of its own), `CLAUDE.md`, the plugin registry, a junction (a symlink outside Windows) to `agents`, `commands`, `hooks`, `output-styles` and skills. All stores of these folders and of skills live inside `~/.claude-config` (`configStore`), the working copy of the global configuration's repository that syncs between the hub and its machines (BTN-1690, `docs/sessions/memory.md`, "The global configuration"). Each of the four folders lives in its own store there, `~/.claude-config/<name>` (`linkedStore`), the way skills do (below): a real `~/.claude/<name>` is moved there and a link is left in its place, so the hook commands in `settings.json` that name `~/.claude/hooks/…` keep working; a missing one is linked back to the store; the account folder's `<name>` links to the store, an old link of its into `~/.claude/<name>` is re-pointed; a `~/.claude/<name>` that links elsewhere stays and the account links to it. Shared skills live in a store, `~/.claude-config/skills/<name>` (`skillStore`): a skill kept in `~/.claude/skills` as a real folder is moved there whole and leaves a link in its place, and the account folder's `skills/<name>` links to the store; an old account link to `~/.claude/skills/<name>` is re-pointed. A store folder that already holds the skill is merged into as memory is (below); a folder the move cannot rename (a file in it is open) stays with a warning in the log until the next launch, and the account links to it as before. The stores of before BTN-1690, `~/.claude-<name>` and `~/.claude-skills`, are moved into `~/.claude-config` (`settleStores`, at every transfer and at the start of the configuration's working copy): an old store is renamed to its new place, or merged into it file by file when that place already exists (a differing file stays behind with a warning, and the old folder with it), then the old place becomes a link to the new one, so a hook command or a link of somebody else's that names it keeps working; the links of `~/.claude` and of the account folders into an old place are re-pointed straight at the new one. The CLI's own `synced` and `.trash` stay, a global skill that links elsewhere (a repository's skill folder) stays and the account links to it, and an account skill that links to a live folder of its own choosing is not touched; an account link left dead by a deleted skill (into the store, an old store or `~/.claude/skills`) is removed (BTN-1736, `docs/packages/files.md`, "The user's own skills"). Project memory lives in a store next to the global folder, `~/.claude-memory/<project>` (`memoryStore`, `sharedMemory`): both `~/.claude/projects/<project>/memory` and the account folder's `projects/<project>/memory` are links to it. Memory begun in either of them (a real folder, not a link) is first moved into the store, the global folder's first: files the store lacks are moved, identical ones dropped, and a file with the same name but different content stays where it is with a warning in the log (merging those, `MEMORY.md` included, is for a human). The folder becomes a link once nothing of its own is left; a link pointing elsewhere (the old target in `~/.claude`, a dangling one) is re-pointed. The walk covers the projects of the account folder as well as the shared ones.
- Why the stores are outside `~/.claude`: the CLI asks before every write whose real path lies in a `.claude` folder that is not the session's own, so a link from an account folder into `~/.claude` made it ask even with `--permission-mode auto` (a chain session stood 9 minutes on such a question, 2026-10-10). With the store outside, writes through both links pass without a question (verified on CLI 2.1.296 and 2.1.310 with a Haiku session), including sessions started by hand. Chain sessions also get the store folder as `autoMemoryDirectory` in `--settings` (`chainSettings`), whatever the "Trim the tools" switch and whatever the project's set: a Claude Code chain session keeps the CLI's file memory and gets no `memory` server (BTN-1647). Agents without that file memory (Codex and others) get the memory through Even Keel's `memory` server, which works on the files of the hub's store folder, a working copy of the project's memory repository (BTN-1029, BTN-1646, `docs/sessions/memory.md`). Skills had the same question (an edit of a shared `SKILL.md` from an account folder, 2026-10-20) and got their own store for it (BTN-256). Checked live on CLI 2.1.310 (BTN-294, a probe skill, Haiku, `--permission-mode auto`): the transfer moved a new skill from `~/.claude/skills` into the store and linked it from both account folders; a `SKILL.md` and a memory file are written without a question from an account folder and from `~/.claude`; sessions in `~/.claude` load skills through its links. `agents` and `hooks` (and so `commands`, `output-styles`) then linked straight into `~/.claude`: from an account folder an edit through them was refused in `auto` ("resolves through a symlink to `~/.claude/hooks/…`, which is outside the allowed working directories"), from `~/.claude` it passed; they got their stores for it (BTN-373). Checked live on CLI 2.1.310 the same way: the transfer moved the real `~/.claude/hooks` and `~/.claude/agents` into `~/.claude-hooks` and `~/.claude-agents` and linked both account folders to them; a hook file and an agent file are written without a question from an account folder and from `~/.claude`; both folders' sessions list the probe agent; the hook commands of `settings.json` that name `~/.claude/hooks/…` run through the link. `commands` and `output-styles` did not exist on that machine and were not seen; they take the same path.
- **A change made right in an account folder's `settings.json` (BTN-901, `src/account/settingsLayer.ts`).** The merge is shallow: a top-level key of the global file replaces the folder's key whole, so `/model`, `/config`, `permissions` or `skillOverrides` written in an account folder (from a terminal, VS Code or a session) used to be lost at the next launch. Now `AccountSettings` keeps per Claude folder, in the state database (`account_settings`), what the last transfer wrote there (`written`) and the account's own layer (`own`). Both the Accounts page and the transfer use `planSettings`: a top-level key is an edit when its value in the folder differs from both `written` and the value the transfer would apply; the transfer leaves the folder's value in place and keeps the old one in `written`, so the edit stays one until resolved. Folder-only keys such as `agentPushNotifEnabled` and `inputNeededNotifEnabled` (written by Remote Control) therefore survive a transfer without a band (EKR-150). `AccountEntry.settingsEdits` gives the page each key with its value from `written` and in the folder as JSON (`SettingsEdit`, `settingsEdit`; cut at 2,000 characters, absent where the key is not there), except `env`, whose values may be secrets: it names only the variables added, removed and changed. Next to the problem band (`AccountSettingsEdits`, `web/src/layout/accountSettings.tsx`, `accountSettings.css`), in the drawer and on `/accounts`, stands one yellow band per account (BTN-1395): its head names the account and how many keys changed, with "All shared", "All for this account only" and "Discard all" when there are two or more, and under it a row per key — the key, "Was" and "Now" (a long value cut, the whole of it in a tip; `env` its variables as tags) and the key's own three buttons. The rows are four columns under a head on a wide band; a band narrower than 900 px (a container query: the drawer, a phone) puts the key and its buttons over the two captioned values, and under 520 px the buttons under them. A chosen row leaves at once and comes back if the command fails; the band goes with its last row. Each button is `account/settings-edit` with `choice` and `key`, or `keys` for the head's: every key is checked before the first is resolved (one that is no edit any more refuses them all), then the folder is transferred once.
  - "Make shared" writes the folder's value into `~/.claude/settings.json` (an `env` without the folder's API key and cloud variables), removes that key from the account's own layer (EKR-151) and transfers it to the folder at once; other accounts get it at their next launch;
  - "This account only" puts it into the account's layer, laid over the global settings at every transfer (`null` there removes the key; an `env` there is kept without the API key and cloud variables, the folder's own are put back);
  - "Discard" transfers as before and the change is lost.
  The choice runs the transfer at once with the daemon rule above (`DaemonRefresh.prepare`). The layer's keys are listed on the `/accounts` row as "Own settings" (`AccountEntry.ownSettings`, `OwnSettings`); × (`account/own-setting`) drops one and transfers again. Keys the CLI writes with no one asking are no edit: `autoUpdatesChannel`, `minimumVersion` (`claude install`, the update channel; read in the CLI 2.1.319 binary), and `apiKeyHelper` stays the folder's own. The CLI's startup migrations also rewrite `model` and `env` (model renames, `DISABLE_AUTOUPDATER`, model pins); those keys stay watched because a person writes them too ([unverified](../unverified/accounts.md#settings-edits-in-account-folders-btn-901)). The first transfer after the upgrade has no record and sees no edits; removing an account drops its record. The edits are cached by the settings layer revision and the time and size of both the folder and global settings files, so the band shows a change before the next launch.
- From `~/.claude.json` — trust and project settings (MCP local scope, `allowedTools`) for projects that are already trusted. The CLI creates several keys for one folder: VS Code writes the drive letter in lowercase — `d:/…`, the CLI — `D:/…` and `D:\…`; a folder counts as trusted if any spelling is trusted, and all its keys are transferred. Path case is ignored only on Windows and macOS, as everywhere Even Keel compares paths — `src/paths.ts`.
- The first-run completion mark (`hasCompletedOnboarding`, `lastOnboardingVersion`), if the folder lacks it: without it an interactive `claude` with the folder's `CLAUDE_CONFIG_DIR` shows the sign-in wizard even though the token is in place.
- The folder's temporary daemon (`claude --bg` starts it itself) keeps its own environment: the environment of the `claude --bg` that started it plus the `settings.json` `env` as it was then. Every session it spawns, a new one or a resumed one, inherits that environment and puts the `settings.json` `env` read at its own start on top (CLI 2.1.302, BTN-129, a probe variable in a sandbox account folder):
  - a new or changed `env` key reaches the next session at once, with the daemon running — through the transfer, at the next launch in the folder; a session already running keeps the value it started with;
  - a removed key stays in every session of that daemon with the value the daemon started with, until the daemon restarts;
  - the environment of a later `claude --bg` does not reach its session at all while the daemon runs, so Even Keel passes nothing per session that way;
  - so a variable `sessionBase` stopped passing (BTN-1115: Even Keel's own secrets and everything of its `.env`, `docs/packages/files.md`, "Keys") still reaches the sessions of a daemon started before, until it restarts: after such an update stop the folder's daemon once there are no live sessions (`claude daemon stop --any` with its `CLAUDE_CONFIG_DIR`), or restart the machine. In a chain session the names of `sessionSecrets` are blanked at once anyway, since the chain's `--settings` outranks the daemon's environment; what lingers is the rest of `.env`.

  The daemon does not take the launch's folder, though: `claude --bg` spawns `claude daemon run --origin transient --spawned-by {…"cwd":"<launch folder>"…}`, and the folder is only a label there. On Windows the spawn goes through WMI `Win32_Process.Create` with `CurrentDirectory = $env:USERPROFILE`, and the fallback direct spawn sets `cwd` to the home folder. So the daemon does not keep a task's worktree or slot from being deleted after Done. Even Keel starts no daemon of its own beforehand. Checked on CLI 2.1.319 by reading the binary and the live daemon's folder and handles ([verified](../verified/accounts.md), EKR-100).

  Only `env` was checked; whether the daemon holds on to any other part of the transfer (`CLAUDE.md`, the plugin registry, the links) was not. So if the transfer changed something and there are no live sessions in the folder (a fresh `claude agents` and `sessions/<pid>.json` entries), Even Keel stops its daemon before launching — `claude daemon stop --any` with the folder's `CLAUDE_CONFIG_DIR`; it does not touch the global daemon (`src/account/daemon.ts`). If there are live ones, the daemon is left alone, the account menu says the configuration will arrive after they finish, and the stop is postponed to the first launch without them. The mark lives in the service's memory. The stop is what keeps removed keys out of new sessions; it is held back by live sessions because `claude daemon stop` terminates every background session of the daemon, idle ones between turns included.
- The transfer only reads the global folder (besides moving its memory and skills into their stores, which leaves what its sessions see the same), so it never marks it as changed. What does is the removal of a profile's key on `/settings` → Trackers and CI (BTN-131, `docs/settings.md`): `DaemonRefresh.expire` marks the global folder and stops its daemon by the same rule — `claude daemon stop --any` with its `CLAUDE_CONFIG_DIR`, only while it has no live `sessions/<pid>.json` (the user's own sessions in `~/.claude` hold it too). While they do, the tab says the removal arrives after they end, and the stop is tried again at the next launch in the global folder. A key written or changed needs no stop: sessions read `env` at their start.
- The page's address moving live (`EVEN_KEEL_PORT`, `EVEN_KEEL_HOST`, `rebind` in `src/service/hosting.ts`) marks every Claude folder the same way, the global one included, and stops each daemon by the same rule (BTN-817): a session gets the address as `EVEN_KEEL_URL` from the service's environment (`sessionEnv`, `src/agent/env.ts`), and a running daemon would hand its sessions the old one. A service restart with a new address marks nothing ([unverified](../unverified/sessions.md#hooks-after-the-pages-address-changes-btn-817)).
