# Account folders and sign-in

The folders, the OAuth token diagnostics and the active account.

## Folders and sign-in

- One configuration folder per account (`CLAUDE_CONFIG_DIR`): the global `~/.claude` (key `global`, listed only after explicit registration) and `~/.claude-accounts/<name>` (`EVEN_KEEL_ACCOUNTS_DIR`).
- **Adding an existing CLI sign-in (BTN-543).** Global Claude and Codex folders are hidden until added through the common Add account dialog, including from setup and the project wizard. Selecting a provider checks its unregistered global folder once (`account/discover`, `AccountWatcher.discoverGlobal`), without polling its limits. A signed-in identity offers "Use this sign-in" (`account/global`, `useGlobal`, which rechecks sign-in) or "Sign in with another account"; without a sign-in the normal choices open directly. Browser Back returns from the other-account choices. Registration is in `global_accounts` (`openAccountHomes`, `src/account/globals.ts`), never in the CLI folder. An upgrade adopts only the global folders present at its first start, once; a fresh installation never adopts them automatically. A machine elsewhere also reads its hidden folders' sign-ins every 10 minutes (`AccountWatcher.offerGlobals`, BTN-1568), so the hub offers "Use it" for its account of the same e-mail there ([machines](../machines.md), "Signing in on a machine"). OpenCode already has only managed folders; Copilot's machine sign-in is added explicitly through its existing choice, without a readable per-machine identity.
- **A first account (BTN-227).** The shared pool names `global` and `codex` by default, folders a fresh install may not have. An account added from the page (signed in or on a key) takes the shared pool's entry of its agent while that entry names no listed folder of the agent (`takesShared`, `withSharedAccount`, `ConfigStore.saveSharedAccount`); the provider is left as it is. Once the entry names a real folder, a new account does not move it.
- **A CLI that is not found.** Each agent says whether `spawn` without a shell starts its binary (`Agent.installed`, `findBinary` in `src/paths.ts`: a path as is, a bare name on `PATH`; on Windows only no extension, `.com` or `.exe`, so an npm `codex.cmd` shim alone does not count). Its agents are `AccountView.missing`: the add dialog shows that provider as an off card with where to get the CLI (`CLI_MISSING` in `web/src/accounts.ts`), the section has no "+ Add" and an empty section of it is not shown. A sign-in whose spawn fails with `ENOENT` says the same. Apart from that, the shared and the project settings offer a provider (the provider field, the rows of models and accounts) only once it has an account or the setting already names it (`offeredProviders`).
- The CLI itself stores and refreshes the tokens; Even Keel reads their presence and expiry times from `.credentials.json` (`expiresAt`, `refreshTokenExpiresAt`) and neither keeps nor copies the token values. `claude auth status --json` runs for each folder once a minute.
- **The macOS Keychain (BTN-742).** A CLI signed in where the login keychain is open (the desktop session) keeps the sign-in not in `.credentials.json` but in a Keychain item: `Claude Code-credentials` without `CLAUDE_CONFIG_DIR`, otherwise `Claude Code-credentials-` and the first 8 hex of the sha256 of the variable's value in NFC, the folder's absolute path as `claudeEnv` gives it (read from the CLI 2.1.317 and seen on a Mac on 2026-11-03). With no file, Even Keel on macOS reads that item through `security find-generic-password -s <name> -w`, parses the same two times and drops the text (`src/account/keychain.ts`); an answer is kept for a minute. A read that takes over 3 s may be held by an access dialog: that item is not asked again until a restart, and the folder's times stay unknown. Under the launchd agent the read went through with no dialog ([verified](../verified/accounts.md), 2026-11-03). An item is never scanned for. "Add account" signs in in a `.pending-*` folder and then renames it by the e-mail, so on macOS `AccountHomes.place` carries the item to the new path's name (BTN-745, `KeychainCredentials.move`): it finds the old item by `-s` alone and takes its account from the attribute dump (`"acct"<blob>=…`): the CLI writes the macOS user name there, not the `claude-code-user` its binary also holds (BTN-748, seen on a Mac on 2026-11-03). It reads the old secret, writes it under the same account as the CLI does — `security -i` with `add-generic-password -U -a <account> -s <name> -X <hex>` on stdin, never in the arguments — and deletes the old item; an item already under the new name, whatever its account, wins and only the old one goes, a failed write keeps the old one. Every way the carry stops — no old item, an unreadable one, a failed write — leaves a `Keychain:` line in the log ([verified](../verified/accounts.md), 2026-11-03). Removing a signed-in account from the page signs it out first, and the CLI's logout deletes its item (seen on a Mac on 2026-11-03). Items left by folders renamed before that, or by folders deleted by hand, stay until deleted by hand (`security delete-generic-password -s <name>`).
- A folder that needs sign-in is not polled for `/usage`, and its previous usage warning is hidden immediately. The header's usage warnings cover every account named by a shared or project pool, each once and with the same name as its account card, regardless of the shared provider. Each account's warning is dismissed separately; the technical reason is in its keyboard-accessible tip. On `/setup`, usage, CLI check and CLI download banners are hidden; sign-in and downloads are shown on the agent cards. Unit tests and fake-page shots cover this; the real sign-in and polling check belongs to BTN-542.
- **On a machine elsewhere (BTN-1245).** "Add account" with that machine picked as "Where it signs in" (BTN-1308), or a press on a machine's signed-out label in a hub account's "Machines" column (BTN-1309), starts the same sign-in on that machine through its CLI: the link and the code pass through the hub, the token stays in the machine's folder (`docs/machines/machine-side.md`, "Signing in on a machine").
- "Add account" — `claude auth login --claudeai` in a temporary `.pending-*` folder; after sign-in the folder is named after the e-mail.
- **Two links of one sign-in (BTN-1292).** The CLI builds two links from one PKCE: the manual one (`redirect_uri` on `platform.claude.com`, the code to paste), which it prints, and its own (`redirect_uri=http://localhost:<port>/callback`), which it only opens with `BROWSER` (on Windows without it, `rundll32 url,OpenURL`) and which ends the sign-in by itself. Under the service no browser opens in session 0, under the tray one opened on the PC. So `authLogin` sets `BROWSER` to a program of its own (`openLoginBrowser`, `src/claude/login-browser.ts`): a `.cmd`, or an `sh` script elsewhere, in a temp folder of the sign-in, that appends the link to a file next to it and opens nothing; `%1` with its quotes, not `%~1`, else `&` cuts the link. It is polled every 500 ms and goes with the CLI's exit; the link reaches the watcher through `Agent.login`'s `onLocalLink` as `AccountLogin.localUrl`, and the dialog offers it as "On this computer" next to "From another device". The listener is on the loopback of the CLI's machine, so `MachineLogin` leaves it out: a sign-in on another machine of a hub has the manual link only. Without `onLocalLink` (other agents) nothing changes.
- **Remote Control of a new sign-in (EKR-148).** Sessions start Remote Control only with `remoteControlAtStartup: true` in the folder's `settings.json` (`remoteAtStartup`). A Claude account added from the page with a claude.ai sign-in (`authMethod` `claude.ai`) gets the key in its own settings layer (`AccountSettings.setOwn`, BTN-901, below) and at once by a transfer, so the global settings never take it away; a key, a cloud or another sign-in gets nothing, since Remote Control does not run there. A claude.ai folder without it is `AccountEntry.remoteOff`: the row's menu and the session panel's "Remote Control is off for this account" (`RemoteOff` `disabled`) offer "Turn on Remote Control" (`account/remote`, `AccountHomes.enableRemote`); the global folder gets the key merged into its own file instead. It works from the account's next session: a live one is never touched (invariant 1).
- **When a sign-in ends (BTN-1443).** A claude.ai sign-in lives about 30 days and use does not extend it; it may end any moment of a window: `claude auth status --text` says `Sign-in ends: between <early> and <late>` ([docs](https://code.claude.com/docs/en/authentication), "Check when a stored login ends"), the late end being `refreshTokenExpiresAt`, the early one 3 days before it (`loginEndsFrom`, `web/src/account-state.ts`). The page counts to the early end: the days left, "Renew" in its last week, the yellow problem a day before it, "any moment now" inside the window; the tip of the days left names both ends. Only `needsLogin` — past the late end or the CLI signed out — makes it an error.
- "Renew" (next to the sign-in's days left) — signing in again in the account folder. The page shows the link and the code field in the add dialog or, for a renewal, the sign-in dialog (below, "Accounts: the drawer, the page…").
- Removing a managed folder — `claude auth logout` and the folder goes away (not the active one, not one a pool entry names: the shared pool's — `account.sharedPool`, its menu item opening Settings → Providers and models — or a project's own — `account.projectPool`; `AccountView.pool`, `poolEntries` in `src/config.ts`). The shared pool's built-in default (`DEFAULT_ACCOUNTS`, `PoolEntry.byDefault`) is no pick and keeps no folder, unless a project runs on it by its provider (`AccountEntry.projects`, `account.projectPool` too); once its folder is gone, the next account of the agent added takes the entry, as a first one does (BTN-644). Removing a global account only forgets its registration: the folder and CLI sign-in stay, with no logout. If there are live sessions, removal is deferred until they end (the menu names the ones holding it); "Don't remove" clears the mark.
- A live session of a folder is one with a live process (a `sessions/<pid>.json` entry), not by `state` from `claude agents`: `blocked`/`working` stay there even for a session whose process and daemon died long ago, and such entries interfere neither with removing the folder nor with stopping its daemon (`liveSessions`).
- `*.lock` folders are locks the CLI puts next to an account folder while a token is refreshed; they are not accounts.
- **Token renewal (EKR-15).** Any call of the CLI may renew the folder's sign-in, and the refresh token it renews with is single-use: a call killed between sending the renewal and writing the answer, or two calls renewing at once, may leave `.credentials.json` with no tokens and the account signed out (21.10.2026, after a reboot; unconfirmed, `docs/unverified.md`). So:
  - Even Keel's short calls of a folder — `claude agents`, `auth status`, `-p /usage`, `-p /context` — run one at a time (`FolderCalls`, `src/claude/calls.ts`). A call past its timeout is given up on, not killed: it holds the folder until it ends and is killed only after five minutes; a call whose timeout passes while it waits never starts. The timeout counts the wait: 30 s, but 2 min for `/usage`, which at the service's start queues behind a `/context` probe per session (about 5 s each, slower under the start's load) and timed out on the first poll after nearly every restart (BTN-632); `/usage` now also goes ahead of the other waiting calls and waits only for the running one (BTN-635). So does the `claude agents` the chain waits on — the session showing after a launch or resume, the listing before and after a stop (EKR-102) — and such a listing that still timed out in the queue is tried again without using up its 30 s wait, up to the five minutes after which the running call is killed (`QueueWait`): before that, one at the service's start paused the chain. Launches, `stop` and `daemon` calls go around it.
  - `auth status` and `/usage` wait until the provider's API answers (`Reachability`, `src/account/network.ts`: any HTTP answer from `api.anthropic.com`, `api.openai.com` or, for OpenCode, `opencode.ai` — `openrouter.ai` for a folder on an OpenRouter key — probed at most every 30 s); the service starts before the network after a reboot. Meanwhile an account keeps what it showed, and `/usage` tries again in 30 s. The log says once when the API stops and starts answering.
  - The CLI leaves a `.oauth_refresh.lock.owner.tmp.<8 hex>` behind when writing the owner of its renewal lock fails half-way; with the session poll's `claude agents` every 3 s they came in bursts of hundreds while a token waited for renewal. Before each `auth status` such files older than an hour are deleted (`sweepRefreshLeftovers`, `src/claude/leftovers.ts`).
- **The name of a folder across sign-ins (BTN-528).** The ledger (`state/account.json`, `AccountRecord`) keeps the last e-mail each folder was signed in as; a sign-out does not clear it. A folder whose sign-in shows no e-mail gets it as `AccountEntry.lastEmail`, and the page names it so (`accountName`); with none known, a signed-out folder is named by its folder (`~/.claude` for a global one), not by its provider. Another account signing in to a folder takes over the name: the user's own name for the folder goes with the old account (`noteAccount`). The page does not hide such a change: a folder named after one account (`folderName`, `namedAfter`) and holding another carries `formerEmail` (`formerOwner`), and two signed-in folders of one agent with one e-mail mark every one but the rightful holder (global or named after the e-mail, else the first; `sameAccountAs`). Both show as an error in the problem band under the row, with "Sign in" (`signInMixup`). The same owner is told by the profile e-mail, not the token's `accountUuid`, which `auth status` does not give.
- The account e-mail in `auth status` is the saved profile from `.claude.json`, not the token owner: the Claude desktop app runs the CLI in `~/.claude` with its own account and rewrites the profile, so keep in `~/.claude` the same account as in the app, or launch the app on an account folder ("The Claude desktop app" below).

## OAuth token diagnostics (BTN-763)

Before each Claude `auth status`, including for a registered `global` folder, `src/claude/oauth.ts` reads `.credentials.json` and the adapter keeps only token-presence flags, expiry times and the file's `mtimeMs`, by `home.key`, until the service restarts. The log records tokens becoming empty, an increased access expiry, and tokens returning. A first reading is a baseline; already empty tokens produce one `OAuth tokens empty since` line. Repeated readings and changes of mtime alone are silent. Times are ISO UTC with milliseconds, taken from the file rather than the poll.

An emptying line includes the previous access and refresh expiry, the selected CLI's version, live PIDs from `sessions/*.json` (`liveRecords`, without calling `claude agents`), and other already read folders whose credential mtime is within five seconds in either direction. This identifies correlation, not which process wrote the file or why. Unknown dates, a failed version read or failed session diagnostics say `unknown`; no sessions or peers say `none`. No token values, lengths or prefixes reach the log or the retained shape.

Both token fields must be strings for a valid reading; either nonempty means tokens are present. Missing/unreadable files, malformed or incomplete JSON, absent OAuth objects and files changed during a read are skipped without clearing the last valid reading. macOS Keychain credentials are not observed by this file diagnostic. The page, account status rules, other adapters and running sessions are unchanged. A real CLI emptying still needs the [next natural occurrence](../unverified/accounts.md#claude-oauth-token-emptying-diagnostics-btn-763).

## Active account

- The active account is the shared provider's entry of the shared pool, `accounts[provider]` of the config (BTN-173; before schema v8 `active` of `state/account.json`; until 2026-10-17 always `accounts.claude`): the account pool of the run profiles (`docs/sessions/models.md`). Moving the "Even Keel" role to an account (the roles field), Claude's or Codex's, writes the shared `provider` of that account's agent and its pool entry (`ConfigStore.saveActive`, `withRunAccount`), so it moves only projects without their own `provider` or account entry; a project with them runs on those. The header shows the shared one, then every other account a project runs on by its provider's pool entry (`projectsByAccount` in `src/config.ts`, `AccountEntry.projects`), its card naming the projects of each (BTN-175). What only Claude has — the `.claude.json` sessions read, MCP failures, the tools view — stays on the shared `accounts.claude` (`claudeAccount` in `src/service.ts`). The project's commands (`beforeStart`, `check`, `afterGreen`) run in the environment of the account the task's session runs on, not the shared Claude one (EKR-26, `docs/chain/worktrees.md`).
- The active account can be switched at any time, even with a chain running: the switch only picks the folder for new launches, so sessions of the active account, mid-turn or not (VS Code chats included), stay where they are and the chain's next session starts on the new account (`switchProblem`). The roles menu says so under "Even Keel". Renewing the active one's sign-in rewrites the folder's tokens, so it waits until every chain is paused or stopped and no session of the active account is mid-turn — `busy` or `waiting`.
- While signing in to the active account is in progress, or it is not signed in or its sign-in has expired, new sessions are not started (the chain pauses with a reason).
- `state/account.json` — for each folder, its account, since when it has been in effect and which one was before it. Folder limits received before the account change in it are not shown; the account that hit a limit is the session's folder and its e-mail at the time of the limit, and `--resume` only if the same folder with the same e-mail is active. An account without an e-mail (OpenCode or Copilot on the machine's sign-in) is identified by its folder key, in both the current view and `accountAt`, including an empty ledger; its e-mail stays null. A folder that signs in with no e-mail after one it was noted with (a key folder reused by OpenCode) is noted with a null one from then on (`noteAccount`): the stale record made every limit of its sessions an account switch, and the chain handed over to a new session on the same spent account at once, again and again. A sign-out still notes nothing. Readiness requires `loggedIn: true` and no `launchBlock`, not an e-mail. This also lets the interrupted task continue after a fix of main without forcing a handoff while its cache is warm.
