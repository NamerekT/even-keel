# Claude account kinds

API, long-token and cloud accounts.

## API accounts (BTN-99)

- An API account is a folder whose sessions pay from an Anthropic API key instead of a subscription. "API key" in the add dialog (`AddAccountDialog`, command `account/api`, `AccountHomes.addApiKey`) creates `~/.claude-accounts/<folder>` with `settings.json` = `{ "env": { "ANTHROPIC_API_KEY": "…" } }` and `.claude.json` with the key's last 20 characters in `customApiKeyResponses.approved`, otherwise the CLI asks whether to use the key. A key shorter than 21 characters or with spaces is refused (`account.apiKeyInvalid`). Before the folder is made, the key is checked with Anthropic (`checkApiKey`, `src/account/keycheck.ts`): `GET /v1/models?limit=1` with it, which costs no tokens; 401 or 403 refuses it (`account.apiKeyRejected`), and a network error, a timeout or any other status refuses it too, as unchecked (`account.apiKeyUnchecked`), so no folder is made with a key nobody looked at. After that the watcher checks each API account's key from its `settings.json` once an hour (`KeyChecks`, in memory, so on every start too): a refused key makes the account `needsLogin` — the page says the key isn't accepted, the chain does not switch to it or launch on it — and a check that learns nothing keeps the last verdict. A folder with `apiKeyHelper` is not checked: there is no key to read. A folder set up by hand with `apiKeyHelper` instead of the variable works the same way. Chain sessions on such a folder's key were run live from the Windows service on 2026-10-25 (CLI 2.1.310, Haiku): one on `--bg` (the SDK was not downloaded yet at its launch) and one through the SDK, each to a merge and Done.
- **Replacing the key** (BTN-418). A revoked or expired key needs no new account: "Replace key" ("Replace token" for Copilot) in the row's ⋯ menu (`AccountRowMenu`), shown whenever the key may be replaced, working or not, and the button next to "The key isn't accepted", open a field for the new one (`ReplaceKeyDialog`, command `account/key`, `AccountWatcher.replaceApiKey`). The key goes into the same folder, so its name, roles, pools and Tally history stay: Claude's `env.ANTHROPIC_API_KEY` in `settings.json` and its last 20 characters in `customApiKeyResponses.approved` of `.claude.json` in place of the old key's (the rest of both files as it was), Codex's `OPENAI_API_KEY` in `auth.json`, OpenCode's provider entry in `auth.json` (`replaceKey`), Copilot's token. Refused before anything is written: a key of the wrong form, as on adding; a folder that does not keep its key itself — the agent's own folder or one with `apiKeyHelper`, which have no such item (`AccountEntry.keyReplaceable`, `account.keyNotHeld`); an OpenCode key of another provider than the one it holds (`account.keyOtherProvider`); a key the provider refuses or that cannot be checked, as on adding; a key of another organization (below). A replaced key's verdict is the new one at once, so the card stops saying it is refused and the chain may switch to the account again. Running sessions keep the key they started with (invariant 1); new ones read the new one, as `settings.json` and `auth.json` are read at a session's start.
- **The key's organization.** An API key's account is the organization that pays: a key of another one is another account. A working key's answer names it — Anthropic's header `anthropic-organization-id` on the models list, OpenAI's `openai-organization` on `GET /v1/me`, asked only after the models list took the key, since OpenAI's models list carries no such header (BTN-649) (`KeyVerdict.organization`) — and a refused key's 401 names none, so it is kept while the key works: on adding and on each hourly check with a 2xx, in the state database (`key_organizations`, step 14, `docs/storage.md`; `src/account/organizations.ts`), which gives accounts added before it one at their next check. A replacing key of another organization than the kept one is refused (`account.keyOtherOrganization`) and the old key stays; with none kept (a key refused before this was there) or an answer without the header, the key is taken and its organization kept. OpenAI's `/v1/me` failing — a refusal of a restricted key without the right, an error, the network — leaves the models list's verdict as it is: the key works, its organization unknown. A workspace inside the organization is not checked: it cannot be seen without an Admin key, and the same organization pays. Anthropic's header, the refusal and a second key of the same organization taken were seen live ([verified](../verified/accounts.md)). OpenAI's header was seen live on `GET /v1/me` and not on `GET /v1/models` (2026-10-31); the refusal of another OpenAI organization's key and a restricted key's `/v1/me` were not ([unverified](../unverified/sessions.md#an-api-keys-organization-header)).
- The account name from the form is not the folder name. The folder is the name made safe for a path (`folderName`: `Team API` → `team-api`, `api` when the name is empty, `-2` when taken) and stays the account's identity: the key in commands and `state/`, and its stand-in e-mail (`withIdentity`). The name itself is kept in `state/account.json` as `accounts.<folder>.name` (schema v4, `nameAccount`) and goes away with the account; the page shows it instead of the folder, and the folder in the account's details.
- `claude auth status --json` in such a folder says `loggedIn: true`, `authMethod: "api_key"` (`"api_key_helper"` with a helper) and no e-mail (`isApiKey`). The folder key stands in for the e-mail wherever an account is told apart by it (`withIdentity`): the limit owner, `state/account.json`, the session pills.
- The transfer of the shared configuration keeps the folder's own `env.ANTHROPIC_API_KEY` and `apiKeyHelper` over the global settings (`mergeSettings`); every other key still comes from `~/.claude`.
- How a Claude folder runs its sessions — `--bg` or the Agent SDK — is the shared setting `execution.claude` since BTN-353 (`auto` by default, `bg`, `sdk`; `transportOf`): `auto` runs an API folder through the SDK and a subscription on `--bg` (`docs/sessions/sdk.md`, "The Agent SDK transport"). The card only says it (`TransportNote`, "Sessions through …", with Anthropic's rule in the tip of a subscription on the SDK); adding a key asks nothing. Before, it was each folder's `transport` in `state/account.json` (schema v10, switched on the card by `account/transport`, chosen with a key by `account/api`); schema v11 (BTN-302) wrote `bg` to each account of an older file without a choice, all but Codex's own folder. Schema v12 moves those choices out of the records into the file's `transports`, and the service's start turns them into the setting once (`executionOfChoices`): `auto` when each is what `auto` gives its folder (a key on `sdk`, a subscription on `bg`), `sdk` when every Claude folder chose it, otherwise `auto` with a log line per folder whose way changes; a folder gone or no Claude one is left out, whether a folder holds a key is read from its `settings.json` (`apiKeyOf`). `transports` is dropped once the setting is written.
- What an API account does not have: limits — `/usage` is not polled for it (it would answer free with no window lines anyway), there are no limit bars, and a key's `rate_limit` stops a session like any error (invariant 1); sign-in renewal and `claude auth logout` on removal; Remote Control, which needs a claude.ai sign-in (`RemoteOff` `api-key`).
- A key out of credit (BTN-165) is held on the current task as on a limit (`docs/chain/exceptions.md`, exception 1): the CLI's `billing_error` ("Credit balance is too low") is `apiError.kind` `credit`, its lamp is `limit`. Its "reset" is the moment the credit is back: while the dispatcher asks (`AccountWatcher.creditBackAfter`), the watcher checks the key every 5 minutes (`CreditChecks`, `checkCredit` in `src/account/credit.ts`, in memory; a Codex key — below) — the models list for the cheapest model (a Haiku, else the newest), then `/v1/messages` with `max_tokens: 1`, a fraction of a cent. Only 2xx restores access; a 400 saying "credit balance is too low" or that the specified API usage limits were reached keeps waiting; anything else learns nothing and is logged. The checks start 5 minutes after the stop and end once access returns or 10 minutes after the dispatcher stopped asking. The panel says the key is out of credit and is checked (`t.session.creditOut`). The hold keeps `credit` (`LimitHold.credit`), so a cold handover after it is journaled with the cause `credit` and the task's session list says the key ran out of credit, not that it hit the usage limit; launches journaled before that say "limit". The service log still words it "limit reached".
- An Anthropic spending cap (BTN-382) is held too: "reached your specified API usage limits" is `apiError.kind` `spend` even when the CLI records `error: unknown`. Its "regain access on YYYY-MM-DD at HH:mm UTC" gives the reset directly (`src/limits/spending.ts`); a missing, invalid or already elapsed date leaves it unknown. The five-minute key check continues even with a known reset: a 2xx permits an earlier resume or handoff if the cap was raised. The account card, drawer and session panel name the spending limit and its reset in local time; their hint explains the checks and account switching. The workspace variant is accepted defensively, and actual automatic recovery remains [unverified](../unverified/sessions.md#api-spending-cap-recovery).
- Instead of the limits, the panel row, the account card and the header (while the API account is the active one) show the folder's spend since local midnight, from Tally (`/api/stats/spend`, `docs/stats.md`; on an OpenRouter key a session's real spend, read from the key, where Even Keel has it), refreshed every 5 minutes and fetched only while some account is on a key. Without Tally there is no figure.
- The prompt cache lifetime of sessions on a key is 5 minutes by default; the `cacheTtl` config key changes it (`docs/sessions/cache.md`).

## Long-token accounts (BTN-1005)

- A long-token account is a Claude subscription folder that signs in with the token of `claude setup-token` instead of the CLI's full sign-in. The add dialog's "Subscription" way offers both as a second row of cards ("Full sign-in", picked by default, and "Long token"); the token goes through `account/token` (`name`, `token`, optional `sameAs`; `AccountWatcher.addLongToken`, `addTokenAccount` in `src/account/tokenAccount.ts`).
- **Storage.** The token is `env.CLAUDE_CODE_OAUTH_TOKEN` in the folder's `settings.json`, as an API account's key: the CLI reads it there for `--bg` and the Agent SDK alike, and the transfer of the shared configuration keeps it (`mergeSettings`). Beside it `even-keel-token.json` (`src/account/longToken.ts`) holds `until` — the day it was added plus a year, since the token carries no readable date — `sameAs` and `refusedAt`. A folder whose `settings.json` got the token by hand is a long-token account too, with no known last day.
- **The check turn.** `claude auth status` answers `loggedIn: true` for any token, a made-up one too, so a token is checked by one short turn in the new folder before the account is kept; a refusal removes the folder and shows the reason under the token field (`account.tokenRejected`), a value that is not a token of that form is refused at once (`account.tokenInvalid`).
- **The page does not drive `claude setup-token`.** It prints nothing without a terminal, and Even Keel has no pty: the dialog shows the command for a terminal of the user's own and a secret field for the token it prints. Probed on 2.1.327 with pipes (BTN-1212): the sign-in itself starts — it hands the `BROWSER` opener (on Windows without one, `rundll32 url,OpenURL`) the automatic link with `redirect_uri=http://localhost:<port>/callback` and `scope=user:inference` and listens there — but its Ink screen writes nothing to stdout or stderr, also with `CI=true`, and a callback it answered ("Sign-in was canceled or failed" for a made-up code) left it silent and running. A real sign-in was not tried: the token would be issued for a year and lost. Decided: no pty dependency; wait for a CLI flag that prints the link and the token without a terminal, looked for at each raise of Claude's `checked` (`docs/releases.md`, "Checking a CLI version").
- **Limits.** `/usage` gives such a folder no windows, so it is not polled and never raises the "/usage unread" warning (`LimitsWatcher.usage` answers `ok` for it); the limits are what the folder's sessions report (`withSessionLimits`) — the five hours and the week, no model's own week, and nothing between sessions, so an early reset is not seen and a chain that hit the limit waits for the reset it was told. With `sameAs` — a Claude folder on a full sign-in of the same account, picked in the dialog — the token folder shows and feeds that folder's limits instead; a `sameAs` folder that was removed or put on a token itself is ignored.
- **A refused token.** The account needs a sign-in once `until` has passed or a session of the folder was refused with `authentication_failed` (the session error kind `auth`; the session itself stops as on any error, invariant 1). `refusedAt` is written into the file, so it outlives a restart; a new token clears it.
- **A new token** goes into the same folder through `account/key` (`replaceToken`): the check turn runs on it, and the old token and file come back when it is refused. The page calls it "Issue a new token": in the row's menu always, as a button in the problem band under the row: red once the token is refused or past its day, yellow for its last 30 days.
- **What it does not have:** Remote Control (the CLI refuses it on an inference-only token; the session's reason is `long-token`), an e-mail (the row is named by the name given, else as a nameless account), `claude auth logout` on removal, and the OAuth diagnostics below `.credentials.json` — there is no such file to watch.
- **On a machine elsewhere** (BTN-1002): the hub's page signs a machine in on a long token instead of the browser sign-in ("Long token" next to "Sign in" under a hub account and in step 3 of "Add a machine"; `docs/machines/machine-side.md`, "Signing in on a machine"). The token file then holds `account` — the hub's claude.ai account (`accountUuid` and e-mail) the person picked by the row, since `auth status` on a token names none; the machine posts the folder under that account with `polls: false`, so the hub's full sign-in polls `/usage` and hands the machine its limits, and the machine's session windows go back to the hub. One full sign-in of the account is enough, best on the hub. "Add account" on a machine offers the hub's two cards for Claude, and under "Long token" first the tokens the hub's own folders run on (BTN-1501, `machines/sharedToken`): the hub reads the token from its folder's `settings.json` and sends it the same way, so the page never holds it.
- **When which.** A full sign-in gives Remote Control, `/usage` with the models' own weeks and the OAuth diagnostics; a long token needs no browser on the machine and lives a year, but gives none of them. A machine without a browser or a person at it takes the token; a machine the person answers sessions on through Remote Control takes the full sign-in.
- **The CLI's own update.** A session on the checked copy of the CLI gets `DISABLE_AUTOUPDATER=1` (`claudeEnv`), `--bg` and SDK alike, so a token session does not move the version a machine pins; on the system CLI the person's own install updates as it is set to.
- Its sessions run as a subscription's do (`--bg` under `Auto`). Not yet seen live: [the token's real lifetime and its refusals](../unverified/accounts.md#a-claude-subscription-on-a-long-token-btn-1005).

## Cloud accounts (BTN-822)

- A cloud account is a Claude folder whose sessions run on a cloud's Claude models and are billed by that cloud. The clouds are `CLOUDS` in `src/account/cloud.ts` (`bedrock`, `vertex`, `foundry`); all three are `CLOUDS_READY`. The add dialog's third way for Claude Code, "Cloud", picks the cloud and how its credentials are found (`CLOUD_WAYS`). Bedrock (`BEDROCK_WAYS`): an AWS profile, a Bedrock API key, an access key pair (with an optional session token), or the environment the service already has; region, the Opus/Sonnet/Haiku model ids or inference profile ARNs, and the inference profile prefix are optional. Vertex (`VERTEX_WAYS`, BTN-823): the ADC file of `gcloud auth application-default login`, a key file (a service account's JSON key or a Workload Identity Federation config), or the service's environment; the project id is required, the region (`global`, `us`, `eu` or a region; the CLI's default is `us-east5`), the model ids (`claude-sonnet-4-5@20250929`) and a region per model are optional. The form's per-model choices are `VERTEX_REGION_MODELS`, copied from CLI 2.1.319; the server takes any `VERTEX_REGION_CLAUDE_*`. Foundry (`FOUNDRY_WAYS`, BTN-824): the resource's API key, Microsoft Entra ID through the Azure SDK's chain (the service's environment, `az login` of its user, the machine's managed identity), or a Bearer token of about an hour; the resource is required, as its bare name or its full `https://<name>.services.ai.azure.com/anthropic` address in one field (`foundryEndpointOf` tells which and why a value is neither, by CLI 2.1.319's own checks), and at least one deployment name, since Foundry has no model check at start. The CLI tells a model's context window by its id, so a deployment named otherwise gets 200K unless the folder's `settings.json` `modelOverrides` maps the model id to it; the form says to name deployments after their models. There is no region: the resource has one.
- **The whole connection is the folder's `settings.json` `env`** (`cloudEnv`): `CLAUDE_CODE_USE_BEDROCK=1` plus `AWS_PROFILE`, `AWS_BEARER_TOKEN_BEDROCK` or `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN`, `AWS_REGION`, `ANTHROPIC_BEDROCK_REGION_PREFIX` and `ANTHROPIC_DEFAULT_*_MODEL`; for Vertex `CLAUDE_CODE_USE_VERTEX=1`, `ANTHROPIC_VERTEX_PROJECT_ID` (the CLI takes the project only from it, not from `GOOGLE_CLOUD_PROJECT` or the key file), `CLOUD_ML_REGION`, `GOOGLE_APPLICATION_CREDENTIALS` for the key file way, `VERTEX_REGION_CLAUDE_*` and the model variables; for Foundry `CLAUDE_CODE_USE_FOUNDRY=1`, `ANTHROPIC_FOUNDRY_RESOURCE` or `ANTHROPIC_FOUNDRY_BASE_URL`, `ANTHROPIC_FOUNDRY_API_KEY` or `ANTHROPIC_FOUNDRY_AUTH_TOKEN` (neither for Entra ID; read back in the CLI's order: a token, a key, else Entra ID) and the model variables holding deployment names. The ADC and environment ways write the same `env` (as the CLI's own wizard does), so a Vertex account reads back as `keyFile` or `adc`. Nothing goes into the state database and there is no schema step: the page reads the connection back from the file (`AccountHomes.cloudOf` → `AccountEntry.cloud`, secrets left out). The transfer of the shared configuration keeps the folder's cloud variables (`isCloudVariable`) and drops the same variables from the global settings (`mergeSettings`), so a global `AWS_PROFILE` never moves a subscription folder onto a cloud.
- **AWS profiles** come from the files of the user the service runs as (`src/account/aws.ts`: `AWS_CONFIG_FILE`/`AWS_SHARED_CREDENTIALS_FILE`, else `~/.aws/config` and `~/.aws/credentials`), read by the command `account/aws` into `AccountView.aws` for the profile field's suggestions; the field strip names that user, since a service under another Windows user does not see the person's own `~/.aws`.
- **Google Cloud credentials** come the same way (`src/account/gcloud.ts`, command `account/gcloud` → `AccountView.gcloud`): the gcloud folder of that user (`CLOUDSDK_CONFIG`, else `%APPDATA%\gcloud` or `~/.config/gcloud`), whether its ADC file is there and of which `type`, the service's own `GOOGLE_APPLICATION_CREDENTIALS`, and the projects of the gcloud configurations and the ADC's quota project for the project field. The ADC way without the file shows the login command to run as that user.
- **The Azure sign-in** too (`src/account/azure.ts`, command `account/azure` → `AccountView.azure`, read when the Foundry form picks Entra ID): whether that user's `azureProfile.json` (`AZURE_CONFIG_DIR`, else `~/.azure`) lists a subscription, and whether the service's environment holds a service principal (`AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and a secret, certificate or federated token file). With neither the form shows `az login` to run as that user.
- **The check before adding.** `account/cloud` → `AccountWatcher.addCloud`: the folder is made, one short turn runs on it through `Agent.write` (`claude -p`, prompt and timeout `CLOUD_CHECK_*` in `src/account/service-defaults.ts`, 120 s — the CLI gives up on AWS credentials after 60 s itself), and a refusal removes the folder again and answers with the cloud's reason (`cloudErrorNotice` in `src/account/cloud-errors.ts`: credentials, credential timeout, payment method, model access, on-demand region, throttling; for Vertex Google's credentials, billing, the disabled `aiplatform.googleapis.com`, a model not in Model Garden or the region, quota, IAM permission — Vertex patterns go first and match only Google's own words; for Foundry Azure's credentials, a missing deployment, a subscription that cannot buy Claude, a refused key or token, throttling, and — only at the check of a new Foundry account — a connection error read as an unreachable resource) or `account.cloudCheckFailed` with the CLI's text. The model that answered is kept in memory (`AccountEntry.checkedModel`) for the dialog's "Checked and added" step.
- **Short-lived credentials** (`cloudShortLived`, `shortLivedProfile`): a profile with `sso_session`, `sso_start_url`, `login_session` or `aws_session_token`, a short-term Bedrock API key (`bedrock-api-key-` prefix) and a key pair with a session token. They expire within hours and are renewed in a browser, so the dialog and the account's tip warn that a chain left alone overnight stops; the long-lived ways are the fix. On Vertex a user's ADC (`authorized_user`; `userCredentials` in `gcloud.ts`) is short-lived, since the organization's session policy may ask for a new sign-in; a key file is not, and the environment way counts as a user's ADC only without the service's own `GOOGLE_APPLICATION_CREDENTIALS`. On Foundry the token way is short-lived: the CLI does not renew a static token. The texts are per cloud.
- **What it does not have**, as an API account: it pays per token (`paysPerToken` — `authMethod` `third_party` — on the server and the page), so `/usage` is not polled, limits are never waited out and there are no limit bars; the row shows spend instead (Tally) and the region as its plan. Tally prices a model by the longest price whose name prefixes its id, so a cloud id (`us.anthropic.claude-…`, an ARN) counts only with a price row of its own in `tally.config.json` (the collector logs it as unpriced); the spend tip says so (`cloudSpendTitle`). No claude.ai sign-in, renewal or `claude auth logout`, no Remote Control (`RemoteOff` `api-key`), and no WebSearch (Bedrock has none). `execution.claude` `auto` runs it through the Agent SDK like a key (`docs/sessions/sdk.md`).
- **Errors in a session.** Bedrock throttling, a Vertex quota refusal (429 `RESOURCE_EXHAUSTED`), Foundry's `RateLimitReached` and the cloud refusals above in a transcript are `apiError.kind` `error` with their `notice`: the session stops as on any error (invariant 1) and is never held as a limit, since throttling has no known reset.
- On `/accounts` a cloud account is its own connection group ("Amazon Bedrock", stripe `--owner-aws`, access `bedrock`; "Google Vertex AI", `--owner-google`, access `vertex`, its project in the tip; "Microsoft Foundry", `--owner-microsoft`, access `foundry`, its resource where the others show the region). Never run live: AWS refused the test account model access on 2026-11-05, Google's trial credits and Azure's free or credit subscriptions do not pay for Claude, and no paid check is made ([Bedrock](../unverified/accounts.md#claude-on-amazon-bedrock-btn-822), [Vertex](../unverified/accounts.md#claude-on-google-vertex-ai-btn-823), [Foundry](../unverified/accounts.md#claude-on-microsoft-foundry-btn-824)).
