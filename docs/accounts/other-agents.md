# The folders of other agents

Codex, OpenCode and Copilot.

## The Codex folders (BTN-168, BTN-176)

- Codex's own folder `CODEX_HOME` or `~/.codex`, key `codex`, listed only after it exists and is explicitly registered (Codex does not create it); and one `CODEX_HOME` per added account under `~/.codex-accounts/<name>` (`EVEN_KEEL_CODEX_ACCOUNTS_DIR`), the same way as Claude's (`AccountHomes`, `src/account/homes.ts`). `CODEX_HOME` isolates everything — `auth.json`, `sessions/`, `state_5.sqlite`, `config.toml` — so each folder has its own sign-in, limits and sessions. A folder name is its account key across both roots: a new one is named apart from every Claude and Codex folder (`folderName`), and a Codex folder named like a Claude one by hand is not listed.
- "+ Add" in the Codex section (`account/add` with `agent: "codex"`) makes a `.pending-*` folder under the Codex root, runs `codex login --device-auth` in it and, signed in, names it by the e-mail — as Claude's add does. Removing an added folder is Claude's too: `codex logout` and the folder goes, after its sessions end. Removing Codex's own folder as an account only forgets its registration, keeping the folder and sign-in, and no Codex account is given to an app (`account.codexApp`).
- A new folder has no `config.toml`: its model is the shared or the project's `models.codex`, else Codex's default (a `config.toml` model the free plan refuses, such as `gpt-5.4-mini`, stays in `~/.codex`). The tracker's plugin in Codex is installed per folder: a new one has none until the user installs it there.
- A Codex account takes the Even Keel role like a Claude one (below). A Codex session starts in the pool's `accounts.codex` (`codex` by default; `docs/sessions/models.md`, "Run profiles"), and the chain judges a Codex task's launch block, limits and handoff account by that folder, not by the active one. There is no switching to another account on a spent limit — the chain waits for the reset or a change of the pool, as with Claude.
- **One free ChatGPT account across Codex and OpenCode (BTN-987).** `extraFree` and `secondFreeProblem` in `src/account/model.ts` use the existing folder order. Codex reads `chatgpt_plan_type` from its `id_token`; OpenCode reads it from its OpenAI OAuth access token (`AccountStatus.chatgptPlan`, below). Only the explicit plan `free` counts; paid and unknown plans do not. A different free identity is refused on adding (`account.secondFree`): the new folder is signed out and removed. The same e-mail, case insensitive, may have one folder in each agent; another folder in the same agent is still refused (`account.sameFree`). Without an e-mail the shared identity cannot be confirmed. Existing extra free folders show `account.extraFree`, cannot start sessions or take the Even Keel role; the first identity's one folder per agent stays usable. Every status refresh, including after a restart, recalculates this from the folders, without a saved exemption. The sign-in window (`planRefused` in `web/src/accountAdd.ts`) folds the CLI's earlier success under "CLI output: the sign-in, before the plan check" and offers "Sign in with another account". [Live check limits](../unverified/accounts.md#one-free-chatgpt-account-across-agents-btn-987).
- **On an OpenAI API key (BTN-177).** "API key" in the Codex step of adding (`account/api` with `agent: "codex"`) makes a folder under the Codex root, named as Claude's API folders are, with `auth.json` = `{ "auth_mode": "apikey", "OPENAI_API_KEY": "…" }` — what `codex login --with-api-key` writes (checked on 0.162.1); Codex reads the key from there on every turn, so the turn's environment is unchanged and `codex login status` says "Logged in using an API key" (0.162.1) or "API key configured" (0.164.0, BTN-383), both read as a key (`parseLoginStatus`, `isApiKey`). The key is in the folder in plain text, as Claude's is in `settings.json`. Before the folder is made, the key is checked with `GET https://api.openai.com/v1/models` (`checkOpenAiKey`, no tokens): 401 or 403 refuses it (`account.codexKeyRejected`), anything else refuses it as unchecked (`account.codexKeyUnchecked`); then hourly, as Claude's. The free-account rule does not apply: a key is used under OpenAI's API terms, not ChatGPT's. Spend today comes from Tally as for Claude's keys (Codex rollouts are priced by GPT model, `docs/tally.md`); a model Tally has no price for shows no figure. A key out of money is waited out as Claude's (BTN-195): OpenAI answers 429 `insufficient_quota`, which codex-cli 0.162.1 words "Quota exceeded. Check your plan and billing details." (read from its binary; seen live on 0.164.0 with a key at zero, 2026-10-25, as the rollout's `task_complete.error`, `codex_error_info` `usage_limit_exceeded`, while the API's own 429 had the code `credit_balance_exhausted` and "You have no credits remaining…"); the rollout fold takes that text, or OpenAI's own "You exceeded your current quota", as `credit` (`CREDIT_TEXT`, `src/codex/rollout.ts`) — any other `quota`, `usage limit` or `rate limit` stays `limit`. The watcher asks the folder's provider (`checkCredit(agent, key)`): for Codex `checkOpenAiCredit` — the models list for a `gpt-` text model with `nano` in its id, else `mini`, then `POST /v1/responses` with `max_output_tokens: 16` (the API's least) and `store: false`. 2xx is money; a 429 with `insufficient_quota` is none yet; a 429 of a rate limit and anything else learns nothing.
- Sign-in status is `codex login status` (`Logged in using ChatGPT` / an API key, above / `Not logged in`); the e-mail and plan come from the `id_token` claims. "Renew" and adding run `codex login --device-auth` through the same sign-in flow as Claude's, with a window of its own: no code field, the one-time code read out of the output (`loginCode`: the line under "Enter this one-time code", or OpenCode's "Enter code: …") into the login's `deviceCode` and shown large with a "Copy" button, the CLI output folded; a code not read leaves the output unfolded, the code in it (not checked live, `docs/unverified.md`); sign-out is `codex logout`.
- Limits of a ChatGPT sign-in are polled from ChatGPT, the folder's rollouts being the fallback (`docs/sessions/limits.md`, "ChatGPT (Codex and OpenCode)"); Tally collects the rollouts of every Codex folder (`docs/tally.md`). The shared configuration is not transferred: Codex reads its own `config.toml`, and the tracker's MCP server comes with every turn.

## The OpenCode folders (BTN-214)

- Only added ones, under `~/.opencode-accounts/<name>` (`EVEN_KEEL_OPENCODE_ACCOUNTS_DIR`): OpenCode keeps its files in the XDG folders of the user, shared with every OpenCode the user runs, so there is no "own folder" to list as with `~/.claude` and `~/.codex`. A folder holds the four XDG folders (`data`, `config`, `state`, `cache`) and the empty `config/opencode/AGENTS.md` that keeps `~/.claude/CLAUDE.md` out (`docs/sessions/opencode.md`, "OpenCode"). Names are unique across all three roots, as for Codex.
- Ways in (`SIGN_INS` in `src/agent/providers.ts`, `LOGIN_METHODS` in `src/opencode/cli.ts`), chosen in the add dialog and sent as `account/add` with `agent: "opencode"` and `method`:
  - `chatgpt` — `opencode providers login -p openai -m "ChatGPT Pro/Plus (headless)"`, a device link and code, shown as Codex's;
  - `none` — no sign-in: the folder is made at once and runs OpenCode's own free models (`opencode/big-pickle`);
  - **OpenCode Go** — a Console key, checked with the Go usage endpoint before the folder is made (`account/api`, `agent: "opencode"`, `provider: "opencode-go"`), then saved as an API credential under `opencode-go`. Its prefix is not used to choose a provider: older Go keys share OpenAI's `sk-` prefix. A 403 accepts a Console key without Go; 401 rejects it with instructions to create a new Console key. Replace key checks Console and preserves the stored provider (`opencode-go` or legacy `opencode`), folder, name and roles. Such a folder is a subscription for usage polling, not a per-token API account; the key stays out of the page state and OpenAI key/credit checks.
  - an API key (`account/api` with `agent: "opencode"`) — written into `data/opencode/auth.json` as `opencode providers login` writes it, under `anthropic` for an `sk-ant-` key, `openrouter` for an `sk-or-` key and `openai` for any other (`keyVendor`), and checked with that provider's API as Claude's and Codex's keys are (`keyProvider` in `src/account/homes.ts`). The entry is `{ "<provider>": { "type": "api", "key" } }` for every provider (seen in OpenCode 1.19.5's own login code). OpenRouter (BTN-843): the key is checked with `GET openrouter.ai/api/v1/key` (`checkOpenRouterKey`; 401/403 refused, its own `account.openRouterKeyRejected`/`account.openRouterKeyUnchecked`; an answer with `is_management_key: true` is refused too, on adding and in "Replace key", with `account.openRouterManagementKey` — a management key takes no model request, BTN-1205), its money after a stop on credit by one output token of the cheapest paid text model of `/api/v1/models` (`checkOpenRouterCredit`; 402 still empty — a free model answers with no money, so it would tell nothing). A session's 402 ("Insufficient credits", "requires more credits") is a stop on credit (`CREDIT_TEXT` in `src/opencode/transcript.ts`). With such a key `opencode models` lists OpenRouter's whole catalogue, so a task's run names a model as any other OpenCode one: `openrouter/minimax/minimax-m3.1-flash`. Besides the balance (below), the card (BTN-847) shows what is left of a spending limit set on the key itself: the same `/api/v1/key` answer has `limit`, `limit_remaining` and `limit_reset` (`openRouterLimit`), read at each check of the key and with each read of its spend (`readOpenRouterKey`, BTN-860), kept in memory by `KeyChecks` (`noteLimit`) and given to the page as `AccountEntry.keyLimit`. The key's row on `/accounts` and in the drawer gets a third named cell after Today and 30 days, "Key limit left $X" (`KeyLeft` in `web/src/layout/accountRows.tsx`; amber from 80% used, red at 100% or nothing left), its tip saying the limit, its reset period, when it was read and, while no key reads the balance, where to add a management key. A key with no limit shows nothing, as before. The balance (`GET /api/v1/credits`) is read with the account's own key first (BTN-1206): OpenRouter documents `/credits` for a management key only, yet on 2026-11-15 it answered the key a session runs on with the same totals. Once it refuses the own key (401/403), the watcher remembers that key (`ownKeyRefused`, in memory, until the folder's key changes) and asks the management key instead; with none, the balance leaves the card. A failed read keeps what was read. The management key (BTN-868) is the optional way when the own key is refused: "Management key" in the row's ⋯ menu, only on an account on an OpenRouter key (`AccountEntry.managementKey`, `false` without one), opens `ManagementKeyDialog` (command `account/management-key`, `AccountWatcher.setManagementKey`). Before it is kept the key reads `GET /api/v1/credits` (`readOpenRouterBalance` in `src/account/management.ts`): 401/403 refuse it (`account.managementKeyRejected`), an answer that cannot be read keeps nothing (`account.managementKeyUnchecked`), an empty value removes the key. The key is kept in the state database (`management_keys`, `docs/storage.md`), never in the account folder its sessions read, and the page gets only the boolean. The balance — `total_credits − total_usage` — is read on save, with the hourly check of the key and with each read of its spend, kept in memory and given as `AccountEntry.balance`: a named cell "Balance $X" after the key limit (`Balance` in `accountRows.tsx`), red when nothing is left or OpenRouter refused the management key later (`{ rejected: true }`, its tip says to put a new one); a read that fails keeps the last balance. Removing the management key keeps a balance the own key reads. Removing the account removes its key.
- **No Claude subscription.** Anthropic allows the Pro/Max sign-in only in Claude Code, and OpenCode dropped it: Claude runs in OpenCode only on an API key. The add dialog says so under the API key way.
- **Copilot is visible but unavailable (BTN-573).** OpenCode on Copilot has not passed a live session check and is blocked until a separate verification task enables it. Copilot Free only offers automatic model selection, whereas OpenCode requests a named model; the checked CLI did not list `github-copilot` models and its attempted run failed. Adding or renewing that sign-in through Even Keel is unavailable. Existing credentials and their credits remain visible with an unsupported note. A folder holding only Copilot cannot be selected or switched to, and is not ready in setup or the project wizard; a mixed folder remains usable with its other providers. Model suggestions omit Copilot, and direct server launch/resume/write calls reject it too. See `docs/sessions/opencode.md`, "OpenCode".
- Status comes from `auth.json`, not a CLI call: no file is a folder signed in with `none`; `subscriptionType` keeps the provider list. For OpenAI OAuth, `parseAuth` reads `https://api.openai.com/auth.chatgpt_plan_type` into `chatgptPlan` and `https://api.openai.com/profile.email` into `email` from the saved access token, with no network request or token renewal. These claims were present on the bench's free ChatGPT sign-in (2026-11-11); missing or malformed claims remain unknown. The CLI owns renewal, so a plan change is visible once its saved token changes. A new ChatGPT folder is named by that e-mail; with none known, or with no sign-in, it is named after the agent (`opencode`, `opencode-2`…). Existing folder keys stay. Sign-out deletes `auth.json`. One folder may hold several providers; the run profile's model (`<provider>/<model>`) picks which one a session uses.
- Limits from ChatGPT, Copilot or Go: ChatGPT's 5-hour and weekly windows, Copilot's monthly allowance and Go's 5-hour, weekly and monthly windows, read every five minutes from the provider's API (`docs/sessions/limits.md`, "Limits of OpenCode and Copilot"). A folder on ChatGPT and a Codex folder on the same ChatGPT account share one limit, and both cards say so. Free models and other API keys have no known windows. A Console key without Go stays Zen; an expired Go key asks for Replace key. The common billing group on the page is OpenCode Zen / Go.
- An account whose limit nothing tells (OpenCode Zen, Copilot signed in on the machine; BTN-342) shows what is known instead: its tokens from Tally, cache included, since local midnight and over the last 30 days (`/api/stats/tokens`, `docs/stats.md`; the "Today" and "30 days" columns of the account row, a line each in the account's summary, `AccountSummary` in `web/src/layout/AccountLevels.tsx`; the group head says "No limit to read: the tokens are from the statistics." in its help tip beside the count, BTN-1379), and "last refused by its limit …" once a chain session hit it (`AccountEntry.lastLimitAt`, from `LimitRetries`, in memory since the start). Tokens, not dollars: Tally prices neither the free models nor Copilot's. On such a limit the chain tries again with a growing wait (`docs/chain/exceptions.md`, exception 1). No numbers of the free models' limits anywhere: OpenCode publishes none and the list of free models changes.

## The Copilot folders (BTN-215)

- Only added ones, under `~/.copilot-accounts/<name>` (`EVEN_KEEL_COPILOT_ACCOUNTS_DIR`), each a `COPILOT_HOME` (`src/copilot/home.ts`): config, `mcp-config.json`, `session-state/`. Even Keel adds each project's checkout to `trustedFolders` of its `config.json` before a turn, so the repository's hooks run (BTN-645, `docs/sessions/copilot.md`). `~/.copilot` is not listed: it is the user's own Copilot, as `~/.local/share/opencode` is OpenCode's. Names are unique across all four roots.
- **The machine sign-in.** `copilot login` normally keeps its token in the OS credential store under `copilot-cli`, with a plaintext fallback in `config.json` if the store is unavailable ([GitHub's authentication reference](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli)). The CLI can fall back to `gh auth token`. Before reading that fallback, Even Keel asks the same CLI binary with the session's `COPILOT_HOME` and environment for `auth.getStatus` over `--headless --stdio` (`src/copilot/machine.ts`, `machineToken`). Only an authenticated `gh-cli` answer for GitHub.com permits `gh auth token --hostname github.com --user <the CLI's login>`. An own OAuth sign-in, another host or an unreadable answer stays unavailable; no different account is substituted. Tokens exist only during the allowance request, never in logs, state or a token cache. So there are two ways in (`SIGN_INS`):
  - `none` — "This machine's sign-in" in the add dialog makes the folder at once (named `copilot`, `copilot-2`…): its sessions run on the CLI's sign-in available in that folder. `CopilotCli.authStatus` asks `machineSignedIn` with the same binary, `COPILOT_HOME` and environment as sessions. Explicit `isAuthenticated: false` marks it signed out and true confirms sign-in. An unavailable CLI, timeout or unreadable/empty/missing status gives `AccountStatus.loggedIn: null`: the card says "Could not check" and launches remain allowed (EKR-84). Every refresh, including after restart, checks again and replaces the previous verdict. Its card reads the allowance only when the CLI confirms its GitHub CLI fallback; otherwise it has no allowance. A signed-out folder gets `Agent.terminalLogin`, exposed through `AccountEntry.terminalLogin`: the problem band shows a copyable command instead of a web sign-in button. Run it on the service machine as the service user: in cmd on Windows, standard sh on Linux/macOS. The command removes `COPILOT_GITHUB_TOKEN`, `GH_TOKEN` and `GITHUB_TOKEN` in a child cmd or sh subshell, sets the selected `COPILOT_HOME` and runs the sessions' binary; the original terminal environment survives success, failure and repeat execution. Without a keyring the CLI asks about plaintext storage in that folder's `config.json`; a piped web login cannot answer this prompt. No web terminal, separate recheck button or copying from `~/.copilot` is involved. A folder's own Even Keel token keeps its priority and key checks. Partial live checks and remaining service/login checks are recorded in [verified](../verified/copilot.md) and [unverified](../unverified/copilot.md#copilot-folder-sign-in-refresh-ekr-73).
  - a token (`account/api` with `agent: "copilot"`) — a fine-grained PAT with the "Copilot Requests" permission (`github_pat_`) or an OAuth token (`gho_`, `ghu_`); a classic `ghp_` token is refused (`account.copilotTokenInvalid`), since Copilot refuses it too. It is kept in the folder's `even-keel.json` and handed to every turn as `COPILOT_GITHUB_TOKEN`, which beats the stored sign-in, so each such folder is its own GitHub identity. It counts as a key: checked with `GET https://api.github.com/user` before the folder is made and hourly after (`checkGitHubToken`; 401 or 403 is `account.copilotTokenRejected`, anything else `account.copilotTokenUnchecked`), a refused one makes the account `needsLogin`. Default folder name `github`.
- **The monthly allowance** (BTN-341, BTN-520). Copilot's budget is AI credits or premium requests, which the CLI does not tell outside its interactive footer. A token folder has its month read from GitHub (`copilot_internal/user`, else the billing API, which needs the token's "Plan" read permission; the card names it when it is missing) and shown as one bar, "N left, resets on the 1st", or the requests used when only the billing API answers; the drawer's narrow column shows what is left as the bare number, its hint says "N left". Extra-usage permission and net billing spend are described below. A confirmed machine fallback reads `copilot_internal/user` directly, without an editor-identification header or a model-token exchange. This source and the adapter's allowance were [checked in Windows session 0](../verified/copilot.md) with CLI 1.0.105 and the checked 1.0.98; own OAuth sessions were also checked on Windows and the Linux plaintext fallback, with no allowance by design ([verified](../verified/copilot.md)). Linux systemd/keyring access, macOS OAuth and other sources remain [unverified](../unverified/copilot.md#copilots-machine-token-and-model-availability-btn-516). Though a token folder counts as a key, it is polled like a subscription (`Agent.keyUsage`), and a spent budget or a limit waits for the month's reset, not for a credit check (`CREDIT_CHECKS` never learns anything for a GitHub token). No Tally figure on the card: Tally prices a Copilot call at the model's API price, not at its credits.
- **Linux plaintext sign-in** (EKR-48, CLI 1.0.105). Without a keyring, plaintext OAuth stays in the account's `COPILOT_HOME`. Login without that variable saved into `~/.copilot/config.json`; the managed CLI reported unauthenticated while its card still said signed in (EKR-73). Interactive login with the managed folder saved there and let a whole chain task complete. The user observed that login without a terminal did not save the token or ask about plaintext. See the [setup workaround](../guide/setup.md).
- **One free account.** GitHub's terms allow one free account per person, and Copilot Free comes with it. Even Keel cannot see a token's plan, so unlike Codex it does not check: several tokens are for several paid seats or several people's own accounts, not to get round one free budget.
