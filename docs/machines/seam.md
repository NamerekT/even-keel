# The seam and the chain over the link

`MachinePort`, one process, the machine's context, the briefs and stores, the chain over the link and its moves. The words (own machine, machine elsewhere, mirror, brief) are in the index's table, [`docs/machines.md`](../machines.md).

## The seam

One installation is a hub and a machine in one process, and there is one code path: the chain (`src/chain/`) reaches sessions, accounts, packages and working folders only through `MachinePort` (`src/machine/port.ts`), which `DispatcherDeps.machine` carries. The chain is given the hub's side of the port, `RemoteMachine` (`src/machine/remote.ts`); the machine's own implementation is `wireMachine` (`src/service/machine-chain.ts`), run behind `MachineRunner`. `wireDispatcher` (`src/service/chain.ts`) builds the hub's side and takes the port as an argument.

| Side | In the chain | In the service's assembly |
| --- | --- | --- |
| Hub | `Dispatcher`: order, the queue and its fill, pauses, skips, released and shelved tasks, the launch of a task (`startTask`, `inTurn`, `src/chain/start.ts`), the skip of a quiet session (`unanswered`, `quietTooLong`, `src/chain/quiet.ts`), `MainCheck`, `MainFix`, `MainWait`, `MainCarry`, `Reviews`, `TaskLists`, `Cleanups`, `Unchanged`, questions to the tracker, the hub's side of the moves (`taskMoves`, `src/machine/tasks.ts`); the rest of `DispatcherDeps` and `MainCheckDeps` (`hubMainDeps`): projects, rules, `parallel`, the chain's state, statuses and comments in the tracker, the CI of main, PR mode | `src/service/hub-bootstrap.ts`, `src/service/chain.ts`: the state database, tracker and CI profiles, projects and settings, the page, Tally |
| Machine | `src/machine/`: the moves of a task's session ("Moves") — `MachineMoves` (`moves.ts`) running `Handovers` (`handover.ts`: limit, resume, relay, checkpoint, answer, "New session", a returned task) and `OverageStops` (`overage.ts`), the git and check side of the CI of main (`mainMachineDeps`, `main.ts`) | `src/service/machine-bootstrap.ts`, `src/service/machine-chain.ts`: accounts and limits, packages and the MCP gateway, slots and worktrees (`wirePlaces`), the session monitor, the launch journal for the slots' occupants, keep-warm |

- **A member of the port** is a command, a query or a snapshot field; the comment of each in `port.ts` says which. A command (`launch`, `stop`, `finish`…) is a numbered command of the link with its result as an event; a query (`locate`, `head`, `merged`…) goes the same way and changes nothing on the machine; a snapshot field (`liveSession`, `busy`, `limited`…) is read from the hub's mirror of the machine ("The mirror", `pool.md`).
- **An action of both sides is the hub's decision and one call of the port.** A red main: `MainFix` decides, `stop` stops. The cleanup after Done: `Cleanups` decides and records the closed task (`archiveClosed`), `finish` stops the sessions and removes the folder. The report of a red main: the hub writes it, `history` gives the commits.
- **Every touch of a session is the same exception to invariant 1 as before** (`docs/chain/exceptions.md`), made on the machine's side.
- **The page, the hooks and the chat** reach the machine through `MachineServices` (`src/machine/services.ts`, BTN-1241), never its objects: account controls, transcript reads (a session's record, feed, pictures, inbox and shared files, the handoff note, the checkpoint's context), the chat's commands and the initial records ("The chain over the link"). The page's state of the machine's sessions and accounts reads the mirror.
- **A transcript read goes to the session's machine** (`MachineLink.transcripts`, `src/service/session-transcripts.ts`, BTN-1574): the machine whose mirror shows the session, else the machine its launch ran on (`LaunchEntry.machine`, else the one the task's other entries name, else the task's `machine_tasks` row: Done releases that row, BTN-1800), else the machine of the project chat it is the session of (`chats.machine_id`, archived chats too: BTN-1794), else the own one. The machine finds the transcript by the session's id in its account folders, with no binding to a chat or a task. A machine elsewhere off the link answers `machines.transcriptOffline`, never "not found", and the own machine never searches its account folders for a session another machine holds.
- **A machine elsewhere without its link** follows and guards the tasks the hub gave it by itself, on the hub's last word ("Moves without the hub", BTN-1226); every other decision waits for the hub.

## One process

`wireLinkedMachine` (`src/service/machine-link.ts`) assembles both roles of an installation: `HubEnd` over the state database, `MachineEnd` over the machine's own database (`wireMachineSide`, `src/service/machine-side.ts`, the same assembly a machine elsewhere runs over HTTPS), and `LocalTransport` (`src/link/local.ts`) between them. The ends call each other, without HTTPS and a certificate, with the same numbers, confirmations and snapshot; what passes is carried through JSON, so both sides see what a machine elsewhere would. A single installation has no other path. The pulse is `LOCAL_HEARTBEAT_MS` (10 days): there is no network to lose.

- **The own machine** (`ownMachine`, `src/machine/own.ts`) is made at the first start of a version that has machines: a row of `machines` named after the host, a token whose secret is kept in the machine's database (`identity`), its id in `service_state` as `machines.own`. Every later start finds it again.
- **When the two databases no longer agree** — one folder restored or removed — a new own machine is made and the old one revoked; `storeToken` empties the machine's outbox and command numbers with the old token. The old own machine's rows of `project_machines` (turned on or off, its own settings, `after_green`) go to the new one, so a state database restored on another host keeps its projects running there; the tasks of `machine_tasks` stay with the revoked machine, for a person to move ("A machine gone", `landings.md`).
- **Consent** to the installation's own projects, each in its folder, is given at the start and before a step of the chain after the projects changed (`agree`); a project gone from the config is served no longer. The same moment puts the own machine into the pool of every project that has none (`fillPool`).
- **Commands the process before kept** and its machine never took are dropped at the start: nothing waits for their result, and a launch among them would start a session the chain did not ask for again. A command the machine took and did not finish is reported as `command.interrupted`, found without a waiter and logged; a launch it began is found by the chain's own recovery of a `starting` task.
- **Moving an installation of the version before** needs nothing by hand: the state database stays the hub's, accounts, packages and slots stay where the machine's code reads them, the own machine and its consents are made as above, and the chain's state is not touched — live sessions are picked up and the current task stays current.

### The order at the start

- The port is built first, the dispatcher on it, and only then is the machine connected (`LinkedMachine.start`): the machine's facts read the chain's state.
- `start` waits for the first snapshot; until it is in the mirror `sessionsRead()` and `accountsRead()` are `false` and no chain steps.
- Before the monitor, hooks and chat start, the link drains the retained outbox, and the hub reads its own `launches`, `session_windows` and `mailbox` and hands them to the machine by the command `records.restore`. Records replayed from the previous process must be included in their initial state, including the mailbox's next id.
- The mailbox gets only the machine's own messages (`loadMail(db, machine)`): its settling (`settleMail`) would otherwise give back to the chat another machine's waiting messages, whose sessions it does not have.
- With them go the sessions of the machine's active project chats (`loadChatSessions`, into `ChatSessions`): a Claude chat's session has no name to be found by (BTN-1772, `docs/sessions/project-chats.md`). A machine elsewhere gets them, with its mail, at each connection (`handMail`).
- The machine never reads the hub's database: its mailbox is made empty (`Mailbox.detached`) and filled by that command, and its launch journal (`MachineRecords.journal`, read by the slots' occupants, the stops, the accounts of its sessions and what it tells the hub) keeps the launches made before it, each once.
- A machine elsewhere's journal (BTN-1803): at each connection `handMail` hands it the hub's entries naming it (`machineJournal`, `src/machine/records.ts`): every entry of each task it ran in the last `MACHINE_JOURNAL_DAYS` (14) or holds now, not the whole archive. A launch the hub's chain makes there is the hub's record, kept through the hub's own machine's outbox; the machine gets it at once by `records.launched` (`MachineNetwork.launched`), never sent back. One offline then gets it with the journal at its connection.

## The machine's context

BTN-1246: the machine's assembly — `wireMachine`, `MachineRunner`, `wireMachineServices`, the places, keep-warm, the task folders (`TaskWorks`), the found repositories (`GitFound`) and the cleanup's lingering sessions — runs on `MachineContext` (`src/service/machine-context.ts`), never on `ChainContext`.

- **The host's objects** (`MachineHost`): accounts and limits, the session monitor, agents, daemons, packages, the mailbox and the launch journal. `assembleMachineHost` (`src/service/machine-host.ts`) builds them with the machine's `MachineContext` for both processes, the service and a machine elsewhere. Their assembly reads `MachineContext`, including the account watcher, monitor, CLI checks and approvals (BTN-1250). The account folders open on the machine database. `PackageHub` is a separate hub object: it owns the credentials, OAuth, tasks and memory servers; the machine's `Packages` has no tracker profiles or hub database.
- **What only the hub knows** comes in the hub brief ("The brief") and is read from the machine's copy (`BriefCopy`, `src/machine/brief.ts`): the config with the machine's projects and their folders, the tasks' own runs, the trackers' task lists, the chains' current tasks, the demo's projects, `unattended`, `trimTools`, the sessions keep-warm pings and the check reports. Over it the machine builds its own `choiceFor`, `planFor`, `agentExtras`, `settingsFor`, `withProject`, `branchOf`, `promptLanguage`, `projectOf` and `taskNote`; the hub keeps its own `choiceFor` for its changelogs and packages.
- **What the machine tells the hub** besides the chain's results is an event of the link (`MachineTell`):
  - `task.leftover` — what a cleanup finished late left on a task (`stopLingering`), which the hub puts on the task's row (`Dispatcher.leftover`);
  - `transcript.changed` — a watched transcript changed, signalled to the page;
  - a change of the task folders or of a found repository has the machine post its facts;
  - `machine.selection` — the CLI choice and its fallback, kept locally first; account activation and filling the accounts' empty shared pool use the same event. The hub applies them to its settings and sends them back in the next brief; a changed CLI choice of the hub supersedes a local fallback;
  - `sessions.read` — the monitor caught up, so the hub settles the mail; the monitor never reads the dispatcher for that.
- The hub writes the stop of a session into the event log on the `stop` command's result, and adds where a launch's task is read from (`withSource`) when it saves the machine's `launch.record`.

## The brief

The hub brief is the command `hub.brief` (`BRIEF_COMMAND`, `HubBrief`): what the machine's assembly reads of the hub, whole each time. `hubBrief` (`src/service/hub-brief.ts`) builds it.

- **When it goes.** `BriefSender` sends it when it differs from the one the machine took (`sameJson`), and again after a failed send or a new connection (a new process of the machine holds none). The own machine's goes at every catch-up. A machine elsewhere's goes at the connection, after an attachment to a project and at the service's 5 s publishing tick (`MachineNetwork.catchUp`), never inside a chain step's catch-up, so a step never waits on a machine elsewhere.
- **Before a command that rests on the task's run** (BTN-1514): `launch`, `launchFix`, `launchCarry`, `relay`, `resume`, `modelBlock` and a move that may start a session, `RemoteMachine` awaits `briefNow`, which sends the brief if it changed (a no-op otherwise) and waits until the machine took it. Otherwise a run set just before `chain/start` would reach a machine elsewhere only at the next tick, and the session would start on the project's model. The own machine has the same `briefNow`, though its step's catch-up mostly covers it.
- **Taken at once.** The machine takes the brief before the command's first await, so a command after it reads the new one even when run side by side.
- **Before the first brief** the machine holds an empty config, and its `accountsRead()` is `false`: no chain steps. The start waits for the first snapshot and sends the first brief before it restores the records; the projects without git are read for a repository once it comes. The brief goes before the facts, so a check report or a run just set is on the machine when the step reads it (freshness: "The mirror", `pool.md`).
- **Folders.** The brief's `config.projects` holds only the machine's projects, each with its folder there: for the own machine the installation's own folder of each project (`agree`), for a machine elsewhere the pool's folder (`project_machines.folder`, else `folderUnder(root, repo)` inside the root its report names).
- **Memory** (BTN-1648). A machine elsewhere's brief carries `memory`: its folders the hub's owner bound to projects' memory beyond its pool (`MemoryFolders.of`), only of the hub's projects. The machine keeps them and its pool's folders as working copies of the hub's memory repositories (`MachineMemory`, `docs/sessions/memory.md`).
- **The rest it carries** — the active projects and whether each is paused, for the sign-in guard (`loginBlock`: the launch account is not signed in again while a chain runs on it), the tracker MCP requirements, `hubServers` (route names only, "MCP through the hub", `link.md`), the catalog (`packages`, the same section), `accounts` ("The project's account on a machine", `pool.md`) and `cliConsent` ("The checked CLI", `elsewhere.md`).

### The launch brief

BTN-1238. `RemoteMachine` prepares a task's text on the hub and sends it as the fourth argument of `MachinePort.launch`; the machine's `Briefed.apply` adds and retains only this received data, without reading a tracker.

- **What it holds** (`LaunchBrief`): `prompt` — the tracker location, vocabulary and task text (or the instruction to read it); `task` — the structured `TaskBrief` for answers without the hub ("The hub away", `link.md`); `own: true` — `Intake.outsider` says the task is not an outsider's, asked at every brief (BTN-1419), so the machine pushes its branch without the guarded files check (`docs/chain/worktrees.md`); `restore` for a task moved off a machine gone ("A machine gone", `landings.md`). A later launch without task text clears the old structured brief.
- **With a move.** The hub also sends a brief with a direct `relay` or a session move that may hand off (`MoveContext.brief`), so a handoff after a machine restart still has the task's text. A move names its task in `MoveCall.task`, which the hub prepares the brief for and routes the move by. An explicit handoff prepares it anew; a regular `follow` reuses the hub's prepared brief, reading it once if the hub restarted, so a waiting limit does not poll the tracker for its text. Replies and paid-usage guards need no brief.
- **Kept.** Without a new payload a handoff uses the machine's retained brief (`launchBriefs`, also read by the tasks server); each in-memory cache holds at most 200 tasks and does not survive its process restart.
- **Missing.** With neither, `apply` throws `chain.briefMissing` for a chain task (a fix or carry session has its report instead) and the chain pauses (BTN-1252): a launch before its session starts, a handoff before it stops the session it replaces, never a prompt without the task.

## The machine's stores

The machine's own database is `state/machine/` (`MACHINE_STEPS`, the tables of the link's steps in `link.md`, "The stores"). Since step 3 it keeps the account folders' `account_limits`, `account_settings` and `machine_state` (`cli.downloaded`). Step 4 (schema version 6, BTN-1250) adds `global_accounts`, `key_organizations`, `management_keys`, `left_folders` and `context_windows`. `machine_state` also keeps `cliCheck.history`, the pending `accounts.adoptLegacy` marker and the local CLI choices (`cli`), and on a machine elsewhere the hub's last word for its moves without the hub, `moves.held` and `brief.kept` ("Moves without the hub"). Approvals stay in memory, configured by the brief; there is no approvals table.

- **The import.** `importMachineStores` (`src/machine/state.ts`) imports the first group once under `stores.imported`, and the second under `stores.hostImported`, so an installation that already passed the first import still gets the second. Each group is transactional, retains existing machine rows and leaves the old hub rows untouched. Later starts read only the machine rows. The frozen machine sample is `test/fixtures/machine-v6/machine.sql`.
- **Not in the backups.** The hub's automatic backups leave the machine's state out: preserve this folder with the service stopped when moving an installation.
- **What stays at the hub.** `key_spends`, for statistics: a machine emits `key.spend` with each measured growth, and the hub commits it and the event's receipt together, so a lost confirmation cannot add the same growth twice. `warm_pings` the same way: a machine emits `warm.ping` with each answered keep-warm ping (BTN-1413). `task_retries`: the idempotency journal of the hub's `tasks_create` executor, including writes queued by a machine; no machine reads it.

## The chain over the link

`RemoteMachine` is the hub's side of the port, `MachineRunner` (`src/machine/runner.ts`) the machine's.

- **A command or a query** is the link's command `port.<member>` with `{args}` as its payload and `project` and `folder` in its own fields: the project of the call, and the session's folder (`resume`, `reply`, `relay`, `stop`, `locate`) or the working folder (`changes`). The machine runs it on its local port and answers with the event `command.done` — `{seq, value}`, or `{seq, notice, cause}` when the handler threw: the chain branches on message codes (`cliCheck.busy`, `slot.*`), so a handler's error is a result, not `command.failed`.
- **The call waits** for the event that names its number. A project's steps go one at a time (`Dispatcher.work`), so a project never steps twice while it waits. The machine takes commands in order and runs their handlers side by side (`MachineOptions.concurrent`): a check of main or a launch does not hold a stop or a query of another project.
- **`command.interrupted`, `command.failed`, `command.refused`** reject the waiting call with `machine.commandInterrupted`, `machine.commandFailed`, `machine.commandRefused`: the chain's own error branches pause it, and nothing launches again. A result nobody waits for (the hub restarted) is a line in the log.
- **A handoff snapshot** (`src/chain/snapshots.ts`) is the machine's event `handoff.snapshot`; the hub keeps it in the state database (`handoffs`). A save that fails leaves the event with the machine, which brings it again.
- **Every touch of a session** is made by the machine's local port: the list of `docs/chain/exceptions.md` is unchanged.

### The services

BTN-1241: every member of `MachineServices` is the command `<group>.<member>` — `account.*` (the page's `AccountControl`), `transcript.*`, `chat.*`, `records.restore`, `records.launched` (BTN-1803), `git.identity` (BTN-1503, the machine page's commit author), `history.task` (BTN-1561, "What a machine elsewhere tells", `elsewhere.md`) — with `{args}` and its value in `command.done`, as for `port.*`. A member left out of `SERVICE_COMMANDS` fails the build.

- `chat.steer` carries the session's project and folder, `chat.saveInbox` the project and the working folder: the machine refuses them outside its consents.
- A file goes whole as base64 inside the JSON (`CarriedFile`), both ways: a picture or a file of the transcript to the page, a reply's files into the session's `.temp/inbox/`.
- The checkpoint hook answers on the hub: only the session's context and its compaction point come from the machine.

### Journal, session records and chat

BTN-1219, `src/machine/records.ts`. Live session views and chat delivery state travel in the facts ("The mirror", `pool.md`); what is kept goes as records.

- **The records.** `MachineRecords` sends `launch.record` (`LaunchEntry`), `session.windows` (the monitor's changed `[sessionId, size]` pairs with their observation time) and `chat.mailbox` (complete changed `Mail` rows and the producer's optional retention cutoff). `Mailbox` keeps its immediate claim/settle behaviour but publishes typed changes, never SQL.
- **The hub's writes.** The hub awaits the writes to `launches`, `session_windows` and `mailbox`; its journal in memory and the event log update after the launch is committed.
- **Mail by machine.** The hub keeps the sending machine with each `mailbox` row (`machine_id`, BTN-1251): the cutoff removes only that machine's old settled rows. Each machine numbers its own messages, so a row's key is its machine and its number (step 62, BTN-1284): two machines' messages of the same number are two rows, and a machine's change never reaches another's. The own machine takes the rows kept before rows knew their machine (`adoptMail`, at `LinkedMachine.start`, before its replayed records).
- **Only forward.** A row's `fate` moves only forward (`waiting` to `delivered` or `returned`, `returned` to `dismissed`), so a late or repeated change never brings a settled message back.
- **A receipt is part of the write.** `saveMachineRecord` locks the machine's row and commits the record with `machines.last_event` in one transaction. A retry at or below that number writes nothing, even after a restart between the commit and the link's separate confirmation. A failed write rolls back both, leaving the event in the outbox. The tables keep their existing layout.
- **Closing the local link** drains the writes into its outbox and attempts their delivery before closing its database.

## Moves

A move of a task's session is what the chain does to the session it already has (BTN-1221): the limit and the temporary model error (resume or handover), the checkpoint, a move a restart cut short, the user's answer and the feedback on a pull request (`deliver`, `deliverLoose`), "New session" (`renew`), a session restarted (`replace`), a returned task and the fix's handoff (`handOverCurrent`, `handOver`), and the stop on paid usage (`guard`). The machine makes them; the hub decides when.

- **The command** is `task.<move>` (`src/machine/move-call.ts`, `MOVES`) with a `MoveCall`: the project, the task as the hub holds it (`CurrentTask`), whether it is still the chain's current task and whether the chain is active, the move's own arguments, and `MoveContext` — what only the hub knows: `blocked`, the prompt language, the main branch, PR mode, a project without git and the report of a fix or carry session.
- **The machine** (`MachineMoves`, `src/machine/moves.ts`) runs the same `Handovers` and `OverageStops` code over its local port and a copy of the task. Their `save` — the task's state kept before the session is touched (`starting`, `move`, `answering`, `reply`, `ask`) — is the event `task.state`, sent in order before the result. The result in `command.done` is `MoveDone`: the move's value, the task's move fields after it and a pause of the chain (`halt`, with `keep` for a refused model). The memory of the moves — the retry ladder of temporary errors and the sources of a handoff after a session that never answered (BTN-650) — is the machine's, shared by all moves; the launch journal goes through the outbox as for any launch.
- **The hub** (`HubMoves`, `src/machine/tasks.ts`) copies the move fields (`fieldsOf`/`applyFields`: `sessionId`, `resumedAt`, `limit`, `starting`, `move`, `answering`, `reply`, `ask`, `message`) from `task.state` and the result into its `CurrentTask` and saves the chain's state. A link error (`machine.command*`) pauses the chain, or for an answer leaves it undelivered, as a failed move would.
- **Only when there is work.** `follow` is sent when the mirror shows the machine something to do — a refused model, a move under way, a limit held or hit, a checkpoint (`followDue`); `guard` when there is a hold or evidence of paid usage (`guardDue`). Otherwise a step would send a command per chain.
- **In tests** a port without `moves` (the dispatcher's fake ports) has `taskMoves` run the same code in the hub's process; the service always goes through the link.

### Moves without the hub

BTN-1226. Only a machine elsewhere moves on its own: `wireMachineSide` with `alone`, which only `src/machine-service.ts` passes; the own machine never loses its link.

- **What it keeps.** The hub's last move call of each task of an active chain (`HeldMove`: the task, its `MoveContext` and `base`, the move fields the hub is known to hold) and the hub's last brief, in `machine_state` as `moves.held` and `brief.kept`. Both are read back at the start before the link's (`MachineMoves.start`, `BriefCopy.keep`); a kept brief is not `received`, so the hub's own still comes before a chain step.
- **When it moves.** While the link is not `online`, every `ALONE_TICK_MS` (15 s) it makes a step's guard and follow of each held task by its own facts (`followDue`, `guardDue` over its local port), as long as its newest brief has the task as its project's current one of a chain not paused. One move of a task at a time, the hub's and its own.
- **What the hub gets.** The end of such a move is `task.state` with `alone` and, when it paused the chain, `halt`: the hub takes the fields into the task and pauses the chain as on its own move's result, and the machine makes no more moves of that task until the hub's next call.
- **No move twice.** The hub's next step follows from the fields it took, so a continuation made without it is not made again; a call of the hub that still holds the task as before (`base`) goes on from the machine's state instead.
