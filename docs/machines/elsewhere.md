# Machines elsewhere

The hub's door for machines (BTN-1242; the page's window of machines is BTN-1056, the machine's own service BTN-1247). `MachineNetwork` (`src/service/machine-network.ts`) is a second `HubEnd` over the same store, serving every machine but the hub's own (`HubOptions.admits`), behind the HTTPS carrier of `hub-server.ts`.

- **The setting** "Hub address for machines" (`machinesAddress`, shared, empty by default): the name or IP machines reach the hub by, a port after it when a router or proxy forwards another one. Set — the hub listens on all interfaces at `EVEN_KEEL_MACHINES_PORT` (4749, read at the start); empty — it does not listen, and no string can be issued. It applies live: a change of the address changes only the strings issued from then on. The page offers the names of `allowedHosts`, the addresses of the network cards (no loopback, no link-local, with the card's name) and `EVEN_KEEL_HOST` when it is no wildcard (`machines/addresses`). A name behind a proxy works only if the proxy passes the machines' port too.
- **The connection string** is the token of "The token and the certificate", issued with no machine yet joined: good for `INVITE_MS` (30 min) and for one join. `HubEnd.invite` revokes every string issued before and never joined with ("Issue again"); `revoke` takes a string or a joined machine back. The machine sends it once, to `POST /link/join` with `{api, about}`, and gets its own secret in exchange (`{secret}`); the string's secret works for nothing else — a stream or a post with it is refused `token` — and a second join with it is `used`, a late one `expired`.
- **The request by the address** (BTN-1620), the way the window offers first: `even-keel join <address>` or `install --machine <address>` takes the hub's address for machines instead of a string (`addressOf` in `src/machine/join.ts`, the port of the link, 4749, by default; a line starting `ekm1.` is never an address). The machine draws a 128-bit nonce and posts, without any token, `POST /link/request` `{api, about, nonce, public}` → `{request, expiresAt}`, or the refusal `busy` (a request from this socket address already waits) or `full` (`MAX_WAITING`, 5, wait), both HTTP 429. It prints the code and asks `POST /link/request/answer` `{request, nonce}` every 2 s: still waiting, `{machine, secret}`, `declined` (403) or `expired` (410); a secret goes on to the usual `/link/join`, so everything after it is the string's. **The code** (`joinCodeOf(fingerprint, nonce)`, `src/link/join-code.ts`) is scrypt (N = 2^15) of the certificate's fingerprint the machine saw and its nonce, cut to 30 bits and written in Crockford's alphabet as `XXX-XXX`; the hub computes it from its own certificate. A machine that checked the certificate as a public one (`public`, behind a proxy) puts an empty fingerprint on both sides, the nonce alone. The slow hash keeps a man in the middle from fitting his own nonce to the same code within the 10 minutes. `JoinRequests` (`src/link/join-requests.ts`) keeps the requests in memory only, `REQUEST_MS` (10 min) each, so a hub restart answers `expired`; one per socket address — behind a proxy every request comes from the proxy's, so one at a time. Admit is `HubEnd.admit()`: a one-time join secret, like a string's, that leaves the strings of the window in force (`invite` revokes them). The link's API is 21.
- **`even-keel join <string or address> [--root <folder>]`** (`src/machine/join.ts`) refuses, in order: a test instance (`EVEN_KEEL_TEST_INSTANCE=1` — the sandbox and bench kits set it, so no test installation reaches a real hub), a line that is not a string, a running service of the installation (the machine's database has one owner), an installation that has projects (it is a hub; a machine joins from a clean one). Then it makes the folder of projects, sends the report, keeps the new token and the root in the machine's database and writes `state/machine-link.json` (hub, machine, root, the time of the join). `even-keel status` prints that file.
- **The installer** (BTN-1243): `even-keel install --machine <string> [--root <folder>] [--service]` (`src/cli-args.ts`, `src/cli-install.ts`) refuses a Node older than 24 and a machine without git, joins in a child process (the tray start) or inside `install.sh`/`install.ps1 -Machine -Projects`, then installs the service; a checkout builds `build:machine` (no page). A string already joined with (`joinedWith`) is not joined again. `install-check.js --machine` waits for 10 s of a running process instead of the page, the CLI 30 s for `contactAt`; the tray shows the contact's age. `machines/invite` answers with `command`, `npx even-keel@<hub version> install --machine <string>`, and `byAddress` `{command, docker}`, the same two commands with the address written by `writtenAddressOf` (`src/link/address.ts`: the default 4749 dropped, 443 named). Guide: `docs/guide/setup.md`, "A machine of a hub".
- **Docker** (BTN-1440, guide `docs/guide/docker.md`, "Machines"). The hub's `compose.yaml` publishes 4749 at `${EVEN_KEEL_MACHINES_PUBLISH:-127.0.0.1}` (a Compose variable only). The templates `compose.machine.yaml` (service `machine`, the tag required) and `compose.hub-machine.yaml` (`even-keel` and `machine`, a volume each, one tag) share the image. Every service sets `hostname:` (`even-keel`, `even-keel-machine`; BTN-1496, held by `src/service/compose.test.ts`): a string issued without a name names the machine by `about.host` at the join (`HubStore.joined`), and the hub's own machine by `os.hostname()`, which Docker would otherwise make the container's ID. `machines/invite` also answers `docker` (`dockerJoinOf` in `src/cli-install.ts`): `EVEN_KEEL_IMAGE_TAG=<hub version>` and `docker compose run --rm machine even-keel join <string>`; the window's step 2 switches between npx and Docker (Docker first when the page's `updates.blocked` is `container`) and shows them with `docker compose up -d`. A hub in a container (`inContainer`) offers no network card in `machines/addresses`, its cards being the container's. The `machine` service sets `EVEN_KEEL_MACHINE=1`: `src/start.ts` then waits for `machine-link.json` (`waitForJoin`, 5 s) instead of starting a hub, holding nothing, so the join from `compose run` goes through and the process goes on as the machine. A machine in the hub's Compose project reaches it as `even-keel`: the pinned fingerprint makes the name irrelevant to TLS. Its report has `container: true`; `HubFollower` with `container` stays `manual` at the hub's version without a launch, and the machine's page replaces `even-keel update` (and the `manual` band) with the `.env` line, `docker compose pull && docker compose up -d` and `docker compose build --pull && docker compose up -d`.
- **The report** (`MachineAbout`, `src/machine/about.ts`): the host, the OS, the versions of Even Keel, Node and git, the agent CLIs found on `PATH` with their versions, whether git has a name and an email, the folder of projects. It goes with the join and with every handshake.
- **Projects.** The window "Add a machine" puts a joined machine into the pools of projects with the command `machines/join` (`{machine, projects: [{project, clone?, folder?}]}`, BTN-1263; `clone` absent — `auto`, the folder decides, BTN-1298): one step job of kind `machine-join` (`joinPlan`, `src/service/machine-pool.ts`) runs the steps of `connectPlan` ("Connect" above) for each project in turn, each step id `<step>@<project>` (`stepOf` in `src/jobs/model.ts`), the subject the machine's name. A failed step stops the whole job, and Retry goes on from it; Cancel takes back only the projects not yet turned on, so the ones already connected stay. `MachineNetwork.attach` (the folder named as the hub's under the machine's root, no checks) is left only to tests. The chain's tasks go to the machine by "The pool".
- **Each machine's own mirror** (BTN-1247). `MachineNetwork` keeps, per machine elsewhere, a peer: its own `RemoteMachine` (made by `remoteOf` in `machine-link.ts` with the same deps as the own machine's), its `BriefSender` and the folders of its pool. A snapshot of that machine fills its mirror, never the own machine's; its launches write its `machine_tasks` rows and its snapshots square them, as the own machine's (`assigned`, `released`, `held`). The chain reaches it through the peer's `port`, and the peer's `capacity` is read at each snapshot. An event goes to its `RemoteMachine` too, except three: `machine.selection` is only a line in the log (the hub's settings follow its own machine, not one elsewhere), `tasks.write` goes to `HubMcp.write` with the machine's id, and `sessions.read` sends its brief. A `/link/mcp` request goes to `HubMcp.relay` with the machine's id, so the pool decides what it may reach; going offline replans the limits. A revoked machine's peer is dropped.
- **The build** (BTN-994, BTN-1609). The hub compares a machine by the link's protocol, not by the version string: two checkouts both say `0.4.0-rc.1` across hundreds of commits. Another API version is refused at the handshake (`VersionRefusal`), and the hub stamps the API of each handshake into the report it keeps (`MachineAbout.api`, `withApi` in `src/link/hub.ts`), so it knows the protocol of a refused machine too. A machine on the link therefore speaks the hub's protocol, and `MachineNetwork.takers` and "after a green main" (`PoolAfterGreen.ready`) take it whatever its version or commit. `buildGap` (`src/service/machine-updates.ts`) names the gap: `protocol` — the card's lamp is blocked with "another build (Even Keel X): the hub does not take it" even while off the link (`MachineCard.otherBuild`), and the page has a warning band naming both protocol versions, with `even-keel update <hub's version>` for a package or the Compose steps for a container; `build` — another commit (a checkout) or version (a package) on the hub's protocol: it works, and the page's fact "Even Keel" carries a quiet tag "another build" whose tip names the hub's build (`MachinePage.build`, `MachineBuildView`). The CLIs are not compared: a machine takes its `cli.<provider>` from the brief and downloads a checked copy itself on the hub's consent ("The checked CLI" below).
- **Coming to the hub's build** (BTN-1609, `MachineUpdates` in `src/service/machine-updates.ts`). At each snapshot of a machine elsewhere (`MachineNetworkOptions.seen`) whose report names another build on the hub's protocol, the hub picks the target (`followTarget`: a checkout goes to the hub's commit, a package to its version, a container nowhere — Docker replaces it), waits until the machine's lanes are not starting, handing over or closing (`busyChains`, up to `SETTLE_MS`, as the hub's own update) and sends the link's command `update.follow` {build, force} (API 20, the group `update` of `MachineServices`), once per target and process. The machine hands it to its `HubFollower.asked`, which runs the same `follow` mode as a refusal (next bullet) and answers `null` when it moves or already runs that build, else its `MachineFollow`, which the hub writes into the report at once (`MachineNetwork.follow`). "Update" on the machine's page (`machines/update`, `machinePageControl.update`, offered while it is online, on the hub's protocol and not in a container) asks the same with `force`: a target an update already failed at is tried again; the answer is at once, the settle and the machine's answer go to the log. While a target is taken, the fact shows "updating to X" instead of the button. A stuck answer (`dirty`, `manual`, `failed`), a failed ask, or a report whose `follow` names a failed update to the hub's target is a line in the log and an entry of the event log opening the machine's page (`machines.updateFailed`, `machines.updateDirty`, `machines.updateManual`; place `{view: 'machine'}`). `service/rebuild.ps1` is not taught a machine's mode: the update goes over the link.
- **Catching up with the hub** (BTN-1275, `HubFollower` in `src/updates/follow.ts`). The `version` refusal carries the hub's commit (`commit`, HEAD of a git checkout read once at the hub's start, `headOf`) and its version of Even Keel (`evenKeel`); `MachineOptions.versionRefused` hands each refusal to the follower, which launches the update process at most once per process. A git checkout runs mode `follow` (`src/updates/runner.ts`): stop, `git fetch --all --tags`, `git checkout --detach <hub's commit>` — the hub's commit, not the newest `dev`, since the hub may have skipped a red one or rolled back; the branch does not move, a rollback puts it back — `npm ci` only when the lock changed, `npm run build:machine`, start, and the answer is a `contactAt` in `machine-link.json` newer than the run's start; a rollback waits for no answer, the hub would refuse the old version anyway. A global npm package installs `even-keel@<hub's version>` the same way. What keeps a machine where it is goes into its report as `MachineAbout.follow` `{to, stuck}`: `failed` (`logs/update.json` names a `follow` to this target that failed: the same commit is never tried again, only another one), `dirty` (tracked changes in the checkout), `manual` (no service manager, a package not installed globally, a hub without a commit for a checkout — it does not move by tag). The machine's page shows it as a warning band, and its fact "Even Keel" names a checkout's commit next to the version (`MachineAbout.commit`, "X · abc1234").
- **What a machine elsewhere tells** (BTN-1559, `src/machine/scope.ts`). Its session monitor reads every session of its account folders, and a computer that served a project before — a hub moved there — holds hundreds of old ones; told whole, they made the snapshot over the link's limit (`MAX_BODY_BYTES`, 8 MB). So `wireMachineSide` with `alone` wraps the runner's reads in `scopedDeps(deps, factsScope(…))`, computed once per pass: the facts name only a task the hub asks about (`briefAsks`) — one its brief lists open (`brief.tasks` less `brief.closed`: the lists hold the chain's archive of the last 7 days too, on a moved hub's computer hundreds of tasks it did, whose sessions read after the snapshot made a 10.5 MB `facts` event, BTN-1563), a chain's current one, a warm one, a fix, a carry or a chat (`isFixName`, `isCarryName`, `isChatName`) — one with a session not finished, and one whose session was active in the last `RECENT_MS` (24 h), which the cleanup after Done reads. Its sessions are their views and their journal's launches; `mailbox`, `owners` and `compactions` are cut to those sessions. The hub's own machine tells everything: its facts never cross the network. A task done more than a day ago on a machine elsewhere has no session view in the facts any more, so its history window does not name it.
- **Its brief** is `hubBrief` with the machine's own folders: for each project of its pool, `folderUnder(root, repo)` inside the root its report names. It is sent at the connection, after an attachment and at the service's 5 s publishing tick (`MachineNetwork.catchUp`), never inside a chain step's catch-up, so a step never waits on a machine elsewhere. The one exception is a command whose result rests on the task's run (BTN-1514): before `launch`, `launchFix`, `launchCarry`, `relay`, `resume`, `modelBlock` and a move that may start a session, `RemoteMachine` awaits `briefNow`, which sends the brief if it changed (a no-op otherwise) and waits until the machine took it. Without it a run set just before `chain/start` reached the launch only at the next tick, and the session started on the project's model. The own machine has the same `briefNow`, though its step's catch-up mostly covers it.
- **The checked CLI** (BTN-1516). A machine elsewhere has no page to give consent to a checked copy on, so the hub's consent is its: the brief's `cliConsent` is the hub's own `cli.downloaded` (`copies().consented()`, the own machine's), and a machine's `copies` (`CopyConsent.hub`) fetches a missing checked copy of a provider in it as of its own consent, at once when a new brief brings it (`resume` in `wireMachineSide`) and at every `blocked`; the copy it finishes is added to its own `cli.downloaded`. Its `agent.copyMissing` carries `downloading`, and the hub's `blocked` (`namedBlock`, `src/machine/block-names.ts`) turns it for a machine elsewhere into `machines.copyMissing` with the machine's name and a state: `downloading` (the wait ends by itself), `consent` (the hub has no consent: download its copy here, the machine follows, or Yours) or `failed` (the hub consented, the machine's download did not go through: its log). The own machine keeps `agent.copyMissing`, whose download the hub's page has. Both codes lift by themselves. A failed download on a machine elsewhere falls back to Yours there only, as every local choice (`machine.selection`).
- **The page's API:** queries `machines/addresses`, `machines/list` (`MachineView`: the report, online, the projects, a pending string's time, the folders another machine holds — `taken`), `machines/invite` (`{name, address?, color?, proxied?}` → `MachineInvite`: the string, the machine's id, its time and the command; an `address` other than the setting's is saved as `machinesAddress` first, through `ConfigStore.saveMachinesAddress`, and the door applied, so the window issues with one call; a `color` outside the palette is refused, a good one is stored as the machine's colour), `machines/admit` (`{request}` → `{machine}`, "The request by the address"); commands `machines/decline` (`{request}`), `machines/revoke`, `machines/join`, `machines/takeOver` ("The folder's mark"), `machines/login`, `machines/code`, `machines/cancel`, `machines/useGlobal` ("Signing in on a machine"). A change is the event `machines` (`LiveSource.onMachines` on the page); the machines' accounts are in the page's state (`machineSignIns`), and so are the waiting requests (`machineRequests`, `MachineRequest` `{id, about, code, from, expiresAt}`, sent as `state` at each change). A string issued with no name names its machine by the report's host at the join (`HubStore.joined`).
- **The window "Add a machine"** (BTN-1056, `web/src/layout/AddMachineDialog.tsx`, `MachineJoined.tsx`): opened by `?addMachine=new` from "+ Machine" at the foot of the machines panel; with one machine there is no panel, so the same button stands under the address in Settings → Interface until a second machine joins (`poolShown`). Step 1 is the address (`HubAddressField`) with the switch "Behind a proxy with a public certificate" under it ("Behind a proxy"), an optional name and the colour: the palette's swatches with the first colour no machine has (`nextColor` in `src/link/colors.ts`, `takenColors`) pressed until another is picked, sent with `machines/invite`; step 2 the command by the address first, then, under "Or with the connection string", the string's command (`CommandBlock`), its time, "Issue again" and the wait, read again from `machines/list` at each `machines` event; when the machine joins, the address becomes `?addMachine=<id>` and step 3 shows the report as checks (`machineChecks`: Node ≥ 24, git with a user, every agent the hub or the machine has), the projects to connect (under each one ticked, the folder field of "Connect" above, `MachineFolderField` with its state, by default the project's folder name under the machine's folder of projects; a taken folder keeps "Connect" off; "Connect" sends `machines/join` without `clone`, so each folder decides, and the job's window, `JobWindow` with its steps under a heading per project, replaces the list until Done) and the hub's subscription accounts with their gap on the machine (`machineAccounts`, signing in through "Signing in on a machine"). Closed while it waits, the window leaves the machine in `machineArrival`, and `MachineArrivalToast` offers to open it at step 3 when the machine joins, until the string expires. **The request window** (`web/src/layout/MachineRequest.tsx`) stands in every tab while `machineRequests` has one (`shownRequests` in `web/src/machineAdd.ts`): the report, the code to compare with the terminal, a count when more wait, Decline and Admit; the tab that admitted waits for the machine and opens "Add a machine" at step 3, and closing it without a decision hides the request in that tab only. `dev:fake`: `?addMachine=new` joins a fake machine 3 s after the command; `?machineRequest=1|docker|many` shows the request window, and Admit joins a fake machine 3 s later; `?machines=…&addMachine=machine-1` opens step 3 of the laptop, where connecting two projects or more fails the last one's push check; `machine-2`'s connects at once.
