# A machine elsewhere: sign-in, mark and process

## Signing in on a machine

BTN-1245: a machine elsewhere signs in through its own CLI, from the hub's page. Anthropic's terms keep a subscription's credentials where they were made, so nothing of the sign-in's result passes through the hub: the CLI writes its token into the machine's account folder, as for a sign-in on the hub.

- **What the page sees.** `MachineNetwork.signIns()` (`MachineSignIn`, `src/link/view.ts`) reads each machine's mirror: its accounts panel by folder — the key, the agent, the e-mail, whether it is signed in — its sign-in under way (`MachineLogin`: the link, a device code, the CLI's output, an error) and the agents whose CLI it lacks. The name is the hub's, read at each snapshot. The state carries it as `machineSignIns`; a change of a machine's mirror republishes the state, and the machine posts its panel at once on every change of its accounts (`machineChanged`), the sign-in's link included.
- **Where it shows** (BTN-1309). The accounts page's column "Machines", after "Used by" while `machineSignIns` lists a machine elsewhere (`AccountMachines` in `web/src/layout/MachineSignIns.tsx`): per hub account, a label for each machine whose folder holds the same agent and e-mail (`machineMarks`, `web/src/machineSignIn.ts`) — its icon and name in a quiet outline (`MachineLabel`, `web/src/ui/MachineLabel.tsx`, 24 px high as the chain's tag), the icon in words in its tip, opening the machine's page; a key before the name when it runs there only on a long token, "no Remote Control" in its tip; a dashed warning label when the folder there is signed out, whose press signs it in again in that folder (`machines/login` with `account`), greyed with a tip off the link. A hub long-token folder beside a full sign-in of the same e-mail gets no labels of its own. After four labels "+N" names the rest in its tip. A machine the account never signed in on is not named: "Add account" signs it in there (below). The column hides on a narrow screen with the row's other details.
- **The machine's accounts page** (BTN-1302, BTN-1570, `/accounts?machine=<id>`, `web/src/pages/MachineAccountsPage.tsx`): the hub's table (`AccountGroups` with `machine`) without the "Machines" column, the machine's label by the title: its accounts with "Used by", limits, extra usage, sessions and "Runs through" as its panel tells them, a signed-out one with an info chip "not signed in" and "Sign in" (`machines/login` with its folder as `account`), then the same gaps picked for this machine (`hubGapsOn` in `web/src/machineAdd.ts`, less a hub account whose folder there is signed out and so already a row), each with only the chip "signed in on the hub, not here" and "Sign in". "Add account" in the head opens the hub's window of adding with this machine picked ("Add account" below). Off the link both are greyed with a tip. With no row at all, the empty state carries "Add account" and says "has no accounts" once the machine's snapshot is in `machineSignIns`, "has not sent its accounts yet" before (`machineAccountsEmpty`). The machine's own folders have the hub row's menu — Even Keel, VS Code, Rename, Remove — done on the machine through `machines/account/*` (BTN-1584, [accounts](../accounts.md), "A machine's accounts").
- **"Add account"** (BTN-1308, `web/src/layout/AddAccountDialog.tsx`, `AddAccountPlace.tsx`): while `machineSignIns` lists a machine elsewhere, the window opened at the provider pick starts with "Where it signs in" — the hub or one machine, a machine off the link greyed with a tip; an opener naming the provider (setup, an agent's group) is the hub's and skips it. Picked is the machine of the page it opened over — `/machines/<id>` or the header's `?machine=<id>` — while it is on the link, else the hub (`defaultPlace` in `web/src/machineAdd.ts`); the pick is `?addOn=<hub|id>` (`placeOf`, `withPlace`). The hub goes on to its provider pick; a machine to its agents (`machineAddChoices`; one whose CLI the machine lacks is greyed with a tip), each one `machines/login` without `account`, the window closing for `MachineLoginDialog`. Claude instead opens the hub's choice of the way (BTN-1501, `MachineClaudeSign` in `web/src/layout/MachineClaudeSign.tsx`, the cards `SignWays` of `SignFields.tsx` with the hub's texts): "Full sign-in" goes on with "Sign in" to `machines/login`; "Long token" lists first "The same token as …" (the hub account's name) for each hub Claude folder on a long token not refused, not past its day and not already a token folder of the same name there (`sharedTokens`), a press sending `machines/sharedToken`, then "A new token" — the pick of the hub's Claude subscriptions not signed in there (`tokenAccounts`: the token is tied to one), the command and the field, sent by `machines/token`; with no such subscription the paste is replaced by a note.
- **The commands.** `machines/login {machine, agent, account?, method?}` (`MachineNetwork.login`) sends `account.renew` when the machine has the folder `account` (its signed-out folder of the same e-mail), else `account.add`: a new account in a `.pending-*` folder named after the e-mail once signed in. `machines/code {machine, code}` and `machines/cancel {machine}` send `account.code` and `account.cancel`. They are the machine's own `AccountControl` behind `MachineServices`, so its sign-in guards (a chain holding the account) apply there. A machine off the link refuses them `machines.offline` before anything is sent.
- **A CLI folder signed in but not added** (BTN-1568). A machine installed anew has its global Claude or Codex folder (`~/.claude`, `$CODEX_HOME`) hidden, as any installation has until "Add account" adds it (`docs/accounts.md`, BTN-543). A machine elsewhere (`options.alone`) reads those folders' sign-ins itself (`AccountWatcher.offerGlobals`, every 10 min and at once when the set of folders not added changes) and posts the signed-in ones in its panel as `globals` (`GlobalSignIn {key, agent, email}`, `MachineSignIn.globals`). A hub account of the same agent and e-mail that the machine lacks gets `MachineGap.global` (`machineGaps`): its row on the machine's accounts page, on its page and at step 3 of "Add a machine" says "signed in here, not added" with "Use it" instead of "Sign in" (`gapCommand`). `machines/useGlobal {machine, agent}` (`MachineNetwork.useGlobal`) refuses `account.unknown` when the machine's panel offers no such folder, else sends `account.useGlobal`: the machine adds it as the hub's own `account/global` does, checking the sign-in again. A folder of another account offers nothing. It is never added without the press, as BTN-543 decided: the chain would run its sessions in a folder the person may use by hand (VS Code), and the press is one click. The hub never reads its own hidden folders so. `dev:fake`: `?machines=global`.
- **A long token** (BTN-1002): `machines/token {machine, account, token, name?}` (`MachineNetwork.token`) sends `account.addLongToken` with the claude.ai account of the hub's folder `account` (`hubAccount`, read from the own machine's `identities`; none — `account.unknown`). The machine checks the token with one short turn and keeps it in a new folder (`docs/accounts.md`, "Long-token accounts"); a refusal comes back as the command's failure, under the window's field. The token is the command's payload, kept in `machine_commands` only until the machine takes it, and not logged. `machines/sharedToken {machine, from}` (`MachineNetwork.sharedToken`, BTN-1501) sends the token the hub's folder `from` already runs on: the hub reads it from that folder's `settings.json` (`hubLongToken` → `heldLongToken`, `src/account/longToken.ts`), so the page names only the folder and never holds the token; the machine's folder takes the hub folder's name and is tied to the account the hub's token was said to be of (its `sameAs` through `hubAccount`, else its file's `account`, else none and the machine matches by name, BTN-1512); a folder with no token there is `account.unknown`. It is the same path a pasted token takes, so the secret gets no new way out of the hub. The page offers the paste (`MachineTokenDialog`) from step 3 of "Add a machine" and a machine's own pages, and both ways from "Add account" on a machine (above), and marks a machine that runs the account only on a token with a key on its label in the "Machines" column, its tip "no Remote Control" (`machineMarks`; `MachineAccount.longToken`).
- **The window.** `MachineLoginDialog` follows the first machine with a sign-in under way, as `LoginDialog` follows the hub's: the same `LoginSteps`, with its commands turned into the machine's (`machineSend`). Closing it cancels the sign-in on the machine.
- **The code** the person types is a one-time authorization code that only the CLI holding its verifier can exchange: it goes as the command's payload, kept in `machine_commands` only until the machine takes it, and is never logged.

## The folder's mark

BTN-1244: a project's folder is served by one machine, whatever host and path reach it — a container, a network share, a second installation on the same repository. The machine that takes the folder writes `.git/even-keel-machine`, one line of JSON `{machine, name}`: its id and the name it knows itself by (the own machine's is its row's, the host's name; a machine elsewhere writes its host's). `GitFolderMarks` (`src/machine/marks.ts`) keeps it in the repository's common git folder, so a linked worktree shares its checkout's mark; a folder without git has none and is free; a mark that cannot be read is nobody's.

- **When.** The own machine claims each project's folder in `agree` (`src/service/machine-link.ts`), before it consents to it. A machine elsewhere claims at `projects.assign` and, at every start of its process (`MachineEnd.settleMarks`), again for every folder it consented to: one that got its git since is marked then.
- **Another machine's mark** leaves the folder without the consent. The machine's end keeps the holder by project (`MachineEnd.hold`) and refuses a command of that project with `command.refused` and the reason `taken`, the holder's id and name; `RemoteMachine` makes it `machines.folderTaken` (`{name, owner}`), and the chain pauses on it. An assignment refused so is the event `projects.taken` (`FolderTaken`); `MachineNetwork.holds` keeps it in memory by machine and project for `MachineView.taken`, named as the hub names the holder when it knows it, else by the mark. A machine that gives a folder up at its start because another took it over loses the consent too.
- **A mark of a machine this hub revoked** is free: the hub sends the assignment again with `takeOver` itself, and the own machine claims over it at once. That is how a new own machine (`ownMachine`) takes the folders of the one it replaced.
- **Off with the token.** A machine whose token the hub refuses (`token`: revoked or unknown) takes its marks off every folder it consented to (`FolderMarks.release`), once per run of refusals; another machine's mark stays.
- **Taking over** a dead machine's folder is explicit: `machines/takeOver {machine?, project, owner}`, after the page's confirmation, with `owner` the holder its refusal named; no `machine` is the own one. The hub checks that the holder it keeps for the project is still `owner` (else `machines.notTaken`, so a confirmed takeover never overwrites a newer mark), then the own machine claims with `takeOver` at the next `agree`, a machine elsewhere gets `projects.assign` with `{takeOver: owner}` in its payload. The pause stays until the chain is resumed. On the page it is `TakeOverButton` (`web/src/pages/TakeOverButton.tsx`, BTN-1261): under the pause `machines.folderTaken` through `noticeFixOf` (`{to: 'takeOver', owner, name}`), with a confirmation naming the machine that loses the folder, then `chain/resume`; a refusal (`machines.notTaken`) stays in the dialog. A machine's page (`/machines/<id>`, `web/src/pages/MachinePage.tsx`, BTN-1262) puts the same button, with `machine` and no resume, into the warning band of each of its `MachinePage.taken`.
- **A test instance** (`EVEN_KEEL_TEST_INSTANCE=1`, `folderMarks`) neither writes nor reads marks; `dev:fake` has no machine at all.

## The machine's process

BTN-1247: an installation that joined a hub starts as a machine. `src/start.ts` checks `state/machine-link.json` (`joinedHub`, written by `join`) and, when it is there, loads `src/machine-service.ts` instead of the state database's preparation and the service.

- **What runs:** `assembleMachineHost` with `planFirst` and its own `Writes`, then `wireMachineSide` over `httpsTransport` with the token kept in the machine's database (`storedHub`) and the report with its root (`storedRoot`), and the host's own starts and ticks of the service (monitor, transcripts' owners, limits, CLI versions and copies, the account watcher, VS Code, packages, keep-warm, CLI checks, the task folders). No state database, no page or its server, no trackers, no Tally database, no dispatcher. The gateway turns to the hub (`throughHub`) once the hub took the first snapshot, so the first brief may have named the hub's servers; then the machine's Tally collector starts and sends its rows over `POST /link/tally` (BTN-1280, `docs/tally.md`, "Machines elsewhere").
- **One per installation.** `holdInstallation` (`src/service/machine-process.ts`) claims `state/even-keel/` as the service does (`src/storage/claim.ts`) with a loopback port that only proves the process lives, so `join` and a second start see it runs; no `pgdata/` is made there, and `readStateDatabase` finds nothing. Without a kept token the process says to join again and exits 1.
- **`contactAt`.** `contactKeeper` writes the time of the last contact into `machine-link.json` when the link comes up, then at most once a minute; `even-keel status` prints it.
- **The sessions' hooks.** With no page here, `HookReceiver` (`src/machine/hook-receiver.ts`) listens at the page's address and carries the hooks' routes to the hub's page (BTN-1260, below, "Hooks through the hub"); the sessions' `EVEN_KEEL_URL` is its address.
- **What is not there yet.** The chain launches on no machine but the hub's own (BTN-993).
