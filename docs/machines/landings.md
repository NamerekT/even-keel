# The main branch, landings and losses

The main branch on machines, after a green main, landings across machines, a machine gone, account limits.

## The main branch on machines

BTN-1567: a project's main branch (`branch`, `docs/settings.md`) is one for its checkout on the hub and its folders on the machines elsewhere of its pool. `BranchControl` (`src/projects/branch-control.ts`) reaches those machines through `BranchMachines`, built on the hub by `branchMachines` (`src/service/branch-machines.ts`) from the machine network.

- **A save moves every folder.** A new branch saved on the page goes first to each machine of the pool turned on, the own one apart (its folder is the hub's checkout), one by one: the command `branch.move` (`branchHere`, `src/machine/branch-here.ts`) fetches the folder's remotes with the project's credentials, so a branch only on a remote is taken with `--track`, then moves it by the hub's rules (`shiftBranch`, `src/projects/branch-move.ts`) and answers what undoes it (`BranchShift`). Then the hub's checkout moves and the key is written. A machine off the link refuses the save (`branch.machineOffline`: turn it on or off in the pool); one that cannot move, a dirty tree say, refuses it with its name and git's reason (`branch.machineFailed`); a refusal of the hub's checkout too. Each refusal puts back the machines already moved (`branch.back`, `shiftBack`: the folder goes where it stood, a branch the move made is dropped). There is no move when a machine comes back: a machine left on the old branch shows the drift below.
- **The checkouts.** A machine elsewhere tells in its facts the branch each folder of its projects with git stands on (`MachineFacts.checkouts`, `null` — detached; `CheckoutWatch`), read at each brief changed, after a command and every 30 s (`CHECKOUT_READ_MS`), so a folder switched by hand shows within that. The hub's own machine does not tell them: its checkout is read as before. The machine tells the branch, not a drift: the hub compares it with its own `branch`, so a save has no false drift before the machine's next brief.
- **The drift of a machine** is `EvenKeelState.machineDrift` (project → machine → `BranchDrift`, `BranchControl.machineDrift`), for the machines of the project's pool turned on. The page shows it as a band on the machine's page and over the rows of the project's "Machines" tab (`BranchDriftBand` with `machine`), with the same two buttons: "Put the folder back" sends `project/branch/restore` with `machine` (`branch.move` on that machine), "Make it the main branch" sends `project/branch/adopt` with `machine`, a save of the machine's branch as any new one (the hub's checkout and the other machines go there too). While the drift lasts the machine serves none of the project's tasks (`held` of `chainMachines`, `src/machine/chain-machines.ts`); a task it holds goes on.
- **Busy.** The refusal `branch.busy` counts a task in hand on any machine (the chain's state is one) and a session of the project's launches mid-turn on a machine elsewhere (its mirror's lamp `working`), besides the own machine's.

## A machine in a project

BTN-994: a machine elsewhere of the pool may run the project with commands of its own — before the start, the check,
after a green main — and its own command for each stdio server of the project's packages (`docs/settings.md`, "A
machine in a project"). The settings tab of the machine in the project edits them; `ProjectPool` carries each row's
values (`settings`), the commands it runs after a green main (`afterGreen`, its own else the project's), the stdio
servers here (`servers`, `Packages.localStdio`) and the project's lists (`commands`) for the fields' grey. "Connect"
takes `copyFrom`, a machine of the pool whose values the new row starts with (`MachineNetwork.place`). The machine's
step `machine-packages` also refuses a server whose command it does not find on its `PATH` or as a path
(`pool.serverMissing`, `missingCommands` in `src/packages/stdio.ts`).

## After a green main

BTN-994: a green `main` runs `commands.afterGreen` on every machine of the pool that has any, its own or the project's.

- **The own machine** runs them in the project's checkout as before (BTN-156): `MainCheck` marks the commit, runs them
  only on main at that commit, and the next launch waits for them. Another machine of the pool may have merged and
  pushed the commit, so the own checkout's main is brought up to it first as a clone's is below (BTN-1597,
  `runAfterGreen(project, commit, true)`); one that cannot be brought up skips with the reason (`afterGreen.notForwarded`:
  changes, a merge under way, commits the green one lacks). With several machines the CI panel's "After green" row names
  the hub's machine.
- **A machine elsewhere** is told by `MainCheckDeps.green` (`PoolAfterGreen`, `src/service/pool-after-green.ts`): for
  each machine of the pool turned on, online and of the hub's version, with commands, the hub writes the commit into
  `project_machines.after_green` (step 60) and sends `runAfterGreen(project, commit, true)`. The machine first brings
  its clone's main up to the commit by fast-forward (`fastForwardTo`, `src/git/sync.ts`: fetch every remote, never past
  the commit; a clone off main, with changes or diverged is left and the run skips as on the hub), then runs its
  commands. One run at a time per machine and project; a green commit during one runs next, the latest only. No launch
  waits for it; its end is a line in the log, which names the machine by the hub's name for it.
- **"Do not run"** (`MachineProjectSettings.afterGreenOff`, BTN-1597): a machine elsewhere whose project's commands do
  not belong there (the hub's own deploy, say) turns them off in its own values; its row has no commands then, the hub
  sends it no run, and its brief's `afterGreen` is empty. An empty list of its own still means the project's.
- **A machine off the link** catches up once: when it is back and briefed (`MachineNetwork` option `briefed`), each
  project of its pool whose last green commit (`ChainState.ci[project].green`, with the guard on) is not its
  `after_green` runs once, on that commit only.
- The tab "Machines" (BTN-1553) gives each row a head — the lamp, the name, its marks, the switch — and under a line its facts, a caption over each value: "Folder", one line cut by an ellipsis with the whole path in its tip, and "After a green main": the machine's own commands a `CommandBlock` each, the project's ones only named ("the project's commands", never repeated on every machine), turned off said in words; the caption's tip says whose they are. The machine pick of "Connect" marks one off the link by a hollow lamp after its name (`machineOption`), and a server of the machine's own values whose name differs from its package's is a tag beside the package (`ServerName`).

## Landings across machines

BTN-1583, on top of the landing of a task's merge into the remote main (BTN-1581, `docs/chain/worktrees.md`, "Landing"). The hub's `Landings` (`src/chain/landings.ts`) keeps the landings under way by project in memory; nothing of it goes to the state database.

- **One turn per project.** A project lands one task at a time on all the machines of its pool: a task ready to land while another of the project's lands waits (`chain: <task> waits to land until the landing of <task> is over`, once), its step held, and takes the turn at the first step after that landing landed or went back to its session. Otherwise a slow landing (a merge of the remote's new commits with `commands.check`, 10–15 minutes) would lose to quick ones again and again. A fix and a carry session of the project take the same turn.
- **Behind the chain.** A step waits for a landing at most `LANDING_WAIT_MS` (2 s, `DispatcherDeps.landingWaitMs` in tests); `none` and a plain push are over well within it. A longer one goes on behind the chain with its task held, so the dispatcher's pass, which steps every lane in turn, is not held for the length of a check; its end wakes the chain (`LandingHost.wake`), and the next step of the task takes its outcome as before.
- **A machine gone mid-landing.** Its `land` call keeps waiting: the result comes when the machine is back (`RemoteMachine.lost` lets go only the commands under the lock of main), and the task waits for it. Meanwhile the landing does not hold the turn (`ChainMachines.online`, the own machine always on): the project's other tasks land on the other machines. A task whose machine is off the link starts no landing, since the call would wait for it. Two landings of one project at once are then possible; a push rejected as not a fast-forward is landed again, as ever. A hub restart forgets a landing under way: the task's next step asks for it again.
- **Fresh main elsewhere.** A landing that went through (`landed` carries the pushed `commit`) has every other machine of the project's pool that is on the link and serves it (`ChainMachines.list`, `serves`) bring its folder's main up to that commit: the port's command `forward` (`fastForwardTo`, `src/git/sync.ts`), the own machine included when another one pushed. Only a fast-forward: a folder off main, with changes to tracked files, in the middle of a merge (`MERGE_HEAD`), ahead or diverged is left as it is (`ForwardOutcome`), each end a line in the log. Nobody waits for it. So sessions merge into a nearly fresh main and fewer landings conflict; what is left the landing catches. A push of the cleanup after Done (`git sync`) does not spread.

## A machine gone

BTN-1270. A machine elsewhere that went off the link, or was revoked, keeps its tasks: their `machine_tasks` rows stay, so no lane takes them (`ChainMachines.holder` names it either way), and the chain never moves them by itself — the machine may come back with the work it did meanwhile. Only a person moves one, with "Reassign".

- **Its lanes.** A lane on a machine merely away stays: the chain waits for it as for any session it cannot read. A lane on a revoked machine ends at the next step (`goneLanes`, `leaveLane` in `src/chain/lanes.ts`): nothing reaches its session any more, and `machinePool` would send its reads to the own machine. Its task is not released; once the task is done, its cleanup only lets go of its row ("The port by task", BTN-1627); a project left without a lane goes to the head of the queue, so its other tasks go on on the other machines.
- **What the page shows.** The state's `stranded` (`Reassigner.stranded`, `src/service/reassign.ts`) lists, by project, the tasks whose row names a machine elsewhere that is not connected (`MachineNetwork.connected`) or is revoked, each with whether the task's branch is on the remote: `git ls-remote` in the hub's folder of the project, asked behind and again after `PUSHED_FRESH_MS` (a minute), a new answer broadcasting the state. A chain row of such a task without a lane carries "Reassign" (`web/src/pages/ChainRow.tsx`), off with a tip saying why while the branch is not known to be there; `dev:fake` `?chain=stranded`.
- **"Reassign"** (`chain/reassign`, `Reassigner.reassign`) asks the remote again and refuses by `reassignable` (`src/machine/reassign.ts`): no machine elsewhere holds the task (`reassign.notHeld`), its machine is connected (`reassign.machineOnline`), the repository has no remote (`reassign.noRemote`), the remote did not answer (`reassign.remoteUnknown`) or lacks the branch (`reassign.notPushed`). Otherwise the row goes, a `task_moves` row keeps the machine left and the branch (step 57, `TaskMoves`, `src/machine/task-moves.ts`), and `Dispatcher.moved` ends the task's lane if it still has one. The pull then gives the task to the first machine with a free place that may run it — never the machine it left (`ChainMachines.runs`).
- **The first launch elsewhere.** While the move has not launched, the hub's brief of the launch carries `restore` (`LaunchBrief`, built in `remoteOf.brief` of `machine-link.ts`): the branch and the text the start prompt ends with — where the task came from (`moved` of the prompts) and the last handoff note the hub keeps (`lastHandoffNote`, BTN-1046), whole. The machine first fetches the branch from its remote over any local one (`restoreBranch`, `src/git/push.ts`; a refusal is `reassign.notRestored` and pauses the lane), then prepares the worktree as usual: an existing branch is brought back into it. The launch marks the move launched; the cleanup after Done (`released`) drops it with the row.
- **The old machine back.** Squaring its snapshot (`Assignments.reconcile`) never gives it a task moved off it, a live session there notwithstanding: the task stays where it went, `HeldChanges.refused` is a line in the log, and that session is left alone (invariant 1) — the person stops it. Its work after the last push is not merged anywhere: the new machine started from the pushed branch, and a later push of the old one is refused as not a fast-forward.
- **What is lost.** Whatever the machine had not pushed: the commits of a turn still running, since the branch goes to the remote at the end of each turn as well as at a handoff, checkpoint or stop (`docs/chain/worktrees.md`, "Task branches on the remote"), and anything a refused push left behind. A branch the machine never pushed cannot move at all; the person brings the machine back or finishes the task there.

## Account limits

BTN-991: the hub holds the picture of each claude.ai account's limits, and one place polls `/usage` per account, so two machines signed in to one account do not both poll its token (`docs/sessions/limits.md`; whether a 429 counts per token or per account does not matter then).

- **The account** of a Claude folder is `oauthAccount.accountUuid` of the `.claude.json` the CLI reads with it (`AccountIdentities`, `src/limits/identity.ts`, read again at most every 30 s). The machine posts it in the facts' `identities` section by folder (`AccountTie`): the account, its e-mail, whether its watcher could poll the folder (`LimitsWatcher.pollable`: a full sign-in, not a long token, not an API key) and whether it skips it now. A long-token folder has no `oauthAccount`: it is posted under the hub's account its token was said to be of (`LongToken.account`, BTN-1002; `accountTie`), never as a poller, so it gets the poller's limits in `picture` and its sessions' windows reach the account's other machines. An account only long tokens are signed in to has no poller: each machine knows it from its sessions alone. Codex, OpenCode and Copilot folders are not in it and each machine polls them as before.
- **The poller** (`AccountPolls`, `src/limits/polls.ts`) is chosen among the machines on the link whose folder of the account could be polled: the hub's own machine whenever it is one of them; otherwise the machine named before, while it stays on the link; otherwise the first by id, a line in the log. A machine that went off the link gives the account to another. An account none can poll has no poller and nobody skips it.
- **The plan** is the command `limits.plan` (`LimitsPlan`): `skip` — the folders whose account another machine polls, sent whole when it changes; `picture` — by folder, the newest limits another machine posted of the folder's account, sent once per time and only when newer than what the machine itself posted, so a picture handed over and posted back is no news. The hub works it out at every change of the mirror and at a machine's going offline; a new connection forgets what the machine was told, and the first plan of every machine but the hub's own carries `skip`, an empty list too (BTN-1247), so a machine elsewhere always gets the plan it waits for. A command that fails makes the hub tell everything again.
- **On the machine** `LimitsWatcher.plan` keeps the skip list and the handed limits (`hub`, newest of all sources as any other): a skipped folder is not polled, its chain does not wait for a first poll of it (`unread`), and its health is "ok". A folder given back is polled no sooner than a poll interval later: its poller may just have polled it. Handed limits are not saved to `account_limits`; the hub hands them again after a restart. A machine off the link keeps the plan it had: it takes a limit from the session's refusal, as before, and does not start polling an account another machine polls.
- **One account on two machines** — the hub logs once that they share one limit window, and `AccountPolls.shared()` lists them for the page of machines (BTN-993).
- **Limits from sessions only** (BTN-1266). A machine's long-token folder whose account has no poller (`AccountPolls.poller`, handed in as `polled`) — or, with no account known, no `sameAs` folder on a full sign-in in its panel — is `MachineAccount.sessionsOnly` (`sessionsOnly` in `src/service/machine-page.ts`), in `machineSignIns` (and in the machine page's query, which the page no longer reads). The page marks it "limits from sessions only", the tip the notice `usage.sessionsOnly`: under the hub's account row in the machine's line (`machineTokens`, the hub's folder signed out too — its "Sign in" is the fix), and under the folder's row on the machine's accounts page (`/accounts?machine=`, `MachineTokenNote` from `machineAccountView`'s `tokens`, BTN-1740), tagged "long token", with "Sign in fully" (`fullSignIn`: again in the hub's Claude folder of the e-mail, else a new one). A hub long-token row gets the same line with "Sign in fully" while no Claude folder of the hub is on a full sign-in (`hubSessionsOnly`): such a token names no account, so a full sign-in of another one also takes the mark off.
- **A token's windows against the poll** (BTN-1267). At each plan the hub compares what a long-token folder's own sessions told (`polls: false`, `source: 'sdk'`; the poll it was handed and posts back is no evidence) with the newest poll (`source: 'usage'`) of a full sign-in of the same account (`tokenWindowsDiffer`, `src/limits/token-windows.ts`): a five hours or a week whose reset stands more than an hour off (`/usage` names it to the hour), or whose later reading spent over 5 points less than the earlier one, while neither window had ended before the other reading. Then the account `AccountPolls.differs`: a line in the log names the window, the machines and that the full sign-in's poll is taken, and `newestElsewhere` stops handing the token folders' session windows to other machines, so the hub's picture does not swing between the two; a later pair that agrees takes it back, with a line. The machine's accounts page marks such a folder under its row "limits differ from the hub's" (`MachineAccount.limitsDiffer`, `MachineTokenNote`), the notice `usage.tokenWindowsDiffer` in its tip, and "New token" next to it, while the machine is online, opens the token window for the hub's full sign-in of the e-mail. `dev:fake`: `/accounts?machines=tokenDiffer&machine=machine-2`.
- **With one machine** the hub's own machine polls every account and nothing is ever sent: behaviour does not change.
- **A machine elsewhere** (BTN-1247) starts its watcher with `planFirst`: no round of polls before the hub's first `limits.plan`, or it might poll what another machine polls. The hub plans its accounts with the own machine's (`MachineNetwork.accounts()` in `steerLimits`) and sends the plan through that machine's own `RemoteMachine` (`tellLimits`).
