# The state database and vacuum

## The database (`src/storage/database.ts`, `src/storage/owner.ts`)

- **The engine** is PGlite (Postgres in WASM, the one Tally embeds): the folder holds `pgdata/` and, while a process holds it, `owner.json`.
- **One owner.** A PGlite folder has one session in one process. The service's main thread owns it: `src/start.ts` opens it before the service module loads (`prepareDatabase` → `keepDatabase`), `src/service.ts` takes it (`keptDatabase`) and closes it last on shutdown. The owner serves the database to `pg` clients on a loopback port of its own (`@electric-sql/pglite-socket`) and writes `{ pid, port }` into `owner.json`. An owner is live only when its pid runs and its port answers, so a file left by a crash is no owner.
- **The claim** (BTN-301, `src/storage/claim.ts`; Tally's local database uses it too, `docs/tally/collector.md`). Before PGlite opens the folder, `owner.json` with `{ pid, since }` and no port is put in place as a hard link, which fails while one is there: of two processes starting together one gets it and the other sees the claim. The port is written over it (a rename) once the server listens; the claim goes when the open fails or the database closes. A claim without a port is an open in progress while its pid runs, for at most 10 minutes; a stale claim is removed and taken again.
- **A folder held by another process** (BTN-1069, `src/storage/startup.ts`). The service waits with the page's `storage.held` notice and the API at 503, and tries again every 3 seconds under the same claim rules, for as long as it takes; it never displaces a live holder. The page names the current holder if it changes. Once the folder opens, the waiting server closes its connections and the full service starts; an open page reconnects by itself. Only the first refusal and the recovery are logged. Any other start error replaces the reason and stops the retries until a restart.
- **PGlite runs on the main thread**, not in a worker of its own: the queries are small, so each holds the event loop only briefly. Readers through the port see whole transactions: the server gets a proxy of the database whose `runExclusive` also takes the transaction lock (`wholeTransactions`), so a read never lands between the statements of the service's transaction.
- **Writes are not awaited** by the service: `Writes` tracks them, logs a failure (`storage: … not saved`) and is settled on shutdown before the database closes. Order holds because PGlite runs queries and transactions in the order they were called, and every write starts its first query at the call. Writes of several rows go through `inTransaction` (a call inside another joins it).
- **`Mailbox`** keeps its rows in memory (`Mailbox.open`) and writes behind, so `settle` stays atomic in one thread and `getState` stays synchronous; the posted questions are loaded at start (`loadQuestions`) and saved behind.
- **A project is named by its id** (`projects.id`) in every `project_id`, as the running service names it (BTN-271): `src/chain/store.ts` reads and writes the ids as they are (`docs/chain/state.md`). Only `setting_values` has a foreign key to `projects`: the chain's tables keep the rows of a removed project.
- **Reading every table in one statement** (`rowsOf`, `src/storage/copy.ts`, the backups) builds a `json_build_object` per 40 tables: one takes at most 100 arguments, two a table, and the database has had over 50 tables since step 63.

What the tests keep on disk — the migrated templates behind `memoryDatabase()` — is in [`tests.md`](tests.md).

## How the rows are written

- **The chain state** is saved whole on every save, in one transaction (`writeChainRecord`), but `chains`, `chain_queue` and `chain_lists` rewrite only the rows that differ from the stored ones (`replaceRows`, one statement a table: a changed row is updated, a gone key deleted, a new one inserted), so a save leaves no dead rows behind. The launch log is appended to. The switches `unattended` and `trimTools` are Even Keel's setting rows: `loadChainState` reads them from `setting_values`, the page writes them through the settings (`ConfigStore.saveChainSwitches`).
- **The settings** are written whole in one statement (`saveSettings`: data-modifying CTEs, so a write through the port is whole too); a row whose value did not change keeps its `updated_at`.
- **`closed_tasks`** is filled by the chain's `finish` (`archiveClosed` in `src/service/chain.ts`) for every task but a fix of main. The page shows a project's archived tasks closed in the last 7 days that its trackers no longer give — a feed or a profile gone, a task deleted — by that status, milestone, priority and labels, so a milestone whose last task closed still lists it (`archivedShown`, `src/chain/archive.ts`); a row archived before step 85 has none of the last three. Tally takes from it the status and the done mark of tasks of trackers other than Huly (`docs/tally/cost.md`, "Where a task lives"). Only a backup keeps it: the v0.1 export has no file for it.

## Vacuum (`src/storage/vacuum.ts`)

PGlite is one session: `show autovacuum` says `on`, but no autovacuum worker runs, so a row an update or a delete leaves dead is never reclaimed unless the owner asks (BTN-952). The service asks twice:

- **At the start**, right after the database is opened and before the service module loads (`compactDatabase` in `src/start.ts`): `VACUUM FULL`, then `ANALYZE`. It rewrites every table without its dead rows, so the files shrink, and gives the planner its row counts. Nothing reads the database yet, so its table locks and its time hold nobody. The log gets `storage: the database was compacted in N ms`.
- **Every hour** while running (`VACUUM_EVERY_MS`, `vacuumDatabase` in `src/service.ts`, through `Writes`): a plain `VACUUM` of the whole database, which makes the dead rows reusable without shrinking the files. No table list: a new often-rewritten table is covered without a change here. No `ANALYZE` in it — it is most of the cost and the row counts of the start are enough for tables this small.

A failure of either is one log line (`storage: the vacuum failed: …`) and nothing else: the service starts and runs without it. Readers that open the folder themselves (`readStateDatabase` with no owner) and the tests do neither.

PGlite is synchronous, so a vacuum holds the event loop for its whole time: on a copy of a bloated working database `VACUUM FULL` took under a second and the hourly `VACUUM` tens of milliseconds ([the measurement](../verified/platforms.md)).
