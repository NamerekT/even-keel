# Schema steps: the rules and the newer steps

## Schema steps

- Versions 1 and 2 were the SQLite file (`PRAGMA user_version`); the numbering goes on in PGlite from 3. The version is the one row of `schema_version`. `STEPS[n]` takes the database from version `2 + n` to the next one in one transaction together with the new version, so a step that fails leaves the old version and none of its tables. Step 3 is the tables of the SQLite versions in Postgres; step 4 (BTN-199) adds `projects`, `setting_definitions`, `setting_values` and `service_state` and moves the rows of `chain_flags` into setting rows (with their two definitions, only when it had rows) before dropping it; step 5 (BTN-200) adds `tracker_profiles` and `projects.profile_id`; step 6 (BTN-209) adds `changelog_versions`; step 7 adds `changelog_versions.spend`; step 8 (BTN-205) lets `chain_lists` hold the list `reviews` (the pull requests of PR mode, `docs/chain/pr-mode.md`); step 9 (BTN-207) adds the `color` definition and writes each project at a position under 8 the color of its position (`position + 1`), so nothing is repainted (`docs/settings.md`); step 10 (BTN-245) lets `chain_lists` hold the list `shelved` (tasks that left the chain for an inactive status after their session's turn, `docs/chain/state.md`); step 11 (BTN-271) drops the uniqueness of `projects.key`; step 12 (BTN-66) adds `tracker_profiles.rules`, `projects.feeds`, `feed_profiles` and the profile and status of `closed_tasks`; step 13 (BTN-345) makes the tracker a project's own: each project without a `tracker` row gets the shared row's value, or `huly` without one, and the shared row goes (the SQLite and v0.1 imports pass through it; an imported config file gets the same from schema v13, `trackersOwned`); step 14 (BTN-418) adds `key_organizations`; step 15 (BTN-475) adds `tracker_profiles.mcp_oauth`; `DATABASE_VERSION` is `2 + STEPS.length`.
- A database newer than the code is refused before anything is written: `storage.newerDatabase`, the blocked page (`src/start.ts`). So is a SQLite file of a version above 2.
- A step is never edited or removed once merged. A schema change is a new step and a new frozen sample `test/fixtures/database-v<N>/even-keel.sql` (the SQL of the tables and rows of that version). Four test files run in parallel: `src/storage/database-schema.test.ts` compares every schema with its frozen sample (columns, indexes, constraints); `database-settings.test.ts` and `database.test.ts` migrate and read every PGlite sample whole (the settings and profiles also through a backup); `database-sqlite.test.ts` imports the SQLite samples `database-v1/`, `database-v2/` whole. They share readers in `database.fixture.ts`; merged steps and samples stay unchanged. The state-file import and the owner's locking, readers and backup tests also run in separate files (`state-files.test.ts`, `state-owner.test.ts`), all on disk.
- The database's version is separate from `SCHEMA_VERSION` of the files (`src/storage/schema.ts`), which still versions the config's format (the imported file, `config-export`/`config-import`) and the files that stay.

- Machine step 4 (schema version 6, BTN-1250): `global_accounts`, `key_organizations`, `management_keys`, `left_folders` and `context_windows` move to `state/machine/`; their old hub tables remain for upgrades. The separate `stores.hostImported` marker in `machine_state` makes the import run even after step 3's import. It also carries `cliCheck.history` and the pending global-account adoption marker. Local CLI choices are saved as `cli`. The frozen sample is `test/fixtures/machine-v6/machine.sql`; `src/machine/schema.test.ts` checks its schema and `state.test.ts` the import. `key_spends` and `task_retries` remain hub tables: the former receives deduplicated `key.spend` events, the latter belongs to the hub's tasks server. The hub's backup does not include the machine folder or its newer credential rows.

- Step 52 (BTN-1216): `project_machines` and `machine_tasks`, which machine may run and runs what (`docs/machines/pool.md`, "Tasks to machines"). The tables start empty; the first start fills the pool with the installation's own machine and names it in `service_state` (`machines.own`), which is no step: it needs the machine's database too. That database is a folder of its own, `state/machine/` (`MACHINE_STEPS`: the outbox, the command numbers, the consents and the connection token), opened by the service next to this one and left out of the backups. The frozen sample is `test/fixtures/database-v52/`; `database-machine-tasks.test.ts` checks the step, the own machine on the sample of step 51 and the assignments.
- Step 53 (BTN-1046): `handoff_notes`, the notes a handoff carries into the next session's prompt. The table starts empty. The frozen sample is `test/fixtures/database-v53/`; `database-handoff-notes.test.ts` checks the step, the sample of step 52 brought to it, the refusal of a write from a session other than the task's newest launch and the project's removal.

- The machine's database, its step 3 (BTN-1246, `docs/machines/seam.md`, "The machine's stores"): `account_limits` and `account_settings` with the columns of the tables here, and `machine_state` (`name`, `value` JSON: `cli.downloaded`, `stores.imported`). - Step 65 (BTN-1112): `builtin_history`, the change history of the built-in tracker's tasks and milestones — a row a field: `project_id`, `task_id` or `milestone_id`, `at` (ISO), `author` (`person`, `agent`, `service`), `model` (an agent's `<Provider> | <model>`), `author_name` (the original author of an imported change), `field`, `before`, `after` as text; a description keeps only its difference, JSON of `DiffLine[]` in `after`. The frozen sample is `test/fixtures/database-v65/`; `database-builtin-history.test.ts` checks it and the step over v64.
