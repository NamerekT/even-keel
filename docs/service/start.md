# What applies on the fly and a slow start

## What applies on the fly

A restart is needed only for a new version of Even Keel (BTN-130). The service looks at the settings in its database (`ConfigStore`, `src/config-store.ts`) and at `.env` (`EnvFile`, `src/env-file.ts`), each every 2 s, and applies a change at once:

- **The config.** Every key (`docs/settings.md`), whether the page saved it or `npm run storage -- config-import` replaced the settings (`docs/storage.md`). A project added gets its tracker, CI watches and packages; a removed one has its chain let go (`Dispatcher.forget`) while its sessions are left as they are; a key renamed under the same `id` moves nothing, since the state names a project by its `id` (BTN-271): one log line. A changed `repo` or tracker rebuilds that project's tracker link (`Trackers.apply`) and CI watches (`CiWatches.apply`). A remote or a first workflow added to the same checkout gets its CI watch within a minute (`docs/ci.md`). A smaller `slot` keeps finding the slots busy tasks are in: the pool spans the most slots it had since the start (`slotSpan`).
- **`.env`.** A variable the process got from outside the file stays as it was, as at the start. `envTargets` says who reads a changed one (the trackers' credentials and the CI tokens are profiles', not `.env`'s: a changed profile rebuilds its tracker links and gives every CI watch a new source, `docs/trackers.md`, `docs/ci.md`): `EVEN_KEEL_ACCOUNTS_DIR` and its `CODEX`, `OPENCODE` and `COPILOT` siblings (`EVEN_KEEL_<AGENT>_ACCOUNTS_DIR`) move the account roots; `EVEN_KEEL_TOKEN` changes the page guard and closes the open event streams, so pages ask for the token again; `EVEN_KEEL_HOST`/`EVEN_KEEL_PORT` move the page to a new server (the old one closes once the new one listens; a refusal keeps the old address and shows `server.rebindFailed` in the config banner); `TALLY_DB_*`/`TALLY_READER_*`/`TALLY_WRITER_*` restart the collector against the new database. The sessions' environment is built at each launch (`AgentOptions.env`), so a removed key never reaches a new session.
- **Start-only.** `EVEN_KEEL_MCP_PORT` (live sessions have the gateway's address in their flags), `EVEN_KEEL_MACHINES_PORT` (the hub's listener for machines; whether it listens follows "Hub address for machines" live), `EVEN_KEEL_STATE_DIR` (the files and the database the service has open), `EVEN_KEEL_CONFIG` (the config file imported once at the first start, `docs/storage.md`), `CLAUDE_CONFIG_DIR` and `CODEX_HOME` (the `global`/`codex` account folders), `EVEN_KEEL_CPU_PROFILE` (below). These are read once; change them with a restart.

## A slow start (BTN-680)

`src/main.ts` is only the entry: it imports `src/start.ts`, the service's real start, and when that import fails because a package is not installed (`ERR_MODULE_NOT_FOUND` "Cannot find package", `src/diagnostics/missing-package.ts`) it writes one line instead of a stack — `even-keel cannot start: the package <name> is not installed. Run \`npm install\` in <folder>, then start it again` — and exits 1; the host restarts it with its backoff (BTN-1239). Every package of the service is resolved while its modules load, before a line of theirs runs, so the check cannot live inside `start.ts`.

`src/diagnostics/stop.ts` records `stopping: SIGINT`/`SIGTERM` before the existing shutdown. `start.ts` installs an `uncaughtExceptionMonitor` before storage starts: fatal exceptions and unhandled rejections write `stopping: uncaughtException`/`unhandledRejection` and the stack synchronously to stderr, preserving Node's default fatal exit. A missing stop line does not exclude SIGKILL, a machine shutdown or a native crash.

Right after it `start.ts` sends every `fetch` and `WebSocket` of the process over HTTP/1.1 through a global dispatcher from the `undici` package (`src/fetch-dispatcher.ts`, BTN-1227). Node 26's own fetch takes HTTP/2 wherever a server offers it, and its bundled undici 8.12.2 crashed the service during a network failure: an idle HTTP/2 session's teardown emitted `error` on a stream nothing listened to (`InformationalError: socket idle timeout`).

`src/diagnostics/start-watch.ts`, started by `src/start.ts` right after `.env` is read:

- **`start: modules … s, storage … s, service … s`** — once the service's top level is done: the time from the process start to `start.ts`'s own modules loaded, then opening and upgrading the storage, then `service.ts` (its imports and its wiring up to the timers).
- **`event loop: blocked up to N ms in the last 5 s (p99 M ms)`** — for as long as the service runs, a 20 ms timer measures the time between ticks. The tick that ends a five-second window records its last interval before reading the histogram and rotating the CPU profile. A block that crosses the boundary therefore stays in the window being reported. Windows with a delay of at least 1 s get a log line. A blocked loop also delays network probes and tracker timeouts.
- **`EVEN_KEEL_CPU_PROFILE=<seconds>`** in `.env` — the process profiles its own CPU through an in-process inspector session (no port opens) for that many seconds of the start, at most 600, sampling every 1 ms, and writes `logs/start-<time>.cpuprofile`. Remove the variable after the run.
- **`EVEN_KEEL_STALL_PROFILE=1`** in `.env` enables continuous in-process sampling at 10 ms. A change takes effect at the next window boundary after the environment reloads. If a startup profile is running, stall sampling starts at the first boundary after it finishes. A window reaching the delay threshold is saved as `logs/stall-<UTC time>.cpuprofile`, at most once an hour per process. The log names the file, the triggering delay and up to five active functions ranked by sampled self time across callers. Chrome DevTools or VS Code shows their stacks and the timeline. The newest 20 stall files are kept across service restarts. Ordinary delay warnings continue during the cooldown and when profiling is off.

Stall profiling is opt-in. On Windows with Node 26.13, a 100 ms timer serialized and parsed 4,000 task-shaped records three times per tick. Across three 15 s runs in each mode with five-second profile rotation, median process CPU time was 688 ms with sampling off and 828 ms with it on (about 0.9% of one core extra). The workload completed 138 and 145 timer ticks per run respectively. BTN-1465 tracks the production observation.

**Measured on 2026-11-01** (BTN-680; two profiles of the live service, 150 s from the node start, 1 ms sampling). Before: the loop was busy 98–100% for the first ~60 s and ~55% after, 109 s of 150; `AccountHomes.list` alone took 27.7 s (`readdirSync` 18 s, `existsSync` 5.8 s — every account's limits and view listed all account folders again, O(accounts²)), the session registries' `readFileSync` 16 s (`TurnRegistry` 10 s, `SdkRegistry` 6 s, on every sessions tick); the loop stalled for 1.1–2.8 s at a time, and every tracker call timed out after 15 s. Now the account folders are read once per synchronous pass and the registries at most once a second. After: 78.5 s of 150, ~100% for the first 40 s and 20–35% after. What was left:

- 9.6 s before `listening`: tsx compiling the `.ts` files changed since the last start on the main thread (esbuild `transformSync` 3.3 s, the synchronous pipe read 3.7 s) and opening PGlite (0.8 s). No call is made yet, so it times nothing out; it is only the price of running `node --import tsx src/main.ts` from the checkout after a pull.
- +15…+30 s: the sessions monitor catching up on transcripts — `readLines` 3.1 s in one go, then folding with stalls of 1.6–2.6 s; this is the window where the trackers timed out. Since BTN-690 transcripts are folded in small slices under one budget per turn of the loop for all readers ([`sessions/agents.md`](../sessions/agents.md)); measured the same day: the longest delay of the loop in the first 180 s went from 6044 ms to 1121 ms (the first 4 s, before the catch-up), no tracker call timed out, the CPU busy 41.8 s of 150, 20–30% from +20 s on. A slice yielding per tail alone was not enough — 735 tails read at once still ran their slices back to back for up to 3.1 s.
- `getState` — 22.4 s of 78.5 (29%): the whole state rebuilt for every broadcast, with stalls of 3.0 and 1.7 s (`launchDays` 1.5 s, `readerOf` 1.2 s in one go). After BTN-690 alone it was 9.6 s of 39.3, the longest 505 ms: those stalls were the loop held by the catch-up, and the two functions took at most 32 and 3 ms at a time. Since BTN-691 the state is built at most once per 200 ms ([`web/interface.md`](../web/interface.md)); measured the same day with a page listening: 8.9 s of 38.9 busy, ~180 builds in 150 s, ~50 ms each once settled, 250–450 ms in the six builds of +16…+30 s, none of whose parts reaches 200 ms alone. What was left is the state's own size — ~2 MB a frame, 736 sessions and 1170 tasks: since BTN-695 only the first frame is whole (~1.6 MB), the rest are patches of 4–70 KB ([`web/interface.md`](../web/interface.md)). Building the state is still whole each time.
- Spawning processes (`execFile`, a synchronous CreateProcess on Windows) — ~6 s per start, git and CLI calls.

**Measured on 2026-11-07** (BTN-827; one profile of 600 s, 21 projects, ~1000 tasks, ~860 sessions, the page open, one chain working). A static file (`/favicon.svg`, 90 s, a probe every 100 ms) four minutes after the start: 324 probes instead of ~900, 66 of them over 50 ms, their median 515 ms, the longest 3.9 s, without the profiler; under it two runs of 90 s gave 522 and 508 probes, 118 over 50 ms each. The loop was busy 63% of the first 180 s and 46.8% of 180…600 s (27.5% after the start on 2026-11-01); 498 busy stretches over 100 ms, the longest 1.0–1.8 s, nearly all of them state builds. What held it, of all the time from 180 s on:

- 18.9% — `runOf` → `DemoService.owns` → `project()` (BTN-776): every call walks the config's projects through `samePath`, a `realpathSync.native` on both sides, with a walk up the parents while the demo's folder is missing; `runOf` runs for every task of the state and every package check. That is two thirds of the state build (24.3%), most of `check` in `src/packages/service.ts` (10.1%) and of the tracker start (12.2%). Since BTN-848 the demo's project is found once per config object (a change replaces `projects` whole): one lookup over 21 projects measured offline at ~5 ms on 2026-11-08, ~5 s a state build of ~1000 tasks before. The live profile of 2026-11-09 (BTN-850, the same window): `runOf`, `DemoService.project` and `samePath` no longer show, `realpath` fell from 16.9% to 0.1% and the state build from 24.3% to 5.3%.
- 2026-11-09, the same profile: the loop was busy 66.3% of 180…600 s, 27.5% of all the time in PGlite's `execProtocolRawSync` — ~5 s of every 20 s, steady. The state database's counters put it on `session_windows`: ~620 inserts, ~1000 updates, ~620 deletes and ~1600 full scans in 12 s, because the monitor remembers 500 written windows while ~800 sessions have one, so every tick writes them all again (BTN-951). The start's summary went from 1–3 windows over 1000 ms to 31–34 from the first start with BTN-946. The tables rewritten that often are bloated and never vacuumed: PGlite runs no autovacuum (BTN-952).
  2026-11-11, after BTN-951 and BTN-952, no profiler (BTN-953): the 17 warm starts from 11-10 13:43 to 11-11 13:51 had 1–2 windows over 1000 ms each (the longest 2.7–6.3 s), chain sessions running through several of them. Seven earlier starts with the fixes, 11-10 02:25–13:30, still had 4–21, with no cause found in the log: the next start of the kind gets a look; `session_windows` had no insert, update, delete or scan in 45 s; the static probe 3–4 min after a start had 2 of 600 over 500 ms, p90 66 ms, the longest 683 ms. A start right after a cold boot of Windows is not comparable: modules 9.3 s instead of 0.3–0.6, every tracker timed out while the network came up, and the loop was held 38 s once.
- 13.2% — the sessions monitor's tick: the registries' `JsonFolder` reads 5.4% (Codex and OpenCode turns, SDK sessions), `realpath` 1.9%, `codex/turns.ts` reads 1.3%, spawns 0.6%; no single part reaches 10%.
- 2.7% — spawning processes, half of it `git` from the CI watcher's `readHead`.
