# The service on each platform

Windows, Linux and macOS, an npm install, a machine of a hub.

## Windows

Two ways to run it: the start at sign-in with a tray icon (BTN-372, `even-keel install`, no administrator — the default) and the Windows service `EvenKeel` (`install.ps1`, runs without a sign-in). One per machine, they share the port: `even-keel install` refuses while the service is registered, `install.ps1` while the `Run` value is.

### The start at sign-in (BTN-372)

- **The host** is the same code as the service's (`service/EvenKeelService.cs` with `EvenKeelHost.cs` and `EvenKeelTray.cs`), compiled by `src/autostart.ts` as `EvenKeel.exe` with `-target:winexe`, so no console window: into `<data>\service` for a package, `service\bin` for a checkout (`hostDirOf`). `installAutostart` ends a running host first (it holds the exe) and removes the exe once its process lets go of it — `--quit` returns when the host frees its mutex, before the process ends, so `removeHostExe` retries `EPERM`/`EBUSY` for up to 10 s (EKR-93) — compiles, writes `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` → `EvenKeel` = `"<exe>" "<root>" "<node>" ["<data>"] --tray` with `reg.exe` and starts it. A value, not a Startup shortcut: a shortcut needs COM through PowerShell, and Settings → Apps → Startup turns either off. `even-keel install` from a checkout ends the host, runs `npm install` and `npm run build` first, as `install.ps1` does; `uninstall` ends the host, deletes the value and the exe with the same retry (the folder too once empty: the service's host may share it).
- **Modes** (the last argument): `--tray` — the host with the icon, one per machine (the mutex `Global\EvenKeel.Host`; a second one exits at once); `--start` — tells a running host to start node, or starts a host with the same arguments and `--tray` through a shell start, which inherits no handles, so a caller reading its output does not wait for the host; `--stop` — the host stops node and keeps it stopped, the call returns once node is down (30 s at most); `--quit` — the host stops node and exits. The commands are the events `Global\EvenKeel.Stop|Start|Quit` and `Stopped`: global, so `rebuild.ps1` over SSH, in another Windows session of the same user, reaches the host on the desktop. A stop for an update keeps the host and its icon for that reason: a host started from SSH would have no tray and end with the SSH session. Node held stopped, or started again by a start or **Restart**, begins its crash backoff anew.
- **The icon**: the page's `dist/web/icon-192.png` with a dot — green running, amber a chain paused (`chain.active[].paused`), blue a session waiting on its question (`sessions[].asking`), grey starting (no answer in the first 2 min after node started) or stopped for an update, red no answer. It reads `GET /api/tray` every 10 s at the address of `EVEN_KEEL_HOST`/`EVEN_KEEL_PORT` from its environment over `.env` of the data folder, the wildcard on loopback as `stateUrlOf` does; the menu and tooltip follow the state's `language`, otherwise the Windows display language. **Restart** kills node and starts it at once; **Quit** ends the host until the next sign-in or `even-keel install`. The log lines are `tray: …` in `logs/even-keel.log`.
- **Under the host** node gets `EVEN_KEEL_LAUNCHER` (the host's exe). `serviceControl` takes it only when the parent process is `EvenKeel.exe` too (`launcherOf`): the sessions inherit the variable, not the parent. Its `PATH` is built at every node start (`FreshPath`, EKR-57): the registry's machine `Path`, then the user's, then the host's inherited entries neither has (fnm, nvm, Volta of the terminal `even-keel install` ran in), compared case-insensitively without a trailing `\`; an unreadable registry leaves the inherited `PATH` and one log line. So a CLI installed after the host's start is found after the tray's Restart; the service `EvenKeel` runs the same code. The control is `autostart`: stop `EvenKeel.exe --stop`, start `EvenKeel.exe <root> <node> [<data>] --start` (`autostartControl`); `even-keel update` finds it from the `Run` value (`registeredAutostart`), `rebuild.ps1` passes `--autostart <exe>` when no service `EvenKeel` is installed and the value is.

### The service

- The service host is `service/EvenKeelService.cs`, compiled during installation by the stock `csc.exe` from .NET Framework; there are no third-party wrappers. It keeps `node --import tsx src/main.ts` running in the repository root (`node dist/src/main.js` in a package, which has no `src/main.ts`), restarts it on a crash and writes the output to `logs/even-keel.log`. A third argument is the data folder of a package: the log goes there and the child gets it as `EVEN_KEEL_DATA`. To debug without the service: `EvenKeelService.exe <root> <node.exe> [<data folder>] --console`.
- `service/install.ps1` and `service/uninstall.ps1` — from PowerShell 7 as administrator. The script does not ask for the account password: the user enters it on the "Log On" tab in services.msc, which also grants the "Log on as a service" right.
- The service reads `.env` from the repository root (a package: from its data folder), and at its first start imports `even-keel.config.json` from there, if there is one; the address and port are `EVEN_KEEL_HOST` and `EVEN_KEEL_PORT` in `.env` (`127.0.0.1:4747` without them), and the port must not be occupied by a manual run.
- The service serves the built `dist/web`: `install.ps1` runs `npm run build`. After a code update, run `install.ps1` again (or `npm run build` and restart the service), otherwise the page is stale or returns 503.
- `install.ps1` stops a running service before `npm install`: the service holds `node_modules/@esbuild/win32-x64/esbuild.exe` (tsx's esbuild child), and npm fails on it with `EPERM`. `npm ci` next to a running Even Keel fails the same way and leaves `node_modules` half-removed (BTN-157: 33 of ~350 packages left); after a stop, `npm ci` again restores it. The binary is held only while the esbuild child runs, that is on a miss of tsx's cache; an update changes the sources, so right after one it is likely, and with a warm cache `npm ci` passed next to a running Even Keel. The service host stops node with `Process.Kill()`, node only, and esbuild exits with it within 2 s (checked with `TSX_DISABLE_CACHE=1`), so stopping the service is enough.
- Stopping the service does not kill background sessions — they are children of the `claude daemon run` daemon.
- **Rebuild after a green main.** `service/rebuild.ps1 -Commit <sha>` builds the checkout it lives in and restarts the service, only if the checkout's HEAD is that commit. With no service `EvenKeel` installed and a `Run` value `EvenKeel` there, it restarts node in the tray host instead (`--autostart`, "The start at sign-in" above). It compiles only the update process (`npx tsc -p tsconfig.updates.json`: `src/updates/run.ts` and what it imports, with `noCheck`, so a package the commit added and nobody installed yet fails nothing; BTN-1239) and hands the rest to the update process in rebuild mode (`node dist/src/updates/run.js rebuild`, "Updating from the page" below), so the wait for the chains and the step order are one code with the page's button: when `package-lock.json` is newer than the installed one — wait, stop, `npm install`, build, start (the running service holds esbuild's binary); otherwise build, wait, stop, start. A failed start or answer restores the running commit (see “Rebuild mode” below). Output goes to the caller and to `logs/update.log`. On the author's workstation it is the last line of Even Keel's own `commands.afterGreen` (`docs/ci.md`), run once GitHub's check of the pushed `dev` is green, whether the chain pushed it or a `git sync` by hand did (BTN-707): `pwsh -NoProfile -Command "& ./service/rebuild.ps1 -Commit (git rev-parse HEAD) *> logs/rebuild.log"`. The `afterGreen` guard has already made sure HEAD is the green commit; `pwsh` is the one process that outlives node's stop (`cmd.exe` running the line dies with it), and its output goes to a file, since the pipe to the service closes when the service stops. Until 2026-11-02 a Forgejo job called it over SSH after the tests; the SSH way below still works for a CI that can reach the workstation. The key's line in the workstation's `authorized_keys` (for an administrator — `C:\ProgramData\ssh\administrators_authorized_keys`) forces the script: `from="<runner host>",restrict,command="pwsh -NoProfile -NonInteractive -File <root>\service\rebuild.ps1" ssh-ed25519 …`; the commit arrives in `SSH_ORIGINAL_COMMAND`.

## Linux and macOS

From a checkout installed by `install.sh`, the last command after a green push can be `service/rebuild.sh "$(git rev-parse HEAD)" >>logs/rebuild.log 2>&1`. It runs as the service user and controls the systemd user unit `even-keel.service` or the launchd agent `local.even-keel`. The script accepts the green SHA as its first argument or from `SSH_ORIGINAL_COMMAND`. Its optional second argument is the hub’s state URL, defaulting to loopback at `EVEN_KEEL_PORT` (4747 by default). A different HEAD skips the build. A match compiles the update process with `tsconfig.updates.json` and passes it the full SHA.

- After starting the unit or bootstrapping the agent, `install.sh` runs `dist/src/service/install-check.js`: up to 60 s for a running service and a response from `/` at the configured address. It uses `listenOf`/`localUrlOf` and the data folder's `.env`; explicitly supplied `EVEN_KEEL_HOST`/`EVEN_KEEL_PORT` are saved into the unit/plist too, above `.env`. A pending launchd PID or systemd `activating` state may recover within that window; an unloaded agent or inactive/failed unit fails at once. A 2xx/3xx or authorization response (401/403) counts; other statuses, including 503, keep waiting. Bootstrap/restart errors and readiness failures print the manager state, launchd's PID/last exit code when available, and the last 40 log lines (journal on Linux), then exit nonzero. Missing diagnostics are marked unavailable; only selected launchd fields are printed, never its environment. The installation stays registered so the user can fix it and retry. On macOS the message points to System Settings → General → Login Items → Allow in the Background (the entry can be `node`). This checks readiness at install time, not continued availability; the Intel Mac disappearance remains [unverified](../unverified/platforms.md#a-launchd-agent-disappearing-after-installation-btn-878).
- `service/install.sh` as your own user (not via `sudo`): `npm install`, `npm run build`, then on Linux the unit `~/.config/systemd/user/even-keel.service` (`systemctl --user`, log — `journalctl --user -u even-keel`), on macOS the agent `~/Library/LaunchAgents/local.even-keel.plist` (`launchctl`, log — `logs/even-keel.log`, no rotation). Running it again rebuilds and restarts. `service/uninstall.sh` removes it.
- `PATH` and the path to `node` are taken from the installer's shell: if `node` changed (nvm and the like), run `install.sh` again.
- The unit has `KillMode=process`, so a restart leaves the CLI daemon of live sessions running. systemd says so in the journal — `Unit process … (claude) remains running after unit stopped` and `Found left-over process … This usually indicates unclean termination` — one pair per process; that is the intended behaviour, not a failure (seen in the BTN-143 trial, Ubuntu 26.04, systemd 259). The MCP gateway's servers are not meant to survive: the service kills them itself on `SIGTERM` (BTN-720), since a left-over one keeps the tracker credentials of its start, and waits for each to exit before node does — `SIGKILL` after 5 s (BTN-723) — so a `huly-mcp` line in that pair means a bug.
- Stopping the service does not kill background sessions: `KillMode=process` in the unit, `AbandonProcessGroup` in the agent. A `--user` unit lives while the user is logged in; to keep it running without a login, use `loginctl enable-linger <user>` (the installer reminds you). The macOS agent lives in the desktop session's domain `gui/<uid>` and works only while the user is signed in to the desktop, at the screen or through Screen Sharing: an SSH login alone has no such domain. `install.sh` checks `launchctl print gui/<uid>` before the build and stops with a message saying so, instead of `Bootstrap failed: 125` at the end (BTN-735). There is no fallback to the background domain `user/<uid>`, without the desktop: Claude Code keeps its sign-in in the login keychain, which only a desktop sign-in unlocks, so sessions started there would not be signed in (assumed, [unverified](../unverified/platforms.md#macos)). A Mac without a screen keeps its session through automatic login (System Settings → Users & Groups; needs FileVault off).
- **The update process** (next section) stops and starts the unit with `systemctl --user stop|start <unit>`, the unit read from `/proc/self/cgroup` (`user@….service/…/<unit>.service`; a system unit gets no button), and the agent with `launchctl bootout gui/<uid>/<label>`, waiting until `launchctl print` no longer finds it, then `launchctl bootstrap gui/<uid> <plist>` after the same check of the domain as `install.sh` (`even-keel update` from SSH on a Mac nobody is signed in to says to sign in, not 125); the label is `XPC_SERVICE_NAME` of the service's environment, the plist `~/Library/LaunchAgents/<label>.plist`.
- Linux was verified live in WSL (Ubuntu 26.04, 2026-10-04): tests and type check, `install.sh` and `uninstall.sh`, signing in to `claude` from the page, `/usage` limits, starting a session in a task worktree, and after Done — stopping the session, cleaning up the worktree and branch, its own `main` sync with a push to origin. The CLI must know a new repository as trusted: otherwise the launch pauses and asks you to open `claude` in it once. A native Ubuntu 26.04 server was gone through by README in BTN-143 (installation) and BTN-157 (updating). macOS was not verified; a smoke of the agent on GitHub's macOS runner, `install.sh` to `uninstall.sh`, runs at every push (`docs/ci/workflows.md`, "macOS").

## An npm install (BTN-265)

The package `even-keel` (`docs/releases.md`, "Publishing to npm") is the built Even Keel: `dist/src`, `dist/tally`, `dist/web`, with the plugins, the status line and the service scripts next to them. Node does not strip types inside `node_modules`, so nothing there runs through tsx; whatever starts a module by its file (the Tally workers, the SDK executor) picks `.js` when its own file is `.js`.

- **Which install.** `src/locations.ts`: `root` is the folder with the nearest `package.json`, `source` is `git` when it has `src/main.ts`, otherwise `npm`. `home` — where `.env`, `state/` and `logs/` are — is `EVEN_KEEL_DATA`, else a checkout's own folder, else the data folder of the platform: `%LOCALAPPDATA%\even-keel`, `~/Library/Application Support/even-keel`, `$XDG_DATA_HOME/even-keel` (`~/.local/share/even-keel`). npm replaces the package's folder at every update, so nothing of the user's lives there. The variable is not `EVEN_KEEL_HOME`: the `tally` plugin finds the code by that one. `tally/bin/sql.mjs` finds the data the same way.
- **The command** `even-keel` (`src/cli.ts`, `bin` of `package.json`): none — run in the terminal; `install`/`uninstall` — `service/install.*`/`uninstall.*` of the package; `update [version]` — stop the service this package runs, `npm install --global --prefix <its prefix> even-keel@<version>`, start it, with no wait for the chains (the page's button waits). With no version it reads `npm view even-keel dist-tags --json` and takes `latest`, or for an installed prerelease the newer of `latest` and `next` (`updateTargetOf`, `src/cli-args.ts`): a release candidate from `npx even-keel@next` would otherwise go back to an older `latest` (BTN-746). When neither is newer than the installed version it says so and leaves the service alone. Run from the npx cache (`_npx` in its path), with no command or `install`, it first installs its own version globally and runs `install` from there: the service and the plugins' paths need a folder npx will not clear.
- **The scripts** tell a package by the missing `src/main.ts`: no `npm install` or build; the log in `<data>/logs`; on Windows the host compiled into `<data>\service` (the package's folder is replaced on update) and registered with the data folder as its third argument; the unit and the agent run `node dist/src/main.js` with `EVEN_KEEL_DATA`. `install.ps1 -Data <dir>` and `EVEN_KEEL_DATA` choose another data folder; the service must run as the user whose data folder it is.

The tray's ten-second poll uses `GET /api/tray` (BTN-826), returning only `{language, asking, paused}`. Counts come directly from the current sessions and active chains, without building the page's state. Questions still take priority over pauses, and an unspecified language keeps the tray's current language. The update runner continues to read `/api/state` for its version and start time.

## A machine of a hub (BTN-1243)

The same installers put a machine of a hub (`docs/machines.md`) on a computer: `even-keel install --machine <string> [--root <folder>] [--service]`, the command the hub's `machines/invite` answers with as `command` (`npx even-keel@<hub's version> install --machine <string>`, `installCommandOf`, `src/cli-install.ts`). No OS is chosen: on Windows the start at sign-in by default, `--service` the service `EvenKeel` (refused elsewhere); on Linux and macOS `install.sh`. From the npx cache the options pass to the global copy (`installArgsOf`, `src/cli-args.ts`).

- **Refusals first**, before anything is installed (`prerequisiteRefusal`): Node older than 24 for any install, no git on `PATH` for a machine. `install.ps1` and `install.sh` check the same on their own, for a run from a checkout.
- **Join before the service.** The join is `even-keel join <string> [--root <folder>]` in a child process (it reads the data folder's `.env`, which must not reach the host's or the unit's environment): in `src/cli.ts` for the start at sign-in, in `install.sh --machine/--root` and `install.ps1 -Machine/-Projects` otherwise (`-Root` would clash with the script's `$root`). A refused join stops the install and leaves an installed service as it was (`install.ps1` starts a stopped one again). A second run with the same string finds it joined and installs the service again.
- **No page.** A checkout builds with `npm run build:machine` (the server's code and assets, no `web/`); a package carries `dist/web` anyway and the machine's process does not serve it.
- **Readiness.** `install-check.js … --machine` waits not for `/` but for the process to keep running 10 s in a row within the 60 s (a process without a kept token exits at once and the manager restarts it). Then the CLI waits up to 30 s for a `contactAt` in `state/machine-link.json` newer than the install's start (`waitForContact`) and says whether the hub was reached and where the log is.
- **The tray** of a machine reads `contactAt` from `machine-link.json` of the state folder (`EVEN_KEEL_STATE_DIR` over `.env`, else `state/` of the data folder) instead of `/api/tray`: green while the last contact is under 3 min old (the machine writes it at most once a minute), grey in the start's grace, red after; no "Open page" item.

Never checked live on another computer: [unverified](../unverified/machines.md#the-machine-installer-on-windows-linux-and-macos-btn-1243).
