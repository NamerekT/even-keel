# Updating from the page (BTN-163, `src/updates/`)

### Containers

The release Dockerfile builds the tag's npm package on the builder architecture, then installs its tarball on the target architecture. The runtime uses Debian, Node 26, Git with SSH, `tini` and the unprivileged `node` user. Compose persists the home directory and requires the page token. Every service of the Compose files sets `stop_grace_period: 30s` over the shutdown's own deadline `SHUTDOWN_MS` (15 s, `src/service/defaults.ts`), since Docker's default 10 s would kill the process mid-shutdown; `src/service/compose.test.ts` holds each file above `SHUTDOWN_MS` (BTN-1442). A host install does not move into a volume as is: the database keeps host paths (project checkouts, account folders, worktrees), so the guide moves only the settings, by `config-export` and the first start's import of `even-keel.config.json`. The image listens on `0.0.0.0` even when run without Compose, so the normal `guardToken` check applies. Volume paths and host commands are in the [Docker guide](../guide/docker.md).

On Linux, `inContainer` recognizes the image's `/etc/even-keel-container` or the runtime markers `/.dockerenv` and `/run/.containerenv`. The updater reports `container` before checking the install source or probing a service manager. Both the page and CLI direct updates to Docker Compose on the host. The CLI refuses service installation before the npx global install or machine join.

### Host installations

The update window on the page (`docs/web/interface.md`) sends `updates/install` or `updates/revert`; the service side is `Updater` (`updater.ts`), the process that does the work is `run.ts` over `runner.ts`.

- **Who may.** `updateBlock` (`model.ts`) gives the reason there is no button, in this order: the checkout is still being read, it is not a git checkout (`readCheckout`, `checkout.ts`), Even Keel does not run under a service manager it can drive (`serviceControl`, `control.ts`: the parent process is the tray host of the start at sign-in or a Windows service in `tasklist /svc`, a systemd user unit, a launchd agent), the checkout has tracked changes (`git status --porcelain --untracked-files=no`), HEAD is not on the tag of the installed version. The last one keeps a developer's checkout (`dev`, a task branch) and the CI-built one out: they update by `rebuild.ps1`. The checkout is read at the start and every 10 min. A package has no checkout (`packageBlock`): it needs a global install whose `--prefix` is known (`globalPrefixOf`, `prefix.ts`; `global` otherwise — a local install, the npx cache) and a service manager.
- **Revert.** `logs/update.json` is the record of the last run (`UpdateRecord`). "Revert" is offered only after an update that went through, to the version it came from (`previousOf`), and only when the storage versions it recorded equal the running ones: `{schema: SCHEMA_VERSION, database: SQLITE_VERSIONS + STEPS.length, tally: TALLY_SCHEMA_VERSION}`. Otherwise `previous.blocked` is `storage` and the page explains the manual way back. A revert release (a release that takes back an earlier one, `### Reverted` in its notes) is an update like any other, so it may come after a storage change; the rule is in `docs/releases.md`.
- **Settling.** Before the process starts, the service waits up to 5 min (`SETTLE_MS`) until `busyChains` (`settle.ts`) is empty: no unpaused chain is launching, handing over or closing a task. A chain waiting for the CI of main does not count — for a rebuild that CI is the run calling it, and the wait survives a restart (`state/`); the project's own check (`ciWait.local`) does. A limit hold (`limitUntil` or `modelWeek`) with no current task or closing also does not count when its reset is more than 60 s away (or unknown for `modelWeek`); at 60 s or less, or past the reset, the chain still counts as busy. A chain that never settles is not waited for past the 5 min. The page shows the projects waited for (`progress.waiting`).
- **The process.** The service cannot update itself: `git checkout`, `npm ci` and the build replace its own code, and stopping it kills its children on systemd and launchd unless they are detached. So `launchRunner` (`launch.ts`) copies the compiled `dist/src/updates/` to a fresh folder in the OS temp folder (with a `package.json` of `"type": "module"` and the mark `.even-keel-update`), writes the plan there and starts `node run.js plan.json` detached (`detached`, `stdio: 'ignore'`), and the service goes on answering. The modules of the runner import only `node:*` and each other, so the copy runs alone. It survives the stop: the Windows host kills only its node child (`Process.Kill`), the unit has `KillMode=process`, the agent `AbandonProcessGroup`. It deletes its folder when done.
- **Steps** (`stepsOf`, `steps.ts`): update — stop, `git fetch --tags`, checkout, `npm ci`, `npm run build`, start, answer; revert — the same without the fetch. The checkout keeps the branch the checkout was on (`git checkout -B <branch> <tag>`, so a `git pull` by hand still works) or stays detached. npm runs through the node of the process (`npm-cli.js` next to it), since the service's `PATH` may lack it. "Answer" polls `GET /api/state` (loopback, no token; `stateUrlOf`) for 2 min (`ANSWER_MS`) until a start later than the one before the update answers with the target version, and the same start still answers 10 s on (`STEADY_MS`), so a service crashing in a loop does not pass. A package's update is stop, `npm install --global --prefix <prefix> even-keel@<version>` (`install`), start, answer, run from the data folder: a working folder inside the package would hold it on Windows while npm replaces it (`workingDir`, `runner.ts`).
- **Keep-warm ahead of the stop** (BTN-1527). Before every stop of a service with a page — an update, a revert, a rebuild and their rollbacks — the process posts `{ms: 240000}` to `/api/updates/warm` (`WARM_AHEAD_MS`, `warmAhead` in `runner.ts`) and waits up to 200 s: the service's keep-warm pings at once every session whose cache would go cold within 4 minutes and answers once those pings and any already in flight are answered (`KeepWarm.ahead`, `docs/sessions/cache.md`, "Timing"). A refusal, an older service without the route or no answer is one line in `update.log`, and the stop goes on. A machine's follow mode asks nothing: its process has no page.
- **Follow mode** (BTN-1275): a machine elsewhere refused for another API version starts the process itself with the hub's commit as the target (`HubFollower`, `docs/machines/elsewhere.md`, "Catching up after a refusal"): `git fetch --all --tags`, `git checkout --detach`, `npm ci` only when `package-lock.json` changed, `npm run build:machine`; its answer is the hub's contact in `machine-link.json`, not `/api/state`, and a failure is recorded so the same commit is not tried again.
- **Rollback** (`rollbackOf`, `runSteps`): a failure at stop or fetch only starts the service again and waits for its answer; at any later step — stop, check out the commit it started from, install, build, start, answer; a package's — stop, install the version it started from (`restore`), start, answer. A failed stop in the rollback is ignored (the service may be down already); any other failed rollback step ends it, recorded as `rollback.failed`.
- **The outcome** is written to `logs/update.json` of the data folder (a temporary file and a rename: the new service reads it at its start), the log of every step and its output to `logs/update.log` (appended). Neither is under `state/`, so they are no state format. The service reads the record at its start and again whenever the file changes (`watchFile`, every 5 s): the process writes it only after its answer step, so after the new service has started (found live in BTN-272). It logs it, and the page shows it as a toast until `updates/seen`. A record that does not end on the running version (`leftRunning`: one that went through ends on its target, a failed one on the version it came from, a failed rollback on either) is left out — no result and no "Revert" — since `even-keel update` from a terminal or a `git pull` by hand moved the install after it; the file stays, the log says so (BTN-315). After a revert the newer release is offered again as "Update": the button is an offer, nothing updates by itself. A process that could not even be started (no `dist/src/updates/run.js`) is a `launch` failure, kept in memory.
- **Rebuild mode.** Both rebuild scripts run the temporary copy of the updater in the foreground. It checks the clean checkout against the requested SHA after compiling. Before stopping the hub it reads `startedAt`, the running version and `hubCommit` from `/api/state`. This commit is the one the hub captured at startup and includes in its version refusal to machines. For an older hub without that field, the last rebuild record can identify the commit if its rebuild or rollback started this very process on the recorded version. An older hub restored this way reports the outcome in the update log. Without a known running commit the script exits before stopping the hub. To bootstrap such an installation, build and restart the intended checkout once.
- **A chain merging meanwhile** (BTN-1426). A chain session runs on through the rebuild (it lives in the agent's daemon, not in the service) and may merge its branch into the checkout mid-build; the settling waits only for launches, handovers and closings. So the updater compares HEAD with the target again at the stop and after each build with the service down (`drift` in `runner.ts`). HEAD moved on along the same branch (the target is its ancestor, the tree clean) — the new HEAD and the version of its `package.json` become the target, one log line names both commits, and `npm install` when `package-lock.json` changed and the build run again, until HEAD holds still, `CATCH_UP_BUILDS` (3) more builds at most; then the run fails. A rebuild that builds before the wait sees it at the stop: with `package-lock.json` unchanged it builds again with the hub still up and waits for the chains again, `CATCH_UP_BUILDS` times at most, and only then stops it (BTN-1527: built with the hub down, 8 of 11 restarts of 20–22.11.2026 kept it down 74–173 s); a changed lock, or HEAD still moving after them, stops it first and builds after. Anything else — another branch, a rewound branch, tracked changes — fails at the stop with the hub left running, as before; seen after the build, it is left to the answer, which fails on the commit, and to the rollback. A merge between the stop and the start (BTN-1479) brings the service up on the new HEAD: the answer sees it answering with the commit the checkout moved on to along its branch and fails at once instead of waiting out its 2 minutes, so the rollback builds that commit. `logs/update.json`'s `to` is the commit built last.
- If the new service fails to start or answer from the target SHA, the updater waits for the chains to settle as before the first stop (a service that came up may be launching the next task, BTN-1479), stops it, restores the previous commit on the checkout’s branch (a detached HEAD stays detached), runs `npm ci` and `npm run build`, starts the service and checks its answer. The rollback never resets the branch under a merge: a checkout moved on along it is built and started where it is instead (`rollback.to` in `logs/update.json`, the answer expected from that commit), and one moved or edited otherwise is left for inspection, the failure marked `moved`. The result records both commits and any failure of the rollback in `logs/update.json`. The page shows which rebuild failed and which commit came back, the one a rollback went on to, or that the moved checkout stopped the rollback (`rebuildMoved`), never that the rollback failed. The existing once-per-commit rule lets the next green push try again.
