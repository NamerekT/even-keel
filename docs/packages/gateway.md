# Packages: the gateway, launch and the check

## The gateway (`gateway.ts`)

- Error diagnostics share OAuth's credential redaction (`src/error-reason.ts`): placeholder values (including arguments and URLs), the target environment, literal environment values and headers, and generated HTTP-mode variables are removed, along with common OAuth fields and Bearer/Basic credentials. Errors are normalized and limited to 500 characters before logging or deduplication; a recovery still logs once. Stderr keeps the last nonempty line, including an unterminated one, and joins chunks before redaction; a line over 2000 characters becomes `[stderr line truncated]` instead of exposing a partial credential. Each launch uses its resolved settings and keys, so changes and restarts need no saved redaction state.

- `http://127.0.0.1:<EVEN_KEEL_MCP_PORT>` (4748 by default), never another interface: Tailscale Service forwards 4747 to localhost, not this port. The route is `/mcp/<project GUID>/<package>@<install id>/<server>`; the gateway finds the install and the project's current settings by it, so a session resumed with its saved flags reaches its server after a restart of the service.
- A Claude session that lives through a restart without a resume can lose a bridged stdio server for good (BTN-1529, CLI 2.1.330, read from the CLI's own MCP logs, `%LOCALAPPDATA%\claude-cli-nodejs\Cache\<folder>\mcp-logs-<server>\`). Only a bridge keeps a GET stream open; the tasks and memory servers answer `GET` with 405, hold nothing between calls and come through any restart. The Windows service kills node (`Process.Kill()`, `service/EvenKeelService.cs`), so `McpGateway.close()` never runs and every stream is reset. The CLI counts the reset and its SDK's two `GET` retries a second later, both `ECONNREFUSED`, as three terminal errors in a row, closes the transport and tries 5 reconnects 1.2, 2.2, 4.7 and 8.8 s apart: about 18 s after the drop it gives up. A restart on the PC is down 19–27 s, the service's start alone about 17 s. The server then stays `failed` until the session's process starts again (a resume), and the transcript's `deferred_tools_delta` only shows it on the next turn, minutes later. In the same session the `forgejo` bridge logged no drop at all, and why is not known.
- So the port is taken at the very start (BTN-1544, `held-port.ts`): `src/start.ts` holds `EVEN_KEEL_MCP_PORT` right after `.env` is read, before the storage and the service, and keeps every request unanswered, its body unread, until `McpGateway.listen` takes the server over and answers them in order. The CLI's reconnects then meet a port that accepts within the first seconds of the new process, and a held request is no error to it; the old route gets the gateway's usual answer once it is ready. A port that cannot be taken (the old process still on it) leaves the hold out and the gateway listens as before, reporting the same error. A start blocked on the storage gives the port back first, answering what waited with 503, and the hub's gateway (port 0) never takes a hold. A Windows stop still kills node: the graceful stop was weighed and left out.
- A bridge's `GET` stream was also cut after about 358 s with no bytes, restart or not, every 360 s after (CLI 2.1.330). The CLI counts each cut as a terminal error, and a `GET` that comes back does not reset the count: only a message does. So every ~18 minutes it closed the transport and sent `initialize` again, which started a new bridge and process, while the old one waited out `IDLE_MS` (30 min). The cut is the client's (BTN-1543): `node:http`'s `requestTimeout` and `headersTimeout` end once a `GET` is read and never touch an open response, while Bun's `fetch`, which the CLI's binary is built on, fails a body that brings nothing for 300 s (`TimeoutError` at 301 s, Bun 1.3.11, while a stream given a comment every 30 s was still open at 450 s). So each open `GET` stream of a bridge gets an SSE comment `: keep-alive` every 30 s (`STREAM_PING_MS`); an SSE parser skips it, so it is no message to the session. An open stream is also a live session: a bridge does not close idle while one is open, and its 30 minutes start when the last one closes. A session that dies closes its socket, so its bridge still goes.
- A tracker profile with an MCP OAuth grant (BTN-475, `docs/trackers.md`, "MCP through OAuth") replaces only `Authorization` of a remote server whose URL is its provider's fixed MCP address (same origin and path, no credentials in the URL): the entry's other headers stay, and its `Authorization` key is no longer required. The gateway sends `Bearer <access token>`, never the old Basic header; a 401 gets one refresh and one retry, a second 401 marks the grant for reconnecting. Redirects are refused, so a token never follows one. A request the gateway fails with an error (no token, a refused grant, a server gone) logs `<package>/<server>: <error>` once until the error changes, and `<package>/<server> works again` once a request of that project goes through (BTN-589).
- A remote HTTP server is proxied with its headers filled from the pool. A stdio server with a known HTTP mode (`HTTP_MODES`, by npm package; Huly: `MCP_TRANSPORT=http`, `MCP_HTTP_HOST`, `MCP_HTTP_PORT`, `MCP_AUTH_TOKEN`, path `/mcp`) runs once per route and environment on a free port with a random bearer token. It is ready once it answers HTTP at all (a `GET` of its path, any status, up to 60 s), not once its port accepts: huly-mcp listens before it attaches its handler, and a request in that gap (150–400 ms on the PC, longer on a slow machine) was never answered — the first `initialize` hung for the probe's 30 s, then 30 s more to the next probe (EKR-6). The log says `<package>/<server> started in N s`. Any other stdio server gets a bridge in the gateway: a child process per MCP session (`Mcp-Session-Id`), JSON replies, `GET` for the server's own messages as SSE, closed by `DELETE` or after 30 minutes with no request and no open `GET` stream.
- A machine elsewhere may run a stdio server with a command and arguments of its own (BTN-994, `docs/settings/levels.md`, "A machine in a project"): its brief's `servers` give them, and `packageTarget` puts them in place of the catalog's entry (`withOverride`, `src/packages/stdio.ts`) before the settings and the placeholders. `Packages.localStdio` lists the stdio servers a project's gateway starts itself, not those carried to the hub (`hubServers`), for the page's fields and the connection's check.
- On Windows a stdio command that is not `node` or an `.exe` (`uv`, `npx`) runs through `cmd.exe`, which gets one joined line: every argument with a space or a shell character is quoted (`shellQuoted`), otherwise a path like `…\Claude Extensions\…` falls apart.
- No token between the session and the gateway; instead `refusal()`: `Host` must be 127.0.0.1 or localhost (DNS rebinding), a request with `Origin` is refused (a browser page), a `POST` must be `application/json` (a browser cannot send it without a preflight).
- Even Keel's own tasks server (BTN-768, `docs/trackers/tasks-server.md`, "The tasks server") is answered in the gateway, after `refusal()`: `/tasks` and `/tasks/<project GUID>` for sessions started by hand, and any package route whose server entry is a local address with the path `/tasks` (`isTasksUrl`, the `tasks` plugin's `.mcp.json`) with the route's project and the `?task=` that `sessionPackages` appends. Streamable HTTP with JSON replies only: a single message or a batch, 202 when nothing needs a reply, 405 for `GET` and `DELETE` (no stream, no MCP session).
- Even Keel's own memory server (BTN-1029, `docs/sessions/memory.md`) is answered the same way, for a package route whose server entry is a local address with the path `/memory` (`isMemoryUrl`, the `agent-bridge` plugin's `.mcp.json`), with `?task=` too; only by the hub's gateway: a machine's carries every call of a memory route to the hub, also before its brief lists the route in `Packages.hubServers()`. Before BTN-1733 it answered 404 to a route its brief did not have yet, so the first probe of a project just added (the hub's own machine too) failed, and `agent-bridge` showed `noResponse` with a red line in the events for minutes until a later probe. It has no route for sessions started by hand, which keep the file memory, and `sessionPackages` leaves it out of a Claude Code chain session's servers too (`readsFileMemory`, BTN-1647): only agents without the CLI's file memory get it.
- Once the link starts, the gateway is the machine's (BTN-990, `docs/machines/link.md`, "MCP through the hub"). A server that holds a key and the tasks server run only in the hub's second gateway, which listens on a free port of 127.0.0.1, and the machine's gateway carries their requests over the link. The hub applies `hubOwned` and publishes only route paths through `Packages.hubServers()` / `GatewayHub.servers` (BTN-1238), including old pinned installs. The machine checks the list before resolving a target: it needs none of the hub's keys or server entries for these routes. The tasks server's package routes are excluded so its local stand-in still handles offline reads, queued writes and files. Every other server still runs in the machine's gateway. `/tasks` also takes `?task=`, the task of the chain session whose call the machine carries.
- A machine elsewhere has no catalog of its own to edit: it follows the hub's from the brief, its installs under the hub's ids (BTN-1299, `Packages.follow`, `docs/machines/link.md`, "MCP through the hub").
- The gateway cannot listen → `PackagesView.gateway` and every chain waits (the red banner; each project's own line points at it).
- Protection's tracker groups (BTN-541) live here, so they hold for every agent, Codex too. A server whose name is a tracker adapter's `mcpServer` gets `refuseDeletes` (the tracker's title) unless the project's effective Protection disables that tracker's group (`TRACKER_GROUPS`). A `tools/call` that deletes a record — the word `delete` in the tool's name, or `destructive` (Jira's `executeDestructive`, whatever operation it runs, BTN-659), or an `arguments.method` with the word `delete` (`deletesRecord`: `delete`, gitea-mcp's `delete_comment`, `deleteLabel`; BTN-476), or a dispatcher calling such a tool (BTN-641: a tool with `invoke`, `call`, `execute` or `run` in its name, such as Huly's `invoke_tool`, naming the tool in `toolName`, `tool_name`, `name` or `tool` and its arguments in `arguments`, `args`, `params`, `input` or `inputs`, an object or its JSON text, nested to any depth; a tool name in the arguments of any other tool, such as `get_tool_schema`, is a read and passes) — never reaches the server: the gateway answers it with a tool result `isError: true` saying the user must delete it or turn the tracker off; in a batch the other requests get `-32600` and nothing is sent. The log says `mcp gateway: <route>: Protection refused <tools>`. A tracker server outside the project's packages is not behind the gateway and is not covered.

## Launch

- Claude (`src/claude/cli.ts`): `--mcp-config <JSON>` and `--strict-mcp-config` before the other flags (`--mcp-config` takes several values and would swallow the prompt), `--plugin-dir` per plugin of the set, and in `--settings` `enabledPlugins: false` for every other enabled plugin (`otherPlugins`). `--strict-mcp-config` cuts off `.mcp.json` of the folder and its parents, user and local scope and the plugins' own MCP: every MCP server goes through `--mcp-config`. A plugin's server is named `plugin_<plugin>_<server>`, so its tools stay `mcp__plugin_huly_huly__*` and the plugin's hooks and permission rules keep working; an MCP package's server keeps its own name.
- `--bg --resume` of a stopped session wakes it with its saved flags (`respawnFlags` in `jobs/<id>/state.json`).
- Codex (`src/codex/mcp.ts`): `-c mcp_servers.<server>.url=<gateway address>` per server, no keys in the turn's environment; a plugin's server is named `plugin_<plugin>_<server>` as in Claude Code.
- Codex reads a Claude Code plugin's skills and hooks (`src/codex/plugins.ts`, BTN-180); commands and agents stay out. Every install is its own marketplace `ek-<install id>`: `Packages.startOf` writes `state/packages/<package>/<install id>/.claude-plugin/marketplace.json` beside the copy (one plugin, `source: "./plugin"`) on its first session (`ensureMarketplace`). On the first turn of a plugin in a Codex folder, `codex app-server` installs it (`plugin/install`, into `<folder>/plugins/cache/<marketplace>/<plugin>`) and turns it off again in the folder's `config.toml` (`config/value/write`), so the user's own Codex sessions do not get it; a folder whose cache already has that directory is not installed into again. Each first turn of a plugin in a folder per service run logs one line, `codex plugins: <plugin>@<marketplace> installed into folder <tag> in <n> s` or `… found in the cache of folder <tag>`, where the tag is the first 8 hex digits of the SHA-256 of the folder's path (the path and the account stay out of the log); later turns log nothing, so the count of these lines in a run is the count of `plugin/install` calls and cache hits (EKR-65). Then `hooks/list` gives the hashes of its hooks, kept in memory while the service runs (a new hash format takes a service restart). The hash trusted is the hook's own: from 0.164.0 `currentHash` is `sha256:<hook>/sha256:<plugin contents>`, and `trusted_hash` accepts only the part before the `/` — the whole value or the plugin's half reads `modified`, no `hooks.state` reads `untrusted`, and either way the hooks are skipped (EKR-29). Before the hashes are kept, `hooks/list` is asked once more with the turn's own flags (below); a hook of the plugin not `trusted` there (or gone from the answer) is the notice `codex.hooksUntrusted`, which names the package, the CLI version and each hook's key with its `trustStatus`, and the launch fails, so a change of the format cannot run the chain without `merge-check`, the context reminders and the mail. A failed install is the notice `codex.pluginsFailed` and the launch fails.
- Every Codex turn then gets `-c` flags: the marketplace (`source_type = "local"`, its folder), the plugin on, the plugin's own MCP servers off (the gateway serves them), every other plugin of the folder's `config.toml` off (as `otherPlugins` for Claude; a key with a `.` cannot be named in `-c` and stays as it is), and `hooks.state` with the hooks trusted by their hash, as one inline table: Codex skips an untrusted hook without a word. No `--ignore-user-config`: it would also drop the folder's `model`, project trust, `[windows] sandbox`, `notify` and memory, so the MCP servers of the folder's `config.toml` still reach Codex sessions. A plugin with skills, hooks, commands or agents is marked `unsupported` only for an agent that does not read all of it (`pluginReach` in `src/agent/projectRules.ts`): OpenCode, which gets the skills, and an agent outside the table.
- OpenCode (`src/opencode/cli.ts`, `sessionConfig`, BTN-214): the gateway's servers as `remote` servers in `OPENCODE_CONFIG_CONTENT`, the project's own `opencode.json(c)` servers turned off by name (no `OPENCODE_DISABLE_PROJECT_CONFIG`: it drops the project's instructions too); the servers of the account's own config still reach it, as with Codex. A plugin's `skills/` goes into `skills.paths` (with the project's own `.claude/skills` and `.agents/skills`, `skillDirs`, `docs/sessions/opencode.md`), and the scripts of its `opencode/` folder into `plugin` (`pluginFiles`, BTN-274: OpenCode's hooks are JS plugins, so a package brings its own, as `agent-bridge` and `huly` do); its Claude Code hooks, commands and agents do not reach OpenCode. The Huly plugin (`opencode/huly.mjs`, from 0.5.8) checks writes to `plugin_huly_huly_(create|update|add)_*` before execution with the command hook's markdown refusal and estimate calibration; an allowed call gets calibration after its result, once per session and project. The package check still marks plugins with Claude Code extras `unsupported` with `skills: true`, shown as "no hooks" (`pluginReach`, read by `check.ts`), even when they bring OpenCode scripts; it does not hold the chain.
- Copilot (`src/copilot/cli.ts`, BTN-215): the gateway's servers as `--additional-mcp-config` (`type: "http"`, `tools: ["*"]`), and since Copilot has no strict mode, `--disable-builtin-mcps` and `--disable-mcp-server` for each server of the project's `.mcp.json`, `.github/mcp.json`, `.vscode/mcp.json`, the account's `mcp-config.json` and the set's plugins (`ownServers`). A plugin goes as `--plugin-dir`, which Copilot loads in the Claude Code format with its skills and hooks: its `pluginReach` is `all`, as for Claude and Codex, so it is not marked `unsupported`. Command-hook execution was checked live on 1.0.98 on Windows on 2026-10-25 by `cli-check`: the agent-bridge package sent `/mail` and `/checkpoint` requests for the test session. Skill loading and full hook-driven handoffs remain unchecked (`docs/unverified.md`).
- The project's standards (BTN-359, `docs/sessions/protection.md`, "Project standards") come with the `agent-bridge` package, so each agent gets them its own way above: Claude Code and Codex from the plugin's hooks (Codex's edit is `apply_patch`), Copilot from the same hooks in the Claude Code format with its own tool names (`view`, `edit`, `create`, `str_replace` — not seen live, `docs/unverified.md`), OpenCode from `opencode/agent-bridge.mjs`. A project without the package's hooks gets no standards.
- `agentExtras` computes the packages before `settingsFor`: each launch of a task updates its pin (`startOf`), and `otherPlugins` names the same set (`installsFor`).

## The check before a launch (`check.ts`)

- Problems of a package in a project: `notInstalled`, `installing`, `installFailed`, `noKey` (with the variables), `noResponse` (the probe — `initialize` through the gateway; a success lives 5 minutes; failures in a row are retried after 30 s, 1, 2, 5, 15, 30 minutes, then once an hour (`PROBE_FAILED_MS`, BTN-589), back to 30 s after a success or any change of the tracker profiles, a save or a new grant (`Probes.retry`); while the project's chain runs, not paused (the machine's brief, `PackagesDeps.waited`), at least once a minute (`PROBE_WAITED_MS`), and at once when a brief brings a chain started or resumed (BTN-1518): the own machine of a hub, left out of a project's pool for an hour, has its probes of the hub's servers (`memory`, `tasks`) refused with 403 (`HubMcp`), and once it was put back into the pool its chain waited for the hour's probe; a failed answer, a server gone, or silence after the server has answered once; for a server that has answered, only the second such miss in a row: the first stays `probing`, asked again in 30 s, since a short drop of the host's network failed every outside call at once and wrote "does not answer" for a healthy server (`Probes.run`, BTN-1248); before its first answer a failed one counts at once), `probing` (shown as a spinner beside the package's switch in the project's packages, "starting" in its tip, not a problem line: it passes in seconds after every service start; no answer yet since the service started or the package was installed, including probes that timed out at 30 seconds, asked again at once rather than in 30 seconds; nothing is asked before the gateway listens, so the first state build of a start is never `noResponse` (BTN-1225); held too, so the chain does not start on a server nobody has asked; the gateway logs `<package>/<server> did not answer initialize in N s, still starting`), and of the set: `noTrackerMcp` when `brief` is explicitly `false` and no enabled package brings the tracker's server — nor `tasks` for a tracker Even Keel's tasks server serves (`servesTasks`, BTN-882; `CheckInput.tracker.also`) — (the auto `brief` turns itself on then instead; not under the banner: the chain pauses on `chain.noTrackerMcp` with two buttons beside it, `docs/chain/pr-mode.md`, BTN-656). `unsupported` is only a mark. Whatever `brief` is, `ProjectPackages.tracker` tells the page the tracker's server and whether a package of the set brings it (`null` for a tracker without one; `PackagesDeps.tracker`, EKR-5), with `through: 'tasks'` when only the tasks server does: the page then names `tasks@even-keel` as the package that brings it and offers no tracker plugin. `also: 'tasks'` says the tasks server serves the tracker, so the page offers it first (BTN-874); `both` — the set brings the tracker's own server and the tasks server at once, which is a warning on the page and holds nothing.
- While a project has a problem that holds it (`blocked`), the dispatcher launches nothing for it (`packagesBlocked`) and goes on by itself once the problem is gone. What only the user fixes — an enabled package `notInstalled`, `installFailed` or with `noKey` (`NEEDS_USER` in `src/packages/check.ts`, `Packages.unready`) — pauses the chain instead (BTN-657): the `packagesPause` hook gives `chain.packagesNotReady` with the packages, checked by every launch, Start, Resume and `wake` like `noTrackerMcp` (`SELF_CLEARING`, so Start and Resume go in paused and the pause lifts by itself once the packages are ready), with "Open the project's packages" (`/p/<id>?pkg=1`) beside it. `installing`, `probing`, `noResponse` and the gateway stay waits: the project's chip says "waiting · packages" (or "· gateway") and its card and page a line naming each package and its problem (`chainWaits` in `web/src/waits.ts`, `ChainWaits.tsx`), with the same button for `noResponse`. `PackagesBanner` shows only the gateway, since it holds every project. A fix session of a red main neither waits nor pauses.
