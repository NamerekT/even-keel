# Packages (BTN-174, `src/packages/`)

What chain sessions get besides the CLI's own tools: plugins and MCP servers, as a set per project, given by flags at every launch. Even Keel keeps the packages, their versions and the keys; the settings files of the accounts and the repositories are not written. Sessions started by hand live by their own `settings.json` and `settings.local.json` and get none of this.

## The file and the cache

- `state/packages.json` (schema v14): `packages` by name, `projects` and `pins` by project GUID like every file of `state/` (`store.ts` renames to keys and back). A package is `kind` (`plugin` — `plugin: { name, marketplace }`; `mcp` — `server`, an entry as `.mcp.json` writes it), `default` (in every project that does not turn it off), `settings` (user overrides of `env` of a stdio server or headers of an HTTP one), `installs` (oldest first, the last one current: `{ id, version, at, servers, extras }`), `removed`. A project has `on`, `off` and its own `settings` per package. `pins[<project>][<task>]` is the install of each package the task started on.
- A plugin package is named as `enabledPlugins` names it, `<plugin>@<marketplace>`; an MCP package by its server's name.
- The cache is `state/packages/<package>/<install id>/`: `plugin/` (a copy of the plugin) and `servers/<server>/` (an npm install of a pinned stdio server). An install no pin holds and that is not current loses its files (`prune`); a removed package stays while a running task holds it.
- No file yet (the first start after the upgrade): the catalog is seeded from what sessions got before (`seedPackages` in `plugins.ts`) — the plugins enabled in the global `settings.json` (on by default), the plugins enabled only in a project's `.claude/settings.json` or `settings.local.json` (on in that project), the user scope servers of `.claude.json`; all of them are installed in the background. So the upgrade does not break a running chain.
- Since schema v14, `settings` holds only user overrides. The page combines the current install's literal environment values or HTTP headers with the package's overrides and then the project's overrides; the gateway applies only overrides to the requested install's server entry, so pinned tasks keep their own defaults. Saving a value equal to the inherited one removes the override; `null` resets it. Migration from older schemas drops package values equal to the current install's defaults (or the source server entry before the first MCP install), then project values equal to the inherited package value. Other values, including values whose original default is no longer known, remain unchanged; pins and install entries are kept.

## Install and update

- A plugin comes from Even Keel's own marketplace or from one the global configuration knows (`known_marketplaces.json`): a source path inside the marketplace is copied from its folder, another source (github, url) from the CLI's cache (`installed_plugins.json`); a plugin the CLI has not installed is refused with "install it in Claude Code first" (`packages.installInClaude`).
- Even Keel's own marketplace (BTN-226) is the `.claude-plugin/marketplace.json` of its checkout (`ownDir`, `ownMarketplace`): its plugins are offered and copied from the checkout with no `claude plugin marketplace add`, as a `directory` marketplace, and it wins over a marketplace of the same name the CLI knows (say, one added from a git URL), so chain sessions get the plugins of the running version. Claude Code still needs it for sessions started by hand: while the global configuration does not know it (`PackagesView.marketplace.known`), `/tools` shows the command with an "Add to Claude Code" button (`packages/marketplace` → `claude plugin marketplace add <checkout>` in the global configuration, `packages.marketplaceAdd` on failure), dismissed in `localStorage`.
- The marketplaces' plugin lists, and whether the own one is known, are read again at most once a minute (`AVAILABLE_MS`) and at once after the button: a marketplace added in a terminal shows up in "Add a package" within a minute, as its empty search says.
- A stdio server `npx -y <package>@<range>` is pinned (`npm.ts`): `npm view` gives the version, `npm install --prefix <cache>` installs it, the command becomes `node <bin of package.json>`. Other commands run as they are, unpinned. The log times an install: `installing <package>`, `npm install <spec> took N s` per pinned server, `<package> <version> installed in N s` (a cold `npm install @firfi/huly-mcp` on the PC: 20 s, 102 MB, EKR-6).
- "Update": for a git or github marketplace first `claude plugin marketplace update <m>` in the global configuration, then a new install next to the current one if the plugin's version or any npm server's changed; otherwise `packages.upToDate`.
- Updating an install does not copy its defaults into `settings`: untouched settings follow the new install, while package and project overrides remain. The effective values in `PackageView.settings` and `ProjectPackages.cells[].settings` are computed, not the persisted override maps.
- What Update would bring: `PackageView.latest` is the version of the plugin where `locatePlugin` finds it (`pluginOffer`), when it is later than the install (`isNewer`, `version.ts`); read again at most once a minute and after an update fetched the marketplace. For a fetched marketplace it is only as fresh as the CLI's last fetch (`lastUpdated` of `known_marketplaces.json`, `PackageView.fetched`; Claude Code fetches them on its own start too): the page says so in the tip, Even Keel fetches nothing on a timer. An MCP package has no `latest`: npm is not asked until Check. A running task, its `--resume` and its handoffs stay on the install they started on (`pins`); the task's pins go when it is done (`release`).

## The user's own skills (`skills.ts`, BTN-339)

- The skills of `~/.claude/skills` (the global folder's `skills`), `$CODEX_HOME/skills` and `~/.agents/skills` reach only their own agent. "Add a package → My skills" (`SkillsStep` in `AddPackage.tsx`, `packages/skills` with `skills` and `project`) wraps the ticked ones into the plugin `my-skills` of the marketplace `even-keel-skills` in `state/skills/` (`.claude-plugin/marketplace.json`, `plugin/{.claude-plugin/plugin.json, skills/<name>}`, links followed), which is one more of Even Keel's own folders beside its checkout (`marketplaces` in `plugins.ts`), so the package `my-skills@even-keel-skills` installs, updates and pins as any plugin. The folder is the state: the chosen skills are the subfolders of `plugin/skills`, so no file of `state/` changed its format.
- The version is `1.0.0+<8 hex>` of every file's path and bytes (`skillsVersion`): the build part leaves no order, so `latest` is any other version (`skillsChanged`). Once a minute with the other marketplaces, and before an Update, the wrapped skills are copied from their folders again (`rewrapSkills`), so an edit shows as `→ <version>`; a skill whose folder is gone keeps its copy (`from: null`, "its folder is gone").
- A second save of the step makes a new install of the package in the catalog and leaves its projects as they are; the plugin does not show in the plugin step's list (`available`).
- Claude Code sessions do not get it (`readsOwnSkills`, `startOf` drops its `--plugin-dir`): they read the same skills from their account folder, and the plugin would list them twice as `my-skills:<name>`. A Codex session does get a skill of Codex's own folder twice, its own and the plugin's.

## Keys

- A pool per project (`keyPool` in `src/profiles/model.ts`, `PackagesDeps.poolOf`): Even Keel's own `.env` without any profile variable, then the values of every default profile, then the profiles of the project's task feeds (BTN-66, `docs/chain.md`), then the project's own profile on top (BTN-200, `docs/trackers.md`, "Profiles"). So the tracker's server of a project gets its profile's account, a package that reads `GITHUB_TOKEN` in a Huly project gets the default GitHub profile's, and the `forgejo` server gets `FORGEJO_TOKEN` of the default Forgejo profile (BTN-201). The page writes a `.env` key into `.env` (`upsertEnv`) and `process.env`, and sees only whether it is set; the "Keys" panel of `/tools` no longer lists tracker variables — they are the profiles' rows on Trackers and CI of `/settings`. The gateway takes a new key or a changed profile at once.
- `${…}` placeholders of a server entry are filled from the pool (`keys.ts`). `${NAME:-default}` reads as in Claude Code: the key is listed, but the server is not held without it and gets the default. A placeholder that names the same key differently (`GITHUB_PERSONAL_ACCESS_TOKEN` ← `GITHUB_TOKEN`, `LINEAR_API_KEY` ← `LINEAR_TOKEN`) is declared by the adapter's `mcpKeys`. The tracker's stdio server (`mcpServer` of the adapter) gets the adapter's variables from the pool.
- Sessions do not get the pool: `sessionBase` drops every variable a package or a tracker reads.

## The gateway (`gateway.ts`)

- `http://127.0.0.1:<EVEN_KEEL_MCP_PORT>` (4748 by default), never another interface: Tailscale Service forwards 4747 to localhost, not this port. The route is `/mcp/<project GUID>/<package>@<install id>/<server>`; the gateway finds the install and the project's current settings by it, so a session resumed with its saved flags reaches its server after a restart of the service.
- A remote HTTP server is proxied with its headers filled from the pool. A stdio server with a known HTTP mode (`HTTP_MODES`, by npm package; Huly: `MCP_TRANSPORT=http`, `MCP_HTTP_HOST`, `MCP_HTTP_PORT`, `MCP_AUTH_TOKEN`, path `/mcp`) runs once per route and environment on a free port with a random bearer token. It is ready once it answers HTTP at all (a `GET` of its path, any status, up to 60 s), not once its port accepts: huly-mcp listens before it attaches its handler, and a request in that gap (150–400 ms on the PC, longer on a slow machine) was never answered — the first `initialize` hung for the probe's 30 s, then 30 s more to the next probe (EKR-6). The log says `<package>/<server> started in N s`. Any other stdio server gets a bridge in the gateway: a child process per MCP session (`Mcp-Session-Id`), JSON replies, `GET` for the server's own messages as SSE, closed by `DELETE` or after 30 minutes idle.
- On Windows a stdio command that is not `node` or an `.exe` (`uv`, `npx`) runs through `cmd.exe`, which gets one joined line: every argument with a space or a shell character is quoted (`shellQuoted`), otherwise a path like `…\Claude Extensions\…` falls apart.
- No token between the session and the gateway; instead `refusal()`: `Host` must be 127.0.0.1 or localhost (DNS rebinding), a request with `Origin` is refused (a browser page), a `POST` must be `application/json` (a browser cannot send it without a preflight).
- The gateway cannot listen → `PackagesView.gateway` and every chain waits (the red banner).

## Launch

- Claude (`src/claude/cli.ts`): `--mcp-config <JSON>` and `--strict-mcp-config` before the other flags (`--mcp-config` takes several values and would swallow the prompt), `--plugin-dir` per plugin of the set, and in `--settings` `enabledPlugins: false` for every other enabled plugin (`otherPlugins`). `--strict-mcp-config` cuts off `.mcp.json` of the folder and its parents, user and local scope and the plugins' own MCP: every MCP server goes through `--mcp-config`. A plugin's server is named `plugin_<plugin>_<server>`, so its tools stay `mcp__plugin_huly_huly__*` and the plugin's hooks and permission rules keep working; an MCP package's server keeps its own name.
- `--bg --resume` of a stopped session wakes it with its saved flags (`respawnFlags` in `jobs/<id>/state.json`).
- Codex (`src/codex/mcp.ts`): `-c mcp_servers.<server>.url=<gateway address>` per server, no keys in the turn's environment; a plugin's server is named `plugin_<plugin>_<server>` as in Claude Code.
- Codex reads a Claude Code plugin's skills and hooks (`src/codex/plugins.ts`, BTN-180); commands and agents stay out. Every install is its own marketplace `ek-<install id>`: `Packages.startOf` writes `state/packages/<package>/<install id>/.claude-plugin/marketplace.json` beside the copy (one plugin, `source: "./plugin"`) on its first session (`ensureMarketplace`). On the first turn of a plugin in a Codex folder, `codex app-server` installs it (`plugin/install`, into `<folder>/plugins/cache/<marketplace>/<plugin>`) and turns it off again in the folder's `config.toml` (`config/value/write`), so the user's own Codex sessions do not get it; then `hooks/list` gives the hashes of its hooks, kept in memory while the service runs (a new hash format takes a service restart). The hash trusted is the hook's own: from 0.164.0 `currentHash` is `sha256:<hook>/sha256:<plugin contents>`, and `trusted_hash` accepts only the part before the `/` — the whole value or the plugin's half reads `modified`, no `hooks.state` reads `untrusted`, and either way the hooks are skipped (EKR-29). Before the hashes are kept, `hooks/list` is asked once more with the turn's own flags (below); a hook of the plugin not `trusted` there (or gone from the answer) is the notice `codex.hooksUntrusted`, which names the package, the CLI version and each hook's key with its `trustStatus`, and the launch fails, so a change of the format cannot run the chain without `merge-check`, the context reminders and the mail. A failed install is the notice `codex.pluginsFailed` and the launch fails.
- Every Codex turn then gets `-c` flags: the marketplace (`source_type = "local"`, its folder), the plugin on, the plugin's own MCP servers off (the gateway serves them), every other plugin of the folder's `config.toml` off (as `otherPlugins` for Claude; a key with a `.` cannot be named in `-c` and stays as it is), and `hooks.state` with the hooks trusted by their hash, as one inline table: Codex skips an untrusted hook without a word. No `--ignore-user-config`: it would also drop the folder's `model`, project trust, `[windows] sandbox`, `notify` and memory, so the MCP servers of the folder's `config.toml` still reach Codex sessions. A plugin with skills, hooks, commands or agents is marked `unsupported` only for an agent other than Claude Code and Codex.
- OpenCode (`src/opencode/cli.ts`, `sessionConfig`, BTN-214): the gateway's servers as `remote` servers in `OPENCODE_CONFIG_CONTENT`, the project's own `opencode.json(c)` servers turned off by name (no `OPENCODE_DISABLE_PROJECT_CONFIG`: it drops the project's instructions too); the servers of the account's own config still reach it, as with Codex. A plugin's `skills/` goes into `skills.paths` (with the project's own `.claude/skills` and `.agents/skills`, `skillDirs`, `docs/sessions.md`), and the scripts of its `opencode/` folder into `plugin` (`pluginFiles`, BTN-274: OpenCode's hooks are JS plugins, so a package brings its own, as `checkpoint` and `huly` do); its Claude Code hooks, commands and agents do not reach OpenCode. The Huly plugin (`opencode/huly.mjs`, from 0.5.8) checks writes to `plugin_huly_huly_(create|update|add)_*` before execution with the command hook's markdown refusal and estimate calibration; an allowed call gets calibration after its result, once per session and project. The package check still marks plugins with Claude Code extras `unsupported` with `skills: true`, shown as "no hooks" (`pluginReach` in `check.ts`), even when they bring OpenCode scripts; it does not hold the chain.
- Copilot (`src/copilot/cli.ts`, BTN-215): the gateway's servers as `--additional-mcp-config` (`type: "http"`, `tools: ["*"]`), and since Copilot has no strict mode, `--disable-builtin-mcps` and `--disable-mcp-server` for each server of the project's `.mcp.json`, `.github/mcp.json`, `.vscode/mcp.json`, the account's `mcp-config.json` and the set's plugins (`ownServers`). A plugin goes as `--plugin-dir`, which Copilot loads in the Claude Code format with its skills and hooks: it is in `READS_PLUGINS` beside Claude and Codex, not marked `unsupported`. Command-hook execution was checked live on 1.0.98 on Windows on 2026-10-25 by `cli-check`: the checkpoint package sent `/mail` and `/checkpoint` requests for the test session. Skill loading and full hook-driven handoffs remain unchecked (`docs/unverified.md`).
- The project's standards (BTN-359, `docs/sessions.md`, "Project standards") come with the `checkpoint` package, so each agent gets them its own way above: Claude Code and Codex from the plugin's hooks (Codex's edit is `apply_patch`), Copilot from the same hooks in the Claude Code format with its own tool names (`view`, `edit`, `create`, `str_replace` — not seen live, `docs/unverified.md`), OpenCode from `opencode/checkpoint.mjs`. A project without the package's hooks gets no standards.
- `agentExtras` computes the packages before `settingsFor`: the first launch of a task pins it.

## The check before a launch (`check.ts`)

- Problems of a package in a project: `notInstalled`, `installing`, `installFailed`, `noKey` (with the variables), `noResponse` (the probe — `initialize` through the gateway; a success lives 5 minutes, a failure is retried in 30 seconds; a failed answer, a server gone, or silence after the server has answered once), `probing` (shown as a spinner on the corner of the project's select, "starting" in its tip, not a chip: it passes in seconds after every service start; no answer yet since the service started or the package was installed, including probes that timed out at 30 seconds, asked again at once rather than in 30 seconds; held too, so the chain does not start on a server nobody has asked; the gateway logs `<package>/<server> did not answer initialize in N s, still starting`), and of the set: `noTrackerMcp` when `brief` is explicitly `false` and no enabled package brings the tracker's server (the auto `brief` turns itself on then instead; the banner names the reason instead of "a package is not ready"). `unsupported` is only a mark. Whatever `brief` is, `ProjectPackages.tracker` tells the page the tracker's server and whether a package of the set brings it (`null` for a tracker without one; `PackagesDeps.tracker`, EKR-5).
- While a project has a problem that holds it (`blocked`), the dispatcher launches nothing for it (`packagesBlocked`) and goes on by itself once the problem is gone; the banner `PackagesBanner` names the projects, except those held only by `installing` and `probing`: after an import they pass in a second, and a banner coming and going shook the whole page. A fix session of a red main does not wait.

## The page

`/tools` starts with the packages table (`web/src/tools/Packages.tsx`): a row per package (kind, version, the install's error; Install when it has none, a primary Update with `→ <latest>` when the marketplace has a later version, a quiet Check otherwise — the same `packages/update`), a column per chosen project with on / off / default and the problems, its head a red lamp with the reasons in its tip only while the chain waits on something that does not pass by itself (`heldLong`, the same rule as the banner); a row opens to its servers, the default switch, the settings (for all and per project) and "Remove". Below: the keys (set or not, a new value), an offer to import the servers of a repository's committed `.mcp.json` (dismissed in `localStorage` until the list changes), an offer to add Even Keel's marketplace to Claude Code (`MarketplaceOffer`). "Add a package" in the head opens a dialog (`AddPackage.tsx`): the kind first, then a plugin of Even Keel's or a known marketplace, or an MCP server — a name, an address with headers (`Name: value` lines) or a command with its environment (`NAME=value` lines, a quoted argument kept whole), and where it is on: every project (`default`) or one (`project` of `packages/plugin` and `packages/server`, on there, off by default); or the user's own skills by checkboxes (`PackagesView.skills`, above). Commands: `POST /api/packages/{install,update,remove,marketplace,plugin,server,skills,import,project,default,setting,key}`; the data is `EvenKeelState.packages`.

The tracker's package in two clicks (EKR-5, `trackerPackage` and `trackerAddPath` in `web/src/tools/packageView.ts`). `/tools?projects=<key>&add=<plugin>@<marketplace>` opens the add dialog on its plugin step with that plugin and the first chosen project (`AddPlugin`); while Claude Code does not know Even Keel's marketplace (`marketplace.known === false`), the dialog first asks to add it — "Yes, add" runs `packages/marketplace`, "No" goes on, and either way the plugin step follows, since chain sessions do without it. Closing the dialog drops `add` with a replace, and a plugin no longer in `available` (the catalog has it already) only drops it. Two ways lead there: "Go to Tools" beside "Task description in the prompt" in the project's settings — active while no package of the project brings the tracker's server, whatever `brief` is, greyed with the package that does in its tip otherwise (on `/settings` there is no project, so no button) — and the project page's "What sessions get" plaque (`web/src/pages/ToolsLink.tsx`): its count adds `noTrackerMcp` to the settings problems, a line says the chain waits (`brief` off) or advises the tracker's plugin (auto or on), and its "Open →" takes the same path. When the catalog has the tracker's plugin but the project has it off, both lead to `/tools?projects=<key>` without `add`, where the table turns it on.
