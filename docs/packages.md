# Packages (BTN-174, `src/packages/`)

What chain sessions get besides the CLI's own tools: plugins and MCP servers, as a set per project, given by flags at every launch. Even Keel keeps the packages, their versions and the keys; the settings files of the accounts and the repositories are not written. Sessions started by hand live by their own `settings.json` and `settings.local.json` and get none of this.

## The file and the cache

- `state/packages.json` (schema v9): `packages` by name, `projects` and `pins` by project GUID like every file of `state/` (`store.ts` renames to keys and back). A package is `kind` (`plugin` — `plugin: { name, marketplace }`; `mcp` — `server`, an entry as `.mcp.json` writes it), `default` (in every project that does not turn it off), `settings` (the values projects start from: `env` of a stdio server, headers of an HTTP one), `installs` (oldest first, the last one current: `{ id, version, at, servers, extras }`), `removed`. A project has `on`, `off` and its own `settings` per package. `pins[<project>][<task>]` is the install of each package the task started on.
- A plugin package is named as `enabledPlugins` names it, `<plugin>@<marketplace>`; an MCP package by its server's name.
- The cache is `state/packages/<package>/<install id>/`: `plugin/` (a copy of the plugin) and `servers/<server>/` (an npm install of a pinned stdio server). An install no pin holds and that is not current loses its files (`prune`); a removed package stays while a running task holds it.
- No file yet (the first start after the upgrade): the catalog is seeded from what sessions got before (`seedPackages` in `plugins.ts`) — the plugins enabled in the global `settings.json` (on by default), the plugins enabled only in a project's `.claude/settings.json` or `settings.local.json` (on in that project), the user scope servers of `.claude.json`; all of them are installed in the background. So the upgrade does not break a running chain.

## Install and update

- A plugin comes from a marketplace the global configuration knows (`known_marketplaces.json`): a source path inside the marketplace is copied from its folder, another source (github, url) from the CLI's cache (`installed_plugins.json`); a plugin the CLI has not installed is refused with "install it in Claude Code first" (`packages.installInClaude`).
- A stdio server `npx -y <package>@<range>` is pinned (`npm.ts`): `npm view` gives the version, `npm install --prefix <cache>` installs it, the command becomes `node <bin of package.json>`. Other commands run as they are, unpinned.
- "Update": for a git or github marketplace first `claude plugin marketplace update <m>` in the global configuration, then a new install next to the current one if the plugin's version or any npm server's changed; otherwise `packages.upToDate`.
- What Update would bring: `PackageView.latest` is the version of the plugin where `locatePlugin` finds it (`pluginOffer`), when it is later than the install (`isNewer`, `version.ts`); read again at most once a minute and after an update fetched the marketplace. For a fetched marketplace it is only as fresh as the CLI's last fetch (`lastUpdated` of `known_marketplaces.json`, `PackageView.fetched`; Claude Code fetches them on its own start too): the page says so in the tip, Even Keel fetches nothing on a timer. An MCP package has no `latest`: npm is not asked until Check. A running task, its `--resume` and its handoffs stay on the install they started on (`pins`); the task's pins go when it is done (`release`).

## Keys

- A pool per project (`keyPool` in `src/profiles/model.ts`, `PackagesDeps.poolOf`): Even Keel's own `.env` without any profile variable, then the values of every default profile, then the project's own profile on top (BTN-200, `docs/trackers.md`, "Profiles"). So the tracker's server of a project gets its profile's account, a package that reads `GITHUB_TOKEN` in a Huly project gets the default GitHub profile's, and the `forgejo` server gets `FORGEJO_TOKEN` of the default Forgejo profile (BTN-201). The page writes a `.env` key into `.env` (`upsertEnv`) and `process.env`, and sees only whether it is set; the "Keys" panel of `/tools` no longer lists tracker variables — they are the profiles' cards on Access. The gateway takes a new key or a changed profile at once.
- `${…}` placeholders of a server entry are filled from the pool (`keys.ts`). `${NAME:-default}` reads as in Claude Code: the key is listed, but the server is not held without it and gets the default. A placeholder that names the same key differently (`GITHUB_PERSONAL_ACCESS_TOKEN` ← `GITHUB_TOKEN`, `LINEAR_API_KEY` ← `LINEAR_TOKEN`) is declared by the adapter's `mcpKeys`. The tracker's stdio server (`mcpServer` of the adapter) gets the adapter's variables from the pool.
- Sessions do not get the pool: `sessionBase` drops every variable a package or a tracker reads.

## The gateway (`gateway.ts`)

- `http://127.0.0.1:<EVEN_KEEL_MCP_PORT>` (4748 by default), never another interface: Tailscale Service forwards 4747 to localhost, not this port. The route is `/mcp/<project GUID>/<package>@<install id>/<server>`; the gateway finds the install and the project's current settings by it, so a session resumed with its saved flags reaches its server after a restart of the service.
- A remote HTTP server is proxied with its headers filled from the pool. A stdio server with a known HTTP mode (`HTTP_MODES`, by npm package; Huly: `MCP_TRANSPORT=http`, `MCP_HTTP_HOST`, `MCP_HTTP_PORT`, `MCP_AUTH_TOKEN`, path `/mcp`) runs once per route and environment on a free port with a random bearer token. Any other stdio server gets a bridge in the gateway: a child process per MCP session (`Mcp-Session-Id`), JSON replies, `GET` for the server's own messages as SSE, closed by `DELETE` or after 30 minutes idle.
- On Windows a stdio command that is not `node` or an `.exe` (`uv`, `npx`) runs through `cmd.exe`, which gets one joined line: every argument with a space or a shell character is quoted (`shellQuoted`), otherwise a path like `…\Claude Extensions\…` falls apart.
- No token between the session and the gateway; instead `refusal()`: `Host` must be 127.0.0.1 or localhost (DNS rebinding), a request with `Origin` is refused (a browser page), a `POST` must be `application/json` (a browser cannot send it without a preflight).
- The gateway cannot listen → `PackagesView.gateway` and every chain waits (the red banner).

## Launch

- Claude (`src/claude/cli.ts`): `--mcp-config <JSON>` and `--strict-mcp-config` before the other flags (`--mcp-config` takes several values and would swallow the prompt), `--plugin-dir` per plugin of the set, and in `--settings` `enabledPlugins: false` for every other enabled plugin (`otherPlugins`). `--strict-mcp-config` cuts off `.mcp.json` of the folder and its parents, user and local scope and the plugins' own MCP: every MCP server goes through `--mcp-config`. A plugin's server is named `plugin_<plugin>_<server>`, so its tools stay `mcp__plugin_huly_huly__*` and the plugin's hooks and permission rules keep working; an MCP package's server keeps its own name.
- `--bg --resume` of a stopped session wakes it with its saved flags (`respawnFlags` in `jobs/<id>/state.json`).
- Codex (`src/codex/mcp.ts`): `-c mcp_servers.<server>.url=<gateway address>` per server, no keys in the turn's environment; a plugin's server is named `plugin_<plugin>_<server>` as in Claude Code.
- Codex reads a Claude Code plugin's skills and hooks (`src/codex/plugins.ts`, BTN-180); commands and agents stay out. Every install is its own marketplace `ek-<install id>`: `Packages.startOf` writes `state/packages/<package>/<install id>/.claude-plugin/marketplace.json` beside the copy (one plugin, `source: "./plugin"`) on its first session (`ensureMarketplace`). On the first turn of a plugin in a Codex folder, `codex app-server` installs it (`plugin/install`, into `<folder>/plugins/cache/<marketplace>/<plugin>`) and turns it off again in the folder's `config.toml` (`config/value/write`), so the user's own Codex sessions do not get it; then `hooks/list` gives the hashes of its hooks, kept in memory while the service runs. A failed install is the notice `codex.pluginsFailed` and the launch fails.
- Every Codex turn then gets `-c` flags: the marketplace (`source_type = "local"`, its folder), the plugin on, the plugin's own MCP servers off (the gateway serves them), every other plugin of the folder's `config.toml` off (as `otherPlugins` for Claude; a key with a `.` cannot be named in `-c` and stays as it is), and `hooks.state` with the hooks trusted by their hash, as one inline table: Codex skips an untrusted hook without a word. No `--ignore-user-config`: it would also drop the folder's `model`, project trust, `[windows] sandbox`, `notify` and memory, so the MCP servers of the folder's `config.toml` still reach Codex sessions. A plugin with skills, hooks, commands or agents is marked `unsupported` only for an agent other than Claude Code and Codex.
- `agentExtras` computes the packages before `settingsFor`: the first launch of a task pins it.

## The check before a launch (`check.ts`)

- Problems of a package in a project: `notInstalled`, `installing`, `installFailed`, `noKey` (with the variables), `noResponse` (the probe — `initialize` through the gateway; a success lives 5 minutes, a failure is retried in 30 seconds; the first probe of `huly` after an install can time out at 30 seconds while the server logs in to Huly, and the retry passes), `probing` (the first probe of the install has not answered yet: held too, so the chain does not start on a server nobody has asked), and of the set: `noTrackerMcp` when `brief` is off and no enabled package brings the tracker's server. `unsupported` is only a mark.
- While a project has a problem that holds it (`blocked`), the dispatcher launches nothing for it (`packagesBlocked`) and goes on by itself once the problem is gone; the banner `PackagesBanner` names the projects, except those held only by `installing` and `probing`: after an import they pass in a second, and a banner coming and going shook the whole page. A fix session of a red main does not wait.

## The page

`/tools` starts with the packages table (`web/src/tools/Packages.tsx`): a row per package (kind, version, the install's error; Install when it has none, a primary Update with `→ <latest>` when the marketplace has a later version, a quiet Check otherwise — the same `packages/update`), a column per chosen project with on / off / default and the problems; a row opens to its servers, the default switch, the settings (for all and per project) and "Remove". Below: the keys (set or not, a new value), an offer to import the servers of a repository's committed `.mcp.json` (dismissed in `localStorage` until the list changes). "Add a package" in the head opens a dialog (`AddPackage.tsx`): the kind first, then a plugin of a known marketplace, or an MCP server — a name, an address with headers (`Name: value` lines) or a command with its environment (`NAME=value` lines, a quoted argument kept whole), and where it is on: every project (`default`) or one (`project` of `packages/plugin` and `packages/server`, on there, off by default). Commands: `POST /api/packages/{install,update,remove,plugin,server,import,project,default,setting,key}`; the data is `EvenKeelState.packages`.
