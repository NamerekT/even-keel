# Packages (BTN-174, `src/packages/`)

What chain sessions get besides the CLI's own tools: plugins and MCP servers, as a set per project, given by flags at every launch. Even Keel keeps the packages, their versions and the keys; the settings files of the accounts and the repositories are not written. Sessions started by hand live by their own `settings.json` and `settings.local.json` and get none of this.

Service wiring lives in `src/service/account-packages.ts`: `wirePackages` connects the catalog and gateway to the service, and `briefOn` selects tracker briefing from the enabled servers. `src/service/accounts.ts` re-exports both entry points.

## The file and the cache

- `state/packages.json` (schema v14): `packages` by name, `projects` and `pins` by project GUID like every file of `state/` (`store.ts` renames to keys and back). A package is `kind` (`plugin` — `plugin: { name, marketplace }`; `mcp` — `server`, an entry as `.mcp.json` writes it), `default` (in every project that does not turn it off), `settings` (user overrides of `env` of a stdio server or headers of an HTTP one), `installs` (oldest first, the last one current: `{ id, version, at, servers, extras, scripts? }`), `removed`, `scripts` (since schema v39: `true` lets npm run install scripts; omitted — `--ignore-scripts`). A project has `on`, `off` and its own `settings` per package. `pins[<project>][<task>]` is the install of each package the task runs on: it holds versions, not the set (BTN-706). Every launch of a task's session (a new one, a handoff, after a blocker or a skip) gets the packages the project has on now, a pinned one on its pinned install while it is there, one turned on since on its current install, written into the pin; a package turned off leaves the session and the pin, and `prune` may then take its old install. Before BTN-706 the pin froze the set too, so a task postponed for a package the user turned on came back without it.
- A plugin package is named as `enabledPlugins` names it, `<plugin>@<marketplace>`; an MCP package by its server's name.
- The cache is `state/packages/<package>/<install id>/`: `plugin/` (a copy of the plugin) and `servers/<server>/` (an npm install of a pinned stdio server). An install no pin holds and that is not current loses its files (`prune`); a removed package stays while a running task holds it.
- No file yet (the first start after the upgrade): the catalog is seeded from what sessions got before (`seedPackages` in `plugins.ts`) — the plugins enabled in the global `settings.json` (on by default), the plugins enabled only in a project's `.claude/settings.json` or `settings.local.json` (on in that project), the user scope servers of `.claude.json`; all of them are installed in the background. So the upgrade does not break a running chain.
- Since schema v14, `settings` holds only user overrides. The page combines the current install's literal environment values or HTTP headers with the package's overrides and then the project's overrides; the gateway applies only overrides to the requested install's server entry, so pinned tasks keep their own defaults. Saving a value equal to the inherited one removes the override; `null` resets it. Migration from older schemas drops package values equal to the current install's defaults (or the source server entry before the first MCP install), then project values equal to the inherited package value. Other values, including values whose original default is no longer known, remain unchanged; pins and install entries are kept.

## The built-in `agent-bridge` (BTN-986)

- The `agent-bridge` plugin of Even Keel's own marketplace (`BUILT_IN_PLUGIN`, `builtInPackage` in `plugins.ts`: `agent-bridge@<own marketplace>`, none when the checkout's marketplace lacks it) is part of Even Keel: the context handoffs, the chat's mail mid-turn, the check before a merge (`commands.check`), the standards, the badge's `status:` line and the `Stop` guard of the `CHECKPOINT:` line all ride on its hooks. Every project has it, from the first start, whatever `enabledPlugins` says.
- It is never turned off: it has only hooks (`hooks/hooks.json`), so nothing of it lies in a session's context until a hook has something to say; the cost is a `node` start per hook call, time and no tokens. Each feature is turned off by its own setting ("Handoffs by context size", an empty `commands.check`, no standards, the badge off); a switch of the package would only duplicate them and break them quietly.
- The seed adds it on by default, and every start puts it back (`keepBuiltIn` in `model.ts`, run by the `Packages` constructor, one log line `packages: <name> is built in and restored: …`): a missing record, `removed: true`, `default: false`, a project's `off`. It installs in the background as any package with no install; a failed install is the catalog's red band as before.
- `packages/project`, `packages/default` and `packages/remove` refuse it with `packages.builtIn`; the page shows a "built in" tag in place of its switches and no Remove, while the version, Update, Check and the pin stay. Sessions started by hand are untouched: its hooks stay silent in a session Even Keel did not start.

## Install and update

On the first start after the rename, the catalog replaces `checkpoint@<own marketplace>` with the built-in `agent-bridge@<own marketplace>` (BTN-999). The old record becomes removed and leaves project on/off choices; its pinned installs stay until their tasks finish, then normal pruning removes them. A task pinned to an old install gets only that plugin, including after a restart or handoff; other tasks get only agent-bridge. Old `enabledPlugins` entries do not seed another package. The transition logs the replacement once and is idempotent; it changes no file format. Installation and failures use the normal package flow.

- A plugin comes from Even Keel's own marketplace or from one the global configuration knows (`known_marketplaces.json`): a source path inside the marketplace is copied from its folder, another source (github, url) from the CLI's cache (`installed_plugins.json`); a plugin the CLI has not installed is refused with "install it in Claude Code first" (`packages.installInClaude`).
- Even Keel's own marketplace (BTN-226) is the `.claude-plugin/marketplace.json` of its checkout (`ownDir`, `ownMarketplace`): its plugins are offered and copied from the checkout with no `claude plugin marketplace add`, as a `directory` marketplace, and it wins over a marketplace of the same name the CLI knows (say, one added from a git URL), so chain sessions get the plugins of the running version. Claude Code still needs it for sessions started by hand: `/accounts` offers registration in the Claude Code card before Add (`AccountMarketplace`, EKR-62), and a quiet check mark once the global configuration knows it (`PackagesView.marketplace.known`). Both states have a tip with the registration and plugin-install commands. The action runs `packages/marketplace` → `claude plugin marketplace add <checkout>` in the global configuration; a missing executable gives `packages.marketplaceCliMissing`, other failures `packages.marketplaceAdd`. With no Claude account, or no own marketplace, there is no action. The drawer and the package catalog of `/settings` have no registration offer and there is no local dismissal.
- The marketplaces' plugin lists, and whether the own one is known, are read again at most once a minute (`AVAILABLE_MS`) and at once after the button: a marketplace added in a terminal shows up in "Add a package" within a minute, as its empty search says.
- A stdio server `npx -y <package>@<range>` is pinned (`npm.ts`): `npm view` gives the version, `npm install --prefix <cache> --prefer-offline --save-exact --ignore-scripts` installs it, the command becomes `node <bin of package.json>`; `--prefer-offline` spares npm a metadata check per cached package (~15 s), the version being resolved already. Other commands (`uvx`, `docker run`, `npx` without `-y`, `bunx`) run as they are, unpinned: they fetch what they like at every start, so `PackageView.unpinned` lists such stdio servers and the package's row shows a "version not pinned" chip whose tip says to write the command as `npx -y <package>@<version>`; an HTTP server has no version and gets no chip.
- The prefix keeps `package.json` and `package-lock.json` (BTN-1131): the exact tree of dependencies the server runs, not only its own version. A copy of the server (below) carries them; an Update that installs a server anew compares its lock with the previous install's (`lockOf`, `dependencyChanges`), logs `packages: <package>/<server>: dependencies changed: ws 8.0.0 → 8.1.0, …` and gives the page `packages.updatedDependencies` with their count. An install from before BTN-1131 has no lock and is not compared.
- npm runs no install scripts of the package or its dependencies (`--ignore-scripts`; `@firfi/huly-mcp`'s `@napi-rs/keyring` comes as prebuilt binaries). A package that needs them gets the "Install scripts" switch in its details (`packages/scripts`, `PackageRecord.scripts`, file schema v39), whose tip warns they run as the service's user; the switch is shown only for a package with a pinned server (`PackageView.scripts` is `null` otherwise). An install remembers whether it ran them (`PackageInstall.scripts`), so after a flip Check installs anew instead of `packages.upToDate`, and does not copy the server from the previous install. A server whose npm name and version are those of the current install, with its folder still there, is copied from that install's `servers/<server>/` instead (BTN-422: a plugin-only update cost a full `npm install`, 51–59 s); the previous install keeps its folder for `prune`, and a failed copy falls back to `npm install`. There is no cache of servers shared across installs (BTN-422 turned it down). The log times an install: `installing <package>`, `npm install <spec> took N s` or `<spec> copied from <install id> in N s` per pinned server, `<package> <version> installed in N s`.
- `@firfi/huly-mcp` up to 0.55.4 pulled in Huly's web front end (`@hcengineering/ui` and what it brings), 97 MB in ~14,000 files it never loads (EKR-14). BTN-627 left them out of the install with npm `overrides` and stubs; 0.55.5 (2026-10-31, upstream issue #334) bundles its code and depends only on `ws`, `dbus-next` and `@napi-rs/keyring`, 16 MB in a full install, so the trim was removed.
- "Update": for a git or github marketplace first `claude plugin marketplace update <m>` in the global configuration, then a new install next to the current one if the plugin's version or any npm server's changed; otherwise `packages.upToDate`.
- Updating an install does not copy its defaults into `settings`: untouched settings follow the new install, while package and project overrides remain. `PackageView.settings` holds the computed values projects start from (the install's defaults under the package's overrides); `ProjectPackages.cells[].own` only the project's own overrides.
- A secret setting's value never reaches the page (BTN-1116, `pageSettings` in `settings.ts`): both maps send `null` for it, meaning "set". A setting is secret by its name (`isSecretSetting`: `KEY`, `TOKEN`, `SECRET`, `PASS`, `AUTH`, `COOKIE`, `SESSION` and the like, any case, so `Authorization`, `X-Api-Key`, `API_KEY`) or by its value (`Bearer …`, `Basic …`, `ghp_…`, `sk-…`), whatever the name; a key a user scope server of `.claude.json`, a repository's `.mcp.json` or the add dialog brings as a literal is one. The page's field of a secret starts empty with "Saved" as its placeholder (`secretInput`), sends only a typed value and keeps the saved one when left empty; a project's own secret has the "own" chip with ↺ (`value: null`) instead of an empty field going back. `setSetting` compares a value with the inherited one in the service, so a typed value equal to it still drops the override.
- What Update would bring: `PackageView.latest` is the version of the plugin where `locatePlugin` finds it (`pluginOffer`), when it is later than the install (`isNewer`, `version.ts`); read again at most once a minute and after an update fetched the marketplace. For a fetched marketplace it is only as fresh as the CLI's last fetch (`lastUpdated` of `known_marketplaces.json`, `PackageView.fetched`; Claude Code fetches them on its own start too): the page says so in the tip, Even Keel fetches nothing on a timer. An MCP package has no `latest`: npm is not asked until Check. A running task, its `--resume` and its handoffs stay on the install of each package they started on (`pins`), while the set itself follows the project's on every launch but `--resume`, which goes with its saved flags (`respawnFlags`); the task's pins go when it is done (`release`).

## The user's own skills (`skills.ts`, BTN-339)

- The skills of `~/.claude/skills` (the global folder's `skills`), `$CODEX_HOME/skills` and `~/.agents/skills` reach only their own agent. "Add a package → My skills" (`SkillsStep` in `AddPackage.tsx`, `packages/skills` with `skills` and `project`) wraps the ticked ones into the plugin `my-skills` of the marketplace `even-keel-skills` in `state/skills/` (`.claude-plugin/marketplace.json`, `plugin/{.claude-plugin/plugin.json, skills/<name>}`, links followed), which is one more of Even Keel's own folders beside its checkout (`marketplaces` in `plugins.ts`), so the package `my-skills@even-keel-skills` installs, updates and pins as any plugin. The folder is the state: the chosen skills are the subfolders of `plugin/skills`, so no file of `state/` changed its format.
- The version is `1.0.0+<8 hex>` of every file's path and bytes (`skillsVersion`): the build part leaves no order, so `latest` is any other version (`skillsChanged`). Once a minute with the other marketplaces, and before an Update, the wrapped skills are copied from their folders again (`rewrapSkills`), so an edit shows as `→ <version>`; a skill whose folder is gone keeps its copy (`from: null`, "its folder is gone").
- A second save of the step makes a new install of the package in the catalog and leaves its projects as they are; the plugin does not show in the plugin step's list (`available`).
- Claude Code sessions do not get it (`readsOwnSkills`, `startOf` drops its `--plugin-dir`): they read the same skills from their account folder, and the plugin would list them twice as `my-skills:<name>`. A Codex session does get a skill of Codex's own folder twice, its own and the plugin's.

## Keys

- A pool per project (`keyPool` in `src/profiles/model.ts`, `PackagesDeps.poolOf`): Even Keel's own `.env` without any profile variable, then the values of every default profile, then the profiles of the project's task feeds (BTN-66, `docs/chain/entry.md`), then the project's own profile on top (BTN-200, `docs/trackers.md`, "Profiles"). So the tracker's server of a project gets its profile's account, a package that reads `GITHUB_TOKEN` in a Huly project gets the default GitHub profile's, and the `forgejo` server gets `FORGEJO_TOKEN` of the default Forgejo profile (BTN-201). The page writes a `.env` key into `.env` (`upsertEnv`) and `process.env`, and sees only whether it is set; the package catalog shows a key in its package's details (a key only a tracker's server reads, under "Tracker keys") and no longer lists the profiles' variables — they are the profiles' rows on Trackers and CI of `/settings`. The gateway takes a new key or a changed profile at once.
- Each applied profile replaces all variables of its kind, including optional fields it leaves unset: a project or feed profile without `GITLAB_URL` removes the default profile's self-hosted address. `serverProfile` follows the same precedence for the server's account.
- `${…}` placeholders of a server entry are filled from the pool (`keys.ts`). `${NAME:-default}` reads as in Claude Code: the key is listed, but the server is not held without it and gets the default. A placeholder that names the same key differently (`GITHUB_PERSONAL_ACCESS_TOKEN` ← `GITHUB_TOKEN`, `LINEAR_API_KEY` ← `LINEAR_TOKEN`) is declared by the adapter's `mcpKeys`; one built from several keys (`JIRA_BASIC_AUTH`, the base64 of `JIRA_EMAIL:JIRA_TOKEN`) by its `mcpValues`, and the server waits for each key it is built from. The tracker's stdio server (`mcpServer` of the adapter) gets the adapter's variables from the pool.
- Sessions do not get the pool: `sessionBase` drops every variable a package, a tracker or a CI reads, the adapters' placeholder names the gateway also reads a key under (the keys of `mcpKeys` and `mcpValues`) and Even Keel's own secrets of `secretCatalog` (the page token, Tally's passwords and key, the badge secret), even when set from outside (`sessionSecrets`); and it drops every variable Even Keel's `.env` put into the environment (`EnvFile.own`), since a session needs nothing of that file — the service's address comes as `EVEN_KEEL_URL` (BTN-1115). The same environment goes to the task's commands, to `cli-check` and to the stdio servers behind the gateway, which get their keys only through the entry's placeholders and the tracker's own variables. A `--bg` daemon started before the change keeps the old environment until it restarts (`docs/accounts.md`). The CLI puts the `env` of the user's and the project's `settings.json` on top of that, so a key kept there for sessions started by hand would reach a chain session past the gateway: the chain's `--settings` (`chainSettings`) sets each of these variables to an empty string, and the flag's `env` outranks the files and the daemon's environment (checked on CLI 2.1.310 with `-p` and `--bg`, BTN-436). An SDK session gets the same `--settings`; Codex reads no `settings.json`. A launch logs, once per account, which of them the account folder's `settings.json` sets.

## The gateway (`gateway.ts`)

- Error diagnostics share OAuth's credential redaction (`src/error-reason.ts`): placeholder values (including arguments and URLs), the target environment, literal environment values and headers, and generated HTTP-mode variables are removed, along with common OAuth fields and Bearer/Basic credentials. Errors are normalized and limited to 500 characters before logging or deduplication; a recovery still logs once. Stderr keeps the last nonempty line, including an unterminated one, and joins chunks before redaction; a line over 2000 characters becomes `[stderr line truncated]` instead of exposing a partial credential. Each launch uses its resolved settings and keys, so changes and restarts need no saved redaction state.

- `http://127.0.0.1:<EVEN_KEEL_MCP_PORT>` (4748 by default), never another interface: Tailscale Service forwards 4747 to localhost, not this port. The route is `/mcp/<project GUID>/<package>@<install id>/<server>`; the gateway finds the install and the project's current settings by it, so a session resumed with its saved flags reaches its server after a restart of the service.
- A tracker profile with an MCP OAuth grant (BTN-475, `docs/trackers.md`, "MCP through OAuth") replaces only `Authorization` of a remote server whose URL is its provider's fixed MCP address (same origin and path, no credentials in the URL): the entry's other headers stay, and its `Authorization` key is no longer required. The gateway sends `Bearer <access token>`, never the old Basic header; a 401 gets one refresh and one retry, a second 401 marks the grant for reconnecting. Redirects are refused, so a token never follows one. A request the gateway fails with an error (no token, a refused grant, a server gone) logs `<package>/<server>: <error>` once until the error changes, and `<package>/<server> works again` once a request of that project goes through (BTN-589).
- A remote HTTP server is proxied with its headers filled from the pool. A stdio server with a known HTTP mode (`HTTP_MODES`, by npm package; Huly: `MCP_TRANSPORT=http`, `MCP_HTTP_HOST`, `MCP_HTTP_PORT`, `MCP_AUTH_TOKEN`, path `/mcp`) runs once per route and environment on a free port with a random bearer token. It is ready once it answers HTTP at all (a `GET` of its path, any status, up to 60 s), not once its port accepts: huly-mcp listens before it attaches its handler, and a request in that gap (150–400 ms on the PC, longer on a slow machine) was never answered — the first `initialize` hung for the probe's 30 s, then 30 s more to the next probe (EKR-6). The log says `<package>/<server> started in N s`. Any other stdio server gets a bridge in the gateway: a child process per MCP session (`Mcp-Session-Id`), JSON replies, `GET` for the server's own messages as SSE, closed by `DELETE` or after 30 minutes idle.
- On Windows a stdio command that is not `node` or an `.exe` (`uv`, `npx`) runs through `cmd.exe`, which gets one joined line: every argument with a space or a shell character is quoted (`shellQuoted`), otherwise a path like `…\Claude Extensions\…` falls apart.
- No token between the session and the gateway; instead `refusal()`: `Host` must be 127.0.0.1 or localhost (DNS rebinding), a request with `Origin` is refused (a browser page), a `POST` must be `application/json` (a browser cannot send it without a preflight).
- Even Keel's own tasks server (BTN-768, `docs/trackers.md`, "The tasks server") is answered in the gateway, after `refusal()`: `/tasks` and `/tasks/<project GUID>` for sessions started by hand, and any package route whose server entry is a local address with the path `/tasks` (`isTasksUrl`, the `tasks` plugin's `.mcp.json`) with the route's project and the `?task=` that `sessionPackages` appends. Streamable HTTP with JSON replies only: a single message or a batch, 202 when nothing needs a reply, 405 for `GET` and `DELETE` (no stream, no MCP session).
- The gateway cannot listen → `PackagesView.gateway` and every chain waits (the red banner; each project's own line points at it).
- Protection's tracker groups (BTN-541) live here, so they hold for every agent, Codex too. A server whose name is a tracker adapter's `mcpServer` gets `refuseDeletes` (the tracker's title) unless the project's effective Protection disables that tracker's group (`TRACKER_GROUPS`). A `tools/call` that deletes a record — the word `delete` in the tool's name, or `destructive` (Jira's `executeDestructive`, whatever operation it runs, BTN-659), or an `arguments.method` with the word `delete` (`deletesRecord`: `delete`, gitea-mcp's `delete_comment`, `deleteLabel`; BTN-476), or a dispatcher calling such a tool (BTN-641: a tool with `invoke`, `call`, `execute` or `run` in its name, such as Huly's `invoke_tool`, naming the tool in `toolName`, `tool_name`, `name` or `tool` and its arguments in `arguments`, `args`, `params`, `input` or `inputs`, an object or its JSON text, nested to any depth; a tool name in the arguments of any other tool, such as `get_tool_schema`, is a read and passes) — never reaches the server: the gateway answers it with a tool result `isError: true` saying the user must delete it or turn the tracker off; in a batch the other requests get `-32600` and nothing is sent. The log says `mcp gateway: <route>: Protection refused <tools>`. A tracker server outside the project's packages is not behind the gateway and is not covered.

## Launch

- Claude (`src/claude/cli.ts`): `--mcp-config <JSON>` and `--strict-mcp-config` before the other flags (`--mcp-config` takes several values and would swallow the prompt), `--plugin-dir` per plugin of the set, and in `--settings` `enabledPlugins: false` for every other enabled plugin (`otherPlugins`). `--strict-mcp-config` cuts off `.mcp.json` of the folder and its parents, user and local scope and the plugins' own MCP: every MCP server goes through `--mcp-config`. A plugin's server is named `plugin_<plugin>_<server>`, so its tools stay `mcp__plugin_huly_huly__*` and the plugin's hooks and permission rules keep working; an MCP package's server keeps its own name.
- `--bg --resume` of a stopped session wakes it with its saved flags (`respawnFlags` in `jobs/<id>/state.json`).
- Codex (`src/codex/mcp.ts`): `-c mcp_servers.<server>.url=<gateway address>` per server, no keys in the turn's environment; a plugin's server is named `plugin_<plugin>_<server>` as in Claude Code.
- Codex reads a Claude Code plugin's skills and hooks (`src/codex/plugins.ts`, BTN-180); commands and agents stay out. Every install is its own marketplace `ek-<install id>`: `Packages.startOf` writes `state/packages/<package>/<install id>/.claude-plugin/marketplace.json` beside the copy (one plugin, `source: "./plugin"`) on its first session (`ensureMarketplace`). On the first turn of a plugin in a Codex folder, `codex app-server` installs it (`plugin/install`, into `<folder>/plugins/cache/<marketplace>/<plugin>`) and turns it off again in the folder's `config.toml` (`config/value/write`), so the user's own Codex sessions do not get it; a folder whose cache already has that directory is not installed into again. Each first turn of a plugin in a folder per service run logs one line, `codex plugins: <plugin>@<marketplace> installed into folder <tag> in <n> s` or `… found in the cache of folder <tag>`, where the tag is the first 8 hex digits of the SHA-256 of the folder's path (the path and the account stay out of the log); later turns log nothing, so the count of these lines in a run is the count of `plugin/install` calls and cache hits (EKR-65). Then `hooks/list` gives the hashes of its hooks, kept in memory while the service runs (a new hash format takes a service restart). The hash trusted is the hook's own: from 0.164.0 `currentHash` is `sha256:<hook>/sha256:<plugin contents>`, and `trusted_hash` accepts only the part before the `/` — the whole value or the plugin's half reads `modified`, no `hooks.state` reads `untrusted`, and either way the hooks are skipped (EKR-29). Before the hashes are kept, `hooks/list` is asked once more with the turn's own flags (below); a hook of the plugin not `trusted` there (or gone from the answer) is the notice `codex.hooksUntrusted`, which names the package, the CLI version and each hook's key with its `trustStatus`, and the launch fails, so a change of the format cannot run the chain without `merge-check`, the context reminders and the mail. A failed install is the notice `codex.pluginsFailed` and the launch fails.
- Every Codex turn then gets `-c` flags: the marketplace (`source_type = "local"`, its folder), the plugin on, the plugin's own MCP servers off (the gateway serves them), every other plugin of the folder's `config.toml` off (as `otherPlugins` for Claude; a key with a `.` cannot be named in `-c` and stays as it is), and `hooks.state` with the hooks trusted by their hash, as one inline table: Codex skips an untrusted hook without a word. No `--ignore-user-config`: it would also drop the folder's `model`, project trust, `[windows] sandbox`, `notify` and memory, so the MCP servers of the folder's `config.toml` still reach Codex sessions. A plugin with skills, hooks, commands or agents is marked `unsupported` only for an agent other than Claude Code and Codex.
- OpenCode (`src/opencode/cli.ts`, `sessionConfig`, BTN-214): the gateway's servers as `remote` servers in `OPENCODE_CONFIG_CONTENT`, the project's own `opencode.json(c)` servers turned off by name (no `OPENCODE_DISABLE_PROJECT_CONFIG`: it drops the project's instructions too); the servers of the account's own config still reach it, as with Codex. A plugin's `skills/` goes into `skills.paths` (with the project's own `.claude/skills` and `.agents/skills`, `skillDirs`, `docs/sessions/opencode.md`), and the scripts of its `opencode/` folder into `plugin` (`pluginFiles`, BTN-274: OpenCode's hooks are JS plugins, so a package brings its own, as `agent-bridge` and `huly` do); its Claude Code hooks, commands and agents do not reach OpenCode. The Huly plugin (`opencode/huly.mjs`, from 0.5.8) checks writes to `plugin_huly_huly_(create|update|add)_*` before execution with the command hook's markdown refusal and estimate calibration; an allowed call gets calibration after its result, once per session and project. The package check still marks plugins with Claude Code extras `unsupported` with `skills: true`, shown as "no hooks" (`pluginReach` in `check.ts`), even when they bring OpenCode scripts; it does not hold the chain.
- Copilot (`src/copilot/cli.ts`, BTN-215): the gateway's servers as `--additional-mcp-config` (`type: "http"`, `tools: ["*"]`), and since Copilot has no strict mode, `--disable-builtin-mcps` and `--disable-mcp-server` for each server of the project's `.mcp.json`, `.github/mcp.json`, `.vscode/mcp.json`, the account's `mcp-config.json` and the set's plugins (`ownServers`). A plugin goes as `--plugin-dir`, which Copilot loads in the Claude Code format with its skills and hooks: it is in `READS_PLUGINS` beside Claude and Codex, not marked `unsupported`. Command-hook execution was checked live on 1.0.98 on Windows on 2026-10-25 by `cli-check`: the agent-bridge package sent `/mail` and `/checkpoint` requests for the test session. Skill loading and full hook-driven handoffs remain unchecked (`docs/unverified.md`).
- The project's standards (BTN-359, `docs/sessions/protection.md`, "Project standards") come with the `agent-bridge` package, so each agent gets them its own way above: Claude Code and Codex from the plugin's hooks (Codex's edit is `apply_patch`), Copilot from the same hooks in the Claude Code format with its own tool names (`view`, `edit`, `create`, `str_replace` — not seen live, `docs/unverified.md`), OpenCode from `opencode/agent-bridge.mjs`. A project without the package's hooks gets no standards.
- `agentExtras` computes the packages before `settingsFor`: each launch of a task updates its pin (`startOf`), and `otherPlugins` names the same set (`installsFor`).

## The check before a launch (`check.ts`)

- Problems of a package in a project: `notInstalled`, `installing`, `installFailed`, `noKey` (with the variables), `noResponse` (the probe — `initialize` through the gateway; a success lives 5 minutes; failures in a row are retried after 30 s, 1, 2, 5, 15, 30 minutes, then once an hour (`PROBE_FAILED_MS`, BTN-589), back to 30 s after a success or any change of the tracker profiles, a save or a new grant (`Probes.retry`); a failed answer, a server gone, or silence after the server has answered once), `probing` (shown as a spinner beside the package's switch in the project's packages, "starting" in its tip, not a problem line: it passes in seconds after every service start; no answer yet since the service started or the package was installed, including probes that timed out at 30 seconds, asked again at once rather than in 30 seconds; held too, so the chain does not start on a server nobody has asked; the gateway logs `<package>/<server> did not answer initialize in N s, still starting`), and of the set: `noTrackerMcp` when `brief` is explicitly `false` and no enabled package brings the tracker's server — nor `tasks` for a tracker Even Keel's tasks server serves (`servesTasks`, BTN-882; `CheckInput.tracker.also`) — (the auto `brief` turns itself on then instead; not under the banner: the chain pauses on `chain.noTrackerMcp` with two buttons beside it, `docs/chain/pr-mode.md`, BTN-656). `unsupported` is only a mark. Whatever `brief` is, `ProjectPackages.tracker` tells the page the tracker's server and whether a package of the set brings it (`null` for a tracker without one; `PackagesDeps.tracker`, EKR-5), with `through: 'tasks'` when only the tasks server does: the page then names `tasks@even-keel` as the package that brings it and offers no tracker plugin. `also: 'tasks'` says the tasks server serves the tracker, so the page offers it first (BTN-874); `both` — the set brings the tracker's own server and the tasks server at once, which is a warning on the page and holds nothing.
- While a project has a problem that holds it (`blocked`), the dispatcher launches nothing for it (`packagesBlocked`) and goes on by itself once the problem is gone. What only the user fixes — an enabled package `notInstalled`, `installFailed` or with `noKey` (`NEEDS_USER` in `src/packages/check.ts`, `Packages.unready`) — pauses the chain instead (BTN-657): the `packagesPause` hook gives `chain.packagesNotReady` with the packages, checked by every launch, Start, Resume and `wake` like `noTrackerMcp` (`SELF_CLEARING`, so Start and Resume go in paused and the pause lifts by itself once the packages are ready), with "Open the project's packages" (`/p/<id>?pkg=1`) beside it. `installing`, `probing`, `noResponse` and the gateway stay waits: the project's chip says "waiting · packages" (or "· gateway") and its card and page a line naming each package and its problem (`chainWaits` in `web/src/waits.ts`, `ChainWaits.tsx`), with the same button for `noResponse`. `PackagesBanner` shows only the gateway, since it holds every project. A fix session of a red main neither waits nor pauses.

## The page

Two places since BTN-802, sharing their rows (`web/src/tools/PackagesParts.tsx`, grouping and problems in `packageGroups.ts`); `/tools` has no packages. Every change is a command sent at once, never a settings draft. Commands: `POST /api/packages/{install,update,remove,marketplace,plugin,server,skills,import,project,default,setting,key}`; the data is `EvenKeelState.packages`.

- **Groups.** By source: Even Keel's marketplace first, the other marketplaces by name, then the MCP servers; the marketplace is named in the group's head, a row shows the plugin's short name. A row is one line at any width — a fold toggle with the name (ellipsis), the version muted with `→ <latest>`, the controls at its right — and opens to its details.
- **The catalog** — the group "Packages" of the shared settings (`/settings`, `PackageCatalog.tsx`). The head has "Check all" (`packages/update` of every installed package in turn, from the page) and "Add a package". Above the groups: the gateway's error, a red band per problem (a failed install, and each enabled cell's problem over all projects, once each; `probing` and `unsupported` stay quiet) with "To the package", which opens and scrolls to its row, and the offers to import the servers of a repository's committed `.mcp.json` (dismissed in `localStorage` until the list changes). A row's right: Install while not installed or failed, Update with a newer version, the switch "Default". Its details: the servers and the "skills and hooks" tag, the error and the last note, the settings' shared values, the keys its servers read, Check (the same `packages/update`) and Remove. The keys no package reads — only a tracker's server — are a card "Tracker keys" below. `/settings?package=<name>` opens the group with that row open.
- **A project's packages** — a dialog over the project's page at `/p/<id>?pkg=1` (`ProjectPackages.tsx`), so the settings panel's hash stays under it and a link leads straight in; "Project packages", the full-width button that opens the panel's Sessions tab before the Agent section (BTN-914, `PackagesButton.tsx`; packages do not depend on the provider), opens it. The button is one line: the short names of the enabled packages (`enabledPackages`, `shortName`) cut with an ellipsis, "none turned on" without any, or — amber while `projectIssues` has any — the first problem as the dialog names it and "N more"; the whole list is its tip. "What the session gets" keeps the fact "Packages" as a reference, without a button. Shown: the project's tracker's plugin, the `tasks` plugin where it serves the tracker, and every enabled package; Even Keel's plugins of other trackers that are off fold into "N more". A row's right: the inheritance chip ("shared", or "own" with ↺, which sends `choice: null`) and the switch (`packages/project` with `on`/`off`), a spinner while `probing`. On top a red band per problem of `projectIssues` (the set's, then each enabled package's) linking to its row; `noTrackerMcp` carries a button per choice of `trackerPackage` instead ("Add tasks@even-keel", "Turn on huly@even-keel"), each with the line on how it differs in its tip, and a missing tracker package without the problem (`brief` auto or on) is a note band with the same buttons; an amber band below says when both the tracker's own server and the tasks server are on (`trackerDoubled`), with "Turn off tasks" beside it, which turns the enabled package that brings the tasks server off for the project (`packages/project` with `off`, BTN-1028). The details: what it brings, the row's problems with their tips, the settings for this project (an empty field takes the shared value, its placeholder), and "To the catalog" for install, update and keys. The foot has "Add to the project" (the add dialog with the project) and "Done". At 760 px and below the dialog takes the whole screen.

"Add a package" opens a dialog (`AddPackage.tsx`): the kind first, then a plugin of Even Keel's or a known marketplace, or an MCP server — a name, an address with headers (`Name: value` lines) or a command with its environment (`NAME=value` lines, a quoted argument kept whole); or the user's own skills by checkboxes (`PackagesView.skills`, above). From the catalog the package is on in every project (`default`); from a project's packages it is on only there (`project` of `packages/plugin` and `packages/server`, off by default elsewhere).

The tracker's package in two clicks (EKR-5, `trackerPackage` in `web/src/tools/packageView.ts`, `packagesPath` in `packageGroups.ts`). A missing tracker package comes as `choices`, the default first (BTN-874): Even Keel's `tasks` where it serves the tracker (`also`), then the tracker's own plugin; each choice is the catalog's installed package of that server to turn on (`name`) or Even Keel's plugin of it to add (`plugin`), and a server with neither is no choice. Every way below goes to the first choice, the pause's buttons and the project's packages offer each, and their tips say how they differ (`choiceTip`): the tracker's own server has more tools and context and works without the service; `tasks` has five tools and needs the service running. `/p/<id>?pkg=1&add=<plugin>@<marketplace>` opens the project's packages with the add dialog over them on its plugin step (`AddPlugin`), opened only after them, or it would end up under them; with at least one Claude account and while Claude Code does not know Even Keel's marketplace (`marketplace.known === false`), the dialog first asks to add it — "Yes, add" runs `packages/marketplace`, "No" goes on, and either way the plugin step follows, since chain sessions do without it. Closing it drops `add` with a replace, and a plugin no longer in `available` (the catalog has it already) only drops it; closing the packages drops both. The ways there: "Project packages" beside "Task description in the prompt" in the project's settings — active while no package of the project brings the tracker's server, whatever `brief` is, greyed with the package that does in its tip otherwise (on `/settings` there is no project, so no button); the "What sessions get" chip in the project page's head (`ToolsChip` in `web/src/pages/ToolsLink.tsx`), whose count adds `noTrackerMcp` to the settings problems and whose tip says the chain waits (`brief` off) or advises a tracker package (auto or on), and warns while both servers are on (then it leads to the project's packages); and the buttons of `chain.noTrackerMcp` (`TrackerFixButtons.tsx`), one per choice, each turning its installed package on at once or opening the add dialog on its plugin. When the catalog has the first choice installed but the project has it off, the button and the chip open the project's packages without `add`, where its switch turns it on; the chip with nothing missing and nothing doubled still leads to `/tools?projects=<id>`. On `/tools` a failed MCP server's fix (`mcpFailed`) links to each project's packages.
