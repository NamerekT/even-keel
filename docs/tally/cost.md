# Cost, limits, signs and tasks

What a session cost, the limit share, signs and the tasks read from Huly.

## Cost

DeepSeek V4.1 Flash uses the off-peak API rates from [DeepSeek's Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/), checked on 2026-10-28: per million tokens, $0.15 input (cache miss), $0.003 cache read and $0.60 output. There is no separate cache write price: `cacheWrite5m` uses the input rate ($0.15), and `cacheWrite1h` is 0. The single `deepseek-v4.1-flash` prefix also covers `deepseek-v4.1-flash-free`. Peak pricing is deliberately not modeled: DeepSeek currently doubles the rates on weekdays at 01:00–04:00 and 06:00–10:00 UTC, excluding Chinese public holidays. Tally has no time-dependent pricing; this flat off-peak rate is a lower estimate of the API-equivalent cost, including for the free Zen variant, and stays a config entry to update when the provider's terms change.

MiniMax M3.1 Flash through OpenRouter (`minimax/minimax-m3.1-flash`, the model as OpenCode writes it) uses the full rates of OpenRouter's public model list (`/api/v1/models`), checked on 2026-11-08: per million tokens, $0.15 input, $0.015 cache read and $0.60 output, no cache write price (written as input, 1 h as 0). OpenRouter halves them from 15:00 to 01:00 UTC; the half price is fewer hours a day, so Tally takes the full one, an upper estimate of what a night run paid (BTN-844: the first task cost $0.185 on OpenRouter's activity page, all of it in the cheap window).

`message_costs` is `messages` × the model's price by the longest matching prefix (`claude-opus-5-5` before `claude-opus-5`; the prefix is chosen once per model rather than per response — on PGlite that makes `period` twice as fast), per million tokens: input, output, cache read, cache write for 5 min and for 1 h, each at its own price. Prices live in the view, not in rows: editing `tally.config.json` recomputes the history too. A model without a price has an empty `cost`, and the run logs it. The prices are Anthropic API prices as of 2026-09-25 (5 min write = 1.25× input, 1 h = 2×). `claude-fable-5-2` (2026-11-09, before a public price page) takes the `tier_8_40_cache_read_0_20` entry of the model catalogue baked into Claude Code 2.1.321; a Fable newer than a key falls to the `claude-fable-5` prefix, priced above it, so a new Fable is a new key. GPT prices are OpenAI's standard tier as of 2026-10-19 (`developers.openai.com/api/docs/pricing`, BTN-234) for the models Codex lists and Even Keel's examples name: `gpt-6-astra`, `gpt-6.1-sol`, `gpt-6-sol`, `gpt-6-luna`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, plus `gpt-6.2-astra` and `gpt-6.2-sol` (their model pages, checked 2026-11-17, EKR-141), with their long-context rate as `longPrompt` (over 272k), and `gpt-5.4-mini` (Codex's default in an old `config.toml`; no cache write price, so a write costs input). Codex writes the model to the rollout as the API names it, so a key is the plain model name. `codex-auto-review` (Codex's hidden model that reviews approvals, a few thousand tokens a call), `gpt-reserve`, Copilot's `mai-code-1.1-flash` and `mai-code-2-flash` (no public API price) and `probe` (the Protection bench's fake local provider) have no price and stay unpriced; they are listed in `unpriced` (exact model names, BTN-243), so the run does not log them — any other model without a price is still logged, and a name in `unpriced` that a price covers is a config error. A new GPT model is a new key, never a shorter prefix such as `gpt-6`: it would silently give one price to every unlisted model of the family, whose prices differ 100×; the test of the shipped config (`src/config.test.ts`) checks each model gets its own entry. Fast mode (`speed = fast`, more expensive for Opus) has not been met in the data: `speed` is stored, the price does not account for it. A price may have `longPrompt` — a threshold `over` and its own five rates: a response whose prompt (input + cache read + both cache writes) is over the threshold pays them on all of its tokens, output included (Haiku 5.5: over 100k tokens, 5×; `src/price-views.test.ts`).

A model the config does not price and `unpriced` does not name takes its price from the models.dev catalogue (BTN-859, `src/catalogue.ts`): OpenCode's copy `<account>/cache/opencode/models.json`, the most recently written of every OpenCode account folder; with none, there are no catalogue prices. Tally never fetches the catalogue itself. The catalogue prices `<provider>/<model>`, and one model costs differently at different providers, so a response keeps its provider (`messages.provider`): OpenCode's `providerID`, `anthropic` for Claude, `openai` for Codex, none for Copilot and the classifier, which therefore never take a catalogue price. Each run asks the catalogue for the models of responses that no config prefix covers (`catalogueWanted`) and replaces the `catalogue` rows of `model_prices` with what it found; the config's sync touches only its own rows. A catalogue row is one exact model, never a prefix: `message_costs` takes the config's longest prefix first and only then the row of exactly the response's `<provider>/<model>` (`price_source` says which). From a catalogue entry: `input`, `output`, `cache_read` (missing — as input), `cache_write` as the 5-minute write (missing — as input), the 1-hour write 0; the first `tiers` entry of type `context` is `longPrompt` over its `size`, else `context_over_200k` over 200k. A response still without a price is logged with both places named. The catalogue holds today's prices, so a catalogue row reprices the history like a config edit does.

`gpt-6.1-terra` was added on 2026-10-27 (BTN-469) from [OpenAI's model page](https://developers.openai.com/api/docs/models/gpt-6.1-terra): per million tokens, input $1, cached input $0.05, output $5, cache write $1.25. Above 272k prompt tokens, input and cache rates double and output is 1.5 times the standard rate, as for the neighbouring GPT entries.

**Real spend on a key** (BTN-860, step 12). The cost above is an estimate by price; an OpenRouter key tells what it has really spent (`usage` of `GET /api/v1/key`), which differs by OpenRouter's choice of provider and its discounts. For an OpenCode account folder on an OpenRouter key, Even Keel (`KeySpend`, `src/account/spend.ts`) reads `usage` before each turn of a chain session (launch and resume, a 5 s timeout), at the end of each turn (the session monitor sees `busy` end) and then once a minute for 10 minutes after the account's last turn. The growth between two reads goes to the session that ran in between; when none ran, to the account's last session while those 10 minutes last, so a growth that arrives late is not lost; after them it is nobody's (the key was used outside the chain). Two sessions in one interval or busy at once on one key are marked shared: their spend cannot be told apart, and they keep the estimate. The rows are Even Keel's `key_spends` (step 35, `docs/storage.md`); the collector copies them whole into its own `key_spends` at each run (`syncKeySpends`; not read — the copy stays). The view `message_paid` is `message_costs` with `paid`: a session's real spend laid over its responses in proportion to their cost, or evenly when none is priced; every other response pays its `cost`. On `/stats`, the task table and a task's sessions show the paid sum and, where some of it is real spend, the estimate in a tip; the period's totals, the chart and the breakdowns stay on the estimate. The reads are kept only in memory, so a service restart loses what the key spent up to the first read after it: a session busy before that first read (its turn went on through the restart, or the read before it failed) is marked shared and keeps the estimate, instead of a real spend that misses the turn's start (BTN-871). A session idle at the restart keeps what was read before it, and loses only a late growth of its last turn that the tail would have caught.

`task_costs` — per task: responses, sessions, tokens, cost, limit shares. `milestone_costs` (step 5) — per project and Huly milestone (`tasks.milestone`): tasks, done ones, sessions, responses, cost, limit shares. The project is the key of the task id, so a release clone sharing a tracker project counts under it, and the milestone tells the release apart (BTN-172); a task not in Huly, or without a milestone, is the row with an empty milestone.

Reconciliation on 2026-10-03: an independent count from the transcripts (by `message.id` — the maximum of tokens, 5 min / 1 h from `usage.cache_creation`, prices from `tally.config.json`) matched `task_costs.cost` to the last digit for BTN-45 (one session, $2.52) and BTN-37 (a session and a subagent, two models, $1.20).

Reconciliation on 2026-10-19 (BTN-252): every `*.jsonl` at any depth under the account folders and the Codex rollouts, recounted without Tally's code, for 2026-10-15..17 and 2026-10-08..10 UTC — each response present on disk matched `message_costs` in every token kind and cost (8697 responses, $446.37; 11703, $605.09), with no double count of a response's rows. A response the CLI copies into a resumed session's file stays with the session that made it. Responses of deleted account folders live only in the database. The page's `history` per local day and `period` totals matched direct SQL to the cent.

## Limit share

Limits come from Even Keel: `GET <evenKeelUrl>/api/state` (`EVEN_KEEL_URL` over the config), `account.accounts[].limits` — it has both the statusline and the `/usage` poll, for each account. If Even Keel does not answer — `state/rate-limits.json` (statusline only, the account by `configDir`). A snapshot with the same time is not duplicated.

`limit_steps`: snapshots with a window number (`wnd`, a new one when the reset moved by more than 30 min from the previous snapshot: the sources round the reset differently) and the maximum percentage in the window before the snapshot (`prev_max`). `limit_intervals`: neighbouring snapshots of one account's window give an interval and an increase — `max(0, current − prev_max)`, not from the previous snapshot: `statusline` and `/usage` round the percentage differently and alternate in one series (21 → 22 → 21 → 22), and an increase from the previous snapshot would count every zigzag anew (BTN-51). When the window changed, the increase equals the current percentage, and the interval starts no earlier than the start of the new window (`reset − 5 h` / `− 7 days`). The first snapshot of a window gives no interval. `limit_windows`: a window per account — reset, start, peak (the highest percentage), the first and last snapshot; the "In weekly limits" tile takes it (window peaks). Snapshots exist since 2026-10-03 15:45: before that Even Keel stored only the latest value, and the transcripts have no limit percentages — the share before then cannot be recovered. `limit_shares`: an interval's increase is divided among this account's responses in the interval (`since < at <= till`) in proportion to their cost at API prices. Since step 19 it is one pass, a sort of responses plus intervals rather than their product: the intervals of one account and span never overlap and their ends are unique snapshot times, so responses and interval ends merge into one stream sorted by time descending, the running minimum of the ends gives each response its nearest end at or after it (an end sorts before a response at the same moment), and an equality join on that end with `at > since` keeps the response. It is an estimate: the percentage is an integer, snapshots come every few minutes, and the desktop app mixes its own sign-in into the `global` account. Since step 20 the account's keep-warm pings share the increase with its responses, each by its cost; a ping's row has its `ping_id` in `message_id`.

## Signs (`src/signs.ts`)

Where a session was marking time — without an LLM, from the projected rows in `session_activity`. A stream is the main session and each subagent separately (`src/stream.ts`). Kinds:

- `failures` — `failureRun` (3) failed calls in a row; `denied` — `deniedRun` (1) permission refusals in a row;
- `repeat` — one command (`Bash` and others — by the command text without extra spaces) `repeatRun` (2) times without an edit between them (`Edit`, `Write`, `MultiEdit`, `NotebookEdit` reset the count);
- `reread` — one file read with `Read` `rereadCount` (5) times in a stream between compactions (the path case-insensitive and with `/`; the count restarts after a compaction, as it does in a handoff's new session);
- `no_commit` — `noCommitReplies` (150) responses of the main session in a row without a successful `git commit`;
- `rewind` — several user prompts under one parent (`/rewind` or editing a message);
- `compact` — context compaction, `handoff` — the session was started by a handoff (`relay`/`checkpoint`/`restart` from Even Keel's log). These two are marks: they give no spans themselves, only get appended to the span they fall into.

Signs of one stream that overlap in time are merged into a span (`spans`, the id is the SHA-1 of the session, the agent and the edge `uuid`s). A session is recomputed when it has a new last row or the key changed — the SHA-1 of the signs version (`SIGNS_VERSION`), the rules and the launch reason.

The rules are `signs` in `tally.config.json` over the defaults, integers ≥ 1. Calibration on 2026-10-03 over all sessions: without a commit p95 is 102 responses, the threshold 150; files reread ≥ 5 times — 18; series of ≥ 3 failures — 16; refusals — 40; repeats ≥ 2 — 15; there was no `/rewind` in the data.

## Tasks from Huly (`src/huly.ts`)

The credentials come from the service, not the environment (BTN-200): the run gets `huly` (`HulyProfiles`, `src/huly-profiles.ts`) — the Huly profile of each task's project — and `refreshTasks`/`reportTaskTimes` group the tasks by credentials, one connection per profile. The service builds it in the root's `src/stats/huly-profiles.ts` and leaves a turned-off profile (BTN-830) out of every part — its project, the fallback, `byId` — so a stopped Huly is not asked. `npm run tally` by hand has no service and uses the `HULY_*` of the environment.

Its own small client (Even Keel's Huly adapter in the root's `src/huly/` and its model are not touched): by the task identifiers from `session_tasks` — title, status, labels (no duplicates, case-insensitive) and `relations`, made symmetric; related tasks outside the selection (neighbours) are fetched whole by id with a second query and written to `tasks` too, and the identifiers of their own relations with a third, so a neighbour's `related` is complete. A task is requested if it is not in `tasks` or its record is older than an hour; one not found in Huly is written with an empty title so as not to be requested on every run. If Huly is unavailable — a line in the log, the run goes on. The api-client noise "no document found, failed to apply model transaction" on connecting is filtered out.

More fields (BTN-55): `priority` (`urgent`, `high`, `medium`, `low`, `no-priority`), `estimate_h` (the `estimation` in hours; 0 — no estimate), `component` (the name), `done` (a status of the `Won` category); `milestone` (the label, BTN-172); `created_at` (the issue's `createdOn`, BTN-362). Records taken before these fields (`title` is present, `priority` is empty) are requested again without waiting for the hour.

Huly learns a task only after its first session, or as a neighbour of one that had sessions: a neighbour has no sessions of its own, is not asked for by itself and is refreshed with the tasks it is related to; a task without sessions does not get into `task_repeats`.

Follow-ups (BTN-362, step 7): a task done badly is not reopened — a new task labelled `Bug` or `Переделка` (`Rework` on the built-in tracker, step 10) is filed over it and related to it. Huly records a relation on both tasks (checked on 2026-10-24), so a follow-up without sessions is in the original's `related`, and Huly cannot be asked for the reverse (`relations._id` finds nothing). The view `task_followups` gives each task with a session the end of its last session (`max(sessions.last_at)`), `followups` and `followup_tasks` (by creation): its related tasks with either label (exact, as `rework`) created after that end. The time gives the pair its direction: of two related tasks, the later one is the follow-up, and a bug the task's own session filed on the way does not count.

Where a task lives (BTN-66, step 6; BTN-1497, `src/task-homes.ts`): a project's tasks may come from task feeds of other trackers and profiles, so the home is decided by the task, not by its project. A task the built-in tracker holds is its own: one read whole from it (see below), or an old id `<source_key>-<N>` a switch off it left behind (`builtinLeftovers`: the closed tasks the copy skipped and the copied ones' old ids, by the keys of the `tracker_transfers` exports and, for a switch before them, of a finished `tracker_exports` copy whose target key the project carries now; a copy without a switch does not count) whose prefix no project or feed gives now (`HulyProfiles.prefixes`). Such a task takes nothing from the launch log but its title: `profile_id` is cleared and `url` is its card, `/p/<project id>?task=<KEY-N>`, or none for a left-behind id (`syncOwnedTasks`, which also clears an older run's values the log's `coalesce` would keep); it is asked of no tracker and its time is reported to none, Huly or the GitLab or Jira project of the same prefix. Every other task, the feeds of a built-in project too, is where its launch read it: each run copies from Even Keel's launch log (`taskSources`, the latest launch that recorded each field) the tracker profile a task was read through (`profile_id`), its link (`url`) and, while the row has no title, its title (`syncTaskSources`); a new row is written as fetched at the epoch, so Huly is asked for its own tasks at once. A task launched through a Huly profile is asked with that profile (`HulyProfiles.byId`), whatever its project runs on now; one whose profile is gone falls back to its project's. `HulyProfiles.elsewhere` lists the task id prefixes of projects and feeds on another tracker: Huly is not asked for them, nor through the default profile, and their title stays the log's. Their `status` and `done` come from Even Keel's archive of closed tasks (`closed_tasks`, read with the log; `closedStates` in `src/closed-tasks.ts`, `syncClosedTasks`, BTN-330): a task of a tracker other than Huly the chain saw closed is done with the status of its latest close, kept when the archive has none, and open without a status once the chain launched it again after that close; a GitHub or Linear task the chain never closed has neither. The `/stats` task table links a task by its `url`, else by the tracker's template.

The built-in tracker (BTN-785, `src/builtin-tasks.ts`): its tasks live in Even Keel's state database, read with the log through `readStateDatabase`. Every run reads every task of the projects whose `tracker` is `builtin` now, named `<KEY>-<N>` as the chain names them, and writes them to `tasks` like Huly's records (`writeTasks`): title, status, labels, `relates` links both ways, priority (the neutral `none`…`urgent`), milestone, `created_at`, `done` (a status of the `Won` category), the estimate (`builtin_tasks.estimate` in minutes, as `estimate_h` in hours) and the component's name (BTN-1497); a task without either has none. Tasks without sessions are written too, so a follow-up is in its original's `related` with its labels and date. A project that left the built-in tracker is skipped: its key names another tracker's tasks now. A task read so is left out of `closedStates`, so the archive does not put an older state over it.

A project moved to another tracker (BTN-1076, `src/task-moves.ts`): once it has switched (BTN-1074), each run reads its copied tasks of the stage `marked` from `tracker_export_tasks` and writes `<source_key>-<number>` → the new key into `task_moves` (step 15), so the task's statistics go on under the new key. Before the switch the old task is the one the chain works, and no link is read. Links are only added or updated, never removed: a project Even Keel forgets keeps its tasks' links. The new task's `tasks` row, while no tracker gave it a title, takes the old task's.
