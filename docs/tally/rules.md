# Rule versions, audit and tests

## Rule versions (BTN-50)

Which rule texts (CLAUDE.md, skills, memory, hooks, settings, agents) were in effect when — so that `/stats` can compare spend before and after a change. A rule file is `ruleFileOf` (`src/rules.ts`): `~/.claude` and the account folders are reduced to one key `~/.claude/…` (except `settings.json` and `.claude.json` — each account has its own), and so are the stores those folders link to (BTN-366, the root's `src/account/share.ts`): `~/.claude-skills/<name>/…` is `~/.claude/skills/<name>/…`, `~/.claude-hooks/…` and `~/.claude-agents/…` are `~/.claude/hooks/…` and `~/.claude/agents/…` (BTN-373), `~/.claude-memory/<slug>/…` is `~/.claude/projects/<slug>/memory/…` — chain sessions write memory by the store's path (`autoMemoryDirectory`); a worktree to the main checkout, a project folder without the drive letter and case (a project may move to another drive). `~/.githooks/**` are hooks (without logs, `*.bak*`, `*.tmp`, `package*.json`), of `.claude.json` only `mcpServers` and `projects.*.{mcpServers, allowedTools}` are stored, with `env`/`headers` values as `***`. The skills `skills/synced/**` and `skills/.*/**` are not rules; a skill folder `skills/<name>` itself is not a file (`rm -r`/`cp -r` of a folder is not written as an edit, BTN-52). The text is `canon` (CRLF → LF, whitespace at the edges trimmed), SKILL.md without frontmatter, the hash is SHA-1.

- Tables: `rule_texts` (text by hash), `rule_files` (key, kind, folder), `rule_seen` (what a session received: `instructions`, `nested_memory`, the body of an invoked skill, a skill's description from `skill_listing`), `rule_snapshots` + `rule_snapshot_files` (disk snapshots), `rule_versions` (versions from `file-history`, backups and git), `rule_edits` (edits by `Edit`/`MultiEdit`/`Write`/`NotebookEdit` and writes to a rule file from `Bash`/`PowerShell` — `added` 0, `removed` empty), `rule_changes` (text changes: source `snapshot`, `transcript`, `file-history`, `backup`, `git`, +/−), `rule_imports` (the edit log, below), `tally_meta`.
- A snapshot is every run (`snapshotRules`): `~/.claude`, the account folders, `~/.claude.json`, `~/.githooks`, and per project of Even Keel — `git ls-files` of the rules and `.claude/settings.local.json`; only files with a changed size or `mtime` are hashed. A file is recorded as deleted only where the run looked (`goneKeys`, BTN-150, BTN-551): a global file only if its file or containing tree was inspected, a project's only when git listed its repository this run. Account copies use the same canonical rule keys as their files; skipped links and unreadable directories do not authorize deletion of their trees. A folder omitted from the account scan, or a project that dropped out (the config unread or empty, git failed), is left as it was. The first run is the initial state, without events; a file that first got into a snapshot with an old `mtime` is too.
- The collector's one-time data repair (`src/rule-repair.ts`, BTN-551) removes false deletion/restoration pairs under `~/.claude/` in the UTC window 2026-10-28 22:35–23:09 (end excluded), only when the next snapshot restores the preceding non-null hash. Both snapshots must be in the window; other keys and real text changes stay. The deletion and `tally_meta.rules_global_scan_repair_20261028` marker (the number of removed snapshots) are one atomic statement. `refreshRuleChanges` then removes the derived false events. This changes no schema; later runs leave the repaired history alone. The live result is in [`verified.md`](../verified.md).
- History before snapshots (`collectRuleHistory`): the transcripts' `file-history-snapshot` (copies in `<account folder>/file-history/<session>/`), the backups `~/.claude/backups/` (`CLAUDE.md.*.bak`, `.claude.json.backup.<ms>`), `git log --first-parent <branch>` of each project's rules, on the project's `branch` (`select repo, branch from projects`; read onward from `rules_git:<repo>` in `tally_meta`).
- The time rule: per version key, versions from transcripts and history go by first appearance, the first is the initial one, each next is a change; only versions earlier than the key's first snapshot count. This way the sources give no false changes against each other.
- When `RULES_VERSION` (`src/rule-steps.ts`) changes, a run rereads all transcripts from zero only for the rules (~10 s) and recomputes the changes.
- The edit log is `ruleHistory` in `tally.config.json` (by default `<EVEN_KEEL_STATE_DIR>/rule-history.jsonl`, outside git): a row is a set `{ id, at, until?, atPrecision exact|hour|day, sessions, files [{ path, action, summary }], purpose, reason, task, source }`. Each run adds new rows and deletes vanished ones (the key is the row's SHA-1), a broken row goes to the log. The server attaches the goal, reason and task to a session's edit set from `sessions` if the time agrees within a tolerance (30 min / 1 h / 24 h by precision), otherwise the log's set stands alone, marked as diverging.
- The log is filled by the sessions themselves, prompted by the hook `tally/bin/rule-hook.mjs` (BTN-151; logic in `src/rule-hook.ts`), wired in `~/.claude/settings.json` by the absolute path to the main checkout: `PostToolUse` with the matcher `Edit|MultiEdit|Write` and `Stop`, both `node "<main checkout>/tally/bin/rule-hook.mjs"`. An edit of a rule file (`ruleFileOf`, memory excluded) adds a reminder to the context, once per file per session: the file, the log's path, the row format with the row's `id` filled in (one past the largest numeric `id` of the log, BTN-374) and the row to go after the last line, the session id, the allowed `purpose`. A stop of a session that changed rule files and has no row with its id (a prefix, as the server matches) is blocked once, with the same reminder and the session's rows that do not parse; so is one whose row has an `id` another row has too, with the next free `id`; the next stop passes, a later one is blocked again only for rule files edited since. What a session was reminded of is `<state>/rule-hook/<session>.json`, swept after a month. An edit of another file ends before TypeScript loads (`tsx` from the main checkout's `node_modules`); any error ends the hook silently.
- The same hook checks every edit of `CLAUDE.md` and `AGENTS.md`, global or nested, against a 13,000-byte ceiling (`src/rule-hook-size.ts`). Only these exact-case file names count, for the ceiling and for the journal reminder alike: Linux loads neither `claude.md` nor `agents.md`, and a lowercase name such as `docs/sessions/agents.md` is an area document; the case of the folders does not matter. The bytes before the edit come from `tool_response.originalFile` (zero for a newly created Write); the bytes after it come from the actual file on disk. A missing original or unreadable file leaves the size check silent. Growth above the ceiling adds instructions to the edit reminder even if that file was already mentioned: move architecture details, history, task IDs and measurements to the area's document or JSDoc; retain principles and traps every task needs, without telegraph-style compression or discarding rules for space. Only the user may raise the ceiling. The edit is never rejected. Stop is blocked once per affected file even with a valid journal row, respecting `stop_hook_active`; journal and size reminders share one block when both apply. A reduction clears the pending size warning, even above the ceiling, and an equal-size edit adds no warning. Optional `oversized` and `sizeBlocked` fields extend the existing session state; old state files still work. The hook's instruction-file recognition does not change the collector's snapshot classification. The root and Tally `CLAUDE.md` also have a Vitest ceiling check (`scripts/instruction-size.test.ts`), covering agents without Claude hooks and growth through merges. Executable coverage and the remaining live-session check are recorded in [`verified.md`](../verified.md) and [`unverified.md`](../unverified.md).
- Since when history exists: the texts of CLAUDE.md and memory in transcripts — since 2026-09-04 (CLI 2.1.260, the first change 2026-09-06), skill descriptions and bodies — since 2026-08-03, hooks, settings and `.claude.json` — since the first snapshot (2026-10-03) and earlier only from backups, `file-history` and git.

## Session audit (BTN-53)

The audit is the skill `tally:session-audit` of the plugin `plugins/tally` (BTN-263, in Even Keel's marketplace; installed by hand in Claude Code, user scope): from any project it compares a recent period with an earlier one — spend, context, tasks, stuck spans, rule changes between them — looks for what changed, and reviews handoffs and compactions (the `handoffs`, `handoff_notes` and `compactions` views). The weekly audit is a special case: the period is the last 7 days, the earlier one the 7 days before them. Its SQL relies on the `audit_*` columns, so a change to them is checked against the skill's queries.

- The skill calls the plugin's launcher `bin/sql.mjs`, which finds the checkout (`EVEN_KEEL_HOME`; else the folders above the plugin, with `tally/bin/sql.mjs` and `tally/tally.config.json`; else `packages.marketplace.dir` of `/api/state` of the running service) and runs its `tally/bin/sql.mjs` with the same arguments and stdin.
- Queries go through `tally/bin/sql.mjs` from any folder (`node <main checkout>/tally/bin/sql.mjs "<sql>"`, `-f file` or stdin): it takes `pg` and `.env` from the main checkout. An external Postgres — the `tally_reader` role (`TALLY_READER_PASSWORD`, `TALLY_READER_USER` to change the name); the embedded database — the port from `<EVEN_KEEL_STATE_DIR or the main checkout's state>/tally/owner.json`, which answers only while the service runs (otherwise the error "served by the Even Keel service, and it is not running"). The environment variables `TALLY_*` and `EVEN_KEEL_STATE_DIR` outrank `.env`: an empty `TALLY_DB_HOST=` reads the embedded database even if `.env` points at the server. In both cases the transaction is read-only — `insert` and the like are rejected by the database. Every value prints as the database's own text (BTN-252): times in UTC with `+00`, `date` and `interval` as Postgres writes them, arrays as `{…}`, `null` as an empty cell; a day by the local zone needs `at time zone` in the query. The collector is not run for an audit.
- The ready sums are the `audit_*` views (the "Schema" section), the queries and the shape of the report are in the skill.
- Prices are an API estimate, not a subscription bill; tasks in `tasks` are refreshed once an hour, so the status may lag.

## Tests

Pure logic — vitest next to the code (`*.test.ts`): row parsing, compression, the task by branch and worktree, incremental tail loading (on a temporary file and an in-memory store), limit snapshots, config, signs and spans on synthetic transcripts, the classifier's excerpt and answer parsing, Huly tasks, turns (`src/turns.test.ts`: turn beginnings, a subagent inside a turn, questions, `turn_duration`, a limit), steps (`src/step-runs.test.ts`: rules, the command signature, the end of a background and a detached run, polls, the outcome). The limit views (`limit_steps`, `limit_intervals`, `limit_windows`) — `src/limit-views.test.ts`: the view bodies from `schema.sql` are substituted as CTEs over test snapshots that shadow `limit_snapshots`; without `TALLY_DB_HOST`/`TALLY_READER_PASSWORD` — on in-memory PGlite, with them — on the live database with the `tally_reader` role, read-only (from a worktree — `node --env-file=<main checkout>/.env node_modules/vitest/vitest.mjs run tally/src/limit-views.test.ts`). A response's and a session's task (`message_costs.task`, `session_tasks`), `milestone_costs` and `task_followups` — `src/task-views.test.ts`: the whole schema (`migrate`) on in-memory PGlite. Migrations — `src/migrations.test.ts` on in-memory PGlite with test steps: an empty database, one without a version, a newer one, a failed step, a role without the owner's rights; step 2 on real steps — `src/false-deletions.test.ts`. The claim of the local folder — `src/local.test.ts`: two opens started together, a claim of a terminated thread. The GitLab and Jira time reports — `src/tracker-times.test.ts` on a faked tracker, their API calls in the adapters' `source.test.ts`, and a live run (EKR-36, `docs/verified/trackers.md`). `limit_shares` — `src/limit-shares.test.ts`: the whole schema on in-memory PGlite against the view's first body from `schema.sql`, and `limit_shares_stored` against `limit_shares` row for row before and after a refresh with late rows; when a run refreshes it — `src/limit-shares-stored.test.ts`, a machine's post — `src/stats/machine-tally.test.ts`. The remaining SQL (cost, `limit_shares` on real data, `task_repeats`, `session_times`, `task_times`), the time reports to Huly and the request to LiteLLM are checked by a live run.
