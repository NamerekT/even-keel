# Schema (`src/schema.sql` — version 1; later changes are steps in `src/migrations.ts`)

Step 13 (`migrations/13-normal-spans.sql`, BTN-966) redefines `audit_sessions`, `audit_tasks` and `task_repeats` without changing their columns. Stuck spend and task span counts exclude spans whose current `span_reasons.reason` is `normal`; absent reasons and `other` count. `stuck_spans` keeps every span. The `/stats` overview and before/after reader use the same filter. Regression coverage in the root's `src/stats/stuck-reader.test.ts` runs a populated v12 upgrade, the audit views and both readers on in-memory PGlite, including reclassification and a repeated migration.

Step 14 (`migrations/14-model-families.sql`, BTN-967) redefines `task_estimates` with the same family expression as `/stats` (`familyOf` in `src/stats/base-sql.ts`): Claude families including Fable, GPT tiers (`sol`, `luna`, `astra`, `terra`) or untiered `gpt`, and DeepSeek, Qwen, Gemini, Kimi, GLM, Mistral and Llama, including the prefixes supported by `familyOf`. Unrecognised or missing models give null. Columns and the most-frequent-family aggregation stay the same; existing sessions get the new grouping when queried. `tally/src/model-families.test.ts` checks a populated v13 upgrade against `/stats`, column preservation and a repeated migration on in-memory PGlite.

Step 15 (`migrations/15-task-moves.sql`, BTN-1076) adds the table `task_moves (old_task, task)` and redefines `session_tasks` to give a session of an old id the new one: a built-in project switched to the tracker its tasks were copied into names them anew ("The built-in tracker"). Every task view goes through `session_tasks`, so cost, times, the audit and the follow-ups count the old sessions for the new task; raw rows (`sessions.launch_task`, `messages.task`) keep the old id. `tally/src/task-moves.test.ts` checks the view and the sync.

Step 16 (`migrations/16-minimax-family.sql`, BTN-1204) redefines `task_estimates` again with `familyOf`'s current expression, which adds MiniMax (`minimax/minimax-m3.1-flash` → `minimax`); before it, MiniMax tasks had a null `model_family`. `tally/src/model-families.test.ts` covers it through the same v13 upgrade.

Step 17 (`migrations/17-machines.sql`, BTN-1280) adds `messages.machine` and `sessions.machine`: the id of the machine elsewhere a row came from, empty on the hub's own rows ("Machines elsewhere" below). No view changes: the views name their columns, and `/stats` reaches the machine through `sessions`.

Step 18 (`migrations/18-chat-sessions.sql`, BTN-1233) adds the table `chat_sessions (session_id, chat)` and redefines `session_tasks` and `message_costs` in full: a session of a project chat (`docs/sessions/project-chats.md`) is no task's, whatever its launch, branch, folder or title names, and its messages fall back to no `messages.task` either. Each run reads the chats' sessions from Even Keel's `chats` (`chatSessions` in `src/chat-sessions.ts`; a database before the chats gives none) and upserts them: a chat keeps only its latest session, so a link Tally holds is never dropped. Every task view goes through these two, so a chat's spend, turns and spans count for no task; `/stats` counts the chats per project of their folder next to the tasks (`docs/stats.md`). `tally/src/chat-sessions.test.ts` and the root's `src/stats/chats-reader.test.ts` check the read, the views and the reader on in-memory PGlite.

Step 19 (`migrations/19-limit-shares-one-pass.sql`, BTN-1351) redefines `limit_shares` with the same columns and rows, computed in one pass ("Limit share" below): the first body joined every response with every interval of its account and filtered by time after the join, which on the live database grew to 122 million rows and 17–29 s per read, past the stats reader's statement timeout. `tally/src/limit-shares.test.ts` compares it with the first body from `schema.sql` on in-memory PGlite over every edge case.

Step 20 (`migrations/20-warm-pings.sql`, BTN-1413) adds the table `warm_pings` and the view `warm_ping_costs`, and redefines `limit_shares` and `task_costs` in full. A keep-warm ping (`docs/sessions/cache.md`) is a fork without a transcript, so before it the pings' tokens were only in the log's `keepwarm:` line, while they took from the account's limit. Even Keel keeps each answered ping in its state database (`warm_pings`, step 70, `docs/storage.md`; a machine elsewhere sends it as the link record `warm.ping`), and each run copies the new ones (`warmPings` in `src/warm-pings.ts`, `syncWarmPings`; a ping Tally holds stays as it is). A ping of a machine elsewhere goes under the account its messages do (`<key>@<machine>`, "Machines elsewhere"); the hub's own has no machine. The pings are not rows of `messages`: a ping is no response of its session, and counting it as one would change the count of responses and the gaps between them. `warm_ping_costs` prices a ping as `message_costs` prices a response (the longest config prefix, the long prompt rates; a ping names no provider, so no catalogue price), gives it `ping_id` (`warm:<session>:<epoch ms>`) and its task through `task_moves`. `limit_shares` takes the pings into its stream next to the responses, a ping's row under its `ping_id` in `message_id`, with the same columns; `task_costs` counts its limit shares with them and appends `warm_pings` and `warm_cost` (its `cost` stays the responses'). `tally/src/warm-pings.test.ts` checks the read, the price, the share and the task on in-memory PGlite.

Step 21 (`migrations/21-session-activity.sql`, BTN-1470) keeps `lines` as the archive for reparsing. `session_activity` holds the ordered inputs to Claude signs, turns, steps and classifier excerpts, including prompt candidates, short text, tool commands, result outcomes and background job identifiers. Local and machine batches write these facts only for newly inserted UUIDs, in the transaction that writes the archive. The first collector on this schema projects historical rows in cursor batches and commits its `tally_meta.session_activity` mark with them. The `compactions` view uses `compaction_nodes`, populated by the migration and an insert trigger. It keeps boundary counters, summary lengths and attachment parents so a summary and its boundary may arrive in different batches or out of order. The step drops the unused `sessions_machine` index. On a copy of the working database neither a pass nor `/stats` read a block of `lines` after it ([the check](../verified/page.md)).

Step 22 (`migrations/22-line-raws.sql`, BTN-1471) moves the raw row out of `lines`, so a read of the narrow columns no longer pulls the compressed JSON into the cache and Postgres does with 512 MB of `shared_buffers` (`tally/deploy/README.md`). Nothing is copied in batches: the old table is renamed `line_raws` whole (heap, TOAST, key, grants) and loses its narrow columns by `drop column`, which rewrites nothing, and a new `lines` is filled in the step by a copy of those columns, about 100 bytes a row. The dropped values stay as dead bytes in the heap of `line_raws` until something rewrites it; no `VACUUM FULL` is needed, as the place of `raw` is not freed but moved. The `compaction_nodes` trigger moves to inserts into `line_raws` and reads the narrow fields from `lines`: a batch writes both in one statement, the raw only for a row `lines` took. The batch from a machine keeps its shape (`LineRow` carries `raw`): the hub splits it.

Step 23 (`migrations/23-worktree-visits.sql`, BTN-1615) redefines `session_tasks` and `message_costs` in full: a worktree folder gives its task to a session without a launch only when the session started there or spent most of its responses there (a response's task, below). A manual session in the main checkout that ran a few commands in an old worktree went wholly to that worktree's task before: BTN-1546 had 4 h of active time and $55.6 of a session that only cleaned up worktrees, against $0.48 of its own sessions. The views recompute the history, so the "Time" card, `/stats` and the audit change at once; a time report already written into Huly, GitLab or Jira (`tasks.reported_at`, "Tasks from Huly") is never rewritten, and reports written before this step may hold such extra time.

Step 24 (`migrations/24-limit-shares-stored.sql`, BTN-1658) adds the materialized view `limit_shares_stored`: `select * from limit_shares`, so the same columns in the same order and types, with the unique index `(message_id, span, till)` a concurrent refresh needs. `limit_shares` is a window over every response of the history, ~2.4 s on the live database, and `seven` in `src/stats/base-sql.ts` computed it anew in `TOTALS`, `TASKS`, `CHATS` and `HISTORY` of each `/stats` and badge read; since the step `seven` reads the stored rows. A writer refreshes them whole (`refresh materialized view concurrently`, `REFRESH_LIMIT_SHARES` in `src/limit-shares-stored.ts`): the collector at the end of a run that read lines, added limit snapshots or copied new keep-warm pings (`refreshShares`, the summary line says `limit shares refreshed in N s` or `kept`), and the hub after a machine's post with responses ("Machines elsewhere"). A full refresh takes in a late response by itself, which is why this is no table of shares the collector keeps (BTN-1351); a read during the refresh reads the previous rows. The shares lag the messages at most until the end of the run that brought them; a changed price or a response's moved task alone waits for the next run with rows, and `/stats` takes the task from `message_costs`, not from the shares. `task_costs` keeps reading `limit_shares`: only ad-hoc SQL and the audit read it, they want the shares of this moment, and a few seconds are fine there. The reader role gets `select` through the writer's default privileges (`tally/deploy`). A later step that drops or changes the columns of `limit_shares` or a view under it (`message_costs`, `limit_intervals`, `warm_ping_costs`) has to drop and recreate `limit_shares_stored` too.

- `lines` — rows with a `uuid`: session, agent, type, time. Service rows without a `uuid` (`ai-title`, `custom-title`, `queue-operation`, `file-history-*` …) are not stored; only session titles are taken from them.
- `line_raws` — the compressed raw row `raw jsonb` of each `lines` row, by its `uuid` (step 22). Only reparsing reads it: the one-time backfills (`MESSAGE_EFFORTS`, the `session_activity` projection) and the audit's deeper queries, joined to `lines` by `uuid`.
- `messages` — one API response (`message.id`): the CLI writes a response as several `assistant` rows, one block per row with a repeated `usage`, and the final `output_tokens` is in the last; when merging, the larger value is taken for each kind of token and the earlier time. Columns: session, agent, account (the file's account folder), project and its folder (`cwd` without the `.claude/worktrees/…` tail), task, branch, `entrypoint`, model, `speed`, tokens `input`, `cache_write_5m`, `cache_write_1h`, `cache_read`, `output`, `effort` (the row's top-level `effort`: `low` … `max`, the level the request went with; `perTurnEffort` is `null` in about a fifth of rows and is not taken). Messages loaded before `effort` was parsed got it once from their `lines` (`MESSAGE_EFFORTS` in `src/db-backfills.ts`, the mark `efforts` in `tally_meta`); transcripts older than the CLI's recording of it have none. A cache write without a `cache_creation` breakdown counts as 5-minute. `<synthetic>` and `isApiErrorMessage` responses are not API responses and do not go into `messages`.
- `tool_calls` — a call (`tool_use`: name, the SHA-1 of the input for finding repeats, a short description as in Even Keel's feed) and its result (`tool_result`: time, `is_error`, error kind, the first 500 characters of the text). Kind: `denied` — a permission refusal (the user or the auto-mode classifier), `hook` — `PreToolUse:…`/`PostToolUse:… hook error`, `error` — everything else. The call and the result write different columns of one row, so the load order does not matter.
- `sessions` — account, project, the titles `custom_title` (set by the user) and `ai_title`, the task and reason from Even Keel's launch log, the first and last row, `project_dir` — the folder of the first response (each run fills in the empty ones, `SESSION_FOLDERS` in `src/db-backfills.ts`), `prompt` — the first human prompt of the main thread, up to 2000 characters, without slash commands and IDE context blocks (`src/prompt.ts`; filled for empty sessions from the earliest candidate in `session_activity` by timestamp and UUID, `''` when a session has none a day after its last row).
- `handoffs` — what each handoff gave the new session (`session_id`): `previous`, task, reason, the whole prompt, the note's path and text. Even Keel saves a snapshot (the `handoffs` table of its database, `<state>/handoffs/<session>.json` before BTN-147) at every handoff (`src/chain/snapshots.ts`), and each run loads the new ones (`source = 'even-keel'`). Handoffs of the launch log without a snapshot are rebuilt from transcripts while those last (the CLI deletes them after 30 days): the prompt from the new session's first prompt, the note from the old session's last `Write` of the note's path and the `Edit`s after it (`source = 'transcript'`, `src/handoffs.ts`; a note that was only edited stays empty). A snapshot replaces a rebuilt row. The view `handoff_notes` adds the sizes and the note's Markdown headings.
- `compactions` (view, step 4) — one row per context compaction, so it compares with a handoff: session, agent, the boundary's `uuid` and time, from its `compactMetadata` `trigger` (`auto`/`manual`), `pre_tokens`, `post_tokens`, `duration_ms`; `summary_chars` — the summary's length (whole, the `…[+N]` cut added back); `seq` — the n-th compaction of the stream, `next_at` — the next one's time or empty, so a session splits into segments and the one after a boundary is a virtual successor. A compaction keeps the session and the file: the CLI writes a `system` row `compact_boundary`, then a `user` row with `isCompactSummary` — the boundary's child, or since about 2026-10 below the attachments written after the boundary, with an earlier timestamp (the summary is prepared in the background, `duration_ms` drops to tens of ms). The summarizing API call is not in the transcript: a compaction has no response, tokens or price here.
- `limit_snapshots` — snapshots of the `5h`/`7d` windows per account: percentage, reset, source, snapshot time.
- `model_prices` — prices, rewritten on every run; `source` (step 11) — `config` for a prefix of `tally.config.json`, `catalogue` for one exact `<provider>/<model>` of the models.dev catalogue ("Cost"); `long_*` — the long prompt rates (`longPrompt`), empty for a model without them.
- `key_spends` (step 12) — Even Keel's real spends of sessions on their keys, copied whole at each run; the view `message_paid` lays them over the responses ("Cost").
- `chat_sessions` (step 18) — a project chat's session (`session_id`) and its chat's id, upserted from Even Keel's `chats` at each run.
- `warm_pings` (step 20) — Even Keel's keep-warm pings: session, time, machine, account, task, project, model and the tokens by kind; the view `warm_ping_costs` prices them (step 20 above).
- `files` — the incremental loading state.
- `signs`, `spans`, `sign_sessions` — signs, spans and with which rules and up to which row a session was computed; `span_reasons` — a span's reason from the classifier; `tasks` — tasks from Huly (below).
- `turns`, `turn_sessions` — turns of the main session and with which key and up to which row a session was computed (the "Task time" section).
- `step_runs`, `step_sessions` — runs of long commands and with which key a session was computed; the views `step_runs_x`, `step_weeks`, `step_growth` (the "Steps" section).
- Views: `session_tasks` — a session's task (`launch_task`, otherwise the task of the first response that has a task, a worktree folder's task only as "A response's task" below says); `stuck_spans` — spans with a task and a reason; `task_repeats` — per task: sessions, handoffs by kind (`relay`, `checkpoint`, `restart`), spans, title, status, labels, `rework` (the label `Переделка` or, since step 10, `Rework` is present), related tasks; for the audit skill (below) — `audit_sessions` (a session: folder, task, launch reason, active minutes, request context and its peak, the share > 150k, cost, stuck spans and call errors), `audit_tasks` (the same sums per task, the task counted in the period of its first response) and `audit_rules` (rule changes with a place and `undone` — a false pair of changes within a day); task times — `session_times` (per session: turns, active time, waiting), `task_times` (per task: sessions, turns, active, waiting, total) and `task_estimates` (`audit_tasks` + time, estimate, `fact_ratio` — actual / estimate, priority, component, `done`, the recorded report, `model_family` — the most frequent model family); `session_efforts` — a session's effort level (the most frequent of its main thread, `mixed` when it changed midway), joined to `audit_sessions` for comparing levels; `task_followups` (step 7) — a task's follow-ups filed over it after its last session ("Tasks from Huly"). The `audit_*` columns do not change: the audit skills' queries rely on them, and `create or replace view` does not allow a new column in the middle — new things go into a separate view.

A response's task: a session launch in Even Keel's log (`launches` of its database, except `postpone`/`skip` and the outcome of a fix of main, `landed`/`dropped`) → the branch `<key>-<number>/…` → the folder `.claude/worktrees/<key>-<number>`. The log is applied retroactively too (`sessions.launch_task`, which the view takes first). `messages.task` is the task of the response itself, while `message_costs.task` is the task of its session (`session_tasks`, BTN-79): the `/stats` page, `task_costs`, limit shares and the audit count a task the same way; the start of a manual session before its branch is not lost, and a session over two tasks goes entirely to the first. A task the response took from its folder rather than its branch (the branch is not `<that task>/…`) is the session's only when the session's first response has it or more than half of its responses do (step 23): a manual session in the main checkout on the project's branch that ran a few commands in a task's worktree gets no task from it, and its responses there count for no task either — `message_costs` keeps a response's own task only for a session Tally does not know. A task from a branch counts from any of its responses, as does the launch. A manual session in a checkout left on a task branch often works on another task: when its custom title, generated title or `prompt` names tasks of the branch's project but not the branch's own, `session_tasks` takes the first one named, in that order (CBL-157 had 23 sessions of ten other tasks, $406, on its branch). A session in `chat_sessions` has no task at all, neither in `session_tasks` nor in `message_costs` (step 18).
