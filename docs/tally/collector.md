# The collector

Running it, what is read, schema versions, machines elsewhere, compressing raw rows.

## Running

- The collector is started by the Even Keel service (`src/stats/tally.ts`, `TallyService`) when `tally` is `local` or `server`: 15 s after startup, then every 5 min from the start of the previous run, and the next one does not start while the previous is going. A run is a separate thread (`src/collect-worker.ts`), so parsing transcripts does not hold the service's event loop; the output goes to the service log, and a run error does not touch the service or the chain. The embedded database is owned by one more service thread (`src/host-worker.ts`), and the page gets its port once the database has opened (if it did not — `/stats` shows an error). An external Postgres without `TALLY_DB_NAME` or `TALLY_WRITER_PASSWORD` — the service does not collect, one line in the log.
- One run by hand, for debugging — `npm run tally` (or `node --import tsx tally/src/main.ts`) from the repository root: read the new data, write a limits snapshot, recompute the signs, turns and steps of changed sessions, ask Huly for stale tasks, classify up to `classify.perRun` spans, exit. Exit code 1 means at least one file failed to load (errors in the output), the rest is written. With the embedded database — only when the service does not hold it (otherwise the error "holds the local database"): a manual run opens PGlite itself and closes it afterwards.
- By hand from an agent session — unset its `CLAUDE_CONFIG_DIR`/`CODEX_HOME` override to read the agent's default global folder. An override changes that source folder; it no longer discards the read marks of existing files outside the scan (before BTN-548 a narrowed scan caused a full reread on the next complete run).
- An external Postgres comes from the root `.env`: `TALLY_DB_HOST`, `TALLY_DB_PORT`, `TALLY_DB_NAME`, `TALLY_WRITER_PASSWORD` (the `tally_writer` role, `TALLY_WRITER_USER` to change the name); a manual run without them takes the embedded database, whatever the service's `tally` says. The config without secrets is `tally/tally.config.json` (`TALLY_CONFIG` — another path).
- Even Keel's launch log, handoff snapshots and projects (`select repo, branch from projects`) are in its database `state/even-keel/` (`EVEN_KEEL_STATE_DIR`), read through the service's port (`readStateDatabase`; the collector runs in a worker thread of the service), or the SQLite file `even-keel.db` and the v0.1 files `launches.jsonl` and `handoffs/` while there is no database (`evenKeelState`, `docs/storage.md`); the account folders are Even Keel's `AccountHomes` (`CLAUDE_CONFIG_DIR`, `EVEN_KEEL_ACCOUNTS_DIR`). From a worktree: `EVEN_KEEL_STATE_DIR=<main checkout>/state node --env-file=<main checkout>/.env --import tsx tally/src/main.ts`. Without `EVEN_KEEL_STATE_DIR` the collector finds no projects (a worktree has no database; without one it falls back to the config file of `EVEN_KEEL_CONFIG`), and the run snapshots no project rule files; before BTN-150 that recorded them as deleted and the next run as created again (2026-10-03, 2026-10-12).
- There is no Windows scheduler task any more (before BTN-70 it was "Tally collector", `tally/scheduler/`). A leftover one is removed as administrator: `Unregister-ScheduledTask -TaskName 'Tally collector' -Confirm:$false`; until it is removed, a second collector on an external Postgres is cut off by `pg_try_advisory_lock`.
- The collector never runs `claude -p /usage`: it takes the limits from Even Keel (see below), and an extra poll gives a 429 on the shared token.

## What is read

- Existing account folders, including Claude's and Codex's global folders even when they are not registered in Even Keel. `AccountHomes.all()` discovers history; `list()` and `find()` still restrict runnable global accounts to registered ones. `scripts/cli-check.ts` also uses `all()` so it can check a global CLI without registering it.
- All `*.jsonl` in `<account folder>/projects/<project>/` and the subagent transcripts `<project>/<session>/subagents/agent-*.jsonl` (their `sessionId` is the parent session, `agentId` is their own; the subagents' cost is included in the task). Everything else in session folders (`tool-results/`, `memory/`) is not read.
- Codex rollouts (BTN-170, `src/rollout.ts`): `rollout-<time>-<id>.jsonl` and the zstd-compressed `.jsonl.zst` in `sessions/` and `archived_sessions/` of each Codex account folder (`rolloutFiles` in `src/scan.ts`; Claude's `projects/` scan skips Codex folders). A response is a `token_usage_record` (codex-cli 0.162, key `response_id`); a rollout without them (0.148) gives a response per `token_count` with a non-zero `last_token_usage`, keyed `codex:<session>:<total_tokens>`. A `token_count` after the rollout's first record is never a response: a CLI that writes records gives each response as one, and a turn stopped between a record and its `token_count` leaves every later `token_count` total behind the records', so matching by total would count them twice (BTN-626). A `token_count` before the first record — an older CLI, the session resumed by a newer one — still counts. Tokens: `input_tokens` minus `cached_input_tokens` and `cache_write_input_tokens` is input, `cached_input_tokens` the cache read, `cache_write_input_tokens` the 5-minute write, `output_tokens` (reasoning included) the output. The model and `effort` come from the latest `turn_context`, the branch from `session_meta.git`, `entrypoint` is `codex-exec` (the CLI, how Even Keel runs it) or `codex-desktop` (the app, by `originator`). A changed rollout is read whole (`loadRollout`: a turn's model is in the `turn_context` it began with), its rows are idempotent by key. Loading writes `messages` and `sessions`, no `lines`: signs, steps and tool calls parse Claude's format. Turns are read directly from rollouts during `refreshTurns` (BTN-469, below), so Codex has task times but no stuck spans. A rollout without one response with tokens gets no session — that drops the Claude sessions Codex Desktop imports (all their `token_count` are zero).
- OpenCode databases (BTN-214, `src/opencode.ts`): `data/opencode/opencode.db` of each OpenCode account folder, SQLite in WAL mode, opened read-only (`responseRows` in the root's `src/opencode/db.ts`). A response is an assistant row of `message`, key `opencode:<id>`; its JSON `data` gives the model (`modelID`, without the provider), the folder (`path.cwd`) and `tokens`: `input` (the cache left out), `cache.read`, `cache.write` as the 5-minute write, `output` plus `reasoning` as the output. A subagent's session (`parent_id`) counts under its parent, the parent's title is the session's `ai_title`, `entrypoint` is `opencode`. The database is read whole when it or its `-wal` changed (the size of both, the later `mtime`); as for Codex, only `messages` and `sessions`; turns are read from the database during `refreshTurns` (BTN-617, Task time). `big-pickle` (OpenCode Zen's free model) is priced at 0. Paid `deepseek-v4.1-flash` and Zen's free `deepseek-v4.1-flash-free` share the `deepseek-v4.1-flash` price prefix: both use DeepSeek's API rates for model comparisons, regardless of what OpenCode charges (see Cost).
- Copilot CLI sessions (BTN-215, `src/copilot.ts`): `session-state/<id>/events.jsonl` of each Copilot account folder, the session id being the folder's name (`copilotSources`). A model call is a `session.usage_record` event, key `copilot:<event id>`: `usage.inputTokens` minus `cacheReadTokens` and `cacheWriteTokens` is input, `cacheWriteTokens` the 5-minute write (Copilot's cache lives 30 min), `outputTokens` (reasoning included) the output, `usage.model` the model; a subagent's call carries its `agentId`. The folder and branch come from `session.start`/`session.resume` `context`, `entrypoint` is `copilot`. A changed file is read whole (`loadCopilot`), only `messages` and `sessions`; turns are read from it during `refreshTurns` (BTN-617, Task time). Checked on a live two-turn session (Copilot CLI 1.0.98): the sums matched the CLI's own `session.shutdown` totals. Copilot names a Claude model with dots (`claude-sonnet-4.6`), which no price key matches, so such responses stay unpriced and logged; Tally prices a call at the model's API price, not at the AI credits it took.
- Incremental loading (`src/load.ts`): per file in `files` — how far it has been read (`read_to`, the byte after the last `\n`), the size, `mtime`, `ino` and the SHA-1 of the first ≤1 KB. An unchanged file is not opened. A grown one has its tail read in 8 MB chunks (a line longer than a chunk makes the chunk grow), each chunk in one transaction together with the new `read_to`, so a failed run continues from the same place. An unfinished last line waits for the next run. A file that became smaller than `read_to`, changed `ino` or its beginning is read again from zero; a renamed one is a new path and is read entirely. There are no duplicates: the keys are the row's `uuid`, the response's `message.id`, `tool_use_id`. `forgetFilesExcept` checks stored paths outside the scan (also for an empty scan) and deletes only marks whose filesystem lookup returns `ENOENT` or `ENOTDIR`. Existing files and unreadable paths keep their offsets. This deletes no session data.

## Schema version and migrations (BTN-133)

- The database records its version in `schema_version` (one row). `src/migrations.ts` holds the numbered steps: `STEPS[n]` takes version n to n + 1 in one transaction together with the new version. Step 0 is `src/schema.sql` — version 1; a database from before versions has no `schema_version`, gets `schema.sql` again (it is idempotent) and becomes version 1.
- **A schema change is a new step** at the end of `STEPS` and `TALLY_SCHEMA_VERSION` + 1 in the root's `src/stats/tally-schema.ts` (the page reads it too; a test checks they are equal). Never edit `schema.sql` or a merged step, never remove one: a released database has already run them. A view changed by a step is redefined in full inside the step.
- Migrations run where the schema used to be created: the owner of the embedded database at open (`openLocalTally`) and every collector run after the lock (`TallyDb.migrate`); whichever migrates logs `tally: database schema v<N> → v<M>` (`migratedLine`).
- The database is newer than the code: the collector writes nothing, logs one line and exits with `HALTED`, and the service stops collecting until a restart; `/stats` answers `newer` with both versions and `restart` — whether the build on disk knows the database's version (`builtTallyVersion`: its last `<n>-*.sql`). Then the page asks for a restart (the service was updated and not restarted), otherwise it names a rollback. The embedded database still opens.
- An external Postgres: a step needs the owner of every table, view and sequence and `CREATE` on `public` — `tally_writer` has them by `tally/deploy` (it owns the database and the schema and creates the tables). When it lacks them, the collector changes nothing and logs, per owner role, the `alter … owner to` / `grant create` statements to run, then halts until a restart.
- A manual run from a worktree with a new step migrates the database it points to. On the live database the service, still on older code, then halts until its checkout gets the step and the service restarts: try a new step on the embedded database (a temporary `EVEN_KEEL_STATE_DIR`) first. The user's environment may carry `TALLY_DB_HOST` and the writer's password, and they outrank the folder: run with `TALLY_DB_HOST=` emptied (BTN-170 migrated the live database that way).
- The service starts each collector run as a worker from the code on disk (`tally/src/*.ts` under tsx, `dist/tally/src/` from the build), so a merge or a build reaches the collector at its next run, before the service restarts. The worker gets the schema version the service loaded at its start (`CollectRun.schema`, BTN-1208): a worker with more steps neither migrates nor collects, logs one line asking for a restart and exits with `HALTED` — until 2026-11-15 it migrated the live database ahead of the page's code. The same way the collector met a config of the old form on 2026-10-14 (BTN-150).
- The steps: 1 — `schema.sql`; 2 — `migrations/2-false-rule-deletions.sql` removes the deletions of runs that lost every live project rule file at once, with their snapshot changes (BTN-150); 3 — `migrations/3-gpt-family.sql` redefines `task_estimates` so `model_family` knows `gpt` (BTN-170); 4 — `migrations/4-compactions.sql` adds the view `compactions` (BTN-254); 5 — `migrations/5-milestones.sql` adds `tasks.milestone`, asks every fetched task again for it, and adds the view `milestone_costs` (BTN-172); 6 — `migrations/6-task-sources.sql` adds `tasks.profile_id` and `tasks.url` (BTN-66); 7 — `migrations/7-task-followups.sql` adds `tasks.created_at`, asks every fetched task again for it, and adds the view `task_followups` (BTN-362); 8 — `migrations/8-handoff-headings.sql` redefines `handoff_notes` so its headings skip fenced code blocks (BTN-87); 9 — `migrations/9-codex-stray-counts.sql` deletes the `codex:` rows of a Codex session from its first record row on, the responses counted twice before BTN-626 (a re-read is idempotent by key and would not remove them); 10 — `migrations/10-rework-label.sql` redefines `audit_tasks`, `task_repeats` and `task_followups` so `rework` and the follow-ups take the built-in tracker's `Rework` beside `Переделка` (BTN-785); 11 — `migrations/11-catalogue-prices.sql` adds `messages.provider` (Anthropic for older Claude rows, OpenAI for Codex's), forgets the read marks of OpenCode's databases so they are read whole again and their responses get theirs, adds `model_prices.source` with the key `(source, model)`, and redefines `message_costs` to take a catalogue price and add `price_source` (BTN-859, "Cost"); 12 — `migrations/12-key-spends.sql` adds the table `key_spends`, Even Keel's real spends of sessions on their keys, and the view `message_paid` (BTN-860, "Cost").

## Machines elsewhere (BTN-1280)

A machine of a hub elsewhere (`docs/machines/elsewhere.md`, "Machines elsewhere") has no Tally database and no tracker; its transcripts reach the hub's database over its link, not straight into it: the embedded PGlite listens on 127.0.0.1 only.

- **On the machine** (`src/machine/tally.ts`, `tally/src/ship.ts`): `startMachineTally` starts 15 s after the hub took the first snapshot, then every 5 min after a pass ends, one pass at a time. A pass scans the account folders as the hub's collector does (`AccountHomes.all()`: transcripts, Codex rollouts, OpenCode and Copilot) and runs the same `load*` with a `Store` of its own (`shipToHub`): no launches and no rule context, so a batch carries only `lines`, `messages`, tool calls and `sessions` (`MachineRows`, `rowsOf`). A batch goes in posts of about 2 MB of JSON (`slices`), 1 MB chunks of a transcript. The read marks are the machine database's `tally_files` (step 5 of `MACHINE_STEPS`), moved only once the hub took every post of the chunk; the first post not taken ends the pass, and the rest waits for the next one. Marks of files gone from the scan are dropped. The machine parses on its service's own thread, not a worker.
- **The wire**: `POST /link/tally` (`{connection, rows}` → `{taken}`), not a numbered event: a hub whose stats are off or not open yet never holds the machine's events back. The number and the receipt are the machine's mark; a post sent again writes the same rows by their keys. API version 11.
- **On the hub** (`src/stats/machine-tally.ts`): `MachineTally` writes one post at a time through `TallyService.writer()` (the database the hub collects into, as the writer) with `TallyDb.writeMachine`. It takes nothing (`taken: false`) while the hub collects nothing (stats off, not chosen, the local database not open), when the database is of another schema version than the build's (the hub's own run migrates it first), or the rows are of another shape. The write does not take the collector's advisory lock: the collector lock is per machine, each machine's pass runs alone in its process, and the rows go by keys. A post with responses refreshes the stored limit shares (step 24) after its answer, outside the queue: posts during a refresh call for one more after it, not one each (`settled()` waits for both, for tests).
- **The mark**: `writeMachine` sets `machine` on messages and sessions and makes each account `<key>@<machine id>` (`machineAccount`), so a machine's `global` is not the hub's. `/stats` lists such an account as "key · machine name".
- **What the hub computes**: everything after loading — signs, turns, steps, the classifier, tracker tasks and time reports, the launch log's labels (`syncLaunches` with the hub's journal, which holds the machines' launches) — runs in the hub's own collector over its database, so the machine's Claude sessions get them at its next run. Codex, OpenCode and Copilot turns are read from their files (`refreshTurns`), which only the machine has: a machine's sessions of those agents have no task time.
- **`/stats`**: `?machine=<id>` (`StatsFilter.machine`) keeps one machine's sessions (`onMachine` in `src/stats/base-sql.ts`: `coalesce(sessions.machine, '')`; the hub's own id is the empty one). The page shows the select "Machine" once the hub has more than one machine.

## Compressing raw rows

Measured on 2026-10-03: 753 files, 280 thousand rows, 1166 MB. Of that, `toolUseResult` is 321 MB (a copy of the `tool_result` block), `tool_result` blocks 274 MB, attachments 196 MB, thinking signatures 70 MB (the thinking text is empty), images 40 MB. Chosen (`src/compact.ts`):

- top-level `toolUseResult`, `wireToolInputs` and `rendered` are dropped — they are copies of what is already in `message`;
- an image's `signature` and `data` (`source.type = base64`) are replaced by the length;
- any string longer than 2000 characters — the first 2000 and `…[+N]`;
- `\u0000` and lone surrogates are removed — `jsonb` does not accept them.

After the first load (754 files, 281 thousand rows, 56 s; a repeat run reads only the tails, fractions of a second) the database is 405 MB: `lines` 354 MB, `tool_calls` 28 MB, `messages` 15 MB. That load dropped only `toolUseResult`; `wireToolInputs` and `rendered` take 40 MB in it, and without them the database is about 365 MB. Inside `lines.raw` the heaviest are attachments (88 MB, of which `prompt_snapshot` is 52 MB) and `message.usage` (48 MB, kept: tokens are recomputed from it if the parsing changes).
