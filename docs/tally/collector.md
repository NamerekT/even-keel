# The collector

Running it, what is read, the database's owner, schema version and migrations, machines elsewhere, compressing raw rows. Paths are in `tally/` unless marked as the root's.

## Running

- **In the service.** The Even Keel service starts the collector (the root's `src/stats/tally.ts`, `TallyService`) when the setting `tally` is `local` or `server`: 15 s after startup, then every 5 min from the start of the previous run, and the next one does not start while the previous is going. A run is a separate thread (`src/collect-worker.ts`), so parsing transcripts does not hold the service's event loop; the output goes to the service log, and a run error does not touch the service or the chain. The embedded database is owned by one more service thread (`src/host-worker.ts`), and the page gets its port once the database has opened (if it did not, `/stats` shows an error). For `server` without `TALLY_DB_NAME` or `TALLY_WRITER_PASSWORD` the service does not collect, with one line in the log.
- **By hand**, for debugging: `npm run tally` (or `node --import tsx tally/src/main.ts`) from the repository root reads the new data, writes a limits snapshot, recomputes the signs, turns and steps of changed sessions, asks Huly for stale tasks, classifies up to `classify.perRun` spans and exits. Exit code 1 means at least one file failed to load (errors in the output); the rest is written. On the embedded database it runs only while the service does not hold it (otherwise the error "holds the local database"): it opens PGlite itself and closes it afterwards.
- **By hand from an agent session**: unset its `CLAUDE_CONFIG_DIR`/`CODEX_HOME`, so the run reads the default global folders too.
- **The variables.** An external Postgres comes from the root `.env`: `TALLY_DB_HOST`, `TALLY_DB_PORT`, `TALLY_DB_NAME`, `TALLY_WRITER_PASSWORD` (the `tally_writer` role, `TALLY_WRITER_USER` to change the name). A run by hand without them takes the embedded database, whatever the service's `tally` says. The config without secrets is `tally/tally.config.json` (`TALLY_CONFIG` — another path).
- **Trap: the environment outranks the folder.** The user's environment may carry `TALLY_DB_HOST` and the writer's password, and they outrank `.env` and `EVEN_KEEL_STATE_DIR`: a run meant for the embedded database needs `TALLY_DB_HOST=` emptied. The same holds for `sql.mjs`, whose empty `TALLY_DB_HOST=` reads the embedded database even if `.env` points at the server.
- **Even Keel's state.** The launch log, handoff snapshots, projects (`select repo, branch from projects`), the closed tasks and the built-in tracker are read from Even Keel's database `state/even-keel/` (`EVEN_KEEL_STATE_DIR`) through the service's port (`readStateDatabase`, `docs/storage/first-start.md`), since the collector runs in a worker thread of the service (`evenKeelState` in `src/collect.ts`). With no database yet it reads the SQLite file `even-keel.db` (`sqliteInMemory`: its rows in a database in memory) or else the v0.1 files `launches.jsonl` and `handoffs/`, and the config file instead of the projects: a merge reaches the collector before the restarted service has imported them. The account folders are Even Keel's `AccountHomes` (`CLAUDE_CONFIG_DIR`, `EVEN_KEEL_ACCOUNTS_DIR`).
- **From a worktree**: `EVEN_KEEL_STATE_DIR=<main checkout>/state node --env-file=<main checkout>/.env --import tsx tally/src/main.ts`. Without `EVEN_KEEL_STATE_DIR` the collector finds no projects (a worktree has no database, and the config file of `EVEN_KEEL_CONFIG` is not there either), and the run snapshots no project rule files.
- **Limits**: the collector never runs `claude -p /usage`. It takes the limits from Even Keel ([`cost.md`](cost.md#limit-share)); an extra poll gives a 429 on the shared token.

## What is read

- **Account folders**, including Claude's and Codex's global folders even when they are not registered in Even Keel: `AccountHomes.all()` finds history, while `list()` and `find()` keep runnable global accounts to the registered ones. The root's `scripts/cli-check.ts` also uses `all()`, so it can check a global CLI without registering it.
- **Claude transcripts**: all `*.jsonl` in `<account folder>/projects/<project>/` and the subagent transcripts `<project>/<session>/subagents/agent-*.jsonl` (their `sessionId` is the parent session, `agentId` their own; the subagents' cost is included in the task). Everything else in session folders (`tool-results/`, `memory/`) is not read.
- **Codex rollouts** (BTN-170, `src/rollout.ts`): `rollout-<time>-<id>.jsonl` and the zstd-compressed `.jsonl.zst` in `sessions/` and `archived_sessions/` of each Codex account folder (`rolloutFiles` in `src/scan.ts`; Claude's `projects/` scan skips Codex folders).
  - A response is a `token_usage_record` (codex-cli 0.162, key `response_id`). A rollout without them (0.148) gives a response per `token_count` with a non-zero `last_token_usage`, keyed `codex:<session>:<total_tokens>`.
  - A `token_count` after the rollout's first record is never a response: a CLI that writes records gives each response as one, and a turn stopped between a record and its `token_count` leaves every later total behind the records', so matching by total would count them twice (BTN-626). A `token_count` before the first record (an older CLI, the session resumed by a newer one) still counts.
  - Tokens: `input_tokens` minus `cached_input_tokens` and `cache_write_input_tokens` is input, `cached_input_tokens` the cache read, `cache_write_input_tokens` the 5-minute write, `output_tokens` (reasoning included) the output.
  - The model and `effort` come from the latest `turn_context`, the branch from `session_meta.git`; `entrypoint` is `codex-exec` (the CLI, as Even Keel runs it) or `codex-desktop` (the app, by `originator`).
  - A changed rollout is read whole (`loadRollout`: a turn's model is in the `turn_context` it began with); its rows are idempotent by key. It writes `messages` and `sessions`, no `lines`: signs, steps and tool calls parse Claude's format, so Codex has task times ([`time.md`](time.md#codex-btn-469-srcrollout-turnsts)) but no stuck spans.
  - A rollout without a single response with tokens gets no session, which drops the Claude sessions Codex Desktop imports (all their `token_count` are zero).
- **OpenCode databases** (BTN-214, `src/opencode.ts`): `data/opencode/opencode.db` of each OpenCode account folder, SQLite in WAL mode, opened read-only (`responseRows` in the root's `src/opencode/db.ts`).
  - A response is an assistant row of `message`, key `opencode:<id>`; its JSON `data` gives the model (`modelID`, without the provider), the folder (`path.cwd`) and `tokens`: `input` (the cache left out), `cache.read`, `cache.write` as the 5-minute write, `output` plus `reasoning` as the output.
  - A subagent's session (`parent_id`) counts under its parent, the parent's title is the session's `ai_title`, `entrypoint` is `opencode`.
  - The database is read whole when it or its `-wal` changed (the size of both, the later `mtime`); only `messages` and `sessions`, as for Codex.
- **Copilot CLI sessions** (BTN-215, `src/copilot.ts`): `session-state/<id>/events.jsonl` of each Copilot account folder, the session id being the folder's name (`copilotSources`).
  - A model call is a `session.usage_record` event, key `copilot:<event id>`: `usage.inputTokens` minus `cacheReadTokens` and `cacheWriteTokens` is input, `cacheWriteTokens` the 5-minute write (Copilot's cache lives 30 min), `outputTokens` (reasoning included) the output, `usage.model` the model; a subagent's call carries its `agentId`.
  - The folder and branch come from `session.start`/`session.resume` `context`, `entrypoint` is `copilot`. A changed file is read whole (`loadCopilot`), only `messages` and `sessions`. The sums match the CLI's own totals ([`../verified/copilot.md`](../verified/copilot.md)).
  - Copilot names a Claude model with dots (`claude-sonnet-4.6`), which no price key matches, so such responses stay unpriced and logged; Tally prices a call at the model's API price, not at the AI credits it took.
- **Incremental loading** (`src/load.ts`): per file in `files` — how far it has been read (`read_to`, the byte after the last `\n`), the size, `mtime`, `ino` and the SHA-1 of the first ≤1 KB.
  - An unchanged file is not opened. A grown one has its tail read in 8 MB chunks (a line longer than a chunk makes the chunk grow), each chunk in one transaction with the new `read_to`, so a failed run goes on from the same place. An unfinished last line waits for the next run.
  - A file that became smaller than `read_to`, or changed `ino` or its beginning, is read again from zero; a renamed one is a new path and is read whole. There are no duplicates: the keys are the row's `uuid`, the response's `message.id`, `tool_use_id`.
  - `forgetFilesExcept` checks stored paths outside the scan (an empty scan too) and deletes only the marks whose lookup returns `ENOENT` or `ENOTDIR`. Existing files and unreadable paths keep their offsets, and no session data is deleted.

## The database's owner (`src/local.ts`)

PGlite has one session per process, so one process owns the embedded database's folder (`openLocalTally`). It opens the database (`timezone` is `UTC`, otherwise PGlite takes the host's zone), migrates the schema, starts a `PGLiteSocketServer` (`@electric-sql/pglite-socket`, the Postgres protocol) on `127.0.0.1` on a free port and writes `<state>/tally/owner.json` (`pid`, `port`).

- **All clients** — the collector, the `/stats` page, `sql.mjs` — go through this port with an ordinary `pg`: a direct `db.query` in the owner process would land inside someone else's open transaction, while the socket separates transactions (other connections wait for `commit`). The socket ignores connection options (`-c default_transaction_read_only`, `statement_timeout`).
- **The claim** is the state database's ([`../storage/database.md`](../storage/database.md), the root's `src/storage/claim.ts`, BTN-320): the owner is alive if its `pid` exists and the port listens, and of two processes opening the folder together one is refused with "process N (the Even Keel service) holds the local database…". Here it differs in three ways:
  - `sql.mjs` waits up to 30 s for the port of a claim without one;
  - the service's `TallyService.stop` removes a claim of its own pid after it terminated the database thread, so a thread cut off mid-open does not hold the folder from the next one;
  - `pg_try_advisory_lock` is reentrant in PGlite (one session), so against a second collector on the embedded database there is `owner.json`, while the lock still guards an external Postgres.
- **After a kill** (which is how the Windows service stops node) the database opens again and PGlite replays the WAL. How long a collection and a page read take on a full history is in [`../verified/page.md`](../verified/page.md); `period` is the slowest read because its eight queries go through one session in turn.

## Schema version and migrations (BTN-133)

- **The version** is the one row of `schema_version`. `src/migrations.ts` holds the steps: `STEPS[n]` takes version n to n + 1 in one transaction with the new version, so migration step N (the file `src/migrations/N-*.sql`) gives version N. Step 1 is `src/schema.sql`: a database from before versions has no `schema_version`, gets `schema.sql` again (it is idempotent) and becomes version 1. Every step is listed in [`migrations.md`](migrations.md).
- **A schema change is a new step** at the end of `STEPS` and `TALLY_SCHEMA_VERSION` + 1 in the root's `src/stats/tally-schema.ts` (the page reads it too; a test checks they are equal). Never edit `schema.sql` or a merged step, never remove one: a released database has already run them. A view changed by a step is redefined in full inside the step.
- **Who migrates**: the owner of the embedded database at open (`openLocalTally`) and every collector run after the lock (`TallyDb.migrate`); whichever migrates logs `tally: database schema v<N> → v<M>` (`migratedLine`).
- **A worker of newer code.** The service starts each run as a worker from the code on disk (`tally/src/*.ts` under tsx, `dist/tally/src/` from the build), so a merge or a build reaches the collector at its next run, before the service restarts. The worker gets the schema version the service loaded at its start (`CollectRun.schema`, BTN-1208): a worker with more steps neither migrates nor collects, logs one line asking for a restart and exits with `HALTED`.
- **The database is newer than the code**: the collector writes nothing, logs one line and exits with `HALTED`, and the service stops collecting until a restart. `/stats` answers `newer` with both versions and `restart`, whether the build on disk knows the database's version (`builtTallyVersion`: its last `<n>-*.sql`); then the page asks for a restart (the service was updated and not restarted), otherwise it names a rollback. The embedded database still opens.
- **An external Postgres**: a step needs the owner of every table, view and sequence and `CREATE` on `public`; `tally_writer` has them by `tally/deploy` (it owns the database and the schema and creates the tables). When it lacks them, the collector changes nothing and logs, per owner role, the `alter … owner to` / `grant create` statements to run, then halts until a restart.
- **A new step from a worktree**: a run by hand migrates the database it points to, and the live service, still on older code, then halts until its checkout gets the step and it restarts. Try a new step on the embedded database of a temporary `EVEN_KEEL_STATE_DIR` first, with `TALLY_DB_HOST=` emptied ("Running" above).

## Machines elsewhere (BTN-1280)

A machine of a hub elsewhere (`docs/machines/elsewhere.md`, "Machines elsewhere") has no Tally database and no tracker; its transcripts reach the hub's database over its link, not straight into it: the embedded PGlite listens on 127.0.0.1 only.

- **On the machine** (the root's `src/machine/tally.ts`, `src/ship.ts`): `startMachineTally` starts 15 s after the hub took the first snapshot, then every 5 min after a pass ends, one pass at a time.
  - A pass scans the account folders as the hub's collector does (`AccountHomes.all()`: transcripts, Codex rollouts, OpenCode and Copilot) and runs the same `load*` with a `Store` of its own (`shipToHub`): no launches and no rule context, so a batch carries only `lines`, `messages`, tool calls and `sessions` (`MachineRows`, `rowsOf`).
  - A batch goes in posts of about 2 MB of JSON (`slices`), 1 MB chunks of a transcript. The read marks are the machine database's `tally_files` (machine step 5, `docs/storage/steps.md`), moved only once the hub took every post of the chunk; the first post not taken ends the pass, and the rest waits for the next one. Marks of files gone from the scan are dropped.
  - The machine parses on its service's own thread, not a worker.
- **The wire**: `POST /link/tally` (`{connection, rows}` → `{taken}`), not a numbered event, so a hub whose stats are off or not open yet never holds the machine's events back. The number and the receipt are the machine's mark; a post sent again writes the same rows by their keys.
- **On the hub** (the root's `src/stats/machine-tally.ts`): `MachineTally` writes one post at a time through `TallyService.writer()` (the database the hub collects into, as the writer) with `TallyDb.writeMachine`.
  - It takes nothing (`taken: false`) while the hub collects nothing (stats off, not chosen, the local database not open), when the database is of another schema version than the build's (the hub's own run migrates it first), or when the rows are of another shape.
  - The write does not take the collector's advisory lock: the lock is per machine, each machine's pass runs alone in its process, and the rows go by keys.
  - A post with responses refreshes the stored limit shares ([`cost.md`](cost.md#the-stored-shares)) after its answer, outside the queue: posts during a refresh call for one more after it, not one each (`settled()` waits for both, for tests).
- **The mark**: `writeMachine` sets `machine` on messages and sessions and makes each account `<key>@<machine id>` (`machineAccount`), so a machine's `global` is not the hub's. `/stats` lists such an account as "key · machine name".
- **What the hub computes**: everything after loading — signs, turns, steps, the classifier, tracker tasks and time reports, the launch log's labels (`syncLaunches` with the hub's journal, which holds the machines' launches) — runs in the hub's own collector over its database, so the machine's Claude sessions get them at its next run. Codex, OpenCode and Copilot turns are read from their files (`refreshTurns`), which only the machine has: a machine's sessions of those agents have no task time.
- **`/stats`**: `?machine=<id>` (`StatsFilter.machine`) keeps one machine's sessions (`onMachine` in the root's `src/stats/base-sql.ts`: `coalesce(sessions.machine, '')`; the hub's own id is the empty one). The page shows the select "Machine" once the hub has more than one machine.

## Compressing raw rows (`src/compact.ts`)

The raw row of each transcript line is kept compressed, in `line_raws` (in `lines` before migration step 22):

- the top-level `toolUseResult`, `wireToolInputs` and `rendered` are dropped: they are copies of what is already in `message`;
- an image's `signature` and `data` (`source.type = base64`) are replaced by the length;
- any string longer than 2000 characters keeps the first 2000 and `…[+N]`;
- `\u0000` and lone surrogates are removed: `jsonb` does not accept them.

`message.usage` is kept whole: tokens are recomputed from it if the parsing changes. This cut a history of about 1.2 GB of transcripts to about a third ([`../verified/page.md`](../verified/page.md)).
