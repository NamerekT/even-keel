# Baton

Диспетчер цепочек сессий Claude Code. Берёт открытые задачи проекта из Huly, строит порядок по связям `blocks`, запускает сессию на первую задачу и, когда задача уходит в Done, запускает следующую. Веб-страница показывает цепочку и по каждой сессии — этап, текущее действие и заполненность контекста. Работает службой Windows на рабочей станции пользователя: агенты запускаются только здесь.

Глобальные правила из `~/.claude/CLAUDE.md` действуют полностью. Ниже — только то, что специфично для этого проекта.

## Стек

- Node.js 24 + TypeScript, тесты — vitest.
- Huly — через `@hcengineering/api-client`, тот же клиент, что у git-хуков в `~/.githooks`.
- Сессии — CLI `claude` (`--bg`, `agents --json`) и транскрипты в `<папка аккаунта>/projects`; `claude agents`, транскрипты, `sessions/<pid>.json` и `settings.json` читаются по каждой папке аккаунта. Свежесть кэша промпта — из транскрипта: срок (5 мин или 1 ч) по `usage.cache_creation` последнего ответа, который писал кэш (оба — берётся 5 мин), отсчёт от первой строки последнего ответа.
- Модель сессии — по ярлыку задачи `Sonnet`/`Opus`/`Haiku` (без регистра и пробелов по краям): `--model <алиас>` на каждом запуске — первом, `--resume`, передаче дел, «Новой сессии»; к промту дописывается `modelPrompts.<алиас>` из `baton.config.json`, если есть. Нет ярлыка или их два разных — модель по умолчанию, второе — с предупреждением в лог (`src/sessions/launch.ts`).
- Ярлык `Вручную` (без регистра и пробелов по краям) убирает задачу из цепочки совсем: её запускает пользователь сам. Отсекается там же, где закрытые (`Dispatcher.setTasks`), поэтому блокером для задач цепочки она не считается.
- В цепочку входят только задачи в Todo и дальше: Backlog (категория `UnStarted`) — склад идей, цепочка его не берёт, и блокером он тоже не считается. Задачу пускает в цепочку перевод в Todo; In Progress и In Review (`Active`) цепочка видит. Задача, которую ведёт сессия и которую вернули в Backlog, остаётся в цепочке, пока сессия посреди хода (`busy`), потом выпадает (`Dispatcher.enters`).
- Интерфейс — React + Vite в `web/`, сборка в `dist/web`, её отдаёт сервер; маршруты клиента сервер отвечает `index.html`. Типы состояния клиент берёт из `src/state.ts` — там только типы, без `node:*`. `npm run dev:web` — Vite с прокси `/api` на `BATON_URL` (по умолчанию `:4747`), `npm run dev:fake` — вёрстка на фейковом состоянии без Huly и сессий (`?link=stale|connecting` — состояния связи, `?chain=idle` — без активной цепочки, чтобы проверить запуск, `?chain=limit` — цепочка ждёт сброса лимита, `?chain=skip` — пропущенная задача и сессия, отложенная блокером, `?chain=restart` — сессия свернулась по лимиту и потеряла Remote Control, кнопка «Новая сессия», `?chain=close` — текущая задача закрывается каждые 10 с и цепочка берёт следующую, `?chain=checkpoint` — по текущей задаче две передачи по контрольной точке, `?chain=leftover` — предупреждения уборки после Done, `?usage=unread|off|waiting` — состояния опроса `/usage`; `?account=out|expired|login|failed|unknown` — состояния активного аккаунта Claude, код `fail` в поле входа — неудачный вход, `?account=pending` — новая конфигурация ждёт завершения сессий аккаунта).
- Лимиты — у каждого аккаунта свои: `claude -p /usage --output-format json --no-session-persistence` в его папке раз в минуту (локальная команда, квоту не тратит) и снимок statusline (он помечен `configDir` сессии, без пометки — глобальный аккаунт); берётся более свежий. С истёкшим access-токеном `/usage` лимитов не отдаёт — это «нет данных» (`stale`), не ошибка. Ответ `/usage` принимается целиком или никак: обе строки окон с процентом и сбросом (`0% used` без сброса — окно не начато). Опрос продолжается, только если ответ прямо говорит `num_turns: 0` и `total_cost_usd: 0`, иначе выключается до перезапуска. Нечитаемый ответ или выключенный опрос страница показывает баннером (`UsageBanner`). Пока окно выбрано, следующая задача не запускается: цепочка ждёт сброса (`limitUntil`) и продолжает сама.
- Аккаунты Claude — по папке конфигурации на аккаунт (`CLAUDE_CONFIG_DIR`): глобальный `~/.claude` (ключ `global`) и `%USERPROFILE%\.claude-accounts\<имя>` (`BATON_ACCOUNTS_DIR`). Токены хранит и обновляет сам CLI; Baton из `.credentials.json` читает только сроки (`expiresAt`, `refreshTokenExpiresAt`), токены не читает и не копирует. `claude auth status --json` по каждой папке раз в минуту. «Добавить аккаунт» — `claude auth login --claudeai` во временной `.pending-*`, после входа папка получает имя по e-mail; «Продлить вход» — вход в папке аккаунта; «Удалить» — `claude auth logout` и папка прочь (не активный, не глобальный, без незавершённых сессий). Ссылку и поле для кода страница показывает в меню аккаунта. Переключить активный аккаунт (и продлить вход активного) можно, когда цепочка на паузе или остановлена и ни одна сессия активного аккаунта не посреди хода — `busy` или `waiting`; что мешает, меню показывает списком. Пока идёт вход в активный аккаунт, он не вошёл или его вход истёк, новые сессии не запускаются (цепочка встаёт на паузу с причиной). `state/account.json` — активный аккаунт и по каждой папке: её аккаунт, с какого момента он действует и какой был до него. Лимиты папки, полученные раньше смены аккаунта в ней, не показываются; аккаунт упора в лимит — папка сессии и её e-mail на момент упора, `--resume` — только если активна та же папка с тем же e-mail.
- Перед каждым запуском в папке аккаунта в неё переносится общая конфигурация (`src/account/share.ts`): `settings.json` (глобальный поверх своего), `CLAUDE.md`, реестр плагинов, junction на `agents`, `hooks`, навыки и память проектов, а из `~/.claude.json` — доверие и настройки проекта (MCP local scope, `allowedTools`) для уже доверенных проектов. Временный демон папки (`claude --bg` поднимает его сам) кэширует конфигурацию: перенос доходит до сессий, запущенных после его перезапуска. Поэтому, если перенос что-то поменял, а незавершённых сессий в папке нет (свежий `claude agents`), Baton перед запуском останавливает её демон — `claude daemon stop --any` с `CLAUDE_CONFIG_DIR` папки, глобальный демон он не трогает (`src/account/daemon.ts`). Есть незавершённые — демон не трогается, меню аккаунта пишет, что конфигурация дойдёт после них, а остановка переносится на первый запуск без них. Отметка живёт в памяти службы.
- Хостинг: self-hosted Forgejo, приватный репозиторий.

## Задачи

Работа по этому репозиторию ведётся через трекер Huly, проект `BTN`.
Правила, статусы и порядок действий — скил `huly-tracker`, читать его перед созданием задачи или началом работы по ней.

- Код пишется под активную задачу, в её worktree. Прямая просьба без задачи — коммит в `main` основного чекаута (глобальный CLAUDE.md).
- Ветка: `btn-<номер>/short-description`. Коммит: `[BTN-<номер>] Message`.
- Содержимое задач (заголовки, описания, комментарии) — на русском.
- Сессия доводит задачу до `main` сама: после одобрения ревьюера сливает ветку (`git merge --no-edit` в основной рабочей копии) — это закрывает задачу. Пользователю — отчёт о сделанном, а не команда слияния. Worktree, ветку и пуш `main` после слияния сессия из цепочки не трогает — это делает Батон (ниже). Сессия, запущенная вручную, убирает за собой сама по навыку.

## Worktree задач

Батон готовит worktree сам (`src/git/worktree.ts`), сессии его не создают.

- Перед первым запуском по задаче — в основном чекауте проекта (`config.projects[project]`) `git worktree add -b <ключ>-<номер>/task .claude/worktrees/<ключ>-<номер> main`, всё в нижнем регистре. Хвост ветки всегда `task`: хукам в `~/.githooks` нужен вид `<ключ>-<номер>/<что-то>`. Worktree по этому пути уже есть — берётся как есть, с его веткой; есть только ветка — возвращается в новый worktree. `.claude/worktrees/` дописывается в `.git/info/exclude`, если git её не игнорирует. Сессия стартует с `cwd` = worktree, промт — ID задачи, строка про готовый worktree и что убирать за собой не надо (`startPrompt`).
- Текущая задача ушла в Done (категория `Won`; отменённая или выпавшая — нет) — `closing` цепочки: ждать, пока её сессия не посреди хода, затем `git worktree remove` (без `--force`), `git branch -d` ветки задачи (только `<ключ>-<номер>/…`), `git push origin --delete`, если она есть на origin, и `git sync`, если у проекта есть remote. Следующая задача запускается после этого.
- Грязный worktree, папка, занятая процессом, неслитая ветка — предупреждение в лог и на страницу проекта (`leftovers` в `state/chain.json`, кнопка «Убрал» — `chain/dismiss`), цепочка идёт дальше. Упал `git sync` — цепочка на паузе с его выводом, силой ничего не пушится; после «Снять с паузы» уборка не повторяется.

Исключение из скила: прямая работа с API Huly здесь разрешена — это суть проекта.

## Инварианты

1. **Остановившуюся сессию диспетчер не трогает.** Вопрос, ошибка — ничего не происходит. Пользователь отвечает с телефона через Remote Control или сам двигает задачу в Huly. Исключение — лимит у сессии текущей задачи незапаузенной цепочки: после сброса лимита или смены аккаунта диспетчер продолжает её через `--resume`, если кэш ещё тёплый (тот же аккаунт, < 55 мин с последнего ответа), иначе останавливает её (`claude stop`, не `rm`) и запускает новую в её рабочей папке с передачей дел (`src/chain/relay.ts`). Лимит — это и ошибка `rate_limit`, и мягкое предупреждение CLI (`usageLimitNote: "wrap_up"`), после которого сессия сама сворачивает ход. Рабочую папку и ветку для передачи даёт git (корень worktree от последнего `cwd`), не транскрипт: его `gitBranch` — ветка папки запуска.
   Второе исключение — кнопка «Новая сессия» (`restart`): пользователь заменяет сессию текущей задачи, если она не посреди хода, — та же передача дел, в журнале `restart` со ссылкой на прежнюю сессию.
   Третье исключение — контрольная точка, которую сессия поставила сама: сессия текущей задачи незапаузенной цепочки закончила ход, и последняя строка её последнего ответа — `CHECKPOINT: <путь>` (так просит глобальный хук `~/.claude/hooks/context-checkpoint.mjs`, когда контекст разросся). Диспетчер делает ту же передачу дел, в промте — путь к записке от корня worktree, в журнале `checkpoint` со ссылкой на прежнюю сессию. Метка после неё — вызов инструмента, новый ответ без метки или сообщение в сессию — гасит её. Передача повторяется, сколько сессии её просят; число передач по задаче видно на странице. Сессия с лимитом идёт по правилу лимита (её промт тоже указывает на записку), а пока лимит выбран или новые сессии не запускаются, метка ждёт.
   «Не трогает» — не останавливает её и ничего ей не пишет. Перестать её ждать диспетчер может, если сессия не посреди хода (`busy`/`waiting`): текущая задача получила в Huly открытый блокер из той же цепочки (сессия отложила её сама, в журнале `postpone`) или пользователь нажал «Пропустить» (`skip`). Пропущенную задачу цепочка не берёт, пока пользователь её не вернёт или она не закроется в Huly.
2. **Huly — источник правды о статусах.** Своё у диспетчера только порядок цепочки, пауза, список пропущенных задач и предупреждения уборки.
3. **Секретов в репозитории нет.** Адреса и учётки — из окружения или локального файла вне git; в репозитории только `.env.example` с фейками.
4. **Пароль Windows диспетчер не принимает и не хранит.** Учётку службы пользователь вводит сам.

## Служба Windows

- Хост службы — `service/BatonService.cs`, собирается штатным `csc.exe` из .NET Framework при установке, сторонних обёрток нет. Держит `node --import tsx src/main.ts` в корне репозитория, перезапускает при падении, пишет вывод в `logs/baton.log`. Для отладки без службы: `BatonService.exe <корень> <node.exe> --console`.
- `service/install.ps1` и `service/uninstall.ps1` — из PowerShell 7 от администратора. Пароль учётки скрипт не спрашивает: пользователь вводит его на вкладке «Вход в систему» в services.msc, она же выдаёт право «Вход в качестве службы».
- Служба читает `.env` и `baton.config.json` из корня репозитория; порт не должен быть занят ручным запуском.
- Служба отдаёт собранный `dist/web`: `install.ps1` запускает `npm run build`. После обновления кода — снова `install.ps1` (или `npm run build` и перезапуск службы), иначе страница старая или 503.
- `claude --bg` ходит через демон-супервизор (`claude daemon run`, канал `\\.\pipe\cc-daemon-…`). Остановка службы фоновые сессии не убивает — они дети демона.

## Тесты

TDD для логики: порядок цепочки, переходы по статусам, разбор транскриптов и ответов Huly. Работа с процессами, сетью и вёрстка тестами не покрываются — проверяются вживую, скриншоты Playwright в `.temp/`.
