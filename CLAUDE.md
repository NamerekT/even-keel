# Even Keel

Раньше назывался Baton (Батон): так он записан в старых коммитах, задачах и памяти; ключ Huly `BTN` и ветки `btn-*` остались.

Диспетчер цепочек сессий Claude Code. Берёт открытые задачи проекта из Huly, строит порядок по связям `blocks`, запускает сессию на первую задачу и, когда задача уходит в Done, запускает следующую. Веб-страница показывает цепочку и по каждой сессии — этап, текущее действие и заполненность контекста. Работает службой Windows на рабочей станции пользователя: агенты запускаются только здесь.

Глобальные правила из `~/.claude/CLAUDE.md` действуют полностью. Ниже — только то, что специфично для этого проекта.

`README.md` (на английском, для тех, кто видит проект впервые) и `LICENSE` (MIT) — публичная документация (BTN-60). Меняется установка, ключ конфига, переменная окружения или поведение, описанное там, — правится и README; версия CLI в разделе «Before you run it» — последняя, на которой проверено.

## Стек

- Node.js 24 + TypeScript, тесты — vitest.
- Трекер — через прослойку `src/tracker/` (BTN-58): нейтральная модель задачи (`model.ts`: `TrackerTask` от адаптера, `Task` — плюс модель и вопрос из ярлыков `Question` или `Вопрос`) и контракт адаптера (`source.ts`, `TaskSource`/`TrackerAdapter`, описание там же в JSDoc — для тех, кто пишет свой). Цепочка, порядок, правила и состояние страницы знают только их. Адаптер выбирается ключом `tracker` в `even-keel.config.json` — общим и у проекта (`{ "repo", "tracker" }`), по умолчанию `huly`; реестр — `src/tracker/adapters.ts`, в репозитории Huly и GitHub. Трекеру, у которого проект не называется ключом, адаптер объявляет `projectKey` — ключ в объекте проекта (у GitHub `github`: `owner/name`), без него или кривой — ошибка конфига; значения приходят в `setup` вторым аргументом. ID задачи — `<ключ проекта>-<номер>`: по нему worktree, ветка и статистика. Чего у трекера нет, адаптер отдаёт пустым. Необязательные `brief` (заголовок и описание дописываются к промту запуска и передачи дел) и `complete` (Even Keel закрывает задачу, увидев её ветку влитой в `main`: `src/git/merged.ts` — вершина ветки в `main` и сдвинута с начала по reflog, `src/tracker/closer.ts`; `true` — задачу перевели, уже закрытая — `false`, ничего не пишется) — у Huly есть оба (BTN-63, `src/huly/source.ts`): описание — markdown, Done — статус категории `Won` из типа проекта. С git-хуком, который тоже переводит в Done, они не спорят: кто первый, тот и закрыл. Ключ `brief` (`true` по умолчанию, общий и у проекта — `{ "repo", "brief" }`, применяется на лету) выключает описание в промте для проектов, где сессии читают задачу сами через MCP трекера. Тогда Even Keel проверяет, видит ли сессия MCP-сервер адаптера (`mcpServer`, у Huly `huly`; `src/tracker/mcp.ts`: user scope и local scope проекта из `.claude.json` глобального и активного аккаунта — по любому написанию пути, `.mcp.json` без `disabledMcpjsonServers`, включённые плагины, минус `disabledMcpServers`) — при старте, смене конфига и перед запуском. Не видит — предупреждение в лог и баннер `McpBanner` (`mcpMissing` в состоянии): сессия получит только номер задачи. На каждый трекер в работе — своя связь и опрос (`src/tracker/link.ts`, `poller.ts`) и строка в меню «Состояние»; ссылка на задачу — по трекеру её проекта (`trackerUrls`, шаблон `issueUrl` с `{id}` или `{number}`).
- Адаптер GitHub Issues (BTN-65, `src/github/`): GraphQL `api.github.com` токеном `GITHUB_TOKEN` (fine-grained, Issues: Read and write). Открытая issue — `Open` (`ToDo`), закрытая как completed (или без причины) — `Completed` (`Won`), not planned и duplicate — `Lost`; блокеры — нативные «blocked by», родитель и подзадачи — sub-issues, приоритет — ярлык `priority: <уровень>` (или `priority/<уровень>`), оценки нет (0). Блокер или родитель из репозитория без проекта — ID `owner/name#номер`. `complete` закрывает issue как completed. Бэклога у GitHub нет — вход в цепочку держать на ярлыке (`requiredLabels`). Pull request задачей не бывает. Проверен вживую (2026-10-04, приватный репозиторий): две issue со связью «blocked by» и вехой прошли цепочкой по очереди, после слияния `complete` закрыл обе как completed. Второй экземпляр Even Keel из сессии Claude Code запускать без её переменных `CLAUDE*`: унаследованный `CLAUDE_CONFIG_DIR` делает `global` папкой аккаунта сессии.
- Плагины Claude Code (BTN-64): репозиторий — маркетплейс `even-keel` (`.claude-plugin/marketplace.json`), по плагину на трекер в `plugins/<трекер>/` — MCP трекера (`.mcp.json`) и навыки (`skills/<имя>`, вызываются как `<трекер>:<имя>`): `task` — работа с задачей, у Huly ещё `split` — разрез на подзадачи и `setup` — заведение репозитория в трекере; на английском и без чужих имён и замеров. Плагин `huly` — образец: сервер `@firfi/huly-mcp`, учётки (`HULY_URL`, `HULY_WORKSPACE`, `HULY_TOKEN` или `HULY_EMAIL`/`HULY_PASSWORD`) — из окружения сессии наследованием, в `.mcp.json` их нет, там только постоянный `TOOLSETS` (набор для работы с задачей). Подстановки `${…}` в `.mcp.json` плагина не годятся: незаданная переменная, даже с `:-` по умолчанию, — сессия считает сервер упавшим и не запускает его (`claude mcp list` при этом пишет «Connected»), а пустой `HULY_TOKEN` сервер не принимает. Учётки пользователь кладёт в `env` своего `~/.claude/settings.json`: его применяет сама сессия, а `share.ts` переносит файл в папки аккаунтов. Системные переменные для цепочки не годятся: `envOf` (BTN-34) убирает `HULY_*` из окружения `claude`, чтобы учётка Even Keel из `.env` не попала в сессии, а сессии — дети демона папки, и окружение у них от того, кто поднял демон. Ставится с глобальной конфигурацией (без `CLAUDE_CONFIG_DIR`): `claude plugin marketplace add <репозиторий>`, затем в репозитории проекта `claude plugin install huly@even-keel --scope project` — `enabledPlugins` в `.claude/settings.json` проекта, его нужно закоммитить, иначе worktree задач его не увидят. Реестр плагинов в папки аккаунтов переносит `share.ts`, поставленное в папке аккаунта перезапишется. С плагином у проекта `brief: false`. Правка плагина — с новой `version` в его `plugin.json`: установленная копия лежит в кэше по версии, и `claude plugin update` с той же версией ничего не берёт. Как пользоваться — `plugins/huly/README.md`. Плагин `github` (BTN-65) — удалённый сервер GitHub (`api.githubcopilot.com/mcp/`, наборы `issues,labels`): HTTP-серверу токен нужен в заголовке, поэтому здесь подстановка `${GITHUB_PERSONAL_ACCESS_TOKEN}` — без переменной сервер всё равно бесполезен. Это не `GITHUB_TOKEN` Even Keel: тот `envOf` убирает из сессий. Связей «blocked by» в MCP нет — навык ставит их через `gh api …/dependencies/blocked_by`. Как пользоваться — `plugins/github/README.md`.
- Huly — адаптер `src/huly/` через `@hcengineering/api-client`, тот же клиент, что у git-хуков в `~/.githooks`.
- Сессии — CLI `claude` (`--bg`, `agents --json`): `EVEN_KEEL_CLAUDE_BIN`, иначе отдельный CLI `~/.local/bin/claude.exe` (вне Windows — `claude`), иначе бинарь самой свежей версии расширения VS Code (его папку обновление расширения удаляет) — и транскрипты в `<папка аккаунта>/projects`; `claude agents`, транскрипты, `sessions/<pid>.json` и `settings.json` читаются по каждой папке аккаунта. `claude agents --json` (2.1.284) не печатает ни `pid`, ни `status`, а `state: done` остаётся и за живой сессией после хода, и за остановленной: живой процесс, `pid` и `busy`/`idle` дают записи `sessions/<pid>.json` с живым `pid` (`withLiveRecords`). Свежесть кэша промпта — из транскрипта: срок (5 мин или 1 ч) по `usage.cache_creation` последнего ответа, который писал кэш (оба — берётся 5 мин), отсчёт от первой строки последнего ответа.
- Модель сессии — по ярлыку задачи `Sonnet`/`Opus`/`Haiku` (без регистра и пробелов по краям): `--model <алиас>` на каждом запуске — первом, `--resume`, передаче дел, «Новой сессии»; к промту дописывается `modelPrompts.<алиас>` из `even-keel.config.json`, если есть. Нет ярлыка или их два разных — модель по умолчанию, второе — с предупреждением в лог (`src/sessions/launch.ts`).
- Промты сессий собираются строго (`src/sessions/prompt.ts`): значение в промте запуска и передачи дел — через `fill`, пустое или не строка — ошибка сборки, цепочка встаёт на паузу с ней, а не уходит в сессию с пустым местом. `modelPrompts` передаётся как есть, подстановок в нём нет: `{имя}`, `{{имя}}`, `${имя}` — ошибка конфига.
- Правила входа в цепочку — `chain` в `even-keel.config.json` (`src/chain/rules.ts`): общий верхний и поверх него свой у проекта (проект — строка-путь или `{ "repo", "chain" }`, ключ проекта заменяет общий целиком). `active` и `terminal` — имена статусов (без регистра и пробелов по краям); нет ключа — по категориям: активные `ToDo` и `Active`, терминальные `Won` и `Lost`. Имя, которого нет в Huly, — предупреждение в лог; статус в обоих списках — ошибка конфига. `requiredLabels` — нужен хоть один из них (пусто — не нужен), `excludedLabels` (по умолчанию `["Manual", "Вручную"]`) убирает задачу совсем, её запускает пользователь сам. Не прошедшая правила по ярлыкам задача отсекается там же, где закрытые (`Dispatcher.setTasks`), и блокером для задач цепочки не считается.
- По умолчанию в цепочку входят задачи в Todo и дальше: Backlog (категория `UnStarted`) — склад идей, ни активный, ни терминальный, цепочка его не берёт. Задачу пускает в цепочку перевод в активный статус. Но открытый блокер в неактивном статусе (BTN-68, `waitingBlockers` в `src/chain/order.ts`, и дальше по его блокерам того же рода) держит задачу цепочки: она не запускается, текущая с таким блокером откладывается (`postpone`), как с блокером из цепочки; все задачи держат такие блокеры — цепочка кончается. Страница показывает его (`ProjectOrder.waiting`) перед задачей, которую он держит (`withWaiting`), приглушённым и под замком: без номера, кнопок и перетаскивания, ссылка — на задачу в трекере. Перевели в активный статус — обычная задача цепочки; закрыли — задача свободна. Задача, которую ведёт сессия и которую вернули в неактивный статус, остаётся в цепочке, пока сессия посреди хода (`busy`), потом выпадает (`Dispatcher.enters`). Уборка worktree — только когда терминальный статус из категории `Won`; ушедшая в терминальный статус другой категории просто выпадает.
- Порядок цепочки (`src/chain/order.ts`): блокеры `blocks`, затем сохранённый порядок (`state/chain.json`), милстоун, приоритет Huly (Urgent → High → Medium → Low → без приоритета), номер задачи. Новая задача встаёт перед первой задачей своего или более низкого приоритета, после более срочных (`withFresh`); текущая задача остаётся первой.
- Язык (BTN-57, `src/language.ts`: `en`, `ru`): `language` в `even-keel.config.json` — язык страницы (`null` или нет ключа — язык браузера, английский, если он незнаком), `promptLanguage` — язык промтов сессий (нет — `language`, затем английский; `src/chain/prompts.ts`). Страница переводит свою рамку (`web/src/i18n/`, `ru.ts` — источник типа, `en.ts` ему равен) и сообщения сервера (BTN-62): причины паузы, уборка, ошибки конфига, входа и команд приходят кодом со значениями (`{ code, params, detail, cause, items }`, `src/notice/notice.ts`), английский текст и список кодов — `src/notice/en.ts`, русский — `web/src/i18n/notices-ru.ts`, страница собирает текст через `say()`. Новый код — запись в обоих файлах, равенство наборов проверяет тип. Лог службы — на английском; вывод git и CLI (`detail`) и строки, сохранённые до BTN-62 (старый `state/chain.json`), показываются как есть. Данные (транскрипты, ярлыки, задачи) не переводятся.
- `even-keel.config.json` служба перечитывает на лету (`src/config-file.ts`): сразу применяются `chain`, `brief`, `modelPrompts`, `stats`, `language` и `promptLanguage`, а `host`, `port`, `projects`, `context` — после перезапуска (в лог — что ждёт). Битый файл — работает последний исправный, ошибка в лог и баннером на странице (`ConfigBanner`).
- Интерфейс — React + Vite в `web/`, сборка в `dist/web`, её отдаёт сервер; маршруты клиента сервер отвечает `index.html`. Типы состояния клиент берёт из `src/state.ts` — там только типы, без `node:*`. `npm run dev:web` — Vite с прокси `/api` на `EVEN_KEEL_URL` (по умолчанию `:4747`), `npm run dev:fake` — вёрстка на фейковом состоянии без Huly и сессий (`?link=stale|connecting` — состояния связи, `?chain=idle` — без активной цепочки, чтобы проверить запуск, `?chain=limit` — цепочка ждёт сброса лимита, `?chain=skip` — пропущенная задача и сессия, отложенная блокером, `?chain=backlog` — блокеры из Backlog под замком перед задачей, которую держат (веха v0.2), `?chain=restart` — сессия свернулась по лимиту и потеряла Remote Control, кнопка «Новая сессия», `?chain=close` — текущая задача закрывается каждые 10 с и цепочка берёт следующую, `?chain=checkpoint` — по текущей задаче две передачи по контрольной точке, `?chain=leftover` — предупреждения уборки после Done, `?usage=unread|off|waiting` — состояния опроса `/usage`, `?config=broken` — баннер битого конфига, `?mcp=missing` — баннер «brief выключен, а MCP-сервера трекера сессии не видят»; `?account=out|expired|login|failed|unknown` — состояния активного аккаунта Claude, код `fail` в поле входа — неудачный вход, `?account=pending` — новая конфигурация ждёт завершения сессий аккаунта, `?account=removing` — папка ждёт завершения сессий, чтобы удалиться, `?account=vscode-chats` — VS Code не переключить из-за открытых чатов, `?account=vscode-broken` — `settings.json` VS Code не читается, `?stats=off|error|empty` — статистика выключена, база недоступна, данных нет — на `/stats` и в полосе страницы проекта, `?rules=empty|thin` — правок правил нет, «До и после» с малой выборкой, `?lang=en|ru` — язык страницы из конфига (без него — язык браузера); фейковая история — с ноября 2023, несколько проектов и папок без проекта).
- Статистика Tally (`tally/`, BTN-44, BTN-49) — страница `/stats` (ссылка в шапке, `web/src/stats/`) по всем проектам Tally: колонка проектов (фильтр и легенда), период, плитки, график расхода, «Откуда расход», таблица задач (строка раскрывается в сессии на оси времени и застревания) и застревания. Раздел «Время и оценки» (BTN-55, `web/src/stats/EstimateSection.tsx`, `accuracy.ts`) — медиана активного времени закрытых задач, доля уложившихся в ×1,5 от оценки и медиана «факт / оценка» по проектам, компонентам и моделям; сравниваются только закрытые задачи с оценкой, без оценки и открытые — счётчиком. В таблице задач — «Оценка», «Время» (активное, за всю задачу, а не за период; полное — в подсказке) и «Ожидание» (из view `task_times`). Раздел «Шаги» (BTN-56, `web/src/stats/StepsSection.tsx`, сервер — `src/stats/steps.ts` и `steps-reader.ts`) — долгие команды агента из `step_runs` Tally за период: по шагу запуски, p50, p90, макс., доля дольше `slowSeconds`, распределение по корзинам, холодный и тёплый запуск, упавшие, доля активного времени задач (по задачам целиком; база — активное время задачи плюс время запусков вне ходов) и p90 по неделям; сверху — шаги, выросшие за неделю (то же правило, что view `step_growth`), внизу — свёрнутые команды без правила, дольше всего в сумме. В раскрытой задаче — строка «Шаги:» с долей каждого шага. Сервер — `src/stats/`: `GET /api/stats/history?scope=all|chain&account=&tz=` (расход по дням и проектам за всю историю — для колонки, тепловой карты календаря и графика), `GET /api/stats/period?from=&to=&projects=&scope=&account=&tz=` (плитки, источники, задачи, застревания), `GET /api/stats/steps?from=&to=&projects=&scope=&account=&tz=` (раздел «Шаги»), `GET /api/stats/task/<ID>` (сессии, отрезки застреваний и шаги задачи). Вся история читается за ~0,5–1,4 с (замеры 2026-10-03 и 2026-10-04, сервер и PGlite; `period` на PGlite — 1,6–1,7 с), агрегата по дням в Tally не нужно. Вид страницы — в URL (`web/src/stats/search.ts`): `range=7d|month|last-month|3m|year|all` (готовый период, скользящий; 30 дней — без параметра) или `from=&to=`, `projects=` (нет — все, пусто — ни одного), `scope=chain`, `account=`, `step=d|w|m` (шаг графика; нет — сам: до ~2 месяцев по дням, до года по неделям, дальше по месяцам). Дни — по местному времени (`tz`). Цвет проекта — слот `LaunchChart` (`projectSlot`/`seriesStyle`), на графике первые шесть выбранных и «прочие». На странице проекта — полоса `web/src/pages/StatsStrip.tsx`: три цифры за 30 дней, маленький график и «Подробнее →» на `/stats?projects=<ключ>`. Недельный лимит (BTN-51) — только за дни со снимками лимитов: `history` и `period` отдают `limits` — первый и последний местный день снимков окна 7d (`limit_snapshots` начинаются 2026-10-03, раньше истории нет); плитка и полоса пишут «с <дня>», до 7 покрытых дней — сумма долей, больше — среднее за неделю по покрытым дням, снимков нет — «нет данных», а не 0 (`weeklyLimit` в `web/src/stats/format.ts`). Период длиннее 7 дней — под плиткой пики недельных окон, попавших в период (`period.windows` из view `limit_windows`, по аккаунту, незакрытое — «идёт»). База Tally (BTN-70) — по умолчанию встроенная, PGlite в `state/tally/pgdata`: ею владеет поток службы и отдаёт её обычному `pg` на свободном порту `127.0.0.1` (`owner.json` рядом), а сборщик служба запускает сама раз в 5 минут (`src/stats/tally.ts`, подробности — `tally/CLAUDE.md`); ни сервера, ни планировщика не нужно, на всех системах одинаково. Заданы `TALLY_DB_HOST`, `TALLY_DB_PORT`, `TALLY_DB_NAME`, `TALLY_READER_PASSWORD` (и `TALLY_WRITER_PASSWORD` для сборщика) — внешний Postgres, Even Keel читает его ролью `tally_reader`. Ответ кэшируется на 60 с, страница обновляет его раз в 5 минут. «Цепочка» — сессии из журнала запусков (`sessions.launch_reason`), не точка входа. Проекты Even Keel — под ключом: сессии по ключу задачи, без задачи — по папке проекта из `even-keel.config.json` (без буквы диска и регистра, с подпапками), строкой «Без задачи»; остальные — группой папки (`folderGroups`): папка уходит под самую внешнюю папку из данных, в которой лежит (не одноуровневую и не содержащую проект Even Keel), группа названа последним сегментом её пути; папки scratch десктопного приложения — одной строкой «App scratch». Задан `TALLY_DB_HOST` без `TALLY_DB_NAME` или пароля — страница и полоса пишут, что статистика выключена; база не отвечает или встроенная не открылась — ошибку, остальной Even Keel работает. Аудит сессий (и недельный) — глобальный навык `session-audit`, запросы — `tally/bin/sql.mjs` только на чтение, views `audit_*` (`tally/CLAUDE.md`).
- Правки правил на `/stats` (BTN-50; сбор версий — «Версии правил» в `tally/CLAUDE.md`): на графике расхода — метки правок (`SpendChart`, `web/src/stats/marks.ts`), под ним — `RulesSection.tsx`: фильтры «Файлы» (виды) и «Цель», метки периода, наборы правок выбранной метки (сессия, задача, цель и причина из журнала, точность «±час»/«±день», расхождение с транскриптом), дифф файла и «До и после» (`RuleCompare.tsx`). Метка — правки сессии (`s:<сессия>`), неприписанные смены с промежутками до 30 мин (`m:…`) или набор журнала без своей сессии (`i:<id>`). Правки памяти меток не дают (`filterSets`): сессии пишут её постоянно, точек было столько, что сравнивать было не на чем; Tally их собирает, фильтра «память» нет. Соседние метки, между которыми началось меньше `minSessions` сессий, сливаются. Клик — метка, Shift/Ctrl-клик — вторая: сравнивается [начало первой − N дней, начало) против [конец второй, + N дней). Метрики стороны: медиана стоимости задачи, сессий на задачу, средний контекст запроса, доля запросов > 150k, $ за запрос, доля застреваний, ошибок и отказов, медиана контекста на входе и доли моделей по запросам основного потока — если смесь моделей сторон разошлась больше чем на 20 % (половина суммы разностей долей), над таблицей предупреждение: у моделей своя цена токена, долларовые строки меняются и без правки (Opus 5 → 5.5 около 23.09 сам срезал $ за запрос вдвое); ответы классификатора Tally (`entrypoint` `tally-classify`, каждый — «сессия» из одного ответа на ~1k) ни в стороны, ни в счёт сессий для слияния меток не входят (BTN-52); выборка в каждой строке; меньше `minTasks` задач или `minSessions` сессий с любой стороны — «мало данных», без цифр. Маршруты: `GET /api/stats/rules?scope=&account=&tz=&projects=&kinds=&purposes=` (метки), `GET /api/stats/rules/diff?changes=<id>,…` (дифф по сменам), `GET /api/stats/rules/compare?before=&after=&days=&projects=&scope=&account=&tz=`. Настройки — `stats.compare` в `even-keel.config.json` (`minTasks` 5, `minSessions` 10, `days` 7), применяются на лету. URL: `kinds=`, `purposes=`; выбранные метки в URL не пишутся.
- Лимиты — у каждого аккаунта свои: `claude -p /usage --output-format json --no-session-persistence` в его папке раз в 5 минут (локальная команда, квоту не тратит) и снимок statusline (он помечен `configDir` сессии, без пометки — глобальный аккаунт); берётся более свежий. Чаще не опрашивать: сервер отвечает на `/api/oauth/usage` 429, его же опрашивает панель расширения VS Code тем же токеном, а CLI (2.1.286) после 429 не спрашивает этот токен ~45 мин. С истёкшим access-токеном или после 429 `/usage` лимитов не отдаёт (строка подписки есть, строк окон нет) — это «нет данных» (`stale`), не ошибка. Ответ `/usage` принимается целиком или никак: обе строки окон с процентом и сбросом (`0% used` без сброса — окно не начато). Опрос продолжается, только если ответ прямо говорит `num_turns: 0` и `total_cost_usd: 0`, иначе выключается до перезапуска. Нечитаемый ответ или выключенный опрос страница показывает баннером (`UsageBanner`). Пока окно выбрано, следующая задача не запускается: цепочка ждёт сброса (`limitUntil`) и продолжает сама.
- Аккаунты Claude — по папке конфигурации на аккаунт (`CLAUDE_CONFIG_DIR`): глобальный `~/.claude` (ключ `global`) и `~/.claude-accounts/<имя>` (`EVEN_KEEL_ACCOUNTS_DIR`). Токены хранит и обновляет сам CLI; Even Keel из `.credentials.json` читает только сроки (`expiresAt`, `refreshTokenExpiresAt`), токены не читает и не копирует. `claude auth status --json` по каждой папке раз в минуту. «Добавить аккаунт» — `claude auth login --claudeai` во временной `.pending-*`, после входа папка получает имя по e-mail; «Продлить вход» — вход в папке аккаунта; «Удалить» — `claude auth logout` и папка прочь (не активный, не глобальный); есть живые сессии — папка помечается (`removing` в `state/account.json`), на неё нельзя переключиться, и удаляется на первой проверке после них (меню называет, какие держат), «Не удалять» снимает пометку. Живая сессия папки — с живым процессом (запись `sessions/<pid>.json`), а не по `state` из `claude agents`: `blocked`/`working` там остаются и за сессией, процесс и демон которой давно умерли, такие записи ни удалению папки, ни остановке её демона не мешают (`liveSessions`). Папки `*.lock` — замки, которые CLI ставит рядом с папкой аккаунта на время обновления токена, это не аккаунты. Почта аккаунта в `auth status` — сохранённый профиль из `.claude.json`, а не владелец токена: десктопное приложение Claude запускает CLI в `~/.claude` со своим аккаунтом и переписывает профиль, поэтому в `~/.claude` держать тот же аккаунт, что в приложении. Ссылку и поле для кода страница показывает в меню аккаунта. Переключить активный аккаунт (и продлить вход активного) можно, когда цепочка на паузе или остановлена и ни одна сессия активного аккаунта не посреди хода — `busy` или `waiting`; что мешает, меню показывает списком. Пока идёт вход в активный аккаунт, он не вошёл или его вход истёк, новые сессии не запускаются (цепочка встаёт на паузу с причиной). `state/account.json` — активный аккаунт и по каждой папке: её аккаунт, с какого момента он действует и какой был до него. Лимиты папки, полученные раньше смены аккаунта в ней, не показываются; аккаунт упора в лимит — папка сессии и её e-mail на момент упора, `--resume` — только если активна та же папка с тем же e-mail.
- Аккаунты — боковая панель справа (`AccountMenu`): папки аккаунтов, аккаунт Even Keel («Отдать Even Keel» — активный аккаунт цепочки) и аккаунты приложений (`src/account/apps.ts`, `src/account/vscode.ts`). Пока приложение одно — VS Code: его аккаунт — `CLAUDE_CONFIG_DIR` в `claudeCode.environmentVariables` пользовательского `settings.json` (`%APPDATA%\Code\User` на Windows, `~/Library/Application Support/Code/User` на macOS, `$XDG_CONFIG_HOME/Code/User` или `~/.config/Code/User` на Linux), `global` — без переменной. Файл переписывается, только если он чистый JSON (с комментариями — ошибка в панели, правка руками), остальные ключи, отступ и конец строки сохраняются. Переключить нельзя, пока открыт хоть один чат Claude в VS Code — живая запись `sessions/<pid>.json` с `entrypoint: "claude-vscode"` в любой папке аккаунта (опрос раз в 5 с и заново перед записью); цепочка и сессии Even Keel не мешают. Перед записью папке переносится общая конфигурация (`DaemonRefresh.prepare`). Аккаунт, на котором сидит приложение, не удаляется. Новый аккаунт VS Code берёт после Developer: Reload Window. Десктопное приложение Claude сюда не входит: оно передаёт CLI свой вход, папкой конфигурации его не переключить.
- Перед каждым запуском в папке аккаунта в неё переносится общая конфигурация (`src/account/share.ts`): `settings.json` (глобальный поверх своего), `CLAUDE.md`, реестр плагинов, junction (вне Windows — символьная ссылка) на `agents`, `hooks`, навыки и память проектов, а из `~/.claude.json` — доверие и настройки проекта (MCP local scope, `allowedTools`) для уже доверенных проектов (CLI заводит на одну папку несколько ключей: VS Code пишет диск строчной буквой — `d:/…`, CLI — `D:/…` и `D:\…`; доверенной папка считается, если доверено любое написание, и переносятся все её ключи; регистр путей не различается только на Windows и macOS, как и везде, где Even Keel сравнивает пути, — `src/paths.ts`), и отметка о пройденном первом запуске (`hasCompletedOnboarding`, `lastOnboardingVersion`), если в папке её нет: без неё интерактивный `claude` с `CLAUDE_CONFIG_DIR` папки показывает мастер со входом, хотя токен на месте. Временный демон папки (`claude --bg` поднимает его сам) кэширует конфигурацию: перенос доходит до сессий, запущенных после его перезапуска. Поэтому, если перенос что-то поменял, а живых сессий в папке нет (свежий `claude agents` и записи `sessions/<pid>.json`), Even Keel перед запуском останавливает её демон — `claude daemon stop --any` с `CLAUDE_CONFIG_DIR` папки, глобальный демон он не трогает (`src/account/daemon.ts`). Есть живые — демон не трогается, меню аккаунта пишет, что конфигурация дойдёт после них, а остановка переносится на первый запуск без них. Отметка живёт в памяти службы.

## Задачи

Работа по этому репозиторию ведётся через трекер Huly, проект `BTN`.
Правила, статусы и порядок действий — скил `huly-tracker`, читать его перед созданием задачи или началом работы по ней.

- Код пишется под активную задачу, в её worktree. Прямая просьба без задачи — коммит в `main` основного чекаута (глобальный CLAUDE.md).
- Ветка: `btn-<номер>/short-description`. Коммит: `[BTN-<номер>] Message`.
- Содержимое задач (заголовки, описания, комментарии) — на русском.
- Сессия доводит задачу до `main` сама: после одобрения ревьюера сливает ветку (`git merge --no-edit` в основной рабочей копии) — это закрывает задачу. Пользователю — отчёт о сделанном, а не команда слияния. Worktree, ветку и пуш `main` после слияния сессия из цепочки не трогает — это делает Even Keel (ниже). Сессия, запущенная вручную, убирает за собой сама по навыку.

## Worktree задач

Even Keel готовит worktree сам (`src/git/worktree.ts`), сессии его не создают.

- Перед первым запуском по задаче — в основном чекауте проекта (`config.projects[project]`) `git worktree add -b <ключ>-<номер>/task .claude/worktrees/<ключ>-<номер> main`, всё в нижнем регистре. Хвост ветки всегда `task`: хукам в `~/.githooks` нужен вид `<ключ>-<номер>/<что-то>`. Worktree по этому пути уже есть — берётся как есть, с его веткой; есть только ветка — возвращается в новый worktree. `.claude/worktrees/` дописывается в `.git/info/exclude`, если git её не игнорирует. Сессия стартует с `cwd` = worktree, промт — ID задачи, строка про готовый worktree и что убирать за собой не надо (`startPrompt`).
- Текущая задача ушла в Done (категория `Won`; отменённая или выпавшая — нет) — `closing` цепочки: ждать, пока её сессия не посреди хода, затем `claude stop` её сессий в этом worktree (иначе живой процесс держит папку: `--bg`-сессия после хода не выходит, `claude agents` показывает её `done`/`idle`), затем `git worktree remove` (без `--force`), `git branch -d` ветки задачи (только `<ключ>-<номер>/…`), `git push origin --delete`, если она есть на origin, и `git sync`, если у проекта есть remote. Следующая задача запускается после этого. `git sync` здесь и ниже — синхронизация `main` (`src/git/sync.ts`): есть алиас `alias.sync` у репозитория или пользователя — он; нет — Even Keel сам: основной чекаут должен стоять на `main`, по каждому remote `git fetch` и `git merge --no-edit <remote>/main` (не сливается чисто — `merge --abort` и ошибка), затем `git push <remote> main` в каждый.
- Режим «слот» (`"slot": true` или число слотов у проекта в `even-keel.config.json`, `src/git/slot.ts`) — пул постоянных worktree на репозиторий вместо нового на каждую задачу: `.claude/worktrees/even-keel`, дальше `even-keel-2`, `even-keel-3`… (`true` — один). Игнорируемые кэши (`Library` Unity, `node_modules`) переживают задачу, и первый запуск новой обрабатывает только разницу; лишний слот нужен, чтобы живая сессия отпущенной задачи (пропущенной, отложенной блокером) осталась в своём, а не была остановлена. Цепочка по-прежнему ведёт одну задачу за раз. Подготовка: слот уже на ветке задачи (`<ключ>-<номер>/…`) — он, как есть, даже грязный. Иначе по каждому слоту: грязный (`git status --porcelain` не пуст) или с сессией другой задачи посреди хода (`busy`/`waiting`, по журналу запусков, `src/sessions/occupants.ts`) — не годится; из годных берётся, по порядку предпочтения: отцепленный от ветки без чужих живых сессий, на чужой ветке без них, ещё не созданный (`git worktree add --detach <слот> main`), с простаивающими сессиями других задач — им `claude stop` (пятое исключение инварианта 1); при равенстве — с меньшим номером. Ни один не годится — ошибка запуска, цепочка на паузе с путями и причинами, слоты не трогаются. Затем `git clean -fd` (без `-x`) и `git switch <ветка>` или `git switch -c <ветка> main`. После Done слот на ветке задачи — `git switch --detach main` (грязный — остаётся на ветке, ветка не удаляется, предупреждение), затем ветка, origin и `git sync`, как без слота; папка слота не удаляется. Слоты на чужих ветках (уборка отпущенной задачи) не трогаются, удаляется только ветка. Число слотов меняется после перезапуска; при уменьшении лишние папки Even Keel больше не берёт и не убирает. Свой worktree задачи, оставшийся с прежнего режима, берётся и убирается по-старому. `claude stop` после Done в слоте — только сессиям этой задачи по журналу запусков.
- Задача, которую цепочка запустила и отпустила не через Done, — выпала (стала родителем: задачи с подзадачами в цепочку не входят; ушла в неактивный статус), отложена блокером, пропущена, цепочку остановили или она встала с ошибкой, — запоминается в `released` в `state/chain.json`. Их статусы Even Keel спрашивает у Huly вместе с задачами цепочки (раз в 30 с); ушла в `Won` и её сессия не посреди хода — та же уборка, что у текущей, но цепочка из-за неё не ждёт и на паузу не встаёт: упавший `git sync` — предупреждение в `leftovers`. Ушла в терминальный статус другой категории, пропала из Huly или цепочка снова её взяла — забывается.
- Грязный worktree, папка, занятая процессом, неслитая ветка — предупреждение в лог и на страницу проекта (`leftovers` в `state/chain.json`, кнопка «Убрал» — `chain/dismiss`), цепочка идёт дальше. Упал `git sync` — цепочка на паузе с его выводом, силой ничего не пушится; после «Снять с паузы» уборка не повторяется.

Исключение из скила: прямая работа с API Huly здесь разрешена — это суть проекта.

## Инварианты

1. **Остановившуюся сессию диспетчер не трогает.** Вопрос, ошибка — ничего не происходит. Пользователь отвечает с телефона через Remote Control или сам двигает задачу в Huly. Исключение — лимит у сессии текущей задачи незапаузенной цепочки: после сброса лимита или смены аккаунта диспетчер продолжает её через `--resume`, если кэш ещё тёплый (тот же аккаунт, < 55 мин с последнего ответа), иначе останавливает её (`claude stop`, не `rm`) и запускает новую в её рабочей папке с передачей дел (`src/chain/relay.ts`). Лимит — это и ошибка `rate_limit`, и мягкое предупреждение CLI (`usageLimitNote: "wrap_up"`), после которого сессия сама сворачивает ход. Рабочую папку и ветку для передачи даёт git (корень worktree от последнего `cwd`), не транскрипт: его `gitBranch` — ветка папки запуска.
   Второе исключение — кнопка «Новая сессия» (`restart`): пользователь заменяет сессию текущей задачи, если она не посреди хода, — та же передача дел, в журнале `restart` со ссылкой на прежнюю сессию.
   Третье исключение — контрольная точка, которую сессия поставила сама: сессия текущей задачи незапаузенной цепочки закончила ход, и последняя строка её последнего ответа — `CHECKPOINT: <путь>` (так просит глобальный хук `~/.claude/hooks/context-checkpoint.mjs`, когда контекст разросся). Диспетчер делает ту же передачу дел, в промте — путь к записке от корня worktree, в журнале `checkpoint` со ссылкой на прежнюю сессию. Метка после неё — вызов инструмента, новый ответ без метки или сообщение в сессию — гасит её. Передача повторяется, сколько сессии её просят; число передач по задаче видно на странице. Сессия с лимитом идёт по правилу лимита (её промт тоже указывает на записку), а пока лимит выбран или новые сессии не запускаются, метка ждёт.
   Четвёртое исключение — задача в Done: когда её сессия закончила ход и не ждёт ответа (не `busy`/`waiting`), диспетчер останавливает её (`claude stop`, не `rm`; транскрипт остаётся, `--resume` вручную возможен) и убирает worktree. После слияния сессии делают не больше пары проверок в том же ходе и кончают отчётом (замер по транскриптам, 2026-09-29).
   Пятое исключение — слот переключают на ветку другой задачи (режим «слот», выше; только когда свободного слота в пуле нет): живые сессии отпущенных задач (пропущенных, отложенных блокером) в слоте диспетчер перед этим останавливает (`claude stop`, не `rm`), иначе ответ такой сессии через Remote Control лёг бы в ветку чужой задачи. Если такая сессия посреди хода (`busy`/`waiting`), слот не переключается, цепочка на паузе с её задачей.
   «Не трогает» — не останавливает её и ничего ей не пишет. Перестать её ждать диспетчер может, если сессия не посреди хода (`busy`/`waiting`): текущая задача получила в Huly открытый блокер из той же цепочки (сессия отложила её сама, в журнале `postpone`) или пользователь нажал «Пропустить» (`skip`). Пропущенную задачу цепочка не берёт, пока пользователь её не вернёт или она не закроется в Huly.
2. **Huly — источник правды о статусах.** Своё у диспетчера только порядок цепочки, пауза, список пропущенных задач, отпущенные задачи, ждущие уборки, и предупреждения уборки.
3. **Секретов в репозитории нет.** Адреса и учётки — из окружения или локального файла вне git; в репозитории только `.env.example` с фейками.
4. **Пароль Windows диспетчер не принимает и не хранит.** Учётку службы пользователь вводит сам.

## Служба

Без службы, на любой системе: `npm install`, `npm run build`, `npm start` в корне репозитория.

Сборщик статистики Tally работает внутри службы (раз в 5 минут, своим потоком), отдельной задачи планировщика или cron не нужно. Встроенную базу держит процесс службы: пока он жив, ручной `npm run tally` с ней отказывается, а `tally/bin/sql.mjs` читает её через порт службы. Жёсткое убийство процесса (так останавливает служба Windows) база переживает.

### Linux и macOS

- `service/install.sh` от своего пользователя (не через `sudo`): `npm install`, `npm run build`, затем на Linux — юнит `~/.config/systemd/user/even-keel.service` (`systemctl --user`, лог — `journalctl --user -u even-keel`), на macOS — агент `~/Library/LaunchAgents/local.even-keel.plist` (`launchctl`, лог — `logs/even-keel.log`, без ротации). Повторный запуск — пересборка и перезапуск. `service/uninstall.sh` убирает.
- `PATH` и путь к `node` берутся из оболочки установщика: сменился `node` (nvm и т. п.) — снова `install.sh`.
- Остановка службы фоновые сессии не убивает: `KillMode=process` у юнита, `AbandonProcessGroup` у агента. Юнит `--user` живёт, пока пользователь в системе; чтобы и без входа — `loginctl enable-linger <пользователь>` (установщик напомнит). Агент macOS работает только при входе в систему.
- Linux проверен вживую в WSL (Ubuntu 26.04, 2026-10-04): тесты и проверка типов, `install.sh` и `uninstall.sh`, вход в `claude` со страницы, лимиты `/usage`, запуск сессии в worktree задачи, после Done — остановка сессии, уборка worktree и ветки, своя синхронизация `main` с пушем в origin. Новый репозиторий CLI должен знать как доверенный: иначе запуск встаёт на паузу с просьбой один раз открыть `claude` в нём. macOS не проверялась.

### Windows

- Хост службы — `service/EvenKeelService.cs`, собирается штатным `csc.exe` из .NET Framework при установке, сторонних обёрток нет. Держит `node --import tsx src/main.ts` в корне репозитория, перезапускает при падении, пишет вывод в `logs/even-keel.log`. Для отладки без службы: `EvenKeelService.exe <корень> <node.exe> --console`.
- `service/install.ps1` и `service/uninstall.ps1` — из PowerShell 7 от администратора. Пароль учётки скрипт не спрашивает: пользователь вводит его на вкладке «Вход в систему» в services.msc, она же выдаёт право «Вход в качестве службы».
- Служба читает `.env` и `even-keel.config.json` из корня репозитория; порт не должен быть занят ручным запуском.
- Служба отдаёт собранный `dist/web`: `install.ps1` запускает `npm run build`. После обновления кода — снова `install.ps1` (или `npm run build` и перезапуск службы), иначе страница старая или 503.
- `claude --bg` ходит через демон-супервизор (`claude daemon run`, канал `\\.\pipe\cc-daemon-…`). Остановка службы фоновые сессии не убивает — они дети демона.

## Тесты

TDD для логики: порядок цепочки, переходы по статусам, разбор транскриптов и ответов Huly. Работа с процессами, сетью и вёрстка тестами не покрываются — проверяются вживую, скриншоты Playwright в `.temp/`.
