# Tally

Сборщик статистики сессий Claude Code (BTN-44): дочитывает транскрипты всех сессий со всех аккаунтов и складывает их в Postgres на `my-server` (`tally/deploy`, BTN-45). Батон и сводки потом только читают базу ролью `tally_reader`.

Правила корневого `CLAUDE.md` действуют. Ниже — только своё.

## Запуск

- Один прогон — `npm run tally` (или `node --import tsx tally/src/main.ts`) из корня репозитория: дочитать новое, записать снимок лимитов, пересчитать признаки изменившихся сессий, спросить у Huly устаревшие задачи, классифицировать до `classify.perRun` отрезков, выйти. Код выхода 1 — хоть один файл не загрузился (ошибки в выводе), остальное записано.
- Руками из сессии Claude Code — только без `CLAUDE_CONFIG_DIR` (`env -u CLAUDE_CONFIG_DIR …`): с ним сборщик видит одну папку аккаунта, а отметки чтения файлов остальных удаляет как пропавших, и следующий прогон перечитывает их с начала (данные не дублируются, но это ~1 ГБ и пара минут; случилось 2026-10-03).
- Доступ — из корневого `.env`: `TALLY_DB_HOST`, `TALLY_DB_PORT`, `TALLY_DB_NAME`, `TALLY_WRITER_PASSWORD` (роль `tally_writer`, `TALLY_WRITER_USER` — чтобы сменить имя). Конфиг без секретов — `tally/tally.config.json` (`TALLY_CONFIG` — другой путь).
- Журнал запусков Батона — `state/launches.jsonl` (`BATON_STATE_DIR`), папки аккаунтов — `AccountHomes` Батона (`CLAUDE_CONFIG_DIR`, `BATON_ACCOUNTS_DIR`). Из worktree: `BATON_STATE_DIR=<основной чекаут>/state BATON_CONFIG=<основной чекаут>/baton.config.json node --env-file=<основной чекаут>/.env --import tsx tally/src/main.ts`. Без `BATON_CONFIG` сборщик не находит проектов (в worktree `baton.config.json` нет) и пишет их файлы правил удалёнными, а следующий прогон — снова созданными: ложная пара смен в `rule_changes` (случилось 2026-10-03).
- Планировщик: `tally/scheduler/install.ps1` из PowerShell 7 от администратора — задача «Tally collector» раз в 5 мин (`-Minutes`), от текущего пользователя с входом S4U: идёт и без входа в систему, без окна, пароль не хранится (инвариант 4). Вывод — `logs/tally.log`. Второй экземпляр, пока идёт первый, не стартует (и планировщик, и `pg_try_advisory_lock` в базе). `uninstall.ps1` снимает задачу, база остаётся.
- `claude -p /usage` сборщик не запускает никогда: лимиты он берёт у Батона (см. ниже), лишний опрос даёт 429 на общем токене.

## Что читается

- Все `*.jsonl` в `<папка аккаунта>/projects/<проект>/` и транскрипты субагентов `<проект>/<сессия>/subagents/agent-*.jsonl` (их `sessionId` — родительская сессия, `agentId` — свой; стоимость субагентов входит в задачу). Прочее в папках сессий (`tool-results/`, `memory/`) не читается.
- Дозагрузка (`src/load.ts`): по файлу в `files` — докуда прочитано (`read_to`, байт после последнего `\n`), размер, `mtime`, `ino` и SHA-1 первых ≤1 КБ. Файл не менялся — не открывается. Вырос — читается хвост кусками по 8 МБ (строка длиннее куска — кусок растёт), каждый кусок — одна транзакция вместе с новым `read_to`, так что упавший прогон продолжается с того же места. Недописанная последняя строка ждёт следующего прогона. Файл стал меньше `read_to`, сменил `ino` или начало — читается заново с нуля; переименованный — новый путь, читается целиком. Дублей нет: ключи — `uuid` строки, `message.id` ответа, `tool_use_id`. Пропавшие пути из `files` удаляются.

## Схема (`src/schema.sql`, создаётся на каждом прогоне, `if not exists` / `create or replace view`)

- `lines` — строки с `uuid`: сессия, агент, тип, время и сжатая сырая строка `raw jsonb`. Служебные строки без `uuid` (`ai-title`, `custom-title`, `queue-operation`, `file-history-*` …) не хранятся, из них берутся только заголовки сессий.
- `messages` — один ответ API (`message.id`): CLI пишет ответ несколькими строками `assistant` по блоку на строку с повтором `usage`, итоговый `output_tokens` — в последней; при слиянии по каждому виду токенов берётся больший, время — меньшее. Колонки: сессия, агент, аккаунт (папка аккаунта файла), проект и его папка (`cwd` без хвоста `.claude/worktrees/…`), задача, ветка, `entrypoint`, модель, `speed`, токены `input`, `cache_write_5m`, `cache_write_1h`, `cache_read`, `output`. Запись кэша без разбивки `cache_creation` считается 5-минутной. Ответы `<synthetic>` и `isApiErrorMessage` — не ответы API, в `messages` не идут.
- `tool_calls` — вызов (`tool_use`: имя, SHA-1 входа для поиска повторов, краткое описание как в ленте Батона) и его результат (`tool_result`: время, `is_error`, вид ошибки, первые 500 знаков текста). Вид: `denied` — отказ в разрешении (пользователь или классификатор авто-режима), `hook` — `PreToolUse:…`/`PostToolUse:… hook error`, `error` — остальное. Вызов и результат пишут разные колонки одной строки, порядок загрузки не важен.
- `sessions` — аккаунт, проект, заголовки `custom_title` (поставил пользователь) и `ai_title`, задача и причина из журнала запусков Батона, первая и последняя строка.
- `limit_snapshots` — снимки окон `5h`/`7d` по аккаунту: процент, сброс, источник, время снимка.
- `model_prices` — цены из `tally.config.json`, переписываются на каждом прогоне.
- `files` — состояние дозагрузки.
- `signs`, `spans`, `sign_sessions` — признаки, отрезки и с какими правилами и до какой строки посчитана сессия; `span_reasons` — причина отрезка от классификатора; `tasks` — задачи из Huly (ниже).
- `turns`, `turn_sessions` — ходы основной сессии и с каким ключом и до какой строки посчитана сессия (раздел «Время задачи»).
- Views: `session_tasks` — задача сессии (`launch_task`, иначе задача первого ответа с задачей); `stuck_spans` — отрезки с задачей и причиной; `task_repeats` — по задаче: сессии, передачи дел по видам (`relay`, `checkpoint`, `restart`), отрезки, заголовок, статус, ярлыки, `rework` (есть ярлык `Переделка`), связанные задачи; для навыка аудита (ниже) — `audit_sessions` (сессия: папка, задача, причина запуска, активные минуты, контекст запросов и пик, доля > 150k, стоимость, застревания и ошибки вызовов), `audit_tasks` (те же суммы по задаче, задача — в периоде своего первого ответа) и `audit_rules` (смены правил с местом и `undone` — ложная пара смен за сутки); время задач — `session_times` (по сессии: ходы, активное время, ожидание), `task_times` (по задаче: сессии, ходы, активное, ожидание, общее) и `task_estimates` (`audit_tasks` + время, оценка, `fact_ratio` — факт / оценка, приоритет, компонент, `done`, записанный отчёт, `model_family` — чаще всего встречающееся семейство модели). Колонки `audit_*` не меняются: сборщик основного чекаута на прежнем `schema.sql` заменяет их через `create or replace view`, а новая колонка в середине этого не даёт — новое идёт отдельным view.

Задача ответа: запуск сессии в журнале Батона (`state/launches.jsonl`, кроме `postpone`/`skip`) → ветка `<ключ>-<номер>/…` → папка `.claude/worktrees/<ключ>-<номер>`. Журнал применяется и задним числом (`sessions.launch_task`, view берёт его первым).

## Сжатие сырых строк

Замер 2026-10-03: 753 файла, 280 тыс. строк, 1166 МБ. Из них `toolUseResult` — 321 МБ (копия блока `tool_result`), блоки `tool_result` — 274 МБ, вложения — 196 МБ, подписи thinking — 70 МБ (текст thinking пустой), картинки — 40 МБ. Выбрано (`src/compact.ts`):

- `toolUseResult`, `wireToolInputs` и `rendered` верхнего уровня выбрасываются — это копии того, что уже есть в `message`;
- `signature` и `data` картинки (`source.type = base64`) заменяются длиной;
- любая строка длиннее 2000 знаков — первые 2000 и `…[+N]`;
- `\u0000` и одиночные суррогаты убираются — их не принимает `jsonb`.

После первой загрузки (754 файла, 281 тыс. строк, 56 с; повторный запуск дочитывает только хвосты, доли секунды) база — 405 МБ: `lines` — 354 МБ, `tool_calls` — 28 МБ, `messages` — 15 МБ. Та загрузка выбрасывала только `toolUseResult`; `wireToolInputs` и `rendered` в ней занимают 40 МБ, без них база около 365 МБ. Внутри `lines.raw` больше всего весят вложения (88 МБ, из них `prompt_snapshot` — 52 МБ) и `message.usage` (48 МБ, оставлен: из него пересчитываются токены, если разбор поменяется).

## Стоимость

`message_costs` — `messages` × цена модели по самому длинному совпавшему префиксу (`claude-opus-5-5` раньше `claude-opus-5`), за миллион токенов: вход, выход, чтение кэша, запись кэша на 5 мин и на 1 ч по своим ценам. Цены — в view, а не в строках: правка `tally.config.json` пересчитывает и историю. Модель без цены — `cost` пустой, прогон пишет её в лог. Цены — API Anthropic на 2026-09-25 (запись 5 мин = 1,25× входа, 1 ч = 2×). Быстрый режим (`speed = fast`, у Opus дороже) в данных не встречался: `speed` хранится, цена его не учитывает.

`task_costs` — по задаче: ответы, сессии, токены, стоимость, доли лимитов.

Сверка 2026-10-03: независимый подсчёт по транскриптам (по `message.id` — максимум токенов, 5 мин / 1 ч из `usage.cache_creation`, цены из `tally.config.json`) совпал с `task_costs.cost` до последнего знака у BTN-45 (одна сессия, $2.52) и BTN-37 (сессия и субагент, две модели, $1.20).

## Доля лимита

Лимиты — из Батона: `GET <batonUrl>/api/state` (`BATON_URL` поверх конфига), `account.accounts[].limits` — там и statusline, и опрос `/usage`, по каждому аккаунту. Батон не отвечает — `state/rate-limits.json` (только statusline, аккаунт по `configDir`). Снимок с тем же временем не дублируется.

`limit_steps`: снимки с номером окна (`wnd`, новое — когда сброс сместился больше чем на 30 мин от прошлого снимка: источники округляют сброс по-разному) и максимумом процента в окне до снимка (`prev_max`). `limit_intervals`: соседние снимки окна одного аккаунта дают интервал и прирост — `max(0, текущий − prev_max)`, а не от прошлого снимка: `statusline` и `/usage` округляют процент по-разному и чередуются в одном ряду (21 → 22 → 21 → 22), прирост от прошлого снимка считал бы каждый зигзаг заново (BTN-51). Окно сменилось — прирост равен текущему проценту, а интервал начинается не раньше начала нового окна (`сброс − 5 ч` / `− 7 дней`). Первый снимок окна интервала не даёт. `limit_windows`: окно по аккаунту — сброс, начало, пик (наибольший процент), первый и последний снимок; его берёт плитка «Недельный лимит» (пики окон). Снимки есть с 2026-10-03 15:45: раньше Батон хранил только последнее значение, а процентов лимита в транскриптах нет — долю до этого не восстановить. `limit_shares`: прирост интервала делится между ответами этого аккаунта в интервале пропорционально их стоимости по ценам API. Это оценка: процент целый, снимки раз в несколько минут, к аккаунту `global` десктопное приложение примешивает свой вход.

## Признаки (`src/signs.ts`)

Где сессия топталась на месте — без LLM, по строкам из `lines`. Поток — основная сессия и каждый субагент отдельно (`src/stream.ts`). Виды:

- `failures` — `failureRun` (3) упавших вызовов подряд; `denied` — `deniedRun` (1) отказов в разрешении подряд;
- `repeat` — одна команда (`Bash` и др. — по тексту команды без лишних пробелов) `repeatRun` (2) раз без правки между ними (`Edit`, `Write`, `MultiEdit`, `NotebookEdit` сбрасывают счёт);
- `reread` — один файл прочитан `Read` `rereadCount` (5) раз за поток (путь без регистра и с `/`);
- `no_commit` — `noCommitReplies` (150) ответов основной сессии подряд без успешного `git commit`;
- `rewind` — у одного родителя несколько промтов пользователя (`/rewind` или правка сообщения);
- `compact` — сжатие контекста, `handoff` — сессия запущена передачей дел (`relay`/`checkpoint`/`restart` из журнала Батона). Эти две — метки: сами отрезка не дают, только дописываются в отрезок, куда попали.

Признаки одного потока, пересекающиеся по времени, сливаются в отрезок (`spans`, id — SHA-1 сессии, агента и крайних `uuid`). Сессия пересчитывается, когда у неё новая последняя строка или сменился ключ — SHA-1 версии признаков (`SIGNS_VERSION`), правил и причины запуска.

Правила — `signs` в `tally.config.json` поверх умолчаний, целые ≥ 1. Калибровка 2026-10-03 по всем сессиям: без коммита p95 — 102 ответа, порог 150; перечитанных ≥ 5 раз файлов — 18; серий из ≥ 3 упавших — 16; отказов — 40; повторов ≥ 2 — 15; `/rewind` в данных не было.

## Задачи из Huly (`src/huly.ts`)

Свой небольшой клиент (`HulyTask` Батона без связей, его модель не трогается): по идентификаторам задач из `session_tasks` — заголовок, статус, ярлыки (без дублей без учёта регистра) и связи `relations`, сделанные симметричными; связанные задачи вне выборки — вторым запросом по id. Задача спрашивается, если её нет в `tasks` или запись старше часа; не найденная в Huly пишется с пустым заголовком, чтобы не спрашивать каждый прогон. Huly недоступен — строка в лог, прогон идёт дальше. Шум api-client «no document found, failed to apply model transaction» на подключении отфильтрован.

Ещё поля (BTN-55): `priority` (`urgent`, `high`, `medium`, `low`, `no-priority`), `estimate_h` (оценка `estimation` в часах; 0 — нет оценки), `component` (название), `done` (статус категории `Won`). Записи, взятые до этих полей (`title` есть, `priority` пуст), спрашиваются заново, не дожидаясь часа.

Задачу Huly узнаёт только после первой её сессии: задача без сессий в `task_repeats` не попадает.

## Время задачи (BTN-55, `src/turns.ts`)

Активное время — по ходам транскрипта, а не по таймеру запуска: так оно есть у всех сессий (цепочка, ручные, VS Code) и задним числом. Ходы считаются по основной сессии и пересчитываются, как признаки, когда у сессии новая последняя строка или сменился ключ (`TURNS_VERSION` и есть ли запуск в журнале Батона).

- Ход — от строки, которая его начала, до последнего ответа перед следующей такой. Начало: промт (`launch` — первый промт сессии, запущенной Батоном; `resume` — промт продолжения после лимита; `prompt` — остальные), `notification` — уведомление о фоновой задаче и самоназначенное пробуждение (`scheduled_task_fire`), `message` — сообщение другой сессии или отчёт фонового субагента. Служебные строки (`<local-command-…>`, `<system-reminder>`, `[Request interrupted`) и сводка сжатия контекста хода не начинают. Ход упёрся в лимит (`limited`) — ошибка `rate_limit` или `usageLimitNote`. Ответы субагентов продлевают ход родителя, отдельно не прибавляются. Долгий инструмент внутри хода (сборка, тесты) — работа.
- `AskUserQuestion` и `ExitPlanMode` внутри хода — от вызова до результата ожидание, не работа (`ask_s`).
- Ожидание разрешения на инструмент в строках транскрипта не видно. Его видно только по `system/turn_duration` (`cli_s`, есть только у `entrypoint: cli`, т.е. у сессий Батона): CLI не считает в ход ни вопросы, ни запросы разрешений. Активное время хода — меньшее из хода по строкам (без `ask_s`) и `turn_duration`, разница уходит в ожидание. В VS Code и десктопе `turn_duration` нет — там ожидание разрешения остаётся в активном времени, и оно завышено ровно на него.
- Ожидание — вопросы и разрешения внутри ходов плюс промежуток от конца хода до следующего промта пользователя (`prompt`). Промежуток после хода, оборванного лимитом, в ожидание не идёт; паузы цепочки и промежутки передачи дел — тоже: следующую сессию начинает `launch`, продолжение после лимита — `resume`, а не промт.
- По задаче (`task_times`) — суммы её сессий (передачи дел, контрольные точки, «Новая сессия»), общее время — от начала первого хода до конца последнего (даты Done в Huly нет).
- Сверка 2026-10-04: суммы по сессиям против `turn_duration` — 140 из 176 cli-сессий в пределах 5%; остальные — двойной счёт CLI при отчётах фоновых субагентов (его ход начинается заново с исходного промта), поэтому `turn_duration` не берётся целиком, а только ограничивает ход. BTN-50: 9 сессий, каждая совпала с CLI до 0,1 мин, 64,7 мин активно из 66,3.

Отчёт о времени в Huly (`reportTimes` в `src/huly.ts`): `TimeSpendReport` на задачу через `addCollection`, `employee: null`, значение — активные часы, описание-метка «Tally: активное время агента по ходам транскриптов». Пишется только задачам в Done, чей первый ход не раньше `reportsSince` в `tally.config.json` (`null` — отчёты выключены; 2026-10-03 — с этого дня ставятся оценки), с активным временем от минуты и последним ходом старше 60 мин. Записанное — в `tasks.reported_h`/`reported_at`; отчёт с той же меткой уже есть в Huly — второй не пишется. Записанный отчёт не обновляется, если задачу потом продолжили.

## Классификатор (`src/classify.ts`, `src/steps.ts`)

Причина отрезка — от Gemini на бесплатном тарифе через LiteLLM на сервере (`/opt/stacks/litellm`): `POST <TALLY_LLM_URL>/chat/completions` с ключом `TALLY_LLM_KEY` (мастер-ключ LiteLLM), `temperature: 0`, `response_format: json_object`. Модель — `TALLY_LLM_MODEL`, по умолчанию `google-gemini-3.1-flash-lite`; при отказе LiteLLM сам идёт по её цепочке `router_settings.fallbacks` (`google-gemini-3.5-flash-lite`, `google-gemma-4-26b-a4b-it`), в `span_reasons.model` и расход пишется ответившая. Квота free tier — на модель, поэтому цепочка Tally не начинается с моделей DocSorter (`google-gemini-3.6-flash` и ниже). Нет URL или ключа — классификатор пропускается со строкой в лог. В промте — задача, признаки отрезка и выдержка: события отрезка и последний промт перед ним, длиннее 120 событий — первые 40, «… N events skipped …», последние 80. Ответ ждётся до 3 мин. Причины: `unclear_task`, `broken_tooling`, `debug_loop`, `waiting_user`, `limit_env`, `normal`, `other`, пояснение — по-русски.

Модель выбрана замером 2026-10-03: 29 отрезков, уже разобранных Haiku (`prompt_version` 1), заново через `3.1-flash-lite`: совпало 21, из 8 расхождений lite точнее в 3, Haiku в 2, остальные спорные; ответ 4–14 с. `gemini-3.7/3.8-flash` (20 запросов в день) там, где успели ответить, совпали с lite, но дневную квоту выбрали за десяток отрезков: ретраи LiteLLM на 429 тоже её тратят. `gemma-4-26b` часто отвечает 500.

## Версии правил (BTN-50)

Какие тексты правил (CLAUDE.md, навыки, память, хуки, настройки, агенты) действовали когда — чтобы на `/stats` сравнить расход до и после правки. Файл правил — `ruleFileOf` (`src/rules.ts`): `~/.claude` и папки аккаунтов сводятся на один ключ `~/.claude/…` (кроме `settings.json` и `.claude.json` — у аккаунта свои), worktree — на основной чекаут, папка проекта — без буквы диска и регистра (Gamma переехал с D: на C:). `~/.githooks/**` — хуки (без логов, `*.bak*`, `*.tmp`, `package*.json`), `.claude.json` хранится только `mcpServers` и `projects.*.{mcpServers, allowedTools}`, значения `env`/`headers` — `***`. Навыки `skills/synced/**` и `skills/.*/**` не правила; папка навыка `skills/<имя>` сама — не файл (`rm -r`/`cp -r` папки правкой не пишется, BTN-52). Текст — `canon` (CRLF → LF, без пробелов по краям), SKILL.md без frontmatter, хеш — SHA-1.

- Таблицы: `rule_texts` (текст по хешу), `rule_files` (ключ, вид, папка), `rule_seen` (что получила сессия: `instructions`, `nested_memory`, тело вызванного навыка, описание навыка из `skill_listing`), `rule_snapshots` + `rule_snapshot_files` (снимки диска), `rule_versions` (версии из `file-history`, бэкапов и git), `rule_edits` (правки `Edit`/`MultiEdit`/`Write`/`NotebookEdit` и запись в файл правил из `Bash`/`PowerShell` — `added` 0, `removed` пусто), `rule_changes` (смены текста: источник `snapshot`, `transcript`, `file-history`, `backup`, `git`, +/−), `rule_imports` (журнал правок, ниже), `tally_meta`.
- Снимок — каждый прогон (`snapshotRules`): `~/.claude`, папки аккаунтов, `~/.claude.json`, `~/.githooks`, по проектам `baton.config.json` — `git ls-files` правил и `.claude/settings.local.json`; хешируются только файлы со сменившимся размером или `mtime`. Первый прогон — исходное состояние, без событий; файл, впервые попавший в снимок со старым `mtime`, — тоже.
- История до снимков (`collectRuleHistory`): `file-history-snapshot` транскриптов (копии в `<папка аккаунта>/file-history/<сессия>/`), бэкапы `~/.claude/backups/` (`CLAUDE.md.*.bak`, `.claude.json.backup.<мс>`), `git log --first-parent main` правил каждого проекта (дочитывается от `rules_git:<репо>` в `tally_meta`).
- Правило времени: по ключу версии из транскриптов и истории идут по первому появлению, первая — исходная, каждая следующая — смена; учитываются только версии раньше первого снимка ключа. Так источники не дают ложных смен друг против друга.
- `RULES_VERSION` (`src/rule-steps.ts`) сменился — прогон перечитывает все транскрипты с нуля только ради правил (~10 с) и пересчитывает смены.
- Журнал правок — `ruleHistory` в `tally.config.json` (по умолчанию `<BATON_STATE_DIR>/rule-history.jsonl`, вне git): строка — набор `{ id, at, until?, atPrecision exact|hour|day, sessions, files [{ path, action, summary }], purpose, reason, task, source }`. Каждый прогон добавляет новые строки и удаляет пропавшие (ключ — SHA-1 строки), битая строка — в лог. Сервер приклеивает цель, причину и задачу к набору правок сессии из `sessions`, если время сходится с допуском (30 мин / 1 ч / 24 ч по точности), иначе набор журнала стоит сам, с пометкой о расхождении.
- С какого времени есть история: тексты CLAUDE.md и памяти в транскриптах — с 2026-09-04 (CLI 2.1.260, первая смена — 2026-09-06), описания и тела навыков — с 2026-08-03, хуки, настройки и `.claude.json` — с первого снимка (2026-10-03) и раньше только по бэкапам, `file-history` и git.

## Аудит сессий (BTN-53)

Аудит — глобальный навык `session-audit` (`~/.claude/skills/session-audit/SKILL.md`, вне git): из любого проекта сравнивает недавний период с прежним — расход, контекст, задачи, застревания, правки правил между ними — и ищет, что поменялось. Недельный аудит — частный случай: период — последние 7 суток, прежний — 7 суток перед ними.

- Запросы — `tally/bin/sql.mjs` из любой папки (`node <основной чекаут>/tally/bin/sql.mjs "<sql>"`, `-f файл` или stdin): `pg` и `.env` берёт из основного чекаута, роль `tally_reader` (`TALLY_READER_PASSWORD`, `TALLY_READER_USER` — чтобы сменить имя), транзакция только на чтение — `insert` и прочее база отклоняет. Сборщик на аудите не запускается.
- Готовые суммы — views `audit_*` (раздел «Схема»), запросы и вид отчёта — в навыке.
- Цены — оценка по API, не счёт подписки; задачи в `tasks` обновляются раз в час, статус может отставать.

## Тесты

Чистая логика — vitest рядом с кодом (`*.test.ts`): разбор строк, сжатие, задача по ветке и worktree, дозагрузка хвоста (на временном файле и хранилище в памяти), снимки лимитов, конфиг, признаки и отрезки на синтетических транскриптах, выдержка и разбор ответа классификатора, задачи Huly, ходы (`src/turns.test.ts`: начала хода, субагент внутри хода, вопросы, `turn_duration`, лимит). Views лимитов (`limit_steps`, `limit_intervals`, `limit_windows`) — `src/limit-views.test.ts` на живой базе ролью `tally_reader`, только чтение: тела view из `schema.sql` подставляются CTE поверх тестовых снимков, заслоняющих `limit_snapshots`; без `TALLY_DB_HOST`/`TALLY_READER_PASSWORD` пропускается (из worktree — `node --env-file=<основной чекаут>/.env node_modules/vitest/vitest.mjs run tally/src/limit-views.test.ts`). Остальной SQL (стоимость, `limit_shares`, `task_repeats`, `session_times`, `task_times`), отчёты о времени в Huly и запрос к LiteLLM проверяются живым прогоном.
