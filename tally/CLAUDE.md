# Tally

A collector of Claude Code session stats (BTN-44): it reads through the transcripts of all sessions from all accounts and stores them in Postgres. Even Keel and the summaries then only read the database.

The database (BTN-70) is by default the embedded one: PGlite (`@electric-sql/pglite`, Postgres in WASM) in Even Keel's `<state>/tally/pgdata` (`EVEN_KEEL_STATE_DIR`, otherwise `state/`), with the same SQL as on the server. With `TALLY_DB_HOST` and the other `TALLY_DB_*` set, it is an external Postgres (on your own server, `tally/deploy`, BTN-45) with the roles `tally_writer` and `tally_reader`; the roles and `GRANT` exist only there.

- PGlite has one session per process, so one process owns the folder (`src/local.ts`, `openLocalTally`): it opens the database (`timezone` is `UTC`, otherwise PGlite takes the host's zone), migrates the schema (below), starts a `PGLiteSocketServer` (`@electric-sql/pglite-socket`, the Postgres protocol) on `127.0.0.1` on a free port and writes `<state>/tally/owner.json` (`pid`, `port`). All clients — the collector, the `/stats` page, `sql.mjs` — go through this port with an ordinary `pg`: a direct `db.query` in the owner process would land inside someone else's open transaction, while the socket separates transactions (other connections wait for `commit`). The socket ignores connection options (`-c default_transaction_read_only`, `statement_timeout`).
- The owner is alive if the `pid` exists and the port is listening (after a crash the `pid` could have gone to another process). A second process opening the folder while the owner is alive gets the error "process N (the Even Keel service) holds the local database…". `pg_try_advisory_lock` in PGlite is reentrant (one session), so against a second collector on the embedded database there is `owner.json`, while the lock remains for an external Postgres.
- After the process is killed (which is how the Windows service stops node), the database opens again and PGlite replays the WAL. Measured on the full history (2026-10-04): 838 files, 318 thousand rows — the first collection 100 s (9 s of it the rules), the next 1.3 s; 1.1 GB on disk (database 479 MB, `pg_wal` 561 MB). Reading the page — `history` 1.0–1.3 s, `period` 1.6–1.7 s, `steps` 0.3 s, `rules` 0.1 s (server: 1.4; 1.05–1.1; 0.74; 0.1 s). `period` is slower because its eight queries go through one session in turn.

The rules of the root `CLAUDE.md` apply. Below is only what is specific to this directory.

## Running

- The collector is started by the Even Keel service (`src/stats/tally.ts`, `TallyService`): 15 s after startup, then every 5 min from the start of the previous run, and the next one does not start while the previous is going. A run is a separate thread (`src/collect-worker.ts`), so parsing transcripts does not hold the service's event loop; the output goes to the service log, and a run error does not touch the service or the chain. The embedded database is owned by one more service thread (`src/host-worker.ts`), and the page gets its port once the database has opened (if it did not — `/stats` shows an error). An external Postgres without `TALLY_DB_NAME` or `TALLY_WRITER_PASSWORD` — the service does not collect, one line in the log.
- One run by hand, for debugging — `npm run tally` (or `node --import tsx tally/src/main.ts`) from the repository root: read the new data, write a limits snapshot, recompute the signs, turns and steps of changed sessions, ask Huly for stale tasks, classify up to `classify.perRun` spans, exit. Exit code 1 means at least one file failed to load (errors in the output), the rest is written. With the embedded database — only when the service does not hold it (otherwise the error "holds the local database"): a manual run opens PGlite itself and closes it afterwards.
- By hand from a Claude Code session — only without `CLAUDE_CONFIG_DIR` (`env -u CLAUDE_CONFIG_DIR …`): with it the collector sees one account folder and deletes the read marks of the other folders' files as vanished, and the next run rereads them from the start (data is not duplicated, but that is ~1 GB and a couple of minutes; happened on 2026-10-03).
- An external Postgres comes from the root `.env`: `TALLY_DB_HOST`, `TALLY_DB_PORT`, `TALLY_DB_NAME`, `TALLY_WRITER_PASSWORD` (the `tally_writer` role, `TALLY_WRITER_USER` to change the name); without them — the embedded database. The config without secrets is `tally/tally.config.json` (`TALLY_CONFIG` — another path).
- Even Keel's launch log is `state/launches.jsonl` (`EVEN_KEEL_STATE_DIR`), the account folders are Even Keel's `AccountHomes` (`CLAUDE_CONFIG_DIR`, `EVEN_KEEL_ACCOUNTS_DIR`). From a worktree: `EVEN_KEEL_STATE_DIR=<main checkout>/state EVEN_KEEL_CONFIG=<main checkout>/even-keel.config.json node --env-file=<main checkout>/.env --import tsx tally/src/main.ts`. Without `EVEN_KEEL_CONFIG` the collector finds no projects (a worktree has no `even-keel.config.json`), and the run snapshots no project rule files; before BTN-150 that recorded them as deleted and the next run as created again (2026-10-03, 2026-10-12).
- There is no Windows scheduler task any more (before BTN-70 it was "Tally collector", `tally/scheduler/`). A leftover one is removed as administrator: `Unregister-ScheduledTask -TaskName 'Tally collector' -Confirm:$false`; until it is removed, a second collector on an external Postgres is cut off by `pg_try_advisory_lock`.
- The collector never runs `claude -p /usage`: it takes the limits from Even Keel (see below), and an extra poll gives a 429 on the shared token.

## What is read

- All `*.jsonl` in `<account folder>/projects/<project>/` and the subagent transcripts `<project>/<session>/subagents/agent-*.jsonl` (their `sessionId` is the parent session, `agentId` is their own; the subagents' cost is included in the task). Everything else in session folders (`tool-results/`, `memory/`) is not read.
- Incremental loading (`src/load.ts`): per file in `files` — how far it has been read (`read_to`, the byte after the last `\n`), the size, `mtime`, `ino` and the SHA-1 of the first ≤1 KB. An unchanged file is not opened. A grown one has its tail read in 8 MB chunks (a line longer than a chunk makes the chunk grow), each chunk in one transaction together with the new `read_to`, so a failed run continues from the same place. An unfinished last line waits for the next run. A file that became smaller than `read_to`, changed `ino` or its beginning is read again from zero; a renamed one is a new path and is read entirely. There are no duplicates: the keys are the row's `uuid`, the response's `message.id`, `tool_use_id`. Paths gone from `files` are deleted.

## Schema version and migrations (BTN-133)

- The database records its version in `schema_version` (one row). `src/migrations.ts` holds the numbered steps: `STEPS[n]` takes version n to n + 1 in one transaction together with the new version. Step 0 is `src/schema.sql` — version 1; a database from before versions has no `schema_version`, gets `schema.sql` again (it is idempotent) and becomes version 1.
- **A schema change is a new step** at the end of `STEPS` and `TALLY_SCHEMA_VERSION` + 1 in the root's `src/stats/tally-schema.ts` (the page reads it too; a test checks they are equal). Never edit `schema.sql` or a merged step, never remove one: a released database has already run them. A view changed by a step is redefined in full inside the step.
- Migrations run where the schema used to be created: the owner of the embedded database at open (`openLocalTally`) and every collector run after the lock (`TallyDb.migrate`).
- The database is newer than the code (the service was rolled back after an update): the collector writes nothing, logs one line and exits with `HALTED`, and the service stops collecting until a restart; `/stats` answers `newer` with both versions. The embedded database still opens.
- An external Postgres: a step needs the owner of every table, view and sequence and `CREATE` on `public` — `tally_writer` has them by `tally/deploy` (it owns the database and the schema and creates the tables). When it lacks them, the collector changes nothing and logs, per owner role, the `alter … owner to` / `grant create` statements to run, then halts until a restart.
- A manual run from a worktree with a new step migrates the database it points to. On the live database the service, still on older code, then halts until `main` gets the step and the service restarts: try a new step on the embedded database (a temporary `EVEN_KEEL_STATE_DIR`) first.
- The service starts each collector run as a worker from the sources on disk (`tally/src/*.ts`), so a merge into `main` reaches the collector at its next run, before the service restarts: a new step migrates the live database, and the page, still on the old code, answers `newer` until the restart. The same way the collector met a config of the old form on 2026-10-14 (BTN-150).
- The steps: 1 — `schema.sql`; 2 — `migrations/2-false-rule-deletions.sql` removes the deletions of runs that lost every live project rule file at once, with their snapshot changes (BTN-150).

## Schema (`src/schema.sql` — version 1; later changes are steps in `src/migrations.ts`)

- `lines` — rows with a `uuid`: session, agent, type, time and the compressed raw row `raw jsonb`. Service rows without a `uuid` (`ai-title`, `custom-title`, `queue-operation`, `file-history-*` …) are not stored; only session titles are taken from them.
- `messages` — one API response (`message.id`): the CLI writes a response as several `assistant` rows, one block per row with a repeated `usage`, and the final `output_tokens` is in the last; when merging, the larger value is taken for each kind of token and the earlier time. Columns: session, agent, account (the file's account folder), project and its folder (`cwd` without the `.claude/worktrees/…` tail), task, branch, `entrypoint`, model, `speed`, tokens `input`, `cache_write_5m`, `cache_write_1h`, `cache_read`, `output`, `effort` (the row's top-level `effort`: `low` … `max`, the level the request went with; `perTurnEffort` is `null` in about a fifth of rows and is not taken). Messages loaded before `effort` was parsed got it once from their `lines` (`MESSAGE_EFFORTS` in `src/db.ts`, the mark `efforts` in `tally_meta`); transcripts older than the CLI's recording of it have none. A cache write without a `cache_creation` breakdown counts as 5-minute. `<synthetic>` and `isApiErrorMessage` responses are not API responses and do not go into `messages`.
- `tool_calls` — a call (`tool_use`: name, the SHA-1 of the input for finding repeats, a short description as in Even Keel's feed) and its result (`tool_result`: time, `is_error`, error kind, the first 500 characters of the text). Kind: `denied` — a permission refusal (the user or the auto-mode classifier), `hook` — `PreToolUse:…`/`PostToolUse:… hook error`, `error` — everything else. The call and the result write different columns of one row, so the load order does not matter.
- `sessions` — account, project, the titles `custom_title` (set by the user) and `ai_title`, the task and reason from Even Keel's launch log, the first and last row, `project_dir` — the folder of the first response (each run fills in the empty ones, `SESSION_FOLDERS` in `src/db.ts`), `prompt` — the first human prompt of the main thread, up to 2000 characters, without slash commands and IDE context blocks (`src/prompt.ts`; filled from `lines` for the empty ones, `''` when a session has none a day after its last row).
- `handoffs` — what each handoff gave the new session (`session_id`): `previous`, task, reason, the whole prompt, the note's path and text. Even Keel saves a snapshot `<state>/handoffs/<session>.json` at every handoff (`src/chain/snapshots.ts`), and each run loads the new ones (`source = 'even-keel'`). Handoffs of the launch log without a snapshot are rebuilt from transcripts while those last (the CLI deletes them after 30 days): the prompt from the new session's first prompt, the note from the old session's last `Write` of the note's path and the `Edit`s after it (`source = 'transcript'`, `src/handoffs.ts`; a note that was only edited stays empty). A snapshot replaces a rebuilt row. The view `handoff_notes` adds the sizes and the note's Markdown headings.
- `limit_snapshots` — snapshots of the `5h`/`7d` windows per account: percentage, reset, source, snapshot time.
- `model_prices` — prices from `tally.config.json`, rewritten on every run; `long_*` — the long prompt rates (`longPrompt`), empty for a model without them.
- `files` — the incremental loading state.
- `signs`, `spans`, `sign_sessions` — signs, spans and with which rules and up to which row a session was computed; `span_reasons` — a span's reason from the classifier; `tasks` — tasks from Huly (below).
- `turns`, `turn_sessions` — turns of the main session and with which key and up to which row a session was computed (the "Task time" section).
- `step_runs`, `step_sessions` — runs of long commands and with which key a session was computed; the views `step_runs_x`, `step_weeks`, `step_growth` (the "Steps" section).
- Views: `session_tasks` — a session's task (`launch_task`, otherwise the task of the first response that has a task); `stuck_spans` — spans with a task and a reason; `task_repeats` — per task: sessions, handoffs by kind (`relay`, `checkpoint`, `restart`), spans, title, status, labels, `rework` (the label `Переделка` is present), related tasks; for the audit skill (below) — `audit_sessions` (a session: folder, task, launch reason, active minutes, request context and its peak, the share > 150k, cost, stuck spans and call errors), `audit_tasks` (the same sums per task, the task counted in the period of its first response) and `audit_rules` (rule changes with a place and `undone` — a false pair of changes within a day); task times — `session_times` (per session: turns, active time, waiting), `task_times` (per task: sessions, turns, active, waiting, total) and `task_estimates` (`audit_tasks` + time, estimate, `fact_ratio` — actual / estimate, priority, component, `done`, the recorded report, `model_family` — the most frequent model family); `session_efforts` — a session's effort level (the most frequent of its main thread, `mixed` when it changed midway), joined to `audit_sessions` for comparing levels. The `audit_*` columns do not change: the audit skills' queries rely on them, and `create or replace view` does not allow a new column in the middle — new things go into a separate view.

A response's task: a session launch in Even Keel's log (`state/launches.jsonl`, except `postpone`/`skip` and the outcome of a fix of main, `landed`/`dropped`) → the branch `<key>-<number>/…` → the folder `.claude/worktrees/<key>-<number>`. The log is applied retroactively too (`sessions.launch_task`, which the view takes first). `messages.task` is the task of the response itself, while `message_costs.task` is the task of its session (`session_tasks`, BTN-79): the `/stats` page, `task_costs`, limit shares and the audit count a task the same way; the start of a manual session before its branch is not lost, and a session over two tasks goes entirely to the first. A manual session in a checkout left on a task branch often works on another task: when its custom title, generated title or `prompt` names tasks of the branch's project but not the branch's own, `session_tasks` takes the first one named, in that order (CBL-157 had 23 sessions of ten other tasks, $406, on its branch).

## Compressing raw rows

Measured on 2026-10-03: 753 files, 280 thousand rows, 1166 MB. Of that, `toolUseResult` is 321 MB (a copy of the `tool_result` block), `tool_result` blocks 274 MB, attachments 196 MB, thinking signatures 70 MB (the thinking text is empty), images 40 MB. Chosen (`src/compact.ts`):

- top-level `toolUseResult`, `wireToolInputs` and `rendered` are dropped — they are copies of what is already in `message`;
- an image's `signature` and `data` (`source.type = base64`) are replaced by the length;
- any string longer than 2000 characters — the first 2000 and `…[+N]`;
- `\u0000` and lone surrogates are removed — `jsonb` does not accept them.

After the first load (754 files, 281 thousand rows, 56 s; a repeat run reads only the tails, fractions of a second) the database is 405 MB: `lines` 354 MB, `tool_calls` 28 MB, `messages` 15 MB. That load dropped only `toolUseResult`; `wireToolInputs` and `rendered` take 40 MB in it, and without them the database is about 365 MB. Inside `lines.raw` the heaviest are attachments (88 MB, of which `prompt_snapshot` is 52 MB) and `message.usage` (48 MB, kept: tokens are recomputed from it if the parsing changes).

## Cost

`message_costs` is `messages` × the model's price by the longest matching prefix (`claude-opus-5-5` before `claude-opus-5`; the prefix is chosen once per model rather than per response — on PGlite that makes `period` twice as fast), per million tokens: input, output, cache read, cache write for 5 min and for 1 h, each at its own price. Prices live in the view, not in rows: editing `tally.config.json` recomputes the history too. A model without a price has an empty `cost`, and the run logs it. The prices are Anthropic API prices as of 2026-09-25 (5 min write = 1.25× input, 1 h = 2×). Fast mode (`speed = fast`, more expensive for Opus) has not been met in the data: `speed` is stored, the price does not account for it. A price may have `longPrompt` — a threshold `over` and its own five rates: a response whose prompt (input + cache read + both cache writes) is over the threshold pays them on all of its tokens, output included (Haiku 5.5: over 100k tokens, 5×; `src/price-views.test.ts`).

`task_costs` — per task: responses, sessions, tokens, cost, limit shares.

Reconciliation on 2026-10-03: an independent count from the transcripts (by `message.id` — the maximum of tokens, 5 min / 1 h from `usage.cache_creation`, prices from `tally.config.json`) matched `task_costs.cost` to the last digit for BTN-45 (one session, $2.52) and BTN-37 (a session and a subagent, two models, $1.20).

## Limit share

Limits come from Even Keel: `GET <evenKeelUrl>/api/state` (`EVEN_KEEL_URL` over the config), `account.accounts[].limits` — it has both the statusline and the `/usage` poll, for each account. If Even Keel does not answer — `state/rate-limits.json` (statusline only, the account by `configDir`). A snapshot with the same time is not duplicated.

`limit_steps`: snapshots with a window number (`wnd`, a new one when the reset moved by more than 30 min from the previous snapshot: the sources round the reset differently) and the maximum percentage in the window before the snapshot (`prev_max`). `limit_intervals`: neighbouring snapshots of one account's window give an interval and an increase — `max(0, current − prev_max)`, not from the previous snapshot: `statusline` and `/usage` round the percentage differently and alternate in one series (21 → 22 → 21 → 22), and an increase from the previous snapshot would count every zigzag anew (BTN-51). When the window changed, the increase equals the current percentage, and the interval starts no earlier than the start of the new window (`reset − 5 h` / `− 7 days`). The first snapshot of a window gives no interval. `limit_windows`: a window per account — reset, start, peak (the highest percentage), the first and last snapshot; the "In weekly limits" tile takes it (window peaks). Snapshots exist since 2026-10-03 15:45: before that Even Keel stored only the latest value, and the transcripts have no limit percentages — the share before then cannot be recovered. `limit_shares`: an interval's increase is divided among this account's responses in the interval in proportion to their cost at API prices. It is an estimate: the percentage is an integer, snapshots come every few minutes, and the desktop app mixes its own sign-in into the `global` account.

## Signs (`src/signs.ts`)

Where a session was marking time — without an LLM, from the rows in `lines`. A stream is the main session and each subagent separately (`src/stream.ts`). Kinds:

- `failures` — `failureRun` (3) failed calls in a row; `denied` — `deniedRun` (1) permission refusals in a row;
- `repeat` — one command (`Bash` and others — by the command text without extra spaces) `repeatRun` (2) times without an edit between them (`Edit`, `Write`, `MultiEdit`, `NotebookEdit` reset the count);
- `reread` — one file read with `Read` `rereadCount` (5) times in a stream (the path case-insensitive and with `/`);
- `no_commit` — `noCommitReplies` (150) responses of the main session in a row without a successful `git commit`;
- `rewind` — several user prompts under one parent (`/rewind` or editing a message);
- `compact` — context compaction, `handoff` — the session was started by a handoff (`relay`/`checkpoint`/`restart` from Even Keel's log). These two are marks: they give no spans themselves, only get appended to the span they fall into.

Signs of one stream that overlap in time are merged into a span (`spans`, the id is the SHA-1 of the session, the agent and the edge `uuid`s). A session is recomputed when it has a new last row or the key changed — the SHA-1 of the signs version (`SIGNS_VERSION`), the rules and the launch reason.

The rules are `signs` in `tally.config.json` over the defaults, integers ≥ 1. Calibration on 2026-10-03 over all sessions: without a commit p95 is 102 responses, the threshold 150; files reread ≥ 5 times — 18; series of ≥ 3 failures — 16; refusals — 40; repeats ≥ 2 — 15; there was no `/rewind` in the data.

## Tasks from Huly (`src/huly.ts`)

Its own small client (Even Keel's `HulyTask` without relations, its model is not touched): by the task identifiers from `session_tasks` — title, status, labels (no duplicates, case-insensitive) and `relations`, made symmetric; related tasks outside the selection are fetched by id with a second query. A task is requested if it is not in `tasks` or its record is older than an hour; one not found in Huly is written with an empty title so as not to be requested on every run. If Huly is unavailable — a line in the log, the run goes on. The api-client noise "no document found, failed to apply model transaction" on connecting is filtered out.

More fields (BTN-55): `priority` (`urgent`, `high`, `medium`, `low`, `no-priority`), `estimate_h` (the `estimation` in hours; 0 — no estimate), `component` (the name), `done` (a status of the `Won` category). Records taken before these fields (`title` is present, `priority` is empty) are requested again without waiting for the hour.

Huly learns a task only after its first session: a task without sessions does not get into `task_repeats`.

## Task time (BTN-55, `src/turns.ts`)

Active time is by transcript turns, not by a launch timer: this way every session has it (chain, manual, VS Code) and retroactively. Turns are counted over the main session and recomputed, like signs, when a session has a new last row or the key changed (`TURNS_VERSION` and whether there is a launch in Even Keel's log).

- A turn runs from the row that began it to the last response before the next such row. A beginning: a prompt (`launch` — the first prompt of a session started by Even Keel; `resume` — the continuation prompt after a limit; `prompt` — the rest), `notification` — a background task notification and a self-scheduled wake-up (`scheduled_task_fire`), `message` — a message from another session or a background subagent's report. Service rows (`<local-command-…>`, `<system-reminder>`, `[Request interrupted`) and the context compaction summary do not begin a turn. A turn that hit a limit (`limited`) — a `rate_limit` error or `usageLimitNote`. Subagent responses extend the parent's turn and are not added separately. A long tool inside a turn (a build, tests) is work.
- `AskUserQuestion` and `ExitPlanMode` inside a turn — from the call to the result — are waiting, not work (`ask_s`).
- Waiting for a tool permission is not visible in the transcript rows. It is visible only through `system/turn_duration` (`cli_s`, present only for `entrypoint: cli`, i.e. Even Keel sessions): the CLI counts neither questions nor permission requests into a turn. A turn's active time is the smaller of the turn by rows (without `ask_s`) and `turn_duration`, and the difference goes into waiting. VS Code and the desktop app have no `turn_duration` — there the permission wait stays in active time, which is overstated by exactly that.
- Waiting is questions and permissions inside turns plus the gap from the end of a turn to the user's next prompt (`prompt`). The gap after a turn cut off by a limit does not go into waiting; chain pauses and handoff gaps do not either: the next session begins with `launch`, the continuation after a limit with `resume`, not a prompt.
- Per task (`task_times`) — the sums of its sessions (handoffs, checkpoints, "New session"); the total time is from the start of the first turn to the end of the last (there is no Done date in Huly).
- Reconciliation on 2026-10-04: sums per session against `turn_duration` — 140 of 176 cli sessions within 5%; the rest are the CLI's double counting on background subagent reports (its turn starts anew from the original prompt), so `turn_duration` is not taken whole but only bounds the turn. BTN-50: 9 sessions, each matched the CLI to 0.1 min, 64.7 min active of 66.3.

The time report in Huly (`reportTimes` in `src/huly.ts`): a `TimeSpendReport` per task via `addCollection`, `employee: null`, the value being the active hours, with the description-label "Tally: активное время агента по ходам транскриптов". It is written only for tasks in Done whose first turn is no earlier than `reportsSince` in `tally.config.json` (`null` — reports off; 2026-10-03 — estimates are set from this day), with active time of a minute or more and a last turn older than 60 min. What was written goes into `tasks.reported_h`/`reported_at`; if a report with the same label is already in Huly, a second one is not written. A written report is not updated if the task is continued afterwards.

## Steps (BTN-56, `src/step-runs.ts`, `refreshSteps` in `src/steps.ts`)

How long the agent's long commands take — a Unity check, tests, a build, a merge — and whether they have become slower. A run is a `Bash`/`PowerShell` call of the main session or a subagent; they are recomputed, like signs, when a session has a new last row or the key changed (`STEPS_VERSION` and the rules).

- The end of a run: for an ordinary call — the result. For a background one (`run_in_background`, gone to the background) — a `<task-notification>` by `tool-use-id` or the task ID (the outcome by its status), otherwise `TaskStop`/`KillShell` (`killed`), otherwise the last poll, otherwise it stays open (`end_by` `open`, the time up to the call's result). A detached one (`&` at the end, `Start-Process` without `-Wait`, `Start-Job`, `nohup`) — likewise by polls. A poll is `TaskOutput`/`BashOutput` by ID, `Read` of the output file or of a log from the command, a command with its name, a bare `sleep`/`Start-Sleep` while a run is open; polls are the run's `polls` counter, not separate runs. The outcome: `fail`, `timeout` (`timed out`, `no exit after`), `killed` (interrupted, stopped).
- A step is the first rule that at least one segment of the command matches (split by `\n`, `;`, `&&`, `||`, `|`): the project's own rules, then the common ones. By default (`DEFAULT_STEPS`) — `unity-check`, `unity-batch`, `vitest`, `dotnet-test`, `build`, `git-merge`; projects have no rules of their own. `steps` in `tally.config.json` — `rules`, `projects.<project>` (over the defaults, `null` removes a rule), `slowSeconds` (60, the threshold of "> 60 s"), `growth` (`ratio` 1.5, `minRuns` 5, `minSeconds` 10). Without a rule — `signature`: the program and the first word (`npm run x` — two), without assignments and `cd`; that is how Even Keel shows commands without a rule.
- A cold run is the first of its step in a place (`place`: a worktree, or a folder and a branch): a new worktree or a slot switched to another branch.
- The tables `step_runs` (a run: step, signature, command up to 300 characters, start, end, mode, how it ended, outcome, place, polls) and `step_sessions`; the views `step_runs_x` (+ `cold`, task, project), `step_weeks` (per project, step and UTC week: count, p50, p90, max, cold, failed) and `step_growth` (a week against the previous one with runs: `grew_p50`/`grew_p90`, the thresholds from `tally_meta` `steps`, where every run writes them).
- Reconciliation on 2026-10-04 (30 days): `dotnet-test` 1413 runs, p50 8 s, p90 34 s; `unity-check` 277, p50 42 s, p90 163 s, cold p50 129 s against 34 s warm, 81 failed or timed out. Two background `unity-check` runs were checked against the transcripts by hand (1265 s and 178 s) and matched. Of the commands without a rule, the longest in total is `python <<EOF` (779 runs, 61 min).

## Classifier (`src/classify.ts`, `src/steps.ts`)

A span's reason comes from Gemini on the free tier through your own LiteLLM proxy: `POST <TALLY_LLM_URL>/chat/completions` with the key `TALLY_LLM_KEY` (the LiteLLM master key), `temperature: 0`, `response_format: json_object`. The model is `TALLY_LLM_MODEL`, by default `google-gemini-3.1-flash-lite`; on a refusal LiteLLM itself goes down its `router_settings.fallbacks` chain (`google-gemini-3.5-flash-lite`, `google-gemma-4-26b-a4b-it`), and the one that answered is written to `span_reasons.model` and to the spend. The free tier quota is per model, so Tally's chain does not start with models that other projects spend on the same key (`google-gemini-3.6-flash` and below). No URL or key — the classifier is skipped with a line in the log. The prompt has the task, the span's signs and an excerpt: the span's events and the last prompt before it; for more than 120 events — the first 40, "… N events skipped …", the last 80. The answer is awaited for up to 3 min. The reasons: `unclear_task`, `broken_tooling`, `debug_loop`, `waiting_user`, `limit_env`, `normal`, `other`; the explanation is in Russian.

The model was chosen by a measurement on 2026-10-03: 29 spans already analysed by Haiku (`prompt_version` 1), redone through `3.1-flash-lite`: 21 matched, of the 8 disagreements lite was more accurate in 3, Haiku in 2, the rest debatable; the answer took 4–14 s. `gemini-3.7/3.8-flash` (20 requests a day), where they managed to answer, matched lite, but used up the daily quota in about ten spans: LiteLLM's retries on 429 spend it too. `gemma-4-26b` often answers 500.

- Taken are the spans of sessions silent for `classify.idleMinutes` (60) and active no earlier than `classify.sinceDays` (14) days ago, newest first, no more than `classify.perRun` (10) per run; `perRun: 0` turns it off.
- A span with a reason is not classified again; `prompt_version` (`PROMPT_VERSION`) is stored with the reason.
- LiteLLM answered with an error (the whole chain refused) — a line in the log, the classifier stands still until the next run. If the answer is not parsed — the reason is `other` with the answer text in the explanation.
- The spend is a row in `messages` (`message_id` `tally-classify:<response id>:<model>`, account `litellm`, project and folder — the Even Keel repository, `entrypoint` `tally-classify`), in the same transaction as the reason. The prices of `google-gemini`/`google-gemma` in `tally.config.json` are 0: free tier, tokens visible, money not.
- Until 2026-10-03 (`prompt_version` 1), Haiku classified through `claude -p` on the subscription: ~19 s and ~$0.01 of API equivalent per span, from the limit windows of Even Keel's active account.

## Rule versions (BTN-50)

Which rule texts (CLAUDE.md, skills, memory, hooks, settings, agents) were in effect when — so that `/stats` can compare spend before and after a change. A rule file is `ruleFileOf` (`src/rules.ts`): `~/.claude` and the account folders are reduced to one key `~/.claude/…` (except `settings.json` and `.claude.json` — each account has its own), a worktree to the main checkout, a project folder without the drive letter and case (a project may move to another drive). `~/.githooks/**` are hooks (without logs, `*.bak*`, `*.tmp`, `package*.json`), of `.claude.json` only `mcpServers` and `projects.*.{mcpServers, allowedTools}` are stored, with `env`/`headers` values as `***`. The skills `skills/synced/**` and `skills/.*/**` are not rules; a skill folder `skills/<name>` itself is not a file (`rm -r`/`cp -r` of a folder is not written as an edit, BTN-52). The text is `canon` (CRLF → LF, whitespace at the edges trimmed), SKILL.md without frontmatter, the hash is SHA-1.

- Tables: `rule_texts` (text by hash), `rule_files` (key, kind, folder), `rule_seen` (what a session received: `instructions`, `nested_memory`, the body of an invoked skill, a skill's description from `skill_listing`), `rule_snapshots` + `rule_snapshot_files` (disk snapshots), `rule_versions` (versions from `file-history`, backups and git), `rule_edits` (edits by `Edit`/`MultiEdit`/`Write`/`NotebookEdit` and writes to a rule file from `Bash`/`PowerShell` — `added` 0, `removed` empty), `rule_changes` (text changes: source `snapshot`, `transcript`, `file-history`, `backup`, `git`, +/−), `rule_imports` (the edit log, below), `tally_meta`.
- A snapshot is every run (`snapshotRules`): `~/.claude`, the account folders, `~/.claude.json`, `~/.githooks`, and per project of `even-keel.config.json` — `git ls-files` of the rules and `.claude/settings.local.json`; only files with a changed size or `mtime` are hashed. A file is recorded as deleted only where the run looked (`goneKeys`, BTN-150): a global file always, a project's only when git listed its repository this run; a project that dropped out (the config unread or empty, git failed) is left as it was. The first run is the initial state, without events; a file that first got into a snapshot with an old `mtime` is too.
- History before snapshots (`collectRuleHistory`): the transcripts' `file-history-snapshot` (copies in `<account folder>/file-history/<session>/`), the backups `~/.claude/backups/` (`CLAUDE.md.*.bak`, `.claude.json.backup.<ms>`), `git log --first-parent main` of each project's rules (read onward from `rules_git:<repo>` in `tally_meta`).
- The time rule: per version key, versions from transcripts and history go by first appearance, the first is the initial one, each next is a change; only versions earlier than the key's first snapshot count. This way the sources give no false changes against each other.
- When `RULES_VERSION` (`src/rule-steps.ts`) changes, a run rereads all transcripts from zero only for the rules (~10 s) and recomputes the changes.
- The edit log is `ruleHistory` in `tally.config.json` (by default `<EVEN_KEEL_STATE_DIR>/rule-history.jsonl`, outside git): a row is a set `{ id, at, until?, atPrecision exact|hour|day, sessions, files [{ path, action, summary }], purpose, reason, task, source }`. Each run adds new rows and deletes vanished ones (the key is the row's SHA-1), a broken row goes to the log. The server attaches the goal, reason and task to a session's edit set from `sessions` if the time agrees within a tolerance (30 min / 1 h / 24 h by precision), otherwise the log's set stands alone, marked as diverging.
- The log is filled by the sessions themselves, prompted by the hook `tally/bin/rule-hook.mjs` (BTN-151; logic in `src/rule-hook.ts`), wired in `~/.claude/settings.json` by the absolute path to the main checkout: `PostToolUse` with the matcher `Edit|MultiEdit|Write` and `Stop`, both `node "<main checkout>/tally/bin/rule-hook.mjs"`. An edit of a rule file (`ruleFileOf`, memory excluded) adds a reminder to the context, once per file per session: the file, the log's path, the row format, the session id, the allowed `purpose`. A stop of a session that changed rule files and has no row with its id (a prefix, as the server matches) is blocked once, with the same reminder and the session's rows that do not parse; the next stop passes, a later one is blocked again only for rule files edited since. What a session was reminded of is `<state>/rule-hook/<session>.json`, swept after a month. An edit of another file ends before TypeScript loads (`tsx` from the main checkout's `node_modules`); any error ends the hook silently.
- Since when history exists: the texts of CLAUDE.md and memory in transcripts — since 2026-09-04 (CLI 2.1.260, the first change 2026-09-06), skill descriptions and bodies — since 2026-08-03, hooks, settings and `.claude.json` — since the first snapshot (2026-10-03) and earlier only from backups, `file-history` and git.

## Session audit (BTN-53)

The audit is the global skill `session-audit` (`~/.claude/skills/session-audit/SKILL.md`, outside git): from any project it compares a recent period with an earlier one — spend, context, tasks, stuck spans, rule changes between them — and looks for what changed. The weekly audit is a special case: the period is the last 7 days, the earlier one the 7 days before them.

- Queries go through `tally/bin/sql.mjs` from any folder (`node <main checkout>/tally/bin/sql.mjs "<sql>"`, `-f file` or stdin): it takes `pg` and `.env` from the main checkout. An external Postgres — the `tally_reader` role (`TALLY_READER_PASSWORD`, `TALLY_READER_USER` to change the name); the embedded database — the port from `<EVEN_KEEL_STATE_DIR or the main checkout's state>/tally/owner.json`, which answers only while the service runs (otherwise the error "served by the Even Keel service, and it is not running"). The environment variables `TALLY_*` and `EVEN_KEEL_STATE_DIR` outrank `.env`: an empty `TALLY_DB_HOST=` reads the embedded database even if `.env` points at the server. In both cases the transaction is read-only — `insert` and the like are rejected by the database. The collector is not run for an audit.
- The ready sums are the `audit_*` views (the "Schema" section), the queries and the shape of the report are in the skill.
- Prices are an API estimate, not a subscription bill; tasks in `tasks` are refreshed once an hour, so the status may lag.

## Tests

Pure logic — vitest next to the code (`*.test.ts`): row parsing, compression, the task by branch and worktree, incremental tail loading (on a temporary file and an in-memory store), limit snapshots, config, signs and spans on synthetic transcripts, the classifier's excerpt and answer parsing, Huly tasks, turns (`src/turns.test.ts`: turn beginnings, a subagent inside a turn, questions, `turn_duration`, a limit), steps (`src/step-runs.test.ts`: rules, the command signature, the end of a background and a detached run, polls, the outcome).
